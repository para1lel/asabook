## 摘要

大语言模型（LLM）应用正从简单聊天机器人演进为动态、通用的智能体程序；这些程序通过扩展 LLM 调用次数和输出 token，帮助 AI 智能体进行推理、探索并解决复杂任务。然而，现有 LLM 服务系统忽略了程序与调用之间的依赖关系，错过了重要的优化机会。我们的分析表明，提交到 LLM 服务引擎的程序经历了很长的累积等待时间，主要原因是单个 LLM 请求和程序层面的队头阻塞。

为此，我们提出 Autellix，这是一个将程序视为一等公民、以最小化端到端延迟的 LLM 服务系统。Autellix 截获程序提交的 LLM 调用，为调度器补充程序级上下文。我们提出两个面向单线程和分布式程序的调度算法，根据程序此前完成的调用抢占并确定 LLM 调用优先级。评估表明，在多种 LLM 和智能体工作负载上，相比 vLLM 等最先进系统，Autellix 在相同延迟下将程序吞吐量提升 4–15 倍。

## 1 引言

作为自主智能体的大语言模型（LLM）通过扩展推理计算增强问题求解能力，也就是增加输出 token 或 LLM 调用次数 [Eva84, Kah11, Kah03, Kum24, Zou24, Mir24]。更多调用和 token 使 LLM 赋予智能体更强的推理 [Wei22a, Cao23, Dee25]、规划与搜索能力 [Wan24, Raf24]、基于先前经验的自我反思能力 [Yao23, Yu24, Fau24]，以及多智能体协作能力 [Mor23, Wan23, Sch24]。这些技术使智能体能够借助工具有效探索外部环境 [Sci23, Gon23, Cao23]，并自主浏览网页 [Nar23, Neu24, Fau24a]、解决 GitHub 问题 [Nar24, Pre24, Oth24]、证明困难的数学问题 [Dee24, Ana24] 等复杂任务。

推理时技术和智能体应用的兴起，标志着应用从静态、专用的 LLM 应用 [Con23, Qiu24] 转向高度动态、通用的*智能体程序* [She24, Wan23, Inc24]。更准确地说，智能体程序是由有向无环图（DAG）表示的动态执行工作流，包含一个或多个智能体的 LLM 调用，以及工具调用（即外部 API 调用）、通用代码执行或人类输入等外部中断（见[背景与相关工作](#section-02)）。我们假设程序的 LLM 调用模式仅在运行时出现，因此难以预先完整了解或预测整个图。

[图 1](#figure-01) 展示了单线程和多线程智能体程序的高度动态性。单线程程序在两个维度上变化：1）程序长度，取决于用户提示；2）由程序控制流决定的 LLM 调用和中断序列。例如，Chatbot 和 ReAct（Reasoning and Acting）[Cao23] 智能体都在 LLM 调用与中断（人类或工具调用）之间循环，并根据人类或 LLM 的决定终止。多线程程序通常形成 DAG。经典的多线程程序 Map-Reduce 和蒙特卡洛树搜索（MCTS）会随时间改变分叉与合并的线程数量，每条线程都可能包含不同的 LLM 调用和中断序列。特别地，MCTS 是推理和基于网页智能体中广泛使用的搜索与规划技术 [Wan24, Raf24, Cap24, Has25]。

现有 LLM 服务引擎（如 vLLM）[Sto23c] 通过提升键值（KV）缓存效率 [Sto23c, She24]、加速 CUDA 内核 [Kas24, Jin24] 以及改进 LLM 请求调度算法 [Jin24, Ram24]，专注于优化单个 LLM 调用或静态 LLM 应用 [Qiu24]。然而，这些优化没有考虑程序级上下文，例如同一程序中 LLM 调用之间的依赖关系或程序级统计量（如总执行时间）。因此，这些系统在复杂程序上往往端到端性能不佳，尤其是程序的端到端延迟（见[第 3 节](#section-03)）。

[图 2](#figure-02) 展示了两个长程序（A、B）和两个短程序（C、D）在 t=0 时提交到最大批大小为 2 的 LLM 服务引擎的突发情况。每个程序包含一个或多个解码长度不同的 LLM 调用。在与程序无关的先到先服务（FCFS）策略下，vLLM 的默认策略 [Sto23c] 会让长 LLM 调用阻塞其他调用，产生*调用级*队头（HoL）阻塞。程序 A、B 的初始长调用先执行，使程序 C、D 直到 t=3、4 才能执行。反复发生的 HoL 阻塞造成总计 **18** 个单位的等待时间。抢占式调度（如多级反馈队列 MLFQ）[Jin24] 通过抢占长调用来运行短调用，从而减少 HoL 阻塞。但没有程序级上下文时，新程序会不断被旧程序的后续调用延迟，形成*程序级* HoL 阻塞。MLFQ 虽然能抢占程序 A、B 的长调用并启动 C、D，却在 t=6–12 反复优先处理 A、B 的后续调用，延迟程序 D。因此，MLFQ 与 FCFS 一样产生 **18** 个单位的等待时间。

我们提出 Autellix，这是一个面向程序而非单个 LLM 调用的 LLM 推理系统。受操作系统进程调度器启发，我们的核心思想是依据程序此前完成调用的总执行时间确定 LLM 调用优先级；长程序不太可能很快完成，因此其调用被降低优先级，使短程序先完成。在[图 2](#figure-02) 中，短程序 C、D 不再被长程序 A、B 的后续调用阻塞，HoL 阻塞几乎消除，总等待时间降至 **12** 个单位。

Autellix 利用全局程序级统计量（如程序在引擎上的累积执行时间）来减少等待并提升引擎吞吐量。我们提出两个不依赖先验工作负载知识的非预知调度算法：面向单线程程序的 *PLAS*（Program-Level Attained Service），以及面向表示为通用动态 DAG 的多线程程序的 *ATLAS*（Adaptive Thread-Level Attained Service）。PLAS 根据源程序当前的累积服务时间（即执行时间）确定 LLM 调用优先级。作为 PLAS 的推广，ATLAS 根据同一程序所有线程中的最大累积服务时间确定优先级，按程序关键路径排序调用 [Zha20]。除减少等待时间外，ATLAS 还通过优先处理否则会阻塞程序进展的关键调用来缩短程序 makespan（见[Autellix 设计](#section-05)）。

由几十到数百次 LLM 调用组成的程序给服务系统带来巨大压力：单个 LLM 引擎对 MCTS 每秒只能处理约 0.2 个程序（见[第 6 节](#section-06)）。因此，Autellix 还将程序的 LLM 调用路由到多个引擎。对于智能体工作负载，我们观察到同一程序内的 LLM 调用通常共享前缀和累积对话状态，而不同程序的调用通常只共享系统提示 [Zha24a]。为避免重复计算程序的 KV 缓存，Autellix 通过将长调用路由到所属程序的引擎、将短调用负载均衡到其他引擎来保持数据局部性；短调用的输入大多由系统提示组成。

我们将 Autellix 原型实现为 vLLM 等 LLM 服务引擎之上的一层 [Sto23c]，并提供有状态 API，使用户能够建立持久会话，而不是使用传统的无状态 API [Ope24a]。我们在不同 LLM 和四种代表性智能体工作负载上评估 Autellix（见[第 6 节](#section-06)）。结果表明，相比 vLLM 等最先进推理系统，Autellix 的吞吐量提升 4–15 倍 [Sto23c]；在多个引擎之间，相比标准负载均衡器，吞吐量最高提升 1.5 倍。

本文的主要贡献如下：

- 首次将智能体程序形式化为由 LLM 调用和中断构成的动态、非确定性 DAG。
- Autellix 使用程序级统计量为调度器提供更充分的信息；其非预知调度器只需同一程序内 LLM 调用的累积服务时间。
- Autellix 在多个引擎之间采用简单的负载均衡策略，平衡数据局部性与 KV 缓存重算。
- 系统易于部署，可无缝集成有状态 API 与现有编程和智能体框架，并取得显著吞吐量收益。

## 2 背景与相关工作

为说明 Autellix 的相关背景，我们概述新兴的 AI 智能体基础设施及其应用，将其分为 LLM 服务层和更高层的智能体层，如[图 3](#figure-03) 所示。

### LLM 服务层

**LLM 推理过程。** 驱动聊天机器人和 AI 应用的大语言模型主要采用 Transformer 架构 [Pol23]，包括 GPT、Claude 和 LLaMA 等仅解码器模型 [Oth20, Oth23, Oth23a, Say23]。每个请求的 LLM 推理分为两个阶段：*预填充*阶段将输入提示转换为中间 token 状态；*解码*阶段基于已有 token 序列逐个自回归生成新 token。为减少计算，LLM 服务系统使用存储中间 token 状态的 *KV 缓存* 加速 token 生成 [Chu22, Sto23c]。

**LLM 服务。** LLM 服务系统同时管理跨引擎的 LLM 调用路由和单个引擎内的 LLM 调用执行（[图 3](#figure-03)）。引擎内的近期创新借鉴传统操作系统的内存管理、内核优化和调度思想 [Zha24, Lin24]。vLLM 等方案采用虚拟内存和分页技术减少 KV 缓存碎片 [Sto23c]，使用共享内存在 LLM 请求间缓存前缀 [Qiu24, She24]，并管理 GPU、CPU 与磁盘之间的缓存层次 [Kas24, Zha23, Sto24]。其他技术改进 GPU 内核以加速自注意力 [R22]、流水线化不同算子 [Kas24]，并实现更好的张量或流水线并行 [Jin24, Sto23d]。LLM 引擎还可以将预填充与解码进行装箱 [Ram24]、抢占 LLM 请求 [Jin24]，以改善响应时间。在多个 LLM 引擎之间，服务系统采用实时迁移 [Lin24a]、预填充与解码分离 [Xu24]、构造前缀树 [Zha24a] 和跨引擎迁移 KV 缓存 [Qiu24] 等负载均衡技术，以满足请求 SLO 并改善尾延迟。上述技术总体上优化的是*独立 LLM 请求*，相当于通用程序中的函数调用；Autellix 则关注程序级优化，尤其是调度，即类似传统操作系统在 CPU 核上管理整个进程。

![AI 智能体基础设施](./autellix/figure-03.png)

### 智能体层

**智能体程序。** 在 LLM 推理层之上，开发者构建复杂的*智能体程序*来协调智能体、工具和人类之间的交互（[图 3](#figure-03)）。本文关注的 LLM 智能体定义为由指定智能体角色的系统提示和 LLM 模型类别组成的元组 [+2]。类似传统操作系统的进程和中断，智能体程序要么通过 LLM 调用直接与 LLM 服务层交互，要么参与外部中断，即在 LLM 引擎之外花费的时间。智能体可以使用工具执行通用函数或外部 API，从而控制数据库、机器人系统或互联网等环境 [Sci23, Gon23, Nar23, Bai24, Sha22, Li24]。更重要的是，智能体编排框架 [Ope24, Con23, Inc24, Wan23]（如 LangChain 和 Autogen）为开发者提供管理程序控制流的原语，决定何时执行智能体、调用工具或请求人类输入。这些原语遵循条件语句、循环、错误处理和终止条件等通用编程语义 [She24, Inc24, Wan23, Kha23]。最后，程序在智能体、工具和人类之间维护输出的全局历史 [Qiu24, Inc24, Gon24, Cui24]。例如，基于 LLM 的聊天机器人会累积 LLM 智能体输出与人类输入之间的消息 [Ope23]。重要的是，Autellix 不修改程序层，而是在程序运行时动态构建程序执行图（DAG）的内部状态，并将其存储在进程表中（见[实现](#section-07)）。

**图 4. 稳态下服务引擎一小时内的 LLM 调用数。** 优化程序等待时间会增加稳态下的 LLM 调用量。

**智能体应用。** 除标准聊天机器人（[图 1](#figure-01)）外，智能体应用（即程序的实例化）还可自动化或辅助网页和用户界面导航（如 OpenAI Operator）[Has25, Neu24, Fau24a, Bai24]、解决 Github 问题 [Nar24, Pre24, Oth24]、解决 IMO 级问题 [Dee24, Ana24]、核查并总结多来源论断（[图 1](#figure-01)）[Gon24, Qiu24]，以及实现精确机器人控制 [Car24]。许多应用通过扩展推理时计算，即 LLM 调用数及相应的总解码 token 数，来提升复杂任务表现。这些测试时方法包括：分步推理以分解任务 [Wei22a, Lew23]，注入显式思维引导推理 [Cao23]，规划或搜索以探索可能解 [Nar23, Bes24, Wan24]，自我批评以评估行动 [Sto23e, Sto24b]，从失败中学习的自我反思 [Yao23, Fau24]，以及多智能体协作 [Wan23, Mor23a]。其中，单线程的 ReAct 智能体将思维链（CoT）技术与环境交互结合（[图 1](#figure-01)），最近已被叠加到 Deepseek 风格（或 o1 风格）LLM 之上，以实现自动推理和工具调用 [Dee25, Oth24, Li25]。多线程程序 MCTS [Wan24] 结合并行规划、自我批评、自我反思和多智能体协作（[图 1](#figure-01)）。此外，分布式程序还可使用 best-of-N 采样、束搜索、前瞻技术和遗传算法探索并发现最优解 [Fau24b, Kum24, Dav24, Che25]。鉴于 LLM 的概率性，推理时技术的广度表明智能体程序及其应用具有三种性质：（1）*动态*，同一程序在不同用户提示下可能产生完全不同的执行模式；（2）*非确定*，未来未知，例如程序何时决定终止；（3）*分布式*，许多程序使用并行调用。因此，Autellix 是非预知的，对程序工作负载或执行图没有任何先验知识。

## 3 动机

今天的 AI 智能体基础设施将 LLM 服务系统与智能体程序解耦（见[第 2 节](#section-02)）。随着组织从服务 LLM 查询转向更高层的 AI 应用，LLM 引擎必须优化程序级目标，如响应时间或端到端延迟 [Qiu24]。形式化地说，单线程程序的端到端延迟包含三个部分：（1）*等待时间*，程序 LLM 调用在引擎上的总排队时间；（2）*执行时间*，LLM 调用累计前馈时间；（3）*中断时间*，等待工具调用或人类输入等外部中断的时间。由于（3）与 LLM 服务无关，本节识别减少等待和执行时间的机会，并在 Autellix 的调度策略设计中处理它们（见[Autellix 设计](#section-05)）。

### 程序级等待时间

<span id="figure-06"></span>

![队头阻塞比例](./autellix/figure-06.png)

**图 6. LLM 调用和程序的等待时间与执行时间之比。** 当短 LLM 调用和程序等待时间显著长于执行时间时，就会发生队头阻塞。

[图 6](#figure-06) 表明，在从经典聊天机器人到 ReAct、MCTS 程序的多种智能体工作负载中，随着负载增加，程序大部分时间用于等待。因此 Autellix 优先减少等待时间，这既能改善程序延迟，也能提高 LLM 引擎吞吐量。更快完成调用会促使程序更快发出后续调用，提高 LLM 调用到达率。[图 4](#figure-04) 展示了在单个 A100-80GB GPU 上使用 LLaMA-3.1-8B [Oth24a] 和完整聊天对话 [Src23] 的一小时稳态轨迹。相比 vLLM 的 FCFS 策略，Autellix 持续处理多 10 个并发 LLM 调用，为提高吞吐量提供更多批处理机会。

**调用级阻塞。** 第一个挑战是 LLM 调用级*队头（HoL）阻塞*。解码较长的 LLM 调用会延迟较短调用，造成显著等待时间 [Jin24]。vLLM 等服务引擎 [Sto23c] 会等待正在执行的调用完成解码后才调度新调用，因此该问题十分明显。我们的评估工作负载具有解码步数的长尾分布，HoL 阻塞严重（见[图 11](#figure-11)）。

为测量阻塞，[图 6](#figure-06) 根据输出 token 数，测量 Chatbot 和 MCTS 工作负载中 LLM 请求等待时间与执行时间的比值。对 FCFS 而言，HoL 阻塞增加短 LLM 调用的等待时间，从而增大比值。抢占类似于操作系统调度器中断长时间运行进程的方式，通过偏向较短调用缓解 HoL 阻塞。[图 6](#figure-06) 显示，抢占式 MLFQ 对短解码产生更小的比值。但没有程序级统计量的抢占不能完全解决问题，下一节将解释原因。

**程序级阻塞。** 第二个挑战是*程序级 HoL 阻塞*，即包含许多 LLM 请求的长程序延迟短程序。现有 LLM 调度器与程序无关，只调度单个请求而不考虑其在整体程序中的位置，导致决策不佳。我们的评估显示，每个程序的 LLM 调用数呈长尾分布，从而增加程序级阻塞（见[第 6 节](#section-06)）。

为量化程序级阻塞，[图 6](#figure-06) 根据 LLM 调用数测量程序等待时间与执行时间之比。在两种工作负载中，当 LLM 调用数较少时，FCFS 与 MLFQ 的比值更高，说明短程序需要长时间等待。因此，MLFQ 等抢占式策略的性能可能接近甚至差于 FCFS（见[第 6 节](#section-06)）。没有程序级上下文时，MLFQ 盲目优先处理新的 LLM 请求；当长程序的新调用被优先处理时，短程序会饥饿。

### 程序级执行时间

<span id="figure-07"></span>

![前缀缓存命中率](./autellix/figure-07.png)

**图 7. 前缀缓存命中率随输入长度的变化。**

程序执行时间很大程度上取决于 LLM 引擎对预填充和解码阶段的管理效率。智能体工作负载通常具有很长的累积预填充，因此 Autellix 关注预填充性能优化。具体来说，前缀缓存可以消除大量预填充计算：它在 LLM 请求之间存储并复用相关键值（KV）缓存条目，如系统提示 [Qiu24, She24]。

**数据局部性。** [图 7](#figure-07) 展示输入长度与平均缓存命中率的关系。缓存命中率定义为传入 LLM 调用的预计算输入 token 中已存在于引擎 KV 缓存的百分比。在单个程序内，无论输入长度如何，缓存命中率都保持在 90% 以上，说明同一程序的 LLM 调用共享相同上下文。相比之下，不同程序之间的缓存命中率随输入长度指数衰减，说明程序之间仅共享系统提示。这些结果表明，跨多个引擎的 LLM 服务系统应考虑程序的*数据局部性*，因为未来请求可以复用其大量 KV 缓存。

## 4 Autellix 设计

我们先介绍 Autellix 的总体架构（[4.1 节](#section-04-01)），再讨论两个关键组件：（1）减少调用级和程序级阻塞的程序感知调度器（[4.2 节](#section-04-02)）；（2）数据局部性感知的负载均衡器（[4.3 节](#section-04-03)）。

<span id="section-04-01"></span>

### 4.1 概览

<span id="figure-08"></span>

![Autellix 系统架构](./autellix/figure-08.png)

**图 8. Autellix 的系统架构。** 用户在本地运行程序，发起有状态会话并向 Autellix 后端提交 LLM 调用。Autellix 使用全局进程表跟踪会话，为自定义负载均衡器和调度器提供信息。

Autellix 是面向智能体程序而非单个 LLM 请求的高层服务引擎。Autellix 的三个主要目标是：（1）改善用户看到的程序整体端到端延迟；（2）为提供方最大化 GPU 利用率；（3）通过第 95 和第 99 百分位延迟衡量并缓解程序饥饿，以提高公平性。

**假设。** Autellix 是非预知的，不了解程序到达、执行工作流结构或一般工作负载分布。程序到达时，其执行 DAG 最初未知；Autellix 在程序运行时动态构建内部表示（IR）。这种灵活性使 Autellix 能推广到任何在底层引擎上调用 LLM 的程序。以往工作 [Qiu24] 将静态 LLM 应用提交给引擎，而 Autellix 假设用户在本地运行通用 Python 程序，并调用 Autellix 后端（见[实现](#section-07)）。

**架构。** [图 8](#figure-08) 展示 Autellix 的总体架构。不同于假设 LLM 调用无状态的现有引擎，Autellix 是有状态的：程序从用户本地运行，与 Autellix 建立会话，并携带会话 ID 随时间发出 LLM 调用。底层实现见[第 5 节](#section-07)。会话开始时，Autellix 在全局进程表中加入对应条目（见[4.2 节](#section-04-02)）。该表跟踪程序元数据，包括总服务时间、线程级元数据以及程序 LLM 调用的等待时间。引擎级调度器（[4.2 节](#section-04-02)）和有状态负载均衡器（[4.3 节](#section-04-03)）都利用该表调度下一解码批次，并根据程序数据局部性将 LLM 调用路由到引擎。

### 4.2 程序感知调度器

**算法 1. Autellix 的程序感知调度器**

- **过程** `Update_Process_Table(Call c, Table pt)`
  - `pd = pt[c.pid]`
  - 注释：总服务时间（PLAS）、最大关键路径（ATLAS）。
  - `pd.service = max(pd.service, c.service + c.model_time)`
  - 注释：更新其他指标……
  - `...`
- **过程** `Scheduler(Queues Q_1, ..., Q_K, Table pt)`
  - **对于** `C_arrived` 中每个 `c`（到达的 LLM 调用）：
    - 注释：使用程序 ID 获取优先级。
    - `c.service = pt[c.pid].service`
    - 取满足 `Q_i^low <= c.service <= Q_i^hi` 的 `i`，设 `c.q_idx = i`。
    - 将 `c` 追加到 `Q_c.q_idx`，并设置 `c.quanta = Q_c.q_idx.quanta`。
  - **对于** `{Q_1, Q_2, ..., Q_K}` 中每个 `c`：
    - **如果** `c.finished()`：更新进程表，并从队列移除 `c`。
    - **如果** `c.quanta <= 0`：从当前队列移除 `c`，追加到下一级队列，增加 `c.q_idx` 并重置时间片。
    - 设置 `wait = pt[c.pid].wait + c.wait`、`service = pt[c.pid].service + c.model_time`。
    - **如果** `wait / service >= beta`（反饥饿）：从当前队列移除 `c`，追加到 `Q_1`，并将 `c.wait`、`c.model_time` 置零。
  - 设置 `B_out = []`（调度下一批 LLM 调用）。
  - **对于** `{Q_1, Q_2, ..., Q_K}` 中每个 `c`：
    - **如果** `engine.can_fit(c)`：将 `c` 追加到 `B_out`。
    - **否则**终止循环。

我们提出一个无需先验知识、旨在最小化程序响应时间（即端到端延迟）的通用高效调度器。为缓解程序和调用两级队头阻塞，Autellix 根据程序级统计量（如累积运行时间，见[4.2.1 节](#section-04-02-01)）给调用分配优先级，并动态抢占调用（见[4.2.2 节](#section-04-02-02)）。完整调度算法见[算法 1](#section-04-02)。

<span id="section-04-02-01"></span>

#### 4.2.1 程序级优先级

为了有效实现程序级优先级，Autellix 依赖全局进程表跟踪关键程序指标，从而为单线程和多线程程序提供更充分的调度信息。

**进程表。** 受传统操作系统启发，Autellix 维护记录所有运行中程序状态的全局进程表。新程序到达时加入条目，程序完成时移除条目。每个程序条目记录：

- *服务时间：* 单线程程序为 LLM 引擎模型执行器上所有已完成调用的累积执行时间；多线程程序为观测到的最长关键路径执行时间。
- *等待时间：* 在 LLM 引擎调度队列中花费的时间，用于反饥饿。
- *引擎 ID：* 程序当前运行的引擎，用于 Autellix 的负载均衡器。
- *线程元数据：* 每条线程对应一个活动 LLM 调用，因此记录程序活动调用及其到达、等待和服务时间。
- *最近调用到达：* 程序最近一次新 LLM 调用到达的时间，用于跟踪陈旧程序。
- *最近调用完成：* 最近一次 LLM 调用完成的时间，用于检测长外部中断。

程序的 LLM 调用完成时，表随之更新。借助进程表，调度器可以理解每个程序的全局状态并调度 LLM 调用。

**单线程程序。**

<span id="figure-09"></span>

![多线程程序的关键路径](./autellix/figure-09.png)

**图 9. 多线程程序的关键路径。** 左侧为穿过 DAG 的关键路径示例；右侧为 14 个单位的最佳 makespan 与 11 个单位的最差 makespan。

最短作业优先（SJF）和最短剩余处理时间（SRPT）等调度策略在单服务器和多服务器设置下可最优地最小化响应时间 [Har18, Akh15]。但它们需要精确知道程序运行时间，违背 Autellix 的非预知假设。相反，最少已获得服务（LAS）算法 [Wie08] 在数据中心网络 [Wan15, Cho15] 和深度学习集群 [Gu19] 等信息无关场景中广泛使用，是一种实用替代方案。

我们提出*程序级已获得服务*（PLAS），将 LAS 扩展到程序。对于单线程程序，其服务时间是此前已完成 LLM 调用的总运行时间。形式上，若具有程序 ID `c_j.id` 的第 j 个 LLM 调用 `c_j` 被提交，PLAS 根据同一 ID 的所有先前 LLM 调用运行时间 `t_k` 之和为其分配优先级 `p(c_j)`：

$$p(c_j) = \sum_{\substack{k < j \\ c_k.id = c_j.id}} t_k$$

这里，优先级值越大表示优先级越低。为降低计算量，调度器从进程表读取程序总服务时间。LLM 调用完成时，更新其程序的总服务时间。因此，PLAS 自然偏向总服务量较少的程序，帮助短程序更早完成并减少响应时间。

**多线程程序。** 与单线程程序不同，多线程程序被建模为 LLM 调用构成的动态 DAG。程序完成时间由 DAG 的*关键路径*决定，即从开始到结束的最长依赖调用序列，如[图 9](#figure-09) 所示。无论引擎能并行处理多少 LLM 调用，只有关键路径上的所有调用完成，程序才会终止。如果不考虑关键路径，程序完成时间会次优；在[图 9](#figure-09) 中，DAG makespan 从 11 增至 14 个单位。

为此，我们提出 *ATLAS*（Adaptive Thread-Level Attained Service），这是 PLAS 的实用推广，根据程序关键路径上的服务时间为调用排序。ATLAS 为新到达的 `c_j` 分配优先级 `p(c_j)`，依据同一程序中父调用集合 `P(c_j)` 的优先级和已完成服务时间：

$$p(c_j) = \begin{cases} 0 & \mathrm{if}\ c_j\ \mathrm{is\ root} \\
\max_{c_k \in \mathcal{P}(c_j)} \{p(c_k) + t_k\} & \mathrm{otherwise} \end{cases}$$

其中 `t_k` 是父调用 `c_k` 的执行时间。递归组合父调用优先级和运行时间后，`p(c_j)` 估计通往 `c_j` 的最长累积服务链，提供非预知的关键路径估计。

同时偏向短程序并优先最长关键路径线程并不容易。ATLAS 在进程表中为每个程序维护一个标量：观测到的最长关键路径。程序中的每个活动 LLM 调用继承该值作为初始优先级；调用完成时，仅当自身关键路径更长才更新该标量。该简单机制无需跟踪调用依赖，就能持续细化程序关键路径估计。因此，ATLAS 偏向关键路径较短的程序和调用，有效近似动态 DAG 的 LAS 策略。由于同一程序的所有调用都从同一条目导出优先级，调度器会自然地聚合同一程序的并行调用，避免落后线程延迟程序完成。

<span id="section-04-02-02"></span>

#### 4.2.2 抢占式调度

<span id="figure-10"></span>

![基于离散优先级的 LLM 调用生命周期](./autellix/figure-10.png)

**图 10. 基于离散优先级的 LLM 调用生命周期。**

Autellix 根据程序历史为每个 LLM 调用分配优先级。然而，按连续优先级调度和抢占程序可能退化为最坏情形的轮询 [Cho15]，其性能差于 FCFS，并引入不必要的上下文切换，包括 CPU 与 GPU 间频繁的 KV 缓存交换 [Jin24]。为避免这一点，Autellix 将优先级离散到有限队列，类似操作系统中的多级反馈队列 [Cho15, Gu19, Arp18]。

**基于多级程序的调度。** Autellix 将 LLM 调用优先级分箱并离散到 K 个队列（`Q_1, Q_2, ..., Q_K`），优先级从 `Q_1` 到 `Q_K` 递减。每个队列 `Q_i` 覆盖范围 `[Q_i^lo, Q_i^hi)`，其中 `Q_1^lo = 0`、`Q_K^hi = infinity`、`Q_(i+1)^lo = Q_i^hi`。

如[图 10](#figure-10) 所示，LLM 调用到达时，Autellix 根据进程表查找程序优先级 `p(c)`。传统 MLFQ 中所有新调用都从最高优先级队列 `Q_1` 开始；Autellix 则依据离散优先级 `p(c) in [Q_i^lo, Q_i^hi)` 将调用分配给第 i 个队列。随后调用获得队列时间片，并在队列内按 FCFS 顺序执行。时间片耗尽时，调用降级到更低优先级队列；等待过久时，Autellix 使用后述反饥饿机制；完成解码时更新进程表。

**反饥饿。** 离散优先级或 MLFQ 风格算法会使长、低优先级程序饥饿 [Gu19, Jin24, Cho15]。简单的反饥饿技术（例如提升等待超过阈值的调用）会使 Autellix 退化为朴素 MLFQ：长程序的调用进入 `Q_1` 后打断短程序 [Jin24, Arp18]。因此，我们利用进程表测量程序级饥饿。具体而言，对程序 `p`，若总等待时间（`W_total = W_p + W_c`）与服务时间（`T_total = T_p + T_c`）之比超过阈值 `beta`，Autellix 将调用 `c` 提升到 `Q_1`：

$$\frac{W_{\mathrm{total}}}{T_{\mathrm{total}}} \geq \beta$$

改变 `beta` 会在程序平均响应时间与公平性之间产生权衡。提升后，只将 `W_c` 和 `T_c`（即调用的等待与运行时间）置零，从而使程序线程（活动 LLM 调用）很可能一起被提升。

**内存管理。** 抢占式调度使 LLM 引擎必须处理大量并发 LLM 调用，KV 缓存块反复交换以服务不同请求，导致频繁的 GPU-CPU 传输 [Jin24]。已有工作在处理当前迭代时预先为下一迭代的请求交换 KV 缓存，以缓解开销 [Jin24]。但 Autellix 是同步的，需要实时更新每个调用的时间片和进程表。因此，Autellix 采用两个优化分别减少 GPU-CPU 交换的频率和开销。

首先，Autellix 采用多步调度，每 N 个解码步骤而非每一步运行一次调度器，从而减少交换总数。由于部分请求可能提前完成，调度器会在 GPU 上过量配置排队请求，确保某些请求在 N 步前完成时新请求立即加入。其次，Autellix 使用更高效的 GPU-CPU 交换内核：不再为每个块调用独立异步传输，而是将所有 KV 块收集到连续缓冲区并一次传输，从而减少碎片和每块开销、提升 PCIe 带宽并降低端到端交换延迟（见[实现](#section-07)）。

### 4.3 负载均衡器

**算法 2. Autellix 的负载均衡器**

- **过程** `Load_Balancer(Call c, Table pt, List Engines)`
  - **如果** `len(c.tokens) <= 2048`（小请求），则 `assigned_engine = Least_Used(Engines)`。
  - **否则**：
    - **如果** `c.pid in pt`（程序已绑定引擎），则 `assigned_engine = pt[c.pid]`。
    - **否则**选择利用率最低的引擎，设置 `assigned_engine = Least_Used(Engines)`，并设置 `pt[c.pid] = assigned_engine`。
  - **返回** `assigned_engine`。
- **过程** `Least_Used(List Engines)`
  - 注释：并行查询引擎工作负载。
  - 设置 `workloads = Query_Engine_Workloads(Engines)`。
  - 设置 `least_used_engine = Argmin(workloads)`。
  - **返回** `least_used_engine`。

随着智能体工作负载扩展，部署多个引擎副本是必要的。但不考虑数据局部性地分发请求会导致次优性能 [Zha24a]。

我们的智能体工作负载分析（见[第 3 节](#section-03)）揭示了短请求与长请求的关键差异。由于共享系统提示，2048 token 以下的短请求在任意引擎上都能获得较高缓存命中率（≥75%）。为这些请求强制保持数据局部性收益很小；当大型并行程序占据特定引擎时，还可能造成利用率偏斜。因此，在负载最低的引擎之间平衡短请求即可用很小开销保持性能。相反，长请求对程序数据局部性更敏感。它们与特定程序的大量前缀重叠，在持续路由到同一引擎时能显著减少重算，值得承受偶尔的排队延迟。

已有工作依赖复杂前缀树量化数据局部性 [Zha24a]；我们的方法则动态地将短请求路由到负载最低的引擎，并将长请求固定到其程序对应的引擎。[算法 2](#section-04-03) 形式化了这一方法，评估显示 Autellix 的负载均衡器在异构工作负载上同时改善吞吐量和延迟（见[第 6 节](#section-06)）。

## 5 实现

Autellix 是一个多引擎 LLM 推理服务系统，由前端、调度器和负载均衡器组成，共约 5000 行 Python 与 CUDA/C++ 代码。

**前端。** Autellix 前端扩展 OpenAI Chat Completion 和 vLLM Python API [Sto23c, Ope25a]，向开发者提供看似无状态的有状态接口。用户只需在 Python 应用中导入 Autellix 库；程序初始化时，Autellix 自动向后端发送 `start_session` 请求。该操作返回唯一会话标识，并在进程表中创建对应条目。后续 LLM 调用会透明地附加会话、程序和线程 ID，再分派到后端。程序完成或出错时，Autellix 调用 `end_session`，删除进程表中的关联条目。作为研究原型，当前前端没有防止用户修改底层软件包的保护；这一限制留待未来解决。

**LLM 引擎。** Autellix 构建于 vLLM v0.6.1 [Sto23c]。为保持改动局部化，我们只修改调度器，集成 PLAS、ATLAS、MLFQ 策略和高效内存交换内核，从而便于实验并清晰归因性能收益。调度器遵循上一节的算法（见[Autellix 设计](#section-05)）。我们还注意到，vLLM 通过 `cudaMemcpyAsync` 逐个传输每个键值（KV）块，产生细碎传输，未充分利用 PCIe 带宽并引入重复 DMA 设置等高开销。为此，我们分配主机缓冲区，将所有 KV 块合并为单个连续块并进行一次批量传输。结果见下一节（见[评估](#section-06)）。

**多引擎。** vLLM 当前不能同时管理多个 LLM 引擎。为了评估负载均衡策略，我们在 `AsyncLLMEngine` 之上构建 `AsyncMultiLLMEngine`。每个引擎副本运行在独立 Python 进程中，协调元引擎通过 `mp.Queue` 和 `mp.Pipe` 等进程间通信（IPC）原语管理副本。元引擎收到请求后，将其分配给合适副本，并向前端返回不阻塞的 future-like 对象。选定的引擎进程异步执行任务，再通过 IPC 通道发送完成结果。元引擎收到结果后解析 future 并向前端提供输出。该设计允许并行处理多个请求，元引擎作为非阻塞协调器负责路由、资源分配和结果收集。

我们的真实世界实验在四种代表性智能体工作负载上评估 Autellix，它们在解码 token、预填充 token 和 LLM 调用数方面差异很大（[图 11](#figure-11)）。

**聊天机器人智能体：ShareGPT [Src23]。** ShareGPT 数据集包含用户生成的对话输入和输出，是典型聊天机器人应用。LLM 调用数呈长尾分布，平均 6.66 次，最多 80 次（[图 11](#figure-11)）。ShareGPT 的对话性质体现在其偏解码调用：平均解码 277 token，而预填充为 256 token，短提示会生成详细回答（[图 11](#figure-11)）。我们的实验将完整对话而非首轮重放为一个程序。

**ReAct 智能体：BFCL [Gon24a]。** Berkeley Function Calling Leaderboard（BFCLv3）评估多轮、多步骤工具使用任务。相比 ShareGPT，BFCL 的 LLM 调用长尾更弱，每程序平均 10.75 次、最多 70 次（[图 11](#figure-11)）。BFCL 偏预填充，每次调用平均 735.06 个 token，原因是系统提示和工具签名很长；解码较短，平均 34.14 个 token（[图 11](#figure-11)）。因此 BFCL 表现为在繁重预填充阶段和短解码及函数调用之间交替的动态工作流。

**蒙特卡洛树搜索：LATS [Wan24]。** LATS 工作负载来自在 HotpotQA [Man18] 上运行 MCTS，计算密集且包含大量并行 LLM 调用。每个程序实例平均包含 159.7 次 LLM 调用，比 ShareGPT 或 BFCL 多一个数量级（[图 11](#figure-11)）。每次调用的预填充和解码阶段平均分别为 467.2 和 72.6 token（[图 11](#figure-11)）。这些分布体现了 MCTS 固有的迭代、并行性质，要求服务系统高效处理大量并发调用。

**混合。** 我们从三个工作负载中等量采样以保证多样性，测试 Autellix 跨程序类别的性能。

实验中，我们从上述工作负载随机采样程序而非 LLM 调用，并按照既有方法 [Sto23c, Jin24] 使用泊松过程 `lambda` 生成程序到达轨迹。这样可使设置贴近真实场景。

### 实验设置

**模型与测试平台。** 我们评估三个模型：LLaMA-3.1-8B、70B 和 Falcon-180B，分别运行在 1、4 和 8 张 GPU 上。实验在 GCP Compute Engine `a2-ultragpu-8g` 实例上进行，实例有八张通过 NVLink 连接的 A100-SXM4-80GB GPU、1360 GB 主机内存、PCIe-4.0×16 和 2 TB 磁盘空间。

**指标。** 现有 LLM 服务系统关注请求级指标，如首 token 时间（TFTT）和每输出 token 时间（TPOT），也称 token 延迟 [Sto23c, Jin24, Kas24]。但这些指标忽略智能体程序端到端延迟。因此，我们引入程序级 token 延迟，定义为程序总响应时间除以生成 token 数 [+3]。面向程序的高吞吐系统应在高请求率下保持较低程序级延迟。为简化表述，下文均将该指标称为*延迟*。

**基线。** 评估包含三个基线。包括 Autellix 在内，所有基线使用相同最大批大小。

- **vLLM [Sto23c]。** vLLM 是最先进的高吞吐 LLM 服务系统，集成连续批处理 [Chu22] 和 PagedAttention [Sto23c] 以减少 KV 缓存碎片。其默认调度策略 FCFS 与应用无关，存在调用级和程序级 HoL 阻塞。我们使用 vLLM v0.6.1。
- **vLLM-opt。** vLLM 的优化版本，启用分块预填充 [Ram23]、前缀缓存 [She24, Qiu24] 和多步调度。根据 vLLM 博客文章 [Tea24]，其性能接近 SGLang [She24] 和 TensorRT [Nvi23]。
- **MLFQ。** 在 vLLM-opt 之上使用多级反馈队列算法 [Jin24] 实现抢占，用于消融程序级和调用级阻塞的影响。

### 端到端单引擎性能

[图 12](#figure-12) 评估 Autellix 对三种基线和四种工作负载（ShareGPT、BFCL、LATS、Mixed）的端到端性能。在所有工作负载上，给定相同 token 延迟时 Autellix 都达到最高吞吐量。相反，vLLM 缺少前缀缓存，导致同一程序调用需要昂贵地重算累积状态（[图 7](#figure-07)），因而表现最差。不同工作负载下 vLLM-opt、MLFQ 和 Autellix 的相对性能有所变化。

前两行绘制单线程 ShareGPT 和 BFCL 的延迟。vLLM 和 vLLM-opt 的 FCFS 调度导致严重 HoL 阻塞，延迟随到达率增加。MLFQ 是抢占式算法，可以缓解调用级 HoL，相比 vLLM-opt 吞吐量提升 1.5 倍；但高负载时仍有程序级 HoL。Autellix 使用 PLAS 同时处理两级 HoL，在重负载下吞吐量最高达到 vLLM 的 8 倍、vLLM-opt 的 2 倍，并比 MLFQ 提高 1.5 倍。

第三行展示多线程 LATS。Autellix 相比 vLLM、MLFQ 和 vLLM-opt 的提升最高分别为 5 倍、2.5 倍和 2 倍。MLFQ 的抢占调度虽有利于单线程程序，却不适合多线程设置：过度优先短请求会扰乱同一程序的线程，加剧程序级 HoL 并阻滞整体进展。Autellix 的 ATLAS 综合优化所有线程的资源分配，保持平衡进展，在重负载下维持高吞吐量。

[图 12](#figure-12) 第四行展示混合工作负载。Autellix 比 vLLM 高 15 倍、比 MLFQ 高 5.5 倍、比 vLLM-opt 高 4 倍。由于减少程序级和调用级阻塞，随着程序异质性（LLM 调用和解码长度的多样性）提高，Autellix 表现更好。

**尾延迟。** 抢占式调度可降低平均延迟，但可能使长程序饥饿并增加尾延迟。[图 13](#figure-13) 报告 LLaMA-3.1-8B 上不同工作负载的第 95（P95）和第 99（P99）百分位延迟。对 ShareGPT，MLFQ 相比 vLLM-opt 显著改善平均延迟（[图 12](#figure-12)），却有较差 P95/99 尾延迟；对 BFCL，MLFQ 在两种情况下都优于 vLLM-opt。在 8 个场景中的 7 个，Autellix 的尾延迟持续低于 MLFQ 和 vLLM-opt，并将 P95/99 尾延迟下的吞吐量最高提高 1.7 倍，说明平均和尾部性能都稳健提升。

### 端到端多引擎性能

<span id="figure-14"></span>

![多引擎主要结果](./autellix/figure-14.png)

**图 14. 多引擎主要结果。** 不同负载均衡策略下的平均、P95/99 延迟。

为评估 Autellix 的数据局部性感知负载均衡器（见[4.3 节](#section-04-03)），我们在相同 PLAS、ATLAS 调度策略下，与两种常用负载均衡策略比较：

- **轮询。** 请求按循环顺序分配到引擎，保证请求数均匀分布，是 Kubernetes 的默认负载均衡策略 [Src17]。它忽略数据局部性，造成昂贵的 KV 缓存未命中和重算开销。
- **最少使用。** 请求分配给系统中 LLM 调用数最低的引擎，可以平衡引擎负载；但和轮询一样忽略数据局部性，并产生频繁 KV 重算。

我们使用四个 LLaMA3.1-8B 副本和两个 LLaMA3.1-70B 副本，在 ShareGPT 和 LATS 工作负载上实验。结果见[图 14](#figure-14)：Autellix 在所有配置中都保持较低平均和尾延迟，吞吐量最高比两个基线高 1.4 倍。ShareGPT 中聊天历史复用显著增强 KV 缓存局部性，因此收益更明显。副本数量增加时优势更大，因为引擎池变大后，请求被路由到具有其局部性的引擎的概率降低。

#### 离线推理

**图 16. 离线批推理。** Autellix 减少处理一批程序所需的时间，即 makespan。

在优先吞吐量而非延迟的离线场景中，大批程序以批量而非交互或流式方式处理。我们考虑所有程序一开始同时提交的场景。[图 16](#figure-16) 展示使用 ShareGPT 数据集时各系统处理全部程序的 makespan。Autellix 始终优于基线，将平均 makespan 降低 10–40%。程序数为 4000 时，MLFQ 无法完成执行。它把所有新请求分配到最高优先级队列，产生大量活动 LLM 请求，导致严重内存竞争和频繁 GPU-CPU 交换。即使有超过 1.2 TB 的交换空间，系统资源仍被耗尽并出现 OOM 错误。

<span id="figure-17"></span>

![推理开销分解](./autellix/figure-17.png)

**图 17. 推理开销分解。** Autellix 显著减少等待时间，并为 vLLM 引入很小的调度器开销；改进的内核还减少交换时间。

[图 17](#figure-17) 分解 Autellix 及其基线中 LLM 调用在服务层花费的时间。总体上，Autellix 通过减少等待和交换时间，为 ShareGPT 与 LATS 获得更低 token 延迟；两者分别归因于程序级调度策略和改进的交换内核。抢占的调度成本较高，Autellix 与 MLFQ 的调度时间都高于 vLLM-OPT 的朴素 FCFS。但 Autellix 通过程序级优先级和更均匀地在优先级队列间分配调用，调度开销仍低于 MLFQ。MLFQ 默认将新调用放入最高级优先队列，因此大多数调用集中在高优先级队列，导致较大调度开销。

#### 与最优调度比较

<span id="figure-18"></span>

![与最优调度策略比较](./autellix/figure-18.png)

**图 18. 与最优调度策略比较。** 在仿真中 Autellix 优于其他调度策略，但与最优策略（SRPT）相比仍存在明显差距。

SRPT 等最优调度策略假设完全知道程序运行时间，这是实践中不现实的假设。因此，我们通过预先暴露每个程序的 LLM 调用总数和解码步骤，用仿真器模拟预知。仿真只考虑调度，每个连续批处理步骤都相同。在这些简化条件下，Autellix 优于 FCFS 及轮询、MLFQ 等抢占式调度器。然而，Autellix 与 SRPT 之间仍有明显差距，说明先验知识可以显著提升性能。

**图 19. Autellix 交换内核的影响。** Autellix 减少总交换次数和 GPU-CPU 交换时间，提升吞吐量。

#### 交换内核的影响

抢占式调度增加系统中的活动 LLM 调用，导致 GPU 内存利用率较高。高请求率下，为获取相关 KV 缓存而频繁进行 GPU-CPU 交换，会带来显著开销 [Jin24]。Autellix 将并行 KV 块传输批量合并为一次操作，最多减少 18 倍交换次数、3–7 倍交换时间，并比 vLLM 的实现内核获得 1.3 倍更高吞吐量（见[图 19](#figure-19)）。

## 7 讨论与未来工作

**图优化。** Autellix 不预先知道程序执行 DAG，而是在运行时动态构建内部表示（IR）。虽然完整的程序执行先验知识不现实，但预测紧接着的步骤可能可行，从而启用分支预测、推测执行等*编译器优化*，让未来 LLM 调用在此前调用完成时并行执行。我们将这些优化留待未来工作。

**后训练。** Deepseek-R1 [Dee25] 和 OpenAI 的 o1/o3 模型 [Ope25] 等推理模型通过端到端强化学习（RL）后训练来优化思维过程。为加速训练，分布式 RL 系统交替执行分布式在线策略采样和训练，收集轨迹并进行策略梯度更新 [She24a, Sto18]。更有效的调度可以减少每次 RL 迭代批量采样的总 makespan，直接使分布式后训练系统受益。

## 8 结论

我们提出 Autellix，这是一个面向高度动态通用程序而非单个 LLM 调用的分布式 LLM 服务系统。Autellix 的关键创新是利用累积服务时间等程序级统计量，更好地确定 LLM 调用优先级并进行调度，从而改善程序端到端响应时间和吞吐量。我们提出面向单线程和多线程程序的两个通用调度算法，以及有效减少程序等待和执行时间的数据局部性感知负载均衡器。实验表明，在相同延迟下，Autellix 相比 vLLM 等最先进系统将程序吞吐量提高 4–15 倍。
