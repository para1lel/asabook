## 摘要

高吞吐量的大语言模型 (LLMs) 服务需要一次性批处理足够多的请求. 然而, 现有系统面临困难, 因为每个请求的键值缓存 (KV cache) 内存非常大, 并且会动态增长和缩减. 如果管理不当, 这些内存可能会因为碎片化和冗余重复而被大量浪费, 从而限制批处理大小. 为了解决这个问题, 我们提出了 PagedAttention, 一种受操作系统中经典虚拟内存和分页技术启发的注意力算法. 在此基础上, 我们构建了 vLLM, 一个 LLM 服务系统, 实现了 (1) KV 缓存内存几乎零浪费, 以及 (2) 在请求内部和跨请求灵活共享 KV 缓存, 以进一步减少内存使用. 我们的评估表明, 与最先进的系统 (如 FasterTransformer 和 Orca) 相比, vLLM 在相同延迟水平下将流行 LLM 的吞吐量提高了 2-4$\times$. 这种提升在处理更长序列, 更大模型和更复杂解码算法时更为显著. vLLM 的源代码已在 [GitHub](https://github.com/vllm-project/vllm) 公开.

## 1\. 引言

大型语言模型 (*LLMs*) 如 GPT [OpenAa23, Browne20] 和 PaLM [Chowdb22] 的出现, 使得编程助手 [Github22, Chena21] 和通用聊天机器人 [OpenAI22, Google23] 等新应用成为可能, 并开始对我们的工作和日常生活产生深远影响. 许多云公司 [OpenAI20, Servic23] 正在竞相提供这些作为托管服务的应用. 然而, 运行这些应用成本非常高, 需要大量硬件加速器, 如 GPU. 据最近估计, 处理一次 LLM 请求的费用可能比传统关键字查询 [Reuter23] 高 10 $\times$ 倍. 鉴于这些高成本, 提高 *LLM 服务* 系统的吞吐量—从而降低每次请求的成本—变得愈发重要.

在 LLM 的核心是一个自回归 Transformer 模型 [Vaswac17]. 该模型根据输入 (提示) 以及迄今为止生成的输出 token 序列, *一次生成一个* token. 对于每个请求, 这个昂贵的过程会重复, 直到模型输出一个终止 token. 这个顺序生成过程使工作负载成为 *内存受限型*, GPU 的计算能力未被充分利用, 并限制了服务吞吐量.

提高吞吐量可以通过将多个请求批处理来实现. 然而, 要在批处理中处理大量请求, 每个请求的内存空间应被有效管理. 例如, [图 1](#figure-01) (左) 展示了在具有 40GB 内存的 NVIDIA A100 GPU 上, 13B 参数 LLM 的内存分布. 大约 65% 的内存分配给模型权重, 这些权重在服务过程中保持静态. 约 30% 的内存用于存储请求的动态状态. 对于 Transformer, 这些状态包括与注意力机制相关的键和值张量, 通常称为 *KV cache* [Popea22], 它们表示来自早期 token 的上下文, 用于按顺序生成新的输出 token. 剩余小部分内存用于其他数据, 包括激活值—在评估 LLM 时创建的临时张量. 由于模型权重是固定的, 并且激活值仅占用 GPU 内存的一小部分, KV cache 的管理方式在决定最大批量大小方面至关重要. 如果管理不当, KV cache 内存可能会显著限制批量大小, 从而影响 LLM 的吞吐量, 如 [图 1](#figure-01) (右) 所示.

在本文中, 我们观察到现有的 LLM 服务系统 [Refd22, NVIDIA23] 在高效管理 KV 缓存内存方面存在不足. 这主要是因为它们将请求的 KV 缓存存储在连续的内存空间中, 而大多数深度学习框架 [Paszka19, Olston17] 要求张量存储在连续的内存中. 然而, 与传统深度学习工作负载中的张量不同, KV 缓存具有独特的特性: 它随着模型生成新 token 动态增长和收缩, 其生命周期和长度在事先无法确定. 这些特性使现有系统的方法在两个方面显得效率低下:

![参见图注](./vllm/figure-02.png)

**图 2.** 在 §[6.2](#S6.SS2) 中实验期间, 不同 LLM 服务系统的平均内存浪费百分比.

首先, 现有系统 [Refd22, NVIDIA23] 存在内部和外部内存碎片问题. 为了在连续空间中存储请求的 KV 缓存, 它们*预分配*一个与请求最大长度相同的连续内存块 (例如, 2048 个 token). 由于请求的实际长度可能远小于其最大长度 (例如, [图 11](#figure-11)), 这可能导致严重的内部碎片. 另外, 即使已知实际长度, 预分配仍然低效: 由于整个内存块在请求生命周期内被保留, 其他较短的请求无法使用当前未使用的内存块部分. 另外, 外部内存碎片也可能很严重, 因为每个请求的预分配大小可能不同. 实际上, 我们在 [图 2](#figure-02) 的分析结果显示, 在现有系统中, 只有 20.4% - 38.2% 的 KV 缓存内存被用于存储实际的 token 状态.

其次, 现有系统无法利用内存共享的机会. LLM 服务通常使用先进的解码算法, 如并行采样和束搜索, 这些算法每个请求会生成多个输出. 在这些情况下, 请求由多个序列组成, 这些序列可以部分共享它们的 KV 缓存. 然而, 由于序列的 KV 缓存存储在单独的连续空间中, 现有系统中无法进行内存共享.

为了解决上述限制, 我们提出了*PagedAttention*, 一种受操作系统 (OS) 解决内存碎片和共享的方案启发的注意力算法: *带分页的虚拟内存*. PagedAttention 将请求的 KV 缓存划分为块, 每块可以包含固定数量的 token 的注意力键和值. 在 PagedAttention 中, KV 缓存的块不必存储在连续空间中. 因此, 我们可以像操作系统的虚拟内存一样以更灵活的方式管理 KV 缓存: 可以将块视为页, 将 token 视为字节, 将请求视为进程. 这种设计通过使用相对较小的块并按需分配来缓解内部碎片问题. 另外, 由于所有块大小相同, 它消除了外部碎片. 最后, 它还使跨同一请求的不同序列, 甚至跨不同请求的块级内存共享成为可能.

在这项工作中, 我们构建了 *vLLM*, 一个基于 PagedAttention 的高吞吐量分布式 LLM 服务引擎, 实现了 KV 缓存内存几乎为零的浪费. vLLM 使用与 PagedAttention 联合设计的块级内存管理和抢占式请求调度. vLLM 支持各种流行的 LLM, 例如 GPT [Browne20], OPT [Zhangb22] 和 LLaMA [Touvra23], 尺寸各异, 包括那些超过单个 GPU 内存容量的模型. 我们在各种模型和工作负载上的评估表明, 与最先进系统 [Refd22, NVIDIA23] 相比, vLLM 将 LLM 服务吞吐量提高了 2-4$\times$, 而完全不影响模型精度. 这种提升在处理更长序列, 更大模型以及更复杂解码算法时更为明显 (§[4.3](#S4.SS3)). 本文的主要贡献如下:

- 我们识别了 LLM 服务中内存分配的挑战, 并量化了这些挑战对服务性能的影响.
- 我们提出了 PagedAttention, 一种在非连续分页内存中操作 KV 缓存的注意力算法, 受操作系统中的虚拟内存和分页机制启发.
- 我们设计并实现了 vLLM, 一个构建在 PagedAttention 之上的分布式 LLM 服务引擎.
- 我们在不同场景下评估了 vLLM, 并证明其远超以往的先进解决方案, 如 FasterTransformer [NVIDIA23] 和 Orca [Refd22].

## 2\. 背景

本节介绍典型 LLM 的生成和服务过程, 以及 LLM 服务中使用的迭代级调度.

### 2.1. 基于 Transformer 的大型语言模型

语言建模的任务是建模一组词的概率 $(x_{1},\ldots,x_{n}).$ 由于语言具有自然的顺序顺序, 通常将整个序列的联合概率分解为条件概率的乘积 (又称*自回归分解* [Bengio00]):

<span id="S2.E1"></span>

$$
P(x)=P(x_{1})\cdot P(x_{2}\mid x_{1})\cdots P(x_{n}\mid x_{1},\ldots,x_{n-1}).\tag{1}
$$

变换器 [Vaswac17] 已成为大规模建模上述概率的事实标准架构. 基于 Transformer 的语言模型最重要的组成部分是其*自注意*层. 对于输入的隐藏状态序列 $(x_{1},\ldots,x_{n})\in\mathbb{R}^{n\times d}$, 自注意层首先对每个位置 $i$ 进行线性变换, 以获得查询, 键和值向量:

<span id="S2.E2"></span>

$$
q_{i}=W_{q}x_{i},\ k_{i}=W_{k}x_{i},\ v_{i}=W_{v}x_{i}.\tag{2}
$$

然后, 自注意力层通过将某一位置的查询向量与其之前的所有键向量相乘计算注意力分数 $a_{\mathrm{ij}}$, 并将输出 $o_{i}$ 计算为值向量的加权平均:

$$
a_{\mathrm{ij}}=\frac{\exp(q_{i}^{\top}k_{j}/\sqrt{d})}{\sum_{t=1}^{i}\exp(q_{i}^{\top}k_{t}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{i}a_{\mathrm{ij}}v_{j}.\tag{3}
$$

除了 [公式 4](#S4.E4) 中的计算, Transformer 模型中的所有其他组件, 包括嵌入层, 前馈层, 层归一化 [Refa16], 残差连接 [Refb16], 输出 logit 计算, 以及 [公式 2](#S2.E2) 中的查询, 键和值转换, 都以 $y_{i}=f(x_{i}).$ 的形式独立按位置应用.

### 2.2. LLM 服务与自回归生成

训练完成后, LLM 通常作为条件生成服务部署 (例如, 完成 API [OpenAI20] 或聊天机器人 [OpenAI22, Google23]). 对 LLM 服务的请求提供一系列 *输入提示* 令牌 $(x_{1},\ldots,x_{n})$, LLM 服务根据 [公式 1](#S2.E1) 生成一系列输出令牌 $(x_{n+1},\ldots,x_{n+T})$. 我们将提示和输出列表的连接称为 *序列*.

由于公式 [1](#S2.E1) 中的分解, LLM 只能逐个抽样并生成新的 token, 每个新 token 的生成过程依赖于该序列中所有的*前置 token*, 特别是它们的 key 和 value 向量. 在这个序列生成过程中, 现有 token 的 key 和 value 向量通常会被缓存以生成未来的 token, 这称为*KV 缓存*. 需要注意的是, 一个 token 的 KV 缓存依赖于它所有的前置 token. 这意味着同一个 token 在序列中不同位置出现时, 其 KV 缓存将会不同.

给定一个请求提示, LLM 服务中的生成计算可以分解为两个阶段:

- **提示阶段.** 以整个用户提示 $(x_{1},\ldots,x_{n})$ 作为输入, 并计算第一个新 token $P(x_{n+1}\mid x_{1},\ldots,x_{n})$ 的概率. 在此过程中, 还会生成 key 向量 $k_{1},\ldots,k_{n}$ 和 value 向量 $v_{1},\ldots,v_{n}$. 由于提示 token $x_{1},\ldots,x_{n}$ 已知, 提示阶段的计算可以通过矩阵-矩阵乘法并行化, 从而高效利用 GPU 的并行性.
- **自回归生成阶段.** 按顺序生成剩余的新标记. 在迭代 $t$ 时, 模型将一个标记 $x_{n+t}$ 作为输入, 并使用键向量 $k_{1},\ldots,k_{n+t}$ 和值向量 $v_{1},\ldots,v_{n+t}$ 计算概率 $P(x_{n+t+1}\mid x_{1},\ldots,x_{n+t})$. 位置 $1$ 到 $n+t-1$ 的键值向量在先前的迭代中已缓存, 本次迭代只计算新的键向量 $k_{n+t}$ 和值向量 $v_{n+t}$. 该阶段在序列达到最大长度 (由用户指定或受 LLM 限制) 或发出序列结束标记 `<eos>` 时完成. 由于数据依赖, 不同迭代的计算无法并行化, 并且通常使用矩阵-向量乘法, 效率较低. 因此, 该阶段无法充分利用 GPU 计算且受限于内存, 是单个请求延迟的主要原因.

### 2.3. LLM 的批处理技术

通过将多个请求进行批处理, 可以提高在服务大型语言模型 (LLMs) 时的计算利用率. 由于这些请求共享相同的模型权重, 移动权重的开销可以在批量请求中分摊, 并且当批量大小足够大时, 这些开销可以被计算开销所覆盖. 然而, 将请求批处理到 LLM 服务并非易事, 原因有二. 首先, 请求可能在不同时间到达. 一个简单的批处理策略要么会让较早的请求等待较晚的请求, 要么会延迟新到的请求直到较早的请求完成, 从而导致显著的排队延迟. 第二, 请求的输入和输出长度可能差异很大 ([图 11](#figure-11)). 一种直接的批处理方法会对请求的输入和输出进行填充以使其长度相等, 这会浪费 GPU 计算和内存.

为了解决这个问题, 已经提出了精细化批处理机制, 比如单元批处理 [Gao18] 和迭代级调度 [Refd22]. 与在请求级别工作的传统方法不同, 这些技术在迭代级别上运行. 在每次迭代之后, 已完成的请求会从批处理中移除, 并添加新的请求. 因此, 新请求可以在等待一次迭代后被处理, 而不必等待整个批次完成. 另外, 通过特殊的 GPU 内核, 这些技术消除了对输入和输出进行填充的需求. 通过减少排队延迟和因填充导致的低效, 精细化批处理机制显著提高了 LLM 服务的吞吐量.

## 3\. LLM 服务中的内存挑战

尽管精细化批处理减少了计算浪费, 并使请求可以以更灵活的方式进行批处理, 但可以一起批处理的请求数量仍受限于 GPU 内存容量, 尤其是用于存储 KV 缓存的空间. 换句话说, 服务系统的吞吐量受 *内存限制*. 克服这种内存限制需要解决内存管理中的以下挑战:

- **大型 KV 缓存.** KV 缓存的大小会随着请求数量迅速增长. 例如, 对于 13B 参数的 OPT 模型 [Zhangb22], 单个 token 的 KV 缓存需要 800 KB 的空间, 计算方式为 $2$ (键和值向量) $\times\ 5120$ (隐藏状态大小) $\times\ 40$ (层数) $\times\ 2$ (每个 FP16 占用字节数). 由于 OPT 可以生成最多 2048 个 token 的序列, 因此存储一次请求的 KV 缓存所需的内存可达 1.6 GB. 现有 GPU 的内存容量在几十 GB 之间. 即使将所有可用内存分配给 KV 缓存, 也只能容纳几十个请求. 低效的内存管理会进一步减少批处理大小, 如 [图 2](#figure-02) 所示. 按照当前趋势, GPU 的计算速度增长快于内存容量 [Gholaa21]. 例如, 从 NVIDIA A100 到 H100, FLOPS 增加超过 2 倍, 但 GPU 内存最多仍为 80GB. 因此, 内存会成为越来越明显的瓶颈.
- **复杂解码算法.** LLM 服务提供一系列解码算法供用户选择, 每种算法对内存管理复杂性有不同影响. 例如, 当用户从单个输入提示请求多个随机样本时, 这是程序建议 [Github22] 中的典型用例, 提示部分的 KV 缓存 (在我们的实验中占总 KV 缓存内存的 12% (§[6.3](#S6.SS3))) 可以共享以减少内存使用. 另一方面, 在自回归生成阶段的 KV 缓存应保持不共享, 因为不同样本的结果依赖于上下文和位置. KV 缓存共享的程度取决于采用的具体解码算法. 在更复杂的算法如束搜索 [Sutska14] 中, 不同请求的束可以共享更大部分 (最多节省 55% 内存, 见 §[6.3](#S6.SS3)) 的 KV 缓存, 并且共享模式会随着解码过程的推进而变化.
- **对未知输入和输出长度的调度.** 对 LLM 服务的请求在输入和输出长度上存在可变性. 这要求内存管理系统能够适应各种提示长度. 随着请求的输出长度在解码过程中增长, 其 KV 缓存所需的内存也会增加, 并可能耗尽可用于新请求或现有提示继续生成的内存. 系统需要做出调度决策, 例如删除某些请求的 KV 缓存, 或将其从 GPU 内存中调出.

### 3.1. 现有系统中的内存管理

由于当前大多数深度学习框架中的操作 [Paszka19, Olston17] 需要将张量存储在连续内存中, 先前的 LLM 服务系统 [Refd22, NVIDIA23] 也将一个请求的 KV 缓存存储为跨不同位置的连续张量. 由于 LLM 输出长度不可预测, 它们会根据请求的最大可能序列长度为请求静态分配一块内存, 而不考虑请求的实际输入或最终输出长度.

[图 3](#figure-03) 展示了两个请求: 请求 A 的最大可能序列长度为 2048, 而请求 B 的最大长度为 512. 现有系统中的块预分配方案主要有三种内存浪费来源: *为将来令牌预留*的空间, *因为为潜在的最大序列长度过度分配而产生的内部碎片*, 以及*来自内存分配器 (如伙伴分配器) 的外部碎片*. 外部碎片永远不会被已生成的令牌使用, 这点在处理请求之前就已知. 内部碎片也不会被使用, 但这只有在请求完成采样后才会显现. 它们都是纯粹的内存浪费. 虽然预留的内存最终会被使用, 但在整个请求期间预留这部分空间, 尤其是当预留空间很大时, 会占用本可用于处理其他请求的空间. 我们在实验中可视化了内存浪费的平均百分比, 如 [图 2](#figure-02) 所示, 揭示了以前系统中实际有效内存可能低至 20.4%.

尽管已经提出了压缩 [Wanga22] 作为解决碎片的一种潜在方案, 但在性能敏感的 LLM 服务系统中执行压缩是不切实际的, 因为 KV 缓存非常庞大. 即使有了压缩, 每个请求的预分配块空间仍然阻碍了现有内存管理系统中针对解码算法的内存共享.

### 4.1. PagedAttention

为了解决 §[3](#S3) 中的内存挑战, 我们引入了 *PagedAttention*, 这是一种受操作系统经典 *分页* 思想启发的注意力算法 [Kilbur62]. 与传统的注意力算法不同, PagedAttention 允许在非连续内存空间中存储连续的键和值. 具体来说, PagedAttention 将每个序列的 KV 缓存划分为 *KV 块*. 每个块包含固定数量 token 的键和值向量 [+2], 我们将其称为 *KV 块大小* ($B$). 记键块为 $K_{j}=(k_{(j-1)B+1},\ldots,k_{\mathrm{jB}})$, 值块为 $V_{j}=(v_{(j-1)B+1},\ldots,v_{\mathrm{jB}}).$ [公式 4](#S4.E4) 中的注意力计算可以转化为以下块级计算:

<span id="S4.E4"></span>

$$
A_{\mathrm{ij}}=\frac{\exp(q_{i}^{\top}K_{j}/\sqrt{d})}{\sum_{t=1}^{\lceil i/B\rceil}\exp(q_{i}^{\top}K_{t}\mathbf{1}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{\lceil i/B\rceil}V_{j}A_{\mathrm{ij}}^{\top},\tag{4}
$$

其中 $A_{\mathrm{ij}}=(a_{i,(j-1)B+1},\ldots,a_{i,\mathrm{jB}})$ 是第 $j$ 个 KV 块的注意力分数行向量.

在注意力计算过程中, PagedAttention 内核会分别识别并提取不同的 KV 块. 我们在 [图 5](#figure-05) 中展示了 PagedAttention 的一个例子: 键和值向量分布在三个块中, 并且这三个块在物理内存上并不连续. 每次计算时, 内核会将查询 token "*forth*" 的查询向量 $q_{i}$ 与一个块中的键向量 $K_{j}$ (例如块 0 的 "*Four score and seven*" 键向量) 相乘以计算注意力分数 $A_{\mathrm{ij}}$, 然后再将 $A_{\mathrm{ij}}$ 与该块中的值向量 $V_{j}$ 相乘, 从而得到最终的注意力输出 $o_{i}$.

总之, PagedAttention 算法允许将 KV 块存储在非连续的物理内存中, 从而在 vLLM 中实现更灵活的分页内存管理.

### 4.2. KV 缓存管理器

vLLM 内存管理器背后的关键思想类似于操作系统中的*虚拟内存*[Kilbur62]. 操作系统将内存分为固定大小的*页*, 并将用户程序的逻辑页映射到物理页. 连续的逻辑页可以对应非连续的物理内存页, 从而允许用户程序像访问连续内存一样访问内存. 另外, 物理内存空间不需要提前完全预留, 使操作系统可以根据需要动态分配物理页. vLLM 使用虚拟内存背后的理念来管理 LLM 服务中的 KV 缓存. 在 PagedAttention 的支持下, 我们将 KV 缓存组织为固定大小的 KV 块, 就像虚拟内存中的页一样.

请求的 KV 缓存表示为一系列*逻辑 KV 块*, 随着新 token 及其 KV 缓存的生成, 从左到右填充. 最后一个 KV 块的未填充位置保留用于未来生成. 在 GPU 工作节点上, *块引擎* 分配一块连续的 GPU DRAM 并将其划分为*物理 KV 块* (这也会在 CPU RAM 上进行以便进行交换; 参见 §[4.5](#S4.SS5)). *KV 块管理器* 还维护*块表*—每个请求的逻辑 KV 块与物理 KV 块之间的映射. 每个块表条目记录逻辑块对应的物理块及其已填充位置的数量. 逻辑 KV 块与物理 KV 块的分离允许 vLLM 动态增加 KV 缓存内存, 而无需提前为所有位置保留内存, 从而消除了现有系统中的大部分内存浪费, 如 [图 2](#figure-02) 所示.

### 4.3. 使用 PagedAttention 和 vLLM 的解码

<span id="figure-06"></span>

![参见图注](./vllm/figure-06.png)

**图 6.** vLLM 中的块表转换.

下面结合 [图 6](#figure-06) 说明 vLLM 如何在单个输入序列的解码过程中执行 PagedAttention 并管理内存:

1. 如同操作系统的虚拟内存, vLLM 初始并不需要为可能生成的最大序列长度预留内存. 它只保留容纳提示计算所生成 KV 缓存所需的 KV 块. 本例的提示有 7 个标记, 因此 vLLM 将前两个逻辑 KV 块 (0 和 1) 映射到两个物理 KV 块 (分别为 7 和 1). 在预填充步骤中, vLLM 使用传统的自注意力算法 (例如 [Daoc22]) 生成提示和第一个输出标记的 KV 缓存. 前 4 个标记的 KV 缓存存入逻辑块 0, 后 3 个存入逻辑块 1, 剩余槽位留给随后的自回归生成阶段.
2. 在第一步自回归解码中, vLLM 使用 PagedAttention 算法在物理块 7 和 1 上生成新标记. 最后一个逻辑块仍有一个可用槽位, 因此新生成的 KV 缓存存入该位置, 并更新块表中的 `#filled` 记录.
3. 在第二步解码时, 最后一个逻辑块已经填满. vLLM 为新的逻辑块分配物理块 3, 将新生成的 KV 缓存存入其中, 并在块表中记录这一映射.

从整体流程看, 每次解码迭代中, vLLM 首先为批处理选择一组候选序列 (更多内容见 §[4.5](#S4.SS5)), 并为新需要的逻辑块分配物理块. 随后, vLLM 将当前迭代的所有输入标记 (即提示阶段请求的所有标记和生成阶段请求的最新标记) 连接为一个序列, 并将其输入到 LLM. 在 LLM 计算期间, vLLM 使用 PagedAttention 内核访问以逻辑 KV 块形式存储的先前 KV 缓存, 并将新生成的 KV 缓存保存到物理 KV 块中. 在一个 KV 块中存储多个标记 (块大小 > 1) 使得 PagedAttention 内核可以在更多位置上并行处理 KV 缓存, 从而提高硬件利用率并降低延迟. 然而, 较大的块大小也会增加内存碎片. 我们在 §[7.2](#S7.SS2) 中研究了块大小的影响.

再次说明, vLLM 会在生成更多 token 及其 KV 缓存时, 动态地将新的物理块分配给逻辑块. 由于所有块都是从左到右填充的, 并且只有在所有前面的块都已满时才会分配新的物理块, vLLM 将单个请求的所有内存浪费限制在一个块内, 因此它可以有效地利用所有内存, 如 [图 2](#figure-02) 所示. 这允许更多请求能够在内存中进行批处理, 从而提高吞吐量. 一旦请求生成完成, 其 KV 块可以被释放, 以存储其他请求的 KV 缓存. 在 [图 7](#figure-07) 中, 我们展示了 vLLM 管理两个序列内存的示例. 两个序列的逻辑块映射到 GPU 工作节点中块引擎预留空间的不同物理块. 两个序列的相邻逻辑块在物理 GPU 内存中不需要是连续的, 并且物理块的空间可以被两个序列有效利用.

### 4.4. 应用到其他解码场景

§[4.3](#S4.SS3) 展示了 PagedAttention 和 vLLM 如何处理基本的解码算法, 例如贪心解码和采样, 这些算法以一个用户提示作为输入并生成单个输出序列. 在许多成功的 LLM 应用中 [Github22, OpenAI20], LLM 服务必须提供更复杂的解码场景, 这些场景表现出复杂的访问模式和更多的内存共享机会. 本节中我们展示了 vLLM 在这些场景中的通用适用性.

**并行采样.** 在基于 LLM 的程序助手中 [Chena21, Github22], LLM 会为单个输入提示生成多个采样输出; 用户可以从各种候选中选择他们喜欢的输出. 到目前为止, 我们隐式地假设一个请求生成单个序列. 在本文余下部分, 我们假设更一般的情况, 即一个请求生成多个序列. 在并行采样中, 一个请求包含多个共享相同输入提示的样本, 使得提示的 KV 缓存也可以共享. 通过其 PagedAttention 和分页内存管理, vLLM 可以轻松实现这种共享并节省内存.

[图 8](#figure-08) 显示了两个输出的并行解码示例. 由于两个输出共享相同的提示, 在提示阶段我们只为提示状态保留一份空间; 两个序列的提示逻辑块映射到相同的物理块: 两个序列的逻辑块 0 和 1 分别映射到物理块 7 和 1. 由于单个物理块可以映射到多个逻辑块, 我们为每个物理块引入了一个*引用计数*. 在本例中, 物理块 7 和 1 的引用计数都为 2. 在生成阶段, 两个输出采样不同的输出标记, 需要单独的 KV 缓存存储. vLLM 在需要多个序列修改的物理块上实现了按块粒度的*写时复制*机制, 类似于操作系统虚拟内存中的写时复制技术 (例如, 在创建子进程时). 具体来说, 在 [图 8](#figure-08) 中, 当样本 A1 需要写入其最后一个逻辑块 (逻辑块 1) 时, vLLM 识别到对应物理块 (物理块 1) 的引用计数大于 1; 它分配了一个新的物理块 (物理块 3), 指示块引擎将物理块 1 的信息复制过去, 并将引用计数降为 1. 接下来, 当样本 A2 写入物理块 1 时, 引用计数已经降为 1; 因此 A2 直接将其新生成的 KV 缓存写入物理块 1.

总之, vLLM 使得在多个输出样本之间共享用于存储提示的 KV 缓存的大部分空间成为可能, 唯一例外的是由写时复制机制管理的最终逻辑块. 通过在多个样本之间共享物理块, 可以大大减少内存使用, 尤其是对于*长输入提示*.

![参见图注](./vllm/figure-08.png)

**束搜索.** 在机器翻译等语言模型任务中 [Refc16], 用户期望 LLM 输出最合适的前 $k$ 个翻译. 束搜索 [Sutska14] 被广泛用于从 LLM 解码最可能的输出序列, 因为它降低了完全遍历样本空间的计算复杂度. 该算法依赖*束宽*参数 $k$, 该参数决定每一步保留的候选数量. 在解码过程中, 束搜索通过考虑所有可能的标记来扩展束中的每个候选序列, 使用 LLM 计算它们各自的概率, 并从 $k\cdot|V|$ 个候选中保留概率最高的 $k$ 个序列, 其中 $|V|$ 是词汇表大小.

与并行解码不同, 束搜索不仅可以共享初始提示块, 还可以在不同候选之间共享其他块, 并且随着解码过程的推进, 共享模式会动态变化, 类似于由复合分叉创建的操作系统中的进程树. [图 9](#figure-09) 显示了 vLLM 如何管理束搜索示例中 $k=4$ 的 KV 块. 在虚线所示的迭代之前, 每个候选序列已经使用了 4 个完整的逻辑块. 所有束候选共享第一个块 0 (即提示). 候选 3 从第二块开始就偏离了其他候选. 候选 0-2 共享前三个块, 并在第四块分歧. 在后续迭代中, 概率前四的候选都来源于候选 1 和 2. 由于原始候选 0 和 3 不再位列前列, 它们的逻辑块被释放, 对应物理块的引用计数减少. vLLM 会释放所有引用计数为 0 的物理块 (块 2, 4, 5, 8). 然后, vLLM 分配新的物理块 (块 9-12) 以存储新候选的 KV 缓存. 现在, 所有候选共享块 0, 1, 3; 候选 0 和 1 共享块 6, 候选 2 和 3 进一步共享块 7.

以前的 LLM 服务系统需要在 beam 候选之间频繁复制 KV 缓存的内存. 例如, 在 [图 9](#figure-09) 所示的情况中, 在虚线之后, 候选 3 需要复制候选 2 的大部分 KV 缓存以继续生成. 通过 vLLM 的物理块共享, 可以显著减少这种频繁的内存复制开销. 在 vLLM 中, 不同 beam 候选的大多数块都可以共享. 仅当新生成的 token 位于旧的共享块内时, 如在并行解码中, 才应用写时复制机制. 这只涉及复制一块数据.

**共享前缀.** 通常, LLM 用户会提供任务的 (较长) 描述, 包括指令和示例输入输出, 也称为*系统提示* [OpenAI23]. 该描述会与实际任务输入拼接形成请求的提示. LLM 基于完整提示生成输出. [图 10](#figure-10) 展示了一个例子. 另外, 可以通过提示工程进一步调整共享前缀, 以提高下游任务的准确性 [Liang21, Lester21].

对于这种类型的应用, 许多用户提示共享一个前缀, 因此 LLM 服务提供商可以提前存储该前缀的 KV 缓存, 以减少在前缀上花费的冗余计算. 在 vLLM 中, 这可以通过由 LLM 服务提供商为一组预定义的共享前缀保留一组物理块来方便地实现, 就像操作系统处理跨进程共享库一样. 带有共享前缀的用户输入提示可以简单地将其逻辑块映射到缓存的物理块 (最后一个块标记为写时复制). 提示阶段的计算只需在用户的任务输入上执行即可.

**混合解码方法.** 前面讨论的解码方法表现出不同的内存共享和访问模式. 然而, vLLM 促进了具有不同解码偏好的请求的同时处理, 这是现有系统 *无法* 高效完成的. 这是因为 vLLM 通过一个通用映射层隐藏了不同序列之间复杂的内存共享, 该层将逻辑块转换为物理块. LLM 及其执行内核对于每个序列只看到一个物理块 ID 列表, 不需要处理跨序列的共享模式. 与现有系统相比, 这种方法扩大了不同采样需求请求的批处理机会, 最终提高了系统的整体吞吐量.

### 4.5. 调度与抢占

当请求流量超过系统容量时, vLLM 必须优先处理部分请求. 在 vLLM 中, 我们对所有请求采用先到先服务 (FCFS) 调度策略, 以确保公平并防止饥饿. 当 vLLM 需要抢占请求时, 它确保最早到达的请求优先被处理, 最新的请求最先被抢占.

LLM 服务面临一个独特的挑战: LLM 的输入提示长度可能差异很大, 而生成的输出长度事先未知, 这取决于输入提示和模型本身. 随着请求数量及其输出的增加, vLLM 可能会耗尽 GPU 的物理块来存储新生成的 KV 缓存. 在这种情况下, vLLM 需要回答两个经典问题: (1) 它应该驱逐哪些块? (2) 如果再次需要, 如何恢复被驱逐的块? 通常, 驱逐策略使用启发式方法来预测哪个块在未来最晚被访问, 并驱逐该块. 由于在我们的情况下, 我们知道一个序列的所有块会一起访问, 因此我们实现了一种全有或全无的驱逐策略, 即要么驱逐序列的所有块, 要么一个都不驱逐. 另外, 一个请求中的多个序列 (例如, 一次 beam 搜索请求中的 beam 候选) 会作为一个*序列组*进行群调度. 由于这些序列之间可能存在内存共享, 一个序列组内的序列总是会被一起抢占或重新调度. 为了回答第二个问题, 即如何恢复被驱逐的块, 我们考虑了两种技术:

- **交换.** 这是大多数虚拟内存实现中使用的经典技术, 它将被驱逐的页面复制到磁盘上的交换空间. 在我们的情况下, 我们将被驱逐的块复制到 CPU 内存中. 如 [图 4](#figure-04) 所示, 除了 GPU 块分配器之外, vLLM 还包括一个 CPU 块分配器, 用于管理交换到 CPU RAM 的物理块. 当 vLLM 用尽用于新 token 的空闲物理块时, 它会选择一组序列进行驱逐, 并将其 KV 缓存转移到 CPU. 一旦它抢占序列并驱逐其块, vLLM 就会停止接受新请求, 直到所有被抢占的序列完成. 一旦请求完成, 其块将从内存中释放, 被抢占序列的块将被带回以继续该序列的处理. 采用此设计, 交换到 CPU RAM 的块数量从不超过 GPU RAM 中的物理块总数, 因此 CPU RAM 上的交换空间受 KV 缓存分配的 GPU 内存限制.
- **重新计算.** 当被抢占的序列被重新调度时, vLLM 重新计算其 KV 缓存. 重新计算的延迟可能明显低于原始延迟, 因为解码时生成的令牌可以与原始用户提示拼接成新的提示, 所有位置的 KV 缓存可以在一次提示阶段迭代中生成.

交换和重新计算的性能取决于 CPU 内存与 GPU 显存之间的带宽以及 GPU 的计算能力. 我们在 §[7.3](#S7.SS3) 中检查了交换和重新计算的速度.

### 4.6. 分布式执行

许多大型语言模型的参数规模超过单个 GPU 的容量 [Browne20, Chowdb22]. 因此, 有必要将它们分布到多个 GPU 上, 并以模型并行的方式执行 [Zheng22, Ref23]. 这就需要一个能够处理分布式内存的内存管理器. vLLM 通过在 Transformer 上支持广泛使用的 Megatron-LM 风格张量模型并行策略, 在分布式环境中表现出色 [Shoeyc19]. 该策略遵循 SPMD (单程序多数据) 执行计划, 其中线性层被分区以进行块矩阵乘法, GPU 通过全规约操作不断同步中间结果. 具体来说, 注意力操作是在注意力头维度上拆分的, 每个 SPMD 进程负责多头注意力中的一部分注意力头.

我们观察到, 即使在模型并行执行的情况下, 每个模型分片仍然处理相同的一组输入标记, 因此需要为相同的位置维护 KV 缓存. 因此, vLLM 在集中式调度器中具有单一的 KV 缓存管理器, 如 [图 4](#figure-04) 所示. 不同的 GPU 工作器共享该管理器, 以及从逻辑块到物理块的映射. 这个通用映射允许 GPU 工作器使用调度器为每个输入请求提供的物理块执行模型. 虽然每个 GPU 工作器具有相同的物理块 ID, 但每个工作器只存储其对应注意力头的一部分 KV 缓存.

在每一步中, 调度器首先为批次中的每个请求准备包含输入标记 ID 的消息, 以及每个请求的块表. 接着, 调度器将该控制消息广播给 GPU 工作器. 然后, GPU 工作器开始使用输入标记 ID 执行模型. 在注意力层中, GPU 工作器根据控制消息中的块表读取 KV 缓存. 在执行期间, GPU 工作器使用全规约 (all-reduce) 通信原语同步中间结果, 而无需调度器的协调, 如 [Shoeyc19] 所示. 最终, GPU 工作器将本次迭代采样的标记发送回调度器. 总之, GPU 工作器在内存管理上无需同步, 因为它们只需要在每次解码迭代开始时随步骤输入一并接收所有内存管理信息.

vLLM 是一个端到端的服务系统, 具有 FastAPI [FastAP23] 前端和基于 GPU 的推理引擎. 前端扩展了 OpenAI API [OpenAI20] 接口, 允许用户为每个请求自定义采样参数, 如最大序列长度和束宽 $k$. vLLM 引擎使用 8500 行 Python 代码和 2000 行 C/CUDA 代码编写. 我们在 Python 中开发调度器和块管理器等控制相关组件, 同时为关键操作如 PagedAttention 开发自定义 CUDA 内核. 对于模型执行器, 我们使用 PyTorch [Paszka19] 和 Transformers [Wolfa20] 实现了流行的大语言模型, 如 GPT [Browne20], OPT [Zhangb22] 和 LLaMA [Touvra23]. 我们使用 NCCL [NVIDIa23] 进行分布式 GPU 工作器之间的张量通信.

### 5.1. 内核级优化

PagedAttention 引入的内存访问模式无法被现有系统高效支持, 因此我们开发了多个 GPU 内核进行优化:

1. **融合重塑和块写入.** 在每层 Transformer 中, 新的 KV 缓存被分割成块, 重塑为针对块读取优化的内存布局, 然后保存到块表指定的位置. 为了减少内核启动开销, 我们将这些操作融合到单个内核中.
2. **融合块读取和注意力.** 我们调整 FasterTransformer [NVIDIA23] 中的注意力内核, 根据块表读取 KV 缓存并实时执行注意力操作. 为了确保合并内存访问, 我们为每个块分配一个 GPU warp 进行读取, 并增加了对同一请求批次中可变序列长度的支持.
3. **融合块复制.** 写时复制机制发出的块复制操作可能作用于不连续的块. 如果使用 `cudaMemcpyAsync` API, 可能会产生大量小数据移动调用. 为减轻开销, 我们实现了一个内核, 将不同块的复制操作合并到一次内核启动中执行.

### 5.2. 支持各种解码算法

vLLM 使用三个基本操作实现各种解码算法:

- `fork`: 从现有序列创建新序列.
- `append`: 将新标记追加到序列中.
- `free`: 删除序列.

例如, 在并行采样中, vLLM 使用 `fork` 从单个输入序列创建多个输出序列, 每次迭代时用 `append` 添加新标记, 再用 `free` 删除满足停止条件的序列. vLLM 也将这套操作用于束搜索和前缀共享. 未来的解码算法同样可以通过组合这些操作得到支持.

## 6\. 评估

在本节中, 我们评估 vLLM 在各种工作负载下的性能.

### 6.1. 实验设置

**模型和服务器配置.** 我们使用带有 13B, 66B 和 175B 参数的 OPT [Zhangb22] 模型, 以及 13B 参数的 LLaMA [Touvra23] 进行评估. 13B 和 66B 是 LLM 的常见大小, 如 LLM 排行榜所示 [ORG23], 而 175B 是著名 GPT-3 [Browne20] 模型的规模. 在我们的所有实验中, 我们在 Google 云平台上使用配备 NVIDIA A100 GPU 的 A2 实例. 详细的模型大小和服务器配置如 [表 1](#table-01) 所示.

**工作负载.** 我们基于 ShareGPT [Team23] 和 Alpaca [Taori23] 数据集合成工作负载, 这些数据集包含真实 LLM 服务的输入和输出文本. ShareGPT 数据集是用户与 ChatGPT [OpenAI22] 分享对话的集合. Alpaca 数据集是由 GPT-3.5 使用 self-instruct [Wangb22] 生成的指令数据集. 我们对数据集进行分词, 并使用其输入和输出长度来合成客户端请求. 如 [图 11](#figure-11) 所示, ShareGPT 数据集的输入提示平均比 Alpaca 数据集长 8.4$\times$, 输出平均长 5.8$\times$, 且方差更高. 由于这些数据集不包含时间戳, 我们使用不同请求率的泊松分布生成请求到达时间.

**基线 1: FasterTransformer.** FasterTransformer [NVIDIA23] 是一个高度优化以降低延迟的分布式推理引擎. 由于 FasterTransformer 没有自己的调度器, 我们实现了一个带有动态批处理机制的自定义调度器, 类似于 Triton [Serveb00] 等现有的服务系统. 具体来说, 我们根据 GPU 内存容量, 在每次实验中设置尽可能大的最大批量大小 $B$. 调度器将获取最多 $B$ 个最早到达的请求, 并将批次发送到 FasterTransformer 进行处理.

- **Orca (Oracle).** 假设系统已知请求实际生成的输出长度. 这代表 Orca 的性能上限, 实际中无法实现.
- **Orca (Pow2).** 假设系统按 2 的幂预留输出空间. 例如, 真实输出长度为 25 时, 系统会预留 32 个位置.

**关键指标.** 我们关注服务吞吐量. 具体来说, 使用不同请求速率的工作负载, 我们测量系统的规范化延迟, 即每个请求的端到端延迟的平均值除以其输出长度, 如 Orca [Refd22] 所示. 高吞吐量的服务系统应在高请求速率下保持低规范化延迟. 在大多数实验中, 我们使用 1 小时的跟踪评估系统. 由于成本限制, OPT-175B 模型使用 15 分钟的跟踪.

### 6.2. 基本采样

### 6.5. 聊天机器人

聊天机器人 [OpenAI22, Google23, Chiang23] 是大型语言模型 (LLMs) 最重要的应用之一. 为了实现聊天机器人, 我们通过将聊天历史记录和最后的用户查询拼接成提示, 让模型生成响应. 我们使用 ShareGPT 数据集来综合聊天历史记录和用户查询. 由于 OPT-13B 模型的上下文长度有限, 我们将提示剪切到最后的 1024 个标记, 并让模型生成最多 1024 个标记. 我们不会在不同对话轮次之间存储 KV 缓存, 因为这样做会占用对话轮次之间其他请求的空间.

## 7. 消融研究

在本节中, 我们研究 vLLM 的各个方面, 并通过消融实验评估我们的设计选择.

### 7.1. 内核微基准

在 PagedAttention 中的动态块映射会影响涉及存储的 KV 缓存的 GPU 操作的性能, 即块读/写和注意力操作. 与现有系统相比, 我们的 GPU 内核 (§[5](#S5)) 涉及访问块表, 执行额外分支以及处理可变序列长度的额外开销. 如 [图 18(a)](#figure-18) 所示, 这导致注意力内核的延迟比高度优化的 FasterTransformer 实现高出 20–26%. 我们认为这种开销很小, 因为它仅影响注意力操作符, 而不影响模型中的其他操作符, 例如 Linear. 尽管有开销, PagedAttention 仍使 vLLM 在端到端性能上明显优于 FasterTransformer (§[6](#S6)).

### 7.2. 块大小的影响

块大小的选择会对 vLLM 的性能产生重大影响. 如果块大小过小, vLLM 可能无法充分利用 GPU 并行性来读取和处理 KV 缓存. 如果块大小过大, 内部碎片会增加, 共享的概率会降低.

在 [图 18(b)](#figure-18) 中, 我们评估了不同块大小下 vLLM 的性能, 使用 ShareGPT 和 Alpaca 的轨迹, 在固定请求率下进行基本采样. 在 ShareGPT 轨迹中, 块大小从 16 到 128 表现最佳. 在 Alpaca 轨迹中, 尽管块大小 16 和 32 表现良好, 但较大的块大小会显著降低性能, 因为序列变得比块大小还要短. 在实际操作中, 我们发现块大小 16 在大多数工作负载中既足够大以高效利用 GPU, 又足够小以避免显著的内部碎片. 因此, vLLM 将其默认块大小设置为 16.

### 7.3. 比较重新计算与交换

vLLM 支持重新计算和交换两种恢复机制. 为了理解这两种方法之间的权衡, 我们评估了它们的端到端性能, 并对其开销进行了微基准测试, 如 [图 19](#figure-19) 所示. 我们的结果显示, 在小块尺寸下, 交换会产生过高的开销. 这是因为小块尺寸通常会导致 CPU 和 GPU 之间进行大量的小数据传输, 从而限制了有效的 PCIe 带宽. 相比之下, 重新计算的开销在不同块尺寸下保持恒定, 因为重新计算不使用 KV 块. 因此, 当块尺寸较小时, 重新计算更为高效, 而当块尺寸较大时, 交换更为高效, 尽管重新计算的开销从未超过交换延迟的 20%. 对于从 16 到 64 的中等块尺寸, 这两种方法表现出相当的端到端性能.

## 8\. 讨论

**将虚拟内存和分页技术应用于其他 GPU 工作负载.** 虚拟内存和分页的理念在管理 LLM 服务中的 KV 缓存时非常有效, 因为该工作负载需要动态内存分配 (输出长度事先未知), 并且其性能受限于 GPU 内存容量. 但这并不适用于所有 GPU 工作负载. 例如, 在 DNN 训练中, 张量形状通常是静态的, 因此内存分配可以提前优化. 在提供非 LLM 的 DNN 服务时, 内存效率的提升也可能不会带来性能改进, 因为其性能主要受计算限制. 在这种情况下, 引入 vLLM 的技术可能会因内存间接访问和非连续块内存的额外开销而降低性能. vLLM 的技术更适合具有类似 LLM 服务属性的工作负载.

**针对 LLM 优化虚拟内存和分页.** vLLM 利用应用特定的语义, 重新解释并增强了虚拟内存和分页的概念. 例如, vLLM 的全有或全无交换策略利用了处理请求时所有对应令牌状态必须存储在 GPU 内存中的事实. 另一个例子是通过重新计算恢复被淘汰的块, 这在操作系统中不可行. vLLM 还将用于内存访问的 GPU 内核与其他操作 (如注意力) 的内核融合, 减轻分页所带来的间接内存访问开销.

## 9\. 相关工作

**通用模型服务系统.** 近年来, 模型服务成为一个活跃的研究领域, 已有众多系统被提出以应对深度学习模型部署的各个方面. Clipper [Cranks17], TensorFlow Serving [Olston17], Nexus [Shen19], InferLine [Cranks20] 和 Clockwork [Gujara20] 是一些早期的通用模型服务系统. 他们研究批量处理, 缓存, 放置和调度, 以服务单一或多个模型. 最近, DVABatch [Cui22] 引入了多项多出口批处理. REEF [Han22] 和 Shepherd [Zhang23] 提议优先服务. AlpaServe [Ref23] 利用模型并行性进行统计复用. 然而, 这些通用系统未能考虑 LLM 推断的自回归性质和标记状态, 导致错失优化机会.

**专用于 Transformer 的服务系统.** 已经有许多针对 Transformer 架构开发的服务系统. 这些系统利用 GPU 内核优化 [Wang21, Aminab22, NVIDIA23, Refc20], 先进的批处理机制 [Fang21, Refd22], 模型并行 [Popea22, Refd22, Aminab22] 和参数共享 [Zhou22] 来实现高效服务. 其中, Orca [Refd22] 与我们的方法最相关.

**与 Orca 的比较.** Orca [Refd22] 的迭代级调度和 vLLM 中的 PagedAttention 是互补技术: 两个系统都旨在提高 GPU 利用率和 LLM 服务吞吐量, 但 Orca 通过调度和交错请求来让更多请求并行处理, vLLM 则提高内存利用率, 让更多请求的工作集进入内存. 通过减少内存碎片并实现共享, vLLM 可以在一个批次中并行运行更多请求, 相对于 Orca 实现 2-4$\times$ 加速. Orca 的细粒度调度和请求交错也会增加内存管理难度, 因而需要 vLLM 提出的技术.

**内存优化.** 加速器的计算能力与内存容量之间日益扩大的差距导致内存成为训练和推理的瓶颈. 为减少训练的峰值内存, 已经使用了交换 [Huang20, Wangb18, Rena21], 重计算 [Chena16, Jain20] 及其组合 [Patil22]. FlexGen [Sheng23] 研究了如何在 GPU 内存有限的情况下交换权重和 token 状态以进行 LLM 推理, 但它并未针对在线服务环境. OLLA [Steine22] 优化了张量的生命周期和位置以减少碎片, 但它没有进行细粒度块级管理或在线服务. FlashAttention [Daoc22] 通过切片和内核优化来减少注意力计算的峰值内存并降低 I/O 成本. 本文在在线服务的背景下引入了块级内存管理的新思路.

## 10\. 结论

本文提出了 PagedAttention, 一种允许注意力键值存储在非连续分页内存中的新型注意力算法, 并展示了 vLLM, 一种通过 PagedAttention 实现高效内存管理的高吞吐量 LLM 服务系统. 受操作系统的启发, 我们展示了如何将诸如虚拟内存和写时复制等已建立的技术适配于高效管理 KV 缓存并处理 LLM 服务中的各种解码算法. 我们的实验表明, vLLM 相较于现有最先进系统实现了 2-4$\times$ 倍的吞吐量提升.
