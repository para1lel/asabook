## 摘要

大语言模型 (LLM) 的高吞吐量服务需要一次批处理足够多的请求. 但现有系统很难做到这一点: 每个请求的键值缓存 (KV cache) 占用大量内存, 而且会动态增长和收缩. 如果管理效率不高, 内存会因碎片和重复副本而大量浪费, 限制批大小. 为此, 我们提出 PagedAttention, 一种借鉴操作系统经典虚拟内存和分页技术的注意力算法. 在此基础上, 我们构建了 LLM 服务系统 vLLM. 它能做到两点: (1) KV 缓存内存接近零浪费; (2) 在请求内部及请求之间灵活共享 KV 缓存, 进一步减少内存占用. 评估结果表明, 在延迟相当的情况下, vLLM 的吞吐量是 FasterTransformer、Orca 等先进系统的 2-4 倍. 序列越长、模型越大、解码算法越复杂, 提升越明显. vLLM 的源代码已在 [GitHub](https://github.com/vllm-project/vllm) 公开.

## 1\. 引言

GPT [Ope23b, Bro20c]、PaLM [Cho22a] 等大型语言模型 (*LLM*) 催生了编程助手 [Git21a, Che21] 和通用聊天机器人 [Sch22, Bar23] 等应用, 并开始深刻影响我们的工作和日常生活. 许多云服务商 [Ope20, Ser23a] 正竞相以托管服务的形式提供这些应用. 然而, 运行这类应用成本很高, 需要大量 GPU 等硬件加速器. 据近期估算, 处理一次 LLM 请求的成本可能是传统关键词查询 [Reu23a] 的 10 倍. 面对这样的成本, *LLM 服务* 系统需要提高吞吐量, 进而降低单次请求的成本.

LLM 的核心是自回归 Transformer 模型 [Vas17]. 模型根据输入 (提示) 和此前已经生成的输出 token 序列, *一次生成一个* token. 每个请求都要重复这一昂贵过程, 直至模型输出终止 token. 顺序生成使工作负载受内存制约, 无法充分利用 GPU 算力, 因而限制了服务吞吐量.

<span id="figure-01"></span>

![现有系统与 vLLM 的内存布局和吞吐量对比](./vllm/figure-01.png)

**图 1.** *左:* 在 NVIDIA A100 上服务 13B 参数 LLM 时的内存布局. 参数 (灰色) 在整个服务期间常驻 GPU 内存. KV 缓存内存 (红色) 随请求分配和释放. 少量内存 (黄色) 临时用于激活值. *右:* vLLM 缓和了现有系统 [Fas21, Yu22a] 中 KV 缓存内存随批大小急剧增长的问题, 明显提高了服务吞吐量.

将多个请求组成批次可以提高吞吐量, 但要扩大批次, 就必须高效管理每个请求占用的内存. [图 1](#figure-01) (左) 展示了一台配备 40 GB 内存的 NVIDIA A100 GPU 在运行 13B 参数 LLM 时的内存分布. 约 65% 的内存分配给模型权重, 这些权重在服务期间保持不变. 另有约 30% 用于存储请求的动态状态. 对 Transformer 而言, 这些状态是注意力机制使用的键和值张量, 通常称为 *KV 缓存* [Pop22a]. 它们记录先前 token 的上下文, 供模型依次生成新的输出 token. 剩余的一小部分内存用于其他数据, 包括激活值, 即运行 LLM 时产生的临时张量. 模型权重固定不变, 激活值占用的 GPU 内存又很少, 因此 KV 缓存的管理方式决定了批次最多能容纳多少请求. 如 [图 1](#figure-01) (右) 所示, 管理效率低下会严重限制批大小, 进而限制 LLM 的吞吐量.

我们发现, 现有 LLM 服务系统 [Yu22a, Fas21] 无法高效管理 KV 缓存. 主要原因是, 大多数深度学习框架 [Pas19, Ols17] 要求张量存放在连续内存中, 这些系统也就把每个请求的 KV 缓存存入一段连续空间. KV 缓存却不同于传统深度学习负载中的张量: 它会随新 token 的生成动态增长和收缩, 生命周期和最终长度也无法预先得知. 这使现有方案在以下两方面效率很低:

<span id="figure-02"></span>

![参见图注](./vllm/figure-02.png)

**图 2.** 在 §[6.2](#S6.SS2) 中实验期间, 不同 LLM 服务系统的平均内存浪费百分比.

第一, 现有系统 [Yu22a, Fas21] 存在内部和外部内存碎片. 为了在连续空间中存储请求的 KV 缓存, 它们会按请求的最大长度 (例如 2048 个 token) *预分配*一段连续内存. 请求的实际长度可能远小于最大长度 (例如 [图 11](#figure-11)), 因而产生严重的内部碎片. 即使实际长度预先已知, 这种分配方式仍然低效: 整段内存在请求的整个生命周期内都被占用, 其他较短的请求无法利用其中尚未使用的部分. 各请求预分配的大小还可能不同, 因而造成严重的外部碎片. [图 2](#figure-02) 的分析结果显示, 现有系统只有 20.4%-38.2% 的 KV 缓存内存真正存储了 token 状态.

第二, 现有系统无法利用内存共享. LLM 服务常用并行采样和束搜索等高级解码算法, 为每个请求生成多个输出. 此时一个请求包含多个序列, 它们本可共享部分 KV 缓存. 但现有系统把各序列的 KV 缓存分别存入独立的连续空间, 无法实现这种共享.

为解决这些问题, 我们提出注意力算法 *PagedAttention*. 它借鉴了操作系统 (OS) 处理内存碎片和共享的办法: *分页虚拟内存*. PagedAttention 把请求的 KV 缓存划分为块, 每块容纳固定数量 token 的注意力键和值. 这些块无须连续存储. 于是, KV 缓存可以像操作系统的虚拟内存一样灵活管理: 块相当于页, token 相当于字节, 请求相当于进程. 较小且按需分配的块减少了内部碎片; 所有块大小相同, 消除了外部碎片; 块还可以在同一请求的不同序列之间, 乃至不同请求之间共享.

我们基于 PagedAttention 构建了高吞吐量分布式 LLM 服务引擎 *vLLM*, 将 KV 缓存内存的浪费降至近乎为零. vLLM 采用与 PagedAttention 协同设计的块级内存管理和抢占式请求调度. 它支持 GPT [Bro20c]、OPT [Zha22]、LLaMA [Tou23] 等不同规模的常见 LLM, 包括单个 GPU 无法容纳的模型. 在多种模型和工作负载上的评估表明, vLLM 完全不影响模型精度, 吞吐量却能达到最先进系统 [Yu22a, Fas21] 的 2-4$\times$. 序列越长、模型越大、解码算法越复杂, 提升越明显 (§[4.3](#S4.SS3)). 本文的贡献如下:

- 我们识别了 LLM 服务中内存分配的挑战, 并量化了这些挑战对服务性能的影响.
- 我们提出了 PagedAttention, 一种在非连续分页内存中操作 KV 缓存的注意力算法, 受操作系统中的虚拟内存和分页机制启发.
- 我们设计并实现了 vLLM, 一个构建在 PagedAttention 之上的分布式 LLM 服务引擎.
- 我们在不同场景下评估 vLLM, 结果表明它大幅超过 FasterTransformer [Fas21] 和 Orca [Yu22a] 等既有先进方案.

## 2\. 背景

本节介绍典型 LLM 的生成和服务过程, 以及 LLM 服务中使用的迭代级调度.

### 2.1. 基于 Transformer 的大型语言模型

语言建模的任务是对 token 序列 $(x_{1},\ldots,x_{n})$ 的概率建模. 语言天然具有先后顺序, 因而通常把整个序列的联合概率分解为条件概率的乘积 (又称*自回归分解* [Ben00]):

<span id="S2.E1"></span>

$$
P(x)=P(x_{1})\cdot P(x_{2}\mid x_{1})\cdots P(x_{n}\mid x_{1},\ldots,x_{n-1}).
$$

Transformer [Vas17] 已成为大规模建模上述概率的事实标准架构. 基于 Transformer 的语言模型最重要的组成部分是*自注意力层*. 对于输入隐藏状态序列 $(x_{1},\ldots,x_{n})\in\mathbb{R}^{n\times d}$, 自注意力层首先对每个位置 $i$ 做线性变换, 得到查询、键和值向量:

<span id="S2.E2"></span>

$$
q_{i}=W_{q}x_{i},\ k_{i}=W_{k}x_{i},\ v_{i}=W_{v}x_{i}.
$$

然后, 自注意力层将某一位置的查询向量与此前所有键向量相乘, 得到注意力分数 $a_{ij}$; 输出 $o_{i}$ 则是值向量的加权平均:

<span id="S2.E3"></span>

$$
a_{ij}=\frac{\exp(q_{i}^{\top}k_{j}/\sqrt{d})}{\sum_{t=1}^{i}\exp(q_{i}^{\top}k_{t}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{i}a_{ij}v_{j}.
$$

除了 [公式 3](#S2.E3) 中的计算外, Transformer 模型的其他组件, 包括嵌入层、前馈层、层归一化 [Ba16]、残差连接 [He16]、输出 logit 计算, 以及 [公式 2](#S2.E2) 中查询、键和值的变换, 都以 $y_{i}=f(x_{i})$ 的形式逐位置独立应用.

### 2.2. LLM 服务与自回归生成

训练完成后, LLM 通常部署为条件生成服务 (例如补全 API [Ope20] 或聊天机器人 [Sch22, Bar23]). LLM 服务的请求包含一列*输入提示* token $(x_{1},\ldots,x_{n})$, 服务根据 [公式 1](#S2.E1) 生成一列输出 token $(x_{n+1},\ldots,x_{n+T})$. 提示与输出拼接后称为*序列*.

由于 [公式 1](#S2.E1) 中的分解, LLM 只能逐个采样并生成新 token. 每个新 token 的生成依赖该序列中所有*此前的 token*, 尤其是它们的键和值向量. 在这个顺序生成过程中, 已有 token 的键和值向量通常会缓存起来, 用于生成后续 token, 这就是 *KV 缓存*. 一个 token 的 KV 缓存取决于它之前的所有 token. 因此, 同一个 token 出现在序列的不同位置时, 其 KV 缓存也不同.

给定一个请求提示, LLM 服务中的生成计算可以分解为两个阶段:

**提示阶段**以完整的用户提示 $(x_{1},\ldots,x_{n})$ 为输入, 计算第一个新 token 的概率 $P(x_{n+1}\mid x_{1},\ldots,x_{n})$. 这一过程还会生成键向量 $k_{1},\ldots,k_{n}$ 和值向量 $v_{1},\ldots,v_{n}$. 提示 token $x_{1},\ldots,x_{n}$ 均已知, 因此提示阶段可以通过矩阵-矩阵乘法并行计算, 高效利用 GPU 的并行能力.

**自回归生成阶段**按顺序生成其余新 token. 在第 $t$ 次迭代中, 模型以 token $x_{n+t}$ 为输入, 根据键向量 $k_{1},\ldots,k_{n+t}$ 和值向量 $v_{1},\ldots,v_{n+t}$ 计算概率 $P(x_{n+t+1}\mid x_{1},\ldots,x_{n+t})$. 位置 $1$ 到 $n+t-1$ 的键值向量已在此前的迭代中缓存, 本轮只计算新的键向量 $k_{n+t}$ 和值向量 $v_{n+t}$. 当序列达到最大长度 (由用户指定或受 LLM 限制), 或模型输出序列结束 token `<eos>` 时, 该阶段结束. 各轮计算存在数据依赖, 无法并行, 且通常采用效率较低的矩阵-向量乘法. 所以这一阶段无法充分利用 GPU 算力, 工作负载受内存制约, 也是单个请求延迟的主要来源.

![参见图注](./vllm/figure-03.png)

### 2.3. LLM 的批处理技术

把多个请求组成批次可以提高 LLM 服务的计算利用率. 这些请求共享同一组模型权重, 因而权重搬运开销可以分摊到整个批次; 批次足够大时, 这部分开销相对于计算开销便可忽略. 但 LLM 服务的请求并不容易批处理, 原因有二. 第一, 请求到达时间不同. 简单的批处理策略要么让先到的请求等待后到的请求, 要么让新请求等到旧请求完成, 两种做法都会造成较长的排队延迟. 第二, 请求的输入和输出长度可能相差很大 ([图 11](#figure-11)). 直接把各请求的输入和输出填充到相同长度, 会浪费 GPU 算力和内存.

针对这一问题, 研究者提出了 cellular batching [Gao18] 和迭代级调度 [Yu22a] 等细粒度批处理机制. 传统方法以请求为单位, 这些机制则以迭代为单位. 每轮迭代结束后, 已完成的请求从批次中移除, 再加入新请求. 新请求只需等待一轮迭代, 无须等整个批次结束. 配合专用 GPU 内核, 输入和输出也不再需要填充. 排队延迟和填充浪费随之减少, LLM 服务的吞吐量得以提高.

## 3\. LLM 服务中的内存挑战

尽管细粒度批处理减少了计算浪费, 也能更灵活地组织请求, 可同时批处理的请求数仍受 GPU 内存容量限制, 尤其取决于 KV 缓存可用空间. 换言之, 服务系统的吞吐量受内存制约. 要突破这一限制, 内存管理需要解决以下问题:

**大型 KV 缓存.** KV 缓存会随请求数迅速增长. 以 13B 参数的 OPT 模型 [Zha22] 为例, 单个 token 的 KV 缓存占用 800 KB, 即 $2$ (键和值向量) $\times\ 5120$ (隐藏状态大小) $\times\ 40$ (层数) $\times\ 2$ (每个 FP16 的字节数). OPT 最多可生成 2048 个 token, 因而一个请求的 KV 缓存可占 1.6 GB. 当前 GPU 的内存容量只有数十 GB. 即便全部用于 KV 缓存, 也只能容纳几十个请求. 内存管理效率低下还会进一步压缩批大小, 如 [图 2](#figure-02) 所示. 当前 GPU 算力的增长也快于内存容量 [Gho21]: 从 NVIDIA A100 到 H100, FLOPS 增加到两倍以上, GPU 内存上限却仍是 80 GB. 因此, 内存会成为越来越明显的瓶颈.

**复杂解码算法.** LLM 服务允许用户选择多种解码算法, 各种算法给内存管理带来的难度不同. 例如, 用户可能对同一个输入提示请求多个随机样本, 这在代码建议 [Git21a] 中很常见. 此时提示部分的 KV 缓存可以共享; 在我们的实验中, 它占 KV 缓存总内存的 12% (§[6.3](#S6.SS3)). 但自回归生成阶段的 KV 缓存不能共享, 因为不同样本的结果及其对上下文和位置的依赖各不相同. KV 缓存能共享多少取决于具体解码算法. 对束搜索 [Sut14] 等更复杂的算法, 不同候选束可以共享更多 KV 缓存 (最多节省 55% 内存, 见 §[6.3](#S6.SS3)), 而共享模式会随解码过程不断变化.

**对未知输入和输出长度的调度.** LLM 服务请求的输入和输出长度并不固定, 内存管理系统必须适应差异很大的提示长度. 解码过程中, 请求输出不断增长, KV 缓存随之扩张, 可能耗尽新请求或已有提示继续生成所需的内存. 系统必须决定如何调度, 例如删除部分请求的 KV 缓存, 或将其换出 GPU 内存.

### 3.1. 现有系统中的内存管理

由于当前大多数深度学习框架中的算子 [Pas19, Ols17] 要求张量存储在连续内存中, 以往的 LLM 服务系统 [Yu22a, Fas21] 也把一个请求在不同位置上的 KV 缓存存为连续张量. LLM 的输出长度无法预测, 因此这些系统会按请求可能达到的最大序列长度静态分配内存, 不考虑实际输入长度或最终输出长度.

[图 3](#figure-03) 展示了两个请求: 请求 A 的最大序列长度为 2048, 请求 B 为 512. 现有系统的内存块预分配有三类主要浪费: *为未来 token 预留*的槽位、*按可能的最大序列长度过量分配造成的内部碎片*, 以及*伙伴分配器等内存分配器造成的外部碎片*. 外部碎片永远不会用于已生成的 token, 而且在请求开始处理前就能确定. 内部碎片同样不会使用, 但要等请求完成采样后才能确定. 两者都是纯粹的内存浪费. 预留空间最终会用到, 但如果整个请求期间一直占用这些空间, 尤其在预留量很大时, 便会挤占原本可用于其他请求的内存. [图 2](#figure-02) 给出了实验中的平均内存浪费比例; 现有系统的实际有效内存最低只有 20.4%.

内存紧缩 [Wan22d] 虽可用于缓解碎片, 但 KV 缓存十分庞大, 在性能敏感的 LLM 服务系统中并不现实. 即使采用内存紧缩, 为每个请求预分配的连续空间仍会妨碍现有内存管理系统针对不同解码算法共享内存.

## 4\. 方法

<span id="figure-04"></span>

![参见图注](./vllm/figure-04.png)

**图 4.** vLLM 系统概览.

为解决 §[3](#S3) 中的问题, 我们开发了新的注意力算法 *PagedAttention*, 并构建了 LLM 服务引擎 *vLLM*. vLLM 的架构见 [图 4](#figure-04). 它采用集中式调度器协调分布式 GPU 工作进程, *KV 缓存管理器*则借助 PagedAttention, 以分页方式管理 KV 缓存. 具体而言, KV 缓存管理器通过集中式调度器下发的指令, 管理 GPU 工作进程上的物理 KV 缓存内存.

下文先在 §[4.1](#S4.SS1) 介绍 PagedAttention 算法, 再在 §[4.2](#S4.SS2) 给出 KV 缓存管理器的设计, 并于 §[4.3](#S4.SS3) 说明该设计如何支持 PagedAttention. 随后, §[4.4](#S4.SS4) 说明它如何管理各种解码方法的内存, §[4.5](#S4.SS5) 讨论可变长度的输入和输出序列. 最后, §[4.6](#S4.SS6) 介绍 vLLM 在分布式环境中的运行方式.

### 4.1. PagedAttention

为解决 §[3](#S3) 中的内存问题, 我们引入 *PagedAttention*: 一种借鉴操作系统经典*分页*思想 [Kil62] 的注意力算法. 与传统注意力算法不同, PagedAttention 允许将连续的键和值存入非连续内存空间. 它把每个序列的 KV 缓存划分为 *KV 块*. 每个块包含固定数量 token 的键和值向量 [+kv-block-layout], 这个数量称为 *KV 块大小* ($B$). 记键块为 $K_{j}=(k_{(j-1)B+1},\ldots,k_{jB})$, 值块为 $V_{j}=(v_{(j-1)B+1},\ldots,v_{jB})$. [公式 3](#S2.E3) 中的注意力计算可以改写为以下块级计算:

<span id="S4.E4"></span>

$$
A_{ij}=\frac{\exp(q_{i}^{\top}K_{j}/\sqrt{d})}{\sum_{t=1}^{\lceil i/B\rceil}\exp(q_{i}^{\top}K_{t}\mathbf{1}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{\lceil i/B\rceil}V_{j}A_{ij}^{\top},
$$

其中 $A_{ij}=(a_{i,(j-1)B+1},\ldots,a_{i,jB})$ 是第 $j$ 个 KV 块的注意力分数行向量.

注意力计算时, PagedAttention 内核分别定位并读取不同的 KV 块. [图 5](#figure-05) 给出了一个例子: 键和值向量分布在三个块中, 这些块在物理内存中并不连续. 每一步, 内核将查询 token "*forth*" 的查询向量 $q_{i}$ 与一个块中的键向量 $K_{j}$ 相乘 (例如块 0 中 "*Four score and seven*" 的键向量), 得到注意力分数 $A_{ij}$; 随后再将 $A_{ij}$ 与该块的值向量 $V_{j}$ 相乘, 得到最终注意力输出 $o_{i}$.

总之, PagedAttention 算法允许将 KV 块存储在非连续的物理内存中, 从而在 vLLM 中实现更灵活的分页内存管理.

### 4.2. KV 缓存管理器

vLLM 内存管理器的核心思想类似于操作系统的*虚拟内存* [Kil62]. 操作系统把内存划分为固定大小的*页*, 再将用户程序的逻辑页映射到物理页. 连续的逻辑页可以对应不连续的物理页, 用户程序仍可像访问连续内存一样进行访问. 物理内存也无须全部预留, 操作系统可以按需动态分配物理页. vLLM 借用这一思路管理 LLM 服务中的 KV 缓存. PagedAttention 使我们能够像组织虚拟内存页一样, 把 KV 缓存组织为固定大小的 KV 块.

请求的 KV 缓存由一系列*逻辑 KV 块*表示. 新 token 及其 KV 缓存生成后, 这些块从左到右依次填充; 最后一个块中的空位留给后续生成. 在 GPU 工作进程上, *块引擎*分配一段连续的 GPU DRAM, 再将其划分为*物理 KV 块* (用于交换的 CPU RAM 也做同样处理, 见 §[4.5](#S4.SS5)). *KV 块管理器*还维护每个请求的*块表*, 即逻辑 KV 块与物理 KV 块之间的映射. 每个表项记录逻辑块对应的物理块和已填充位置数. 将逻辑块与物理块分离后, vLLM 可以动态扩展 KV 缓存, 无须提前为所有位置预留内存, 从而消除[图 2](#figure-02) 所示的大部分浪费.

从整体流程看, 每次解码迭代中, vLLM 先选择一组候选序列组成批次 (详见 §[4.5](#S4.SS5)), 并为新需要的逻辑块分配物理块. 随后, 它把本轮的所有输入 token 拼成一个序列, 包括提示阶段请求的所有 token, 以及生成阶段请求的最新 token, 再将该序列送入 LLM. LLM 计算时, PagedAttention 内核访问以逻辑 KV 块形式存储的已有 KV 缓存, 并把新生成的 KV 缓存写入物理块. 一个 KV 块中存放多个 token (块大小 > 1), 可让 PagedAttention 内核并行处理更多位置上的 KV 缓存, 提高硬件利用率并缩短延迟. 但块越大, 内存碎片也越多. §[7.2](#S7.SS2) 将分析块大小的影响.

随着 token 及其 KV 缓存不断生成, vLLM 会动态地为逻辑块分配新的物理块. 所有块都从左到右填充, 只有前面的块全部填满后才分配新块, 因此单个请求浪费的内存不会超过一个块. 如 [图 2](#figure-02) 所示, 这几乎用满了全部内存, 让更多请求得以进入同一批次, 从而提高吞吐量. 请求生成结束后, 它的 KV 块会被释放, 供其他请求存储 KV 缓存. [图 7](#figure-07) 展示了 vLLM 管理两个序列的例子. 两个序列的逻辑块映射到 GPU 工作进程中块引擎预留区域内的不同物理块. 相邻的逻辑块在 GPU 物理内存中无须连续, 两个序列都能充分利用物理块空间.

### 4.4. 应用到其他解码场景

§[4.3](#S4.SS3) 说明了 PagedAttention 和 vLLM 如何处理贪心解码、采样等基本算法: 输入一个用户提示, 生成一条输出序列. 许多 LLM 应用 [Git21a, Ope20] 还要求服务支持更复杂的解码方式, 其访问模式更复杂, 也有更多内存共享机会. 本节说明 vLLM 同样适用于这些场景.

**并行采样.** 在基于 LLM 的编程助手中 [Che21, Git21a], LLM 会为一个输入提示生成多个采样结果, 用户可以从中挑选最满意的一个. 此前我们默认一个请求只生成一条序列. 本文余下部分采用更一般的设定, 即一个请求生成多条序列. 并行采样中的多个样本共享同一个输入提示, 因而也能共享提示的 KV 缓存. 借助 PagedAttention 和分页内存管理, vLLM 可以直接实现这种共享, 减少内存占用.

[图 8](#figure-08) 是两个输出并行解码的示例. 两个输出共享同一提示, 所以提示阶段只需为提示状态保留一份空间. 两个序列的提示逻辑块映射到同一组物理块: 逻辑块 0 和 1 分别映射到物理块 7 和 1. 一个物理块可以映射到多个逻辑块, 因此每个物理块都有一个*引用计数*. 本例中, 物理块 7 和 1 的引用计数均为 2. 进入生成阶段后, 两个输出会采样不同的 token, 因而需要各自的 KV 缓存空间. 对于可能被多个序列修改的物理块, vLLM 实现了块级*写时复制*, 类似于操作系统虚拟内存中的做法 (例如创建子进程时). 在 [图 8](#figure-08) 中, 样本 A1 准备写入最后一个逻辑块 (逻辑块 1) 时, vLLM 发现对应物理块 1 的引用计数大于 1, 于是分配新的物理块 3, 指示块引擎复制物理块 1 的内容, 并把原块的引用计数减至 1. 此后样本 A2 写入物理块 1 时, 引用计数已经是 1, 可以直接写入新生成的 KV 缓存.

因此, 除了由写时复制管理的最后一个逻辑块, vLLM 可以让多个输出样本共享提示 KV 缓存所占的大部分空间. 样本间共享物理块可以大幅减少内存占用, 对*长输入提示*尤其有效.

**束搜索.** 在机器翻译等语言模型任务中 [Wu17], 用户期望 LLM 输出最合适的前 $k$ 个翻译. 束搜索 [Sut14] 被广泛用于从 LLM 中解码出概率最高的输出序列, 因为它降低了遍历整个样本空间的计算复杂度. 该算法用*束宽* $k$ 决定每一步保留多少个候选. 解码时, 束搜索枚举所有可能的 token 来扩展束中的每条候选序列, 用 LLM 计算各自的概率, 再从 $k\cdot|V|$ 个候选中保留概率最高的 $k$ 条, 其中 $|V|$ 是词表大小.

<span id="figure-09"></span>

![参见图注](./vllm/figure-09.png)

**图 9.** 束搜索示例.

与并行解码不同, 束搜索不仅能共享初始提示块, 还可以让不同候选共享后续块. 共享关系会随解码推进而变化, 类似于操作系统中经过多次 `fork` 形成的进程树. [图 9](#figure-09) 展示了 $k=4$ 的束搜索中 vLLM 如何管理 KV 块. 在虚线所示的迭代之前, 每条候选序列已经占用 4 个完整的逻辑块. 所有候选都共享第一个块 0 (即提示). 候选 3 从第 2 个块起便与其他候选不同. 候选 0-2 共享前 3 个块, 在第 4 个块分开. 下一轮迭代中, 概率最高的 4 条候选都来自候选 1 和 2. 原有候选 0 和 3 不再入选, 它们的逻辑块会被释放, 相应物理块的引用计数随之减少. vLLM 释放引用计数降为 0 的全部物理块 (块 2, 4, 5, 8), 再分配新物理块 (块 9-12), 存储新候选的 KV 缓存. 此时所有候选共享块 0, 1, 3; 候选 0 和 1 共享块 6, 候选 2 和 3 还共享块 7.

现有 LLM 服务系统需要在束候选之间频繁复制 KV 缓存. 以 [图 9](#figure-09) 为例, 经过虚线所示的迭代后, 候选 3 必须复制候选 2 的大部分 KV 缓存才能继续生成. vLLM 共享物理块, 因而大幅降低了这类复制开销. 不同束候选的大部分块都可以共享; 只有新 token 需要写入已有共享块时, 才像并行解码一样触发写时复制, 而且只需复制一个块.

**共享前缀.** LLM 用户通常会提供较长的任务描述, 其中包含指令和输入输出示例, 也称为*系统提示* [Ope23c]. 任务描述与实际输入拼成请求的完整提示, LLM 据此生成输出. [图 10](#figure-10) 给出了一个例子. 共享前缀还可以通过提示工程进一步调整, 以提高下游任务的准确率 [Li21, Les21].

在这类应用中, 许多用户提示具有相同前缀. LLM 服务提供商可以预先保存该前缀的 KV 缓存, 避免重复计算. 在 vLLM 中, 提供商只需为一组预定义的共享前缀保留物理块, 类似于操作系统在进程间共享库. 含共享前缀的用户提示可把逻辑块直接映射到这些缓存的物理块, 仅将最后一块标为写时复制. 提示阶段只需计算用户实际输入的部分.

![参见图注](./vllm/figure-10.png)

**混合解码方法.** 上述解码方法具有不同的内存共享和访问模式. vLLM 仍能同时处理采用不同解码设置的请求, 而现有系统*无法*高效做到这一点. 原因在于, vLLM 用一个将逻辑块转换为物理块的通用映射层, 隐藏了序列之间复杂的共享关系. 对 LLM 及其执行内核而言, 每个序列只是一列物理块 ID, 无须处理跨序列共享. 与现有系统相比, 这使采样要求不同的请求更容易组成批次, 从而提高整个系统的吞吐量.

### 4.5. 调度与抢占

当请求流量超过系统容量时, vLLM 必须优先处理部分请求. 在 vLLM 中, 我们对所有请求采用先到先服务 (FCFS) 调度策略, 以确保公平并防止饥饿. 当 vLLM 需要抢占请求时, 它确保最早到达的请求优先被处理, 最新的请求最先被抢占.

LLM 服务有一个特殊难题: 输入提示的长度差异很大, 输出长度又由提示和模型共同决定, 无法预先得知. 随着请求数和输出长度增长, vLLM 可能耗尽 GPU 物理块, 无处存放新生成的 KV 缓存. 此时要回答两个经典问题: (1) 驱逐哪些块? (2) 再次需要时, 如何恢复被驱逐的块? 常见驱逐策略用启发式方法预测未来最晚访问的块, 再将其驱逐. 在 vLLM 中, 一个序列的所有块总是一起访问, 因而可以采用全有或全无策略: 要么驱逐整条序列的所有块, 要么一个都不驱逐. 同一请求中的多条序列 (例如一次束搜索请求的候选束) 还会组成*序列组*统一调度. 组内序列可能共享内存, 所以总是一起抢占或重新调度. 对于第二个问题, 我们考虑两种恢复方式:

**交换.** 这是大多数虚拟内存实现采用的经典技术, 即把被驱逐的页复制到磁盘交换空间. 在 vLLM 中, 被驱逐的块会复制到 CPU 内存. 如 [图 4](#figure-04) 所示, 除 GPU 块分配器外, vLLM 还包含一个 CPU 块分配器, 用于管理换至 CPU RAM 的物理块. 当新 token 耗尽空闲物理块时, vLLM 会选择一组序列驱逐, 并把它们的 KV 缓存转移到 CPU. 一旦某个序列被抢占且其块被驱逐, vLLM 便暂停接收新请求, 直至所有被抢占的序列处理完毕. 请求完成后, 它占用的块会被释放, 被抢占序列的块再换回 GPU, 继续处理该序列. 在这种设计下, 换至 CPU RAM 的块数不会超过 GPU RAM 中的物理块总数, 因而 CPU RAM 的交换空间上限由分配给 KV 缓存的 GPU 内存决定.

**重新计算.** 被抢占的序列重新进入调度时, vLLM 直接重新计算其 KV 缓存. 重新计算的延迟可能远低于原始延迟, 因为解码阶段生成的 token 可以与原始用户提示拼接为新提示, 从而在一次提示阶段迭代中生成所有位置的 KV 缓存.

交换和重新计算的性能取决于 CPU 内存与 GPU 显存之间的带宽以及 GPU 的计算能力. 我们在 §[7.3](#S7.SS3) 中检查了交换和重新计算的速度.

### 4.6. 分布式执行

许多 LLM 的参数规模超过单个 GPU 的容量 [Bro20c, Cho22a], 必须拆分到多个 GPU 上以模型并行方式执行 [Zhe22, Li23j]. 相应地, 内存管理器也要支持分布式内存. vLLM 支持 Transformer 中常用的 Megatron-LM 式张量模型并行 [Sho19], 因而能够在分布式环境中运行. 该策略采用 SPMD (单程序多数据) 执行方式: 拆分线性层完成分块矩阵乘法, GPU 之间则持续通过 all-reduce 同步中间结果. 注意力算子按注意力头维度拆分, 每个 SPMD 进程负责多头注意力中的一部分头.

即使采用模型并行, 每个模型分片处理的仍是同一组输入 token, 因而需要相同位置的 KV 缓存. 所以, 如 [图 4](#figure-04) 所示, vLLM 只在集中式调度器中设置一个 KV 缓存管理器. 各 GPU 工作进程共享该管理器, 也共享逻辑块到物理块的映射. 借助这份公共映射, 工作进程可以使用调度器为各输入请求指定的物理块执行模型. 每个工作进程看到的物理块 ID 相同, 但只存储其负责的注意力头所对应的那部分 KV 缓存.

每一步开始时, 调度器先准备控制消息, 其中包含批次内各请求的输入 token ID 和块表, 再将消息广播给 GPU 工作进程. 工作进程据输入 token ID 执行模型; 到注意力层时, 按控制消息中的块表读取 KV 缓存. 执行期间, 工作进程无须调度器协调, 直接通过 all-reduce 通信原语同步中间结果 [Sho19]. 最后, 它们把本轮采样到的 token 发回调度器. 因此, GPU 工作进程不必就内存管理相互同步, 只需在每轮解码迭代开始时随输入一起接收完整的内存管理信息.

vLLM 是端到端服务系统, 包含 FastAPI [Fas23] 前端和 GPU 推理引擎. 前端扩展 OpenAI API [Ope20] 接口, 允许用户为每个请求指定最大序列长度、束宽 $k$ 等采样参数. vLLM 引擎由 8.5K 行 Python 和 2K 行 C++/CUDA 代码构成. 调度器、块管理器等控制组件用 Python 编写, PagedAttention 等关键算子则使用自定义 CUDA 内核. 模型执行器基于 PyTorch [Pas19] 和 Transformers [Wol20] 实现 GPT [Bro20c]、OPT [Zha22]、LLaMA [Tou23] 等常见 LLM. 分布式 GPU 工作进程之间的张量通信使用 NCCL [Ncc15].

### 5.1. 内核级优化

PagedAttention 引入的内存访问模式无法由现有系统高效处理, 因此我们为它开发了多个 GPU 内核. (1) *融合重排与块写入.* 在每个 Transformer 层中, 新的 KV 缓存先被划分成块, 再重排成适合块读取的内存布局, 最后保存到块表指定的位置. 为减少内核启动开销, 我们把这些操作融合到一个内核中. (2) *融合块读取与注意力计算.* 我们改造了 FasterTransformer [Fas21] 的注意力内核, 使其按照块表读取 KV 缓存并即时完成注意力计算. 为实现合并内存访问, 每个块由一个 GPU warp 读取. 该内核还支持同一请求批次中的可变序列长度. (3) *融合块复制.* 写时复制机制发出的块复制操作可能涉及不连续的块. 如果使用 `cudaMemcpyAsync` API, 就会触发大量小规模数据传输. 为降低开销, 我们实现了一个内核, 把不同块的复制操作合并到一次内核启动中.

### 5.2. 支持各种解码算法

vLLM 用三个关键方法实现各种解码算法: `fork`、`append` 和 `free`. `fork` 从现有序列创建新序列, `append` 向序列追加一个新 token, `free` 则删除序列. 例如, 并行采样先用 `fork` 从一个输入序列创建多个输出序列, 每轮迭代再用 `append` 添加新 token, 并用 `free` 删除满足停止条件的序列. vLLM 也以同样的方式实现束搜索和前缀共享. 我们认为, 组合这三个方法也能支持未来的解码算法.

## 6\. 评估

在本节中, 我们评估 vLLM 在各种工作负载下的性能.

### 6.1. 实验设置

**模型和服务器配置.** 评估采用 13B、66B 和 175B 参数的 OPT [Zha22] 模型, 以及 13B 参数的 LLaMA [Tou23]. LLM 排行榜 [Org23] 显示, 13B 和 66B 是常见规模, 175B 则与 GPT-3 [Bro20c] 的规模相同. 所有实验均在 Google Cloud Platform 的 A2 实例上运行, 实例配备 NVIDIA A100 GPU. 模型大小和服务器配置详见 [表 1](#table-01).

**工作负载.** 我们根据 ShareGPT [Sha23b] 和 Alpaca [Tao23] 数据集合成工作负载, 两者都包含来自真实 LLM 服务的输入、输出文本. ShareGPT 收集了用户分享的 ChatGPT [Sch22] 对话. Alpaca 是 GPT-3.5 通过 self-instruct [Wan22e] 生成的指令数据集. 我们先对数据集分词, 再按输入和输出长度合成客户端请求. 如 [图 11](#figure-11) 所示, ShareGPT 的输入提示平均是 Alpaca 的 8.4$\times$, 输出平均是 5.8$\times$, 方差也更大. 这两个数据集都没有时间戳, 因此我们按不同请求率的泊松分布生成请求到达时间.

**基线 1: FasterTransformer.** FasterTransformer [Fas21] 是针对低延迟高度优化的分布式推理引擎. 它没有自己的调度器, 因此我们实现了采用动态批处理机制的自定义调度器, 与 Triton [Tri18] 等现有服务系统类似. 每次实验都根据 GPU 内存容量, 将最大批大小 $B$ 设为尽可能大的值. 调度器按到达顺序取最多 $B$ 个请求, 组成批次交给 FasterTransformer 处理.

<span id="figure-14"></span>

![参见图注](./vllm/figure-14a.png)

![参见图注](./vllm/figure-14b.png)

**图 14.** 在 Alpaca 数据集上使用 OPT-13B 进行并行生成和束搜索.

**基线 2: Orca.** Orca [Yu22a] 是面向吞吐量优化的先进 LLM 服务系统. Orca 没有公开实现, 因此我们自行复现. 我们假定 Orca 使用伙伴分配算法确定 KV 缓存的存储地址, 并根据它为请求输出超额预留的空间量实现三个版本:

- **Orca (Oracle).** 假设系统预先知道请求最终会生成多长的输出. 该版本代表 Orca 在实际中无法达到的性能上限.
- **Orca (Pow2).** 假设系统为输出预留的空间最多是实际需求的 2$\times$. 例如, 真实输出长度为 25 时, 系统会预留 32 个位置.
- **Orca (Max).** 假设系统总是预留到模型的最大序列长度, 即 2048 个 token.

**主要指标.** 我们关注服务吞吐量. 对于请求速率不同的工作负载, 我们沿用 Orca [Yu22a] 的方法测量系统的归一化延迟: 将每个请求的端到端延迟除以输出长度, 再取平均值. 高吞吐量服务系统在请求速率较高时仍应保持较低的归一化延迟. 大多数实验使用 1 小时的请求轨迹; 受成本限制, OPT-175B 实验使用 15 分钟的轨迹.

### 6.2. 基本采样

我们在三个模型和两个数据集上评估 vLLM 执行基本采样 (每个请求生成一个样本) 的性能. [图 12](#figure-12) 第一行是 ShareGPT 的结果. 随着请求速率上升, 延迟起初缓慢增加, 随后陡增. 一旦请求速率超过服务系统的处理能力, 队列长度会无限增长, 请求延迟也随之增加.

在 ShareGPT 上, vLLM 保持相近延迟时可承受的请求速率是 Orca (Oracle) 的 $1.7\times$-$2.7\times$, 是 Orca (Max) 的 $2.7\times$-$8\times$. PagedAttention 能高效管理内存, 让 vLLM 在一个批次中容纳比 Orca 更多的请求. 例如, [图 13(a)](#figure-13) 显示, OPT-13B 上 vLLM 同时处理的请求数是 Orca (Oracle) 的 $2.2\times$, 是 Orca (Max) 的 $4.3\times$. 相比 FasterTransformer, vLLM 可承受的请求速率最高达到其 $22\times$, 因为 FasterTransformer 没有细粒度调度机制, 内存管理也和 Orca (Max) 一样低效.

[图 12](#figure-12) 第二行和 [图 13(b)](#figure-13) 给出了 Alpaca 上的结果, 趋势与 ShareGPT 相近. [图 12(f)](#figure-12) 是一个例外: vLLM 相比 Orca (Oracle) 和 Orca (Pow2) 的优势较小. 原因是 OPT-175B 的模型和服务器配置 ([表 1](#table-01)) 可将较大的 GPU 内存空间用于 KV 缓存, 而 Alpaca 的序列又很短. 在这种条件下, 即使内存管理效率不高, Orca (Oracle) 和 Orca (Pow2) 仍能把大量请求放进同一批次. 因而系统性能受计算而非内存制约.

### 6.5. 聊天机器人

聊天机器人 [Sch22, Bar23, Chi23] 是 LLM 最重要的应用之一. 实现时, 系统把聊天历史与用户最后一次查询拼成提示, 再让模型生成回复. 我们使用 ShareGPT 数据集合成聊天历史和用户查询. OPT-13B 的上下文长度有限, 因此提示只保留最后 1024 个 token, 模型最多生成 1024 个 token. 不同对话轮次之间不保留 KV 缓存, 否则两轮对话之间也会占用本可供其他请求使用的空间.

## 7\. 消融研究

在本节中, 我们研究 vLLM 的各个方面, 并通过消融实验评估我们的设计选择.

### 7.1. 内核微基准

PagedAttention 的动态块映射会影响读写已存 KV 缓存的 GPU 算子, 即块读写和注意力算子. 与现有系统相比, 我们的 GPU 内核 (§[5](#S5)) 为访问块表、执行额外分支和处理可变序列长度付出了额外开销. 如 [图 18(a)](#figure-18) 所示, 注意力内核的延迟因此比高度优化的 FasterTransformer 实现高 20-26%. 我们认为这部分开销不大, 因为它只影响注意力算子, 不影响 Linear 等其他模型算子. 即便如此, PagedAttention 仍使 vLLM 的端到端性能明显优于 FasterTransformer (§[6](#S6)).

### 7.2. 块大小的影响

块大小直接影响 vLLM 的性能. 块过小时, vLLM 读取和处理 KV 缓存时可能无法充分利用 GPU 的并行能力; 块过大则会增加内部碎片, 降低共享概率.

[图 18(b)](#figure-18) 使用 ShareGPT 和 Alpaca 请求轨迹, 在固定请求率下执行基本采样, 比较不同块大小时 vLLM 的性能. ShareGPT 上, 块大小为 16-128 时性能最好. Alpaca 上, 16 和 32 表现良好; 块再增大, 序列就会短于块本身, 性能明显下降. 实际使用中, 块大小 16 足以让 GPU 得到有效利用, 同时又能在大多数工作负载下避免严重的内部碎片. 因此, vLLM 默认采用 16.

### 7.3. 比较重新计算与交换

vLLM 支持重新计算和交换两种恢复机制. 为比较两者的取舍, 我们评估了端到端性能, 并对开销做了微基准测试, 结果见 [图 19](#figure-19). 块较小时, 交换开销过高. 小块会让 CPU 与 GPU 之间出现大量小规模数据传输, 限制实际 PCIe 带宽. 重新计算不使用 KV 块, 开销不随块大小变化. 因此, 小块更适合重新计算, 大块更适合交换; 不过重新计算开销从未超过交换延迟的 20%. 块大小处于 16-64 时, 两种方式的端到端性能相当.

## 8\. 讨论

**将虚拟内存和分页技术应用于其他 GPU 工作负载.** 虚拟内存和分页适合管理 LLM 服务的 KV 缓存, 因为这类工作负载需要动态分配内存 (输出长度事先未知), 性能又受 GPU 内存容量限制. 但并非所有 GPU 工作负载都有这些特点. 例如, DNN 训练中的张量形状通常固定, 可以提前优化内存分配. 对非 LLM 的 DNN 服务而言, 性能主要受计算制约, 提高内存效率未必能提升性能. 此时引入 vLLM 的技术, 反而可能因内存间接寻址和非连续块内存带来的额外开销而降低性能. 不过, 我们仍期待 vLLM 的技术用于其他具有类似性质的工作负载.

**面向 LLM 的虚拟内存与分页优化.** vLLM 利用应用自身的语义, 对虚拟内存和分页做了重新解释与扩展. 例如, 全有或全无的换出策略利用了这样一个事实: 处理请求时, 对应的全部 token 状态都必须位于 GPU 内存中. 再如, vLLM 可以通过重新计算恢复被驱逐的块, 而操作系统无法采用这种方式. 它还把内存访问 GPU 内核与注意力等其他操作的内核融合, 降低分页间接寻址的开销.

## 9\. 相关工作

**通用模型服务系统.** 近年来, 模型服务一直是活跃的研究方向, 许多系统分别处理深度学习模型部署中的不同问题. Clipper [Cra17], TensorFlow Serving [Ols17], Nexus [She19], InferLine [Cra20] 和 Clockwork [Guj20] 是较早的通用模型服务系统. 它们研究单模型或多模型服务中的批处理、缓存、放置和调度. 此后, DVABatch [Cui22] 引入多入口多出口批处理, REEF [Han22] 和 Shepherd [Zha23f] 提出服务抢占, AlpaServe [Li23j] 则利用模型并行实现统计复用. 这些通用系统没有考虑 LLM 推理的自回归特性和 token 状态, 因而错过了一些优化机会.

**专用于 Transformer 的服务系统.** 围绕 Transformer 架构已经出现许多专用服务系统. 它们通过 GPU 内核优化 [Wan21a, Ami22, Fas21, Ma20]、高级批处理机制 [Fan21, Yu22a]、模型并行 [Pop22a, Yu22a, Ami22] 和参数共享 [Zho22] 提高服务效率. 其中, Orca [Yu22a] 与本文的方法最相关.

**与 Orca 的比较.** Orca [Yu22a] 的迭代级调度和 vLLM 中的 PagedAttention 是互补技术: 两个系统都旨在提高 GPU 利用率和 LLM 服务吞吐量, 但 Orca 通过调度和交错请求来让更多请求并行处理, vLLM 则提高内存利用率, 让更多请求的工作集进入内存. 通过减少内存碎片并实现共享, vLLM 可以在一个批次中并行运行更多请求, 相对于 Orca 实现 2-4$\times$ 加速. Orca 的细粒度调度和请求交错也会增加内存管理难度, 因而需要 vLLM 提出的技术.

**内存优化.** 随着加速器算力与内存容量的差距扩大, 内存已成为训练和推理的瓶颈. 为降低训练时的内存峰值, 既有工作采用了交换 [Hua20, Wan18a, Ren21b]、重计算 [Che16, Jai19] 及两者的组合 [Pat22]. FlexGen [She23a] 研究在 GPU 内存有限时如何交换权重和 token 状态以执行 LLM 推理, 但不针对在线服务. OLLA [Ste22] 通过优化张量的生命周期和位置来减少碎片, 但没有细粒度的块级管理, 也不处理在线服务. FlashAttention [Dao22] 通过分块和内核优化, 降低注意力计算的内存峰值和 I/O 成本. 本文则把块级内存管理用于在线服务.

## 10\. 结论

本文提出 PagedAttention, 一种允许将注意力键和值存入非连续分页内存的新注意力算法; 同时给出 vLLM, 一套通过 PagedAttention 高效管理内存的高吞吐量 LLM 服务系统. 借鉴操作系统, 我们说明了如何把虚拟内存、写时复制等成熟技术用于管理 KV 缓存, 并支持 LLM 服务中的多种解码算法. 实验表明, vLLM 的吞吐量是现有先进系统的 2-4 倍.
