## 摘要

过去一年, 大型语言模型 (LLM) 越来越普及. 它们前所未有的规模和高昂硬件成本阻碍了进一步推广, 因此需要更高效的硬件设计. 仅仅运行 LLM 推理就需要大量硬件, 这使得评估不同硬件设计成为新的瓶颈. 本文提出 LLMCompass, 一个面向 LLM 工作负载的硬件评估框架. LLMCompass 速度快, 准确, 通用, 能够描述并评估不同的硬件设计. LLMCompass 包含一个映射器, 可自动寻找性能最优的映射和调度方案; 同时还包含基于面积的成本模型, 帮助架构师分析设计选择. 与真实硬件相比, LLMCompass 估计的延迟在不同算子和输入规模上的平均误差率为 10.4%, 在 LLM 推理上的平均误差率为 4.1%. 借助 LLMCompass, 在商用硬件上模拟运行 GPT-3 175B 推理的 4 卡 NVIDIA A100 节点只需 16 分钟, 其中包括映射器 26,400 轮参数搜索. 借助 LLMCompass, 本文分析了架构层面的影响, 并探索了新的高性价比硬件设计. 通过降低计算能力, 或用传统 DRAM 替代高带宽内存 (HBM), 这些设计相较 NVIDIA A100 的性能/成本最高可提升 3.41 倍, 有望帮助 LLM 普及. LLMCompass 计划完全开源.

## 1 引言

大型语言模型 (LLM) 是 OpenAI ChatGPT [Ope22], Github Copilot [Git21] 和 Google Bard [Bar23] 背后的技术, 正受到全社会的广泛关注. LLM 的能力与模型规模有关 [Kap20a, Hof22a]; 相比小模型 [Rad19, Dev18], 大模型 [Bro20, Cho22b] 展现出令人印象深刻的能力 [Wei22f], 而未来的模型预计将超过万亿参数 [Fed22].

LLM 的这一空前规模给部署带来了挑战. 要提供 GPT-3 (175B 参数) 的推理服务, 仅容纳模型参数 (半精度) 就至少需要五张 NVIDIA A100. 这种高昂的硬件成本阻碍了 LLM 的进一步普及, 也促使计算机架构师设计更具成本效益的硬件. 我们认为 LLM 推理硬件设计面临三个挑战:

**缺少评估硬件设计的工具.** 在开始编写 RTL 代码之前, 硬件设计师可能希望先勾勒并比较不同的设计选择. 这样的硬件评估工具在编写 RTL 之前应具备多种性质:

- **快速且准确.** LLM 推理需要大量计算和内存硬件资源, 因此工具需要尽可能快, 同时不能牺牲准确性.
- **具有架构描述能力.** 工具应足够通用, 能够描述不同的设计选择; 如果只能应用于某一种架构, 计算机架构师的设计空间就会受限.
- **性能最优.** 硬件性能还受到软件编程方式的影响, 例如工作负载如何映射到硬件. 评估工具应优化这一软件层面, 充分展现每种设计的硬件能力.
- **考虑成本.** 我们还希望了解不同硬件设计选择如何影响硬件成本, 从而分析性能与成本之间的权衡.

现有工具无法同时满足这些要求. Roofline 模型分析速度快但不准确, 周期级模拟器准确但缓慢. FPGA 仿真准确并能提供面积统计, 却需要大量工程工作. 要在 LLM 时代评估大规模硬件设计, 需要一种新的硬件评估工具.

<span id="figure-01"></span>

![图 1](./llmcompass/figure-01.png)

**图 1.** LLMCompass 概览. LLMCompass 可以作为通用评估工具, 帮助硬件设计流程.

**不了解不同硬件设计选择如何影响 LLM 推理性能.** LLM 是一种新兴应用, 其硬件特征仍有待理解. 除了巨大的计算和内存需求外, LLM 还以自回归方式生成 token, 这一点也很独特. 我们希望探究这些性质是否会改变传统的架构经验.

**缺少能让 LLM 普及的高性价比硬件设计.** LLM 功能强大, 但部署成本过高. 要提供 GPT-3 服务, 一个 DGX A100 计算节点的成本可能超过 100,000 美元 [Dgx20]; 每张 NVIDIA A100 含有 540 亿个晶体管和 80 GB 高带宽内存 (HBM). 高昂的硬件成本阻碍了 LLM 的普及.

本文针对这些挑战, 做出三项主要贡献.

**(1) 提出 LLMCompass, 一个面向 LLM 推理工作负载的硬件评估框架 ([第 3 节](#section-3)).** 主流机器学习硬件平台具有许多架构共性, LLMCompass 利用这一事实, 为它们建立了通用的硬件描述模板. 我们还观察到, LLM 的计算图由矩阵乘法, softmax, 层归一化等稠密算子组成; 这些算子具有结构化且可预测的计算和内存访问模式. 因此, LLMCompass 可以在更高层次上逐 tile (逐块) 模拟, 速度快于周期精确模拟器, 同时不损失准确性. 该框架实现了一个映射器, 用于手动管理内存层次结构, 并为稠密工作负载寻找性能最优的映射和调度方案. LLMCompass 还提供基于公开参数的成本和面积模型, 帮助设计师分析不同的设计选择.

LLMCompass 在三种商用硬件设计上进行了验证: NVIDIA A100 [Nvi20], AMD MI210 [Amd21a] 和 Google TPUv3 [Nor21, Jou20]. 与真实硬件相比, LLMCompass 估计的延迟在不同算子和输入规模上的误差率为 10.4%, 在 LLM 推理上的误差率为 4.1%. LLMCompass 使用 Python 实现, 但仍然很快: 在一台普通硬件上模拟运行 GPT-3 175B 推理的 4 卡 A100 节点只需 15-16 分钟, 其中包括映射器 26,400 轮参数搜索 ([图 5](#figure-05) (i), 测试使用一颗 Intel Xeon Gold 6242R CPU @ 3.10GHz 核心).

**(2) 利用 LLMCompass 分析架构影响, 并探索硬件设计选择如何影响 LLM 推理 ([第 4 节](#section-4)).** 我们发现, *预填充*和*解码*需要不同的硬件条件. *预填充*可以显著受益于更强的计算能力和更大的缓冲区, 而*解码*几乎无法从中受益, 对内存带宽更敏感. 这些洞见促使我们思考新的硬件设计范式.

**(3) 提出两个不同于传统经验的高性价比硬件设计 ([第 5 节](#section-5)).** 我们发现, 当今的硬件设计范式倾向于把大量计算能力和 SRAM 放入连接高端 HBM 的大芯片中. 我们分析 LLM 推理特征, 并说明当前硬件设计为何效率不高:

- LLM 推理大多受 I/O 限制, HBM 可以带来较低延迟. 然而, HBM 容量限制了 batch 大小, 使大量计算能力难以充分利用. 基于这一观察, 即使把计算能力和缓冲区大小削减一半, 仍可达到原性能的 95.3%.
- 增大 batch 可以显著提高吞吐量, 因为整个 batch 只需读取一次模型参数. 由于内存容量限制 batch 大小, 进而限制吞吐量, 我们提出用传统 DRAM 替代 HBM. 更大的 batch 可以弥补内存带宽损失, 使吞吐量提升 1.42 倍, 性能/成本提升 3.41 倍.

## 2 背景

<span id="section-2-1"></span>

### 2.1 大型语言模型与 Transformer

大型语言模型是 Transformer 模型 [Vas23] 的变体, 拥有大量在大规模语料上预训练的参数 [Min23]. 如今的 LLM 最多可以拥有一万亿参数 [Fed22]. 与小模型相比, 大模型 (例如 GPT-3 175B [Bro20]) 展现了涌现能力 [Wei22f], 少样本学习 [Bro20] 等一系列非凡能力. 模型规模增加以及随之而来的内存和计算需求给硬件带来了独特挑战.

![图 2](./llmcompass/figure-02.png)

**图 2.** 带张量并行的仅解码器 Transformer 层. GPT-3 175B [Bro20] 由 96 个这样的层堆叠而成.

<span id="figure-03"></span>

![图 3](./llmcompass/figure-03.png)

**图 3.** LLMCompass 硬件描述模板. 本例中每个设备有 2 个核心, 每个核心有 2 条 lane.

我们关注仅解码器 Transformer 模型 [Phu22], 这是当前大多数 LLM 采用的架构: LLaMA [Oth23], GPT [Bro20, Rad19], Bloom [Wor23], PaLM [Cho22b] 等. Transformer 层是这些模型的基本构件. 正如[图 2](#figure-02) 所示, 每层由多头注意力块和 MLP 块组成. 这些层堆叠起来, 构成 LLM 的主要内存和计算需求. Transformer 还使用学习得到的词汇表嵌入和位置嵌入, 但对于 GPT-3 这类大模型, 它们对内存或计算需求的贡献都不显著 ($<2$%). 在不失一般性的前提下, 我们聚焦多头注意力 Transformer (GPT 风格). 还有其他变体, 例如多查询注意力 [Cho22b], 混合专家 [Fed22], 以及并行 Attention 和 MLP [Cho22b]. 由于这些变体共享一组通用算子, LLMCompass 可以无缝支持它们.

<span id="section-2-2"></span>

### 2.2 LLM 推理

给定输入提示和所需输出 token 数量, LLM 推理可以分为两个阶段 [Pop23]:

- *预填充 (Prefill)*: 处理输入提示并计算 KV cache. KV cache 是每一层注意力块中已存储的 Key 和 Value 张量 [Pop23].
- *解码 (Decoding)*: 以自回归方式逐个生成输出 token. 新生成 token 的 Key 和 Value 会拼接到 KV cache, 并用于生成下一个 token.

*预填充*和*解码*的延迟主要分别由输入和输出序列长度决定. 在*预填充*阶段, 整个输入序列都需要与全部参数相乘, 因此通常受计算限制; 在*解码*阶段, 每个新 token 都需要与全部参数相乘并拼接到 KV cache, 因此通常受读取参数和 KV cache 的速度限制.

延迟和吞吐量是评价 LLM 推理系统的关键指标. 对于聊天机器人 [Ope22] 等交互式应用, 必须优化延迟; 对于数据整理 [Nar22] 或表单处理 [Che21f] 等后台数据处理应用, 吞吐量更重要. 延迟和吞吐量之间的权衡由 batch 大小决定: 更大的 batch 会提高吞吐量, 但代价是更高的延迟.

<span id="section-2-3"></span>

### 2.3 LLM 推理的并行化

由于计算和内存操作量很大, 将 LLM 推理并行到多个设备上是有益的. 这不仅带来更好的性能, 而且当模型参数和 KV cache 无法放入单个设备的内存时, 多设备并行可能是必要的. LLM 推理有两种模型并行方案: 流水线并行和张量并行. 在流水线并行中, 模型的不同层被分组为连续分区, 像硬件流水线一样分配给不同设备. 这种方案可以显著提高吞吐量, 但会增加延迟. 另一方面, Megatron-LM [Sho20] 提出的张量并行将每一层切分到可用设备上, 从而降低延迟, 但需要频繁的设备间通信和同步. 正如[图 2](#figure-02) 所示, 这种方案要求每个 Transformer 层执行两次 *all-reduce*: 一次在注意力块之后, 另一次在 MLP 块之后.

## 3 LLMCompass

LLMCompass (**L**arge **L**anguage **M**odel **Com**putation **P**erformance and **A**rea **S**ynthesis) 的概览见[图 1](#figure-01). 要评估 Transformer 大型语言模型在硬件系统上的运行性能 (例如吞吐量和延迟), 需要两个输入: LLM 的计算图和**硬件描述** ([第 3.1 节](#section-3-1)). 给定输入后, **性能模型** ([第 3.2 节](#section-3-2)) 生成性能报告; **映射器**与**架构模拟器**一起进行参数搜索, 寻找最优映射和调度方案. 同时, **面积模型** ([第 3.4 节](#section-3-4)) 生成面积和成本报告.

<span id="section-3-1"></span>

### 3.1 硬件描述模板

如[图 3](#figure-03) 所示, LLMCompass 的硬件描述模板如下:

- 一个**系统** (例如 DGX 节点) 由多个设备组成, 设备通过设备间互连 (例如 NVLink 或 Infinity Link) 连接.
- 每个**设备** (例如 GPU) 由多个核心, 共享的全局缓冲区和片外主存组成. **全局缓冲区** (例如 NVIDIA GPU 中的 L2 cache) 连接主存, 设备间互连和所有核心.
- 每个**核心** (例如 NVIDIA GPU 中的流式多处理器) 可以有多个 lane, 它们共享一个**局部缓冲区** (例如 NVIDIA GPU 中的 L1 cache). 局部缓冲区通过片上互连连接到全局缓冲区.
- 每条**lane**彼此独立, 并拥有自己的**向量单元**, **脉动阵列**, 寄存器和控制逻辑.

在现有设备中, 局部和全局缓冲区通常是片上 SRAM: cache, scratchpad, 或二者的组合. LLMCompass 不区分 cache 和 scratchpad, 因为内存由映射器显式管理. 我们认为这一假设并不损失一般性, 因为高度优化的库也会仔细管理内存. 主存通常是片外 DRAM, 例如 HBM, DDR memory 和 CXL memory 等, 都可以用参数化的硬件描述模板表示.

### 3.2 性能模型

Transformer 的计算图由一组 Transformer 层堆叠而成. 每层由一系列算子组成, 包括矩阵乘法 (*Matmul*), *Softmax*, 层归一化 (*LayerNorm*) 和激活函数 (例如 GPT 中使用的 GELU [Hen16b, Bro20, Rad19]). 在多设备设置中, 还需要 *all-reduce* 等通信原语来执行张量并行. 关键挑战是如何在给定硬件系统上模拟不同算子和通信原语的性能; 这需要了解硬件, 以及如何在具有多级计算系统和多级内存层次的系统上映射和调度算子.

为此, LLMCompass 引入映射器和架构模拟器来构建性能模型. 概念上, 我们以递归方式模拟算子在所选硬件上的运行: 首先将问题划分为能放入全局缓冲区的更小子问题, 再将子问题划分为能放入每个核心局部缓冲区的更小子子问题. 映射器生成划分, 映射和调度, 并通过参数搜索寻找最优方案. LLMCompass 始终尝试寻找性能最优的映射, 以充分展现硬件能力.

<span id="section-3-2-1"></span>

#### 3.2.1 矩阵乘法

矩阵乘法的模拟过程如[图 4](#figure-04) 所示. $\mathbf{A}$ 是一个有 $M$ 行, $K$ 列的 $M\times K$ 矩阵. 同样, $\mathbf{B}$ 和 $\mathbf{C}$ 分别是 $K\times N$ 和 $M\times N$ 矩阵. 广义矩阵乘法定义为 $\mathbf{C}=\mathbf{AB}+\mathbf{C}$.

**从主存到全局缓冲区:** 为了最大化数据复用, 矩阵乘法通常以 tile-by-tile 的方式计算 [Lam91a]. 如[图 4](#figure-04) 左侧所示, 矩阵 $\mathbf{A}$, $\mathbf{B}$ 和 $\mathbf{C}$ 被划分为足以放入全局缓冲区的 tile. 每一步将一个 $A_{\mathrm{tile}_{m,k}}$, $B_{\mathrm{tile}_{k,n}}$ 和 $C_{\mathrm{tile}_{m,n}}$ 读入全局缓冲区, 由核心执行计算, 再写回结果.

**从全局缓冲区到局部缓冲区:** tile 位于全局缓冲区后, 我们需要将 $C_{\mathrm{tile}_{m,n}}=A_{\mathrm{tile}_{m,k}}B_{\mathrm{tile}_{k,n}}+C_{\mathrm{tile}_{m,n}}$ 的计算并行到多个核心. 如[图 4](#figure-04) 中部所示, 这些 tile 进一步划分为能放入每个核心局部缓冲区的更小子 tile. 此时就变成了把子 tile 映射到核心上的调度问题.

[图 4](#figure-04) 右侧展示了两种可能的调度方案:

- **调度方案 1:** 不同核心处理同一列中不同的 $C_{\mathrm{subtile}}$. 在 *wave 0*, 由于 *core 0* 和 *core 1* 都需要读取相同的 $B_{\mathrm{subtile}}$, 它们对全局缓冲区的内存访问应当合并. 我们的模拟器会自动识别并处理这种内存访问合并. 由于同一核心持续更新同一个 $C_{\mathrm{subtile}}$, 无需先把部分结果写回全局缓冲区再读出; 模拟器也会自动处理这一"写后读"依赖.
- **调度方案 2:** 不同核心处理同一个 $C_{\mathrm{subtile}}$. *Core 0* 和 *core 1* 先读取数据并计算部分结果, 然后执行归约并写回最终结果.

在实际情况下, 核心和 tile 更多, 调度空间会比[图 4](#figure-04) 中的示例复杂.

**从局部缓冲区到 lane:** 类似地, 在每个核心内部, 子 tile 会进一步划分为子子 tile, 映射到共享局部缓冲区的 lane 上. 随后, 子子 tile 被传递到脉动阵列. LLMCompass 使用 SCALE-Sim [Sam18, Sam20] (一个周期级脉动阵列模拟器) 模拟脉动阵列行为并得到周期数. LLMCompass 会把 SCALE-Sim 的结果缓存到查找表中, 避免重复模拟. 如果需要, 向量单元会执行归约.

**映射器:** 映射器通过参数搜索确定最佳 tile 方案和调度方案. 为了让计算与内存访问重叠, 我们在内存层次的每一级都加入软件流水线 (双缓冲) 作为调度选项. 启用软件流水线的缺点是需要额外缓冲空间, 会减小最大 tile 大小, 可能降低脉动阵列利用率. 不过, 我们发现软件流水线在大多数情况下都有益.

<span id="section-3-2-2"></span>

#### 3.2.2 通信原语

我们使用 AHEAD [Abd19] 和 LogGP [Ale95] 中的链路模型. 设 $L$ 为链路延迟, $O$ 为数据传输的额外开销, $B$ 为链路带宽. 通过链路传输 $n$ 字节数据的延迟 $T$ 如[式 1](#equation-01)和[式 2](#equation-02)所示:

<span id="equation-01"></span>

$$
T=L+O+\frac{\hat{n}}{B}
$$

<span id="equation-02"></span>

$$
\hat{n}=\left\lceil\frac{n}{\mathit{MaxPayload}}\right\rceil*{\mathit{\mathit{Flit\_size}}}+n
$$

在此基础上, 我们实现了 ring all-reduce [Pat09], 这是一种带宽最优的 all-reduce 算法. 基于 NVLink [Fol17], 我们使用 16 字节的 $\mathit{\mathit{Flit\_size}}$ 和 256 字节的 $\mathit{MaxPayload}$. 我们不再建模其他通信原语, 因为 LLM 推理只需要张量并行的 *all-reduce* 和流水线并行的 *peer-to-peer*.

<span id="section-3-2-3"></span>

#### 3.2.3 其他算子

我们使用与[第 3.2.1 节](#section-3-2-1)类似的方法建模 *Softmax*, *LayerNorm* 和 *GELU*. 区别只有两点:

- 它们的维度更少, 因此更简单: *Softmax* 和 *LayerNorm* 处理二维数据, *GELU* 处理一维数据, 而 *Matmul* 处理三维数据. 由于每个维度都需要 tile 和调度, 映射器的搜索空间小得多.
- 它们不使用脉动阵列. *Softmax* 使用在线算法实现 [Mil18a], *GELU* 使用 $\tanh$ 近似 [Hen16b].

### 3.3 性能模型验证

本节在三种真实硬件平台上验证框架: (1) 一台由 4 张 80 GB NVIDIA A100 SXM4 GPU 组成, 通过 NVLink 全互连的数据中心 GPU 节点; (2) 一台由 8 个 TPUv3 核心组成, 以二维环面拓扑连接的 Google Cloud TPU 节点; (3) 一张 AMD MI210 GPU [+2]. 结果见[图 5](#figure-05). 对于 NVIDIA GPU, 我们使用 CUDA 11.7 和 PyTorch 2.0, 以半精度 (FP16) 测试算子, 并为 *LayerNorm* 和 *GELU* 启用 `torch.compile` 以最大化性能. 通信原语 *all-reduce* 使用 nccl-tests [Ncc21] 测试, 该工具用于测试 NVIDIA GPU 的通信原语性能. 对于 Google TPU, 我们使用 JAX 0.4.18 测试算子和通信原语. 由于 TPU 的硬件特征, *Matmul* 使用 bfloat16 (BF16) 测试, 其他算子使用 FP32. 对于 AMD GPU, 我们使用 ROCm 5.4.2 和 PyTorch 2.0 [+3], *Matmul* 使用 FP16, 其他算子使用 FP32. 通过使用输入规模为 1 的算子运行, 测得包含框架开销在内的 kernel 启动开销.

如[图 5](#figure-05) 所示, 对于 *Matmul*, *Softmax*, *LayerNorm*, *GELU* 和 *all-reduce*, LLMCompass 的平均误差率分别为 9.0%, 12.0%, 11.3%, 5.0% 和 14.9%. 对于 LLM 推理, LLMCompass 在*预填充*和*解码*阶段的平均误差率分别为 0.69% 和 7.5%. **总体而言, LLMCompass 在不同输入规模的不同算子上的平均误差率为 10.4%, 在*预填充*和*解码*阶段的平均误差率为 4.1%.**

虽然不能完全匹配真实硬件, LLMCompass 能够显示朴素 Roofline 模型无法显示的相似趋势. 例如在[图 5](#figure-05) (d) 中, 当 *LayerNorm* 的归约维度增大到极端值时, 吞吐量应因归约成本增加而下降, LLMCompass 捕捉到了这一趋势.

LLMCompass 的结果完全可解释, 不需要加入任何人为修正因子; 我们认为这种可解释性比完全匹配结果更重要. LLMCompass 与真实硬件不一致的可能原因包括:

- **硬件知识不足.** 我们对 GPU 和 TPU 的微架构 (例如硬件流水线或调度器设计) 了解很少. 输入规模较大时, 硬件利用率高, 一些开销可以被隐藏; 输入规模较小时, 开销难以隐藏, 微架构细节会显著影响性能. 此外, LLMCompass 将 NVIDIA GPU 的 Tensor Core 和 AMD GPU 的 Matrix Core 模拟为脉动阵列, 而现实可能并非如此.
- **软件知识不足.** 我们不知道这些平台上的算子和通信原语如何实现, 因为它们是闭源库. 我们针对每个输入规模进行充分的参数搜索以最大化性能, 但现实中的库可能使用启发式方法决定映射和调度, 在所有输入规模上未必最优. 例如, 对于 $M=64$, $N=K=12288$ 的 *Matmul*, 我们发现 AMD MI210 的性能不到 Roofline 性能的 25%, 而 NVIDIA A100 可以达到 50%. 此外, 还有一些关键信息不可得. 例如, 我们找不到 TPU-TPU 通信的数据包格式, 只能使用 NVLink 数据包格式.
- **非理想硬件.** LLMCompass 假设频率固定, 但测试真实硬件时无法控制数据中心 GPU 或 TPU 节点的频率. LLMCompass 还假设带宽可以满速利用, 而现实中可能存在其他开销, 例如错误校正码.

### 3.4 面积和成本模型

芯片设计师通过增大芯片面积提升单芯片性能时, 每片晶圆能容纳的芯片数量会减少, 也可能降低良率, 从而增加成本. LLMCompass 集成面积和成本模型, 使设计师能够分析性能与面积之间的权衡. 这些模型使用硬件描述, 以及已知组件的估计晶体管数量和/或芯片面积来计算设备总芯片面积, 方法如下.

在每个核心的 lane 中, 我们根据开源设计, 流片结果和生成器 [Zar19, Mck18a, Gen21] 估计向量单元和脉动阵列的晶体管数量. 我们使用经验面积模型 [Rag09] 估计每条 lane 的寄存器文件面积开销. 对于每个核心内由多条 lane 共享的局部缓冲区, 以及由多个核心共享的全局缓冲区, 我们将其建模为 SRAM cache, 使用 CACTI [Mur09] 推导面积, 并将结果缩放到 7 nm 工艺. 对于内存和设备间互连, 我们根据标注过的 A100 和 MI210 芯片照片 [Pat22a, Smi22b] 估计 PHY 和控制器面积. 在计算中, 控制器面积随工艺节点缩放, 但 PHY 面积保持不变, 因为内部模拟器件不易缩放.

## 4 架构影响

借助 LLMCompass, 我们可以开展设计空间探索, 并了解如何为 LLM 推理设计高效硬件系统. 本节使用 LLMCompass 研究不同计算系统配置, 内存带宽和缓冲区大小如何影响 LLM 推理性能, 并分析其架构影响. 这些洞见启发我们在[第 5 节](#section-5)提出新设计.

<span id="section-4-1"></span>

### 4.1 实验设置

对于未特别说明的规格, 我们使用 NVIDIA A100 的规格 (见[表 1](#table-01)) 和 4 路张量并行. *预填充*延迟通过运行一个 GPT-3 层测量, batch 大小为 8 (延迟和吞吐量之间的平衡点), 输入序列长度为 2048 (GPT-3 的中长序列). *解码*延迟是运行一个 GPT-3 层并生成第 1024 个输出 token 时的延迟, batch 大小为 8, 输入序列长度为 2048. 所有算子均使用 FP16.

<span id="section-4-2"></span>

### 4.2 计算系统

我们测试了五种不同的计算系统设计, 如[表 3](#table-03) 所示. 从 A 到 E, 我们逐渐增大每个核心的脉动阵列, 向量单元和局部缓冲区容量. B 表示完整的 GA100. 为比较少量大核心和大量小核心的设计选择, 我们让 B, C, D, E 具有相同的总计算能力和总缓冲区大小. 配置 A 的计算能力只有其他配置的四分之一. 所有设计的总缓冲区大小相同, 寄存器文件大小随向量宽度变化.

[图 7](#figure-07) 展示了这些设计的*预填充*和*解码*延迟. 与 GA100 相比, 设计 A 的*预填充*延迟高 3.25 倍, 但*解码*只慢 0.1%, 面积仅为 57.8%. 拥有最大核心的设计 E 的*预填充*和*解码*延迟分别增加 12.4% 和 30.8%, 但芯片面积最多可以减少 7.7%.

**分析:** 对于*预填充*阶段, B 比 A 快得多, 因为*预填充*受计算限制. 随着每核心脉动阵列和向量单元扩大, tile 大小也需要增大, 才能充分利用更大的计算单元. 更大的 tile 可能带来更多填充, 因为问题规模需要量化到 tile 大小和硬件大小. 虽然大脉动阵列和向量单元面积效率更高, 但更难调度和充分利用.

由于*解码*受 I/O 限制, 增加计算能力几乎没有帮助, 这解释了 A 和 B 性能相近. 由于*解码*中的矩阵乘法很窄 (例如 $16\times{}12288$), 更大的脉动阵列更难充分利用, 性能会下降.

**影响:**

- *提高计算能力对预填充帮助显著, 但对解码帮助很小.*
- *相较解码, 大型脉动阵列对预填充更高效.*

### 4.3 主存

由于主存容量更像是一种约束 (需要足够容量存放参数和 KV cache), 我们关注主存带宽的影响. [图 8](#figure-08) 展示了从 400 到 3200 GB/s 扫描内存带宽的性能结果. 对于*预填充*, 带宽从 800GB/s 增加到 2000GB/s 可使延迟降低 14.3%, 继续增加到 3200GB/s 只带来 3.5% 的边际收益. 对于*解码*, 带宽从 800GB/s 增加到 2000GB/s 可获得 1.88 倍加速, 继续增加到 3200GB/s 还可提升 26%.

<span id="figure-08"></span>

![图 8](./llmcompass/figure-08.png)

**图 8.** GPT-3 每层的预填充延迟.

**分析:** 在*预填充*阶段, 带宽从 400GB/s 增加到 800GB/s 时, *Matmul* 显著加快. 继续增加带宽不会显著影响 *Matmul* 性能, 因为它变成了计算受限. 对于受 I/O 限制的 *GELU*, *LayerNorm* 和 *Softmax*, 更大的内存带宽可以实现显著加速.

在*解码*阶段, 增加内存带宽会显著加快 *Matmul*, 主要因为它们很窄 (batch 为 1 时变成向量-矩阵乘法) 且受 I/O 限制. 在这一阶段, *GELU*, *LayerNorm* 和 *Softmax* 的输入规模较小, 主要受 kernel 启动开销支配, 几乎不受内存带宽影响.

*解码对内存带宽比预填充敏感得多.*

### 4.4 局部和全局缓冲区

**局部缓冲区.** 我们将硬件规格固定为 NVIDIA A100 (见[表 1](#table-01)), 扫描局部缓冲区大小. 结果见[图 9](#figure-09). 对于*预填充*, 局部缓冲区从 64KB 增加到 192KB, 性能提高 18.0%, 面积增加 5.8%. 继续增加到 1024KB, 性能只提高 0.2%, 面积却增加 28.8%. 对于*解码*阶段, 局部缓冲区从 64KB 增加到 1024KB, 性能只提高 0.5%.

<span id="figure-09"></span>

![图 9](./llmcompass/figure-09.png)

**图 9.** GPT-3 每层的预填充延迟.

**分析:** 更大的局部缓冲区降低了矩阵乘法延迟, 因此主要降低了*预填充*延迟. 更大的局部缓冲区允许使用更大的矩阵 tile, 从而提高脉动阵列利用率. 192KB 的局部缓冲区刚好足以在 FP16 和双缓冲技术下完成 $128\times 128\times 128$ 的矩阵乘法, 并能充分利用 $16\times 16$ 脉动阵列, 这为 NVIDIA A100 的设计选择提供了线索. 当脉动阵列已经充分利用后, 继续增加局部缓冲区大小只能带来边际收益. 对于*解码*阶段, 增加局部缓冲区没有帮助, 因为它受 I/O 限制.

**全局缓冲区.** 全局缓冲区大小的性能趋势与[图 9](#figure-09) 类似. 全局缓冲区从 10MB 增加到 40MB, *预填充*加速 11.8%, 面积增加 9.6%. 继续增加到 80MB, 性能只提高 0.01%, 面积却增加 11.7%. 对于*解码*, 全局缓冲区从 10MB 增加到 80MB, 性能只提高 0.7%.

**分析:** 更大的全局缓冲区允许使用更大的矩阵 tile, 提高脉动阵列利用率和全局缓冲区级别的数据复用. 同样, 当脉动阵列饱和后, 增加全局缓冲区大小的收益会递减. *解码*阶段不受计算限制, 因此几乎无法从更大的全局缓冲区中受益.

- *大缓冲区有利于预填充, 但不利于解码.*
- *缓冲区应足够大, 以充分利用脉动阵列. *

### 5.1 面向延迟的设计

LLM 推理延迟是从收到请求到生成最后一个 token 的总时间, 是聊天机器人等交互式应用的关键指标. 它由*预填充*延迟 (处理输入序列的时间) 和*解码*延迟 (以自回归方式生成输出序列的时间) 组成. 除非输入序列远长于输出序列, 否则推理延迟通常由*解码*主导. *解码*是 I/O 密集型阶段, 主要受读取模型参数和 KV cache 限制.

**观察:** 延迟主要受 I/O 限制, 因此内存带宽是降低延迟的关键, HBM 是最佳选择. 然而, HBM 容量有限, batch 不能太大: KV cache 和中间值的大小与 batch 成正比. 因此, 大量计算能力无法充分利用.

**方案:** 如[表 4](#table-04) 左侧所示, 我们提出一种面向延迟的高效设计, 在使用与 GA100 相同内存系统的同时削减一半计算能力.

**结果:** 与 NVIDIA GA100 相比, 芯片面积减少 42.1%, 平均性能保持在 95.3%. 结果见[图 10](#figure-10).

削减计算能力只会损害受计算限制的*预填充*性能. 当输入序列较长, 输出序列较短时, *预填充*占比更高, 性能下降也更明显; 这解释了为什么在输入长度 2048, 输出长度 256 时, 我们只能达到 GA100 80% 的性能. 当输入更短, 输出更长时, 我们削减后的面向延迟设计可以达到 GA100 99% 的性能.

<span id="section-5-2"></span>

### 5.2 面向吞吐量的设计

对于表单处理或数据整理等后台应用, 吞吐量可能比延迟更重要. 提高吞吐量通常有两种方式:

- **降低延迟:** 延迟主要受读取参数和 KV cache 的 I/O 限制, 因此降低延迟的最佳方式是进一步提高内存带宽. HBM 已经很昂贵, 在不增加成本的情况下可能难以实现.
- **增大 batch:** 更大的 batch 通常更有利于吞吐量, 因为整个 batch 只需读取一次参数. 更大的 batch 也能提高硬件利用率, 代价是消耗更多计算功率并增加 KV cache 访问.

**观察:** 与降低延迟相比, 增大 batch 是提高吞吐量更高效的方式, 后者需要昂贵的高端 HBM 甚至 SRAM. batch 越大, 就需要更多内存容量来容纳更大的 KV cache 和中间值.

**方案:** 如[表 4](#table-04) 右侧所示, 我们提出一种面向吞吐量的设计. 为了容纳更大的 batch, 我们使用 512GB DRAM, 由 256 条 PCIe 5.0 通道供电, 总内存带宽为 1TB/s. (根据面积模型, 800$mm^{2}$ 芯片的周长可以容纳约 400 条 PCIe 5.0 通道.) 考虑到 HBM 的高成本和有限容量, 该设计更具成本效益. 更大的 batch 需要更强的计算能力, 因此我们将脉动阵列和局部缓冲区扩大 4 倍; 同时将核心数和向量单元减半, 以维持与 GA100 相近的芯片面积.

**结果:** 与 NVIDIA GA100 相比, 芯片面积略小, 吞吐量平均提高 1.42 倍. 结果见[图 12](#figure-12). 用传统 DRAM 替代 HBM 后, 成本降低 58.3%, 性能/成本总提升达到 3.41 倍.

**讨论:** 我们的设计拥有 GA100 6.4 倍的内存容量, 扣除模型参数占用的固定空间后, 可支持大于 12 倍的 batch. 理想情况下, 带宽只有 GA100 一半时, 该配置仍可将吞吐量提高 6 倍以上. 然而, batch 只会减少模型参数访问, 不会减少 KV cache 读取. batch 很大时, KV cache 访问会成为新的瓶颈, 削弱 batch 带来的收益. 随着输入和输出长度增加, KV cache 读取时间变长, 吞吐量会下降, 如[图 12](#figure-12) (a) 所示.

从延迟角度看, 这种面向吞吐量的设计可能并不理想: 平均延迟比 GA100 差 9.21 倍. 虽然每个 batch 只需读取一次模型参数, 但更大的 batch 意味着需要读取更多 KV cache 和中间值. 在 LLM 推理中, 延迟和吞吐量之间不存在免费的收益.

## 6 相关工作

<span id="section-6-1"></span>

### 6.1 大规模硬件设计评估

评估硬件设计的性能, 面积和成本等特征, 对硬件设计师非常有用. 可选方法包括:

**Roofline 模型分析** [Wil09]. Roofline 模型是分析式的, 评估速度快, 可用于不同架构的性能比较. 但相对于真实硬件能力, 它可能过于乐观.

**周期级模拟** [Bak09, Bec15, Gut18, Sun19b, Ger18, Kim12, Gon17, Uba12, Kha20a, Par19, Sam18, Sam20]. 周期级模拟器的典型速度低于每秒 10 万条指令, 因此不适合评估 LLM 规模的工作负载. 由于这类模拟器通常针对特定架构设计, 很难描述与其设计目标完全不同的硬件, 例如 GPGPU-sim [Bak09] 依赖 GPU ISA, 几乎不可能用来评估 TPU 风格设计. 这些模拟器通常还要求用户提供待评估程序; 如果软件程序未优化, 就可能导致不公平的比较.

**FPGA 仿真.** 另一种方法是用 RTL 实现设计, 再在 FPGA 上仿真. RTL 代码可以手写, 也可以由加速器生成器生成 [Ven19, Nvd18, Tin23, Gen21]. 虽然仿真速度快, 但能够运行大语言模型的大型设计需要很长的综合时间, 也可能需要多块 FPGA 才能容纳设计. 此外, 每评估一种新设计, 用户都需要重写 RTL 并重新综合, 还要负责高效映射工作负载, 以充分利用硬件.

**比较.** 如[表 5](#table-05) 所示, LLMCompass 比 Roofline 模型分析更准确, 比周期级模拟器更快且更通用, 也比 FPGA 仿真需要更少工程投入. 在 LLM 时代评估大规模硬件设计时, 我们认为 LLMCompass 适合用于初始设计阶段, 以确定核心数量, 内存带宽等高层硬件特征. 虽然本文在大型 Transformer 模型背景下描述 LLMCompass, 它也可以应用于其他稠密神经网络模型.

**LLMCompass 可以补充 FPGA 仿真.** 设计师可以先进行初步设计空间探索, 再承担 FPGA 仿真和实现所提设计 RTL 的高昂成本.

<span id="section-6-2"></span>

### 6.2 加速器设计空间探索

自 CNN 时代以来, 已有许多工作关注如何探索最优硬件设计和映射 [Par19, Dav19, Dav20, Lu17, Ven19, Yan20c, Heg21, Li21d, Rea17, Zha22d]. LLMCompass 在设计考量和侧重点上与这些工作不同:

- 这些工作主要面向卷积神经网络 (CNN), 关注循环并行化, 循环顺序和数据流 (例如权重驻留或输出驻留); 这些并不是 Transformer LLM 的主要设计考量. LLMCompass 更适合矩阵乘法的 tile 划分和调度, 以及 *LayerNorm* 等其他 Transformer 算子.
- LLMCompass 面向 GPU 规模的设计, 其规模远大于 Eyeriss [Che16h] 等 CNN 加速器. LLM 工作负载也显著大于 CNN 工作负载.

**LLMCompass 也可以补充设计空间探索.** LLMCompass 以 Python 库实现, 可以无缝集成到 FAST [Zha22d] 等设计空间探索框架中. FAST 使用内部 TPU 性能模拟器, 因此适用范围受限. 我们认为, 快速且准确, 完全开源的 LLMCompass 可以推动硬件设计空间探索研究普及.

### 6.3 加速 LLM 推理

已有许多 Transformer 加速器 [Tam21, Wan22j, Wan21f, Ham21], 主要通过剪枝或近似计算等软硬件协同设计来加速 Transformer. 这些技术对于最大规模模型是否有效, 还有待观察. 此外, 当前 LLM 的主要挑战来自模型的巨大规模, 这也是本文的重点.

也有许多工作从软件层面加速 LLM 推理 [Ami22a, Pop23, Dao22f, Dao23c, She23d]. LLMCompass 可以通过建模它们的计算和内存访问模式, 兼容这些优化技术. 我们不讨论 FlashAttention [Dao22f] 等技术, 因为它们与本文关注点正交: 这些工作关注软件层面, 通常针对 NVIDIA GPU 等特定硬件平台实现.

<span id="section-7"></span>

## 7 结论

本文提出 LLMCompass, 一个快速, 准确且具有架构描述能力的 LLM 推理硬件评估框架. LLMCompass 的硬件描述模板, 映射器和架构模拟器, 使硬件设计师能够评估对周期级模拟器而言不可行的大规模 LLM 芯片设计. 集成的面积和成本模型还可以帮助设计师分析性能与成本之间的权衡. 借助 LLMCompass, 我们分析了硬件设计如何影响 LLM 推理. 基于这些发现, 我们提出面向延迟和面向吞吐量的设计, 相比 NVIDIA GA100, 性能/成本分别提升 1.06 倍和 3.41 倍. 未来我们计划扩展 LLMCompass, 使其支持更多机器学习工作负载以及 LLM 微调.
