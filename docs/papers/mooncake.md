## 摘要

Mooncake 是 Moonshot AI 为领先的大语言模型服务 Kimi 提供的服务平台. 它采用以 KVCache 为中心的解耦架构, 将预填充集群与解码集群分离. 它还利用 GPU 集群中未被充分使用的 CPU, DRAM 和 SSD 资源, 实现解耦的 KVCache 缓存. Mooncake 的核心是以 KVCache 为中心的调度器, 它在满足延迟相关服务级别目标 (SLO) 的同时, 权衡如何最大化整体有效吞吐量. 传统研究假定所有请求都会得到处理, 而 Mooncake 还要应对高度过载场景带来的问题. 为缓解这些问题, 我们开发了基于预测的提前拒绝策略. 实验表明, Mooncake 在长上下文场景中表现出色. 与基线方法相比, Mooncake 在满足 SLO 的情况下, 可在某些模拟场景中将吞吐量最多提高 525%. 在真实工作负载下, Mooncake 的新架构使 Kimi 能多处理 75% 的请求.

## 1 引言
<span id="section-01-01"></span>

### 1.1 开发 Mooncake 的动机

随着大语言模型 (LLM) 在各种场景中迅速普及 [Ope22, Tou23b, Che21, Pac23], LLM 服务的工作负载已经明显多样化. 这些工作负载在输入/输出长度, 到达频率和到达分布上各不相同, 更重要的是, 它们要求不同类型的服务级别目标 (SLO). 作为模型即服务 (MaaS) 提供商, Kimi [Moo23] 的主要目标之一是求解一个包含多个复杂约束的优化问题. 优化目标是最大化整体有效吞吐量, 这会直接影响收入, 而约束则反映不同级别的 SLO. 这些 SLO 通常涉及延迟要求, 主要包括首 Token 时间 (TTFT) 和 Token 间时间 (TBT).

<span id="figure-01"></span>

![Mooncake 架构](./mooncake/figure-01.png)

**图 1.** Mooncake 架构.

要实现这一目标, 前提是充分利用 GPU 集群中可用的各类资源.
具体而言, 当前的 GPU 服务器通常以高度集成的节点形式提供 (例如 DGX/HGX 超级计算机 [Nvi22]), 但仍有必要将这些节点解耦并重构成多个资源池, 每个资源池针对不同但相互协作的目标优化. 例如, 许多研究者 [Pat23, Zho24, Hu24b] 建议将预填充服务器与解码服务器分离, 因为 LLM 服务的这两个阶段具有截然不同的计算特性, 而 KVCache 会随着请求从预填充服务器转移到解码服务器.

基于这一想法, 我们发现 KVCache 调度是 LLM 服务调度的中心. 要提高整体吞吐量, 通常有两种一般性方法: *1)* 尽可能复用 KVCache, 以减少所需的计算资源; *2)* 尽量增加每个批次中的 Token 数量, 以提高模型 FLOPs 利用率 (MFU). 但是, 从远端位置复用 KVCache 会延长 TTFT, 大批量则会增大 TBT. 因此, 使用这两种面向吞吐量的优化都可能违反延迟相关的 SLO.

按照上述原则, 我们提出了一种围绕 KVCache 进行调度和优化的解耦设计. [图 1](#figure-01) 展示了我们目前用于 LLM 服务的**以 KVCache 为中心的解耦架构**, 即 Mooncake. 对每个请求, 全局调度器 (Conductor) 需要选择一对预填充实例和解码实例, 并按以下步骤调度请求: *1)* 将尽可能多的可复用 KVCache 传输到选定的预填充实例; *2)* 以分块/分层方式完成预填充阶段, 并将输出 KVCache 持续流式传输到对应的解码实例; *3)* 加载 KVCache, 将请求加入解码实例的连续批处理过程并生成请求输出.

虽然这一过程看似直接, 但由于限制很多, 选择策略十分复杂. 在预填充阶段, 主要目标是尽可能复用 KVCache, 避免重复计算. 但是, 等待低层级存储中的 KVCache 可能违反 TTFT SLO. 同时, KVCache 服务器上的高需求可能造成网络拥塞, 延长等待时间.
因此, Conductor 还负责预测 KVCache 块的未来使用情况, 并据此执行换入换出和复制等调度操作.
最热的数据块应复制到多个节点, 以避免获取拥塞; 最冷的数据块则应换出, 以降低保留成本.
预填充调度还受预填充节点可用 DRAM 空间的限制, 当大部分内存预留给全局 KVCache 池时尤其如此.

相比之下, 解码阶段有不同的优化目标和约束. 目标是在一个解码批次中聚合尽可能多的 Token, 以提高 MFU.
但是, 这一目标不仅受 TBT SLO 限制, 还受 VRAM 能容纳的聚合 KVCache 总大小限制.

更重要的是, 现有 LLM 服务研究假定资源充足, 主要关注提高资源利用率. 相比之下, 当前 GPU/加速器供应有限, 许多 MaaS 提供商都面临严重的过载问题, 尤其是在高峰时段. 此类场景下的调度会遇到现有工作尚未研究的特殊问题. 例如, 我们需要预测未来负载; 如果预填充阶段结束后不会有可用的解码槽位, 就应提前拒绝部分请求, 避免浪费计算资源.
然而, 直接实现这种提前拒绝策略会意外造成过载量波动. 因此, 我们希望预测特定查询的生成长度, 并预测短期内的整体负载, 从而实现更好的拒绝策略. 此外, 还需要区分请求优先级, 以实现基于优先级的调度.
本文将这些问题统称为**面向过载的调度**, 并给出我们的初步研究结果.

<span id="section-01-02"></span>

### 1.2 Mooncake 的设计与结果

在本文后续各节中, 我们首先概述 Mooncake 的架构, 包括主要组件和处理请求的典型工作流 ([§ 3](#section-03)). 然后, 我们介绍实现过程中的主要设计选择, 尤其是当前研究尚未覆盖的部分.

首先, 我们在 [§ 5](#section-05) 中讨论如何实现独立的预填充节点池, 使其能顺畅处理上下文长度的动态分布. 我们采用分块流水线并行 (CPP) 机制, 将单个请求的处理扩展到多个节点, 这对降低长上下文输入的 TTFT 很有必要. 与传统的序列并行 (SP) 方案相比, CPP 可以减少网络消耗, 并简化对频繁弹性扩缩容的依赖. 分层预填充对这一机制形成补充, 它能够流式传输 KVCache 以重叠延迟.

接下来, 我们在 [§ 6](#section-06) 中详细介绍以 KVCache 为中心的请求调度算法, 它在实例负载与以 TTFT 和 TBT SLO 衡量的用户体验之间取得平衡. 其中包括一种基于启发式规则的自动热点迁移方案, 它无需准确预测 KVCache 的未来使用情况, 即可复制热点 KVCache 块. 实验结果表明, 我们的缓存感知调度可以显著降低真实场景中的 TTFT. 在使用公开数据集, 模拟数据和真实工作负载进行的端到端实验中, Mooncake 在长上下文场景中表现出色. 与基线方法相比, Mooncake 在满足 SLO 的同时, 可将吞吐量最多提高 525%. 在真实工作负载下, Mooncake 使 Kimi 能多处理 75% 的请求.

最后, 现有 LLM 服务工作假定所有请求都会得到处理, 而 Mooncake 由于 Kimi 的用户请求快速增长, 持续面临过载. 因此, Mooncake 的调度需要根据系统负载判断接受还是拒绝传入请求. 我们在 [§ 7](#section-07) 中讨论一种特殊的提前拒绝策略, 它可以减少过载场景中浪费的计算资源. 我们还会进一步研究直接采用提前拒绝所造成的负载波动问题, 以及预测未来负载如何缓解这一问题.

Mooncake 目前是服务 Kimi 的主要平台, 已成功应对工作负载的指数增长, 证明了它能够扩展到大规模, 高度过载的工作负载. 不过, 仍有许多问题需要研究, 本文也列出了这些未来方向.

> 为保护专有信息并便于复现, 本文报告的所有实验结果都基于真实工作负载轨迹的重放, 但使用了与 LLaMA2-70B 架构相同的**虚拟模型**. 轨迹只包含请求到达时间, 输入 Token 数量, 输出 Token 数量和重新映射后的块哈希, 不含任何真实用户内容. 轨迹已在 [https://github.com/kvcache-ai/Mooncake](https://github.com/kvcache-ai/Mooncake) 开源.

## 2 预备知识与问题定义

现代大语言模型 (LLM) 基于 Transformer 架构, 使用注意力机制和多层感知机 (MLP) 处理输入. GPT [Rad19] 和 LLaMA [Tou23] 等常用的 Transformer 模型采用仅解码器结构. 从逻辑上看, 每个推理请求分为两个阶段: 预填充阶段和解码阶段.

<span id="figure-02"></span>

![虚拟 LLaMA2-70B 模型在不同序列长度或批量大小下的预填充与解码阶段归一化吞吐量和延迟](./mooncake/figure-02.png)

**图 2.** 虚拟 LLaMA2-70B 模型在不同序列长度或批量大小下的预填充与解码阶段归一化吞吐量和延迟.

在预填充阶段, 所有输入 Token 会并行处理. 这一阶段生成第一个输出 Token, 同时存储计算所得键和值的中间结果, 即 KVCache. 随后, 解码阶段使用该 KVCache 自回归地生成新 Token, 并将计算产生的新键和值加入 KVCache. 由于预填充阶段可以同时处理输入 Token, 除短请求外, 这一阶段通常是计算密集型的. 注意力网络的计算复杂度随输入长度呈二次增长, MLP 的复杂度则呈线性增长, 因此预填充阶段的计算时间通常随输入长度超线性增长, 如 [图 2](#figure-02) 左侧所示.

相比之下, 受自回归生成限制, 解码阶段在每个批次中一次只能处理一个 Token. 因而它受内存限制, 计算时间随批量大小次线性增长, 如 [图 2](#figure-02) 右侧所示. 解码阶段常用的一项优化是连续批处理 [Yu22a, Kwo23]. 每次迭代前, 调度器会检查所有请求的状态, 将新到达的请求加入批次的预填充阶段, 同时移除已经完成的请求.

由于预填充阶段和解码阶段的特性不同, MaaS 提供商会设置不同指标来衡量对应的服务级别目标 (SLO). 具体来说, 预填充阶段主要关注从请求到达到生成第一个 Token 之间的延迟, 即首 Token 时间 (TTFT). 解码阶段则关注同一请求连续两次生成 Token 之间的延迟, 即 Token 间时间 (TBT).

作为 MaaS 提供商, 必须达到服务协议规定的 SLO 指标, 以保证服务质量.
例如, $\mathrm{TTFT}_{\mathrm{P90}} = 4\times$ 这一指标表示, 90% 推理请求的 TTFT 不会超过同等条件下无干扰运行单个请求时的四倍. 具体而言, 在本文的端到端实验中 ([§ 8.1](#section-08-01)), 我们设置 $\mathrm{TTFT}_{\mathrm{P90}} = 10\times$, $\mathrm{TBT}_{\mathrm{P90}} = 5\times$. 在真实部署中, 我们为 TTFT 和 TBT 设置固定 SLO. 如果监控发现 SLO 未达到, 我们会增加推理资源或拒绝部分传入请求.

但是, 由于当前 GPU 供应具有偶发性, 通常无法对推理集群进行弹性横向扩展. 因此, 决定拒绝哪些请求成为面向过载调度的核心问题. 我们的主要目标是在遵守 SLO 的同时最大化整体吞吐量, 其他研究将这一概念称为有效吞吐量 (goodput) [Zho24, Wu24a].
我们的方法有所不同: 只有完整执行结束的请求才计入有效吞吐量. 否则, 先前消耗或生成的所有 Token 都不会计入, 对应资源也会被浪费. 换言之, 如果请求无法在 SLO 内完整执行完毕, 就应尽早将其拒绝. 实现这一目标不仅需要优化预填充阶段和解码阶段的架构, 还需要具备预测短期未来负载的能力.

## 3 Mooncake 解耦架构概述

如 [图 1](#figure-01) 所示, Mooncake 采用解耦架构, 不仅将预填充节点与解码节点分离, 还汇集 GPU 集群的 CPU, DRAM, SSD 和 RDMA 资源, 实现解耦的 KVCache.
这种解耦缓存利用未被充分使用的资源, 提供充足的缓存容量和传输带宽, 无需额外成本即可实现高效的近 GPU 前缀缓存.

<span id="figure-03"></span>

![CPU 内存中的 KVCache 池](./mooncake/figure-03.png)

**图 3.** CPU 内存中的 KVCache 池. 每个块都带有一个由自身哈希及其前缀共同决定的哈希值, 用于去重.

[图 3](#figure-03) 展示了 KVCache 块的存储和传输逻辑. 在 CPU 内存中, KVCache 以分页块的形式存储. 根据请求模式, 它可以采用 LRU (最近最少使用), LFU (最不频繁使用) 或基于请求特征的算法等缓存淘汰算法. 这些 KVCache 块在 CPU 和 GPU 之间的传输由一个独立的, 基于 (GPUDirect) RDMA 的组件 Messenger 处理.
这种架构还使我们能够向外部用户提供上下文缓存 API, 以提高 KVCache 复用率.

为了调度所有这些解耦组件, Mooncake 在中心位置实现了名为 Conductor 的全局调度器.
Conductor 负责根据 KVCache 当前的分布和工作负载分派请求. 如果对未来推理有利, 它还会复制或换出部分 KVCache 块.
具体来说, [图 4](#figure-04) 展示了一个请求的典型工作流. Token 化结束后, Conductor 选择一组预填充节点和一个解码节点, 然后启动包含四个步骤的工作流:

<span id="figure-04"></span>

![推理实例的工作流](./mooncake/figure-04.png)

**图 4.** 推理实例的工作流. ($*$) 对预填充实例而言, KVCache 层的加载和存储操作会逐层执行, 并与预填充计算并行, 以减小传输开销 (见 [§ 5.2](#section-05-02)). ($\dagger$) 对解码实例而言, 异步加载与 GPU 解码并发执行, 避免 GPU 空闲.

**1) KVCache 复用:** 选定的预填充节点 (组) 接收请求, 其中包括原始输入, 可复用前缀缓存的块 ID, 以及为请求分配的完整缓存的块 ID. 它根据前缀缓存块 ID, 将前缀缓存从远端 CPU 内存加载到 GPU 内存, 以启动请求. 如果不存在前缀缓存, 则跳过此步骤. 选择过程要在三个目标之间取得平衡: 尽可能复用 KVCache, 平衡不同预填充节点的工作负载, 并保证 TTFT SLO.
这会形成以 KVCache 为中心的调度, 我们将在 [§ 6](#section-06) 中进一步讨论.

**2) 增量预填充:** 预填充节点 (组) 使用前缀缓存完成预填充阶段, 并将新生成的增量 KVCache 存回 CPU 内存. 如果未缓存输入 Token 的数量超过某个阈值 ($\mathit{prefill\_chunk}$), 预填充阶段会拆分成多个块, 以流水线方式执行. 该阈值的选择以充分利用对应 GPU 的计算能力为目标, 通常大于 1000 个 Token. [§ 5.1](#section-05-01) 解释了为什么使用分块但仍然解耦的预填充节点.

**3) KVCache 传输:** 每个节点都部署了前述 Messenger 服务, 用于管理和传输这些缓存. 每个 Messenger 都作为独立进程运行在相应的推理实例中, 接收信号以完成高速的跨机器 KVCache 传输. 此步骤异步执行, 并与上述增量预填充步骤重叠; 每个模型层生成的 KVCache 会流式传输到目标解码节点的 CPU 内存, 以缩短等待时间.

**4) 解码:** 所有 KVCache 都到达解码节点的 CPU DRAM 后, 请求以连续批处理方式加入下一个批次. Conductor 会根据当前负载预选解码节点, 以确保不违反 TBT SLO. 但是, 由于预填充阶段结束后预期负载可能已经变化, 本地调度器还会再次检查该 SLO. 这次复查可能导致请求被拒绝, 此时相应的预填充成本会被浪费.

## 4 采样的真实请求轨迹

为了便于进一步研究 LLM 服务, 我们从 1 小时的在线请求数据中采样一个子集, 创建了开源请求轨迹.
为了保留请求之间的缓存关系, 我们优先收集同一会话中的请求.

该轨迹数据集包含 23,608 条记录, 字段包括 *timestamp*, *input_length*, *output_length* 和 *hash_ids*.
我们收录了重新映射后的块哈希, 它们对分析和实现 KVCache 复用策略尤其有用.
据我们所知, 这是第一个可用于真实复用分析的开源数据集.

## 5 预填充池的实现

解码节点不可改动, 而设计独立弹性预填充池的必要性和最佳实践仍有争议.
例如, 许多研究者 [Pat23, Zho24, Hu24b] 与我们一样倾向使用解耦架构, 但引入分块预填充 [Agr24a] 后是否仍有必要分离, 值得讨论.
分块预填充将输入 Token 拆分为多个小块, 再让这些块加入连续批处理过程. 这种方法有两个明确的优点:
*1)* 不做分离时, 所有节点得到相同对待, 调度更简单;
*2)* 将分块预填充内联到解码批次中, 可以提高解码批次的计算强度, 从而获得更好的 MFU.

但是, 经过仔细权衡, 我们决定保留 Mooncake 的解耦架构. 只有当请求的预填充无需分块即可转发, 且不会损害 TBT SLO 时, 才会将其内联到解码批次中.
这一决定主要有两个原因:
*1)* 预填充节点需要采用不同的跨节点并行设置来处理长上下文 ([§ 5.1](#section-05-01)).
*2)* 这为节省 VRAM 提供了特殊机会 ([§ 5.2](#section-05-02)).

<span id="section-05-01"></span>

### 5.1 多节点预填充

近期 LLM 支持的上下文长度增长很快, 已从 8k 增长到 128K, 甚至 1M [Goo24a].
通常, 此类长上下文请求的输入 Token 数量可以达到输出 Token 的 10 到 100 倍, 因此优化 TTFT 十分重要.
长上下文预填充中存在丰富的并行性, 因而最好使用多个 8x GPU 节点并行处理, 而不是只用单个节点.
但是, 将张量并行 (TP) 扩展到多个节点后, 每层都需要执行两次成本高昂的 RDMA 全归约操作, 会显著降低预填充节点的 MFU.

最近, 许多工作提出了序列并行 (SP) [Sam23, Liu23, Bra23, Li23q, Kor22, Li23g, Fan24a].
SP 将请求的输入序列划分到不同节点, 以实现加速.
这些 SP 方法利用注意力算子的结合性; 在实现 Ring Attention [Liu23] 或 Striped Attention [Bra23] 时, 每层至少需要进行一次跨节点通信.
这样可以大幅减少网络消耗并提高 MFU.

但是, 与只使用单节点 TP 相比, 采用 SP 后的 MFU 仍然更差.
理想的部署方式会将预填充节点组织成两组: 一组只使用 TP, 另一组使用 SP.
只有在满足 TTFT SLO 确有必要时, 请求才会分派到 SP 组.
这种进一步解耦会带来动态调整各组节点数量的问题, 因为静态并行设置可能导致整个集群利用率偏低.
近期研究 [Wu24a] 提出弹性序列并行, 以动态扩大或缩小 SP 组.
这种方法虽然可行, 却会增加架构复杂度.
例如, 它要求预先建立全局通信组; 在调整过程中考虑缓存复用利用率和违反 SLO 要求等指标时, 也会使 Conductor 的设计更加复杂.
对于部署期间需要频繁即时扩缩容的场景, 这会造成很大困难.
同时, SP 仍然需要频繁的跨节点通信, 这既会降低 MFU, 又会与跨节点 KVCache 传输争用网络资源.

为解决这一问题, Mooncake 利用仅解码器 Transformer 的自回归特性, 为长上下文预填充实现了分块流水线并行 (CPP).
我们把预填充集群中每 X 个节点组成一个流水线预填充节点组.
对每个请求, 输入 Token 会被划分为若干块, 每块长度不超过 $\mathit{prefill\_chunk}$.
同一请求的不同块可以由不同节点同时处理, 从而并行完成处理并缩短 TTFT.

CPP 有两个主要优点: *1)* 与训练中的流水线并行类似, 它只需在每个流水线阶段的边界进行跨节点通信, 而且通信很容易与计算重叠. 这样可以提高 MFU, 并减少与 KVCache 传输之间的网络资源争用. *2)* 它自然适用于短上下文和长上下文, 不会为短上下文预填充带来明显开销, 也避免了频繁动态调整节点分区.
训练系统 [Li21b] 已经研究过这种基于流水线的加速方法, 但据我们所知, 由于长上下文推理直到最近才出现, 这是它首次用于推理阶段.

<span id="section-05-02"></span>

### 5.2 分层预填充

除计算能力外, 有限的 VRAM 空间也是宝贵资源, 我们希望尽量减少状态, 主要是 KVCache, 对 VRAM 的占用.
理论上, 如果一个请求的 KVCache 大小为 $S$, 处理时间为 $T$, 则其占用成本为 $S*T$.
如果请求被分块, 并且各块的处理通过分块预填充内联到其他解码请求中, $T$ 会增大, 因而占用成本也会增加.

<span id="figure-07"></span>

![不同请求长度下的 KVCache 存储延迟](./mooncake/figure-07.png)

**图 7.** 存储不同请求长度的 KVCache 所需的延迟 (分层延迟是指分层预填充与不存储 KVCache 的预填充之间的延迟差).

此外, 由于预填充逐层处理且受计算限制, KVCache 的传输和转储可以与计算重叠, 进一步降低占用成本.
在 Mooncake 中, KVCache 的加载和存储通过启动与等待操作异步执行. 每一层的注意力计算开始前, 模型会等待该层 KVCache 的异步加载完成, 并触发下一层 KVCache 的异步加载. 注意力计算完成后, 系统启动该层 KVCache 的异步存储. 所有层的计算结束后, 进程等待全部异步存储操作完成. 通过重叠传输, 预填充实例的执行时间可以大致等于 KVCache 加载时间或标准预填充时间, 具体取决于前缀缓存占输入长度的比例. [图 7](#figure-07) 所示的 KVCache 存储延迟实验结果表明, 分层预填充可以有效降低长上下文请求的延迟.

这种重叠效果的主要优点是, 只要 VRAM 能容纳单个请求, 我们在预填充调度中就可以不考虑可用 VRAM 大小.
如 [图 1](#figure-01) 所示, 预填充节点的调度只考虑 KVCache 分布和可用 DRAM 大小.

未来, 我们打算进一步利用这些空闲 VRAM. 例如, OpenAI 最近提出使用批处理 API [Ope24a], 用户能够以低 50% 的成本发送异步请求组, 但只有明确的 24 小时周转时间. 该服务适合处理不要求立即响应的作业. 这些批处理请求没有严格的 TBT 要求, 因此, 如果 VRAM 有足够空间容纳对应 KVCache, 我们甚至可以将它们的解码阶段内联到预填充处理中, 以获得更好的 MFU.

## 6 以 KVCache 为中心的调度

本节主要讨论 Conductor 在正常条件下如何调度请求和 KVCache 块, 过载场景留到下一节讨论.

<span id="algorithm-01"></span>

**算法 1: 以 KVCache 为中心的调度算法**

<div class="paper-algorithm">

- **输入:** 预填充实例池 $P$, 解码实例池 $D$, 请求 $R$, 缓存块大小 $B$.
- **输出:** 处理 $R$ 的预填充实例和解码实例 $(p,d)$.
- $\mathit{block\_keys} \leftarrow \mathrm{PrefixHash}(R.\mathit{prompt\_tokens}, B)$
- $\mathit{TTFT} \leftarrow \inf$
- $p \leftarrow \emptyset$
- $\mathit{best\_prefix\_len}, \mathit{best\_matched\_instance} \leftarrow \mathrm{FindBestPrefixMatch}(P, \mathit{block\_keys})$
- **对于** $\mathit{instance} \in P$:
  - $\mathit{prefix\_len} \leftarrow \mathit{instance.prefix\_len}$
  - $T_{\mathrm{queue}} \leftarrow \mathrm{EstimatePrefillQueueTime}(\mathit{instance})$
  - **如果** $\frac{\mathit{best\_prefix\_len}}{\mathit{prefix\_len}} < \mathit{kvcache\_balancing\_threshold}$: *(缓存感知的预填充调度)*
    - $T_{\mathrm{prefill}} \leftarrow \mathrm{EstimatePrefillExecutionTime}(\mathrm{len}(R.\mathit{prompt\_tokens}), \mathit{prefix\_len})$
    - **如果** $\mathit{TTFT} > T_{\mathrm{queue}} + T_{\mathrm{prefill}}$:
      - $\mathit{TTFT} \leftarrow T_{\mathrm{queue}} + T_{\mathrm{prefill}}$
      - $p \leftarrow \mathit{instance}$
  - **否则:** *(缓存感知且兼顾平衡的预填充调度)*
    - $\mathit{transfer\_len} \leftarrow \mathit{best\_prefix\_len} - \mathit{prefix\_len}$
    - $T_{\mathrm{transfer}} \leftarrow \mathrm{EstimateKVCacheTransferTime}(\mathit{instance}, \mathit{best\_matched\_instance}, \mathit{transfer\_len})$
    - $T_{\mathrm{prefill}} \leftarrow \mathrm{EstimatePrefillExecutionTime}(\mathrm{len}(R.\mathit{prompt\_tokens}), \mathit{best\_prefix\_len})$
    - **如果** $\mathit{TTFT} > T_{\mathrm{transfer}} + T_{\mathrm{queue}} + T_{\mathrm{prefill}}$:
      - $\mathit{TTFT} \leftarrow T_{\mathrm{transfer}} + T_{\mathrm{queue}} + T_{\mathrm{prefill}}$
      - $p \leftarrow \mathit{instance}$

  - **拒绝** $R$; **返回**
- **如果** $\frac{\mathit{best\_prefix\_len}}{p.\mathit{prefix\_len}} > \mathit{kvcache\_balancing\_threshold}$:
  - $\mathrm{TransferKVCache}(\mathit{best\_matched\_instance}, p)$ *(KVCache 热点迁移)*
- **返回** $(p,d)$

### 6.1 预填充全局调度

以往的 LLM 服务研究通常采用负载均衡策略, 根据分配的请求数评估各实例的负载. 但是, Mooncake 在选择预填充实例时还会考虑其他因素, 不仅包括负载, 也包括前缀缓存命中长度和可复用 KVCache 块的分布. 将请求路由到前缀缓存长度较长的预填充实例可以减少计算成本, 但为了保持整个系统的平衡并满足 TTFT SLO, 将请求调度到其他节点有时更有利. 为处理这些复杂因素, 我们提出缓存感知的全局调度算法, 同时考虑前缀缓存带来的预填充时间和实例负载对应的排队时间.

[算法 1](#algorithm-01) 详细说明了缓存感知预填充调度的机制. 对每个新请求, 输入 Token 会被划分成若干块, 每个块都会计算一个哈希键. 具体做法是, 将一个块中的 Token 与前一块的哈希键 (如果存在) 拼接, 再生成哈希键. 然后, 请求的块键会依次与每个预填充实例的缓存键比较, 以确定前缀匹配长度 ($\mathit{prefix\_len}$). vLLM 已经实现了类似的复用逻辑, 但开源版本的 vLLM 只支持本地 KVCache 缓存.

有了这些匹配信息, Conductor 会根据请求长度和 $\mathit{prefix\_len}$ (各实例的值不同) 估计相应的执行时间. 然后, 它加上该请求的预计等待时间, 得到请求在该实例上的 TTFT. 最后, Conductor 将请求分配给 TTFT 最短的实例, 并相应更新该实例的缓存时间和队列时间. 如果无法达到 SLO, Conductor 会直接向上层返回 HTTP 429 Too Many Requests 状态码.

该调度框架的骨架很直接, 复杂之处隐藏在各组件的工程实现中. 例如, 为预测一个请求在预填充阶段的计算时间, 我们采用从离线测试数据中得到的预测模型. 该模型根据请求长度和前缀缓存命中长度估计预填充时长. Transformer 的计算模式很有规律, 只要有足够的离线数据, 该预测的误差界就很小. 请求的排队时间通过汇总所有排队请求的预填充时间计算. 在实际实现中, TTFT 会并行计算, 因而处理时间与推理时间相比可以忽略.

传输时间的预测更困难, 因为它不仅取决于传输的数据大小, 还取决于当前网络状态, 尤其是发送节点是否拥塞. 这也使得复制热点 KVCache 块成为必要, 下一节将对此展开讨论.

<span id="section-06-02"></span>

### 6.2 缓存负载均衡

在 Mooncake 集群中, 每台预填充机器都管理自己的一组本地前缀缓存. 这些缓存的使用频率差异很大. 例如, 几乎每个请求都会访问系统提示词, 而存储某份本地长文档内容的缓存可能只有一个用户使用. 如 [§ 6.1](#section-06-01) 所述, Conductor 要在缓存匹配和实例负载之间达到最佳平衡, 它的作用至关重要. 因此, 从分布式缓存系统的角度看, 负载均衡也很重要. 具体来说, 系统需要制定缓存备份策略, 确保全局预填充调度既能获得高缓存命中率, 又能保持低负载.

这个 KVCache 调度问题的一种稻草人方案是收集每个块的全局使用情况, 用预测模型预测其未来使用情况, 再据此做出调度决策. 但是, 与估计预填充时间不同, 工作负载高度动态, 会随时间显著变化. 对用户规模快速增长的 MaaS 提供商而言尤其如此, 准确预测未来使用情况是不可能的. 因此, 我们提出基于启发式规则的自动热点迁移方案, 改善缓存负载均衡.

<span id="figure-08"></span>

![Mooncake 集群中的预填充调度实验](./mooncake/figure-08.png)

**图 8.** Mooncake 集群中的预填充调度实验.

如前所述, 当实例负载较高时, 请求不一定会被发往前缀缓存长度最长的预填充实例. 在这种情况下, 如果估计的额外预填充时间短于传输时间, Conductor 会将缓存位置和请求转发给另一个实例. 该实例主动从持有方获取 KVCache, 并将其存储在本地. 更重要的是, 如果最佳远端前缀匹配长度不大于当前本地可复用前缀与某个阈值的乘积, 我们倾向于直接计算输入 Token [+threshold] 这两种策略不仅能缩短请求的预填充时间, 还会自动复制热点缓存, 使它们可以更广泛地分布在多台机器上.

为验证策略的效果, 我们开展了调度实验, 将随机调度和负载均衡调度与我们的策略进行比较. 我们还比较了 [§ 6.1](#section-06-01) 所述的缓存感知调度, 以及本节所述兼顾缓存负载均衡的 KVCache 中心调度. 在随机调度中, 每个请求任意选择一个预填充实例. 在负载均衡调度中, 则选择负载最轻的实例. 为进行评估, 我们使用夜间空闲机器搭建了一个包含 8 个预填充实例和 8 个解码实例的 Mooncake 集群, 并在实验中重放了 23,000 个真实请求. 我们使用平均 TTFT 和 TTFT SLO 达标率评估各调度算法的性能. [图 8](#figure-08) 所示的实验结果表明, 缓存感知策略和缓存负载均衡策略都能显著降低请求的 TTFT. 我们以 KVCache 为中心的调度算法在两项指标上都优于随机调度和负载均衡调度. 更多实验结果见 [§ 8](#section-08).

## 7 面向过载的调度

现有大多数 LLM 服务工作都假定所有请求会得到处理, 并据此优化请求的吞吐量或 TTFT 和 TBT. 但是, 在真实场景中处理每个传入请求既不经济, 也不现实. 对于用户请求量迅速增长的商业推理服务, 集群推理资源的增长速度远慢于传入请求的增长速度. 因此, 过载是当前 LLM 服务中的常见问题, 在高峰时段尤其如此.

为了平衡成本和用户体验, 在系统负载达到预设阈值前, 系统应尽可能多地处理请求. 达到该点后, 其余请求会被直接拒绝或推迟到稍后重试. Mooncake 作为解耦推理系统, 可以采用更灵活的调度策略, 但也会遇到非解耦系统中不存在, 以往工作 [Pat23, Zho24, Hu24b] 也未提及的特殊调度问题.

本节介绍一种专门为解耦架构设计的提前拒绝策略, 并处理该方法造成的负载波动. 然后, 我们探讨为什么必须预测生成长度才能缓解这些问题.

<span id="section-07-01"></span>

### 7.1 过载场景中的调度

当系统发生过载时, 调度需要根据系统负载判断接受还是拒绝传入请求. 这一过程的一个核心问题是如何定义"系统负载", 因为该定义会影响拒绝请求的阈值. 在传统耦合系统中, 预填充阶段与解码阶段之间存在干扰, 因而 TTFT 和 TBT 的预测可能很复杂. 所以, 负载通常只用正在处理的请求数与系统最大容量之比衡量.

Mooncake 采用解耦架构, 独立处理预填充阶段和解码阶段. 因此, 我们直接用 SLO 满足情况衡量负载. 具体来说, 我们将 $l_{\mathrm{ttft}}$ 和 $l_{\mathrm{tbt}}$ 分别定义为请求的 TTFT 和 TBT SLO 约束. 预填充实例和解码实例的负载通过比较实例上预测的最大 TTFT 和 TBT 与 $l_{\mathrm{ttft}}$ 和 $l_{\mathrm{tbt}}$ 来确定. 有了这两个标准, Mooncake 的调度需要做出两个主要决定: 第一, 根据预填充实例的负载判断是否接受预填充阶段; 第二, 根据解码实例的负载判断是否继续执行解码阶段.

<span id="section-07-02"></span>

### 7.2 提前拒绝

在实际运行中, 预填充实例或解码实例的单独负载不能准确反映系统实际处理的请求数. 产生这一差异的原因是, 调度单个请求的预填充实例和解码实例之间存在时间差. 如果预填充阶段已经完成, 请求却因为负载过高而被解码实例拒绝, 预填充阶段消耗的计算资源就会浪费. 因此, 在预填充期间成功处理的实际请求数会少于负载指标显示的数量.

要解决这个问题, 很自然的做法是把解码实例的负载评估提前到预填充阶段开始之前. 我们将这一策略称为**提前拒绝**. 请求到达时, Conductor 根据预填充池和解码池中较高的负载, 评估是否接受请求. 提前拒绝能显著减少被拒请求带来的无效计算, 并改善负载均衡.

### 7.3 提前拒绝造成的负载波动

但是, 提前拒绝会带来新的问题. [图 9](#figure-09) 展示了在一个包含 20 台机器的集群中使用提前拒绝策略后, 观察到的 20 分钟真实实例负载. 图中显示预填充机器与解码机器之间存在明显的反相波动. 当集群中的预填充机器较少, 或预填充阶段耗时更长时, 这种现象会更加明显.

进一步研究后, 我们发现该负载波动问题源于预测解码负载与实际执行之间的时间差. 根据当前解码负载进行调度本身就存在延迟. 这种延迟会使预填充实例和解码实例的负载发生波动和相位错开, [图 10](#figure-10) 所述的理论示例展示了这一点. 绿色曲线表示预填充实例的负载 (缩放到 0 至 1), 黄色曲线表示解码实例的负载.

<span id="figure-10"></span>

![采用两种提前拒绝策略时的实例负载](./mooncake/figure-10.png)

**图 10.** 采用提前拒绝和基于预测的提前拒绝时的实例负载.

在阶段 1, 预填充实例和解码实例的负载都较低, 因此 Conductor 接受大量请求, 直到预填充实例达到负载上限. 在阶段 2, 预填充实例处理的请求被调度到解码实例, 使解码实例负载升高. 于是, Conductor 拒绝传入请求, 预填充实例的负载随之降低. 在阶段 3, 没有新请求进入解码阶段, 负载因而下降. 此时, Conductor 再次接受大量请求, 直到预填充实例满载. 在阶段 4, 随着解码实例负载上升, Conductor 拒绝请求, 使预填充实例保持低负载. 预填充实例与解码实例之间这种剧烈的负载波动会降低推理集群的资源利用率.

<span id="section-07-04"></span>

### 7.4 基于预测的提前拒绝

为解决负载波动问题, 我们提出基于预测的提前拒绝框架, 用于处理 Mooncake 这类解耦 LLM 服务系统在过载场景下的调度问题. 如 [图 10](#figure-10) 所示, 该框架预测传入请求经过预填充阶段后的解码负载, 再用预测结果判断是否接受请求, 从而缓解波动问题. 该策略的核心是准确预测下一时段的解码负载. 我们提出两种方法:

**请求级:** 以往工作指出, LLM 服务的负载预测面临一个重大问题: 每个请求的输出长度未知. 如果能提前确定输出长度, 就可以更准确地估计 TTFT 和 TBT. 这样便能预测一个解码实例可以完成的请求数, 以及指定时间后会新增的请求数, 从而得到该时刻的负载. 但是, 预测每个请求的输出长度成本很高 [Hu24b], 或者准确率较低; 在资源稀缺且需要准确预测的过载条件下尤其如此, 因而请求级预测十分困难.

**系统级:** 与请求级预测不同, 系统级预测不尝试预测单个请求的完成时间. 它估计指定时间后实例的整体批次数量或 TBT 状态. 此类预测持续进行, 对精度的要求较低, 因此更适合过载场景.

Mooncake 目前采用系统级预测策略: 我们假设每个请求的解码阶段耗时相同, 均为 $t_d$. 首先, 对给定时刻 $t$, 将预填充实例在 $t$ 时刻可以完成的请求加入统一的解码实例. 接着, 从解码实例中移除会在 $t$ 之前完成的请求 (即其执行时间超过 $t_d$). 最后, 计算所有解码实例的平均 TBT 与 $l_{\mathrm{tbt}}$ 之比, 以预测负载. 请求级预测留待未来研究.

### 8.2 过载场景下的性能

本节评估过载场景下的性能, 重点考察系统能够处理的最大请求数, 如 [§ 7](#section-07) 所述. 基线策略在两个阶段开始前根据负载拒绝请求, 但它会拒绝已经过预填充阶段处理的请求, 造成资源浪费. 相比之下, 我们提出提前拒绝和基于预测的提前拒绝策略, 分别详见 [§ 7.2](#section-07-02) 和 [§ 7.4](#section-07-04). 这些策略会综合考虑系统负载, 从而减少不必要的请求拒绝.

## 9 相关工作

研究者已经投入大量工作, 通过调度, 内存管理和资源优化提高 LLM 服务系统的效率.
FasterTransformer [Nvi19a], TensorRT-LLM [Ten23] 和 DeepSpeed Inference [Ami22] 等生产级系统旨在显著提高吞吐量.
Orca [Yu22a] 采用迭代级调度, 以便在不同阶段并发处理; vLLM [Kwo23] 则使用动态 KVCache 管理来优化内存.
FlexGen [She23], SARATHI [Agr24a] 和 FastServe [Wu23a] 引入新的调度和换入换出策略, 在有限硬件上有效分配工作负载, 这些优化通常可以相互补充.

Mooncake 的设计建立在这些进展之上, 尤其受益于 vLLM 开源社区, 对此我们深表感谢.

近期研究也认同我们分离预填充阶段和解码阶段的观点, 由此形成提高系统吞吐量的解耦架构. Splitwise [Pat23] 在 arXiv 上发表时, Mooncake 尚处于开发早期, 这进一步推动了我们的进展. 许多同期工作印证了我们的发现, 包括 DistServe [Zho24] 和 TetriInfer [Hu24b]: DistServe 优化各阶段的资源分配和并行策略, 以最大化 GPU 有效吞吐量; TetriInfer 同时采用分块预填充, 两阶段解耦和预测式两阶段调度算法, 以优化资源利用率.

前缀缓存也得到广泛采用, 它使 KVCache 可以在多个请求间复用, 减少 LLM 推理系统的计算开销 [Ten23, Kwo23]. Prompt Cache [Gim24] 会在推理服务器上预先计算并存储常用文本的 KVCache, 便于复用并显著降低推理延迟. SGLang [Zhe24] 采用 RadixAttention, 它在基数树结构中使用最近最少使用 (LRU) 缓存, 从而针对各种复用模式高效地实现自动共享.

在这些方法中, 与我们同期的 AttentionStore [Gao24a] 提出分层 KVCache 系统, 使用低成本内存和存储介质容纳所有请求的 KVCache. Mooncake 的架构与 AttentionStore 有许多相同的设计选择. 但是, 在长上下文推理中, KVCache 会变得极大, 既需要高容量和高效数据传输, 也需要以 KVCache 为中心的全局调度.
同时, Mooncake 不是独立的缓存服务; 它同时包含节省内存的缓存存储机制和缓存感知调度策略, 进一步提高前缀缓存效率.

近期研究 [Sri24] 还开始探索提示词调度, 其本质就是以 KVCache 为中心的调度. 我们印证了该领域的许多结果, 但在线轨迹中的真实可复用率远低于开源基准复现的结果. 理论上, 即使假设存储容量和 TTFT SLO 都无限, 当前工作负载中最多也只有 50% 的 KVCache 可以复用. 但是, 可复用率高度依赖应用场景; 在某些场景中, 例如我们的论文对话服务 [https://papers.cool/](https://papers.cool/), 它可以达到 90%. 我们还强调, 调度需要受 SLO 约束并面向过载, 不能只考虑吞吐量.

## 10 未来工作

将 LLM 服务的不同部分解耦为专用资源池, 是 Mooncake 获得高资源利用率的关键.
未来, 我们计划沿这一路径探索更多机会, 尤其是使用异构加速器的可能性.
当前的旗舰加速器会在计算能力, 内存带宽和容量等多项指标之间取舍, 因此用途广泛, 却无法在每一项指标上都达到最佳.
例如, 如果只考虑单位成本带宽或单位功耗带宽, 当前的 GDDR 乃至 LPDDR 方案可以比旗舰加速器高一个数量级.
我们还特别关注使用存内处理 [Yan20b, Lag21, Li23r, Sri23a] 或混合键合 [Akb24, Kor23, Zha13, Zha17a, Kim16a] 技术实现面向内存设备的新方案, 此类设备近期或许能同时提供高带宽和高容量.
这些技术很适合降低解码阶段执行内存受限操作的成本.

在同时包含计算型加速器和带宽型加速器的异构加速器环境中, 我们还可以探索更先进的解耦架构.
例如, 与其他线性变换算子不同, 解码阶段注意力算子的算术强度只与注意力头数除以键/值头数所得的比值成正比.
增加批量大小无法提高这一强度, 而且它通常比其他算子更受内存限制.
因此, 可以将注意力算子与其他线性算子分离, 进一步提高资源利用率.
我们的初步模拟结果 [Che24e] 表明, 该架构很有希望提高整体吞吐量.
DeepSeek-v2 [Dee24] 最近提出的 MLA 算子则直接提高算术强度, 从另一个角度解决该问题, 也展现出很大潜力.

与此正交的另一个方向是, 许多算法试图减小 KVCache 的大小, 这会从两个重要方面使 Mooncake 受益: 1) 增加批量大小以提高利用率; 2) 提高 KVCache 缓存命中率以降低预填充成本.
该领域目前十分活跃, 包括压缩 KVCache 的不同方法 [Yu24, Cai24b, Liu24c, He24a, Liu24a, Liu24m], 按各种指标选择重要 Token [Guo24a, Dev24, Yao24a, Yan24f, Adn24, Li24c, Zha23g], 在不同层之间共享 KVCache [Zuh24, Wu24, Cha23b], 以及采用含有不使用 KVCache 算子的混合架构 [Sun24b, Gu23, Pen23b, Dao24, Lie24, Bot24].

在调度方面, 我们正在开发一项高级策略, 以考虑不同的请求优先级和具有不同 TTFT/TBT SLO 的场景.
该策略旨在提高系统面对各种运行条件时的响应能力和效率.
有效管理 KVCache 对优化缓存复用同样至关重要, 其中包括复制, 迁移, 以及针对部分命中和过期场景的专用淘汰策略.
我们还计划动态平衡预填充实例和解码实例, 并研究通过面向批处理的卸载任务利用空闲资源的策略.
这种方法使我们能够在工作负载波动期间最大化资源利用率.

## 11 结论

本文提出 Mooncake, 一种以 KVCache 为中心的解耦架构, 用于高效服务 LLM, 尤其适合处理长上下文和过载场景. 我们讨论了在满足延迟相关 SLO 要求的同时最大化整体有效吞吐量时涉及的必要性, 问题和设计选择.
