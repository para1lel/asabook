## 摘要

近期, 用于生成任务的大规模 Transformer 模型 (例如 GPT-3) 受到广泛关注, 这凸显了为此类模型提供服务支持的必要性. 由于这些模型以自回归方式生成下一个标记, 处理一个推理请求时必须多次运行模型, 模型的每次迭代为该请求生成一个输出标记. 然而, 现有推理服务系统在处理这种具有多次迭代特征的工作负载时表现不佳, 原因是其调度机制不够灵活, 无法改变当前正在处理的请求批次; 批次中较早完成的请求不能返回客户端, 而新到达的请求必须等待当前批次完全结束.

本文提出迭代级调度 (iteration-level scheduling), 一种以迭代粒度而非请求粒度调度执行的新机制, 其中调度器调用执行引擎, 仅在批次上运行模型的一次迭代. 此外, 为了同时在 Transformer 模型上应用批处理和迭代级调度, 我们提出选择性批处理 (selective batching), 只对选定的一组操作应用批处理. 基于这两项技术, 我们实现了分布式服务系统 ORCA, 并加入了支持数千亿参数模型扩展的设计. 在 GPT-3 175B 模型上的评估表明, ORCA 在延迟和吞吐量方面都能显著超过 NVIDIA FasterTransformer: 在相同延迟水平下吞吐量提升 36.9×.

## 1 引言

语言生成任务正成为聊天机器人 [Orc09, Orc52]、摘要 [Orc41, Orc45, Orc54]、代码生成 [Orc13] 和图像描述生成 [Orc65, Orc66] 等多种应用的重要组成部分. 此外, AI21 Labs [Orc37]、DeepMind [Orc26, Orc48]、Google [Orc15, Orc21, Orc63]、Meta Platforms [Orc10, Orc67]、Microsoft [Orc50]、Microsoft & NVIDIA [Orc59] 以及 OpenAI [Orc12] 发布的近期工作表明, 包括翻译 [Orc11, Orc17]、分类 [Orc20, Orc53]、问答 [Orc32, Orc33, Orc40] 在内的每类语言处理任务都可以转化为语言生成问题, 并且沿着这一方向取得了显著改进. 生成模型的兴起并不局限于语言领域; AI 社区也越来越关注图像、视频、语音或多个领域混合等其他领域的生成问题 [Orc19, Orc38, Orc51, Orc62]. 生成模型的核心是 Transformer 架构 [Orc60] 及其变体 [Orc15, Orc47, Orc48, Orc49]. Transformer 模型依靠注意力机制 [Orc60] 学习更好的表示, 使序列中的每个元素都可以与其他元素直接连接, 这是循环模型 [Orc25] 无法做到的.

为了在现实应用中使用生成模型, 我们通常把推理过程交给一个独立服务, 由它负责 ML 推理服务. 这类服务需要以低延迟和高吞吐量为客户端请求提供推理结果, 对它的需求增长推动了 Triton Inference Server [Orc07] 和 TensorFlow Serving [Orc42] 等推理服务系统的发展. 这些系统可以使用独立开发的 DNN 执行引擎来执行实际的张量操作. 例如, 我们可以组合 Triton 和 FasterTransformer [Orc04], 后者是一个针对 Transformer 模型推理优化的执行引擎, 来部署语言生成服务. 在这种组合中, Triton 主要负责把多个客户端请求组成批次, 而 FasterTransformer 从 Triton 接收批次并以批处理方式执行推理.

遗憾的是, 我们发现现有推理系统, 包括服务系统层和执行引擎层, 在处理 Transformer 生成模型的请求时都存在局限. 这些模型以自回归方式生成下一个标记, 因而应该运行与待生成标记数相同的次数; 而对于 ResNet [Orc24] 和 BERT [Orc18] 等其他模型, 一个请求运行一次模型即可处理. 也就是说, 处理生成模型的请求时必须多次迭代模型; 每次迭代生成一个输出标记, 该标记会作为下一次迭代的输入. 这种多次迭代特征使当前推理系统的设计受到质疑, 因为服务系统以请求粒度调度执行引擎. 在这种设计下, 服务系统把一批请求发送给引擎后, 引擎会在处理完批次中的所有请求后一次性返回整个批次的推理结果. 由于不同客户端请求可能需要不同的迭代次数, 批次中较早完成的请求不能返回客户端, 从而增加延迟. 在批次派发后到达的请求也必须等待批次处理完成, 这会显著增加请求的排队时间.

本文提出以迭代粒度而非请求粒度调度执行引擎. 具体来说, 服务系统调用引擎, 仅在批次上运行模型的一次迭代. 这样, 新到达的请求只需等待一次模型迭代就有机会被处理. 服务系统在引擎每次返回后检查请求是否完成, 因而已完成的请求也可以立即返回客户端.

不过, 同时应用批处理和迭代级调度会带来一个显著挑战. 与传统的请求级调度不同, 新调度方式可能发出一个请求批次, 其中每个请求目前已经处理的标记数不同. 在这种情况下, Transformer 模型无法以批处理方式处理这些请求, 因为注意力机制包含不可批处理的张量操作, 其输入张量的形状取决于已处理标记数而可能不同.

为了解决这一挑战, 我们建议只对选定的一组操作应用批处理, 并将其称为选择性批处理. 选择性批处理考虑不同操作的特征, 将批次拆分, 对每个请求分别执行 Attention [+1] 操作, 同时对 Transformer 模型的其他操作应用批处理. 我们观察到, 不对 Attention 操作的执行进行批处理只会对效率产生很小影响. 由于 Attention 操作不涉及任何模型参数, 对 Attention 应用批处理无法通过在多个请求之间复用已加载参数来减少 GPU 内存读取量.

基于这些技术, 我们设计并实现了面向 Transformer 生成模型的分布式服务系统 ORCA. 为了处理大规模模型, ORCA 采用了层内并行和层间并行等并行策略, 这些策略最初由 Transformer 训练系统 [Orc55, Orc58] 开发. 我们还为所提出的迭代级调度设计了新的调度算法, 并额外考虑内存管理和跨工作进程的流水线执行.

我们使用不同配置的 OpenAI GPT-3 [Orc12] 模型评估 ORCA, 参数规模最高达到 341B. 结果表明, ORCA 显著超过 FasterTransformer [Orc04], 在相同延迟水平下吞吐量提升 36.9×. 尽管本文始终以语言模型为主要示例, 实验也只在语言模型上进行, 但只要其他领域的生成模型基于 Transformer 架构并采用自回归生成过程 [Orc19, Orc38, Orc51, Orc62], 就能从我们的方法中受益.

## 2 背景

我们介绍 GPT [Orc12, Orc47] 的推理过程, 它是本文贯穿使用的 Transformer 生成模型代表性示例, 以及 ML 推理服务系统.

**GPT 的推理过程.** GPT 是一种基于 Transformer [Orc60] 某个架构变体的自回归语言模型. 它以文本为输入并生成新的文本作为输出. 具体而言, 模型接收一系列输入标记, 然后通过生成后续输出标记来补全序列. [图 1a](#figure-01) 展示了一个简化的计算图, 它表示一个三层 GPT 模型的这一过程, 其中节点和边分别表示 Transformer 层及层之间的依赖关系. Transformer 层按照节点上的数字所示的顺序执行, 使用同一组模型参数的节点 (即表示同一层的节点) 填充相同颜色.

生成的输出标记会反馈给模型以生成下一个输出标记, 形成顺序的逐个标记推理过程. 生成单个标记的这一自回归过程, 是将输入送入模型的所有层来完成的, 输入可以是客户端提供的一系列标记, 也可以是之前生成的输出标记. 我们将运行所有层称为模型的一次迭代. 在 [图 1a](#figure-01) 的示例中, 推理过程包含三次迭代. 第一次迭代 ("iter 1") 一次性接收所有输入标记 ("I think this"), 并生成下一个标记 ("is"). 这次迭代构成初始化阶段, 负责处理输入标记并生成第一个输出标记. 接下来的两次迭代 ("iter 2" 和 "iter 3") 构成增量阶段, 接收前一次迭代的输出标记并生成下一个标记.

在这个例子中, "iter 3" 生成特殊的序列结束标记 "&lt;EOS&gt;", 因而是终止输出生成的最后一次迭代. 增量阶段包含多次迭代, 因为每次迭代只能处理一个标记; 相比之下, 初始化阶段通常通过并行处理所有输入标记实现为一次迭代. 原始 Transformer [Orc60] 使用两组 Transformer 层, 而 GPT 的架构只有一组层, 即 decoder. [图 1b](#figure-01) 展示了 GPT 使用的一个 Transformer 层. 在组成 Transformer 层的操作中, Attention 是区别 Transformer 与其他架构的核心. 从高层看, Attention 操作计算感兴趣标记的加权平均, 使序列中的每个标记都能感知其他标记. 它接收 query、key 和 value 三个输入, 计算当前标记的 query 与感兴趣标记的所有 key 的点积, 对点积应用 Softmax 得到权重, 然后对与这些权重对应的所有 value 做加权平均.

**图 1.** GPT 推理过程、Transformer 层和内部状态使用示意图.

由于 Attention 需要所有前序标记的 key 和 value, [+2] 我们把 key 和 value 视为必须跨多次迭代维护的内部状态. 一个朴素的无状态推理过程会在每次迭代重新计算序列中的所有标记 (包括客户端提供的输入标记和目前生成的输出标记) 的 key 和 value. 为避免这种重复计算, fairseq [Orc43] 提出了增量解码, 保存 key 和 value 以便在后续迭代中复用. FasterTransformer [Orc04] 和 Megatron-LM [Orc03] 等其他 Transformer 系统也采用相同方法.

[图 1c](#figure-01) 展示了 Transformer 的状态使用模式, 以及同样维护内部状态的 LSTM [Orc25]. 主要区别在于, Transformer 中状态的大小 (Attention key 为 $k$, value 为 $v$) 随迭代增加, 而 LSTM 中状态的大小 (内部 memory 为 $c$, LSTM 层输入/输出为 $h$) 保持不变. 处理索引为 $t$ 的标记时, Attention 操作会接收所有前序 Attention key $k_{l,1:t-1}$ 和 value $v_{l,1:t-1}$, 以及当前 key $k_{l,t}$ 和 value $v_{l,t}$. [+3] 因此, Attention 操作必须根据已经处理的标记数, 在不同形状的张量上执行计算.

在 Attention 操作之前, 依次是层归一化操作 (LayerNorm) 和 QKV Linear (用于获取 query、key、value 的线性和拆分操作). Attention 之后的操作依次为线性操作 (Attn Out Linear)、用于残差连接的加法操作 (Add)、层归一化操作 (LayerNorm)、多层感知机 (MLP) 操作以及另一个残差连接操作 (Add).

**ML 推理服务系统.** ML 驱动应用需求的增长, 使 ML 推理服务成为现代数据中心的一项关键工作负载. 用户 (应用的终端用户或内部微服务) 向推理服务提交请求, 服务使用配置的 ML 模型和已分配的资源返回请求结果, 其资源通常配备 GPU 和 TPU 等专用加速器. 具体而言, 服务运行 DNN 模型并使用输入数据为请求生成输出. 与数据中心中的其他服务一样, 管理良好的推理服务应在合理成本内提供低延迟和高吞吐量.

为了满足这些约束, 服务运营者经常使用 Triton Inference Server [Orc07] 和 TensorFlow Serving [Orc42] 等 ML 推理服务系统. 这些系统可以看作位于底层模型执行引擎之上的抽象层, 底层引擎包括 TensorRT [Orc06]、TVM [Orc14]、TensorFlow [Orc08] 以及许多其他系统 [Orc44, Orc46]. 它们不依赖具体的 ML 模型、执行引擎或计算硬件. 服务系统把主要数学操作交给引擎, 自身负责提供接收推理请求的端点、调度引擎执行并向请求发送响应. 因此, 这些系统关注执行批处理 [Orc07, Orc16, Orc35, Orc42, Orc56]、从多个模型变体中选择合适模型 [Orc16, Orc27, Orc30, Orc57]、在同一设备上部署多个模型 (分别对应不同推理服务) [Orc07, Orc29, Orc35, Orc56] 等方面.

在服务系统提供的功能和优化中, 使用 GPU 等加速器时, 批处理是实现高加速器利用率的关键. 启用批处理运行执行引擎时, 来自多个请求的输入张量会在送入模型第一个操作前合并为一个大的输入张量. 加速器更偏好大输入张量, 因为这样可以更好地利用大量并行计算单元, 所以引擎吞吐量高度依赖批次大小, 即引擎共同处理的推理请求数. 对于涉及内存密集型操作的模型, 批处理执行还可以复用从片外内存加载的模型参数.

[图 2](#figure-02) 展示了使用现有服务系统和执行引擎为生成式语言模型提供服务的总体流程. 服务系统的主要组件 (例如 Triton [Orc07]) 是调度器, 负责从队列取出请求组成批次, 并调度执行引擎 (例如 FasterTransformer [Orc04]) 处理该批次. 执行引擎运行所服务模型的多次迭代, 然后把生成的文本返回服务系统. 在 [图 2](#figure-02) 中, 服务系统调度引擎批处理两个请求 ($x_1$: "I think", $x_2$: "I love"), 引擎分别为请求 $x_1$ 和 $x_2$ 生成 "this is great" 和 "you".

## 3 挑战与解决方案

本节描述服务 Transformer 生成模型时的挑战, 并提出两项技术: 迭代级调度和选择性批处理.

**C1: 提前完成和后加入的请求.** 现有系统的一个主要局限是, 服务系统和执行引擎只有在以下时机才会交互: (1) 服务系统在空闲引擎上调度下一个批次; 或 (2) 引擎完成当前批次的处理. 换句话说, 这些系统以请求粒度调度执行, 引擎会固定一个请求批次, 直到批次中的所有请求都完成. 这在服务生成模型时会造成问题, 因为批次中的每个请求可能需要不同的迭代次数, 从而有些请求会早于其他请求完成.

在 [图 3](#figure-03) 所示的例子中, 尽管请求 $x_2$ 早于请求 $x_1$ 完成, 引擎仍在所有迭代中对 "active" 和 "inactive" 请求执行计算. 对 inactive 请求的额外计算 ($x_2$ 在 iter 3 和 4 中) 限制了批处理执行的效率. 更糟糕的是, 这种行为阻止已完成请求提前返回客户端, 带来了大量额外延迟. 这是因为引擎只有在完成批次中所有请求的处理后才把执行结果返回服务系统. 同样, 当新请求在当前批次执行中途到达时, 前述调度机制会使新请求一直等待, 直到当前批次中的所有请求完成. 我们认为, 当前的请求级调度机制无法高效处理具有多次迭代特征的工作负载. 注意, 提前完成和后加入请求的问题不会出现在语言模型训练中; 训练过程使用 teacher forcing 技术 [Orc64], 在一次迭代中完成整个批次的处理.

![输入长度相同但完成时间不同的请求](./orca/figure-03.png)

**图 3.** 请求输入长度相同但部分请求较早完成的示例. 阴影标记表示输入标记. "-" 表示调度机制带来的额外计算输入和输出.

**S1: 迭代级调度.** 为了解决上述局限, 我们提出以迭代粒度调度执行. 从高层看, 调度器重复以下过程: (1) 选择下一步运行的请求; (2) 调用引擎, 为选定请求执行一次迭代; (3) 接收该次调度迭代的执行结果. 由于调度器每次迭代都能收到返回结果, 它可以检测请求是否完成, 并立即把生成的标记返回客户端. 对于新到达的请求, 在当前调度迭代执行后, 请求就有机会开始处理 (即调度器可能在下一步选择它), 从而显著减少排队延迟. 采用迭代级调度后, 调度器可以完全控制每次迭代处理多少请求以及处理哪些请求.

[图 4](#figure-04) 展示了 ORCA 使用迭代级调度时的系统架构和总体流程. ORCA 提供一个端点 (例如 HTTPS 或 gRPC), 推理请求从这里进入系统, 响应也从这里发出. 端点把新到达的请求放入请求池, 该组件在请求生命周期内管理系统中的所有请求. 请求池由调度器监视, 调度器负责: 从请求池选择一组请求, 调度执行引擎在这组请求上运行一次模型迭代, 接收执行结果 (即输出标记), 并将每个输出标记追加到对应请求来更新请求池. 引擎是执行实际张量操作的抽象, 这些操作可以并行分布到多台机器上的多个 GPU. 在 [图 4](#figure-04) 的示例中, 调度器与请求池交互, 决定下一步处理哪些请求, 并调用引擎运行四个选定请求: ($x_1$, $x_2$, $x_3$, $x_4$). 调度器向引擎提供首次调度请求的输入标记. 在此例中, $x_3$ 和 $x_4$ 尚未运行任何迭代, 所以调度器分别为 $x_3$ 交付 ($x_{31}$, $x_{32}$), 为 $x_4$ 交付 ($x_{41}$, $x_{42}$, $x_{43}$). 引擎在四个请求上运行一次模型迭代, 返回每个请求一个生成的输出标记 ($x_{15}$, $x_{23}$, $x_{33}$, $x_{44}$). 请求处理完成后, 请求池移除该请求并通知端点发送响应. 与 [图 2](#figure-02) 中必须在调度批次上运行多次迭代, 直到其中所有请求都完成的方法不同, ORCA 调度器可以在每次迭代改变要处理的请求. 我们会在 [第 4.2 节](#S4.SS2) 介绍每次迭代选择请求的具体算法.

**C2: 批处理任意请求集合.** 实际使用迭代级调度时, 我们面临的一个主要挑战是批处理. 为了达到高效率, 执行引擎应能以批处理方式处理任意选定的请求集合. 如果不进行批处理, 就必须逐个处理选定的请求, 无法利用 GPU 的大规模并行计算能力.

遗憾的是, 即使对于一对请求 ($x_i$, $x_j$), 也无法保证下一次迭代能够合并执行并替换为批处理版本. 对于一对请求, 下一次迭代不能一起批处理有三种情况: (1) 两个请求都处于初始化阶段, 但输入标记数不同 (例如 [图 4](#figure-04) 中的 $x_3$ 和 $x_4$); (2) 两个请求都处于增量阶段, 但各自处理的标记索引不同 ($x_1$ 和 $x_2$); 或 (3) 两个请求处于不同阶段: 初始化或增量 ($x_1$ 和 $x_3$). 要以批处理方式执行多个请求, 每个请求的执行必须由相同操作组成, 且每个操作消耗形状相同的输入张量. 在第一种情况下, 两个请求不能批处理, 因为输入张量的 "length" 维度 (即输入标记数) 不相等. 第二种情况下, 两个请求的 Attention key 和 value 张量形状不同, 因为它们处理的标记索引不同, 如 [图 1c](#figure-01) 所示. 对于第三种情况, 不同阶段的迭代不能批处理, 因为它们接收的输入标记数不同; 初始化阶段的一次迭代会并行处理所有输入标记以提高效率, 而增量阶段的每次迭代只接收一个标记作为输入 (我们假设使用 fairseq 风格的增量解码 [Orc43]).

只有当两个选定请求处于同一阶段, 且输入标记数相同 (初始化阶段) 或标记索引相同 (增量阶段) 时, 才能应用批处理. 这一限制显著降低了现实工作负载中形成批次的可能性,

**S2: 选择性批处理.** 我们提出选择性批处理, 这是一种灵活组成请求批次的批处理执行技术. 它不对组成模型的所有张量操作进行 "批量化", 而是只对少数操作选择性地应用批处理.

上述批处理问题的核心在于, 前述三种情况 [+4] 对应不规则形状的输入 (或状态) 张量, 这些张量无法合并成一个大张量并输入批处理操作. 在传统批处理机制中, Transformer 层每次迭代接收形状为 $[B, L, H]$ 的三维输入张量, 该张量由批次中多个请求的 $[L, H]$ 输入张量拼接而成, 其中 $B$ 是批次大小, $L$ 是共同处理的标记数, $H$ 是模型的隐藏大小. 例如, [图 3](#figure-03) 中的 "iter 1" (初始化阶段) 接收形状为 $[2, 2, H]$ 的输入张量, "iter 2" (增量阶段) 接收形状为 $[2, 1, H]$ 的张量. 但是, 当调度器决定在 [图 4](#figure-04) 的批次 ($x_1$, $x_2$, $x_3$, $x_4$) 上运行一次迭代时, 初始化阶段请求的输入 ($x_3$: $[2, H]$, $x_4$: $[3, H]$) 无法合并为形状 $[B, L, H]$ 的单个张量, 因为 $x_3$ 和 $x_4$ 的输入标记数不同, 分别为 2 和 3.

有趣的是, 并非所有操作都无法处理这种不规则形状张量. 通过将张量展平, 可以让非 Attention 矩阵乘法和层归一化等操作处理不规则形状的张量.

例如, 上述 $x_3$ 和 $x_4$ 的输入张量可以组成形状为 $[\sum L, H] = [5, H]$ 的二维张量, 不需要显式的批次维度. 由于 Linear、Layer-Norm、Add 和 GeLU 等非 Attention 操作不需要区分不同请求的张量元素, 该张量可以输入这些操作. 另一方面, Attention 操作需要请求的概念 (即需要批次维度), 以便只在同一请求的标记之间计算注意力, 通常通过调用 cuBLAS 的批量矩阵乘法例程完成.

选择性批处理感知每个操作的不同特征; 它拆分批次, 对 Attention 操作分别处理每个请求, 同时对不需要请求概念的其他操作应用按标记 (而非按请求) 的批处理. [图 5](#figure-05) 展示了它如何处理 [图 4](#figure-04) 所述的请求批次 ($x_1$, $x_2$, $x_3$, $x_4$). 该批次有 7 个输入标记需要处理, 因而我们让输入张量形状为 $[7, H]$, 并应用非 Attention 操作. 在 Attention 操作之前, 插入 Split 操作, 对每个请求的拆分张量分别运行 Attention 操作. 然后通过 Merge 操作, 把 Attention 操作的输出重新合并成形状为 $[7, H]$ 的张量, 让其余操作恢复批处理功能.

为了让增量阶段的请求使用前几次迭代处理过的标记的 Attention key 和 value, ORCA 在 Attention K/V manager 中维护生成的 key 和 value. 管理器为每个请求分别维护这些 key 和 value, 直到调度器明确要求移除某个请求的 key 和 value, 即该请求完成处理. 增量阶段请求 ($x_1$ 和 $x_2$) 的 Attention 操作从管理器取得前序标记的 key 和 value ($x_{11}$、$x_{12}$、$x_{13}$ 属于 $x_1$; $x_{21}$ 属于 $x_2$), 再结合 Split 操作提供的当前标记 query、key 和 value, 计算当前标记与前序标记之间的注意力.

## 4 ORCA 设计

基于上述技术, 我们设计并实现了面向 Transformer 生成模型的分布式服务系统 ORCA. 在介绍 [图 4](#figure-04) 时, 我们已经讨论了 ORCA 的系统组件和总体执行模型. 本节回答如何构建高效系统, 使其能够扩展到拥有数千亿参数的大规模模型, 并介绍迭代级调度的调度算法, 即每次迭代如何从请求池选择一个请求批次.

### 4.1 分布式架构

近期工作 [Orc12, Orc31] 表明, 扩展语言模型可以显著提高模型质量. 因此, 为这类大语言模型提供服务的系统支持变得越来越重要, 尤其是在模型无法容纳于单个 GPU 时. 此时, 应将模型参数及其对应计算拆分, 分布到多个 GPU 和机器上.

ORCA 组合了 Transformer 模型的已知并行技术: 层内并行和层间并行. 这两种模型并行策略也被 FasterTransformer [Orc04] 使用, 最初是为分布式训练开发的. 层内并行 [Orc55, Orc58] 将矩阵乘法 (即 Linear 和 Attention 操作) 及其相关参数拆分到多个 GPU 上. 我们省略这种策略如何划分每个矩阵乘法的细节. 另一方面, 层间并行将 Transformer 层拆分到多个 GPU 上. ORCA 为每个 GPU 分配相同数量的 Transformer 层. [图 6](#figure-06) 展示了在一个 4 层 GPT 模型上应用层内和层间并行的示例. 4 层被拆分为 2 个层间分区, 每个分区中的层再被划分为 3 个层内分区. 我们把每个分区分配给一个 GPU, 总共使用 6 个 GPU.

ORCA 执行引擎使用上述技术支持分布式执行. [图 7](#figure-07) 展示了 ORCA 引擎的架构. 每个 worker 进程负责模型的一个层间分区, 并且可以放置在不同的机器上. 具体来说, 每个 worker 管理一个或多个 CPU 线程, 每个线程专门负责控制一个 GPU, 线程数取决于层内并行度.

ORCA 执行引擎的执行过程如下. 引擎被调度为一个请求批次运行一次模型迭代后, 引擎 master 将有关该调度批次的信息转发给第一个 worker 进程 (Worker1). 这些信息包括当前迭代的标记和控制消息, 控制消息由批次内请求的 id、当前标记索引 (增量阶段请求) 以及输入标记数 (初始化阶段请求) 组成. Worker1 的 controller 将从引擎 master 收到的信息交给控制 GPU 的线程, 每个线程解析信息并向关联 GPU 发出适当的 GPU kernel. 例如, Attention 操作的 kernel 使用请求 id 和当前标记索引, 获取 Attention K/V manager 中保存的前序 key 和 value 的 GPU 内存地址. 同时, controller 也把控制消息转发给下一个 worker (Worker2) 的 controller, 不等待 Worker1 GPU 上发出的 kernel 完成. 与 Worker1 不同, 最后一个 worker (Worker2) 的 controller 会等待 (即与之同步) GPU kernel 完成, 以获取每个请求的输出标记并将标记发送回引擎 master.

为了尽可能让 GPU 保持繁忙, 我们设计 ORCA 引擎以最小化 CPU 和 GPU 之间的同步. 我们观察到, 当前的分布式推理系统 (例如 FasterTransformer [Orc04] 和 Megatron-LM [Orc03]) 在每个进程接收控制消息 [+5] 时都会进行 CPU-GPU 同步, 因为它们通过 GPU 到 GPU 的通信通道 —NCCL [Orc05] 交换消息. 这些控制消息每次迭代都要交换, 带来不可忽略的性能开销. 相比之下, ORCA 将控制消息 (加上标记) 和张量数据传输使用的通信通道分开, 避免对 CPU 使用的数据调用 NCCL. [图 7](#figure-07) 表明, ORCA 引擎只使用 NCCL 交换中间张量数据 (用虚线箭头表示), 因为这些数据由 GPU 产生和消费. 控制消息由 CPU 线程用于发出 GPU kernel, 在引擎 master 和 worker controller 之间通过不涉及 GPU 的独立通信通道 (例如 gRPC [Orc02]) 发送.

### 4.2 调度算法

ORCA 调度器决定每次迭代应选择和处理哪些请求. 选择性批处理技术允许引擎以批处理方式运行任意请求集合, 因此调度器在组成批次时具有很高的灵活性. 现在剩下的主要问题是如何在每次迭代选择请求.

我们让 ORCA 调度器使用一个简单算法, 不改变客户端请求的处理顺序; 先到达的请求先处理. 也就是说, 我们保证迭代级的先到先服务 (FCFS) 属性. 对于具有多次迭代特征的工作负载, 我们将迭代级 FCFS 定义如下: 对于请求池中的任意一对请求 ($x_i$, $x_j$), 如果 $x_i$ 比 $x_j$ 更早到达, 那么 $x_i$ 运行的迭代次数应不小于 $x_j$. 注意, 如果晚到请求需要更少的迭代才能完成, 它可能比早到请求更早返回客户端.

此外, 调度器还需考虑其他因素: 增大批次大小的收益递减以及 GPU 内存约束. 增大批次大小会以更高延迟换取更高吞吐量, 但批次变大后, 回报 (即吞吐量的增幅) 会递减. 因此, 与其他服务系统 [Orc07, Orc16] 一样, ORCA 也设置最大批次大小, 即一个批次中允许的最大请求数. ORCA 系统运营者可以调节这个参数, 在满足延迟预算的同时最大化吞吐量. 我们将在 [第 6.2 节](#S6.SS2) 的实验结果中进一步讨论.

另一个因素是 GPU 内存约束. 在多个操作之间复用中间结果缓冲区来优化内存使用, 是各种系统 [Orc04, Orc06] 采用的成熟技术, ORCA 也采用了这种技术. 不过, 与可以立即复用的中间结果缓冲区不同, Attention K/V manager 用来存储 key 和 value 的缓冲区, 在 ORCA 调度器通知相应请求已完成处理之前无法回收. 当没有空间存储下一个标记的新 Attention key 和 value, 调度器可能无法为请求池中的任何请求发出迭代, 朴素实现会使调度器陷入死锁. 因此, ORCA 调度器需要知道 manager 预分配内存区域的剩余大小.

ORCA 调度器综合考虑了所有这些因素: 按到达时间最多选择 "max batch size" 个请求, 并在请求第一次被调度时为其 key 和 value 预留足够空间. 我们在算法 1 中描述调度过程. 算法从请求池选择一个请求批次 (第 4 行), 并调度该批次 (第 5 行). Select 函数 (第 17 行) 按请求到达时间从请求池最多选择 max_bs 个请求 (第 20–22 行). 算法 1 未展示请求到达和返回的过程; 可以认为存在并发线程, 将新到达请求插入 request_pool, 并从 request_pool 移除已完成请求. 当调度器考虑处于初始化阶段的请求 (即请求尚未被调度过) 时, 它使用请求的 `max_tokens` [+6] 属性, 预先为存储 key 和 value 保留 max_tokens 个 GPU 内存 slot (第 23–26 行). 调度器根据 n_rsrv (当前已预留 slot 数) 判断预留是否可行 (第 25 行); 一个 slot 的大小定义为存储单个标记的 Attention key 和 value 所需的内存. n_slots 是 ORCA 系统运营者调节的参数, 表示分配给 Attention K/V manager 的内存区域大小 (以 slot 计). 由于请求中的标记数不可能超过 max_tokens, 如果预留可行, 就能保证 manager 在请求完成前为新生成的 key 和 value 分配缓冲区.

与需要量化延迟和吞吐量权衡的 max_bs 调节不同, ORCA 系统运营者无需实验就能轻松配置 n_slots. 给定模型规格 (例如隐藏大小、层数等) 以及层内和层间并行度, ORCA 的 GPU 内存使用量主要取决于 n_slots. 因此, 运营者只需在内存约束下使用尽可能大的 n_slots.

**算法 1: ORCA 调度算法.**

- **参数:** $n_{\mathrm{workers}}$: worker 数, $\mathit{m\!a\!x}_{bs}$: 最大批次大小, $n_{\mathrm{slots}}$: K/V slot 数.
- $n_{\mathrm{scheduled}} \leftarrow 0$ 且 $n_{\mathrm{rsrv}} \leftarrow 0$.
- **当** `true` **时:**
  - $\mathit{batch}, n_{\mathrm{rsrv}} \leftarrow \mathrm{Select}(\mathit{request\_pool}, n_{\mathrm{rsrv}})$.
  - 调度引擎在该批次上运行一次模型迭代.
  - **对于** 返回批次中的每个请求:
    - 将 `req.state` 设为 `RUNNING`, 然后增加 $n_{\mathrm{scheduled}}$.
    - **如果** $n_{\mathrm{scheduled}}=n_{\mathrm{workers}}$, 等待一个已调度批次返回.
    - **对于** 返回批次中的每个请求, 将 `req.state` 设为 `INCREMENT`.
    - **如果** `finished(req)`, 设置 $n_{\mathrm{rsrv}} \leftarrow n_{\mathrm{rsrv}}-\mathrm{req.max\_tokens}$.
    - 减少 $n_{\mathrm{scheduled}}$.
- **函数 `Select(pool, n_rsrv)`:**
  - 设置 $\mathit{batch} \leftarrow \{\}$, 并设置 $\mathit{pool} \leftarrow \{\mathit{req} \in \mathit{pool} \mid \mathrm{req.state} \ne \mathrm{RUNNING}\}$.
  - 按到达时间对 `pool` 排序.
  - **对于** `pool` 中的每个请求:
    - **如果** `batch.size() = max_bs`, 跳出循环.
    - **如果** `req.state = INITIATION`, 设置 $\mathit{new\_n}_{\mathrm{rsrv}} \leftarrow n_{\mathrm{rsrv}} + \mathrm{req.max\_tokens}$.
    - **如果** $\mathit{new\_n}_{\mathrm{rsrv}} > n_{\mathrm{slots}}$, 跳出循环.
    - 设置 $n_{\mathrm{rsrv}} \leftarrow \mathit{new\_n}_{\mathrm{rsrv}}$, 并将 `req` 加入 `batch`.
  - **返回** $\mathit{batch}, n_{\mathrm{rsrv}}$.

**流水线并行.** ORCA 调度器让引擎中 worker 的执行跨多个批次形成流水线. 直到 n_scheduled (当前已调度批次数) 达到 n_workers (算法 1 第 9–10 行) 之前, 调度器不会等待已调度批次返回. 这样, 调度器让引擎中并发运行的批次数保持为 n_workers, 也就意味着引擎中的每个 worker 都在处理一个批次而不会空闲.

![ORCA 和 FasterTransformer 的执行流水线](./orca/figure-08.png)

**图 8.** ORCA 和 FasterTransformer 中流水线并行的使用对比, 其中 $X_i$ 是请求 $X$ 的第 $i$ 次迭代.

[图 8a](#figure-08) 展示了 3 个 ORCA worker 的执行流水线, 最大批次大小为 2. 假设请求 A 先于 B 到达, B 又先于 C, 依此类推. 首先, 调度器按到达时间选择请求 A 和 B, 调度引擎处理请求 A 和 B 的批次 (称为批次 AB), Worker1、Worker2 和 Worker3 依次处理该批次. 调度器只有在注入另外两个批次 CD 和 EF 后, 才等待批次 AB 返回. 批次 AB 返回后, 由于 A 和 B 是请求池中到达最早的请求, 它们会再次被选中并调度.

相比之下, 当前服务系统和执行引擎之间的接口 (例如 Triton [Orc07] 与 FasterTransformer [Orc04] 的组合) 受请求级调度限制, 不允许在当前批次运行结束前注入另一个批次. 也就是说, 在当前批次 AB 结束前, Triton 不能向 FasterTransformer 注入下一个请求 C. 为了在这一约束下实现多个层间分区的流水线执行, FasterTransformer 将请求批次拆分成多个微批次 [Orc28], 并在这些微批次之间对分区执行进行流水线化.

在 [图 8b](#figure-08) 中, FasterTransformer 将批次 AB 拆为两个微批次 A 和 B. 每个分区以批处理方式处理一个微批次 (其规模小于原批次), 因此批处理带来的性能收益会变小. 此外, 当微批次大小过大, 使微批次数少于分区数时, 该方法可能在流水线中插入气泡. FasterTransformer 必须在批处理效率 (更大的微批次) 和流水线效率 (更少的流水线气泡) 之间权衡, 而 ORCA 没有这种权衡 — 得益于迭代级调度 — 可以在不把批次拆成微批次的情况下轻松对请求进行流水线化.

## 5 实现

我们基于 CUDA 生态实现了 ORCA, 代码约 13K 行 C++. ORCA 引擎控制平面的通信使用 gRPC [Orc02], 数据平面 (包括层间和层内通信) 使用 NCCL [Orc05]. 由于 ORCA 专注于 Transformer 生成模型, 它提供了多种常用 Transformer 层作为模型构建模块, 包括原始编码器-解码器 Transformer [Orc60]、GPT [Orc47] 以及 Raffel 等人 [Orc49] 讨论的其他变体.

我们还像其他 Transformer 训练或推理系统 [Orc01, Orc04, Orc58] 一样, 为 LayerNorm、Attention 和 GeLU 操作实现了融合 kernel. 例如, Attention 操作中计算 query 与 key 的点积、对点积应用 Softmax 以及对 Attention value 做加权平均的过程, 被融合进一个 CUDA kernel. 此外, 我们更进一步融合拆分后的 Attention 操作 kernel, 方法是简单拼接不同请求 kernel 的所有线程块. 尽管这种融合会使一个 kernel 中的线程块具有不同的特征和生命周期 (因为它们处理不同形状的张量, 这通常不符合 CUDA 编程实践), 我们发现这种融合可以提高 GPU 利用率并降低 kernel 启动开销 [Orc34, Orc39], 因而有益.

**基线系统.** 我们与 FasterTransformer [Orc04] 比较, 它是一个通过分布式执行支持大规模 Transformer 模型的推理引擎. 虽然 Megatron-LM [Orc03] 和 DeepSpeed [Orc01] 等其他系统也支持分布式执行, 但这些系统主要为训练工作负载设计和优化, 与针对推理优化的系统相比性能相对较低.

**图 10.** 按生成标记数归一化的端到端中位延迟和吞吐量. 标签 "orca($\mathit{m\!a\!x\_bs}$)" 表示 ORCA 的最大批次大小为 $\mathit{m\!a\!x\_bs}$ 的结果. 标签 "ft($\mathit{m\!a\!x\_bs},\mathit{mbs}$)" 表示 FasterTransformer 的最大批次大小为 $\mathit{m\!a\!x\_bs}$、微批次大小为 $\mathit{mbs}$ 的结果.

现在, 我们通过在不同负载下使用合成请求跟踪测量延迟和吞吐量, 评估 ORCA 的端到端性能. 合成跟踪时, 从 $U(32, 512)$ 中采样每个请求的输入标记数, 这是从 32 到 512 (含端点) 的均匀分布. max_gen_tokens 属性从 $U(1, 128)$ 中采样, 这意味着最少和最多耗时的请求分别需要运行模型 1 次和 128 次迭代.

与 [第 6.1 节](#S6.SS1) 所示微基准不同, 为测量端到端性能, 我们测试包括 ORCA 调度器在内的整个 ORCA 软件栈. 客户端请求按照上文所述的合成跟踪到达 ORCA 调度器. 我们报告不同最大批次大小配置下的结果. 对于没有自有调度器的 FasterTransformer, 我们实现了一个自定义调度器, 接收客户端请求, 组成批次并把批次注入 FasterTransformer 实例. 自定义调度器从请求队列中动态取出至多 max batch size 个请求组成批次, 这是 Triton [Orc07] 和 TensorFlow Serving [Orc42] 等现有服务系统最常用的调度算法. 同样, 我们报告不同最大批次大小配置和不同微批次大小下的结果; 微批次大小是 FasterTransformer 中控制流水线行为的额外参数 (见 [第 4.2 节](#S4.SS2)).

[图 10](#figure-10) 展示了端到端中位延迟和吞吐量. 由于跟踪中的每个请求需要不同的处理时间 (大致与生成标记数成正比), 我们报告按每个请求生成标记数归一化的中位延迟. 从图中可以看出, ORCA 的吞吐量显著高于 FasterTransformer, 延迟也更低. 唯一例外是低负载下的 101B 模型 ([图 10a](#figure-10)). 此时, ORCA 和 FasterTransformer 都没有足够的请求组成批次. 因此, 延迟主要取决于引擎性能, 如 [图 9b](#figure-09) 所示. 随着负载加重, ORCA 在延迟小幅增加的同时提供更高吞吐量, 因为 ORCA 调度器让晚到请求搭上当前正在执行批次的便车. 相比之下, FasterTransformer 无法高效处理以下请求: (1) 到达时间不同; (2) 完成所需迭代次数不同; 或 (3) 输入标记数不同. 其峰值吞吐量为 0.49 req/s, 延迟也高得多. 对于使用多于一个层间分区的 175B 或 341B 模型 ([图 10b](#figure-10) 和 [图 10c](#figure-10)), 在所有负载水平下, ORCA 的延迟和吞吐量都优于 FasterTransformer; 在相近延迟水平比较时, 吞吐量高出一个数量级. 例如, 对 175B 模型, 要达到 190ms 的中位归一化延迟 (这是 [图 9c](#figure-09) 中 "orca(128)" 按生成标记数归一化执行时间的两倍), FasterTransformer 吞吐量为 0.185 req/s, 而 ORCA 吞吐量为 6.81 req/s, 即提升 36.9×.

**不同批次大小配置.** [图 10](#figure-10) 表明, 增大 ORCA 的最大批次大小会提高吞吐量, 而不会影响延迟. 这是因为 ORCA 的迭代级调度解决了请求提前完成和后加入的问题. 不过, 在任意硬件设置、模型和工作负载下, 增大批次大小并不能保证不会负面影响延迟. 如 [第 4.2 节](#S4.SS2) 所述, 必须同时考虑所需延迟和吞吐量要求, 谨慎设置最大批次大小. 有趣的是, FasterTransformer 中更大的最大批次大小不一定有助于提高吞吐量. 我们在不同负载下测试所有模型的最大批次大小 (max_bs) 和微批次大小 (mbs) 的所有组合, 发现 (max_bs, mbs) = (1, 1) 或 (8, 8) 是最佳选择. 根据 [第 4.1 节](#S4.SS1) 的讨论, FasterTransformer 基于微批次的流水线可能效率较低, 因为引擎至多以批处理方式处理 mbs 个请求, 这解释了为什么 mbs 达到最大可能值 (与 max_bs 相同) 的配置性能更好. 此外, 增大 max_bs 虽然可以因批次变大而提升性能, 但也会增加把输入标记数或生成标记数差异很大的请求组成同一批次的可能性. 在这种情况下, FasterTransformer 无法高效处理批次, 因为 (1) 对批次的第一次迭代, FasterTransformer 会把请求当作拥有最短输入长度来处理; (2) 提前完成的请求不能立即返回客户端.

**同质请求跟踪.** 我们使用同质请求跟踪测试 ORCA 和 FasterTransformer 的行为, 即跟踪中的所有请求拥有相同的输入标记数和 max_gen_tokens 属性. 由于所有请求完成处理所需的迭代次数相同, 该跟踪不会出现请求提前离开的问题. 因此, 如 [图 11](#figure-11) 所示, 增大 max_bs 现在会明显提升 FasterTransformer 的性能. 尽管如此, 除最大批次大小为 1 的情况外, ORCA 仍然超过 FasterTransformer (max_bs=8); 在最大批次大小为 1 时, ORCA 退化为一个不执行批处理的 ORCA worker 简单流水线.

## 7 相关工作与讨论

**循环模型的细粒度批处理.** 我们想重点介绍 BatchMaker [Orc23], 它是最相关的先前工作之一. BatchMaker 是一个面向 RNN 的服务系统, 以 RNN 单元为粒度执行调度和批处理, 动机是 RNN 重复相同计算的独特特征. 请求到达后, BatchMaker 将处理请求的数据流图拆分为 RNN 单元, 以单元 (而非整个图) 为粒度调度执行, 并对相同单元 (如果有) 的执行进行批处理. 由于每个 RNN 单元总是执行完全相同的计算, 无论单元所在位置 (即标记索引) 如何, BatchMaker 都能以批处理方式执行多个 RNN 单元. 这样, 新到达的 RNN 请求可以加入 (或已完成的请求可以离开) 当前执行的批次, 而无需等待批次完全结束.

然而, BatchMaker 无法为 Transformer 模型组成单元批次, 因为图中存在太多不同单元 (封装处理一个标记的计算子图; [图 1c](#figure-01)). 不同标记索引 $t$ 的每个单元都必须使用不同的 Attention Key/Value 集合. 由于每个 $t$ 的单元都不同, 图包含 $L$ 个不同单元 ( $L$ 表示输入和生成标记数), 因此在给定时刻出现相同计算单元的可能性显著降低 (例如, 在 [图 10](#figure-10) 中, $L$ 的范围为 $33 = 32 + 1$ 到 $640 = 512 + 128$). 所以单元执行大多会被串行化, BatchMaker 退化为非批处理执行. BatchMaker 也不支持需要模型并行和流水线并行的大型模型.

BatchMaker 侧重于检测和对齐可批处理的 RNN 单元, 而我们设计 ORCA 的核心原则是, 每次读取模型参数时尽可能执行更多计算. 这一原则基于如下观察: 对于大规模模型, 从 GPU 全局内存读取参数是端到端执行时间的主要瓶颈. 遵循这一原则, 我们采用迭代级调度和选择性批处理, 在一次参数读取中处理所有 "ready" 标记, 无论标记处理是否可以批处理 (非 Attention 操作) .

**Transformer 模型的专用执行引擎.** Transformer 模型的出色性能推动了专用推理系统的发展. FasterTransformer [Orc04]、LightSeq [Orc61]、TurboTransformers [Orc22] 和 EET [Orc36] 都是这类系统. 这些系统都作为 Triton Inference Server [Orc07] 和 Tensor-Flow Serving [Orc42] 等现有服务系统的后端执行引擎. 也就是说, 这些系统把调度职责交给服务系统层, 遵循传统请求级调度. ORCA 则建议在更细粒度上调度执行, 而现有系统若不改变调度器与执行引擎之间的协调机制就无法做到这一点. 在这些系统中, 只有 FasterTransformer 支持分布式执行. Megatron-LM [Orc03] 和 DeepSpeed [Orc01] 也可用于分布式执行, 但它们主要针对大规模训练而非推理服务进行优化.

**服务系统与执行引擎之间的接口.** Triton Inference Server [Orc07] 和 Clipper [Orc16] 等通用服务系统, 作为处理客户端请求和调度底层执行引擎的抽象层. 通过分离服务层和执行层的设计与实现, 这种方式很有益. 不过, 我们发现两层之间普遍使用的接口对于 GPT [Orc12] 这类具有多次迭代特征的模型限制过多. 因此, ORCA 将调度器和引擎紧密集成, 简化了两项提议技术 (迭代级调度和选择性批处理) 的应用. 本文没有研究一种既支持这两项技术又不丧失抽象分离的通用接口设计, 探索这种可能性可以成为有趣的主题; 这一问题留待未来工作.

## 8 结论

我们提出结合选择性批处理的迭代级调度, 这是一种为 Transformer 生成模型服务、实现低延迟和高吞吐量的新方法. 迭代级调度使调度器以迭代粒度而非请求粒度与执行引擎交互, 选择性批处理则支持对处理不同位置标记的任意请求进行批处理, 这是将批处理与迭代级调度结合的关键. 基于这些技术, 我们设计并实现了名为 ORCA 的分布式服务系统. 实验显示了该方法的有效性: 在相同延迟水平下, ORCA 的吞吐量比当前最先进系统高一个数量级.
