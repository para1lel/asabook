## 摘要

DistServe 将预填充与解码计算分离, 以提高大型语言模型 (LLM) 的服务性能. 现有 LLM 服务系统将两个阶段共置, 并跨所有用户和请求对预填充与解码计算进行批处理. 我们发现, 这种策略既会造成严重的预填充-解码干扰, 也会将两个阶段的资源分配与并行方案绑定在一起. LLM 应用通常分别关注两个阶段的延迟: 预填充阶段的首 token 延迟 (TTFT), 以及解码阶段每个请求的每输出 token 延迟 (TPOT). 面对严格的延迟要求, 现有系统只能优先保证其中一项延迟, 或者超额配置计算资源来同时满足两项要求.

DistServe 将预填充与解码计算分配到不同的 GPU, 从而消除两者之间的干扰. 给定应用的 TTFT 和 TPOT 要求后, DistServe 会联合优化资源分配与并行策略, 并为每个阶段分别定制方案. DistServe 还会根据服务集群的带宽放置这两个阶段, 尽量降低分离带来的通信开销. 因此, 以每块 GPU 在 TTFT 和 TPOT 约束内可处理的最大请求速率衡量, DistServe 显著改善了 LLM 服务性能. 评估结果表明, 在多种常用 LLM、应用和延迟要求下, DistServe 能比最先进的系统多处理 $7.4\times$ 的请求, 或满足严格 $12.6\times$ 的 SLO, 同时让 $>90\%$ 的请求保持在延迟约束内.

## 1 引言

大型语言模型 (LLMs), 例如 GPT-4 [Ope23], Bard [Bar23] 和 LLaMA [Tou23d], 代表了生成式人工智能的重大变革. 它们开始重塑现有的互联网服务, 从搜索引擎到个人助理 [Inf23], 并使全新的应用成为可能, 如通用聊天机器人 [Sch22, Chi23b] 和编程助手 [Che21, Roz23]. 然而, 这些进展也带来了一个重大挑战: 处理端到端的 LLM 查询可能比标准搜索查询慢得多 [Reu23]. 为了满足各种应用的严格延迟要求, 服务提供商需要超额配置计算资源, 特别是大量 GPU, 从而导致成本效率下降. 因此, 在保持高 SLO 达成率 (满足 SLO 的请求比例) 的前提下, 优化每次 LLM 查询的成本, 对于所有 LLM 服务来说越来越重要.

一个大型语言模型 (LLM) 服务分两个阶段响应用户查询. *预填充阶段*处理由一系列令牌组成的用户提示, *一步生成*响应的第一个令牌. 随后, *解码阶段*按顺序*多步生成*后续令牌; 每个解码步骤都根据前一步生成的令牌生成一个新令牌, 直到到达终止令牌. 这两个阶段的处理方式使 LLM 服务区别于传统服务. LLM 服务的延迟通过两个关键指标衡量: *首令牌时间* (TTFT), 即预填充阶段的持续时间, 以及*每输出令牌时间* (TPOT), 即每个请求生成令牌的平均时间 (首令牌除外) [+1]. 不同应用对这两个指标的要求不同. 例如, 实时聊天机器人 [Sch22] 优先考虑较低的 TTFT 以便及时响应, 而 TPOT 只需快于人类阅读速度 (即每分钟 250 词) 即可. 相比之下, 文档摘要更看重较低的 TPOT, 以便更快生成摘要.

因此, 考虑到应用对 TTFT 和 TPOT 的需求, 一个有效的 LLM 服务系统应平衡这些需求, 最大化*每 GPU 有效吞吐量*. 它的定义是: 对每块已配置 GPU, 在满足 SLO 达成目标 (例如 90%) 的前提下可服务的最大请求速率. 每 GPU 有效吞吐量越高, 单次查询成本就越低.

由于预填充和解码阶段共享 LLM 权重和工作内存, 现有 LLM 服务系统通常会将两个阶段共置在 GPU 上, 并在请求之间批处理预填充和解码步骤, 以最大化整体系统吞吐量, 即所有用户和请求每秒生成的 token 数 [Yu22a, Kwo23a]. 然而, 为满足延迟要求, 这些系统必须超额配置计算资源. 为说明这一点, [图 1](#figure-01) 展示了使用现有系统服务 13B LLM 时 P90 TTFT 和 TPOT 随请求速率增加的变化 [Kwo23]. 工作负载模式和两项延迟约束模拟了使用 LLM 为文章生成简短摘要的场景. 在 90% 的 SLO 达成率下, 单个 A100 GPU 的最大有效吞吐量受 TTFT 和 TPOT 中更严格的要求限制, 约为每秒 1.6 个请求 (rps). 如果两个阶段分别在独立 GPU 上服务, 性能会明显不同. 橙色和绿色曲线表明, 预填充阶段达到每 GPU 5.6 rps, 解码阶段达到 10 rps. 理想情况下, 为预填充分配 2 块 GPU, 为解码分配 1 块 GPU, 就能以整体 10 rps 的速率服务模型, 即每 GPU 3.3 rps, 比现有系统高 2.1 倍. 这种差异主要源于预填充和解码的共置, 因为这两个阶段的计算特性和延迟要求截然不同 (§[2.1](#S2.SS1)).

首先, 共置会导致强烈的*预填充-解码干扰*. 预填充步骤通常比解码步骤耗时更长. 将二者批处理后, 批次中的解码步骤必须等待预填充步骤完成, 因而 TPOT 显著延长; 同样, 加入解码步骤也会使 TTFT 明显增加, 如 [图 2](#figure-02) 所示. 即使分开调度, 二者仍会争用资源. 等待 GPU 执行的解码任务会因正在运行的预填充任务而产生更长的排队延迟, 反之亦然. 优先调度其中一个阶段的任务, 可能导致另一个阶段无法满足延迟要求.

其次, 预填充和解码计算在延迟要求和对不同形式并行性的偏好上存在差异 (§[3](#S3)). 然而, 将预填充和解码共置, 会使它们的资源分配耦合, 从而无法实施更适合满足各阶段特定延迟需求的不同并行策略.

为了克服这些挑战, 我们提出将大型语言模型推理的预填充和解码阶段分离, 并分配到不同的 GPU 上. 我们的方法有两个好处. 首先, 在不同 GPU 上独立运行每个阶段消除了预填充与解码的干扰. 其次, 它允许根据各阶段的特定延迟需求独立扩展每个阶段, 并采用定制的资源分配和模型并行策略. 虽然分离会导致 GPU 之间的中间状态通信, 但我们显示在现代 GPU 集群中通信开销可以忽略不计 (§[3.3](#S3.SS3)), 并且如果管理得当, 分离能够显著提高每个 GPU 的吞吐量.

基于上述洞察, 在本工作中, 我们构建了 DistServe [+repo], 一个通过分离预填充和解码阶段来优化有效吞吐量的 LLM 服务系统. 考虑到 TTFT 和 TPOT 的需求, DistServe 首先通过联合优化预填充和解码阶段的 GPU 分配及并行策略, 在假设服务单个模型副本的情况下独立地扩展每个阶段. 该优化确保最大化每 GPU 的有效吞吐量, 并可能根据各自的延迟要求为每个阶段分配不同数量的 GPU 和并行策略. 然后, DistServe 通过复制将此分配扩展到多个实例, 直到满足用户要求的流量率 (§[4](#S4)). DistServe 还具有一个算法, 可根据其分配方案和集群带宽来放置预填充和解码计算, 从而最小化阶段间中间状态传输的开销.

我们将 DistServe 实现为 LLM 推理引擎之上的编排层. 我们在多种 LLM 上评估 DistServe, 并采用三类重要的实际 LLM 应用负载: 聊天机器人、编程助手和文档摘要. 在各种延迟约束下, DistServe 比最先进的方案最多可处理 $7.4\times$ 的请求, 或满足严格 $12.6\times$ 的 SLO. 本文的贡献如下:

- 识别现有大型语言模型服务系统中预填充-解码干扰和资源耦合的问题, 并提出将预填充和解码阶段分离的方案.
- 设计一种新的放置算法, 自动选择预填充和解码实例的有效吞吐量最优方案.
- 对 DistServe 进行基于实际工作负载的全面评估.

## 2 背景和动机

一个大型语言模型 (LLM) 服务采用客户端-服务器架构: 客户端将一段文本作为请求提交给服务器; 服务器在 GPU 上托管 LLM, 对请求执行推理, 再将生成结果返回给客户端 (或以流式方式传输). 如 §[1](#S1) 所述, 由于 LLM 特有的预填充-解码过程, 服务可能需要根据应用需求, 为 TTFT 和 TPOT 同时设定严格的服务级目标 (SLO). 服务系统必须满足两项 SLO, 同时尽量降低昂贵 GPU 带来的成本. 换句话说, 我们希望服务系统对每块已配置 GPU, 在满足 SLO 达成目标的前提下最大化每秒处理的请求数, 即*最大化每 GPU 有效吞吐量*. 接下来, 我们将详细说明 LLM 推理计算 (§[2.1](#S2.SS1)), 并讨论现有的 LLM 服务优化方法 (§[2.2](#S2.SS2)).

### 2.1 LLM 推理

现代大语言模型 (LLM) [Ope23, Tou23d] 根据输入序列预测下一个 token. 预测过程需要计算序列中每个 token 的隐藏表示. LLM 可以接收数量不定的输入 token, 并行计算它们的隐藏表示; 计算量会随并行处理的 token 数呈超线性增长. 无论输入 token 有多少, 计算都需要大量 I/O, 将 LLM 权重和中间状态从 GPU 的 HBM 移到 SRAM. 这一点不随输入规模改变.

预填充步骤处理一个通常包含许多 token 的新序列, 并同时处理这些 token. 与预填充不同, 每个解码步骤只处理前一步生成的一个新 token. 因此, 两个阶段的计算特性有显著差异. 用户提示不太短时, 预填充步骤往往受计算能力限制. 例如, 对 13B LLM 而言, 预填充一个 512-token 序列会使 A100 接近计算瓶颈 (参见 §[3.1](#S3.SS1)). 相比之下, 解码阶段虽然每步只处理一个新 token, 产生的 I/O 却与预填充阶段相近, 因而受 GPU 内存带宽限制.

在两个阶段中, 每个 token 位置都会生成称为 KV 缓存 [Kwo23] 的中间状态, 后续解码步骤还会再次使用这些状态. 为避免重复计算, 系统会将其保存在 GPU 内存中. 由于两个阶段共享内存中的 LLM 权重和 KV 缓存, 大多数 LLM 推理引擎会将预填充与解码阶段共置在 GPU 上, 尽管二者的计算特性不同.

### 2.2 LLM 服务优化

在实时在线服务中, 会有多个请求到来, 必须在 SLO 范围内提供服务. 将它们的计算进行批处理和并行化是实现低延迟, 高吞吐量以及 GPU 高利用率的关键.

**批处理.** 当前的服务系统 [Yu22a, Kwo23, Agr23] 使用一种被称为*连续批处理*的批处理技术. 这种方法将新请求的预填充与正在进行的解码批量处理. 它提高了 GPU 利用率, 并最大化整个系统的吞吐量, 即所有用户和请求每秒生成的 token 数. 然而, 如 §[1](#S1) 所述以及 §[2.3](#S2.SS3) 的进一步分析, 这种方法会在 TTFT 与 TPOT 之间产生权衡. 连续批处理的一种高级变体 [Agr23] 尝试将长预填充拆成若干块, 再附加解码任务, 以免超过 GPU 的性能上限, 从而平衡 TTFT 和 TPOT; 但从本质上说, 它仍以 TTFT 为代价换取 TPOT, 而且无法消除干扰 (§[2.3](#S2.SS3)). 总之, 对预填充和解码做批处理, 必然会牺牲 TTFT 或 TPOT 中的一项.

**模型并行.** 在 LLM 服务中, 模型并行通常分为算子内并行和算子间并行 [Li23j, Zhe22, Sho20]. 两者都可以支持更大的模型, 但对服务性能的影响不同. 算子内并行把矩阵乘法等计算密集型算子分配到多个 GPU 上, 以加快计算, 但会产生大量通信. 它能缩短执行时间 [+2], 从而降低延迟, 尤其是预填充阶段的 TTFT, 但要求 GPU 之间具有高带宽连接 (如 NVLINK). 算子间并行把 LLM 的各层组织为多个阶段, 每个阶段在一块 GPU 上运行, 形成流水线. 阶段间通信会适度增加执行时间, 但系统的请求处理能力可以随 GPU 数量线性扩展. 本文还揭示了模型并行的另一项作用: 执行时间缩短后, 预填充和解码阶段的排队延迟也会减少. §[3](#S3) 将进一步分析这一点. 除模型并行外, 无论模型实例采用何种并行配置, 对其进行复制也能线性扩展系统的请求处理能力.

这些并行策略创造了一个复杂的优化空间, 需要根据应用的延迟要求谨慎权衡.

### 2.3 问题与机遇

现有系统将预填充和解码计算共置并做批处理, 以最大化整个系统的吞吐量. 对服务提供商而言, 这种方式成本较低. 然而, 当服务有服务级目标 (SLO) 时, 受下述问题影响, 现有方法很难同时维持较高的服务质量和较低的成本.

**预填充-解码干扰.** 如 [图 2](#figure-02) 所示, 在一批解码请求中加入一个预填充任务, 就会显著拖慢两种计算, 使 TTFT 和 TPOT 明显增加. 具体来说, 批内的解码任务必须等待耗时更长的预填充任务完成, 因而 TPOT 会延长; 预填充任务越长, 减速越明显, 如 [图 2](#figure-02)(b) 所示. 在预填充任务中加入解码任务也会延长预填充的完成时间, 尤其是在 GPU 已经满载时 ([图 2](#figure-02) 中的蓝色曲线).

一种缓解这种干扰的方案称为*附带解码任务的分块预填充* [Agr23, Dee23]. 它把长预填充拆成若干块, 再将一个预填充块与少量解码任务放入同一批次, 也就是让解码任务“搭便车”. 这种方法可以减轻长预填充任务对解码任务的拖慢, 但无法消除影响. 此外, 它还会给预填充任务增加额外开销, 而且很难通过调整块大小来缓解. 首先, 如果块大小远低于能使 GPU 饱和的拐点, 预填充任务就会与同批次的解码任务争用资源, 无法独占 GPU, 因而执行时间更长. 其次, 如果将块大小增大到接近 GPU 饱和, 留给解码 token 的空间就会减少, 解码任务能搭载进来的机会也随之降低. 分块预填充还会显著增加预填充任务的内存访问量. 这是因为计算每个后续块时, 都要反复将之前所有块的 KV 缓存从 HBM 读入 SRAM. 具体来说, 如果一个预填充任务被分成 $N$ 个等大的块, 总共需要读取 $N+(N-1)+...+1=O(N^2)$ 个块的 KV 缓存, 而不分块时只需 $O(N)$. 上下文越长, 这项开销越大.

**调度无效.** 即使取消预填充与解码的批处理, 改为依次调度, 也不能缓解干扰. 解码任务需要等待 GPU 上正在执行的预填充任务, 因而可能产生更长的排队延迟. 此外, 只包含解码任务的批次通常无法充分利用 GPU. 无论优先调度哪个阶段, 另一个阶段的延迟都会受到不利影响, 因此优先级调度并不能解决问题.

**资源与并行耦合.** 预填充和解码阶段共置在同一组 GPU 上, 必然会共享资源和并行设置. 但两个阶段的计算特性和延迟要求各不相同, 需要更具异构性的资源分配. 例如, 预填充阶段往往受计算能力限制, 适合增加算子内并行度来缩短执行时间, 从而满足严格的 TTFT SLO. 相比之下, 解码阶段的最优并行配置取决于运行时的批量大小. 受这种耦合影响, 现有系统会按 TTFT 与 TPOT 中要求更严格的一项配置资源和并行方案, 而该方案对另一个阶段可能并不合适. 为同时满足两项 SLO, 系统往往需要配置过多资源.

**机会.** 为解决这些问题, 我们提出将预填充阶段与解码阶段分离. 本文用“实例”表示管理一份完整模型权重副本的资源单元. 使用模型并行时, 一个实例可以对应多块 GPU. 当两个阶段分配到不同的 GPU 上时, 每个阶段各自管理一份模型权重副本, 分别形成*预填充实例*和*解码实例*. 预填充实例收到请求后, 只执行该请求的预填充计算并生成第一个输出 token. 随后, 它把中间结果 (主要是 KV 缓存) 发送给负责后续步骤的解码实例. 解码计算的 GPU 利用率通常较低, 因而一个解码实例可以对应多个预填充实例. 这样便能批处理更多解码任务, 提高 GPU 利用率.

将预填充和解码进行分离, 可以消除两个阶段之间的干扰, 使各阶段分别专注于 TTFT 或 TPOT. 两类实例可以采用不同的资源和并行策略来满足各种延迟要求. 通过调整分配给两类实例的 GPU 数量和并行度, 我们可以最大化整个系统的每 GPU 有效吞吐量, 避免资源过度配置, 从而在满足服务质量要求的同时降低每次查询的成本. 接下来, 我们将说明如何找出各阶段的最佳资源分配和并行方案.

## 3 权衡分析

分离两个阶段后, 我们可以独立分析各阶段的特性, 进而指导算法设计. 设计空间也随之扩大: 每个阶段都要根据各自的延迟要求独立扩展和调度.

本节分析预填充实例 (§[3.1](#S3.SS1)) 和解码实例 (§[3.2](#S3.SS2)) *分离后*的计算模式, 以找出关键参数, 并为各阶段的批处理和并行策略提出准则. 随后, 我们讨论实际部署中的若干注意事项 (§[3.3](#S3.SS3)). 这些分析是优化每 GPU 有效吞吐量的基础.

### 3.1 预填充实例分析

<span id="figure-03"></span>

![参见图注](./distserve/figure-03.png)

**图 3.** 在使用 13B 参数的 LLM 提供服务时, 不同批量大小和输入长度下, 预填充阶段和解码阶段的吞吐量.

分离后, 预填充阶段通过并行处理用户提示中的全部 token 生成第一个 token. 在给定到达率的情况下, 我们的目标是用最少的资源满足服务的 TTFT 延迟要求.

**批处理策略.** 预填充步骤通常是计算密集型任务. [图 3](#figure-03)(a) 展示了预填充阶段的吞吐量如何随输入长度和批量大小变化. 对 13B 参数的 LLM 而言, 处理一条长 512 token 的序列就足以让 A100 GPU 满载; 模型越大, 达到 GPU 饱和所需的序列越短. GPU 受计算能力限制后, 继续增加批内请求数不会提高效率, 反而会按比例延长整批任务的处理时间, 拖慢其中所有请求. 因此, 预填充实例需要预先分析特定 LLM 和 GPU 的性能, 找出临界输入长度 $L_{m}$; 超过该长度后, 预填充阶段将受计算能力限制. 只有待调度请求的输入长度小于 $L_{m}$ 时, 才应考虑增大批量. 实际应用中, 用户提示的平均长度通常达到数百个 token [Sha23b], 因而预填充实例的批量通常较小.

<span id="figure-04"></span>

![参见图注](./distserve/figure-04.png)

**图 4.** 在两块 A100 GPU 上使用不同并行方式服务 66B 参数的 LLM 时的平均 TTFT.

**并行方案.** 为研究纯预填充实例偏好的并行方式, 我们分别采用算子间并行和算子内并行, 在两块 A100 GPU 上运行一个 66B LLM. 为简化问题, 假设所有请求的输入长度均为 512 token, 且到达过程服从泊松分布. [图 4](#figure-04)(a) 比较了不同到达率下的平均 TTFT: 到达率较低时, 算子内并行效率更高; 随到达率上升, 算子间并行开始占优. 分离后, 预填充阶段的行为类似 M/D/1 队列, 因而可以用排队论验证这一观察.

我们先从不使用并行的单设备情形定义符号: 由于预填充长度相同, 每个请求的执行时间 $D$ 保持不变. 单个请求就能使 GPU 饱和, 因此请求采用先到先服务 (FCFS) 调度, 不做批处理. 假设泊松到达率为 $R$, 利用率条件为 $R D<1$, 则平均 TTFT ($\mathit{Avg\_TTFT}$) 可由 M/D/1 队列 [Sho18] 的闭式解建模:

<span id="S3.E1"></span>

$$
\small \mathit{Avg\_TTFT}=D+\frac{R D^{2}}{2(1-R D)},
$$

其中第一项代表执行时间, 第二项对应排队延迟. 基于公式 [1](#S3.E1), 我们结合了并行性.

在 2 路算子间并行情况下, 我们假设请求级延迟变为 $D_{s}$, 且最慢阶段需要 $D_{m}$ 完成. 由于层间激活通信可以忽略不计 [Zhe22, Li23j], 有 $D\approx D_{s}\approx 2\times D_{m}$. 2 路算子间并行的平均 TTFT 推导如下:

<span id="S3.E2"></span>

$$
\small \mathit{Avg\_TTFT}_{\mathrm{inter}}=D_{s}+\frac{R D_{m}^{2}}{2(1-R D_{m})}=D+\frac{R D^{2}}{4(2-R D)}.
$$

对于算子内并行, 我们引入加速系数 $K$, 其中 $1<K<2$, 反映了算子内并行的高通信开销导致的非理想加速. 当执行时间为 $D_{s}=\frac{D}{K}$ 时, 2 路算子内并行的平均 TTFT 为:

<span id="S3.E3"></span>

$$
\small \mathit{Avg\_TTFT}_{\mathrm{intra}}=\frac{D}{K}+\frac{R D^{2}}{2K(K-R D)}.
$$

对比公式 [2](#S3.E2) 和 [3](#S3.E3) 可知: 在较低速率下, 执行时间 (第一项) 占主导, 算子内并行减少执行时间, 因而更高效. 随着速率增加, 排队延迟 (第二项) 变得更重要, 算子间并行开始占优, 这与 [图 4](#figure-04)(a) 一致.

预填充阶段对并行性的偏好还受 TTFT SLO 和加速系数 $K$ 的影响. 从 [图 4](#figure-04)(a) 可以看出, 更严格的 SLO 会使算子内并行更有利, 因为它能缩短执行时间. $K$ 的取值取决于输入长度, 模型架构, 通信带宽和放置方式 [Sho20, Zhe22] 等因素. 如 [图 4](#figure-04)(b) 所示, $K$ 减小时, 算子内并行的效果会明显下降. §[4](#S4) 将开发算法, 在考虑这些因素的同时优化资源和并行配置.

### 3.2 解码实例分析

与预填充实例不同, 解码实例采用另一种计算模式: 它从预填充实例接收 KV 缓存和第一个输出 token, 再逐个生成后续 token. 对解码实例而言, 优化目标是用最少的计算资源满足应用的 TPOT 要求.

**批处理策略.** 单个解码任务主要受带宽限制, 因而批处理是避免 GPU 利用率过低、提高每 GPU 有效吞吐量的关键. 在预填充和解码共置的现有系统中, 增大解码批量会与延迟目标冲突, 请求速率较高时尤其如此. 共享 GPU 会让预填充任务与解码任务争用资源, 从而在 TTFT 和 TPOT 之间形成权衡. 例如, 到达率升高会产生更多预填充任务; 若优先处理这些任务以满足 TTFT 要求, 就要占用更多 GPU 时间, 进而损害 TPOT.

相反, 分离架构提供了一种解决方案, 通过将多个预填充实例分配到单个解码实例. 这种方法允许在专用 GPU 上为解码阶段积累更大的批量大小, 而不会牺牲 TPOT.

<span id="figure-05"></span>

![参见图注](./distserve/figure-05.png)

**图 5.** 在不同并行度下, 以批量大小 128、输入长度 256 服务 13B LLM 时的解码阶段延迟和吞吐量.

**并行方案.** 分离后, 解码实例需要为所有活跃请求保存 KV 缓存, 因而批量大小可能受 GPU 内存容量限制. 通过模型并行扩展解码实例, 或采用 PagedAttention [Kwo23]、GQA [Ain23a] 等更先进的 LLM KV 缓存管理技术, 可以继续增大解码批量, 直至接近计算瓶颈. 随着批量接近该瓶颈, 解码计算开始呈现与预填充阶段相似的特征. 基于这一观察, [图 5](#figure-05) 研究了大批量下不同并行度对应的延迟和吞吐量: 算子内并行能够降低延迟, 但通信与划分后利用率下降会使收益递减; 算子间并行则几乎能线性扩展吞吐量. 因此, TPOT SLO 非常严格时, 算子内并行是降低 TPOT、满足延迟目标的关键. 在此之外, 算子间并行更适合线性提高吞吐量.

当模型可以适配到单个 GPU 的内存时, 对于预填充和解码实例, 复制是一种与模型并行性竞争的选项, 可以线性扩展系统的吞吐能力. 它还可能减少排队延迟—如公式 [1](#S3.E1) 所示—通过用 $R/N$ 替换 $R$, 假设请求均匀分配到 $N$ 个副本, 但代价是需要在 GPU 内存中维护额外的模型权重副本.

### 3.3 实际问题

我们已经给出了为各阶段选择批处理和并行方案的方法. 本节讨论在实际部署预填充与解码分离架构时遇到的若干问题.

**可变预填充长度.** §[3](#S3) 假设所有请求的提示长度相同. 实际部署中, 请求长度会随 LLM 应用而变化. 对采用算子间并行的预填充实例而言, 不同长度请求会使各流水线阶段的执行时间不同, 形成流水线气泡 [Hua19b, Nar19]. 因此, 实际结果会与 M/D/1 队列模型得出的结论略有偏差. 为解决这一问题, §[4](#S4) 将提出根据工作负载搜索并行方案的算法, 并通过调度尽量减少气泡 (§[4.3](#S4.SS3)).

**通信开销.** 从预填充实例向解码实例传输 KV 缓存会产生显著开销. 例如, OPT-66B 上一个 512-token 请求的 KV 缓存约为 1.13GB. 假设平均到达率为 10 rps, 每秒需要传输 11.3GB 数据, 即需要约 90Gbps 带宽才能使该开销近乎不可见. KV 缓存大小还会随平均输入长度和到达率增加. 许多用于 LLM 的现代 GPU 集群都配有 InfiniBand (如 800Gbps). 当跨节点带宽有限时, DistServe 则依赖常见的节点内 NVLINK; A100 GPU 之间的峰值带宽为 600GB/s, 同样可使传输开销忽略不计 (见 §[6.3](#S6.SS3)). 不过, 这一要求会对预填充与解码实例的放置施加额外约束, 下一节将对此加以考虑.

通过以上分析, 我们识别出工作负载模式、放置约束、SLO 要求、并行方案和资源分配等设计分离式服务系统时需要考虑的关键参数. 如何自动搜索这些参数, 找到每 GPU 有效吞吐量最优的配置, 仍是一项挑战, 下一节将讨论这一问题.

## 4 方法

我们构建 DistServe 来解决上述问题. 给定模型、工作负载特征、延迟要求和 SLO 达成目标, DistServe 将确定: (a) 预填充与解码实例的并行方案; (b) 各类实例的数量; (c) 在物理集群上的放置方式. 我们将这一结果称为放置方案. 目标是找到每 GPU 有效吞吐量最大的放置方案.

如 §[3.3](#S3.SS3) 所述, 在不同集群配置下管理分离的预填充与解码阶段之间的通信, 是一项关键设计考量. 本节先介绍两种放置算法: 一种用于拥有高速跨节点网络的集群 (§[4.1](#S4.SS1)), 另一种用于缺少这类基础设施的环境 (§[4.2](#S4.SS2)), 后者引入了额外约束. 接着, 我们将给出能够适应真实工作负载特征的在线调度优化 (§[4.3](#S4.SS3)).

### 4.1 高节点亲和集群的部署

<span id="alg1"></span>

**算法 1: 高节点亲和性放置算法.**

<div class="paper-algorithm">

- **输入:** LLM $G$, 每实例节点上限 $N$, 每节点 GPU 数 $M$, GPU 内存容量 $C$, 工作负载 $W$, 流量速率 $R$.
- **输出:** 放置方案 $\mathit{best\_plm}$.
- $\mathit{config_p},\mathit{config_d}\leftarrow\emptyset,\emptyset$.
- **对于** $\mathit{intra\_op}\in\{1,2,...,M\}$:
  - **对于** $\mathit{inter\_op}\in\{1,2,...,\frac{N\times M}{\mathit{intra\_op}}\}$:
    - **如果** $\frac{G.\mathit{size}}{\mathit{inter\_op}\times\mathit{intra\_op}}<C$:
      - $\mathit{config}\leftarrow(\mathit{inter\_op},\mathit{intra\_op})$.
      - $\hat{G}\leftarrow\mathrm{parallel}(G,\mathit{config})$.
      - $\mathit{config.goodput}\leftarrow\mathrm{simu\_prefill}(\hat{G},W)$.
      - **如果** $\frac{\mathit{config_p.goodput}}{\mathit{config_p.num\_gpus}}<\frac{\mathit{config.goodput}}{\mathit{config.num\_gpus}}$:
        - $\mathit{config_p}\leftarrow\mathit{config}$.
      - $\mathit{config.goodput}\leftarrow\mathrm{simu\_decode}(\hat{G},W)$.
      - **如果** $\frac{\mathit{config_d.goodput}}{\mathit{config_d.num\_gpus}}<\frac{\mathit{config.goodput}}{\mathit{config.num\_gpus}}$:
        - $\mathit{config_d}\leftarrow\mathit{config}$.
- $n,m\leftarrow\lceil\frac{R}{\mathit{config_p.goodput}}\rceil,\lceil\frac{R}{\mathit{config_d.goodput}}\rceil$.
- $\mathit{best\_plm}\leftarrow(n,\mathit{config_p},m,\mathit{config_d})$.
- **返回:** $\mathit{best\_plm}$.

</div>

在配备 InfiniBand 的高节点亲和性集群中, KV 缓存的跨节点传输开销可以忽略不计, DistServe 可不受限制地把预填充和解码实例部署在任意两个节点上. 我们为此类场景提出两级放置算法: 先分别优化预填充和解码实例的并行配置, 使两个阶段各自获得最佳的每 GPU 有效吞吐量; 再通过复制匹配整体流量速率.

但要为单一类型的实例, 如预填充实例, 找到最优并行配置仍有难度. 原因是工作负载的输入长度、输出长度和到达模式各异, 而 SLO 达成率 (即满足 TTFT 要求的请求比例) 又没有简单的解析公式. 在真实测试平台上评估 SLO 耗时过长. 因此, 我们构建模拟器来估计 SLO 达成率, 并假设已知工作负载的到达过程和输入、输出长度分布. 虽然短时间间隔难以预测, 但较长时间尺度 (如数小时或数天) 上的工作负载模式通常可预测 [Li23j, Zha23b]. DistServe 根据历史请求轨迹拟合分布, 并从该分布重新采样轨迹, 作为模拟器的输入工作负载以计算 SLO 达成率. 随后, DistServe 枚举放置方案, 通过二分搜索和模拟试验找出满足 SLO 达成目标的最大请求速率.

算法 [1](#alg1) 概述了这一过程. 在集群容量限制下, 我们分别为预填充和解码实例枚举所有可行的并行配置. 对某个预填充阶段配置, 用 `simu_prefill` 模拟并通过二分搜索找出其最大有效吞吐量; 解码阶段同理, 使用 `simu_decode`. 确定两个阶段的最优并行配置后, 再按其有效吞吐量进行复制, 以满足用户所需的整体流量.

算法 [1](#alg1) 的复杂度为 $O(\mathrm{NM}^{2})$, 其中 $N$ 是每个实例可用的节点上限, $M$ 是现代集群中每个节点的典型 GPU 数 (如 8). 搜索空间可控; 如 §[6.5](#S6.SS5) 所示, 在我们的最大配置中, 求解时间不足 1.3 分钟.

**模拟器构建.** 算法 [1](#alg1) 需要根据工作负载和并行方案, 估计不同 SLO 与 SLO 达成目标下的有效吞吐量. 为构建准确的模拟器, 我们分别分析预填充和解码阶段的 FLOPs 与内存访问次数, 并用延迟模型近似推理执行时间. 详见附录 [A](#A1). DNN 工作负载具有较高的可预测性 [Guj20, Li23j], 因而模拟器与真实的性能分析结果较为一致, 这一点也在 §[6.4](#S6.SS4) 中验证.

到这里为止, 算法 [1](#alg1) 假设预填充与解码实例可放置在集群中任意两个节点上 (也可以在同一节点), 且 KV 缓存通过高带宽网络传输. 许多真实集群中, 节点内 GPU 有高带宽 NVLINK 互连, 但跨节点 GPU 的带宽有限. 接下来我们给出应对这一限制的算法.

<span id="alg2"></span>

**算法 2: 低节点亲和性放置算法.**

<div class="paper-algorithm">

- **输入:** LLM $G$, 每实例节点上限 $N$, 每节点 GPU 数 $M$, GPU 内存容量 $C$, 工作负载 $W$, 流量速率 $R$.
- **输出:** 放置方案 $\mathit{best\_plm}$.
- $\mathit{config}^{*}\leftarrow\emptyset$.
- **对于** $\mathit{inter\_op}\in\{1,2,...,N\}$:
  - $\mathcal{P}\leftarrow\mathrm{get\_intra\_node\_configs}(G,M,C,\mathit{inter\_op})$.
  - **对于** $P_p\in\mathcal{P}$:
    - **对于** $P_d\in\mathcal{P}$:
      - **如果** $P_p.\mathit{num\_gpus}+P_d.\mathit{num\_gpus}\le M$:
        - $\mathit{config}\leftarrow(\mathit{inter\_op},P_p,P_d)$.
        - $\hat{G}_p,\hat{G}_d\leftarrow\mathrm{parallel}(G,\mathit{config})$.
        - $\mathit{config.goodput}\leftarrow\mathrm{simulate}(\hat{G}_p,\hat{G}_d,W)$.
        - **如果** $\frac{\mathit{config}^{*}.\mathit{goodput}}{\mathit{config}^{*}.\mathit{num\_gpus}}<\frac{\mathit{config.goodput}}{\mathit{config.num\_gpus}}$:
          - $\mathit{config}^{*}\leftarrow\mathit{config}$.
- $n\leftarrow\lceil\frac{R}{\mathit{config}^{*}.\mathit{goodput}}\rceil$.
- $\mathit{best\_plm}\leftarrow(n,\mathit{config}^{*})$.
- **返回:** $\mathit{best\_plm}$.

</div>

### 4.2 低节点亲和力集群的部署

一个直观方案是始终将预填充与解码实例放在同一节点, 利用 GPU 节点内通常具备的 NVLINK. 对于大型模型, 如参数量为 175B (350GB) 的模型, 一台包含 8 块 GPU 的节点甚至无法容纳一对预填充与解码实例 ($80G\times 8=640G<350\times 2\mathrm{GB}$). 我们将此作为额外放置约束, 并与模型并行一起优化, 如算法 [2](#alg2) 所示.

关键观察是, 中间状态只会在预填充和解码实例的对应层之间传输. 通过算子间并行, 我们将层划分为若干阶段, 并把每个实例划分为“实例段”, 每段对应一个特定的算子间阶段. 在同一节点中共置处于相同阶段的预填充段和解码段后, 中间状态只能通过 NVLINK 传输. 节点内部, 同一实例的各段采用相同的并行度和资源分配. 由于每个节点的 GPU 数通常有限 (一般为 8 块), 我们可以枚举单个节点的可能配置, 再用模拟器找出有效吞吐量最高的配置.

如算法 [2](#alg2) 所示, 我们先枚举算子间并行度, 得到所有可能的实例段. 对每个段, 通过调用 `get_intra_node_configs` 获得节点内的所有可能配置. 随后用模拟找出最优配置, 并通过复制满足目标流量速率.

### 4.3 在线调度

<span id="figure-06"></span>

![参见图注](./distserve/figure-06.png)

**图 6.** DistServe 运行时系统架构

DistServe 的运行时架构如 [图 6](#figure-06) 所示. DistServe 采用简单的 FCFS (先到先服务) 调度策略. 所有到达的请求先进入集中式控制器, 再被分派到队列最短的预填充实例处理预填充, 然后分派给负载最小的解码实例完成解码步骤. 这一设置虽然简单, 但针对真实工作负载的特征做了若干优化.

**减少流水线气泡.** 为缓解非均匀提示长度导致的流水线气泡 (§[3.3](#S3.SS3)), 我们调度请求时会平衡流水线中各批次的执行时间. 对预填充和解码实例而言, 批中新 token 的数目可可靠地反映该批的实际执行时间. 对预填充实例, 我们分析目标模型和 GPU, 找出使 GPU 饱和所需的最短提示长度 $L_{m}$. 预填充批次的总序列长度会接近 $L_{m}$: 可以把多个短于 $L_{m}$ 的请求合并为一批, 也可以单独调度长于 $L_{m}$ 的请求. 对解码实例, 将最大批量大小设为 $L_{m}$.

**应对突发流量.** 工作负载的突发性可能导致大量 KV 缓存从预填充实例传往解码实例, 从而使解码实例的内存过载. 为避免这一情况, DistServe 用“拉取”方式传输 KV 缓存, 而不是“推送”方式: 解码实例*按需*从预填充实例获取 KV 缓存, 并将预填充实例的 GPU 内存用作队列缓冲. 这样, 预填充实例在处理完提示后只需把 KV 缓存保留在 GPU 内存中, 就能继续处理其他预填充任务. 两类实例可以各自按自己的节奏运行, 无需复杂协调.

**重新规划.** DistServe 的资源与并行方案针对特定工作负载模式优化; 随时间推移, 工作负载模式改变后, 该方案可能变得次优. DistServe 定期重新规划. 工作负载分析器会监控请求的平均输入、输出长度和平均到达率等关键参数. 检测到明显的模式变化时, DistServe 会根据近期历史数据重新运行放置算法. 这一过程很快: 所提算法只需数秒 (§[6.5](#S6.SS5)), 重新加载 LLM 权重也能在数分钟内完成, 远短于真实工作负载通常按小时变化的时间尺度.

**抢占与容错.** DistServe 尚未实现抢占 [Han22a]、容错 [Zha21c] 等高级运行时策略, 它们与分离架构相互补充. 不过, 我们讨论了它们如何适用于 DistServe. 在 DistServe 中, FCFS 策略可能产生“车队效应”, 即较长请求在预填充阶段阻塞较短请求. 如已有研究 [Wu23b] 所建议, 加入抢占策略可提高效率, 且能够在本系统的架构中实现. 虽然容错不是当前 DistServe 的主要关注点, 但仍需加以考虑. 在传统的共置式和基于复制的系统中, 一个实例故障通常不会影响其他副本实例. 但在 DistServe 中, 预填充与解码实例的依赖关系会带来故障传播风险. 例如, 一个映射到多个预填充实例的解码实例发生故障, 可能会使整个服务和集群瘫痪. 这两项都留待未来工作.

## 5 实现

DistServe 是一个端到端分布式 LLM 服务系统, 包含放置算法模块、RESTful API 前端、编排层和并行执行引擎. 算法模块、前端和编排层由 6.5K 行 Python 代码实现. 并行执行引擎由 8.1K 行 C++/CUDA 代码实现.

放置算法模块实现 §[4](#S4) 所述的算法和模拟器, 为特定模型与集群配置作出放置决策. 前端提供与 OpenAI API 兼容的接口, 客户端可指定最大输出长度、温度等采样参数. 编排层管理预填充和解码实例, 负责请求分发、KV 缓存传输和结果交付. 跨节点 GPU 通信使用 NCCL [Ncc23], 节点内通信使用异步 CudaMemcpy, 避免传输过程中阻塞 GPU 计算. 每个实例由并行执行引擎驱动. 该引擎通过 Ray [Mor18] actor 实现 GPU worker, 以分布式方式执行 LLM 推理并管理 KV 缓存. 它集成连续批处理 [Yu22a]、FlashAttention [Dao22c]、PagedAttention [Kwo23] 等多项近期 LLM 优化, 并支持 OPT [Zha22a]、LLaMA [Tou23d] 等常用开源 LLM.

### 6.1 实验设置

**集群测试平台.** 我们在一个包含 4 个节点和 32 块 GPU 的集群上部署 DistServe. 每个节点配备 8 块通过 NVLINK 连接的 NVIDIA SXM A100-80GB GPU, 节点间带宽为 25Gbps. 由于节点间带宽有限, 除使用模拟器的消融研究 (§[6.4](#S6.SS4)) 外, 大多数实验采用低节点亲和性放置算法 ([算法 2](#alg2)).

**模型和工作负载设置.** 与以往的 LLM 服务研究 [Kwo23] 类似, 我们选择学术界和工业界广泛使用的 OPT [Zha22a] 系列. 较新的 GPT 模型系列开始采用 GQA [Ain23] 和 MQA [Sha19] 等节省内存的注意力机制. 这些模型的 KV 缓存更小, 传输开销更低, 因而 DistServe 在其上的表现会更好. 我们选择使用经典 MHA [Vas17] 的 OPT, 以充分考验传输开销. 所有实验均采用 FP16 精度. 对于工作负载, 如 [表 1](#table-01) 所示, 我们选择三种典型的 LLM 应用, 并根据其服务目标凭经验设置 SLO, 因为据我们所知, 这些应用尚无通用的 SLO 设置. 每种应用选取一个合适的数据集并从中抽样请求. 由于数据集均不包含时间戳, 我们以不同请求速率的泊松分布生成请求到达时间. 受篇幅所限, 聊天机器人工作负载在三款 OPT 模型上测试, 另外两种工作负载则在 OPT-66B 上测试; 其规模与近期开放权重 LLM 系列 [Tou23d] 中的最大模型相当.

- **聊天机器人** [Sch22]: 聊天机器人应用采用 ShareGPT 数据集 [Sha23b], 其中收录了用户分享的 ChatGPT 对话. 为保证响应速度, OPT-13B 的 TTFT SLO 设为 0.25 秒, TPOT SLO 设为 0.1 秒, 后者快于人类正常阅读速度. 随着模型执行延迟增加, OPT-66B 和 OPT-175B 的两项 SLO 略有放宽.
- **代码补全** [Che21]: 代码补全任务采用 HumanEval [Che21]. 该数据集包含 164 道带函数签名或文档字符串的编程题, 用于评估代码补全模型. 代码补全模型作为个人实时编程助手使用, 因此两项 SLO 都设置得较严格.
- **摘要** [Sum23]: 这是一项常见的 LLM 任务, 目标是为长文章、随笔乃至学术论文生成简明摘要. 我们使用包含摘要任务的 LongBench [Bai23a] [+longbench]. 如 [图 7](#figure-07) 所示, LongBench 的输入长度远超另外两个数据集. 因此, TTFT SLO 设置得较宽松, TPOT 要求则较严格.

**评估指标.** 我们以 *SLO 达成率*为主要指标. 给定一个 SLO 达成目标 (例如 90%) 后, 我们关注每块 GPU 的最大有效吞吐量, 以及系统能够承受的最严格 SLO. 评测重点是 90% 的 SLO 达成率 (所有曲线图均以竖线标出), 同时也会改变请求速率和延迟要求, 观察 SLO 达成率如何变化. 附录还给出 SLO 达成目标为 99% 时的结果, 用于说明系统在更严格达成目标下的表现.

**基线.** 我们将 DistServe 与两个基线系统比较:

- **vLLM [Kwo23]:** vLLM 是学术界和工业界广泛使用的代表性 LLM 服务系统. 它通过*连续批处理* [Yu22a] 提高吞吐量, 并以 *PagedAttention* [Kwo23] 减少 KV 缓存分配造成的内存碎片. 不过, 它把预填充和解码计算共置, 以最大化系统总吞吐量, 因而难以经济地满足延迟要求. vLLM 仅支持算子内并行, 因此按照既有工作 [Kwo23], 三款 OPT 模型的算子内并行度分别设为 1、4 和 8.
- **DeepSpeed-MII [Dee23]:** DeepSpeed Model Implementations for Inference (MII) 支持*分块预填充*: 它将长提示拆成较小的块, 再与短提示组合, 恰好填满目标 token 预算. 这种方法能缓解长预填充任务造成的预填充-解码干扰, 但无法彻底消除. 为公平比较, OPT-13B 和 OPT-66B 的算子内并行度与 vLLM 相同. DeepSpeed-MII 无法服务 OPT-175B: 其 $\mathit{vocab\_size}=50272$, 底层内核要求 $\mathit{vocab\_size}/\mathit{intra\_op}$ 是 8 的倍数, 而算子内并行度为 8 时不满足此条件; 改为 4 虽能满足该条件, 却会导致显存不足.

### 6.2 端到端实验

本节在真实应用数据集上比较 DistServe 与各基线系统的端到端性能.

**聊天机器人.** 我们在三款 OPT 模型上评估 DistServe 的聊天机器人性能. [图 8](#figure-08) 第一行显示, 随着请求速率逐步上升, 违反延迟要求的请求增多, SLO 达成率随之下降. 竖线表示系统仍能让超过 90% 请求满足延迟要求时, 每块 GPU 所能承受的最大请求速率.

在 ShareGPT 数据集上, DistServe 的请求速率比 vLLM 高 $2.0\times$-$4.6\times$. 这是因为 DistServe 通过分离部署消除了预填充-解码干扰. 两个阶段可分配不同资源并采用定制的并行策略, 分别优化各自的目标. 具体而言, 分析 175B 模型所选的放置策略 [+3] 可知, 预填充实例采用 inter-op = 3、intra-op = 3, 解码实例采用 inter-op = 3、intra-op = 4. 在这一放置下, DistServe 能够平衡 ShareGPT 上两个实例的负载, 以最低成本满足延迟要求. 这种放置并不直观, 很难靠人工找到, 说明搜索算法确实有效. 对 vLLM 而言, 共置预填充和解码会明显拖慢解码阶段, 大幅抬高 TPOT. 聊天机器人对 TPOT 的要求严格, 因而 vLLM 即使让多数请求满足 TTFT SLO, 仍会因大量请求违反 TPOT SLO 而拉低总体 SLO 达成率. 与 DeepSpeed-MII 相比, DistServe 的请求速率高 $1.6\times$-$7.4\times$. DeepSpeed-MII 在较大模型上的表现更好, 因为预填充任务更大, 分块预填充能在一定程度上缓解干扰. 然而, 如 §[2.3](#S2.SS3) 所述, 分块预填充比完整预填充更慢; 它以改善 TPOT 为代价, 因而难以满足 TTFT SLO.

[图 8](#figure-08) 第二行反映了系统对延迟要求变化的适应能力. 我们固定请求速率, 再通过 *SLO Scale* 参数同时线性缩放 [表 1](#table-01) 中的两项延迟要求. SLO Scale 越小, 延迟要求越严格. 这里要观察的是, 系统在达到目标达成率的前提下, 能承受多严格的 SLO Scale. 结果显示, DistServe 能承受比 vLLM 严格 $1.8\times$-$3.2\times$ 的 SLO, 比 DeepSpeed-MII 严格 $1.7\times$-$1.8\times$ 的 SLO, 因而可提供响应更及时的服务.

**代码补全.** [图 9](#figure-09)(a) 展示了服务 OPT-66B 时的代码补全性能. DistServe 的请求速率比 vLLM 高 $5.7\times$, 可承受的 SLO 严格 $1.4\times$; 与 DeepSpeed-MII 相比, 请求速率高 $1.6\times$, SLO 严格 $1.4\times$. 代码补全模型作为实时编程助手, 对 TTFT 的要求比聊天机器人更严格, 因而两个系统最终都受 TTFT 限制. DistServe 消除了来自解码任务的干扰, 搜索算法还会自动提高预填充实例的算子内并行度, 从而缩短预填充任务的平均延迟, 让更多请求满足 TTFT 要求.

**摘要.** [图 9](#figure-09)(b) 展示了服务 OPT-66B 时的摘要性能. DistServe 的请求速率比 vLLM 高 $4.3\times$, 可承受的 SLO 严格 $12.6\times$; 与 DeepSpeed-MII 相比, 请求速率高 $1.8\times$, SLO 严格 $2.6\times$. LongBench 中抽样的请求输入较长, 给预填充计算带来很大压力. 但摘要任务对 TTFT 的要求较宽松, TPOT 服务质量反而尤其重要. vLLM 将预填充和解码共置, 遇到长预填充任务时解码阶段会显著变慢, 因而无法满足 TPOT 要求.

### 6.4 消融研究

我们研究 DistServe 的两项关键创新: 分离和放置搜索算法. 在 §[6.2](#S6.SS2) 中, 我们遵循 vLLM 原始论文 [Kwo23], 为其选择默认的并行设置. 因此, 我们实现“vLLM++”, 它会枚举不同的并行方案并选择最优方案. 对 DistServe, 我们还比较算法 [2](#alg2) 找到的放置方案 (DistServe-Low) 与算法 [1](#alg1) 找到的方案 (DistServe-High). 后者搜索约束较少, 并假设较高的跨节点带宽. 由于 vLLM 不支持算子间并行, 且物理测试平台没有高跨节点带宽, 这一实验采用模拟.

**模拟器精度.** DNN 模型的执行具有很高的可预测性 [Guj20], 并行配置下也是如此 [Li23j, Zhe22]. 我们在 [表 2](#table-02) 中研究模拟器的准确度. 对“vLLM”和“DistServe-Low”, 我们比较模拟器报告的 SLO 达成率与测试平台上不同速率下的真实运行结果. 各种情况下的误差均小于 2%, 验证了模拟器的准确性.

**结果.** [图 11](#figure-11) 展示了四个系统在 ShareGPT 数据集上服务 OPT-66B 时的性能. “vLLM++”与“vLLM”的性能相同, 因为默认并行设置 (intra-op=4) 的每 GPU 有效吞吐量最高. 这进一步说明了分离的重要性. 预填充与解码阶段之间的干扰, 会显著减少通过调整并行度获得性能提升的空间. 相比之下, “DistLLM-High”可在“DistLLM-Low”之上进一步改进, 因为它不受这样的部署约束: 同一节点上的预填充与解码实例必须共享相同的模型阶段. 通过分离, 我们可为预填充和解码实例采用定制的并行方案, 在不受耦合效应影响的情况下优化各自的目标.

### 6.5 算法运行时间

[图 12](#figure-12) 显示了在 AWS m5d. metal 实例上, 具有 96 个核心的情况下, 随着提供给单个实例的 GPU 数量 ($N\times M$) 增加, 算法 [1](#alg1) (DistServe-Low) 和算法 [2](#alg2) (DistServe-High) 的运行时间. 根据结果, DistServe 随 GPU 数量良好扩展, 并且与模型大小无关. 这是因为模拟器只模拟离散事件, 因此无论模型多大, 运行时间都是相同的. 另一方面, 两个算法高度可并行化, 因为不同并行策略的搜索彼此独立, 从而使算法的执行时间随着 CPU 核心数量增加几乎线性加速.

随着 GPU 数量的增加, “Dist-Low”的执行时间变得比“Dist-High”更长. 这是因为“Dist-High”中对预填充和解码实例并行策略的搜索是独立的, 可以并行进行. 但对于“Dist-Low”, 由于部署上存在额外的限制, 我们需要枚举预填充和解码实例的所有可能的节点内并行组合. 即便如此, 算法的执行时间仍以分钟计, 并且由于它只需要在每次重新部署之前执行一次, 因此这个开销是可以接受的.

## 7 讨论

本文研究以有效吞吐量为优化目标的大规模 LLM 服务, 并为这一场景提出 DistServe. LLM 已用于多种服务场景, 各场景的优化目标和资源限制并不相同, 因而很难用一种方案解决所有 LLM 服务问题. 本节讨论 DistServe 的适用范围, 以及其他场景中可能更合适的方案.

**面向吞吐量的场景.** 对延迟不敏感的离线应用通常不要求很快返回结果 [She23]. 此时, 服务系统可以转而最大化总吞吐量, 而不是有效吞吐量, DistServe 的优势也可能减弱. 分块预填充并搭载解码任务 [Agr23, Dee23] 等技术或许更合适, 因为它能让每个批次填充至计算受限阈值, 在每次迭代中保持较高的 GPU 利用率.

**资源受限的场景.** 小型企业和个人研究者往往没有足够资源在大规模集群上部署 LLM [She23, Son23]. 当环境中只有少量甚至一块 GPU 时, DistServe 的设计空间会大幅缩小, 很难通过调整并行策略和资源分配来改善服务性能, 有时甚至完全无法调整. 此时, vLLM 和 DeepSpeed-MII 这类不做分离的系统 [Kwo23, Dee23] 架构更简单, 可以降低部署复杂度并提高运行效率.

**长上下文场景.** 现在越来越多的 GPT 模型支持超长上下文, 例如 Claude-3 [Ant24]、Gemini-1.5 [Goo24a] 和 Large World Model (LWM) [Liu24l], 它们的上下文窗口都达到 100 万 token. 在这类场景中, KV 缓存大小随提示长度线性增长, 传输开销也会增加. 不过, 预填充计算量按平方增长, 因而传输时间相对于预填充任务的占比会下降. 同时, 上下文变长会进一步拉大预填充与解码任务的计算需求差距, 加重两者之间的干扰. 因此, DistServe 的分离方法在长上下文服务中仍有应用价值.

## 8 相关工作

**推理服务.** 近年来出现了大量推理服务研究, 从 TorchServe [Ser23]、NVIDIA Triton [Nvi19b] 等通用生产系统, 到专门针对基于 Transformer 的 LLM 优化的系统 [Li23j, Yu22a, Agr23, Wu23b, Fan21, Nvi19a, Zho22, Su23]. Orca [Yu22a] 引入连续批处理来提高吞吐量. vLLM [Kwo23] 提出 PagedAttention, 以细粒度方式管理 KV 缓存. SARATHI [Agr23] 采用分块预填充, 将预填充请求拆成若干块并搭载解码请求, 从而提高硬件利用率. FastServe [Wu23b] 实现迭代级抢占调度, 减少长任务造成的排队延迟. 不过, 这些系统都将预填充和解码共置, 因而存在严重干扰. 同期的 Splitwise [Pat23]、TetriInfer [Hu24b] 和 DéjàVu [Str24] 也采用类似的分离思路优化 LLM 推理, 进一步说明了这种方法的有效性. DistServe 的区别在于更关注有效吞吐量优化, 并详细考察网络带宽的影响.

**面向有效吞吐量优化的系统.** 深度学习应用中已有不少有效吞吐量优化研究. Pollux [Qia21] 动态调整作业资源, 改善深度学习集群的调度性能并提高集群级有效吞吐量. Sia [Sub23] 采用异构感知调度, 将集群资源有效匹配给可弹性伸缩、自适应资源的作业. Clockwork [Guj20] 和 Shepherd [Zha23b] 通过延迟感知调度与抢占提高服务有效吞吐量, 但只面向传统小模型. AlpaServe [Li23j] 面向 LLM, 用模型并行对 GPU 执行进行统计复用, 从而提高资源利用率, 但它只处理非自回归生成. DistServe 是首个为自回归 LLM 推理优化有效吞吐量的工作.

**资源分离.** 资源分离系统 [Sha18b, Guo23d, Com23a] 将硬件资源从传统单体服务器基础设施中拆出, 分成独立管理的资源池. 这样可以更灵活、高效地扩展部署, 并提高资源利用率. 具有高速网络带宽和异构硬件支持的真正分离式数据中心可使许多应用受益 [Zha23a, Aud22, Jin24]. DistServe 也通过分离系统组件, 让资源可以独立扩缩和管理.

**训练中的模型并行.** DistServe 与大量训练模型并行研究 [Zhe22, Sho20, Hua19b, Raj20a, Nar19] 相互独立. 如 §[3.3](#S3.SS3) 所述, 推理服务工作负载具有训练环境所没有的特征. 这些系统与 DistServe 的交集在于沿不同维度实现模型并行的方法. DistServe 可以把新的并行优化纳入放置搜索算法.

## 9 结论

本文提出 DistServe, 一种将预填充和解码计算分离的 LLM 服务架构. DistServe 最大化每块 GPU 的有效吞吐量, 即在每块已配置 GPU 都达到 SLO 达成目标时所能服务的最大请求速率, 因而能在保证 SLO 的同时, 将每次 LLM 查询的成本最多降低 $7.4\times$. 研究结果表明, 随着延迟在 LLM 服务中日益重要, 分离预填充与解码是一种有望改善性能和服务质量保证的策略.

## 附录 A LLM 推理的延迟模型

为了准确模拟不同放置策略的有效吞吐量, 我们使用分析模型预测 LLM 推理中预填充和解码阶段的执行时间.

在现代大型语言模型服务系统中 [Nvi19a, Kwo23, Wu23b], 受内存限制的操作如 Softmax 和 LayerNorm 通常会与矩阵乘法内核融合以提高效率. 因此, GEMM 占据了整体延迟的主导地位, 我们的分析主要集中于它们.

### A.1 符号定义

以下是与模型架构相关的符号:

- $h$: 隐藏层大小
- $n$: 注意力头数
- $s$: 头大小 ($h=n\cdot s$)
- $m$: FFN 中间层大小

注意: 如果使用张量并行, $h$, $n$ 和 $m$ 应该除以张量并行的大小.

下面是描述将要执行的批次的符号:

- $B$: 批量大小
- $l_{0},l_{1},\dots,l_{B-1}$: 批次内每个请求的输入长度
- $t$: 批次中的 token 数量 ($t=\sum_{i=0}^{B-1}l_{i}$)
- $t_{2}$: 输入长度的平方和 ($t_{2}=\sum_{i=0}^{B-1}l_{i}^{2}$)
- $b$: 注意力内核中的块大小. 该参数用于 FlashAttention [Dao22c], 这是一种当前大型语言模型服务系统采用的常见内核优化技术.

### A.2 预填充阶段延迟建模

由于注意力操作使用了特别优化的内核, 我们首先讨论预填充阶段的另外四个矩阵乘法:

<span id="table-03"></span>

![论文原表 3](./distserve/table-03.png)

**表 3.**

这些操作的算术强度 (AI) 为 $O(t)$. 在 NVIDIA A100-80GB GPU 上, 当 AI 超过 156 时, 它是计算受限的. 由于 $t$ 在实际情况下通常可以达到几百, 这些操作都是计算受限的. 因此, 我们可以根据总 FLOPs 来建模这些操作的延迟:

$$
T_{1}=C_{1}\cdot(4th^{2}+2thm)
$$

接下来, 我们讨论使用 FlashAttention[Dao22c] 优化的预填充注意力操作. 由于注意力只在同一请求的 token 之间计算, 当前实现会为同一批次中的每个请求启动注意力内核. 对于一个注意力头和一个包含 $l$ 个 token 的请求, 注意力内核总共需要执行 $2sl+3sl\cdot(l/b)\approx 3sl\cdot(l/b)$ 次内存读写, 以及 $2sl^{2}+sl(l/b)\approx 2sl^{2}$ 次 FLOPs. 因此, 当 $b=16$ 时 AI 为 $2b/3=10.677$, 当 $b=32$ 时为 $21.333$, 说明该操作在 A100 GPU 上受内存带宽限制. 因此, 整个注意力层的延迟 (包括所有请求和所有注意力头) 可建模为:

$$
T_{2}=C_{2}\cdot n\cdot\sum_{i=0}^{B-1}\frac{3sl_{i}^{2}}{b}=C_{2}\cdot\frac{3nst_{2}}{b}=C_{2}\cdot\frac{3ht_{2}}{b}
$$

总体而言, 预填充阶段的延迟可以建模为:

$$
T_{\mathrm{Prefill}}=C_{1}\cdot(4th^{2}+2thm)+C_{2}\cdot\frac{3ht_{2}}{b}+C_{3}
$$

我们使用 $C_{3}$ 来量化其他开销, 如 Python 运行时, 系统噪声等. 然后我们使用分析和插值来确定 $C_{1}$, $C_{2}$ 和 $C_{3}$ 的值.

**表 4.**

这些操作的 AI 是 $O(B)$. $B$ 受 GPU 内存大小和严格延迟要求限制, 因此在现有的服务场景中, 这些操作受内存带宽限制. 总内存读写为 $8Bh+4h^{2}+2hm+2Bm$, 并且由于 $h$ 和 $m$ 通常显著大于 $B$, 我们可以将延迟建模为:

至于解码注意力操作, 对于一个注意力头和一个具有 $l$ 个生成 token 的请求, 它需要执行 $3sl$ 次内存读写, 以及 $2sl$ 次 FLOPs. 该操作受内存带宽限制, 因此我们可以将解码注意力的延迟建模为:

$$
T_{4}=C_{5}\cdot n\cdot 3s\sum_{i=0}^{B-1}l_{i}=C_{5}\cdot 3ht
$$

总结一下, 解码阶段的延迟为:

$$
T_{\mathrm{Decoding}}=C_{4}\cdot(4h^{2}+2hm)+C_{5}\cdot 3ht
$$

在这里我们没有引入开销项 (比如在分析阶段的 $C_{3}$), 因为 $4h^{2}+2hm$ 已经是一个常数, 并且开销可以放入 $C_{4}$ 中. 同样地, 我们使用分析和插值来确定 $C_{4}$ 和 $C_{5}$ 的数值.
