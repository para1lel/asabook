## 摘要

大型语言模型 (LLM) 推理由两个不同的阶段组成—预填充阶段, 用于处理输入提示, 以及解码阶段, 用于自回归生成输出标记. 虽然在小批量下预填充阶段能够有效地饱和 GPU 计算, 但解码阶段由于每次请求生成一个标记, 导致计算利用率较低. 在使用流水线并行时, 预填充和解码时间的差异也会导致微批次之间的不平衡, 进一步因为气泡而导致效率下降.

我们提出了 Sarathi 来应对这些挑战. Sarathi 使用分块预填充, 将一个预填充请求拆分为大小相等的块, 并使用解码最大化批处理, 通过使用单个预填充块构建批次, 并用解码填充剩余的槽位. 在推理过程中, 预填充块饱和 GPU 计算, 而解码请求通过“搭便车”参与, 其成本相比仅解码批次低一个数量级. 分块预填充允许从单个预填充请求构建多个解码最大化批次, 最大化可以搭便车的解码覆盖率. 另外, 这些批次的统一计算设计改善了微批次之间的不平衡, 显著减少了流水线气泡.

我们的技术在各类模型和硬件上显著提升了推理性能. 对于在 A6000 GPU 上的 LLaMA-13B 模型, Sarathi 提高了解码吞吐量最多可达 10$\times$, 并将端到端吞吐量加速最多可达 1.33$\times$. 对于在 A100 GPU 上的 LLaMa-33B, 我们实现了端到端吞吐量提高 1.25$\times$, 解码吞吐量提高最多达 4.25$\times$. 与 GPT-3 的流水线并行结合使用时, Sarathi 将气泡减少了 6.29$\times$, 从而端到端吞吐量提升了 1.91$\times$.

## 1 引言

语言模型的扩展 [Advanb01, CoRR22, CoRR23, CoRRb01] 已经导致它们在各种复杂任务中的能力出现 [Res22] — 自然语言处理, 问答, 代码生成等. 这导致它们在涵盖对话引擎 [CoRR23, Chatga00, Anthra00, Charaa00], 搜索 [Bing00, Komo00, You00, Perpla00, Googla00], 代码助手 [Githua00, Replia00, Amazoa00] 等的应用中的使用量激增. 对这些大型模型进行推理所需的大量 GPU 计算, 再加上它们的广泛使用, 使得大语言模型推理成为主要的 GPU 工作负载. 因此, 优化大语言模型推理变得非常重要, 并且最近引起了极大的关注 [Efficb22, Highta23, July22].

在本文中, 我们首先分析了导致大型语言模型 (LLM) 推理效率低下的根本原因. 每个 LLM 推理请求都经历两个阶段—预填充阶段, 对应输入提示的处理; 解码阶段, 对应自回归生成标记. 预填充阶段会并行处理输入序列中的所有标记, 即使批量大小很小, 也会导致 GPU 利用率很高. 例如, 在 A6000 GPU 上, 对于 LLaMA-13B 模型, 序列长度为 512 个标记的预填充即使批量大小仅为 1, 也会使 GPU 计算资源达到饱和. 另一方面, 解码阶段在每次自回归过程中只处理单个标记, 导致在较小批量情况下 GPU 利用率非常低. 例如, 我们的实验显示, 在小批量情况下, 每个标记的解码成本可能高达 $\sim 200$ 倍预填充每个标记的成本. 另外, 由于一个请求只经过一次预填充, 但需要多次解码 (每生成一个标记进行一次解码), 总体推理效率因此受到显著影响.

提高大型语言模型 (LLM) 解码效率的一个策略是通过模型并行性增加批量大小. 在高带宽连接的服务器上, 例如 NVIDIA DGX A100, 张量并行性 [Xivb09] 可以在最多 8 个 GPU 上部署 LLM, 从而支持大批量大小和高效解码. Pope 等人 [Efficb22] 显示, 张量并行性可以在专业 TPUv4 集群上扩展到 256 个设备. 然而, 在如此大规模的张量并行下, 当超集群不可用时可能导致性能下降. 在这种情况下, 流水线并行性 [Narayb19, Systeb22] 可以帮助增加批量大小. 因此, 像 Orca [July22] 这样的系统依赖流水线并行来扩展 LLM 推理, 并采用使用微批量缓解流水线停滞或气泡的知名解决方案 [Advanf19]. 然而, 正如我们在本文中所展示的, 基于标准微批量的调度仍然可能由于 LLM 推理的独特特性而产生流水线气泡. 具体来说, LLM 推理由长度不一的预填充 (prefills) 和解码 (decodes) 混合组成. 这导致不同微批的处理时间不同, 从而产生显著气泡并浪费 GPU 周期, 如 [图 1](#figure-01)(a) 所示. 请注意, 图中的第一个气泡是由于提示 (prompt) 大小不同, 而第二个气泡是由于提示和解码计算时间不匹配造成的.

本文介绍了 Sarathi 的设计和实现, 这是一种高效的大型语言模型推理技术. Sarathi 使用分块预填充和解码最大批量处理来解决 1) 解码效率低下和 2) 流水线气泡的问题. 分块预填充将预填充请求拆分为相等的计算大小块. 另外, Sarathi 使用解码最大化批处理, 通过使用单个预填充块构建批次, 并填充剩余批次的解码. 这种混合批处理提供了既饱和又统一的工作单元, 从而解决了低效解码和流水线气泡的问题.

由于预填充和解码阶段的计算需求不同, 我们方法的关键见解是, 将预填充和解码请求混合在同一批中可以实现均匀的高计算利用率. 然而, 由于每个请求只有一个预填充阶段, 随后是多个解码阶段 (每个生成的令牌), 我们没有足够的预填充请求来总能创建混合批次的预填充和解码. 分块预填充允许我们从单一预填充请求构建多个混合批次, 从而扩大可搭载预填充的解码覆盖范围. 在我们的混合批处理中, 单个预填充块确保了高 GPU 利用率, 而解码阶段则请求“搭载”. 给定一个大型语言模型应用的平均预填充与解码令牌比例, 我们选择一个能最大化整体性能的预填充块大小.

Sarathi 构建的混合批次具有统一的计算需求. 因此, 当与管道并行性结合使用时, Sarathi 确保微批量的良好平衡, 从而显著减少了管道气泡, 如[图 1](#figure-01) (#figure-01) (b) 所示.

我们在不同型号和硬件上评估了 Sarathi—LLaMA-13B 搭载在 A6000 GPU, LLaMA-33B 搭载在 A100 GPU, 以及在模拟的 64 个 A100 GPU 集群中实现 8 路流水线和 8 路张量并行的 GPT-3. 对于 A6000 上的 LLaMA-13B, Sarathi 将译码吞吐量提升了最多 10$\times$, 端到端吞吐量提升了高达 1.33$\times$. 同样, 对于 LLaMA-33B 在 A100 上的测码吞吐量提升了 4.25$\times$, 端到端吞吐量提升了 1.25$\times$. 当使用流水线并行时, Sarathi 将气泡减少 6.29$\times$, 实现端到端加速 1.91$\times$.

我们论文的主要贡献包括:

1.1.

分块预填充, 允许构建计算饱和且均匀的工作单元.

2.2.

解码最大化批处理, 允许低效解码“搭载”, 并使用高效的预填充.

3.3.

将分块预填充和解码最大批量处理应用于流水线并行性, 以显著减少流水线气泡.

4.4.

对多种模型, 硬件和并行策略进行的广泛评估, 展示了吞吐量提升最高 1.91$\times$ 的水平.

## 2 背景

我们首先概述了 Transformer 架构, 随后简要讨论了 LLM 推理的两个阶段, 以及流水线并行.

### 2.1 Transformer 架构

[图 2](#figure-02) 显示了 Transformer 解码器块的架构. 每个解码器块由两个主要模块组成: 自注意力和前馈网络 (FFN). 这些模块可以划分为以下六个操作: preproj, attn, postproj (在注意力模块内), 以及 ffn_ln1, ffn_ln2 (在 FFN 内) 和其他 (例如层归一化, 激活函数, 残差连接等).

### 2.2 填充和解码阶段

Transformer 推理从填充阶段开始, 该阶段并行处理给定批次的所有输入令牌. 在此阶段, Transformer 块的输入是一个形状为 $[B,L,H]$ 的张量, 其中 $B$ 表示批次大小, $L$ 表示每个请求的序列长度 (即给定查询中的输入令牌数量), $H$ 表示模型的嵌入维度 (例如, LLaMA-13B 为 5120).

[表 1](#table-01) 显示了各种操作的输入, 输出和权重张量的形状. 每个 Transformer 块首先对给定输入 $X$ 进行自注意力计算. 通常使用多头注意力, 但为了说明的简便, 我们只考虑一个头. X 上的线性变换 preproj (使用形状为 $[H,H]$ 的权重张量 $W^{Q}$, $W^{K}$ 和 $W^{V}$) 生成了通常称为查询, 键和值的 $Q$, $K$ 和 $V$, 每个的形状为 $[B,L,H]$. 在内部, preproj 是 $X$ 与形状为 $[H,3H]$ 的组合权重张量进行的单次矩阵- 矩阵相乘.

接下来, 对 $Q$, $K$ 和 $V$ 进行 attn 计算, 生成形状为 $[B,L,H]$ 的张量 $Y$. 最后, postproj 对 $Y$ 进行线性变换 (使用形状为 $[H,H]$ 的权重矩阵 $W_{o}$), 返回形状为 $[B,L,H]$ 的张量 $Z$.

接下来, FFN 模块执行两次批量矩阵- 矩阵相乘. 在 ffn_ln1 中, $Z$ 与形状为 $[H,H_{2}]$ 的权重张量相乘, 生成形状为 $[B,L,H_{2}]$ 的输出张量, 然后在 ffn_ln2 中与形状为 $[H_{2},H]$ 的权重张量相乘, 输出形状为 $[B,L,H]$ 的张量. 这里, $H_{2}$ 指模型的第二个隐藏维度.

解码阶段执行与预填充相同的操作, 但仅针对在上一次自回归迭代中生成的单个标记. 因此, 解码阶段的输入张量的形状为 $[B,1,H]$ (与预填充的 $[B,L,H]$ 不同). 另外, 每个新标记的注意力计算依赖于所有先前标记在同一请求中的 key ($K$) 和 value ($V$) 张量. 为了避免在每次迭代中重新计算所有标记的 $K$ 和 $V$, 大多数实现会将这些值缓存到 GPU 内存中—这称为 KV 缓存. 注意, 每个标记的 $K$ 和 $V$ 张量的形状为 $[1,H]$.

### 2.3 多 GPU LLM 推理

随着大型语言模型 (LLMs) 模型规模的增大, 将它们扩展到多 GPU 以及多节点部署变得必要 [Efficb22, Sphera00]. 另外, LLM 推理吞吐量, 特别是解码阶段的吞吐量, 受到我们能够放入 GPU 的最大批量大小的限制. 因此, 推理效率可以通过模型并行 (model-parallelism) 受益, 该方法将模型权重分片到多个 GPU, 从而释放内存以支持更大的批量大小. 先前的工作已经使用了张量并行 (tensor-parallelism, TP) [Xivb09] (节点内) 和流水线并行 (pipeline-parallelism, PP) [July22, Fastea00, Fast23] (跨节点) 来实现此目的.

TP 将每一层在参与的 GPU 之间分片. 这会将模型权重和 KV 缓存平均分配到各 GPU 工作器上, 从而实现每 GPU 批量大小的线性扩展. 然而, 这会带来较高的通信成本, 因为每一层需要两次全归约操作—一次在注意力计算中, 另一次在前馈网络 (FFN) 中 [Xivb09]. 另外, 由于这些通信操作处于关键路径中, TP 通常仅在由高带宽互连 (如 NVLink) 连接的单节点内使用. PP 主要用于支持非常大型模型的跨节点部署, 因为这些模型无法适应单个节点.

与 TP 相比, PP 按模型层进行划分, 每个 GPU 负责部分层. 为了让所有 GPU 在“流水线”中保持忙碌, 采用了微批处理. 这些微批在每次迭代中沿流水线从一个阶段移动到下一个阶段. 与 TP 相比, PP 的计算- 通信比具有明显优势, 因为我们只需为多层计算发送一次激活. 另外, PP 仅需通过点对点通信操作进行通信, 而 TP 则需要更昂贵的全规约操作. 因此, 当集群规模无法获得像 NVlink 这样的高带宽连接时, PP 是唯一可行的模型并行方法. 在这种情况下, 使用 PP 可以帮助每个节点支持的最大批量增加 2-3$\times$, 从而提高 LLM 推理效率.

## 3 动机

本节中, 我们展示了 LLM 推理效率低下的两个主要原因: (1) 解码阶段受限于内存, (2) 使用流水线并行导致 LLM 产生显著的流水线气泡. 这些因素共同导致 LLM 推理的 GPU 利用率低下.

### 3.1 分析预填充和解码吞吐量

**图 3.** LLaMa-13B 在 A6000 GPU 上不同批量大小的每标记预填充和解码时间 (序列长度 = 1024). 即使批量大小为 1, 预填充也会让 GPU 计算达到饱和, 并导致各批量大小的每标记时间几乎保持恒定. 解码未充分利用 GPU 计算, 批量大小为 1 时的成本可高达预填充的 200$\times$. 随着批量大小增加, 解码的线性操作的增量成本几乎为零. 注意力成本不会因批量大小而受益, 因为它受内存限制.

[4(a)](#figure-04) 显示了不同批量大小 ($B$) 和序列长度 ($L$) 下预填充阶段和解码阶段的吞吐量. 我们观察到, 当 $B\times L\geq 512$ 时, 预填充阶段的吞吐量在大约 180 令牌/毫秒时达到饱和: 例如, 单个预填充请求可以在 $L\geq 512$ 处实现峰值吞吐量. 相比之下, 小批量下解码吞吐量呈线性增长. 为了进一步理解解码阶段的饱和点, 我们对单层进行分析, 而不是完整模型的 40 层. 这使我们能够在 GPU 上适配 40$\times$ 更大的批量, 因为模型权重和 KV 缓存的内存占用减少. 我们发现解码在更大的批量下达到饱和 (例如, 256 批量和 1024 序列长度). 如此大的批量在完整模型下是不可行的.

为了解释这种行为, 我们对各个操作的算术强度进行了分析: 算术强度衡量每次内存读/写可用于计算的量, 可用于区分计算受限和内存受限的操作. [4(b)](#figure-04) 分别展示了各个操作在预填充阶段 (左) 和解码阶段 (右) 的算术强度. 如图所示, 在预填充阶段, 即使批量大小为 1, 所有操作的算术强度都很高. 另一方面, 这些操作在解码阶段的算术强度下降了两个数量级以上. 只有在非常大的批量大小为 256 时, 解码阶段才开始变得计算密集. 然而, 由于每个请求的 KV 缓存占用, 将批量大小扩展到如此高的值是不可行的. 例如, 在 A6000 GPU 上, 对于 LLaMA-13B 模型, 序列长度为 1K 时, 最大可容纳的批量大小为 18 个请求. 因此, 在目前实际可用的批量大小范围内, 解码阶段仍然受内存限制.

这两个阶段吞吐量扩展的差异源于预填充阶段执行 (批量) 矩阵- 矩阵乘法, 而解码阶段执行向量- 矩阵乘法. 众所周知, 算术强度高于 GPU FLOPS: 内存带宽比的内核是计算绑定的, 可以高效执行 [Matria00]. 相比之下, 算术强度较低的内核由于受内存限制, 无法充分利用 GPU.

### 3.2 LLM 推理中的流水线气泡

流水线并行 (PP) 是一种在跨节点部署大模型时很受欢迎的策略, 因为与张量并行 (TP) 相比, 它的通信开销更低. PP 按层划分模型, 每个 GPU 负责部分层; 而 TP 则是在参与的 GPU 之间分配每一层. 如 [§2.3](#S2.SS3) 所讨论的, 与 TP 相比, PP 有更好的计算- 通信比, 并且不需要昂贵的互连.

然而, PP 的一个挑战是它会引入流水线气泡或 GPU 空闲期, 因为后续的流水线阶段必须等待前一阶段中相应微批的完成. 流水线气泡是训练任务中已知的问题, 它们出现在前向和反向传递之间, 因为前一阶段需要等待反向传递到达. 因此, 在 PP 训练任务中通常采用微批处理, 以将气泡在构成一个批次的多个微批之间摊薄 [Systeb22, Narayb19, Advanf19].

与训练不同, 由于推理任务只进行前向传播而不进行反向传播, 人们可能会认为在推理过程中使用微批次可以完全避免流水线气泡. 事实上, 先前关于变换器推理的工作, 例如 FasterTransformer [Fastea00] 和 FastServe [Fast23] 使用微批次, 并且没有考虑流水线并行中的气泡问题.

Orca [July22] 表明, 使用迭代级调度可以消除流水线调度中的气泡 (参见 [July22] 中的 [图 8](#figure-08)). 然而, 正如我们在本文中所展示的, 即使对请求进行迭代级调度, 每个微批次 (或迭代) 在大型语言模型推理中所需的计算量也可能不同 (因此执行时间也会不同), 这取决于微批次中预填充和解码 token 的组成 (参见 [图 5](#figure-05)). 我们在推理过程中识别出三种类型的气泡: (1) 类似 $\mathrm{PB}_{1}$ 的气泡, 由于两个连续微批次中预填充 token 数量不同而产生; (2) 类似 $\mathrm{PB}_{2}$ 的气泡, 由于预填充阶段和解码阶段的计算时间不同而产生, 当一个阶段紧随另一个阶段时出现; (3) 类似 $\mathrm{PB}_{3}$ 的气泡, 由于微批次之间解码计算时间的差异产生, 因为累积的上下文长度 (KV 缓存长度) 在不同请求中会有所不同. 这些流水线气泡是浪费的 GPU 周期, 并且直接对应于流水线并行服务吞吐量的损失. 如果我们能够确保每个微批次执行均匀的计算, 就可以缓解这些流水线气泡.

### 3.3 见解

我们的实验表明, 预填充阶段和解码阶段的计算利用模式非常不同—即使只有一个请求, 预填充也可以使 GPU 计算达到饱和, 而解码阶段则需要较大的批量才能高效利用计算资源. 然而, 由于大的批量占用大量 KV 缓存, 这是不切实际的. 这种不成比例的资源利用意味着对于每个请求, 存在高计算利用率的阶段 (由于高效的预填充), 随后可能会有长时间低效的解码阶段, 导致整体 GPU 利用率低. 另外, 跨微批次的计算时间不均匀会导致流水线空闲, 导致多 GPU 流水线并行部署效率低下.

这一观察使我们得出关键见解, 即可以通过以下方式构造均匀且计算密集的批次: (1) 通过分块预填充将大型预填充请求切分为较小, 计算高效且均匀的块; (2) 创建一个包含预填充块和其上附加解码的混合批次. 因此, 创建这种均匀且计算密集的批次可以确保 GPU 在整个过程中保持高利用率, 并通过消除流水线中不同阶段微批次的运行时差异来最小化多 GPU 部署中的流水线空闲.

## 4 Sarathi: 设计与实现

在本节中, 我们描述了 Sarathi 的设计与实现, 它采用了两种技术—分块预填充和解码最大批处理, 以提高大语言模型 (LLM) 推理的性能.

### 4.1 概述

像 FasterTransformer 这样的传统推理引擎
[Fastea00] 执行请求级别的推理调度. 它们以请求为粒度处理批次; 也就是说, 只有当当前批次中的所有请求完成后, 才会选择下一个批次的请求在模型副本上执行. 虽然这降低了调度框架的操作复杂性, 但在资源使用上效率不高. 批次中较短的请求必须填充到与最长请求相同的长度, 因此会进行浪费工作而无法提前退出. 另一种方法是迭代级调度, 这在 Orca [July22], vLLM [Easy00] 和 HuggingFace TGI [Text00] 等较新系统中被提出, 其中根据预定的批次大小, 请求可以动态地进入和退出批次.

然而, 现有的迭代级调度系统并不关注构成批次的请求, 也不关注批次之间的执行时间差异. 具体而言, 一个批次可能只包含预填充阶段的请求, 仅包含解码阶段的请求, 或者是混合请求, 包括少量预填充和解码请求, 唯一的约束是批次大小在任何时候都是 $b$. 正如 §[3.3](#S3.SS3) 中讨论的, 这种批次形成导致计算单位不均匀, 造成资源利用的突发性波动和流水线空闲. Sarathi 通过引入两项关键技术来应对这一挑战: 分块预填充 (chunked-prefills) 和最大化解码批处理 (decode-maximal batching).

### 4.2 分块预填充 (Chunked-prefills)

分块预填充是一种基于两个关键洞察的预填充拆分机制. 首先, 对于特定的模型和 GPU, 增加预填充 token 的数量在超过某个点之后会显示出吞吐量递减的收益, 如 [4(a)](#figure-04) 所示. 例如, Llama-13B 模型在 A6000 GPU 上, 当预填充 token 数量为 512 或更高时, 能够达到预填充吞吐量的峰值. 在块大小为 256 时, 我们看到峰值吞吐量仅略微下降 12.5%. 另外, 随着模型隐藏维度的增加, 充分利用 GPU 计算所需的块大小会下降; 例如, GPT-3 的单层 (隐藏大小 = 12288) 在 A100 GPU 上的吞吐量在块大小为 256 时达到峰值. 这意味着可以通过精心切分的预填充块形成一个能够充分利用计算的批次. 其次, 在许多实际场景中, 预填充的大小相当大, 在生产工作负载中通常为 1K – 4K, 因此为将预填充请求拆分为更小的计算单元提供了可能.

![参见图注](./sarathi/figure-06.png)

**图 6.** 展示了在 Sarathi 中不同块预填充迭代中注意力掩码的设置示例 (q 和 k 分别表示“查询”和“键” token). v (“值”) 的注意力掩码设置方式类似.

实现分块预填充需要谨慎设置注意力掩码. 假设一个请求的输入提示大小为 1K, 如果将其拆分为四个每个大小为 256 个标记的块, 我们需要确保为每个后续预填充块适当设置注意力掩码, 直到提示结束. 为了便于说明, 使用一个块大小为四的示例, [图 6](#figure-06) 展示了 Sarathi 如何在三个连续迭代中逐步为预填充提示的每个连续块设置注意力掩码: 每个查询标记 $q_{i}$ 可以看到它之前的所有标记的键 (和值), 但不能看到之后的标记. 以这种方式设置注意力掩码确保分块预填充的计算在数学上等同于完整预填充.

分块预填充的开销. 将预填充序列的输入分割成多个较小的块有两个潜在的开销来源. 首先, 随着块大小变小, 分块预填充计算的算术强度会降低. 因此, 较小的块可能会由于 GPU 利用率低而影响预填充效率. 然而, 这可以通过对给定模型- 硬件组合和预期工作负载下各种块大小的预填充吞吐量进行一次性分析来轻松解决, 并可以选择一个块大小, 以使模型的端到端吞吐量最大化.

其次, 由于对请求的先前块中的令牌的 KV 缓存需要重复访问, 分块预填充在注意力计算中会产生轻微的开销. 虽然直到提示结束的每次分块预填充操作在 FFN 上执行的计算次数相同, 但在第一个块之后的每个后续块的注意力内核都必须重新从 GPU 内存中读取先前令牌的所有 KV 对, 如 [图 6](#figure-06) 所示. 例如, 如果预填充序列被分为 $N$ 块, 那么第一个块的 KV 缓存将被加载 $N$ 次, 第二个块的 KV 缓存将被加载 $N-1$ 次, 依此类推. 然而, 由于注意力计算时间增加造成的开销并不会显著影响端到端的预填充效率, 因为注意力计算在整体前向传递时间中占比很小, 如 [表 2](#table-02) 所示. 我们在 [§5.4](#S5.SS4) 中对分块预填充的开销进行了详细分析.

### 4.3 最大解码批处理

利用分块预填的优势需要我们仔细构建一个混合批次, 该批次由预填和解码令牌的混合组成, 以最大化计算利用率并确保所有批次的计算时间统一. 我们提出最大解码批处理, 以通过利用分块预填的理念来缓解迭代调度中计算和记忆利用的不平衡.

在最大解码批处理 (decode-maximal batching) 中, 我们通过使用单个预填充块 (prefill chunk) 并将剩余槽位附加解码标记 (decode tokens) 来构建批处理. 这个混合批处理为我们提供了既能充分利用计算能力又均匀的工作单元. 接下来我们讨论如何构建混合批处理以实现最大效率.

#### 4.3.1 用预填充附加解码

要将解码附加到预填充中, 我们需要注意两件事. 首先, 我们需要确定可以附加的解码的最大可能批处理大小, 并确定构成预填充块的预填充标记数量. 其次, 为了实际利用混合批处理的 GPU 饱和预填充计算使解码高效, 我们需要将预填充块和批处理解码的线性操作计算融合为单个操作.

解码批次. 与预填充块一起并行的最大解码批次大小, 是基于可用 GPU 内存 ($M_{G}$), 每个 GPU 模型参数的内存需求 ($M_{S}$) 以及模型支持的最大序列长度 $L$ 来确定的. 每个请求的预填充 ($P$) 和解码 ($D$) 令牌总数不能超过该最大序列长度. 假设每对 K 和 V 所需的内存为 $m_{\mathrm{kv}}$, 则最大允许的批次大小 $B$ 的确定如下:

$$
B=\lfloor\left(\frac{M_{G}-M_{S}}{L*m_{\mathrm{kv}}}\right)\rfloor
$$

在基准方案中, 仅解码的批次的最大大小为 $B$. 在 Sarathi 中, 解码的最大数量为 $B-1$, 因为它们与一个预填充块一起进行 (预填充块的 KV 缓存也需要保留在 GPU 内存中, 直到对应的解码迭代开始).

在解码最大化批处理情况下, 我们融合了所有线性操作, 同时让预填充和解码的注意力计算分别进行. 解码请求的注意力操作会进行批处理, 而预填充块中的注意力操作则单独处理.

解码效率. 回想一下, 预填充和解码阶段遵循相同的计算路径, 即线性操作在预填充和解码阶段使用相同的权重张量. 然而, 与预填充相比, 一个解码迭代只包含少量输入标记 (等于批次大小). 因此, 在基准解码中, 大部分计算时间都花在从 GPU 全局内存中获取模型权重上.

相比之下, decode-maximal 批处理通过矩阵乘法在解码标记上进行计算, 将解码标记与预填充标记组合在一次矩阵乘法操作中. 这实际上消除了单独加载模型权重用于解码的需求—即, 一旦模型权重被获取用于预填充, 它们也会被用于解码. 因此, decode-maximal 批处理将解码从内存受限阶段转变为计算受限阶段. 通过这种方式, 当解码与预填充捆绑在一起时, 在 Sarathi 中的额外成本微乎其微 (注意注意力成本保持不变).

### 4.4 确定理想的块大小

在 Sarathi 中, 一个重要的设计考虑是如何选择最合适的块大小. 一个直接的选择是选择能够饱和模型预填充吞吐量的最小块大小. 然而, 我们发现这种策略在许多情况下并不是最有效的.

为了展示块大小的重要性, 我们引入了一个简单的符号“P: D 比例”, 它计算为给定批次中预填充令牌数量与解码令牌数量的比值. 例如, P: D 比例为 10 意味着预填充令牌的数量是解码令牌的 10 倍. 对于固定的 P D, 较低的 P: D 比例意味着相比于较高 P: D 比例的批次, 批次中有更多的解码令牌.

<span id="figure-07"></span>

![参见图注](./sarathi/figure-07.png)

**图 7.** 瓷砖量化对 A6000 GPU 上 LLaMA-13B 单次迭代运行时的影响.

Sarathi 中预填充块的大小会影响可以使用最大解码批处理伴随的解码数量. 例如, 考虑一个批次包含四个请求 (其中一个请求处于预填充阶段, 三个请求处于解码阶段) 和块大小为 128. 大小为 P 的预填充将产生 P/128 个预填充块, 从而允许 P/128 $\times 3\approx P/42$ 个解码被伴随. 因此, 在这种情况下, 当 P: D 比例大于 42 时, 它允许我们将所有解码与预填充重叠. 类似地, 如果块大小为 256, 则当 P: D 比例大于 84 时, 所有解码都可以被伴随. 因此, 较小的块大小可以帮助在给定的预填充序列中伴随更多的解码令牌.

注意, 随着 P: D 比例下降, 解码时间会增加. 因此, 超过某个点后, 优化解码比在高峰效率下执行预填充更为重要. 例如, 如果预填充和解码阶段分别消耗总时间的 10% 和 90%, 那么即使 $5\times$ 预填充存在额外开销也是可以接受的, 只要解码可以通过 $2\times$ 或更多得到优化.

总结来说, 确定合适的块大小涉及权衡: 较小的块可以附带更多的解码, 但会以降低预填充效率为代价, 而较大的块则预填充效率高, 但能附带的解码较少. 因此, 理想的块大小取决于预期的 P: D 比例以及给定应用中预填充和解码时间之间的分配.

瓷砖量化效应. 另外, 我们还观察到与块大小相关的一个复杂细节. GPU 通过将给定矩阵划分为瓷砖并分配给不同的线程块进行并行计算来执行矩阵乘法 (matmul). 这里, 每个线程块指一组线程, 并执行相同数量的算术运算. 因此, 当矩阵维度可以被瓷砖大小整除时, 矩阵乘法可以达到最大的 GPU 利用率. 否则, 由于瓷砖量化, 一些线程块会执行额外 (浪费) 的计算 [Matria00].

注意, 当序列长度刚刚超过 128 的倍数 (我们实验中的块大小) 时, 计算预填充序列的时间会突然增加. 例如, 如 [图 7](#figure-07) 所示, 将序列长度从 128 个令牌增加到 256 个令牌, 迭代时间增加了 27%—从 55ms 增加到 69.8ms. 然而, 仅增加一个令牌, 迭代时间会进一步增加到 92.33ms—由于仅增加一个额外令牌, 迭代时间戏剧性地增加了 32%. 这表明, 当序列长度是块大小的倍数时, GPU 在矩阵乘法操作 (matmuls) 上效率最高.

因此, 选择理想的块大小是一个双重决策. 首先, 根据给定工作负载所需的 prefill 效率选择块大小. 接下来, 确保块大小与附带解码 token 数量的总和是 tile 大小的倍数. 这保证了融合操作的相关矩阵维度保持为 tile 大小的倍数. 例如, 如果选择的块大小为 256, tile 大小为 128, 且最大允许批量大小为 $B$, 那么, prefill 块大小应为 $256-(B-1)$.

### 4.5 实现

我们在 nanoGPT 代码库上实现了 Sarathi [GPTb00], 并支持分块预填充和最大解码批处理. 为了与 Orcas 的迭代级调度进行比较, 我们使用混合批处理机制, 对每个批次允许的预填充数量没有限制. 这确保了由于实现差异, 基线方法和 Sarathi 之间的结果没有差异. 为了计算注意力操作, 我们使用了 xformers 实现 [OPERAa00], 在我们的设置中, 它的性能优于 PyTorch 2.0 内置的注意力实现: 即 flash attention, 节省内存的注意力和数学注意力内核. 为了避免在每次解码迭代中分配 KV 缓存内存, 我们根据每个实验的最大序列长度预先分配 KV 缓存, 并在需要时原地更新相应的 KV 对.

我们在代码库中支持不同的模型配置, 以在不同模型和硬件组合上评估 Sarathi. 例如, 为了评估 LLaMA-13B, 我们将层数和注意力头数设置为 40, 隐藏层大小设置为 5120. 对于 LLaMA-33B, 我们使用 60 层, 52 个注意力头和 6656 的隐藏层大小. 对于 GPT-3, 我们使用 96 层, 96 个注意力头和 12288 的隐藏层大小. 配置依据这些模型公开可用的架构参数 [Llama00, Undera00].

#### 5.1.1 解码加速

我们首先展示了我们技术对解码阶段吞吐量的影响, 这个吞吐量是基于解码一个标记所花费的平均时间计算的. 对于基线系统, 我们通过将处理一次解码迭代的时间除以批量大小来计算每个标记的平均解码时间. 在 Sarathi 中, 解码是搭载进行的, 对于一个包含 $p+d$ 个标记的批次, 其中 $p$ 表示预填充块大小, $d$ 表示解码批量大小, 我们找到解码最大批次与仅包含大小为 $p$ 的预填充批次之间的运行时间差异, 并将时间差归因为 $d$ 请求批次的边际解码时间. 然后使用此边际解码时间来计算每个标记的解码时间.

[图 8](#figure-08) 显示了在 A6000 GPU 上 LlaMa-13B 对批大小进行变化时, 三种不同预填充序列长度下, 块大小为 256 的结果, 直到各自适配的最大值. 我们观察到, 分块预填充可以将解码效率提高至基线的十倍左右. Sarathi 的解码吞吐量较高, 因为最大解码批处理通过矩阵乘法计算解码令牌, 一旦从 GPU 全局内存中取出模型权重 — 无论是预填充还是解码 — 都可以重复使用.

我们观察到, 当我们增加批量大小或序列长度时, 解码加速会下降. 这种现象是预期中的, 原因如下: (1) 随着批量大小增加, 基线系统中的解码变得更加高效; (2) 注意力的计算成本随着序列长度呈二次增长: 由于我们所有的改进都来自优化线性操作, 更高的注意力成本减少了我们的改进空间. 然而, 在所有情况下, 我们的解码吞吐量提升仍然显著 ($2.8\times-10\times$).

#### 5.1.3 不同比例 $P:D$ 的影响

在本小节中, 我们使用各种序列长度和块大小, 研究不同 $P:D$ 比例对端到端推理吞吐量的影响, 以覆盖广泛的应用场景. $P:D$ 比例是这些实验中的一个重要参数: 较低的 $P:D$ 比例表示与具有较高 $P:D$ 比例的其他请求相比, 该请求包含更多的解码令牌. 尽管较低的 $P:D$ 比例意味着解码将构成推理成本的更大部分, 因此 Sarathi 将有更多的攻击面, 但这也意味着用于搭载解码的预填块将更少. 这种权衡导致了 Sarathi 的改进在特定 $P:D$ 比例上达到峰值, 然后在两侧逐渐减弱. 我们将在下面对此进行更详细的讨论.

[图 9](#figure-09) 绘制了我们的实验结果. 我们发现, 对于不同的预填充块大小和批量大小场景, 我们技术的峰值效率出现在不同的 $P:D$ 比例下. 如果 $C$ 是块大小, $B$ 是批量大小, 那么我们可以证明, 当解码与预填充块完美搭配时, 这一峰值会出现. 当预填充块的数量 ($=P/C$) 与所需的解码迭代次数 (=$D/(B-1)$) 相同, 即 $P:D=C/(B-1)$ 时, 就会发生这种情况. 例如, 当批量大小为 18 且块大小为 256 时, Sarathi 在序列长度为 1K 时, 在 $P:D=14$ ($\approx C/(B-1)=256/17$) 达到峰值吞吐量提升 $1.27\times$, 如 [9(a)](#figure-09) 所示. 对于序列长度=1K 且批量大小为 18 的情况下, 使用块大小为 512 也能显著提升性能, 增益高达 $1.23\times$ 在 $P:D=28$ ($\approx C/(B-1)=512/17$), 而块大小为 128 时增益要低得多. 虽然较小的块提供了更多的解码重叠可能性, 但将预填充拆分为非常小的块会导致算术强度降低, 即 matmul 效率降低并且开销增加 (由于 KV 缓存的多次读取), 从而降低端到端性能. 因此, 与较小的块大小 128 相比, 使用块大小 256/512 可获得更高的吞吐量. 请注意, 当使用较大块大小时, 峰值增益出现在更高的 $P:D$ 比例.

当推理既不完全被预填充 (prefills) 也不完全被解码 (decodes) 主导时, 我们可以实现峰值性能 (换句话说, 当 $P:D$ 比率平衡时). 这种状态允许我们更高效地同时进行预填充和解码. 否则, 如果 $P:D$ 较低, Sarathi 会耗尽预填充令牌; 如果 $P:D$ 较高, 则会耗尽解码令牌. 在这些情况下, Sarathi 可以切换到不同的块大小, 或者像标准基线处理那样, 只处理预填充或仅解码批次. 然而, 请注意, 尽管存在这种变化, 我们的改进在广泛的 $P:D$ 比率范围内仍然约为 10%.

#### 5.1.4 批量和块大小变化的影响

在本节中, 我们通过改变每个序列长度的批量大小和块大小, 更深入地研究 Sarathi 的性能. 在所有这些实验中, 我们关注执行场景中 $P:D$ 比率平衡的情况, 即当 $P:D=C/(B-1)$ 和所有解码令牌都与预填充完美叠加时. 这使我们能够测量系统的峰值性能.

[图 10](#figure-10) 显示了这些实验的结果. 对于每种序列长度和块大小的配置, 我们展示了不同批量大小的影响. 另外, 对于每次运行, 我们还显示了不同操作的运行时间, 即 preproj, attention, postproj 和 ffn.

请注意, decode-maximal 批处理通过对预填充和解码标记进行线性操作来批处理, 从而提高计算利用率. 因此, 与基线相比, 线性操作的运行时间显著减少, 最多可达 $1.6\times$ (参见第一行的 ffn 运行时间). 然而, 请注意, 改善的幅度还取决于 $P:D$ 比例 (换句话说, 取决于解码所占时间的比例). 例如, 使用 256 的块大小可以使可搭载的解码次数相比使用 512 的块大小增加一倍. 因此, 在最优配置 ($P:D=C/(B-1)$) 中, 对于块大小为 256, 解码在总运行时间中占的比例更高, 相比于块大小为 512 的最优配置. 因此, 当使用 256 块大小时, 我们的吞吐量增益更高.

我们还观察到, 不同线性操作使用我们的方法时速度提升不同. ffn 模块中的线性计算运行时间减少最多, 为 $1.3\times$-$1.6\times$. 相比之下, preproj 和 postproj 的运行时间减少为 $1.05\times$-$1.38\times$. 对于小批量大小, 我们发现大部分吞吐量提升是由于 decode-maximal 批处理下 ffn 计算效率更高.

### 5.2 与迭代级调度的比较

在我们迄今为止的评估中, 我们考虑了一个基线系统, 该系统一次处理仅填充或仅解码的批次. 这就是像 FasterTransformer 这样的流行框架部署 Transformer 模型的方式. 相比之下, Orca 的迭代级调度 [July22] 可以在单次迭代的粒度上向正在运行的批次中添加 (或移除) 请求.

迭代级调度也会影响 GPU 的利用率: 当请求在不同时间到达或离开时, 一些新到请求的填充操作会自动与已经运行请求的解码操作重叠. 因此, 我们预计迭代级调度至少在某些情况下会比基线更好. 然而, 我们强调, 在迭代级调度中, 填充与解码之间的重叠更多是一种副作用, 其行为可能会因为请求的大小以及到达或离开时间而有显著差异. 更重要的是, 目前的迭代级调度方法会在单个填充阶段提交请求的整个输入序列. 这在很大程度上限制了将解码 token 与填充操作捆绑的机会.

为了理解对整体吞吐量的影响, 我们在两种场景下评估最先进的迭代级调度器 Orca [July22]: 其最佳情况和最坏情况. 在最佳情况下, Orca 调度能够将一个新请求的完整预填充与正在进行的解码重叠. 在最坏情况下, 所有请求同时开始和结束. 在后一种情况下, Orca 调度的行为类似于我们之前的基线, 即预填充和解码令牌的计算之间没有重叠. 需要注意的是, 在 Orca 的平均情况下, 可能会有多个完整的预填充 (对应多个请求) 与一些解码重叠—这会进一步限制 Orca 利用预填充叠加解码令牌的能力.

[图 11](#figure-11) 显示了我们这些实验的结果. 首先 ([图 11](#figure-11)a), 我们展示了 $P:D=C/(B-1)$ 的最佳选择结果, 其中 $C=256$ 和 $B$ 是适合该序列长度的最大批量大小. 如预期, 最坏情况的 Orca 调度表现与基线相似. 我们发现, 对于 1K 的小序列长度, 最佳情况的 Orca 调度实现了高出 1.11$\times$ 的吞吐量. 这是由于最佳情况调度中预填充和解码请求的偶然重叠. 然而, 随着序列长度的增加, 最佳情况 Orca 调度的性能下降接近基线. 这是我们 $P:D=C/(B-1)$ 选择的一个结果. 随着序列长度的增加, 批量大小 $B$ 减少, 从而导致更高的最佳 $P:D$. 由于 Orca 将整个输入序列作为单个预填充请求提交, 较高的 $P:D$ 意味着它很快就耗尽了预填充令牌, 此时它处理剩余的解码令牌类似于基线, 即使是在最佳情况版本中也会变得低效. Sarathi 始终表现出色, 在三个序列长度下, 整体吞吐量分别增长 1.27$\times$, 1.25$\times$ 和 1.23$\times$.

在迭代级调度中需要考虑的另一个方面是变量序列长度对请求延迟的影响. 由于预填充时间随着输入序列长度的增加而增加, 在正在运行的批处理中添加更长的预填充序列可能会延迟当前的解码, 这反过来会增加这些正在进行的请求在 Orca 调度中的延迟. Sarathi 由于使用较小的块预填充而避免了这种情况.

接下来, 我们在 [图 11](#figure-11)b 中评估不同块大小下不同 $P:D$ 比例的吞吐量提升. 对于这个实验, 我们只考虑序列长度为 1K, 因为在这个范围内最优的 Orca 基线能够达到最高性能. 请注意, 最优的 Orca 调度可以被视为 Sarathi 的一种特殊情况, 其中块大小 $C$ 设置为最大序列长度. 如图所示, 随着块大小增加, 最优 $P:D$ 向右移动. 块大小为 256 的 Sarathi 在较低 $P:D$ 范围内表现最佳, 与基线相比, 达到峰值吞吐量提升 1.27$\times$. 块大小为 512 的 Sarathi 在整体上优于 Orca 的最优情况, 并在较高 $P:D$ 范围内表现最佳, 达到峰值吞吐量提升 1.23$\times$. 相比之下, Orca 的最优情况增益更平缓, 在更高的 $P:D$ 处达到峰值吞吐量提升 1.11$\times$.

接下来, 我们比较 [12(b)](#figure-12) 中不同场景下的整体请求完成时间. 该图绘制了完成给定数量请求所需的时间 (我们的模拟考虑了总共 10K 个请求). 与仅 TP 配置相比, TP-PP 执行在存储参数所需的内存上更少, 从而为 KV 缓存提供了更多空间. 因此, TP-PP 部署支持比仅 TP 部署高 2.45$\times$ 的批处理量, 同时我们观察到, 仅 TP 执行比使用 Orca 调度的基线 TP-PP 快 1.28$\times$, 这是由于后者存在大量流水线气泡. 然而, 通过分块预填充和最大解码批处理, 启用 Sarathi 的 PP 执行相比基线 TP-PP 加速了 1.91$\times$, 相比仅 TP 执行加速了 1.48$\times$. 因此, Sarathi 通过显著减少流水线气泡, 使流水线并行执行成为 LLM 推理的一个有吸引力的选项.

### 5.4 分块预填充的消融研究

在本小节中, 我们评估将完整的预填充计算拆分为多个较小的预填充块如何影响 Sarathi 中预填充阶段的效率. 为了量化这一点, 我们使用整个序列一次性计算预填充阶段所需的时间—这代表我们的基线预填充性能. 对于每个长序列, 我们随后使用分块预填充计算预填充, 并将其端到端运行时间与基线进行比较. 两者之间的差异表明了分块预填充的开销.

预填充分块有两个潜在的开销来源: (1) 与基线相比, 它使用了更小的块大小, 这可能降低 GPU 利用率; (2) 它需要根据请求中的块数多次加载每个块的 KV 缓存. 因此, 为了充分理解预填充分块的开销, 我们研究了以下内容: (1) 分块对仅预填充批次的注意力计算的影响, (2) 分块对仅预填充批次整体运行时间的影响, 以及 (3) 当分块预填充与最大解码批处理结合使用时的端到端吞吐量. 我们通过将块大小从 64 变化到 512 进行研究, 如 [图 13](#figure-13) 所示.

首先, 我们观察到较小的块大小会带来显著的开销, 无论是注意力计算还是整体预填充运行时间. 例如, 块大小为 64 会在注意力计算上产生 $3\times$ 的开销 (见 [13(a)](#figure-13)), 在整体预填充时间上大约产生 $5\times$ (见 [13(b)](#figure-13)). 正如大家所预期的, 较大块大小的分块预填充开销较低: 这是 GPU 利用率更高以及较大块减少 KV 缓存重加载的综合效果. 总体来看, 我们发现块大小为 256 和 512 时能提供合理的预填充效率, 将端到端预填充计算损失分别限制在 20% 和 10% 以内.

其次, Sarathi 可以通过提高解码吞吐量来弥补部分预填充效率的损失. 例如, 我们从 [13(c)](#figure-13) 可以看到, 尽管在预填充时速度比基线慢 $5\times$, 但块大小为 64 的性能几乎可以匹配基线, 而块大小为 128 的吞吐量则高出最多 $1.16\times$, 尽管其预填充比基线慢超过 $2\times$, 这主要是因为捎带了更多解码. 瓷砖量化效应在 [图 13](#figure-13) 中也很明显, 当块大小为 128 的倍数时, Sarathi 的吞吐量提升更高; 例如, 块大小为 256 的加速效果优于 320.

## 6 讨论

在本文中, 我们全面展示了 Sarathi 如何在多种模型和硬件配置下提升 LLM 推理的性能. 然而, 还有多个需要进一步研究的挑战.

首先, 我们仅关注在 Sarathi 中实现高效调度机制以提高 LLM 推理吞吐量. 然而, 现实世界的部署需要在多个维度上同时优化推理服务基础设施, 例如延迟, 排队延迟, 公平性等. 要在 Sarathi 中实现这些目标, 需要重新审视调度策略. 其次, 虽然我们展示了在给定 P: D 比例下的适当块大小, 但我们将如何选择最优块大小留待未来工作探索, 因为这取决于多个因素, 如硬件, 模型特性, 序列长度以及预填充- 解码 (prefill-decode) 标记的组成, 尤其是在 P: D 比例可能事先未知的场景中. 第三, 本文中我们做了一个简单假设, 即批次中的每个请求具有相同数量的预填充和解码标记 (模拟实验除外), 而在现实中, 不同的 LLM 推理请求的序列长度可能会有显著差异. 最后, 我们关注的序列长度最多为 3K, P: D 比例范围为 1-200. 我们认为这些代表了许多现实世界部署的情况. 然而, 近年来对支持非常长序列 (例如数万到数十万 [LLMs00]) 的兴趣也有所增加. 这些极大序列长度可能带来新的挑战, 因为注意力机制的成本随着标记数呈二次增长. 我们正在积极研究这些挑战.

## 7 相关工作

在本节中, 我们沿着两个维度对相关工作进行了简要总结: 系统优化和模型创新.

### 7.1 系统优化

内存管理: 在自回归解码中, 给定请求需要生成的令牌数是事先未知的. 因此, 传统系统会基于对最大令牌数的保守估计为 KV 缓存预先分配内存. 最近, vLLM 证明这种方法效率低下, 并提出了一个框架—受虚拟内存抽象启发—能够对 KV 缓存进行增量内存分配 [Easy00]. 这有助于提高批处理大小, 尤其是在不同请求之间令牌数量差异较大时. FlexGen [Highta23] 旨在提高资源受限场景下离线 LLM 推理的吞吐量, 例如, 在单个 GPU 上运行大型模型. 为实现这一目标, FlexGen 采用了内存卸载, 量化和调度的巧妙组合.

优化 (自我) 注意力: 在 [Selfat22] 中, 作者提出了一种算法, 将自注意力的内存需求从 $O(n^{2})$ 降低到 $O(1)$, 相对于序列长度而言. FlashAttention [Daod22] 提出了基于平铺的算法, 通过最小化在不同 GPU 内存层之间读取/写入的字节数量来加速注意力计算. 后续关于 FlashAttention 的工作 [Daoa23] 在并行性和工作分区 [Daoa23] 方面进一步改进了它. 在我们的实验中, 我们发现 xformers 内存高效注意力实现 [OPERAa00] 是最有效的.

内核级优化: FasterTransformer [Fastea00] 为变换器的编码器和解码器块提出了优化层. 这些基于低级 GPU 优化, 如内核融合. 我们预计这种低级优化同样会对 Sarathi 有益.

调度优化: Orca 提出了一种迭代级别的调度框架, 避免了由于早期为将不同序列长度的请求批处理在一起而使用的 token 填充而浪费计算 [July22]. 另外, Orca 通过在生成请求的序列结束 token 时立即返回响应来降低延迟. FastServe 提出了一种抢占式调度框架, 以最小化作业完成时间 [Fast23]. 一些其他调度框架包括 Triton [Servea00] 和 Clipper [NSDI17], 它们将服务层与模型的执行引擎分离. 我们当前的工作专注于优化执行层, 并可以与这些系统提出的不同调度策略一起使用.

之前几项工作的优化可以补充我们的优化, 例如, 更优化的注意力实现将使 Sarathi 扩展到更长的序列长度, 而动态内存分配将有助于支持更大的批处理大小, 依此类推.

### 7.2 模型创新

关于模型创新的大量研究工作试图解决基于 Transformer 的语言模型的不足, 或在模型架构上迈出下一步, 超越 Transformer. 例如, 多查询注意力在所有注意力头中共享相同的键和值, 以减少 KV 缓存的大小 [One19], 从而允许更大的批处理大小. 最近的一些研究也表明, 可以通过量化显著压缩模型大小 [Accurb23, Accura23, Effica23, Llm22]. 专家混合模型主要旨在减少每次迭代中被激活的模型参数数量 [Effica22, MoE23, Mitiga23]. 最近, 保留网络被提出作为 Transformer 的继任者 [Retena23]. 在本工作中, 我们重点从 GPU 的角度解决最流行的 Transformer 模型的性能问题. 模型创新与我们的工作是正交的.

## 8 结论

在本文中, 我们确定了大型语言模型 (LLM) 推理效率低下的两个主要原因: 1) 由于解码阶段缺乏并行性且受内存限制, 导致 GPU 利用率不佳; 2) 不同迭代中预填充 (prefill) 和解码时间不一致, 产生显著的流水线空隙, 导致微批次不平衡. 为了解决这些挑战, 我们提出了 Sarathi, 一种结合分块预填充 (chunked-prefills) 和解码最大化批处理 (decode-maximal batching) 的新方法. 解码最大化批处理通过将解码与预填充结合, 从而将内存受限的解码阶段转变为计算密集型, 提高了 GPU 利用率. 分块预填充有助于提供更多可供解码依附的预填充, 同时提供统一的工作单元, 这显著减少了流水线空隙. 我们证明, Sarathi 在不同模型和硬件配置下都显著提高了端到端吞吐量.
