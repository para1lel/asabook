## 摘要

大型深度学习模型能显著提高准确率, 但要训练数十亿乃至数万亿参数并不容易. 数据并行和模型并行等现有方案受设备内存限制, 难以容纳这些模型, 也难以同时兼顾计算, 通信和开发效率. 我们提出了一种新的内存优化方法, 即零冗余优化器 (*ZeRO*); 它大幅提升训练速度, 同时扩大可高效训练的模型规模. *ZeRO* 消除了数据并行和模型并行训练中的内存冗余, 同时保留较低的通信量和较大的计算粒度, 因而模型规模可以随设备数量增长而扩展, 效率也能维持在较高水平. 对内存需求和通信量的分析表明: 借助现有硬件, *ZeRO* 有望扩展到 1 *万亿* 以上参数.

我们实现并评估了 ZeRO: 它在 400 个 GPU 上训练超过 100B 参数的大模型时取得超线性加速, 吞吐量达到 15 Petaflops. 与 SOTA 相比, 可训练的模型规模提高了 8 倍, 可实现性能提高了 10 倍. 从易用性来看, *ZeRO* 无需模型并行即可训练多达 13B 参数的大模型 (例如, 规模超过 Megatron GPT 8.3B 和 T5 11B), 而模型并行对科学家而言更难使用. 最后, 研究人员利用 *ZeRO* 带来的系统突破, 训练出当时世界上最大的语言模型 (17B 参数), 并取得创纪录的准确率.

## 1 扩展引言

深度学习 (DL) 模型的规模不断增大, 模型越大, 准确率收益也越明显. 在自然语言处理 (NLP) 领域, Transformer 推动了 Bert-large (0.3B) [Dev18], GPT-2 (1.5B) [Rad19], Megatron-LM (8.3B) [Sho20] 和 T5 (11B) [Raf19] 等大模型的发展. 要让模型规模从数百亿参数继续增长到数万亿参数, 首先必须解决训练问题—这些模型显然装不进单个设备 (如 GPU 或 TPU) 的内存, 只增加设备数量也无法扩展训练.

基本数据并行 (DP) 不会降低单个设备的内存占用. 在当前一代配备 32 GB 内存的 GPU 上, 参数量超过 1.4B 的模型便会内存不足. 流水线并行 (PP), 模型并行 (MP) 和 CPU 卸载等现有方案, 都需要在功能, 易用性, 内存效率及计算/通信效率之间取舍, 而这些因素对高速、大规模训练都很重要.

在现有的大模型训练方案中, MP 或许最有希望. 当时文献中规模最大的两个模型, T5 11B [Raf19] 和 Megatron-LM 8.3B [Sho20], 都依靠模型并行训练, 分别由 Mesh-Tensorflow [Sha18a] 和 Megatron-LM [Sho20] 实现. 然而, MP 很难继续扩展到更大的模型. MP 纵向拆分模型, 把每一层的计算和参数分布到多个设备上, 因此层与层之间需要大量通信. 单个节点内的 GPU 间带宽较高, 这种方法尚能高效运行; 一旦超出单个节点, 效率便会迅速下降 [Sho20]. 我们用 Megatron-LM 在两个 DGX-2 节点上测试了一个 40B 参数模型, 每个 V100 GPU 的性能约为 $5\,\mathrm{Tflops}$ (不到硬件峰值的 5%).

那么, 怎样才能绕过现有方案的限制, 更高效地训练大模型? 为回答这个问题, 我们先分析现有训练系统的全部内存消耗, 并将其分成两部分: 1) 对大模型而言, 绝大部分内存由*模型状态*占用, 包括优化器状态 (例如 Adam 的动量和方差 [Kin15]), 梯度和参数. 2) 其余内存用于激活值, 临时缓冲区和因碎片化而无法使用的空间, 本文统称为*残余状态*. 我们提出 *ZeRO*—零冗余优化器—在保持较高计算和通信效率的前提下, 优化这两部分的内存效率. 两部分面对的问题不同, 因此我们分别设计并讨论相应方案.

**优化模型状态内存** 模型状态通常占据训练内存的大头, 但 DP 和 MP 等现有方法都没有给出令人满意的解决方案. DP 的计算和通信效率较高, 内存效率却很低; MP 的计算和通信效率则可能很低. 具体来说, DP 在所有数据并行进程中复制完整的模型状态, 造成重复占用; MP 通过划分这些状态提高内存效率, 却往往把计算切得过细, 并引入高昂的通信开销, 因而难以高效扩展. 这些方法还会在整个训练过程中静态保留全部模型状态, 即使某些状态只在特定时刻才会用到.

**图 1.** 比较不采用优化与采用三阶段 *ZeRO*-DP 优化时, 每个设备上模型状态的内存占用. $\Psi$ 表示模型规模 (参数数量), $K$ 表示优化器状态的内存乘数, $N_d$ 表示 DP 度. 示例假设模型规模为 $\Psi=7.5\mathrm{B}$, DP 度为 $N_d=64$, 并采用基于 Adam 优化器的混合精度训练, 此时 $K=12$.

据此, 我们设计了 *ZeRO*-DP, 即由 ZeRO 驱动的数据并行. 它兼具 DP 的计算/通信效率与 MP 的内存效率. *ZeRO*-DP 不再复制模型状态, 而是对其进行*分区*, 从而消除数据并行进程之间的状态冗余; 训练时采用动态通信调度, 保留 DP 的计算粒度和通信量, 因而不会牺牲计算/通信效率.

*ZeRO*-DP 包含三个主要优化阶段 (见 [图 1](#figure-01)), 分别划分优化器状态, 梯度和参数. 依次叠加这些阶段后:

1. 划分优化器状态 ($P_{\mathrm{os}}$): 内存占用降至原来的 $1/4$, 通信量与 DP 相同;
2. 再划分梯度 ($P_{\mathrm{os}+g}$): 内存占用降至原来的 $1/8$, 通信量与 DP 相同;
3. 再划分参数 ($P_{\mathrm{os}+g+p}$): 内存降幅与 DP 度 $N_d$ 成线性关系. 例如, 划分到 64 个 GPU 上 ($N_d=64$) 可将内存占用降至原来的 $1/64$, 通信量只增加约 50%.

ZeRO-DP 消除内存冗余后, 集群的全部聚合内存都可用于训练. 三个阶段全部启用时, ZeRO 仅用 1024 个 NVIDIA GPU 就能训练万亿参数模型. 采用 Adam [Kin15] 一类优化器进行 16 位精度训练时, 万亿参数模型约需 16 TB 内存存放优化器状态, 梯度和参数. $16\,\mathrm{TB}/1024=16\,\mathrm{GB}$, 仍在 GPU 的合理容量范围内 (例如设备内存为 32 GB 的 GPU).

**优化残余状态内存** *ZeRO*-DP 提高模型状态的内存效率后, 激活值, 临时缓冲区和无法使用的内存碎片可能成为新的瓶颈. 我们设计了 *ZeRO*-R, 分别优化这三类残余内存.

1. 对于为反向传播而保存的前向激活值, 激活检查点 [Che16] 虽有帮助, 对大模型却仍不够. *ZeRO*-R 识别并消除现有 MP 方法中的激活值副本, 通过激活值分区来压缩这部分内存; 必要时还会把激活值卸载到 CPU.
2. *ZeRO*-R 为临时缓冲区设定合适的大小, 在内存占用与计算效率之间取得平衡.
3. 训练时, 不同张量的生命周期不同, 因而会产生内存碎片. 即使空闲内存总量足够, 碎片化造成的连续空间不足仍可能使内存分配失败. *ZeRO*-R 根据张量的生命周期主动管理内存, 避免内存碎片化.

*ZeRO*-DP 与 *ZeRO*-R 共同构成一套用于深度学习训练的内存优化系统, 本文统称为 *ZeRO*.

<strong><em>ZeRO</em> 与 MP</strong>: *ZeRO* 消除了 DP 的内存低效后, 自然会出现几个问题: 我们是否还需要 MP, 何时需要, *ZeRO* 又如何与 MP 配合? 有了 *ZeRO*, 仅为容纳大模型而采用 MP 就不再那么必要. 在降低单设备内存占用方面, *ZeRO*-DP 至少与 MP 同样有效; 当 MP 无法均匀切分模型时, *ZeRO*-DP 甚至更好. 它的扩展效率也与 MP 相当或更高. 数据并行还很容易使用, 能应用于多种工作负载. 相比之下, 当前的 MP 方法往往要求模型开发者修改模型, 系统开发者实现分布式算子, Megatron-LM 等现有方案支持的算子和模型也很有限.

不过, 有些场景仍需要 MP: i) 与 *ZeRO*-R 配合时, MP 可以降低超大模型的激活内存占用. ii) 对于激活内存不成问题的较小模型, 如果只用 DP 会使聚合批量过大并影响收敛, MP 也有帮助. [+2] 此时可以结合 *ZeRO* 与 MP, 在可接受的聚合批量下容纳模型.

我们证明 *ZeRO* 可以与 MP 结合. 当 DP 度为 $N_d$, MP 度为 $N_m$ 时, 每个设备上的理论最大内存降幅为 $N_d\times N_m$ 倍. 这样一来, 1024 个 GPU 或许可以容纳万亿参数模型: 每个 DGX-2 节点内采用 16 路模型并行, 节点之间采用 64 路数据并行, 并以适中的批量高效运行!

**模型规模** 与 MP 结合后, *ZeRO*-100B 可以高效运行 170B 参数模型; 仅使用 Megatron 等现有系统时, 模型超过 40B 参数便无法高效扩展, 见 [图 2](#figure-02). 与 SOTA 相比, 模型规模提高了 8 倍以上.

**速度** 内存效率提高后, 吞吐量随之增加, 训练也更快. 如 [图 2](#figure-02) 所示, *ZeRO* 在 400 个 NVIDIA V100 GPU 组成的集群上运行 100B 参数模型时, 每个 GPU 的性能超过 38 TFlops, 聚合性能超过 15 Petaflops. 对同等规模的模型, 训练速度比 SOTA 高 10 倍以上.

**可扩展性** 在 64-400 个 GPU 的范围内, 我们观察到超线性加速: GPU 数量翻倍时, 性能提升超过一倍. 这是 *ZeRO*-DP 的特性. DP 度越高, 模型状态在每个 GPU 上占用的内存越少, 因而单个 GPU 能容纳更大的批量并取得更高性能. 我们预计 GPU 数量超过 400 后, 这一趋势仍会延续.

**降低大模型训练门槛** *ZeRO*-100B 让数据科学家无需使用要求重构模型的 MP 或 PP, 就能训练多达 13B 参数的模型, 超过当时文献中最大的 T5 11B 模型. 数据科学家因而可以直接试验大模型, 不必先处理并行化问题. 相比之下, PyTorch Distributed Data Parallel 等现有系统运行 1.4B 参数模型时就会内存不足.

**新的 SOTA 模型** *ZeRO* 支持了当时规模最大且准确率创下纪录的 17B 参数语言模型 Turing-NLG [Mic20].

我们将 *ZeRO* 作为开源深度学习训练优化库 DeepSpeed 的一部分发布 [+3]. 我们计划在 2020 年 5 月底前公开本文所述的全部实现, 并启用 *ZeRO*-DP 的第三阶段参数分区 ($P_{\mathrm{os}+g+p}$), 进一步支持万亿参数模型. 我们也计划向整个深度学习社区开放 *ZeRO*, 推动大规模模型训练继续发展并得到普及.

## 2 相关工作

### 2.1 数据, 模型和流水线并行

并行化是大规模训练大模型的主要手段. 如果模型能装进单个设备的内存, 通常用数据并行 (DP) 将训练扩展到多个设备. DP 会在每个设备上复制模型参数. 每一步训练时, 一个小批量会平均分给所有数据并行进程; 各进程在不同的数据子集上执行前向和反向传播, 再用跨进程平均后的梯度更新本地模型.

当模型装不进设备内存时, 模型并行 (MP) [Sha18a, Sho20] 和流水线并行 (PP) [Hua19, Har18] 会分别纵向和横向拆分模型, 再把各部分分配给不同进程. 第 [1](#section-01) 节已经讨论 *ZeRO* 与 DP, MP 的关系. 下面介绍 PP, 以及它与降低内存占用的关系.

PP 按层横向拆分模型, 在不同设备上运行各个分区, 并用微批处理隐藏流水线气泡 [Hua19, Har18]. 横向拆分会让权重绑定难以实现, 微批处理则会给批归一化带来困难. G-pipe [Hua19] 等常见 PP 实现会同时划分模型参数和全部激活值, 但为了隐藏流水线气泡, 批量大小必须随流水线分区数增加. 大批量可能减慢收敛, 也需要大量内存保存激活值. PipeDream [Nar19] 采用另一种 PP 实现: 它保留多个陈旧参数副本, 以便在不显著增大批量的情况下隐藏流水线气泡, 代价是内存效率下降. 这种训练方式也不等同于标准深度学习训练, 可能影响收敛. 相比之下, *ZeRO* 能达到与 PP 相同或更高的内存效率, 又没有 PP 在功能, 性能和收敛方面的限制.

### 2.2 不依赖并行的内存优化方法

除 MP 和 PP 外, 还有多项研究专门降低深度学习训练的内存开销.

#### 2.2.1 减少激活内存

已有工作通过压缩 [Jai18], 激活检查点 [Che16, Jai19] 或在线分析 [Wan18a] 来降低激活内存. 这些方法彼此互补, 也能与 *ZeRO* 配合. *ZeRO*-R 的激活内存优化就可以和激活检查点同时使用.

#### 2.2.2 CPU 卸载

[Pud20, Rhu16] 利用现代计算节点的异构结构, 分别通过算法设计和虚拟内存把模型状态卸载到 CPU 内存. GPU-CPU-GPU 传输最多可能占去 $50\%$ 的训练时间 [Pud20]. *ZeRO* 则不把模型状态存到受 PCIe 带宽严重限制的 CPU 内存中, 仍能显著降低内存占用. 只有少数情况下, *ZeRO*-R 才会把超大模型的激活检查点卸载到 CPU 以提高性能 (详见第 [6.1](#section-06-01) 节).

#### 2.2.3 内存高效优化器

[Sha18, Ani19] 通过维护更粗粒度的模型参数与梯度统计量, 降低自适应优化方法的内存占用, 但可能影响模型的收敛保证. *ZeRO* 与这些工作相互独立: 它不改变优化方法, 也不影响模型收敛, 只减少每个设备上优化器状态和梯度的内存占用.

### 2.3 训练优化器

自适应优化方法 [Duc11, Kin15, You17, You19] 对大模型取得 SOTA 性能和准确率很重要. 与 SGD 相比, 它们会为每个模型参数和梯度维护细粒度的一阶、二阶统计量, 因而占用大量内存. *ZeRO* 可将这类优化器的内存占用降低几个数量级, 使设备内存有限的硬件也能用这些复杂方法训练大模型. 这还为开发和使用更复杂, 内存开销更大, 但可能收敛得更好的优化器提供了空间.

## 3 内存都去哪儿了?

先退一步, 看看当前训练系统怎样使用内存. 以 1.5B 参数的 GPT-2 为例, 16 位权重 (或参数) 只需 3 GB, 但 TensorFlow 和 PyTorch 都无法在单个 32 GB GPU 上训练它. 多出来的内存究竟去了哪里? 训练时, 大部分内存用于模型状态, 即优化器状态, 梯度和参数这几类张量. 其余内存用于激活值, 临时缓冲区和碎片化空间, 本文称为*残余状态*. 下面分别分析这两部分内存消耗.

### 3.1 模型状态: 优化器状态, 梯度和参数

训练过程中, 模型状态占据了大部分设备内存. 以深度学习训练中常用的 Adam [Kin15] 为例, 它需要保存两类优化器状态: i) 时间平均动量; ii) 用于计算更新的梯度方差. 因此, 使用 ADAM 训练时, 内存必须同时容纳动量和梯度方差的副本, 还要保存梯度与权重本身. 在这三类与参数相关的张量中, 优化器状态通常占用最多, 混合精度训练时尤其如此.

**混合精度训练** 在当前一代 NVIDIA GPU 上, 训练大模型的 SOTA 方法是混合精度 (fp16/32) 训练 [Mic17]. 参数和激活值以 fp16 保存, 从而利用 GPU 上高吞吐量的 Tensor Core [Nvi17a]. 前向和反向传播都使用 fp16 权重与激活值. 但为了在反向传播结束后准确计算并应用更新, 混合精度优化器还会保留一份 fp32 参数副本, 以及其他所有优化器状态的 fp32 副本.

仍以 Adam 为例. 用 Adam 对含 $\Psi$ 个参数的模型做混合精度训练时, 参数和梯度各需一份 $\mathrm{fp}16$ 副本, 分别占 $2\Psi$ 字节. 优化器状态还包括参数, 动量和方差的 $\mathrm{fp}32$ 副本, 三者分别占 $4\Psi$ 字节. 记优化器状态的内存乘数为 $K$, 即额外需要 $K\Psi$ 字节; 混合精度 Adam 的 $K=12$. 总内存需求因此为 $2\Psi+2\Psi+K\Psi=16\Psi$ 字节. 对 1.5B 参数的 GPT-2 而言, 至少需要 $24\,\mathrm{GB}$, 远高于单独保存 $\mathrm{fp}16$ 参数所需的 $3\,\mathrm{GB}$.

### 3.2 剩余内存消耗

**激活值** 在训练中可能占用大量内存 [Che16]. 例如, 用 1K 序列长度和 32 的批量大小训练 1.5B 参数 GPT-2, 约需 60 GB 内存 [+4]. 激活检查点 (或激活重计算) 是常用方法, 可将激活内存大致降到总激活量的平方根, 代价是增加 $33\%$ 的重计算 [Che16]. 对这个模型, 激活内存可由此降到约 8 GB.

尽管降幅明显, 模型继续增大后, 即使采用激活检查点, 激活内存仍可能很高. 例如, 100B 参数的 GPT 类模型在批量大小为 32 时, 即使用了激活检查点, 仍需约 60 GB 内存.

**临时缓冲区** 用于保存中间结果, 在大模型中也会占用不少内存. 梯度 all-reduce, 梯度范数计算等操作通常先把所有梯度合并成一个扁平缓冲区, 再执行运算, 以提高吞吐量. 例如, all-reduce 的跨设备带宽会随消息增大而提高. 梯度本身通常是 fp16 张量, 但融合缓冲区可能因操作而采用 fp32. 模型很大时, 这部分开销不可忽略. 对 1.5B 参数模型, 一个扁平 fp32 缓冲区就需要 $6\,\mathrm{GB}$.

**内存碎片:** 前面讨论的是训练真正消耗的内存. 但即使剩余内存很多, 可用内存仍可能耗尽, 原因就是碎片化. 如果找不到足够大的连续空间, 即使空闲内存总量超过请求大小, 分配也会失败. 训练超大模型时, 我们观察到明显的内存碎片; 在极端情况下, 尚有超过 30% 内存空闲就已经出现 OOM.

## 4 *ZeRO*: 思路与概览

*ZeRO* 包含两组优化: i) *ZeRO*-DP 用于降低模型状态的内存占用; ii) *ZeRO*-R 用于降低残余内存. 本节概述这些优化及其依据, 说明 *ZeRO* 怎样在保持效率的同时压缩内存. 效率是必要约束: 如果不考虑效率, 把全部参数状态移到 CPU 内存, 或任意提高 MP 度, 都能轻易降低设备内存占用.

### 4.1 思路与概览: *ZeRO*-DP

由 *ZeRO* 驱动的 DP 基于三点观察:

1. DP 的扩展效率高于 MP, 因为 MP 会减小计算粒度并增加通信开销. 超过某个临界点后, 计算粒度过小会降低单 GPU 效率, 更高的通信开销则会阻碍跨 GPU 扩展, 跨节点时尤为明显. DP 的计算粒度更大, 通信量更低, 因而效率高得多.
2. DP 的内存效率很低, 因为所有数据并行进程都重复保存模型状态. MP 则通过划分模型状态提高内存效率.
3. DP 和 MP 都在整个训练期间保留全部模型状态, 但这些状态并非始终需要. 例如, 某一层的参数只在该层执行前向和反向传播时才会用到.

据此, *ZeRO*-DP 保留 DP 的训练效率, 同时取得 MP 的内存效率. 它不复制模型状态, 而是对其进行*分区* (第 [5](#section-05) 节), 并利用模型状态随时间变化的需求设计动态通信调度, 尽量压低通信量 (第 [7](#section-07) 节). 因此, 单设备内存占用会随 DP 度增加而*线性*下降, 通信量仍接近默认 DP, 效率得以保留.

<span id="section-04-02"></span>

### 4.2 思路与概览: *ZeRO*-R

#### 4.2.1 减少激活内存

这里有两点观察:

1. MP 会划分模型状态, 却常常需要复制激活内存. 例如, 如果纵向拆分线性层参数并在两个 GPU 上并行计算, 每个 GPU 都需要完整的激活值才能计算自己的分区
2. 对 GPT-2 及更大的模型, 算术强度 (每次迭代的计算量与激活检查点数据量之比) 很高 ($\geq 10K$), 并且随隐藏维度线性增长. 因此, 即使带宽不高, 也能掩盖激活检查点的数据搬移开销.

*ZeRO* 在 GPU 之间对激活检查点进行*分区*, 消除 MP 中的重复副本, 并在需要时通过 all-gather 重建完整数据. 激活内存会按 MP 度成比例下降. 对超大模型, *ZeRO* 还可以把激活分区移到 CPU 内存; 由于这类模型的算术强度很高, 效率仍可维持在较好水平.

#### 4.2.2 管理临时缓冲区

*ZeRO*-R 使用固定大小的缓冲区, 避免临时缓冲区随模型规模一起膨胀, 同时把缓冲区保持在足以高效计算的大小.

#### 4.2.3 管理碎片化内存

内存碎片来自短生命周期与长生命周期对象的交错. 前向传播时, 激活检查点长期保留, 重计算产生的激活值却很快释放. 反向计算时也类似: 激活梯度生命周期短, 参数梯度生命周期长. 因此, *ZeRO* 把激活检查点和梯度移入预先分配的连续缓冲区, 在运行过程中完成内存整理. 这样既增加可用内存, 也减少分配器寻找连续空闲空间的时间.

## 5 深入分析 *ZeRO*-DP

传统 DP 在每个设备上复制模型状态, 带来很高的内存开销. *ZeRO*-DP 把优化器状态, 梯度和参数分散到各个数据并行进程, 从而消除这些副本. [图 1](#figure-01) 对有无 *ZeRO*-DP 时的内存需求作了量化比较, 并展示依次划分 (1) 优化器状态, (2) 梯度和 (3) 参数后的累计内存占用. 这三个优化阶段分别记为 $P_{\mathrm{os}}$, $P_g$ 和 $P_p$, 下文逐一说明.

### 5.1 $P_{\mathrm{os}}$: 优化器状态分区

当 DP 度为 $N_d$ 时, 我们把优化器状态均分为 $N_d$ 份, 第 $i$ 个数据并行进程只更新第 $i$ 份对应的优化器状态. 因此, 每个进程只需保存并更新全部优化器状态的 $\frac{1}{N_d}$, 随后也只更新 $\frac{1}{N_d}$ 的参数. 每个训练步骤结束时, 所有数据并行进程执行一次 all-gather, 得到完整的已更新参数.

**内存节省:** 如 [图 1](#figure-01) 所示, 优化器状态分区后, 内存占用从 $4\Psi+K\Psi$ 降为 $4\Psi+\frac{K\Psi}{N_d}$. 图中的具体示例表明, 7.5B 参数模型采用 64 路 DP ($N_d=64$) 和 $P_{\mathrm{os}}$ 时需 31.4 GB, 标准 DP 则需 120 GB. 当 $N_d$ 很大时, 模型状态内存从 $4\Psi+12\Psi=16\Psi$ 字节降为 $4\Psi+\frac{12\Psi}{N_d}\approx 4\Psi$ 字节, 即缩小 4 倍.

### 5.2 $P_g$: 梯度分区

每个数据并行进程只更新自己的参数分区, 因而只需要这些参数归约后的梯度. 在反向传播中, 某一层的梯度一旦产生, 就只归约到负责更新对应参数的进程. 归约完成后, 梯度不再需要, 占用的内存可以立即释放. 保存梯度所需的内存由 $2\Psi$ 字节降到 $\frac{2\Psi}{N_d}$.

这实际上是一次 reduce-scatter: 不同参数对应的梯度被归约到不同进程. 为提高实际效率, 我们采用分桶策略, 把同一分区对应的梯度装入一个桶, 再一次归约整个桶. NVIDIA AMP [Nvi19] 优化器也会对 all-reduce 梯度计算分桶, 以重叠通信和计算, 思路与此相近. 不同之处在于, 我们在分区边界执行 reduce 而非 all-reduce, 既压缩内存, 又重叠计算和通信.

**内存节省:** 去掉梯度和优化器状态的冗余后, 内存占用进一步降至 $2\Psi+\frac{14\Psi}{N_d}\approx 2\Psi$. 在 [图 1](#figure-01) 的示例中, 7.5B 参数模型采用 64 路 DP ($N_d=64$) 和 $P_{\mathrm{os}+g}$ 时只需 16.6 GB, 标准 DP 则需 120 GB. 当 $N_d$ 很大时, 模型状态内存从 $2\Psi+14\Psi=16\Psi$ 字节降为 $2\Psi+\frac{14\Psi}{N_d}\approx 2\Psi$ 字节, 即缩小 8 倍.

### 5.3 $P_p$: 参数分区

与优化器状态和梯度一样, 每个进程只保存自己分区对应的参数. 前向或反向传播需要其他分区的参数时, 再由相应的数据并行进程广播过来. 这种做法看似会产生大量通信, 但我们证明, 它只把基线 DP 的总通信量提高到 1.5 倍, 内存占用却能随 $N_d$ 成比例下降.

**内存节省:** 参数分区把含 $\Psi$ 个参数的模型从 $16\Psi$ 字节降到 $\frac{16\Psi}{N_d}$. 在 [图 1](#figure-01) 的示例中, 7.5B 参数模型采用 64 路 DP ($N_d=64$) 和 $P_{\mathrm{os}+p+g}$ 时, 模型状态只占 1.9 GB, 标准 DP 则需 120 GB. 由此得到一个重要结论: *只要有足够多的设备共同保存模型状态, ZeRO 就能让 DP 容纳任意规模的模型*.

### 5.4 模型规模的影响

三个分区阶段 $P_{\mathrm{os}}$, $P_{\mathrm{os}+g}$ 和 $P_{\mathrm{os}+g+p}$, 最多可将每个数据并行进程的模型状态内存分别缩小 4 倍, 8 倍和 $N_d$ 倍. [表 1](#table-01) 给出几个示例模型在不同 DP 度和三个 *ZeRO*-DP 阶段下的模型状态内存. 不使用 *ZeRO* 时, 无论 DP 度是多少, 内存占用都等于表中第一行. 当 $N_d=64$ 时, *ZeRO* 分别采用 $P_{\mathrm{os}}$, $P_{\mathrm{os}+g}$ 和 $P_{\mathrm{os}+g+p}$, 可训练最大 7.5B, 14B 和 128B 参数的模型. 当 $N_d=1024$ 时, 全部优化 ($P_{\mathrm{os}+g+p}$) 可以支持 1 万亿参数, 甚至任意规模的模型! 没有 *ZeRO* 时, 仅靠 DP 能运行的最大模型不到 1.5B 参数.

## 6 深入分析 *ZeRO*-R

<span id="section-06-01"></span>

### 6.1 $P_{a}$: 分区激活检查点

如第 [4.2](#section-04-02) 节所述, MP 的设计要求复制激活值, 因而模型并行 GPU 上会保存冗余副本. *ZeRO* 对激活值进行分区, 并且只在某层激活值即将参与计算时, 临时恢复这一层的完整副本. 具体来说, 某层完成前向传播后, 输入激活值会分散到所有模型并行进程, 一直保存到反向传播再次需要它时. 此时 *ZeRO* 执行 all-gather, 重新物化一份完整激活值. 该优化记为 $P_a$. 它与激活检查点 [Che16] 配合使用, 只保存分区后的检查点, 不再保存重复副本. 如果模型极大而设备内存很少, 还可以把这些分区检查点卸载到 CPU, 以额外通信为代价, 将激活内存开销降到接近零; 第 [7](#section-07) 节会讨论这一代价. 该形式记为 $P_{a+\mathrm{cpu}}$.

**内存节省** 分区激活检查点使 *ZeRO* 的激活内存按 MP 度成比例下降. 以 [表 4](#table-04) 的 100B 模型为例, 批量大小为 32, 序列长度为 1024, MP 度为 16. 如果每个 Transformer 层保存一个激活检查点, 单个 GPU 仅保存这些检查点就需约 33 GB. 使用 *ZeRO* 的 $P_a$ 后, 可降到约 2 GB; 再把这 2 GB 卸载到 CPU, 激活内存便接近于零.

### 6.2 $C_B$: 固定大小缓冲区

*ZeRO* 谨慎选择临时数据缓冲区的大小, 以平衡内存占用和计算效率. 有些操作的效率很依赖输入大小, 输入越大, 效率越高. 例如, 大规模 all-reduce 的带宽远高于小规模操作. NVIDIA Apex 和 Megatron 等高性能库因此会先把全部参数融合到一个缓冲区, 再执行这些操作. 但融合缓冲区的内存开销与模型规模成正比, 最终会成为限制. 例如, 3B 参数模型的 32 位融合缓冲区需要 12 GB. 模型过大时, 我们改用大小固定且仍能保持性能的融合缓冲区. 这样, 缓冲区不再随模型增长, 同时又足够大, 不会明显损失效率.

### 6.3 $M_D$: 内存碎片整理

训练中的内存碎片来自激活检查点和梯度计算. 带激活检查点的前向传播只保留选定激活值, 其余激活值会被丢弃, 因为反向传播时可以重新计算. 这样, 短生命周期内存 (被丢弃的激活值) 与长生命周期内存 (检查点激活值) 便交错在一起. 反向传播也一样: 参数梯度长期保留, 激活梯度和计算参数梯度所需的其他缓冲区很快释放. 两类对象交错, 再次产生碎片.

空闲内存充足时, 少量碎片通常无关紧要. 但大模型训练往往紧贴内存上限, 碎片会造成两个问题: i) 空闲总量足够, 却因连续空间不足而 OOM; ii) 分配器花费大量时间搜索满足请求的连续空间, 导致效率下降.

*ZeRO* 预先为激活检查点和梯度分配连续内存块, 数据产生后立即复制进去, 从而在运行过程中整理碎片. $M_D$ 让 *ZeRO* 能以更大的批量训练更大的模型, 也能在内存紧张时提高效率.

## 7 *ZeRO*-DP 的通信分析

*ZeRO* 通过消除内存冗余扩大可训练的模型规模, 随之而来的问题是: 内存效率是否以更高的通信量为代价? 换句话说, 由 *ZeRO* 驱动的 DP 与基线 DP 相比需要多少通信? 答案分两部分: i) 使用 $P_{\mathrm{os}}$ 和 $P_g$ 时, *ZeRO*-DP 不增加通信量, 内存最多缩小 8 倍; ii) 在此基础上再使用 $P_p$ 时, 通信量最多增至 1.5 倍, 内存占用则进一步缩小 $N_d$ 倍. 本节给出具体分析, 先简要回顾标准 DP 的通信量.

### 7.1 数据并行通信量

数据并行训练在反向传播结束后, 先平均所有数据并行进程的梯度, 再计算下一步更新. 梯度平均通过 all-reduce 集合通信完成. 模型足够大时, all-reduce 完全受通信带宽限制, 因此本文只分析每个数据并行进程发送和接收的数据总量.

SOTA all-reduce 实现分两步. 第一步是 reduce-scatter, 不同进程分别归约数据的不同部分; 第二步是 all-gather, 每个进程收集所有进程上的归约结果. 两步合起来就是 all-reduce. reduce-scatter 和 all-gather 都采用流水线实现. 对含 $\Psi$ 个元素的数据, 每一步各移动 $\Psi$ 个元素, 因此标准 DP 每个训练步骤总共移动 $2\Psi$ 个元素.

### 7.2 *ZeRO*-DP 通信量

#### 7.2.1 使用 $P_{\mathrm{os}+g}$ 的通信量

梯度分区后, 每个进程只保存更新自身参数分区所需的梯度. 因此, *ZeRO* 不再对梯度执行 all-reduce, 只需一次 reduce-scatter, 通信量为 $\Psi$. 各进程更新自己负责的参数分区后, 再执行 all-gather, 收集所有进程更新后的参数, 通信量同样为 $\Psi$. 每个训练步骤的总通信量是 $\Psi+\Psi=2\Psi$, 与基线 DP 完全相同.

#### 7.2.2 使用 $P_{\mathrm{os}+g+p}$ 的通信量

参数分区后, 每个数据并行进程只保存自己更新的参数. 前向传播时, 它需要接收其他所有分区的参数, 但可以用流水线方式避免额外的内存占用. 在计算某个分区对应的前向传播前, 负责该分区的进程先把权重广播给所有数据并行进程; 该分区计算完成后, 参数即可丢弃. 总通信量为 $\frac{\Psi\times N_d}{N_d}=\Psi$. 换句话说, 参数 all-gather 被重新调度并摊到整个前向传播过程中, 每部分参数用完即释放. 反向传播时还要按相反顺序再执行一次同样的 all-gather.

因此, 总通信量等于两次参数 all-gather 加一次梯度 reduce-scatter, 即 $3\Psi$, 是基线的 1.5 倍. 梯度分区和参数分区都利用了同一点: 梯度和参数状态并非始终需要. 只在需要时通信这些状态, 就能减少内存占用.

## 8 *ZeRO*-R 的通信分析

我们把 *ZeRO*-R 的分区激活检查点 ($P_a$) 与基线 MP 的通信量作比较, 结果表明, $P_a$ 增加的通信通常不到基线 MP 的十分之一. 随后, 我们结合 DP 通信量分析 $P_a$ 的额外开销, 判断它何时能通过增大批量, 减少 DP 通信来提高效率. 系统据此决定是否以及何时启用 $P_a$ 和 $P_{a+\mathrm{cpu}}$.

激活检查点分区的通信权衡取决于模型规模, 检查点策略和 MP 策略. 为给出具体结论, 下面分析由 SOTA MP 方法 Megatron-LM 实现的 Transformer 模型.

Megatron-LM 使用激活检查点时, 每个 Transformer 块在前向传播中执行两次大小为 $\mathit{batch}\times\mathit{seq\_length}\times\mathit{hidden\_dim}$ 的 all-reduce, 前向重计算再执行两次, 反向传播又执行两次. 一次 all-reduce 的通信量为 $2\times\mathit{message\_size}$, 因此每个块的总通信量是 $12\times\mathit{seq\_length}\times\mathit{hidden\_dim}$.

*ZeRO*-R 对激活检查点分区后, 每个检查点在反向传播的前向重计算之前, 需要额外执行一次 all-gather. 通常每个 Transformer 块保存一份输入激活检查点, 因而每块需要一次 all-gather. all-gather 的通信量等于 $\mathit{message\_size}$, 所以 $P_a$ 的额外通信量是 $\mathit{seq\_length}*\mathit{hidden\_dim}$. 这不到原始模型并行通信量的 $10\%$.

MP 与 DP 结合时, $P_a$ 只让模型并行通信量增加 $10\%$, 却可能把数据并行通信量降低一个数量级. 当数据并行通信是性能瓶颈时, 效率会明显提高. $P_a$ 按 MP 度缩小激活内存, 因而批量大小也能按同一比例增加. 对大模型, MP 度可达 16 (一个 DGX-2 节点的 GPU 数量), 批量最多可增大 16 倍. 数据并行通信量与批量大小成反比, 所以 $P_a$ 让批量增大一个数量级时, 数据并行通信量也可能下降一个数量级.

如果启用 $P_{a+\mathrm{cpu}}$, 分区后的激活检查点会卸载到 CPU, 激活内存几乎降为零, 但 CPU 与 GPU 之间的数据搬移量会增至 $P_a$ 的 2 倍. 在极端情况下, 即使使用 $P_a$, 小批量仍会使 DP 通信成为主要瓶颈. 只要 CPU 数据传输开销低于 DP 通信开销, $P_{a+\mathrm{cpu}}$ 就能通过增大批量提高效率; 对小批量而言, 这一条件通常成立.

系统根据模型和硬件特性, 利用上述分析决定是否以及何时启用 $P_a$ 和 $P_{a+\mathrm{cpu}}$.

## 9 迈向 1 万亿参数

当时已发布的最大模型约有 10B 参数, 训练起来已经很困难. 模型规模终将走向 1 万亿参数, 比现有规模大 3 个数量级, 但途中必然会遇到障碍, 意外和新的技术. 我们并不声称已经了解或解决所有问题. *ZeRO* 处理的是其中最基础的系统问题之一: 怎样让当前硬件容纳这种规模的模型, 同时保持良好的系统扩展性.

**相较 SOTA 的跃升** 当时的 SOTA 框架 Megatron 在 DGX-2 系统上能以可接受吞吐量训练的最大模型为 16-20B 参数. 如果把模型并行扩展到多个 DGX 节点, 有限的节点间带宽会使效率显著下降.

*ZeRO* 大幅提高可高效运行的模型规模. 当前一代硬件无需让细粒度模型并行跨越节点边界, 就能运行更大的模型. 如 [表 1](#table-01) 所示, 启用全部优化 ($P_{\mathrm{os}+g+p}$) 后, *ZeRO* 仅用 DP 就能在 1024 个 GPU 上容纳超过 1 *万亿* 参数. 另一种做法是结合模型并行, 见 [表 2](#table-02): 1024 个 GPU 中, 每个 DGX-2 节点内采用 16 路模型并行, 节点间采用 64 路数据并行, 同样可以容纳超过 1 *万亿* 参数. 高效运行万亿参数模型已经不再遥不可及!

**算力缺口** 要在可接受的时间内端到端训练万亿参数模型, 仍需要巨大的算力, 而当时的 AI 集群并不具备这种能力.

为了估算资源需求, 我们把它与 Bert-Large 作简单比较. Bert-Large 可以在 1024 个 GPU 组成的 DGX-2H 集群上用 $67$ 分钟完成训练 [Nar19a]. 对单个样本, 1 万亿参数模型的计算量很容易达到 Bert-Large 的 $3000$ 倍 (1 万亿 / 3.3 亿). 即使序列长度和训练样本总数都不变, 并假设硬件与计算效率相同, 训练 1T 模型也要 140 天. 实际上, 模型变大后, 数据量和序列长度可能都会增加, 训练时间会超过一年. 要在合理时间内训练 1T 参数模型, 需要 exa-flop 级系统. 当这种算力出现时, 我们希望 *ZeRO* 能提供高效运行 1T 模型所需的系统技术.

## 10 实现与评估

我们的实现聚焦于高效训练约 $\sim 100\mathrm{B}$ 参数的模型. 这比当时已发布的最大模型大一个数量级 (例如 T5-11B [Raf19]), 又能在现有硬件上 (例如 1000 个 V100 GPU) 于合理时间内训练. 为此, 我们实现并评估了 *ZeRO* 的一部分优化: *ZeRO*-DP 的 $P_{\mathrm{os}+g}$ 加上 ZeRO-R. 这一实现称为 *ZeRO*-100B. 结果表明, *ZeRO*-100B 能高效训练多达 170B 参数的模型, 规模是 SOTA 的 8 倍, 速度最高提高 10 倍, 易用性也更好. *ZeRO*-100B 支持了当时全球最大的已发布模型 Turing-NLG, 并取得新的 SOTA 准确率.

### 10.1 实现与方法论

**实现** 我们在 PyTorch 中实现了 *ZeRO*-100B, 包含 $P_{\mathrm{os}+g}$ 和 *ZeRO*-R 的全部优化. 接口兼容所有实现为 `torch.nn.Module` 的模型. 用户只需用该接口包装模型, 就能像使用传统 DP 一样使用由 *ZeRO* 驱动的 DP, 无需修改模型本身. 这种 DP 还能与包括 Megatron-LM 在内的任意 MP 形式结合.

**硬件** 实验集群包含 400 个 V100 GPU ($25$ 个 DGX-2 节点), 节点间通信带宽为 800 Gbps.

**基线** 不使用 MP 的实验以 PyTorch Distributed Data Parallel (DDP) 为基线. 使用 MP 的实验以 Megatron-LM 为基线, 因为据我们所知, 它是当时的 SOTA. 我们采用 NVIDIA 在 2019 年 9 月发布的开源 Megatron-LM 版本 [+5]. 当时最新结果显示, Megatron-LM 可在 32 个 DGX-2 节点 (共 512 个 32 GB V100 GPU) 上扩展到 16B 参数模型 [Sho20].

***ZeRO*** 不使用 MP 的实验采用 *ZeRO*-100B 中由 *ZeRO* 驱动的 DP 实现. 使用 MP 的实验则把这种 DP 与 Megatron-LM 的 MP 结合.

**模型配置** 本节使用与 GPT-2 [Rad19] 类似的 Transformer 模型. 通过改变隐藏维度和层数, 得到不同参数规模. [表 4](#table-04) 列出实验配置, AE 附录提供更多细节.

### 10.2 速度与模型规模

*ZeRO*-100B 能在 400 个 GPU 上高效运行多达 170B 参数的模型, 比 Megatron-LM 大 8 倍以上. [图 2](#figure-02) 比较了不同模型规模下, *ZeRO*-100B 结合 MP 与单独使用 Megatron MP 的单 GPU 吞吐量. 对 8B-100B 参数模型, *ZeRO*-100B 的平均持续性能达到 15 PetaFlops (超过峰值的 30%). 基线 MP 则会随模型增大而迅速变慢: MP 的 GPU 间通信量很高; 模型大到必须跨节点后, 单链路带宽从 300 GB/s (NVSwitch) 降到 12.5 GB/s (InfiniBand EDR), 性能随之明显下降. *ZeRO*-100B 相对基线最高加速 10 倍, 大模型上的优势尤其明显.

*ZeRO*-100B 超过 100B 参数后性能略有下降, 原因是内存不足以容纳更大的批量. 下一节将说明它的超线性加速特性; 随 GPU 数量增加, 性能应会继续改善.

### 10.3 超线性可扩展性

*ZeRO*-100B 在超大模型上呈现超线性扩展. [图 3](#figure-03) 给出 60B 参数模型从 64 个 GPU 扩展到 400 个 GPU 的结果, 我们预计 GPU 继续增加时仍会保持这一趋势. DP 度提高后, $P_{\mathrm{os}+g}$ 会降低 *ZeRO*-100B 的单 GPU 内存占用, 使每个 GPU 能容纳更大的批量 [+6], 再借助更高的算术强度提升吞吐量.

### 10.4 普及大规模模型训练

对许多数据科学家而言, MP 和 PP 很难使用, 这是训练大模型的常见障碍. *ZeRO* 不要求修改模型, 用法与基线 DP 一样简单, 却能显著扩大模型规模并提高速度. [图 4](#figure-04) 表明, *ZeRO*-100B 不使用 MP 也能在 128 个 GPU 上训练多达 13B 参数的模型, 单 GPU 平均吞吐量超过 40 TFlops. 没有 *ZeRO* 时, 仅靠 DP 最多只能训练 1.4B 参数模型, 单 GPU 吞吐量不足 20 TFlops. 由于没有 MP 的通信开销, 这些模型也可以在配置较低的计算节点上训练, 不需要 NVLINK 或 NVSwitch 等高速节点内互连; MP 要取得良好效率则离不开它们.

### 10.6 Turing-NLG, 拥有 17B 参数的 SOTA 语言模型

截至 2020 年 5 月 12 日, Turing-NLG 以超过 17B 参数成为全球最大模型. 它在 Webtext-103 上取得 10.21 的困惑度, 刷新语言模型 SOTA. Turing-NLG 使用 *ZeRO*-100B 端到端训练; [图 5](#figure-05) 对比了它与此前 SOTA, 8.3B 参数 Megatron-LM, 在 300K 次迭代中的验证困惑度. *ZeRO*-100B 训练该模型时的持续吞吐量为 41.4 TFlops/GPU.

## 11 结语

从 HPC 和系统角度看, 我们认为 *ZeRO* 给大模型训练带来了根本变化. 当前实现 *ZeRO*-100B 已把模型规模提高 8 倍, 吞吐量提高 10 倍以上, 在现代 GPU 集群上取得超线性加速, 并训练出全球最大模型, 但这些仍只是 *ZeRO* 能力的一小部分. 完整的 *ZeRO* 有望把模型规模再提高一个数量级, 支持未来的万亿参数模型训练.

我们最看好的一点是, *ZeRO* 不会给数据科学家增加门槛. 与 MP 和 PP 不同, 它不需要重构模型, 用法与标准 DP 一样简单, 很适合继续研究大模型训练. 我们计划通过开源和社区反馈, 让整个深度学习社区都能使用 *ZeRO*, 推动大规模模型训练的发展和普及.
