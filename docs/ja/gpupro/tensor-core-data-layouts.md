::: info 概要
- アンペレの `mma.sync` は warp 内の各スレッドのレジスタから A、B、C を読み込み、結果 D もレジスタに保存されます。
- ホッパーの `wgmma.mma_async` は、共有メモリからマトリックスディスクリプタを介して直接入力を読み取ることができ、accumulator は各スレッドのレジスタによって保持されます。
- ブラックウェルの `tcgen05.mma` は accumulator を TMEM に移動させます。 ブロックスケール MMA で使用されるスケールファクターも TMEM に保存されています。
:::

数学的には、tensor コアの三世代が行うことは変わっていません。すべては行列の乗算と加算です。

$$
D = AB + C
$$

ここで、A と B は 2 つの乗算行列、C は入力の累積項、D は出力の結果です。 この式はこれらの行列がどこに保存されているか、また tensor コアがどの順に読み取るかも示していません。

まさにこの章で取り上げる問題です。 tensor コア命令は、固定されたハードウェアルールに従ってレジスタ、共有メモリアドレス、または TMEM 座標を解釈します。 要素が間違った位置に配置されると、命令はそれを別の行列要素として計算に参加させ、誤った結果となります。

次に、Ampere、Hopper、Blackwell の 3 世代のアーキテクチャにおけるデータ経路をたどり、それぞれ同一の 3 つの質問を検証します: MMA はどこから入力を読み取るのか? 累積結果はどこに保存されているのでしょうか? kernel は指令で求められる layout をどのように記述しているのでしょうか? 特定の写像を説明する際には、「[データ layout とその表記法](/ja/gpupro/data-layout/)」章で紹介された表記法を引き続き使用します。

## まず、2 つの重要なストレージ要件を忘れないでください

具体的な指示を見る前に、まず layout デザインが満たすべき追加の 2 つの要件を確認しましょう。 グローバルメモリからデータを転送する際、warp によってアクセスされたアドレスは、できるだけ少数の連続したアラインメントされたメモリトランザクションに統合されるべきです。 共有メモリにアクセスする際は、バンクの競合を避けるためにアドレスを異なる銀行間で分散させるべきです。

Tensor Core の layout 要件と組み合わせると、kernel の layout には実際には 3 つのチェックが必要です: グローバルメモリアクセスがマージされているか、共有メモリアクセスがバンク競合を引き起こすか、そして各要素が MMA 指令で指定された場所に位置しているかのです。 最初の 2 つの項目は先に紹介しました。3 つ目の項目については以下で詳しく説明します。

## アンペア: レジスタ内の operand と accumulator

まずはアンペレを見てみましょう。 一般的に `mma.sync.aligned.m16n8k*` 級数命令を用いて tensor コア行列の乗算と加算を行います。 `mma.sync` レジスタから A、B、C を取得し、計算された D に対してレジスタに書き戻します。

単一の `mma.sync` は warp 全体によって共同で実行されます。 A、B、C/D 行列の tile は、PTX の仕様に従い warp レジスタ内の 32 スレッドに分配されます。 各スレッドは tile の一部のみを保持しており、これをスレッドのレジスタフラグメントと呼びます。 32 本の糸で固定されたパーツを組み合わせると、完全なマトリックス tile ができます。

したがって、MMA を実行する前に、Ampere kernel は通常、A と B を一時的に共有メモリに格納し、その後 `ldmatrix` を使って正しいスレッドレジスタに読み込み、 `mma.sync` に必要な断片を形成します。

```text
SMEM --ldmatrix--> registers
registers --mma.sync--> registers
registers --普通 store--> SMEM 或 GMEM
```

`mma.sync` 実行時に重要なのは各レジスタの内容だけです。 上記は高性能 kernel の最も一般的なデータパスです。 他のロードやレジスタ操作もこれらの値を準備できます。

### コンクリート断片マッピング

次に、 `mma.sync.aligned.m16n8k16` を例に取り、マトリックス tile の要素が warp 内の 32 スレッドのレジスタにどのように割り当てられているかを見てみましょう。 ここで、A は行メジャー、B は列メジャー、A/B は `fp16` または `bf16`、C/D は `fp32` を使用します。 warp 全体をまとめて計算します:

$$
D_{16\times8}=A_{16\times16}B_{16\times8}+C_{16\times8}.
$$

各スレッドのレーン ID は、そのスレッドが保持する要素(A、B、C、D)を決定します。 まずは C/D accumulator を最も観察しやすいものから始めましょう。

PTX で指定されたマッピングを見ると、4 車線ごとに繰り返されることがわかります。レーン 0–3 は 0・8 行目、4–7 レーンは 1・9 行目、という具合です。 したがって、32 車線は 8 つの連続した 4 車線グループに分割できます。 現在のレーン ID を $l$ し、次のように定義します。

$$
g=l\mathbin{//}4, \qquad t=l\bmod 4.
$$

整数の割り算でグループ番号は $g$、残りを取るとグループ $t$ 内のレーンの位置が得られます。

$g$ 番目のグループは tile の $g$ 行と $g+8$ 行の出力を共同で担当します。グループ内の $t$ 番目のレーンは、これら 2 つの行の $2t$ 列と第 $2t+1$ 列を担当します。したがって、各レーンは 4 つの `fp32` 累積値を持ちます。 その論理座標は以下の通りです:

$$
(g, 2t), \qquad
(g, 2t+1), \qquad
(g+8,2t), \qquad
(g+8,2t+1).
$$

例えば、レーン 5 は次のようになります:

$$
g=5\mathbin{//}4=1, \qquad t=5\bmod4=1,
$$

したがって、C/D の 4 つの要素を保持します。

$$
(1,2), \quad (1,3), \quad (9,2), \quad (9,3).
$$

フラグメントは同じ $g$ と $t$ を使用しますが、この場合、座標は $(m,k)$ を表します。 各レーンは 8 つの `fp16` または `bf16` 要素を保持し、それぞれ 2 つの要素は 32 ビットレジスタに詰め込まれます。

$$
\begin{aligned}
\text{register 0}: &\ (g, \ 2t+\{0,1\}), \\
\text{register 1}: &\ (g+8, \ 2t+\{0,1\}), \\
\text{register 2}: &\ (g, \ 2t+\{8,9\}), \\
\text{register 3}: &\ (g+8, \ 2t+\{8,9\}).
\end{aligned}
$$

行列座標系では、行 $m=g$ と $m=g+8$ 行のレーンには、K の下半分と上半分に隣接する要素のペアが存在します。

B 断片の座標は $(k,n)$ として表されます。 各レーンは 4 つの `fp16` または `bf16` 要素を保持し、同様に各 2 つの要素は 32 ビットレジスタにパックされます。

$$
\begin{aligned}
\text{register 0}: &\ (2t+\{0,1\}, \ g), \\
\text{register 1}: &\ (2t+\{8,9\}, \ g).
\end{aligned}
$$

断片 B に関しては、 $g$ が $n$ 座標を決定し、 $t$ レジスタ番号と合わせて座標 $k$ 決定します。

この座標セットを前の章の layout マーカーに置き換えてください。 C/D の最初の 8 行は `8×8` 局所パターンを形成し、次のように表すことができます。

```text
S[(8, 4, 2) : (4@laneid, 1@laneid, 1@reg)]
```

三次元は以下の順に表されます:

```text
(row, column_pair, element_in_pair)
```

ここで、隣接する 2 つの列が `column_pair` を形成し、 `element_in_pair` は列の対における要素の位置を表します。 したがって、行列座標 `(row, col)` 原子座標に対応します。

```text
(row, col // 2, col % 2)
```

最初の 2 つの座標はレーンの ID を決定し、最後の座標はレーン内のフラグメントスロットを示します:

```text
lane_id = row·4 + col // 2
slot    = col % 2
```

レーン 5 が保持する `(1,2)` と `(1,3)` を例に取ると、それぞれ `(1,1,0)` と `(1,1,1)` の原子座標が割り当てられているため、レーン `1·4+1=5` にマッピングされ、それぞれスロット 0 とスロット 1 に保存されます。

完全な C/D 断片には、M 方向に 2 つの局所モードが含まれています。 layout 記述を容易にするために `8×8` 原子が抽出されますが、ハードウェアは完全な `mma.m16n8k16` 命令を実行します。

### `ldmatrix`: 共有メモリから断片を構築する

上記はすでに、 `mma.sync` が必要とするレジスタ断片の種類を示しています。 次の質問ですが、A と B はすでに共有メモリに存在しているので、どうやってすべてを一度に正しいスレッドレジスタに送るのでしょうか? Ampere はこの `ldmatrix` を提供します。 以下はその `.m8n8.b16` 形態についての議論です。

```text
ldmatrix.sync.aligned.m8n8.x1.shared.b16
ldmatrix.sync.aligned.m8n8.x2.shared.b16
ldmatrix.sync.aligned.m8n8.x4.shared.b16
```

この一連の指示は warp 全体によって協調的に実行されます。 `.x1`、 `.x2`、 `.x4` はそれぞれ 1、2、4 `8×8` マトリックスブロックをロードします。 `m` 番目のマトリックスブロックの `r` 行目については、レーン `m·8+r` で開始アドレスが提供されます。 したがって、 `.x1` 0〜7 レーンをアドレス、0 `.x2` 15 レーン `.x4` 32 レーンすべてを利用します。

下の図は `.x1` を示しています。 図の左側では、T0–T7 はそれぞれ 8 行の開始アドレスを提供しますが、「アドレス提供」と「受信データ」は別物です。ロードされた 64 要素は 32 スレッドすべてに分散されます。 レーン $l$ 受ける:

```text
row  = l // 4
cols = 2·(l % 4), 2·(l % 4) + 1
```

例えば、0 行目の 8 つの要素はレーン 0–3 に割り当てられています。レーン 0 は列 0–1、レーン 1 は列 2–3 を受け取り、という具合です。 各レーンで受信される 2 つの `fp16` 要素は 32 ビットレジスタにパッケージ化されます。図の左側はアドレスを提供する人物を示し、右側は最終的にデータを保持する人物を示しています。 逆方向の矢印は Hopper(`sm_90`)によって追加された `stmatrix` を示し、レジスタ断片を共有メモリに書き戻します。

オプションの `.trans` 修飾子は、各 `8×8` 行列ブロックを列メジャー方式で読み込みます。 `ldmatrix` を使わない場合は、kernel は通常のロードやレジスタ操作を使ってフラグメントを構築できますが、クロスレーンデータ配布は自分で管理する必要があります。

![ldmatrix は warp レジスタフラグメントに 8×8 の共有メモリ tile を読み込みます。 図の逆ストマトリックス経路はホッパー sm_90 およびその後のアーキテクチャにのみ適用可能です](../../gpupro/images/ldstmatrix.svg)

### 結果を書き返し、共有メモリをスウィズィングします

`mma.sync` が完了した後も、C/D はレジスタフラグメントに格納されます。Ampere では、epilogue は通常、スレッドが通常のストアを使い、結果を共有メモリやグローバルメモリに書き込み、必要に応じて warp シャッフルや部分的な再配置を用いて実行されます。

次に入力側を見てみましょう。 通常の店舗は 1 行を連続して書きたいが、 `ldmatrix` 行を横断して読み込む。 同じ共有メモリ layout は、両方のアクセス方式に対応しなければなりません。 `(8,64)` `float16` tile を例にすると、各行は正確に 128 バイトを占めます。 一般的な 4 バイトバンクの粒度では、固定列の 8 つの要素が 128 バイトの行ストライドのため同じバンクに入り、8 方向の競合が生じます。

Ampere kernel は通常、共有メモリ内の物理配置を変更するために XOR アドレス計算を手書きします。 これにより、クロスライン読み取りを異なるバンク間で分散しながら連続した行アクセスが可能になります。 前章でこのプロセスがすでに詳しく説明されており、以下の図も直感的な比較を示しています。

![通常の行メジャーtile では、行方向の書き込みは異なるバンクに分散され、列方向の読み込みは同じバンクに集中されます。 XOR スウィズルは、列方向を異なるバンクに分配します。](../../gpupro/images/swizzle_conflict.svg)は、結合された行を壊すことなく書きます。

## ホッパー: 共有記憶から直接読む

### WGMMA: 4 warp で相乗計算

ホッパーの時代には、MMA のコラボレーションは単一の warp から warpgroup へと拡大しました。 warpgroup は 4 つの連続した warp で構成され、合計 128 本の糸です。 二人は共に演奏 `wgmma.mma_async`。

入力経路ではより重要な変化が起こります。 B は行列ディスクリプタを介して共有メモリから読み込みます。 A は共有メモリやレジスタからも得られます。 これら 2 つの形態は一般的に SS と RS と呼ばれています。

```text
SS: A from SMEM, B from SMEM -> wgmma -> register accumulator
RS: A from registers, B from SMEM -> wgmma -> register accumulator
```

共有メモリからの入力が来た場合、kernel は A/B レジスタ断片を構築するために `ldmatrix` を使う必要がなくなりました。 WGMMA はデータを直接読み込みますが、マトリックスの開始地点、次のデータセットに移動する際に移動するバイト数、共有メモリに使われるスウィズルの種類を知る必要があります。 これらすべての情報は行列記述子に保存されます。

### マトリックスディスクリプタで tile を見つける方法

マトリックス記述子はレジスタに保存された 64 ビットの値です。これは WGMMA の共有メモリを読み取るための「アドレッシング命令」と考えることができます。行列データは共有メモリに残り、記述子はこの tile の見つけ方とトラバース方法のみを記録します。

| フィールド | 記述子によって記録される内容 |
|---|---|
| `matrix start address` | 共有メモリにおけるマトリックス開始点 |
| `leading dimension byte offset` (`ldo`) | 先頭次元から次のデータセットへ移動するためのバイトオフセット |
| `stride dimension byte offset` (`sdo`) | 次のデータセットへ移動するために使われるバイトのオフセット |
| `matrix base offset` | スウィズル反復パターンにおけるマトリックスの出発点 |
| `swizzle mode` | スウィズルなし、32B、64B、または 128B スウィズル |

WGMMA はまず `matrix start address` の tile の起点を見つけ、その後 `ldo` と `sdo` を使って次のデータセットに移行します。 3 つのアドレスフィールドはすべて 16 バイト単位でエンコードされています。 行列に対応するリーディング次元とストライド次元の方向については、メジャーモードとスウィズルモードがそれぞれの方向を決定します。

K メジャーのスウィズル layout を例に取ると、 `ldo` は固定コード値 1, `sdo` が最初の 8 行から最後の 8 行までのバイトオフセットを表します。 `swizzle mode` 原子の形状を決定し、原子内部の XOR アドレスを再配置します。 `matrix base offset` は、この繰り返しパターンの集合における行列の出発点の位置を示します。 スタートがパターン境界と正確に一致している場合、ベースオフセットは 0 になります。

以下の図はこのプロセスを視覚的に示しています。 例では、A は K メジャーと 128B のスウィズルを用いています。水平は K 次元、垂直は M 次元、各色ブロックは `8×128 B` 原子です。 左上の黒い点は `start_address` を示しています。 K 方向は固定された原子配置に従って展開されるため、 `ldo` は 1 として符号化されます。 8 段下に横断する際は、 `sdo` を使って次のグループに到達します。 ターゲット原子を見つけた後、スウィズルモードで原子内の要素のバイト位置を決定します。

![K メジャー128 B Swizzle では、行列記述子が開始アドレスと SDO を使って 8 行グループを特定し、固定された原子配列を介して XOR スウィズルでバイト位置](../../gpupro/images/wgmma_descriptor_kmajor.svg)を決定します

これでなぜディスクリプタが実際のバイト順と一致しなければならないのかがわかります。 TMA が共有メモリにデータを 128B スウィズルで書き込みすると、WGMMA ディスクリプタもこのデータを 128B スウィズルで解釈します。 TMA と WGMMA はそれぞれ独自の記述子を持ち、異なる命令を送りますが、同じ物理的配置を記述しなければなりません。

### accumulator はまだレジスタに残っています

WGMMA は共有メモリから直接入力を読み込み、計算された C/D は warpgroup 内の各スレッドのレジスタに散らばっています。 epilogue はこれらのレジスタ断片を処理します。 各スレッドが保持する累積値の数は、WGMMA の命令形状と蓄積タイプによって決まります。

したがって、ホッパーkernel は同時に 2 つの layout 表現を認識します。共有メモリの A/B は行列ディスクリプタで記述され、レジスタの A と C はスレッドごとのレジスタ断片で表されます。 B は常に共有記憶から生まれており、A はどちらかの経路を選択できます。

## ブラックウェル: accumulatorーが TMEM に入る

### TMEM における accumulator

ブラックウェルでは、入力側がホッパーの手法を引き継ぎます。すなわち、ディスクリプタを通じて共有メモリ内で A と B を見つけ、ディスクリプタが指定した layout に従って読み込む `tcgen05.mma` です。 特定のモードでは TMEM から A も許可されます。

主な変更点は accumulator の保管場所にあります。 ホッパーは各スレッドのレジスタに C/D を格納します。 ブラックウェルはそれらを tensor メモリ、通称 TMEM に組み込みます。 epilogue が結果を処理する必要がある場合、データをレジスタに読み込む `tcgen05.ld`:

```text
A/B in SMEM --tcgen05.mma--> C/D in TMEM
C/D in TMEM --tcgen05.ld--> register fragment --store--> GMEM
```

`tcgen05.mma` 非同期実行。 命令を出した後、kernel は MMA が完了するまで待たなければならず、epilogue は `tcgen05.ld` を通じて結果を読み取ることができます。 `tcgen05.ld` 自体も非同期です。 ターゲットレジスタを使う前に、 `tcgen05.wait::ld` を実行する必要があります。 ここで、読み書き layout が一致しなければなりません。結果がどの TMEM レーン/カラムに書き込まれるか `tcgen05.mma`、 `tcgen05.ld` データを対応する場所から取得し、各スレッドのレジスタに割り当てる必要があります。

### ブロックスケール MMA におけるスケール要因

前章の<a href="/ja/gpupro/data-layout/#tmem-におけるスケールファクターのクロス-warp-放送">TMEM では、スケールファクターズのクロス warp 放送</a>を `M=128`, `SFK=4` 例と共に用いて、TMEM におけるスケールファクターズのパッケージングと `.warpx4` 複製を導出しました。 では、データパスを進めましょう: これらの値がどのように TMEM に入力され、MMA が現在必要な数バイトをどのように選択しているか。

ブロックスケール MMA には、2 つのスケールファクターが必要です:

```text
SFA(M, SFK)
SFB(N, SFK)
```

`SFA[m,sfk]` K スケールブロックの `m` `sfk` スケールブロックである A 直列の要素に使用されます。 `SFB[n,sfk]` B の列 `n` にも同じスケーリングを行います。 ここでは前章の論理索引付け順序が用いられています。 PTX テーブルは `SFB[sfk,n]` と同じ B 面行列を形状 `SFB_M x N` で書きます。

A と B は通常、TMA によって共有メモリに読み込まれ、その後 MMA によって直接読み込まれます。 スケールファクターは TMEM に入力する必要がありますが、TMA の転送経路は共有メモリにのみ送られるため、その間に追加の `tcgen05.cp` があります。

```text
A, B:     GMEM --TMA--> SMEM --tcgen05.mma--> Tensor Core
SFA, SFB: GMEM --TMA--> SMEM --tcgen05.cp--> TMEM --tcgen05.mma--> Tensor Core
```

### `tcgen05.cp` TMEM の書き方

まず、前章で得た完全な layout を思い出してください:

```text
S[(4, 32, 4) : (4@TCol, 1@TLane, 1@TCol)]
+ R[4 : 32@TLane]
```

ここでは、 `S[...]` `(Mgroup, lane, sfk)` TMEM 内のバイト位置にマッピングされます。 データ型を持つ TIRx layout では、ストライド `@TCol` バッファ要素で測定されます。 ここでは、各スケールファクターが 8 ビットを占めるため、論理 TCol 位置は `4*Mgroup+sfk` されます。 連続した 4 つの位置は 32 ビットのハードウェア TCol セルに詰め込まれます。 同等に、 `hardware_TCol=(4*Mgroup+sfk)//4`、 `byte_in_word=(4*Mgroup+sfk)%4`。

`R[...]` は、 `TLane` 軸に沿って 4 つのコピーが複製されることを意味します。 `tcgen05.cp` `.32x128b.warpx4` フォームはまさにこれを行います。まず 32 レーンのウィンドウに書き込み、その後同じデータを他の 3 つの warp ウィンドウにブロードキャストします。

### `scale_vec` Word コピー

データはすでに TMEM に保存されており、次に 32 ビットの TMEM ワードがどのように内部的にスケールするかを見る必要があります。 `scale_vec` 1 行あたりの SFA か 1 列あたりの SFB が 1 つ、2 つ、または 4 つの論理スケールを含むかを決定します。 4 バイトのワードを埋めるために、短いスケールベクトルはワード内で繰り返されます:

```text
scale_vec::1X: [SF0, SF0, SF0, SF0]
scale_vec::2X: [SF0, SF1, SF0, SF1]
scale_vec::4X: [SF0, SF1, SF2, SF3]
```

`SFA_ID` や `SFB_ID` は MMA にどのコピーを読むべきか指示します。 1X はバイトオフセット 0、1、2、または 3 として選択可能です。 2X はオフセット 0 または 2 で、低半語または高半語を意味します。 4X は 4 バイトすべてを使うので、ID は 0 でなければなりません。

ここでの Word 内でのコピーは前 `R[4 : 32@TLane]` とは異なります。前者は 32 ビット Word からバイトをコピーし、後者は 4 つの TMEM レーンウィンドウにデータをコピーします。 スケールは K ブロック内のすべての K 要素で共有されており、これは前述の 2 つとは異なる 3 番目の要素です。

## 第 3 世代アーキテクチャにおけるスレッドごとのレジスタフラグメント

3 世代のアーキテクチャを総合して見ると、マトリックスデータは特定の段階でレジスタ断片として各スレッドのレジスタに配布されます。 断片の具体的な形状とマッピングは対応する命令によって決まります。

Ampere では、共有メモリからデータを読み込み、 `mma.sync` から読み取るレジスタ断片を構築し `ldmatrix`。

Hopper では、 `wgmma` 累積された結果をレジスタフラグメントに書き込み、epilogue に渡して処理を続けさせます。

ブラックウェルでは、計算中の accumulator は TMEM に格納されます。 epilogue が始まる前に、結果をレジスタフラグメントに読み込み `tcgen05.ld`。

したがって、レジスタ断片は三世代アーキテクチャにおいて異なる役割を果たします。 Ampere と Hopper は計算時に accumulator を保存するためにこれを使います。 ブラックウェルは主に TMEM と epilogue の境界で使っています。 以前に導入された m8n8 型原子は一般的な例です。 `tcgen05.ld` と `tcgen05.st` は他のデータ移動形状もサポートしています。

## 3 つのデータ経路の比較

| 建築 | メイン MMA 司令部 | A/B 主な情報源 | accumulator の位置 | 共有メモリ layout の表現方法 |
| --- | --- | --- | --- | --- |
| アンペア | `mma.sync` | レジスタ | レジスタ | kernel は通常、手書きのアドレス計算とスウィズルを実行します |
| ホッパー | `wgmma.mma_async` | A はレジスタや SMEM から得られます。 SMEM からの B | レジスタ | マトリックス記述子は歩幅とスウィズルモードを記録します |
| ブラックウェル | `tcgen05.mma` | 主に SMEM から; 一部の A モードは TMEM から得られることがあります | TMEM | ディスクリプタは SMEM 入力を記述し、TMEM layout は別途 accumulator とスケールファクターを記述します |

3 世代を比較すると、この進化の軌跡は非常に明確です。Ampere はまず入力をレーンごとのレジスタ断片に整理し、 ホッパーは tensor コアがディスクリプタを通じて共有メモリを直接読み取ることを可能にします。 ブラックウェルはその後、accumulator とスケールファクターを TMEM に移しました。

kernel を書く際には、データフローに沿ってセグメントごとに確認できます。つまり、前の命令でデータが書き込む配置がどうであれ、次の命令は layout やディスクリプタを使って読み取るべきです。 中間に誤解があれば、tensor コアが元素を誤読することがあります。 たとえ結果が正しくても、不適切なメモリアクセス方法のためにパフォーマンスが低下する可能性があります。
