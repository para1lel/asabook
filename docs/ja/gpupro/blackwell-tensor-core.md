::: info 概要
- `tcgen05.mma` 通常、A と B は SMEM から読み出し、C/D accumulator は TMEM で更新されます。 epilogue では、 `tcgen05.ld` を通じて結果をレジスタに読み戻します。
- `cta_group::1` 現在の CTA を使い、同時に 1 つの CTA ペア `cta_group::2` 使う; この 2 つのモードは異なる TMEM accumulator マップに対応します。
- ブロックスケール MMA は TMEM に SFA と SFB も必要です。 本章で用いる読み込み経路では、まず SMEM に入り、その後 `tcgen05.cp` TMEM に移行し、CTA ペア A および B の作業分担に従ってシャード化または複製されます。
:::

「[Tensor Core データ layout の進化](/ja/gpupro/tensor-core-data-layouts/)」章では、Ampere、Hopper、Blackwell アーキテクチャにおけるマトリックス乗算累積(MMA)のデータパスをすでに紹介しています。 本章ではさらに Blackwell の `tcgen05.mma` に焦点を当てます。すなわち、MMA 命令の開始方法、accumulator が TMEM にどのようにマッピングされるか、そして `cta_group` が現在の CTA を使って動作するか CTA ペアで動作させるかを決定する方法です。

前章で議論した TMA([非同期データ転送: TMA](/ja/gpupro/tma/))は通常、A tile と B tile を SMEM に非同期移動させる役割を担います。 ここでは、A と B がすでに SMEM に入っている段階から、 `tcgen05.mma` がどのように行列の乗算と蓄積を行うか、結果が TMEM にどのように対応するか、そしてなぜブロックスケール MMA が追加のスケールファクターデータパスを必要とするのかを紹介します。

*デフォルト設定を `M=128`、 `N=16` 保ち、K 次元に沿って計算を徐々に進めていきます。各反復で生成される部分や、それらが TMEM にどのように蓄積されるかを観察できます。また、A と B の転置設定を切り替えたり、N を変更したりして、異なる構成下での入力 tile、出力 tile、命令パラメータの変化を比較することもできます。*

まずは画像のデフォルト状態を見てみましょう。 図の各セルは `16×16` 要素ブロックを表しているため、tile C の出力形状は `128×16` ですが、縦に 8 セル、横に 1 セルとして表示されます。反復をクリックするたびに、tensor コアは A から `8×1` ブロックの `128×16` スライスと B から 1 ブロックの `16×16` スライスを読み取り、その `128×16` 部分の和を生成します。

最初の反復では `accum=0` が使われ、TMEM の元の累積値を読み取るのではなく、現在の積を対応する C tile に直接書き込みます。

```text
C[0:128, 0:16] =
    A[0:128, k:k+16] × B[k:k+16, 0:16]
```

その後の反復は `accum=1` に切り替わり、TMEM の既存結果に新しい部品や累積結果が追加されます。

```text
C[0:128, 0:16] +=
    A[0:128, k:k+16] × B[k:k+16, 0:16]
```

すべてのキテレーションは同じブロック `128×16` TMEM 領域を更新します。 最後の反復が完了した後にのみ、このエリアに最後の C tile が残ります。

図の下部には、この MMA で使用される記述子と PTX 命令も示されています。 次のセクションでは、各分野を一つずつ説明します。

次に、命令開始方法、 `cta_group` 操作範囲、TMEM layout を紹介します。

## `tcgen05.mma` 実行方法

`tcgen05.mma` はブラックウェル tensor コアの行列乗算命令です。 これは単一のスレッドで独立して行われるスカラーの乗算・加算ではなく、完全な行列 tile を扱います。

Ampere の `mma.sync` や Hopper の `wgmma.mma_async` とは異なり、 `tcgen05.mma` は単一スレッドの意味論を採用しています。 選択したスレッド 1 つだけで命令が発行され、ハードウェアが完全な tile レベルの行列乗算と蓄積を開始します。他のスレッドは同じ MMA 命令を別々に提出する必要はありません。

以下は、A と B の両方が SMEM からでブロックスケーリングが使用されていない場合の `tcgen05.mma` の一般的な命令フォーマットです。

```text
tcgen05.mma.cta_group.kind
    [d-tmem], a-desc, b-desc, idesc,
    {disable-output-lane}, enable-input-d {, scale-input-d};
```

各部品の機能は以下の通りです。

| フィールド | 機能 |
| --- | --- |
| `cta_group` | MMA が現在の CTA リソースを使うのか、それとも CTA ペアリソースを使うのかを指定します |
| `kind` | A と B がどの要素に属するデータ型カテゴリを指定します |
| `d-tmem` | TMEM における C/D accumulator の開始アドレス |
| `a-desc`, `b-desc` | SMEM における A と B のアドレスと layout を記述してください |
| `idesc` | M、N、K、A/B、C/D の具体的なデータ型や、operand メジャーモードなどの命令パラメータを指定します |
| `disable-output-lane` | 結果を更新しない TMEM レーンを指定する; デフォルトの例ではレーンを塞がれません |
| `enable-input-d` | 相互作用図の `accum` に対応する。 偽の場合は `D=A×B`、真の場合は `D=A×B+D` を計算します |
| `scale-input-d` | 蓄積前の既存の D を拡大するためのオプションパラメータ; この章の例ではこの方法が使われていません |

インタラクショングラフのデフォルト構成は `cta_group::1.kind::f16` を使用します。 この本の後続の kernel も通常 `.kind::f16` を使用し、 `idesc` で `f32` accumulator を選択します。 `.kind::f16` A と B が 16 ビット浮動小数点圏に属することを指定します。 A と B が `f16` を使うか `bf16` か、C/D が `f16` か `f32` を使うかは、すべて `idesc` によって規定されています。

`cta_group` 単一スレッドの意味論は変更せず、この MMA が現在の CTA を使うか CTA ペアリソースを使うかを決定します。 具体的な CTA の分業および TMEM マッピング、ならびにブロックスケール形式に必要な SFA および SFB TMEM アドレスについては、以下の関連セクションで説明します。

本章で議論した SMEM からの経路 A と B については、2 種類の layout を同時に考慮する必要があります。

- SMEM layout は tensor コアが A および B をどのように解釈・読み込むかを決定します。
- TMEM の配置は、C/D accumulator が TMEM のレーンや列にどのようにマッピングされるかを決定します。

これら 2 つの layout は異なるメモリ空間に配置されており、具体的なマッピングは現在の `tcgen05.mma` の命令形状、データ型、operand メジャーモードによって決まります。 この章では、「[データ layout とその表記法](/ja/gpupro/data-layout/)」章で紹介された命名軸とスウィズルの概念を用いてこれらのマッピングを説明します。

`tcgen05.mma` を送信することは非同期操作が開始されたことを示すだけで、結果が書き込まれたという意味ではありません。 同じスレッドが 1 つ以上の MMA を連続して送信し、その後実行することができます

```text
tcgen05.commit
```

スレッドが以前に発行した非同期 `tcgen05` 操作を `mbarrier` 追跡します。 ハードウェアがこれらの操作を完了すると、対応する `mbarrier` に完了信号を送ります。

待機中、kernel 内の他の warp が動き続けたり、次の tile を準備したりすることができます。 accumulator が実際に `tcgen05.ld` を読み取ったとき、consumer は対応する `mbarrier` が完了して実行されるのを待つ必要があります

```text
tcgen05.fence::after_thread_sync
```

完了通知とその後の TMEM 訪問の順序を確立します。 そうでなければ、epilogue でまだ更新中の TMEM データを読み取ることができます。 以下の非同期セクションでは、このメカニズムを詳しく説明します。

## TMEM における accumulator

Ampere や Hopper では、PTX プログラミングモデルから accumulator がレジスタ上に配置されています。MMA によって生成された結果は、計算に関与するスレッド間にレジスタ断片として分散され、epilogue はこれを直接読み取って処理できます。 accumulatorーtile が大きいほど、これらの長く残る断片はより多くのレジスタを占めます。

ブラックウェルは長寿命 accumulatorーを TMEM に移行しました。 TMEM は CTA scope を備えた二次元オンチップメモリ空間です。 この `sm_100a` では、各 CTA の TMEM は 128 行のレーンと 512 列の col を含み、各セルは 32 ビットで構成されています。 `tcgen05.mma` 計算中に TMEM で accumulator を継続的に更新し、最後に epilogue で型変換、要素ごとの操作、ストアのために `tcgen05.ld` を通じて結果をレジスタに読み込みます。

`tcgen05.ld` 自体も非同期命令です。 ターゲットレジスタを使用する前に、warp によって以前に発行された TMEM 負荷が完了したことを確認するための `tcgen05.wait::ld` が必要です。

これにより、accumulator はメインサイクル中に長期間レジスタを占有する必要がなくなりました。 それに伴い、問題は TMEM の割り当てと layout に移ります。MMA は正しい TMEM 座標に結果を書き込み、epilogue はその配置に従ってこれらの値を読み返さなければなりません。 次の章では、TMEM の割り当て、アドレス指定、読み書きについてさらに詳しく扱います。

## `cta_group` 作戦範囲の決定方法

`cta_group::1` を使う場合、MMA は現在の CTA の TMEM のみを更新します。 次に、A が稠密行列である場合、つまり A のすべての要素が明示的に格納され、A と B の両方が SMEM からディスクリプタを介して読み取られる一般的なケースについてまず説明します。 特定の `tcgen05.mma` barrier 構成では TMEM から A も許可されています。

`cta_group::2` を使用する場合、MMA は CTA ペア内の 2 つの CTA から同時に TMEM にアクセスします。 CTA ペアは、同じ cluster 内の 2 つの CTA で構成され、 `%cluster_ctarank` 最も低いビットでのみ異なります。すなわち、一方は偶数、もう一方は奇数です。 以降、それぞれ偶数型 CTA と奇数型 CTA と呼ばれます。

ハードウェアは CTA ペアのうち 1 本のスレッドだけで送信 `tcgen05.mma`; 指令は偶数個の CTA または奇数個の CTA で発行できますが、ピアの CTA はアクティブなままなければなりません。 この本に従う kernel は、MMA は偶数回の CTA で 1 スレッドから送信され、完了はコミットによって通知される `tcgen05.commit` 合意しています。

accumulator の配置は、 `cta_group`、M 次元、A が密行列か構造化疎行列か、 `tcgen05.mma.ws` を使うかによって決定されます。 この layout は論理座標 `(m,n)` `TLane` および `TCol` にどのように写るかを指定します。

`N` 命令記述子によって指定されます。 この節で議論する `f16` / `bf16` パスでは、 `cta_group::1` 8 から 256 までの `N` を 8 段階で、 `cta_group::2` `N` を 16 段階で 256 までサポートしています。 以下の 4 つの図は、これらの有効な値を表現するために記号 `N` を使用しています。 紫は SMEM operand、オレンジは TMEM accumulator、緑は Tensor Core MMA のデータパスを示します。

### `cta_group::1`, `M = 128`

これが最も直接的な状況です。 CTA は 128 行を含む出力 tile を計算し、その CTA の TMEM にはちょうど 128 列のレーンも含まれます。 したがって、accumulator の `m` 行目は直接 TMEM レーン `m` にマッピングされ、N 次元は TMEM 列に沿って展開します。

最終的な結果は 128 車線の列と北の柱を占めました。 この CTA は自身の SMEM から A、B を読み取り、完全な accumulatortile を自身の TMEM に保存します。

!['cta_group::1','M=128': ライン m は直接 TMEM レーン m](../../gpupro/images/mma_cg1_m128.svg)に対応します

### `cta_group::1`, `M = 64` (`.ws` なし)

図は前の表記法を継続しており、 `C` は MMA 出力 accumulator を表します。 その論理的な形は `M x N` である。 このセクションは `M = 64` を取るため、 `C` の形状は `64 x N` です。 TMEM には現在も 128 レーンの列があります。 ここでは標準 `tcgen05.mma` について議論しており、 `.ws` 接尾辞付きの重み定常形ではありません。 TMEM マッピングは layout F を使用しています。

layout F は、ハードウェアのデータパスに応じて 128 の TMEM レーンを 4 つの 32 レーンゾーンに分割し、それぞれ `warp-rank % 4 = 0,1,2,3` に対応しています。 64 列の M 列も 4 つのグループに分かれ、それぞれ 16 列ずつ、順番に配置されています。 各グループは 16 列しかないため、32 レーンのエリア内のレーンの半分だけが現在の tile で使用されます。

`a` を TMEM レーンの整列を表し、値が 0 または 16 とします。 論理線 `m` に対応する TMEM レーンは次の通りです。

```text
group        = m // 16
row_in_group = m % 16
TLane        = group * 32 + a + row_in_group
```

TMEM レーンのアライメントが 0 の場合、マッピングは次のようになります。

```text
rows  0-15  -> lanes   0-15
rows 16-31  -> lanes  32-47
rows 32-47  -> lanes  64-79
rows 48-63  -> lanes 96-111
```

したがって、レーン `16-31`、 `48-63`、 `80-95`、 `112-127` はこの tile には属しません。

kernel が別の独立した `M=64` accumulatortile を格納する必要がある場合は、レーンのアラインメントを 16 に設定できます。 このようにして、その 4 行は以前に空いた車線の位置を反映しています。

```text
rows  0-15  -> lanes  16-31
rows 16-31  -> lanes  48-63
rows 32-47  -> lanes  80-95
rows 48-63  -> lanes 112-127
```

図のオレンジ色の帯は現在のレーンアライメント 0 の tile に対応し、スラッシュ帯はレーンアライメント 16 が使える位置を示しています。 2 つの tile はレーンの位置が重ならないため、同じ TMEM 列を使用できます。 N 次元は依然として TMEM 列に沿って展開します。

!['cta_group::1'、'M=64'、.ws は使わない: 4 列連続 16 列で 32 列をレーンストライドとする; レーンの配置は 0 または 16 に設定でき、別の「M=64」tile 用の補完的な](../../gpupro/images/mma_cg1_m64.svg)を残します

### `cta_group::2`, `M = 256`

`M = 256` 時、CTA の 128 レーンの列では M の全寸法を収容できず、accumulator は CTA ペア内の 2 つの TMEM に分散されます。

偶数の CTA は論理行を `0-127` 保存し、奇数の CTA は論理行を `128-255` 保存します。 両 CTA はそれぞれの TMEM からレーン `0-127` を使用し、N 次元はそれぞれの完全な TMEM 列に沿って展開します。

物理的には、これらは 2 つの CTA に属する 2 つの 128 列 TMEM です。 論理的には、これらは合わせて accumulatortile `256×N` を表します。 A と B が 2 つの CTA の SMEM にどのように分配されるかは、特定の kernel によるデータの整理方法に依存し、accumulator の layout には含まれません。

!['cta_group::2','M=256': M 次元は CTA ペア内の 2 つの CTA に連続して割り当てられ、それぞれ 128 ラインを保持します](../../gpupro/images/mma_cg2_m256.svg)

### `cta_group::2`、 `M = 128` (A は稠密行列)

`cta_group::2, M=128` と A が密度の高い行列の場合、PTX は Layout B を使って accumulator を整理します。 まず、タスクを M 次元に沿って分割します。CTA でも C の行は `0-63`、奇数の CTA は `64-127` 行を保存します。

その後、各 CTA は内部で 64 行の M を 2 つのグループに分割し、各グループは 32 本のラインで構成されます。 N 次元は前半分と後半分にも分かれています。 これら 2 つの M 列と 2 つの N ハーフブロックは `2×2` マッピングを形成し、CTA の 4 つの 32 車線区域に配置されます。

| N レンジ | CTA 内の M 列 | TMEM レーン |
| --- | --- | --- |
| `0 ... N/2-1` | `0-31` | `0-31` |
| `0 ... N/2-1` | `32-63` | `32-63` |
| `N/2 ... N-1` | `0-31` | `64-95` |
| `N/2 ... N-1` | `32-63` | `96-127` |

`m_local = m % 64` とすると、論理要素 `C[m,n]` を含む CTA と TLane は次のように書けます。

```text
CTA   = even,  if m < 64
        odd,   if m >= 64

TLane = m_local,       if n < N/2
        64 + m_local,  if n >= N/2
```

例えば、 `N=16` 時、 `C[10,3]` は偶数 CTA の TLane 10 に位置します。 `C[10,11]` 依然として均等な CTA に位置していますが、N の後半に属しているため TLane 74 にマッピングされています。

ここでは、密度 A に対応する layout B を記述します。もし A が構造化されたスパース行列であれば、 `cta_group::2, M=128` 別の layout C を使用し、上記の写像を直接適用することはできません。

![cta_group: : 2, M=128、A は密度の高い行列です。各 CTA は 64 行の M を格納し、N の 2 つの半分はレーン軸の上下半分に対応します](../../gpupro/images/mma_cg2_m128.svg)

これら 4 つの layout は、各 accumulator 要素をどの CTA とどの TMEM 位置に書き込む `tcgen05.mma` を指定します。 その後の `tcgen05.ld` は、元の論理 C tile を正しく読み戻すために、一致する TMEM アドレスとロード形状を使用しなければなりません。

## ブロックスケール MMA

MXFP8 と NVFP4 は、先に導入された 2 つの特定のブロックスケール形式です。 <a href="/ja/gpupro/data-layout/#tmem-におけるスケールファクターのクロス-warp-放送">データ layout の章</a>では、ブロックスケーリングの計算、SFA、TMEM における SFB パッキング、クロス warp 複製が紹介されています。 <a href="/ja/gpupro/tensor-core-data-layouts/#ブロックスケール-mma-におけるスケール要因">Tensor Core のデータ layout の進化</a>、 `scale_vec` の `tcgen05.cp` データパスとバイト選択をさらに示しています。 ここではこれらの詳細を繰り返しません。スケールファクターが CTA ペアにどのように配置されているかを見てください。

ここで必要な関係は 2 つあります。 `SFA(M,SFK)` A の各行に対してスケール因子を提供し、 `SFB(N,SFK)` B の各列に対してスケール因子を提供します。 ブロックスケール `tcgen05.mma` は TMEM から読み込み、A と B は SMEM から読み取っています。

```text
A, B:     global memory -> SMEM -> tcgen05.mma
SFA, SFB: global memory -> SMEM -> tcgen05.cp -> TMEM -> tcgen05.mma
```

### 2 つの CTA がどのようにスケールファクターを配置するか

論理座標 `(m,n)` の出力では、A は `SFA[m,sfk]`、B は `SFB[n,sfk]` を使用します。 したがって、CTA ペアにおけるスケール因子の配置は、M 次元と N 次元の割り方に依存します。

図の `M=256` の MMA を例に取ると、偶数の CTA は C の `0-127` 行を計算し、奇数の CTA は `128-255` 行を計算します。 必要なのは SFA に対応する以下の行だけです:

```text
偶数 CTA: SFA[0:128,   :]
奇数 CTA: SFA[128:256, :]
```

図では共通の実装が用いられています。2 つの CTA はそれぞれ B の N 列の半分をローカル SMEM に移動させますが、協調型 MMA は B tile 全体を同時に使用します。 したがって、完全な N 次元に対応する SFB は両方の CTA に同時に提供する必要があります:

```text
SFB[0:N, :]
```

一般的な実装では、まず SFB を CTA ペアの 2 つの SMEM にマルチキャストし、その後 `tcgen05.cp.cta_group::2` がそれぞれの CTA からそれぞれの SMEM を書き込みます。

これには CTA 内の内部コピー層も含まれます。 SFA でも SFB でも、 `tcgen05.cp.32x128b.warpx4` はその CTA の 4 つの 32 レーン TMEM パーティション(`TLane 0-31`、 `32-63`、 `64-95`、 `96-127`)に 32 レーンのベース layout をコピーします。

したがって、図では SFA は M 次元に沿って 2 つの CTA に分割されており、SFB はそれぞれの CTA に 1 つのシェアを持ちます。 各 CTA の TMEM に入力すると、両者ともそれぞれの CTA の 4 つの 32 レーンパーティションにコピーされます。

## `tcgen05` 指示がどのように正しくデータを渡すか

`tcgen05.mma` 単一のスレッドから開始するだけでよいものの、tile レベルの協調操作を実行します。 `cta_group` この操作に現在の CTA を使うか、SMEM と TMEM の CTA ペアを同時に使うかを決定します。 対応する TMEM layout は、最終的にどの `TLane` `TCol` とどの CTA の座標を最終的に書くかを決定します。 本章で用いるブロックスケールパスでは、SFA と SFB はまず `tcgen05.cp` を介して TMEM に移行され、その後 CTA ペア A と B の分担に従ってシャード化または複製されます。

したがって、 `tcgen05.cp`、 `tcgen05.mma`、 `tcgen05.ld` などの非同期命令を接続する際には、同時に 3 つのことを確保しなければなりません。すなわち、操作が正しい CTA または CTA ペアで動作すること、producer が生成したデータ layout が consumer の期待する layout に一致していること、そして consumer が対応する完了およびシーケンス機構を通じてデータが安全に使用できることを確認することです。 いずれの条件も満たされない場合、ハードウェアが誤った TMEM 座標からデータを解釈したり、データが更新中の間に早期に読み取ってしまうことがあります。

`tcgen05` の鍵を理解することは、指示が使用する CTA リソース、データのマッピング場所、そして次の段階で結果をいつ読み取れるかという 3 つの質問にまとめることができます。
