::: info 概要
- 永続 kernel により、既に常駐している CTA や CTA cluster が複数の出力 tile を継続的に計算できるため、CTA の立ち上げや公開準備のオーバーヘッドを削減します。
- cluster 発射管制(CLC)は、稼働中の CTA や cluster がまだ開始されていない打ち上げをキャンセルし、grid 座標を乗っ取ることを可能にします。
- CLC は非同期完了を要求し、その結果は共有メモリと `mbarrier` を通じてワーカーに届けられます。 現在の tile を完成させた作業者は、作業量の不均一による休憩時間を減らし、未処理の作業を継続できます。
:::

前の章では、tile のピースがどのように計算を完了するか、すなわち A と B がどのように SMEM に移行するか、tensor コアがどのように MMA を実行、非同期操作がどのようにデータを `mbarrier` を通じて渡すかに焦点を当てていました。 行列が多くの出力 tile に分割される場合、kernel はもう一つの問題も解決しなければなりません。すなわち、これらの tile をどの順序で CTA や CTA クラスタに割り当てるべきかということです。

出力行列を 100 枚の tile に分割したとします。 最も単純な方法は、100 個の CTA を起動し、0 番目の CTA の計算 tile 0、1 つ目の CTA の計算 tile 1、というように順に進めることです。 GPU は通常、100 の CTA すべてを同時に実行できないため、そのうちいくつかは先に実行されます。 CTA が終了してリソースを解放した後、ハードウェアはすべての tile が処理されるまで続く CTA を開始します。

従来の固定数永続 kernel は別の方法を用いています。長期間実行されている CTA やクラスタのセットだけを起動し、各ワーカーがループ内で複数の tile を連続的に計算できるようにします。 これにより CTA の開始と繰り返し準備のコストは削減されますが、新たなスケジューリングの問題も生じます。例えば、ある作業員が現在の tile を完成させた後、次の tile はどこから来るのかという点です。

本章ではブラックウェルの cluster 発射制御(CLC)を紹介します。 CLC kernel の起動 grid は依然としてすべての出力 tile をカバーしていますが、実行中のワーカーはまだ開始されていない CTA や cluster のローンチをキャンセルし、その座標を乗っ取ることができます。 これにより、grid 全体のタスク番号が保持されるだけでなく、配属作業員が実際の完了に基づいて動的に作業を請求できるようになります。

## 静的永続スケジューラの制限

以下に、すでに実行を開始し、繰り返しタスクを取得できる CTA や cluster を総称してワーカーと呼びます。

最も簡単なスケジューリング方法は、各作業員がどの tile を扱うかを事前に計算することです。 例えば、grid ストライド割り当てを用いた後、tile が 12 枚でワーカーが 4 枚になった場合、結果は次のようになります。

```text
worker 0: tile 0, 4, 8
worker 1: tile 1, 5, 9
worker 2: tile 2, 6, 10
worker 3: tile 3, 7, 11
```

4 人のワーカーが同時に動作でき、tile ごとの計算負荷が近ければ、この静的割り当ては問題になりません。 しかし、kernel が実際に使用できる SM の数は、起動前に必ずしも分かっていません。 例えば、他の核が SM の一部を占めている場合があります。 上の作業員 3 が長時間作業を始められないと仮定すると、作業員 0、1、2 がそれぞれの tile を完成させた後に作業員 3 が残りの `3、7、11` を処理する前に作業します。 この時点で、kernel のほとんどのクワラはすでに退出しており、1 つのワーカーだけが実行を続け、長いローンチテールを形成しています。

tile によって計算負荷が異なる場合があります。 境界処理、マスキング、スパースコンピューティング、または GEMM を中心に融合した他の操作は、特定の tile を遅くすることもあります。 静的スケジューラーは実際の作業開始前に作業分担を定義するため、実際の完了時間に基づいてタスクを再配分することは不可能です。

CLC はこれら 12 枚の tile を異なる方法で整理しています。 発射 grid には 12 の CTA があり、 `blockIdx.x` は 0 から 11 までの範囲で、 `blockIdx.x = i` CTA は tile `i` を担当します。 現在 3 つの CTA しか収容できず、スケジューラーがまず CTA0、1、2 を打ち上げると仮定すると、CTA3 から 11 は一時的にローンチキューに残り、リソースが利用可能になるまで待ちます。

CTA 0 はすでに tile 0 で計算済みと仮定します。 今はやめることはできませんが、まだ始まっていないハードウェアから仕事を依頼するだけです。 ハードウェアが CTA 3 を選択すると、CTA 3 の起動をキャンセルし、CTA 3 が使うべきだった `blockIdx` 座標を CTA 0 に戻します。 CTA 0 この座標に基づいて、tile 3 を見つけて tile 3 を完成させ、次のジョブを再度リクエストします。

キャンセルされた CTA 3 は実行を開始しなかったため、移行すべきレジスタや実行状態が存在しませんでした。 座標 3 のみが CTA 0 にハードウェアを託します。 この kernel 内の座標は tile 3 のタスク番号として機能します。 すでに稼働中の CTA は、この方法で未発表の作業を引き継ぎ、CLC はこれを「仕事の盗み」と呼んでいます。

したがって、各座標は一度だけ処理されます。通常は独自の CTA を開始する場合もあれば、開始前にキャンセルされてすでに稼働中の作業者に引き継がれる場合もあります。 打ち上げキュー内にキャンセル可能な座標があれば、待機作業員は事前に指定された CTA 開始を待つことなく計算を続けられます。

上記の例では、CTA を dispatch ユニットとして扱っています。 kernel がスレッドブロック cluster を使用している場合、CLC はまだ開始されていない cluster の起動を各時点でキャンセルし、その座標をすでに稼働中のクラスタに渡します。 スレッドブロック cluster は Hopper から提供される実行層です。複数の CTA が共同スケジュールされており、クラスタ範囲間の同期やクラスタ内の他の CTA の分散共有メモリへのアクセスが可能となります。 ブラックウェルの CLC は、これらの CTA や cluster 座標を動的にスケジューリングする責任を担っています。

## CLC の要請

労働者がすでに現在の tile を取っているとします。 次の作品を得るために、まず以下の書類を提出します:

```text
clusterlaunchcontrol.try_cancel.async
```

`try_cancel` grid スケジューラーに、まだ始まっていない CTA や cluster をキャンセルしようとします。 ハードウェアはその結果を 16 バイトレコードにエンコードし、共有メモリに書き込みます。 通常、リクエストを送信するために 1 つのスレッドだけが選ばれます。 複数のスレッドが同時に実行されると、複数のキャンセルリクエストが生成され、結果となる場所は別々に準備し、各リクエストは barrier の到着カウントと送信カウントに含めます。

このリクエストは非同期です。 命令が出された後、ワーカーは現在の tile の計算を続けられます。 この時点では、共有メモリから結果をすぐに読み取ることはできません。 CLC はこの 16 バイトが書き込まれたら、 `mbarrier` を通じて報告します。 具体的な方法は前章の TMA ロードと同じです。リクエストを開始したスレッドが到着を報告し、tx-count に 16 バイトをレジスタします。 ワーカーは対応する barrierphase が完了した後にのみ結果を問い合わせることができます。

リクエストが完了した後、まずキャンセルが成功したかどうかを確認しましょう:

```text
clusterlaunchcontrol.query_cancel.is_canceled
```

このクエリは述語を返します。 結果が正しければ、スケジューラは保留中の打ち上げをキャンセルしたことを意味します。 次に実行します:

```text
clusterlaunchcontrol.query_cancel.get_first_ctaid
```

これによりキャンセルされた CTA の `(x, y, z)` 座標が得られます。 キャンセルがクラスタの場合、最初の CTA の座標を返します。 kernel はこの座標を対応する出力 tile に変換します。

もし結果が誤りであれば、そのリクエストが管理可能な座標を得られていないことを意味します。 最も一般的な理由は、ローンチキューに保留中の作業が残っていないか、スケジューラがより高い優先度の kernel をスケジューリングしようとしている場合です。 失敗を観察した後、作業者はタスクの回収を終了すべきです。 PTX の規定によると、この期間を過ぎて再度キャンセル申請を行うことは定義されていない行為と見なされます。

CLC は「ミッションなし」を示す特定の数字を使いません。 `is_canceled` が真を返す場合にのみ、 `get_first_ctaid` の結果が有効となります。 失敗したリクエストに対する座標の読み取りも定義されていない動作です。

dispatch ャが複数の CTA を含む cluster の場合、キャンセルリクエストは一度に cluster 全体を占拠します。 `get_first_ctaid` cluster 内の最初の CTA の座標と、残りの CTA およびそれぞれのローカルブロックインデックスを返して、それぞれの grid 座標を取得します。

## リクエストと現在の計算を重ねる

作業者はまず自分の `blockIdx` を使って最初の tile を決定します。 その後、ループ内の各ラウンドは以下のステップを実行します。

1. `try_cancel` を提出し、次の可能な作品を事前にリクエストし、
2. リクエスト実行時に現在の tile を計算します。
3. 現在の tile が完成したら、対応する CLC の `mbarrier` を待ちます。
4. キャンセルが成功したかどうか確認してください。
5. 成功したら、返された座標を使って次のラウンドに進みます。失敗したら退出します。

以下の擬似コードは、barrier 初期化、位相更新、応答バッファに必要な非同期プロキシフェンスを省略し、タスク取得と計算の順序のみを示しています。

```text
tile = decode(blockIdx)

while true:
    async_try_cancel(result, barrier)
    compute(tile)
    wait(barrier)

    if not is_canceled(result):
        break

    tile = decode(get_first_ctaid(result))
```

なぜ現在の tile を計算する前に次のピースを要求するのでしょうか? grid スケジューラはリクエスト処理に時間がかかるからです。 現在の tile の計算が終わるまで待ってからリクエストを提出すると、遅延は 2 つの tile の間に直接収まり、作業者は停止して待たざるを得なくなります。

早期提出後、スケジューラーはリクエストを処理し、同時に現在の tile を計算できます。 現在の tile が完成すると、次の共同作業はしばしばすでに共有メモリに書き込みされています。 TMA はデータ転送遅延をカバーするために計算を用い、CLC はスケジューリングリクエスト遅延をカバーするために現在の tile 計算を使用します。両者とも同じ非同期パイプライン方式を使用しています。

CLC は非同期プロキシを介して共有メモリに応答を書き込み、通常のスレッドはジェネリックプロキシを通じて結果をクエリします。 `mbarrier` 待ちは非同期応答が完了したことを確認するために使われます。 実際には、新しいリクエストを送信し応答を読み取った後、コードは PTX 要件に従って対応するプロキシフェンスを実行し、非同期プロキシと汎用プロキシ間のアクセス順序を確立し、次の非同期書き込みラウンドと未完了の読み取りとの競合を防ぎます。 さらに、kernel は CTA やクラスタ scope 内で barrierphase やスレッド同期を適切に処理する必要があります。

## CLC の使用時期

静的スケジューラと CLC は同じ tile 計算ボディを共有することができます。 ただし、「次の tile はどこから来るのか?」という質問だけが違います。

```text
静态调度：根据 worker ID 和迭代次数算出下一个 coordinate
CLC 调度：由硬件返回一个尚未启动的 CTA 或 cluster coordinate
```

静的スケジューリングはほとんどタスクのオーバーヘッドがありません。 利用可能な SM の数が安定し、各 tile のコストが近い場合、静的な計算式で十分です。

CLC は、運用資源や tile コストを事前に把握しにくい状況により適しています。 もし一部の SM が他の kernel に占有されていたり、異なる tile 間で実行時間の差が大きい場合、タスクを最初に完了したワーカーが保留中の座標を引き継ぎ続けることができ、ローンチテール作業に費やす時間を数人のワーカーに減らすことができます。

TIRx では、CLC を動的 tile スケジューラとしてカプセル化できます。 GEMM のメインループと epilogue は現在の tile 座標のみを受け入れます。それが静的な式で計算されるのか、CLC によって返されるのかを知る必要はありません。 この方法により、kernel の計算コードは変更されず、次のコーディネーターを提供するスケジューラだけを置き換えます。
