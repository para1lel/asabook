::: info 概要
- `TileLayout` 論理 tile がネームラインにどのように配置されるかを表すために、 `S[...]`、 `R[...]`、オフセットを用います。
- `TileLayout.apply()` 論理要素の基本的な物理座標を計算する; レプリカ情報は `layout.replica` に保存され、その layout を用いた tile 操作で処理されます。
- `SwizzleLayout` 共有メモリにおける XOR ベースのアドレス再配列を記述します。 標準的な tilelayout を同時に表現したい場合 `ComposeLayout` 両方の組み合わせを使うことができます。
:::

[データ layout とその表記法](/ja/gpupro/data-layout/)tile 形状、名前付き軸を持つストライド、複製寸法、固定オフセットを導入しました。 この章では、TIRx プログラム内でこれらの layout をどのように構築、使用、クエリするかを説明します。

例えば、以下の表記法は TMEM にある `128×256` tile を表しています:

```python
S[(128, 256) : (1@TLane, 1@TCol)]
```

TIRx プログラムでは、このマーカーを使って直接 `TileLayout` を構築し、バッファにバインドすることができます:

```python
layout = TileLayout(S[(128, 256) : (1@TLane, 1@TCol)])

pool.alloc(shape, dtype, layout=layout)

T.decl_buffer(shape, dtype, scope=scope, layout=layout)
```

したがって、バッファは物理的な layout を記録します。 その後の tile 操作では、各アクセスで要素がどのレーン、レジスタ、または線形記憶場所にあるかを再指定することなく、この情報を直接読み取ることができます。

この章で使用されている layout オブジェクトとネームラインは、 `tvm.tirx.layout` に位置しています:

```python
from tvm.tirx.layout import (
  TileLayout,
  SwizzleLayout,
  ComposeLayout,
  S,
  R,
  laneid,
  warpid,
  tid_in_wg,
  TLane,
  TCol,
  m,
  tcgen05_atom_layout,
  tmem_datapath_layout,
  wg_local_layout,
)
```

layout の結果が必ずしも線形アドレスである必要はありません。また、 `laneid`、 `warpid`、 `TLane`、 `TCol` などのハードウェア座標でもあることがあります。 従来の TMEM layout では、論理行を `TLane` に、論理列を `TCol` にマッピングしていました。 次に、レーン軸と warp 軸の両方を使うレジスタフラグメントを見てみましょう。

```python
frag = TileLayout(
  S[(8, 2, 4, 2) : (4@laneid, 1@warpid, 1@laneid, 1)]
)
```

同じ物理軸が何度も現れることがあります。 ここでは、最初のものと三番目のものの両方がこの作品に貢献 `laneid`。 ラストストライドには明確な軸タグがないため、デフォルトの軸 `m` を使用します。

[データ layout とその表記法](/ja/gpupro/data-layout/) レーン内のフラグメントスロットを区別するために、 `@reg` が使われます。 現在、TIRx API は軸 `reg` 個別に登録していません。 layout がレジスタバックのローカルバッファにバインドされている場合、デフォルトの軸 `m` スレッドのローカル線形位置を表します。 バッファ scope はデータが実際にレジスタに保存されていることを判定するため、ここでの `m` はデータがグローバルメモリや共有メモリに保存されているという意味ではありません。

`m` や `TCol` のようなストレージ軸では、ストライドはバッファ要素で測定されます。 32 ビットの TMEM バッファの場合、 `TCol` 沿いに 1 要素を進めると 32 ビットのハードウェアコルに対応します。 8 ビットまたは 16 ビットバッファの場合、複数の隣接要素が同じハードウェアコルにパッケージ化されます。スケールファクターの例では後述が詳細に説明します。

## tilelayout

`TileLayout` は TIRx における主要なアフィン layout オブジェクトで、通常は次のように表記されます。

```python
TileLayout(S[shape : strides])
```

`S[...]` シャード仕様です。これは一連のイターエクステントとストライドを提供し、論理 tile が指定された軸上の基本的な物理的位置にどのようにマッピングするかを決定します。

同じ値を複数の物理的な場所に表示する必要がある場合は、レプリカ仕様を追加できます:

```python
TileLayout(S[shape : strides] + R[replica_shape : replica_stride])
```

固定オフセットを追加することもできます:

```python
TileLayout(S[shape : strides] + R[replica_shape : replica_stride] + offset)
```

API 内で、各イッターは三つ組です:

```text
(extent, stride, axis)
```

`extent` はイターが含まれる位置の数を示し、 `stride` は前進する一歩ごとにどれだけの動きが起こるかを示し、 `axis` は移動がどの物理軸上にあるかを示します。

### シャード

シャードは `S[...]` によって構築されています。 論理インデックスを 1 つ以上の ITER に分割し、基礎となる物理座標を生成します。 前の `frag` には 4 つのシャードイターが含まれており、 `8`、 `2`、 `4`、 `2` の拡張があります。 対応するストライドは座標を `laneid`、 `warpid`、さらに `laneid`、デフォルトの直線軸 `m` にマッピングします。

これは今も標準的な Shape-Stride ルールですが、各ストライドは明確な名前付き軸に属し、同じ線形アドレスにすべてが蓄積されるわけではありません。

### レプリカ

レプリカは `R[...]` によって構築され、同じ論理要素の追加物理的コピーを記述するために使われます。 レプリカイッターは論理インデックスに依存せず、物理空間で追加のオフセットを列挙します。

例えば:

```python
R[2 : 4@warpid]
```

`warpid` 軸に沿って 2 枚のコピーを配置し、その間に 4 つの warp を間隔で配置することを示します。

GPU ハードウェアはしばしば同じデータを複数の warp、レーン、ストレージ領域にブロードキャストする必要があります。 レプリカはこの挙動を「1 つの論理データポイントが複数の物理座標に対応する」と直接表現しています。

### オフセット

オフセットはすべてのマッピング結果に追加されます。 以下の集合の式では、 `O` と表されます。

例えば:

```python
5@warpid
```

layout 全体が `warpid` 軸に沿って 5 ポジション移動したことを表しています。

オフセットは tile の開始座標を指定するためや、同じハードウェアリソース内の異なるエリアに複数の tile を配置するために使用できます。

### 3 つの部分を組み合わせる

論理座標 `x` では、シャードによって生成される基底座標を `D(x)` とします。 `TileLayout` 固定オフセットを追加し、レプリカイタに基づいて追加位置を列挙します:

```text
L(x) = { D(x) + r + O | r in R }
```

ここで、 `r` はレプリカイテによって列挙されるオフセットを表します。 レプリカがなければ、 `R` はゼロのオフセットのみを含むとみなすことができ、集合には座標が 1 つだけとなります。 レプリカが存在する場合、コレクションには各コピーの所在が含まれます。 現在、 `layout.apply()` は基本座標として `D(x)+O` のみを計算し、 `R` を列挙していません。 レプリカ ITER は `layout.replica` に保存され、その layout を使った tile 操作で処理されます。

TIRx の完全な構文は以下の通りです。

```python
layout = TileLayout(
  S[(8, 2, 4, 2) : (4@laneid, 1@warpid, 1@laneid, 1)]
  + R[2 : 4@warpid]
  + 5@warpid
)
```

左から右へ読みます: `S[...]` 論理 tile を置き、 `R[...]` 4 つの warp 位置に 2 枚目のコピーを追加し、 `5@warpid` すべての位置を全体で移動します。5.

すでにシャード、レプリカ、オフセットオブジェクトを直接構築している場合は、以下も使用できます:

```python
TileLayout.from_iters(shard, replica, offset)
```

通常の kernel コードは、layout の形状、歩幅、軸を直接表示できるため、より一般的に `S[...]` や `R[...]` を使用します。

## 命名軸

layout の軸は匿名の次元ではなく、各名前はハードウェアまたはコンパイラの layout 座標を表します。 以下はこの章で遭遇したいくつかの斧のセットです。

| 軸 | 意味 |
|---|---|
| `bx`, `by`, `bz` | grid 内の CTA の座標 |
| `cbx`, `cby`, `cbz` | cluster 内の CTA の座標 |
| `tx` | CTA 内のスレッドの座標 |
| `warpid`, `laneid` | warp ID と warp 内のスレッドのレーン ID です |
| `wgid`, `tid_in_wg`, `wid_in_wg` | warpgroup ID や、warpgroup 内のスレッドや warp の位置 |
| `m` | デフォルトの線形物理軸; 対応するストレージの種類はバッファ scope によって決まります |
| `TLane`, `TCol` | TMEM のレーン方向とコル方向 |

Axis の名前自体も layout の一部です。 整数値が同じでも、異なる軸にあることはハードウェアの位置が異なることを示します。 例えば、 `1@tx` と `1@tid_in_wg` は意味が異なり、 `1@laneid` は `1@TLane` ではありません。 `TCol` ストライドは依然としてバッファ要素で測定されます。 要素幅が 32 ビットの場合にのみ、ハードウェアのコルと 1 対 1 対応します。

## 前方マッピング

`apply()` 論理座標から始めて、シャードとオフセットに対応する基本的な物理座標を計算します。 3 種類の入力タイプをサポートしています:

```python
layout.apply(linear_coord)
layout.apply(*shard_coord)
layout.apply(*logical_coord, shape=input_shape)
```

第三の形式は計算過程を最もよく示します。 論理座標を次のようにします。

```text
x = (x0, x1, ..., xr-1)
```

対応する論理形状は次の通りです:

```text
(S0, S1, ..., Sr-1)
```

まず、論理座標を行メジャー順に平坦化します。

```text
flat = x0 * S1 * S2 * ... * Sr-1
     + x1 * S2 * ... * Sr-1
     + ...
     + xr-2 * Sr-1
     + xr-1
```

次に、シャードの範囲に応じて:

```text
(e0, e1, ..., en-1)
```

`flat` をコンポーネントに分けましょう:

```text
(c0, c1, ..., cn-1)
```

`k` 番目のシャードの歩幅が `sk` で軸が `ak` であれば、物理座標に対する `ck` の寄与は次の通りです:

```text
ck * sk @ ak
```

同じ軸からの寄与を合計し、最後に固定オフセットを加えます。 `apply()` 返された座標辞書はこのステップから得られた結果です。

残りの 2 つの形式は中央から計算されます。 `layout.apply(linear_coord)` すでにフラット化されたインデックスを直接受信します。 `layout.apply(*shard_coord)` は各シャードイタの座標を直接受け取るため、フラッテンやスプリットはもはや実行されません。 `shape=input_shape` を用いる場合、論理形状の次元性と分解はシャードの範囲と同じである必要はありませんが、フラット化後のインデックスがシャードで表される論理範囲を超えていなければよいのです。

`apply()` レプリカを列挙しないでください。 完全な layout 内のレプリカイタはベース座標以外に追加の位置を加えますが、この情報は `layout.replica` に保存され、実際に layout を利用する tile 操作で処理されます。

次に、前のシャード、レプリカ、オフセットからの `layout` を詳細に計算します。 入力座標を tile `(8, 16)` `(1, 3)` として解釈します:

```python
layout.apply(1, 3, shape=[8, 16])

# {"laneid": 5, "warpid": 5, "m": 1}
```

この結果は 3 つのステップで得られます。 まず、 `(1, 3)` `(8, 16)` の行長順に従ったフラット指数 `19` になります。 次に、シャードの拡張 `19` `(8, 2, 4, 2)` 以下に分割します。

```text
(c0, c1, c2, c3) = (1, 0, 1, 1)
```

各成分にそれぞれの歩幅を掛け合わせると、基座標は `laneid=5`、 `warpid=0`、 `m=1` となります。 最後に、 `5@warpid` を加えて返り値の `warpid=5` を得ます。

`apply()` はレプリカを列挙しないため、返却値はこの基底位置のみを含みます。 現在の layout の `R[2 : 4@warpid]` では、その layout を使って `warpid=5` と `warpid=9` の 2 つの物理的な場所を扱う tile 操作も可能です。

`(8, 16)` tile 全体に対する基底写像は次の通りです:

```text
laneid = 4 * i + (floor(j / 2) mod 4)
warpid = floor(j / 8) + 5
m      = j mod 2
```

レプリカはその後、 `warpid` に `0` または `4` を追加します。 そのため、シャードとオフセットは tile を warp 5 と 6 に、レプリカは warp 9 と 10 にコピーを配置しました。

## 例: ブラックウェル tensor メモリ

ネームラインはストレージ座標を表すこともあります。 TMEM はハードウェアのレーン座標とコル座標を使用し、それぞれ `TLane` と `TCol` を TIRx layout で書き込みます。

以下の layout を考えてみましょう。

```python
layout = TileLayout(
  S[(2, 128, 112) : (112@TCol, 1@TLane, 1@TCol)]
)
```

論理 tile の形状とシャードの範囲は `(2, 128, 112)` されるため、分割後の 3 つのコンポーネントが論理座標そのものです。 元素 `(a, l, c)` について:

```text
TLane = l
TCol  = 112 * a + c
```

このトレイルは 128 の面積と歩幅 `1@TLane` 128 列の TMEM レーンを埋めていました。 他の 2 つの `TCol` イテーターは合計で 224 の `TCol` 場所をカバーしています。

```text
TCol in [0, 224)
```

TMEM の配置では、各次元が 2 のべき乗である必要はありません。 ここでは、拡張 112 の列イターを直接使用できます。 このような 2 つの領域は合計 224 `TCol` 位置をカバーするため、128 の範囲を完成させる必要はありません。 実際の kernel も積極的にそのようなサイズを選択することがあります。例えば、ブロックスケールの FP8 GEMM は、2 つの accumulator ステージとスケールファクターごとに TMEM を共同で割り当てることができ、単一の accumulatortile で 256 列を埋める必要はありません。

## スケールファクターの配置

前述の accumulator 配置は 1 対 1 のマッピングで、各論理 accumulator 要素は 1 つの TMEM 座標のみに対応します。 ブロックスケール型 MMA では、複数の warp ウィンドウで同じ論理スケールファクターが見える必要があるため、レプリケーションが用いられます。 まず、完全なスケールファクターの配置で繰り返し現れる `32×sf_per_mma` 原子を見てみましょう。

```python
scale = TileLayout(
  S[(32, sf_per_mma) : (1@TLane, 1@TCol)]
  + R[4 : 32@TLane]
)
```

論理スケール座標 `(r, s)` に対して、シャードはまず次のように示します:

```text
TLane = r
TCol  = s
```

8 ビットスケールファクターバッファの場合、ここでの `TCol` 座標もバッファ要素で測定されます。 4 つの連続した要素位置は 32 ビットハードウェアのコルに詰め込まれます。 ハードウェアの Col 番号とバイト位置はそれぞれ `s//4` と `s%4` です。

レプリカは `TLane` 軸 32 に 4 つのコピーを作成し、ストライドとして使います。

```text
TLane = r + 32 * q, where q in {0, 1, 2, 3}
TCol  = s
```

したがって、この 32 列のグループは `0-31`、 `32-63`、 `64-95`、 `96-127` レーンに同時に現れます。 各 warp は 32 レーンの TMEM ウィンドウに対応し、同じスケールファクターセットにアクセスできます。 完全な layout には M 方向と K スケールブロック方向の外側のイターも含まれています。 ここで、atom は MMA が読み取りた局所的なパターンを一度だけ記述する役割を担います。 具体的なハードウェアデータパスについては[Tensor Core データ layout の進化](/ja/gpupro/tensor-core-data-layouts/)を参照してください。

accumulator とスケールファクターは依然として同じ `TileLayout` モデルを使用しています。前者は通常 TMEM 内の基底座標の集合であり、後者は同じ `TLane` 空間に複製を加え `TCol` ます。

## 共通 layout 構成器

実際には、kernel は通常すべてのハードウェア layout を手動で書き込む必要はありません。 TIRx は共通パターンのコンストラクタを提供します。

```python
tmem_datapath_layout(datapath, rows, cols)
```

`tcgen05.mma` に書かれた TMEM accumulatorlayout を返します。 `datapath` 行マッピング方式を選択します。 例えば、 `"D"` 行から `M=128` まで直接マッピングする場合、 `"F"` は複数のレーンエリアに分散して配置 `M=64` されます。

```python
tcgen05_atom_layout(instr_shape, tensor_shape, dtype)
```

`tcgen05.ld` またはデータ移動形状に対応するレジスタ tile の配置 `tcgen05.st` 返します。 `instr_shape` は `"32x32b"`、 `"16x64b"`、 `"16x128b"` などの文字列で、 `tensor_shape` と `dtype` は共同で対応する反復係数を決定します。

このオブジェクトは warpgroup のスレッドレジスタに分散された tile を表します。 TMEM と局所断片間の `Tx.wg.copy_async` に用いられる場合、ローリングはマッチする warp 集合 `tcgen05.ld` を選択するか、それに応じて `tcgen05.st` できます。 各 warp はそれぞれ 32 レーンの TMEM パーティションを処理します。

```python
wg_local_layout(cols, rows=128)
```

warpgroup-ローカルレジスタ tile を返します。 論理行を `tid_in_wg` に、同じ行内の列をそのスレッドのローカルな `m` 軸にマッピングします。 デフォルトの `rows=128` を使うと、各スレッドは 1 行を保持します。

これらの構成体は同じイタリングと名前付き軸モデルを用いて依然として `TileLayout` を返します。 コンストラクタは kernel の共通ハードウェアマッピングのみを生成します。

## SwizzleLayout と ComposeLayout

`TileLayout` はアフィン layout で、ネーミング軸上のストライド、複製、オフセットを記述し、レジスタ断片、TMEM tile、スケールファクター配置の表現に適しています。

共有メモリスウィズルはアフィン変換ではありません。 XOR によって線形共有メモリアドレスを再配置し、各バンクへの要素配置を変えます。 したがって、TIRx はそれを表現するために別のオブジェクトを使用します。

```python
SwizzleLayout(...)
```

スウィズルだけを記述するなら、 `SwizzleLayout` を直接バッファに割り当てることができます。 アフィン tile マッピングの上にスウィズルを重ねたい場合は、 `ComposeLayout` を使います。

```python
ComposeLayout(swizzle, tile)
```

ここでは、 `tile` はデフォルトの `m` 軸上で線形アドレスのみを生成する必要があります。 計算中、tilelayout はまずこのアドレスを取得し、次にスウィズルし、最後に再配置します。 これにより、アフィン形状-歩幅写像や非アフィンの XOR 変換が単独で明確なまま維持されます。

## なぜ Swizzle が必要なのか

[データ layout とその表記法](/ja/gpupro/data-layout/)は共有メモリバンクの競合と XOR スウィズルを導入しました。 ここでは、API 内でどのように表現されているかに焦点を当てます。

float16 tile `(8, 64)` 行メジャーを考えてみましょう:

```python
TileLayout(S[(8, 64) : (64@m, 1@m)])
```

論理要素 `(i, j)` の線形要素アドレスは次の通りです:

```text
m = 64 * i + j
```

各行は 64 個の float、つまり 128 バイトで構成されています。 固定 `j` で列に沿って読み込むと、各行が 128 バイト変わり、複数の訪問が同じバンクグループに重複することもあります。

Swizzle はアドレスの低い部分を高い行ビットに依存させるため、元々同じ銀行に属していた列アクセスが複数のバンクに分散されます。

## スウィズル変換

`SwizzleLayout` 3 つの整数パラメータで制御されます:

```text
per_element = M
swizzle_len = B
atom_len    = S
```

これら 3 つのパラメータはバイトではなくビット数です。 次の式は線形要素アドレス `m` を入力として取ります。

`M` は保持すべきビット数、XOR に関わるビットフィールド幅 `B`、2 ビットフィールド間の距離 `S` を示します。 まず、 `m` の低 `M` ビットを保持し、隣接する要素の小さなグループが連続したままにします。 残りの高値を右にシフトすると次のようになります:

```text
x = m >> M
```

次に、位置 `[S, S+B)` `x` の XOR を `[0, B)` に移動し、最後に以前に予約されていた低 `M` ビットが復元されます。

```text
mask = (1 << B) - 1

low  = m & ((1 << M) - 1)
x    = m >> M
x2   = x ^ ((x >> S) & mask)

addr = (x2 << M) | low
```

正当なスウィズルには `S >= B` が必要です。

この変換は tile に含まれる論理要素を変えず、共有メモリ内の物理アドレスのみを変えます。 その後の MMA 読み取りでも同じロジック tile が使われていますが、対応する銀行アクセスパターンが変わっています。

## Swizzle パラメータを選択します

実際には、スウィズルパラメータは通常、データ型と共有メモリスウィズルモードで決定されます。 一般的なモデルには 32 バイト、64 バイト、128 バイトのスウィズルがあります。

`per_element` ベクトル群内の要素が連続性を保つために、どれだけの要素アドレスの低点を保持するかを決定します。 float16 の場合、16 バイトベクトルは 8 つの要素を含むので、次のようになります。

```text
M = log2(8) = 3
```

128 バイトの Swizzle 使用例:

```python
SwizzleLayout(per_element=3, swizzle_len=3, atom_len=3)
```

ここで 128 バイトは Swizzle Atom の各行の幅を指します。 完全な原子は 8 行から成ります。これらのパラメータは各 16 バイトベクトル群を連続に保ち、より高いアドレスビットを並べ替え、列アクセスのバンクパターンを分散させることができます。

正則核はこれらのパラメータを繰り返し手動で導出する必要はありません。 データ型とディスクリプタモードは通常、特定の構成を決定する。 kernel は TIRx layout、TMA ディスクリプタ、MMA が同じ共有メモリ構成を使用していることを確認する必要があります。

スウィズルされた共有メモリ割り当ては次のように書けます:

```python
tile = TileLayout(S[(8, 64) : (64@m, 1@m)])
swizzle = SwizzleLayout(per_element=3, swizzle_len=3, atom_len=3)

layout = ComposeLayout(swizzle, tile)
```

共有メモリバッファへの最終的なバインディングは結合 `layout` です。 次に、この layout を使って実際の住所マッピングを確認しましょう。

## 例: 128B Swizzle を `(8, 64)` float16 tile に適用する

上記の 128 バイトの Swizzle を使い続けてください。 前の行メジャーtile は線形要素アドレスを使用しています:

```text
m = 64 * i + j
```

注文:

```text
q = floor(j / 8)
r = j mod 8
```

前のスウィズル式に代入すると、物理要素アドレスは次のようになります。

```text
addr = 64 * i + 8 * (q xor i) + r
```

例として列 `j=0` を挙げると、この時点で `q=0` `r=0`:

```text
addr = 72 * i
```

共有メモリは 32 バンクで構成され、各バンクワードは 4 バイトです。 float16 の場合:

```text
bank = floor(addr / 2) mod 32
```

したがって、8 行は次の通りに対応します:

```text
i = 0: bank 0
i = 1: bank 4
i = 2: bank 8
i = 3: bank 12
i = 4: bank 16
i = 5: bank 20
i = 6: bank 24
i = 7: bank 28
```

今回は、8 つの異なる銀行を使ったコラムアクセスが行われました。 スウィズルが使われない場合は、同じ列内のアドレスが `m=64*i` されるため、次のようになります。

```text
bank = floor(64 * i / 2) mod 32 = 0
```

8 本のラインすべてがバンク 0 に到達します。 Swizzle は論理 tile を変更しず、要素の物理アドレスのみを変更し、このアクセスモードが同じバンクに集中しないようにしました。

上記の導出は、この float16 列アクセスが 8 つの銀行に分散していることを示しています。 他のアクセスが競合フリーかどうかは、データ型、各アクセスの幅、ハードウェア命令が使用するアクセス形状にも依存します。 この章の冒頭にある相互作用図では、データ型とスウィズルモードを切り替えることで、異なる組み合わせのアドレスマッピングを直接比較できます。

すでにコンストラクターでカバーされている `tcgen05` layout については、 `tmem_datapath_layout` や `tcgen05_atom_layout` などのヘルパーを直接使うことができます。 他のアフィン配置では、 `S[...]`、 `R[...]`、オフセット表現が依然として用いられます。 `TileLayout` を問い合わせる際、 `apply()` 論理要素の基本的な物理座標のみを計算し、レプリカを列挙しません。 共有メモリースウィズルは `SwizzleLayout` で表されます。 線形 `m` アドレスしか出さない tilelayout に重ねたい場合は `ComposeLayout(swizzle, tile)` を使いましょう。
