## 概要

大規模言語モデル（LLM）は関数呼び出しを使って外部ツールやデータソースに接続する。しかし現在の LLM 関数呼び出しは本質的に同期的であり、各呼び出しが LLM 推論をブロックするため、 LLM の動作と関数の同時実行が制限される。本稿では非同期 LLM 関数呼び出しのシステム AsyncLM を提案する。AsyncLM は LLM が関数呼び出しを同時に生成・実行できるようにして LLM の動作効率を高める。各呼び出しの完了を待つ代わりに、 AsyncLM は関数呼び出しが返ると実行中の LLM に非同期で通知する割り込み機構を導入する。関数呼び出しと割り込みのインコンテキストプロトコルを設計し、 LLM を割り込み意味論に適応させる微調整戦略を提供し、これらの機構を LLM 推論処理上で効率的に実装する。Berkeley function calling leaderboard（BFCL）の一連のベンチマークタスクで、 AsyncLM は同期的な関数呼び出しと比較してエンドツーエンドのタスク完了レイテンシを 1.6$\times$-5.4$\times$ に削減できることを示す。さらに、割り込み機構を拡張して新しい人間-LLM または LLM-LLM インタラクションを可能にする方法を議論する。

## 1 はじめに

関数呼び出し機能により、大規模言語モデル（LLM）は天気予報や計算機などの外部データソースやツールにアクセスできる。商用およびオープンソースの LLM はこの機能を統合しており [Sch24, Pat23b]、動的環境で動作する自律 AI エージェント [Wan24k] から、記号推論と LLM を組み合わせて複雑な問題を解くニューロシンボリックシステム [Tri24] まで、多様なアプリケーションに新たな可能性を開いている。

LLM の関数呼び出しは同期的であり、 LLM と関数呼び出しエグゼキュータが交互に呼び出しを生成・実行する。実装は簡単だが、この方式はリソース効率も応答性も高くない。各関数呼び出しは、リソース消費の大きい LLM 推論を関数が返るまでブロックする。エグゼキュータから見ると、すべての関数呼び出しを LLM が開始した順番に完了しなければならず、これが並行性を制限する。タスクの複雑さと関数の数が増えるほど、こうした非効率は悪化する [Zah24]。

<span id="figure-01"></span>

![同期関数呼び出しと非同期関数呼び出しのタイムライン](../../papers/async-llm-function-calling/figure-01.png)

**図 1. 同期関数呼び出しと非同期関数呼び出し。** 非同期関数呼び出しでは、関数呼び出しがバックグラウンドで実行されている間も LLM が独立タスクの token 生成を続けられるため、 LLM の動作効率が向上する。

これらの課題への取り組みとして、関数呼び出しを並列化するコンパイラ [Kim24a]、順次呼び出しを融合してオーバーヘッドを削減する方法 [Sin24a]、簡潔な呼び出し構文 [Che23c]、関数呼び出し向け LLM サービングシステムの最適化 [Abh24, Gao24b, Xu24b] などが研究されてきた。これらは関数実行時間や関数呼び出し数の削減に役立つが（[第 2 節](#section-02)）、関数呼び出しが同期的であるという制約、たとえば LLM が関数呼び出しエグゼキュータの完了を待つことに根本的に制限される。

この制約を克服するため、 LLM と関数呼び出しエグゼキュータの間の*非同期*インタラクションを可能にするシステム AsyncLM を提案する。AsyncLM では LLM とエグゼキュータが互いをブロックせず独立に動作する。これは、関数呼び出しの完了のようなイベントが LLM token 生成ストリームのような主プログラムフローから独立して発生する、非同期プログラミングパラダイムに着想を得ている。[図 1](#figure-01) に概念を示す。

AsyncLM の中心的な機構は*割り込み可能な* LLM デコーディングである。AsyncLM では関数呼び出しはノンブロッキングであり、関数呼び出しが返るとエグゼキュータが*割り込み token* を LLM の token 生成ストリームに注入して非同期に通知する。この概念は単純だが、 AsyncLM は LLM とエグゼキュータを調整する際に二つの課題を解決しなければならない。（i）割り込み token のタイミングを慎重に選び、 LLM が生成中の他タスクや関数呼び出しへの干渉を避ける必要がある。例えば別の関数呼び出しの引数の途中に割り込みを注入すると、進行中の関数呼び出し生成と返された関数呼び出しの双方が壊れる可能性がある。（ii） LLM は注入された割り込みを正しく処理しなければならない。このような割り込みはモデルが学習した会話パターンには従わないからである。

これらの課題に対処するため、非同期関数呼び出しのインターフェースと LLM 微調整戦略を共同設計する。（i）関数呼び出しと割り込みを表す token 効率のよいドメイン固有言語 CML を開発する（[第 3 節](#section-03)）。AsyncLM は token 生成中に CML 構文を検出して関数呼び出しの開始と終了を識別し、それに応じて割り込みを遅延させる。CML は割り込み構文に必要なコンテキストを埋め込むことで、割り込み後に LLM が処理を再開することも助ける。（ii） LLM を微調整し、非同期関数呼び出しの生成、割り込み処理からの再開、関数呼び出しの返りを待つために一時停止すべきときの LLM サービングシステムへの通知を教える（[第 4 節](#section-04)）。この三つの場合はすべて CML をインターフェースとして使う。さらに LLM が待機を選ぶと、 AsyncLM はブロッキング状態を管理する最も効率的な戦略、例えば KV cache の破棄、スワップ、保持を決定する。

AsyncLM には同期関数呼び出しに対して二つの利点がある。第一に、 AsyncLM は関数の生成と実行を重ね合わせて実行時間を削減する。この性質により、最悪の場合でも AsyncLM は並列実行を伴う同期関数呼び出しと少なくとも同じ速さになる（[第 6.3 節](#section-06-03)）。第二に、 AsyncLM は将来の関数呼び出しの依存グラフを事前に知らなくても自動並列性を実現する。例えば、数学系譜 API を使って「Leonhard Euler が自分の学術的祖先かどうか教えて」というタスクと、 `find_advisors(str)`$\rightarrow$`list[str]` という API 定義が与えられたとする。AsyncLM は並列深さ優先探索のように `find_advisors` を再帰的かつ並列に呼び出せる。対照的に、同期関数呼び出し方式でこのようなタスクを効率よく扱うのは難しい。事前に並列化可能な関数呼び出しのリストを決める必要があるからである（[第 2 節](#section-02)）。

Llama 3 モデル [Dub24] 上に AsyncLM を実装し、入力プロンプト中の CML 例と指示でモデルを導くインコンテキストプロンプティングによって GPT-4o の微調整をエミュレートする（[第 5 節](#section-05)）。両モデルを Berkeley Function Calling Leaderboard（BFCL）の関数呼び出しタスクスイートで評価する [Yan24d]（[第 6 節](#section-06)）。ベンチマーク比較では、 AsyncLM は同期順次関数呼び出しに対してエンドツーエンドのタスク完了を最大 1.6$\times$-5.4$\times$ 高速化し、同期並列関数呼び出しに対して最大 2.1$\times$ のスピードアップを達成する。AsyncLM が関数呼び出しの正確性に与える影響も評価し、微調整した Llama モデルでは同期関数呼び出しと同じ水準の正確性を保つことを示す。特に GPT-4o は明示的な微調整なしで非同期関数呼び出しを扱える。最後に、導入した割り込み機構を割り込み可能な LLM アシスタントなど、人間-LLM や LLM-LLM のインタラクションを含む新しい AI アプリケーションに利用する可能性を議論する。

![同期・並列・非同期の LLM-エグゼキュータ相互作用の比較](../../papers/async-llm-function-calling/figure-02.png)

**図 2. LLM-エグゼキュータ相互作用の比較。** 並列関数呼び出しは関数呼び出しを先に生成して並列実行することでエンドツーエンドの実行時間を短縮するが、 LLM はすべての呼び出しが完了するまで待つ必要がある。非同期関数呼び出しは、関数呼び出しがバックグラウンドで実行されている間に LLM が token を生成できるようにすることでこの制約を克服する。**タスク：** *「webpage.html を event.pdf に要約し、 style.txt に従った体裁で attendee.xls の参加者にメールし、ディレクトリに記載がなければ学科長を CC に入れよ。」*

## 2 背景と関連研究

LLM をコード実行で拡張する概念 [Mia23] は広く研究されており、検索拡張生成 [Kha22, Yao22b]、自律エージェント [Hua24c, Wan24k]、ニューロシンボリック問題解決 [Pan23, Tri24] などで検討されている。

**関数呼び出しの生成を学習する。** LLM が外部システムと対話する最も一般的な方法はツールまたは関数呼び出し [Sch24, She23c] であり、モデルが外部エグゼキュータ（API サーバーやコードインタープリタなど）への呼び出しを自律的に生成する。この能力は多様なタスクデータセットでの微調整 [Pat23b] またはインコンテキスト指示 [Lia24] によって洗練される。引数を含む関数の説明は、多くの場合 JSON のような構造化プロンプト形式で与えられる。我々の方法はこのパラダイムを非同期関数呼び出しへ拡張し、 LLM に（1）呼び出し生成時の実行時間を考慮させ、（2）割り込み意味論を使って後続の呼び出しを決定させる。

**効率的な LLM 関数呼び出し。** 関数呼び出しにおける主要な課題は、リソース利用を高めてレイテンシを下げる効率最適化である。関数呼び出し処理を改善するため、さまざまな最適化戦略が研究されてきた。例えば並列関数呼び出し [Kim24a, Ope23d] は同時に実行できる呼び出しを LLM にまとめさせ、外部コンパイラがバッチを並列実行向けに最適化できるようにする。順次関数呼び出しの最適化には、関数呼び出し融合 [Sin24a]、キャッシュ [Sin24b]、呼び出し表現の簡潔な構文 [Che23c]、関数呼び出しの部分実行 [Xu24b] などがあり、一つのコードブロックの生成と実行を重ね合わせる。

**同期インタラクションの限界。** 現在の LLM は同期関数呼び出しを行う。生成と実行が交互になるため、無状態な LLM 推論では関数呼び出しごとに新しいセッションが必要となり、余分なオーバーヘッドが生じる。待機中の KV cache を効率よく管理する研究 [Abh24, Yu25b, Gao24b] はこの問題から動機づけられた。さらに重要なのは、同期関数呼び出しがリソース利用を根本的に制限する点である。token 生成と関数実行を同時に行えないからである。ReWOO [Xu23b] は LLM に推論と観測を分離するようプロンプトで指示し、複数の関数呼び出しを一度に実行してこの制限に対処する。我々の研究は概念的に ReWOO と整合するが、 LLM の推論戦略には依存しないため、より広く適用できる。

**我々のアプローチ。** AsyncLM は非同期実行によって同期関数呼び出しの限界に対処する。[図 2](#figure-02) は同期方式に対する非同期関数呼び出しの利点を示す。関数並列化の最適化 [Kim24a, Ope23d] はエンドツーエンドの実行時間を短縮するが、 LLM は関数呼び出しの完了を待つためリソースがアイドルになる。非同期関数呼び出しは、進行中の関数呼び出しと並行して LLM が独立タスクの token を生成し続けることでこのボトルネックをなくす。非同期呼び出しを支えるため、 AsyncLM は関数呼び出しが返ったときに実行中の LLM へ非同期で通知する機構を導入し、 LLM を微調整して割り込みを理解し並行実行を活用させる。

AsyncLM は二つの主要なイノベーションを中心に構成される。第一に、ドメイン固有言語（CML）で非同期関数呼び出しと割り込みを記述し、必要なコンテキストを埋め込んで統合する（[第 3 節](#section-03)）。第二に、微調整戦略で LLM に非同期イベントへの応答、並行関数呼び出しの生成、先行呼び出しの完了を待つために一時停止すべきときのサービングシステムへの通知を学習させる（[第 4 節](#section-04)）。これにより関数呼び出しの依存関係を正しく扱う。これらのコンポーネントを AsyncLM の LLM サービングシステムに実装し、 token 生成を監視し、エグゼキュータ上の関数呼び出しをスケジュールし、必要に応じて割り込みを注入または生成を一時停止して token ストリームを管理する（[第 5 節](#section-05)）。

## 3 CML による非同期インタラクションの表現

<span id="figure-03"></span>

![CML における非同期関数実行ワークフロー](../../papers/async-llm-function-calling/figure-03.png)

**図 3. 非同期関数実行ワークフロー。** LLM は CML 形式で関数呼び出しを生成し、それをリアルタイムに監視してコードエグゼキュータへバックグラウンドで送る。関数呼び出しが完了すると、エグゼキュータは実行結果とともに割り込みを挿入して LLM に非同期で通知する。

非同期関数呼び出しと割り込みを表現する、 *Context Markup Language*（CML）という単純なドメイン固有言語を定義する。CML は LLM とエグゼキュータのインターフェースとして機能し、構文によって各コンポーネントがこのインターフェースを通じて対話する際に必要なコンテキストを提供できるようにする。例えば LLM は CML で関数呼び出しを生成してエグゼキュータに通知し、エグゼキュータは CML の割り込み token を挿入して完了を知らせる。[図 3](#figure-03) にその例を示す。

CML は `[CALL]`、 `[INTR]`、 `[TRAP]`、 `[END]`、 `[HEAD]` という最小限の専用 token を使う。`[CALL]`、 `[INTR]`、 `[TRAP]` は*制御ブロック*を開始し、それぞれ関数呼び出し（[第 3.1 節](#section-03-01)）、割り込み（[第 3.2 節](#section-03-02)）、特殊な割り込みであるトラップを表す。`[END]` は制御ブロックの終端を示し、 `[HEAD]` は関数呼び出し ID などの任意メタデータと関数呼び出し本体を分ける。本節では CML の意味論を定義する。

<span id="section-03-01"></span>

### 3.1 関数呼び出しの開始

AsyncLM では LLM が次の形式で関数呼び出しを開始する：`[CALL] {function call} [END]`。関数呼び出しは、エグゼキュータがサポートする Python コードや JSON 抽象構文木（AST）など、任意の有効な実行可能言語で記述できる。ただし各関数呼び出しブロック内では一つの言語だけを一貫して使う。独立した関数呼び出しは並列実行できるよう別々のブロックに置く。

生成された関数呼び出しは token ストリームをブロックせずに実行を開始するため、暗黙の並列性が得られる。例えば[図 3](#figure-03)のように LLM が二つの関数呼び出し（`search_nearby` と `put`）を生成すると、エグゼキュータはそれぞれを別のワーカーで処理し、関数呼び出しの生成と実行をパイプライン化できる。この重なりによってレイテンシが減少し、 `search_nearby` の実行とテキストメッセージ生成を同時に行える。関数呼び出しは依存順に生成され、依存する呼び出しが正しい順序で実行される。例えば花屋を検索してメッセージを作成し終えた後にだけ、 LLM は `text` 関数呼び出しを生成できる。

**割り込み用 ID の割り当て。** 後続の呼び出しや推論で関数結果を参照する必要がある場合、 LLM は関数ヘッダに ID を含められる（例：`[CALL] job1 [HEAD] {function call} [END]`）。ここで `job1` は一意な ID として機能する。衝突を避けるため、 LLM は Python 変数の命名規則に従って ID を生成する。ID はセッション全体で一意でなければならない。プロトタイプでは実装していないが、一意性検査を構文検証の一部として含められる（[第 5.1 節](#section-05-01)）。

<span id="section-03-02"></span>

### 3.2 割り込みのトリガー

エグゼキュータが登録済み ID を持つ関数呼び出しを完了すると、 token ストリームの末尾（つまり LLM コンテキスト）に割り込みブロックを挿入して LLM に非同期で通知する。割り込みブロックが追加された後、 token 生成が再開する。割り込みブロックの形式は `[INTR] {id} [HEAD] {value} [END]` であり、 `{id}` は対応する `[CALL]` ブロックの ID（前の例の `job1` など）と一致する。`{value}` には関数の出力やエラーメッセージなど、エグゼキュータの結果が入る。

**クリティカルセクション。** 割り込みは LLM の token 生成フローを変更するため、割り込み後のコンテキストが CML 構文に従うことを保証する必要がある。例えば関数呼び出しの生成中に割り込みブロックを挿入すると、生成された token が論理的に不正となり CML 構文に違反する可能性がある。これを防ぐため、 AsyncLM は特定の token 生成期間中は割り込みを一時的に無効にする。これは OS が別の割り込みを処理している間に低優先度割り込みを遅延させる方法に着想を得ている。割り込みマネージャに実装された*クリティカルセクション*フラグ（[第 5.3 節](#section-05-03)）が、エグゼキュータが割り込みを挿入できるかを決める。関数呼び出しブロックの生成中はフラグを `false` にし、 LLM がブロックを抜けると `true` に戻す。クリティカルセクション中に発生した割り込みはキューに入り、フラグが `true` になったときに挿入される。

**割り込みを待つ。** 同期関数呼び出しでは、 LLM は関数呼び出し後に token 生成を停止し、呼び出しの完了を待つ。対照的に非同期関数呼び出しでは、 LLM は待たずに他タスクの token 生成を続けられる。しかしタスク間に依存関係がある場合、 LLM は関数結果を待つため一時停止しなければならないことがある。標準の `[EOS]` token ではこの目的に不十分である。token 生成が完了してリソースを解放できるのか、関数結果が到着するまで一時停止しているだけなのかを表せないからである。

この曖昧さを解決するため、 AsyncLM は自己開始型の割り込みである*トラップ*を導入し、 token 生成をいつ停止するかを LLM サービングシステムに通知する（[第 5.4 節](#section-05-04)）。各トラップは `[TRAP][END]` という単純な構造を持つ。トラップは非同期関数呼び出しの明示的な境界を作り、非同期関数処理用に LLM を微調整する訓練サンプルの生成に役立つ（[第 4 節](#section-04)）。また、サービングシステムの最適化機会も提供する（[第 5 節](#section-05)）。

<span id="section-04"></span>

## 4 割り込み処理の学習

CML を使って（i）非同期関数呼び出しとトラップを生成し、（ii）先行する関数呼び出しの結果を届ける割り込みを処理するよう LLM を訓練する微調整方式を提案する。中心となる考えは、 LLM とエグゼキュータの理想的なインタラクションをモデル化する、シミュレーションされた関数呼び出しと割り込みを含むデータセットを構築することである。公開されている関数呼び出しデータセットからタスク記述と関数定義を抽出し、推定完了時間を加え、プロンプトの一部として JSON 形式で LLM に提示する [Ope23d, Pat23b, Lia24]。簡単のため、各タスクは有限個の関数呼び出しで完了できると仮定する。

<span id="section-04-01"></span>

### 4.1 訓練目標

AsyncLM の微調整の主目的は、タスク依存関係を守り、推定関数実行時間を考慮しつつ、非同期関数呼び出しを効果的に使って総タスク完了時間（makespan）を最小化するよう LLM を訓練することである。具体的には LLM は次の判断を行う必要がある。

**次の関数呼び出しを決める。** LLM はコンテキストに基づいて次に呼ぶ関数を選択する。 [+1] すぐに呼び出せる、すなわち未解決の依存関係がない関数を識別し、最適なものを選ぶ。AsyncLM は Longest-Processing-Time-first（LPT）戦略を使い、準備のできた関数のうち推定実行時間が最も長いものを優先して呼び出す。この方法は関数呼び出しの生成と実行の重なりを最大化してアイドル時間を減らすため、複数の独立関数を呼べる場合に特に有効である。LPT は並列関数呼び出しの状況で最適である（[第 6 節](#section-06)）。

[+1]: ここでいう*コンテキスト*とは、現在 LLM に見えている token 列を指す。

**割り込みを処理する。** コンテキストに割り込みが現れると、 LLM は現在のタスクの token 生成を続けるか、割り込みを処理するかを決めなければならない。例えば完了したタスクの優先度が現在のタスクより低い場合や、それが系列の最後のタスクである場合、 LLM は割り込みを無視してよい。AsyncLM は次の関数呼び出しを決めるときと同じ優先度原則で割り込みを処理する。割り込みによって新たに呼び出せる関数が生じ、その関数が選択肢の中で推定処理時間最長なら、 LLM はそれを次に呼ぶよう訓練される。例えば[図 2](#figure-02)のタスクスケジューリングでは、 ``Read html'' と ``Read xls'' が完了したとき、 LLM は処理時間の長い ``Summarize & save pdf'' を ``Fetch contact'' より先に実行する。

**トラップを生成する。** 将来の割り込みへの依存のため呼び出せる関数がなく、生成すべき他の token もない場合、 LLM は token 生成を一時停止するためトラップを生成しなければならない。

<span id="section-04-02"></span>

### 4.2 訓練サンプルの生成

訓練サンプルを作成するため、マルチターンシナリオを持つ LLM ベンチマークの既存の関数呼び出しトレースを使い、 LLM とエグゼキュータの理想的なインタラクションをシミュレートする [Lu24, Yan24d, Yao24]。

**DAG 生成。** データセットの各サンプルから関数呼び出しの有向非巡回グラフ（DAG）を抽出する Python プログラムを開発した。逐次シナリオでは DAG は線形で、ノードが関数呼び出し、エッジが依存関係を表す。並列シナリオでは DAG が分岐して独立関数呼び出しを表す。マルチターンシナリオは複数の DAG からなる。

**割り込みのシミュレーション。** LPT 戦略を使い、これらの DAG 上で LLM とエグゼキュータのインタラクションをシミュレートする。各シミュレーションでは、特定の関数名への過学習を防ぐため、関数呼び出しに 1 ms から 1 s のランダムな推定実行時間を割り当てる。この推定値は入力プロンプトの一部として LLM に与える。割り込み時刻を決めるため、シミュレーションごとに出力 token あたり時間（TPOT）を 5 ms から 30 ms の範囲でランダムに設定し、生成 token 数を数えて経過時間を追跡する。関数呼び出しが完了すると、実行結果を含む割り込みブロックを挿入する。DAG の全関数が依存関係を待っている場合は、トラップブロックを挿入して次の割り込みを注入する。

<span id="figure-04"></span>

![token モニタ、 エグゼキュータ、 割り込みマネージャ、 トラップハンドラを備えた AsyncLM 推論プロセス](../../papers/async-llm-function-calling/figure-04.png)

**図 4. AsyncLM の LLM 推論プロセスの概要。** LLM は自己回帰的に token を生成する。AsyncLM は token 生成を監視して CML を認識し、認識した CML 構文に基づいて非同期関数呼び出し、割り込み、トラップを管理する追加手順をこのプロセスに加える。1 から 5 までの番号は、関数呼び出しの生成から実行と結果の返却までの論理フローを示す。

## 5 実装

[図 4](#figure-04)に示すように、 LLM の自己回帰 token 生成をインターセプトして AsyncLM を実装する。システムは Python の `transformers` ライブラリで構築される [Wol20]。AsyncLM は token モニタ、エグゼキュータ、割り込みマネージャ、トラップハンドラという四つの主要コンポーネントからなる。本節では各コンポーネントの実装と LLM 推論への変更を説明する。これらの一部はサービングシステムを変更せずクラウド LLM API 上で実装できるが（[第 5.5 節](#section-05-05)）、そのような実装が実用的なのは特定のシナリオに限られる（[第 6.2 節](#section-06-02)）。

<span id="section-05-01"></span>

### 5.1 Token モニタ

token モニタは LLM の token 生成プロセスを監査・制御する。主な機能は（i） token ストリームで関数呼び出しまたはトラップを検出したときにエグゼキュータまたはトラップハンドラへ直ちに通知すること、（ii） CML 構文への準拠を強制することである。LLM の次 token サンプリング過程へのフックとして実装され、次 token の分布を制約して生成 token が有効な CML 構文に従うようにする [Gen23c]。有限状態機械（FSM）で CML 規則を強制し、 `[INTR]` token を LLM が生成するのを阻止する。割り込みは LLM ではなくシステムが注入する必要があるため、これによって「幻覚した」割り込みを防ぐ。各 token のサンプリング後、 token モニタは関数呼び出しまたはトラップを確認し、検出した場合はエグゼキュータ（[第 5.2 節](#section-05-02)）またはトラップハンドラ（[第 5.4 節](#section-05-04)）に直ちに通知する。さらに LLM が割り込み可能な状態かを判定してクリティカルセクションフラグを設定し、生成 token とフラグを割り込みマネージャ（[第 5.3 節](#section-05-03)）に送る。

<span id="section-05-02"></span>

### 5.2 エグゼキュータ

エグゼキュータは LLM が生成した関数呼び出しの実行を管理する。token モニタから、（我々のプロトタイプでは Python 構文で整形された）各関数呼び出しと、将来の割り込みを管理する任意の ID を受け取る。各関数呼び出しは専用ワーカーで実行され、リソースが許せば複数の呼び出しを同時に実行できる。ワーカーは API サーバーやコードインタープリタなどの外部システムと直接やり取りする。関数が完了すると、エグゼキュータは結果と ID を割り込みマネージャに送る（[第 5.3 節](#section-05-03)）。

<span id="section-05-03"></span>

### 5.3 割り込みマネージャ

割り込みマネージャには三つの主な機能がある：（i）割り込みキューの管理、（ii）クリティカルセクションフラグに基づく token 生成プロセスの割り込み可能時点の追跡、（iii） CML 形式の割り込みブロックの token ストリームへの挿入である。エグゼキュータが関数呼び出しを完了すると結果を割り込みキューに追加する。各デコードステップで、割り込みマネージャは token モニタから新しく生成された token とクリティカルセクションフラグを受け取る（[第 5.1 節](#section-05-01)）。プロセスが割り込み可能、つまりクリティカルセクションフラグが立っていない場合、キューにあるすべての割り込みを CML で整形して token 化し、生成 token に追加する。これらの token は次のデコードステップで LLM に処理される。

<span id="section-05-04"></span>

### 5.4 トラップハンドラ

トラップハンドラの目的は、タスク完了レイテンシを増やさず GPU メモリ内のアイドル KV cache 使用量を最小化することである。token モニタがトラップ、つまり token 生成を一時停止する必要を検出すると、現在のコンテキストをトラップハンドラに通知する。トラップハンドラはこの通知に基づき、現在のコンテキストの token 数と次の割り込み完了までの推定時間を考慮して、一時停止中の KV cache 管理戦略を決定する。先行研究は、 KV cache の再計算が token 数に対して二次的にスケールし、ホストメモリへのスワップが線形にスケールすることを示している [Abh24, Gim24]。これらのコストのスケーリング特性に基づき、再計算時間とスワップ時間の両方が推定待ち時間を超える場合は KV cache を GPU メモリに保持する。それ以外では再計算レイテンシが低ければ再計算し、スワップレイテンシが低ければスワップする。理想的なトラップ処理戦略の実例を[第 6.2 節](#section-06-02)で示す。

<span id="section-05-05"></span>

### 5.5 Chat Completion API への実装

AsyncLM の適応性を示すため、サービングシステムを変更せず OpenAI の（ストリーミング） chat completion API を使って実装する。エグゼキュータの実装はそのまま再利用できる。token モニタでは、 API がサンプル token をすでにストリームするため、制約付きデコーディングなしで CML パーサだけを実装する。割り込みマネージャの割り込み挿入を模倣するため、割り込みがトリガーされるたびに API サーバーへ新しいリクエストを開始し、前のセッションを破棄する。クラウド API はステートレスで、割り込みを挿入する新しいセッションごとに KV cache 全体を最初から再計算するため、トラップハンドラは不要である。 [+2] この実装が実用的なのは time-to-first-token（TTFT）レイテンシが低い場合だけであり、一般にほとんどのクラウドサービスはそうではない（詳細は[第 6.2 節](#section-06-02)）。

[+2]: 一部の LLM サービスは再利用のためプロンプトをキャッシュできるが、そのキャッシュは通常、実行時ではなく文書など頻繁にアクセスされる情報のために設計されている。

<span id="section-06"></span>

## 6 評価

我々の評価は二つの問いに答える：（i） *レイテンシ*（[第 6.1 節](#section-06-01)-[第 6.4 節](#section-06-04)）、つまり非同期関数呼び出しが同期方式と比べてタスク完了レイテンシをどれだけ減らすか、（ii） *正確性*（[第 6.5 節](#section-06-05)）、つまり非同期機構が生成関数呼び出しの正確性にどう影響するかである。

**ワークロード。** タスク完了レイテンシと関数呼び出し正確性を評価するため、 Berkeley function calling leaderboard（BFCL） [Yan24d] を使う。これは車両制御、旅行予約、ファイルシステム操作、 Twitter API など八つの領域にわたる現実の関数呼び出しを収録する。BFCL には 84 個の固有関数がある。異なる関数呼び出しシナリオをカバーするため BFCL の三つのデータセット `v1-parallel`、 `v2-parallel-live`、 `v3-base-multi-turn` を利用する。`v1-parallel` と `v2-parallel-live` は 400 個の並列関数呼び出しシナリオを、 `v3-base-multi-turn` は 200 個のマルチステップ関数呼び出しシナリオを提供する。より複雑なマルチステップ並列関数呼び出しをシミュレートするため、新しい `v3-multi-step-parallel` データセットを作成した。このデータセットは、 `v3-base-multi-turn` の第 1 ラウンドから三つの異なるマルチステップサンプルをランダムに組み合わせた 200 シナリオで構成される。合計 800 サンプルのうち 200 を微調整に、残り 600 を評価に使う。各関数の測定実行時間は 30 ms から 500 ms、平均は 110 ms である。

**AsyncLM の設定。** LLM のデプロイ設定としてローカルとクラウドの二つを考える。ローカルデプロイでは LLM 推論と関数実行を NVIDIA RTX 4090 GPU 搭載の同一マシンで行う。このデプロイには 3B と 1B パラメータの Llama-3.2 モデル [Dub24] を使う。Llama モデルは LlamaFactory [Zhe24a] のデフォルト設定に従って微調整する。ローカルモデルは Text-Generation-Interface [Tex22] でサーブする。クラウドデプロイでは関数実行だけをローカルで行う。GPT-4o と GPT-4o-mini を使い、各データセットから一例を選んで解釈方法の詳細な指示を与える少数ショットプロンプトで適応する。

**ベースライン。** 同期 LLM 関数呼び出しと比較するため、二つの同期ベースラインを用いる。

- *Sync*：LLM コード生成と実行を交互に行う順次関数呼び出し。
- *Sync-Parallel*：並列関数呼び出し [Ope23d, Kim24a]。LLM が独立した関数呼び出しをまとめ、エグゼキュータが並列実行する。

AsyncLM の二つの実装も比較する。

- *Async-Naive*：基盤の LLM サービングシステムを変更しない chat completion API ベースの実装。
- *Async*：共同設計した推論プロセスを備える AsyncLM。

クラウド（GPT-4o）における *Async* のレイテンシ測定では、 OpenAI API の平均 token 生成レイテンシ統計（出力 token あたり 5 ms）に基づくエミュレーション結果を報告する。これはクラウド LLM に AsyncLM を実装したときのレイテンシ上の利点の大まかな推定である。

BFCL で関数呼び出しを生成する LLM の公式正確性は GPT-4o で 62%、 Llama-3.2-3B で 43% であることに注意されたい [Yan24d]。誤った関数呼び出しは必要な手順を欠落させたり冗長な手順を含めたりするため、これはレイテンシ評価にバイアスを生む可能性がある。この干渉を抑えるため、プロンプトに正解を含む「チートシート」を加え、測定間で生成される関数呼び出しの一貫性を確保する。

<span id="section-06-01"></span>

### 6.1 並列関数呼び出し

まず関数呼び出しが互いに依存しない単純な設定を用い、結果を[図 5](#figure-05)に示す。並列関数呼び出しは一般的である [Ope23d]。例えば「明日は Seattle と Vancouver のどちらが雨になる可能性が高いか」とユーザーが尋ねたとき、 LLM は Seattle の天気データ用と Vancouver 用の二つの関数呼び出しを生成し、それらを並列実行できる。この評価では BFCL の `v1-parallel` と `v2-parallel-live` を使う。

**結果。** *Async* は *Sync* に対してレイテンシを最大 2.1$\times$ 改善する。エンドツーエンドのタスク完了レイテンシは、最初の token 生成から最後の token 生成までの時間として測定する。ローカルデプロイでは *Async* が *Sync* より 1.6$\times$ 高速で、クラウドでは 2.1$\times$ 高速だった。比較として *Sync-Parallel* はローカルで *Sync* より 1.3$\times$、クラウドで 1.7$\times$ 高速である。*Async-Naive* は *Async* より遅いが、ローカルでは *Sync-Parallel* より 1.2$\times$ 高速である。

### 6.2 マルチステップ並列関数呼び出し

関数呼び出しに依存関係がある複雑な設定を評価するため、三つの独立タスクからなり各タスクが 1-5 回の順次関数呼び出しを必要とする `v3-multi-step-parallel` データセットで AsyncLM を評価する。結果を[図 6](#figure-06)に示す。これらのシナリオで AsyncLM はタスク順序の依存関係を守り、各関数呼び出しの割り込み ID を管理しなければならない。例えば「make pasta」タスクは、（i） `boil_water()` の後に `put_pasta_noodles` を行う系列と、（ii） `chop_vegetables()` の後に `stir_fry()` を行い、最後に `mix_everything()` に至る系列という二つの独立系列を含み得る。

**結果。** AsyncLM は独立系列の関数呼び出しを並列化して *Sync* より最大 5.4$\times$ レイテンシを削減し、 *Sync-Parallel* は *Sync* より 3.2$\times$ レイテンシを削減する。[図 2](#figure-02)に示すように、 LLM がまとめたすべての関数の完了を待つ必要がある *Sync-Parallel* と違い、 *Async* は LPT 戦略で個々の関数呼び出しをスケジュールする。これにより LLM は token 生成サイクルをより効果的に最適化でき、 CPU 命令スケジューリングのアウトオブオーダ実行に似た動作になる。

### 6.3 レイテンシ分析

非同期関数呼び出しがレイテンシを下げる仕組みを理解するため、並列関数呼び出し（[第 6.1 節](#section-06-01)）の理論分析を行う。証明はすべて[付録 A](#appendix-a)に示す。

**生成と実行の重ね合わせ。** 非同期関数呼び出しは同期関数呼び出しと少なくとも同じ速さである。単純な並列関数呼び出しにおける *Sync* の総レイテンシは次でモデル化できる。

$$
L_{\mathrm{Sync}}(F)=\sum_{f\in F}G(f)+\sum_{f\in F}E(f),
$$

ここで $F$ は実行が互いに依存しない関数の集合、 $G(f)$ は $f\in F$ の token 生成レイテンシ、 $E(f)$ は実行時間である。*Sync-Parallel* の総レイテンシは

$$
L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)=\sum_{f\in F}G(f)+\max_{f\in F}E(f),
$$

並列化のオーバーヘッドは無視できると仮定する。LPT ヒューリスティックを使う *Async* の総レイテンシは

$$
L_{\mathrm{Async}}(F)=\max_{f\in F}\left(E(f)+\sum_{g\in\mathrm{pred}(f,F)}G(g)\right),
$$

ここで $\mathrm{pred}(f,F)=\{g\in F\mid E(f)\leq E(g)\}$ である。直感的には、各関数呼び出し $f$ は同じかそれ以上の優先度を持つすべての関数呼び出しを生成した後に開始するという意味であり、 $\mathrm{pred}(f,F)$ の生成時間の合計に相当する。生成 token 数が同じで、 *Sync-Parallel* と *Async* に $G(f)$ と $E(f)$ 以外の追加オーバーヘッドがないと仮定すれば、最悪の場合でも *Async* は *Sync-Parallel* と少なくとも同じ速さであることを証明する。

<span id="theorem-06-01"></span>

**定理 6.1。** 任意の独立関数集合 $F$ について、 $L_{\mathrm{Async}}(F)\leq L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)<L_{\mathrm{Sync}}(F)$。

**平均関数実行時間によるスピードアップの特徴付け。** $E(\cdot)$ が正規分布に従うと仮定し、 $\overline{E}$ と $\overline{G}$ を使って *Sync* に対する *Async* の期待スピードアップを推定する。$\overline{E}$ は平均実行時間、 $\overline{G}$ は $F$ の関数の平均生成時間を表す。

<span id="theorem-06-02"></span>

**定理 6.2。** $|F|$ が大きいとき、スピードアップ比 $\frac{L_{\mathrm{Sync}}}{L_{\mathrm{Async}}}$ はおよそ $1+\frac{\overline{E}}{\overline{G}}$ で、誤差は $\mathcal{O}((\frac{\overline{E}}{\overline{G}})^2)$ のオーダーである。

この結果は、平均実行時間が長いタスク（高価な I/O など）ほど大きなスピードアップを得られ、実行時間が短いタスク（単純な算術演算など）では AsyncLM の利益が小さい可能性を示す。

**LPT ヒューリスティックを使う理由。** LPT は並列関数呼び出しに対して最適である。非同期並列関数呼び出しで LPT ヒューリスティックが総レイテンシを最小化することを証明する。長い関数の実行を早く開始すれば token 生成との重なりが最大になり、全体の完了時間が短くなる。これを形式化するため、

<span id="theorem-06-03"></span>

**定理 6.3。** [定理 6.1](#theorem-06-01)に続き、 LPT 順序から逸脱して総レイテンシを下げることはできない。

これらの分析は、生成と実行を重ねることで非同期関数呼び出しが有利になること、および特に関数が互いに独立な場合に LPT ヒューリスティックを使う根拠を概ね示している。

<span id="section-06-04"></span>

### 6.4 システムオーバーヘッド

**AsyncLM の推論オーバーヘッド。** AsyncLM は *Sync* と比べて二つの潜在的な LLM 推論オーバーヘッドを導入する。（i） CML と関数呼び出し ID の使用による構文オーバーヘッド、（ii）関数実行結果とその ID を LLM コンテキストに注入する割り込みによるオーバーヘッドである。*Sync* と *Sync-Parallel* も関数呼び出しに固有形式、例えば Markdown コード構文でのラップを必要とするため、構文オーバーヘッドは小さい。AsyncLM が関数呼び出しごとに加える制御 token は 2 または 3 個で、生成される総 token 数に比べれば無視できる。同様に割り込みオーバーヘッドの大部分は *Sync* に対するインコンテキスト割り込み ID から生じる。どちらの方法も LLM コンテキスト内で関数の返り値を受け取るからである。`v3-multi-step-parallel` データセットで *Async* は *Sync* より平均 20 token 多く、3B モデルの GPU メモリに約 90 ms のレイテンシと 27.5 MB の追加 KV cache を生じるが、総メモリ使用量の 5% 未満である。

**サービングシステムを協最適化しない場合の性能。** OpenAI API 上で AsyncLM（*Async-Naive*）を実装するのは、 time-to-first-token（TTFT）レイテンシが高いため GPT-4o では実用的でない。GPT-4o では *Async-Naive* のレイテンシは *Sync-Parallel* より 1.5$\times$ 高い（[図 6](#figure-06)）。増加の原因は割り込みごとに新しい API 呼び出しを開始するオーバーヘッドであり、平均 TTFT は 310 ms となる。興味深いことにローカル Llama-3B の *Async-Naive* はこのような高い TTFT を経験せず、平均 TTFT は 59 ms にすぎないため *Sync-Parallel* より 1.1$\times$ 高速である。プロンプトキャッシュやステートフル推論などの技術で *Async-Naive* の TTFT オーバーヘッドを軽減し、性能を改善できる可能性がある。

<span id="figure-07"></span>

![Llama-1B と Llama-3B のトラップ処理戦略の図](../../papers/async-llm-function-calling/figure-07.png)

**図 7. メモリ内のアイドル KV cache をレイテンシを犠牲にせず最小化するトラップ処理戦略の図。** 最適な戦略は次の割り込みまでの推定時間とコンテキスト内の token 数に依存する。

**タスク依存関係下の LPT ヒューリスティック。** 実験では LPT が有効なヒューリスティックであることが示された。[図 6](#figure-06)のローカル *Async* 評価では、 LPT は次の関数をランダムに選ぶ方法より平均 8% 高速だった。ただし関数に依存関係がある場合、 LPT が最適である保証はない。$c$ が $a$ に依存し、実行時間が $E(a)<E(b)<E(c)$ を満たす関数 $a$、 $b$、 $c$ を考える。LPT は将来の依存を考えないため $b$-$a$-$c$ とスケジュールするが、最適順序は $a$-$c$-$b$ である。この課題は資源制約付きプロジェクトスケジューリングに属する NP 困難問題である [Bru99, Har22a]。LPT は現在利用できる情報だけを考慮し、将来の依存を予測しない貪欲ヒューリスティックである。

**トラップ処理戦略。** トラップハンドラはコンテキスト長からスワップと再計算の予想レイテンシを推定し、アイドル KV cache のメモリ使用を減らせる。[図 7](#figure-07) は KV cache のスワップ（線形）と再計算（二次）のレイテンシモデルを使い、 Llama-1B と Llama-3B 上の AsyncLM における最適なトラップ処理戦略を分析する。例えば次の割り込みが 100 ms 後に来ると予想され、コンテキストが 300 token の場合、1B モデルでは KV cache を破棄して再計算できるが、3B では再計算オーバーヘッドが高いためスワップすべきである。

### 6.5 関数呼び出しの正確性

AsyncLM が LLM の正確な関数呼び出し、すなわち正しいシグネチャ、引数、呼び出し順序を生成する能力にどう影響するかを評価するため、マルチステップ並列データセットで各ベースラインの関数呼び出しトレースを調べる。必要な関数定義がすべてプロンプトにあることを保証する。関数呼び出し正確性は、各関数呼び出しを正解呼び出しと厳密 AST マッチングし、実行順序も照合して測定する。

二つの LLM 適応戦略、微調整と少数ショットプロンプティングを比較する。Llama モデルは両方で適応し、 GPT-4o は少数ショットプロンプティングだけで適応する。CML 構文の効果を理解するため、 *Sync* の関数呼び出しを CML で整形するシナリオも試す。[表 1](#table-01) にこれらの適応戦略での GPT-4o と Llama の結果を示す。

<span id="table-01"></span>

![同期・非同期方式の関数構成正確性の表](../../papers/async-llm-function-calling/table-01.png)

**表 1.** マルチステップ並列関数呼び出しにおける *Sync* と *Async* の平均関数構成正確性（AST マッチング）。（FT）は微調整モデル、（ICL）は少数ショットプロンプトを表す。

**CML が正確性に与える影響。** *Sync* の応答を CML 構文で整形しても正確性への影響は小さい。GPT-4o の正確性はほぼ変わらず、 Llama-3B はわずかに改善する。CML を使うと微調整モデルの正確性がやや高くなるが、これは微調整サンプルが CML 形式だったためと考えられる。

**非同期関数呼び出しが正確性に与える影響。** GPT-4o（少数ショットプロンプト）と微調整 Llama モデルは *Sync* と *Async* で同程度の正確性を保つ。これは非同期関数呼び出しがモデルの関数呼び出し正確性を低下させないことを示唆する。一方、少数ショットプロンプトで適応した Llama モデルは *Sync* から *Async* に切り替えると正確性が大きく低下する。小規模モデルは CML 構文に適応するインコンテキスト学習能力が限られるためである。

**LLM 適応における微調整と少数ショットプロンプト。** GPT-4o は少数ショットプロンプトで非同期関数呼び出しによく適応するが、 GPT-4o-mini のような小規模モデルは *Async* で正確性がやや下がる。少数ショットの Llama モデルは全体的な正確性が低いのに対し、微調整は性能を大きく改善する。特に微調整した Llama モデルは *Async* での正確性が *Sync* の GPT-4o より高く、小規模 LLM に対する微調整の重要性を示している。

### 6.6 議論 — 人間がトリガーする割り込み

<span id="figure-08"></span>

![ユーザートリガー割り込みのレイテンシ評価](../../papers/async-llm-function-calling/figure-08.png)

**図 8. ユーザートリガー割り込みの評価。** [図 6](#figure-06)の実験を繰り返すが、各タスクはプロンプトではなく割り込みで表され、0、200、400 ms に到着する。

AsyncLM が提案する割り込み機構は非同期関数呼び出しを可能にするだけでなく、新しい人間-LLM および LLM-LLM インタラクションも可能にする。まずこの機構の柔軟性を議論し、次に実世界の例で可能性を示す。

**割り込みの一般性と柔軟性。** AsyncLM はエグゼキュータ通知を超えて割り込み機能を拡張し、ユーザー入力やシステムトリガーなどの外部イベントを割り込みで通知できるようにする。これによりリアルタイムインタラクションが可能になり、ユーザーは現在のタスクが終わるまで待たずに進行中の LLM 推論を中断してタスクを追加・調整できる。本稿では詳述しないが、マルチターン対話データセットから新しいタスクをランダムに注入することで、ユーザートリガー割り込みを微調整データセットに組み込んだ。このデータセットは実際の人間-LLM インタラクションを完全には表さない可能性があるが、次のシナリオで有効性を調べた。

**割り込み可能な AI アシスタント。** 現在の LLM チャットボットは同期的に動作し、ユーザーは完全な応答を待たなければならない。この方式は体感レイテンシを増やし、リアルタイムのタスク処理を制限する。AsyncLM では LLM が応答を生成している途中でも、ユーザーが直ちに新しい要求を出せる。例えばユーザーは初めに「Seattle のホテルを探して」と頼み、すぐに「Space Needle の近く」と追加できる。同様に水曜日に予定した会議について「やっぱり木曜日にして」と言って以前の要求を修正できる。

このシナリオを調べるため、マルチステップ並列関数呼び出し実験を繰り返し、タスクをプロンプトではなくユーザートリガー割り込みの系列として提示した。割り込みを 200 ms ごとに挿入し、 [図 8](#figure-08)に示す *Async* のエンドツーエンドタスク完了レイテンシを測定した。比較のため同じタスクで *Sync* と *Sync-Parallel* を実行し、どちらも順次処理した。*Async* は *Sync* と比較してレイテンシを 2.4$\times$ 削減したが、 *Sync-Parallel* は 1.1$\times$ の削減にとどまった。*Sync-Parallel* の改善が限られるのは、すべての関数呼び出しを一度に生成する必要があり、このシナリオに適さないためである。

**複数エージェント間の LLM 通信。** AsyncLM は複数の自律 LLM エージェントが同時に通信することも可能にする。通常、エージェント間通信は同期メッセージ交換 [Wu23c, Cha24a] を使い、エージェントは順番に行動する。これによりマルチタスク能力が制限され、通信がラウンドロビン形式に縛られる。AsyncLM では割り込み機構で一対多または多対多のエージェント通信を実装できる。各エージェントは割り込みとして他のエージェントにメッセージを送り、より動的なインタラクションを可能にする。これはより現実的な LLM ベースの社会シミュレーション [Zho24b, Par23] にもつながり得る。この新しい通信パターンは複雑性を増し、人間の会話のようにいつ発言するかを LLM が学ぶ必要を生じさせる可能性がある。

<span id="section-07"></span>

## 7 結論

AsyncLM は LLM と関数エグゼキュータを独立に動作させることで非同期 LLM 関数呼び出しを可能にするシステムである。中核となる革新は LLM 推論を割り込み可能にしたことであり、（1）非同期インタラクションを促進するインコンテキストインターフェース CML、（2） LLM が非同期意味論を活用してタスク完了レイテンシを最適化するための適応、（3） LLM 推論パイプライン上での割り込み機構の効率的な実装からなる。BFCL ベンチマークの実証評価では、 AsyncLM は同期方式と比べレイテンシを 1.6x–5.4x 削減した。AsyncLM は外部ツール、データソース、人間、他の LLM と対話する LLM の動作効率を高める新たな可能性を開く。

## 付録 A レイテンシ分析

本節では独立関数集合に対する異なる実行モデルの総レイテンシを分析し、非同期関数呼び出しの利点を示す定理の証明スケッチを与える。

### A.1 コンテキストと定義

$F=\{f_1,f_2,\dotsc,f_n\}$ を $n$ 個の独立関数の集合とする。各関数 $f\in F$ は token 生成レイテンシ $G(f)>0$ と実行時間 $E(f)>0$ を持つ。平均生成レイテンシを $\overline{G}=\frac{1}{n}\sum_{f\in F}G(f)$、平均実行時間を $\overline{E}=\frac{1}{n}\sum_{f\in F}E(f)$ と定義する。

異なる実行モデルの総レイテンシは次のとおりである。

- *同期実行（$\mathrm{Sync}$）*：token を生成し、関数を順次実行する。

$$
L_{\mathrm{Sync}}(F)=\sum_{f\in F}G(f)+\sum_{f\in F}E(f)=n(\overline{G}+\overline{E}).
$$

- *並行実行を伴う同期（$\mathrm{Sync}\text{-}\mathrm{Parallel}$）*：token を順次生成し、関数を並行実行する。

$$
L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)=\sum_{f\in F}G(f)+\max_{f\in F}E(f).
$$

- *最長処理時間（LPT）* ヒューリスティックを使う*非同期実行（$\mathrm{Async}$）*：token を順次生成し、 $E(f)$ の降順で関数をスケジュールする。

$$
L_{\mathrm{Async}}(F)=\max_{f\in F}\left(E(f)+\sum_{g\in\mathrm{pred}(f,F)}G(g)\right),
$$

ここで $\mathrm{pred}(f,F)=\{g\in F\mid E(f)\leq E(g)\}$ である。

### A.2 定理 6.1 の証明スケッチ

<span id="theorem-06-01-appendix"></span>

**定理 6.1。** 任意の独立関数集合 $F$ について、 $L_{\mathrm{Async}}(F)\leq L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)<L_{\mathrm{Sync}}(F)$。

1. $L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)<L_{\mathrm{Sync}}(F)$ の確立：

最大実行時間はすべての実行時間の合計より小さいため、

$$
\max_{f\in F}E(f)<\sum_{f\in F}E(f),
$$

次が導かれる。

$$
L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)<\sum_{f\in F}G(f)+\sum_{f\in F}E(f)=L_{\mathrm{Sync}}(F)\text{。}
$$

2. $L_{\mathrm{Async}}(F)\leq L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)$ の確立：

LPT ヒューリスティックでは $E(f_1)\geq E(f_2)\geq\dotsb\geq E(f_n)$ となるように関数を並べる。関数 $f_i$ の完了時刻は

$$
C(f_i)=\left(\sum_{j=1}^{i}G(f_j)\right)+E(f_i)\text{。}
$$

総レイテンシは $L_{\mathrm{Async}}(F)=\max_{1\leq i\leq n}C(f_i)$ である。すべての $i$ について、

$$
\sum_{j=1}^{i}G(f_j)\leq\sum_{f\in F}G(f),\quad E(f_i)\leq E(f_1)=\max_{f\in F}E(f),
$$

ゆえに

$$
C(f_i)\leq\sum_{f\in F}G(f)+\max_{f\in F}E(f)=L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F),
$$

したがって $L_{\mathrm{Async}}(F)\leq L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)$ である。

### A.3 定理 6.2 の証明スケッチ

<span id="theorem-06-02-appendix"></span>

**定理 6.2。** $n=|F|$ が大きいとき、比 $\frac{L_{\mathrm{Sync}}(F)}{L_{\mathrm{Async}}(F)}$ はおよそ $1+\frac{\overline{E}}{\overline{G}}$ で、誤差のオーダーは $\left(\frac{\overline{E}}{\overline{G}}\right)^2$ である。

$n$ が大きいとき、 $E(f)$ が正規分布に従うと仮定し、順序統計量を使って累積 token 生成レイテンシと最大実行時間を近似できる。

$$
\sum_{f\in F}G(f)\approx n\overline{G},\quad \max_{f\in F}E(f)\approx\overline{E}+\sigma\sqrt{2\ln n}\text{。}
$$

$L_{\mathrm{Async}}(F)\leq L_{\mathrm{Sync}\text{-}\mathrm{Parallel}}(F)$ という不等式を使うと、総レイテンシは

$$
L_{\mathrm{Async}}(F)\approx n\overline{G}+\overline{E}+\sigma\sqrt{2\ln n}\text{。}
$$

総レイテンシの比は

$$
\frac{L_{\mathrm{Sync}}(F)}{L_{\mathrm{Async}}(F)}\approx\frac{n\overline{G}+n\overline{E}}{n\overline{G}+\overline{E}+\sigma\sqrt{2\ln n}}\text{。}
$$

大きな $n$ では $\varepsilon=\dfrac{\overline{E}+\sigma\sqrt{2\ln n}}{n\overline{G}}\ll 1$ なので、 $\dfrac{1}{1+\varepsilon}\approx 1-\varepsilon$ と近似できる。この近似を適用すると、

$$
\frac{L_{\mathrm{Sync}}(F)}{L_{\mathrm{Async}}(F)}\approx\left(1+\dfrac{\overline{E}}{\overline{G}}\right)\left(1-\dfrac{\overline{E}+\sigma\sqrt{2\ln n}}{n\overline{G}}\right)\text{。}
$$

$O(1/n)$ のオーダーの項を無視すると、

$$
\frac{L_{\mathrm{Sync}}(F)}{L_{\mathrm{Async}}(F)}\approx 1+\dfrac{\overline{E}}{\overline{G}}\text{。}
$$

この近似の誤差は $\left(\dfrac{\overline{E}}{\overline{G}}\right)^2$ のオーダーである。

### A.4 定理 6.3 の証明スケッチ

<span id="theorem-06-03-appendix"></span>

**定理 6.3。** LPT 順序から逸脱して総レイテンシを下げることはできない。

矛盾を導くため、 LPT 順序から逸脱し、 LPT スケジュール $\sigma^*$ より総レイテンシが低いスケジュール $\sigma'$ が存在すると仮定する。このとき $\sigma'$ には、 $E(f_i)<E(f_j)$ なのに $f_j$ が $f_i$ より後にスケジュールされる関数 $f_i$、 $f_j$ が存在する。

$\sigma'$ における $f_i$ と $f_j$ の前の累積 token 生成レイテンシをそれぞれ $S_i$、 $S_j$ とし、 $S_j=S_i+G(f_i)$ とする。完了時刻は

$$
C_{\sigma'}(f_j)=S_j+G(f_j)+E(f_j)=S_i+G(f_i)+G(f_j)+E(f_j)\text{。}
$$

$f_i$ と $f_j$ を入れ替えてスケジュール $\sigma''$ を得る。$f_j$ の token 生成レイテンシの合計は $S_j''=S_i$、 $f_i$ では $S_i''=S_j''+G(f_j)$ となる。新しい完了時刻は

$$
C_{\sigma''}(f_i)=S_i''+G(f_i)+E(f_i)=S_i+G(f_j)+G(f_i)+E(f_i)\text{。}
$$

交換前後の完了時刻を比較すると、

$$
C_{\sigma''}(f_i)-C_{\sigma'}(f_i)=E(f_i)-E(f_j)<0\text{。}
$$

したがって $f_i$ と $f_j$ の交換は常に最大完了時間を短縮する。このような交換を繰り返せば、どのスケジュールも総レイテンシを増やさず LPT スケジュールへ変換できる。これは $\sigma'$ の方が $\sigma^*$ より低い総レイテンシを持つという仮定に矛盾する。ゆえに LPT 順序からの逸脱が総レイテンシを下げることはない。
