## 要約

生成タスク向けに学習された大規模 Transformer ベースモデル (例: GPT-3) は近年大きな関心を集めており, この系列のモデルをサービングするシステム支援の必要性を強調している. これらのモデルは自己回帰的に次のトークンを生成するため, 推論リクエストを処理するにはモデルを複数回実行する必要があり, モデルの各反復はリクエストに対して 1 つの出力トークンを生成する. しかし既存の推論サービングシステムは, 複数反復という特性を持つこのワークロードで十分に機能しない. 現在処理中のリクエストバッチを変更できない柔軟性の低いスケジューリング機構が原因で, バッチ内で先に終了したリクエストはクライアントへ返せず, 新しく到着したリクエストは現在のバッチが完全に終了するまで待たされる.

本論文では, リクエストではなく反復の粒度で実行をスケジュールし, スケジューラがエンジンにバッチ上のモデルを 1 回の反復だけ実行させる新しい機構, 反復レベルスケジューリングを提案する. さらに Transformer モデルでバッチ処理と反復レベルスケジューリングを同時に適用するため, 選択した操作にだけバッチ処理を適用する選択的バッチ処理を提案する. これら 2 つの技術に基づき, 数千億パラメータのモデルまでスケールできる追加設計を備えた分散サービングシステム ORCA を実装した. GPT-3 175B モデルでの評価では, ORCA はレイテンシとスループットの両方で NVIDIA FasterTransformer を大幅に上回り, 同じレイテンシ水準でスループットを 36.9× 改善した.

## 1 はじめに

言語生成タスクは, チャットボット [Adi20, Rol21a], 要約 [Nal16, Pau18, See17], コード生成 [Che21], キャプション生成 [Xu15, Yan16] など多くのアプリケーションでますます重要になっている. AI21 Labs [Lie21], DeepMind [Hof22, Rae21a], Google [Cho22b, Du21a, Wei22e], Meta Platforms [Art21a, Zha22], Microsoft [Raj22], Microsoft & NVIDIA [Smi22a], OpenAI [Bro20b] の近年の研究は, 翻訳 [Bro90, Dab20], 分類 [Dix18, Sch21b], 質問応答 [Kha20, Kwi19a, Mih18b] などあらゆる言語処理タスクを言語生成問題として定式化でき, この方向で大きな改善を実現できることを示している. 生成モデルの台頭は言語分野に限られず, AI コミュニティは画像, 動画, 音声, 複数分野の混合など他分野の生成問題にも関心を高めている [Din21, Lin21, Ram21, Wan22f]. 生成モデルの中心には Transformer アーキテクチャ [Vas17d] とその変種 [Cho22b, Rad19b, Rae21a, Raf20b] がある. 注意機構 [Vas17d] によって Transformer モデルはより良い表現を学習でき, 系列の各要素が他の要素すべてと直接接続できる. これは再帰モデル [Hoc97a] では不可能だった.

生成モデルを実際のアプリケーションで使うため, 推論手順を ML 推論サービングを担当する別サービスに委ねることが多い. クライアントリクエストへ低レイテンシかつ高スループットで推論結果を返すサービスへの需要が高まり, Triton Inference Server [Tri21] や TensorFlow Serving [Ols17a] などの推論サービングシステムが発展した. これらのシステムは, 実際のテンソル演算を行う独立開発の DNN 実行エンジンを利用できる. 例えば Triton と, Transformer ベースモデルの推論に最適化された実行エンジン FasterTransformer [Fas21] を組み合わせれば言語生成サービスを配置できる. この場合 Triton は主に複数のクライアントリクエストをバッチにまとめ, FasterTransformer は Triton からバッチを受け取ってバッチ形式で推論を行う.

残念ながら, サービングシステム層と実行エンジン層の双方を含む既存の推論システムには, Transformer ベース生成モデルのリクエストを扱う上で限界がある. これらのモデルは自己回帰的に次のトークンを生成するよう学習されているため, 生成するトークン数と同じ回数モデルを実行する必要がある. 一方 ResNet [He16c] や BERT [Dev19b] のようなモデルでは, モデルを 1 回実行すればリクエストを処理できる. つまり生成モデルのリクエストを処理するにはモデルを複数反復し, 各反復で 1 つの出力トークンを生成して次の反復の入力にする必要がある. この複数反復特性は, サービングシステムがリクエスト粒度でエンジン実行をスケジュールする現在の設計に疑問を投げかける. この設計では, サービングシステムがリクエストバッチをエンジンへ送ると, エンジンはバッチ内の全リクエストを処理した後にバッチ全体の推論結果を一度に返す. クライアントリクエストごとに必要な反復数が異なるため, バッチ内で先に終了したリクエストをクライアントへ返せず, レイテンシが増加する. バッチをディスパッチした後に到着したリクエストもバッチ処理を待つ必要があり, リクエストの待ち時間が大きくなる.

本論文では, リクエストではなく反復の粒度でエンジン実行をスケジュールする. 具体的にはサービングシステムがエンジンを呼び出し, バッチ上でモデルを 1 回だけ反復させる. その結果, 新しく到着したリクエストはモデルの 1 回の反復を待つだけで処理対象となる機会を得る. サービングシステムはエンジンから返るたびにリクエストの完了を確認できるため, 完了したリクエストを直ちにクライアントへ返せる.

それでもバッチ処理と反復レベルスケジューリングを同時に適用すると, 目立つ課題が生じる. 従来のリクエストレベルスケジューリングと異なり, 提案方式では各リクエストがそれまでに処理したトークン数の異なるリクエストバッチを発行できる. この場合, Transformer へのリクエストはバッチ形式で処理できない. 注意機構にはバッチ化できないテンソル操作があり, その入力テンソルの形状が処理済みトークン数に応じて変わるためである.

この課題に対処するため, 選択した操作だけにバッチ処理を適用する選択的バッチ処理を提案する. 操作ごとの特性を考慮し, バッチを分割して Attention [+1] 操作は各リクエストを個別に処理し, Transformer の他の操作にはバッチ処理を適用する. Attention 実行をバッチ化しない決定が効率に与える影響は小さいことを確認した. Attention 操作にはモデルパラメータがないため, Attention をバッチ化しても複数リクエスト間でロード済みパラメータを再利用して GPU メモリ読み出しを減らす利点がない.

これらの技術に基づき, Transformer ベース生成モデル向け分散サービングシステム ORCA を設計・実装した. 大規模モデルを扱うため, ORCA は Transformer モデル用の学習システム [Sha18c, Sho19] で開発された層内並列および層間並列を採用する. また提案する反復レベルスケジューリングのために新しいスケジューリングアルゴリズムを設計し, メモリ管理とワーカー間のパイプライン実行も考慮した.

さまざまな構成の OpenAI GPT-3 [Bro20b] モデルを用いて ORCA を評価し, パラメータ数を 341B まで拡張した. 結果は ORCA が FasterTransformer [Fas21] を大幅に上回り, 同じレイテンシ水準でスループットを 36.9× 改善することを示した. 本論文では言語モデルを通じて説明し実験も言語モデルだけで行うが, 他分野の生成モデルでも Transformer アーキテクチャに基づき自己回帰生成手順 [Din21, Lin21, Ram21, Wan22f] を使う限り本手法の恩恵を受けられる.

## 2 背景

本節では, 本論文全体で代表例として用いる Transformer ベース生成モデル GPT [Bro20b, Rad19b] の推論手順と, ML 推論サービングシステムについて説明する.

**GPT の推論手順.** GPT は Transformer [Vas17d] のアーキテクチャ変種の 1 つに基づく自己回帰言語モデルである. テキストを入力として受け取り, 新しいテキストを出力する. 具体的には一連の入力トークンを受け取り, 後続出力トークンを生成して系列を完成させる. [図 1a](#figure-01) は 3 層 GPT モデルでこの手順を表す簡略化した計算グラフを示し, ノードとエッジはそれぞれ Transformer 層と層間の依存関係を表す. Transformer 層はノード上の数字の順に実行され, 同じモデルパラメータ集合を使うノード (同じ層を表すノード) は同じ色で塗られる.

生成された出力トークンはモデルに戻され, 次の出力トークンを生成するため, 順次 1 つずつの推論手順になる. 1 トークンを生成する自己回帰手順は, クライアントから来た入力トークン列または以前に生成した出力トークンを入力としてモデルの全層を実行することで行われる. 全層の実行をモデルの 1 回の反復と定義する. [図 1a](#figure-01) の例では推論手順は 3 回の反復からなる. 最初の反復 ("iter 1") はすべての入力トークン ("I think this") を一度に受け取り, 次のトークン ("is") を生成する. この反復は入力トークンを処理して最初の出力トークンを生成する開始フェーズを構成する. 次の 2 つの反復 ("iter 2" と "iter 3") は増分フェーズを構成し, 直前の反復の出力トークンを受け取って次のトークンを生成する.

この例では "iter 3" が特殊な系列終了トークン "&lt;EOS&gt;" を生成する最後の反復であり, 出力生成を終了する. 増分フェーズが複数反復からなるのは各反復が 1 トークンしか処理できないためである. 一方開始フェーズは通常, すべての入力トークンを並列処理して 1 回の反復として実装される. 元の Transformer [Vas17d] は Transformer 層を 2 スタック持つが, GPT のアーキテクチャは decoder という 1 つの層スタックで構成される. [図 1b](#figure-01) は GPT で使われる Transformer 層を示す. Transformer 層を構成する操作のうち Attention は Transformer を他のアーキテクチャと区別する本質である. 高いレベルでは Attention 操作は関心対象トークンの加重平均を計算し, 系列内の各トークンが他のトークンを認識できるようにする. query, key, value の 3 入力を受け, 現在トークンの query と関心対象トークンのすべての key の内積を計算し, 内積に Softmax を適用して重みを得て, その重みに対応するすべての value の加重平均を行う.

<span id="figure-01"></span>

![GPT 推論, Transformer 層, 内部状態利用の図](../../papers/orca/figure-01.png)

**図 1.** GPT の推論手順, Transformer 層, 内部状態利用の図.

Attention はすべての先行トークンの key と value を必要とするため, [+2] key と value を複数反復にわたり保持すべき内部状態とみなす. 素朴なステートレス推論手順では, 系列内の全トークン (クライアント提供入力とそれまでに生成した出力の両方) の key と value を各反復で再計算する. この再計算を避けるため fairseq [Ott19a] は増分デコードを提案し, key と value を保存して後続反復で再利用する. FasterTransformer [Fas21] や Megatron-LM [Sho19] など Transformer の他システムも同じことを行う.

[図 1c](#figure-01) は, 内部状態も保持する LSTM [Hoc97a] とともに Transformer の状態利用パターンを示す. 主な違いは, Transformer の状態サイズ (Attention key の $k$ と value の $v$) が反復とともに増加するのに対し, LSTM の状態サイズ (内部メモリの $c$ と LSTM 層の入力/出力の $h$) は一定である点である. インデックス $t$ のトークンを処理するとき, Attention は先行 Attention key $k_{l,1:t-1}$ と value $v_{l,1:t-1}$ のすべてに加え, 現在の key $k_{l,t}$ と value $v_{l,t}$ を受け取る. [+3] したがって Attention 操作は, すでに処理したトークン数に応じて異なる形状のテンソルで計算を行う必要がある.

Attention 操作の前には layer normalization 操作 (LayerNorm) と QKV Linear (query, key, value を得るための linear および split 操作) がある. Attention 後の操作は linear 操作 (Attn Out Linear), 残差接続のための add 操作 (Add), layer normalization 操作 (LayerNorm), multilayer perceptron (MLP) 操作, もう 1 つの残差接続操作 (Add) の順である.

**ML 推論サービングシステム.** ML 駆動アプリケーションへの需要増加により, ML 推論サービングサービスは現代のデータセンターにおける重要なワークロードになった. ユーザー (エンドユーザーまたはアプリケーションの内部マイクロサービス) は推論サービスにリクエストを送信し, サービスはプロビジョニングされたリソースで事前定義 ML モデルに基づく応答を返す. リソースには通常 GPU や TPU などの専用アクセラレータが備わる. 具体的にはサービスが入力データで DNN モデルを実行し, リクエストの出力を生成する. データセンターの他サービスと同様, 適切に管理された推論サービスは妥当なコスト内で低レイテンシと高スループットを提供すべきである.

この制約を満たすため, サービス運用者は Triton Inference Server [Tri21] や TensorFlow Serving [Ols17a] などの ML 推論サービングシステムを使う. これらは TensorRT [Ten17a], TVM [Che18e], TensorFlow [Aba16c] などの基盤モデル実行エンジンの上に位置する抽象化であり, その他多数 [Pas19a, Ped11] を含む多様な ML モデル, 実行エンジン, 計算ハードウェアに依存しない. 主な数学演算の駆動をエンジンに委ねる一方, サービングシステムは推論リクエストを受けるエンドポイント公開, エンジン実行のスケジューリング, リクエストへの応答送信を担う. そのためこれらのシステムは, 実行のバッチ化 [Tri21, Cra17a, Lee18b, Ols17a, She19b], 複数モデル変種からの適切なモデル選択 [Cra17a, Hsi18, Kan17, She17a], 同一デバイスへの複数モデル配置 [Tri21, Jia18b, Lee18b, She19b] などに注力する.

サービングシステムが提供する機能と最適化の中で, GPU のようなアクセラレータ利用時に高い利用率を達成する鍵はバッチ処理である. 実行エンジンをバッチ処理有効で実行すると, 複数リクエストの入力テンソルはモデル最初の操作に入る前に 1 つの大きな入力テンソルへまとめられる. アクセラレータは大量の並列計算ユニットを活用するため小さい入力より大きい入力を好むので, エンジンのスループットはバッチサイズ, つまりエンジンが同時に処理するリクエスト数に強く依存する. モデルパラメータがメモリ集約的な操作に関わる場合, オフチップメモリからロードしたパラメータを再利用できることもバッチ実行の利点である.

[図 2](#figure-02) は既存のサービングシステムと実行エンジンで生成言語モデルを提供する全体ワークフローを示す. サービングシステムの主要コンポーネント (例: Triton [Tri21]) はスケジューラであり, キューからリクエストを取得してバッチを作り, 実行エンジン (例: FasterTransformer [Fas21]) にバッチを処理させる. 実行エンジンは提供モデルを複数反復実行し, 生成テキストをサービングシステムへ返す. [図 2](#figure-02) では, サービングシステムが 2 つのリクエスト ($x_1$: "I think", $x_2$: "I love") をバッチとして処理するようスケジュールし, エンジンが $x_1$ と $x_2$ にそれぞれ "this is great" と "you" を生成する.

## 3 課題と提案手法

本節では Transformer ベース生成モデルをサービングする課題を説明し, 反復レベルスケジューリングと選択的バッチ処理という 2 つの技術を提案する.

**C1: 早期終了リクエストと後加入リクエスト.** 既存システムの大きな制限は, サービングシステムと実行エンジンが (1) サービングシステムがアイドルエンジンに次のバッチをスケジュールした時, または (2) エンジンが現在のバッチ処理を終えた時にしか相互作用しないことである. つまりこれらのシステムはリクエスト粒度で実行をスケジュールし, バッチ内の全リクエストが終了するまでエンジンがリクエストバッチを固定する. 生成モデルのサービングでは, バッチ内の各リクエストが異なる反復数を必要とし, 一部が他より早く終了するため問題になる.

[図 3](#figure-03) の例では, リクエスト $x_2$ が $x_1$ より早く終了しても, エンジンは全反復を通じて "active" と "inactive" の両方を計算する. inactive リクエスト ($x_2$ の iter 3 と 4) への余分な計算はバッチ実行の効率を制限する. さらにこの挙動は終了済みリクエストのクライアントへの早期返却を妨げ, 大きな追加レイテンシを生む. エンジンが実行結果をサービングシステムへ返すのはバッチ内全リクエストの処理を終えた時だけだからである. 同様に現在のバッチ実行中に新しいリクエストが到着すると, 前述の機構により現在のバッチ内の全リクエストが終了するまで待つことになる. 現在のリクエストレベルスケジューリングは複数反復特性を持つワークロードを効率的に扱えないと考える. なおこの早期終了・後加入問題は言語モデルの学習には生じない. 学習手順は teacher forcing 技法 [Wil89] によりバッチ全体を 1 回の反復で処理し終えるためである.

<span id="figure-03"></span>

![入力長が同じで一部が早く終了するリクエスト](../../papers/orca/figure-03.png)

**図 3.** リクエストの入力長は同じだが終了時刻が異なる場合の例. 網掛けトークンは入力トークンを表す. "-" はスケジューリングによる余分な計算の入力と出力を表す.

**S1: 反復レベルスケジューリング.** 上記の制限に対処するため, 反復粒度で実行をスケジュールする. 高いレベルではスケジューラは次を繰り返す: (1) 次に実行するリクエストを選択する; (2) エンジンを呼び出して選択リクエストの 1 反復を実行する; (3) スケジュールした反復の実行結果を受け取る. 毎反復返却を受けるため, スケジューラはリクエスト完了を検出して生成トークンを直ちにクライアントへ返せる. 新着リクエストは現在スケジュールされた反復の実行後に処理開始の機会を得るため, キュー待ちを大幅に短縮できる. 反復レベルスケジューリングでは, 各反復で処理するリクエスト数とリクエストを完全に制御できる.

[図 4](#figure-04) は反復レベルスケジューリングを用いる ORCA のシステム構成と全体ワークフローを示す. ORCA は推論リクエストが到着し応答が送られるエンドポイント (例: HTTPS または gRPC) を公開する. エンドポイントは新着リクエストをリクエストプールに入れ, プールはライフタイム中の全リクエストを管理する. プールを監視するスケジューラは, プールから集合を選び, 集合上でモデルの 1 反復を実行するようエンジンをスケジュールし, 実行結果 (出力トークン) を受け取り, 各出力トークンを対応リクエストに追加してプールを更新する. エンジンは実際のテンソル演算を実行する抽象であり, 複数マシンに分散した複数 GPU で並列化できる. [図 4](#figure-04) の例ではスケジューラがリクエストプールと対話して次の実行リクエストを決め, 4 リクエスト ($x_1$, $x_2$, $x_3$, $x_4$) を実行するようエンジンを呼び出す. 初回スケジュールのリクエストには入力トークンを渡す. この場合 $x_3$ と $x_4$ はまだ反復を実行していないため, $x_3$ には ($x_{31}$, $x_{32}$), $x_4$ には ($x_{41}$, $x_{42}$, $x_{43}$) を渡す. エンジンは 4 リクエストで 1 反復を実行し, 各リクエスト 1 個ずつの出力トークン ($x_{15}$, $x_{23}$, $x_{33}$, $x_{44}$) を返す. リクエストが完了するとプールは削除し, エンドポイントに応答送信を通知する. [図 2](#figure-02) の方式ではバッチ内全リクエストの終了まで複数反復を走らせる必要があるのに対し, ORCA スケジューラは反復ごとに処理リクエストを変更できる. 各反復でのリクエスト選択アルゴリズムは [セクション 4.2](#section-04-02) で詳しく説明する.

<span id="figure-04"></span>

![ORCA システム概要](../../papers/orca/figure-04.png)

**図 4.** ORCA システムの概要. 点線で表したコンポーネント間の相互作用は, 実行エンジンの各反復で発生する. $x_{ij}$ は $i$ 番目リクエストの $j$ 番目トークンである. 網掛けトークンはクライアントから受けた入力, 網掛けなしは ORCA が生成したトークンを表す. 例えばリクエスト $x_1$ は入力トークン 2 個 ($x_{11},x_{12}$) で到着し, すでに 2 反復を実行していて, 1 回目と 2 回目がそれぞれ $x_{13}$ と $x_{14}$ を生成した. 一方 $x_3$ はまだ反復を実行していないため入力トークン ($x_{31},x_{32}$) だけを持つ.

**C2: 任意のリクエスト集合のバッチ処理.** 反復レベルスケジューリングを実際に使う際の大きな課題はバッチ処理である. 高効率のため実行エンジンは任意に選ばれたリクエスト集合をバッチ形式で処理できる必要がある. バッチ処理がなければ選択リクエストを 1 つずつ処理することになり, GPU の大規模並列計算能力を失う.

しかしリクエスト対 ($x_i$, $x_j$) であっても, 次の反復の実行を統合してバッチ版に置き換えられる保証はない. 次の反復を一緒にバッチ処理できないケースは 3 つある: (1) 両方が開始フェーズで入力トークン数が異なる (例: [図 4](#figure-04) の $x_3$ と $x_4$); (2) 両方が増分フェーズで互いに異なるインデックスのトークンを処理する ($x_1$ と $x_2$); (3) 一方が開始, 他方が増分という異なるフェーズにある ($x_1$ と $x_3$). 複数リクエストの実行をバッチ化するには各実行が同一操作で構成され, 各操作が同じ形状の入力テンソルを消費しなければならない. 第 1 の場合, 入力テンソルの "length" 次元 (入力トークン数) が等しくないためバッチ処理できない. 第 2 の場合は [図 1c](#figure-01) のようにトークンインデックスが異なり Attention key と value のテンソル形状が違う. 第 3 の場合は入力トークン数が違うため異なるフェーズの反復をバッチ化できない; 開始フェーズは効率のため全入力トークンを並列処理し, 増分フェーズでは各反復が単一トークンを入力に取る (fairseq 形式の増分デコード [Ott19a] を想定する).

選択した 2 リクエストが同じフェーズにあり, 開始フェーズでは入力トークン数が同じ, 増分フェーズではトークンインデックスが同じ場合にだけバッチ処理できる. この制約により実ワークロードでバッチ化できる可能性は大きく低下する,

**S2: 選択的バッチ処理.** 選択的バッチ処理は, 高い柔軟性でリクエストをバッチに組み立てるバッチ実行技術である. モデルを構成するすべてのテンソル操作を "batchify" する代わりに, 一部の操作だけを選択してバッチ化する.

上記のバッチ処理問題では, 3 つのケース [+4] が不規則形状の入力 (または状態) テンソルに対応し, それらを 1 つの大テンソルにまとめてバッチ操作へ渡せない. 標準バッチ機構では各反復で Transformer 層が形状 $[B, L, H]$ の 3 次元入力テンソルを受け取る. これはバッチ内リクエストの複数の $[L, H]$ 入力テンソルを連結して作り, $B$ はバッチサイズ, $L$ は同時処理トークン数, $H$ はモデルの隠れサイズである. 例えば [図 3](#figure-03) の "iter 1" (開始フェーズ) は形状 $[2, 2, H]$, "iter 2" (増分フェーズ) は形状 $[2, 1, H]$ のテンソルを入力に取る. しかしスケジューラが [図 4](#figure-04) のバッチ ($x_1$, $x_2$, $x_3$, $x_4$) で反復を実行すると, 開始フェーズの $x_3$: $[2,H]$ と $x_4$: $[3,H]$ は入力トークン数が 2 と 3 で異なるため, 形状 $[B,L,H]$ の 1 テンソルにまとめられない.

興味深いことに, すべての操作がこのような不規則形状テンソルと非互換なわけではない. テンソルを平坦化すれば, 非 Attention 行列乗算や layer normalization などは不規則形状テンソルを扱える.

例えば前述の $x_3$ と $x_4$ の入力テンソルは, 明示的なバッチ次元なしで形状 $[\sum L,H]=[5,H]$ の 2 次元テンソルを構成できる. このテンソルは異なるリクエストの要素を区別する必要がない Linear, Layer-Norm, Add, GeLU などすべての非 Attention 操作へ入力できる. 一方 Attention 操作は同一リクエストのトークン間だけを計算するためリクエストの概念 (つまりバッチ次元) を必要とし, 通常は cuBLAS のバッチ行列乗算ルーチンで実現する.

選択的バッチ処理は各操作の特性の違いを把握し, バッチを分割して Attention 操作は各リクエストを個別処理し, リクエスト概念を持たない他操作にはトークン単位 (リクエスト単位ではなく) のバッチ処理を適用する. [図 5](#figure-05) は [図 4](#figure-04) のリクエストバッチ ($x_1$, $x_2$, $x_3$, $x_4$) を処理する選択的バッチ処理を示す. このバッチには処理対象の入力トークンが 7 個あるため入力テンソルを $[7,H]$ として非 Attention 操作を適用する. Attention 前に Split 操作を挿入し, 分割テンソル上で各リクエストの Attention を個別実行する. Attention の出力は Merge 操作で形状 $[7,H]$ のテンソルに戻され, 残りの操作のバッチ機能を回復する.

増分フェーズのリクエストが前反復で処理したトークンの Attention key と value を使えるよう, ORCA は Attention K/V manager に生成 key と value を保持する. manager はスケジューラが特定リクエストの key と value を削除するよう明示的に求めるまで, リクエストごとに key と value を保持する. つまりリクエストが処理を終えるまでである. 増分フェーズのリクエスト ($x_1$ と $x_2$) の Attention 操作は, manager から過去トークンの key と value ($x_1$ の $x_{11},x_{12},x_{13}$; $x_2$ の $x_{21}$) を取得し, Split 操作の現在トークンの query, key, value と合わせて現在トークンと過去トークンの注意を計算する.

## 4 ORCA 設計

上述の技術に基づき Transformer ベース生成モデル向け分散サービングシステム ORCA を設計・実装した. [図 4](#figure-04) の説明でシステムコンポーネントと ORCA の全体実行モデルはすでに述べた. 本節では数千億パラメータの大規模モデルへスケールする効率的なシステムを構築する残りの問題に答え, 反復レベルスケジューリングで各反復にリクエストプールからバッチを選ぶ方法を説明する.

<span id="section-04-01"></span>

### 4.1 分散アーキテクチャ

近年の研究 [Bro20b, Kap20] は, 言語モデルをスケールさせるとモデル品質を劇的に改善できることを示している. したがって, 特にモデルが 1 GPU に収まらない場合, そのような大規模言語モデルをサービングするシステム支援が重要になる. この場合, モデルパラメータと対応する計算を分割し, 複数 GPU とマシンに分散すべきである.

ORCA は Transformer モデル向けの既知の並列化技術, 層内並列と層間並列を組み合わせる. FasterTransformer [Fas21] でも使われるこの 2 つのモデル並列戦略は, もともと分散学習のために開発された. 層内並列 [Sha18c, Sho19] は行列乗算 (Linear と Attention 操作) および関連パラメータを複数 GPU に分割する. 各行列乗算をどう分割するかの詳細は省略する. 一方, 層間並列は Transformer 層を複数 GPU に分割する. ORCA は各 GPU に同じ数の Transformer 層を割り当てる. [図 6](#figure-06) は 4 層 GPT モデルへの層内・層間並列適用例を示す. 4 層を 2 つの層間パーティションに分け, 各パーティションの層を 3 つの層内パーティションに細分化する. 各パーティションを 1 GPU に割り当て, 合計 6 GPU を使う.

ORCA 実行エンジンは上記技術で分散実行をサポートする. [図 7](#figure-07) は ORCA エンジンのアーキテクチャを示す. 各 worker プロセスはモデルの層間パーティションを担当し, 互いに異なるマシンへ配置できる. 各 worker は GPU 制御専用の CPU スレッドを 1 つ以上管理し, スレッド数は層内並列度に依存する.

ORCA 実行エンジンの実行手順は次のとおりである. エンジンがリクエストバッチのモデル 1 反復を実行するようスケジュールされると, engine master はスケジュールバッチの情報を最初の worker (Worker1) へ転送する. 情報には現在反復のトークンと制御メッセージが含まれ, 制御メッセージはバッチ内リクエストの id, 現在トークンのインデックス (増分フェーズ), 入力トークン数 (開始フェーズ) からなる. Worker1 の controller は engine master から受け取った情報を GPU 制御スレッドへ渡し, 各スレッドが解析して対応 GPU へ適切な GPU kernel を発行する. 例えば Attention kernel はリクエスト id と現在トークンインデックスを使い, Attention K/V manager が保持する過去 key と value の GPU メモリアドレスを得る. 同時に controller は Worker1 の GPU kernel 完了を待たず, 制御メッセージを次 worker (Worker2) の controller にも転送する. Worker1 と異なり最後の worker (Worker2) の controller は発行済み GPU kernel の完了を待ち (同期し), 各リクエストの出力トークンを取得して engine master へ返す.

GPU をできるだけビジーに保つため, ORCA エンジンは CPU と GPU の同期を最小化する. 現在の分散推論システム (FasterTransformer [Fas21] や Megatron-LM [Sho19]) は各プロセスが制御メッセージを受け取るたびに CPU-GPU 同期を行う [+5]. GPU 間通信チャネル —NCCL [Ncc21] でメッセージを交換するためである. この制御メッセージ交換は反復ごとに発生し, 無視できないオーバーヘッドになる. 一方 ORCA は制御メッセージ (トークンを含む) とテンソルデータ転送の通信チャネルを分離し, CPU 用データに NCCL を使わない. [図 7](#figure-07) が示すように ORCA エンジンは中間テンソルデータ (破線矢印) の交換だけに NCCL を使う. このデータは GPU が生成・消費するためである. GPU kernel 発行に CPU スレッドが使う制御メッセージは, GPU を含まない別チャネル (例: gRPC [Grp21]) で engine master と worker controller の間に送る.

### 4.2 スケジューリングアルゴリズム

ORCA スケジューラは各反復で選択・処理するリクエストを決める. 選択的バッチ処理によりエンジンは任意のリクエスト集合をバッチ形式で実行できるため, スケジューラはバッチを構成する集合を柔軟に選択できる. 残る主要な問いは各反復でどのリクエストを選ぶかである.

ORCA スケジューラにはクライアントリクエストの処理順を変えない単純なアルゴリズムを使わせ, 早く到着したリクエストを早く処理する. これは反復レベルの first-come-first-served (FCFS) 特性を保証するということである. 複数反復特性のワークロードに対し, 反復レベル FCFS を次のように定義する: リクエストプール内の任意のリクエスト対 ($x_i$, $x_j$) で $x_i$ が $x_j$ より先に到着したなら, $x_i$ は $x_j$ と同じかそれ以上の反復を実行していなければならない. 遅いリクエストの完了に必要な反復数が少なければ, 遅く到着したリクエストが先にクライアントへ返ることもある.

さらにスケジューラは, バッチサイズ増加の逓減効果と GPU メモリ制約を考慮する必要がある. バッチサイズを増やすとスループット増加とレイテンシ増加を交換するが, バッチが大きくなるほど戻り (スループット増加) は逓減する. したがって他のサービングシステム [Tri21, Cra17a] と同様, ORCA にも最大バッチサイズ, つまりバッチ内の最大リクエスト数がある. ORCA の運用者はこのノブを調整し, レイテンシ予算を満たしながらスループットを最大化できる. 実験結果とともに [セクション 6.2](#section-06-02) で詳しく議論する.

もう 1 つは GPU メモリ制約である. 複数操作の中間結果バッファを再利用してメモリ使用量を最適化するのは各種システム [Fas21, Ten17a] が使う既知の技術であり, ORCA も採用する. ただしすぐ再利用できる中間結果バッファと異なり, Attention K/V manager が key と value を格納するバッファは対応リクエストの処理完了を ORCA スケジューラが通知するまで回収できない. 次トークン用の新しい Attention key と value を格納する空きがなく, プール内どのリクエストにも反復を発行できないと, 素朴な実装ではスケジューラがデッドロックする. そのため ORCA スケジューラは manager に事前割当てされたメモリ領域の残量を把握する必要がある.

ORCA スケジューラはこれらすべてを考慮し, 到着時刻に基づき最大 "max batch size" 件を選び, リクエストが初めてスケジュールされる時に key と value の格納領域を予約する. スケジューリング手順をアルゴリズム 1 に示す. アルゴリズムはリクエストプールからバッチを選び (4 行), バッチをスケジュールする (5 行). Select 関数 (17 行) は到着時刻に基づきプールから最大 max_bs 件を選ぶ (20–22 行). アルゴリズム 1 はリクエスト到着と返却を描かないが, 新着リクエストを request_pool に挿入し完了リクエストを削除する並行スレッドがあると考えればよい. 開始フェーズのリクエスト, すなわちまだ一度もスケジュールされていないリクエストを考慮するとき, スケジューラはリクエストの `max_tokens` [+6] 属性を使って key と value 用に max_tokens 個の GPU メモリ slot を事前予約する (23–26 行). 予約可能かは現在予約済み slot 数 n_rsrv (1 slot は単一トークンの Attention key と value に必要なメモリ量) に基づき決める (25 行). n_slots は ORCA 運用者が調整するパラメータで, Attention K/V manager に割り当てるメモリ領域の大きさを slot で示す. リクエストのトークン数は max_tokens を超えないため, 予約できれば完了まで新規 key と value 用バッファを割り当てられることが保証される.

レイテンシとスループットのトレードオフを定量化する必要がある max_bs の調整と違い, n_slots は実験なしで簡単に設定できる. モデル仕様 (隠れサイズ, 層数など) と層内・層間並列度が与えられると ORCA の GPU メモリ使用量は主に n_slots で決まる. したがって運用者はメモリ制約内で最大の n_slots を使えばよい.

**アルゴリズム 1: ORCA スケジューリングアルゴリズム.**

- **パラメータ:** $n_{\mathrm{workers}}$: worker 数, $\mathit{m\!a\!x}_{bs}$: 最大バッチサイズ, $n_{\mathrm{slots}}$: K/V slot 数.
- $n_{\mathrm{scheduled}} \leftarrow 0$ および $n_{\mathrm{rsrv}} \leftarrow 0$.
- **`true` の間:**
  - $\mathit{batch}, n_{\mathrm{rsrv}} \leftarrow \mathrm{Select}(\mathit{request\_pool}, n_{\mathrm{rsrv}})$.
  - エンジンにバッチのモデル 1 反復を実行させる.
  - **返却バッチの各** リクエストについて:
    - `req.state` を `RUNNING` に設定し, $n_{\mathrm{scheduled}}$ を増やす.
    - **もし** $n_{\mathrm{scheduled}}=n_{\mathrm{workers}}$ ならスケジュール済みバッチの返却を待つ.
    - **返却バッチの各** リクエストについて `req.state` を `INCREMENT` に設定する.
    - **もし** `finished(req)` なら $n_{\mathrm{rsrv}} \leftarrow n_{\mathrm{rsrv}}-\mathrm{req.max\_tokens}$ とする.
    - $n_{\mathrm{scheduled}}$ を減らす.
- **関数 `Select(pool, n_rsrv)`:**
  - $\mathit{batch} \leftarrow \{\}$, $\mathit{pool} \leftarrow \{\mathit{req} \in \mathit{pool} \mid \mathrm{req.state} \ne \mathrm{RUNNING}\}$ とする.
  - `pool` を到着時刻でソートする.
  - `pool` の各リクエストについて:
    - **もし** `batch.size() = max_bs` なら break.
    - **もし** `req.state = INITIATION` なら $\mathit{new\_n}_{\mathrm{rsrv}} \leftarrow n_{\mathrm{rsrv}} + \mathrm{req.max\_tokens}$ とする.
    - **もし** $\mathit{new\_n}_{\mathrm{rsrv}} > n_{\mathrm{slots}}$ なら break.
    - $n_{\mathrm{rsrv}} \leftarrow \mathit{new\_n}_{\mathrm{rsrv}}$ とし, `req` を `batch` に追加する.
  - **返す:** $\mathit{batch}, n_{\mathrm{rsrv}}$.

**パイプライン並列.** ORCA スケジューラはエンジン内 worker の実行を複数バッチにわたりパイプライン化する. 現在スケジュール済みバッチ数 n_scheduled が n_workers に達するまで (アルゴリズム 1 の 9–10 行), スケジューラはスケジュール済みバッチの返却を待たない. これによりエンジン内の同時実行バッチ数を n_workers に保ち, すべての worker がアイドルにならずバッチを処理する.

![ORCA と FasterTransformer の実行パイプライン](../../papers/orca/figure-08.png)

**図 8.** ORCA と FasterTransformer のパイプライン並列利用の比較. $X_i$ はリクエスト $X$ の $i$ 回目の反復である.

[図 8a](#figure-08) は最大バッチサイズ 2 の 3 ORCA worker 実行パイプラインを示す. リクエスト A が B より先に到着し, B が C より先, 以下同様と仮定する. 最初にスケジューラは到着時刻で A と B を選び, A と B のリクエストバッチ (バッチ AB) をエンジンに処理させる. Worker1, Worker2, Worker3 が順に処理する. スケジューラはさらに 2 バッチ CD, EF を投入してからバッチ AB の返却を待つ. AB が返ると, プールで最も早く到着した A と B が再び選ばれスケジュールされる.

対照的に現在のサービングシステムと実行エンジンのインターフェース (例: Triton [Tri21] と FasterTransformer [Fas21]) はリクエストレベルスケジューリングのため, 現在のバッチが終わる前に別バッチを投入できない. つまり現在のバッチ AB が終わるまで Triton は次のリクエスト C を FasterTransformer に投入できない. この制約下で複数の層間パーティションをパイプライン実行するため, FasterTransformer はリクエストバッチを複数マイクロバッチ [Hua19c] に分割し, パーティション実行をマイクロバッチ間でパイプライン化する.

[図 8b](#figure-08) では FasterTransformer がバッチ AB をマイクロバッチ A と B に分ける. 各パーティションは元のバッチより小さいマイクロバッチをバッチ形式で処理するため, バッチ処理の性能利得が小さくなる. またマイクロバッチサイズが大きく, マイクロバッチ数がパーティション数より少なくなると, パイプラインにバブルを挿入する可能性がある. FasterTransformer はバッチ効率 (大きいマイクロバッチ) とパイプライン効率 (少ないバブル) のトレードオフを必要とするが, ORCA は反復レベルスケジューリングのおかげでこのトレードオフがなく, バッチをマイクロバッチに分けずにリクエストを容易にパイプライン化できる.

## 5 実装

CUDA エコシステムに基づき 13K 行の C++ で ORCA を実装した. ORCA エンジンの制御プレーン通信には gRPC [Grp21], 層間・層内通信を含むデータプレーンには NCCL [Ncc21] を使う. Transformer ベース生成モデルに焦点を当てるため, ORCA は元の encoder-decoder Transformer [Vas17d], GPT [Rad19b], Raffel ら [Raf20b] が議論した他の変種などのモデル構築ブロックとして一般的な Transformer 層を提供する.

LayerNorm, Attention, GeLU 演算子には, Transformer の学習・推論システム [Dee21, Fas21, Sho19] と同様に融合 kernel も実装した. 例えば Attention の query と key の内積, 内積への Softmax, Attention value の加重平均を計算する手順を 1 つの CUDA kernel に融合する. さらに異なるリクエスト用 kernel の全スレッドブロックを単純連結し, 分割 Attention 演算子の kernel も融合する. 異なる形状のテンソルを処理するため 1 kernel 内のスレッドブロックの特性と寿命が異なる (CUDA プログラミングでは一般に推奨されない) が, この融合は GPU 利用率を向上し kernel 起動オーバーヘッドを減らすため有益だと分かった [Kwo20a, Ma20a].

FasterTransformer のパイプライン挙動を制御する追加ノブであるマイクロバッチサイズ ([セクション 4.2](#section-04-02) 参照) を変え, 最大バッチサイズ構成とともに結果を報告する.

[図 10](#figure-10) はエンドツーエンドの中央値レイテンシとスループットを示す. トレース内の各リクエストは異なる処理時間を要し, それはおおよそ生成トークン数に比例するため, 各リクエストの生成トークン数で正規化した中央値レイテンシを報告する. ORCA は FasterTransformer よりスループットが大幅に高くレイテンシが低い. 例外は低負荷の 101B モデル ([図 10a](#figure-10)) だけである. この場合両システムともバッチ処理できるリクエスト数が不足し, レイテンシは主にエンジン性能 ([図 9b](#figure-09)) に依存する. 負荷が重くなると ORCA はレイテンシを少し増やすだけで高いスループットを提供する. ORCA スケジューラが後着リクエストを進行中バッチに便乗させるためである. 対照的に FasterTransformer は (1) 到着時刻が異なる, (2) 終了に必要な反復数が異なる, (3) 入力トークン数が異なるリクエストを効率よく扱えず, 最大スループット 0.49 req/s と大幅に高いレイテンシになる. 複数の層間パーティションを使う 175B または 341B モデル ([図 10b](#figure-10) と [図 10c](#figure-10)) では, 全負荷水準で ORCA がレイテンシとスループットの両方で FasterTransformer を上回り, 同程度のレイテンシで比較するとスループットが一桁高い. 例えば 175B で中央値正規化レイテンシ 190ms ([図 9c](#figure-09) の "orca(128)" の正規化実行時間の 2 倍) に合わせると, FasterTransformer のスループットは 0.185 req/s, ORCA は 6.81 req/s で, 36.9× の高速化となる.

**バッチサイズ構成の変化.** [図 10](#figure-10) は ORCA の最大バッチサイズを増やすとレイテンシを変えずにスループットが上がることを示す. 反復レベルスケジューリングが早期終了・後加入問題を解決するためである. ただし任意のハードウェア, モデル, ワークロードでバッチサイズ増加がレイテンシを悪化させない保証はない. [セクション 4.2](#section-04-02) のとおり必要レイテンシとスループットを考慮して最大バッチサイズを慎重に設定する. FasterTransformer では最大バッチサイズを大きくしても必ずしもスループットは向上しない. 各モデルを異なる負荷で試し, max batch size (max_bs) とマイクロバッチサイズ (mbs) の全組合せを調べると (max_bs, mbs) = (1, 1) または (8, 8) が最良だった. [セクション 4.1](#section-04-01) の議論のように FasterTransformer のマイクロバッチパイプラインは効率が低くなり得る. エンジンは最大 mbs 件だけをバッチ処理するため, 最大可能な mbs (max_bs と同じ) の構成が良い理由を説明できる. また max_bs の増加はバッチサイズ増加で性能を上げる一方, 入力または生成トークン数の差が大きいリクエストを同じバッチに入れる可能性も高める. この場合 FasterTransformer はバッチを効率よく扱えない. (1) バッチの最初の反復では最短入力長と同じ長さだとみなして処理し, (2) 早期終了リクエストを直ちにクライアントへ返せないためである.

**同質リクエストのトレース.** 同じ入力トークン数と max_gen_tokens 属性を持つ同質リクエストのトレースで ORCA と FasterTransformer を試す. 全リクエストの完了に必要な反復数が同じため早期離脱問題は起きない. その結果 [図 11](#figure-11) のように max_bs 増加が FasterTransformer の性能に明確な正の効果を持つ. それでも max batch size 1 の場合を除き ORCA は FasterTransformer (max_bs=8) を上回る. batch size 1 では ORCA はバッチ処理しない ORCA worker の単純パイプラインに退化する.

**図 11.** 同質リクエストのトレースで 175B モデルを使ったエンドツーエンド中央値レイテンシとスループット. 全リクエストの特性が同じなのでレイテンシは正規化しない.

## 7 関連研究と議論

**再帰モデルの細粒度バッチ処理.** 関連性の高い先行研究として BatchMaker [Gao18a] を挙げる. BatchMaker は RNN セルの粒度でスケジューリングとバッチ処理を行う RNN サービングシステムで, 同じ計算を繰り返す RNN の特性に動機づけられている. リクエスト到着時, BatchMaker はリクエスト処理のデータフローグラフを RNN セルへ分割し, セル (グラフ全体ではなく) 粒度で実行をスケジュールし, 同一セルがあればバッチ実行する. 各 RNN セルは常に全く同じ計算を行うため, セルの位置 (トークンインデックス) に関係なく複数セルをバッチ実行できる. こうして新着 RNN リクエストを現在の実行バッチへ参加させ, 完了リクエストを離脱させる際もバッチ終了を待たずに済む.

しかし Transformer ではグラフ内の異なるセル (トークン処理の計算を包む部分グラフ; [図 1c](#figure-01)) が多すぎるため, BatchMaker はセルのバッチを作れない. 異なるトークンインデックス $t$ の各セルは異なる Attention Key/Value 集合を使う必要がある. 各 $t$ のセルが異なるためグラフには $L$ 個の異なるセル ($L$ は入力と生成トークン数) があり, ある時点で同じ計算のセルが存在する可能性が大幅に低くなる (例えば [図 10](#figure-10) で $L$ は $33=32+1$ から $640=512+128$). したがってセル実行はほぼ直列化し, BatchMaker は非バッチ実行へ戻る. また BatchMaker はモデル並列とパイプライン並列を必要とする大規模モデルをサポートしない.

BatchMaker がバッチ可能な RNN セルの検出と整列を目的とするのに対し, ORCA の設計原則はモデルパラメータを読む各ラウンドで可能な限り多く計算することである. 大規模モデルでは GPU グローバルメモリからのパラメータ読み出しがエンドツーエンド実行時間の主要ボトルネックだという洞察に基づく. この原則に従い, 反復レベルスケジューリングと選択的バッチ処理を適用し, トークンをバッチ化できるか (非 Attention 操作) どうかに関係なく, すべての "ready" トークンを 1 回のパラメータ読み出しで処理する.

**Transformer モデル向け専用実行エンジン.** Transformer ベースモデルの優れた性能は専用推論システムの開発を促した. FasterTransformer [Fas21], LightSeq [Wan21d], TurboTransformers [Fan21b], EET [Li21c] が例である. これらは Triton Inference Server [Tri21] や Tensor-Flow Serving [Ols17a] など既存サービングシステムのバックエンド実行エンジンとして振る舞う. つまりスケジューリングをサービングシステム層へ委ね, 典型的リクエストレベルスケジューリングに従う. ORCA はより細かい粒度で実行をスケジュールするが, スケジューラと実行エンジンの調整機構を変えない現在のシステムでは不可能である. これらのシステムのうち分散実行をサポートするのは FasterTransformer だけである. Megatron-LM [Sho19] と DeepSpeed [Dee21] も分散実行に使えるが, 主に推論サービングではなく大規模学習向けに最適化されている.

**サービングシステムと実行エンジンのインターフェース.** Triton Inference Server [Tri21] や Clipper [Cra17a] のような汎用サービングシステムは, クライアントリクエスト処理と基盤実行エンジンの実行スケジューリングを抽象化する. サービング層と実行層の設計・実装を分離するこの方式は有効である. しかし GPT [Bro20b] のように複数反復特性を持つモデルには, 2 層間で普及しているインターフェースが制限されすぎる. そこで ORCA はスケジューラとエンジンを密に統合し, 反復レベルスケジューリングと選択的バッチ処理という提案技術の適用を簡単にする. 本論文では抽象分離を失わずに 2 技術を支える一般インターフェース設計を研究しないが, その可能性は興味深いテーマであり将来課題とする.

## 8 結論

Transformer ベース生成モデルのサービングで低レイテンシと高スループットを達成する新しい手法として, 選択的バッチ処理を伴う反復レベルスケジューリングを示した. 反復レベルスケジューリングはスケジューラと実行エンジンの相互作用をリクエストではなく反復粒度にし, 選択的バッチ処理は異なる位置のトークンを処理する任意リクエストのバッチ化を可能にする. これは反復レベルスケジューリングにバッチ処理を適用する上で重要である. これらの技術に基づき ORCA という分散サービングシステムを設計・実装した. 実験は手法の有効性を示し, 同じレイテンシ水準で ORCA は現在の最先端システムより一桁高いスループットを提供する.
