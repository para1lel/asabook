## 要旨

長時間の対話が想定される複数ラウンド対話などのストリーミングアプリケーションに大規模言語モデル（LLM）を導入することが急務となっているが、そこには 2 つの大きな課題がある。第一に、デコード段階で過去のトークンの Key と Value の状態（KV）をキャッシュすると、大量のメモリを消費する。第二に、一般的な LLM は、学習時の系列長を超える長いテキストへ汎化できない。直近の KV だけをキャッシュするウィンドウアテンションは自然な方法だが、テキスト長がキャッシュサイズを超えると機能しないことを示す。そこで、最初のトークンの KV を保持するとウィンドウアテンションの性能がほぼ回復する「アテンションシンク」という興味深い現象を観察した。本論文ではまず、最初のトークンが意味的に重要でなくても、アテンションの「シンク」として強いアテンションスコアを受けるためにアテンションシンクが生じることを示す。この分析に基づき、*有限長*のアテンションウィンドウで学習した LLM を、ファインチューニングなしで*無限の系列長*へ汎化させる効率的なフレームワーク StreamingLLM を導入する。StreamingLLM により、Llama-2、MPT、Falcon、Pythia が 400 万トークン以上にわたって安定かつ効率的に言語モデリングできることを示す。さらに、事前学習時に専用のアテンションシンクとしてプレースホルダートークンを追加すると、ストリーミングでの運用をさらに改善できることを見いだした。ストリーミング設定では、StreamingLLM はスライディングウィンドウ再計算ベースラインを最大 $22.2\times$ 高速化する。コードとデータセットは[リンク](https://github.com/mit-han-lab/streaming-llm)で公開している。

## 1 はじめに

大規模言語モデル（LLM）[Rad18, Bro20, Zha22, Ope23, Tou23, Tou23a] は広く普及しつつあり、対話システム [Sch22, Tao23, Chi23]、文書要約 [Goy20, Zha23r]、コード補完 [Che21, Roz23]、質問応答 [Kam23a] など、多くの自然言語処理アプリケーションを支えている。事前学習済み LLM の能力を十分に引き出すには、長い系列を効率よく正確に生成できなければならない。たとえば、理想的な ChatBot アシスタントは、直近一日分の会話内容にわたって安定して動作できる。しかし LLM にとって、Llama-2 [Tou23a] の 4K など、事前学習時より長い系列長へ汎化することはきわめて難しい。

これは、LLM が事前学習時のアテンションウィンドウに制約されるためである。このウィンドウサイズを拡張する取り組み [Che23x, Kai23, Pen23] や、長い入力に対する学習 [Dao22, Dao23a] と推論 [Pop22, Xia23, Ana23, Wan21f, Zha23g] の効率を改善する取り組みが数多く行われているものの、扱える系列長は本質的に*有限*であり、永続的な運用には適さない。

本論文ではまず、LLM のストリーミングアプリケーションという概念を導入し、次の問いを立てる。

> *効率と性能を犠牲にせず、無限長の入力に対して LLM を運用できるだろうか？*

LLM を無限の入力ストリームへ適用すると、主に 2 つの課題が生じる。

1. [図 1](#figure-01)（a）に示すように、Transformer ベースの LLM はデコード段階で過去の全トークンの Key と Value の状態（KV）をキャッシュするため、メモリ使用量が過大になり、デコード遅延も増加しうる [Pop22]。
2. 既存モデルの長さ外挿能力には限界があり、系列長が事前学習時に設定されたアテンションウィンドウサイズを超えると性能が低下する [Pre21, Che23x]。

ウィンドウアテンション [Bel20]（[図 1](#figure-01)b）と呼ばれる直感的な方法は、直近のトークンの KV 状態だけを固定サイズのスライディングウィンドウに保持する。キャッシュが最初に満たされた後はメモリ使用量とデコード速度を一定に保てるが、[図 3](#figure-03)に示すように、系列長がキャッシュサイズを超えると、すなわち*最初のトークンの KV を一つ追い出すだけでも*モデルは破綻する。もう一つの方法は、[図 1](#figure-01)c に示す再計算付きスライディングウィンドウであり、トークンを一つ生成するたびに直近のトークンの KV 状態を再構築する。この方法は高い性能を示す一方、ウィンドウ内で二次のアテンション計算を行うため著しく遅く、実用的なストリーミングアプリケーションには向かない。

<span id="figure-01"></span>

![StreamingLLM と既存手法の比較](../../papers/streaming-llm/figure-01.png)

**図 1.** **StreamingLLM と既存手法の比較。** 長さ $L$ のテキストで事前学習した言語モデルが、第 $T$ トークン（$T\gg L$）を予測する。（a）Dense Attention の時間計算量は $O(T^2)$ で、キャッシュサイズは増え続ける。テキスト長が事前学習時のテキスト長を超えると性能が低下する。（b）Window Attention は直近 $L$ トークンの KV をキャッシュする。推論は効率的だが、先頭トークンの Key と Value が追い出されると性能が急落する。（c）Sliding Window with Re-computation は、新しいトークンごとに直近 $L$ トークンから KV 状態を再構築する。長いテキストでも高い性能を示す一方、コンテキストの再計算に二次のアテンションを含むため計算量は $O(T L^2)$ となり、かなり遅い。（d）StreamingLLM は安定したアテンション計算のために*アテンションシンク*（複数の最初のトークン）を直近のトークンとともに保持する。効率がよく、長いテキストでも性能が安定する。パープレキシティは、PG-19 テストセットの最初の一冊（65K トークン）を対象に Llama-2-13B モデルで測定した。

ウィンドウアテンションが機能しない理由を調べると、自己回帰 LLM に興味深い現象が見つかった。すなわち、[図 2](#figure-02)に示すように、言語モデリングタスクとの関連性にかかわらず、驚くほど大きなアテンションスコアが最初のトークンに割り当てられる。これらのトークンを「**アテンションシンク**」と呼ぶ。意味的な重要性はないにもかかわらず、大きなアテンションスコアを集めるのである。その理由は、すべてのコンテキストトークンに対するアテンションスコアの合計を 1 にする必要がある SoftMax 演算にあると考える。したがって、現在のクエリと強く一致する過去のトークンがほとんどなくても、合計を 1 にするため、モデルは不要なアテンション値をどこかへ割り当てなければならない。*最初の*トークンがシンクトークンになる理由は直感的である。自己回帰言語モデリングの性質上、最初のトークンはほぼすべての後続トークンから見えるため、アテンションシンクとして働くよう学習されやすい。

この知見に基づき、有限のアテンションウィンドウで学習した LLM を、ファインチューニングせず無限長のテキスト上で動作させる簡潔で効率的なフレームワーク StreamingLLM を提案する。StreamingLLM は、アテンションシンクが高いアテンション値を持つことを利用し、これらを保持することでアテンションスコアの分布を通常時に近く保つ。そのため StreamingLLM は、アテンション計算の基準点となりモデル性能を安定させるため、アテンションシンクトークンの KV（最初の 4 トークンだけで十分）をスライディングウィンドウの KV とともに保持する。StreamingLLM により、Llama-2-[7, 13, 70]B、MPT-[7, 30]B、Falcon-[7, 40]B、Pythia-[2.9, 6.9, 12]B などのモデルは 400 万トークンを確実にモデル化でき、さらに長い系列も扱える可能性がある。実行可能な唯一のベースラインである再計算付きスライディングウィンドウと比べ、StreamingLLM は最大 $22.2\times$ の高速化を達成し、LLM のストリーミング利用を実現する。

さらに、アテンションシンクに関する仮説を確認し、ストリーミング運用に必要なアテンションシンクトークンを一つだけにするよう言語モデルを事前学習できることを示す。具体的には、すべての学習サンプルの先頭に追加する学習可能なトークンを、専用のアテンションシンクとして用いることを提案する。1 億 6000 万パラメータの言語モデルを一から事前学習し、このシンクトークンを一つ追加すると、ストリーミング時にもモデル性能が保たれることを示す。これは、同じ性能を得るために複数の最初のトークンをアテンションシンクとして再導入する必要がある通常のモデルとは対照的である。

<span id="figure-02"></span>

![Llama-2-7B の平均アテンションロジット](../../papers/streaming-llm/figure-02.png)

**図 2.** 長さ 16 の文 256 件について、Llama-2-7B の*平均*アテンションロジットを可視化した。次の点が観察される。（1）最初の 2 層（層 0 と 1）のアテンションマップは、直近のトークンがより多くのアテンションを受ける「局所」パターンを示す。（2）下位 2 層より上では、すべての層とヘッドでモデルが最初のトークンへ強くアテンションを向ける。

最後に、StreamingLLM は LLM のコンテキスト長を拡張するのではなく、KV キャッシュ内のトークンから一貫したテキストを効率よく生成する手法であることを強調する。メモリ使用量と過去データへの依存を抑えながら継続的に動作させる用途に適している。また、StreamingLLM はコンテキスト拡張手法と組み合わせ、参照可能な直近コンテキストを広げることもできる。

## 2 関連研究

LLM を長いテキストへ適用する研究は幅広く行われており、主に**長さ外挿**、**コンテキストウィンドウ拡張**、**LLM による長いテキストの利用改善**という 3 領域に分かれる。これらは関連して見えるが、一方向の進展が必ずしも別方向の進展につながるわけではない点に注意が必要である。たとえば、LLM のコンテキストサイズを拡張しても、そのサイズを超えたときのモデル性能は改善せず、いずれの方法も長いコンテキストの有効利用を保証しない。本研究の StreamingLLM フレームワークは主に最初の領域に属し、事前学習時のウィンドウサイズを大幅に超え、無限長にもなりうるテキストへ LLM を適用する。LLM のアテンションウィンドウサイズを拡張するものでも、長いテキストに対するモデルの記憶や利用能力を強化するものでもない。後二者の領域は本研究の焦点と直交しており、本手法と統合できる。

**長さ外挿**は、短いテキストで学習した言語モデルがテスト時に長いテキストを扱えるようにすることを目指す。主要な研究方向の一つは、Transformer モデルが学習時のウィンドウを超えて動作できるようにする相対位置エンコーディング手法の開発である。その一例である Rotary Position Embeddings（RoPE）[Su21] は、各アテンション層のクエリと Key を変換して相対位置を取り込む。有望ではあるものの、その後の研究 [Pre21, Che23x] では、学習時のウィンドウを超えるテキスト上で性能が低下することが示された。別の手法である ALiBi [Pre21] は、クエリと Key の距離に基づいてアテンションスコアへバイアスを加え、相対位置情報を導入する。この手法は外挿性能を改善したが、MPT モデルでの実験では、テキスト長が学習時の長さを大幅に超えると破綻した。しかし、既存手法はいずれも無限の長さ外挿には達しておらず、ストリーミングアプリケーションに適した LLM は存在しない。

**コンテキストウィンドウ拡張**は、LLM のコンテキストウィンドウを広げ、一回の順伝播でより多くのトークンを処理できるようにする。主要な研究方向の一つは学習効率の問題を扱う。学習時のアテンション計算量は二次であるため、長いコンテキストを持つ LLM の開発は、計算量とメモリの両面で難しい。解決策には、アテンション計算を高速化してメモリ使用量を削減する FlashAttention [Dao22, Dao23a] のようなシステム面の最適化から、モデル品質と引き換えに効率を得る近似アテンション手法 [Zah20, Bel20, Wan20a, Kit20] まである。近年は、RoPE を用いた位置補間とファインチューニングにより、事前学習済み LLM を拡張する研究 [Che23x, Kai23, Blo23a, Pen23] が急増している。しかし、以上の手法が拡張できる LLM のコンテキストウィンドウはいずれも有限であり、無制限の入力を扱うという本論文の主題には及ばない。

**LLM による長いテキストの利用改善**は、コンテキストを単に入力として受け取るだけでなく、その内容をよりよく捉えて利用できるよう LLM を最適化する。Liu ら [Liu23z] と LongChat [Li23h] が指摘するように、先の二方向で成功しても、長いコンテキストを有効に利用できるとは限らない。LLM で長いコンテキストを有効利用することは、依然として課題である。本研究では、直近のトークンを安定して活用し、LLM を連続的にストリーミング利用できるようにすることに焦点を当てる。

## 3 StreamingLLM

<span id="figure-03"></span>

![20K トークンのテキストにおける言語モデリングのパープレキシティ](../../papers/streaming-llm/figure-03.png)

**図 3.** 複数の LLM について、20K トークンのテキストにおける言語モデリングのパープレキシティを示す。共通して次の傾向が見られる。（1）入力長が事前学習時のアテンションウィンドウサイズを超えると、Dense Attention は機能しなくなる。（2）入力長がキャッシュサイズを超え、最初のトークンが追い出されると、Window Attention は破綻する。（3）StreamingLLM は安定した性能を示し、そのパープレキシティは Sliding Window with Re-computation ベースラインとほぼ一致する。

<span id="section-3-1"></span>

### 3.1 ウィンドウアテンションの失敗とアテンションシンク

ウィンドウアテンションは推論時の効率がよい一方、言語モデリングのパープレキシティが極端に高くなる。そのため、モデル性能はストリーミングアプリケーションでの運用に適さない。本節では、ウィンドウアテンションが失敗する理由をアテンションシンクという概念で説明する。この考察が StreamingLLM の着想となった。

**パープレキシティが急増する地点の特定。** [図 3](#figure-03)は、20K トークンのテキストにおける言語モデリングのパープレキシティを示す。テキスト長がキャッシュサイズを超え、最初のトークンが除外されるとパープレキシティが急増することは明らかである。これは、予測対象トークンからの距離にかかわらず、最初のトークンが LLM の安定性を保つうえで不可欠であることを示唆する。

**なぜ*最初の*トークンの KV を削除すると LLM は破綻するのか？** [図 2](#figure-02)に、Llama-2-7B モデルの全層・全ヘッドのアテンションマップを可視化する。下位 2 層より上では、すべての層とヘッドでモデルが一貫して最初のトークンに注目している。この結果が意味することは明瞭である。最初のトークンの KV を削除すると、アテンション計算における SoftMax 関数（[式 1](#equation-01)）の分母から相当な部分が失われる。この変化により、アテンションスコアの分布は通常の推論時に期待されるものから大きくずれる。

<span id="equation-01"></span>

$$
\mathrm{SoftMax}(x)_i = \frac{e^{x_i}}{e^{x_1} + \sum_{j=2}^{N} e^{x_j}}, \quad x_1 \gg x_j, j \in 2, \dots, N
$$

言語モデリングで最初のトークンが重要となる理由には、2 つの可能性がある。（1）その意味内容が重要であるか、（2）モデルがその絶対位置へのバイアスを学習しているかである。両者を区別するため、最初の 4 トークンを改行トークン `\n` に置き換える実験を行う（[表 1](#table-01)）。その場合も、モデルは最初の改行トークンを大きく重視した。さらに、それらを再導入すると、言語モデリングのパープレキシティは元の最初のトークンを保持した場合と同程度まで回復した。この結果は、先頭トークンの意味内容より、その絶対位置のほうが重要であることを示唆する。

**LLM は最初のトークンをアテンションシンクとして参照する。** モデルが言語モデリングとの意味的関連性にかかわらず最初のトークンへ過度に注目する理由を説明するため、「*アテンションシンク*」という概念を導入する。SoftMax 関数（[式 1](#equation-01)）の性質上、参照するすべてのトークンにゼロを割り当てることはできない。したがって、現在の埋め込みが予測に必要な情報を単独で十分に含んでいても、全層・全ヘッドで他のトークンから何らかの情報を集約する必要がある。その結果、モデルは不要なアテンション値を特定のトークンへ捨てる傾向を持つ。量子化における外れ値でも同様の観察 [Xia23, Bon23] がなされており、解決策の候補として SoftMax-Off-by-One [Mil23] が提案されている。

![長いテキストに対するウィンドウアテンションの性能](../../papers/streaming-llm/table-01.png)

**表 1.** ウィンドウアテンションは長いテキストで性能が低い。直近の 1020 トークンとともに最初の 4 トークンを再導入すると（4+1020）、パープレキシティは回復する。元の最初の 4 トークンを改行トークン `\n` に置き換えた場合（4`\n`+1020）も、同程度までパープレキシティが回復する。キャッシュ構成 $x$+$y$ は、最初の $x$ トークンと直近の $y$ トークンを追加することを表す。パープレキシティは、PG19 テストセットの最初の一冊（65K トークン）で測定した。

<span id="table-02"></span>

![再導入する最初のトークン数が StreamingLLM に与える影響](../../papers/streaming-llm/table-02.png)

**表 2.** 再導入する最初のトークン数が StreamingLLM に与える影響。（1）Window Attention（0+$y$）ではパープレキシティが急増する。（2）最初のトークンを一つまたは二つ導入するだけではモデルのパープレキシティが完全には回復せず、モデルが最初の一トークンだけをアテンションシンクとして利用しているわけではないことが分かる。（3）最初の 4 トークンを導入すれば通常は十分であり、それ以上追加しても効果は逓減する。キャッシュ構成 $x$+$y$ は、最初の $x$ トークンを直近の $y$ トークンに追加することを表す。パープレキシティは、連結した PG19 テストセットの 400K トークンで評価した。

Llama-2、MPT、Falcon、Pythia など、さまざまな自己回帰 LLM が、なぜ他のトークンではなく一貫して*最初のトークン*をアテンションシンクとして参照するのだろうか？ 私たちの説明は単純である。自己回帰言語モデリングは逐次的であるため、最初のトークンはすべての後続トークンから見えるのに対し、後半のトークンは限られた数の後続トークンからしか見えない。その結果、最初のトークンは不要なアテンションを集めるアテンションシンクとして学習されやすい。

LLM は通常、一つではなく複数の最初のトークンをアテンションシンクとして利用するよう学習されている。[表 2](#table-02)に示すように、最初の 4 トークンをアテンションシンクとして導入すれば LLM の性能は回復するが、一つまたは二つだけでは完全に回復しない。このパターンが生じるのは、事前学習時に、すべての入力サンプルで共通する開始トークンがこれらのモデルに含まれていなかったためだと考える。Llama-2 は各段落に ``<s>`` トークンを付加するが、テキストをチャンク分割する前に付加するため、0 番目の位置はほぼランダムなトークンになる。このように一様な開始トークンがないため、モデルは複数の最初のトークンをアテンションシンクとして使う。すべての学習サンプルの先頭に一貫した学習可能トークンを追加すれば、その一つだけが専用のアテンションシンクとして働き、一貫したストリーミングのために複数の最初のトークンを必要としなくなると仮定する。この仮説は [第 3.3 節](#section-3-3)で検証する。

### 3.2 アテンションシンクを備えたローリング KV キャッシュ

<span id="figure-04"></span>

![StreamingLLM の KV キャッシュ](../../papers/streaming-llm/figure-04.png)

**図 4.** StreamingLLM の KV キャッシュ。

学習済み LLM で LLM ストリーミングを実現するため、モデルをファインチューニングせずにウィンドウアテンションのパープレキシティを回復できる単純な手法を提案する。現在のスライディングウィンドウ内のトークンに加え、アテンション計算へ最初の数トークンの KV を再導入する。[図 4](#figure-04)に示すように、StreamingLLM の KV キャッシュは概念上、2 つの部分に分けられる。（1）アテンションシンク（最初の 4 トークン）がアテンション計算を安定させる。（2）Rolling KV Cache が言語モデリングに不可欠な直近のトークンを保持する。StreamingLLM の設計は汎用的で、RoPE [Su21] や ALiBi [Pre21] などの相対位置エンコーディングを用いる任意の自己回帰言語モデルへそのまま組み込める。

相対距離を決め、トークンへ位置情報を加えるとき、StreamingLLM は*元のテキスト内*の位置ではなく、*キャッシュ内*の位置を用いる。この違いは StreamingLLM の性能に欠かせない。たとえば、現在のキャッシュ（[図 4](#figure-04)）にトークン [0, 1, 2, 3, 6, 7, 8] があり、第 9 トークンをデコードしている場合、割り当てる位置は [0, 1, 2, 3, 4, 5, 6, 7] となる。元のテキスト内の位置 [0, 1, 2, 3, 6, 7, 8, 9] ではない。

RoPE のようなエンコーディングでは、回転変換を導入する*前*のトークンの Key をキャッシュする。その後、各デコード段階でローリングキャッシュ内の Key に位置変換を適用する。一方、ALiBi との統合はより直接的である。ここでは、アテンションスコアに「飛び飛び」のバイアスではなく連続した線形バイアスを適用する。このようにキャッシュ内で位置埋め込みを割り当てる方法は StreamingLLM の機能に不可欠であり、事前学習時のアテンションウィンドウサイズを超えてもモデルを効率よく動作させられる。

### 3.3 アテンションシンクを用いた LLM の事前学習

<span id="table-03"></span>

![通常のアテンションと Zero Sink および学習可能な Sink Token の比較](../../papers/streaming-llm/table-03.png)

**表 3.** 事前学習時にゼロトークンまたは学習可能なシンクトークンを先頭へ付加した場合と、通常のアテンションとの比較。ストリーミング時のパープレキシティを安定させるには、通常のモデルでは複数の最初のトークンが必要になる。Zero Sink はわずかに改善するが、それでも他の最初のトークンを必要とする。一方、学習可能な Sink Token で学習したモデルは、シンクトークンだけを加えればストリーミング時のパープレキシティが安定する。キャッシュ構成 $x$+$y$ は、最初の $x$ トークンと直近の $y$ トークンを追加することを表す。パープレキシティは PG19 テストセットの最初のサンプルで評価した。

[第 3.1 節](#section-3-1)で述べたように、モデルが複数の最初のトークンへ過度のアテンションを向ける大きな理由は、余分なアテンションスコアを受け止める専用のシンクトークンがないことにある。このため、モデルは意図せず、全位置から見えるトークン、主に最初のトークンをアテンションシンクとして用いる。解決策の一つは、不要なアテンションスコアの受け皿となる学習可能な大域的アテンションシンクトークンを意図的に組み込み、これを「Sink Token」とすることである。別の方法として、通常の SoftMax 関数を SoftMax-off-by-One [Mil23] のような変種へ置き換えることも考えられる。

<span id="equation-02"></span>

$$
\mathrm{SoftMax}_1(x)_i = \frac{e^{x_i}}{1+\sum_{j=1}^{N} e^{x_j}},
$$

この関数では、すべてのコンテキストトークンに対するアテンションスコアの合計を 1 にする必要がないため、同様に有効な可能性がある。$\mathrm{SoftMax}_1$ は、アテンション計算で Key と Value の特徴量がすべてゼロのトークンを先頭に付加することと等価である。本フレームワークに合わせ、この手法を「Zero Sink」と呼ぶ。

検証のため、同一設定のもとで 1 億 6000 万パラメータの言語モデルを 3 つ一から事前学習する。第 1 のモデルは標準の SoftMax アテンション（Vanilla）を用い、第 2 のモデルは通常のアテンション機構を $\mathrm{SoftMax}_1$（Zero Sink）へ置き換え、第 3 のモデルはすべての学習サンプルに学習可能なプレースホルダートークン（Sink Token）を付加する。[表 3](#table-03)に示すように、Zero Sink はアテンションシンクの問題をある程度軽減するが、それでもモデルは他の最初のトークンをアテンションシンクとして利用する。Sink Token の導入は、アテンション機構の安定化にきわめて有効である。この Sink Token を直近のトークンと組み合わせるだけでモデル性能を十分に安定させられ、評価時のパープレキシティもわずかながら改善する。以上を踏まえ、今後の LLM では、ストリーミング運用を最適化するため、すべてのサンプルに Sink Token を含めて学習することを推奨する。

## 4 実験

StreamingLLM を、近年の代表的な 4 つのモデルファミリー、Llama-2 [Tou23a]、MPT [Mos23]、Pythia [Bid23]、Falcon [Alm23] を用いて評価する。Llama-2、Falcon、Pythia は RoPE [Su21] を採用し、MPT は ALiBi [Pre21] を採用している。いずれも近年の研究で大きな影響を与えた位置エンコーディング手法である。多様なモデルを選ぶことで、知見の妥当性と頑健性を確かめる。StreamingLLM を、Dense Attention、Window Attention、Sliding Window with Re-computation などの既存ベースラインと比較する。以下の StreamingLLM の実験では、別途記載がない限り、デフォルトで最初の 4 トークンをアテンションシンクとして用いる。

### 4.3 Instruction-tuned モデルによるストリーミング質問応答の結果

StreamingLLM を実環境へ適用できることを示すため、実際によく用いられる Instruction-tuned LLM を使い、複数ラウンドの質問応答を再現する。

まず ARC-[Challenge, Easy] データセットの全質問・回答ペアを連結し、その連続ストリームを Llama-2-[7, 13, 70]B-Chat モデルへ入力して、各回答位置のモデル出力を完全一致基準で評価する。[表 5](#table-05)に示すように、Dense Attention は Out-of-Memory（OOM）エラーを起こすため、この設定には適さない。Window Attention は効率よく動作するが、入力長がキャッシュサイズを超えるとランダムな出力を生成するため精度が低い。対照的に、StreamingLLM はストリーミング形式を効率よく処理し、サンプルを一つずつ扱う one-shot ベースラインと同等の精度を示す。

StreamingLLM により適した状況を示すため、LongEval [Li23h] ベンチマークに着想を得たデータセット StreamEval を導入する。[図 8](#figure-08)に示すように、長い範囲にわたってクエリを一度だけ行う LongEval とは異なり、新しい情報を 10 行入力するたびにモデルへ問い合わせる。各クエリの答えは常に 20 行前にあり、質問が通常は直近の情報に関するものである実環境を再現する。[図 9](#figure-09)に示すように、StreamingLLM を用いた LLM は、入力長が 120K トークンへ近づいても妥当な精度を保つ。対照的に、Dense Attention と Window Attention は、それぞれ事前学習時のテキスト長と KV キャッシュサイズに達すると機能しなくなる。さらに、コンテキストを拡張した 2 つのモデル、LongChat-7b-v1.5-32k [Li23h] と Llama-2-7B-32K-Instruct [Tog23] を用い、StreamingLLM がコンテキスト拡張手法と組み合わせられることを示す。StreamingLLM におけるコンテキスト拡張とは、ストリーミング LLM の最大キャッシュサイズを広げ、より広い局所情報を捉えられるようにすることを意味する。

### 4.5 効率の結果

<span id="figure-10"></span>

![Sliding Window with Re-computation と StreamingLLM のデコード遅延とメモリ使用量の比較](../../papers/streaming-llm/figure-10.png)

**図 10.** Sliding Window with Re-computation ベースラインと StreamingLLM のトークンあたりデコード遅延およびメモリ使用量を比較し、X 軸にキャッシュサイズ（アテンションウィンドウサイズ）を示す。StreamingLLM はトークンあたり最大 $22.2\times$ の高速化を達成し、再計算ベースラインと同程度のメモリ使用量を保つ。

StreamingLLM のデコード遅延とメモリ使用量を、許容できる品質を持つ唯一のベースラインである Sliding Window with Re-computation と比較する。両手法を HuggingFace Transformers ライブラリ [Wol20] で実装し、Llama-2-7B と Llama-2-13B モデルを用いて NVIDIA A6000 GPU 1 基でテストした。[図 10](#figure-10)に示すように、キャッシュサイズの増加に対し、StreamingLLM のデコード遅延は線形に増加する。Sliding Window with Re-computation ベースラインのデコード遅延は二次的に増加する。したがって、StreamingLLM はトークンあたり最大 $22.2\times$ という大幅な高速化を達成する。遅延を削減しながら、StreamingLLM のメモリ使用量は再計算ベースラインと同程度に保たれる。

## 5 結論

LLM をストリーミングアプリケーションへ導入することが急務となっているが、効率上の制約と、テキストが長くなったときの性能低下という課題がある。Window Attention は部分的な解決策となるものの、最初のトークンを除外すると性能が急落する。これらのトークンが「アテンションシンク」として働くことを認識し、LLM がファインチューニングなしで無制限のテキストを扱えるようにする単純で効率的なフレームワーク StreamingLLM を導入した。直近のトークンとともにアテンションシンクを追加することで、StreamingLLM は最大 400 万トークンのテキストを効率よくモデル化できる。さらに、専用の Sink Token を用いてモデルを事前学習すると、ストリーミング性能を改善できることを示した。StreamingLLM は初めて LLM の事前学習時のウィンドウサイズと実際のテキスト生成長を切り離し、LLM のストリーミング運用への道を開く。

**再現性に関する声明。** 本論文で示した知見はすべて再現できる。コードとデータセットは、この [GitHub リポジトリ](https://github.com/mit-han-lab/streaming-llm)で公開している。本論文で使用したモデルはすべて公開されており、その入手先も示している。ハイパーパラメータ、学習プロトコル、評価方法など、実験の詳細は実験節（[第 4 節](#section-4)）に記載している。提供した資源を用いれば、読者は提示した結果をすべて再現できると確信している。

**影響に関する声明。** StreamingLLM は、[NVIDIA TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM/tree/main/examples/llama#run-llama-with-streamingllm)、[Intel Extension for Transformers](https://github.com/intel/intel-extension-for-transformers)、[HuggingFace Transformers](https://huggingface.co/docs/transformers/v4.39.3/en/internal/generation_utils#transformers.SinkCache)、[MLC LLM](https://github.com/mlc-ai/mlc-llm/pull/1459) など、さまざまな LLM サービングソリューションで広く採用されている。

## 6 議論

**応用。** StreamingLLM は、複数ラウンド対話など、大容量のメモリや過去データへ強く依存せず継続的に動作することが重要なストリーミングアプリケーションに特に適している。たとえば、LLM ベースの日常アシスタントアプリケーションでは、StreamingLLM によりモデルを長期間途切れずに動作させられる。応答は直近のやり取りに基づくため、キャッシュを頻繁に更新する必要がない。従来手法では、会話長が学習時の長さを超えるとキャッシュをリセットして直近のコンテキストを失うか、直近のテキスト履歴から Key-Value（KV）状態を再計算する必要があり、効率が悪い場合がある。

**制約。** StreamingLLM はストリーミング環境で LLM の効率を改善するが、モデルのコンテキストウィンドウを拡張するものでも、長期記憶能力を強化するものでもない。[第 8 節](#section-8)で詳述するように、モデルは現在のキャッシュ内でしか動作できない。そのため StreamingLLM は、長文書の質問応答（QA）や要約など、長期記憶と広範なデータ依存を必要とするタスクには適さない。一方、日常会話や短い文書の QA のように短期記憶だけを必要とする状況には優れており、キャッシュを更新せず直近のコンテキストから一貫したテキストを生成できる点が強みである。

**より広い社会的影響。** StreamingLLM は LLM の効率と利用しやすさを大きく改善し、さまざまな分野での利用を広げる。対話エージェントなどのアプリケーションで継続的かつ高速なやり取りを可能にすることで、StreamingLLM は、特に固定長モデルを必要とする状況でユーザー体験を改善する。この進歩により、より滑らかで文脈を踏まえた対話が可能となり、教育、医療、顧客サービスなどの分野に恩恵をもたらす可能性がある。また、StreamingLLM の処理効率は計算負荷を削減し、環境面で持続可能な AI 技術の必要性にも沿う。この点は、技術資源が限られた地域で高度な AI ツールを利用しやすくするうえで重要である。ただし、StreamingLLM がもたらしうる悪影響は、誤情報や偏ったコンテンツを生成するリスクなど、一般的な言語モデルに伴うものと同じである。強固な倫理指針と安全対策によって、こうしたリスクへ対処することが不可欠である。まとめると、StreamingLLM は言語モデルに共通するリスクの一部を持つものの、ユーザー体験の改善、AI 利用の普及、持続可能性の促進に寄与する。こうした利点は、この技術を責任ある形で運用し、倫理的に利用する重要性を示している。

## 7 追加の関連研究

**Sparse Transformer。** 効率的な Transformer モデルに関する文献は、主に自己アテンション機構の計算量とメモリ量を削減することへ焦点を当てている。関連する一連の研究では、局所ウィンドウや固定ストライドのブロックパターンなど、固定の事前定義パターンへ視野を制限することでアテンション行列を疎にする [Tay22a]。Sparse Transformer [Chi19] はアテンション行列の疎な因数分解を導入し、アテンションの計算量を $O(n\sqrt{n})$ へ削減する。LongFormer [Bel20] は、拡張された局所ウィンドウアテンションと、タスクに応じた大域アテンションを組み合わせる。Extended Transformer Construction（ETC）[Ain20] は、大域から大域、局所から局所、局所から大域、大域から局所という 4 種類のアテンションパターンを組み込んだ新しい大域・局所アテンション機構を提示する。ETC を基礎として、BigBird [Zah20] は、大域トークン、局所スライディングウィンドウアテンション、ランダムアテンションを用いる、もう一つの線形計算量アテンションを提案する。しかし、これらの手法には複数の制約がある。第一に、Sparse Transformer と ETC は、特定のブロック疎な行列積に対応するカスタム GPU カーネルを必要とする。第二に、LongFormer、ETC、BigBird はいずれも大域アテンションパターンへ依存しており、自己回帰言語モデルには適さない。第三に、これらの手法は事前学習済みモデルと互換性がなく、一から再学習する必要がある。対照的に、本手法は標準 GPU カーネルで容易に実装でき、NLP コミュニティで広く使われている Dense Attention ベースの事前学習済み自己回帰言語モデルと互換性がある。この互換性には、既存の事前学習済みモデルをファインチューニングなしで活用できるという大きな利点がある。

**同時期の研究。** 本研究と Han ら [Han23x] の研究は同時期に行われた。同研究は言語モデルにおける長さ汎化の失敗を理論的に研究し、3 つの分布外要因を特定した。この分析に基づく手法では、「$\Lambda$」字型のアテンションパターンを用い、位置エンコーディング距離を再構成して、LLM の長さ汎化を改善する。この手法は本研究の方法と似ている。一方、本研究は、Transformer モデルが意味内容の少ない最初のトークンへ高いアテンションスコアを割り当てる「アテンションシンク」現象を明らかにする。この現象は長さ汎化の失敗という範囲を超え、Transformer モデルにより広く存在する問題を示す。この「アテンションシンク」の挙動は自己回帰言語モデルだけでなく、BERT（[第 13 節](#section-13)を参照）などの Encoder Transformer や Vision Transformer（ViT）[Dar23a] でも観察され、Transformer アーキテクチャに広く存在することが示唆される。「アテンションシンク」現象を抑えるため、事前学習時に学習可能な Sink Token を導入することを提案し、広範なアブレーション研究によって知見を裏付ける。

これと並行して、Darcet ら [Dar23a] は Vision Transformer において、ランダムな背景パッチトークンへ同様にアテンションが集中する現象を観察し、これを「register」と呼んだ。この register は大域的な画像情報の受け皿として働く。同研究は、専用の「register」トークンを追加してアテンション分布を均衡させる。本研究で見いだした「アテンションシンク」は、この概念と対応する。本論文の「アテンションシンク」は、後続トークンから不釣り合いに多くのアテンションを集める最初のトークンである。事前学習時に専用の Sink Token を導入すると、モデルがコンテンツトークンを不適切にアテンションシンクとして用いることを防ぎ、アテンションをより有効に分配できる。ただし、重要な相違もある。Vision Transformer の「register」は中間層で大域情報の保持器として機能するのに対し、本研究の「アテンションシンク」は自己回帰モデルの最初のトークンとして配置される。この位置の違いは、アテンション計算の SoftMax 関数が、アテンションシンクの出現により本質的な役割を果たしている可能性を示唆する。

## 14 事前学習段階でより多くの Sink Token を用いる

[第 3.3 節](#section-3-3)では、事前学習段階で専用の Sink Token を一つ組み込んでもモデル性能へ影響せず、アテンションシンクを一つのトークンへ集中させることでストリーミング性能が改善することを示した。本節では、事前学習時にさらに多くの Sink Token を追加すると、事前学習済み言語モデルの性能をさらに最適化できるかを検討する。

[図 15](#figure-15)に示すように、事前学習時に一つまたは二つの Sink Token を組み込むと、いずれもベースライン（Vanilla）モデルとよく似た事前学習損失曲線を示す。しかし、[表 9](#table-09)に示すように、2 番目の Sink Token を導入しても、ほとんどのベンチマークタスクで性能は大きく改善しない。

さらに [表 10](#table-10)で分析すると、追加の Sink Token を組み込んでもストリーミング性能は改善しないことが分かる。興味深いことに、安定したストリーミング性能を保つため、モデルは両方の Sink Token に依存するように見える。これらの知見は、一つの Sink Token でストリーミング性能を改善するには十分だが、追加しても言語モデル全体の性能はそれ以上向上しないことを示す。これは、複数の「register」が有用だとされる Vision Transformer（ViT）[Dar23a] の知見と対照的である。
