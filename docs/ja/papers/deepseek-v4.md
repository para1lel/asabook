## 概要

DeepSeek-V4 シリーズのプレビュー版として、高性能な二つの Mixture-of-Experts（MoE）言語モデル、すなわち 1.6T パラメータ（49B をアクティブ化）の DeepSeek-V4-Pro と、284B パラメータ（13B をアクティブ化）の DeepSeek-V4-Flash を提示します。いずれも 100 万トークンのコンテキスト長をサポートします。DeepSeek-V4 シリーズでは、アーキテクチャと最適化に複数の重要な改良を加えています。(1) Compressed Sparse Attention（CSA）と Heavily Compressed Attention（HCA）を組み合わせ、長いコンテキストの効率を高めるハイブリッドアテンションアーキテクチャ、(2) 従来の残差接続を強化する Manifold-Constrained Hyper-Connections（*m*HC）、(3) 収束の高速化と学習安定性の向上を実現する Muon オプティマイザです。二つのモデルは、多様で高品質な 32T トークンを超えるデータで事前学習し、その後、能力を引き出してさらに高める包括的な後学習パイプラインを適用します。DeepSeek-V4-Pro の最高推論強度モードである DeepSeek-V4-Pro-Max は、オープンモデルの最先端を塗り替え、主要タスクで前世代モデルを上回ります。同時に、DeepSeek-V4 シリーズは長いコンテキストのシナリオで高い効率を発揮します。100 万トークンのコンテキスト設定では、DeepSeek-V4-Pro が必要とする単一トークン推論 FLOPs は DeepSeek-V3.2 の 27%、KV キャッシュは 10% にすぎません。これにより 100 万トークンのコンテキストを通常運用でサポートでき、長期タスクとさらなるテスト時スケーリングがより現実的になります。モデルのチェックポイントは [https://huggingface.co/collections/deepseek-ai/deepseek-v4](https://huggingface.co/collections/deepseek-ai/deepseek-v4) で公開しています。

## 1 はじめに

推論モデル [Ope24, Guo25] の登場はテスト時スケーリングという新たなパラダイムを確立し、大規模言語モデル（LLM）の性能を大幅に向上させました。しかし、このスケーリングパラダイムは標準的なアテンション機構 [Vas17] が持つ二次の計算量によって根本的に制約され、超長コンテキストと推論過程に実用上許容できないボトルネックを生じさせます。同時に、複雑なエージェントワークフローから大規模な文書横断分析まで、長期にわたるシナリオやタスクの登場により、超長コンテキストを効率よくサポートすることも今後の進歩に不可欠となりました。近年のオープンソースの取り組み [Dee24a, Yan25a, Min25, Kim25] は汎用能力を前進させてきましたが、超長系列を扱ううえでのこの根本的なアーキテクチャ効率の低さは依然として主要な障害であり、テスト時スケーリングによるさらなる向上を制限し、長期シナリオやタスクのさらなる探究を妨げています。

超長コンテキストにおける効率の壁を打破するため、1.6T パラメータ（49B をアクティブ化）の DeepSeek-V4-Pro と、284B パラメータ（13B をアクティブ化）の DeepSeek-V4-Flash のプレビュー版を含む DeepSeek-V4 シリーズを開発しました。アーキテクチャ上の革新により、DeepSeek-V4 シリーズは超長系列を処理する計算効率を飛躍的に高めています。このブレークスルーによって 100 万トークンのコンテキスト長を効率的にサポートでき、次世代 LLM に 100 万トークン級コンテキストの新時代をもたらします。超長系列を効率的に扱う能力は、テスト時スケーリングの次なるフロンティアを切り開き、長期タスクのより深い研究への道を拓き、オンライン学習のような将来のパラダイムを探究するために必要な基盤を築くと考えています。

DeepSeek-V3 アーキテクチャ [Dee24a] と比べ、DeepSeek-V4 シリーズは DeepSeekMoE フレームワーク [Dai24] と Multi-Token Prediction（MTP）戦略を維持しながら、アーキテクチャと最適化に複数の重要な革新を導入しています。長いコンテキストの効率を高めるため、Compressed Sparse Attention（CSA）と Heavily Compressed Attention（HCA）を組み合わせたハイブリッドアテンション機構を設計しました。CSA は系列方向に KV キャッシュを圧縮してから DeepSeek Sparse Attention（DSA）[Dee25a] を実行する一方、HCA は KV キャッシュを高い圧縮率で圧縮しつつ、密なアテンションを維持します。モデリング能力を強化するため、従来の残差接続を改良する Manifold-Constrained Hyper-Connections（*m*HC）[Xie26] を導入しました。さらに、DeepSeek-V4 シリーズの学習に Muon [Kel24, Liu25] オプティマイザを導入し、収束の高速化と学習安定性の向上を実現しています。

DeepSeek-V4 シリーズの効率的な学習と推論、そして生産性の高い開発を実現するため、複数のインフラストラクチャ最適化を導入しています。第一に、計算、通信、メモリアクセスを完全にオーバーラップさせる、MoE モジュール用の単一融合カーネルを設計・実装しました。第二に、開発生産性と実行時効率のバランスを取るため、ドメイン固有言語（DSL）の TileLang [Wan26] を使用します。第三に、学習と推論の間でビット単位の再現性を確保する、効率的なバッチ不変かつ決定論的なカーネルライブラリを提供します。第四に、学習フレームワークでは、テンソル単位のチェックポイントによって autograd フレームワークを拡張し、再計算をきめ細かく制御します。また、Muon オプティマイザ用のハイブリッド ZeRO 戦略、再計算と融合カーネルによる低コストの *m*HC 実装、圧縮アテンションを管理する二段階コンテキスト並列化によって学習効率を高めます。第五に、推論フレームワークでは、ディスク上のストレージ戦略を備えた異種 KV キャッシュ構造を設計し、共有プレフィックスの効率的な再利用を可能にします。加えて、後学習段階では、MoE エキスパート重みとインデクサの QK 経路に FP4 量子化認識学習を取り入れ、メモリと計算量を削減します。

ハイブリッド CSA と HCA に加え、計算とストレージの精度最適化を採用することで、DeepSeek-V4 シリーズは DeepSeek-V3.2 と比べて推論 FLOPs と KV キャッシュサイズを大幅に削減しており、特に長いコンテキストの設定で顕著です。[図 1](#figure-01) の右側は、DeepSeek-V3.2 と DeepSeek-V4 シリーズについて、単一トークン推論 FLOPs の推定値と累積 KV キャッシュサイズを示しています。1M トークンのコンテキストでは、アクティブパラメータ数がより多い DeepSeek-V4-Pro でさえ、単一トークン FLOPs（等価な FP8 FLOPs で測定）は DeepSeek-V3.2 の 27%、KV キャッシュサイズは 10% にすぎません。さらに、アクティブパラメータ数が少ない DeepSeek-V4-Flash は効率を一段と高めます。1M トークンのコンテキスト設定では、単一トークン FLOPs は DeepSeek-V3.2 の 10%、KV キャッシュサイズは 7% にすぎません。また、DeepSeek-V4 シリーズでは、ルーティングされるエキスパートパラメータに FP4 精度を使用します。既存ハードウェアにおける FP4 $\times$ FP8 演算のピーク FLOPs は現時点で FP8 $\times$ FP8 と同じですが、将来のハードウェアでは理論上 $1/3$ 高い効率で実装でき、DeepSeek-V4 シリーズの効率をさらに向上できます。

事前学習では、DeepSeek-V4-Flash を 32T トークン、DeepSeek-V4-Pro を 33T トークンでそれぞれ学習しました。事前学習後、二つのモデルはいずれも 1M 長のコンテキストをネイティブかつ効率的にサポートできます。社内評価では、パラメータ効率に優れた設計により、DeepSeek-V4-Flash-Base はすでに大半のベンチマークで DeepSeek-V3.2-Base を上回っています。DeepSeek-V4-Pro-Base はこの優位性をさらに拡大し、推論、コーディング、長いコンテキスト、世界知識の各タスクで全面的に優れた性能を示し、DeepSeek の基盤モデルに新たな性能基準を打ち立てています。

DeepSeek-V4 シリーズの後学習パイプラインは、ドメイン特化エキスパートを個別に育成し、その後オンポリシー蒸留 [Lu25, Gu25] で統一モデルへ統合する二段階のパラダイムを採用しています。まず、数学、コーディング、エージェント、指示追従など、対象とする各ドメインについて別々のエキスパートモデルを独立に学習します。ベースモデルは最初に、高品質なドメイン固有データを用いて教師ありファインチューニング（SFT）を受け、基礎能力を確立します。続いて Group Relative Policy Optimization（GRPO）[Guo25] を用いた強化学習（RL）を適用し、特定の成功基準に合わせた報酬モデルの導きによって、ドメインに沿う行動へモデルをさらに最適化します。この段階で、それぞれの分野に秀でた多様な専門エキスパートが得られます。最後に、これらの異なる技能を統合するため、オンポリシー蒸留を通じて単一の統一モデルを学習します。ここでは統一モデルが生徒となり、教師モデルに対する逆 KL 損失を最適化します。

**主要評価結果の概要**

- **知識**：幅広い世界知識の評価では、DeepSeek-V4-Pro の最高推論強度モードである DeepSeek-V4-Pro-Max が、SimpleQA [Ope24b] と Chinese-SimpleQA [He24] のベンチマークで主要なオープンソースモデルを大幅に上回ります。MMLU-Pro [Wan24c]、HLE [Pha25]、GPQA [Rei24] で評価する教育知識については、DeepSeek-V4-Pro-Max がオープンソースの比較対象をわずかに上回ります。これらの知識評価では依然として主要なプロプライエタリモデル Gemini-3.1-Pro に及ばないものの、DeepSeek-V4-Pro-Max はその差を大きく縮めています。
- **推論**：推論トークンを増やすことで、DeepSeek-V4-Pro-Max は標準的な推論ベンチマークにおいて GPT-5.2 と Gemini-3.0-Pro を上回る性能を示します。ただし GPT-5.4 と Gemini-3.1-Pro にはわずかに及ばず、最先端のフロンティアモデルから約 3～6 か月遅れた開発軌道にあることを示唆します。さらに、DeepSeek-V4-Flash-Max は GPT-5.2 および Gemini-3.0-Pro に匹敵する性能を達成し、複雑な推論タスクに対して非常に費用対効果の高いアーキテクチャとなっています。
- **エージェント**：公開ベンチマークでは、DeepSeek-V4-Pro-Max は Kimi-K2.6 や GLM-5.1 など主要なオープンソースモデルと同等ですが、最先端のクローズドモデルにはわずかに劣ります。社内評価では、DeepSeek-V4-Pro-Max は Claude Sonnet 4.5 を上回り、Opus 4.5 の水準に迫ります。
- **長いコンテキスト**：DeepSeek-V4-Pro-Max は 100 万トークンのコンテキストウィンドウを用いる合成・実用ユースケースで優れた結果を示し、学術ベンチマークでは Gemini-3.1-Pro さえ上回ります。
- **DeepSeek-V4-Pro と DeepSeek-V4-Flash**：DeepSeek-V4-Flash-Max はパラメータ規模が小さいため、知識評価の性能が低くなります。しかし、より大きな思考予算を割り当てると、推論タスクでは同等の結果を達成します。エージェント評価では、DeepSeek-V4-Flash-Max は複数のベンチマークで DeepSeek-V4-Pro-Max に並ぶ一方、より複雑で難易度の高いタスクでは大きなモデルに及びません。

## 2 アーキテクチャ

全体として DeepSeek-V4 シリーズは Transformer [Vas17] アーキテクチャと Multi-Token Prediction（MTP）モジュール [Glo24, Dee24a] を維持しつつ、DeepSeek-V3 に対して複数の重要な改良を加えています。(1) 第一に、従来の残差接続を強化する Manifold-Constrained Hyper-Connections（*m*HC）[Xie26] を導入します。(2) 第二に、Compressed Sparse Attention と Heavily Compressed Attention によって長いコンテキストの効率を大幅に高める、ハイブリッドアテンションアーキテクチャを設計します。(3) 第三に、Muon [Kel24, Liu25] をオプティマイザとして採用します。Mixture-of-Experts（MoE）コンポーネントには、DeepSeek-V3 からわずかな調整を加えただけの DeepSeekMoE [Dai24] アーキテクチャを引き続き採用します。Multi-Token Prediction（MTP）[Qi20, Glo24, Li24g, Dee24a] の構成は DeepSeek-V3 と同一です。明記していないその他の詳細はすべて DeepSeek-V3 [Dee24a] で確立した設定に従います。[図 2](#figure-02) に DeepSeek-V4 の全体アーキテクチャを示し、以下で詳細を説明します。

### 2.1 DeepSeek-V3 から継承した設計

**Mixture-of-Experts。** 以前の DeepSeek シリーズモデル [Dee24, Dee24a] と同様、DeepSeek-V4 シリーズの Feed-Forward Networks（FFN）にも、細粒度のルーティングエキスパートと共有エキスパートを設ける DeepSeekMoE パラダイム [Dai24] を採用します。DeepSeek-V3 とは異なり、アフィニティスコアを計算する活性化関数を $\mathrm{Sigmoid}(\cdot)$ から $\mathrm{Sqrt}(\mathrm{Softplus}(\cdot))$ に変更します。負荷分散には補助損失を用いない戦略 [Wan24d, Dee24a] も採用し、個々の系列内の極端な偏りを防ぐ軽量な系列単位のバランス損失を追加します。DeepSeek-V4 ではルーティング先ノード数の制約を取り除き、学習効率を維持するよう並列化戦略を慎重に再設計しました。さらに DeepSeek-V3 と比べ、最初のいくつかの Transformer ブロックにある密な FFN 層を、ハッシュルーティング [Rol21] を用いる MoE 層へ置き換えます。ハッシュルーティング戦略は、入力トークン ID に関する事前定義のハッシュ関数に従い、各トークンの対象エキスパートを決定します。

**Multi-Token Prediction。** DeepSeek-V3 と同様に、DeepSeek-V4 シリーズにも MTP モジュールと目的関数を設けます。MTP 戦略は DeepSeek-V3 で検証済みであるため、DeepSeek-V4 シリーズでも変更せず同じ戦略を採用します。

### 2.2 Manifold-Constrained Hyper-Connections

[図 2](#figure-02) に示すように、DeepSeek-V4 シリーズは Manifold-Constrained Hyper-Connections（*m*HC）[Xie26] を導入し、隣接する Transformer ブロック間の従来の残差接続を強化します。単純な Hyper-Connections（HC）[Zhu25] と比べ、*m*HC の中核となる考え方は、残差写像を特定の多様体上に制約し、モデルの表現力を保ちながら層をまたぐ信号伝播の安定性を高めることです。本節では標準的な HC を簡潔に紹介し、安定した学習のために *m*HC をどのように設計したかを説明します。

**標準的な Hyper-Connections。** 標準的な HC は、残差ストリームの幅を $n_{\mathrm{hc}}$ 倍に拡張します。具体的には、残差ストリームの形状を $\mathbb{R}^{d}$ から $\mathbb{R}^{n_{\mathrm{hc}}\times d}$ へ拡張します。ここで $d$ は実際の層入力の隠れ次元です。$l$ 番目の層の前にある残差状態を $X_{l}=[\mathbf{x}_{l,1};\ldots;\mathbf{x}_{l,n_{\mathrm{hc}}}]^\top\in\mathbb{R}^{n_{\mathrm{hc}}\times d}$ とします。HC は、入力写像 $A_{l}\in\mathbb{R}^{1\times n_{\mathrm{hc}}}$、残差変換 $B_{l}\in\mathbb{R}^{n_{\mathrm{hc}}\times n_{\mathrm{hc}}}$、出力写像 $C_{l}\in\mathbb{R}^{n_{\mathrm{hc}}\times 1}$ という三つの線形写像を導入します。残差状態の更新は次式で表されます。

$$
X_{l+1}=B_{l}X_{l}+C_{l}\mathcal{F}_{l}(A_{l}X_{l}),\tag{1}
$$

ここで $\mathcal{F}_{l}$ は $l$ 番目の層（例えば MoE 層）を表し、その入力と出力の形状はいずれも $\mathbb{R}^{d}$ です。実際の層入力 $A_{l}X_{l}\in\mathbb{R}^{d}$ も $d$ 次元であるため、拡張された残差幅は内部層の設計に影響しません。HC は残差幅を実際の隠れ次元から切り離し、計算オーバーヘッドを最小限に抑えながら補完的なスケーリング軸を提供します。これは通常、$n_{\mathrm{hc}}$ が隠れ次元 $d$ よりはるかに小さいためです。しかし、HC はモデル性能を高める可能性を示している一方、複数層を積み重ねると学習中に数値的不安定性が頻発し、HC のスケーリングを妨げることが分かりました。

**多様体制約付き残差写像。** *m*HC の中核的な革新は、残差写像行列 $B_{l}$ を二重確率行列の多様体（Birkhoff 多面体）$\mathcal{M}$ に制約し、層をまたぐ信号伝播の安定性を高めることです。

$$
B_{l}\in\mathcal{M}\coloneq\{M\in\mathbb{R}^{n\times n}\mid M\mathbf{1}_{n}=\mathbf{1}_{n},\;\mathbf{1}_{n}^\top M=\mathbf{1}_{n}^\top,\;M\geqslant 0\}.\tag{2}
$$

この制約により写像行列のスペクトルノルム $\|B_{l}\|_{2}$ は 1 以下となるため、残差変換は非拡大的になり、順伝播と逆伝播の双方で数値安定性が向上します。また、集合 $\mathcal{M}$ は乗算について閉じており、*m*HC を深く積み重ねる状況でも安定性が保証されます。さらに、信号が相殺されるリスクを避けるため、入力変換 $A_{l}$ と出力変換 $C_{l}$ も Sigmoid 関数によって非負かつ有界になるよう制約します。

**動的パラメータ化。** 三つの線形写像のパラメータは動的に生成され、動的な成分（入力依存）と静的な成分（入力非依存）に分解されます。入力 $X_{l}\in\mathbb{R}^{n_{\mathrm{hc}}\times d}$ が与えられると、まず平坦化して正規化します：$\hat{X}_{l}=\mathrm{RMSNorm}(\mathrm{vec}(X_{l}))\in\mathbb{R}^{1\times n_{\mathrm{hc}}d}$。次に従来の HC に従い、制約のない生のパラメータ $\tilde{A}_{l}\in\mathbb{R}^{1\times n_{\mathrm{hc}}}$、$\tilde{B}_{l}\in\mathbb{R}^{n_{\mathrm{hc}}\times n_{\mathrm{hc}}}$、$\tilde{C}_{l}\in\mathbb{R}^{n_{\mathrm{hc}}\times 1}$ を生成します。

$$
\tilde{A}_{l} =\alpha_{l}^{\mathrm{pre}}\cdot(\hat{X}_{l}W^{\mathrm{pre}}_{l})+S_{l}^{\mathrm{pre}},\tag{3}
$$

$$
\tilde{B}_{l} =\alpha_{l}^{\mathrm{res}}\cdot\mathrm{Mat}(\hat{X}_{l}W^{\mathrm{res}}_{l})+S_{l}^{\mathrm{res}},\tag{4}
$$

$$
\tilde{C}_{l} =\alpha_{l}^{\mathrm{post}}\cdot(\hat{X}_{l}W^{\mathrm{post}}_{l})^\top+S_{l}^{\mathrm{post}},\tag{5}
$$

ここで $W^{\mathrm{pre}}_{l},W^{\mathrm{post}}_{l}\in\mathbb{R}^{n_{\mathrm{hc}}d\times n_{\mathrm{hc}}}$ と $W^{\mathrm{res}}_{l}\in\mathbb{R}^{n_{\mathrm{hc}}d\times n_{\mathrm{hc}}^{2}}$ は動的成分を生成する学習可能なパラメータです。$\mathrm{Mat}(\cdot)$ は大きさ $1\times n_{\mathrm{hc}}^{2}$ のベクトルを大きさ $n_{\mathrm{hc}}\times n_{\mathrm{hc}}$ の行列へ変形します。$S_{l}^{\mathrm{pre}}\in\mathbb{R}^{1\times n_{\mathrm{hc}}}$、$S_{l}^{\mathrm{post}}\in\mathbb{R}^{n_{\mathrm{hc}}\times 1}$、$S_{l}^{\mathrm{res}}\in\mathbb{R}^{n_{\mathrm{hc}}\times n_{\mathrm{hc}}}$ は学習可能な静的バイアスです。また、$\alpha_{l}^{\mathrm{pre}}$、$\alpha_{l}^{\mathrm{res}}$、$\alpha_{l}^{\mathrm{post}}\in\mathbb{R}$ は小さな値で初期化される学習可能なゲーティング係数です。

**パラメータ制約の適用。** 制約のない生のパラメータ $\tilde{A}_{l},\tilde{B}_{l},\tilde{C}_{l}$ を得た後、数値安定性を高めるため、先に説明した制約を適用します。具体的には、入力写像と出力写像に Sigmoid 関数 $\sigma(\cdot)$ を用い、非負かつ有界であることを保証します。

$$
A_{l} =\sigma(\tilde{A}_{l}),\tag{6}
$$

$$
C_{l} =2\sigma(\tilde{C}_{l}).\tag{7}
$$

残差写像 $\tilde{B}_{l}$ は、二重確率行列の多様体 $\mathcal{M}$ へ射影します。これには Sinkhorn-Knopp アルゴリズムを使用します。まず $\tilde{B}_{l}$ に指数関数を適用して正値性を保証し、$M^{(0)}=\exp(\tilde{B}_{l})$ を得てから、列正規化と行正規化を反復します。

$$
M^{(t)}=\mathcal{T}_{r}(\mathcal{T}_{c}(M^{(t-1)})),\tag{8}
$$

ここで $\mathcal{T}_{r}$ と $\mathcal{T}_{c}$ は、それぞれ行正規化と列正規化を表します。この反復は、制約された二重確率行列 $B_{l}=M^{(t_{\max})}$ に収束します。実用的な値として $t_{\max}=20$ を選びます。

### 2.3 CSA と HCA によるハイブリッドアテンション

コンテキスト長が極端な規模に達すると、アテンション機構がモデルの主要な計算ボトルネックになります。DeepSeek-V4 では、Compressed Sparse Attention（CSA）と Heavily Compressed Attention（HCA）という二つの効率的なアテンションアーキテクチャを設計し、両者を交互に配置するハイブリッド構成を採用することで、長文シナリオにおけるアテンションの計算コストを大幅に削減します。CSA は圧縮と疎なアテンションの両戦略を統合します。まず $m$ トークンごとの Key-Value（KV）キャッシュを一つのエントリへ圧縮し、各クエリトークンが $k$ 個の圧縮 KV エントリだけにアテンションする DeepSeek Sparse Attention（DSA）[Dee25a] を適用します。HCA は、$m^{\prime}$（$\gg m$）トークンごとの KV キャッシュを一つのエントリへ統合し、極端な圧縮を目指します。CSA と HCA のハイブリッドアーキテクチャは DeepSeek-V4 シリーズの長いコンテキストにおける効率を著しく改善し、100 万トークンのコンテキストを実用可能にします。本節ではハイブリッドアテンションアーキテクチャの中核技術を説明し、詳細を明確に示すオープンソース実装 [+1] も提供します。

#### 2.3.1 Compressed Sparse Attention

[図 3](#figure-03) に CSA の中核アーキテクチャを示します。まず $m$ トークンごとの KV キャッシュを一つのエントリへ圧縮し、DeepSeek Sparse Attention を適用してさらに高速化します。

**圧縮された Key-Value エントリ。** 入力隠れ状態の系列を $H\in\mathbb{R}^{n\times d}$ とします。ここで $n$ は系列長、$d$ は隠れ次元です。CSA はまず、二系列の KV エントリ $C^{a},C^{b}\in\mathbb{R}^{n\times c}$ と、それぞれに対応する圧縮重み $Z^{a},Z^{b}\in\mathbb{R}^{n\times c}$ を計算します。ここで $c$ はヘッド次元です。

$$
C^{a} =H\cdot W^{a\mathrm{KV}},\quad C^{b}=H\cdot W^{b\mathrm{KV}},\tag{9}
$$

$$
Z^{a} =H\cdot W^{aZ},\quad\ \ Z^{b}=H\cdot W^{bZ},\tag{10}
$$

ここで $W^{a\mathrm{KV}},W^{b\mathrm{KV}},W^{aZ},W^{bZ}\in\mathbb{R}^{d\times c}$ は学習可能なパラメータです。次に、圧縮重みと学習可能な位置バイアス $B^{a},B^{b}\in\mathbb{R}^{m\times c}$ に従って、$C^{a}$ と $C^{b}$ の $m$ 個の KV エントリごとに一つへ圧縮し、$C^{\mathrm{Comp}}\in\mathbb{R}^{\frac{n}{m}\times c}$ を生成します。各圧縮エントリ $C^{\mathrm{Comp}}_{i}\in\mathbb{R}^{c}$ は次式で計算します。

$$
[S^{a}_{mi:m(i+1)-1};S^{b}_{m(i-1):mi-1}] =\mathrm{Softmax}_{\mathrm{row}}([Z^{a}_{mi:m(i+1)-1}+B^{a};Z^{b}_{m(i-1):mi-1}+B^{b}]),\tag{11}
$$

$$
C^{\mathrm{Comp}}_{i} =\sum_{j=mi}^{m(i+1)-1}S^{a}_{j}\odot C^{a}_{j}+\sum_{j=m(i-1)}^{mi-1}S^{b}_{j}\odot C^{b}_{j},\tag{12}
$$

ここで $\odot$ は Hadamard 積を表します。$\mathrm{Softmax}_{\mathrm{row}}(\cdot)$ は行方向の softmax 演算を表し、$Z^{a}$ と $Z^{b}$ の合計 $2m$ 要素にわたって正規化します。$i=0$ のとき、$Z^{b}_{m(i-1):mi-1}$ は負の無限大、$C^{b}_{m(i-1):mi-1}$ はゼロでパディングします。各 $C^{\mathrm{Comp}}_{i}$ は $2m$ 個の KV エントリから得られますが、$C^{\mathrm{Comp}}_{i}$ に用いる $C^{b}$ のインデックスと、$C^{\mathrm{Comp}}_{i-1}$ に用いる $C^{a}$ のインデックスは重複します。したがって CSA は実際には系列長を $\frac{1}{m}$ に圧縮します。

**疎な選択のための Lightning Indexer。** 圧縮 KV エントリ $C^{\mathrm{Comp}}$ を得た後、CSA は DSA 戦略を適用し、コアアテンションに用いる top-k 個の圧縮 KV エントリを選択します。まず CSA は $C^{\mathrm{Comp}}$ と同じ圧縮演算を実行し、圧縮インデクサキー $K^{\mathrm{IComp}}\in\mathbb{R}^{\frac{n}{m}\times c^{I}}$ を得ます。ここで $c^{I}$ はインデクサのヘッド次元です。次に、クエリトークン $t$ に対し、インデクサクエリ $\{\mathbf{q}_{t,1}^{I};\mathbf{q}_{t,2}^{I};...;\mathbf{q}_{t,n_{h}^{I}}^{I}\}$ を低ランク方式で生成します。

$$
\mathbf{c}_{t}^{Q} =\mathbf{h}_{t}\cdot W^{\mathrm{DQ}},\tag{13}
$$

$$
[\mathbf{q}_{t,1}^{I};\mathbf{q}_{t,2}^{I};...;\mathbf{q}_{t,n_{h}^{I}}^{I}]=\mathbf{q}_{t}^{I} =\mathbf{c}_{t}^{Q}\cdot W^{\mathrm{IUQ}},\tag{14}
$$

ここで $\mathbf{h}_{t}\in\mathbb{R}^{d}$ はクエリトークン $t$ の入力隠れ状態、$\mathbf{c}_{t}^{Q}\in\mathbb{R}^{d_{c}}$ はクエリ用の圧縮潜在ベクトル、$d_{c}$ はクエリ圧縮次元、$n_{h}^{I}$ はインデクサクエリヘッド数を表します。$W^{\mathrm{DQ}}\in\mathbb{R}^{d\times d_{c}}$ と $W^{\mathrm{IUQ}}\in\mathbb{R}^{d_{c}\times c^{I}n_{h}^{I}}$ は、それぞれインデクサクエリのダウンプロジェクション行列とアッププロジェクション行列です。次に、クエリトークン $t$ と先行する圧縮ブロック $s$（$s$ < $\mathrm{Floor}(\frac{t}{m})$）とのインデックススコア $I_{t,s}\in\mathbb{R}$ を次式で計算します。

$$
[w_{t,1}^{I};w_{t,2}^{I};...;w_{t,n_{h}^{I}}^{I}]=\mathbf{w}_{t}^{I} =\mathbf{h}_{t}\cdot W^{w},\tag{15}
$$

$$
I_{t,s} =\sum_{h=1}^{n_{h}^{I}}w_{t,h}^{I}\cdot\mathrm{ReLU}\left(\mathbf{q}^{I}_{t,h}\cdot K^{\mathrm{IComp}}_{s}\right),\tag{16}
$$

ここで $W^{w}\in\mathbb{R}^{d\times n_{h}^{I}}$ は学習可能な行列、$w_{t,h}^{I}\in\mathbb{R}$ は $h$ 番目のインデクサヘッドの重みです。クエリトークン $t$ のインデックススコア $I_{t,:}$ が与えられると、top-k セレクタを用いて圧縮 KV エントリの部分集合 $\mathcal{C}^{\mathrm{SprsComp}}_{t}$ を選択的に保持し、後続のコアアテンションに使用します。

$$
\mathcal{C}^{\mathrm{SprsComp}}_{t}=\left\{C^{\mathrm{Comp}}_{s}\ \Big|\ I_{t,s}\in\mathrm{Top-k}(I_{t,:})\right\}.\tag{17}
$$

**Key-Value を共有する MQA。** 疎な KV エントリを選択した後、CSA は Multi-Query Attention（MQA）[Sha19] 方式でコアアテンションを実行します。$\mathcal{C}^{\mathrm{SprsComp}}_{t}$ に含まれる各圧縮 KV エントリは、アテンションのキーと値の両方として機能します。具体的には、クエリトークン $t$ について、まず圧縮潜在ベクトル $\mathbf{c}_{t}^{Q}$ からアテンションクエリ $\{\mathbf{q}_{t,1};\mathbf{q}_{t,2};...;\mathbf{q}_{t,n_{h}}\}$ を生成します。

$$
[\mathbf{q}_{t,1};\mathbf{q}_{t,2};...;\mathbf{q}_{t,n_{h}}]=\mathbf{q}_{t}=\mathbf{c}_{t}^{Q}\cdot W^{\mathrm{UQ}},\tag{18}
$$

ここで $n_{h}$ はクエリヘッド数、$W^{\mathrm{UQ}}\in\mathbb{R}^{d_{c}\times cn_{h}}$ はクエリのアッププロジェクション行列です。潜在クエリベクトル $\mathbf{c}_{t}^{Q}$ は、インデクサクエリに用いるものと共有されます。次に、$\{\mathbf{q}_{t,i}\}$ と $\mathcal{C}^{\mathrm{SprsComp}}_{t}$ に対して MQA を実行します。

$$
\mathbf{o}_{t,i}=\mathrm{CoreAttn}\left(\texttt{query=}\mathbf{q}_{t,i},\texttt{key=}\mathcal{C}^{\mathrm{SprsComp}}_{t},\texttt{value=}\mathcal{C}^{\mathrm{SprsComp}}_{t}\right),\tag{19}
$$

ここで $\mathbf{o}_{t,i}\in\mathbb{R}^{c}$ は $t$ 番目のトークンにおける $i$ 番目のヘッドのコアアテンション出力、$\mathrm{CoreAttn}(\cdot)$ はコアアテンション演算を表します。

**グループ化出力プロジェクション。** DeepSeek-V4 の構成では $cn_{h}$ が非常に大きくなります。そのため、コアアテンション演算の出力 $[\mathbf{o}_{t,1};\mathbf{o}_{t,2};...;\mathbf{o}_{t,n_{h}}]=\mathbf{o}_{t}\in\mathbb{R}^{cn_{h}}$ を $d$ 次元の隠れ状態へ直接射影すると、大きな計算負荷が生じます。このコストを抑えるため、グループ化出力プロジェクション戦略を設計しました。具体的には、まず $n_{h}$ 個の出力を $g$ グループに分け、各出力グループ $\mathbf{o}^{G}_{t,i}\in\mathbb{R}^{c\frac{n_{h}}{g}}$ を $d_{g}$ 次元の中間出力 $\mathbf{o}^{G^{\prime}}_{t,i}\in\mathbb{R}^{d_{g}}$ へ射影します。ここで $d_{g}<c\frac{n_{h}}{g}$ です。最後に、中間出力 $[\mathbf{o}^{G^{\prime}}_{t,1};\mathbf{o}^{G^{\prime}}_{t,2};...;\mathbf{o}^{G^{\prime}}_{t,g}]\in\mathbb{R}^{d_{g}g}$ を最終アテンション出力 $\mathbf{\hat{o}}_{t}\in\mathbb{R}^{d}$ へ射影します。

**図 4.** HCA の中核アーキテクチャ。より強い圧縮を行い、$m^{\prime}$（$\gg m$）トークンの KV エントリを一つへ統合します。また、少数のスライディングウィンドウ KV エントリを追加し、局所的で細粒度な依存関係を強化します。

#### 2.3.2 Heavily Compressed Attention

[図 4](#figure-04) に HCA の中核アーキテクチャを示します。KV キャッシュを高い圧縮率で圧縮しますが、疎なアテンションは使用しません。

**圧縮された Key-Value エントリ。** 概して HCA の圧縮戦略は CSA と似ていますが、より大きな圧縮率 $m^{\prime}$（$\gg m$）を用い、重複する圧縮は行いません。入力隠れ状態の系列を $H\in\mathbb{R}^{n\times d}$ とすると、HCA はまず元の KV エントリ $C\in\mathbb{R}^{n\times c}$ と、それに対応する圧縮重み $Z\in\mathbb{R}^{n\times c}$ を計算します。

$$
C =H\cdot W^{\mathrm{KV}},\tag{20}
$$

$$
Z =H\cdot W^{Z},\tag{21}
$$

ここで $W^{\mathrm{KV}},W^{Z}\in\mathbb{R}^{d\times c}$ は学習可能なパラメータです。次に、圧縮重みと学習可能な位置バイアス $B\in\mathbb{R}^{m^{\prime}\times c}$ に従って、$C$ の $m^{\prime}$ 個の KV エントリごとに一つへ圧縮し、$C^{\mathrm{Comp}}\in\mathbb{R}^{\frac{n}{m^{\prime}}\times c}$ を生成します。各圧縮エントリ $C^{\mathrm{Comp}}_{i}\in\mathbb{R}^{c}$ は次式で計算します。

$$
S_{m^{\prime}i:m^{\prime}(i+1)-1} =\mathrm{Softmax}_{\mathrm{row}}(Z_{m^{\prime}i:m^{\prime}(i+1)-1}+B),\tag{22}
$$

$$
C^{\mathrm{Comp}}_{i} =\sum_{j=m^{\prime}i}^{m^{\prime}(i+1)-1}S_{j}\odot C_{j}.\tag{23}
$$

この圧縮演算によって、HCA は系列長を $\frac{1}{m^{\prime}}$ に圧縮します。

**Key-Value を共有する MQA とグループ化出力プロジェクション。** HCA も CSA と同様に、KV を共有する MQA とグループ化出力プロジェクション戦略を採用します。KV 圧縮後、クエリトークン $t$ に対して、HCA はまずアテンションクエリ $\{\mathbf{q}_{t,1};\mathbf{q}_{t,2};...;\mathbf{q}_{t,n_{h}}\}$ を低ランク方式で生成します。

$$
\mathbf{c}_{t}^{Q} =\mathbf{h}_{t}\cdot W^{\mathrm{DQ}},\tag{24}
$$

$$
[\mathbf{q}_{t,1};\mathbf{q}_{t,2};...;\mathbf{q}_{t,n_{h}}]=\mathbf{q}_{t} =\mathbf{c}_{t}^{Q}\cdot W^{\mathrm{UQ}},\tag{25}
$$

ここで $\mathbf{h}_{t}\in\mathbb{R}^{d}$ はクエリトークン $t$ の入力隠れ状態、$n_{h}$ はクエリヘッド数を表します。$W^{\mathrm{DQ}}\in\mathbb{R}^{d\times d_{c}}$ と $W^{\mathrm{UQ}}\in\mathbb{R}^{d_{c}\times cn_{h}}$ は、それぞれクエリのダウンプロジェクション行列とアッププロジェクション行列です。次に $\{\mathbf{q}_{t,i}\}$ と $C^{\mathrm{Comp}}$ に対して MQA を実行します。

$$
\mathbf{o}_{t,i}=\mathrm{CoreAttn}\left(\texttt{query=}\mathbf{q}_{t,i},\texttt{key=}C^{\mathrm{Comp}},\texttt{value=}C^{\mathrm{Comp}}\right),\tag{26}
$$

ここで $\mathbf{o}_{t,i}\in\mathbb{R}^{c}$ は $t$ 番目のトークンにおける $i$ 番目のヘッドのコアアテンション出力です。次に CSA と同様、HCA は $n_{h}$ 個の出力を $g$ グループに分け、各出力グループ $\mathbf{o}^{G}_{t,i}\in\mathbb{R}^{c\frac{n_{h}}{g}}$ を $d_{g}$ 次元の中間出力 $\mathbf{o}^{G^{\prime}}_{t,i}\in\mathbb{R}^{d_{g}}$ へ射影します。ここで $d_{g}<c\frac{n_{h}}{g}$ です。最後に、中間出力 $[\mathbf{o}^{G^{\prime}}_{t,1};\mathbf{o}^{G^{\prime}}_{t,2};...;\mathbf{o}^{G^{\prime}}_{t,g}]\in\mathbb{R}^{d_{g}g}$ を最終アテンション出力 $\mathbf{\hat{o}}_{t}\in\mathbb{R}^{d}$ へ射影します。

#### 2.3.3 その他の詳細

以上で説明した CSA と HCA の中核アーキテクチャに加え、ハイブリッドアテンションには複数の技術を取り入れています。記述を明瞭にするため、上の説明ではこれらの追加技術を省略し、本節で簡潔に説明します。また簡潔さのため、本節では中核的な考え方だけに焦点を当て、一部の細かな詳細を省く場合があります。曖昧さのない詳細については、オープンソース実装を参照することを推奨します。

**クエリと Key-Value エントリの正規化。** CSA と HCA のいずれでも、コアアテンション演算の直前に、クエリの各ヘッドと圧縮 KV エントリの唯一のヘッドへ追加の RMSNorm 演算を適用します。この正規化はアテンションロジットの爆発を防ぎ、学習安定性を高める可能性があります。

**部分的な Rotary Positional Embedding。** CSA と HCA のいずれでも、アテンションクエリ、KV エントリ、コアアテンション出力に Rotary Positional Embedding（RoPE）[Su24] を部分的に適用します。具体的には、CSA と HCA で用いる各クエリベクトルと KV エントリベクトルの末尾 64 次元に RoPE を適用します。KV エントリはアテンションのキーと値の双方として機能するため、単純なコアアテンション出力 $\{\mathbf{o}_{t,i}\}$ は KV エントリの加重和から得られる絶対位置埋め込みを持ちます。この対策として、各 $\mathbf{o}_{t,i}$ の末尾 64 次元に、位置 $-i$ の RoPE も適用します。これにより、コアアテンション出力も相対位置埋め込みを持ち、各 KV エントリのコアアテンション出力への寄与が、クエリと KV エントリの距離にも関連するようになります。

**Sliding Window Attention の追加分岐。** CSA と HCA で因果性を厳密に保つため、各クエリは先行する圧縮 KV ブロックだけにアテンションします。そのため、クエリは自身の圧縮ブロック内にある他のトークンの情報へアクセスできません。一方、言語モデリングでは通常、直近のトークンほどクエリトークンとの関連が強くなります。こうした理由から、局所的な依存関係をよりよくモデル化するため、CSA と HCA の双方にスライディングウィンドウ方式の補助アテンション分岐を導入します。具体的には、各クエリトークンについて、直近の $n_{\mathrm{win}}$ トークンに対応する未圧縮の KV エントリを $n_{\mathrm{win}}$ 個追加で生成します。CSA と HCA のコアアテンションでは、スライディングウィンドウ内のこれらの KV エントリを圧縮 KV エントリとともに使用します。

**Attention Sink。** CSA と HCA のコアアテンションには、attention sink [Xia24a, Ope25c] の技法を用います。具体的には、学習可能な一連の sink ロジット $\{z^{\prime}_{1},z^{\prime}_{2},...,z^{\prime}_{n_{h}}\}$ を設定します。$h$ 番目のアテンションヘッドでは、アテンションスコアの分母に $\mathrm{Exp}(z^{\prime}_{h})$ を加えます。

$$
s_{h,i,j}=\frac{\mathrm{Exp}(z_{h,i,j})}{\sum_{k}\mathrm{Exp}(z_{h,i,k})+\mathrm{Exp}(z^{\prime}_{h})},\tag{27}
$$

ここで $s_{h,i,j},z_{h,i,j}\in\mathbb{R}$ は、$i$ 番目のクエリトークンと、先行する $j$ 番目のトークンまたは圧縮ブロックとの間における、$h$ 番目のアテンションヘッドのアテンションスコアとアテンションロジットを表します。この技法により、各クエリヘッドはアテンションスコアの総和を 1 以外、さらには 0 に近い値へ調整できます。

#### 2.3.4 効率に関する考察

ハイブリッド CSA と HCA を低精度の計算・ストレージと組み合わせることで、DeepSeek-V4 シリーズのアテンションモジュールは、アテンション FLOPs と KV キャッシュサイズの双方で高い効率を実現し、特に長いコンテキストのシナリオで顕著です。第一に、KV エントリには混合ストレージ形式を採用します。Rotary Positional Embedding（RoPE）の次元には BF16 精度を用い、残りの次元には FP8 精度を適用します。このハイブリッド表現により、純粋な BF16 ストレージと比べて KV キャッシュサイズをほぼ半分に削減できます。第二に、Lightning Indexer 内のアテンション計算は FP4 精度で実行し、極端に長いコンテキストでアテンション演算を高速化します。第三に、DeepSeek-V3.2 より小さなアテンション top-k を DeepSeek-V4 シリーズで選択し、短文・中程度の長さのテキストに対するモデル効率を高めます。最後に、そして最も重要な点として、圧縮アテンションとハイブリッドアテンションの技法により、KV キャッシュサイズと計算 FLOPs の双方を大幅に削減します。

LLM アテンションの一般的な構成の一つである、ヘッド次元 128 の BF16 GQA8 [Ain23] をベースラインとすると、1M コンテキスト設定における DeepSeek-V4 シリーズの KV キャッシュサイズは、ベースラインの約 $2\%$ まで大幅に削減できます。さらに、すでに効率的なベースラインである DeepSeek-V3.2 [Dee25a] と比べても、DeepSeek-V4 シリーズは依然として効率面で大きな優位性を示します。両者の推論 FLOPs と KV キャッシュサイズの比較は[図 1](#figure-01) の右側に示します。

**アルゴリズム 1：DeepSeek-V4 の Muon オプティマイザ。**

- **必要条件：** 学習率 $\eta$、モメンタム $\mu$、重み減衰 $\lambda$、更新再スケーリング係数 $\gamma$。
- 各学習ステップ $t$ **について**：
  - 論理的に独立した各重み $W \in \mathbb{R}^{n \times m}$ **について**：
    - $G_t = \nabla_W \mathcal{L}_t(W_{t-1})$。**勾配を計算する。**
    - $M_t = \mu M_{t-1} + G_t$。**モメンタムバッファを蓄積する。**
    - $O^{\prime}_t = \mathrm{HybridNewtonSchulz}(\mu M_t + G_t)$。**Nesterov 技法とハイブリッド Newton-Schulz。**
    - $O_t = O^{\prime}_t \cdot \sqrt{\max(n, m)} \cdot \gamma$。**更新の RMS を再スケーリングする。**
    - $W_t = W_{t-1} \cdot \left(1 - \eta \lambda \right) - \eta O_t$。**重み減衰と更新を実行する。**

### 2.4 Muon オプティマイザ

Muon [Kel24, Liu25] オプティマイザは収束が速く学習安定性も高いため、DeepSeek-V4 シリーズの大半のモジュールで使用します。Muon 最適化の完全なアルゴリズムをアルゴリズム 1 にまとめます。

**基本構成。** 埋め込みモジュール、予測ヘッドモジュール、*m*HC モジュールの静的バイアスとゲーティング係数、および全 RMSNorm モジュールの重みには AdamW [Los17] オプティマイザを維持します。その他のモジュールはすべて Muon で更新します。[Liu25] に従い、Muon パラメータにも重み減衰を適用し、Nesterov [Nes83, Kel24] 技法を用い、AdamW のハイパーパラメータを再利用するため更新行列の Root Mean Square（RMS）を再スケーリングします。ただし、直交化にはハイブリッド Newton-Schulz 反復を使用します。

**ハイブリッド Newton-Schulz 反復。** 与えられた行列 $M$ の Singular Value Decomposition（SVD）を $M=U\Sigma V^\top$ とします。Newton-Schulz 反復は、$M$ を $U V^\top$ へ近似的に直交化することを目的とします。通常、最大特異値が 1 を超えないよう、まず $M$ を $M_{0}=M/\|M\|_{F}$ と正規化します。その後、各 Newton-Schulz 反復で次の演算を実行します。

$$
M_{k}=aM_{k-1}+b(M_{k-1}M_{k-1}^\top)M_{k-1}+c(M_{k-1}M_{k-1}^\top)^{2}M_{k-1}.\tag{28}
$$

ハイブリッド Newton-Schulz は、異なる二段階にわたって 10 回の反復を実行します。最初の 8 ステップでは係数 $(a,b,c)=(3.4445,-4.7750,2.0315)$ を用いて急速な収束を促し、特異値を 1 に近づけます。最後の 2 ステップでは係数 $(a,b,c)=(2,-1.5,0.5)$ に切り替え、特異値を正確に 1 へ安定させます。

**アテンションロジットの爆発の回避。** DeepSeek-V4 シリーズのアテンションアーキテクチャでは、アテンションクエリと KV エントリに RMSNorm を直接適用でき、アテンションロジットの爆発を効果的に防げます。そのため、Muon オプティマイザでは QK-Clip 技法 [Liu25] を使用しません。

## 3 汎用インフラストラクチャ

### 3.1 エキスパート並列化における細粒度な通信・計算オーバーラップ

Mixture-of-Experts（MoE）は Expert Parallelism（EP）によって高速化できます。しかし EP は複雑なノード間通信を必要とし、インターコネクトの帯域幅とレイテンシに大きな要求を課します。EP の通信ボトルネックを緩和し、より低いインターコネクト帯域幅要件のもとで高いエンドツーエンド性能を得るため、通信と計算を単一のパイプライン化カーネルへ融合して通信・計算をオーバーラップさせる、細粒度 EP 方式を提案します。

**通信レイテンシは隠蔽できる。** EP 方式の重要な洞察は、MoE 層において通信レイテンシを計算の背後へ効果的に隠蔽できることです。[図 5](#figure-05) に示すように、DeepSeek-V4 シリーズの各 MoE 層は主に四段階へ分解できます。通信律速の *Dispatch* と *Combine*、計算律速の *Linear-1* と *Linear-2* です。プロファイリングから、単一の MoE 層では通信の合計時間が計算時間より短いことが分かりました。したがって、通信と計算を一つのパイプラインへ融合した後も計算が主要なボトルネックであり、エンドツーエンド性能を落とさずに、より低いインターコネクト帯域幅を許容できます。

<span id="figure-05"></span>

![DeepSeek-V4 図 5](../../papers/deepseek-v4/figure-05.png)

**図 5.** EP 方式と関連研究の図。Comet [Zha25e] は Dispatch と Linear-1、Linear-2 と Combine をそれぞれオーバーラップさせます。本 EP 方式は、エキスパートを wave に分割してスケジューリングすることで、より細粒度なオーバーラップを実現します。理論上の高速化率は DeepSeek-V4-Flash アーキテクチャの構成で評価しています。

**細粒度 EP 方式。** インターコネクト帯域幅の要件をさらに下げ、オーバーラップの利点を拡大するため、より細粒度なエキスパート分割方式を導入します。多くの関連研究 [Aim25, Zha25e] に着想を得て、エキスパートを *wave* に分割してスケジューリングします。各 wave は少数のエキスパートで構成されます。wave 内の全エキスパートが通信を完了すると、他のエキスパートを待たずに直ちに計算を開始できます。[図 5](#figure-05) に示すように、定常状態では、現在の wave の計算、次の wave のトークン転送、完了したエキスパートの結果送信がすべて同時に進みます。これによりエキスパート間に細粒度なパイプラインが形成され、wave 全体を通じて計算と通信の双方が連続します。wave ベースのスケジューリングは、長い裾を持つ小バッチに遭遇しやすい強化学習（RL）ロールアウトなど、極端なケースの性能を高めます。

**性能とオープンソースの Mega-Kernel。** 細粒度 EP 方式を NVIDIA GPU と HUAWEI Ascend NPU の両プラットフォームで検証しました。強力な非融合ベースラインと比べ、一般的な推論ワークロードでは $1.50\sim 1.73\times$、RL ロールアウトや高速エージェントサービングなどレイテンシに敏感なシナリオでは最大 $1.96\times$ の高速化を達成します。CUDA ベースの mega-kernel 実装 **MegaMoE** [+2] を DeepGEMM のコンポーネントとしてオープンソース化しています。

**観察と提案。** 効率的なハードウェア設計を支援し、よりよいソフトウェア・ハードウェア協調設計を実現するため、カーネル開発から得た観察と教訓を共有し、ハードウェアベンダーへいくつか提案します。

- **計算・通信比。** 通信と計算の完全なオーバーラップは、帯域幅だけでなく計算・通信比に依存します。ピーク計算スループットを $C$、インターコネクト帯域幅を $B$ とすると、$C/B\leqslant V_{\mathrm{comp}}/V_{\mathrm{comm}}$ のとき通信を完全に隠蔽できます。ここで $V_{\mathrm{comp}}$ は計算量、$V_{\mathrm{comm}}$ は通信量です。DeepSeek-V4-Pro では、各トークン・エキスパート対が $6hd$ FLOPs（SwiGLU の gate、up、down プロジェクション）を必要とする一方、通信は $3h$ バイト（FP8 Dispatch + BF16 Combine）だけなので、次式に簡略化できます。

  $$
  \frac{C}{B}\leqslant 2d=6144\;\mathrm{FLOPs/Byte}.
  $$

  すなわち、インターコネクト帯域幅 1 GBps ごとに、6.1 TFLOP/s の計算に伴う通信を隠蔽できます。帯域幅がこの閾値に達するとボトルネックではなくなり、帯域幅をさらに増やすために追加のシリコン面積を割り当てても、効果は逓減します。将来のハードウェア設計では、無条件に帯域幅を拡大するのではなく、このような均衡点を目標にすることを推奨します。
- **電力予算。** 極端なカーネル融合は、計算、メモリ、ネットワークを同時に高負荷にし、電力スロットリングが主要な性能制約になります。将来のハードウェア設計では、このような完全並行ワークロードに十分な電力余裕を持たせることを提案します。
- **通信プリミティブ。** dispatch 段階では、各 GPU がリモート GPU からアクティベーションを能動的に読み取る pull ベースの方式を採用し、細粒度な push に伴う高い通知レイテンシを避けます。GPU 間シグナリングのレイテンシが低い将来のハードウェアでは push が実用的になり、より自然な通信パターンを実現できます。
- **活性化関数。** SwiGLU を、指数演算や除算を含まない低コストの要素単位活性化に置き換えることを提案します。これにより GEMM 後処理のオーバーヘッドが直接削減され、活性化関数の計算によって GEMM パイプラインが停止することを防ぎ、全体の計算スループットと資源利用率を高めます。

### 3.2 TileLang による柔軟で効率的なカーネル開発

実際には、精緻なモデルアーキテクチャから数百個の細粒度 Torch ATen 演算子が生じます。TileLang [Wan26] を用いて、その大半を置き換える融合カーネル群を開発し、最小限の労力で最適な性能を実現します。また検証時には、アテンションの変種のような演算子を迅速に試作できます。これらのカーネルは、モデルアーキテクチャの開発、大規模学習、そして最終的な推論サービスの本番展開において重要な役割を果たします。ドメイン固有言語（DSL）である TileLang は、開発生産性と実行時効率のバランスを取り、迅速な開発を可能にしつつ、同じコードベース内で深い反復的最適化を支援します。さらに TileLang コミュニティと緊密に協力し、より俊敏で効率的かつ安定したカーネル開発ワークフローを育成しています。

**Host Codegen による呼び出しオーバーヘッドの削減。** アクセラレータの性能が向上し続けるにつれ、CPU 側のオーケストレーションオーバーヘッドがますます顕著になります。小さく高度に最適化されたカーネルでは、このような固定的なホストオーバーヘッドが利用率とスループットの上限になりがちです。一般的な原因の一つは、実行時の契約チェックなどのホスト側ロジックが、柔軟性のため通常 Python で書かれ、呼び出しごとに固定コストを生じることです。

このオーバーヘッドは、ホスト側ロジックの大半を生成ホストコードへ移す *Host Codegen* によって緩和します。具体的には、まず IR（Intermediate Representation）レベルでデバイスカーネルと軽量ホストランチャーを同時生成し、言語フロントエンドから解析したデータ型、ランク・形状制約、ストライド・レイアウトの仮定など必要なメタデータを埋め込みます。次にランチャーを TVM-FFI [Che18] フレームワーク上のホストソースコードへ変換します。コンパクトな呼び出し規約とゼロコピーのテンソル相互運用により、ホスト側オーバーヘッドを最小化します。実行時には、生成ホストコードが検証と引数マーシャリングを行い、呼び出しごとの全チェックを Python 実行経路から外します。測定では、CPU 側の検証オーバーヘッドが数十～数百マイクロ秒から、呼び出しあたり 1 マイクロ秒未満へ低下します。

**SMT ソルバー支援による形式的な整数解析。** TileLang カーネルには複雑なテンソル添字演算が含まれ、強力な形式的整数解析が必要です。レイアウト推論、メモリハザード検出、境界解析などのコンパイルパスでは、対応する最適化を有効にするため、整数式が特定の性質を満たすかをコンパイラが検証しなければなりません。したがって、より強力な形式解析能力によって、さらに高度で複雑な最適化の機会を引き出せます。

このため、Z3 SMT ソルバー [Dem08] を TileLang の代数系へ統合し、テンソルプログラムに現れる大半の整数式へ形式解析能力を提供します。TileLang の整数式を Z3 の量化子なし非線形整数算術（QF_NIA）へ変換し、計算オーバーヘッドと形式的表現力のバランスを取ります。Integer Linear Programming（ILP）ソルバーを基盤とする QF_NIA は、カーネルに一般的な標準線形整数式をシームレスに解決します。さらに、固有の非線形推論能力により、可変テンソル形状に対するベクトル化など高度な課題へ効果的に対処します。妥当な資源制限のもとで、Z3 はコンパイル時間のオーバーヘッドを数秒に抑えながら、全体の最適化性能を高めます。その効果は、ベクトル化、バリア挿入、コード簡略化など複数のパスに及びます。

**数値精度とビット単位の再現性。** 本番環境では、数値的な正しさと再現性が生のスループットと同じく重要です。そのため、既定では精度を優先します。コンパイラレベルで fast-math 最適化を無効化し、精度に影響する近似は、明示的に opt-in するフロントエンド演算子（例：`T.__exp`、`T.__log`、`T.__sin`）としてのみ提供します。一方、厳密な IEEE-754 セマンティクスが必要な場合、TileLang は明示的な丸めモードを備えた IEEE 準拠の intrinsic（例：`T.ieee_fsqrt`、`T.ieee_fdiv`、`T.ieee_add`）を提供し、開発者が数値動作を正確に指定できるようにします。

手書き CUDA ベースラインに対してカーネルを検証するため、ビット単位の再現性も目指します。TileLang の代数簡略化と lowering 規則を主要な CUDA ツールチェーン（例：NVCC）に合わせ、意図しないビットレベル差を生む変換を避けます。レイアウト注釈（例：`T.annotate_layout`）により、レイアウト依存の lowering 判断をユーザーが固定し、評価と累積の順序を参照 CUDA 実装と一致させ、必要に応じてビット単位で同一の出力を得られます。

評価の結果、精度と再現性を重視したこれらの設計判断は性能を犠牲にしません。保守的な既定値でも TileLang カーネルは競争力を維持し、数値制約を選択的に緩和して高速化する調整項目も公開します。

### 3.3 高性能なバッチ不変・決定論的カーネルライブラリ

効率的な学習と推論を実現するため、高性能計算カーネルを包括的に開発します。基本機能とハードウェア利用率の最大化に加え、学習の再現性を保証し、事前学習、後学習、推論パイプライン間でビット単位の整合を取ることも重要な設計目標です。そこで、性能オーバーヘッドを最小限に抑えた、エンドツーエンドでビット単位にバッチ不変かつ決定論的なカーネルを実装します。これらのカーネルは、デバッグ、安定性解析、一貫した後学習動作に有用です。

**バッチ不変性。** バッチ不変性は、任意のトークンの出力がバッチ内の位置にかかわらずビット単位で同一になることを保証します。バッチ不変性の実現における主な課題は次のとおりです。

- **アテンション。** バッチ不変性を実現するには、単一系列のアテンション計算を複数の Stream Multiprocessor（SM）へ分散して SM の負荷を均衡させる split-KV 法 [Dao23] を使用できません。しかし、この技法を捨てると深刻な wave quantization 問題 [+3] が生じ、GPU 利用率へ悪影響を与えます。これに対処するため、バッチ不変デコード用の二重カーネル戦略を開発します。第一のカーネルは単一 SM 内で系列全体のアテンション出力を計算し、完全に埋まった wave の高スループットを保証します。第二のカーネルは、最後の部分的に埋まった wave のレイテンシを最小化して wave quantization を緩和するため、単一系列に複数 SM を使用します。二つのカーネルをビット単位で同一にするため、第二のカーネルの計算経路を慎重に設計し、累積順序を第一のカーネルと一致させます。さらに第二のカーネルは、thread-block cluster 内の分散共有メモリ [+4] を利用し、SM 間の高速データ交換を可能にします。この二重カーネル法により、バッチ不変デコードのオーバーヘッドを実質的に無視できる範囲へ抑えます。
- **行列乗算。** 従来の cuBLAS ライブラリ [Nvi24] はバッチ不変性を実現できません。そこで DeepGEMM [Zha25f] によってエンドツーエンドで置き換えます。また非常に小さなバッチサイズでは、従来の実装は通常、性能向上のため split-k [Osa23] 技法を用います。ところが split-k は、DeepSeek-V4 の重要な機能であるバッチ不変性を保証できません。そのため大半のシナリオで split-k を廃止しますが、性能低下を招く可能性があります。これに対処する最適化群を導入し、主要なシナリオの大半で、行列乗算実装が標準 split-k の性能に匹敵するか、上回るようにします。

**決定性。** 決定論的な学習は、ハードウェアやソフトウェアの問題をデバッグするうえで非常に有用です。また、損失スパイクなどの異常が学習中に現れた場合、決定性によって数値的原因を容易に特定し、モデル設計をさらに改善できます。学習中の非決定性は通常、非決定論的な累積順序に由来し、多くは atomic add 命令の使用によって生じます。この問題は主に逆伝播中、特に次の部分で発生します。

- **アテンションの逆伝播。** 疎なアテンションの従来の逆伝播実装では、KV トークンの勾配を累積するため `atomicAdd` を使用します。浮動小数点加算が結合的でないため、非決定性が生じます。この問題に対処するため、各 SM に個別の累積バッファを割り当て、その後、全バッファに対してグローバルな決定論的加算を行います。
- **MoE の逆伝播。** 異なる rank の複数 SM が受信 rank 上の同じバッファへ同時にデータを書き込む場合、書き込み位置の調整も非決定性を生みます。これを解決するため、各 rank 内でトークン順序を前処理する機構と、複数 rank 間のバッファ分離を組み合わせます。この戦略は、エキスパート並列化の送信結果と MoE 逆伝播の累積順序の双方で決定性を保証します。
- ***m*HC における行列乗算。** *m*HC には出力次元がわずか 24 の行列乗算があります。非常に小さなバッチサイズでは split-k [Osa23] アルゴリズムを使わざるを得ず、単純な実装は非決定性を生みます。これを克服するため、各分割部分を別々に出力し、後続カーネルで決定論的リダクションを実行して、性能と決定性の双方を維持します。

### 3.4 学習フレームワーク

学習フレームワークは、DeepSeek-V3 [Dee24a] のために開発したスケーラブルで効率的なインフラストラクチャを基盤とします。DeepSeek-V4 の学習では、この堅牢な基盤を継承しつつ、高い学習効率と安定性を保ちながら、Muon オプティマイザ、*m*HC、ハイブリッドアテンション機構という新しいアーキテクチャコンポーネントに対応する複数の重要な革新を導入します。

#### 3.4.1 Muon の効率的な実装

Muon オプティマイザはパラメータ更新の計算に勾配行列全体を必要とするため、Zero Redundancy Optimizer（ZeRO）[Raj20] との併用は困難です。従来の ZeRO は AdamW のような要素単位のオプティマイザ向けに設計され、単一のパラメータ行列を複数 rank に分割して更新できます。この競合に対処するため、Muon 用の ZeRO bucket 割り当てにハイブリッド戦略を設計します。

密なパラメータでは ZeRO 並列化の最大規模を制限し、ナップサックアルゴリズムでパラメータ行列を各 rank へ割り当て、各 rank の負荷をほぼ均衡させます。各 rank の bucket は、rank 間で最大の bucket サイズに合わせてパディングし、効率的な reduce-scatter 演算を可能にします。各 rank が管理するパラメータ行列は最大五つであり、この設定では通常、パディングによるメモリオーバーヘッドは 10% 未満です。データ並列化の全体規模が ZeRO の上限を超える場合、追加のデータ並列グループ間で Muon 更新を冗長に計算し、計算量と引き換えに bucket の総メモリ量を削減します。

MoE パラメータでは、各エキスパートを独立に最適化します。まず全層の全エキスパートにある SwiGLU [Sha20] の down projection 行列をすべて平坦化し、続いて up projection 行列と gate 行列を平坦化します。次に、論理的に独立した行列を分割せず、ベクトルを全 rank へ均等に分配できるよう、平坦化ベクトルをパディングします。エキスパート数が多いため、MoE パラメータの ZeRO 並列化には上限を設けず、パディングのオーバーヘッドも無視できます。

さらに各 rank では、同一形状の連続パラメータを自動的に統合し、Newton-Schulz 反復をバッチ実行してハードウェア利用率を高めます。また、Muon の Newton-Schulz 反復は BF16 行列乗算で計算しても安定することを確認しました。これを利用し、データ並列 rank 間で同期する MoE 勾配を確率的丸めによって BF16 精度へ量子化し、通信量を半減します。低精度加算器が生む累積誤差を避けるため、従来の木またはリングベースの reduce-scatter collective を二段階方式へ置き換えます。まず all-to-all 演算で rank 間の局所勾配を交換し、その後各 rank が FP32 で局所和を計算します。この設計は数値的な堅牢性を維持します。

#### 3.4.2 費用対効果とメモリ効率に優れた *m*HC 実装

*m*HC の導入は従来の残差接続と比べ、アクティベーションのメモリ消費とパイプライン段階間の通信量を増やします。これらのコストを抑えるため、複数の最適化戦略を実装します。

第一に、学習と推論の双方に向けて *m*HC の融合カーネルを慎重に設計・実装します。第二に、中間テンソルを選択的にチェックポイントする再計算戦略を導入します。具体的には、層間の隠れ状態の大半と、正規化された全層入力を再計算しつつ、計算負荷の高い演算の再計算を避けます。これにより、メモリ節約と計算オーバーヘッドのバランスを取ります。第三に、増加したパイプライン通信に対応し、*m*HC の一部演算を並行実行できるよう、DualPipe 1F1B オーバーラップ方式を調整します。

これらの最適化により、*m*HC の実時間オーバーヘッドをオーバーラップした 1F1B パイプライン段階のわずか 6.7% に抑えます。エンジニアリング最適化の詳細は *m*HC の専論文 [Xie26] に記載されています。

#### 3.4.3 長いコンテキストのアテンションに対する Context Parallelism

従来の Context Parallelism（CP）は系列次元を分割し、各 rank が連続する $s$ トークンを保持します。この方式は、CSA と HCA という圧縮アテンション機構に二つの課題をもたらします。一方で、学習サンプルは複数系列をパックして作られ、各系列は $m$（または $m^{\prime}$）倍で独立に圧縮され、末尾の $m$ 未満のトークンは破棄されます。その結果、圧縮 KV 長は通常 $\frac{s}{m}$ より短く、rank 間で異なります。他方、圧縮には連続する $m$ 個の KV エントリが必要であり、隣接する二つの CP rank の境界をまたぐ場合があります。

これらの課題に対処するため、二段階の通信方式を設計します。第一段階では、各 rank $i$ が末尾の未圧縮 KV エントリ $m$ 個を rank $i+1$ へ送ります。次に rank $i+1$ は、受信したエントリの一部を局所の未圧縮 KV エントリ $s$ 個とともに圧縮し、一部にパディングを含む固定長 $\frac{s}{m}+1$ の圧縮エントリを生成します。第二段階では、全 CP rank にまたがる all-gather 演算で局所圧縮 KV エントリを収集します。次に、融合された select-and-pad 演算子が、総長 $\texttt{cp\_size}\cdot\frac{s}{m}$ の完全な圧縮 KV エントリ集合へ再編成します。パディングエントリは末尾に置きます。HCA と CSA のインデクサでは、各クエリトークンが参照できる圧縮 KV エントリの範囲を規則によって事前計算できます。CSA の疎なアテンションでは、top-$k$ セレクタが各クエリから見える圧縮 KV エントリのインデックスを明示的に指定します。

#### 3.4.4 柔軟な Activation Checkpointing のための自動微分拡張

従来の activation checkpointing 実装はモジュール全体の粒度で動作し、逆伝播中に出力アクティベーションを保持するか再計算するかを決めます。この粗い粒度では、再計算コストとアクティベーションのメモリ占有量とのトレードオフが最適でないことがよくあります。代替手法として、層全体の順伝播・逆伝播ロジックを手動実装し、テンソルのチェックポイント状態を明示的に管理できます。細粒度な制御は可能ですが、自動微分フレームワークの利便性を失い、開発の複雑さが大幅に増します。

プログラミング効率を損なわず細粒度な制御を実現するため、自動微分を支援するテンソル単位の activation checkpointing 機構を実装します。この機構では、開発者は順伝播を実装し、自動チェックポイントと再計算の対象となる個々のテンソルへ選択的に注釈を付けるだけです。フレームワークは TorchFX [Ree22] で計算グラフ全体をトレースします。注釈を付けた各テンソルについて逆向きに走査し、再計算に必要な最小部分グラフを特定します。これを再計算グラフと定義し、対応する勾配計算の直前に逆伝播ロジックへ挿入します。

手動実装と比べ、この設計は学習中に追加オーバーヘッドを生じません。フレームワーク内の再計算は、注釈付きテンソルの GPU メモリを直接解放し、再計算したテンソルのストレージポインタを再利用することで実装し、GPU メモリコピーは行いません。さらに、グラフトレースではモデルを具体的に実行するため、各テンソルの基底ストレージポインタを追跡でき、ストレージを共有するテンソル（例えば reshape 演算の入力と出力）の再計算を自動的に重複排除できます。これにより、再計算の注釈時に開発者が低レベルなメモリ詳細を考える必要がなくなります。

### 3.5 推論フレームワーク

推論フレームワークは大部分を DeepSeek-V3 から継承していますが、KV キャッシュ管理にいくつか違いがあります。

#### 3.5.1 KV キャッシュの構造と管理

DeepSeek-V4 のハイブリッドアテンション機構から生じる異種 KV キャッシュを効率的に管理するため、カスタム KV キャッシュレイアウトを設計します。[図 6](#figure-06) にレイアウトを示し、以下で詳しく説明します。

**DeepSeek-V4 における異種 KV エントリ。** DeepSeek-V4 シリーズのハイブリッドアテンション機構は、Key-Value（KV）キャッシュサイズと更新規則が異なる複数種の KV エントリを導入します。疎な選択を行う Lightning Indexer は、主アテンションとは異なる埋め込みサイズを持つ追加次元を KV キャッシュへ導入します。CSA と HCA の圧縮技法は系列長をそれぞれ $\frac{1}{m}$、$\frac{1}{m^{\prime}}$ に縮め、KV キャッシュ全体を削減します。その結果、KV キャッシュサイズは層ごとに異なります。さらに Sliding Window Attention（SWA）層も、異なる KV キャッシュサイズと独立したキャッシュヒット・エビクションポリシーで動作します。圧縮分岐では $m$ トークンごとに一つの KV エントリを生成します。残りのトークン数が圧縮に不足する場合、圧縮演算を実行できるまで、保留中の全トークンと関連する隠れ状態をバッファに保持する必要があります。これらのバッファ済みトークンは位置コンテキストによって決まる系列状態を表し、KV キャッシュフレームワーク内で管理されます。

![DeepSeek-V4 図 6](../../papers/deepseek-v4/figure-06.png)

**図 6.** DeepSeek-V4 の KV キャッシュレイアウト。KV キャッシュは、CSA/HCA 用の従来型 KV キャッシュと、SWA および CSA/HCA でまだ圧縮できないトークン用の状態キャッシュという二つの主要部分で構成されます。状態キャッシュでは、各リクエストに固定サイズのキャッシュブロックを割り当てます。ブロック内の SWA 区画は直近 $n_{\mathrm{win}}$ トークンに対応する KV エントリを保存し、CSA/HCA 区画はまだ圧縮できない未圧縮の末尾状態を保存します。従来型 KV キャッシュでは、リクエストごとに複数ブロックを割り当てます。各キャッシュブロックは $\mathrm{lcm}(m,m^{\prime})$ 個の元トークンをカバーし、$k_{1}=\frac{\mathrm{lcm}(m,m^{\prime})}{m}$ 個の CSA 圧縮トークンと $k_{2}=\frac{\mathrm{lcm}(m,m^{\prime})}{m^{\prime}}$ 個の HCA 圧縮トークンを生成します。

**ハイブリッドアテンション KV キャッシュ管理の課題。** ハイブリッドアテンション機構は、PagedAttention とその変種が前提とする基本的な仮定に反します。近年のハイブリッド KV キャッシュ管理アルゴリズム（例：Jenga [Zha25g]、Hymba [Don25]）は一般的なハイブリッドアテンションモデルや特定構造を対象としますが、二つの主要な障害により、PagedAttention フレームワークのもとで全層の KV キャッシュを統合できません。

- Sliding Window Attention で使われるものなど、多様なキャッシュポリシー。
- アラインメント要件を含む、高性能アテンションカーネルが課す制約。

DeepSeek-V4 の KV キャッシュを効率的に管理するため、二つの課題を克服する対応戦略を設計します。

**SWA と未圧縮末尾トークン用の状態キャッシュ。** 第一の障害に対処するため、別のキャッシュ管理機構を採用します。SWA は限られた KV キャッシュサイズで性能を高めるよう設計されているため、圧縮分岐の未圧縮末尾トークンとともに状態空間モデルとして扱うのが妥当です。対応する KV キャッシュは、現在位置のみに依存する系列固有の状態とみなせます。そこで、固定かつ有限サイズの状態キャッシュプールを事前割り当てし、各系列へ動的に割り当てます。

**疎なアテンションカーネルの協調設計。** 第二の障害について、従来の高性能アテンションカーネルは、性能最適化のため通常、ブロックあたり固定数 $B$ のトークンを仮定します。これは CSA では $B\cdot m$ 個、HCA では $B\cdot m^{\prime}$ 個の元トークンに対応します。高性能な疎アテンションカーネルを用いれば、異なる層でブロックあたりのトークン数を変えても性能は低下しません。実現には KV キャッシュレイアウトと疎アテンションカーネルの協調設計が必要です。例えば、キャッシュラインへ揃うようブロックをパディングすると性能を高められます。したがって、圧縮率 $m$ の CSA と圧縮率 $m^{\prime}$ の HCA では、ブロックあたりの元トークン数を、二つの圧縮率の最小公倍数 $\mathrm{lcm}(m,m^{\prime})$ の任意の倍数にできます。

#### 3.5.2 ディスク上の KV キャッシュストレージ

DeepSeek-V4 をサービングする際、ディスク上の KV キャッシュストレージ機構を利用し、共有プレフィックスを持つリクエストのプリフィルの繰り返しをなくします。CSA/HCA の圧縮 KV エントリと Sliding Window Attention（SWA）の未圧縮 KV エントリには、別々のストレージ管理策を設計します。

CSA と HCA では、圧縮 KV エントリをすべてディスクへ保存します。リクエストが保存済みプレフィックスにヒットすると、最後の完全な圧縮ブロックまで、プレフィックスに対応する圧縮 KV エントリを読み込んで再利用します。特に、末尾の不完全ブロックにあるプレフィックストークンは、CSA と HCA の未圧縮 KV エントリを保存していないため、未圧縮 KV エントリを復元するために再計算が必要です。

SWA KV エントリは圧縮されず全層に存在するため、その量は圧縮された CSA・HCA KV エントリの約 8 倍です。大規模な SWA KV エントリを効率的に扱うため、ディスク上の SWA KV エントリを管理する三つの異なる戦略を提案・実装します。各戦略はストレージオーバーヘッドと計算冗長性の異なるトレードオフを提供します。

- **完全 SWA キャッシュ。** 全トークンの完全な SWA KV エントリを保存し、計算の冗長性をゼロにします。この戦略では、ヒットしたプレフィックス内の末尾 $n_{\mathrm{win}}$ トークンのディスクキャッシュを読むだけで、そのプレフィックスの SWA KV エントリを再構築できます。計算冗長性はゼロですが、現代の SSD ベースストレージシステムでは非効率です。ヒットするリクエストごとに、保存済み SWA KV キャッシュのごく一部しかアクセスされず、偏った書き込み集中型アクセスパターンが生じます。
- **周期的チェックポイント。** $p$ トークンごとに、その中の末尾 $n_{\mathrm{win}}$ トークンの SWA KV エントリをチェックポイントします。$p$ は調整可能なパラメータです。プレフィックスがヒットすると、最新のチェックポイント状態を読み込み、残りの末尾トークンを再計算します。$p$ を調整することで、ストレージと計算を必要に応じてトレードオフできます。
- **SWA キャッシュなし。** SWA KV エントリを一切保存しません。プレフィックスがヒットした場合、SWA KV エントリを復元するために、より多くの再計算が必要です。具体的には、各アテンション層で各トークンの SWA KV エントリは、前層にある直近 $n_{\mathrm{win}}$ トークンの SWA KV エントリだけに依存します。したがって、キャッシュ済み CSA・HCA KV エントリを利用すれば、$L$ 層モデルで末尾 $n_{\mathrm{win}}$ 個の SWA KV エントリを復元するには、末尾 $n_{\mathrm{win}}\cdot L$ トークンを再計算すれば十分です。

具体的なデプロイ環境に応じて最適な戦略を選び、ストレージと計算の望ましいトレードオフを実現します。

## 4 事前学習

### 4.1 データ構築

DeepSeek-V3 の事前学習データを土台に、より多様で高品質かつ有効コンテキストの長い学習コーパスの構築に取り組みます。データ構築パイプラインは継続的に改善しています。Web 由来データには、一括自動生成コンテンツやテンプレート化コンテンツを除去するフィルタリング戦略を実装し、モデル崩壊のリスクを軽減します [Zhu24]。数学とプログラミングのコーパスは引き続き学習データの中核であり、中間学習段階でエージェントデータを取り入れ、DeepSeek-V4 シリーズのコーディング能力をさらに高めます。多言語データでは、DeepSeek-V4 用により大きなコーパスを構築し、異文化にまたがるロングテール知識の把握を改善します。DeepSeek-V4 では長文書データのキュレーションを特に重視し、科学論文、技術報告書、その他の独自の学術的価値を持つ資料を優先します。以上を組み合わせた事前学習コーパスは 32T トークンを超え、数学コンテンツ、コード、Web ページ、長文書、その他の高品質カテゴリを含みます。

事前学習データには、おおむね DeepSeek-V3 と同じ前処理戦略を用います。トークン化では、DeepSeek-V3 tokenizer を基礎にコンテキスト構築用の特殊トークンを少数導入しつつ、語彙サイズは 128K のままです。DeepSeek-V3 の token splitting [Dee24a] と Fill-in-Middle（FIM）[Dee24b] 戦略も継承します。[Din24a] に着想を得て、異なるソースの文書を適切な系列へパックし、サンプルの切り捨てを最小化します。DeepSeek-V3 とは異なり、事前学習中にサンプル単位のアテンションマスキングを用います。

### 4.2 事前学習の設定

#### 4.2.1 モデル設定

**DeepSeek-V4-Flash.** Transformer 層数を 43、隠れ次元 $d$ を 4096 に設定します。最初の二層には純粋な sliding window attention を用い、後続層では CSA と HCA を交互に使用します。CSA では圧縮率 $m$ を 4、インデクサクエリヘッド数 $n_{h}^{I}$ を 64、インデクサヘッド次元 $c^{I}$ を 128、疎なアテンションで選択する KV エントリ数（attention top-k）を 512 に設定します。HCA の圧縮率 $m^{\prime}$ は 128 です。CSA と HCA の双方で、クエリヘッド数 $n_{h}$ を 64、ヘッド次元 $c$ を 512、クエリ圧縮次元 $d_{c}$ を 1024 に設定します。出力プロジェクショングループ数 $g$ は 8、各中間アテンション出力の次元 $d_{g}$ は 1024 です。sliding window attention の追加分岐では、ウィンドウサイズ $n_{\mathrm{win}}$ を 128 に設定します。全 Transformer ブロックに MoE 層を用いますが、最初の三つの MoE 層には Hash routing 戦略を使用します。各 MoE 層は一つの共有エキスパートと 256 個のルーティングエキスパートからなり、各エキスパートの中間隠れ次元は 2048 です。ルーティングエキスパートのうち、各トークンで六つをアクティブ化します。multi-token prediction の深さは 1 です。*m*HC の拡張係数 $n_{\mathrm{hc}}$ は 4、Sinkhorn-Knopp 反復回数 $t_{\max}$ は 20 です。この構成で DeepSeek-V4-Flash は総パラメータ 284B を持ち、各トークンで 13B をアクティブ化します。

**DeepSeek-V4-Pro.** Transformer 層数を 61、隠れ次元 $d$ を 7168 に設定します。最初の二層には HCA を用い、後続層では CSA と HCA を交互に使用します。CSA では圧縮率 $m$ を 4、インデクサクエリヘッド数 $n_{h}^{I}$ を 64、インデクサヘッド次元 $c^{I}$ を 128、疎なアテンションで選択する KV エントリ数（attention top-k）を 1024 に設定します。HCA の圧縮率 $m^{\prime}$ は 128 です。CSA と HCA の双方で、クエリヘッド数 $n_{h}$ を 128、ヘッド次元 $c$ を 512、クエリ圧縮次元 $d_{c}$ を 1536 に設定します。出力プロジェクショングループ数 $g$ は 16、各中間アテンション出力の次元 $d_{g}$ は 1024 です。sliding window attention の追加分岐ではウィンドウサイズ $n_{\mathrm{win}}$ を 128 に設定します。全 Transformer ブロックに MoE 層を用いますが、最初の三つの MoE 層には Hash routing 戦略を使用します。各 MoE 層は一つの共有エキスパートと 384 個のルーティングエキスパートからなり、各エキスパートの中間隠れ次元は 3072 です。ルーティングエキスパートのうち、各トークンで六つをアクティブ化します。multi-token prediction の深さは 1 です。*m*HC の拡張係数 $n_{\mathrm{hc}}$ は 4、Sinkhorn-Knopp 反復回数 $t_{\max}$ は 20 です。この構成で DeepSeek-V4-Pro は総パラメータ 1.6T を持ち、各トークンで 49B をアクティブ化します。

#### 4.2.2 学習設定

**DeepSeek-V4-Flash.** 大半のパラメータには Muon オプティマイザ [Kel24, Liu25] を用いますが、埋め込みモジュール、予測ヘッドモジュール、全 RMSNorm モジュールの重みには AdamW オプティマイザ [Los17] を用います。AdamW のハイパーパラメータは $\beta_{1}=0.9$、$\beta_{2}=0.95$、$\varepsilon=10^{-20}$、$\mathrm{weight\_decay}=0.1$ です。Muon はモメンタムを 0.95、重み減衰を 0.1 とし、AdamW の学習率を再利用するため、各更新行列の RMS を 0.18 へ再スケーリングします。DeepSeek-V4-Flash を 32T トークンで学習し、DeepSeek-V3 と同様に、バッチサイズ（トークン単位）を小さな値から 75.5M へ増やし、学習の大半で 75.5M に維持するバッチサイズスケジュール戦略を採用します。最初の 2000 ステップで学習率を線形ウォームアップし、学習の大半で $2.7\times 10^{-4}$ に維持します。学習の終了近くでは、最終的に余弦スケジュールに従って $2.7\times 10^{-5}$ まで減衰させます。学習は系列長 4K から始め、16K、64K、1M へ段階的に拡張します。疎なアテンションは、最初の 1T トークンでは密なアテンションでモデルをウォームアップし、系列長 64K で導入して残りの学習中も維持します。アテンションの疎性を導入する際、まず短い段階で CSA の Lightning Indexer をウォームアップし、その後、学習の大半を疎なアテンションで行います。補助損失を用いない負荷分散ではバイアス更新速度を 0.001 に設定します。単一系列内の極端な不均衡を避けるため、バランス損失の重みを 0.0001 に設定します。MTP 損失の重みは学習の大半で 0.3、学習率の減衰開始時に 0.1 とします。

**DeepSeek-V4-Pro.** 具体的なハイパーパラメータ値を除き、DeepSeek-V4-Pro の学習設定は DeepSeek-V4-Flash とほぼ同じです。大半のパラメータには Muon オプティマイザを用いますが、埋め込みモジュール、予測ヘッドモジュール、全 RMSNorm モジュールの重みには AdamW オプティマイザを用います。AdamW と Muon のハイパーパラメータは DeepSeek-V4-Flash と同じです。DeepSeek-V4-Pro を 33T トークンで学習し、最大バッチサイズを 94.4M トークンとするバッチサイズスケジュール戦略も採用します。学習率スケジュールは DeepSeek-V4-Flash とほぼ同じですが、ピーク学習率を $2.0\times 10^{-4}$、終了時学習率を $2.0\times 10^{-5}$ に設定します。学習は系列長 4K から始め、16K、64K、1M へ段階的に拡張します。DeepSeek-V4-Flash と比べ、DeepSeek-V4-Pro はより長い密なアテンション段階から始め、疎なアテンションの導入戦略は DeepSeek-V4-Flash と同じ二段階学習法に従います。補助損失を用いない負荷分散ではバイアス更新速度を 0.001 に設定します。単一系列内の極端な不均衡を避けるため、バランス損失の重みを 0.0001 に設定します。MTP 損失の重みは学習の大半で 0.3、学習率の減衰開始時に 0.1 とします。

#### 4.2.3 学習不安定性の緩和

兆単位パラメータの MoE モデルの学習には大きな安定性の課題があり、DeepSeek-V4 シリーズも例外ではありません。学習中に顕著な不安定性へ直面しました。単純なロールバックで学習状態を一時的に復元できても、損失スパイクの再発を防げないため、長期的な解決策としては不十分でした。経験的に、スパイクの発生は一貫して MoE 層の外れ値と結びつき、ルーティング機構自体が外れ値の出現を悪化させるようです。そこで、ルーティングが引き起こす悪循環を断つことと、異常値を直接抑えることの二面から問題に対処しました。幸い、学習安定性を効果的に保つ二つの実用的な技法を発見しました。基礎機構の包括的な理論理解は現時点で未解決ですが、コミュニティによるさらなる探究を促すため公開します。

**Anticipatory Routing。** バックボーンネットワークとルーティングネットワークの同期更新を分離すると、学習安定性が大幅に向上することを発見しました。そこでステップ $t$ では、現在のネットワークパラメータ $\theta_{t}$ で特徴を計算しますが、ルーティングインデックスは過去のネットワークパラメータ $\theta_{t-\Delta t}$ で計算・適用します。実際には、モデルパラメータを二度読み込むオーバーヘッドを避けるため、ステップ $t-\Delta t$ でステップ $t$ のデータを先に取得します。後にステップ $t$ で使うルーティングインデックスを「先取りして」計算・キャッシュするため、この手法を Anticipatory Routing と呼びます。インフラストラクチャレベルでも大幅に最適化しました。第一に、ルーティングインデックスの事前計算にはデータに対する一回の順伝播しか必要ないため、パイプライン実行と計算・Expert Parallelism（EP）通信のオーバーラップを慎重に編成し、Anticipatory Routing の追加実時間オーバーヘッドを約 20% に抑えました。第二に、損失スパイクが発生したときだけ短いロールバックを起動して Anticipatory Routing を有効化し、一定期間このモードで動作した後に標準学習へ戻す自動検出機構を導入しました。最終的に、この動的な適用により、モデル性能を損なわず、全体の追加学習オーバーヘッドを無視できる範囲に抑えながら損失スパイクを回避できます。

**SwiGLU Clamping。** 先行研究 [Bel17, Gem24] では、数値範囲を制約して学習安定性を高めるため clamping が明示的に用いられています。実際の学習では、SwiGLU clamping [Ope25c] が性能を損なわず外れ値を効果的に除去し、学習過程の安定化に大きく寄与することを経験的に確認しました。DeepSeek-V4-Flash と DeepSeek-V4-Pro の学習全体を通じ、SwiGLU の線形成分を $[-10,10]$ の範囲へ clamp し、gate 成分の上限を $10$ としました。

## 5 後学習

### 5.1 後学習パイプライン

事前学習に続いて後学習段階を実施し、DeepSeek-V4 シリーズの最終モデルを得ました。学習パイプラインはおおむね DeepSeek-V3.2 を踏襲しましたが、方法論上の重要な置換を行いました。混合 Reinforcement Learning（RL）段階を On-Policy Distillation（OPD；[Lu25, Gu25]）で完全に置き換えています。

#### 5.1.1 スペシャリスト学習

ドメインスペシャリストは DeepSeek-V3.2 の学習パイプラインを適応して開発しました。具体的には、各モデルを最初のファインチューニング段階と、それに続くドメイン固有のプロンプト・報酬信号に導かれた Reinforcement Learning（RL）によって順に最適化します。RL 段階では Group Relative Policy Optimization（GRPO）アルゴリズムを実装し、以前の研究 [Guo25, Dee25a] とほぼ同じハイパーパラメータを維持します。

**推論強度。** 推論タスクにおけるモデル性能は、投入される計算量によって根本的に左右されると広く認識されています。そこで、異なる推論強度に最適化したモデルを開発するため、異なる RL 構成のもとで別々のスペシャリストモデルを学習しました。[表 2](#table-02) のとおり、DeepSeek-V4-Pro と DeepSeek-V4-Flash はいずれも三つの推論強度モードをサポートします。各モードでは RL 学習中に異なる長さペナルティとコンテキストウィンドウを適用し、推論出力のトークン長が異なります。異なる推論モードを統合するため、`<think>` と `</think>` トークンで区切る専用の応答形式を用います。さらに「Think Max」モードでは、[表 3](#table-03) のように、モデルの推論過程を導く特定の指示をシステムプロンプトの先頭へ付加します。

**Generative Reward Model。** 通常、検証しやすいタスクは単純なルールベースの verifier やテストケースで効果的に最適化できます。一方、検証しにくいタスクは従来、スカラー報酬モデルの学習に大量の人手注釈を必要とする Reinforcement Learning from Human Feedback（RLHF）へ依存してきました。しかし DeepSeek-V4 シリーズの後学習段階では、従来のスカラーベース報酬モデルを使用しません。代わりに、検証しにくいタスクへ対処するため rubric に導かれた RL データをキュレーションし、Generative Reward Model（GRM）で方策軌跡を評価します。重要なのは、GRM 自体へ直接 RL 最適化を適用することです。このパラダイムでは actor ネットワークがネイティブに GRM として機能し、モデルの評価（判定）能力を標準的な生成能力とともに共同最適化できます。役割を統一するとモデル内部の推論能力が評価過程へ自然に融合し、非常に堅牢なスコアリングが得られます。さらに、モデルが自身の論理を利用して複雑なタスク間で汎化するため、この手法は最小限の多様な人手注釈だけで優れた性能を実現します。

#### 5.1.2 On-Policy Distillation

専用のファインチューニングと強化学習によって複数のドメイン特化エキスパートを学習した後、エキスパート能力を最終モデルへ統合する主要技法として、複数教師の On-Policy Distillation（OPD；[Lu25, Gu25]）を用います。OPD はドメインエキスパートの知識と能力を単一の統一モデルへ効率的に移す、効果的な後学習パラダイムです。生徒自身が生成した軌跡における教師モデルの出力分布から生徒を学習させることで実現します。形式的には、$N$ 個のエキスパートモデルの集合 $\{\pi_{E_{1}},\pi_{E_{2}},\dots,\pi_{E_{N}}\}$ が与えられたとき、OPD 目的関数を次のように定義します。

$$
\mathcal{L}_{\mathrm{OPD}}(\theta)=\sum_{i=1}^{N}w_{i}\cdot\mathrm{D}_{\mathrm{KL}}\left(\pi_{\theta}\parallel\pi_{E_{i}}\right).\tag{29}
$$

この式で $w_{i}$ は各エキスパートへ割り当てる重みを表し、通常はエキスパートの相対的な重要性で決まります。逆 KL 損失 $\mathrm{D}_{\mathrm{KL}}\left(\pi_{\theta}\parallel\pi_{E_{i}}\right)$ の計算には、オンポリシー学習を維持するため、生徒 $\pi_{\theta}$ から学習軌跡をサンプリングする必要があります。基礎ロジックにより、統一方策 $\pi_{\theta}$ は現在のタスクコンテキストに関連する専門エキスパートから選択的に学びます（例えば数学推論タスクでは数学エキスパート、プログラミングタスクではコーディングエキスパートと整合します）。この機構を通じ、物理的に異なるエキスパート重みの知識をロジットレベルの整合によって統一パラメータ空間へ統合し、従来の重みマージや混合 RL 技法で生じやすい性能低下を実質的に回避します。この段階では、さまざまなドメインを網羅する十を超える教師モデルから単一の生徒モデルを蒸留します。

上の OPD 目的を扱う際、先行研究では通常、全語彙 KL 損失を各トークン位置のトークンレベル KL 推定へ簡略化し、方策損失の計算で $\texttt{sg}\big[\log\frac{\pi_{E_{i}}(y_{t}|x,y_{<t})}{\pi_{\theta}(y_{t}|x,y_{<t})}\big]$（`sg` は stop gradient 演算）をトークンごとの advantage 推定として置くことで RL フレームワークを再利用します。この手法は資源効率に優れますが、勾配推定の分散が大きくなり、学習不安定性を招きがちです。そのため OPD には全語彙ロジット蒸留を採用します。逆 KL 損失の計算で完全なロジット分布を保持すると、勾配推定が安定し、教師知識を忠実に蒸留できます。次節では、全語彙 OPD を大規模に実現するエンジニアリング上の取り組みを説明します。

### 5.2 後学習インフラストラクチャ

後学習インフラストラクチャは、DeepSeek-V3.2 用に開発したスケーラブルなフレームワークを基盤とします。具体的には、第 3.4 節で説明した分散学習スタックと、効率的な自己回帰サンプリングのために先に導入したロールアウトエンジンを統合します。この基盤上に、本研究では次の主要な拡張を導入します。これらの設計により、十を超える異なる教師モデルが関与する超長コンテキスト RL と OPD マージタスクを効率的に実行でき、モデルリリースの反復サイクルを大幅に加速します。

#### 5.2.1 FP4 Quantization-Aware Training

デプロイ時の推論高速化とメモリトラフィック削減のため、後学習段階で Quantization-Aware Training（QAT）[Ben18] を導入し、教師・参照モデルを含むモデルを量子化による精度低下へ適応させます。FP4（MXFP4）量子化 [Dar23] を二つのコンポーネントへ適用します。(1) GPU メモリ占有の主因である MoE エキスパート重み [Ope25c]、(2) CSA のインデクサにある Query-Key（QK）経路です。後者では QK アクティベーションをすべて FP4 でキャッシュ、読み込み、乗算し、長いコンテキストでのアテンションスコア計算を高速化します。加えて、この QAT 過程でインデックススコア $I_{:,:}$ を FP32 から BF16 へ量子化します。この最適化により、KV エントリの再現率 99.7% を維持しつつ、top-k セレクタを 2$\times$ 高速化します。

MoE エキスパート重みでは、QAT の一般的手法に従い、オプティマイザが保持する FP32 マスター重みをまず FP4 へ量子化し、計算用に FP8 へ逆量子化します。特筆すべきことに、FP4 から FP8 への逆量子化は無損失です。FP8（E4M3）は FP4（E2M1）より指数ビットが二つ多く、より広い動的範囲を持つためです。したがって、各 FP8 量子化ブロック（$128\times 128$ タイル）内の FP4 サブブロック（$1\times 32$ タイル）における最大・最小スケール係数の比が一定の閾値を超えなければ、細粒度なスケール情報を FP8 の拡張された動的範囲に完全に収められます。現在の重みがこの条件を満たすことを経験的に検証しました。これにより、QAT パイプライン全体が既存の FP8 学習フレームワークを変更せず完全に再利用できます。逆伝播では、順伝播と同じ FP8 重みに関して勾配を計算し、FP32 マスター重みへ直接伝播します。これは量子化演算を通して Straight-Through Estimator（STE）を適用することに相当します。また、転置重みを再量子化する必要もありません。

逆伝播を伴わない RL 学習の推論・ロールアウト段階では、模擬量子化ではなくネイティブな FP4 量子化重みを直接使用します。これにより、サンプリング中のモデル動作をオンライン展開と完全に一致させると同時に、カーネルのメモリ読み込みを削減して実際に高速化し、メモリ消費も大幅に低減します。CSA のインデクサにある QK 経路も同様に処理します。

#### 5.2.2 全語彙 OPD の効率的な教師スケジューリング

本フレームワークは、教師数が実質的に無制限で、各教師が兆単位のパラメータを持ちうる全語彙 On-Policy Distillation（OPD）をサポートします。これを実現するため、全教師重みを集中型分散ストレージへオフロードし、教師の順伝播中に ZeRO に似たパラメータシャーディングでオンデマンドに読み込み、I/O と DRAM の双方の負荷を軽減します。また、全教師について語彙サイズ $|V|>100\mathrm{k}$ のロジットを単純に実体化することは、ディスクへスプールしても非現実的です。順伝播中、教師の最終層隠れ状態だけを集中バッファへキャッシュして対処します。学習時にはキャッシュ状態を取得し、対応する予測ヘッドモジュールへ通して完全なロジットを即時再構築します。この設計は再計算オーバーヘッドを無視できる範囲に抑えつつ、明示的なロジット実体化に伴うメモリ負担を完全に回避します。教師予測ヘッドの GPU メモリ占有を抑えるため、データ分配時に教師インデックス順で学習サンプルを並べます。これにより各教師ヘッドは mini-batch ごとに一度だけ読み込まれ、任意の時点でデバイスメモリにある教師ヘッドは最大一つです。全パラメータと隠れ状態の読み込み・オフロードはバックグラウンドで非同期に進み、クリティカルパスの計算をブロックしません。最後に、教師と生徒のロジット間の正確な KL ダイバージェンスを専用 TileLang カーネルで計算し、計算を高速化して動的メモリ割り当てを抑えます。

#### 5.2.3 プリエンプション対応の耐障害ロールアウトサービス

GPU リソース利用率を最大化しつつ、高優先度タスクへハードウェアを迅速に割り当てるため、GPU クラスタはクラスタ全体のプリエンプティブタスクスケジューラを使用し、実行中の任意のタスクがいつでもプリエンプトされます。また、大規模 GPU クラスタではハードウェア障害が頻発します。このため、RL/OPD ロールアウト用にプリエンプション対応の耐障害 LLM 生成サービスを実装します。

具体的には、各生成リクエストへトークン粒度の Write-Ahead Log（WAL）を実装します。リクエストで新しいトークンを生成するたび、そのリクエストの WAL へ直ちに追記します。プリエンプト時には推論エンジンを一時停止し、未完了リクエストの KV キャッシュを保存します。再開時には永続化した WAL と保存 KV キャッシュでデコードを継続します。致命的なハードウェアエラーが起きても、WAL 内の永続化トークンでプリフィル段階を再実行し、KV キャッシュを再構築できます。

重要なのは、未完了リクエストを最初から再生成すると長さバイアスが入るため、数学的に誤っていることです。短い応答ほど中断を生き残りやすいため、最初から再生成すると、中断が起きるたびにモデルが短い系列を生成しやすくなります。推論スタックがバッチ不変かつ決定論的なら、サンプラーの擬似乱数生成器へ固定した同一の seed を用いて再生成することでも、この正確性の問題へ対処できます。しかし、この手法でもデコード段階を再実行する追加コストがかかり、トークン粒度 WAL 法よりはるかに非効率です。

#### 5.2.4 RL フレームワークの 100 万トークンコンテキストへの拡張

100 万トークン系列で RL と OPD を効率的に行うため、対象を絞った最適化を導入します。ロールアウト段階では、第 5.2.3 節で詳述したプリエンプション対応の耐障害ロールアウトサービスを採用します。推論・学習段階では、ロールアウトデータ形式を軽量メタデータと大容量のトークン単位フィールドへ分解します。データ分配中、ロールアウトデータ全体のメタデータを読み込み、グローバルなシャッフルとパッキングレイアウト計算を実行できます。大容量のトークン単位フィールドは、ノード内データ冗長性をなくす共有メモリデータローダーで読み込み、mini-batch 粒度で使用後すぐ解放し、CPU と GPU のメモリ負荷を大幅に軽減します。デバイス上の mini-batch 数をワークロードに応じて動的に決め、計算スループットと I/O オーバーラップの効率的なトレードオフを実現します。

#### 5.2.5 エージェント AI 用サンドボックスインフラストラクチャ

後学習と評価におけるエージェント AI の多様な実行要件へ応えるため、本番品質のサンドボックスプラットフォーム **DeepSeek Elastic Compute（DSec）**を構築します。DSec は API ゲートウェイ（`Apiserver`）、ホストごとのエージェント（`Edge`）、クラスタモニター（`Watcher`）という三つの Rust コンポーネントからなり、カスタム RPC プロトコルで相互接続し、3FS 分散ファイルシステム [Dee25b] 上で水平スケールします。本番環境では、単一 DSec クラスタが数十万の同時サンドボックスインスタンスを管理します。

DSec の設計は四つの観察に基づきます。(1) エージェントワークロードは非常に異種で、軽量な関数呼び出しから、多様な OS・セキュリティ要件を持つ完全なソフトウェアエンジニアリングパイプラインまで広がる、(2) 環境イメージは数が多く巨大だが、迅速に読み込み、反復的なカスタマイズを支援しなければならない、(3) 高密度デプロイには効率的な CPU・メモリ利用が必要である、(4) サンドボックスのライフサイクルは、プリエンプトとチェックポイントベースの再開を含む GPU 学習スケジュールと協調しなければならない、という観察です。これらを踏まえ、以下で DSec の四つの中核設計を個別に説明します。

**単一の統一インターフェースで扱う四つの実行バックエンド。** DSec は四つの実行バックエンドを抽象化する単一の Python SDK（`libdsec`）を公開します。**Function Call** はステートレスな呼び出しをウォームアップ済みコンテナプールへ分配し、コールドスタートのオーバーヘッドをなくします。**Container** は Docker と完全互換で、EROFS [Gao19] のオンデマンド読み込みを利用してイメージを効率的に組み立てます。Firecracker [Aga20] 上に構築する **microVM** は、セキュリティに敏感な高密度デプロイへ VM レベルの分離を加えます。QEMU [Bel05] 上に構築する **fullVM** は任意のゲスト OS をサポートします。四つはいずれも、コマンド実行、ファイル転送、TTY アクセスという共通 API を持ち、パラメータを一つ変更するだけで切り替えられます。

**階層ストレージによる高速イメージ読み込み。** DSec は階層化オンデマンド読み込みによって、高速起動と大規模で増え続ける環境イメージ群を両立します。コンテナでは、ベースイメージとファイルシステム commit を 3FS を基盤とする読み取り専用 EROFS 層として保存し、overlay の `lowerdir` へ直接マウントします。マウント時にファイルメタデータをローカルディスクで即座に利用できる状態に保ち、データブロックは要求時に 3FS から取得します。microVM では DSec が `overlaybd` [Li20] ディスク形式を使用します。読み取り専用ベース層はインスタンス間共有のため 3FS に置き、書き込みはローカルの copy-on-write 層へ行います。こうしたスナップショットは連鎖でき、効率的なバージョン管理とミリ秒単位の再開が可能です。

**大規模同時実行下の密度最適化。** クラスタあたり数十万のサンドボックスを収容するため、DSec は二つの資源ボトルネックへ対処します。第一に、仮想化環境で重複するページキャッシュ占有量を削減し、メモリ回収を適用して安全なオーバーコミットを可能にします。第二に、コンテナランタイムのスピンロック競合を緩和し、サンドボックスあたりの CPU オーバーヘッドを削減して、ホストあたりのパッキング密度を大幅に高めます。

**軌跡ロギングとプリエンプト後の安全な再開。** DSec は各サンドボックスに対してグローバルに順序付けられた軌跡ログを維持し、すべてのコマンド呼び出しと結果を永続的に記録します。軌跡には三つの目的があります。(1) **クライアントの fast-forwarding**：学習タスクがプリエンプトされてもサンドボックスリソースを保持し、再開時に DSec が完了済みコマンドのキャッシュ結果を再生してタスク復旧を高速化し、非冪等演算の再実行によるエラーも防ぐ、(2) **細粒度な来歴管理**：各状態変化の起源と対応結果を追跡できる、(3) **決定論的再生**：任意の過去セッションを軌跡から忠実に再現できる、という目的です。

### 5.3 標準ベンチマーク評価

#### 5.3.1 評価設定

**知識と推論。** 知識・推論データセットには MMLU-Pro [Wan24c]、GPQA [Rei24]、Human Last Exam [Pha25]、Simple-QA Verified [Haa25]、Chinese-SimpleQA [He24]、LiveCodeBench-v6 [Jai24]、CodeForces（内部ベンチマーク）、HMMT 2026 Feb、Apex [Bal25]、Apex Shortlist [Bal25]、IMOAnswerBench [Luo25]、PutnamBench [Tso24] が含まれます。

コードについては、LiveCodeBench-v6 と内部 Codeforces ベンチマークで DeepSeek-V4 シリーズを評価します。Codeforces では、114 問からなる 14 回の Codeforces Division 1 コンテスト（2025 年 5 月～11 月）を収集します。Elo レーティングは次のように計算します。各コンテストで問題ごとに 32 個の候補解答を生成します。問題ごとに独立して、その中から 10 個を非復元抽出し、ランダム順に並べて提出系列を作ります。各提出はドメインエキスパートが構築したテストスイートで判定します。正解した問題のスコアは OpenAI（2025）のペナルティ方式に従います。モデルは、同じ回数の失敗後に同じ問題を解いた人間参加者のスコア中央値を受け取ります。これにより各サンプル提出系列のコンテスト総得点を得て、コンテスト順位へ変換し、その後、標準 Codeforces レーティングシステムで推定レーティングへ変換します。コンテスト単位の期待レーティングは、問題ごとの 10 提出について可能な全ランダム選択・順序にわたる推定レーティングの期待値です。モデル全体のレーティングは、全 14 コンテストのコンテスト単位期待レーティングの平均です。

推論・知識タスクでは温度を 1.0 とし、Non-think、High、Max モードのコンテキストウィンドウをそれぞれ 8K、128K、384K トークンに設定します。数学タスク（HMMT、IMOAnswerBench、Apex、HLE など）は次のテンプレートで評価します：`"{question}\nPlease reason step by step, and put your final answer within \boxed{}."`。数学タスクの DeepSeek-V4-Pro-Max では、より深い推論を引き出すため次のテンプレートを用います：`"Solve the following problem. The problem may ask you to prove a statement, or ask for an answer. If finding an answer is required, you should come up with the answer, and your final solution should also be a rigorous proof of that answer being valid.\n\n{question}"`。

形式数学タスクは Lean v4.28.0-rc1 [Mou21] 上のエージェント設定で評価し、Lean コンパイラと意味的 tactic 検索エンジンへアクセスし、最高推論強度で最大 500 回のツール呼び出しを実行します。加えて、より計算集約的なパイプラインも評価します。まず自然言語の候補解答を生成して自己検証 [Sha25] でフィルタリングし、残った解答を形式エージェントへ指針として与え、対応する Lean 文を証明させます。この設計は非形式推論で探索を改善しつつ、形式検証で厳密な正しさを維持します。厳密 verifier の Comparator が両設定で受理した場合に限り、提出を正解と数えます。

K2.6 と GLM-5.1 は、API が過負荷でクエリへ応答しなかったため、一部の項目を空欄にしています。

**1M トークンコンテキスト。** DeepSeek-V4 シリーズは 1M トークンコンテキストをサポートするため、OpenAI MRCR [Ope24d] と CorpusQA [Lu26] をベンチマークに選び、長いコンテキストでモデル性能を評価します。全モデルの構成を標準化するため、Claude Opus 4.6 と Gemini 3.1 Pro をこれらのタスクで再評価します。GPT-5.4 は API が多数のクエリへ応答しなかったため評価しませんでした。

**エージェント。** エージェントデータセットには Terminal Bench 2.0 [Mer26]、SWE-Verified [Ope24e]、SWE Multilingual [Yan25b]、SWE-Pro [Den25]、BrowseComp [Wei25]、MCPAtlas [Ban26a] の公開評価セット、GDPval-AA [Pat25, Aa25]、Tool-Decathlon [Too26] が含まれます。

コードエージェントタスク（SWE-Verified、Terminal-Bench、SWE-Pro、SWE Multilingual）では、社内開発した評価フレームワークで DeepSeek-V4 シリーズを評価します。このフレームワークは bash ツールとファイル編集ツールという最小限のツールを提供します。最大インタラクションステップ数は 500、最大コンテキスト長は 512K トークンです。Terminal-Bench 2.0 については、GLM-5.1 が指摘した環境関連の問題を認識しています。それでも一貫性のため、元の Terminal-Bench 2.0 データセットでの性能を報告します。Terminal-Bench 2.0 Verified サブセットで、DeepSeek-V4-Pro は約 72.0 点を達成します。

検索エージェントタスク（BrowseComp、HLE w/ tool）でも、Web 検索と Python ツールを備えた社内ハーネスを使用し、最大インタラクションステップ数を 500、最大コンテキスト長を 512K トークンに設定します。BrowseComp には DeepSeek-V3.2 [Dee25a] と同じ全破棄コンテキスト管理戦略を用います。

### 5.4 実世界タスクの性能

標準化ベンチマークでは、多様な実世界タスクの複雑さを捉えることが難しく、テスト結果と実際のユーザー体験の間に隔たりが生じがちです。これを埋めるため、従来のベンチマークより実世界の利用パターンを優先する独自の内部指標を開発しました。この手法は最適化を具体的な利点へ結びつけます。評価フレームワークは DeepSeek API と Chatbot の主要ユースケースを特に対象とし、モデル性能を実用上の要求へ合わせます。

#### 5.4.1 中国語の文章作成

DeepSeek の主要ユースケースの一つは中国語の文章作成です。実用文と創作文について厳密な評価を行いました。[表 12](#table-12) は、実用文タスクにおける DeepSeek-V4-Pro と Gemini-3.1-Pro のペア比較です。タスクは一般的な日常文章作成クエリで構成され、プロンプトは通常、簡潔で明快です。評価で中国語文章作成の性能が最も高い外部モデルであるため、Gemini-3.1-Pro をベースラインに選びました。結果は DeepSeek-V4-Pro が総合勝率 62.7% 対 34.1% でベースラインを上回ることを示します。主な理由は、中国語の文章作成シナリオで Gemini が固有の文体上の好みをユーザーの明示的要件より優先する場合があることです。

[表 13](#table-13) は創作文の比較で、指示追従と文章品質の二軸で評価します。Gemini-3.1-Pro と比べ、DeepSeek-V4-Pro は指示追従で 60.0%、文章品質で 77.5% の勝率を達成し、指示追従はわずかに改善、文章品質は大幅に向上しています。DeepSeek-V4-Pro はユースケース全体の分析では優れた結果を示しますが、複雑度の高い制約や複数ターンシナリオを含む、特に難しいプロンプトだけに限定すると、Claude Opus 4.5 が DeepSeek-V4-Pro に対する性能上の優位性を維持します。[表 14](#table-14) のように、Claude Opus 4.5 の勝率は 52.0% 対 45.9% です。

#### 5.4.2 検索

検索拡張型の質問応答は DeepSeek チャットボットの中核能力です。DeepSeek の Web とアプリでは、「non-think」モードが Retrieval-Augmented Search（RAG）を用い、「thinking」モードがエージェント検索を用います。

**Retrieval Augmented Search。** 客観・主観の両 Q&A カテゴリで DeepSeek-V4-Pro と DeepSeek-V3.2 をペア評価しました。[表 11](#table-11) のように、DeepSeek-V4-Pro は DeepSeek-V3.2 を大差で上回り、両カテゴリで一貫した優位性を示します。単一値検索と計画・戦略タスクで最も顕著に向上し、DeepSeek-V4-Pro が正確な事実回答を見つけ、検索コンテキストから構造化された計画を統合することに優れていると示唆されます。ただし DeepSeek-V3.2 は比較・推薦タスクで比較的競争力を保っており、検索結果に対する均衡の取れた多視点推論が必要なシナリオでは DeepSeek-V4-Pro に改善の余地があります。

**エージェント検索。** 標準 RAG と異なり、エージェント検索はクエリごとに検索・取得ツールを反復呼び出しでき、全体の検索性能を大幅に高めます。DeepSeek-Chat の thinking モードでは、事前定義した「思考予算」内で応答精度を最大化するようエージェント検索機能を最適化しました。[表 9](#table-09) のように、エージェント検索は一貫して RAG を上回り、特に複雑なタスクで顕著です。またコスト効率も高く、標準 RAG よりわずかに高価なだけです（[表 10](#table-10)）。

## 6 結論、限界、今後の方向性

本研究では、超長コンテキスト処理の効率障壁を打破する次世代大規模言語モデルを目指し、DeepSeek-V4 シリーズのプレビュー版を提示します。CSA と HCA を組み合わせたハイブリッドアテンションアーキテクチャにより、DeepSeek-V4 シリーズは長系列の効率を飛躍的に高めます。アーキテクチャ上の革新と広範なインフラストラクチャ最適化により、100 万トークン級コンテキストをネイティブかつ効率的にサポートし、将来のテスト時スケーリング、長期タスク、オンライン学習など新たなパラダイムに必要な基盤を確立します。評価結果は、DeepSeek-V4-Pro の最高推論強度モードである DeepSeek-V4-Pro-Max が、オープンモデルの最先端を塗り替えることを示します。知識ベンチマークで従来のオープンソースモデルを大幅に上回り、フロンティアのプロプライエタリモデルに迫る優れた推論性能を達成し、競争力のあるエージェント能力を提供します。一方、DeepSeek-V4-Flash-Max は費用対効果に非常に優れたアーキテクチャを維持しながら、主要クローズドモデルに匹敵する推論性能を達成します。DeepSeek-V4 シリーズはオープンモデルに 100 万トークン級コンテキストの新時代をもたらし、より高い効率、規模、知能への道を拓くと考えています。

極限の長いコンテキスト効率を追求するため、DeepSeek-V4 シリーズは大胆なアーキテクチャ設計を採用しました。リスクを最小化するため、多くの予備検証済みコンポーネントと技法を残しました。これらは効果的ですが、アーキテクチャを比較的複雑にしました。今後のイテレーションでは、より包括的かつ原則に基づく調査を行い、アーキテクチャを最も本質的な設計へ絞り込み、性能を犠牲にせず洗練させます。また Anticipatory Routing と SwiGLU Clamping は学習不安定性の緩和に有効と証明されましたが、その原理は十分に理解されていません。学習安定性の根本課題を積極的に研究し、内部指標の監視を強化して、安定した大規模学習に対する、より原則的で予測可能な手法を目指します。さらに MoE と疎なアテンションアーキテクチャにとどまらず、より疎な埋め込みモジュール [Che26b] など、新しい次元でのモデル疎性を積極的に探究し、能力を損なわず計算・メモリ効率をさらに高めます。低レイテンシのアーキテクチャとシステム技術も継続的に調査し、長いコンテキストのデプロイとインタラクションの応答性を高めます。また長期・複数ラウンドのエージェントタスクの重要性と実用価値を認識し、この方向でイテレーションと探究を続けます。モデルへのマルチモーダル能力の導入にも取り組んでいます。最後に、より良いデータキュレーション・合成戦略を開発し、ますます広範なシナリオとタスクでモデルの知能、堅牢性、実用性を継続的に高めます。
