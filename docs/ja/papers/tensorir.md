### 概要

さまざまなデバイスへ深層学習モデルを展開することが重要な課題となっている。ハードウェア専用化の波は、多次元テンソル計算のための多様な高速化プリミティブをもたらした。こうした新しい高速化プリミティブと新興の機械学習モデルは、極めて大きなエンジニアリング上の課題を生んでいる。本論文では、これらのテンソル計算プリミティブを含むプログラムを最適化するコンパイラ抽象 TensorIR を提示する。TensorIR は既存の機械学習コンパイラで用いられるループネスト表現を一般化し、テンソル計算を第一級の要素として扱う。さらに、この抽象の上にエンドツーエンドのフレームワークを構築し、与えられたテンソル計算プリミティブに対して深層学習モデルを自動最適化する。実験結果から、TensorIR によるコンパイルは指定されたハードウェアバックエンドのテンソル計算プリミティブを自動的に利用し、複数のプラットフォームにおいて最先端の手動最適化システムと競合する性能を実現することが分かった。

## 1 はじめに

<span id="figure-01"></span>

![キャプション参照](../../papers/tensorir/figure-01.png)

**図 1。** ハードウェア専用化の動向。古典的な高速化手法では、ベクトルユニットを用いて複数のスカラー計算を同時に処理し、現在も CPU プラットフォームで広く使われている。しかし、増大し続ける計算スループット要求に応えるため、現代のアクセラレータは専用の高次元テンソル計算命令を備えることが多く、テンソル化プログラム最適化が必要となる。

画像認識 [He16, Sim15, How17]、自然言語処理 [Vas17, Dev18, Rad19]、ゲーム [Mni13, Lil15, Sch17] など、さまざまな領域で高性能な機械学習モデルの展開が新たな課題となっている。機械学習の進展により、幅広いモデルを支援する必要が生じた。同時に、サーバーから組み込み環境まで、広範なデバイスへスマートアプリケーションを展開する需要も高まっている。

ハードウェア専用化の波は、この問題をさらに複雑にする（[図 1](#figure-01)）。機械学習の高速化を目的として、現代のハードウェアバックエンドは Nvidia Tensor Core [Nvi17] や Google TPU [Jou17a] など、テンソル計算を高速化する専用プリミティブを導入している。分野の専門家も、ドメイン固有のテンソル演算子ライブラリを高速化するため、高度に最適化された一連の命令を慎重に構成して部分計算を行うマイクロカーネル・プリミティブの開発を始めている。これらのハードウェア命令とマイクロカーネル・プリミティブは通常、多次元テンソル領域に作用し、多次元ロード、ドット積、行列乗算などのテンソル演算を実質的に実行する（[図 1](#figure-01)）。このような不透明なテンソル計算高速化構成要素を*テンソル化組み込み関数*、それらを利用する変換手順を*テンソル化*と呼ぶ。これらのハードウェアバックエンドを最大限に活用するには、階層的ループネスト、多次元ロード、テンソル組み込み関数を含むプログラムを現代の機械学習システムが最適化しなければならない。この問題を*テンソル化プログラム最適化*と呼ぶ。

現在のテンソル化プログラムの多くは、分野の専門家によって最適化されている。専門家はテンソル化プリミティブを多次元ループ、スレッドパターン、データキャッシュと組み合わせ、Intel MKL-DNN [Int17]、ARM Compute Library [Arm17]、NVIDIA cuDNN [Che14] などの専用カーネルライブラリを作成する。これらは TensorFlow [Aba16]、PyTorch [Pas19]、MXNet [Che15] などの機械学習フレームワークから利用される。しかし、増え続けるモデルとバックエンドを支援するには膨大なエンジニアリング作業が必要であり、急速に変化・拡大する機械学習アプリケーションへライブラリが適応するまでには反復サイクルを要するため、新しい機械学習モデルの進化を妨げている。

<span id="figure-02"></span>

![キャプション参照](../../papers/tensorir/figure-02.png)

**図 2。** 熟練した開発者は、問題を $4\times4$ 行列乗算と、それを利用するループへ分割し、両者を別々に最適化できる。これにより、対象ハードウェアの専用テンソル命令を効果的に利用できる。

本論文では、自動コンパイルによってテンソル化プログラム最適化問題へ取り組む。従来の機械学習コンパイル研究 [Che18, Vas18] の多くは、ループネスト変換から成るプログラム空間を探索するもので、テンソル化プログラムを自動処理できない。自動プログラム最適化をテンソル化プログラムへ持ち込めば、現代のハードウェアバックエンドが備えるドメイン固有高速化の利点を引き出せる。この目標には、次の主要な課題がある。

**テンソル化プログラムの抽象** テンソル化プログラム用の自動コンパイラを構築するには、与えられた機械学習演算子について、等価になり得るテンソル化計算を実用的に捉えられる抽象が必要である。特に、多次元メモリアクセス、スレッド階層、異なるハードウェアバックエンドのテンソル化計算プリミティブを表現できなければならない。また、機械学習で対象となる演算子の大半を表現できるだけの表現力も必要である。

**テンソル化プログラム最適化の巨大な設計空間** もう一つの課題は、与えられた演算子に対して最適化済みテンソル化プログラムを自動生成することである。コンパイラは、ループタイリング、スレッド化、データレイアウト変換の効果的な利用など、専門家が用いる多彩な手法を活用しなければならない。さらに、これらの変換をテンソル化計算と同時に行う必要があり、解析と自動化は一層複雑になる。変換の組合せは巨大な探索空間を形成する。与えられた探索空間から最適化済みテンソル化プログラムを見つける効果的な方法が必要である。

これらの課題に対処するため、自動テンソルプログラム最適化の抽象 *TensorIR* を導入する。まず、*block* という新しい構成要素を導入し、テンソル化計算領域を外側のループネストから分割・分離できるようにする。この新しい抽象により、テンソル化計算を効果的に表現し、ループネスト、スレッド、メモリ階層と組み合わせられる。また、豊富な最適化候補の空間を表すプログラム変換プリミティブを導入し、この抽象と変換プリミティブの上に新しい自動スケジューリングアルゴリズムを構築する。さらに TensorIR 抽象は、不規則計算とテンソル計算が混在するプログラムも表現・最適化でき、通常のテンソル式 [Che18] を超えて支援範囲を広げる。本論文の貢献は次のとおりである。

- テンソル化計算とループ変換を分離する、新しいテンソル化プログラム抽象を提案する。同じ抽象によって、テンソル組み込み関数とハードウェア制約も統一的に表現できる。

- 正しさを検証しながら、テンソル化プログラム最適化の豊富な探索空間を生成する変換プリミティブを構築する。

- テンソル化を認識する新しい自動スケジューラを設計・実装する。

TensorIR をエンドツーエンドのコンパイルフレームワークへ統合した結果、既存の機械学習コンパイル手法を最大 $7\times$ 上回り、高度に最適化されたプラットフォーム固有手法と競合する性能を自動的に実現できた。

## 2 アプローチ概観

<span id="figure-03"></span>

![キャプション参照](../../papers/tensorir/figure-03.png)

**図 3。** 提案手法の概要。block という主要な抽象によってテンソル化計算を分割・分離し、テンソル化演算を含むループ変換をさらに可能にする。

本節では、提案手法の主要な着想を説明し、論文全体を概観する。動機を示すため、まず [図 2](#figure-02) に示す、専門家がテンソル化プログラムを最適化する流れを見る。テンソル化計算プリミティブは通常、元のテンソル演算子計算の部分問題に対応する。そのため専門家は自然に*分割統治*を選ぶ。すなわち、元のプログラムをテンソル化計算の部分問題と、その計算を利用するループネストに分け、別々に最適化する。分割統治により、開発者は他の部分を気にせず一つの部分問題へ集中できる。さらに、複数のテンソル化計算実装を対象にできる。

既存の機械学習コンパイラは、主に二種類の手法を採用する（[図 3](#figure-03)）。Halide [Rag13]、TVM [Che18]、Tiramisu [Bag19]、AKG [Zha21k]、MLIR/Affine [Lat21]、AMOS [Zhe22d] はボトムアップ手法を採り、スカラー演算本体を囲むループネスト・イテレータで探索空間をモデル化した後、探索または多面体最適化によって最良のループネスト変換を見つける。HTA [Fra04]、Fireiron [Hag20]、Stripe [Zer19] はトップダウン手法を採り、ネストした多面体構造によって問題を部分問題へ段階的に分解する。手動のテンソル化プログラム最適化で分割統治が重要であることを踏まえると、同じ着想を機械学習コンパイラ設計へ持ち込めるか、という問いが自然に生じる。

本論文は肯定的な答えを示す。具体的には、ループネストへ *block* という新しい抽象を導入する。Block は、内部の問題空間と外部の問題を*分離*するために必要十分なシグネチャ情報を持つ。Block シグネチャをインターフェースとして、内側と外側の問題をそれぞれ独立に変換し続けられる。手動の分割統治と同様、block は一般にハードウェアバックエンドのテンソル化計算プリミティブを表すために使うが、分割統治が有効な場合には、より大きな対象部分問題の分離にも使える。重要なのは、TensorIR でテンソル計算が第一級の要素であることだ。Block を含むループネストは、反復空間の一般化された抽象とみなせる。TensorIR 抽象の詳細設計は [第 3 節](#section-3) で述べる。

テンソル化プログラム最適化を自動化するため、ハードウェアのテンソル計算プリミティブに導かれた問題分割方法の探索空間を構築し、プログラム変換を用いて部分問題の解法をさらに探索する。テンソル化プログラム向け自動スケジューリングアルゴリズムは [第 4 節](#section-4) で述べる。

本手法の分割統治は、従来のコンパイラ手法であるボトムアップとトップダウンの探索空間を包含し、HPC と機械学習エンジニアリングで典型的な最適化技法を、自動テンソル化を可能にする抽象へ一般化する。ライブラリとコンパイルパイプラインで一般的な判断を自動化することで、ベンダー固有ライブラリと競合する解を自動生成できる。実験結果は [第 5 節](#section-5) に示す。

### 3.1 Block

TensorIR の block は、多次元バッファの部分領域上で行うテンソル化計算を表す。[図 5](#figure-05) は行列乗算（matmul）計算の block 例である。Block 本体は、抽象的なテンソル化計算を表す block イテレータ変数 $v_y, v_x, v_k$ の集合でパラメータ化される。これらの変数値の異なる組合せでインスタンス化すると、block は異なる具体的な実行 block インスタンスへ対応する。イテレータ変数は、外側のループイテレータを含む式に束縛でき、それによって block インスタンスの実行順序が定まる。

**設計理由** Block の主な設計理由はテンソル化計算の分離である。Block 本体を調べずに、その外側のループネストを変換できるようにしたい。しかしスカラー計算と異なり、不透明なテンソル計算本体から変換に必要な依存情報を抽出できるとは限らない。そこで、変換に十分な依存情報を含む block シグネチャを導入する。変換については [第 3.2 節](#section-3-2) で述べる。さらにシグネチャは、変換中のイテレータ束縛が正しいかを独立に検証するためにも利用できる。詳しくは [第 3.3 節](#section-3-3) で述べる。

**Block イテレータ領域** Block イテレータを任意のループネストへ束縛して本体計算をインスタンス化すること自体は可能だが、その大半は同じ計算に対応しない。変換間で計算の一貫性を保つため、イテレータの領域情報と制約を block シグネチャに格納する。[図 5](#figure-05) の例では、$vx$、$vy$、$vk$ は領域 $[0, 16)$ のイテレータへ束縛されなければならない。また $vk$ はリダクション軸なので、リダクションがアトミックでない限り並列ループへ束縛できない。制約を満たすループの構築方法は複数あるため、領域制約を設けても外側のループ変換には大きな余地が残る。本手法の領域シグネチャは、イテレータの整数領域集合と関係を表現する一つの具体的な方法とみなせる。実装効率と推論の簡潔さからこの表現を選ぶが、同じ設計思想は整数集合・関係を表す他の形式的領域表現にも適用できる [Vas06]。

**アクセス領域と依存関係** 十分な依存情報を提供するため、block シグネチャは、多次元バッファに関する block のアクセス領域と読み書き依存を含む。[図 5](#figure-05) では、block は $A[vy*4: vy*4 + 4, vk*4: vk*4 + 4], B[vk*4: vk*4 + 4, vx*4: vx*4 + 4]$ を読み、領域 $C[vy*4: vy*4 + 4, vx*4: vx*4 + 4]$ へ書き込む。この依存情報を変換時に用いる。各 block の依存は、他の文（block）ではなく多次元バッファに対してのみ記す。この間接化により、テンソル化プログラム最適化に不可欠なデータレイアウト変換や再計算など、より幅広い変換が可能になる。

**リダクション Block と初期化** リダクション計算には通常、初期化と更新の二段階がある。これを二つの block へ自然に対応付けられる一方、タイリングや計算位置など、両段階のスケジューリング判断を一緒に行うことが役立つ場合が多い。そこで、リダクションを行う block に任意の初期化文を導入する。初期化文はリダクションの最初の反復で実行される。このリダクション block 表現は主に変換時に有用である。二つの block による表現と、初期化 block による表現の間を変換するプリミティブを用意し、低水準コード生成に最適な表現を選べるようにする。

### 3.2 スケジューリング変換

<span id="figure-08"></span>

![キャプション参照](../../papers/tensorir/figure-08.png)

**図 8。** ハードウェア組み込み関数を用いたテンソル化プログラムの自動最適化。入力ワークロードは $64\times64\times64$ 行列乗算の後に RELU 演算子を適用するもの、合成テンソル組み込み関数はドット積命令で実装される $4\times4\times4$ 行列乗算である。テンソル化候補生成では $64\times64\times64$ GEMM を $4\times4\times4$ のサブタイルへ分割し、部分計算を分離する。次にテンソル化プログラム・スケッチ生成で計算をスケジュールし、生成されたデータ移動（AutoCopy）block を挿入する。これらは独立にスケジュールされる。最後に進化的探索でスケッチ内のランダムな判断を埋め、検証機構によって不正なプログラムを除外する。

与えられた入力プログラムに対し、同等の意味を持つ豊かなプログラム探索空間を生成する必要がある。TensorIR プログラムを意味的に等価な最適化済みプログラムへ変換するプリミティブを導入する。既存のテンソルプログラム最適化 [Rag13, Che18, Bag19] の慣例に従い、この手続きをスケジューリングと呼ぶ。

Block が、子 block を葉とするループネストだけを含む場合、その block はスケジュール可能である。子 block のシグネチャと依存情報を解析することで、スケジュール可能な block 内のループネストと子 block の計算位置を変換できる。スケジュール可能な block は、スケジュール不可能な子 block、たとえば不透明な Tensor Core 計算を含められる。不透明な block も、スケジュール可能な子 block を含められる。Block の分離により、同じ不透明 block を維持しながら、スケジュール可能な部分の探索空間を独立かつ効率的に探索できる。本小節の残りでは、スケジュールプリミティブを説明する。

**ループ変換** ループタイリング（split、reorder）や計算位置の変更などのループ変換は、メモリ局所性を改善してプログラムを最適化する重要な手段である。これらのループ変換プリミティブも提供する。例は [図 6](#figure-06) に示す。各葉のスカラー計算文から直接依存を抽出する既存のテンソルコンパイラと異なり、本手法は block シグネチャだけを調べて依存を計算する。ループ変換のほか、ループを GPU スレッドへ束縛するプリミティブや、ベクトル化・アンローリングなどの注釈ヒントも支援する。Block の分離によって、インライン化や協調フェッチなど、block をまたぐ重要な協調最適化が妨げられることはない。本手法のループ変換は従来研究が提供したものを包含するため、TensorIR は [第 2 節](#section-2) で述べた探索空間を再現できる。

**Blockization** ループ変換プリミティブは block の全体的な階層を維持する。[第 2 節](#section-2) で触れたように、部分領域の計算を新しい子 block へ分離して問題を分割すると有効な場合がある。この変換を *blockization* と呼ぶ（[図 7](#figure-07)）。新しい子 block はテンソル化計算に対応するため、blockization 後のプログラムはスカラーを基礎とするものではなくなる。Blockization により、テンソル化候補になり得る部分を分離できる。このほか、block 階層を変更できるプリミティブも導入する。たとえばキャッシュプリミティブは、入力データを共有メモリへキャッシュする子 block を追加する。また、単一のリダクション block と、それに対応する初期化・更新 block の間を双方向に変換できる。

**スケジューリングと TensorIR の分離** 従来のテンソルコンパイラ [Rag13, Che18] の多くは、宣言的スケジューリング言語によってスケジュール木を構築する。これらへ新しいスケジューリングプリミティブを加えるには、スケジュール木のデータ構造と、対応する低水準化規則の両方を変更する必要がある。本手法では、各スケジューリングプリミティブを、一つの TensorIR プログラムから別のプログラムへの独立した変換として実装する。この設計は拡張しやすく、複数の開発者が安定した TensorIR 抽象を基に新しいプリミティブを並行して開発できる。さらに、任意の変換段階でプログラムを出力してデバッグしたり、自動書き換えとスケジュール変換を組み合わせたりできる。

<span id="section-3-3"></span>

### 3.3 検証

Block とバッファの読み書き関係は元の計算を完全に捉え、ループネストとスレッド割当ての正しさを検証するために使われる。

**ループネスト検証** ループネストが与えるイテレータ束縛が、領域の大きさとイテレータ独立性を含むイテレータ領域制約に適合するかを検査する。たとえば、二つのデータ並列 block イテレータを $v_1 = i; v_2 = i * 2$ と束縛すると、$v_1$ と $v_2$ が独立でないためプログラムは不正となる。一方、$v_1 = i / 4; v_2 = i \% 4$ は正しい束縛になり得る。ループイテレータから block イテレータ変数への準アフィン写像を見つけるパターンマッチャを構築し、そのパターンで束縛の独立性と領域を検証する。イテレータ領域に加え、生産者 block が書き込むバッファ領域が下流の消費者の読取り領域を常に覆うよう、生産者・消費者関係を検査することも重要である。

**スレッド検証** GPU やスレッドを支援する他のアクセラレータ向けにプログラムを構築する場合、スレッド階層とメモリ階層について追加の検証が必要である。次の三種類を検証する。

- **スレッド束縛**：同じスレッドへ束縛された異なるイテレータが整合し、バックエンドの起動制約を満たすことを確認する。

- **協調メモリアクセス**：複数スレッドが協調して共有メモリに格納するバッファを生成する block について、その block が同じグループ内の全スレッドからの下流要求を覆うことを確認する。同時に、この block へ入力を供給する上流 block は、同じグループ内の全スレッドによる読取り要求を覆わなければならない。

- **実行スコープ**：テンソル組み込み関数が正しい実行スコープで動作することを検証する。たとえば Tensor Core は warp レベルで動作する必要がある。

**スケジュールプリミティブの正しさ** 変換の正しさを保証するため、各スケジュールプリミティブへ検査を追加する。プリミティブがループネストだけを変更する場合、block の反復領域と依存が変わらないため、検証手続きを使って正しさを確認できる。Blockization など block を変更するプリミティブについては、プリミティブ固有の必要条件を求める。

ループネスト検証とスレッド検証は不正な TensorIR プログラムを除外するために使い、スケジュールプリミティブ検査は変換前後の TensorIR プログラムが等価であることを保証するために使う。TensorIR プログラムを手動で誤って作成・インポート・スケジュールした場合、ユーザーは警告またはエラーを受け取る。[第 4 節](#section-4) で述べるように、コンパイラでプログラムを自動生成する場合、検証は探索空間を調べる際の偽陽性を除外できる。したがって、ユーザープログラムとコンパイル済みプログラムの両方が検証の恩恵を受ける。

### 3.4 プログラミング作業量

[図 4](#figure-04) に示すように、TensorIR の Python-AST 方言を提供し、開発者が Python 上で TensorIR プログラムを直接構築、ダンプ、検査、変更、変換できるようにした。ユーザーが計算と最適化をすべて手動指定すると、プログラミング作業量は大きくなる。本フレームワークでは TensorFlow/PyTorch からモデルをインポートし、高水準演算子から TensorIR プログラムを自動生成できる。さらに、自動スケジューリング（[第 4 節](#section-4)）により、特定のハードウェアプラットフォーム向けにタイリングやキャッシュなどの最適化を自動で提供する。カスタム演算子が必要な場合は Python 方言で TensorIR を記述でき、その場合もシステムが最適化変換を自動的に提供する。したがって、通常はプログラミング作業量を最小限に抑えられる。

## 4 テンソル化プログラムの自動スケジューリング

前節では TensorIR 抽象と一連の変換プリミティブを導入した。これらの改善を十分に活用するには、一連の変換を自動最適化し、計算をネイティブのテンソル組み込み関数へ対応付ける自動手法が必要である。本節では、この問題を解くテンソル化認識自動スケジューラを説明する。

[図 8](#figure-08) は提案手法の概要である。システムはユーザーからのワークロード記述と、ハードウェアプラットフォームのテンソル組み込み関数記述を入力とする。自動スケジューラは、まず計算パターンを調べてテンソル化候補を生成する。次に、テンソル化計算を使うプログラム・スケッチ候補を生成し、計算パターンに基づいてデータ移動を決める。テンソル化プログラム・スケッチから導かれた探索空間に対し、学習ベースのコストモデルに導かれた進化的探索を行う。全体の処理はテンソル化を中心とし、新しい block 抽象でテンソル化計算を分離する。以降の各小節で各段階の詳細を述べる。

<span id="section-4-1"></span>

### 4.1 テンソル組み込み関数の抽象

最適化でテンソル組み込み関数を利用するには、その意味とバックエンド実装をシステムへ与える方法が必要である。ハードウェアバックエンドのテンソル組み込み関数を記述するために、*同じ* TensorIR 抽象を用いる。各テンソル化命令について、二つの block から成る TensorIntrin 構成要素を導入する。一方の block は計算の*意味*を、もう一方はテンソル化計算の低水準*実装*を記述する。

[図 8](#figure-08) の例では、スカラー本体 $C[i, j] \mathrel{+}= A[i, k] * B[k, j]$ を持つ通常のループネストで計算の意味を表し、内部のドット積命令 $\texttt{accel.dot}$ で組み込み関数を実装する。TensorIntrin の多次元バッファ仕様には、データ型、ストレージスコープ、メモリレイアウト、連続性制約も含める。これらの制約は検証段階で使われる。

一般的なプラットフォームでは、テンソル組み込み関数を特殊なメモリスコープ、データレイアウト、および対応するロード・ストア命令と組み合わせて使うことが多い。たとえば NVIDIA GPU で `nvcuda::wmma::mma_sync` API によって密な計算を行う場合、入力オペランドの準備と出力結果の取得に、それぞれ `nvcuda::wmma::load_matrix_sync` と `nvcuda::wmma::store_matrix_sync` を適用する必要がある。ARM CPU では、*a64_gemm_u8_8* $\times$ *12* のようなマイクロカーネルが、オペランドをインターリーブされたレイアウトへ格納するよう要求する。開発者は、テンソル計算の各入出力オペランドに特殊なストレージスコープを指定し、こうした制約をシステムへ知らせられる。

<span id="section-4-2"></span>

### 4.2 テンソル化候補の生成

バックエンド対象と入力プログラムの組が与えられると、まずプログラム本体を利用可能な TensorIntrin と照合し、テンソル化候補を生成する。照合は段階的に行う。最初に添字を考慮せず式パターン $C[.] \mathrel{+}= A[.] \times B[.]$ を照合し、次に添字間の対応付け候補を提案して照合を絞り込む。[図 9](#figure-09) はこの照合過程を順に示す。この例では行列乗算組み込み関数をバックエンド記述とする。このテンソル組み込み関数の計算は次式で表せる。

$$
    C[x,y] \mathrel{+}= A[x,k] \times B[k,y]
$$

バッチ行列乗算のようなワークロードは容易に照合できる。$$C[b,i,j] \mathrel{+}= A[b,i,r] \times B[b,r,j],$$ と記述し、$x, y, k$ を $i, j, r$ へ対応付ければよい。しかし、より複雑な添字式パターンを持つ 2 次元畳み込み（Conv2D）では、

$$
\begin{aligned}
    C[n, h, w, co] \mathrel{+}= &A[n, h * s_h + r_h * d_h, w*s_w+r_w*d_w, r_c] \\ \times &B[r_c, r_h, r_w, co],
\end{aligned}
$$

$x, y, k$ と $n, h, w, c, r_h, r_w, r_c$ の対応は単純ではない。

このような一般的な場合、計算式を次の等価な形へ書き換える。

$$
\begin{aligned}
    C[n, h, w, co] \mathrel{+}= A_r[n, h, w, r_h, r_w, r_c] \times B[r_c, r_h, r_w, co],\\
    A_r[n, h, w, r_h, r_w, r_c] = A[n, h * s_h + r_h * d_h, w*s_w+r_w*d_w, r_c].
\end{aligned}
$$

この変換を *ReIndex* と呼ぶ。バッファアクセス添字に現れる中間イテレータを使って、バッファアクセス式を書き換える。新しい計算をテンソル組み込み関数へ照合するため、各イテレータが現れるバッファアクセスを調べる。たとえば、$n, h, w$ と $x$ は $A(Ar), C$ の添字、$co$ と $y$ は $B, C$ の添字、$r_h, r_w, r_c$ と $k$ は $A, C$ の添字に現れる。この出現パターンを調べることで、計算のイテレータをテンソル組み込み関数のイテレータへ対応付けられる。具体的には、$\operatorname{fuse}(n, h, y)$ を $x$、$co$ を $y$、$\operatorname{fuse}(r_h, r_w, r_c)$ を $k$ へ対応付ける。ここで $\operatorname{fuse}()$ は複数のイテレータを融合する演算で、次のように再帰的に定義できる。

$$
\begin{aligned}
    \operatorname{fuse}(i_1) &= i_1 \\
    \operatorname{fuse}(i_1, i_2, \dots, i_{r}) &= \operatorname{fuse}(i_1, i_2, \dots, i_{r-1}) * \operatorname{extent}(i_{r}) + i_{r},
\end{aligned}
$$

ここで $\operatorname{extent}$ はイテレータ $i_r$ の範囲である。すると計算を次の形へ変換できる。

$$
\begin{aligned}
    C_t[\operatorname{fuse}(n, h, w), co] \mathrel{+}= &A_t[\operatorname{fuse}(n, h, w), \operatorname{fuse}(r_h, r_w, r_c)] \\ \times &B_t[\operatorname{fuse}(r_h, r_w, r_c), co],
\end{aligned}
$$

ここで、

$$
\begin{aligned}
    C_t[\operatorname{fuse}(n, h, w), co] = &C[n, h, w, co], \\
    A_t[\operatorname{fuse}(n, h, w), \operatorname{fuse}(r_h, r_w, r_c)] = &A_r[n, h, w, r_h, r_w, r_c] \\
    B_t[\operatorname{fuse}(r_h, r_w, r_c), co] = &B[r_h, r_w, r_c, co].
\end{aligned}
$$

この対応付けを用いて block インスタンス空間と外側のループを再形成し、*ReIndex* バッファのレイアウトを変換する。レイアウト書換え block を挿入して $A, B, C$ をそれぞれ $A_t, B_t, C_t$ へ書き換え、$A_t, B_t, C_t$ で計算本体を書き換える。以上の処理後、計算本体はテンソル組み込み関数と互換になる。

**ループ再編成と早期 Blockize** 計算本体だけでなく、テンソル計算領域が TensorIntrin の記述と一致することも保証しなければならない。再編成後の block インスタンス空間の形状は、テンソル組み込み関数の部分問題サイズで割り切れない場合がある。前段階で得た各計算本体について、計算 block と入出力オペランドを、最も近い割り切れる形状まで必要に応じてパディングする。次にタイリングでテンソル組み込み関数のループネストと一致する内側ループを作り、さらに内側ループを blockize して対応するテンソル計算を分離する。この段階で生成した候補が必ずテンソル化に成功するわけではない。メモリレイアウトやスレッドなど、後続の変換に依存する制約もあるためである。こうした制約はテンソル化候補へ埋め込まれ、検証時に確認される。

**処理の形式的記述** ここまで、テンソル化候補生成を高水準に概観した。本小節の残りでは、この処理を形式的に記述する。組み込み関数のスカラー式を次のように形式化できるとする。

<span id="equation-02"></span>

$$
    O[\mathbf{v}_{0}] = f(O[\mathbf{v}_{0}], I_1[\mathbf{v}_1], I_2[\mathbf{v}_2], \dots, I_k[\mathbf{v}_k]).
$$

ここで $O$ は出力オペランド、$I_{[1: k]}$ は入力オペランド、$\mathbf{v}$ はこの計算をパラメータ化するイテレータ集合、$\mathbf{v}_{[0:k]}$ は $\mathbf{v}$ に属するイテレータの全リスト、$f$ は検出された式パターンである。これは一般的なドット積と行列乗算の組み込み関数を包含する。さらに、ワークロードのスカラー式を次のように形式化できるとする。

$$
\begin{aligned}
    \tilde{O}[g_{0}(\tilde{\mathbf{v}}_{0})] = f(\tilde{O}[g_{0}(\tilde{\mathbf{v}}_{0})], \tilde{I}_1[g_1(\tilde{\mathbf{v}}_1)], \dots, \tilde{I}_k[g_k(\tilde{\mathbf{v}}_k)]),
\end{aligned}
$$

$\tilde{O}$、$\tilde{I}_{[1: k]}$、$\tilde{\mathbf{v}}_{[0:k]}$ はそれぞれの対応物であり、$f$ は完全に同じである。$g_{[0:k]}$ はイテレータのリストを実際のバッファアクセス位置へ写す関数である。たとえば Conv2D では、$g_{A}(n, h, w, r_h, r_w, r_c)=(n, h * s_h + r_h * d_h, w*s_w+r_w*d_w, r_c).$ となる。

問題をより単純な標準形へ帰着させるため、*ReIndex* スケジュール変換を適用する。これはオペランドの中間キャッシュバッファを作り、イテレータに従ってレイアウトを変更する。形式的には、$\tilde{I}_1[g_1(\tilde{\mathbf{v}}_1)]$ に *ReIndex* を実行すると、計算の前に次の書換え block を作る。

$$
\begin{aligned}
    \hat{I}_{1}[\tilde{\mathbf{v}}_1] = \tilde{I}_1[g_1(\tilde{\mathbf{v}}_1)].
\end{aligned}
$$

すべてのオペランドへ *ReIndex* を適用すると、ワークロードのスカラー式は次の形へ帰着する。

<span id="equation-03"></span>

$$
    \hat{O}[\tilde{\mathbf{v}}_{0}] = f(\hat{O}[\tilde{\mathbf{v}}_{0}], \hat{I}_1[\tilde{\mathbf{v}}_1], \dots, \hat{I}_k[\tilde{\mathbf{v}}_k]),
$$

このとき、[式 2](#equation-02) と [式 3](#equation-03) のバッファアクセス添字はイテレータへ直接対応する。

[式 2](#equation-02) と [式 3](#equation-03) を照合するため、$\mathbf{v}_0, \mathbf{v}_1, \mathbf{v}_2, \dots \mathbf{v}_k$ のそれぞれがイテレータ $v \in \mathbf{v}$ を含むかを調べ、その特性ベクトル $\chi(v) \in \{0,1\}^{k+1}$ を定義する。形式的には、

$$
\begin{aligned}
    \chi(v)_i &= [v \in \mathbf{v}_i] \quad i \in [0, k],
\end{aligned}
$$

ここで $[]$ は Iverson 括弧であり、条件が真なら 1、偽なら 0 を返す（[図 9](#figure-09)）。$\forall v \in \mathbf{v}, \exists \tilde{v} \in \tilde{\mathbf{v}}, \chi(v) = \tilde{\chi}(\tilde{v})$ であれば、対応付けを提案できる。現実装では、$\mathbf{v}$ のイテレータはすべて異なる特性ベクトルを持つと安全に仮定できる。そこで各 $v \in \mathbf{v}$ について、$\chi(v) = \tilde{\chi}(\tilde{v})$ を満たすすべての $\tilde{v}$ を融合し、その融合イテレータを $v$ へ対応付ける。

$\mathbf{v}_{[0:k]}$ または $\tilde{\mathbf{v}}_{[0:k]}$ の各リスト内におけるイテレータ順は、特性関数 $\chi$ または $\tilde{\chi}$ の値へ影響しない。しかし $\chi(v) = \tilde{\chi}(\tilde{v})$ を満たすすべての $\tilde{v}$ を融合するとき、その順序はテンソル組み込み関数と互換になるようオペランドをメモリ上で再編成する方法へ影響する。現実装は全ワークロードへ既定順序を使うが、将来は異なる融合順序へ一般化できる。

<span id="section-4-3"></span>

### 4.3 テンソル化プログラム・スケッチ生成

テンソル化候補の集合に対し、テンソル化を含む大規模なプログラム探索空間を構築する必要がある。既存の階層的探索空間生成 [Zhe20] をテンソル計算へ一般化する。テンソル化計算を含むプログラム・スケッチを生成して探索空間を構築し、生成されたスケッチが導く選択肢を列挙する。[図 8](#figure-08) 右側に示すように、プログラム・スケッチはプログラム構造の一部を固定しつつ、ループタイリングサイズや計算キャッシュ判断など、残るパラメータ選択の余地を残す。事前定義したスケッチ生成規則を反復適用してスケッチを生成する。重要なのは、block シグネチャを調べ、解析時にアクセス領域情報を使うことで、テンソル化計算へ適用できるスケッチ生成規則を構築することである。

**データ移動を第一級の要素にする** 既存のテンソルプログラム用自動スケジューラは計算スケジュールへ設計の重点を置き、異なるメモリスコープ間のデータ移動を二次的に扱う。しかしテンソル組み込み関数が計算スループットを大幅に高めると、データ移動がテンソルプログラムのボトルネックになる。さらにデータ移動の判断は、タイリング、スレッド束縛、実行スコープ、生産者・消費者データフローの粒度など、計算スケジュールの判断へ依存することが多い。これらの知見から、自動スケジューラでデータ移動を第一級の要素とし、計算スケジュールから切り離す。具体的には、スケッチ生成規則がデータ移動を行うと決めた場所へ *AutoCopy* block を挿入する（[図 8](#figure-08)）。コピー block はメモリスケジュールの詳細を隠し、block シグネチャのレベルで必要なバッファアクセス情報だけを公開する。コピー block の分離により、スケッチ生成はデータ移動の方法を考慮せず、計算スケジュールを独立に決められる。*AutoCopy* block 本体は、バッファ位置の対応付け、スレッド、ストレージスコープ要件を含むデータ移動タスクの詳細を記述する。データ移動スケジューラはこの情報を入力とし、中間キャッシュ段階の挿入、データ移動用テンソル組み込み関数の利用、ベクトル化、協調フェッチ、バンク競合を避けるストライド・パディングなど、メモリ関連のスケジュール変換を実行する。

<span id="section-4-4"></span>

### 4.4 進化的探索

テンソル化プログラム・スケッチ生成後、数十億の派生プログラム候補が得られる。進化的探索でこの空間を調べ、最適化済みテンソル化プログラムを見つける。探索は、与えられたプログラム・スケッチに対する選択肢のランダム初期化から始める。続いて現在のプログラム集合へ変異を施し、変異候補から有望なプログラムを選んで、対象ハードウェアバックエンド上でベンチマークする。評価段階のデータを収集し、学習済みコストモデルを更新する。

**テンソル化計算のコストモデル** プログラムから抽出した特徴量を使う、ブースティング木アンサンブル [Che16b] ベースのコストモデルを構築する。特徴ベクトルにはメモリアクセスパターン、再利用、ループ注釈に関する情報が含まれる。特に、block シグネチャから分離して特徴を抽出するとともに、Tensor Core の使用を示す場合など、block 本体からも特徴を抽出する。このコストモデルは、従来手法をテンソル化プログラムへ一般化したものとみなせる。テンソル化プログラム向けの効果的なコストモデルは、有望な将来研究分野だと考える。

**検証** 探索中にプログラムをランダムに変異させると、テンソル組み込み関数の制約を満たさなかったり、ループネスト候補が不正だったりして、無効なプログラムが生じ得る。偽陽性の可能性があるため、探索には検証段階が必要である。[第 3.3 節](#section-3-3) の手法を進化的探索中の候補へ適用し、不正なプログラムを識別して排除する。検証段階は進化的探索アルゴリズムの負担を減らし、探索中の少数の偽陽性生成を許容できるようにする。

## 5 評価

TensorIR を Apache TVM [Che18] 上へ実装した。本論文で述べる知見は、他の機械学習コンパイルフレームワークにも役立つ。本節の評価では次の問いに答える。

- TensorIR は一般的な機械学習演算子群を最適化できるか（[第 5.1 節](#section-5-1)）。

- TensorIR はエンドツーエンドのネットワーク実行性能を高められるか（[第 5.2 節](#section-5-2)）。

- TensorIR は異なるハードウェアプラットフォーム上のテンソル組み込み関数を支援できるか（[第 5.3 節](#section-5-3)）。

これらの観点から TensorIR を評価するため、GPU と CPU プラットフォーム上で既存の機械学習コンパイル手法と比較する。具体的な設定は対応する各小節で述べる。

さらに、すべての評価を通じて、TensorIR はベンダー固有ライブラリ、およびそれらを利用するフレームワークと比べてどうか、という問いにも関心がある。これらのライブラリの多くは、専任のエンジニアチームによって高度に最適化されている。すべての設定で、TensorIR は外部ライブラリを呼び出さずにエンドツーエンドの自動最適化を行う。

## 6 関連研究

深層学習フレームワーク [Aba16, Pas19, Che15] は、cuDNN [Che14]、MKL-DNN [Int17]、TensorRT [Ten17a]、ArmComputeLibrary [Arm17] など、ベンダー最適化ライブラリを呼び出して深層ニューラルネットワークを最適化する。ライブラリには開発コストがあり、特定のハードウェアに固有である。TensorIR はライブラリ開発を補完し、ベンダーライブラリと同等の性能を自動的に提供することで、支援範囲を広げ、開発コストを下げる。これらのフレームワークは TensorIR を利用して、さまざまなハードウェアバックエンド向けに最適化済みテンソル化プログラムを生成できる。

行列乗算やドット積のように計算負荷の高い線形代数演算子は、科学計算で重要であるため、HPC コミュニティでは長年にわたる最適化対象である。CUTLASS [Ker22] はその一例である。分割統治は HPC と機械学習エンジニアリングで典型的な最適化手法である。TensorIR はこれらの考えを取り入れ、自動テンソル化を可能にする抽象へ一般化する。

機械学習コンパイラとテンソルコンパイラは、テンソルプログラムに異なる抽象を導入している。Halide [Rag13] と TVM [Che18] は、スカラー本体を持つループネストの最適化プリミティブを記述できるスケジューリング言語を用いる。Tensor Comprehensions [Vas18]、Tiramisu [Bag19]、MLIR/Affine [Lat21] は多面体モデル [Vas06] でループネスト依存を解析する。これらはスカラー計算を持つループネストをボトムアップで最適化する。Fireiron [Hag20] と Stripe [Zer19] は、ネストした多面体構造でテンソルプログラムをトップダウンにモデル化する。TensorIR は両方の手法の知見を組み合わせ、表現をテンソル化プログラムへ一般化する。IREE [Ire19] は、プラットフォーム固有の最適化パイプラインを利用するエンドツーエンド・コンパイルフロー向けコンパイラチェーンである。TensorIR はテンソル化処理の自動化に焦点を置き、人手を介さず複数のプラットフォーム向け最適化コードを生成する。TACO [Kjo17, Cho20, Sen20a] は疎テンソル代数用コンパイラである。Cortex [Feg21] はテンソルコンパイルを再帰計算へ一般化した。本研究はこれらと直交する。将来、TensorIR 抽象とこれらの研究の知見を組み合わせ、さらに幅広い計算を支援できると考える。

自動化は機械学習コンパイルとテンソルプログラム最適化の重要な課題である。AutoTVM [Che18a] は、学習済みコストモデルとテンプレート誘導探索でテンソルプログラムを最適化する学習ベース手法を導入した。Triton [Til19] は、効果的なプログラム最適化のためにタイルベースのテンプレート表現を導入する。FlexTensor [Zhe20a] はテンプレートを自動生成する。Halide はモンテカルロ木探索を使う自動スケジューラを構築する [Ada19]。Ansor [Zhe20] は階層的探索空間によって自動スケジューリングを改善する。本研究の自動スケジューリングアルゴリズムはこれらの手法から学び、ドメイン固有ハードウェア高速化に最適なテンソル化計算へ一般化する。

自動ベクトル化 [Ros07, Kon13] はコンパイラ研究における長年の課題である。テンソル化は、現代のアクセラレータでテンソル組み込み関数 [Nvi17, Int19, Arm17a, Mor18a] を利用するため、ベクトル化問題を一般化したものとみなせる。この課題を扱う既存研究 [Bha20a, Zha21k, Wen21, Zhe22d] もある。AKG [Zha21k] は多面体手法でテンソル化探索空間を調べ、UNIT [Wen21] は汎用的なテンソル化フローを導入し、AMOS [Zhe22d] はテンソル式を通じてテンソル化組み込み関数への自動対応付けを可能にする。本手法は、テンソル化計算の新しい抽象を提案し、テンソル化を他の最適化と同時に行うことで、これらの従来手法を一般化する。TensorIR は、テンソル化を認識する自動スケジューリング手法をさらに発展させる基盤となる。

## 7 結論

自動テンソル化プログラム最適化の抽象 TensorIR を提案した。テンソル化計算を分離し、プログラム最適化のための効果的な変換プリミティブを提供する block という主要な抽象を設計した。テンソル化と他の最適化を同時に行い、高性能なプログラムを生成する自動スケジューリングアルゴリズムを構築した。本研究がテンソル化プログラム最適化のさらなる研究を促し、ハードウェアとソフトウェアの専用化へ新たな機会をもたらすことを期待する。
