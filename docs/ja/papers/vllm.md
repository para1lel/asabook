## 要約

大規模言語モデル（LLM）を高いスループットでサービングするには、十分な数のリクエストを一度にバッチ処理する必要がある。しかし、リクエストごとのキー・バリューキャッシュ（KV キャッシュ）は巨大で、しかも動的に増減するため、既存システムでは扱いが難しい。管理が非効率だと、断片化や重複コピーによってメモリが大幅に浪費され、バッチサイズが制限される。この問題に対し、オペレーティングシステムの古典的な仮想メモリとページング技術に着想を得たアテンションアルゴリズム PagedAttention を提案する。さらに、その上に LLM サービングシステム vLLM を構築する。vLLM は（1）KV キャッシュメモリの浪費をほぼゼロにし、（2）リクエスト内およびリクエスト間で KV キャッシュを柔軟に共有してメモリ使用量をさらに減らす。評価の結果、vLLM は FasterTransformer や Orca などの最先端システムと同程度のレイテンシを保ちながら、一般的な LLM のスループットを 2-4$\times$ 向上させた。この改善は、シーケンスが長いほど、モデルが大きいほど、またデコーディングアルゴリズムが複雑なほど顕著である。vLLM のソースコードは [https://github.com/vllm-project/vllm](https://github.com/vllm-project/vllm) で公開されている。

## 1\. はじめに

GPT [Ope23b, Bro20c] や PaLM [Cho22a] などの大規模言語モデル（*LLM*）の登場により、プログラミングアシスタント [Git21a, Che21] や汎用チャットボット [Sch22, Bar23] といった新しいアプリケーションが実現し、仕事や日常生活に大きな影響を与え始めている。多くのクラウド企業 [Ope20, Ser23a] が、これらのアプリケーションをホスト型サービスとして提供しようと競っている。しかし、こうしたアプリケーションの実行には多くの GPU などのハードウェアアクセラレータが必要であり、コストが非常に高い。最近の推定では、LLM リクエストの処理コストは従来のキーワード検索 [Reu23a] の 10$\times$ に達する可能性がある。この高いコストを踏まえると、*LLM サービング*システムのスループットを高め、リクエスト当たりのコストを下げることがますます重要になる。

LLM の中核には、自己回帰型 Transformer モデル [Vas17] がある。このモデルは、入力（プロンプト）とそれまでに生成した出力トークン列に基づき、単語（トークン）を*一つずつ*生成する。各リクエストでは、モデルが終了トークンを出力するまで、この高コストな処理を繰り返す。この逐次生成によりワークロードは*メモリバウンド*となり、GPU の計算能力を十分に活用できず、サービングスループットが制限される。

![キャプションを参照](../../papers/vllm/figure-01.png)

**図 1。** *左：* NVIDIA A100 で 13B パラメータの LLM をサービングする際のメモリ配置。パラメータ（灰色）はサービング中を通して GPU メモリに保持される。KV キャッシュ（赤）のメモリは、サービングリクエストごとに割り当て、解放される。少量のメモリ（黄色）は、アクティベーション用に一時的に使われる。*右：* vLLM は、既存システム [Fas21, Yu22a] で見られる KV キャッシュメモリの急増を抑え、サービングスループットを大幅に高める。

複数のリクエストをまとめてバッチ処理すれば、スループットを高められる。ただし、一つのバッチで多数のリクエストを処理するには、各リクエストのメモリ領域を効率よく管理しなければならない。例えば、[図 1](#figure-01)（左）は、40 GB のメモリを備えた NVIDIA A100 GPU で 13B パラメータの LLM を実行したときのメモリ配分を示す。約 65% はモデルの重みに割り当てられ、サービング中は変化しない。約 30% はリクエストの動的状態の保存に使われる。Transformer では、この状態はアテンション機構のキーとバリューのテンソルからなり、一般に *KV キャッシュ* [Pop22a] と呼ばれる。KV キャッシュは先行トークンのコンテキストを表し、新しい出力トークンを順に生成するために使われる。残りのわずかなメモリは、LLM の評価時に作られる一時テンソルであるアクティベーションなどに使われる。モデルの重みは一定で、アクティベーションが占める GPU メモリもわずかなため、最大バッチサイズは KV キャッシュの管理方法に大きく左右される。管理が非効率だと、[図 1](#figure-01)（右）に示すように、KV キャッシュがバッチサイズを大幅に制限し、LLM のスループットも低下する。

本稿では、既存の LLM サービングシステム [Yu22a, Fas21] が KV キャッシュを効率よく管理できていないことを指摘する。主な理由は、リクエストの KV キャッシュを連続したメモリ領域に格納していることにある。多くのディープラーニングフレームワーク [Pas19, Ols17] が、テンソルを連続メモリに置くことを要求するためである。しかし、従来のディープラーニングワークロードのテンソルとは異なり、KV キャッシュはモデルが新しいトークンを生成するにつれて動的に増減し、その存続期間も長さも事前には分からない。この性質のため、既存システムの方式は次の二点で著しく非効率になる。

<span id="figure-02"></span>

![キャプションを参照](../../papers/vllm/figure-02.png)

**図 2。** §[6.2](#S6.SS2) の実験における、各 LLM サービングシステムの平均メモリ浪費率。

第一に、既存システム [Yu22a, Fas21] では、内部断片化と外部断片化が発生する。リクエストの KV キャッシュを連続領域に格納するため、リクエストの最大長（例えば 2048 トークン）に相当する連続メモリを*事前割り当て*する。実際のリクエスト長は最大長よりはるかに短いことがあり（例えば [図 11](#figure-11)）、深刻な内部断片化につながる。実際の長さが事前に分かっていても、事前割り当ては非効率である。リクエストの存続中は領域全体が予約されるため、他の短いリクエストは、その時点で使われていない部分も利用できない。リクエストごとに事前割り当てサイズが異なるため、外部断片化も大きくなり得る。[図 2](#figure-02) のプロファイリング結果によれば、既存システムで実際のトークン状態の格納に使われる KV キャッシュメモリは 20.4%-38.2% にすぎない。

第二に、既存システムはメモリ共有の機会を活用できない。LLM サービスでは、並列サンプリングやビームサーチなど、一つのリクエストから複数の出力を生成する高度なデコーディングアルゴリズムがよく使われる。この場合、リクエストを構成する複数のシーケンスは、KV キャッシュの一部を共有できる。しかし、既存システムでは各シーケンスの KV キャッシュを別々の連続領域に格納するため、共有できない。

これらの制約を解消するため、*PagedAttention* を提案する。これは、オペレーティングシステム（OS）がメモリの断片化と共有に用いる*ページング付き仮想メモリ*に着想を得たアテンションアルゴリズムである。PagedAttention はリクエストの KV キャッシュをブロックに分割し、各ブロックに一定数のトークンのアテンションキーとバリューを格納する。KV キャッシュのブロックは、連続した領域に置く必要がない。このため、OS の仮想メモリと同じように KV キャッシュを柔軟に管理できる。ブロックをページ、トークンをバイト、リクエストをプロセスとみなせばよい。この設計は、比較的小さなブロックを必要に応じて割り当てることで内部断片化を抑える。すべてのブロックが同じ大きさなので、外部断片化もなくなる。さらに、同じリクエストの異なるシーケンス間だけでなく、異なるリクエスト間でもブロック単位でメモリを共有できる。

本研究では、PagedAttention を基盤として、KV キャッシュメモリの浪費をほぼゼロに抑える高スループット分散 LLM サービングエンジン *vLLM* を構築する。vLLM は、PagedAttention と協調して設計されたブロック単位のメモリ管理とプリエンプティブなリクエストスケジューリングを用いる。GPT [Bro20c]、OPT [Zha22]、LLaMA [Tou23] など、単一 GPU のメモリ容量を超えるものも含め、さまざまな規模の一般的な LLM をサポートする。各種モデルとワークロードで評価した結果、モデルの精度をまったく損なわずに、最先端システム [Yu22a, Fas21] と比べて LLM サービングスループットを 2-4$\times$ 向上させた。シーケンスが長いほど、モデルが大きいほど、またデコーディングアルゴリズムが複雑なほど、改善は大きい（§[4.3](#S4.SS3)）。本稿の貢献は次のとおりである。

- LLM サービングにおけるメモリ割り当ての課題を明らかにし、サービング性能への影響を定量化する。
- OS の仮想メモリとページングに着想を得た、非連続なページメモリ上の KV キャッシュを扱うアテンションアルゴリズム PagedAttention を提案する。
- PagedAttention を基盤とする分散 LLM サービングエンジン vLLM を設計、実装する。
- さまざまな条件で vLLM を評価し、FasterTransformer [Fas21] や Orca [Yu22a] など従来の最先端手法を大幅に上回ることを示す。

## 2\. 背景

本節では、一般的な LLM の生成とサービングの手順、および LLM サービングで使われる反復単位のスケジューリングについて説明する。

### 2.1. トランスフォーマーベースの大規模言語モデル

言語モデリングの目的は、トークン列 $(x_{1},\ldots,x_{n})$ の確率をモデル化することである。言語には自然な順序があるため、列全体の同時確率を条件付き確率の積、すなわち*自己回帰分解* [Ben00] として因数分解するのが一般的である。

<span id="S2.E1"></span>

$$
P(x)=P(x_{1})\cdot P(x_{2}\mid x_{1})\cdots P(x_{n}\mid x_{1},\ldots,x_{n-1}).
$$

Transformer [Vas17] は、上記の確率を大規模にモデル化する際の事実上の標準アーキテクチャとなっている。Transformer ベースの言語モデルで最も重要な構成要素は、*自己注意*層である。入力隠れ状態列 $(x_{1},\ldots,x_{n})\in\mathbb{R}^{n\times d}$ に対し、自己注意層はまず各位置 $i$ に線形変換を適用し、クエリ、キー、バリューの各ベクトルを得る。

<span id="S2.E2"></span>

$$
q_{i}=W_{q}x_{i},\ k_{i}=W_{k}x_{i},\ v_{i}=W_{v}x_{i}.
$$

次に、自己注意層は、ある位置のクエリベクトルとそれ以前の全キーベクトルとの積から注意スコア $a_{ij}$ を計算し、バリューベクトルの加重平均として出力 $o_{i}$ を求める。

<span id="S2.E3"></span>

$$
a_{ij}=\frac{\exp(q_{i}^{\top}k_{j}/\sqrt{d})}{\sum_{t=1}^{i}\exp(q_{i}^{\top}k_{t}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{i}a_{ij}v_{j}.
$$

[式 3](#S2.E3) の計算を除き、埋め込み層、フィードフォワード層、層正規化 [Ba16]、残差接続 [He16]、出力ロジット計算、[式 2](#S2.E2) のクエリ、キー、バリュー変換を含む Transformer の他のすべての構成要素は、$y_{i}=f(x_{i})$ の形で位置ごとに独立して適用される。

### 2.2. LLM サービスと自己回帰的生成

学習後の LLM は、Completion API [Ope20] やチャットボット [Sch22, Bar23] などの条件付き生成サービスとして配備されることが多い。LLM サービスへのリクエストは*入力プロンプト*のトークン列 $(x_{1},\ldots,x_{n}),$ を与え、サービスは[式 1](#S2.E1) に従って出力トークン列 $(x_{n+1},\ldots,x_{n+T})$ を生成する。プロンプトと出力を連結した列を*シーケンス*と呼ぶ。

[式 1](#S2.E1) の分解により、LLM は新しいトークンを一つずつしかサンプリング、生成できない。各トークンの生成は、そのシーケンス内のすべての*先行トークン*、具体的にはそれらのキーとバリューベクトルに依存する。この逐次生成では、将来のトークンを生成するために既存トークンのキーとバリューベクトルをキャッシュすることが多く、これを *KV キャッシュ*と呼ぶ。あるトークンの KV キャッシュは、その前にあるすべてのトークンに依存する。したがって、同じトークンでもシーケンス内の位置が異なれば KV キャッシュも異なる。

リクエストのプロンプトが与えられると、LLM サービスの生成計算は二つのフェーズに分けられる。

**プロンプトフェーズ**は、ユーザープロンプト全体 $(x_{1},\ldots,x_{n})$ を入力とし、最初の新しいトークンの確率 $P(x_{n+1}\mid x_{1},\ldots,x_{n})$ を計算する。この過程では、キーベクトル $k_{1},\ldots,k_{n}$ とバリューベクトル $v_{1},\ldots,v_{n}$ も生成される。プロンプトトークン $x_{1},\ldots,x_{n}$ はすべて既知なので、このフェーズの計算は行列-行列積で並列化でき、GPU が備える並列性を効率よく利用できる。

**自己回帰生成フェーズ**は、残りの新しいトークンを順に生成する。反復 $t$ では、モデルは一つのトークン $x_{n+t}$ を入力とし、キーベクトル $k_{1},\ldots,k_{n+t}$ とバリューベクトル $v_{1},\ldots,v_{n+t}$ を用いて確率 $P(x_{n+t+1}\mid x_{1},\ldots,x_{n+t})$ を計算する。位置 $1$ から $n+t-1$ のキーとバリューは以前の反復でキャッシュ済みであり、この反復では新しい $k_{n+t}$ と $v_{n+t}$ だけを計算する。シーケンスが最大長（ユーザー指定または LLM の上限）に達するか、シーケンス終端（*&lt;eos&gt;*）トークンが出力されると、このフェーズは完了する。反復間にはデータ依存があるため計算を並列化できず、効率の低い行列-ベクトル積がよく使われる。その結果、GPU の計算能力を十分に利用できず、処理はメモリ制約となり、単一リクエストのレイテンシの大半を占める。

### 2.3. LLM のバッチ処理技術

複数のリクエストをバッチ処理すれば、LLM サービング時の計算資源利用率を高められる。各リクエストは同じモデルの重みを共有するため、重みの転送コストはバッチ内のリクエストに分散される。バッチサイズが十分に大きければ、このコストは計算コストに比べて無視できるほど小さくなる。しかし、LLM サービスのリクエストをバッチ処理するのは、二つの理由から容易ではない。第一に、リクエストの到着時刻は異なる。単純なバッチ戦略では、先着したリクエストが後続のリクエストを待つか、先着リクエストが完了するまで新着リクエストを待たせるため、キューイング遅延が大きくなる。第二に、リクエストごとに入出力長が大きく異なることがある（[図 11](#figure-11)）。単純な方法では、リクエスト間で入出力長を揃えるためにパディングが必要となり、GPU の計算資源とメモリを浪費する。

この問題に対処するため、cellular batching [Gao18] や反復単位のスケジューリング [Yu22a] など、細粒度のバッチ処理機構が提案されている。リクエスト単位で動作する従来手法と異なり、これらは反復単位で動作する。各反復の終了後、完了したリクエストをバッチから除き、新しいリクエストを加える。したがって、新しいリクエストはバッチ全体の完了を待たず、一回の反復を待つだけで処理を開始できる。専用の GPU カーネルを使えば、入出力のパディングも不要になる。キューイング遅延とパディングの無駄を減らすことで、細粒度バッチ処理は LLM サービングのスループットを大きく高める。

## 3\. LLM サービングにおけるメモリの課題

細粒度のバッチ処理は計算の無駄を減らし、リクエストを柔軟にバッチ化できるようにするが、一つのバッチに含められるリクエスト数は依然として GPU のメモリ容量、特に KV キャッシュ用の領域に制約される。言い換えれば、サービングシステムのスループットは*メモリバウンド*である。この制約を克服するには、次のメモリ管理上の課題に対処しなければならない。

**大規模な KV キャッシュ。** KV キャッシュのサイズは、リクエスト数とともに急速に増える。例えば、13B パラメータの OPT モデル [Zha22] では、1 トークンの KV キャッシュに 800 KB、すなわち $2$（キーとバリューベクトル）$\times\ 5120$（隠れ状態サイズ）$\times\ 40$（層数）$\times\ 2$（FP16 当たりのバイト数）の領域が必要になる。OPT は最大 2048 トークンのシーケンスを生成できるため、1 リクエストの KV キャッシュには最大 1.6 GB が必要になる。現在の GPU のメモリ容量は数十 GB 程度である。利用可能なメモリをすべて KV キャッシュに割り当てても、収容できるのは数十リクエストにすぎない。非効率なメモリ管理は、[図 2](#figure-02) に示すように、バッチサイズをさらに小さくする。また、近年は GPU の計算速度がメモリ容量より速く伸びている [Gho21]。例えば NVIDIA A100 から H100 では、FLOPS は 2 倍以上になった一方、GPU メモリは最大 80 GB のままである。このため、メモリは今後さらに大きなボトルネックになると考えられる。

**複雑なデコーディングアルゴリズム。** LLM サービスは複数のデコーディングアルゴリズムを提供しており、どれを選ぶかによってメモリ管理の複雑さが変わる。例えば、プログラム候補の生成 [Git21a] でよく行われるように、一つの入力プロンプトから複数のランダムサンプルを要求する場合、プロンプト部分の KV キャッシュを共有してメモリ使用量を減らせる。この部分は、実験では KV キャッシュメモリ全体の 12% を占める（§[6.3](#S6.SS3)）。一方、自己回帰生成フェーズの KV キャッシュは、サンプルごとに結果が異なり、コンテキストと位置にも依存するため共有できない。共有できる KV キャッシュの量は、デコーディングアルゴリズムによって異なる。ビームサーチ [Sut14] のような高度なアルゴリズムでは、異なるビーム間でより多くの KV キャッシュを共有でき（最大 55% のメモリを節約、§[6.3](#S6.SS3)）、共有の形もデコーディングの進行に応じて変化する。

**長さが不明な入出力のスケジューリング。** LLM サービスへのリクエストは、入出力の長さが一定ではない。このため、メモリ管理システムは幅広いプロンプト長に対応する必要がある。デコーディング中に出力が伸びると KV キャッシュに必要なメモリも増え、新規リクエストや既存プロンプトの生成を続けるためのメモリが尽きることもある。システムは、一部のリクエストの KV キャッシュを削除したり GPU メモリからスワップアウトしたりするなど、スケジューリング上の判断を下さなければならない。

### 3.1. 既存システムにおけるメモリ管理

現在のディープラーニングフレームワークでは、多くの演算子 [Pas19, Ols17] がテンソルを連続メモリに格納することを要求する。そのため、従来の LLM サービングシステム [Yu22a, Fas21] も、各位置の KV キャッシュをリクエストごとに一つの連続テンソルとして格納する。LLM の出力長は予測できないため、実際の入力長や最終的な出力長にかかわらず、リクエストが取り得る最大シーケンス長に基づいてメモリ領域を静的に割り当てる。

[図 3](#figure-03) は、最大シーケンス長が 2048 のリクエスト A と、最大 512 のリクエスト B を示す。既存システムの事前割り当て方式でメモリを浪費する主な要因は三つある。将来のトークン用の*予約*スロット、想定される最大シーケンス長に合わせた過剰割り当てによる*内部断片化*、そしてバディアロケータなどのメモリアロケータが生む*外部断片化*である。外部断片化領域は生成トークンに使われることがなく、これはリクエストを処理する前から分かっている。内部断片化領域も使われないが、それが判明するのはリクエストのサンプリングが終わった後である。どちらも純粋なメモリ浪費である。予約領域は最終的には使われるが、リクエストの全期間にわたって確保しておくと、特に予約領域が大きい場合に、他のリクエストを処理できたはずの空間を占有する。[図 2](#figure-02) は実験中の平均メモリ浪費率を示しており、従来システムの実効メモリ利用率が 20.4% まで下がり得ることが分かる。

断片化の解決策としてコンパクション [Wan22d] が提案されているが、KV キャッシュは非常に大きいため、性能が重視される LLM サービングシステムでの実行は現実的ではない。コンパクションを行っても、各リクエストに事前割り当てした領域が、デコーディングアルゴリズム固有のメモリ共有を妨げる。

### 4.1. PagedAttention

§[3](#S3) のメモリ上の課題に対処するため、オペレーティングシステムにおける古典的な*ページング* [Kil62] に着想を得たアテンションアルゴリズム *PagedAttention* を導入する。従来のアテンションアルゴリズムと異なり、PagedAttention は連続するキーとバリューを非連続なメモリ空間に格納できる。具体的には、各シーケンスの KV キャッシュを *KV ブロック*に分割する。各ブロックには一定数のトークンのキーとバリューベクトルが含まれ [+kv-block-layout]、この数を *KV ブロックサイズ*（$B$）と呼ぶ。キーブロックを $K_{j}=(k_{(j-1)B+1},\ldots,k_{jB})$、バリューブロックを $V_{j}=(v_{(j-1)B+1},\ldots,v_{jB})$ とする。[式 3](#S2.E3) のアテンション計算は、次のブロック単位の計算に変換できる。

<span id="S4.E4"></span>

$$
A_{ij}=\frac{\exp(q_{i}^{\top}K_{j}/\sqrt{d})}{\sum_{t=1}^{\lceil i/B\rceil}\exp(q_{i}^{\top}K_{t}\mathbf{1}/\sqrt{d})},\ o_{i}=\sum_{j=1}^{\lceil i/B\rceil}V_{j}A_{ij}^{\top},
$$

ここで $A_{ij}=(a_{i,(j-1)B+1},\ldots,a_{i,jB})$ は、第 $j$ KV ブロックに対するアテンションスコアの行ベクトルである。

アテンション計算では、PagedAttention カーネルが各 KV ブロックを個別に特定して読み出す。[図 5](#figure-05) に例を示す。キーとバリューベクトルは三つのブロックに分散し、物理メモリ上では連続していない。各時点で、カーネルはクエリトークン（"*forth*"）のクエリベクトル $q_{i}$ とブロック内のキーベクトル $K_{j}$（例えばブロック 0 の "*Four score and seven*" のキーベクトル）を乗算してアテンションスコア $A_{ij}$ を計算する。その後、$A_{ij}$ とブロック内のバリューベクトル $V_{j}$ を乗算して、最終的なアテンション出力 $o_{i}$ を得る。

以上のように、PagedAttention は KV ブロックを非連続な物理メモリに格納できるため、vLLM はより柔軟なページ方式のメモリ管理を実現できる。

### 4.2. KV キャッシュマネージャ

vLLM のメモリマネージャの基本的な考え方は、オペレーティングシステムの*仮想メモリ* [Kil62] に似ている。OS はメモリを固定サイズの*ページ*に分割し、ユーザープログラムの論理ページを物理ページにマッピングする。連続する論理ページを非連続な物理ページに対応させられるため、ユーザープログラムはメモリが連続しているかのようにアクセスできる。物理メモリ領域をすべて事前に予約する必要もなく、OS は必要に応じて物理ページを動的に割り当てられる。vLLM は、この仮想メモリの考え方を LLM サービスの KV キャッシュ管理に用いる。PagedAttention により、KV キャッシュを仮想メモリのページに相当する固定サイズの KV ブロックとして構成する。

リクエストの KV キャッシュは一連の*論理 KV ブロック*として表され、新しいトークンとその KV キャッシュが生成されるたびに左から右へ埋められる。最後の KV ブロックの空き位置は、後続の生成用に予約される。GPU ワーカー上では、*ブロックエンジン*が連続した GPU DRAM 領域を確保し、*物理 KV ブロック*に分割する（スワップ用の CPU RAM でも同様に行う。§[4.5](#S4.SS5) 参照）。*KV ブロックマネージャ*は、リクエストごとの論理 KV ブロックと物理 KV ブロックの対応を示す*ブロックテーブル*も保持する。各エントリには、論理ブロックに対応する物理ブロックと、使用済み位置の数を記録する。論理 KV ブロックと物理 KV ブロックを分離することで、vLLM は全位置のメモリを事前に予約せず、KV キャッシュを動的に拡張できる。この仕組みにより、[図 2](#figure-02) に示す既存システムのメモリ浪費の大半を取り除ける。

### 4.3. PagedAttention と vLLM によるデコーディング

<span id="figure-06"></span>

![キャプションを参照](../../papers/vllm/figure-06.png)

**図 6。** vLLM におけるブロックテーブルの変換。

次に、[図 6](#figure-06) の例を用いて、vLLM が単一入力シーケンスのデコード中に PagedAttention を実行し、メモリを管理する過程を説明する。① OS の仮想メモリと同様に、vLLM は生成され得る最大シーケンス長のためのメモリを最初から予約しない。代わりに、プロンプト計算で生成される KV キャッシュを収めるのに必要な KV ブロックだけを予約する。この例ではプロンプトが 7 トークンなので、最初の二つの論理 KV ブロック（0 と 1）を二つの物理 KV ブロック（それぞれ 7 と 1）にマッピングする。プレフィルステップでは、従来の自己注意アルゴリズム（例えば [Dao22]）を用いてプロンプトと最初の出力トークンの KV キャッシュを生成する。そして最初の 4 トークンの KV キャッシュを論理ブロック 0 に、続く 3 トークンを論理ブロック 1 に格納する。残ったスロットは後続の自己回帰生成フェーズ用に予約する。② 最初の自己回帰デコードステップでは、物理ブロック 7 と 1 上で PagedAttention を使って新しいトークンを生成する。最後の論理ブロックにはスロットが一つ残っているため、新たな KV キャッシュをそこに格納し、ブロックテーブルの #filled レコードを更新する。③ 2 回目のデコードステップでは最後の論理ブロックが満杯なので、新たな KV キャッシュを新しい論理ブロックに格納する。そのために新しい物理ブロック（物理ブロック 3）を割り当て、この対応関係をブロックテーブルに記録する。

処理全体を見ると、各デコーディング反復で vLLM はまず、バッチに含める候補シーケンスを選び（詳細は §[4.5](#S4.SS5)）、新たに必要となる論理ブロックに物理ブロックを割り当てる。次に、その反復の全入力トークン、すなわちプロンプトフェーズのリクエストに含まれる全トークンと、生成フェーズのリクエストに含まれる最新トークンを一つのシーケンスに連結し、LLM に入力する。LLM の計算中は、PagedAttention カーネルで論理 KV ブロックとして保存された既存の KV キャッシュにアクセスし、新たに生成した KV キャッシュを物理 KV ブロックへ保存する。一つの KV ブロックに複数のトークンを格納すると（ブロックサイズ > 1）、PagedAttention カーネルはより多くの位置の KV キャッシュを並列処理でき、ハードウェア利用率が上がってレイテンシが短くなる。ただし、ブロックサイズを大きくするとメモリ断片化も増える。ブロックサイズの影響は §[7.2](#S7.SS2) で検討する。

このように vLLM は、トークンとその KV キャッシュが増えるにつれて、新しい物理ブロックを論理ブロックへ動的に割り当てる。すべてのブロックを左から右へ埋め、それ以前のブロックがすべて満杯になった場合にだけ新しい物理ブロックを割り当てるため、リクエスト当たりのメモリ浪費を一ブロック以内に抑えられる。その結果、[図 2](#figure-02) に示すように、メモリを効率よく利用できる。より多くのリクエストをメモリに収めてバッチ処理できるため、スループットも向上する。リクエストの生成が終わると、その KV ブロックは解放され、別のリクエストの KV キャッシュに再利用できる。[図 7](#figure-07) は、vLLM が二つのシーケンスのメモリを管理する例を示す。両シーケンスの論理ブロックは、GPU ワーカーのブロックエンジンが予約した領域内の異なる物理ブロックへマッピングされる。各シーケンスで隣り合う論理ブロックは、物理 GPU メモリ上で連続している必要がなく、両シーケンスが物理ブロック領域を効率よく利用できる。

### 4.4. 他のデコーディングシナリオへの応用

§[4.3](#S4.SS3) では、PagedAttention と vLLM が、一つのユーザープロンプトから一つの出力シーケンスを生成する貪欲デコーディングやサンプリングなど、基本的なデコーディングアルゴリズムを扱う方法を示した。多くの LLM アプリケーション [Git21a, Ope20] では、LLM サービスは、より複雑なアクセスパターンと多くのメモリ共有機会を持つ高度なデコーディングにも対応する必要がある。本節では、こうした方式にも vLLM を適用できることを示す。

**並列サンプリング。** LLM ベースのプログラミングアシスタント [Che21, Git21a] では、一つの入力プロンプトから複数の出力サンプルを生成し、ユーザーが候補の中から好みの出力を選べる。ここまでは、一つのリクエストが一つのシーケンスを生成すると暗黙に仮定してきた。以降は、一つのリクエストが複数のシーケンスを生成する、より一般的な場合を扱う。並列サンプリングでは、一つのリクエストに、同じ入力プロンプトを共有する複数のサンプルが含まれるため、プロンプトの KV キャッシュも共有できる。vLLM は PagedAttention とページ方式のメモリ管理により、この共有を容易に実現してメモリを節約する。

[図 8](#figure-08) は、二つの出力を並列デコードする例を示す。どちらも同じプロンプトを共有するため、プロンプトフェーズではプロンプト状態一つ分の領域だけを予約する。両シーケンスのプロンプト用論理ブロックは同じ物理ブロックへマッピングされる。具体的には、両シーケンスの論理ブロック 0 と 1 が、それぞれ物理ブロック 7 と 1 に対応する。一つの物理ブロックを複数の論理ブロックへマッピングできるため、各物理ブロックに*参照カウント*を設ける。この例では、物理ブロック 7 と 1 の参照カウントはいずれも 2 である。生成フェーズでは二つの出力が異なるトークンをサンプリングするため、それぞれに KV キャッシュ領域が必要になる。vLLM は、複数のシーケンスから変更され得る物理ブロックに対し、OS の仮想メモリ（例えばプロセスの fork 時）と同様の*コピーオンライト*機構をブロック単位で実装する。[図 8](#figure-08) でサンプル A1 が最後の論理ブロック（論理ブロック 1）へ書き込む際、対応する物理ブロック 1 の参照カウントが 1 より大きいことを検出する。そこで新しい物理ブロック 3 を割り当て、ブロックエンジンに物理ブロック 1 の内容をコピーさせ、参照カウントを 1 に減らす。続いてサンプル A2 が物理ブロック 1 へ書き込むときには参照カウントがすでに 1 なので、新しく生成した KV キャッシュをそのまま物理ブロック 1 に書き込める。

つまり vLLM は、コピーオンライトで管理される最後の論理ブロックを除き、プロンプトの KV キャッシュ領域の大半を複数の出力サンプル間で共有できる。物理ブロックの共有は、特に*入力プロンプトが長い*場合にメモリ使用量を大きく減らす。

![キャプションを参照](../../papers/vllm/figure-08.png)

**図 8。** 並列サンプリングの例。

**ビームサーチ。** 機械翻訳などの LLM タスク [Wu17] では、ユーザーは LLM が出力する上位 $k$ 個の適切な翻訳を求める。ビームサーチ [Sut14] は、サンプル空間を完全に探索する計算量を抑えながら、LLM から最も確率の高い出力シーケンスをデコードする手法として広く使われている。このアルゴリズムは、各ステップで保持する上位候補数を決める*ビーム幅* $k$ を用いる。デコード中は、ビーム内の各候補シーケンスをすべてのトークン候補で展開し、LLM でそれぞれの確率を計算したうえで、$k\cdot|V|$ 個の候補から確率の高い上位 $k$ シーケンスを残す。ここで $|V|$ は語彙サイズである。

![キャプションを参照](../../papers/vllm/figure-09.png)

**図 9。** ビームサーチの例。

並列デコーディングと異なり、ビームサーチでは最初のプロンプトブロックだけでなく、他のブロックも候補間で共有できる。デコーディングが進むにつれて共有関係は動的に変化し、複数回の fork で形成される OS のプロセスツリーに似た形になる。[図 9](#figure-09) は、ビーム幅 $k=4$ の例で vLLM が KV ブロックを管理する様子を示す。点線で示す反復の前には、各候補シーケンスが四つの完全な論理ブロックを使っている。すべての候補が最初のブロック 0（プロンプト）を共有し、候補 3 はブロック 1 から他の候補と分岐する。候補 0-2 は最初の三ブロックを共有し、四つ目で分岐する。次の反復では、確率上位の四候補がすべて候補 1 と 2 から派生する。元の候補 0 と 3 は上位から外れるため、その論理ブロックを解放し、対応する物理ブロックの参照カウントを減らす。vLLM は参照カウントが 0 になった物理ブロック 2、4、5、8 をすべて解放し、新しい候補の KV キャッシュ用に物理ブロック 9-12 を割り当てる。この時点では、すべての候補がブロック 0、1、3 を共有し、候補 0 と 1 はブロック 6、候補 2 と 3 はブロック 7 も共有する。

従来の LLM サービングシステムでは、ビーム候補間で KV キャッシュを頻繁にコピーする必要があった。例えば[図 9](#figure-09) では、点線より後で候補 3 が生成を続けるために、候補 2 の KV キャッシュの大半をコピーしなければならない。vLLM は物理ブロックを共有することで、このコピーコストを大幅に減らす。異なるビーム候補間でほとんどのブロックを共有でき、新しいトークンを既存の共有ブロックへ書き込む場合にだけ、並列デコーディングと同じコピーオンライトを適用する。このときコピーするデータは一ブロックだけである。

**共有プレフィックス。** 一般に LLM のユーザーは、指示と入出力例を含む長いタスク説明を与える。これは*システムプロンプト* [Ope23c] とも呼ばれる。この説明を実際のタスク入力と連結してリクエストのプロンプトを作り、LLM はプロンプト全体に基づいて出力を生成する。[図 10](#figure-10) に例を示す。共有プレフィックスは、プロンプトエンジニアリングで調整し、下流タスクの精度を高めることもできる [Li21, Les21]。

この種のアプリケーションでは、多くのユーザープロンプトが同じプレフィックスを持つ。そのため LLM サービスプロバイダーは、プレフィックスの KV キャッシュをあらかじめ保存し、重複する計算を減らせる。vLLM では、プロバイダーが定義した共有プレフィックスごとに物理ブロックを予約すればよい。これは、OS がプロセス間で共有ライブラリを扱う方法に似ている。共有プレフィックスを含む入力プロンプトでは、論理ブロックをキャッシュ済みの物理ブロックへそのままマッピングし、最後のブロックだけをコピーオンライトに指定する。プロンプトフェーズでは、ユーザーのタスク入力だけを計算すればよい。

![キャプションを参照](../../papers/vllm/figure-10.png)

**図 10。** 機械翻訳における共有プロンプトの例。例文は [Bro20c] から採用した。

**デコーディング手法の混在。** ここまで述べたデコーディング手法は、それぞれ異なるメモリ共有とアクセスのパターンを持つ。それでも vLLM は、デコーディング設定の異なるリクエストを同時に処理できる。既存システムでは、これを効率よく実行できない。vLLM は、論理ブロックを物理ブロックへ変換する共通のマッピング層によって、シーケンス間の複雑な共有関係を隠蔽する。LLM と実行カーネルからは、シーケンスごとの物理ブロック ID のリストだけが見え、シーケンス間の共有関係を扱う必要がない。したがって既存システムよりも、サンプリング要件の異なるリクエストを同じバッチに含めやすくなり、システム全体のスループットが向上する。

<span id="S4.SS5"></span>

### 4.5. スケジューリングとプリエンプション

リクエスト量がシステムの処理能力を超えると、vLLM は一部のリクエストを優先しなければならない。vLLM は全リクエストに先着順（FCFS）のスケジューリング方針を適用し、公平性を保ってスタベーションを防ぐ。リクエストをプリエンプトする場合は、到着の早いものを先に処理し、最も新しいものからプリエンプトする。

LLM サービスには固有の難しさがある。入力プロンプトの長さは大きく異なり、生成される出力の長さも入力プロンプトとモデルの双方に依存するため、事前には分からない。リクエスト数と出力長が増えるにつれ、vLLM では新しい KV キャッシュを格納する GPU の物理ブロックが尽きることがある。このとき、典型的な二つの問題に答える必要がある。（1）どのブロックを退避させるか。（2）再び必要になったとき、退避したブロックをどう復元するか。一般的な退避方針では、将来最も遅くアクセスされるブロックをヒューリスティックに予測して退避させる。本稿の場合、あるシーケンスの全ブロックはまとめてアクセスされると分かっているため、シーケンスの全ブロックを退避させるか、一つも退避させない「全か無か」の方針を実装する。また、一つのリクエスト内の複数シーケンス（例えば一つのビームサーチリクエストのビーム候補）は、*シーケンスグループ*としてまとめてスケジューリングする。シーケンス間でメモリを共有している可能性があるため、グループ内のシーケンスは常に一緒にプリエンプトし、一緒に再スケジューリングする。二つ目の問題であるブロックの復元には、次の二方式を検討する。

**スワッピング。** 多くの仮想メモリ実装が使う古典的な方法で、退避させたページをディスク上のスワップ領域へコピーする。本稿では、退避させたブロックを CPU メモリへコピーする。[図 4](#figure-04) に示すように、vLLM は GPU ブロックアロケータに加えて CPU ブロックアロケータを備え、CPU RAM へスワップした物理ブロックを管理する。新しいトークン用の空き物理ブロックがなくなると、退避させるシーケンス群を選び、その KV キャッシュを CPU へ転送する。一つのシーケンスをプリエンプトしてブロックを退避させた後は、プリエンプトした全シーケンスが完了するまで新しいリクエストを受け付けない。リクエストが完了すると、そのブロックを解放し、プリエンプトしたシーケンスのブロックを GPU へ戻して処理を再開する。この設計では、CPU RAM へスワップするブロック数が GPU RAM の物理ブロック総数を超えない。そのため、CPU RAM のスワップ領域は、KV キャッシュに割り当てた GPU メモリ容量を上限とする。

**再計算。** プリエンプトしたシーケンスを再スケジューリングするときに、KV キャッシュを再計算する。デコーディング中に生成したトークンを元のユーザープロンプトと連結して新しいプロンプトにすれば、全位置の KV キャッシュを一回のプロンプトフェーズ反復で生成できるため、再計算のレイテンシは当初のレイテンシより大幅に短くなることがある。

スワッピングと再計算の性能は、CPU RAM と GPU メモリ間の帯域幅、および GPU の計算能力に左右される。§[7.3](#S7.SS3) で両方式の速度を調べる。

<span id="S4.SS6"></span>

### 4.6. 分散実行

多くの LLM は、パラメータサイズが単一 GPU の容量を超える [Bro20c, Cho22a]。したがって、複数の GPU に分割し、モデル並列で実行する必要がある [Zhe22, Li23j]。このため、分散メモリを扱えるメモリマネージャが求められる。vLLM は、Transformer で広く使われている Megatron-LM 方式のテンソルモデル並列化 [Sho19] をサポートし、分散環境でも動作する。この方式は SPMD（Single Program Multiple Data）の実行スケジュールに従い、線形層を分割してブロック単位の行列積を行い、GPU 間で all-reduce により中間結果を継続的に同期する。具体的には、アテンション演算をアテンションヘッド次元で分割し、各 SPMD プロセスがマルチヘッドアテンションの一部のヘッドを担当する。

モデル並列で実行しても、各モデルシャードは同じ入力トークン群を処理するため、同じ位置の KV キャッシュを必要とする。そこで vLLM は、[図 4](#figure-04) のように集中型スケジューラ内に一つの KV キャッシュマネージャを置く。各 GPU ワーカーは、このマネージャと論理ブロックから物理ブロックへのマッピングを共有する。共通のマッピングにより、各ワーカーは入力リクエストごとにスケジューラから与えられた物理ブロックを用いてモデルを実行できる。すべてのワーカーが同じ物理ブロック ID を使う一方、各ワーカーが保存するのは担当するアテンションヘッドの KV キャッシュだけである。

各ステップで、スケジューラはまず、バッチ内の各リクエストの入力トークン ID とブロックテーブルを含むメッセージを作る。次に、この制御メッセージを GPU ワーカーへブロードキャストする。各ワーカーは入力トークン ID を使ってモデルの実行を始め、アテンション層では制御メッセージ内のブロックテーブルに従って KV キャッシュを読み出す。実行中は、スケジューラの介入なしに all-reduce 通信プリミティブで中間結果を同期する [Sho19]。最後に、その反復でサンプリングしたトークンをスケジューラへ返す。つまり各 GPU ワーカーは、デコーディング反復の開始時にステップ入力とともに全メモリ管理情報を受け取ればよく、メモリ管理のためにワーカー同士で同期する必要はない。

## 5\. 実装

<span id="table-01"></span>

![論文の表 1](../../papers/vllm/table-01.png)

**表 1。** モデルサイズとサーバー構成。

vLLM は、FastAPI [Fas23] フロントエンドと GPU ベースの推論エンジンを備えたエンドツーエンドのサービングシステムである。フロントエンドは OpenAI API [Ope20] のインターフェースを拡張し、最大シーケンス長やビーム幅 $k$ などのサンプリングパラメータをリクエストごとに指定できる。vLLM エンジンは 8.5K 行の Python と 2K 行の C++/CUDA コードで実装されている。スケジューラやブロックマネージャなどの制御コンポーネントは Python で開発し、PagedAttention などの主要な演算にはカスタム CUDA カーネルを用いる。モデル実行部では、PyTorch [Pas19] と Transformers [Wol20] を使い、GPT [Bro20c]、OPT [Zha22]、LLaMA [Tou23] などの一般的な LLM を実装している。分散 GPU ワーカー間のテンソル通信には NCCL [Ncc15] を使用する。

### 5.1. カーネルレベルの最適化

PagedAttention が導入するメモリアクセスパターンは既存システムでは効率よく扱えないため、最適化した GPU カーネルを複数開発した。（1）*reshape とブロック書き込みの融合。* 各 Transformer 層では、新しい KV キャッシュをブロックに分割し、ブロック読み出しに適したメモリレイアウトへ reshape してから、ブロックテーブルが指定する位置へ保存する。カーネル起動のオーバーヘッドを減らすため、これらを一つのカーネルに融合する。（2）*ブロック読み出しとアテンションの融合。* FasterTransformer [Fas21] のアテンションカーネルを改変し、ブロックテーブルに従って KV キャッシュを読み出しながらアテンション演算を行う。連続したメモリアクセスを実現するため、各ブロックの読み出しに一つの GPU warp を割り当てる。また、一つのリクエストバッチ内でシーケンス長が異なる場合にも対応する。（3）*ブロックコピーの融合。* コピーオンライト機構が発行するブロックコピーは、非連続なブロックを対象とすることがある。`cudaMemcpyAsync` API を使うと、小さなデータ転送を何度も呼び出すことになる。このオーバーヘッドを抑えるため、異なるブロックのコピーを一回のカーネル起動にまとめる。

### 5.2. 様々なデコーディングアルゴリズムのサポート

vLLM は `fork`、`append`、`free` という三つの基本メソッドを使って、さまざまなデコーディングアルゴリズムを実装する。`fork` は既存のシーケンスから新しいシーケンスを作り、`append` はシーケンスに新しいトークンを追加し、`free` はシーケンスを削除する。例えば並列サンプリングでは、`fork` を使って一つの入力シーケンスから複数の出力シーケンスを作成する。その後、反復ごとに `append` で新しいトークンを加え、停止条件を満たしたシーケンスを `free` で削除する。vLLM はビームサーチとプレフィックス共有にも同じ方法を用いる。これらのメソッドを組み合わせれば、将来のデコーディングアルゴリズムにも対応できると考えている。

## 6\. 評価

本節では、さまざまなワークロードにおける vLLM の性能を評価する。

### 6.1. 実験設定

**モデルとサーバーの構成。** 評価には、パラメータ数 13B、66B、175B の OPT [Zha22] と、13B の LLaMA [Tou23] を使用する。13B と 66B は LLM リーダーボード [Org23] に見られる一般的な規模で、175B は GPT-3 [Bro20c] と同じ規模である。すべての実験には、Google Cloud Platform 上の NVIDIA A100 GPU を備えた A2 インスタンスを使用する。モデルサイズとサーバー構成の詳細を[表 1](#table-01) に示す。

**ワークロード。** 実際の LLM サービスの入出力テキストを含む ShareGPT [Sha23b] と Alpaca [Tao23] に基づいて、ワークロードを合成する。ShareGPT は、ユーザーが共有した ChatGPT [Sch22] との会話を集めたデータセットである。Alpaca は、GPT-3.5 が self-instruct [Wan22e] で生成した命令データセットである。各データセットをトークナイズし、その入出力長からクライアントリクエストを合成する。[図 11](#figure-11) に示すように、ShareGPT の入力プロンプトは Alpaca より平均 8.4$\times$ 長く、出力は平均 5.8$\times$ 長いうえ、分散も大きい。これらのデータセットにはタイムスタンプがないため、異なるリクエスト率のポアソン分布から到着時刻を生成する。

**ベースライン 1：FasterTransformer。** FasterTransformer [Fas21] は、レイテンシ向けに高度に最適化された分散推論エンジンである。独自のスケジューラを持たないため、Triton [Tri18] など既存のサービングシステムに似た動的バッチ処理機構を備えるスケジューラを実装する。各実験では GPU メモリ容量に応じ、最大バッチサイズ $B$ を可能な限り大きく設定する。スケジューラは到着が早い順に最大 $B$ 件のリクエストを取り出し、そのバッチを FasterTransformer へ送って処理する。

**ベースライン 2：Orca。** Orca [Yu22a] は、スループット向けに最適化された最先端の LLM サービングシステムである。Orca は公開されていないため、独自に実装した。KV キャッシュの格納先アドレスはバディアロケータで決めると仮定し、リクエスト出力用にどれだけ余分な空間を予約するかに応じて三つの版を実装する。

**主要指標。** サービングスループットに注目する。リクエスト率の異なるワークロードを使い、Orca [Yu22a] と同様に、各リクエストのエンドツーエンドレイテンシを出力長で割った値の平均、すなわち正規化レイテンシを測る。高スループットのサービングシステムは、高いリクエスト率でも正規化レイテンシを低く保つ必要がある。大半の実験では 1 時間のトレースを使うが、OPT-175B だけはコスト上の制約から 15 分のトレースを用いる。

### 6.2. 基本サンプリング

基本サンプリング（リクエスト当たり 1 サンプル）での vLLM の性能を、三つのモデルと二つのデータセットで評価する。[図 12](#figure-12) の一行目は ShareGPT の結果である。リクエスト率を上げると、レイテンシは初め緩やかに増え、その後急増する。リクエスト率がサービングシステムの処理能力を超えると、キュー長が際限なく伸び、リクエストのレイテンシも増え続けるためである。

ShareGPT では、同程度のレイテンシを保ったまま、vLLM は Orca（Oracle）の $1.7\times$-$2.7\times$、Orca（Max）の $2.7\times$-$8\times$ のリクエスト率を維持できる。PagedAttention がメモリを効率よく管理し、Orca より多くのリクエストを一つのバッチで処理できるためである。例えば [図 13（a）](#figure-13) に示すように、OPT-13B では vLLM が同時に処理するリクエスト数は Orca（Oracle）の $2.2\times$、Orca（Max）の $4.3\times$ である。FasterTransformer と比べると、最大 $22\times$ のリクエスト率を維持できる。FasterTransformer は細粒度のスケジューリング機構を使わず、Orca（Max）と同様にメモリ管理も非効率だからである。

[図 12](#figure-12) の二行目と [図 13（b）](#figure-13) は Alpaca の結果で、ShareGPT と同じ傾向を示す。唯一の例外は [図 12（f）](#figure-12) で、Orca（Oracle）と Orca（Pow2）に対する vLLM の優位性が比較的小さい。OPT-175B のモデルとサーバー構成（[表 1](#table-01)）では KV キャッシュ用に大容量の GPU メモリを利用できる一方、Alpaca のシーケンスは短いためである。この条件では、メモリ管理が非効率でも Orca（Oracle）と Orca（Pow2）が多数のリクエストをバッチ処理できる。その結果、システム性能はメモリより計算資源に制約される。

### 6.3. 並列サンプリングとビームサーチ

PagedAttention のメモリ共有効果を、代表的な二つのサンプリング手法である並列サンプリングとビームサーチで評価する。並列サンプリングでは、リクエスト内のすべての並列シーケンスがプロンプトの KV キャッシュを共有できる。[図 14](#figure-14) の一行目に示すように、サンプリングするシーケンス数が多いほど、Orca ベースラインに対する vLLM の改善も大きくなる。同じく二行目は、ビーム幅を変えたビームサーチの結果を示す。ビームサーチはより多くの KV キャッシュを共有できるため、vLLM の性能上の利点もさらに大きい。OPT-13B と Alpaca における Orca（Oracle）比の改善は、基本サンプリングの $1.3\times$ から、ビーム幅 6 のビームサーチでは $2.3\times$ になる。

[図 15](#figure-15) は、共有で節約したブロック数を、共有しない場合の総ブロック数で割ったメモリ節約率を示す。並列サンプリングでは 6.1%-9.8%、ビームサーチでは 37.6%-55.2% のメモリを節約する。ShareGPT で同じ実験を行うと、並列サンプリングでは 16.2%-30.5%、ビームサーチでは 44.3%-66.3% となる。

### 6.4. 共有プレフィックス

[図 10](#figure-10) のように、異なる入力プロンプト間でプレフィックスを共有する場合の vLLM の効果を検証する。モデルには多言語 LLaMA-13B [Tou23]、ワークロードには WMT16 [Boj16] の英独翻訳データセットを使う。指示と複数の翻訳例を含む二種類のプレフィックスを作り、一方には一つの例（one-shot）、もう一方には五つの例（few-shot）を含める。one-shot のプレフィックスを共有すると、vLLM のスループットは Orca（Oracle）の $1.67\times$ になる（[図 16（a）](#figure-16)）。より多くの例を共有すると、$3.58\times$ に達する（[図 16（b）](#figure-16)）。

### 6.5. チャットボット

チャットボット [Sch22, Bar23, Chi23] は LLM の主要な用途の一つである。チャット履歴と直近のユーザークエリを連結してプロンプトとし、モデルに応答を生成させる。ShareGPT を使ってチャット履歴とユーザークエリを合成する。OPT-13B のコンテキスト長には上限があるため、プロンプトは末尾 1024 トークンに切り詰め、モデルにも最大 1024 トークンを生成させる。会話のターン間では KV キャッシュを保存しない。保存すると、ターンの間も他のリクエストが利用できる領域を占有するためである。

[図 17](#figure-17) に示すように、vLLM は三つの Orca ベースラインより $2\times$ 高いリクエスト率を維持できる。ShareGPT には長い会話が多く含まれるため、ほとんどのリクエストで入力プロンプトが 1024 トークンになる。バディアロケータを使う Orca ベースラインは、出力長の予測方法にかかわらず、リクエスト出力用に 1024 トークン分の領域を予約する。このため、三つの Orca ベースラインはほぼ同じ挙動を示す。これに対し vLLM は、PagedAttention が断片化と予約領域の問題を解消するため、長いプロンプトも効率よく処理できる。

## 7\. アブレーション研究

本節では vLLM の各要素を調べ、アブレーション実験によって設計上の選択を評価する。

### 7.1. カーネル・マイクロベンチマーク

PagedAttention の動的なブロックマッピングは、保存された KV キャッシュを扱う GPU 演算、すなわちブロックの読み書きとアテンション演算の性能に影響する。既存システムに比べ、本稿の GPU カーネル（§[5](#S5)）には、ブロックテーブルへのアクセス、追加の分岐、可変シーケンス長の処理によるオーバーヘッドがある。[図 18（a）](#figure-18) に示すように、アテンションカーネルのレイテンシは、高度に最適化された FasterTransformer の実装より 20%-26% 高い。このオーバーヘッドが影響するのはアテンション演算だけで、Linear などモデル内の他の演算には影響しないため、小さいと考えている。オーバーヘッドがあっても、PagedAttention を使う vLLM のエンドツーエンド性能は FasterTransformer を大幅に上回る（§[6](#S6)）。

### 7.2. ブロックサイズの影響

ブロックサイズの選択は vLLM の性能に大きく影響する。小さすぎると、KV キャッシュの読み出しと処理で GPU の並列性を十分に活用できない。大きすぎると、内部断片化が増え、共有できる可能性が下がる。

[図 18（b）](#figure-18) では、ShareGPT と Alpaca のトレースを用い、リクエスト率を固定して基本サンプリングを行い、ブロックサイズごとの vLLM の性能を評価する。ShareGPT では、ブロックサイズ 16-128 が最もよい性能を示す。Alpaca では 16 と 32 は良好だが、シーケンスがブロックサイズより短くなるため、それ以上では性能が大きく低下する。実際には、16 は GPU を効率よく使うには十分大きく、ほとんどのワークロードで大きな内部断片化を避けるには十分小さい。そのため vLLM の既定ブロックサイズは 16 としている。

### 7.3. 再計算とスワップの比較

vLLM は、復旧方式として再計算とスワッピングの両方をサポートする。両方式のトレードオフを調べるため、[図 19](#figure-19) に示すようにエンドツーエンド性能を評価し、オーバーヘッドをマイクロベンチマークする。小さなブロックでは、スワッピングのオーバーヘッドが過大になる。CPU と GPU の間で小さなデータ転送が何度も発生し、実効 PCIe 帯域幅が制限されるためである。一方、再計算は KV ブロックを使わないため、オーバーヘッドはブロックサイズによらず一定である。したがって、小さなブロックでは再計算、大きなブロックではスワッピングの方が効率よい。ただし、再計算のオーバーヘッドがスワッピングのレイテンシの 20% を超えることはない。中程度のブロックサイズである 16-64 では、両方式のエンドツーエンド性能は同程度である。

## 8\. 議論

**仮想メモリとページング技術の他の GPU ワークロードへの適用。** 仮想メモリとページングは、出力長が事前に分からず動的なメモリ割り当てが必要で、性能が GPU メモリ容量に制約される LLM サービングの KV キャッシュ管理に有効である。ただし、すべての GPU ワークロードに当てはまるわけではない。例えば DNN 学習では、通常テンソル形状が固定されているため、メモリ割り当てを事前に最適化できる。また、LLM 以外の DNN サービングは主に計算バウンドなので、メモリ効率を高めても性能が改善しない場合がある。このような状況に vLLM の技術を導入すると、メモリの間接参照と非連続なブロックメモリの追加コストにより、かえって性能が下がる可能性がある。それでも、LLM サービングと似た性質を持つ他のワークロードへ vLLM の技術が応用されることを期待している。

**仮想メモリとページングの適用における LLM 固有の最適化。** vLLM はアプリケーション固有の意味を利用して、仮想メモリとページングの考え方を再解釈し、拡張する。一例は「全か無か」のスワップアウト方針である。リクエストの処理には、対応するすべてのトークン状態が GPU メモリ上に必要という性質を利用する。もう一つは、退避させたブロックを再計算で復元する方法で、OS では利用できない。さらに、メモリアクセス用の GPU カーネルをアテンションなど他の演算と融合し、ページングによる間接参照のオーバーヘッドを抑える。

## 9\. 関連研究

**汎用モデルサービングシステム。** モデルサービングは近年盛んに研究され、ディープラーニングモデルの配備に関するさまざまな問題へ取り組むシステムが提案されている。Clipper [Cra17]、TensorFlow Serving [Ols17]、Nexus [She19]、InferLine [Cra20]、Clockwork [Guj20] は、初期の汎用モデルサービングシステムである。単一または複数モデルのサービングにおけるバッチ処理、キャッシュ、配置、スケジューリングを研究している。近年では、DVABatch [Cui22] が multi-entry multi-exit batching を導入し、REEF [Han22] と Shepherd [Zha23f] がサービングのプリエンプションを提案した。AlpaServe [Li23j] はモデル並列を使って統計的多重化を行う。しかし、これらの汎用システムは LLM 推論の自己回帰性とトークン状態を考慮しないため、最適化の機会を逃している。

**Transformer 専用サービングシステム。** Transformer アーキテクチャの重要性から、専用のサービングシステムも数多く開発されている。これらは GPU カーネルの最適化 [Wan21a, Ami22, Fas21, Ma20]、高度なバッチ処理機構 [Fan21, Yu22a]、モデル並列 [Pop22a, Yu22a, Ami22]、パラメータ共有 [Zho22] を利用して効率よくサービングする。その中では Orca [Yu22a] が本手法と最も近い。

**Orca との比較。** Orca [Yu22a] の反復単位スケジューリングと vLLM の PagedAttention は相補的な技術である。どちらも GPU 利用率を上げ、LLM サービングのスループットを高めることを目指す。Orca はリクエストをスケジューリングしてインタリーブし、より多くのリクエストを並列処理する。一方 vLLM はメモリ利用率を高め、より多くのリクエストのワーキングセットをメモリに収める。断片化を減らして共有を可能にすることで、一つのバッチでより多くのリクエストを並列実行し、Orca に対して 2-4$\times$ の高速化を達成する。Orca のような細粒度のスケジューリングとインタリーブはメモリ管理を難しくするため、vLLM の技術はさらに重要になる。

**メモリ最適化。** アクセラレータの計算能力とメモリ容量の差が広がり、学習と推論の双方でメモリがボトルネックになっている。学習時のピークメモリを減らすため、スワッピング [Hua20, Wan18a, Ren21b]、再計算 [Che16, Jai19]、両者の組み合わせ [Pat22] が使われてきた。FlexGen [She23a] は GPU メモリが限られた環境で、LLM 推論の重みとトークン状態をスワップする方法を研究するが、オンラインサービングは対象としない。OLLA [Ste22] はテンソルの寿命と配置を最適化して断片化を抑えるが、細粒度のブロック管理やオンラインサービングは行わない。FlashAttention [Dao22] はタイリングとカーネル最適化により、アテンション計算のピークメモリと I/O コストを削減する。本稿は、オンラインサービングにブロック単位のメモリ管理を導入する。

## 10\. 結論

本稿は、アテンションのキーとバリューを非連続なページメモリへ格納できる新しいアテンションアルゴリズム PagedAttention と、それを使ってメモリを効率よく管理する高スループット LLM サービングシステム vLLM を提案した。OS に着想を得て、仮想メモリやコピーオンライトなど確立された技術を、LLM サービングの KV キャッシュ管理と各種デコーディングアルゴリズムへ適用する方法を示した。実験では、vLLM が最先端システムに対して 2-4$\times$ のスループット向上を達成した。
