## 概要

本稿では、あらゆる AI エージェントに対し、強化学習（RL）に基づく大規模言語モデル（LLM）の訓練を可能にする、柔軟で拡張可能なフレームワーク *Agent Lightning* を提示する。既存手法は RL 訓練をエージェントと密結合するか、マスキングを伴う系列連結に依存するのに対し、*Agent Lightning* はエージェント実行と訓練を完全に分離するため、さまざまな方法で開発された既存エージェント（LangChain、OpenAI Agents SDK、AutoGen などのフレームワークを利用したものや、スクラッチから構築したもの）に、コードをほぼ一切変更せず統合できる。エージェント実行をマルコフ決定過程として定式化することで、統一データインターフェースを定義し、クレジット割り当てモジュールを含む階層型 RL アルゴリズム LightningRL を提案する。これにより、あらゆるエージェントが生成した軌跡を訓練用の遷移へ分解できる。その結果、RL はマルチエージェントシナリオや動的ワークフローなどの複雑な相互作用ロジックを扱える。システム設計では、Training-Agent Disaggregation アーキテクチャを導入し、エージェント可観測性フレームワークをエージェントランタイムに取り込むことで、標準化されたエージェント微調整インターフェースを提供する。Text-to-SQL、検索拡張生成、数学ツール利用の各タスクにおける実験では、安定した継続的な改善が得られ、実世界のエージェント訓練とデプロイにおける本フレームワークの可能性が示された。

## 1 はじめに

大規模言語モデル（LLM）の近年の進歩により、AI エージェントは検索、コード生成、ツール利用などの複雑なタスクを効果的に処理できるようになった。これらのエージェントは、LLM の能力を活用して多様なタスク要件に適応する優れた柔軟性を備えている。プロンプトエンジニアリングは性能の改善に役立つものの、LLM には依然として重大な制約がある。とりわけ、複数ターンのコーディングワークフロー、非公開ドメインのデータセット、未知のツールなど、明示的に訓練されていない状況へデプロイすると誤りを起こしやすい。そのため、AI エージェントは製品におけるエンドツーエンドのソフトウェア開発のような、複雑な実世界タスクを今なお確実には解決できない [Liu24v]。この制約は、こうした状況で LLM の可能性を十分に引き出すには、エージェント内のモデルを訓練または微調整する必要があることを示している [Che23d, Jin25b, Son25a, Mal25b]。

さらに、実世界のエージェント内でモデルを訓練することは、モデル能力の限界を押し広げるうえで重要になる可能性が高い。エージェントの実行中、システムは実世界の問題解決の複雑さを捉えた豊富な相互作用データを生成する。このような実世界の経験は、規模と多様性の両面で従来の人手で整備されたデータセットを上回り、将来の LLM 訓練にとって重要となる [Sil25, Yao25b, Kim25]。したがって、このデータを微調整に活用することは、エージェントの専門技能を改善するだけでなく、動的で対話的な環境に適した、より汎用的な LLM の開発も促進する。

DeepSeek-R1 [Dee25c] や Kimi k1.5 [Tea25h] などの推論モデルにおける近年の進歩をもたらした強化学習（RL）は、エージェントシナリオで LLM を最適化するための強力な枠組みを提供する。教師あり学習では複雑な対話タスクについて詳細なステップ単位の注釈が必要だが、それらは乏しく、作成にも費用がかかる。一方、RL は結果に基づく報酬信号に依存する。これにより、タスク固有の整備済みデータが不要となり、エージェントは多様なタスクにわたる環境フィードバックから、望ましい振る舞いを直接学習できる。さらに、RL の試行錯誤という性質は、人間が問題解決能力を獲得する方法とよく似ており、モデルはデプロイ環境に根差した行動方策を学習できる。この能力は、LLM が生成したテキストトークンを実世界の行動へ変換する可能性を開き、RL をエージェントベースシステム内のモデル訓練に自然に適合させる。

しかし、RL の枠組みをエージェントへ拡張すると、アルゴリズム設計とシステム実装の双方に大きな課題が生じる。既存の LLM 向け RL 手法とフレームワークは、主として選好アラインメントや数学的推論など、静的な単一呼び出しタスク向けに設計されている。これに対し、エージェントはこの設定を超える複雑性と多様性を示す。複雑性は、実行が異なるプロンプトと応答を伴う複数の LLM 呼び出しに加え、外部ツール、API、環境との相互作用を含むことが多いという点にある。多様性は、さまざまなアプリケーションの要件に応じて異なるエージェントを設計する必要性から生じる。これらの課題は、エージェントにおける大規模 LLM 調整への RL 適用を妨げている。

本稿では、あらゆる AI エージェントに対して LLM の RL ベース訓練を可能にする、柔軟で拡張可能なフレームワーク *Agent Lightning* を提案する。[図 1](#figure-01) に示すとおり、*Agent Lightning* は*エージェント実行と RL 訓練を完全に分離*し、開発者が既存エージェントをほぼ一切コード変更せずに訓練できるようにする。

この分離は、エージェント実行をマルコフ決定過程（MDP）として定式化することに基づく。ここで、*状態*は実行状況を十分に記述する変数値を含む、エージェント実行の現在のスナップショットを表す。*行動*は方策 LLM が生成する出力に対応し、その後、状態の更新に用いられる。この定式化に基づき、エージェント軌跡を遷移の系列として構造化する、RL 訓練用の統一データインターフェースを提案する。各遷移は、現在の状態（LLM 入力）、行動（LLM 出力）、報酬を含む。この統一データインターフェースは、基盤となるオーケストレーションロジックとエージェントフレームワークの詳細を抽象化するため、あらゆるエージェントに適用できる。さらに、収集した遷移を用いて方策 LLM を最適化するため、エージェント訓練向けに設計した階層型 RL アルゴリズム LightningRL を導入する。LightningRL は各遷移へクレジットを割り当てた後、既存の LLM 向け単一ターン RL 手法と完全に互換性のある方法で方策を更新する。このモデル化とアルゴリズムには、非常に柔軟なコンテキスト構築、複数エージェントの選択的な同時最適化、コンテキスト累積による系列の過度な長大化の緩和など、多くの利点がある。

上記の具体的な定式化に基づき、*Agent Lightning* は、あらゆるエージェントに適用できる標準化された訓練サービスを確立するため、Training-Agent Disaggregation（TA Disaggregation）アーキテクチャを導入する。フレームワークは Lightning Server と Lightning Client から構成される。Lightning Server は RL 訓練システムのコントローラとして機能し、訓練プロセスを管理するとともに、更新済みモデルの OpenAI 互換 API をクライアントへ公開する。Lightning Client は 2 つの機能コンポーネントからなる。一方はデータ送受信のためにサーバと通信し、もう一方はエージェントを実行してデータを収集し、エージェントランタイムとして機能する。

統一データインターフェースにより、エージェントランタイムは OpenTelemetry [Ope25j] のような包括的な可観測性フレームワークを、軌跡収集のための訓練プロセスへ活用できる。これは可観測性インフラストラクチャと RL 訓練を接続し、最適化手法が豊富な監視データを利用できるようにするとともに、スケーラビリティと柔軟性を高める基盤を形成する。エージェントランタイムは、*Automatic Intermediate Rewarding（AIR）*機構によって報酬の疎性を緩和するアルゴリズムも支援できる。AIR は、ツール呼び出しの返却状態などのシステム監視信号に基づいて、遷移へ中間報酬を割り当てる。開発者はこの機構を容易にカスタマイズでき、エージェントにおける疎な報酬の問題を効果的に緩和して、より有効な訓練を実現できる。

LangChain で実装した Text-to-SQL エージェント、OpenAI Agents SDK で構築した検索拡張生成エージェント、AutoGen で開発したツール利用型の数学質問応答エージェントなど、複数のタスクを通じて *Agent Lightning* の有効性を示す。これらの実験の報酬曲線は、*Agent Lightning* が異なるエージェントシナリオにわたって継続的かつ安定した性能向上をもたらし、実世界タスクを解決する大きな可能性を持つことを示している。

要約すると、*Agent Lightning* は以下の点でエージェント訓練を前進させる。

- *Agent Lightning* は、エージェントと RL 訓練を完全に分離した最初のフレームワークである。この分離により、実装方法を問わず、ほぼ一切コードを変更せずに *Agent Lightning* をあらゆる AI エージェントへ適用できる。訓練をエージェントの実行ロジックに整合させることで、実世界のアプリケーションにおけるエージェント性能を直接向上させる。これにより、開発者は静的な事前訓練モデルを超え、適応的で学習ベースのエージェントが持つ可能性を十分に引き出せる。また、統一データインターフェースとしても機能し、多様なエージェント生成データを収集してモデル能力を改善する。この分離を実現するため、*Agent Lightning* はアルゴリズムとインフラストラクチャの双方に専用設計を導入する。

- アルゴリズムについては、*Agent Lightning* はエージェントの MDP 定式化に基づき、統一データインターフェースを導入する。このインターフェースはさまざまなエージェント実行ロジックの複雑さを抽象化し、実行中に収集したデータを訓練軌跡へ直接変換できるようにする。さらに Agent Lightning は、軌跡レベルのリターンを各呼び出しが生成した応答へ割り当てるクレジット割り当てモジュールを備えた、階層型 RL フレームワークを採用する。この設計は既存の単一ターン RL アルゴリズムと容易に統合でき、効率的で効果的な訓練を可能にする。

- システムについては、*Agent Lightning* は RL 訓練とエージェント実行を明確に分離する Training-Agent Disaggregation アーキテクチャを導入する。このアーキテクチャは Lightning Server と Lightning Client によって実現され、両者はあらゆるエージェントに適用できる標準化されたモデル訓練サービスを提供する。Lightning Client はエージェントランタイムとして機能し、コード変更を必要とせず、エージェント実行を透過的に管理して軌跡を収集する。この設計により、訓練シナリオで可観測性インフラストラクチャを再利用でき、拡張性、スケーラビリティ、多様なエージェントフレームワークとの容易な統合が確保される。

## 2 現代の AI エージェント

AI エージェントは多様で急速に進化しているため、正確に定義することは難しい。複数の研究が AI エージェントの形式化と分類を試みているが [Gra23, She23c, Ant24c, Ant25e, Kim25d, Xu25i]、本稿の目的は新しい定義の導入ではない。その代わり、AI エージェントについて共通の理解となる抽象的な定式化を提示する。すなわち、*AI エージェントとは、その実行中に 1 回以上の LLM 呼び出しを含むソフトウェアシステムである*。この広い定義は、事前定義されたコードパスに従うワークフローベースシステム [Ant24c] から、動的な計画、推論、長期的な操作が可能な高度なマルチエージェント [Ant25e, Kim25d, Xu25i] まで、既存の幅広い AI エージェントを包含する。

本節では、エージェント構築に使われる一般的なコンポーネント、それらの典型的なオーケストレーション、エージェントを容易に開発するためのフレームワークを含め、現代の AI エージェントを概観する。

<span id="section-2-1"></span>

### 2.1 コンポーネント

一般に、エージェントを構築するコンポーネントは 2 種類に分けられる。

- **LLM**、またはより一般には基盤モデル（FM）は、エージェント内の中核となる推論・生成エンジンとして機能する。各 LLM 生成は、入力（プロンプト）から出力（応答）へのステートレスな写像である。LLM は計算要件が大きいため、通常は高性能サーバまたはクラウドプラットフォーム上で稼働し、エージェントは API エンドポイントを介してアクセスする。エンドポイントには、商用プロバイダ（OpenAI、Google など）と、セルフホスト型のソリューション（vLLM [Kwo23]、SGLang [Sgl25a] など）がある。エージェントは、それぞれ一意のエンドポイント URL で識別される複数の LLM を利用して、異なるタスクを実行したり、多様な機能を実現したりできる。エージェントが利用する LLM の集合を $\mathcal{M} = \{ M_i \}_{i=1}^m$ と定義する。ここで $m$ はエージェント内の LLM 数である。各 $M_i$ は異なるモデルまたはバージョンでもよく、明確化のため、モデル名をそのパラメータ $\theta_i$ と関連付けられる。

- **ツール**は、データベースからの情報検索、コード実行、API との対話など、特定のタスクを行うためにエージェントが呼び出す機能である。ツールは、呼び出し間でコンテキストを保持するかどうかに応じて、ステートレスにもステートフルにもなり得る。また、外部 API、ローカルプログラム、ライブラリなど、さまざまな方法で実装できる。近年、ツールはエージェントとツール間の相互作用を標準化し、容易な統合と相互運用性を実現するため、MCP（Model Context Protocol）[Mod25] またはその他のエージェント通信プロトコルに従うことが多い。$\mathcal{T} = \{ T_j \}_{j=1}^t$ をエージェントが利用できるツールの集合とし、$t$ をツール数とする。

<span id="section-2-2"></span>

### 2.2 オーケストレーション

コンポーネント集合 $\mathcal{M} \cup \mathcal{T}$ を機能的な構成要素として用いる場合、実行フロー、依存関係、コンポーネント間の順序を含むオーケストレーションは、通常、タスク要件に基づいてユーザがカスタマイズする。エージェントとその実行フローの詳細な例は、[3.1.3 節](#section-3-1-3)に示す。

重要な点として、このオーケストレーションは固定的でも決定論的でもない場合が多い。現代の AI エージェントは、変化するコンテキストに基づき、LLM が後続の行動を決定したりツールを選択したりする動的な振る舞いを示す。例えば、LLM にクエリの改善か質問への直接回答かを決めさせることで、上記の RAG エージェントとデータベースとの対話ターン数は変化し得る。ゲームプレイエージェントも一例である。行動を生成し、環境からフィードバックを受け取る反復プロセスは LLM 呼び出しの系列として表され、各呼び出しはゲーム内の意思決定ステップに対応する。この反復プロセスを展開することで、LLM が現在のゲーム状態と過去の行動に基づいて戦略を適応させる、エージェントの動的な振る舞いを捉えられる。

この動的な相互作用は、最適化を改善し得る豊富なタスク固有の振る舞いを捉える一方、データモデル化と下流学習にも大きな課題をもたらすため、現在の RL 訓練フレームワークで異なるエージェントを実装することは非現実的で、スケールしない。

<span id="section-2-3"></span>

### 2.3 実装

開発者は複数の方法で AI エージェントを作成できる。完全な制御とカスタマイズのため、エージェントをすべてスクラッチから構築する場合もある。一方、インフラストラクチャを提供し、開発を加速する既存のエージェント開発フレームワークを利用する開発者もいる。これらのフレームワークには、LangChain [Lan25c]、OpenAI Agents SDK [Ope25i]、AutoGen [Aut25a] などのオーケストレーションプラットフォームが含まれる。

エージェントフレームワークは、モジュール化されたコンポーネント（LLM とツール）と柔軟な動的オーケストレーション機構を提供し、タスク要件とエージェントの実行時状態の双方に適応するワークフローをユーザが定義できるようにする。しかし、エージェントをスクラッチから構築する場合でも、フレームワークを使う場合でも、通常は自動的な自己改善の機構を欠き、エージェント最適化を含まない。実世界のシナリオ、とりわけ非公開データを扱う場合、エージェント性能は要件に達しないことが多く、自動最適化が必要となる。

<span id="section-3"></span>

## 3 Agent Lightning

ここから、提案する *Agent Lightning* フレームワークを説明する。まず、[3.1 節](#section-3-1)で統一データインターフェースを定義し、エージェント設計に依存せず、実行中に収集するデータを規定する。次に、[3.2 節](#section-3-2)でエージェントにおけるマルコフ決定過程を示し、強化学習（RL）の基礎を与える。その後、[3.3 節](#section-3-3)でエージェントから収集したデータを利用して LLM を更新する階層型 RL アルゴリズムを提示する。最後に、[3.4 節](#section-3-4)で、エージェント訓練プロセスを大幅に効率化する複数の設計要素を備えた専用インフラストラクチャを説明する [+1]。

<span id="section-3-1"></span>

### 3.1 統一データインターフェース

データ駆動型のエージェント最適化は、根本的にエージェント実行中に生成されるデータへ依存する。そこで *Agent Lightning* では、このデータを RL 訓練アルゴリズムへ供給する方法を規定する、統一データインターフェースを定義する。このインターフェースは非常に汎用的であり、あらゆる AI エージェントから収集したデータへ適用できる。

AI エージェントは特殊な種類のソフトウェアであり、あらゆるソフトウェア実行と同様、有向非巡回グラフ（DAG）として表現できる [Aho07, Aba16]。このグラフでは、各ノードが集合 $\mathcal{M} \cup \mathcal{T}$ に含まれるコンポーネント（LLM またはツール）の呼び出しに対応し、各エッジがコンポーネント間の依存関係または制御フローを表す。しかし、整理されていないエージェント実行トレースから完全なグラフを解析することは容易ではなく、訓練目的には不要であることも分かった。マルコフ決定過程（MDP）の概念を活用すれば、RL 最適化の実行には、現在の*状態*と、状態遷移へ影響する主要因（すなわち*呼び出し*）を特定するだけでよい。

<span id="section-3-1-1"></span>

#### 3.1.1 状態と呼び出し

$\texttt{state}$ をエージェント実行のスナップショットとして定義する。これにはプログラムカウンタ、変数値、コールスタック、リソースコンテキストなどの情報が含まれ得る。これらは、エージェントの実行に伴って変化する変数の集合として抽象化できる。同じタスク $x$ を複数回実行すると、エージェントの動的な振る舞いによって異なる実行トレースが生成され得る。$x$ の $k$ 回目の実行について、時刻 $t$ で $V$ 個の変数を含む $\texttt{state}$ は次のように表される。

<span id="equation-01"></span>

$$
\texttt{state}_t(x,k) = \left\{ \texttt{variable}_i^{x,k,t} \right\}_{i=1}^{V}.
$$

状態はエージェント実行中に継続的に変化する。例えば、for ループのカウンタは増加し、単純な文字列操作は中間変数を変更する。しかし、このような中間操作や補助コードはエージェント最適化に不可欠ではない。ここでは、コンポーネントが使用または変更し、プログラムの意図などの重要な意味を表す主要変数に注目し、これを*意味変数*と呼ぶ [Qiu24]。状態と意味変数の具体例は、[3.1.3 節](#section-3-1-3)と[図 2](#figure-02) に示す。

意味変数の変更は、エージェントの*コンポーネント呼び出し*を通じて発生する。$x$ の $k$ 回目の実行が $N$ 回のコンポーネント呼び出しからなると仮定する。

<span id="equation-02"></span>

$$
\texttt{execution}(x,k) = \left\{ \texttt{call}_i^{x,k} \right\}_{i=1}^{N},
$$

ここで、$i$ 番目のコンポーネント呼び出しを $\texttt{call}$ として次のように定義する。

<span id="equation-03"></span>

$$
\texttt{call}_i^{x,k} = (\texttt{meta}_i^{x,k}, \texttt{input}_i^{x,k}, \texttt{output}_i^{x,k}), \quad\mathrm{with}~\texttt{output}_i^{x,k} = C_i(\texttt{input}_i^{x,k}).
$$

ここで、$C_i \in \mathcal{M} \cup \mathcal{T}$ はこの呼び出しで実行されるコンポーネント（LLM またはツール）、$\texttt{input}_i^{x,k}$ と $\texttt{output}_i^{x,k}$ は入力データと出力データを表す。$\texttt{meta}_i^{x,k}$ は、$C_i$ の名前、種類、バージョン、API エンドポイントに加え、LLM 呼び出しのサンプリング戦略や温度など、呼び出しに関するメタ情報を含む。

$\texttt{state}$ はエージェントのスナップショットを表すため、すべての入力と出力は特定時刻の意味変数である。

<span id="equation-04"></span>

$$
\texttt{input}_i^{x,k}\in\texttt{state}_{t_1}(x,k), \quad \texttt{output}_i^{x,k}\in \texttt{state}_{t_2}(x,k).
$$

$\texttt{state}$ 内のすべての情報が、呼び出されるコンポーネントに必要、または可視であるとは限らない。例えば[図 2](#figure-02)では、$\texttt{state}$ が 4 個の意味変数を含む一方、最初のクエリを書く際に LLM が参照できるのはユーザ入力だけであり、検索ツールも生成済みクエリだけを入力として受け取る。

<span id="section-3-1-2"></span>

#### 3.1.2 報酬とデータセット

エージェント実行中に収集したデータから学習できるよう、タスク完了品質を測定する報酬信号を導入する。各エージェント実行にはスカラー報酬 $\{r_1, \dots, r_N\}$ が付与され、各 $r_i \in \mathbb{R}$ は $i$ 番目の呼び出しの品質に対応する。報酬信号を伴う実行は次のように表される。

<span id="equation-05"></span>

$$
\texttt{execution}^R(x,k) = \left\{ (\texttt{call}_i^{x,k},r_i^{x,k}) \right\}_{i=1}^{N}.
$$

報酬信号は、タスクとエージェント設計に応じて、中間ステップまたはエージェント実行の終了時に与えられる。ツール呼び出しの成功やタスクの部分的完了を示す中間報酬 $r_i$（$i < N$）は、より粒度の細かいフィードバックを提供し、エージェントの学習プロセスを導く。最終報酬 $r_N$ は通常、タスク全体の達成におけるエージェントの成功度を評価する。多くの実世界シナリオでは、実行全体の結果を評価する終端報酬 $r_N$ しか得られない。これは、中間報酬 $r_1, \dots, r_{N-1}$ がなく、学習が最終結果だけに依存する、一般的な定式化の特殊例である。

訓練または評価用のデータセットは、タスク集合 $\mathcal{X}=\{x_1,\dots,x_{|\mathcal{X}|}\}$ と報酬関数からなり、$|\cdot|$ は集合の大きさを表す。タスクは複数回実行でき、各実行は報酬関数に従って注釈される。

#### 3.1.3 説明例

エージェント実行と統一データインターフェースを具体的に説明するため、[図 2](#figure-02) に示す典型的な検索拡張生成（RAG）エージェントを考える。このエージェントは、まず関連文書を検索し、次にその文書に基づいた応答を生成することで、ユーザの問い合わせへ回答する。エージェントは、生成方策モデル（$\mathcal{M} = \{\mathrm{LLM}\}$）と検索ツール（$\mathcal{T} = \{\mathrm{Search}\}$）という 2 つの主要コンポーネントから構成される。

実行フローは次のとおりである。

1. ユーザが質問（`UserInput`）を含む特定のタスク（$x$）を送信する。

2. エージェントが LLM を呼び出し、`UserInput` を条件として検索クエリ（`Query`）を生成する。

3. Search ツールが、生成された `Query` を用いて関連パッセージ（`Passages`）を検索する。

4. エージェントが LLM を再度呼び出し、検索された `Passages` と元の `UserInput` の双方を利用して最終回答（`Answer`）を生成する。

完了時に、報酬関数（`RAG_F1` など）が生成された `Answer` の品質を評価する。本定式化では、各 `state` は意味変数の現在値を保持する（[図 2](#figure-02)の緑色の矩形は有効な値を持つ変数を、灰色の矩形は現在の状態で値を持たない変数を表す）。エージェントの実行中、コンポーネント（LLM またはツール）の呼び出しは関連する意味変数を更新し、次の状態への変化をもたらす。したがって、あるタスク $x$ に対するエージェント実行は、呼び出しの順序付き系列（[図 2](#figure-02)の右側）として表され、各呼び出しはコンポーネント、その入力、出力、対応する報酬（通常は最終呼び出しにのみ存在）からなる。

重要な点として、統一データインターフェースは非 LLM コンポーネントによるものを含め、すべての状態変化を取得するため、柔軟で高度にカスタマイズ可能な最適化手法を実現する。例えば、マルチエージェントシステム内の特定エージェントを選択的に最適化できる（詳細は[3.2.2 節](#section-3-2-2)、実験は[4.1 節](#section-4-1)）。また、プロンプト調整など、モデル微調整以外の最適化も支援する。本稿は LLM 中心の最適化に焦点を当てるが、この拡張性は本手法の幅広い適用可能性を示している。実装の詳細は GitHub リポジトリに示す [+2]。

各状態で完全な実行コンテキストを取得することにより、統一データインターフェースは方策学習に十分な情報を提供し、エージェント実行と RL 訓練を明確に分離する。この設計は、実行 DAG 全体の明示的な解析を必要とせず、任意で複雑なエージェント相互作用ロジックを扱えるため、多様なエージェントワークフローに対する RL ベース最適化を大幅に簡素化する。

### 3.2 エージェントにおけるマルコフ決定過程

<span id="section-3-2-1"></span>

#### 3.2.1 定式化

最適化対象の単一 LLM を含むエージェントという単純な場合から考える。この LLM を方策モデルとして扱うと、その意思決定過程を部分観測マルコフ決定過程（POMDP）としてモデル化でき、RL 適用の基礎となる。POMDP の組 $\mathcal{M} = (\mathcal{S}, \mathcal{O}, \mathcal{A}, \mathcal{P}, \mathcal{R})$ は次のように定義できる。

- $\mathcal{S}$ は状態空間で、すべての可能な状態に対応する。すなわち $\texttt{state}_t\in\mathcal{S}$ である。

- $\mathcal{O}$ は観測空間で、方策 LLM へのすべての可能な入力に対応する。すなわち $\texttt{input}_t\in\mathcal{O}$ である。

- $\mathcal{A}$ は行動空間で、単一の行動を、方策 LLM の 1 回の呼び出しから生成されるトークン系列全体として定義する。すなわち $\texttt{output}_t\in\mathcal{A}$ である。

- $\mathcal{T}(s'|s,a)$ は、新しい状態への（通常は未知の）遷移ダイナミクスを定義する。

- $\mathcal{R}(s,a)$ は、状態・行動の組をスカラー報酬へ写像する報酬関数である。

具体的には、各ステップ $t$ でエージェントのスナップショットは $\texttt{state}_t$ であり、LLM はコンテキスト $\texttt{input}_t$ を観測する。[3.1.1 節](#section-3-1-1)で説明したように、$\texttt{input}_t$ は、方策 LLM の意思決定に必要または可視な $\texttt{state}_t$ の部分を表す意味変数である。次に LLM は、トークン系列 $\texttt{output}_t = (y_{t,1}, y_{t,2}, \dots, y_{t, N_t})$ を出力として生成する。この系列は単一の行動として扱われ、$a_t \in \mathcal{A}$ と表される。$a_t$ の実行後、エージェントは新しい $\texttt{state}_{t+1}$ へ遷移する。行動の品質を評価するため、スカラー報酬 $r_t = \mathcal{R}(s_t, a_t)$ が与えられる場合がある。リターンは報酬の和として定義される。

$$
R=\sum_{t=1}^T r_t.
$$

方策モデルの目標はリターンを最大化することである。

<span id="section-3-2-2"></span>

#### 3.2.2 RL 用データの抽出

上記の MDP 定式化に基づき、RL のため、方策 LLM のすべての決定と対応する報酬を含む軌跡を収集する必要がある。そのため、各実行（すなわち[式 5](#equation-05)）から、$\theta$ でパラメータ化された方策 LLM の更新に関連する情報、すなわち LLM 呼び出しの生の入力、出力、報酬だけを抽出し、次のように表す。

<span id="equation-06"></span>

<span id="equation-07"></span>

$$
\begin{aligned}
&\texttt{execution}^{\mathrm{RL}}(x,k) = \left\{( \texttt{input}_t^{x,k}, \texttt{output}_t^{x,k},r_t^{x,k}) \right\}_{t=1}^{T},\\
&\mathrm{with}~\texttt{output}_t^{x,k} = \pi_{\theta}(\texttt{input}_t^{x,k}).
\end{aligned}
$$

ここで $\pi_\theta$ は最適化対象の LLM、$T$ はこの軌跡における呼び出し回数である。[図 2](#figure-02) はこのデータ抽出プロセスを示す。

LLM 呼び出しはステートレスで、非常に柔軟である。その入力には、LLM の役割や目標を指定する命令プロンプト、会話履歴、タスクや実行によって異なるユーザ問い合わせ、推論ステップ、検索文書など、複雑なエージェントロジックが生成するさまざまな情報を符号化できる。エージェントフレームワークは、テンプレートや構造化形式などにより、これらの入力と出力をさらにレンダリングまたは解析する場合がある。RL 訓練の目的では、MDP 定式化により、煩雑で変化しやすいロジックと処理を無視し、LLM の現在の入力と出力だけに注目できる。この方法では、LLM 入力を取得した詳細な理由と情報源を省略する。*この抽出により、高度に動的なエージェント実行から生成されるトレースの、煩雑だが自明ではない解析を避けられ、あらゆる AI エージェントへ RL を適用できる。*

要約すると、統一データインターフェースと MDP 定式化により、*Agent Lightning* はタスク固有のエージェント設計と学習ベースの方策最適化を明確に分離し、モジュール化された動的エージェントシステムにおける効果的な RL ベース最適化の基礎を形成する。

**単一 LLM のマルチエージェント設定への適用。** 上記の定式化は、単一 LLM のマルチエージェントシナリオへ柔軟に適用できる。この場合、LLM はプロンプトに基づき、実行の異なる段階で複数の役割を担える。[図 2](#figure-02)の RAG の場合、最初の LLM 呼び出しでは、モデルに検索へ集中するよう指示し、検索クエリ $a_1$ を生成できる。このクエリが $\texttt{state}$ を変更し、新しい $\texttt{input}$ を形成する。2 回目の LLM 呼び出しでは、与えられた質問への回答に集中するようモデルへ指示し、最終回答 $a_2$ を生成できる。この回答の品質が最終報酬 $r_2$ を決定する。このように、単一 LLM が 2 つのエージェントとして機能できる。さらに *Agent Lightning* は、対応するエージェントの遷移を最適化プロセスへ含めることで、マルチエージェントシステム内のエージェントを選択的に最適化できる。マスキング手法と比べ、遷移の選択ははるかに便利で直感的である。

**複数 LLM 設定への拡張。** 固有のパラメータを持つ複数の異なる LLM を共同最適化する必要がある場合、直接的な方法では各 LLM を独立した MDP として扱い、個別に最適化する。これは訓練を簡素化する一方、方策間の依存関係を無視し、準最適な協調をもたらす可能性がある。より原理的な方法では、マルチエージェント強化学習（MARL）またはゲーム理論を用い、各 LLM を固有の目的と方策を持つエージェントとして扱う [Low17, Zha21f]。このような方法は、潜在的な相互作用ダイナミクスと、複数 LLM 間の競争的または協調的な振る舞いをより適切に捉える。

### 3.3 LightningRL：エージェント内の LLM を最適化する階層型 RL 手法

<span id="section-3-3-1"></span>

#### 3.3.1 LLM の単一ターン強化学習に関する準備

LLM 向け RL の近年の進歩は、モデルがプロンプトへの応答を一度に生成する単一呼び出し問題に焦点を当ててきた。これらのアルゴリズムは、主として数学や論理パズルなどの領域に適用される [Dee25c, Xie25c]。この設定では、タスク $x$ が与えられると、LLM は方策 $\pi_\theta$ から応答 $\texttt{output} = (y_1, \ldots, y_N)$ をトークン単位で生成し、各トークンが行動として扱われる。応答全体の生成後、解答の正しさまたは品質に基づいてスカラー報酬 $r(x, \texttt{output}, \hat{y})$ が割り当てられる。ここで $\hat{y}$ はタスク $x$ の正解である。典型的なトークンレベル損失は次のように簡略化できる [+3]。

<span id="equation-08"></span>

$$
\mathcal{L}(\theta) = -\mathbb{E}_{x \sim \mathcal{X},\, \texttt{output} \sim \pi_\theta(\cdot|x)}\left[ \sum_{j=1}^N \log \pi_\theta(y_j | x, y_{<j}) \cdot A_j \right],
$$

ここで $A_j$ はトークンレベルのアドバンテージ推定値、$\mathcal{X}$ はタスク集合である。一般的なアルゴリズムの主要な違いは、アドバンテージ項 $A_t$ の推定方法にある。標準 PPO [Ouy22] は学習済み critic モデルを使用し、価値関数によってアドバンテージを定義する。これに対し、近年の手法は訓練を簡素化するため、独立した価値関数を不要としている。例えば GRPO [Sha24d] は、同じプロンプトに対して生成された応答群の報酬の平均と標準偏差で、ある応答の報酬を正規化し、アドバンテージを計算する。同様に REINFORCE++ [Hu25d] はより単純なベースラインを用い、現在の応答の報酬と訓練バッチ全体の平均報酬との差をアドバンテージとして定義する。

<span id="section-3-3-2"></span>

#### 3.3.2 LightningRL によるエージェントシナリオへの拡張

上記の MDP 定式化では、単一 LLM 呼び出し中に生成されるトークン系列全体を 1 つの行動として扱う。方策は完全なエピソードを完了するため、相互作用を通じてこのような行動を複数回行う必要がある。一方、LLM は出力をトークン単位で生成し、既存の LLM 向け RL アルゴリズムの大半は単一ターンの相互作用向けに設計され、単一応答内のトークン生成の最適化へ注力している。この隔たりを埋めるため、*Agent Lightning* は LightningRL と呼ぶ単純な階層型強化学習（HRL）手法を導入する。この手法は、既存の LLM 向け単一ターン RL 手法へ変更なしで統合でき、あらゆるエージェントシナリオの最適化を効果的に支援する。

<span id="figure-03"></span>

![図 3. LightningRL アルゴリズムの説明。（a）単一呼び出し GRPO。LLM はタスクへの応答を一度に生成する。同じタスクの出力をグループ化し、アドバンテージ推定に用いる。（b）従来の複数ターン GRPO。各軌跡は複数の LLM 呼び出しを含み、同じタスクの軌跡をグループ化してアドバンテージ推定に用いる。LLM が生成していないトークンは、最適化中にマスクされる（灰色の破線枠）。（c）提案する LightningRL。軌跡を遷移へ分解し、同じタスクの遷移をグループ化してアドバンテージ推定に用いる。各遷移は現在の入力／コンテキスト、出力、報酬を含む。入力は現在のエージェント状態の一部であり、報酬はクレジット割り当てモジュールが計算する。](../../papers/agent-lightning/figure-03.png)

**図 3.** LightningRL アルゴリズムの説明。**（a）**単一呼び出し GRPO。LLM はタスクへの応答を一度に生成する。同じタスクの出力をグループ化し、アドバンテージ推定に用いる。**（b）**従来の複数ターン GRPO。各軌跡は複数の LLM 呼び出しを含み、同じタスクの軌跡をグループ化してアドバンテージ推定に用いる。LLM が生成していないトークンは、最適化中にマスクされる（灰色の破線枠）。**（c）**提案する LightningRL。軌跡を遷移へ分解し、同じタスクの遷移をグループ化してアドバンテージ推定に用いる。各遷移は現在の入力／コンテキスト、出力、報酬を含む。入力は現在のエージェント状態の一部であり、報酬はクレジット割り当てモジュールが計算する。

[図 3](#figure-03) に示すように、*Agent Lightning* は遷移を用いてデータを整理し、各遷移は[式 6](#equation-06)の組 $(\texttt{input}_t^{x,k}, \texttt{output}_t^{x,k}, r_t^{x,k})$ として定義される。各遷移は、コンテキストの構築方法を問わず、現在の LLM 呼び出しの入力コンテキストを含む。LightningRL は 2 段階の機構を適用する。まずエピソードレベルのリターン $R$ をクレジット割り当てモジュールが行動へ割り当て、次に各行動内のトークンへさらに分解して、トークンレベルの教師信号を生成する。現行実装では、LightningRL はエピソード内の各行動が同じ価値、すなわち最終リターン $R$ と等しいと単純に仮定する。第 2 段階は、既存の LLM 向け単一ターン RL アルゴリズムが処理する。

この設計には複数の利点がある。*第一に、任意の単一ターン RL アルゴリズム、特に一般に軽量で効率的な価値関数を用いない手法を、変更せず直接利用できる。*例えば GRPO では、同じプロンプトから生成したサンプルをグループ化し、アドバンテージを推定する。ここでも同じ方法を採る。各タスク $x$ を複数回実行して異なる実行データを生成し、それぞれを個別の行動へ分解する。次に、これらのサンプルをタスク単位でグループ化し、[式 8](#equation-08)の統計量を計算する。PPO と REINFORCE++ にも同様の適応を適用できる。

*第二に、LightningRL は方策観測を柔軟に構築できる。*データは個々の遷移単位で整理され、各遷移が固有の報酬を持つためである。現在の入力／観測は状態から柔軟に導出できる。例えば $\texttt{input}_t$ は、LLM が生成した過去ステップの要約、テンプレートで組み立てた構造化プロンプト、LLM の現在の役割を示す命令のいずれでもよい（[3.2.2 節](#section-3-2-2)で説明）。これに対し、従来手法は軌跡内のすべてのターンを単一応答へ連結し、更新箇所をマスキングで制御することが多く、このように柔軟でモジュール化されたコンテキスト構築を支援できない。

*第三に、マスキング戦略と比べ、LightningRL はより堅牢でスケーラブルな実装を提供する。*マスキングベースの手法は、訓練とエージェント実行ロジックの密結合を必要とするだけでなく、Rotary Positional Embeddings（RoPE）[Su24] など広く使われる位置符号化手法が前提とする、LLM 内のトークン連続性も損なう。さらに、マスキングはコード検証、デバッグ、カーネル設計を大幅に複雑化し、複雑なマスクでは効率が低下することが多い。これに対し LightningRL はエージェント軌跡を遷移へ分解し、LLM の入力構造へ自然に整合させ、追加のマスキングを不要にする。この設計は実装を簡素化し、スケーラビリティを高める。さらに、遷移形式でデータを整理することは、全ターンの連結によるコンテキスト累積と過度に長いコンテキストの問題を緩和する。長い軌跡を遷移のバッチへ分解し、バッチ累積などの手法による効率的な更新を可能にする。

**より高度なクレジット割り当て。** クレジット割り当てモジュールは、ヒューリスティクスや学習済みモデルに基づく割り当てなど、より高度な戦略を将来統合できる。将来の方向性の一つとして、高水準の価値関数を導入し、各行動 $a_t$ の期待リターンを個別に推定して、より細かなクレジット分配を行うことが考えられる。それでも実験結果は、単純な均等割り当て戦略が複数のシナリオとデータセットで有効であることを示す。

### 3.4 Agent Lightning のシステム設計

実世界のエージェント向けに LLM を訓練することは、RL 訓練フレームワークとエージェント開発フレームワークの統合を必要とする困難な取り組みである。これらのフレームワークは複雑で急速に進化し、本質的に分断されている場合が多いため、連携が難しい。*Agent Lightning* フレームワークは、RL とその他の最適化手法を用いたエージェントの円滑な開発と訓練を可能にする統一的なソリューションによって、この課題へ対処する。

#### 3.4.1 Training-Agent Disaggregation アーキテクチャ

LLM 向け RL 訓練フレームワークは、trainer と rollout という 2 つの主要コンポーネントからなる。trainer はモデル重みの更新を担当し、rollout は trainer が使うデータである軌跡を取得する。数学的推論などの単一ターン RL タスクでは、rollout プロセスは単純で、特定のプロンプトを与えて LLM 応答を生成するだけである。これに対し、複数ターンと環境との相互作用を伴うエージェントタスクでは、rollout にエージェントの完全な実行が必要となる。これには複数回の LLM 生成だけでなく、ツール利用などのネイティブコード実行も含まれる。

*Agent Lightning* の中核的な革新は、計算負荷の高い LLM 生成と、従来のプログラミング言語で記述された、軽量だが多様で柔軟なアプリケーションロジックおよびツールを分離する Training-Agent Disaggregation アーキテクチャにある。前者は RL フレームワークが管理し、後者に OpenAI 互換 API を公開する（[図 4](#figure-04)）。後者は GPU リソースと同じ場所へ配置する必要がなく、独立して管理・実行できるため、エージェントの振る舞いをより柔軟に定義できる。

**エージェント非依存の訓練と trainer 非依存のエージェント。** *Agent Lightning* の Training-Agent Disaggregation アーキテクチャの主要な利点は、訓練フレームワークとエージェントを相互に独立させることである。この設計により、VeRL [She24a] などの訓練フレームワークは*エージェント非依存*となる。関心対象は LLM の最適化とハードウェアリソース管理だけであり、特定のエージェントロジックとは結合しない。逆に、クライアント側で動作するエージェントは*trainer 非依存*となり、訓練フレームワークの実装詳細から独立して機能できる。この分離はエージェントの開発とデプロイに大きな柔軟性をもたらし、開発者は訓練インフラストラクチャの制約を受けず、エージェントロジックに集中できる。[付録 A](#appendix-a)では、*Agent Lightning* を用いて既存エージェントを容易に最適化するコード例を示し、その使いやすさと適応性を説明する。

上記の設計目標を実現するため、*Agent Lightning* は *Agent Lightning* Server と *Agent Lightning* Client からなる 2 コンポーネントアーキテクチャを導入する（[図 4](#figure-04)）。サーバは RL フレームワークと容易に統合できるよう設計され、訓練プロセスと LLM 最適化を管理する。タスクのオーケストレーション、データ管理、クライアントとの通信も担当する。クライアントはエージェントをカプセル化し、訓練フレームワークから独立して動作させることで、エージェントの開発と実行を柔軟にする。ユーザがアップロードしたタスクデータセットを受け取ると、RL フレームワークとともに初期化されたサーバが訓練手順を統括する。サーバはデータセットをバッチに分割し、イベント駆動システムを使ってクライアントと協調しながら、生成段階と訓練段階の遷移を管理する。タスクバッチはインベントリ方式でクライアントへ配布され、サーバは利用可能なタスクを記録し、クライアントが準備できるとタスクを割り当てる。タスクごとに一意の OpenAI 互換 API エンドポイントが、タスクと同時にクライアントへ渡される。このエンドポイントにより、クライアントはサーバへ接続し、データの追跡・取得プロセスを実行できる。次にクライアントは、エージェントランタイム（[3.4.2 節](#section-3-4-2)）でエージェントを実行し、トレースと報酬を生成する。トレースは収集されてサーバへ返され、サーバがデータを処理して訓練フレームワークへ渡し、モデルパラメータを更新する。このアーキテクチャは RL フレームワークとエージェント開発フレームワーク双方の強みを活かし、効率的でスケーラブルなエージェント訓練を可能にする。

<span id="section-3-4-2"></span>

#### 3.4.2 エージェントランタイム

*Agent Lightning* client は、実行の統括、データ取得、エラー処理、サーバとの通信を行う、エージェントのランタイムマネージャである。エージェント訓練ワークフローを堅牢、スケーラブル、効率的にする。

**エージェント実行のデータ並列性。** 現代の RL 訓練では、計算リソースを十分に利用し、訓練ループのボトルネックとなる rollout レイテンシを減らすため、大きなバッチサイズが不可欠である。大規模バッチを処理するには、複数のエージェントインスタンスを並列実行する必要がある。*Agent Lightning* client はデータ並列性を利用し、複数のエージェントインスタンスを効率的に同時管理・実行して、スループットを最大化し、レイテンシを最小化する。具体的には 2 段階の並列化戦略を実装する。ノード内並列化では、1 台のマシン上で 1 つの client が複数の worker を実行し、各 worker が異なるエージェントインスタンスを実行する。ノード間並列化では、異なるマシン上で複数の client が動作し、それぞれが固有のエージェントインスタンス群を管理する。このアーキテクチャは、分散システム全体で柔軟なスケーリングと効率的なリソース利用を可能にする。

**コード変更を伴わないデータ取得。** 既存のエージェントコードベースへ容易に統合するため、Lightning client はエージェントロジックを変更せずに関連データを取得する 2 種類の計装手法を採用する。第 1 の手法は OpenTelemetry [Ope25j] と AgentOps [Age25] に基づく。OpenTelemetry のトレース機能でエージェントコードを自動計装し、実行トレース、LLM 呼び出し、環境との相互作用を取得する。OpenTelemetry に依存したくないユーザ向けに、*Agent Lightning* は OpenAI 互換 API エンドポイントへ組み込んだ基本的なトレース機構も提供する。この機構は軽量でスケーラブルであり、OpenTelemetry と互換性のないエージェント開発フレームワークでも、データを効率的に取得できる。

**エラー処理と堅牢性。** 訓練プロセスの安定性と信頼性は極めて重要であり、とりわけ長時間の訓練セッションではさまざまな障害の影響を受ける。エラーはエージェントのクラッシュ、ネットワーク中断、無効な出力など、複数の原因から発生し得る。RL アルゴリズム固有の探索と活用のダイナミクスにより、RL 訓練での発生頻度は推論時より大幅に増える場合がある。このようなエラーを適切に処理しなければ、大幅な停止時間と計算リソースの浪費につながる。これに対処するため、*Agent Lightning* client は訓練時の堅牢性を確保する包括的なエラー処理機構を備える。クラッシュや長時間停止したツール呼び出しなど、エージェントコードが適切に処理しなかった障害を検出し、訓練プロセス全体が中断しないようにする。失敗したタスクは再試行するか、別のエージェントインスタンスへ再割り当てでき、デバッグと監視のための詳細なログも保持される。この設計は停止時間を最小化し、訓練効率を最大化して、エージェント性能の継続的な改善を可能にする。

**Automatic Intermediate Rewarding（AIR）。** RL 訓練では報酬が遅延し疎になるため、学習プロセスが妨げられる場合がある。エージェント実行のさまざまな段階でフィードバックを与える中間報酬は、より頻繁で有益な信号を提供し、訓練プロセスを大幅に改善できる。しかし、多くの場合、高価な人手注釈や複雑な報酬計算ロジックなど、大きなオーバーヘッドを必要とする。エージェント実行から中間報酬を抽出する方法は、訓練プロセスにとって非常に重要である。*Agent Lightning* client は、システム監視データを中間報酬へ変換する AIR 機構を提供し、訓練フレームワークがこれらの信号を利用して、より効果的に学習できるようにする。

**スケーラビリティのための環境・報酬サービス。** 環境と報酬関数は RL 訓練の重要なコンポーネントである。軽量でローカル実行できる環境と報酬関数は、エージェントインスタンスと同じ worker 内で直接実行できる。一方、携帯電話エミュレータや複雑な報酬計算ロジックのように、リソース負荷が高いか初期化コストが大きいものは、共有サービスとしてホストする方が効率的である。現在、*Agent Lightning* client は単純なプーリング方式で環境と報酬計算サービスをホストでき、将来はより複雑なサーバレスアーキテクチャを支援するよう拡張できる。

### 4.1 LangChain による Text-to-SQL

このタスクでは、自然言語の質問とデータベースが与えられ、エージェントは関連情報を取得する SQL クエリを生成し、その後、質問へ回答する必要がある。Spider データセット [Yu18b] を用いる。これは、自然言語の質問から実行可能な SQL クエリを生成するモデルの能力を評価するよう設計された、複雑なクロスドメイン Text-to-SQL ベンチマークである。138 の異なるドメインを対象とする多様なスキーマを備えた 200 個のデータベースに対し、10,000 件を超える質問を含み、テスト時に未知のデータベースへ汎化することをモデルへ要求する。ベースモデルとして $\texttt{Llama-3.2-3B-Instruct}$ [Met24a] を用いる。

この事例は LangChain で実装し、マルチエージェントシステムとして設計する。3 つのエージェントを含み、ワークフローは次のとおりである。SQL writer エージェントがまず SQL クエリを生成し、そのクエリを実行する。クエリが正しければ、SQL executor はデータベースから情報を返し、誤っていればエラーメッセージを返す。次に checking エージェントが SQL クエリの正しさと、取得情報の妥当性および十分性を評価する。このエージェントは、クエリを書き直すか、直接回答を生成するかを決定する。書き直しが必要なら、re-writing エージェントは checker LLM のフィードバックに基づいてクエリを修正する。書き直しが不要なら、質問応答も担当する re-writing エージェントが、取得した情報と質問を用いて最終回答を生成する。このワークフローでは、SQL の生成、確認、書き直しを同じ LLM が行うが、各タスクに合わせた異なるプロンプトを用いるため、実質的に 3 つのエージェントとして機能する。訓練時は、そのうち SQL writing と re-writing の 2 エージェントだけを最適化する。この 2 エージェントは同時に最適化される。この事例は、*Agent Lightning* がマルチエージェントシステム内の 1 つ以上のエージェントを選択的に最適化できることを示す。

このタスクでは、有効な SQL クエリを構文・意味の両面で生成、修正すること、クエリと取得情報の品質を確認すること、現在のコンテキストを理解して十分な情報が得られたかを評価すること、正しい情報を得るため SQL を改善すること、最後に取得結果に基づいて質問へ回答することなど、多様な能力が LLM に求められる。

このタスクの報酬は、質問への最終回答が正しいかどうかで決定する。モデルの最終性能も、テストセットの回答正解率に基づいて評価する。

### 4.2 OpenAI Agents SDK による検索拡張生成

第 2 のタスクは典型的な検索拡張生成（RAG）タスクである。質問と文書データベースが与えられると、エージェントはまず自然言語クエリを生成し、既存の retriever ツールを用いて根拠文書を検索する。MuSiQue データセット [Tri22] を使用する。これは真の合成的推論を促すよう設計された、難易度の高いマルチホップ質問応答ベンチマークである。浅いショートカットで解ける場合が多い従来のベンチマークと異なり、MuSiQue は接続された単一ホップ質問を体系的に組み合わせるボトムアップ手法で構築され、ある推論ステップが別のステップの出力へ決定的に依存することを保証する。さらに、実世界の検索設定を模倣するため、与えるデータベースは 2,100 万文書を含む Wikipedia 全体とする。また、BGE モデル [Baa23, Zha23k] が生成した埋め込みとコサイン類似度を retriever ツールとして用いる。このマルチホップ質問と大規模な検索対象は、エージェントに大きな課題をもたらす。ベースモデルとして $\texttt{Llama-3.2-3B-Instruct}$ [Met24a] を用いる。

このエージェントは OpenAI Agents SDK で実装する。ワークフローは前述の Text-to-SQL タスクに似ているが、より単純である。方策 LLM はまずクエリを生成し、その後、検索文書に応じてクエリを改善するか回答を生成するかを決定する。このワークフローでは 1 つの LLM を使用し、マルチエージェント設定は採用しない。つまり、LLM が行うべきすべての処理を含む 1 つの命令だけを使う。SQL タスクと異なり、ここでのクエリは自由テキストであるため、検索と推論のステップはよりオープンエンドとなる。また、与えるデータベースは前述のタスクよりはるかに大きい。このタスクは、意味的に有効な検索クエリを形成し、取得したテキスト情報を基に推論するエージェントの能力を検証する。

訓練中の報酬は、形式スコア $R_{\mathrm{format}}$ と正解度スコアの加重和である。具体的には、LLM が指定形式で出力でき、対応する内容が $\texttt{<think>...</think>}$、$\texttt{<query>...</query>}$、$\texttt{<answer>...</answer>}$ などの指定トークンで囲まれていれば、形式スコアは 1 となる。正解度スコア $R_{\mathrm{correctness}}$ は、予測回答と正解回答の単語レベル F1 スコアとして計算する。2 つのスコアは $R=0.9 \times R_{\mathrm{correctness}} + 0.1  \times R_{\mathrm{format}}$ として組み合わせる。

### 4.3 AutoGen によるツール利用型数学 QA

第 3 のタスクは、算術・記号問題を解くためにツール（具体的には電卓）を呼び出すエージェントの能力を評価する、数学中心の QA タスクである。推論と精密な計算を必要とする多様な数学問題からなる Calc-X データセット [Kad23] を用いる。Calc-X は GSM8K や Ape210K などの既存数学データセットを修正し、外部ツールを推論ワークフローへ統合することを重視しているため、ツール拡張エージェントの検証に適している。ベースモデルとして $\texttt{Llama-3.2-3B-Instruct}$ [Met24a] を用いる。

エージェントは AutoGen で実装され、単純だがツールを多用するワークフローに従う。自然言語の数学問題が与えられると、エージェントは最終回答を生成する前に、いつ、どのように電卓ツールを呼び出して中間値を計算するかを決定しなければならない。ワークフローは単一 LLM で実行され、この LLM がツール呼び出しの生成、ツール出力の解釈、最終回答の形成を担当する。そのためモデルには、数学問題の構造を理解し、構文的に正しいツール呼び出しを発行し、ツール出力を最終的な推論チェーンへ適切に統合することが求められる。

最終報酬は、エージェントが質問へ正しく回答したかどうかに基づく。モデル性能も、テストセットの回答正解率で評価する。

## 5 議論

<span id="section-5-1"></span>

### 5.1 関連研究

**LLM 向け複数ターン RL の近年の進歩。** LLM 向け RL の発展と verl [She24a] などのオープンソース RL 訓練フレームワークの登場に伴い、より高度なエージェント訓練シナリオを支援するため、これらのフレームワークを拡張することへの関心が高まっている。RAGEN [Wan25ag]、Trinity-RFT [Pan25a]、rLLM [Tan25e]、Search-R1 [Jin25b, Thu25] などの近年の研究は、複数ターンの対話環境における RL を検討してきた。これらの手法は通常、エージェントの各ターンを単一の長い系列へ連結し、適切な最適化のために特定のマスクを割り当てる。

本手法は連結ではなく、MDP 定式化、統一データインターフェース、クレジット割り当てモジュールを活用して、データを個別の遷移へ整理する。これは、実世界のエージェントに特徴的な複雑な相互作用ロジックを捉えるうえで複数の利点を持つ。*第一に*、遷移ベースのモデル化は、マルチエージェントオーケストレーションを含む幅広いエージェントアーキテクチャとワークフロー [Ant25e] を支援する。この柔軟性は訓練とデプロイの隔たりを埋め、RL ベース最適化を実世界エージェントの動的かつ多様な性質へ整合させる。連結ベースの手法は、単純で逐次的なワークフローを持つ少数のエージェントにしか適さず、より高度なパターンを扱うことが難しい。*第二に*、連結したターンではなく遷移としてデータを整理することで、コンテキスト長累積の問題を緩和する。エージェントが複数ターンの相互作用、ツール出力、MCP [Mod25] などのプロトコル交換、マルチエージェント通信を通じてコンテキストを蓄積すると、得られる系列は LLM の入力長制限を頻繁に超えるか、訓練サービスにより多くの計算量とメモリを要求する。遷移を単一サンプルとして扱うことで、ターン累積による系列長増加を大幅に軽減できる。*第三に*、現在の LLM 入力だけを訓練サンプルへ含めるため、本フレームワークはカスタムマスキング戦略を不要にする。一方、連結で適切な最適化を行うには、入力、損失、注意機構向けのカスタムマスキング戦略を設計する必要がある。これらはアプリケーション固有で汎化できない場合が多く、訓練プロセスとエージェント実行ロジックの密結合を必要とする。また位置の連続性を損ない、実装とデバッグを難しくする。*第四に*、遷移ベースの定式化は、より効果的なクレジット割り当て機構を提供する階層型 RL アルゴリズム [Zho24i] など、高度な RL アルゴリズムの可能性を開く。アルゴリズム上の柔軟性により、複雑なエージェントシナリオ向けに設計された新しい RL 手法への道が開かれる。

**LLM 向け大規模 RL 訓練システム。** LLM 向け RL の発展は、verl [She24a]、OpenRLHF [Hu25a]、TRL [Wer20]、ROLL [Wan25z]、AReaL [Fu25] などの安定した堅牢な訓練システムに支えられてきた。これらのシステムは主として、単一ターンシナリオでの効率的な LLM 訓練へ注力する。エージェントベースアプリケーション向けの拡張も提供するが [Cao25b, Ver25]、一般に開発者は訓練システム内でエージェントを再構築する必要がある。この要件は、既存の RL フレームワークが、連結順序やマスク適用位置の決定など、訓練データを正しく整理するため、訓練側にエージェントの実行ロジックを把握するよう求めることから生じる可能性がある。その結果、エージェントは訓練フレームワークと密結合する方法で実装されなければならない。しかし、既存のエージェント開発エコシステムは多様であり、この制約を満たすことは難しい。実際、実世界のエージェントは高度にカスタマイズ可能であり、OpenAI Agents SDK [Ope25i]、LangChain [Lan25c]、AutoGen [Aut25a] などのさまざまなフレームワークで開発されるか、LLM SDK を用いてスクラッチから直接構築されることも多い。これらのエージェントを既存 RL フレームワークへ移行するには、通常、ユーザがフレームワーク要件に合わせて、エージェント実行ロジックを手作業で適応または再実装する必要がある。このプロセスは労力を要し、誤りやすく、異種エージェントエコシステム全体へスケールさせることが難しい。さらに移行には、Ray [Mor18] やその他の分散システムへの習熟など、RL 訓練フレームワークの専門知識が必要となる場合が多く、多くの開発者に大きな障壁となり得る。加えて、密結合は RL 訓練プロセス自体にも追加負担を課す。エージェントは各種 MCP サーバ、外部ツール、API など複雑な依存関係を含み得るためである。これらのコンポーネントを RL 訓練フレームワーク内へ統合すると、複雑性と追加オーバーヘッドが生じ、中核的な RL の目的から注意が逸れ、保守性とスケーラビリティが損なわれる。

本フレームワークは RL 訓練をエージェントから完全に分離するため、システム設計の点でこれらの研究とは大きく異なる。これにより、RL 訓練エンジン内へデータ収集ロジックを書く必要がなくなり、エージェント側のコード変更もほぼ不要となる。その結果、異なるフレームワークで開発されたエージェントでも、ユーザがスクラッチから構築したものでも、容易に統合できる。さらに、本モデル化は理論上、幅広い RL 訓練フレームワークとの統合を支援し、柔軟性とスケーラビリティをさらに高める。

**アルゴリズム中心の複数ターン RL 研究。** 複数ターン RL は RL アルゴリズム分野で注目されてきたテーマであり、ArCHer [Zho24i] はテキストゲームを、WebShop [Yao22c] は電子商取引タスクを扱う。これらの研究では通常、RL エージェントが複数ターンにわたって環境と相互作用するが、実験では比較的小さな方策モデル（例えばパラメータ数 1B 未満）または Parameter Efficient Fine Tuning（PEFT）だけを用いることが多く、その実装を大規模モデルで再利用することは難しい。

**アプリケーション固有の RL 訓練。** DeepSeek-R1 [Dee25c] における RL 手法の成功以降、RAG やコーディングなど特定のシナリオへ RL を適用することへの関心が急増した。Search-R1 [Jin25b] と R1-Searcher [Son25a] は、より良いクエリを生成し検索能力を改善するよう LLM を訓練するために RL を適用し、[4.2 節](#section-4-2)の RAG 例と類似している。DeepSWE [Luo25d] は複数ターンの相互作用を用いて、コードの記述、関数呼び出し、API 利用を LLM へ教える。[4.1 節](#section-4-1)の Text-to-SQL 例では、LLM が単純な SQL クエリを生成した。一方、ReTool [Fen25a] や SimpleTIR [Xue25a] などの研究は、RL 学習によってツール統合型の長い推論を強化することを目指す。

これらの研究は主に特定のタスクまたはシナリオへ焦点を当て、訓練と推論の双方で事前定義されたワークフローに依存する場合が多い。したがって、汎用的なエージェント訓練を対象としていない。これに対し、本手法は特定のタスクやシナリオに限定されず、あらゆる AI エージェントに対する統一手法を提供し、AI エージェントと RL 訓練手法を橋渡しする。

<span id="section-5-2"></span>

### 5.2 今後の課題

**より多くの最適化手法。** 本モデル化フレームワークは、RL に加えて、[3.1.3 節](#section-3-1-3)で述べた自動プロンプト最適化など、他の最適化手法も十分に支援する。より一般的には、主要コンポーネントとその呼び出しへ注目することは、RL ベース手法に限定されない、エージェント最適化の基本原則である。そのため、実行トレース内で最適化対象となるコンポーネント部分集合を指定する、*Component of Interest*（CoI）の概念を導入する。例えば、プロンプトテンプレートのレンダリングをツール呼び出しとして扱い、このツールを CoI とすることで、*Agent Lightning* はプロンプト最適化手法を支援できる。この統一的で拡張可能なデータ構造は、包括的な下流最適化とエージェント振る舞いの分析を支援する。より多くの最適化手法を支援することは、今後の開発ロードマップの一部である。

**RL アルゴリズムの改善。** より効率的な RL アルゴリズムの開発は、より複雑なエージェントシナリオにおけるモデル最適化を解決する鍵となる。これには長期的なクレジット割り当て、探索アルゴリズム、オフポリシーアルゴリズムなどが含まれるが、それらに限定されない。Agent Lightning は遷移単位でデータをモデル化・整理するため、追加アルゴリズムを統合しやすい。

**エージェント向け RL システムインフラストラクチャの進歩。** LLM 向け RL を支えるインフラストラクチャは進化を続けており、*Agent Lightning* のようなエージェント RL フレームワークとの共同発展に大きな機会をもたらす。有望な方向の一つは、システムコンポーネントをさらに分離することである。具体的には、trainer、rollout（推論エンジン）、エージェントワークフローを分離し、rollout のボトルネックへ対処して、大規模 RL 訓練のスケーラビリティを高める。このようなアーキテクチャ改善の検討は、より効率的で柔軟な RL パイプラインにつながり得る。さらに、長期タスクの最適化では、RL アルゴリズムとシステム設計双方の協調的な革新により、複雑なエージェントをより効果的に訓練できるようになる。

**効率的なサービング。** LLM サービングについては、Parrot [Qiu24] など、より LLM に適した抽象化を持つ高度な手法を検討し、リソース利用率と応答時間を最適化できる。長いコンテキストの高速化では、Minference [Jia24e] など、長いコンテキスト処理向けの疎計算手法により、性能を大幅に向上できる。さらに、サービング環境とツールのリソーススケジューリングを改善することで、多様なデプロイシナリオにおける運用を効率化し、スケーラビリティを向上できる。

## 付録 A Agent Lightning で既存エージェントを最適化する例

Agent Lightning を用いて既存エージェントを最適化する例を示す。ゲーム環境（例えば 20 Questions または数当て）と相互作用する単純なエージェントがある場合、エージェントコード自体を変更せず、Agent Lightning フレームワークで性能を最適化できる。エージェントの典型的なフォルダ構成は次のとおりである。

```text
agent/
  |- data/train.jsonl
  |- environments/game_server.py
  |- agent.py
```

**リスト 1：** エージェントコードのフォルダ構成

この例では、`agent.py` ファイルにエージェントのロジック関数 `agent_function` があり、LLM のエンドポイントとゲーム環境を受け取り、ゲームへの回答を返す。ゲームサーバは `environments/game_server.py` が作成し、`(game_seed, ground_truth)` の組を `data/train.jsonl` に保存する。Agent Lightning でこのエージェントを最適化するには、エージェントコードを変更せずに Agent Lightning フレームワークで性能を最適化する `train.py` ファイルを作成できる。その例を次に示す [+4]。

```python
# train.py
from agent import agent_function
from environments.game_server import GameServer
from agent_lightning import Client, Resource, Task

# TODO: 環境は個別に管理できる
game_server = GameServer()

# Task は `.jsonl` ファイルに保存されたデータオブジェクトに対応する
# Resource はサーバから取得するメタデータであり、
#   LLM エンドポイントを含む
def agent_run(resource: Resource, task: Task):
  game_url = game_server.create_game(task.game_seed)
  answer = agent_function(resource.model_api, game_url)
  reward = game_url.score(answer, task.ground_truth)
  return reward

# AgentLightningServer を起動し、その URL を環境変数で渡す
client = Client(os.environ["AgentLightningServerUrl"])
# 事前にアップロードしたデータ ID も指定できる
client.upload_data("data/train.jsonl", test_file=None)
client.train(agent_run, nworkers=-1)
```
