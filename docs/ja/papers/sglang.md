## 概要

大規模言語モデル （LLM） は、複数回の生成呼び出し、高度なプロンプト技法、制御フロー、構造化された入出力を必要とする複雑なタスクに利用される機会が増えている。しかし、こうしたアプリケーションをプログラミングし、実行するための効率的なシステムは不足している。本稿では、複雑な言語モデルプログラムを効率よく実行するシステム SGLang を導入する。SGLang はフロントエンド言語とランタイムからなる。フロントエンドは、生成と並列性制御のためのプリミティブによってプログラミングを簡素化する。ランタイムは、KV キャッシュ再利用のための RadixAttention や、構造化出力のデコーディングを高速化する圧縮有限状態機械などの新しい最適化によって実行を高速化する。実験では、エージェント制御、論理推論、few-shot 学習ベンチマーク、JSON デコーディング、検索拡張生成パイプライン、マルチターンチャットなどのタスクについて、さまざまな大規模言語モデルとマルチモーダルモデル上で、SGLang が最先端の推論システムと比べて最大 $6.4\times$ 高いスループットを達成することを示す。コードは [https://github.com/sgl-project/sglang](https://github.com/sgl-project/sglang) で公開されている。

## 1 はじめに

近年の LLM の能力向上によって用途が広がり、より幅広い一般タスクへ取り組み、自律エージェントとして動作できるようになった [Ope23, Bub23, Par23, Wan23d, Sum23a]。このようなアプリケーションでは、LLM が複数ラウンドの計画と推論を行い、外部環境と相互作用する。これは、ツールの使用 [Sch24, Pat23b]、複数の入力モダリティ [Gem23, Ala22]、few-shot 学習 [Bro20b]、self-consistency [Wan22g]、skeleton-of-thought [Nin24]、tree-of-thought [Yao23] など幅広いプロンプト技法 [Liu23l] によって実現される。これらの新しいユースケースはいずれも、複数回の、多くの場合は相互に依存する LLM 生成呼び出しを必要とし、複雑なタスクの完遂に複数呼び出し構造を用いる傾向を示している [Yao22b, Kim23]。

こうしたパターンの登場は、LLM との対話が単純なチャットから、より高度なプログラム的利用へ移行していることを示す。ここでプログラム的利用とは、プログラムによって LLM の生成過程をスケジュールし、制御することである。本稿では、このようなプログラムを「言語モデルプログラム」（Language Model Programs、LM Programs）と呼ぶ [Beu23, Kha23]。前述の高度なプロンプト技法とエージェント型ワークフローは、LM プログラムの範囲に含まれる。LM プログラムには二つの共通特性がある。（1）LM プログラムは通常、制御フローを挟んだ複数の LLM 呼び出しを含む。これは、複雑なタスクを完遂し、全体的な品質を高めるために必要である。（2）LM プログラムは構造化入力を受け取り、構造化出力を生成する。これは、LM プログラムを合成し、既存のソフトウェアシステムへ統合するために必要である。

LM プログラムが広く使われているにもかかわらず、これを表現し実行する現在のシステムは依然として非効率である。本稿では、LM プログラムを効率よく使う際の主要な課題を二つ挙げる。*第一に、LLM の非決定的な性質のため、LM プログラムのプログラミングは煩雑で難しい。* LM プログラムの開発には、多量の文字列操作、プロンプトの実験的な調整、壊れやすい出力解析、複数の入力モダリティの処理、並列機構の実装が必要になることが多い。この複雑さは、単純なプログラムでさえ可読性を大きく損なう（[第 2 節](#section-02)）。

*第二に、そして重要なことに、冗長な計算とメモリ使用のため、LM プログラムの実行は非効率である。* 最先端の推論エンジン（vLLM [Kwo23]、TGI [Tex22]、TensorRT-LLM [Ten23] など）は、ワークロードを直接把握することなく、レイテンシの短縮とスループットの向上を目指して最適化されている。このためシステムは汎用的で堅牢になるが、特定のワークロードでは大きな非効率も生じる。代表例が Key-Value （KV）キャッシュの再利用である（[第 3 節](#section-03)）。KV キャッシュは、生成推論に不可欠な再利用可能な中間テンソルからなる。LM プログラムを通常どおりバッチ実行すると、共通のプリフィックスを共有する異なる LLM 呼び出し間で、KV キャッシュを再利用できる機会が数多く生じる。しかし、現行システムにはこの再利用を可能にする有効な仕組みがなく、不要な計算とメモリの浪費につながる。別の例は、構造化出力（JSON モードなど）の制約付きデコーディングであり、LLM の出力は正規表現が定める特定の文法規則に従うよう制限される（[第 4 節](#section-04)）。この制約下では、一度に複数のトークンをデコードできる場合が多い。しかし、既存システムは一度に一トークンしかデコードせず、デコーディング速度が最適ではない。

これらの課題に対処するため、本稿では LLM のための構造化生成言語（<u>S</u>tructured <u>G</u>eneration <u>Lang</u>uage）SGLang を提示する。中核となる考え方は、LM プログラムの複数呼び出し構造を体系的に利用し、効率よく実行することである。[図 1](#figure-01) に示すように、SGLang はフロントエンド言語とバックエンドランタイムの二つからなる。フロントエンドは LM プログラムのプログラミングを簡素化し、ランタイムはその実行を高速化する。両者は連携して性能を高められるが、それぞれ独立して機能することもできる。

SGLang は Python に埋め込まれたドメイン固有言語として導入する。生成用プリミティブ（`extend`、`gen`、`select` など）と並列性制御用プリミティブ（`fork`、`join` など）を提供する。SGLang は Python の制御フローとライブラリに対応するため、ユーザーは Python のネイティブ構文によって高度なプロンプトワークフローを容易に開発できる。本稿では SGLang のインタプリタとコンパイラを提供する。インタプリタはプロンプト状態をストリームとして管理し、プリミティブ操作をストリームへ投入して非同期に実行することで、同期とプログラム内並列性を適切に制御する。SGLang プログラムはトレースしてコンパイルし、さらに最適化することもできる。

ランタイム側では、SGLang プログラムの実行を高速化する複数の新しい最適化を提案する。*第一の技法*である RadixAttention は、複数の生成呼び出し間で KV キャッシュを自動的に再利用できるようにする。既存の推論エンジンでは、リクエストの処理が完了すると KV キャッシュが破棄されるため、複数の呼び出し間で再利用できず、実行速度が大幅に低下する。これに対し、本システムは全リクエストの KV キャッシュを基数木内の LRU キャッシュとして維持する。この方法は KV キャッシュを従来型のキャッシュとして管理し、基数木を用いて照合、挿入、削除を効率よく行う。キャッシュ認識型スケジューリングポリシーと組み合わせることで、ランタイムはさまざまな再利用パターンを効率よく処理できる。*第二の技法*は圧縮有限状態機械であり、構造化出力の制約付きデコーディングを高速化する。既存システムは許可されないトークンの確率をマスクし、次の一トークンだけに制約を適用するため、一度に一トークンしかデコードできない。本システムは制約を解析し、それを表す圧縮有限状態機械を構築する。この方法は、可能な場合に複数トークンのパスを一ステップのパスへ圧縮し、一度に複数トークンをデコード可能にして速度を高める。最後に、SGLang は OpenAI の GPT-4 のように API でのみ利用できるモデルもサポートする。このための*第三の技法*として、API 専用モデルの複数呼び出しプログラムを最適化する API 投機的実行を導入する。

SGLang を用いて、エージェント制御、論理推論、few-shot 学習ベンチマーク、JSON デコーディング、検索拡張生成パイプライン、マルチターンチャット、マルチモーダル処理を含むさまざまな LLM アプリケーションを実装した。NVIDIA A10G および A100 GPU 上で、Llama-7B/70B [Tou23a]、Mistral-8x7B [Jia24]、LLaVA-v1.5-7B（画像）[Liu24n]、LLaVA-NeXT-34B（動画）[Zha24j] などのモデルについて性能を評価した。実験結果では、幅広いワークロード、モデル、ハードウェア構成において、SGLang が Guidance [Gui22]、vLLM [Kwo23]、LMQL [Beu23] を含む既存のプログラミングシステムと推論システムに比べ、最大 $6.4\times$ 高いスループットを達成した。

## 2 プログラミングモデル

本節では、一貫して用いる例を通して SGLang のプログラミングモデルを導入し、言語プリミティブと実行モードを説明して、ランタイム最適化の機会を概説する。このプログラミングモデルは、柔軟で合成可能なプリミティブを提供することにより、複数呼び出しワークフローにおける煩雑な操作（文字列操作、API 呼び出し、制約指定、並列処理など）を簡素化できる。

**一貫して用いる例。** この言語は Python に埋め込まれたドメイン固有言語である。[図 2](#figure-02) は、branch-solve-merge プロンプト法 [Sah23] を用いて画像に関するエッセイを評価するプログラムを示す。関数 `multi_dimensional_judge` は `s`、`path`、`essay` の三つの引数を取る。`s` はプロンプト状態を管理し、`path` は画像ファイルのパス、`essay` はエッセイ本文である。`+=` 演算子により、新しい文字列と SGLang プリミティブを状態 `s` に追加して実行できる。関数はまず画像とエッセイをプロンプトへ追加する。次に `select` でエッセイが画像に関連するか確認し、結果を `s["related"]` に格納する。関連している場合は、プロンプトを三つに fork し、異なる観点から並列に評価して、`gen` で結果を `f["judgment"]` へ格納する。続いて評価を統合し、要約を生成して、文字による評点を付ける。最後に、正規表現制約 `regex` が定義するスキーマに従い、結果を JSON 形式で返す。SGLang はこのプログラムを大幅に簡素化する。OpenAI API に似たインターフェースで同等のプログラムを実装すると、手動の文字列操作と並列性制御のため、コード行数は $2.1\times$ になる。

**言語プリミティブ。** SGLang は、プロンプト状態、生成、並列性を制御するプリミティブを提供する。これらは Python の構文やライブラリと併用できる。プリミティブは次のとおりである。「`gen`」はモデルを呼び出して生成を行い、第一引数で指定した名前の変数に結果を格納する。「`regex`」引数をサポートし、正規表現が定義する文法（JSON スキーマなど）に出力を従わせられる。「`select`」はモデルを呼び出し、リストから確率が最も高い選択肢を選ぶ。「`+=`」演算子または「`extend`」はプロンプトへ文字列を追加する。「`[variable_name]`」演算子は生成結果を取得する。「`fork`」はプロンプト状態の並列な分岐を作り、「`join`」はプロンプト状態を再結合する。「`image`」と「`video`」は画像および動画入力を受け取る。

**実行モード。** SGLang プログラムを実行する最も単純な方法はインタプリタであり、ここではプロンプトを非同期ストリームとして扱う。`extend`、`gen`、`select` などのプリミティブはストリームへ投入され、非同期に実行される。これらのノンブロッキング呼び出しにより、Python コードは生成の完了を待たずに実行を続けられる。これは CUDA カーネルの非同期起動に似ている。各プロンプトはバックグラウンドスレッドのストリーム実行器によって管理され、プログラム内並列性を可能にする。生成結果の取得は準備が整うまでブロックし、正しい同期を保証する。別の方法として、SGLang プログラムを計算グラフにコンパイルし、グラフ実行器で動かすこともでき、より多くの最適化が可能になる。本稿はデフォルトでインタプリタモードを使用し、コンパイラモードの結果を[付録 D](#appendix-d) で論じる。SGLang は独自の SGLang Runtime（SRT）によってオープンウェイトモデルをサポートするほか、OpenAI や Anthropic などの API モデルにも対応する。

**比較。** LLM のプログラミングシステムは、高水準（LangChain、DSPy など）と低水準（LMQL、Guidance、SGLang など）に分類できる。高水準システムは、DSPy のプロンプトオプティマイザのように、事前定義または自動生成されたプロンプトを提供する。低水準システムは通常プロンプトを変更せず、プロンプトとプリミティブを直接操作できるようにする。SGLang は LMQL や Guidance に似た低水準システムである。[表 1](#table-01) に機能の比較を示す。SGLang はランタイム効率をより重視し、協調設計された独自のランタイムを備えるため、後で導入する新しい最適化が可能である。高水準言語（DSPy など）は低水準言語（SGLang など）へコンパイルできる。[第 6 節](#section-06) では、ランタイム効率を高めるため、SGLang を DSPy のバックエンドとして統合する例を示す。

## 3 RadixAttention による効率的な KV キャッシュ再利用

SGLang プログラムは複数の生成呼び出しを連結し、「`fork`」プリミティブで並列なコピーを作成できる。また、異なるプログラムインスタンスが一部の共通部分（system prompt など）を共有することも多い。こうした状況では、実行中に共有プロンプトプリフィックスが数多く生じ、KV キャッシュを再利用する機会が増える。LLM 推論中、KV キャッシュは前方パスから得た中間テンソルを格納し、後続トークンのデコーディングで再利用する。この名称は self-attention 機構の key-value ペアに由来する [Vas17]。KV キャッシュの計算はプリフィックストークンだけに依存する。そのため、同じプロンプトプリフィックスを持つリクエストは KV キャッシュを再利用でき、冗長な計算とメモリ使用を減らせる。背景と例の詳細は[付録 A](#appendix-a) に示す。

KV キャッシュを再利用できる場合、SGLang プログラムを最適化する上での主要な課題は、複数の呼び出しとインスタンスをまたいで KV キャッシュを再利用することである。一部のシステムは特定の再利用パターンを検討しているが [Kwo23, Ye24, Jur24, Gim24]、手動設定が必要な場合が多く、動的な木構造などすべての再利用パターンを扱うことはできない。そのため、最先端の推論システムの多くは、リクエストごとに KV キャッシュを再計算する。これらの制限と本手法との差異は[第 7 節](#section-07) で論じる。

本節では、実行時に KV キャッシュを自動的かつ体系的に再利用する新しい技法 RadixAttention を導入する。既存システムは生成リクエストの終了後に KV キャッシュを破棄するが、本システムはプロンプトと生成結果のキャッシュを基数木に保持し、プリフィックスの探索、再利用、挿入、削除を効率よく行えるようにする。キャッシュヒット率を高めるため、LRU 削除ポリシーとキャッシュ認識型スケジューリングポリシーを実装する。RadixAttention は、連続バッチ処理 [Yu22a]、paged attention [Kwo23]、tensor parallelism [Sho19] などの技法と互換性がある。キャッシュヒットがない場合のメモリおよび時間オーバーヘッドも無視できるほど小さい。

**RadixAttention。** 基数木は、従来の trie（プリフィックス木）より空間効率のよいデータ構造である。通常の木と異なり、基数木の辺には単一の要素だけでなく、長さの異なる要素列もラベルとして付けられるため、効率が大きく向上する。本システムは基数木を用い、トークン列と対応する KV キャッシュテンソルの写像を管理する。KV キャッシュテンソルは非連続なページレイアウトで格納し、各ページの大きさは一トークンに相当する。GPU メモリは KV キャッシュですぐに埋まるため、最も長く使われていない葉を最初に削除する単純な LRU ポリシーを導入する。葉を先に削除することで、共通の祖先が葉になって削除されるまでは、その祖先を再利用できる。

連続バッチ処理では、現在実行中のバッチが使うノードを削除できない。そのため、各ノードは、そのノードを使用中のリクエスト数を表す参照カウンタを維持する。参照カウンタがゼロならノードを削除できる。固定サイズのメモリプールをキャッシュとして事前割り当てしない点に注意されたい。代わりに、キャッシュ済みトークンと現在実行中のリクエストが同じメモリプールを共有する。したがって、システムはキャッシュと実行中リクエストへ動的にメモリを割り当てる。十分な数の待機リクエストを実行するときは、バッチサイズを大きくするため、キャッシュ済みトークンをすべて削除する。[図 3](#figure-03) は、複数のリクエストが到着する際に基数木を維持する方法を示す。フロントエンドインタプリタが完全なプロンプトをランタイムへ送り、ランタイムがプリフィックスの照合と再利用を行う。木構造は CPU に格納され、維持のオーバーヘッドは無視できる。`fork` プリミティブの実行中、フロントエンドはまずヒントとしてプリフィックスを送り、木へ正しく挿入されるようにする。その後、残りのプロンプトを送る。この「Frontend Hint」はランタイムのスケジューリングと照合を簡素化し、フロントエンドとランタイムを協調設計する利点を示す。

<span id="figure-03"></span>

![LRU 削除ポリシーによる RadixAttention 操作の九段階の例](../../papers/sglang/figure-03.png)

**図 3.** LRU 削除ポリシーを用いた RadixAttention 操作の例を、九つの時点について示す。さまざまなリクエストに応じて基数木が動的に変化する様子を示している。リクエストには、二つのチャットセッション、few-shot 学習クエリのバッチ、self-consistency サンプリングが含まれる。各辺のラベルは部分文字列またはトークン列を表す。ノードの色は状態を表し、緑は新規ノード、青はその時点でアクセスされたキャッシュノード、赤は削除されたノードである。ステップ（1）では、基数木は空である。ステップ（2）では、サーバーがユーザーメッセージ「Hello」を処理し、LLM 出力「Hi」で応答する。System prompt「You are a helpful assistant」、ユーザーメッセージ「Hello!」、LLM 応答「Hi!」は、すべて一つの新しいノードにつながる一本の辺へまとめられる。ステップ（3）では新しいプロンプトが到着し、サーバーはそのプリフィックス（会話の第一ターン）を基数木から見つけ、KV キャッシュを再利用する。新しいターンは新規ノードとして木に追加される。ステップ（4）では新しいチャットセッションが始まる。（3）のノード「b」を二つに分割し、二つのチャットセッションが system prompt を共有できるようにする。ステップ（5）では第二のチャットセッションが続く。しかしメモリ制限のため、（4）のノード「c」を削除しなければならない。新しいターンは（4）のノード「d」の後ろへ追加される。ステップ（6）では、サーバーが few-shot 学習クエリを受け取り、処理して木へ挿入する。新しいクエリは既存ノードとプリフィックスを共有しないため、ルートノードが分割される。ステップ（7）では、サーバーが few-shot 学習クエリをさらに一バッチ受け取る。これらのクエリは同じ few-shot 例を共有するため、（6）のノード「e」を分割して共有を可能にする。ステップ（8）では、サーバーが第一のチャットセッションから新しいメッセージを受け取る。第二のチャットセッションの全ノード（「g」と「h」）は最も長く使われていないため削除される。ステップ（9）では、（8）のノード「j」にある質問について、self-consistency プロンプト用と思われる追加の回答サンプリング要求を受け取る。これらのリクエストの空間を確保するため、（8）のノード「i」、「k」、「l」を削除する。

**キャッシュ認識型スケジューリング。** キャッシュヒット率を $\frac{\text{キャッシュ済みプロンプトトークン数}}{\text{プロンプトトークン数}}$ と定義する。待機キューに多くのリクエストがある場合、その実行順序はキャッシュヒット率に大きく影響する。例えば、リクエストスケジューラが無関係なリクエスト間を頻繁に切り替えると、キャッシュスラッシングが生じ、ヒット率が低下する可能性がある。そこで、ヒット率を高めるキャッシュ認識型スケジューリングアルゴリズムを設計する。バッチ処理設定では、リクエストを一致プリフィックス長でソートし、先着順ではなく、一致プリフィックスの長いリクエストを優先する。[アルゴリズム 1](#algorithm-01)（付録）は、連続バッチ処理を用いたキャッシュ認識型スケジューリングの疑似コードを示す。このアルゴリズムは最長共有プリフィックス優先順を使う。レイテンシにより敏感な設定でも、キャッシュ再利用を改善するため、限定的なバッチ並べ替えを許容できる場合がある。また、オフラインの場合の最適スケジューリングについて次の定理を証明する。[+1]

<span id="theorem-03-01"></span>

**定理 3.1。** リクエストのバッチについて、キャッシュサイズが最大リクエスト長以上なら、リクエストの基数木を深さ優先探索順で訪問することにより、最適なキャッシュヒット率を達成できる。最長共有プリフィックス優先順は深さ優先探索順と等価である。

証明は[付録 A.3](#appendix-a-3) に示す。オンラインの場合、DFS 順は乱されるが、[付録 A.3](#appendix-a-3) で説明するように、本スケジュールは完全な基数木の追加部分で DFS の挙動を近似する。貪欲なキャッシュ認識型スケジューリングは高スループットを達成できる一方、飢餓を招く場合がある。他の公平なスケジューリング手法 [She23b] との統合は今後の課題とする。

**分散の場合。** RadixAttention は複数 GPU へ拡張できる。Tensor parallelism では、各 GPU がシャーディングされた KV キャッシュを維持する。木の操作は同じなので、追加の同期は不要である。複数ワーカーによる data parallelism は[付録 A.4](#appendix-a-4) で論じる。

## 4 圧縮有限状態機械による効率的な制約付きデコーディング

LM プログラムでは、ユーザーがモデル出力を JSON スキーマなど特定の形式に従わせたい場合が多い。これにより制御可能性と堅牢性が向上し、出力も解析しやすくなる。SGLang は `regex` 引数を提供し、多くの実用的な場面に十分な表現力を持つ正規表現によって、このような制約を適用する。既存システムは、正規表現を有限状態機械（FSM）に変換して対応する [Wil23]。デコーディング中は現在の FSM 状態を維持し、次の状態から許可トークンを取得して、無効なトークンの確率をゼロに設定し、一トークンずつデコードする。しかし、一度に複数トークンをデコードできる場合、このトークン単位の方法は非効率である。例えば、[図 2](#figure-02) の定数列 `{"summary": "` は、[図 4](#figure-04)（c）に示す通常のデコーディング過程で複数のトークンにまたがり、デコード時に有効な次トークンが一つしかなくても、複数のデコーディング段階を必要とする。したがって、列全体を一ステップ（すなわち一回の前方パス）でデコードできる。ところが、既存システムでは FSM とモデルランナーが統合されておらず、複数トークンを処理できないため、一度に一トークンしかデコードできず、速度が遅い。

<span id="figure-04"></span>

![通常 FSM と圧縮 FSM のデコーディング過程](../../papers/sglang/figure-04.png)

**図 4.** 通常 FSM と圧縮 FSM のデコーディング過程（下線 `_` は空白を表す）。

SGLang は圧縮 FSM を用いた高速な制約付きデコーディングランタイムを構築し、この制限を克服する。このランタイムは FSM を解析し、[図 4](#figure-04)（b）に示すように、隣接する単一遷移辺を一本の辺に圧縮して、複数のトークンをまとめてデコードできる箇所を認識する。[図 4](#figure-04)（d）では、圧縮遷移辺上の複数トークンを一回の前方パスでデコードでき、デコーディング過程が大幅に高速化される。また汎用的であり、すべての正規表現に適用できる。背景と実装の詳細は[付録 B](#appendix-b) に示す。

## 5 API 投機的実行による効率的なエンドポイント呼び出し

前節までの最適化はオープンウェイトモデルを対象とし、モデル推論過程を変更する必要があった。SGLang は OpenAI の GPT-4 のように API アクセスしか提供されないモデルでも動作する。しかし、この種のモデルではブラックボックスの API エンドポイントしか呼び出せない。

本節では、投機的実行によって複数呼び出し SGLang プログラムの実行を高速化し、API コストを削減する、ブラックボックス API モデル向けの新しい最適化を導入する。例えば、プログラムが `s += context + "name:" + gen("name", stop="\n") + "job:" + gen("job", stop="\n")` という複数呼び出しパターンで、人物の説明を生成するようモデルに依頼するとする。単純に実行すると、二つの `gen` プリミティブは二回の API 呼び出しに対応し、ユーザーは `context` の入力トークン料金を二度支払う必要がある。SGLang では、最初の呼び出しで投機的実行を有効にし、停止条件を無視してさらに数トークン生成させられる。インタプリタは追加の生成出力を保持し、後続のプリミティブと照合して再利用する。慎重にプロンプトを設計すれば、モデルが高い精度でテンプレートに一致し、一回分の API 呼び出しのレイテンシと入力コストを節約できる場合がある。

## 6 評価

さまざまな LLM ワークロードについて SGLang の性能を評価する。続いて、各コンポーネントの有効性を示すため、アブレーション実験とケーススタディを行う。SGLang は PyTorch [Pas19a] で実装し、FlashInfer [Ye24a] と Triton [Til19] のカスタム CUDA カーネルを使用する。

### 6.1 設定

**モデル。** 密な Llama-2 モデル [Tou23a]、疎な mixture of experts である Mixtral モデル [Jia24]、マルチモーダルの LLaVA 画像モデル [Liu23f] および動画モデル [Zha24j]、API モデルの OpenAI GPT-3.5 を評価する。オープンウェイトモデルのパラメータ数は 70 億から 700 億であり、float16 精度を用いる。

**ハードウェア。** 実験の大半は、NVIDIA A10G GPU（24GB）を備える AWS EC2 G5 インスタンスで実行する。7B モデルは一枚の A10G GPU で動かし、より大きいモデルは複数の A10G GPU で tensor parallelism [Sho19] を用いて動かす。追加実験の一部は A100G（80GB）GPU で実行する。

**ベースライン。** SGLang を、それぞれ独自の言語とデフォルトランタイムを持つ高水準プログラミングシステム、および標準的な OpenAI 風 Completion API を用いる低水準推論エンジンの両方と比較する。特に記載がない限り、すべてのシステムが同じ結果を計算するよう、計算結果を変える最適化は有効にしない。ベースラインは次のとおりである。

- Guidance [Gui22] は LLM を制御するための言語である。Guidance v0.1.8 と llama.cpp バックエンドを使用する。
- vLLM [Kwo23] は高スループットの推論エンジンである。vLLM v0.2.5 とデフォルトの API サーバーを使用する [+2]。
- LMQL [Beu23] はクエリ言語である。LMQL v0.7.3 と Hugging Face Transformers バックエンドを使用する。

**ワークロード。** 5-shot MMLU [Hen20] と 20-shot HellaSwag [Zel19] ベンチマークを評価する。MMLU では一トークンをデコードし、HellaSwag では `select` プリミティブを用いて最も確率の高い回答を選ぶ。ReAct エージェント [Yao22b] と生成エージェント [Par23] については、元論文からトレースを抽出して再生する。GSM-8K 問題には Tree-of-thought [Yao23]、ヒント生成には Skeleton-of-thought [Nin24] を用いる。そのほか、branch-solve-merge [Sah23] 技法を用いた LLM 評価器、正規表現でスキーマを指定する JSON デコーディング、各ターンの入力を 256-512 トークンからランダムにサンプリングする 4 ターンのマルチターンチャットを使用する。マルチターンチャット（短）は短い出力（4-8 トークン）、マルチターンチャット（長）は長い出力（256-512 トークン）を意味する。また、公式サンプルの DSPy 検索拡張生成（RAG）パイプライン [Kha23] も用いる。

**指標。** スループットとレイテンシの二つの性能指標を報告する。スループットでは、十分に大きなプログラムインスタンスのバッチを実行して最大スループットを求め、一秒あたりに実行されるプログラムインスタンス数（programs per second、p/s）を比較する。レイテンシでは、バッチ処理を行わず一度に一プログラムを実行し、複数インスタンスの平均レイテンシを報告する。

### 6.2 エンドツーエンド性能

**オープンウェイトモデルの結果。** レイテンシとスループットの結果を[図 5](#figure-05) と[図 6](#figure-06) に示す。SGLang はスループットを最大 $6.4\times$ 改善し、レイテンシを最大 $3.7\times$ 短縮する。これは、KV キャッシュ再利用、単一プログラム内の並列性の利用、高速な制約付きデコーディングによるものである。以下では、各ベンチマークで高速化が得られる理由を説明する。

MMLU では、SGLang は RadixAttention によって 5-shot 例の KV キャッシュを再利用できる。RadixAttention はスループットとレイテンシの両方に効果がある。KV キャッシュを共有すると総メモリ使用量が減り、より大きなバッチサイズを使用できるため、最大スループットが向上する。RadixAttention は prefill の計算も減らし、最初のトークンのレイテンシを短縮する。HellaSwag では、SGLang は few-shot 例と複数選択肢に共通する質問プリフィックスの KV キャッシュを再利用し、二段階の共有を実現する。ReAct エージェントと生成エージェントでは、エージェントテンプレートと過去の呼び出しの KV キャッシュを再利用する。Tree-of-thought と Skeleton-of-thought では、単一プログラム内の生成呼び出しを並列化し、KV キャッシュを可能な限り再利用する。JSON デコーディングでは、圧縮有限状態機械を用いて一度に複数トークンをデコードし、処理を高速化する。マルチターンチャットでは、チャット履歴の KV キャッシュを再利用する。KV キャッシュ再利用は主にプリフィックス時間を短縮するため、短い出力ほど高速化が目立つ。長い出力では、異なるチャットセッション間の共有が少なく、デコーディング時間が支配的なので、ほとんど高速化されない。DSPy RAG パイプラインでは、共通のコンテキスト例の KV キャッシュを再利用する。これらのベンチマークにおけるキャッシュヒット率は 50%-99% である。[図 13](#figure-13)（付録）に実際のヒット率と最適ヒット率を示す。本稿のキャッシュ認識型スケジューリングは、平均で最適ヒット率の 96% に達する。

最後の五つのベンチマークの一部では、性能が遅く機能も不足しているため、LMQL と Guidance を除外する。LMQL の問題は遅いトークン単位処理と未最適化のバックエンドにあり、Guidance はバッチ処理と並列性をサポートしない。

### 6.3 アブレーション実験

**キャッシュヒット率とレイテンシ／スループット。** [図 8](#figure-08)（a）（b）は、tree-of-thought ベンチマークにおけるキャッシュヒット率と性能指標（最初のトークンのレイテンシ、総レイテンシ、バッチサイズ、スループット）の関係を示す。この図は、ランタイムで一致トークンの一部を無効にして得た。キャッシュヒット率が高いほど、バッチサイズとスループットは大きくなり、レイテンシは短くなる。

**RadixAttention の有効性。** 複数の代表的なベンチマークで RadixAttention と各コンポーネントの有効性を評価する。[図 8](#figure-08)（c）の「No Cache」はキャッシュを使用しないこと、「No Tree-Structure」は木構造キャッシュではなく単純な表ベースキャッシュを使用すること、「FCFS Schedule」は本稿のキャッシュ認識型スケジューリングではなく先着順ポリシーを使用すること、「Random Schedule」はリクエストをランダムな順序でスケジュールすること、「No Frontend Parallelism」はインタプリタの並列性を無効にすること、「No Frontend Hint」はインタプリタから fork ヒントを送らないこと、「Full optimizations」はすべての最適化を有効にすることを意味する。実験結果は、最高の性能を得るには各コンポーネントが必要であることを示す。フロントエンドインタプリタの並列性とヒントを無効にしてもランタイム性能は最適でなくなり、フロントエンド言語とランタイムを協調設計する重要性が分かる。

**圧縮有限状態機械の有効性。** JSON デコーディングベンチマークで、圧縮有限状態機械と各コンポーネントの有効性を評価する。実験では、一度に複数トークンをデコードできるため、圧縮有限状態機械がスループットを $1.6\times$ 向上させることが分かった。また、状態機械を前処理し、その結果を一バッチのリクエストで再利用する必要がある。リクエストごとに前処理をやり直すと、スループットは $2.4\times$ 低下する。

## 7 関連研究

KV キャッシュの再利用についてはさまざまな研究があり、その多くは本研究と同時期に行われた。RadixAttention は、KV キャッシュを木ベースの LRU キャッシュとして扱うことを初めて提案した点で独自である。多段階共有、キャッシュ認識型スケジューリング、フロントエンドとランタイムの協調スケジューリング、分散の場合をサポートする最初の手法である。

vLLM [Kwo23] と ChunkedAttention [Ye24] は system prompt の共有など単純な再利用を扱うが、多段階の木構造共有や LRU キャッシュには対応しない。PromptCache [Gim24] はプリフィックスを越えたモジュール型 KV キャッシュ再利用を提案するが、精度が最大 43% 低下する可能性がある。HydraGen [Jur24]、FlashInfer [Ye24a]、ChunkedAttention [Ye24] は CUDA カーネル最適化を重視し、LRU キャッシュの概念を含まない。API Serve [Abh24] と LLM-SQL [Liu24o] は、外部 API 呼び出しやリレーショナルデータベースとのインターリーブなど、特定アプリケーション向けの KV キャッシュ再利用を研究するが、本稿の基数木やキャッシュ認識型スケジューリングは備えていない。

Guidance [Gui22]、LMQL [Beu23]、DSPy [Kha23]、LangChain [Lan22]、AutoGen [Wu23]、LLM Compiler [Kim23] など、LLM プログラミングおよびエージェントフレームワークも複数存在する。Guidance と LMQL は SGLang に最も近く、[第 2 節](#section-02) で比較した。本稿の新規性は、提案するプログラミングモデルを高速化する新しいランタイム最適化にある。SGLang はほかのフレームワークと互換性があり、それらを高速化できる（評価における DSPy の例など）。SGLang は、ほかの一般的な多くの推論最適化にも対応する [Yu22a, Pop22, Ami22, Kwo23, Ye24a, Dao22, Lin24, Hoo24, Kan24, Liu24c, Liu24p, Ge24]。

## 8 今後の方向性と結論

**今後の方向性。** SGLang は進展を遂げたが、今後の研究につながる制限がいくつか残っている。これには、SGLang を追加の出力モダリティへ対応させること、RadixAttention を複数段階のメモリ階層（DRAM、Disk など）で動作させること [She23]、RadixAttention で曖昧な意味照合を可能にすること、SGLang 上に高水準プリミティブを提供すること、キャッシュ認識型スケジューリングの飢餓を解消すること [She23b]、スケジューリングやメモリ計画など高度な静的最適化を実行できるよう SGLang コンパイラを強化することが含まれる。

**結論。** 本稿では、構造化言語モデルプログラムを効率よくプログラミングし、実行するためのフレームワーク SGLang を導入した。SGLang は、RadixAttention、圧縮有限状態機械、言語インタプリタなどの新しい最適化により、複雑な LM プログラムのスループットとレイテンシを大幅に改善する。高度なプロンプト技法やエージェントワークフローを開発するために有用なツールである。ソースコードは公開されている。

### A.1 KV キャッシュの背景

現在利用されている LLM の大半は、GPT-3 [Bro20b]、PaLM [Cho22b]、LLaMA [Tou23a] など、自回帰 Transformer アーキテクチャ [Vas17] に基づいている。これらのモデルは、先行するトークンに基づいて、系列内の次のトークンの確率を予測する。推論時、モデルはまず一連の入力トークンを一回の forward pass で処理する（この処理を「prefill」と呼ぶ）。続いて出力トークンを逐次デコードし、各トークンはそれ以前のトークンに依存する（この処理を「decoding」と呼ぶ）。一連の入力トークンを受け取り、一連の出力トークンを生成する処理を、一回の生成呼び出しと呼ぶ。この処理を通じて各トークンはいくつかの中間テンソルを生成し、それらは後続トークンのデコードに使われる。これらの中間テンソルは「KV Cache」と呼ばれ、その名は self-attention 機構の key-value ペアに由来する。本稿の最適化を論じるうえで重要なのは、KV キャッシュの計算がそれ以前のすべてのトークンにのみ依存するため、同じプリフィックスを持つ異なる系列は、プリフィックストークンの KV キャッシュを再利用して冗長な計算を避けられるという点である。

LM プログラムでは、複数のテキスト断片と生成呼び出しを一つのプロンプトへ追加することが多い。連鎖した複数の呼び出しにわたり、先行トークンについて計算済みの KV キャッシュを保存すれば、冗長な計算を減らせる。ただし、この最適化には追加のストレージとより複雑なメモリ管理が必要であり、無償でも容易でもない。また LM プログラムでは、一つのプロンプトから複数の出力を生成したり、現在の状態から新しいプロンプトを fork したりすることも一般的である [Li22]。基本的なプリフィックス共有は vLLM [Kwo23] で研究されている。不規則な木構造共有など、より高度な共有パターンも利用できる。[図 9](#figure-09) は、複数の呼び出しにまたがる KV キャッシュ共有の代表的な四パターンを示すが、既存システムのうち、すべてを自動的に処理できるものはない。これに対し、[第 3 節](#section-03) の RadixAttention は、実行時にすべてを自動処理できる。

**アルゴリズム 1：Continuous batching を用いた RadixAttention のキャッシュ認識型スケジューリング。**

- **入力：** 基数木 $T$、メモリプール $P$、現在実行中のバッチ $B$、待機キュー $Q$。
- **出力：** 完了したリクエストと更新後のシステム状態。
- **待機キューからすべてのリクエストを取得：**
  - $\mathrm{requests}\leftarrow Q.\text{get\_all\_requests}()$ とする。
- **すべての待機リクエストについて一致するプリフィックスを探索：**
  - **各** $\mathrm{req}\in\mathrm{requests}$ **について：**
    - $\mathrm{req.prefix\_node}, \mathrm{req.prefix\_len}\leftarrow T.\text{match\_prefix}(\mathrm{req.input\_tokens})$ とする。
- **一致したプリフィックスの長さに従ってリクエストをソート：**
  - $\mathrm{requests}$ をソートする。
- **次のバッチに入れるリクエストを選択：**
  - $\mathrm{available\_size}\leftarrow T.\text{evictable\_size}()+P.\text{available\_size}()$ とする。
  - $\mathrm{current\_size}\leftarrow 0$ とする。
  - $\mathrm{new\_batch}\leftarrow []$ とする。
  - **各** $\mathrm{req}\in\mathrm{requests}$ **について：**
    - **もし** $\mathrm{req}.\text{size}()+\mathrm{current\_size}<\mathrm{available\_size}$ **なら：**
      - $\mathrm{req}$ を $\mathrm{new\_batch}$ へ追加する。
      - $\mathrm{delta}\leftarrow T.\text{increase\_ref\_counter}(\mathrm{req.prefix\_node})$ とする。
      - $\mathrm{available\_size}\leftarrow\mathrm{available\_size}+\mathrm{delta}$ とする。
  - $\mathrm{new\_batch}$ 内のリクエストを $Q$ から削除する。
- **リクエストを現在実行中のバッチへ挿入：**
  - $\mathrm{new\_batch}$ を $B$ へマージする。
- **新しいメモリを割り当て、必要なら削除を実行：**
  - $\mathrm{needed\_size}\leftarrow B.\text{needed\_size}()$ とする。
  - $\mathrm{success}, \mathrm{buffer}\leftarrow P.\text{alloc}(\mathrm{needed\_size})$ とする。
  - **もし** `not success` **なら：**
    - $T$ から $\mathrm{needed\_size}$ を削除する。
    - $\mathrm{success}, \mathrm{buffer}\leftarrow P.\text{alloc}(\mathrm{needed\_size})$ とする。
  - $\mathrm{buffer}$ を用いて $B$ を実行する。
- **完了したリクエストを処理：**
  - $\mathrm{finished\_requests}\leftarrow B.\text{drop\_finished\_requests}()$ とする。
  - **各** $\mathrm{req}\in\mathrm{finished\_requests}$ **について：**
    - $T$ にある $\mathrm{req.prefix\_node}$ の参照カウンタを減らす。
    - $\mathrm{req}$ を $T$ へ挿入する。
- **返り値：** $\mathrm{finished\_requests}$。

### A.2 キャッシュ認識型スケジューリングの疑似コード

[アルゴリズム 1](#algorithm-01) は、continuous batching を用いる RadixAttention のキャッシュ認識型スケジューリングの疑似コードを示す。

<span id="appendix-a-3"></span>

### A.3 [定理 3.1](#theorem-03-01) の証明

**定理 3.1。** リクエストのバッチについて、キャッシュサイズが最大リクエスト長以上なら、リクエストの基数木を深さ優先探索順で訪問することにより、最適なキャッシュヒット率を達成できる。最長共有プリフィックス優先順は深さ優先探索順と等価である。

::: details 証明
まず、深さ優先探索（DFS）順が最適なキャッシュヒット率を達成することを示す。$R$ をバッチ内のリクエスト集合、$T$ を $R$ から構築した基数木とする。$T$ の各辺 $e$ について、$e$ に対応する KV キャッシュは少なくとも一度計算しなければならない。$|e|$ を $e$ に対応する KV キャッシュのサイズとする。$C$ を $R$ に対する KV キャッシュの計算量とする。次の下界を得る。

$$
C \geq \sum_{e\in\text{edges}(T)}|e|.
$$

基数木 $T$ を DFS 順で訪問するとする。$T$ の各辺 $e$ について、$e$ に対応する KV キャッシュを初めて計算した後は、$e$ の部分木全体を計算する。$e$ の部分木を計算している間、辺 $e$ は継続してヒットするため、追加の計算は発生しない。$e$ を根とする部分木の計算が完了すると、辺 $e$ は再び訪問されない。キャッシュサイズが基数木 $T$ の最長経路に等しい最大リクエスト長以上である場合、部分木の $e$ を含む共通プリフィックスは継続してヒットするため、辺 $e$ はその部分木の計算中に削除されない。したがって、各辺 $e$ に対応する KV キャッシュは一度だけ計算される。よって、下界を達成する。

$$
C = \sum_{e\in\text{edges}(T)}|e|.
$$

キャッシュヒット率を

$$
\frac{\sum_{r\in R}\text{number of cached prefill tokens in }r}{\sum_{r\in R}\text{number of prefill tokens in }r},
$$

と定義すると、これは $1-\frac{C}{\sum_{r\in R}\text{number of prefill tokens}}$ に等しく、その上界に達するため、最適性が得られる。

次に、最長共有プリフィックス優先順が DFS 順と等価であることを帰納法で示す。

- **基底：** はじめは何もキャッシュされていないため、$T$ のノード $x$ に対応する任意のリクエストが処理される。根から $x$ までの経路上のノード $\{v_1,\ldots,v_n\}$ に対応するすべてのリクエストは、再計算を必要としない。ノード $\{v_1,\ldots,v_n,x\}$ に対応するリクエストの計算量は、有効な DFS と一致する。根から $x$ までの経路がキャッシュされる。
- **帰納：** $T$ のノード $y$ を直前に訪問し、訪問済みノードが DFS 順と一致していると仮定する。$P$ を根から $y$ までの経路とする。このとき、未訪問の各ノードと訪問済みノードとの lowest common ancestor は $P$ 上にある。$P$ 上のノードはキャッシュされているため、$P$ 上に lowest common ancestor を持つ未訪問ノード $z$ が最長の共有プリフィックスを持つ。最長共有プリフィックス優先順は $z$ を選択し、これは有効な DFS 順となる。根から $z$ までの経路は最新の経路なのでキャッシュされる。

:::

オンラインの場合、DFS 順は崩れるが、最長共有プリフィックスによるスケジューリングは、暗黙の基数木で拡張された部分における DFS の動作を近似する。新しいリクエストバッチを追加するステップを考えることで、これを示す。

$T$ をこれまでに訪問した基数木の部分、$T'$ を新しいリクエストバッチの追加後に得られる新しい基数木全体とする。$C$ を $T$ 内のキャッシュ済みノード集合とする。$\text{longest}(C)$ を、根からの経路が最長であり、かつ $T'$ 内にまだ完全には訪問されていない部分木を持つ $C$ 内のノードとする。

最長共有プリフィックスによるスケジューリングは、$\text{longest}(C)$ を根とする $T'$ 内の部分木を DFS 順で処理する。この処理中に削除が生じる可能性があり、$C$ に残るキャッシュ済みノードは $C^{(1)}\subseteq C$ となる。続いて、$\text{longest}(C^{(1)})$ を根とする $T'$ 内の部分木について DFS が行われる。

同様に $C^{(2)},\ldots,C^{(k)}$ が得られ、最終的に $C^{(k)}$ は、その $T'$ 内の部分木が完全には訪問されていない葉ノードを一つだけ含む。この時点で、有効な DFS の状態へ到達している。$T'$ の残りの部分は、[定理 3.1](#theorem-03-01) の証明で説明したとおり DFS 順で訪問される。

### A.4 データ並列分散 RadixAttention

RadixAttention を複数のレプリカワーカー（すなわちデータ並列）のある分散環境へ適用するため、各ワーカーが自身の部分木を保持し、ルーターがメタ木を管理する機構を開発した。このメタ木は、すべての部分木と対応デバイスを追跡する trie として機能する。新しいリクエストバッチがルーターへ到着すると、メタ木上でプリフィックスマッチングを実行する。特定のワーカーおよび同一グループ内の他リクエストとの共有プリフィックス長によって測る各リクエストの affinity に基づき、冗長な計算を最小限にする効率的な振り分けを行うため、さまざまなポリシーを実装する。新しいリクエストが処理されるたびに、ルーターとワーカーはそれぞれの木を独立して更新する。ワーカーノードで削除が発生した場合、その削除をキューへ記録し、ルーターは低負荷時にキューを処理してメタ木を更新する。この分散構成を四つのワーカーと MMLU データセットで評価したところ、この弱整合分散キャッシュ設計によるオーバーヘッドは小さく、線形スケーリングと最適なキャッシュヒット率を達成した。データ局所性の最大化と並列処理効率の間にはトレードオフがある。このトレードオフを最適化する高度なスケジューリングポリシーの検討は今後の研究課題である。また、並行研究の Preble [Sri24] は、SGLang の初期版に基づくデータ並列スケジューリングを研究している。

## 付録 B 圧縮有限状態機械の追加詳細

本節では、制約付きデコーディングを高速化する圧縮有限状態機械の背景と実装詳細を述べる。LLM に正規表現（regex）へ従わせることを目指す。正規表現は表現力が高く、JSON schema など一般的な形式を表現できる。そのため、正規表現を有限状態機械（FSM）へ変換し、デコーディング中の生成過程を導く [Wil23]。FSM は基本的に、ノード（状態）とエッジ（文字列／文字を伴う遷移）からなるグラフである。初期状態から始まり、遷移のたびにエッジ上の文字列を追加して次の状態へ移り、終端状態の集合によって処理を終了する。この機構は、[図 10](#figure-10) に示すように、FSM の現在状態からの遷移に基づいて無効なトークンを除外し、LLM のデコーディングを導く。デコーディングでは、終端状態に達するまで FSM 内で複数回遷移する場合がある。

<span id="figure-10"></span>

![正規表現から FSM への変換と、それによるデコーディングの誘導](../../papers/sglang/figure-10.png)

**図 10.** 正規表現を FSM へ変換し、FSM がデコーディング過程を導く方法の例。

制約付きデコーディングが難しいのは、制約が自然言語の形式で表されることが多いからである。すなわち、正規表現は文字／文字列で記述される一方、LLM はそれらをトークンとして解釈し処理するよう設計されている。文字列とトークンの対応は複雑で一対一ではないため、扱いが難しくなる [Kuc23]。

本節は以前のブログ記事 [+3] に基づいている。背景をさらに知り、より容易に理解するため、ブログ記事も参照されたい。

### B.1 圧縮有限状態機械の実装詳細

圧縮 FSM の構築を単純化するため、元の FSM はトークンではなく文字／文字列上に構築する。singular transition edge と compressed edge の概念を、次のように形式的に定義する。

- **Singular transition edge：** あるエッジについて、1）始点ノードの後続ノードが一つだけであり、2）受理可能な文字／文字列が一つだけである場合、そのエッジを singular transition edge とする。
- **Compressed edge：** 連続して隣接する複数のエッジ $(e_0,e_1,\ldots,e_k)$ によって圧縮されたエッジは、$e_1,\ldots,e_k$ が singular transition edge である場合、かつその場合に限り compressed edge である。compressed edge のテキストは、$e_0,e_1,\ldots,e_k$ のテキストを連結したものである。

文字に基づく FSM から始め、singular transition edge をそれ以上圧縮できなくなるまで、その直前のエッジへ再帰的にマージすることで、圧縮 FSM が得られる。この方法はデコーディング過程を高速化する。[図 11](#figure-11) は、圧縮 FSM を用いる SGLang ランタイムの効率を示す。

### B.2 再トークン化によるトークン化アーティファクトへの対応

新しいトークンが生成されると、そのトークンの文字列を取得し、現在状態から出るすべてのエッジを探索して、デコード直後の文字列で始まるエッジを見つけ、その先へ進む。ただし、遷移エッジが十分に圧縮され、非常に長い文字列を含む場合は、後続ラウンドでデコードされる文字列も予測できる。ここで高速化が生じ、この処理を *Jump Forward* と呼ぶ。しかし、後続のデコーディング段階に備えて文字列をトークンへ変換する必要があり、LLM 固有の事前学習法とトークン化法のため、これは単純ではない。直接分割すると、意図した意味が変わる可能性がある [Tra24]。例えば、[図 2](#figure-02) の正規表現で圧縮されたテキストは `{"summary": "` であり、tokenizer に従えば `{"`、`summary`、`":`、`_"` とだけトークン化できる。`{"`、`summa`、`ry`、`":_` のように任意に分割することはできない。この問題に対処するため、元の tokenizer を用いて、それまでの全テキストと圧縮エッジのテキストを再トークン化し、LLM の元の入力形式との整合性を保つ。これによる再トークン化のオーバーヘッドはわずかである。

<span id="appendix-b-3"></span>

### B.3 今後の拡張：歪んだ確率への対応

文字列とトークンの隔たりによる課題は、確率分布の偏りも生じさせる [Tra24]。例えば、[図 2](#figure-02) の正規表現 `"[ABCD][+-]?"` は `A+` から `D-` までの成績を表す。しかし、これを `Excellent|Above Average|Fair|Below Average` などの広い表現へ置き換えると、`Above Average` が圧縮遷移上にあるため、ランタイムが `A` を `Above Average` へ誤って対応づけ、成績の序列を誤って表現する可能性がある。これは LLM が具体的な選択肢の範囲を認識せず、不適切なトークン系列を生成するために起こる。各選択肢の正確な確率を計算するには、その選択肢を生じさせるすべてのトークン系列の確率を合計する必要があり、デコーディングが複雑になり、オーバーヘッドも増える。一つの回避策は、選択肢または正規表現を prefill prompt に直接含め、LLM に選択肢を認識させ、適切なトークン系列で決定を出力するよう導くことである。しかし、この方法は確率の歪みという根本的な問題を解決しないため、圧縮 FSM の精度向上にはさらなる研究が必要である。

## 付録 D コンパイラモード

本文で用いたインタプリタモードに加え、SGLang プログラムを計算グラフとしてコンパイルし、グラフ実行器で実行する方法もある。グラフを書き換え、より多くの静的計画を実行できるため、コンパイル最適化の機会が広がる。

<span id="appendix-d-1"></span>

### D.1 設計と実装

SGLang の中間表現（IR）を設計し、SGLang プログラムの構造と操作を計算グラフとして表現する。このグラフには、プリミティブ演算子のノードと依存関係のエッジが含まれる。[図 14b](#figure-14) に、[図 14a](#figure-14) のプログラムに対応するグラフを示す。このプログラムでは、装飾された関数の呼び出しまたは fork のたびに、新しいプロンプト状態またはストリームが作成される。

ノードには複数の種類がある。SGLang プログラムにおける演算子 `+=` と `+` の各オペランドは、IR ノードとして表現される。これには `ConstantText`、`Argument`、`Gen`、`Select`、`Variable`、`Fork`、`GetForkItem`、`Join` がある。依存関係には二種類ある。ストリーム内依存では、`+=` を用いてストリームへ投入された操作を、そのストリーム内の先行するすべての操作の後に実行しなければならない。ストリーム間依存は、あるストリームが別のストリームから変数値を取得する必要があり、同期を要するときに発生する。fork などの操作は複数のストリームを操作するため、ストリーム間依存を生じさせる。

グラフを生成するため、抽象引数でプログラムを実行する tracing を用い、グラフを動的に構築する。この方法はデータ依存制御フローを持たないプログラムに限られる。この制限には今後対処する予定である。構築したグラフはグラフ実行器で実行できるため、元の Python プログラムを再解釈する必要がない。これにより、グラフ書き換えによる最適化、ランタイムオーバーヘッドの削減、プログラムのシリアライズが可能になる。実行時にはデータストリームごとにストリーム実行器を起動し、IR ノードをトポロジカル順にストリームへ振り分ける。

<span id="appendix-d-2"></span>

### D.2 コンパイラ最適化のケーススタディ：プリフィックス共有を改善するコード移動

SGLang IR のコンパイル最適化として、プリフィックス共有を改善するコード移動を検討する。auto-tuning や命令選択など、より多くの古典的コンパイラ技法も適用できると考えている。

この最適化は、グラフ内のノードを並べ替えて定数プリフィックスを長くすることで、プリフィックス共有を改善する。元の計算を厳密には保存しないため、積極的な最適化に分類される。例えば、プロンプトを「Here is a question + {question}. Please act as a math expert and solve the given question.」から「Please act as a math expert and solve the given question. Here is a question + {question}.」へ変更すると、共有可能なプリフィックスが長くなる。この最適化が興味深いのは、SGLang に自然言語命令が含まれるため、従来のプログラム解析では実現できない点である。代わりに、GPT-4 にグラフノードの並べ替えを指示する。SGLang IR の概念を GPT-4 に教えるため、複数の例を含むプロンプトを作成したところ、GPT-4 は一部の単純な SGLang プログラムへこの最適化を適用できた。

この最適化の有効性を評価する。インターネットから 20 個のプロンプトテンプレートを収集し、SGLang で実装する。このうち 5 個を few-shot 学習例、残りの 15 個をテストケースとして用いる。評価の結果、15 個中 12 個のテンプレートで、GPT-4 は意味を変えずにグラフノードを並べ替えることに成功した。これは変更後のプロンプトを手作業で確認した。平均すると、この最適化によって共有可能なプリフィックス長が 60 トークン増加し、GPT-4 の有効性が示された。最適化されたプロンプト順序を作れなかったのは、グラフノードが表す意味を誤って理解したためである。元の意味が変わる場合でもすべての定数を前へ移すなど、最適化が積極的すぎる。本ケーススタディは、コンパイラ最適化への GPT-4 の利用を検討するものである。この種の最適化を将来信頼できるものにするには、さらに研究が必要である。
