## 概要

本稿では、Vibe Coding からエージェント型エンジニアリングへのパラダイム移行を目指して設計された次世代基盤モデル GLM-5 を提案します。GLM-5 は、前世代モデルのエージェント、推論、コーディング（ARC）能力を基礎に DSA を採用し、長いコンテキストの忠実性を維持しながら、学習と推論のコストを大幅に削減します。モデルのアラインメントと自律性を高めるため、生成と学習を分離して後学習の効率を飛躍的に向上させる、新たな非同期強化学習基盤を実装しました。さらに、強化学習の品質を高める新しい非同期エージェント RL アルゴリズムを提案し、複雑で長期にわたるインタラクションからモデルがより効果的に学習できるようにしました。これらの革新により、GLM-5 は主要な公開ベンチマークで最先端の性能を達成しています。とりわけ重要なのは、実世界のコーディングタスクで前例のない能力を示し、エンドツーエンドのソフトウェアエンジニアリング課題において従来のベースラインを上回ったことです。コード、モデル、その他の情報は [https://github.com/zai-org/GLM-5](https://github.com/zai-org/GLM-5) で公開しています。

## 1 はじめに

汎用人工知能（AGI）の実現には、モデルパラメータを増やすだけでなく、知能の効率と自律的改善のアーキテクチャを根本から見直す必要があります。GLM-4.5 では、エージェント、推論、コーディング（ARC）能力を単一の Mixture-of-Experts（MoE）アーキテクチャに統合することで、多様なベンチマークにおいて最先端の結果を得られることを示しました。しかし、大規模言語モデル（LLM）が受動的な知識リポジトリから能動的な問題解決者へと移行するにつれ、計算コストと実世界への適応性、特に複雑なソフトウェアエンジニアリングへの適応性という二つの課題が主要なボトルネックになっています。

これらの障壁を克服するため、次世代フラッグシップモデル GLM-5 を提案します。GLM-5 は性能と効率の双方でパラダイムシフトを実現し、ArtificialAnalysis.ai、LMArena Text、LMArena Code など、主要な公開リーダーボードで最先端に到達しました。さらに重要なことに、GLM-5 は実世界のコーディングに新たな基準を打ち立て、SWE-bench のような従来の静的ベンチマークの範囲を大きく超える、複雑なエンドツーエンドのソフトウェア開発タスクを処理する卓越した能力を示しています。

**手法。**

図 5 に GLM-5 の学習パイプライン全体を示します。ベースモデルの学習は、コードと推論を早期から重視した 27 兆トークンの大規模コーパスから始まります。次に、独立した中間学習フェーズを設け、コンテキスト長を 4K から 200K へ段階的に拡張しました。特に長いコンテキストを持つエージェントデータに注力し、複雑なワークフローでの安定性を確保しています。後学習では標準的な SFT にとどまらず、推論 RL、エージェント RL、汎用 RL の順に進む強化学習パイプラインを採用しました。重要なのは、全工程でオンポリシーのステージ間蒸留を用いて破滅的忘却を防ぎ、堅牢な汎用モデルへ移行しながら鋭い推論能力を維持したことです。GLM-5 の性能向上を支える技術的貢献は、次のとおりです。

第一に、学習と推論のコストを大幅に削減する新しいアーキテクチャである DSA（DeepSeek Sparse Attention）[Dee25a] を採用しました。GLM-4.5 は標準的な MoE アーキテクチャで効率を高めましたが、DSA はトークンの重要度に応じて注意資源を動的に配分します。これにより、長いコンテキストの理解や推論の深さを損なうことなく、計算オーバーヘッドを大幅に削減できます。DSA により、モデルを 744B パラメータまで拡大し、学習トークン予算を 28.5T トークンに増やしました。

第二に、新しい非同期強化学習基盤を構築しました。GLM-4.5 で導入した slime フレームワークと分離型ロールアウトエンジンを土台に、生成と学習をさらに分離して GPU 使用率を最大化します。従来は反復速度を妨げていた同期ボトルネックを回避し、エージェント軌跡を大規模に探索できるため、RL 後学習パイプラインの効率が大きく向上します。

第三に、自律的な意思決定の品質を高める、新しい非同期エージェント RL アルゴリズムを提案します。GLM-4.5 では、反復的自己蒸留と結果監督によってエージェントを学習しました。GLM-5 では、多様で長期にわたるインタラクションから継続的に学べる非同期アルゴリズムを開発しました。動的環境における計画と自己修正能力を高めるよう最適化されており、実世界のコーディングシナリオにおける優れた性能に直接つながっています。

最後に、GLM-5 は開発初日から中国の GPU エコシステムにフルスタックで対応しています。Huawei Ascend、Moore Threads、Hygon、Cambricon、Kunlunxin、MetaX、Enflame という国内主要 7 チッププラットフォームにおいて、基盤カーネルから上位の推論フレームワークまで一貫した最適化を完了しました。

これらの進歩により、GLM-5 は単に高性能なモデルにとどまらず、次世代 AI エージェントのための、より効率的で実用的な基盤となります。効率的なエージェント型汎用知能の最前線をさらに前進させるため、GLM-5 をコミュニティに公開します。

## 2 事前学習

GLM-4.5 と同様に、GLM-5 のベースモデルは、汎用言語・コーディング能力のための事前学習と、エージェント・長文脈能力のための中間学習という二段階を経ます。GLM-5 の全学習段階でトークン予算を拡大し、ベースモデル全体では 28.5 兆トークンを使用します。

### 2.1 アーキテクチャ

**モデルサイズのスケーリング。**

GLM-5 はエキスパート数を 256 に増やし、エキスパート並列通信のオーバーヘッドを抑えるため、層数を 80 に減らしています。その結果、総パラメータ数 744B、アクティブパラメータ数 40B のモデルとなりました。総パラメータ数 355B、アクティブパラメータ数 32B の GLM-4.5 と比べると、総サイズは 2 倍です。

![GLM-5 表 1](../../papers/glm-5/table-01.png)

**表 1.** GQA-8 と MLA の各変種における評価結果。

**Multi-latent Attention。**

縮小したキー・値ベクトルを使用する Multi-latent Attention（MLA）[Dee24] は、Grouped-Query Attention（GQA）と同等の有効性を保ちながら、長いコンテキスト系列に対して GPU メモリ使用量を抑え、処理を高速化します。

しかし Muon オプティマイザを使用した実験では、576 次元の潜在 KV キャッシュを持つ MLA は、8 クエリグループの GQA（GQA-8、2048 次元 KV キャッシュ）に性能が及びませんでした。この差を解消するため、GLM-4.5 の Muon オプティマイザレシピを変更しました。従来は、マルチヘッドのクエリ、キー、値に対する上方射影行列 $W^{UQ},W^{UK},W^{UV}$ に行列直交化を適用していました。代わりに、これらの行列をヘッドごとの小さな行列に分割し、それぞれ独立に行列直交化します。Muon Split と呼ぶこの手法により、異なるアテンションヘッドの射影重みを異なるスケールで更新できます。表 1 に示すように、MLA の性能は効果的に改善され、GQA-8 に並びます。実際、Muon Split を用いると、GLM-5 のアテンションロジットのスケールは、クリッピング戦略を使わなくても事前学習中に安定することも確認しました。

MLA には、デコード時の計算コストが高いという欠点もあります。デコードでは MLA が 576 次元の内積を実行するのに対し、GQA は 128 次元です。DeepSeek-V3 のアテンションヘッド数は H800 の roofline に合わせて選択されていますが [Zha25b]、他のハードウェアには適しません。学習とプリフィルでは MLA が Multi-head Attention（MHA）形式を取ることを踏まえ、ヘッド次元を 192 から 256 に増やし、アテンションヘッド数を 3 分の 1 減らしました。学習時の計算量とパラメータ数を一定に保ちながら、デコード計算を削減できます。表 1 の MLA-256 は、Muon Split のもとで MLA と同等の性能を示します。

![GLM-5 表 2](../../papers/glm-5/table-02.png)

**表 2.** DeepSeek-V3.2 と GLM-5 の受理長の比較。

**パラメータ共有を用いた Multi-token Prediction。**

Multi-token Prediction（MTP）[Glo24, Dee24a] はベースモデルの性能を高め、推測デコーディングのドラフトモデルとしても機能します [Lev23]。ただし学習時に次の $n$ トークンを予測するには、$n$ 個の MTP 層が必要です。そのため、MTP パラメータと KV キャッシュのメモリ使用量は推測ステップ数に比例します。DeepSeek-V3 は 1 層の MTP だけで学習し、推論時には次の 2 トークンを予測しますが、学習と推論の不一致により 2 番目のトークンの採択率が低下します。そこで、学習時に 3 つの MTP 層でパラメータを共有する方法を提案します。ドラフトモデルのメモリコストを DeepSeek-V3 と同じに保ちながら、採択率を高められます。表 2 に示すように、非公開プロンプトセットで推測ステップ数を同じ 4 にした場合、GLM-5 の受理長は DeepSeek-V3.2 より長くなります。

#### 2.1.1 DeepSeek Sparse Attention（DSA）による継続事前学習

![GLM-5 表 3](../../papers/glm-5/table-03.png)

**表 3.** MLA と DSA のベースモデルにおける長文脈ベンチマークの比較。

学習には DSA を使用します。DSA [Dee25a] の中心的な考え方は、$128\text{K}$ のコンテキストでは計算量が極めて大きくなる従来の密な $O(L^{2})$ アテンションを、動的かつ細粒度の選択機構に置き換えることです。スライディングウィンドウのような固定パターンとは異なり、DSA は内容を参照して重要なトークンを判断します。研究上とりわけ興味深いのは、密なベースモデルからの継続事前学習によって導入された点です。ゼロから学習する莫大なコストを回避し、「密なウォームアップ」と「疎な学習への適応」という二段階で移行します。DeepSeek-V3.2-Exp は密な前世代モデルと同じベンチマーク性能を維持し、長いコンテキストのアテンションエントリの 90% が実際に冗長であることを示しました。DSA は長い系列のアテンション計算を約 1.5～2 倍削減します。これは推論負荷の高いエージェントにとって重要であり、128K のコンテキストを半分の GPU コストで処理できます。

![MLA と DSA の SFT 損失曲線](../../papers/glm-5/figure-06.png)

**図 6.** MLA と DSA の学習における SFT 損失曲線の比較。ウィンドウサイズ 50 の移動平均で平滑化しています。

DSA の学習は、中間学習終了時のベースモデルから開始します。ウォームアップ段階は 1000 ステップで、各ステップでは 202,752 トークンの系列を 14 本学習し、最大学習率は 5e-3 です。続く疎適応段階では、中間学習と同じデータおよびハイパーパラメータを使用し、20B トークンを学習します。学習予算は DeepSeek-V3.2 の 943.7B トークンより大幅に少ないものの、元の MLA モデルと同等の性能へ DSA モデルを適応させるには十分でした。表 3 に示すように、DSA モデルの長文脈性能は MLA モデルに近い値です。DSA 学習の有効性をさらに検証するため、DSA と MLA を同じ SFT データでそれぞれファインチューニングしたところ、学習損失と評価ベンチマークの双方で同等でした。

#### 2.1.2 効率的なアテンション変種のアブレーション評価

DSA [Dee25a] に加えて、GLM-9B を用いて複数の効率的なアテンション機構を検討しました。GLM-9B は GLM-4 シリーズの一つで、[https://github.com/zai-org/GLM-4](https://github.com/zai-org/GLM-4) から入手できます。ベースラインは全 40 層でグループクエリアテンションを使用し、128K トークンのコンテキストウィンドウでファインチューニングされています。次の手法を評価します。

- Sliding Window Attention（SWA）Interleave：全アテンション層とウィンドウ化アテンション層を固定的に交互配置し、ネットワーク全体に一律適用する方式。
- Gated DeltaNet（GDN）[Yan25]：二次計算量の softmax アテンションをゲート付き線形再帰に置き換え、系列長に対するアテンション計算量を二次から線形へ削減する線形アテンションの変種。

これらのベースラインをもとに、二つの改善を提案します。

- SWA Pattern（探索ベース）：PostNAS [Gu25a] に着想を得て、SWA に変換する最適な層の部分集合を特定し、残りの層には完全アテンションを維持する探索ベースの適応手法を導入します。長文脈の下流タスクで性能を最大化する構成をビーム検索で決定します。計算コストを抑えるため、探索は 16K のコンテキスト長だけで行い、得られたパターンを他のすべての入力長へ一般化します。具体的にはビームサイズを 8 とし、1 ステップで 2 層ずつ最適化します。40 層の GLM-9B では約 10 ステップで収束します。各ステップで候補パターンを 16K コンテキストの RULER ベンチマーク [Hsi24] で評価し、上位 8 候補を次のステップに残します。最終パターンは `SFSSFFSSSFFFFSSFSFFFFFFSFSFSSFSSFSFSSFSSS` です。`S` は SWA 層、`F` は全アテンション層を表します。表 4 に示すように、探索ベースの構成は固定交互配置を大幅に上回ります。16K だけで最適化したにもかかわらず、すべての検証対象コンテキスト長で有効性を維持し、優れた長さの汎化を示します。
- SimpleGDN：継続学習への適応において GDN を改善しながら、事前学習済み重みを最大限に再利用するための最小限の線形化戦略です。`Conv1d` と明示的なゲーティングモジュールを完全に除去し、事前学習済みの Query、Key、Value の射影重みを線形再帰形式へ直接写像します。追加パラメータを不要にしながら、線形アテンションの効率上の利点を維持します。

![GLM-5 表 4](../../papers/glm-5/table-04.png)

**表 4.** GLM-9B ベースラインと二つの SWA 変種について、*追加学習を一切行わない*場合の RULER ベンチマーク結果。両 SWA 手法は、全アテンション層と SWA 層を 1:1 とし、ウィンドウサイズは 4096 トークンです。探索ベースの SWA パターンは 16K コンテキスト長で一度だけ探索し、すべての入力長に一律適用します。

表 5 の結果から、高効率アテンション手法には明確なトレードオフの階層があることが分かります。単純に交互配置した Sliding Window Attention（SWA）は、長文脈タスクで破滅的な低下を引き起こします（RULER@128K で $-$30.35 など）。探索ベースの層選択は、重要な箇所に完全アテンションを残すことで、この差を大幅に縮めます。GDN などの線形アテンション変種は品質をさらに改善しますが、追加パラメータが必要です。SimpleGDN は事前学習済み重みを最大限再利用し、最良のバランスを実現します。それでも、これらの手法では、継続学習への適応中に高効率アテンションが避けがたく情報を失うため、細粒度検索タスクに本質的な精度差が残ります。半数の層で完全アテンションを維持しても、RULER@128K では最大 5.69 ポイント、RepoQA@128K では 7.33 ポイントの差があります。これに対して DSA は構造上無損失です。Lightning Indexer は長距離依存を捨てずにトークン単位の疎性を実現するため、品質を損なわず全層に適用できます。

これを検証するため、Multi-latent Attention を備えた GLM-4.7-Flash（[https://huggingface.co/zai-org/GLM-4.7-Flash](https://huggingface.co/zai-org/GLM-4.7-Flash)）で小規模な DSA 実験を行いました。標準的な DSA の手順に従い、学習は二段階です。（i）全ベースモデル重みを固定し、インデクサのみを 1,000 ステップ（バッチサイズ 16）学習するウォームアップ、（ii）モデルとインデクサを 150B トークンで共同学習する段階です。表 6 は 4K から 128K までの RULER の結果をまとめています。ウォームアップのみの変種（GLM-4.7-Flash + DSA ウォームアップ）でもベースライン性能の大半を維持し、低下は小さく、最長の 128K コンテキストウィンドウに集中しています（$79.21\to 71.35$）。短いコンテキストではほぼ影響がありません。150B-トークンの共同学習を終えると、GLM-4.7-Flash + DSA は残る差のほぼすべてを解消します。16K（$+0.86$）、32K（$+0.49$）、64K（$+1.72$）ではベースラインを上回り、128K での差も 0.35 ポイントにとどまります。

### 2.2 事前学習データ

**Web。**

GLM-4.5 のデータパイプラインを基礎に、大規模 Web データセットの選択基準を改善しました。文埋め込みに基づく別の DCLM [Li25a] 分類器を導入し、標準分類器では得られない高品質データを追加で特定・集約します。長尾知識の課題には、Wikipedia エントリと LLM がラベル付けしたデータで最適化した World Knowledge 分類器を用い、従来は中～低品質とされたデータから有用な情報を抽出します。

**コード。**

主要コードホスティングプラットフォームの新しいスナップショットと、コードを含む Web ページの大規模なコレクションでコード事前学習コーパスを拡張しました。その結果、曖昧重複除去後の一意トークンが 28% 増加しました。コーパスの完全性を高めノイズを減らすため、Software Heritage のコードファイルにおけるメタデータアラインメントの問題を修正し、より正確な言語分類パイプラインを採用しました。ソースコードとコード関連 Web 文書には、GLM-4.5 の品質を考慮したサンプリング戦略を踏襲します。さらに、Scala、Swift、Lua など、より広範な低リソースプログラミング言語専用の分類器を学習し、これらの言語のサンプリング品質を改善します。

**数学と科学。**

推論能力をさらに高めるため、Web ページ、書籍、論文から高品質な数学・科学データを収集します。Web ページのコンテンツ抽出パイプラインと、書籍・論文向け PDF 解析機構を改善してデータ品質を高めました。大規模言語モデルで候補文書を評価し、教育的価値の高い内容のみを残します。長文脈文書には分割集約型評価アルゴリズムを開発し、評価精度を高めます。フィルタリングパイプラインでは、合成データ、AI 生成データ、テンプレートベースデータを厳格に除外します。

### 2.3 中間学習

GLM-4.5 で導入した中間学習フレームワークをもとに、GLM-5 では学習量と最大コンテキスト長の双方を拡大し、推論、長文脈、エージェント能力をさらに強化します。

**コンテキストと学習規模の拡張。**

コンテキストウィンドウを 32K（1T トークン）、128K（500B トークン）、200K（50B トークン）の三段階で拡張します。GLM-4.5 の最大 128K に対し、200K の追加段階は、超長文文書や複雑な複数ファイルコードベースを処理する能力を大幅に高めます。後半の段階では、それに合わせて長い文書と合成エージェント軌跡をアップサンプリングします。

**ソフトウェアエンジニアリングデータ。**

リポジトリ単位のコードファイル、コミット diff、GitHub issue、Pull Request、関連ソースファイルを連結して一つの学習系列にする方式を維持します。GLM-5 ではリポジトリ単位のフィルタリング基準を緩和して対象リポジトリを広げ、約 1,000 万件の issue-PR ペアを得る一方、個々の issue に対する品質フィルタリングを強化してノイズを削減します。各 issue-PR ペアについて関連ファイルの取得範囲も広げ、より豊かな開発コンテキストと、実世界のソフトウェアエンジニアリングシナリオの幅広い網羅性を確保しました。フィルタリング後、データセットの issue-PR 部分は約 160B 一意トークンです。

**長文脈データ。**

長文脈の学習セットは、自然データと合成データの双方で構成します。自然データは、書籍、学術論文、汎用事前学習コーパスの文書から、PPL、重複除去、長さによる多段階フィルタリングを通して選別し、知識集約型領域をアップサンプリングします。合成データの構築では、NextLong [Gao25] と EntropyLong [Jia25] に着想を得て、多様な手法で長距離依存を作りました。類似度の高いテキストを交互配置パッキングで集約して系列化し、lost-in-the-middle 現象を緩和するとともに、多様な長文脈タスクの性能向上を目指します。200K 段階では、OpenAI の元の枠組みを拡張する複数の変種を備えた少量の MRCR-like データも加え、長い複数ターン対話での想起を強化します。実験では、データの多様性を段階的に高めるほど長文脈性能が向上しました。特に、最初の 128K 段階に続いて 200K の中間学習を行うことで、128K コンテキストウィンドウ内の性能もさらに改善しました。

### 2.4 学習基盤

#### 2.4.1 メモリ効率

**柔軟な MTP 配置。** 交互パイプライン並列 [Nar21] では、モデル構成要素を各段階に柔軟に割り当てます。MTP モジュールは埋め込み、Transformer、出力構成要素にまたがり、他のモジュールより大幅に多くのメモリを使用するため、段階間に不均衡が生じます。MTP の出力層を主出力層と最終段階に配置してパラメータ共有を可能にし、埋め込みと Transformer 構成要素は一つ前の段階に配置します。これにより最終段階のメモリ負荷を減らし、パイプラインランク間のバランスを改善します。

**Pipeline ZeRO2 勾配分割。** 各パイプラインランクは複数の段階を保持し [Nar21]、単純な実装では勾配累積とオプティマイザ更新のため、各段階が完全な勾配バッファを必要とします。ZeRO2 [Raj20] に着想を得て、データ並列ランク間で勾配をシャード化し、各段階が完全な勾配の $1/dp$ だけを保持するようにします。さらに、完全な累積バッファは同時に 2 段階分だけ保持し、ダブルバッファリングで再利用します。一方の段階バッファが連続するマイクロバッチの勾配を蓄積している間に、前の段階バッファの勾配同期を並行実行します。実運用上の追加同期オーバーヘッドを生じさせず、常駐勾配メモリを段階ごとの分割バッファと、巡回累積用の完全なバッファ 2 個に削減できます。

**Muon 分散オプティマイザのゼロ冗長通信。** 単純な Muon 実装では、各データ並列ランクで完全なモデルパラメータを all-gather するため、一時的なメモリ急増と冗長な通信が発生します。all-gather を各ランクが所有するパラメータシャードに限定し、ローカル計算とシャード通信を重複実行させます。これにより冗長な通信をなくし、オプティマイザに由来するピークメモリオーバーヘッドを大きく削減します。

**Pipeline 活性値オフロード。** パイプラインウォームアップ中は前向き実行が逆伝播より先行し、中間活性値の寿命が長くなります。前向き実行後に活性値をホストメモリへオフロードし、逆方向実行の前に再読み込みします [Yua24]。層単位でオフロードし、ピークメモリをさらに削減します。細粒度再計算と組み合わせることで、活性値を GPU メモリに常駐させる必要をほぼなくせます。オフロードと再読み込みは計算に重ねつつ、peer-to-peer 通信や MoE トークンルーティング（分配と結合）との競合を避けるようスケジューリングします。ほぼゼロのオーバーヘッドで、活性値メモリ使用量を大幅に削減できます。

**ピークメモリを削減する系列分割型出力射影。** 出力射影と交差エントロピー損失では、逆伝播用の活性値の保存や、損失計算時の高精度化によって、一時的なメモリオーバーヘッドが発生します。これを抑えるため、入力系列を小さなチャンクに分割し、各チャンクで射影と損失を独立に計算します。一つのチャンクで前向きと逆方向パスを完了し、活性値を解放してから次へ進みます。その結果、チャンク数を増やすほどピークメモリが低下します。適切なチャンク数を選べば、チャンク化しない実行と同等の性能を保ちながら、出力層のメモリ負荷を緩和できます。

#### 2.4.2 並列処理効率

**効率的な遅延重み勾配計算。** パイプラインバブルを減らすため、重要経路上にある一部の重み勾配計算を遅延させます [Qi23]。最適化したストレージと通信重複実行を用いる細粒度遅延により、メモリオーバーヘッドを抑えつつスループットを改善します。

**効率的な長系列学習。** 系列が長いほど、データ並列グループとパイプライン並列グループの負荷不均衡が深刻になります。ワークロードを考慮した系列並べ替え、アテンション計算の動的再分配、データ並列ランクを異なるサイズのコンテキスト並列グループに柔軟に分割することで対処します [Ge25, Wan25b]。階層型 all-to-all は QKV テンソルのノード内通信とノード間通信を重ね、レイテンシを削減します。

#### 2.4.3 INT4 量子化認識学習

低精度での精度を改善するため、SFT 段階で INT4 QAT を適用します。さらに学習時間のオーバーヘッドを抑えるため、学習とオフライン重み量子化の双方に使える量子化カーネルを開発し、学習と推論がビット単位で同一に動作することを保証します。

## 3 後学習

GLM-5 の後学習は、ベースモデルを、堅牢な推論、コーディング、エージェント能力を備えた高性能アシスタントへ変換することを目的とします。図 5 のように、パイプラインは段階的なアラインメント戦略を採用します。まず高度な交互配置思考モードを導入するマルチタスク Supervised Fine-Tuning（SFT）を行い、次に推論タスクとエージェントタスクそれぞれに特化した Reinforcement Learning（RL）を実施し、最後に人間らしいアラインメントのための汎用 RL を行います。最終調整としてオンポリシーのステージ間蒸留を用いることで、各学習段階で得た性能向上を活かしながら、能力の後退を効果的に抑えます。

### 3.1 教師ありファインチューニング

![Interleaved Thinking と Preserved Thinking](../../papers/glm-5/figure-07.png)

**図 7.** Interleaved Thinking と Preserved Thinking の概念図。

GLM-4.5 と比較して、GLM-5 は SFT 段階における*エージェント*と*コーディング*のデータ規模を大幅に拡大しました。SFT コーパスは三つの主要カテゴリを含みます。

- **一般対話**：質疑応答、文章作成、ロールプレイ、翻訳、複数ターン対話、長いコンテキストでの対話。
- **推論**：数学、プログラミング、科学の推論。
- **コーディングとエージェント**：フロントエンド・バックエンドのエンジニアリングコード、ツール呼び出し、コーディングエージェント、検索エージェント、汎用エージェント。

さらに、SFT 中の最大コンテキスト長を 202,752 トークンに拡張しました。更新したチャットテンプレートと合わせ、モデルは三つの異なる思考特性をサポートします（図 7）。

- **Interleaved Thinking**：各応答とツール呼び出しの前に思考し、指示遵守と生成品質を高めます。Interleaved 思考は [Claude](https://platform.claude.com/docs/en/build-with-claude/extended-thinking#interleaved-thinking) が初めて導入しました。
- **Preserved Thinking**：コーディングエージェントの場面では、複数ターンの会話を通じてすべての思考ブロックを自動的に保持し、既存の推論を再利用します。最初から推論し直す必要がないため、情報の欠落や不整合を減らし、長期かつ複雑なタスクに適しています。Claude も Opus 4.5 以降で [Preserved Thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking#thinking-block-preservation-in-claude-opus-4-5-and-later) を採用しています。
- **Turn-level Thinking**：セッション内でターンごとに推論を制御できます。軽量なリクエストでは思考を無効にしてレイテンシとコストを抑え、複雑なタスクでは有効にして正確性と安定性を高めます。

行動の間に思考し、ターンをまたいで一貫性を保つことで、GLM-5 は複雑なタスクに対して、より安定し制御しやすい挙動を示します。

**一般対話**では、GLM-4.5 より論理的かつ簡潔な応答スタイルへ最適化しました。ロールプレイタスクには、多言語と多様な役割設定を網羅する、より広範で多様なデータセットを収集・構築しました。特に指示遵守、言語表現力、創造性、論理的一貫性、長い対話での整合性など複数の評価軸を定義し、自動フィルタリングと人手によるフィルタリングを併用してデータを選別・改善しています。

**推論**タスクでは、モデルの推論の深さをさらに高めました。論理推論では、検証可能な問題を作り、棄却サンプリングによって高品質データを合成します。数学・科学問題には難易度ベースのフィルタリングを適用し、GLM-4.7 にとって難しい問題だけを残します。

**コーディング**と**エージェント**のタスクでは、GLM-4.5 より多くの実行環境を構築して高品質な軌跡を収集し、特に実世界のシナリオと長期タスクを重視します。エキスパート強化学習と棄却サンプリングにより SFT データをさらに改善しました。軌跡中の誤った区間は保持しますが、損失関数ではマスクします。これにより、誤った行動を強化せずに、エラー修正の挙動を学習できます。

### 3.2 推論 RL

**RL アルゴリズム基盤。**

RL アルゴリズムは GRPO [Sha24] を基礎とし、IcePop [Zha25c] を取り入れて*学習・推論間の不一致*、すなわち RL 最適化中の推論分布と学習分布の差を緩和します。勾配更新に用いる*学習方策* $\pi^{\text{train}}$ と、軌跡サンプリングに用いる*推論方策* $\pi^{\text{infer}}$ を明確に区別します。元の IcePop 定式化から KL 正則化項を除去し、RL による改善を加速します。最終的な最適化損失は次のとおりです。

$$
\begin{aligned}
\mathcal{L}(\theta)=
-\mathbb{E}_{
x \sim \mathcal{D},
\{y_i\}_{i=1}^{G} \sim \pi^{\text{infer}}_{\theta_{\text{old}}}(\cdot \mid x)
}
&\Bigg[
\frac{1}{G}
\sum_{i=1}^{G}
\frac{1}{|y_i|}
\sum_{t=1}^{|y_i|}
\operatorname{pop}(\rho_{i,t}, 1/\beta, \beta) \\
&\quad\cdot
\min\!\left(
r_{i,t}\hat{A}_{i,t},
\operatorname{clip}\!\left(
r_{i,t},
1-\epsilon_{\text{low}},
1+\epsilon_{\text{high}}
\right)
\hat{A}_{i,t}
\right)
\Bigg].
\end{aligned}
\tag{1}
$$

ここで、学習・推論間の不一致比率を次のように定義します。

$$
\rho_{i,t}=\frac{\pi_{\theta_{\text{old}}}^{\text{train}}(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta_{\text{old}}}^{\text{infer}}(y_{i,t}\mid x,y_{i,<t})}.
$$

$\operatorname{pop}(\cdot)$ は不一致比率が大きく外れたサンプルを抑制します。

$$
\operatorname{pop}(\rho_{i,t},1/\beta,\beta)=\begin{cases}\rho_{i,t},&1/\beta\leq\rho_{i,t}\leq\beta,\\
0,&\text{otherwise}.\end{cases}
$$

PPO 形式の重要度比率とグループ正規化アドバンテージは、元の GRPO の定義に従います。

$$
r_{i,t}=\frac{\pi_{\theta}^{\text{train}}(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta_{\text{old}}}^{\text{train}}(y_{i,t}\mid x,y_{i,<t})},\quad\hat{A}_{i,t}=\frac{R_{i}-\operatorname{mean}(R_{1},\dots,R_{G})}{\operatorname{std}(R_{1},\dots,R_{G})}.
$$

学習時のハイパーパラメータは $\beta=2,\epsilon_{\text{low}}=0.2,\epsilon_{\text{high}}=0.28$ です。学習は完全なオンポリシーで、グループサイズとバッチサイズはともに 32 です。

**DSA RL から得られた知見。**

DSA アーキテクチャを採用するモデルで、非常に大規模な RL 学習を行いました。MLA と比べて、DSA は top-k の最も関連性の高いキー・値エントリを検索し、その部分集合に対して疎アテンションを計算するインデクサを追加します。検索した top-k の結果は RL の安定性に不可欠です。これは、MoE モデルがルーティングリプレイ [Zhe25] によって有効化した top-k エキスパートを保持し、学習・推論間の一貫性を確保する仕組みに似ています。しかし、この戦略をそのままインデクサリプレイに転用し、各トークン位置のインデクサ top-k インデックスを保存するのは現実的ではありません。インデクサの $k=2048$ は MoE で一般的な $k$ よりはるかに大きく、全インデックスの保存は莫大なストレージコストと、学習エンジンと推論エンジン間の通信オーバーヘッドを生じさせます。

決定論的な top-k 演算子を採用すると、DSA インデクサによるトークン選択の学習・推論間不一致を効果的に解消できることが分かりました。SGLang の DSA Indexer が使用する CUDA ベースの非決定論的 top-k と比べ、単純な `torch.topk` はやや低速ですが決定論的です。より一貫した出力を生成し、RL に大きな改善をもたらします。一方、CUDA や TileLang 実装など他の非決定論的 top-k 演算子では、わずか数ステップで RL 性能が急落し、エントロピーも大幅に低下しました。そのため、全 RL 段階を通じて、学習エンジンの DSA Indexer では `torch.topk` を既定の top-k 演算子とします。また学習の高速化とインデクサの不安定な学習を防ぐため、RL 中は既定でインデクサパラメータを固定します。

**複数領域を混合した推論 RL。**

推論 RL では、数学、科学、コード、Tool-Integrated Reasoning（TIR）の四領域を混合して学習します。数学・科学データは、オープンソースデータセット [Du25, Mos25] と、外部アノテーション事業者と共同開発したデータ集合から選別します。GLM-4.7 がほとんど正答できない、または常に失敗する一方、より強い教師モデル（GPT-5.2 xhigh、Gemini 3 Pro Preview など）には解ける問題へ学習を集中させる難易度フィルタリングも行います。コードでは、競技プログラミング形式のタスクと科学計算コードタスクの双方を扱います。前者は主に Codeforces、TACO [Li23]、SYNTHETIC-2-RL [Int25a] などから収集し、後者は社内の問題を、正答に必要な最小限のコード実装へ分解して構築します。TIR には数学・科学 RL データのうち難しい部分集合を再利用し、外部ツールを使って回答するよう明示的に設計した STEM 問題もアノテーション事業者と共同で作成します。RL 学習中は、領域・データソース別の評価モデルまたは評価システムで二値の結果報酬を生成します。四領域の全体的な混合比はほぼ均等であり、混合 RL のもとで各領域に安定かつ有意な改善が一貫して見られます。

### 3.3 エージェント RL

GLM-5 のエージェント性能を高めるため、完全非同期かつ分離された RL フレームワークを開発し、コーディングエージェントと検索エージェントのタスクで GLM-5 を最適化します。単純な同期 RL では、長期エージェントロールアウトの間に GPU の大きなアイドル時間が発生します。中央の Multi-Task Rollout Orchestrator を介して推論エンジンと学習エンジンを分離し、多様なエージェント型ワークロードの高スループットな共同学習を実現します。

非同期オフポリシー条件で学習を安定させるため、二つの主要な仕組みを導入します。第一に、Token-in-Token-out（TITO）ゲートウェイが行動単位の正確な対応を保持し、再トークン化の不一致を取り除きます。第二に、Direct Double-sided Importance Sampling を用います。ロールアウト時の対数確率にトークン単位のクリッピング（$[1-\epsilon_{\ell},1+\epsilon_{h}]$）を適用し、過去の方策チェックポイントを追跡せずにオフポリシーバイアスを効率的に制御します。大規模 MoE モデルの長文脈推論では、DP-aware ルーティングによって KV キャッシュの再利用を最大化し高速化します。エージェント環境の規模を拡大するため、10K を超える実世界の Software Engineering（SWE）、ターミナルタスク、高難度の多段ホップ検索タスクという三領域で、検証可能な学習環境を拡張します。エージェント型 RL の詳細は第 4 節で説明します。

### 3.4 汎用 RL

**多次元の最適化目標。**

汎用 RL の最適化目標を、*基礎的な正しさ*、*感情的知性*、*タスク固有の品質*という、相互補完的な三つの次元に分解します。

*基礎的な正しさ*は応答品質の土台です。指示遵守の失敗、論理的不整合、事実誤認、知識のハルシネーション、言語の不自然さなど、モデル出力の利用価値を損なう広範なエラー種類を対象とします。エラー率を最小化し、応答を*利用可能*なベースラインまで引き上げることが目的です。これは、その後のすべての最適化に先立つ条件です。どれほど洗練されて見える応答でも、事実誤認を含んだりユーザー意図を誤解したりすれば、ユーザーを積極的に誤導しかねません。

*感情的知性*は、正しさの先にあるユーザー体験を最適化します。共感的で洞察に富み、自然な人間のコミュニケーションに近いスタイルの応答を生成し、モデルとのやり取りをより自然で魅力的にすることを目指します。

*タスク固有の品質*は、個々のタスクに応じた細粒度の最適化を行います。基礎的な正しさで確立した利用可能性を土台に、応答を単に正しいだけのものから、各タスクカテゴリで真に高品質なものへ高めます。文章作成、テキスト処理、主観・客観の質疑応答、ロールプレイ、翻訳など幅広いタスクを対象とします。タスク領域ごとに必要な報酬信号が異なるため、ハイブリッド報酬システムが必要です。

**ハイブリッド報酬システム。**

上記の多様な目標を監督するため、*ルールベース報酬関数*、*結果報酬モデル*（ORM）、*生成型報酬モデル*（GRM）という、相互補完的な三種類の報酬信号を統合したハイブリッド報酬システムを構築します。それぞれに異なる長所と短所があり、その組み合わせが安定的、効率的、拡張可能な汎用 RL 学習の鍵です。

ルールベース報酬は精密で解釈可能な信号を与えますが、決定的なルールとして表現できる側面に限られます。ORM は分散が低く学習効率が高い反面、方策が核心能力を本当に改善せず表面的なパターンを利用する報酬ハッキングの影響を受けやすい性質があります。GRM は言語モデルでスカラー値または構造化評価を生成するため、そのような悪用に比較的強い一方、分散が高くなる傾向があります。三種類を組み合わせることで、精度、効率、堅牢性のバランスを取り、単独の構成要素が持つ弱点を緩和します。

**Human-in-the-loopのスタイルアラインメント。**

汎用 RL パイプラインの特徴は、人間が書いた高品質な応答を明示的に取り入れることです。モデル生成応答だけに頼らず、専門家による人間の応答をスタイルと品質の基準点として導入します。モデル生成のみで最適化すると、冗長、定型的、または熟練した人間の文章が持つ機微に欠けるといった、明らかに「モデルらしい」パターンへ収束しやすいという観察に基づいています。人間が書いた例に触れさせることで、より自然で人間に沿った応答パターンを身につけるよう促します。

### 3.5 オンポリシーのステージ間蒸留

多段階 RL パイプラインで異なる目標を順番に最適化すると、以前に獲得した能力が累積的に低下する可能性があります。これを緩和するため、オンポリシーのステージ間蒸留を**最終段階**として実施します。オンポリシー蒸留アルゴリズム [Gu25, Yan25a, Xia26, Lu25] を採用し、前の SFT・RL 段階（推論 RL と汎用 RL）で得た能力を迅速に回復します。具体的には、それまでの各学習段階の最終チェックポイントを教師モデルとし、学習プロンプトは対応する教師の RL 学習セットからサンプリングして、適切な比率で混合します。式 1 のアドバンテージ項を次式に置き換えると学習損失が得られます。`sg` は `.detach()` などの勾配停止操作を表します。

$$
\hat{A}_{i,t}=\text{sg}\left[\log\frac{\pi_{\theta_{\text{teacher}}}^{\text{infer}}(y_{i,t}\mid x,y_{i,<t})}{\pi_{\theta}^{\text{train}}(y_{i,t}\mid x,y_{i,<t})}\right].
\tag{2}
$$

現在は推論エンジンで教師のロジットを取得しています。将来は推論バックエンドを学習エンジンへ移行し、推論には MLA の Multi-Query Attention（MQA）モードを統一的に採用する予定です（$\pi_{\theta_{\text{teacher}}}^{\text{infer}}\rightarrow\pi_{\theta_{\text{teacher}}}^{\text{train}}$）。学習時は、データスループットを高めるため GRPO のグループサイズを 1、バッチサイズを 1024 に設定します。この段階ではアドバンテージを推定するためにプロンプトごとの大きなサンプルグループを維持する必要がなく、教師モデルとの差から直接アドバンテージを計算できるためです。

### 3.6 RL 学習基盤：*slime* フレームワーク

GLM-5 でも、slime を統一後学習基盤として継続利用し、大規模なエンドツーエンド Reinforcement Learning（RL）を可能にします。新しいシステム構成要素を導入するのではなく、GLM-5 は slime の能力を*全面的に活用*します。（1）自由形式のロールアウトのカスタマイズとサーバーベース実行モデルでタスク網羅性を広げる、（2）混合精度学習/ロールアウト、MTP、Prefill-Decode（PD）分離を組み合わせ、とりわけ複数ターン RL ワークロードのスループットを大幅に高める、（3）ハートビート駆動ロールアウト障害耐性とルーター単位のサーバーのライフサイクル管理で堅牢性を高める、という三点です。

#### 3.6.1 スケールアウト：高度にカスタマイズ可能なロールアウトによる柔軟な学習

GLM-5 の後学習は多様な目標にまたがります。タスク別の分岐を設けずこの多様性に対応するため、slime の高度にカスタマイズ可能なロールアウトインターフェースと、サーバーベースロールアウト実行を利用します。

**高度にカスタマイズ可能なロールアウト。** slime は、基盤を変更せずにタスク固有ロールアウトロジックを実装できる柔軟なインターフェースを提供します。複数ターンインタラクションループ、ツール呼び出し、環境フィードバック処理、検証器主導の分岐などに対応します。GLM-5 はこの機能を利用し、推論 RL、汎用 RL、エージェント RL、オンポリシー蒸留など、幅広い領域と学習パラダイムを単一の学習スタックでサポートします。

**HTTP API を用いたサーバーベースロールアウト。** slime はロールアウトサーバーと推論ルーターを標準 HTTP API で公開し、通常の推論エンジンと同じ方法でサービング層を利用できます。これによりロールアウトロジックを学習プロセス境界から切り離します。外部エージェントフレームワークや環境はサーバー/ルーターのエンドポイントを直接呼び出せる一方、短期の単一ターン学習でも長期の複数ターン軌跡でも、最適化バックエンドは変わりません。

#### 3.6.2 スケールアップ：RL ロールアウトのテールレイテンシ最適化

RL ロールアウトの最適化対象は総スループットではなく*エンドツーエンドのレイテンシ*であり、各ステップで最も遅い長尾サンプルが支配的です。一つの遅い軌跡がバッチ完了、バッファ準備完了、学習器更新などの同期ポイントを停止させ、実時間上の進捗を直接決めることがあります。そのため GLM-5 は、slime のレイテンシ重視のサービングとスケジューリング機構を全面的に活用し、中央値レイテンシと、より重要なテールレイテンシの双方を最小化します。

**MLA 向け DP-attention を備えたマルチノード推論による無待ち行列サービング。** 待ち行列遅延を避けるには、突発的なトラフィック下でもロールアウトリクエストを即座に処理する必要があり、そのためには大きな KV キャッシュ容量が必要です。GLM-5 は、十分な分散 KV キャッシュを確保するため、マルチノード推論デプロイ（8 ノードに EP64 と DP64 を配置する構成など）を採用します。DP-attentionの主な目的は、異なるランク間での KV コピーを防ぐことです。

**FP8 ロールアウトと MTP によるテールレイテンシ削減。** GLM-5 はロールアウト推論に FP8 を使用し、トークン当たりレイテンシと長い軌跡の完了時間を短縮します。また、slime の Multi-Token Prediction（MTP）のサポートを利用します。これは RL ロールアウトに一般的な小規模バッチのデコード環境で特に効果的です。テールレイテンシは、まれな長いコンテキスト、複雑な複数ターン推論、ツール呼び出しの多いトレースなど、バッチサイズが小さい場合の遅いサンプルに左右されることが多いため、MTP は長尾に大きな効果をもたらします。最も遅いサンプルの完了時間を改善し、ステップ単位の停滞時間を短縮します。

**複数ターン RL でプリフィルとデコードの干渉を防ぐ PD 分離。** 複数ターン環境では、対話履歴、ツールトレース、コードコンテキストなど、長いプレフィックスのプリフィルが頻繁に発生します。DP-attentionのもとでプリフィルとデコードを同じサービングリソースに混在させると、重いプリフィルがサーバー上の継続中のデコードを先取り、または妨げる深刻な干渉が起きます。他のサンプルが連続的に進まず、テールレイテンシが急激に悪化します。そこで GLM-5 は slime の Prefill-Decode（PD）分離を利用します。プリフィルとデコードを専用リソースで動かすことでデコードを安定かつ中断なく維持し、長期サンプルが継続的に進めるようにします。複数ターンエージェント型 RL のテール挙動が大幅に改善されます。

#### 3.6.3 ロールアウトの堅牢性：ハートビート駆動の障害耐性

大規模環境では、個別サーバークラッシュ、ネットワーク障害、性能低下などの一時的な障害を避けられません。GLM-5 は slime のハートビート駆動障害耐性を利用し、そのような状況でも学習を継続します。ロールアウトサーバーは定期的にハートビートを送り、オーケストレーション層が監視します。異常なサーバーは先回りして停止され、推論ルーターから登録解除されます。再試行は障害または劣化したサーバーを避けて正常なサーバーへ自動ルーティングされるため、一つのサーバー障害がロールアウトを中断することなく、エンドツーエンドの RL 学習を継続できます。

## 4 エージェント型エンジニアリング

ここでは、**Vibe Coding**（人間によるプロンプト）から**エージェント型エンジニアリング**への移行を説明します。Vibe Coding では、人間が AI モデルにプロンプトを与えてコードを書かせます。エージェント型エンジニアリングでは、AI エージェント自身がコードを書き、計画、実装、反復を行います。長期タスクを支えるため、GLM-5 は完全非同期かつ分離された RL フレームワークを用い、エージェントロールアウト中のアイドル時間を減らして GPU 使用率を大幅に高めます。エージェント環境を拡大するため、環境構築パイプラインを開発しました。コーディングタスクでは、実世界のソフトウェアエンジニアリング issue とターミナルタスクに基づき、10,000 を超える検証可能な学習シナリオを構築します。検索エージェントには、自動的かつ拡張可能な複雑な複数ステップ推論データ合成パイプラインを開発し、エージェント型学習用データを作ります。

### 4.1 エージェントタスク向け非同期 RL

エージェントタスクに RL を適用するため、長期のエージェントロールアウトを効率的に処理し、多様なエージェントフレームワークをまたぐ柔軟なマルチタスク RL 学習に対応する、完全非同期かつ分離された RL 基盤を設計しました。

RL 学習にはグループ単位の方策最適化アルゴリズムを使用します。各問題 $x$ について、前の方策 $\pi_{\text{old}}$ から $K$ 本のエージェントトレース $\{y_{1},\dots,y_{K}\}$ をサンプリングし、次の目的関数に対してモデル $\pi_{\theta}$ を最適化します。

$$
L(\theta)=\mathbb{E}_{x\sim\mathcal{D}}\!\left[\frac{1}{K}\sum_{i=1}^{K}\left(r(x,y_{i})-\bar{r}(x)\right)\right],
$$

ここで、$\bar{r}(x)\;=\;\frac{1}{K}\sum_{i=1}^{K}r\bigl(x,y_{i}\bigr)$ はサンプリングした応答の平均報酬です。最適化にはモデル生成トークンだけを使用し、損失計算では環境フィードバックを無視します。

#### 4.1.1 エージェント学習向け非同期 RL 設計

ロールアウトプロセスは長尾な性質を持つため、単純な同期 RL ではエージェント型タスクの生成負荷が大きく不均衡になり、ロールアウト段階に多くのバブルが発生して GPU のアイドル時間が増えます。学習スループットを高めるため、エージェント RL には完全非同期の学習パラダイムを採用し、GPU 使用率と学習効率を向上させます。具体的には、学習エンジンと推論エンジンを異なる GPU デバイスに分離します。推論エンジンは軌跡を連続生成し、所定の数に達した時点でバッチを学習エンジンに送り、モデルを更新します。方策の遅延を減らし、学習をおおむねオンポリシーに保つため、ロールアウトエンジンが使うモデル重みを学習エンジンと定期的に同期します。学習エンジンはモデルパラメータを更新し、$K$ 回の勾配更新ごとに新しい重みを推論エンジンへ送り返します。非同期化は全体の学習効率を大きく高めますが、異なる軌跡が異なるモデルバージョンで生成されるため、深刻なオフポリシー問題も生じます。ロールアウト方策が変わるたびに重み更新が異なる最適化問題を扱うことになるため、推論エンジンの重み更新ごとにオプティマイザもリセットします。

**サーバーベースマルチタスク学習設計。**

マルチタスク RL ではタスクごとにツールセットとロールアウトロジックが異なるため、軌跡生成は異質です。この問題に対処するため、マルチタスク RL 学習向けにサーバーベース Multi-Task Rollout Orchestrator を導入します。複数のタスクサービスを登録した中央オーケストレータにより、slime RL 学習フレームワークと多様な下流タスクの互換性を確保します。各タスクは固有のロールアウトロジックと報酬ロジックを独立したマイクロサービスとして実装し、中央オーケストレータに登録して管理・スケジューリングします。ロールアウト段階では、中央オーケストレータがタスクごとのロールアウト比率と生成速度を制御し、タスク間で均衡したデータ収集を実現します。さらに重要なのは、すべてのエージェント型タスクの軌跡を統一されたメッセージリスト表現に標準化することです。Software Engineering タスクなど複雑なエージェント型フレームワークの共同学習に加え、異質なワークロードの集中型後処理とログ記録にも対応できます。タスク固有ロジックと中核学習ループを明確に分離し、マルチタスク RL 学習に容易に統合できる設計です。GLM-5 学習基盤の基盤として、1k を超える同時ロールアウト、タスクサンプリング比率の自動的・動的な調整、タスク進捗の細粒度な監視をサポートします。

#### 4.1.2 非同期学習の安定性向上

**Token-in-Token-out と Text-in-Text-out。**

RL ロールアウトにおける *token-in-token-out*（TITO）は、推論エンジンが生成した*正確な*トークン化とデコード済みトークン列を学習パイプラインが受け取り、そのまま学習用軌跡の構築に使うことを意味します。一方、*text-in-text-out* はロールアウトエンジンを最終テキストを返すブラックボックスとみなし、学習器が損失計算前にテキストを再トークン化し、軌跡、境界、切り詰めを再構築します。この小さく見える違いは重要です。再トークン化はトークン境界、空白/正規化、切り詰め、特殊トークンの配置に微妙な差を生じさせ、行動と報酬/アドバンテージのステップアラインメントを損なう可能性があります。ロールアウトをストリーミング、切り詰め、または多数のアクター間で交互配置する場合は特に深刻です。token-in-token-out は、サンプリングした行動と最適化対象の行動を正確に対応させるため、非同期 RL 学習に不可欠です。アクターは軌跡断片（トークン ID とメタデータ）を即座に送ることができ、有損なテキスト往復変換も学習器側の事後的な再トークン化も不要です。実装では、ロールアウトタスクからの全生成リクエストを捕捉し、各軌跡のトークン ID とメタデータを記録する TITO Gateway を用います。煩雑なトークン ID 処理を下流エージェントロールアウトロジックから隔離し、RL 学習における再トークン化の不一致を防ぎます。

**Token クリッピングのための Direct Double-sided Importance Sampling。**

第 3 節の同期 RL と異なり、非同期環境では一つの軌跡を生成する間にロールアウトエンジンが何度も更新される可能性があるため、正確な挙動確率 $\pi_{\theta_{\text{old}}}$ を追跡する計算コストは現実的ではありません。さもなければ、多数の過去モデルチェックポイント $\{\pi_{\theta_{\text{old}}^{(1)}},\dots,\pi_{\theta_{\text{old}}^{(N)}}\}$ を維持する必要があり、実装上不可能です。

そこでまず、ロールアウト中に得た対数確率を挙動の代理として直接再利用する、簡略化したトークン単位重要度サンプリングを採用します。重要度サンプリング比率を $r_{t}(\theta)=\frac{\pi_{\theta}}{\pi_{\text{rollout}}}$ とし、従来の $\pi_{\theta_{\text{old}}}$ を除くことで、旧方策推論を別途行う計算オーバーヘッドをなくします。次に、両側校正によるトークン単位のマスク戦略を用います。標準 PPO の非対称クリッピングとは異なり、信頼領域を $[1-\epsilon_{\ell},1+\epsilon_{h}]$ に制限します。$\epsilon_{\ell}$ と $\epsilon_{h}$ はクリッピングハイパーパラメータです。この範囲外のトークンは勾配計算から完全にマスクし、方策の極端な乖離による不安定性を防ぎます。IcePop 機構 [Tea25c] と似ていますが、$\pi_{\theta_{\text{old}}}$ も除くため、より単純で安定した学習が可能です。

トークン単位クリッピングを用いた最適化目的関数は、形式的には次のように書けます。

$$
L(\theta)=\mathbb{E}_{t}\left[f(r_{t}(\theta),\epsilon_{l},\epsilon_{h})\hat{A}_{t}\log\pi_{\theta}(a_{t}|s_{t})\right]
\tag{3}
$$

重要度サンプリング比率 $r_{t}(\theta)$ は次式で計算します。

$$
r_{t}(\theta)=\exp\left(\log\pi_{\theta}(a_{t}|s_{t})-\log\pi_{\text{rollout}}(a_{t}|s_{t})\right)
\tag{4}
$$

校正関数 $f(x;\epsilon_{\ell},\epsilon_{h})$ によって、安定性をさらに強化します。

$$
f(x;\epsilon_{\ell},\epsilon_{h})=\begin{cases}x,&\text{if }1-\epsilon_{\ell}<x<1+\epsilon_{h}\\
0,&\text{otherwise}\end{cases}
\tag{5}
$$

実験では、ロールアウト時の対数確率の再利用により、制御された範囲のオフポリシーバイアスを許容する代わりに、過去の方策追跡を不要にし、学習の安定性を高められることが分かりました。

**オフポリシーサンプルとノイズの多いサンプルの除外。**

非同期 RL では、過度に長い軌跡が大きくオフポリシーになり、学習を不安定にする可能性があります。このようなサンプルを除くため、生成時にロールアウトエンジンが使った方策重みバージョンを記録します。各応答について、関与したモデルバージョンの系列 $(w_{0},\ldots,w_{k})$ を $w_{0}<\cdots<w_{k}$ として記録します。現在の方策バージョンを $w^{\prime}$ とし、最も古いロールアウトバージョンが古すぎる、すなわち $w^{\prime}-w_{0}>\tau$ の場合にサンプルを破棄します。$\tau$ は所定のしきい値です。これにより、現在の方策から大幅に遅れた軌跡を除外します。

また、コーディングエージェントのサンドボックスは本質的に不安定で、環境クラッシュなどモデルと無関係な理由で失敗する場合があります。このような失敗はモデル能力ではなく環境の不安定性を反映するため、ノイズの多い学習信号になります。そこでサンプルごとの失敗理由を記録し、環境崩壊による失敗を除外します。GRPO のようなグループベースサンプリング手法では、失敗サンプルを除くとグループが不完全になります。その場合、有効サンプルがグループサイズの半数を超えていれば有効サンプルを繰り返してグループを埋め、そうでなければグループ全体を破棄します。この手順により、偽の報酬ノイズを減らし、学習の安定性を高めます。

**高速化のための DP-aware ルーティング。**

大規模 MoE 推論の Data Parallelism（DP）環境で KV キャッシュの局所性を保つため、DP-aware ルーティング機構を提案します。複数ターンエージェント型ワークロードでは、同一ロールアウトからの連続リクエストが同じプレフィックスを共有します。KV の再利用を最大化するため、ロールアウト単位の親和性を強制し、一つのエージェントインスタンスに属する全リクエストを同じ DP ランクへルーティングします。具体的には、整合ハッシュによりロールアウト ID を固定 DP ランクへ対応付ける状態保持型ルーティング層を導入します。ターンをまたいでも対応付けは変わらず、ランク間キャッシュミスを解消します。長期的な不均衡を防ぐため、ハッシュとハッシュ空間上の軽量な動的負荷再均衡を組み合わせます。DP ランク間の KV 同期を必要とせず、冗長なプリフィル計算を避けられます。ロールアウトが長くなっても、プリフィルコストは全コンテキスト長ではなく増分トークン数に比例します。その結果、長文脈のエージェント型推論でエンドツーエンドレイテンシが改善し、実効スループットも向上します。

### 4.2 エージェント環境のスケーリング

多様なエージェントタスクの RL を支えるため、コード中心のワークフローとコンテンツ生成ワークフローの双方に根拠のあるフィードバックを返す、検証可能で実行可能な環境を構築します。エージェント型コーディングタスクには二つの環境構築パイプラインを開発しました。実世界のソフトウェアエンジニアリング issue に基づく環境セットアップパイプラインと、ターミナルエージェント環境の合成パイプラインです。コーディング以外にはスライド生成環境も導入します。エージェントは構造化 HTML を操作し、実行可能なレンダリングとレイアウトベース検証によって検証されます。

#### 4.2.1 ソフトウェアエンジニアリング（SWE）環境

実行環境を構築する前に、実世界の Issue-Pull Request（PR）ペアを大量に収集し、厳格なルールベースおよび LLM ベースフィルタリングで、真正かつ高品質な issue 記述を選別します。インスタンスをバグ修正、機能実装、リファクタリング、その他のタスク種類に分類し、モデルの実装とテストパッチが一致するよう必要なタスク要件を含めます。RepoLaunch [Zha25a] フレームワークに基づく環境セットアップパイプラインを使用し、実世界の SWE issue から実行環境を大規模に構築します。リポジトリのインストールと依存関係セットアップを自動分析して環境とテストコマンドを作り、LLM でテスト出力に応じた言語別ログ解析関数を生成します。これにより Fail-to-Pass（F2P）と Pass-to-Pass（P2P）のテストケースを抽出できます。このパイプラインにより、数千のリポジトリから 10k を超える検証可能な環境を構築しました。Python、Java、Go、C、CPP、JavaScript、TypeScript、PHP、Ruby の 9 言語を網羅します。

#### 4.2.2 ターミナル環境

**シードデータからの合成。**

検証可能なターミナルエージェント環境を大規模に構築するため、タスクドラフト生成、具体的なタスク実装、反復的なタスク最適化の三段階からなるエージェント型データ合成パイプラインを設計しました。実世界のソフトウェアエンジニアリングとターミナルベースのコンピュータ操作シナリオから集めたシードタスクを出発点として、LLM で発想を広げ、検証可能なターミナルタスクドラフトを多数生成します。構築エージェントが各ドラフトを Harbor [Tea26c] 形式の具体的なタスクに変換します。構造化タスク説明、Docker 化された実行環境、対応するテストスクリプトが含まれます。その後、改良エージェントが人手で定義した評価基準に従ってタスクを検査し、反復的に改善します。Docker イメージを確実にビルドできること、テストケースがタスク仕様と一致すること、潜在的な悪用や抜け道に強い環境であることを保証します。全体として、Docker 構築精度が 90% を超える、多様で検証可能なターミナルエージェント環境を数千件生成します。

**Web コーパスからの合成。**

Web コーパスに基づく、LLM が検証したターミナルベースコーディングタスクを構築する拡張可能で自動化されたパイプラインを開発します。構築エージェントが自身が初回評価器も兼ねる閉ループ設計です。まずコード関連の Web ページを大規模に収集し、データ品質分類器で高品質な内容だけを残し、非技術的内容が中心のページや実質的なコードコンテンツのないページを除外します。さらに、ターミナル形式タスクに変換しやすい Web ページを選びます。トピックカテゴリと難易度レベルごとに層化サンプリングを行い、タスクプールの分布バランスと多様性を確保します。次に、Harbor のタスク構築仕様（[https://harborframework.com/docs/tasks/task-tutorial](https://harborframework.com/docs/tasks/task-tutorial)）を、選択したソース Web ページとともにコーディングエージェントへ与えます。タスクのスキーマ、形式要件、例タスクが含まれます。エージェントは（i）Web ページの内容に基づく完全なターミナルタスクを合成し、（ii）自身の出力に Harbor 検証スクリプトを実行します。失敗した場合は、すべての自動チェックに通るまで原因を診断し、タスクを反復修正します。この自己検証ループを通過したタスクだけを最終データセットに採用します。

#### 4.2.3 検索タスク

深層検索の情報探索タスクに向けて、難しい多段ホップ QA ペアを生成するデータ合成パイプラインを構築します。各問題は、複数の Web ソースから集めた根拠に基づく複数ステップ推論を必要とします。

**Web Knowledge Graph（WKG）の構築と問題生成。** 初期段階の検索エージェントの軌跡から、遭遇したすべての URL を収集・重複除去し、多様な領域にわたる高情報量の Web ページを 200 万件以上残します。LLM はエンティティ認識、ノイズフィルタリング、構造化情報抽出のための意味的解析を行います。WKG は新しいページで継続的に更新し、下流検証信号を利用したエンティティアラインメント、属性正規化、関係統合、意味的一貫性修正により精緻化します。WKG から低～中頻度のエンティティをシードノードとしてサンプリングし、重複実行を抑えながら多段ホップ近傍を展開して完全な部分グラフを作ります。高難度かつ複数領域の推論を狙ったプロンプトで、各部分グラフを複数エンティティの関係連鎖を暗黙に含む問題へ変換します。

**高難度問題のフィルタリングと検証。** 難易度と正しさを両立するため、三段階のパイプラインを使用します。（1）ツールなしの推論モデルが 8 回の独立試行のうち一度でも正答した問題を除外します。（2）基本的な検索、閲覧、計算を用いる初期エージェントが数ステップで解ける問題を除外します。（3）検証エージェントで双方向検証を行います。第 2 段階の検索軌跡から候補回答を集め、候補とアノテーションされた正解データの双方について問題-回答一貫性を独立検証します。回答が一意でない、根拠が矛盾する、ラベルが誤っているサンプルを除外します。これにより、高品質、高難度で信頼できる多段ホップ QA ペアが得られます。

#### 4.2.4 検索エージェントのコンテキスト管理を用いた推論

BrowseComp [Wei25] の性能は評価プロンプトと評価モデルの双方に敏感で、オープンソースの評価モデルは系統的なバイアスを持ち込む可能性があります。一貫性と再現性を確保するため、すべての評価モデルを用いる構成要素を OpenAI 公式評価プロンプトと非公開モデル o3-mini に統一します。ケーススタディでは、この構成が人手でアノテーションした正解データと最もよく一致したため、全検索エージェント評価に採用します。

先行研究 [Dee25a] はコンテキスト管理を導入し、*Discard-all* ではツール呼び出しの履歴全体を削除してコンテキストをリセットします。さらに、極端に長いコンテキスト、たとえば 100k トークンを超えた場合、モデル精度が大きく低下することを確認しました。そこで単純な *Keep-recent-k* 戦略を採用します。インタラクション履歴がしきい値 $k$ を超えたとき、直近 $k$ ラウンドより古いコンテンツを折り畳み、コンテキスト長を制御します。軌跡を $(q,r_{1},a_{1},o_{1},r_{2},a_{2},o_{2},\cdots,r_{n},a_{n},o_{n})$ とします。$q$ は問題、$r_{i}$ はラウンド $i$ の推論、$a_{i}$ は行動（*search*、*open*、*find*、*python* の 4 ツール）、$o_{i}$ はツール観測です。直近 $k$ ラウンドより前の観測だけを折り畳みます：$o_{i}\leftarrow\text{Tool result is omitted to save tokens.}\quad i=1,\ldots,n-k$。実験では $k=5$ とし、安定した改善が得られました。GLM-5 は keep-recent-$k$ なしの 55.3% から、ありの 62.0% へ向上します。keep recent $k$ の値を変える、またはコンテキスト長が所定のトークンしきい値に達した時点で keep-recent を実行する場合も、同じ結果になることを確認しました。

これをもとに keep-recent と Discard-all を組み合わせ、ハイブリッドな*階層型コンテキスト管理* 戦略を構成します。keep-recent を用いた推論中に合計コンテキスト長がしきい値 $T$ を超えた場合、ツール呼び出し履歴全体を破棄し、新しいコンテキストで再開します。その後も keep-recent 戦略を継続します。パラメータ検索により $T=32k$ を選択しました。

図 8 のように、この戦略は異なる計算予算のもとでコンテキスト空間を効果的に解放します。モデルはより多くのステップを実行でき、性能は一貫して向上します。Discard-all 単独と比べ、keep-recent-k との組み合わせは全予算で安定した改善をもたらし、最終スコアは 75.9 です。コンテキスト管理を備えたすべてのオープンソースモデルを上回ります。

#### 4.2.5 スライド生成

強化学習と棄却サンプリングファインチューニングで専門のスライド生成エキスパートを学習し、スライド生成の性能を体系的に改善する自己改善型パイプラインを採用します。まず Supervised Fine-Tuning（SFT）でモデルを初期化し、基本的なスライド生成能力を与えます。続いてプレゼンテーションスライドに一般的な美的・構造的性質に基づく多段階報酬で RL を行い、生成品質を大幅に改善します。さらに棄却サンプリングファインチューニングとマスクファインチューニングを行い、RL で得た知識を学習コーパスへ戻します。この手順はデータ品質とモデル能力を協調的かつ反復的に高めます。

HTML ベーススライド生成の報酬信号を三段階に分ける、**多段階報酬定式化**を提案します。

**Level 1：静的マークアップ属性。** 生成 HTML の宣言的属性を対象とし、配置、間隔、色、タイポグラフィ、彩度、その他のスタイル属性を含みます。専門的なデザイン原則に基づき、モデルがこれらの宣言を生成する際の挙動を規制するルールを設計します。生成 HTML が構文的に解析可能であることを保証するとともに、マークアップレベルの設計空間を、表現力、構造の明瞭さ、視覚的調和、可読性に適した部分空間へ制約します。架空画像と重複画像の検出機構も導入し、架空または冗長な図を抑制します。

**Level 2：実行時レンダリングプロパティ。** 静的検査と異なり、レンダリング中の DOM ノードの実行時プロパティ、たとえば要素の幅と高さ、境界ボックス、その他の幾何学的レイアウト指標を評価します。これらを制約し、生成スライドの空間構成を人間の美的嗜好に近づけます。高スループットでレンダリング処理を実行し、必要な実行時プロパティを抽出できる分散レンダリングサービスを開発しました。学習中には、長すぎるコンテンツの強制切り詰めや、間隔の過剰操作など、複数の報酬ハッキングが見られました（図 9）。レンダラー実装の悪用可能な抜け穴を解消し、報酬信号が幾何学的指標への表面的適合ではなく、美的に一貫したレイアウトを実際に促すよう改善しました。

![Slide RL 学習における報酬ハッキングの例](../../papers/glm-5/figure-09.png)

**図 9.** スライド RL 学習における報酬ハッキングの例。実行時レンダリングで根拠のある属性値を取得するため、このようなハッキング挙動に対して堅牢に評価できます。

**Level 3：視覚的知覚特徴。** 実行時レンダリング制約に加え、レンダリング後のスライドの知覚レベル評価を取り入れます。たとえば、異常な空白パターンを補助信号として検出し、全体の構図のバランスと視覚美観をさらに改善します。

**学習戦略。** RL 中にこれらの信号を共同最適化し、生成 HTML の構造的有効性、レイアウト構成、全体的な視覚美観を改善します。報酬設計に加えて動的サンプリングで学習分布を作り替えます。構造的に単純なサンプルの一部を確率的に除外し、より難しいページに最適化を集中させ、複雑な構成シナリオでの堅牢性を高めます。最適化を安定させるためトークン単位方策勾配損失 [Yu25] も採用します。さらに、同一サンプルの異なるロールアウト結果を複数の学習バッチに分配するバランス調整戦略を導入し、最適化バイアスを減らして学習安定性を高めます。

**棄却サンプリング。**

棄却サンプリング段階では、RL に用いた報酬関数をデータフィルタリングパイプラインへ転用し、高品質な学習部分集合を構築します。ページ単位のフィルタリング基準にはコード有効性とコンパイル可能性を含みます。軌跡単位ではツール実行正しさと全体的なコンテンツ多様性の制約も適用し、構造の一貫性を確保します。Best-of-$N$ 選択戦略により、独立に生成した複数候補から最高品質のサンプルを残します。分布を高品質なインスタンス側へ効果的に再重み付けし、サンプル効率と学習安定性を高めます。

**マスクに基づく改良。**

棄却サンプリングで低品質な出力の大半を除けますが、少数のページだけに欠陥がある軌跡もあります。これらを丸ごと捨てると、有効なデータ利用率が下がり、生成コストが増えます。そこで欠陥のあるページを自動特定してマスクし、同じ軌跡の高品質コンテンツを残すマスクに基づく修正機構を導入します。価値ある教師信号を維持し、有効なデータ効率を高め、不要な再生成のオーバーヘッドを減らすことで、全体の学習効率を改善します。

**実験的な改善。**

生成ページのうち 16:9 アスペクト比に厳密に準拠する割合は 40% から 92% へ増加し、ページのオーバーフローも大幅に減少しました。人手評価では、GLM-4.5 に対する GLM-5 の勝率はコンテンツ品質で 60%、レイアウト合理性で 57.5%、視覚美観で 65%、総合で 67.5% でした。提案した多段階報酬設計と自己改善型フレームワークの有効性を実証する結果です。

## 5 GLM-5 の中国製チップ基盤への適応

ハードウェアエコシステムが異質であるため、GLM-5 を多様な中国製チップ基盤へ適応するのは難しく、高性能なデプロイが複雑になります。それでも Huawei Ascend、Moore Threads、Hygon、Cambricon、Kunlunxin、MetaX、Enflame という国内主要 7 チッププラットフォームとの緊密な協力により、GLM-5 のフルスタック適応を実現しました。本節では Ascend Atlas シリーズを事例として、極限の量子化、高性能カーネル融合、高度な推論エンジンスケジューリングという三本柱に基づく適応手法を説明します。

**混合精度 W4A8 量子化。**

750B パラメータの GLM-5 を 1 台の Atlas 800T A3 機器に収めるため、高度な W4A8 混合精度量子化戦略を実装しました。msModelSlim（[https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/80RC3alpha003/devaids/auxiliarydevtool/modelslim_0001.html](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/80RC3alpha003/devaids/auxiliarydevtool/modelslim_0001.html)）を使い、モデル構成要素ごとに異なる精度を適用します。標準 Attention と MLP ブロックは W8A8（INT8）、MoE エキスパートは W4A8（INT4）へ圧縮し、精度を大きく損なわずメモリ使用量を劇的に削減します。外れ値抑制の QuaRot [Ash24] やスケーリング校正の `Flex_AWQ_SSZ` など高度なアルゴリズムも用い、低ビットデプロイの安定性を維持します。

**高性能融合カーネル。**

Ascend NPU における疎アテンションの計算ボトルネックを克服するため、Lightning Indexer、Sparse Flash Attention、MLAPO（Multi-head Latent Attention 前処理最適化）というカスタム融合カーネル群を開発しました。Lightning Indexer はスコア計算、ReLU、TopK 演算を一つのカーネルに統合し、NPU で計算とメモリアクセスを重複実行させます。Sparse Flash Attention カーネルは GLM-5 の疎パターンに特化して最適化し、KV キャッシュからの TopK トークン選択と疎アテンション計算を並行処理します。最後に MLAPO は 13 個の小さな前処理演算子を一つの「スーパー演算子」に融合し、Vector ユニットと Cube ユニットの並列処理でエンドツーエンド効率を高めます。

**推論エンジンの専用最適化。**

ハードウェア使用率を最大化するため、主要な二つの推論エンジン、vLLM-Ascend と SGLang を適応しました。

- **非同期スケジューリング：** vLLM 内で Device-to-Host（D2H）のサンプリングコピーと次のデコードステップの準備を重複実行させ、スケジューリングの「バブル」をなくします。
- **コンテキスト管理：** RadixCache（プレフィックス共有）や Prefix Cache（KV ストレージをシステム RAM へ拡張）により、長文脈性能に重要な KV エントリを効率的に再利用します。
- **並列戦略：** Attention Data Parallelism（DP）と MoE Expert Parallelism（EP）を組み合わせ、さらに AllReduce 演算を分割する FlashComm で、通信レイテンシを計算の背後に隠します。
- **Multi-Token Prediction（MTP）：** 1 推論ステップで複数トークンを生成し、NPU の計算密度を大幅に高め、系列全体の生成時間を短縮します。

これらのハードウェアレベルの協調最適化により、中国製の単一ノード上の GLM-5 は、海外製 GPU を二つ使うクラスタに匹敵する性能を達成し、長系列シナリオのデプロイコストを 50% 削減します。

#### 6.1.3 エージェント能力の評価

エージェント型ベンチマークには BrowseComp [Wei25]、BrowseComp-ZH [Zho25]、$\tau^{2}$-Bench [Bar25]、MCP-Atlas [Ban26a]、Tool-Decathlon [Li25b]、Vending-Bench 2 [Bac25]、GDPval-AA [Pat25] を使用します。BrowseComp は言語エージェントが Web 閲覧で難問を解く能力を測り、BrowseComp-ZH は主に中国語 Web を対象とします。BrowseComp のコンテキスト管理には DeepSeek-V3.2、Kimi K2.5 と同じ discard-all 戦略を使います。$\tau^{2}$-Bench は双制御環境における対話型エージェントの能力を評価します。Retail と Telecom には、ユーザーの早すぎる終了による失敗を避けるため、小さなプロンプト調整を加えます（[B.3 節](#b3-2-bench-向けに最適化したユーザーシミュレータ)）。Airline では Claude Opus 4.5 システムカード [Ant25a] の領域修正を適用し、より正確な結果を得ます。MCP-Atlas は、Model Context Protocol（MCP）サーバーが与えられた状態で LLM が複数ステップワークフローを実行する能力を測る、実世界のツール利用ベンチマークです。公平な比較のため全モデルを公開 500 タスクで再評価し、デプロイ条件によるタスク失敗を避けるためタイムアウトをタスク当たり 4 分から 10 分へ延長しました。MCP-Atlas の評価モデルは Gemini 3 Pro です。Tool-Decathlon もツール利用ベンチマークですが、実世界の長期タスクを対象とします。Vending-Bench 2 は、前世代の Vending-Bench より多くの実世界要因を含むシミュレーション環境で、長期的な事業運営における LLM のエージェント型能力を測ります。GDPval は経済的価値のあるタスクでの AI エージェントの性能に注目します。

表 7 に示すように、GLM-5 は GLM-4.7 からエージェント型ベンチマーク全般で大幅に改善しました。BrowseComp ではコンテキスト管理の有無にかかわらず、最前線 LLM の中で最先端です。BrowseComp-ZH でも Claude Opus 4.5 と Gemini 3 Pro を上回ります。$\tau^{2}$-Bench、MCP-Atlas、Tool-Decathlon という三つのツール利用エージェント型タスクでは Claude Opus 4.5 と同等で、強力なツール利用能力を示します。Vending-Bench 2 の \$4,432 という結果は、長期事業タスクを扱う能力をさらに示します。経済的シナリオの GDPval-AA では Claude Opus 4.5 を上回り、GPT-5.2（xhigh）に次ぐ成績です。

### 6.2 実世界のエージェント型エンジニアリング体験の評価

リーダーボードより実世界での体験が重要です。社内 CC-Bench を CC-Bench-V2 へ更新し、フロントエンド、バックエンド、長期タスクにまたがる現実的なエージェント型エンジニアリング環境で、モデルがエンドツーエンドタスクを正しく完遂できるか評価します。CC-Bench-V2 は人手ラベルを完全に廃し、Claude Code などのエージェント harness、単体テスト、Agent-as-a-Judge によって全自動で評価します。

**フロントエンド。** まずエージェントが生成したフロントエンドプロジェクトをビルドし、構文、依存関係、互換性のエラーを確認します。次に Playwright と bash ツールを備えた GUI エージェントがユーザーインタラクションをシミュレーションし、Agent-as-a-Judge でエンドツーエンドの正しさを検証します。

**バックエンド。** C++、Rust、Go、Java、TypeScript、Python の実世界のオープンソースプロジェクトからタスクを採取し、機能実装、バグ修正、回帰修復、性能最適化を扱います。すべての変更は、現実的なエンジニアリング制約のもとで単体テスト全体を通過する必要があります。

**長期。** まず、大規模コードベースでモデルの情報探索能力を評価します。これは人間の開発者のように正しいファイルを見つけ、プロジェクトコンテキストを理解するための前提です。次に、大量のコミット履歴を持つマージ済み Pull Request を採掘し、コミットを一貫したタスクチェーンにまとめて作る複数ステップ連鎖タスクによって、エンドツーエンドの正しさを評価します。エージェントはチェーンを順番に実行し、コンテキストを維持して段階間の依存関係を解決する能力を試されます。単体テストと Agent-as-a-Judge を組み合わせ、機能的な正しさと意味的な準拠の双方を検証します。

#### 6.2.1 フロントエンド評価：Agent-as-a-Judge

フロントエンド開発シナリオに特化した包括的な自動評価ベンチマークを開発しました。ランディングページ、管理ダッシュボード、データ可視化、グラフィックスとアニメーション、オンライン生産性ツール、インタラクティブゲーム、フォーム駆動型ワークフローなど、開発者が日常的に構築する多様なアプリケーションを対象とし、HTML、React、Vue、Svelte、Next.js という主要技術スタックを網羅します。

各テストケースは、具体的で実装可能な複数の仕様を含む*タスク*と、それぞれの仕様から直接導かれたチェック項目を持つ*チェックリスト*で構成されます。評価は二段階です。1）**静的検証**：生成コードを正常にビルド・実行できるか確認します。2）**Agent-as-a-Judge**：正常に動くコードに対し、GUI エージェントが人間のテスト挙動をシミュレーションして各チェック項目を対話的に検証し、要件の達成度に応じてスコアを付けます。指標は次のとおりです。*Build Success Rate（BSR）*は正常に初期化・実行できたプロジェクトの割合、*Instance Success Rate（ISR）*は関連する全仕様を満たしたプロジェクトの割合、*Check-item Success Rate（CSR）*は全チェック項目の細粒度な達成率です。データ分布と構築・検証手順の詳細は [付録 B.4.1](#b41-フロントエンド評価) に示します。

![Agent-as-a-Judge の評価パイプライン](../../papers/glm-5/figure-10.png)

**図 10.** Agent-as-a-Judge の評価パイプライン。生成した各フロントエンドプロジェクトをまずビルドして静的正しさを確認し、成功したインスタンスを自律的な Judge Agent が対話的にテストして各チェック項目の機能的正しさを判断します。

**Agent-as-a-Judge。**

フロントエンドの正しさは本質的に視覚的かつ対話的です。バグはユーザーがボタンをクリックしたりウィンドウサイズを変えたりしたときに初めて現れる場合が多く、静的解析と固定テストスイートだけでは十分ではありません。そこで Agent-as-a-Judge（図 10）を導入します。生成プロジェクトを Docker コンテナにデプロイし、ビルドして静的な正しさを確認します。成功したインスタンスは自律的な Judge Agent に渡します。これは Playwright MCP ツールを備え、Claude Sonnet 4.5 を使用する Claude Code で、閉ループで動作します。各チェック項目についてソースコードを読み、実際の UI と対話し（クリック、キー入力、スクリーンショット）、ターミナル出力を調べ、合格か不合格かを判断します。

信頼性を検証するため、Agent-as-a-Judge と独立した人間の専門家の判断を二つの観点で比較します。*項目単位の一貫性*では 130 チェック項目を抽出し、人間の専門家が独立にスコアを付け、エージェントの判断と比較しました。94% で一致し、不一致は機能的仕様ではなく、主観的な視覚品質基準に集中しました。*ランキングの一貫性*では Claude Sonnet 4.5、Claude Opus 4.5、Gemini 3 Pro、GLM-4.7、DeepSeek-V3.2 など 8 種類の最先端モデルを自動フレームワークと人間の双方で評価しました。モデルランキングの Spearman 相関係数は 85.7% で、強い正の相関があります。

表 8 のように、GLM-5 は BSR 98.0% を達成し、CSR では Claude Opus 4.5 と競争力があります。一方で、三つのスタックすべてに明確な ISR の差が残ります。個々の要件の大半は満たせても、タスク全体をエンドツーエンドで完遂する能力では Claude Opus 4.5 に及ばないことを示します。

#### 6.2.2 バックエンド評価

バックエンド評価では、コーディングエージェントが現実的なエンジニアリング制約のもとで、実世界のサーバー側コードベースに、テストを正しく通過する変更を加えられるかを測ります。Python、Go、C++、Rust、Java、TypeScript の 6 言語にまたがる 85 タスクを選定しました。検索エンジン、データベースエンジン、Web フレームワーク、AI 推論サービス、知識管理システム、独立したアルゴリズム・システムプログラミング課題などの領域を含みます。タスクの種類は機能実装、バグ修正、回帰修復、性能最適化で、日常のバックエンド開発の多様性を反映します。

全自動評価を可能にするため、各タスクには機能の正しさとエッジケース処理を検証する、人手で作成した 5～10 個の単体テストを用意します。タスクは Terminal-Bench 形式でパッケージ化され、プロジェクトの実際のビルド環境から初期化した Docker コンテナ内で動きます。エージェントには必要な変更を説明する自然言語の問題記述を与えます。Pass@1 を報告し、関連する単体テストがすべて通った場合だけタスクを解決済みとみなします。この厳格な全件合格基準によりベンチマークは特に難しく、GLM-5 と Claude Opus 4.5 は同等の性能で（表 8）、双方とも GLM-4.7 を大幅に上回ります。

#### 6.2.3 長期評価

長期評価は、本番品質のエージェント型エンジニアリングと単一ターンの Vibe Coding を分ける能力を対象とします。すなわち、巨大なコードベース内を移動し、各行動が後続ステップのコンテキストを変える複数ステップ開発を遂行する能力です。これを相互補完的な二つのタスクに分解します。

**大規模リポジトリ探索。** 一定以上に複雑なコーディングタスクには、大規模で未知のリポジトリから正しいソースファイルを見つける能力が不可欠です。数万ファイルを含む、実在するスター数の多い GitHub リポジトリを用いて自動ベンチマークを構築します。各問題は業務上の意味の水準で、ユーザー向けの自然言語として記述し、ファイル名、クラス名、関数名への言及を厳密に避けます。また、ユーザー向け説明から実装へ至るまでに、一つまたは二つの論理的な段階を必要とします。たとえば、生成動画のリップシンクがずれるという問題は、動画生成バックエンド内のパラメータ調整ブロックに対応します。対象ファイルは探索難易度を最大化するよう選びます。ディレクトリの深さが 3 レベル以上、キーワード検索では見つけにくい不透明な名称、リポジトリ内で重複しない固有機能、主要機能領域の外側、という条件です。3 回の実行の平均 Pass@1 を報告し、探索中にエージェントが対象ファイルを正常に読めれば解決済みとします。このタスクでは GLM-5 が Claude Opus 4.5 を上回り（表 8）、両者とも GLM-4.7 を大幅に上回ります。リポジトリ探索の成否は純粋なコード生成能力よりも、ディレクトリ単位の推論と意味的な関連付けによってファイル空間を反復的に狭める戦略的検索に左右されることを示します。エージェント型ツール利用軌跡による GLM-5 の学習は、この点で明確な優位性をもたらします。

**複数ステップ連鎖タスク。** SWE-bench などの主流コーディングベンチマークは評価を単一コミットの独立した変更へ単純化しているため、一つのステップが次のステップのコードベース状態を変える段階的開発の能力を評価できません。そこで高品質なリポジトリのマージ済み Pull Request を採掘し、次のパイプラインでタスクチェーンを組み立てる長期ベンチマークを構築します。

1. **PR のフィルタリング。** テストを含み、3～15 コミットで、線形（非マージ）履歴を持つマージ済み PR だけを残します。
2. **意味的グループ化。** LLM が隣接コミット間の意味的関連性をペア単位で評価し、動的プログラミングでコミット順を保ちながらグループ内の一貫性を最大化する、タスクグループの最適な分割を求めます。
3. **パッチの仕分け。** 各タスクの累積差分を三つに分けます。*正解パッチ*（エージェントが生成すべき中核コード）、*テストパッチ*（検証テスト）、*自動適用パッチ*（自動適用する設定とフィクスチャ）です。
4. **問題文の生成。** LLM がパッチとコミットメッセージからタスクごとの自然言語問題記述を生成します。
5. **タスク分類。** タスクを自動分類し（機能 / バグ修正 / リファクタリング / テスト / 設定）、エラー解消、重要経路精度、テスト通過の三軸で評価します。
6. **環境検証。** Docker 環境を構築し、正解パッチを適用してチェーン全体に回帰がないことを確認します。

$K$ タスクのチェーンが与えられると、エージェントは基礎コミットから順番に作業します。タスク $k$ を終えると変更をコミットし、タスク $k{+}1$ の自動適用パッチを適用するため、コードベース状態は累積的に変化します。評価では各コミットを順に確認し、完全テストスイートの実行前にタスク $1$ から $k$ までのテストパッチを累積適用します。現在のタスクの失敗と、それ以前のタスクに対する回帰の双方を検出できます。個々のタスクの Pass@1 を報告します。この連鎖型かつ状態再帰型の設計は、単一コミットのベンチマークでは測れない長距離コンテキスト追跡、計画、段階的開発能力を直接評価します。表 8 のように、GLM-5 は GLM-4.7 から大幅に改善しましたが、Claude Opus 4.5 との差はまだ大きいままです。チェーン全体でエラーが累積するためです。一つのタスクでの不適切な変更が、後のタスクのテストをひそかに壊す可能性があります。この差を縮めるには、長文脈の一貫性と長期的な自己修正を前進させる必要があり、いずれも現在研究を進めている領域です。

#### 6.2.4 変化し続ける SWE タスクでの評価

SWE-bench Verified は静的かつ公開された人手検証済みテストセットで、公開から 2 年以上経過しているため、SWE-rebench [Bad25] でも評価します。SWE-rebench は自動パイプラインで新しい実世界の GitHub issue 修正タスクを継続的に採掘します。汚染を避け、時間変化に強い評価が可能で、静的ベンチマークの性能ではなく、新しいソフトウェアエンジニアリング問題への汎化をより適切に測れます。表 9 は SWE-rebench における GLM-5 の公式性能です。GLM-5 が新しい SWE 問題へ効果的に汎化できることを確認できます。

### 6.3 実世界の汎用能力の評価

![GLM-5 の実世界汎用能力の比較](../../papers/glm-5/figure-11.png)

**図 11.** 五つの実世界汎用能力領域における GLM-4.7 と GLM-5 の性能比較。

標準化された学術ベンチマークは有用な信号を与えますが、モデルが実際にどう使われるかを十分に捉えられません。この差を認識し、デプロイで観察した高頻度のユーザーインタラクションパターンに基づく実世界の汎用能力で GLM-5 を評価します。機械翻訳、多言語対話、指示遵守、世界知識、ツール呼び出しを含みます。

従来のベンチマーク中心の評価と異なり、ユーザーが直接感じられる品質向上につながる改善を測ることが目的です。各能力には、社内の人手評価と自動評価、外部の人手評価と自動ベンチマークを組み合わせ、診断の細かさとモデル間の比較可能性を両立します。外部ベンチマークを使う場合は、狭く構成されたテスト分布ではなく、現実的なインタラクションパターンを反映するデータセットを優先します。

図 11 は五つの実世界能力領域における GLM-5 と GLM-4.7 の比較結果です。機械翻訳、多言語対話、指示遵守、世界知識、ツール呼び出しの全評価軸で、GLM-5 は一貫して改善しています。

各能力の詳細な評価プロトコルとデータセット説明を以下に示します。

#### 6.3.1 機械翻訳

**ZMultiTransBench。**

この社内データセットは、自社収集した高頻度の翻訳シナリオから得た 1,220 サンプルで構成されます。中国語からスペイン語（$300$）、ロシア語（$250$）、フランス語（$220$）、韓国語（$200$）、日本語（$150$）、アラビア語（$50$）、ドイツ語（$50$）という 7 言語ペアを含みます。全サンプルは翻訳学の正規教育を受けた大学院生が選別・翻訳し、独立に検証しました。人工的なテストケースより、自然な利用状況を重視しています。固定ベースライン応答とのペア単位比較で評価し、GPT-4.1 に基づく自動評価器が意味の忠実性、流暢さ、総合的な翻訳品質を判断します。

**MENT-SNS。**

言語的に難しいコンテキストでの堅牢性をさらに評価するため、MENT [Tia26] のソース文を採用します。Social Network Services（SNS）、Cross-Culture、Poetry、Literature の四領域にわたる $753$ 組の英中文ペアです。スラング、同音異義の言葉遊び、慣用表現、歴史的言及、比喩表現など複雑な言語現象で翻訳をストレステストするために選んでいます。ZMultiTransBench と同様、全サンプルは専門教育を受けた大学院生が選別・検証しました。固定ベースライン応答との同じペア単位比較プロトコルを用い、GPT-4.1 を自動評価モデルとします。

#### 6.3.2 多言語対話

**LMArena。**

LMArena（[https://arena.ai/leaderboard/text](https://arena.ai/leaderboard/text)）の Elo レーティングを報告します。コミュニティが投稿した大規模なペア単位比較から得られた値で、自由形式対話におけるモデルの相対的な好みを反映し、会話性能の外部信号となります。

**ZMultiDialBench。**

公開リーダーボードに加えて、社内の多言語対話ベンチマークである ZMultiDialBench でも人手評価します。データセットは多様な対話カテゴリにわたる 141 件の選別済みインスタンスで構成されます。複数国の各言語のネイティブ話者である注釈者が提供した高品質な会話データと、オンラインユーザーが報告した難しい失敗ケースから収集しました。人間の注釈者は、カテゴリ固有の標準評価基準に従い、匿名化したモデル応答に 1～10 のポイント単位のスコアを付けます。

#### 6.3.3 指示追従

**IF-Badcase。**

IF-Badcase は、本番環境の実ユーザーが報告した指示遵守の**失敗事例**から作った社内ベンチマークです。現実的で複数の制約を持つ指示に厳密に従えるかを評価し、手順の正確性、論理的一貫性、厳格な書式要件を重視します。詳細なチェックリストに基づくプロトコルで、順序付きステップ、ルールベース条件、構造的仕様など明示的制約の遵守を検証します。全サンプルを人間の専門家がアノテーション、レビュー、反復フィルタリングし、450 件のテストインスタンスに選別しました。

**IF-Bench [Pya25]。**

IF-Bench は特定の書式ルール、長さ上限、内容上の制約など、複雑で客観的な制約に LLM が従う能力を評価します。自由形式生成品質ではなく検証可能な遵守に注目し、正確な指示遵守能力を定量化します。

**MultiChallenge [Sir25]。**

MultiChallenge は現実的な複数ターン対話型シナリオで LLM を調べます。正確な指示遵守、コンテキスト配分、文脈内推論を必要とする複雑なインタラクションを対象とします。

#### 6.3.4 世界知識

**SimpleQA [Wei24]。**

SimpleQA は、疑義のない単一の答えを持つ難しい問題で短文の事実性を測ります。応答を正解、不正解、未回答に分類してモデルの校正を評価し、生成長さより精度を優先します。

**Chinese SimpleQA [He24]。**

SimpleQA の方法を中国語コンテキストに適応し、6 つの主要領域と 99 のサブトピックにわたる事実性を評価します。信頼できる自動採点向けに設計された、高品質かつ静的な短文回答問題を用いて、LLM の知識精度を測ります。

#### 6.3.5 ツール呼び出し

**ToolCall-Badcase。**

ToolCall-Badcase は、本番環境でユーザーが報告したツール呼び出しの**失敗事例**から作った社内ベンチマークです。各インスタンスには検証可能な正解ツール呼び出しがあり、ツール選択と引数正しさを客観的に評価できます。モデルが（1）正しいツールを呼び出すか、（2）正しく構造化され、意味的にも正確な引数を渡すかを評価します。曖昧さを除き評価可能性を確保するため、全サンプルを複数回レビューし、書き直しと検証しました。最終データセットは、現実的なツール呼び出し能力を反映する 200 件のテストケースで構成されます。

## 7 結論

本報告では、高性能な推論と極限の計算効率の隔たりを根本から埋める次世代基盤モデル GLM-5 を紹介しました。「Vibe Coding」から真の「エージェント型エンジニアリング」へ移行することで、オープンウェイトモデルが複雑な実世界のワークフローにおいて、最上位の非公開システムに匹敵できることを示しました。GLM-5 は AI の実用性におけるパラダイムシフトを表します。モデルをオープンソースとすることで、コミュニティが静的ベンチマークの先へ進み、効率的なエージェント型汎用知能の最前線を探究できるようにします。AI エージェントが複雑なタスクを自律的に計画、実装、反復する新時代を後押しします。

## 8 イースターエッグ

**「Pony Alpha」**の実験は、私たちにとってまさに重要な転機でした。GLM-5 を OpenRouter 上で匿名公開するのは大胆な決断でしたが、その結果は大きな確信を与えてくれました。ブランド名を外すことでモデル本来の能力そのものを評価してもらい、純粋で偏りのないフィードバックを得られました。概要は次のとおりです。

Pony Alpha は数日のうちに大きな話題となりました。OpenRouter コミュニティの開発者は、特に複雑なコーディングタスク、エージェント型ワークフロー、ロールプレイシナリオにおける卓越した性能に気づき始めました。

憶測が広がり、Anthropic などの研究所から流出した更新（Claude Sonnet 5）、Grok の非公開リリース、DeepSeek V4 ではないかと多くのユーザーが予想しました。初期統計では、25% が Claude Sonnet 5、20% が DeepSeek、10% が Grok、残りが GLM-5 と予想しました。

実際に GLM-5 だったと最終確認された瞬間は、私たちにとって非常に大きな意味を持ちました。中国の LLM が最前線の水準で競争できるのかという疑念に、事実上答えることができたからです。Pony Alpha（GLM-5）の成功は単なるベンチマークスコアの問題ではなく、エンジニアリング水準の信頼性へ焦点を移したことを意味します。

匿名公開により、地政学的なバイアスを越えることができました。コミュニティがモデルを受け入れたのは、実際に機能したからです。この成功を喜びつつも、現実的でなければなりません。オープンウェイトモデルと非公開最前線の頂点との差は縮まっていますが、競争はまだ終わっていません。拡張可能で効率的、かつ知的なシステムが実現できることの限界を押し広げる姿勢は変わりません。

### B.2 ARC ベンチマークの評価

Humanity's Last Exam（HLE）およびその他の推論タスク：最大生成長さは $131,072$ トークン（$temperature=1.0,top\_p=0.95,max\_new\_tokens=131072$）です。既定ではテキストのみの部分集合を報告し、* を付した結果は完全セットによるものです。GPT-5.2（medium）を評価モデルとします。HLE-with-tools の最大コンテキスト長は $202,752$ トークンです。

SWE-bench および SWE-bench Multilingual：調整した指示プロンプトと OpenHands を使って SWE-bench スイートを実行します。設定は $temperature=0.7,top\_p=0.95,max\_new\_tokens=16384$、コンテキストウィンドウは 200K です。

BrowseComp：コンテキスト管理なしでは直近 5 ターンの詳細を残します。コンテキスト管理ありでは DeepSeek-V3.2 と Kimi K2.5 と同じ discard-all 戦略を使います。

Terminal-Bench 2.0（Terminus 2）：Terminus フレームワークで、$timeout=2h,temperature=0.7,top\_p=1.0,max\_new\_tokens=8192$、128K コンテキストウィンドウの設定で評価します。リソース上限は CPU 16 個、RAM 32 GB です。

Terminal-Bench 2.0（Claude Code）：Claude Code 2.1.14（思考モード）で、$temperature=1.0,top\_p=0.95,max\_new\_tokens=65536$ の設定で評価します。実時間時間上限は除去しますが、タスクごとの CPU とメモリ制約は維持します。Claude Code に起因する環境上の問題を修正し、曖昧な指示を解消した検証済み Terminal-Bench 2.0 データセットでも結果を報告します（[https://huggingface.co/datasets/zai-org/terminal-bench-2-verified](https://huggingface.co/datasets/zai-org/terminal-bench-2-verified)）。スコアは 5 実行の平均です。

CyberGym：Claude Code 2.1.18（思考モード、Web ツールなし）で、$temperature=1.0,top\_p=1.0,max\_new\_tokens=32000$、タスク当たり 250 分のタイムアウトで評価します。1,507 タスクに対する単一実行 Pass@1 です。

MCP-Atlas：全モデルを思考モード、公開部分集合 500 タスク、タスク当たり 10 分のタイムアウトで評価します。評価モデルは Gemini 3 Pro です。

$\tau^{2}$-Bench：Retail と Telecom では、ユーザーの早すぎる終了による失敗を避けるため、小さなプロンプト調整を加えます。Airline には Claude Opus 4.5 システムカードが提案する領域修正を適用します。

Vending-Bench 2：Andon Labs が独立に実行します（[https://andonlabs.com/evals/vending-bench-2](https://andonlabs.com/evals/vending-bench-2)）。

- Just generate one line at a time to simulate the user's message.
- Do not give away all the instruction at once. Only provide the information that is necessary for the current step.
- Do not hallucinate information that is not provided in the instruction. Follow these guidelines:
 1. If the agent asks for information NOT in the instruction:

- Try to make the conversation as natural as possible, and stick to the personalities in the instruction.
# Constraint Handling:
- Provide requests strictly based on what is explicitly stated in the instruction.
- Do not assume, extend, substitute, or generalize in any form.
- Do not modify or relax constraints on:
- Time / Date
- Budget
- Specific terms (e.g., "same" must not be replaced with "similar")
- Core Rule: Any attribute NOT mentioned in the instruction can be either changed or kept the same
- Examples:
 - If instruction says "exchange red item to blue": Only color must change, other attributes (size, material, etc.) are flexible
 - If instruction says "exchange red item to blue, keep the same size": Both color must change AND size must stay the same
- Exception: Only follow additional constraints when explicitly stated in the instruction
# Domain-Specific Rules:
## For Retail scenarios:
- Focus on product attributes and exchange/return processes as specified in instructions.
- During confirmations: Always respond based strictly on the original instruction, never deviate to match agent's provided options. Restate your requirement from the instruction rather than selecting from agent's choices.
 - Example: If the agent provides specific options (A/B/C) but the instruction states a general requirement (e.g., "same as pending order"), always restate or confirm based on what the instruction says, not by directly selecting from the agent's provided options.
# When NOT to finish the conversation:
- Do not end until you have clearly and completely expressed all your requirements and constraints.
- Do not end until the agent has completed all tasks mentioned in the instruction and verified no operations were missed.
- Do not end if the agent's execution results do not match your expectations or are incorrect/incomplete.
# When you CAN finish the conversation:
- Only when all above conditions are satisfied AND all tasks are completed correctly.
- OR when you have clearly expressed complete requirements but the system explicitly states it cannot complete them due to technical limitations - in this case, accept transfer to human.
# How to finish the conversation:
- If the agent has completed all tasks, generate the '###STOP###' token to end the conversation.
# Note:
- You should carefully check if the agent has completed all tasks mentioned in the instruction before generating '###STOP###'.

**データ例**

各テストケースは、**Task**、**Checklist**、**専用 Environment**の三要素で構成されます。代表例を次に示します。

```text
 Task: Develop an online drawing tool that includes a brush, an eraser, a white canvas, and a save button.
 The brush color and thickness should be selectable via buttons on the left. Users can draw on the canvas by clicking and dragging the mouse.
 The eraser size should be selectable via buttons on the left. Users can erase content by clicking and dragging the mouse over the canvas.
 Once the drawing is complete, clicking the "Save" button should allow the user to save the image locally.
 Please implement this using the React framework in the current directory.

 Checklist:
 The user can select the brush color and thickness using the left-hand buttons, and drawing is functional via mouse click-and-drag on the canvas.
 The user can select the eraser size using the left-hand buttons, and erasing is functional via mouse click-and-drag on the canvas.
 Upon clicking the "Save" button, the generated image is successfully saved to the local machine.
```

**データ構築と検証**

データ品質を確保するため、厳格な四段階パイプラインを実施します。

- Stage 1：Task Synthesis。senior フロントエンドエキスパートがタスクを設計し、実世界のエンジニアリング課題を反映しながら、多様なシナリオと技術にわたる均衡した分布を保ちます。
- Stage 2：Checklist Generation and Refinement。まず Claude Sonnet 4.5 でタスク仕様 $T$ に基づく候補チェックリストを合成し、専門家が綿密に監査・統合します。複数回の改良により、各チェック項目が意味的に曖昧でなく、客観的で、ユーザー要件を漏れなく網羅することを保証します。
- Stage 3：Execution-ベース Correction。Agent-as-a-Judge フレームワークと人間の専門家の間で cross-検証を行います。判断の不一致があれば基礎データを再評価・修正し、潜在的なノイズを取り除きます。
- Stage 4：Dynamic Benchmark Iteration。高い識別力を維持するため、状態-of-the-art コーディングエージェントにとって簡単になったタスクを除きながらテストスイートを反復更新します。専門家主導の選別により、最終的に 220 件の高品質フロントエンドコーディングタスクと対応チェックリストを構築しました。
