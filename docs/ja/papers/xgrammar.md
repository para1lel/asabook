## 概要

LLM エージェントの応用は複雑さと多様性を増しており、コード、構造化された関数呼び出し、身体性を持つエージェントのコマンドとして解析できる構造化出力への需要が高まっている。こうした発展により、LLM 推論における構造化生成が強く求められている。文脈自由文法は、制約付きデコーディングによって構造化生成を実現する柔軟な方法である。しかし、文脈自由文法の実行時には、語彙中の全トークンについて複数のスタック状態をたどる必要があり、構造化生成に無視できないオーバーヘッドが生じる。本稿では、大規模言語モデル向けの柔軟かつ効率的な構造化生成エンジン XGrammar を提案する。XGrammar は、語彙を事前検査可能な文脈非依存トークンと、実行時に解釈する必要がある文脈依存トークンに分割し、文脈自由文法の実行を高速化する。さらに、文法の文脈を拡張して文脈依存トークン数を減らす変換を構築する。加えて、文脈依存トークンの検査を高速化する効率的な永続スタックを構築する。最後に、文法計算と GPU 実行を重ね合わせるため、文法エンジンと LLM 推論エンジンを協調設計する。評価の結果、XGrammar は既存手法に対して最大 100 倍の高速化を達成した。LLM 推論エンジンと組み合わせることで、エンドツーエンドの低遅延 LLM サービングにおいて、ほぼゼロのオーバーヘッドで構造化生成を実現できる。

## 1 はじめに

<span id="figure-01"></span>

![図 1. 提案手法の概要。XGrammar はまずプッシュダウン・オートマトンで直前までの LLM 出力を解析し、多様な文法を柔軟に扱いながら照合スタック状態を得る。次にスタック先頭を用い、主要な最適化である適応的トークンマスクキャッシュを索引して部分マスクを取得する。部分マスクの大半は文脈非依存トークンであり、前処理時に決定される。一方、少数の文脈依存部分は実行時に決定される。これにより完全なトークンマスクが得られ、効率的な制約付きデコーディングが可能になる。](../../papers/xgrammar/figure-01.png)

**図 1.** 提案手法の概要。XGrammar はまずプッシュダウン・オートマトンで直前までの LLM 出力を解析し、多様な文法を柔軟に扱いながら照合スタック状態を得る。次にスタック先頭を用い、主要な最適化である適応的トークンマスクキャッシュを索引して部分マスクを取得する。部分マスクの大半は文脈非依存トークンであり、前処理時に決定される。一方、少数の文脈依存部分は実行時に決定される。これにより完全なトークンマスクが得られ、効率的な制約付きデコーディングが可能になる。

大規模言語モデル (LLM) の近年の進歩は、コード生成 [Che21, Wan21h]、デバッグ [Pea22, Moz24]、関数呼び出しによる外部ツールの利用 [Ope24j, Lan24]、ロボット制御 [Liu23q] といった複雑な応用に新たな可能性をもたらした。これらの応用では、LLM の出力が JSON、SQL、あるいはタスク固有の形式や文法に従うことを要求する*構造化生成*が強く求められる。下流のアプリケーションは、構造化出力をそのまま利用してシステムとの後続インタラクションを行える。

制約付きデコーディング [Deu19, Kuc23] は、構造化生成で広く用いられる方法である。各デコードステップで構造に適合するトークンだけを生成可能にすることで、LLM 出力が指定構造に従うことを保証する。各ステップではまず語彙全体を走査して無効なトークンを特定し、その確率をゼロにして生成を防ぐ。多様な応用で生じる豊富な構造形式を扱うには、制約を記述し検査する柔軟な仕組みが必要である。文脈自由文法 (CFG) [Cho56, Poe22, Sch21d] は、一連の規則によって構造を定義する一般的な方法を提供する。各規則は文字列または別の規則列を含み、再帰的に組み合わせて複雑な構造を表現できる。正規表現などの代替形式と比べ、CFG は再帰構造を許すため柔軟性が高く、JSON、SQL、ドメイン固有言語 (DSL) などの一般的な言語の記述に適している。

しかし、この柔軟性のため、CFG をそのまま制約付きデコーディングに適用するのは効率的でない。第 1 に、各デコードステップで語彙中の候補トークンすべてに対して CFG を解釈する必要があり、Llama 3.1 [Dub24] では語彙が 128k に達する。第 2 に、CFG の解釈には、それまでに照合した再帰規則を追跡するスタック状態が必要であり、スタックパターンの組合せをすべて事前計算してキャッシュすることはできない。第 3 に、LLM が生成する各トークンは複数文字からなり、文法要素の境界をまたいで、実行時に再帰やスタックのポップを引き起こす場合がある。この境界の不一致を文法実行時に注意深く扱わなければならない。

本稿では、これらの課題を解決するため、大規模言語モデル向けの柔軟かつ効率的な構造化生成エンジン XGrammar を導入する。XGrammar は文脈自由文法 (CFG) を表すバイト単位のプッシュダウン・オートマトンを構築する。[図 1](#figure-01) に示す主要な着想は、トークンをオートマトンの局所的な文脈だけで判定できる**文脈非依存トークン**と、スタック状態全体が必要な**文脈依存トークン**に分類することである。すべての文脈非依存トークンの正当性を事前計算し、オートマトン上の位置ごとに適した記憶形式を持つ適応的トークンマスクキャッシュへ保存する。また、各局所規則の文脈を拡張し、文脈依存トークン数を削減するアルゴリズムを構築する。さらに、永続スタックにより状態の分岐とロールバックを高速化し、文脈依存トークン検査とキャッシュ前処理を促進する。最後に、文法エンジンと LLM 推論エンジンを協調設計して文法計算と GPU 計算を重ね合わせ、構造化生成のオーバーヘッドを最小化する。

評価の結果、文脈自由文法のトークン当たりレイテンシは、現在の最先端手法と比べて最大 100 倍削減された。また、XGrammar を統合した Llama-3.1 向け LLM サービングエンジンは、H100 GPU 上の構造化出力を伴うエンドツーエンド・サービングで最大 80 倍高速化した。XGrammar はオープンソース化し、主要なオープンソース LLM フレームワークへ統合する。

本稿の主な貢献は次のとおりである。

- 文脈非依存トークンを利用してマスク生成のオーバーヘッドを大幅に減らす、適応的トークンマスクキャッシュを導入する。

- 高速なロールバックと状態分岐を可能にし、文脈依存トークン処理を促進する永続実行スタックを設計する。

- LLM サービングフレームワークと協調設計した効率的な文法エンジンを構築し、構造化生成のオーバーヘッドを最小限に抑える。

## 2 背景

<span id="section-2-1"></span>

### 2.1 LLM の制約付き生成

<span id="figure-02"></span>

![図 2. トークン単位マスクによる制約付きデコーディング。各ステップで構造上無効となるトークンを LLM が生成することを防ぐ。](../../papers/xgrammar/figure-02.png)

**図 2.** トークン単位マスクによる制約付きデコーディング。各ステップで構造上無効となるトークンを LLM が生成することを防ぐ。

GPT-4 [Ope23]、Llama [Dub24]、Mistral [Jia23] などの大規模言語モデル (LLM) は自己回帰的にテキストを生成し、先行するトークン列に基づいて一度に 1 トークンを予測する。初期プロンプトから始まり、応答が完了するまでモデルがトークンを順次追加する。LLM ではトークンが基本的な入出力単位である。各トークンは固定文字列を表すが、完全な意味単位に対応するとは限らず、Unicode 文字を途中で分割することもある [Wan20e]。この性質が構造化テキスト生成を難しくする。各ステップでモデルは語彙全体に対する logits ベクトルを出力し、softmax 関数 [Bri89] で確率分布に変換する。サンプラーはこの分布から次のトークンを選ぶ。

制約付きデコーディングは、[図 2](#figure-02) のように各ステップで利用可能なトークンを制限し、LLM 生成テキストの構造を誘導する。各ステップで必要な構造に違反するトークンを無効と判定し、その logit を $-\infty$ に設定する。softmax 後の確率はゼロとなる一方、他の有効トークン間の相対確率は保たれる。これにより、有効なトークンだけがサンプリングされる。無効トークンの特定とマスクを効率よく行うことは、生成速度を直接左右するため重要である。

<span id="figure-03"></span>

![再帰的に構成できる配列と文字列の CFG、および文字列照合時に可能な 2 つの照合スタック。](../../papers/xgrammar/figure-03.png)

**図 3.** 上: 再帰的に構成できる配列と文字列の文脈自由文法。この CFG は [図 1](#figure-01) のプッシュダウン・オートマトンへ変換される。<code>[^"\\]</code> は <code>"</code> と <code>\\</code> 以外の全文字を表す。下: 文字列 <code>["a</code> を CFG に照合するときに可能な 2 つの照合スタック。各スタックは CFG 規則の可能な展開を表す。スタック中の辺とノードは [図 1](#figure-01) の PDA の遷移と状態に対応する。

<span id="section-2-2"></span>

### 2.2 文脈自由文法とプッシュダウン・オートマトン

文脈自由文法 (CFG) [Cho56] は、構造化生成の構造を定義するため広く使われている。[図 3](#figure-03) の例のように、CFG は複数の規則からなり、各規則は文字または別規則への参照を含む。これらを再帰的に組み合わせて複雑な構造を定義できる。そのため CFG は、JSON、SQL、さまざまなドメイン固有言語の記述に適する。CFG の再帰性は、LLM の構造化生成でもよく使われる正規表現などの単純なパターンより高い表現力をもたらす。

プッシュダウン・オートマトン (PDA) [Sch63, Eve63] はスタックで入れ子構造を管理し、CFG が生成する言語の認識に一般に使われる。本稿では、元の定義と等価でありながらアルゴリズムの説明に適した PDA 定義を用いる。[図 1](#figure-01) に PDA の例を、[図 3](#figure-03) にそのスタックの詳細を示す。PDA は複数の有限状態オートマトン (FSA) からなり、各 FSA は 1 つの文法規則を表し、スタックが再帰的な規則展開を扱う。FSA の遷移には、特定の文字を受理する文字辺と、別規則への再帰的な進入を可能にする規則参照辺がある。PDA の形式的定義は [第 7 節](#section-7) に示す。文字列を照合するとき、PDA は主規則から開始し、規則参照辺をスタックへプッシュして子規則を再帰的に展開する。規則全体を照合するとスタックをポップし、直前の規則へ戻る。スタック先頭には現在到達したノードを置く。文法が非決定的で、同じ入力文字に対して複数の遷移があり得る場合、PDA は経路ごとに複数の並列スタックを維持できる。しかし、スタック長が無制限であるため状態数は無限となり、すべての場合のトークンマスクを事前計算することは現実的でない。これが効率的な制約付きデコーディングを難しくする。

## 3 XGrammar

[図 1](#figure-01) に示すように、XGrammar はバイト単位のプッシュダウン・オートマトンで文脈自由文法を解釈する。各文字辺は 1 バイト以上を含められるため、不規則なトークン境界を処理し、UTF-8 文字の一部を含むトークンも扱える。照合を高速化するオートマトン構造の最適化は [第 3.4 節](#section-3-4) で述べる。前処理段階では [第 3.1 節](#section-3-1) の適応的トークンマスクキャッシュを生成し、文脈非依存トークンを事前計算して実行時のマスク生成を高速化する。[第 3.2 節](#section-3-2) の文脈拡張がこのキャッシュの有効性をさらに高める。実行時にはキャッシュがマスクの大部分を素早く生成し、[第 3.3 節](#section-3-3) の永続実行スタックが残りの文脈依存トークンを効率よく処理する。また、[第 3.5 節](#section-3-5) ではマスク生成と LLM 推論を重ね合わせ、制約付きデコーディングのオーバーヘッドを最小化する。LLM がマスク制約下で新しいトークンを生成すると、そのトークンでプッシュダウン・オートマトンのスタック状態を更新し、次のマスク生成に用いる。

<span id="section-3-1"></span>

### 3.1 適応的トークンマスクキャッシュ

<span id="figure-04"></span>

![図 4. トークンマスクキャッシュの例。トークンは、文脈非依存で受理、文脈非依存で拒否、文脈依存の 3 種類に分けられる。前 2 種は実行時のマスク生成で直接判定できる。](../../papers/xgrammar/figure-04.png)

**図 4.** トークンマスクキャッシュの例。トークンは、文脈非依存で受理、文脈非依存で拒否、文脈依存の 3 種類に分けられる。前 2 種は実行時のマスク生成で直接判定できる。

トークンマスクキャッシュの生成を高速化するため、適応的トークンキャッシュはトークンを 2 種類に分ける ([図 4](#figure-04))。大多数を占めて事前計算できる文脈非依存トークンと、数は少ないが実行時に低速な処理を要する文脈依存トークンである。この分類は、プッシュダウン・オートマトンによるトークン検証の仕方に関係する。スタック状態の遷移を考慮すると、トークンをオートマトンへ照合する過程は次の 3 種類に分けられる。

1. 照合が子規則へ展開し、新しい要素をスタックへプッシュする。

2. 照合が現在の規則内で進み、スタック先頭ノードを新しい位置へ更新する。

3. 照合が現在の規則末尾に達して親規則へ戻り、要素をスタックからポップする。

前 2 種のトークン検証は現在の規則内の位置を表すスタック先頭ノードだけに依存するため、これらを*文脈非依存トークン*と定義する。一方、第 3 種では検証時に実行スタック全体を調べる必要があり、*文脈依存トークン*と定義する。プッシュダウン・オートマトンの各ノードについて、実行時にそのノードがスタック先頭となる文脈非依存トークンの集合があり、その有効性は事前に決定できる。そこで、これらの有効性を事前計算し、スタック先頭ノードをキーとするキャッシュに保存する。これを適応的トークンマスクキャッシュと呼ぶ。次段落で説明するように、キャッシュ内容に応じて最も効率的な記憶形式も適応的に選択する。

実行時には、スタック先頭から文脈非依存トークンの有効性を直接取得してトークンマスクを生成する。残る少数の文脈依存トークンは、完全なスタックでプッシュダウン・オートマトンを実行して検証する。文法の曖昧性によって並列スタックがある場合、各マスクで受理されたトークンの和集合を取り、各スタックのトークンマスクを最終マスクへ統合する。本手法では実行時に文脈非依存トークンを検査する必要がないため、トークンマスクの計算量は大幅に減る。実験では、JSON 文法を使う Llama-3.1 モデルで文脈依存トークンは 1% 未満 (128k 中 1134) にすぎない。

<span id="figure-05"></span>

![図 5. 適応的な記憶形式。受理優勢の場合は拒否トークンと文脈依存トークンを保存する。拒否優勢の場合は受理トークンと文脈依存トークンを保存する。両者が同数に近いまれな場合は、受理・拒否トークンを語彙サイズのビット集合へ圧縮する。](../../papers/xgrammar/figure-05.png)

**図 5.** 適応的な記憶形式。受理優勢の場合は拒否トークンと文脈依存トークンを保存する。拒否優勢の場合は受理トークンと文脈依存トークンを保存する。両者が同数に近いまれな場合は、受理・拒否トークンを語彙サイズのビット集合へ圧縮する。

**適応的な記憶。** [図 5](#figure-05) のように、トークンマスクキャッシュはメモリ使用量を抑えるため適応的な記憶形式を用いる。各オートマトンノードについて、語彙を受理された文脈非依存トークン、拒否された文脈非依存トークン、文脈依存トークンの 3 部分へ分ける。3 部分で全トークンを覆うため、小さい 2 部分だけを保存すればよい。文脈非依存トークン集合は、ほぼすべてが受理される*受理優勢*か、ほぼすべてが拒否される*拒否優勢*になる傾向がある。文字列規則の `[^"\\]*` のようなワイルドカードを現在のノードから照合できる場合はほぼ全トークンが有効であり、少数の特定文字しか受理しないノードではほぼ全トークンが無効になるためである。この観察から、次の適応的記憶形式を設計した。

1. 受理優勢の場合、拒否された文脈非依存トークンと文脈依存トークンを 2 つの配列へ保存する。

2. 拒否優勢の場合、受理された文脈非依存トークンと文脈依存トークンを 2 つの配列へ保存する。

3. 受理・拒否トークンがほぼ同数となるまれな場合、両方の文脈非依存トークンを保存し、語彙サイズのビット集合へ圧縮する。

したがって、受理優勢と拒否優勢のどちらでも、小さなトークン部分集合だけを保存すればよく、メモリ使用量を大幅に削減できる。実装では 3 種の記憶形式を列挙し、それぞれのコストを計算して最小サイズの形式を選ぶ。Llama-3.1 モデルと JSON 文法では、総メモリ使用量を 0.2% (160 MB から 0.46 MB) まで削減できる。

複数の並列スタックがある場合はトークンマスクを統合する必要がある。[アルゴリズム 1](#algorithm-01) のように、統合アルゴリズムは記憶形式に応じて最適化される。受理優勢マスク (受理トークンが多く、拒否トークンだけを保存) では、拒否トークンを $\mathit{PartialRej}$ と交差させる。拒否優勢マスク (拒否トークンが多く、受理トークンだけを保存) では、受理トークンを $\mathit{PartialAcc}$ へ加える。最終マスクの拒否トークンは差集合 $\mathit{PartialRej} \setminus \mathit{PartialAcc}$ である。集合演算を小さなトークン部分集合に限定することで効率を高める。

<span id="algorithm-01"></span>

**アルゴリズム 1: トークンマスクの効率的な統合。**

- **入力:** $k$ 個の並列スタックに対するトークンマスク $\{M_i=(\mathit{Acc}_i,\mathit{Rej}_i)\}_{i=1}^{k}$、語彙 $\mathcal{V}$。
- **出力:** 最終トークンマスク $M=(\mathit{Acc},\mathit{Rej})$。
- **初期化:** $\mathit{PartialAcc}\gets\emptyset$、$\mathit{PartialRej}\gets\mathcal{V}$。
- **各** $i=1$ **から** $k$ **について:**
  - **もし** $M_i$ が受理優勢なら:
    - $M_i$ は拒否トークン列 $\mathit{Rej}_i$ だけを保存する。
    - $\mathit{PartialRej}\gets\mathit{PartialRej}\cap\mathit{Rej}_i$。
  - **それ以外:**
    - $M_i$ は受理トークン列 $\mathit{Acc}_i$ だけを保存する。
    - $\mathit{PartialAcc}\gets\mathit{PartialAcc}\cup\mathit{Acc}_i$。
- $M\gets\bigl(\mathcal{V}\setminus(\mathit{PartialRej}\setminus\mathit{PartialAcc}),\ \mathit{PartialRej}\setminus\mathit{PartialAcc}\bigr)$。

### 3.2 文脈拡張

<span id="figure-06"></span>

![図 6. 文脈拡張。各規則は、その規則を完了した後に必ず照合される文字列集合を表す拡張接尾辞集合を得る。文脈依存トークンの未照合部分は、拡張接尾辞の接頭辞であるか、拡張接尾辞から始まらなければならず、それ以外は拒否される。](../../papers/xgrammar/figure-06.png)

**図 6.** 文脈拡張。各規則は、その規則を完了した後に必ず照合される文字列集合を表す拡張接尾辞集合を得る。文脈依存トークンの未照合部分は、拡張接尾辞の接頭辞であるか、拡張接尾辞から始まらなければならず、それ以外は拒否される。

<span id="algorithm-02"></span>

**アルゴリズム 2: 拡張接尾辞オートマトンの抽出。**

- **入力:** プッシュダウン・オートマトン $\mathcal{P}$、規則 $R$。
- **出力:** $R$ に対する拡張文脈 FSA $\mathcal{A}_R^{\mathrm{ctx}}$。
- **初期化:** $\mathcal{A}_R^{\mathrm{ctx}}$ を空の FSA とする。
- **$\mathcal{P}$ 中で** $R$ **を参照する各辺** $s\xrightarrow{R}t$ **について:**
  - $\mathcal{A}_{\delta}$ を空の FSA、$\mathit{visited}\gets\{\}$ とする。
  - ノード $t$ を $\mathcal{A}_{\delta}$ へ追加する。
  - $\mathrm{ExtractOne}(t,\mathcal{A}_{\delta},\mathit{visited})$。
  - $\mathcal{A}_R^{\mathrm{ctx}}\gets\mathrm{FSAUnion}(\mathcal{A}_R^{\mathrm{ctx}},\mathcal{A}_{\delta})$。
- **関数** $\mathrm{ExtractOne}(\mathit{start},\mathcal{A}_{\delta},\mathit{visited})$:
  - **もし** $\mathit{start}$ が $\mathit{visited}$ にあれば:
    - **戻る。**
  - $\mathit{start}$ を $\mathit{visited}$ へ追加する。
  - **もし** $\mathit{start}$ が $\mathcal{P}$ の終端ノード、**または**別規則を参照する辺を持つなら:
    - $\mathcal{A}_{\delta}$ で $\mathit{start}$ を終端にする。
    - **戻る。**
  - $\mathit{start}$ から出る各辺 $\mathit{start}\xrightarrow{c}\mathit{end}$ **について:**
    - $\mathit{end}$ と $\mathit{start}\xrightarrow{c}\mathit{end}$ を $\mathcal{A}_{\delta}$ へ追加する。
    - $\mathrm{ExtractOne}(\mathit{end},\mathcal{A}_{\delta},\mathit{visited})$。

適応的トークンマスクキャッシュで実行時に検査するトークン数は減るが、すべての文脈依存トークンの検査は依然として実行時のボトルネックである。文脈依存トークンをさらに減らすため、XGrammar は [図 6](#figure-06) の文脈拡張を導入し、文法の文脈情報を利用して前処理時により多くの文脈依存トークンを拒否する。

前節で述べたように、照合中に現在の規則末尾へ到達してもトークンの残りを検査する必要があり、親規則へ戻らなければならない場合、そのトークンは文脈依存となる。しかし文法を解析すると、多くの場合にトークンの残り部分が無効だと分かる。多くの規則は末尾に達した後、親規則中で戻れる位置が限られ、その位置からさらに照合できる文字列集合も限られるためである。

この観察に基づき、文脈拡張は規則ごとに、親規則へ戻った後に受理可能な文字列集合を事前計算する。これを*拡張接尾辞*と呼ぶ。文脈依存トークンの未照合部分は、拡張接尾辞の接頭辞であるか、拡張接尾辞から始まらなければならない。それ以外は拒否される。上位規則の文脈で失敗するトークンを除くことで、文脈依存トークン数を効率よく減らす。Llama-3.1 モデルと JSON 文法では、文脈依存トークンを 90% (1,134 から 120) 削減する。

[アルゴリズム 2](#algorithm-02) は、各規則の拡張接尾辞を求める文脈拡張を示す。規則 $R$ について、拡張接尾辞を有限状態オートマトン (FSA) $\mathcal{A}_R^{\mathrm{ctx}}$ で表す。ctx は context の略であり、この FSA はプッシュダウン・オートマトンから抽出される。まず、プッシュダウン・オートマトン中で $R$ を参照し、規則 $R'$ に属するすべての辺 $e=(s,t)$ を探す。$R'$ は $R$ と異なるとは限らない。次に、$t$ から始めて規則 $R'$ のオートマトンを深さ優先探索 (DFS) し、$R$ の後に続き得る文字列を表す部分グラフを求める。規則間の再帰参照を避けるため、別規則を参照する辺は部分グラフに含めない。そのため、抽出される部分グラフは文字ラベルの辺だけを持つ。あるノードが文字辺と規則参照辺の両方を持つ場合、そのノードで探索を止める。抽出した部分グラフを $\mathcal{A}_R^{\mathrm{ctx}}$ へ統合する。すべての規則についてこの処理を繰り返し、規則 $R$ の照合後に、抽出済みの $\mathcal{A}_R^{\mathrm{ctx}}$ 中のどの文字列にも照合できない文脈依存トークンを拒否する。

拡張文脈オートマトンの抽出では規則参照辺を考慮しないが、それでも多くの有用な文脈情報を抽出できる。[第 3.4 節](#section-3-4) のインライン化最適化が断片規則を親規則へインライン化し、子規則を調べずに文脈依存トークンを拒否できるようにするためである。

### 3.3 永続実行スタック

<span id="figure-07"></span>

![図 7. 永続スタックは、現在のステップにある複数の照合スタックと過去ステップのスタックを 1 本の木へまとめる。メモリ消費を抑え、状態を以前のステップへ戻すことができる。](../../papers/xgrammar/figure-07.png)

**図 7.** 永続スタックは、現在のステップにある複数の照合スタックと過去ステップのスタックを 1 本の木へまとめる。メモリ消費を抑え、状態を以前のステップへ戻すことができる。

文法エンジンは文脈依存トークンを扱う必要があるため、それらに対してプッシュダウン・オートマトンを効率よく実行しなければならない。さらに、オートマトン中の全位置について文脈非依存トークン集合を前処理するときにも、プッシュダウン・オートマトンを実行する。どちらの場合も複数の並列スタックを維持し、各トークンの文字を照合しながら分岐する必要がある。効率的な状態分岐を支えるため、永続実行スタック [Dri89] で複数のスタックを管理し、プッシュダウン・オートマトンを実行する。過去時点のスタックも管理して状態のロールバックを可能にし、トークン集合に対する実行を高速化する。

[図 7](#figure-07) のように、永続実行スタックは現在時点の並列スタックと過去時点のスタックを 1 本の木へまとめ、各スタックを根からの経路として表す。スタック先頭は木のノードへのポインタとして保存される。隣接時点のスタックは深い部分の大半を共有し、プッシュまたはポップされるノードは少ないため、この統合により複数スタックを保存する際の冗長性を避けられる。トークンの新しい文字を照合するとき、文法の曖昧性によってスタックを複数へ分け、規則の異なる展開に対応させる場合がある。このときスタック全体を複製せず、そのスタックの枝だけを分ければよく、状態分岐の負担が減る。

永続実行スタックは、過去時点のスタックを保つことで高速な状態ロールバックも実現する。実行時には履歴のスライディングウィンドウを維持する。以前の状態へ戻すには現在のスタックポインタを変更するだけで、定数時間しかかからない。多くのトークンは `read`、`ready`、`reader` に共通する `read` のような接頭辞を共有するため、大量のトークン検査でロールバックは特に有用である。検査するトークンを辞書順に並べて共通接頭辞長を最大化する。続いて 1 つずつ検査し、各トークンの検査前に前のトークンとの共通接頭辞直後の状態へ戻す。これにより共通接頭辞の重複検査を避け、検査する文字数を減らせる。Llama-3.1 モデルと JSON 文法では、語彙全体で検査する文字数を 30% に削減し、前処理を大幅に高速化する。

**ロールバックは、より多くの応用で効率的な構造化生成を可能にする。** LLM の応用には、出力を以前のトークンへ戻すものが多い。たとえば jump-forward decoding [Yin24a] の再トークン化では、文脈中の一部トークンを戻して新しいトークンを挿入する。ロールバック後も構造化生成を続けるため、出力トークンと同時にオートマトン状態を戻せる。Tree-of-thought [Yao23a]、SGLang [She24]、投機的デコーディング手法 SpecInfer [Mia24a] の投機モデルなど、LLM に木構造での生成を要求する応用も多い。出力木の枝ごとにオートマトン状態を維持し、出力が分岐するときは状態を素早く分け、各出力枝に別々の照合状態を持たせられる。各枝では木上のスタック先頭ポインタだけを保てばよいため、分岐は高速である。このように永続実行スタックは、これらすべての応用で効率的な構造化生成を保証する。

### 3.4 プッシュダウン・オートマトンの構造最適化

最終的な実行効率を高めるため、プッシュダウン・オートマトンの構造をさらに最適化する。これらは従来のコンパイラ最適化の考え方に基づくが、効率的な制約付きデコーディングに特に有効である。

**規則のインライン化。** 指定された文脈自由文法には、要素が少ない断片規則が多数あり、それらはプッシュダウン・オートマトン中の小さな FSA へ変換される場合がある。一方では、実行時に断片規則の内部まで調べる必要があり、文法の曖昧性が増す。他方、文脈拡張では断片規則への参照を考慮しないため、抽出する文脈オートマトンが小さくなる。断片規則の構造を使って文脈依存トークンを拒否する機会も失われる。

そこで、断片規則向けの自動インライン化戦略 [Sch77] を導入する。他規則を参照しない規則を繰り返し選び、親規則へインライン化する。オートマトンの規模が爆発しないよう、インライン化対象と結果の大きさを定数で制限する。この処理で断片規則はほぼ消え、トークン検査が効率化し、文脈拡張の効果も高まる。

**プッシュダウン・オートマトンのノード統合。** 曖昧性の多くは、1 つのノードから同じラベルを持つ複数の辺が出ることで生じる。トークン照合中にそのノードへ到達し、次の文字がラベルと一致すると、照合スタックは出辺ごとの複数スタックへ分かれる。スタック数が増えれば、各スタックで文脈依存トークンを検査してマスクを統合する計算量も増える。この種の曖昧性を減らすため、ノード統合アルゴリズムは、a) 同じ始点から同じラベルの辺で指され、b) 他の辺から指されない後続ノードを統合する。

epsilon 辺も照合の曖昧性を増やす。オートマトン中の epsilon 辺 $s \xrightarrow{\epsilon}t$ は、文字を消費せずに $s$ から $t$ へ直接移れることを表す。照合が $s$ へ達すると、実行スタックは先頭が $s$ のものと $t$ のものに分かれ、どちらも照合を続けられる。この曖昧性を減らすため、$s$ に他の出辺がないか、$t$ に epsilon でない入辺がない限り、$s$ と $t$ を 1 ノードへ統合する。

2 つの最適化はオートマトンの等価性を保ちながら、ノードと辺の数を減らす。実行時のスタック数とトークン検査の計算量が減り、マスク生成が高速になる。

### 3.5 マスク生成と LLM 推論の重ね合わせ

<span id="figure-08"></span>

![図 8. マスクキャッシュ構築を LLM のプリフィルと、マスク生成を LLM デコードと重ね合わせてオーバーヘッドを最小化する。](../../papers/xgrammar/figure-08.png)

**図 8.** マスクキャッシュ構築を LLM のプリフィルと、マスク生成を LLM デコードと重ね合わせてオーバーヘッドを最小化する。

以上の最適化でトークンマスク生成は大幅に高速化するが、CPU 計算はなお必要である。制約付きデコーディングのオーバーヘッドをさらに除くため、[図 8](#figure-08) のようにマスク生成計算と LLM 推論を重ね合わせる。マスク生成は CPU だけを使い、過去に生成されたトークンだけに依存する。サンプリングを除く LLM 推論は GPU だけを使い、同じく過去のトークンだけに依存する。このため、CPU 上のマスク生成と GPU 上の LLM 推論を並列化できる。サンプリング直前に同期し、GPU が CPU からマスクを受け取ってマスク付きサンプリングを行い、新しいトークンを生成する。前処理も、LLM がプロンプトを処理するプリフィル段階と重ね合わせられる。この CPU と GPU の協調により、トークン制約はほぼゼロの推論オーバーヘッドで適用される。実際にはマスク生成時間は LLM 推論時間より短く、生成のボトルネックにはならない。

### 4.1 マスク生成効率

制約付きデコーディングのオーバーヘッドを測るため、マスク生成効率を評価する。まず、正規表現へ変換可能な JSON schema を用いて正規表現ベースの手法を評価する。正規表現では扱えない複雑な場合として、無制約 JSON (ECMA-404 [Ecm13])、XML (XML 1.0 標準 [Bra08])、Python DSL (Python 文法仕様 [Pyt24a] を改変) の文脈自由文法を評価する。無制約 JSON はリストとオブジェクトを任意に入れ子にでき、正規表現では処理できない。Python DSL は基本的な制御フロー (if、for、while) とデータ型 (str、int、float、bool) を含むが、インデントは無視する。JSON schema と無制約 JSON には JSON-mode-eval データセット [Nou24] を、XML と Python には合成データセットを使う。ベースラインは、Outlines [Wil23] (v1.0)、llama.cpp [Ger23a] の文法エンジン (b3998)、lm-format-enforcer [Gat25] (v0.10.9、CFG 非対応の正規表現ベース手法) の 3 つである。すべての手法を、AMD Ryzen 9 7950X CPU と NVIDIA RTX 4090 GPU 上の Llama-3.1-8B-Instruct で評価する。

## 5 関連研究

構造化生成のアルゴリズムを改善する研究がある。[Koo24] は文字単位のプッシュダウン・オートマトンをトークン単位へ変換するアルゴリズムを提案する。[Wan23n] はプロンプトで LLM の出力構造を指定する。[Roz23, Cha23d, Li23o] は構造化生成の品質を高める LLM のファインチューニングを検討する。XGrammar の手法はこれらと直交し、組み合わせて利用できる。

制約付きデコーディングに焦点を当てた先行研究もある。lm-format-enforcer [Gat24] などは正規表現で構文を表すが、複雑な CFG を扱えない。Synchromesh [Poe22] と llama.cpp [Ger23a] はそれぞれ LR パーサと PDA で CFG を処理しマスクを生成するが、実行時に語彙全体を検査するため大きな負担となる。Outlines [Wil23] は字句解析器と構文解析器で文法を扱い、キャッシュでマスク生成を高速化するが、直近の字句トークンだけを考えるため、LLM トークンが複数の字句トークンにまたがると誤判定する場合がある ([Koo24] の付録 A)。Syncode [Uga24] は複数の字句トークンにまたがるキャッシュを用いるが、全トークンをオフライン処理する必要があり、前処理の負担が大きい。XGrammar は PDA で CFG を扱い、適応的トークンマスクキャッシュにより前処理時と実行時にトークンを適応的に処理する。他のシステム最適化も組み合わせ、両段階の負担を最小化する。

Guidance [Gui22]、LMQL [Beu23a]、SGLang [She24] は構造を宣言する柔軟な方法を提供する。XGrammar はこれらの改善と補完関係にあり、実行を高速化するバックエンドエンジンとして利用できる。

LLM サービングエンジン [Mlc23, She24, Kwo23, Lig23c] は複数の同時利用者に対する効率的な生成を支えるため、動的な要求スケジューリングを行う continuous batching [Yu22a] などのエンジン技術や、効率的なメモリ管理を行う低水準 KV キャッシュ技術 PagedKVCache [Kwo23] を使う。AICI [Mos24] は構造化生成を高速化する CPU-GPU 並列計算方式を提案する。これらの LLM サービングエンジンは、既存の推論技術の上で XGrammar を利用し、構造化生成を効率化できる。

<span id="section-6"></span>

## 6 おわりに

本稿では、LLM 向けの柔軟かつ効率的な構造化生成エンジン XGrammar を提案した。XGrammar は語彙を文脈非依存トークンと文脈依存トークンへ分ける。文脈非依存トークンを事前検査し、その結果を適応的トークンマスクキャッシュへ保存する。さらに、文脈依存検査の実行を高速化する永続スタックを導入する。最後に、文法実行と GPU 計算を重ね合わせるため文法エンジンと LLM 推論を協調設計する。本システムはトークンマスク生成を大幅に高速化し、エンドツーエンドの LLM 推論でゼロオーバーヘッドの構造化生成を可能にする。さまざまなプラットフォームで、より広範な構造化生成を実現する基盤となることを期待する。

## 7 PDA 変種の形式的定義

本稿では、元の定義と等価でありながら、構文解析アルゴリズムとトークンマスクキャッシュの構築を説明しやすいプッシュダウン・オートマトン (PDA) の変種を定義する。キャッシュのキーはこの PDA の状態そのものになる。これは次の組として定義される。

$$
P = \bigl( R, \Sigma, \{A_r\}_{r \in R}, q_{\mathrm{main}}, \delta \bigr),
$$

ここで、

- $R$ は有限の文法規則集合である。

- $\Sigma$ は有限の入力アルファベットである。

- 各規則 $r \in R$ に対応する有限状態オートマトンは

  $$
  A_r = \bigl( Q_r, \Sigma \cup R, q^{\mathrm{start}}_r, F_r, \delta_r \bigr),

  $$

  で与えられる。$Q_r$ は有限状態集合、$q^{\mathrm{start}}_r \in Q_r$ は開始状態、$F_r \subseteq Q_r$ は受理状態集合、$\delta_r$ は $Q_r$ 上に定義された遷移関数である。$A_r$ の遷移ラベルは入力文字と規則参照の双方を含むアルファベット $\Sigma \cup R$ から取られる。

- $q_{\mathrm{main}}$ は主規則に対応する開始状態である。

- $\delta$ は PDA の動作を制御する大域遷移関数であり、2 種類の遷移を扱う。

  - *文字遷移*: 状態 $q \in Q_r$ で入力記号 $a \in \Sigma$ を読むと、同じオートマトン内で $q \xrightarrow{a}q'$ と遷移できる。

  - *規則参照遷移*: 状態 $q \in Q_r$ で規則 $s \in R$ を参照するラベルを持つ遷移は、現在の戻り情報をスタックへプッシュし、$A_s$ の開始状態 $q^{\mathrm{start}}_s$ へ移る。

解析状態は組の集合 $\{(s_i,q_i)\}$ で表す。$s_i$ は戻り情報を符号化したスタック内容、$q_i$ は現在状態であり、ある $r \in R$ について $q_i \in Q_r$ である。プッシュダウン・オートマトンは非決定的遷移を含み得るため、複数の解析スタックと状態が同時に存在し得る。本文では簡単のため、現在状態 $q_i$ をスタック先頭に置く。したがって解析状態は解析スタックの集合として表される。

次に、この PDA 変種を標準 PDA へ変換する形式的な変換を示す。標準 PDA を得るため、新しいプッシュダウン・オートマトン

$$
P' = \bigl( Q, \Sigma, \Gamma, \delta', q_0, F \bigr)
$$

を次のように構築する。状態集合 $Q$ は全 FSA の状態の和集合である。

$$
Q = \bigcup_{r \in R} Q_r,
$$

初期状態を $q_0=q_{\mathrm{main}}$ とする。スタックアルファベット $\Gamma$ は戻り情報を記録するため、

$$
\Gamma = \{\, (r, q) \mid r \in R,\; q \in Q_r \,\},
$$

と定義する。各記号 $(r,q)$ は、呼出し元の規則と戻り状態からなる規則呼出しの文脈を符号化する。

標準 PDA の遷移関数 $\delta'$ は、変種 PDA の振る舞いを模倣するよう定義する。ある $\delta_r$ 中の各文字遷移が

$$
q \xrightarrow{a} q' \quad \mathrm{with}\ a \in \Sigma\ \mathrm{and}\ q, q' \in Q_r,
$$

なら、$\delta'$ に

$$
\delta'(q, a, \gamma) \ni (q', \gamma) \quad \mathrm{for\ all}\ \gamma \in \Gamma.
$$

を含める。$\delta_r$ 中の各規則参照遷移が

$$
q \xrightarrow{s} q' \quad \mathrm{with}\ s \in R,
$$

なら、戻り情報をプッシュして被呼出し規則へ制御を移す $\epsilon$ 遷移で再帰呼出しを模倣する。形式的には

$$
\delta'(q, \epsilon, \gamma) \ni \Bigl( q^{\mathrm{start}}_s, \, (r,q') \cdot \gamma \Bigr) \quad \mathrm{for\ all}\ \gamma \in \Gamma,
$$

とする。ここで $q$ はオートマトン $A_r$ に属し、$(r,q')\cdot\gamma$ は $(r,q')$ を $\gamma$ へプッシュしたスタックである。最後に、オートマトン $A_r$ が受理状態 $q \in F_r$ へ達すると、標準 PDA はスタック先頭をポップして再帰呼出しからの復帰を模倣する。現在のスタックが $(r',q')\cdot\gamma$ なら、

$$
\delta'(q, \epsilon, (r',q')) \ni (q', \gamma).
$$

と定義する。受理状態集合 $F$ は、空スタックで到達する $\bigcup_{r \in R}F_r$ 中の状態である。

この構築から、変種 PDA の文字遷移は $P'$ におけるスタック操作なしの状態遷移へ直接対応し、規則参照遷移はプッシュとジャンプへ対応することが分かる。同様に、FSA の照合完了と親規則への復帰は、スタックのポップと保存された戻り状態への遷移で実現する。このように標準 PDA $P'$ は、変種 PDA の再帰的な振る舞いを正確に模倣する。

## 8 XGrammar と jump-forward decoding の相乗効果

jump-forward decoding は構造化生成を高速化する手法である。現在の入力に基づいて後続出力を文法から一意に推論できるとき、LLM のデコードとサンプリングを省き、出力を直接トークン化して文脈へ追加する。これにより LLM 生成のエンドツーエンド効率が高まる。この手法は XGrammar が用いる制約付きデコーディングと直交する。XGrammar は jump-forward decoding も支援し、両者を効果的に組み合わせて効率をさらに高められることを示す。

SGLang エンジンでサービングする Llama-3.1-8B-Instruct モデルを使い、AMD Ryzen 9 7950X CPU と NVIDIA RTX 4090 GPU を搭載した計算機で性能を評価する。すべての実験でバッチサイズは 1 とする。XGrammar を既存のデコードバックエンド Outlines と比較し、それぞれについて jump-forward decoding の有無を試す。評価指標は出力トークン当たり時間である。

[図 11](#figure-11) のように、XGrammar は一貫して Outlines を上回り、jump-forward decoding と組み合わせたときに最高の効率を達成する。これは構造制約をよりよく利用して生成を高速化できることを示す。

## 9 XGrammar のクロスプラットフォーム配置

<span id="figure-12"></span>

![図 12. ブラウザの JavaScript 環境における XGrammar を用いた構造化生成と非構造化生成のエンドツーエンド性能比較。](../../papers/xgrammar/figure-12.png)

XGrammar を幅広いプラットフォームへ展開する方法を検討する。Emscripten [Zak11] で XGrammar を WebAssembly [Haa17] へコンパイルし、JavaScript バインディングを構築する。これにより、ノート PC や携帯電話などの可搬端末のクライアント側ブラウザで XGrammar を実行できる。さらに Web バインディングをブラウザ内 LLM 推論フレームワーク WebLLM [Web23b] へ統合し、構造化生成を可能にする。

JSON-mode-eval データセットでエンドツーエンド性能を評価する。4 ビット量子化した Llama-3.1-8B-Instruct [Dub24] を M3 Max 搭載 MacBook Pro (MacOS 14.5) 上の Google Chrome で、Qwen-2.5-0.5B-Instruct [Yang24b] を iPhone 14 Pro Max (iOS 18) 上の Safari で実行する。

結果を [図 12](#figure-12) に示す。生成トークン数を同じに保ち、XGrammar を用いた構造化生成と非構造化生成の time to first token (TTFT) および time per output token (TPOT) を比較する。どちらの環境でも XGrammar のオーバーヘッドはほぼゼロであり、将来のオンデバイス・エージェントを高性能に支援できる大きな可能性を示す。
