## 概要

生成大規模言語モデル（LLM）の応用は急速に増え、高価で電力消費の大きい GPU が大規模に配備されている。LLM 推論の特性を分析すると、各推論要求には計算集約的なプロンプト計算とメモリ集約的なトークン生成という二つのフェーズがあり、レイテンシ、スループット、メモリ、電力の特性がそれぞれ異なる。最先端のバッチ処理とスケジューリングを用いても、トークン生成フェーズは計算資源を十分に利用できない。プロンプト計算と違い、トークン生成には最新 GPU の計算能力が不要であり、より低い電力とコストで実行できる。

これらの知見に基づき、LLM 推論要求の二つのフェーズを別々のマシンへ分割するモデル配備・スケジューリング手法 Splitwise を提案する。Splitwise は各フェーズに適したハードウェアを使い、フェーズごとの資源管理を可能にする。現在の GPU クラスタに備わる高速バックプレーン相互接続上で、最適化したネットワークライブラリにより要求状態を効率よく転送する。Splitwise を使い、スループット、コスト、電力に最適化した同種・異種 LLM 推論クラスタを設計する。既存設計と比べ、Splitwise クラスタはコストを 20% 下げながら最大 $1.4\times$ のスループットを達成する。または、同じ電力・コスト予算で $2.35\times$ のスループットを提供できる。

## 1 はじめに

生成大規模言語モデル（LLM）の近年の進歩により、応答品質と精度は大きく向上した [Ope23f, Sch23b]。この流れから、さまざまな分野で LLM が広く採用されている [Goo24, Mic24]。現代の LLM の大半は Transformer アーキテクチャ [Wol19, Vas17d] で構築され、似た特性を示す [Pat24c]。Transformer の規模は、3 億 4000 万パラメータの初期 BERT [Dev19b] から、1750 億パラメータという巨大な GPT-3 [Oth20] へ増え続け、GPT-4 はさらに多いと噂される。

LLM は通常、高価で電力消費の大きい GPU 上で動く [Nvi23f]。LLM の急激な大規模配備は、世界的な GPU 容量不足を招いた [Nvi23d]。多数の応用が LLM を利用するため、LLM 推論の計算需要は学習を大きく上回る。さらに、LLM の学習には高価な専用スーパーコンピュータが必要なので [Ope22b, Lee22]、高い学習コストを償却するには大量の推論が必要となる。LLM 推論ジョブは学習より桁違いに小さいものの、必要な計算量のため依然として高価である。

![表 1。NVIDIA A100 と H100 の仕様。](../../papers/splitwise/table-01.png)

**表 1。** NVIDIA A100 と H100 の仕様。

一つの要求に対する生成 LLM 推論は、出力トークンを一つずつ生成するため、モデルの複数回の順伝播からなる。ここには対照的な二つの計算フェーズがある。第一は*プロンプト計算フェーズ*であり、すべての入力プロンプトトークンを一回の順伝播で並列計算し、最初の出力トークンを生成する。このフェーズは計算集約的で、最新 GPU の高い FLOPs（1 秒当たりの浮動小数点演算数）を必要とする。第二は*トークン生成フェーズ*であり、直前のトークンの順伝播と、それまでの全トークンからキャッシュした文脈に基づいて後続トークンを逐次生成する。計算並列性がないため、最先端のバッチ処理を用いても、このフェーズはメモリ帯域幅と容量に制約されやすい。両フェーズを同じマシンで動かすと、プロンプトとトークンの任意の混合バッチにより、エンドツーエンドのレイテンシが不安定になることが多い。このため、対話型アプリケーションの厳しい推論サービスレベル目標（SLO）を満たすには、高価な GPU を過剰配備しなければならない。同時に、クラウドサービスプロバイダ（CSP）は GPU 需要を満たすため多数の新規データセンタを建設し、電力の壁に直面している [Pow23]。

業界は計算能力の高い新 GPU を出し続けており、新世代ほど電力消費と価格が上がる。しかし [表 1](#table-01) のように、近年は高帯域幅メモリ（HBM）の容量と帯域幅が同じ割合では伸びていない。最新の NVIDIA H100 GPU は A100 に比べて計算能力が $3.43\times$、電力が $1.75\times$ である一方、メモリ帯域幅は $1.6\times$ にとどまり、容量は増えていない。

**本研究。** プロンプト計算とトークン生成の特性が異なるため、推論要求を分割して別々のマシンで実行することを提案する。これにより各フェーズのハードウェア資源を個別に管理し、GPU 利用率とシステム全体の効率を高められる。各フェーズに異なる、より適したハードウェアも使える。この構成には、プロンプト計算でキャッシュした文脈を、プロンプト処理マシンからトークン生成マシンへ低レイテンシで送る必要がある。現在のデータセンタにあるバックエンド InfiniBand 相互接続上で転送を最適化し、体感できる性能低下なしに効率を向上させる。

Splitwise により、LLM 推論要求の本番トレース [Azu24] を使って、コスト、スループット、電力に最適化したクラスタを設計する。GPU 世代間でメモリと計算能力の伸びが乖離しているため、フェーズごとに異なる GPU と電力上限も評価する。これにより、ユーザにはより高いドル当たり性能（Perf/&#36;）、CSP にはより高いワット当たり性能（Perf/W）を提供できる。入手しやすい旧世代 GPU も選択できる。

Splitwise ベースの LLM 推論クラスタは、既存クラスタよりコストを 20% 下げながら $1.4\times$ 高いスループットを達成できる。または、同じコスト・電力予算で $2.35\times$ のスループットを提供できる。

**要約。** 本研究の貢献は次のとおりである。

1.  本番トレースを用い、NVIDIA A100 と H100 GPU 上の LLM 推論について、プロンプトとトークン生成フェーズの実行・利用パターンの違いを広範に分析した。

2.  利用可能なハードウェアを効率よく使うため、プロンプト計算とトークン生成を別マシンへ分割する Splitwise を提案した。

3.  Splitwise による同種・異種クラスタ配備を探索し、総コスト、要求スループット、配備電力を最適化した。

4.  本番トレースを使って Splitwise のシステム設計を評価した。

## 2 背景

<span id="section-2-1"></span>

### 2.1 大規模言語モデル

現代の LLM は Transformer に基づく。Transformer は注意機構 [Vas17d] と多層パーセプトロン層を使い、それぞれ入力を理解して出力を生成する。Transformer ベースの LLM には encoder-only [Dev19b, Liu19a]、decoder-only [Rad19b, Les23, Sch23b]、encoder-decoder [Sch23a] がある。本稿が扱う生成 LLM は通常 decoder-only または encoder-decoder である。

<span id="section-2-2"></span>

### 2.2 生成 LLM の推論フェーズ

[図 1](#figure-01) に生成 LLM 推論の例を示す。プロンプトを受信すると、一回の反復内ですべての入力トークンを並列計算し、最初のトークンを生成する。これをプロンプト処理フェーズと呼ぶ。プロンプト計算中に注意層が生成した文脈は、以後の全トークン生成反復で必要なため key-value（KV）キャッシュへ保存する。最初のトークン以後、モデルの順伝播には直前に生成したトークンと KV キャッシュだけを入力する。このため後続トークン生成は、計算負荷の高いプロンプトフェーズよりメモリ帯域幅と容量を多く必要とする。

### 2.4 要求のバッチ処理

推論要求をまとめて処理するとスループットを高められる。複数の先行研究がバッチ処理を調べている [Yu22a, Agr23]。[図 2](#figure-02) は一般的な三方式の時間軸を示す。既定方式は*要求単位*だけでバッチ化する（[図 2a](#figure-02)）。準備済みの要求をまとめるが、その全順伝播が終わるまで他の要求を実行しない。トークン生成が長い要求もあるため、途中で到着した要求の待ち時間が伸び、TTFT と E2E レイテンシが高くなる。*連続バッチ処理* [Yu22a]（[図 2b](#figure-02)）では、モデルの各順伝播前にスケジューリングする。ただし各バッチはプロンプト中の要求だけ、またはトークン中の要求だけで構成される。TTFT に影響するプロンプトを優先し、待機中のプロンプトがトークンフェーズをプリエンプトできる。TTFT は短くなるが TBT のテール、ひいては E2E が大きく増えうる。最後は*混合バッチ処理*（[図 2c](#figure-02)）[Agr23] である。各順伝播でスケジューリングし、両フェーズを同時に実行できる。TBT への影響は減るが、プロンプトと同時に動くトークンフェーズは長くなるため、なくなりはしない。以下では特記しない限り混合バッチ処理を用いる。

<span id="section-2-5"></span>

### 2.5 モデル並列化

モデル並列化では、効率とメモリ容量を高めるため、モデルを複数 GPU、さらに複数マシンへ分割できる。LLM 推論は通常パイプライン並列とテンソル並列を使う。パイプライン並列（PP）は層を GPU 間に分け、同じ層の演算子とテンソルは同じ GPU に置く。テンソル並列（TP）はテンソルを GPU 間に分け、全層を各 GPU に複製する。PP の GPU 間通信量は少ないが、TP は各層で高帯域通信を必要とする。一般に、NVLink [Nvi23e] などで接続された同一マシン内の GPU では TP の性能が高い。以下では最良のレイテンシを得るため 8 GPU 間で TP を用いる。

<span id="section-2-6"></span>

### 2.6 GPU クラスタと相互接続

LLM 用途の増加に伴い、複数の CSP が GPU 製品を拡充し、大規模 GPU クラスタを配備している [Lee22, Azu22, Cor23]。通常、各マシンは NVIDIA のフラッグシップ GPU（A100 または H100）を 8 基搭載する。各 GPU は高帯域 Mellanox InfiniBand [Nvi23c, Mic23] でクラスタ内の全 GPU と接続され、高帯域データプレーンを形成する。現在のクラウドでは GPU ペア当たり 25-50 GBps の InfiniBand 帯域幅が提供される [Mic23, Hpc23]。

## 3 特性分析

本節では LLM 推論の性能と利用特性を調べ、Splitwise の設計を導く知見を得る。

**本番トレース。** 2023 年 11 月 11 日に二つの Azure LLM 推論サービスから取得した本番トレースを使う。現在一般的な*コーディング*と*対話*を表す。トレースの一部は <https://github.com/Azure/AzurePublicDataset> で公開した [Azu24]。分析用トレースは 20 分間で、到着時刻、入力サイズ（プロンプトトークン数）、出力サイズを含む。GDPR などのプライバシー要件によりプロンプト内容は見えない。そのため本番トレースから入出力サイズを定め、必要なトークン数の入力を送り、要求ごとに対応する数の出力を強制生成する。測定指標は入出力サイズだけに依存するため、入力文面は性能に影響しない。セキュリティ保証のあるクラウドサービスを模すため、要求間で KV キャッシュは再利用しない。

**モデル。** [表 3](#table-03) に評価モデルを示す。BLOOM [Les23] と Llama2 [Sch23b] はいずれも最先端のオープンソース LLM で、Transformer ベースの decoder-only モデルである。生産レベルの精度を最もよく表すため、各モデルで最大の版を使う。特記しない限り、8 基の H100 [Nvi23f] を持つマシン上の vLLM [Kwo23] で BLOOM-176B と Llama-70B を実行する。

### 3.3 レイテンシ

**TTFT。** [図 5a](#figure-05) はプロンプト数が TTFT に与える影響を示す。範囲は両トレースから選んだ。両モデルともサイズにほぼ比例して TTFT が増える。プロンプトフェーズは GPU 利用率が高く計算律速だからである。

**TBT。** [図 5b](#figure-05) は複数要求の出力を強制的にまとめたときの TBT を示す。バッチサイズが増えても影響は小さく、64 でも TBT は $2\times$ にしかならない。

**E2E。** [図 5c](#figure-05) はバッチ処理なしの両モデルにおける E2E の各百分位である。要求ごとの入出力サイズのばらつきが明瞭である。E2E の大半はトークンフェーズに費やされる。プロンプトが大きく生成が少ないコーディングでも同じで、BLOOM-176B では入力 1500 のプロンプトフェーズが出力 6 のトークンフェーズと同時間を要する。

*知見 III：* 大半の要求では、E2E 時間の多くがトークン生成に費やされる。

### 3.4 スループット

[図 6](#figure-06) はバッチ処理がスループット（毎秒トークン数）へ与える影響を示す。プロンプトでは毎秒処理する入力数と定義する。2048 を超えると低下し、トレース中央値ではバッチサイズ 2 未満に相当する。一方 [図 6b](#figure-06) のトークンフェーズでは、メモリ不足になる 64 までバッチとともに増え続ける。

### 3.5 メモリ利用率

LLM 推論では、GPU メモリがモデルの重みと活性値、KV キャッシュを保持する（[第 2.2 節](#section-2-2)）。バッチ内トークン数とともに KV キャッシュ容量も増える。[図 7](#figure-07) は両フェーズでバッチ内トークン数を増やした際の容量利用率を示す。プロンプトでは入力が KV キャッシュを生成する。出力では処理中の*各*アクティブトークンが、それまでの*全コンテキスト*の KV キャッシュへアクセスする。

*知見 V：* プロンプトのバッチ処理は計算律速だが、トークンフェーズはメモリ容量に制約される。

### 3.6 電力利用率

クラウド事業者はマシン配備時に、データセンタコストへ直接影響するピーク消費電力を考慮する [Bar18]。GPU は通常の計算機より電力を多く使うため、GPU クラスタでは特に重要である [Pat24c, Pat23d]。[図 8](#figure-08) は両フェーズの GPU 電力を熱設計電力（TDP）で正規化して示す。計算集約的なプロンプトではバッチとともに増える。メモリ律速のトークンでは処理数を増やしても変わらない。

特性の違いから、異なるハードウェア上で両フェーズを動かす影響を測る。[表 1](#table-01) は DGX-A100 [Nvi23e] と DGX-H100 [Nvi23f] の仕様である。メモリ対計算比は A100 が有利である。[表 4](#table-04) の結果では、プロンプト（TTFT）よりトークン生成（TBT）への影響が小さい。生成が少ないコーディングはプロンプト支配なので、A100 の E2E への影響は対話より大きい。また A100 の総推論コストとエネルギーは H100 以下である。

## 4 Splitwise

以上の知見に基づき、LLM 推論のプロンプトと生成フェーズを別マシンへ分ける Splitwise を提案する。

[図 10](#figure-10) は全体像である。プロンプトとトークン処理用に別々のマシンプールを維持し、第三の混合プールは負荷に応じて伸縮する。全マシンに選択モデルを事前ロードする。新要求にはプロンプトとトークンの一組を割り当てる。前者は入力を処理して最初のトークンと KV キャッシュを生成し、キャッシュを後者へ送り、後者が応答完了まで生成を続ける。トークンマシンは連続バッチ処理、混合プールは混合連続バッチ処理を使う。

要求率が低いときは低レイテンシを、高いときは二つのプール間の断片化による性能・スループット低下の回避を目指す。

<span id="figure-10"></span>

![図 10。Splitwise の高レベルシステム図。](../../papers/splitwise/figure-10.png)

**図 10。** Splitwise の高レベルシステム図。

[図 10](#figure-10) のように階層型二段スケジューリングを用いる。クラスタレベルスケジューラ（CLS）①はプール管理と要求ルーティングを担い、マシンレベルスケジューラ（MLS）②は待機キューと各マシンのバッチ処理を管理する。

<span id="section-4-1"></span>

### 4.1 クラスタレベルスケジューリング

**マシンプール管理。** CLS はプロンプト、トークン、混合プール③を維持する。Splitwise は予想負荷と入出力分布に応じて初期割当を行う。高負荷時の断片化を減らし SLO を満たすため、両専用プールから混合プールへ動的に出入りできる。混合中も元の役割を保持し、反対種の待機タスクがなくなると元へ戻る。切替レイテンシは無視できる。負荷分布が想定から大きく外れると、粗粒度の*用途変更*で専用プール間を移す。これは長時間混合状態にある場合など、低頻度で行う。

**要求ルーティング。** CLS は Join the Shortest Queue（JSQ）[Zhu00, Gup07] で各要求に両マシンを割り当てる。キュー長は待機トークン数で定義する。各マシンはメモリ容量・キュー変化を定期報告するが、毎反復ではない。KV 転送をプロンプト計算と重ねるため、両マシンを同時に割り当てる（[第 4.3 節](#section-4-3)）。

キューが閾値を超えると CLS は混合プールを探し、満杯なら反対の専用プールを探して混合へ移す。混合マシンは通常の非 Splitwise マシン同様に混合バッチ処理する。混合要求が尽きると元へ戻る。例えばキューが長ければプロンプトマシンを混合へ移してトークンを動かし、完了後に戻す。

<span id="section-4-2"></span>

### 4.2 マシンレベルスケジューリング

各マシンの MLS は GPU メモリ利用率を追跡し、待機キュー④を維持し、各反復のバッチを決め、CLS へ状態を報告する。

**プロンプトマシン。** MLS は先着順（FCFS）で処理する。[図 6a](#figure-06) では 2048 トークンを超えるとスループットが下がるため、複数プロンプトの合計を 2048 に制限する。この値はモデルやハードウェアに応じて設定できる。

**トークンマシン。** FCFS で可能な限りまとめる。[図 6b](#figure-06) のようにメモリ不足までスループットが伸びるため、メモリを追跡し、限界近くでトークンを待機させる。

**混合マシン。** TTFT SLO のため新プロンプトを直ちに優先する。トークン実行中で余力がなければ*プリエンプト*する。トークンの*飢餓*を防ぐため、待ち時間とともに優先度を上げ、要求ごとの回数を制限する。

<span id="section-4-3"></span>

### 4.3 KV キャッシュ転送

[第 2 節](#section-2) のとおり KV キャッシュはプロンプトで作られ、生成中に増え続ける。Splitwise は推論完了のためプロンプトからトークンマシンへ⑤転送する（[図 10](#figure-10)）。この遅延が主なオーバーヘッドであり、以下で影響と最適化を述べる。

<span id="figure-11"></span>

![図 11。Splitwise の KV キャッシュ転送最適化。](../../papers/splitwise/figure-11.png)

**図 11。** Splitwise の KV キャッシュ転送最適化。

[図 11a](#figure-11) は一バッチを単純に直列転送したガント図である。転送はプロンプト完了と最初のトークン生成後に始まり、次の出力生成前に完了しなければならない。このため最大 TBT と E2E に直接影響する。

所要時間はプロンプト数に比例するキャッシュサイズと両マシン間帯域幅による。高速 InfiniBand でも大きなプロンプトでは TBT のかなりの割合になりうる。

Splitwise は転送をプロンプト計算と重ねる。各層の計算で対応キャッシュが生成されると、次層を計算しながら非同期転送する。[図 11b](#figure-11) のようにオーバーヘッドが減る。層単位転送により、トークンフェーズの早期開始やプロンプト側メモリの早期解放も可能になる。

層単位転送は次層計算と並行するため、正確性には細粒度同期が必要で、小さなプロンプトでは干渉により TTFT が増えうる。ただし小さいキャッシュは遅延を隠す必要がない。バッチ数は開始時に既知なので、小さければ直列、大きければ層単位を選ぶ。[第 6.1 節](#section-6-1) で総オーバーヘッドが小さいことを示す。

### 4.4 Splitwise によるプロビジョニング

Splitwise を使って LLM 推論クラスタを電力、コスト、スループットに最適化する。

**マシン種別。** *Splitwise-AA*、*Splitwise-HH*、*Splitwise-HA*、*Splitwise-HHcap* の四種を提案する。先頭文字はプロンプト、次はトークンの種別であり、A は DGX-A100、H は DGX-H100、Hcap は電力制限した DGX-H100 を表す。[表 5](#table-05) に各設計のコスト、電力、ハードウェアを示す。

Splitwise-AA は両プールに DGX-A100、HH は DGX-H100 を使う。これは同種で交換可能なマシンを持つ事業者で一般的な構成である。

Splitwise-HA はプロンプトに DGX-H100、トークンに DGX-A100 を使う。[表 4](#table-04) と知見 VII（A100 はトークンでコスト・電力効率が高い）に基づく。

Splitwise-HHcap は両方に DGX-H100 を使うが、トークンマシンを定格の 70%、各 GPU を 50% 低く制限する。[図 9](#figure-09) と知見 VII（プロンプトは影響を受けるがトークンは半減しても影響しない）に基づく。

**マシン数。** 適切な数を配備する必要がある。[第 5 節](#section-5) のイベント駆動シミュレータで設計空間を探索する。入力は（1）設計、（2）各入出力・バッチサイズの TTFT と TBT を推定する性能モデル、（3）対象分布由来の短いトレース、（4）SLO、（5）制約、（6）最適化目標である。これにより所望の最適点を探す。例えばスループット制約とコスト最小化から、設計ごとの等スループット・コスト最適クラスタを得る。

<span id="figure-12"></span>

![図 12。Splitwise-HH のプロビジョニング設計空間。ピーク 70 RPS を対象とし、コスト最適な 27 プロンプト、3 トークン構成を $\star$ で示す。](../../papers/splitwise/figure-12.png)

**図 12。** Splitwise-HH のプロビジョニング設計空間。ピーク 70 RPS を対象とし、コスト最適な 27 プロンプト、3 トークン構成を $\star$ で示す。

**探索空間。** [図 12](#figure-12) はコーディング負荷（2 分トレース）に対するプロンプト・トークン台数の二次元空間である。シミュレータは TTFT、TBT、E2E の各百分位を出力する。全 SLO を満たすものから目的関数を最適化する。図の $\star$ は 70 RPS を最小コストで達成する 27 台と 3 台の構成で、*等スループット・コスト最適*と呼ぶ。

**最適化。** 目標は*スループット*、*コスト*、*電力*である。スループットは CSP とユーザ双方に重要である。同じスループットでコストが高くても電力と設置面積が減れば CSP は許容しうるが、ユーザには通常許容できない。電力最適化は同じデータセンタへ多くの GPU を置けるため CSP に有用だが [Pat23c, Pat24c]、ユーザの重要度は低い場合がある。本研究は動的消費電力でなく配備電力だけを扱う。

<span id="section-4-5"></span>

### 4.5 実用上の考慮事項

**精度への影響。** 可逆な KV キャッシュ転送を使い乱数を加えないため、精度は変わらない。単一マシンと同じパラメータと状態で推論する。

**スケーラビリティ。** LLM 要求は通常の ML 要求より長く [Guj20, Gup20a]、同規模なら調度オーバーヘッドは小さい。ただし大規模では CLS がボトルネックになりうる。分割・複製スケジューリング [Ous13, Bou14, Sch13a] は拡張性を改善でき、Splitwise と直交する。

**信頼性と耐障害性。** いずれかのマシンが故障すれば、現在の LLM サービス同様に最初から再実行する [Kwo23, Hug21]。またはプロンプト後の KV キャッシュをインメモリ DB にチェックポイントし、再計算を省いてトークンから再開できる。生成中も定期保存できる。安全で効率的な復旧設計は範囲外である。

### 5.1 実験設定

実機評価のため vLLM [Kwo23] 上に KV 転送を実装し、公開した [Add24]。[表 1](#table-01) の仕様を持つ Azure 上の DGX-A100、DGX-H100 VM 各 2 台で動かし、[第 3 節](#section-3) のデータも取得した。InfiniBand で接続され、H100 は二倍の 400 Gbps である。

通常の vLLM はトークンのプリエンプションを伴う連続バッチ処理だけを備え、TBT が高くなりうるため、[図 2c](#figure-02) の混合連続バッチ処理 [Yu22a] を実装した。

各マシンにプロンプトまたはトークン役割を与え、最初のトークン生成時に [第 4.3 節](#section-4-3) の方法で KV キャッシュを送る。GPU 駆動通信ライブラリ MSCCL++ [Msc23] で単純転送と層単位転送を実装する。

プロンプトマシンは MSCCL++ のゼロコピー片方向 `put` により、受信命令なしで準備済みデータを InfiniBand 送信する。全層の `put` 後に、トークン側が待つセマフォへ通知する。同期も同じ接続を使う。要求は異なる宛先へ行きうるので、バッチ内の各要求に別のセマフォを割り当てる。vLLM ではブロック単位で送り、同じセマフォなら連続性も考慮して転送数を減らす。

### 6.2 等電力スループット最適クラスタ

**クラスタ配備。** [第 4.4 節](#section-4-4) の方法で、各設計を特定負荷のピークに同じ電力で配備する。基準電力は DGX-H100 40 台分で、A100 は同予算に 70 台入る。全台で混合処理するので 40P/T、70P/T と記す。

コーディングでは Splitwise-AA を 55P、15T とする。Baseline-A100 同様 H100 基線より 75% 多い。[図 16](#figure-16) の凡例に両負荷の構成を示す。分布はプール数へ反映され、HH はコーディングで 35P、5T、対話で 25P、15T となる。

**レイテンシとスループット。** [図 16](#figure-16) は等電力で入力負荷ごとの全指標を示す。コーディング（[図 16a](#figure-16)）では HH、HHcap、AA が H100 基線を上回る。基線は大プロンプトの混合処理で TBT が悪化する。AA は高スループットだが TTFT が高く、HA は高負荷でも低 TTFT/E2E を得る。高負荷では混合プールが断片化を避け、HA の P50 TBT は 90 RPS 後に H100 が混合へ入り低下する。

対話（[図 16b](#figure-16)）では HHcap がレイテンシを含む全項目で優れる。生成フェーズがコーディングより長く、トークンマシンに有利だからである。

### 6.5 バッチジョブ向けクラスタ

スループット最適時も厳しい SLO を課したが、バッチジョブなら高負荷で生成性能を上げられる。等電力最適を高負荷にすると A100 基線と AA が 0.89 RPS/&#36; で最良となる。全マシンが混合へ移るため Splitwise は同台数基線へ退化する。HH と H100 基線も同様に 0.75 RPS/&#36; となる。

## 7 議論

**新モデルへの拡張性。** 20 億 [Jav23, Zha22] から 1760 億 [Les23] 以上 [Ope23f] まで規模は多様だが、現代の生成 Transformer には二つのフェーズがある。MoE などの変種も同じである。Splitwise はこれだけを利用するため、自回帰処理に両フェーズがある限り将来の LLM にも適用できる。[第 6.4 節](#section-6-4) のように、一モデル用クラスタで他モデルも効率よく処理できる。

**代替計算ハードウェア。** 現在データセンタ推論で一般的な H100/A100 を使う [Nvi24f]。T4 などはメモリ不足である。方法論は要件に合う CPU、FPGA、ASIC [Dom19] にも適用できる。プロンプトは高計算・高帯域・低容量、トークンは中計算・高容量・高帯域を要する。AMD MI-250 [Amd23a] や HBM 付き Intel Sapphire Rapids [Int22a] は有効かもしれないが、実機や最適化実装がなく将来へ残す。

**両マシン間の相互接続。** 全設計で InfiniBand を仮定する。A100 を含む場合は低帯域である。同種では一般的だが、実現可能でも HA の H100-A100 接続は容易に得られない。CPU 経由 InfiniBand の HPC クラウド [Azu23] や RoCE Ethernet [Mit18] が代替となる。最適化転送により $10\times$ 低い帯域でも有効だろう。転送前圧縮も帯域を減らせる [Liu23t]。

**異種プロンプト／トークンマシン。** モデルとトレースの変化には頑健だが、異なる GPU でデータセンタを分断する HA などは CSP に課題をもたらしうる。

**往復する対話。** 現在の API は全履歴を送る [Ope23f]。将来 GPU 容量が十分なら文脈をキャッシュして再計算を避けられ、プロンプトのメモリ利用は変わる。次の要求に備えて KV キャッシュをプロンプト側へ戻す必要もありうる。

<span id="section-8"></span>

## 8 関連研究

**異種スケジューリングとデータフロー。** 対話サービス向け異種調度 [Zha19k, Pat23e, Rom21a] はコスト、エネルギー、性能を均衡させるが、全負荷を同一マシンで動かす。異種 CPU 調度 [Haq15, Van12, Haq17, Kum03, Yan17b, Che09] はプロファイルや監視でフェーズを識別して割り当てるが、バッチの複雑さを扱わない。分散データフロー [Dea08, Isa07, Shv10, Zah12] は大規模グラフと汎用性を扱う。Splitwise 推論は二段の静的グラフとして GPU 抽象を持つ枠組み [Mor18] で実装できるが、専用二フェーズ設計とフェーズ対応資源管理・バッチ処理が異なる。

**モデルサービング。** 近年はバッチ [Yu22a, Kwo23, Sto23d, Agr23, Ami22]、調度 [Kwo23, Pop22, She23b, Wu23a, Tur23, Hon23b]、メモリ [Dao22, Kwo23, Det22, Sto24] が研究される。CPU や低計算デバイスも提案された [Int23, Num23]。いずれも両フェーズを同一マシンで動かすが、Splitwise で分ければ性能を改善できる。

動画・ML サービスはレイテンシ制約下の依存モデル列を調度する [Hu21b, Cra20, Rom21a, Kan19, Alb22]。プロファイルに基づき機械間で割り当てる。推薦推論はモデル内外に計算・メモリ異種性があり、CPU とアクセラレータの選択 [Gup20a, Kwo19]、補完的モデルの併置 [Cho23b]、異種資源の分割 [Cen20, Jia21b] がある。Splitwise も要求内異種性を使うが、LLM の特性に応じた別の最適化を行う。

<span id="section-9"></span>

## 9 結論

LLM 推論の二フェーズを詳細に分析し、資源利用の違いを得た。Splitwise は別マシンへ分けてフェーズ別管理を可能にする。スループット、コスト、電力へ最適化した設計は負荷変化にも強い。性能 SLO 下で、同コストかつ 15% 低い電力で $1.76\times$、または同コスト・電力で $2.35\times$ のスループットを達成する。
