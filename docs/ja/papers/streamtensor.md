## 概要

データフローアーキテクチャ上で深層学習ワークロードを効率よく実行することは、メモリボトルネックを克服し、性能を最大化するうえで重要である。計算カーネル間で中間結果をストリーミングすれば効率を大幅に改善できるものの、既存手法ではカーネル間の相関、外部メモリアクセスの管理、バッファ最適化への対処が難しい。本研究では、ストリームベースのデータフローアクセラレータを自動的に構築し、最適化するコンパイラフレームワーク StreamTensor を提案する。StreamTensor は、ストリームレイアウトを明示的に符号化する新しい iterative tensor 型システムを導入し、カーネル融合、バッファ割り当て、メモリ最適化を円滑に実現する。テンソルタイリング、カーネル融合、リソース割り当てを含む 3 階層の設計空間を体系的に探索することで、StreamTensor は計算強度、メモリ効率、データストリーミングのバランスを取り、性能を最大化する。大規模言語モデル（LLM）を用いた FPGA 上での評価により、StreamTensor は最先端の FPGA LLM アクセラレータおよび GPU と比べてレイテンシをそれぞれ最大 0.76 倍、0.64 倍に短縮し、GPU と比べてエネルギー効率を最大 1.99 倍に高めた。これらの結果は、スケーラブルなデータフローベース深層学習アクセラレーションにおける StreamTensor の有望性を示している。

## 1 はじめに

<span id="section-1-1"></span>

### 1.1 データフローアーキテクチャ

データフローアーキテクチャは、NVIDIA H100 [Nvi23b] や Google TPUv4 [Jou23a] などの Von Neumann 型アーキテクチャに代わるものとして、大規模言語モデル（LLM）をはじめとする新しい AI アプリケーションのメモリウォールを克服するために、採用と研究が進んでいる。LLM は自己回帰的であるため、デコード段階はメモリ帯域に強く制約され、よりメモリ効率の高いアーキテクチャが求められる。AMD Versal [Gai19]、Sambanova SN40L [Pra24]、IBM AIU [Bur22] は、再構成可能なデータフローアーキテクチャを備えた商用 AI アクセラレータであり、多くの研究 [Pra17, Now17, Che24u] もデータフローアーキテクチャのレイテンシとエネルギー効率上の利点を示している。

[図 1](#figure-01) は、データフローアクセラレータの典型的な計算パターンを示す。[図 1(b)](#figure-01) に示すように、データフローアクセラレータには次のオンチップコンポーネントが含まれる。

1. **カーネル**：並列プロセッサ（例：シストリックアレイ）を用いて演算子または粗粒度の *task*（例：行列乗算）を計算し、入出力用のストリームインターフェースを提供する。
2. **トークン**：カーネル間で通信される最小単位の要素。
3. **First-in First-out（FIFO）**：生産側と消費側で異なるトークンレートを均衡させるために蓄積されたストリームトークンを保持し、デッドロックや不要なカーネルストールを防ぐ。
4. **ストリームレイアウトコンバータ**：ローカルな ping-pong バッファを介し、生産側と消費側のカーネルで異なる計算パターンに合わせて、実行中にストリームレイアウトを変換する。
5. **Direct Memory Access（DMA）**：外部メモリと通信し、メモリマップドインターフェースをストリームインターフェースへ、またはその逆へ変換する。

**図 1.** データフローアクセラレータの計算パターン。

カーネルは動的スケジューリング [Jos18] による *dataflow* 回路として設計される場合もあれば、オンチップデータを効率よく再利用するために、異なる *dataflow* 戦略（例：input stationary）を採用する場合もある [Che17a]。同じ用語を用いているが、これらの *dataflow* の概念は、本稿で扱うデータフローアーキテクチャおよびアクセラレータとは概念上独立している。

データフローアーキテクチャの中心的な考え方は、外部メモリへ頻繁にアクセスする代わりに、オンチップ FIFO を介してカーネル間で中間結果をストリーミングすることである。たとえば [図 1(b)](#figure-01) では、*Kernel0* が生成した中間結果は、[図 1(a)](#figure-01) のように外部メモリを経由せず、*Kernel1* と *Converter0* へ直接ストリーミングされる。[Pra24] で提案された慣例に従い、データフローカーネル間のストリーミングを有効にすることを *stream-based kernel fusion* と呼ぶ。さらに [図 1(c)](#figure-01) に示すように、データフローアクセラレータのスケジュールでは、*Kernel0* の完了前に *Kernel1* と *Converter0* が実行を開始できる。この実行の重なりにより、全体のスループットとレイテンシの両方を大幅に改善できる。

### 1.2 データフローアクセラレータのプログラミング

[図 2](#figure-02) は、現在のデータフローアクセラレータプログラミングのパラダイムを示す。データフローアクセラレータは一般に、アプリケーション固有アクセラレータとドメイン固有アクセラレータ（DSA）の 2 種類に分かれるため、それぞれを個別に説明する。

<span id="section-1-2-1"></span>

#### 1.2.1 アプリケーション固有アクセラレータ

このカテゴリでは、データフローコンポーネントとスケジュールが 1 つのアプリケーションに合わせて設計される。したがって、*programming* は通常、アーキテクチャおよびマイクロアーキテクチャの *design* または *generation* を指す。従来は Hardware Description Language（HDL）、High-level Synthesis（HLS）、Chisel [Bac12] のような meta-HDL がこの目的に用いられてきた [Che05, Zha18a, Chi18a, Sar23]。近年では、生産性を高めるために Accelerator Design Language（ADL）が登場し [Che24v, Dur20, Tho20]、計算、メモリレイアウト、データフロースケジュールを記述する型システムとプリミティブが導入されている。[図 2](#figure-02) に示すように、既存の解決策では、アプリケーションをデータフロースケジュールとコンポーネントへ変換する作業を人手で行い、それらを HLS、meta-HDL トランスパイラ、またはベンダー EDA ツールへ渡してハードウェアを生成する必要がある。ADL と HLS フレームワークには Design Space Exploration（DSE）[Koe16, Koe18, Ben19a, Ye22, Ago22, Zha24z] が組み込まれているものの、これらの取り組みは主に個々のカーネルの最適化に焦点を当てている。

<span id="section-1-2-2"></span>

#### 1.2.2 データフロー DSA

DSA は汎用プロセッサではなく、特定のアプリケーションクラスまたは特定ドメインの計算を効率よく実行するよう設計されている。DSA は多くの場合、Coarse-grained Reconfigurable Architecture（CGRA）に類似したアーキテクチャ [Gai19, Pra24, Pra17, Now17] として実現され、オンチップリソースを再構成してさまざまなデータフロー設計を実装する。現代の DSA は、C/C++ プリミティブ [Gai19, Zhu23c, Zhu24e] や Spatial [Koe18]、Halide [Rag13]、TVM [Che18f] などの Domain-specific Language（DSL）を用いてプログラムされ、ドメインに最適化されたコードを生成する。[図 2](#figure-02) に示すように、開発者はこれらの DSL または API を用いて、アプリケーションを論理コンポーネントへ手作業で変換しなければならない。その後、ソフトウェアコンパイラがそれらを物理リソースへマッピングし、オンチップ実行用の最終バイナリを生成する。これらの DSL はデータフローカーネルの自動チューニング機能を備えることが多いが、主眼はデータフローアプリケーション全体ではなく個々のカーネルの最適化にあり、大きな性能向上の余地が残されている。

<span id="section-1-3"></span>

### 1.3 課題

<span id="section-1-3-1"></span>

#### 1.3.1 課題 1：カーネル間の相関

先行研究 [Ye22, Ye24c] は、カーネル間の相関がアクセラレータ性能に影響し得ることを示している。カーネルはパイプライン方式で実行されるため、最適なスループットを得るには各レイテンシの均衡を取る必要がある。さらに、バッファで接続されたカーネルでは、非効率なメモリ使用を避けるため、並列化戦略を揃える必要がある。しかし先行研究が考慮したのは、メモリマップドアクセスに対応する ping-pong バッファだけであった。FIFO ではデータを順番どおりに push／pull しなければならず、制約がより厳しい。そのため、各カーネルについて次の課題が生じる。

1. *タイリング*：ストリーミングを可能にし、ローカルバッファリングを最小限に抑え、メモリ効率を維持できるタイルサイズを選択する。
2. *置換*：データストリーミング中のメモリ使用量を減らすようループ順序を変更する。
3. *ベクトル化*：レイテンシの均衡を取り、ストリーミング効率を高めるアンロール戦略を選択する。

これらの決定はカーネル間で相互依存するため、解析モデルや手作業の設計による大域的最適化は困難である。

<span id="section-1-3-2"></span>

#### 1.3.2 課題 2：外部メモリアクセス

既存コンパイラの大半 [Ye22, Ago22, Ye24c, Zha22e, Zha24z, Bas25] は、すべてのデータがオンチップに収まると仮定しているが、大規模アプリケーションでは現実的でない。オフチップメモリが関与する場合、各 DMA は次の問題に対処しなければならない。

1. メモリアクセスとカーネル実行をどのように重ねるか。
2. ストリーミングパターンに最も適したデータレイアウトは何か。
3. 帯域幅を最大化するため、データをどのようにパック／ベクトル化するか。

これらには単純でないパターン解析が必要で、手作業で扱うと誤りが生じやすい。DMA の設計はカーネルのタイリングおよびスケジューリングとも密接に結び付いており、複雑さをさらに増している。

<span id="section-1-3-3"></span>

#### 1.3.3 課題 3：ストリームベースのカーネル融合

ストリームベースのカーネル融合の目的は、すべての中間結果をオンチップでストリーミングし、外部メモリの使用を入出力に限定することである。しかし、生産側と消費側のカーネルでは計算パターンが異なるため、ストリームレイアウトに互換性がないことが多い。そのため、次の処理が必要になる。

1. カーネル間のレイアウト互換性を確認する。
2. 最小限の実行時ストリームレイアウトコンバータを生成する。
3. コンバータが利用可能なオンチップメモリに収まることを保証する。

これらの手順には複雑なパターン解析とシステム全体の把握が必要であり、手作業での解決は現実的でない。

<span id="section-1-3-4"></span>

#### 1.3.4 課題 4：FIFO サイズ決定

[図 1](#figure-01) に示すように、*Kernel1* が *Converter0* より遅い場合、FIFO がオーバーフローまたはアンダーフローし、ストールが連鎖して最終的にデッドロックへ至る可能性がある。動的スケジューリングによる解決策は存在するが [Jos21]、粗粒度アクセラレータは依然として手作業でのサイズ決定に依存しており [Che24v, Che24u]、多数の FIFO には対応できない。近年の自動化手法 [Hon24c] はシミュレーションで FIFO サイズを決定するが、時間がかかり、スケーラビリティに欠ける。

### 1.4 本研究の提案

[第 1.3 節](#section-1-3) で述べた課題により、[図 2](#figure-02) に示す現在のパラダイムを大規模なデータフローアクセラレータへ拡張することは難しい。そこで、[図 3](#figure-03) に示す設計パラダイムへの転換を提案する。個々のデータフローカーネルにおけるローカルバッファやベクトル化の設計には ADL／HLS／HDL または DSL が不可欠であるため、完全自動化を主張するものではない。しかし、個々のカーネルを設計または生成した後は、コンパイラがデータフロースケジュールを自動生成し、カーネルをアプリケーションレベルのデータフローアクセラレータへ組み立て、[第 1.3 節](#section-1-3) で挙げた課題をアルゴリズムによって解決すべきだと考える。これは GPU のソフトウェアエコシステムに似ている。そこでは CUDA や Triton [Til19b] などの DSL を用いて個々の GPU カーネルを設計または自動チューニングする一方、カーネルの組み立てとスケジューリングはコンパイラが自動的に処理し、効率とスケーラビリティを兼ね備えたプログラミングパラダイムを実現している。

この考えに基づき、データフローアーキテクチャでテンソルストリーミングを自動化するコンパイラ *StreamTensor* を提案する。本稿では、各課題へ体系的かつ階層的に対処する方法を説明する。先駆的な研究として、StreamTensor は各課題に対するアルゴリズム上の解決策を提案し、大規模ベンチマークを通じてその有効性を示す。これらの解決策は最適とは限らないが、明確に定義された最適化部分問題を明らかにし、異なる設計空間をまたぐ協調最適化の機会をもたらす。要約すると、本稿の貢献は次のとおりである。

1. ストリームベースのデータフローアクセラレータとそれに対応するランタイムシステムを自動生成する、初の PyTorch-to-device データフローコンパイラ StreamTensor を提案する。
2. ストリーム情報を体系的に符号化する iterative tensor（`itensor`）型を初めて提案する。この型システムは、ストリームベースのカーネル融合とデータフローコンポーネント生成の基盤となり、データフローアクセラレータ設計のスケーラビリティと生産性を高める。
3. テンソルタイリング空間、カーネル融合空間、リソース割り当て空間からなる 3 つの設計空間を提案し、複雑なデータフローアーキテクチャの設計空間をアルゴリズム的かつ階層的に扱う。さらに、リソース使用量を削減し、レイテンシとスループットを改善するため、各設計空間に探索アルゴリズムを提案する。
4. 区分関数に基づくトークン動作モデルを提案し、データフローアクセラレータにおけるデータフロー FIFO のサイズ決定問題をスケジューリング問題へ変換する。さらに、この問題を解く線形計画法（LP）アルゴリズムを提案し、デッドロックを防ぎながらリソース使用量を削減する。
5. LLM を用いて FPGA プラットフォーム上で StreamTensor を評価し、最先端の FPGA LLM アクセラレータおよび GPU と比べてレイテンシをそれぞれ最大 0.76 倍、0.64 倍に短縮し、GPU と比べてエネルギー効率を最大 1.99 倍に高めることを確認した。

## 2 StreamTensor フレームワーク

StreamTensor は、PyTorch モデルを最適化されたデータフロー実装へ変換するためのコンパイルフレームワークである。MLIR [Lat21a] コンパイルフレームワークを基盤としている。StreamTensor の全体アーキテクチャを [図 4](#figure-04) に示す。コンパイル処理は Torch-MLIR [Tor21] から得た PyTorch モデルを入力として開始し、複数の段階を経る。最初に、MLIR 組み込みの Linear Algebra（Linalg）演算を用いて、テンソル演算を構造化された Intermediate Representation（IR）へ変換する。続いて、要素単位演算の融合など、MLIR の Linalg パスによってこの IR を最適化する。その後 StreamTensor は Design Space Exploration（DSE）アルゴリズムを適用し、計算パターンに基づいてタイルサイズ、アンロール係数、置換などの要因を考慮しながら、最適なタイリング戦略を決定する。次に Linalg IR をデータフロー IR へ変換し、計算を階層的な task として編成する。この段階では、DMA、ストリームレイアウトコンバータ、FIFO を含むすべてのデータフローコンポーネントを生成する。外部メモリアクセスを最小化するストリームベースのカーネル融合や、生産側と消費側の実行を均衡させる FIFO サイズ決定など、重要な最適化もここで行う。最終段階で、StreamTensor はハードウェア固有コードとホストランタイムを生成する。StreamTensor がメモリ割り当て、ストリーム接続、ディレクティブの具現化を処理することで、HLS などのベンダーコンパイラは対象のデータフローアーキテクチャを生成できる。同時に、ホスト CPU とデータフローアクセラレータ間のデータ転送、カーネル実行、同期を管理するホストランタイムコードも生成する。

## 3 中間表現

<span id="section-3-1"></span>

### 3.1 型システム

StreamTensor は、IR の効率的な検証と最適化を可能にする型システムを導入する。StreamTensor 専用の型および演算検証器により、この型システムは任意の変換パスを適用した後の IR の妥当性を保証する。

<span id="section-3-1-1"></span>

#### 3.1.1 動機

従来、`tensor` 型はデータ型と、その形状を表す整数のリストを符号化する [Che18f, Rag13, Lat21a, Hag23a]。テンソルにはメモリマップド方式でアクセスでき、たとえばオフセットと形状に基づいてスライスを抽出または挿入できる。しかし、データフローカーネルは FIFO を介して通信する。FIFO は厳密なアクセス順序を強制し、メモリマップドアクセスではなくストリームアクセスのパターンに従う。そのため、従来のテンソル型ではデータフロー通信の正しさを保証できない場合がある。生産側と消費側が同じテンソル型を共有していても、ストリームのアクセス順序は曖昧なままとなり、意図しない動作を引き起こし得る。たとえば Graphene [Hag23a] では、テンソル型が符号化するのはメモリマップドレイアウトだけである。その結果、同じテンソル型を扱っていても、生産側が行優先順でストリームを生成し、消費側が列優先順を期待している場合、データの解釈を誤り、論理的な破損につながる。したがって、既存の解決策はタイリングなどの Linalg レベルの最適化には十分であるものの、データフローコンポーネントの生成やデータフロー最適化への適用では誤りが生じやすく、スケールしない。

#### 3.1.2 Iterative Tensor 型

この問題に対処するため、ストリームレイアウト情報を明示的に符号化する新しい `itensor` 型を提案する。これにより、型に基づく検証と最適化の両方が可能になり、効率も高まる。[図 5](#figure-05) は、同じ `tensor<8x8xf32>` 型の `tensor` から変換した 3 つの `itensor` の例を示す。テンソルを `itensor` へ変換するには、まず同一形状のテンソルスライスまたはベクトルに分割する。たとえば [図 5(b)](#figure-05) では、テンソルを形状 `4x2` の 8 個のテンソルスライスに分割する。続いて、定義された反復空間（通常は入れ子ループ）内でこれらのスライスへ反復的にアクセスする。反復空間は、tripcount とステップサイズという 2 つのリストで定義される。[図 5(b)](#figure-05) の反復空間は `[4,2]*[2,4]` であり、反復インデックス `[0,0]`、`[0,4]`、`[2,0]`、`[2,4]` などを生成する。反復空間からデータ空間への写像はアフィンマップで指定される。たとえば [図 5(b)](#figure-05) の `(d0,d1)->(d1,d0)` は、反復インデックスを転置する。したがってデータアクセスのインデックスは `[0,0]`、`[4,0]`、`[0,2]`、`[4,2]` などとなり、[図 5(b)](#figure-05) に示すように、この転置が反映される。`itensor` ではテンソルスライスへ複数回アクセスでき、そのパターンは反復マップに明示的に符号化される。たとえば [図 5(c)](#figure-05) では、反復空間が `[4,2,2]*[2,1,4]`、反復マップが `(d0,d1,d2)->(d2,d0)` であり、次元 `d1` はいずれのデータ次元にも対応しない。`d1` が 0 から 1 まで反復すると、それより下位のすべての次元（`d2` など）も再び反復される。その結果、対応するデータ次元（例：行次元）にも再アクセスし、形状 `4x2` のテンソルスライスについて `[0,0]`、`[4,0]`、`[0,0]`、`[4,0]`、`[0,2]` などのインデックスを生成する。`itensor` 型に要素形状、反復空間、反復マップを符号化することで、データフローカーネルのストリームパターンを一意に決定できる。生産側と消費側の `itensor` 型が一致する場合、その間にストリーミング通信を安全に確立できる（[図 5](#figure-05) の *Case1*）。一致しない場合は両者の間にストリームレイアウトコンバータを挿入する必要があり（[図 5](#figure-05) の *Case2*）、レイアウト変換に必要な最小 ping-pong バッファサイズを `itensor` 型から解析的に推論できる。レイアウトコンバータ生成の詳細は [第 5.2.1 節](#section-5-2-1) で説明する。既存のテンソルベース型システムはストリーム情報を持たないため、ストリームベースのカーネル融合には不十分であり、ストリームベースのデータフロー最適化における有用性が制限される。

<span id="section-3-1-3"></span>

#### 3.1.3 Stream 型

従来のテンソルコンパイラでは、低レベルの最適化とコード生成を可能にするため、高レベルのテンソル IR を低レベルのメモリ／バッファ IR へ *bufferize* する必要がある。この慣例に従い、bufferization の際に `itensor` 型から lower される `stream` 型を提案する。不変の `itensor` オブジェクトとは異なり、`stream` オブジェクトはハードウェア FIFO を表し、ストリームの read や write などの演算による変更をサポートする。`stream` 型が符号化するのはデータ型と FIFO 深さだけであり、ストリームレイアウト情報は bufferization 中に除去される。そのため、データフローコンポーネントの生成と最適化は `itensor` レベルの IR で完了させなければならない。bufferization 後の `stream` IR は、より低レベルのハードウェア／ランタイム最適化とコード生成に用いられる。

### 3.2 演算

[第 3.1 節](#section-3-1) の型システムを基盤として、StreamTensor はさまざまなデータフロー動作を表す `itensor` 演算と `stream` 演算を導入する。さらに、データフローアクセラレータの多層階層を表す構造演算を導入し、`itensor` レベルと `stream` レベルの両 IR で共有する。

<span id="section-3-2-1"></span>

#### 3.2.1 Iterative Tensor 演算

[表 1](#table-01) は `itensor` レベルの演算一式を示す。全体として、これらの演算は名前から役割が分かるため、意味が分かりにくいものだけを取り上げる。`itensor_write` は概念上、要素を FIFO へ書き込む、つまり push する操作として理解できる。これは destination-carried 演算であり、デスティネーションは `dest` オペランドを介して渡される `itensor` である。たとえば [図 5(b)](#figure-05) の `itensor`（`itensor(b)` と呼ぶ）への反復的な書き込みは、次のように表せる。

```text
%empty = itensor_empty() : itensor(b)
%res0 = scf.for 0 to 8 step 2 iter_args={%arg0 = %empty} {
  %res1 = scf.for 0 to 8 step 4 iter_args={%arg1 = %arg0} {
    %value = ... : tensor<4x2xf32> // %value is defined
    %output = itensor_write %value into %arg1 : ...
    scf.yield %output : itensor(b)
  } : itensor(b)
  scf.yield %res1 : itensor(b)
} : itensor(b)
```

ここで `scf` は、`for` ループを含む構造化制御フロー用の MLIR 組み込み dialect である。`scf.for` も destination-carried であり、`%empty` が引数として渡され、`itensor_write` を通じて反復的に push される。最終的に `%res0` が最終結果として返される。一方、`itensor_read` は FIFO から要素を pull する操作を表す。たとえば `itensor(b)` の読み出しは、次のように表せる。

```text
%source = ... : itensor(b) // %source is defined
scf.for 0 to 8 step 2 {
  scf.for 0 to 8 step 4 {
    %empty = tensor.empty() : tensor<4x2xf32>
    %value = itensor_read %source init %empty : ...
    ... = ... %value ... // %value is used
  }
}
```

`itensor_converter` には、実行中にストリームレイアウトを変換するローカル ping-pong バッファが含まれる。たとえば [図 5](#figure-05) の *Case1* では、source と target が同じ `itensor` 型を共有するため、FIFO を介して接続できる。*Case2* では型が異なるため、コンバータを挿入しなければならない。このストリームレイアウトに対応するには、最小 `8x2` の ping-pong バッファが必要である。source が ping バッファへ書き込む間、target は pong バッファを 2 回読み出し、その後で両者を交換する。

<span id="section-3-2-2"></span>

#### 3.2.2 Stream 演算

[表 2](#table-02) は `stream` レベルの演算を示す。これらも大半は名前から役割が分かるため、`itensor` 演算との主な違いだけを取り上げる。[第 3.1.3 節](#section-3-1-3) で述べたように、`stream` オブジェクトは変更可能であり、destination-carried セマンティクスは使用しない。FIFO の push と pull は次のように記述できる。

```text
%stream = stream() : stream<f32, depth: 32>
scf.for 0 to 8 step 2 {
  scf.for 0 to 8 step 4 {
    %value = ... : f32 // %value is defined
    stream_write %value into %stream : ...
  }
}
scf.for 0 to 8 step 2 {
  scf.for 0 to 8 step 4 {
    %value = stream_read %stream : ...
    ... = ... %value ... // %value is used
  }
}
```

destination-carried 方式の `itensor` と異なり、新しい複製を作成せず、同じ `%stream` を一貫して使用する点に注意されたい。`stream` IR はコード生成に適しているが、define-use 解析を複雑にする。そのため、高レベルのデータフロー最適化には `itensor` の方が適している。`stream` 演算は、`itensor` 型システムによる厳密な検証を受けた `itensor` 演算から lower されるため、その正しさは構成によって保証される。

#### 3.2.3 構造演算

`itensor` 演算と `stream` 演算が動作をモデル化するのに対し、構造演算は階層をモデル化する。[表 3](#table-03) は StreamTensor のすべての構造演算を示す。`kernel` 演算はデータフローカーネル（[図 1](#figure-01)）を表し、`task` 演算のグラフを含む。入出力には `tensor` を取り、境界で `itensor` との間を変換する。この暗黙の変換が DMA として働く。`kernel` 内の通信にはオンチップストリーミングを用い、`kernel` 間の通信には外部メモリを用いる。例を次に示す。

```text
%source = ... : tensor<8x8xf32> // %source is defined
%result = kernel(
  %arg : itensor<b> = %source : tensor<8x8xf32>
) {
  ... = ... %arg ... // %arg is used
  %output = ... : itensor<c> // %output is defined
  yield %output : itensor<c>
} : tensor<8x8xf32>
```

カーネル境界で変換することにより、カーネル融合中に DMA を明示的に扱う必要がなくなり、変換の効率と解析可能性が高まる。一方、`task` 演算は transparent であり、その境界では型を変換しない。これはカーネル内のデータフロー task を表し、階層的なデータフロー設計では入れ子にすることもできる。`itensor` レベルでは、`task` は destination-carried であり、出力が `inits` を介してデスティネーションへ書き込まれるため、define-use 解析の効率が高まる。例を次に示す。

```text
%empty = ... : itensor(b)
%result = task @example inits={%arg = %empty} {
  %value = ... : tensor<4x2xf32> // %value is defined
  %output = itensor_write %value into %arg : ...
  yield %output : itensor(b)
} : itensor(b)
```

lowering と bufferization の後、同じコードは次のようになる。

```text
%stream = stream() : stream<f32, depth: 32>
task @example {
  %value = ... : f32 // %value is defined
  stream_write %value into %stream : ...
}
```

`task` は `itensor` 演算と `stream` 演算の両方を組み合わせており、異なるレベルのデータフロー最適化に用いる 2 つの IR をまたぐ統一的な構造抽象化であることが分かる。最終的に、すべてのデータフロー `task` はコード生成のために MLIR 組み込みの `call` 演算と `func` 演算へ lower される。

## 4 コンパイルパイプライン

型システムと演算を基盤として、Linalg IR をハードウェア実装と対応するランタイムへコンパイルするパイプラインを導入する。すべてのコンパイルパスを [図 4](#figure-04) に示す。本節では、このコンパイラを理解するうえで固有かつ不可欠な、Linalg からデータフローへの変換、データフローカーネル融合、データフロー最適化に焦点を当てる。

<span id="section-4-1"></span>

### 4.1 Linalg からデータフローへの変換

[図 6(a)-(c)](#figure-06) は、Linalg からデータフローへの変換処理を示す。元の Linalg 演算（[図 6(a)](#figure-06)）をまず [図 6(b)](#figure-06) の形へタイリングする。ここで `scf.for` は、タイリングのループネストを表す。各反復で `extract_slice` が入力テンソルのタイルを抽出し、タイル化した Linalg 演算へ渡す。演算が出力タイルを生成した後、`insert_slice` がそれらを完全なテンソルへ戻す。続いて [図 6(c)](#figure-06) に示すように、タイル化された各ループネストをその場で `kernel` 演算へ変換する。入出力の `tensor` は `kernel` の境界で `itensor` との間を変換される。`itensor` 型は次の情報から推論される。

1. 入れ子になった `scf.for` ループ：反復の tripcount とステップサイズが `itensor` の反復空間を定義する。
2. `extract_slice` 演算と `insert_slice` 演算のオフセットおよびサイズ：オフセットは反復マッピングを定義し、サイズは要素形状を定義する。たとえばオフセット `[%iv2, %iv0]` は反復マップ `(d0,d1,d2)->(d2,d0)` を生成する。

変換後、`extract_slice` 演算と `insert_slice` 演算は、それぞれ `itensor_read` 演算と `itensor_write` 演算に置き換えられる。得られた `scf.for` ループネストを `task` で囲み、データフローカーネルがデータフロー task を含む単一レベルのデータフロー階層を形成する。Linalg のセマンティクスをデータフローへ変換することで、その後のデータフロー指向の変換と最適化が可能になる。

<span id="section-4-2"></span>

### 4.2 データフローカーネル融合

タイル化したすべての Linalg 演算をデータフローカーネルへ変換した直後、これらのカーネルは従来の `tensor` を介して通信し、そのデータは最終的に外部メモリへ格納される。この通信オーバーヘッドを減らすため、StreamTensor はストリームベースのカーネル融合を適用する。[図 6(c)-(d)](#figure-06) は、この処理を示す。*Kernel0* と *Kernel1* を融合するには、まず *Kernel0* の出力 `itensor` 型と *Kernel1* の入力 `itensor` 型を比較する。[第 3.1.2 節](#section-3-1-2) で述べたように、型が一致すればカーネルを直接融合できる。一致しなければ、[図 6(d)](#figure-06) に示すストリームレイアウトコンバータを挿入する。融合後のカーネルは 2 つの `task` と 1 つの `converter` で構成され、すべてが `itensor` を介して通信する。`itensor` はオンチップストリーム FIFO へ lower される。`itensor` 型システムにより、コンバータがオンチップメモリを消費する可能性と引き換えに、あらゆるデータフローカーネルを *by design* で融合できる。[第 5.2 節](#section-5-2) では、メモリ制約下におけるカーネル融合空間の探索を説明する。

融合後、StreamTensor は外部メモリアクセスの効率を高める追加の最適化パスを適用する。具体的には、バーストメモリアクセスに適したデフォルトレイアウトとタイル化レイアウトを相互変換するため、`tensor` の `pack` 演算と `unpack` 演算を `kernel` の前後に挿入する。たとえば `64x64` テンソルを `[16,16]` のタイルサイズで処理すると、パック後のテンソル形状は `4x4x16x16` となる。外部メモリ帯域幅を最大限に利用するため、StreamTensor はテンソルをベクトルによって widening する。たとえば 512-bit DDR または HBM と `uint8` 要素を用いる場合、64 要素を `vector<64>` にまとめると帯域幅を完全に利用できる。[図 6](#figure-06) では、パックしたテンソルを形状 `4x4x2x2xvector<8x8>` へ widening している。`pack` 演算と `widen` 演算は最終的にホスト CPU 上のランタイム演算へ lower され、アクセラレータ用のデータを準備するため、レイテンシとメモリのオーバーヘッドが生じることに注意されたい。ただし、静的テンソル（例：事前学習済みパラメータ）では、`pack` と `widen` をそれらのテンソルへ直接融合できるため、ランタイムコストは生じない。動的テンソル（例：activation）では、効果的な Linalg タイリング空間の探索により、`pack` 演算と `widen` 演算を直前の層の `unpack` 演算および `unwiden` 演算へ畳み込める。その結果、`pack` 演算と `widen` 演算が必要なのはモデルの入出力だけとなり、ランタイムにおけるメモリとレイテンシのオーバーヘッドは無視できるほど小さくなる。

### 4.3 データフロー最適化

<span id="section-4-3-1"></span>

#### 4.3.1 具現化

[図 7(a) と (b)](#figure-07) は、コンバータと DMA の *materialization* 処理を示す。Materialization では、高レベルのデータフローコンポーネントを低レベルの実装へ変換する。通常、その実装は `tensor` 演算と `itensor` 演算を含む `scf.for` ループネストである。当初、コンバータは `itensor_converter` で表され、DMA は `kernel` 境界における `tensor` から `itensor`、またはその逆の変換を通じて暗黙に処理される。この抽象化により、カーネル融合とコンバータ最適化が容易になる。たとえば、1 つの生産側に複数の消費側があるために生成された冗長なコンバータは、MLIR の Common Sub-expression Elimination（CSE）によって除去できるが、materialization 後にはこの処理が難しくなる。一方、materialization 後は、すべてのデータフローコンポーネントが入れ子の `task` として表されるため、その後のデータフロー最適化を効率よく容易に行える。コンバータについては、[図 7(a)](#figure-07) に示すように、*Converter0* が `16x64` ping-pong バッファで接続された 2 つの `scf.for` ループネストを含む。この 2 つのループネストは、元の完全な `64x64` テンソルを反復処理するため、*共有* の親 `scf.for` ループで囲まれる。したがって、`16x64` ping-pong バッファは 4 回再利用され、オンチップメモリリソースの使用量を実質的に 4 分の 1 へ削減する。[第 5.2 節](#section-5-2) では、ping-pong バッファの形状と共有ループを `itensor` 型から推論する方法を説明する。

DMA については、[図 7(a)](#figure-07) に示すように、`tensor<4x4x2x2xvector<8x8>>` から `itensor<16x16...>` への入力型変換が、次の動作を行う DMA を表す。1）外部メモリから `vector<8x8>` データを `4x4x2x2` 回ロードする。2）外部メモリアクセスのレイテンシを隠蔽するため、このデータを `16x16` ping-pong バッファへ格納する。3）`itensor` 型で符号化されたレイアウトに従ってデータを FIFO へ push する。[図 7(b)](#figure-07) では、これら 3 つの動作を `scf.for` ループネストで実装する *DMA0* が自動生成されている。`itensor` ベースの型システムは、コンバータと DMA に必要なすべての情報を符号化している点に注意されたい。従来のテンソル型にはこの機能がなく、データフローコンポーネント生成における有用性が制限される。

<span id="section-4-3-2"></span>

#### 4.3.2 Iterative Tensor Folding

[図 7(b)-(c)](#figure-07) は、`itensor` の folding を示す。FIFO で接続された *DMA0* の `itensor_write` と *Kernel0* の `itensor_read` があるとする。これらは、ストリーミングで接続された 2 つの別個のローカルバッファを表す。Folding により FIFO を除去し、2 つのバッファを統合する。この最適化はオンチップメモリの使用量を減らすとともに、カーネル間の実行の重なりを増やし、全体のレイテンシを改善できる。[図 7(c)](#figure-07) に示すように、取得したタイルを *Kernel0* の `linalg.generic` 演算へ直接渡し、冗長なバッファリングと通信を除去する。`itensor` folding では、生産側と消費側のメモリアクセスパターンが完全に一致しなければならない。この制約は、任意のデータフローカーネル間に適用できるストリームベースのカーネル融合よりも厳しい。したがって、すでに融合されたカーネルに対する追加の最適化として `itensor` folding を実装する。

<span id="section-4-3-3"></span>

#### 4.3.3 Iterative Tensor のベクトル化

データフローカーネルは並列に動作することが多いため、十分な帯域幅を確保するにはデータフロー FIFO をベクトル化しなければならない。[図 7(c)-(d)](#figure-07) は、`itensor` を `vector<2x4>` へベクトル化する処理を示す。*DMA0+Kernel0* 側では、`itensor_write` が `transfer_read`（バッファからの読み出し）に続いて `itensor_write`（FIFO への書き込み）を行うループになる。*Converter0* 側では、読み出しに対して同様の変換を適用する。この処理により、FIFO の帯域幅をデータフローカーネルの並列度に合わせる。

<span id="section-5"></span>

## 5 設計空間

実現可能で最適化されたアクセラレータを生成するには、コンパイルパスのパラメータを適切に設定しなければならない。[図 4](#figure-04) に示すように、設計空間全体を Linalg タイリング空間、カーネル融合空間、リソース割り当て空間という 3 つの部分空間に分割する。

<span id="section-5-1"></span>

### 5.1 Linalg タイリング空間

Linalg タイリング空間は、各データフローカーネルのタイリング係数、アンロール係数、置換戦略、入出力のベクトル化を決定する。StreamTensor では、この空間を Linalg 演算のグラフで表し、ループの tripcount、ステップサイズ、ループ種別（reduction または parallel）などのプロパティを各ノードへ注釈する。探索結果もこのグラフへ書き戻し、変換パスの設定に用いる。

タイリングについては、ハイパーパラメータ `default_tile_size` をユーザーへ公開し、すべてのカーネルの全次元に適用する。アンロールについては intensity-aware アルゴリズムを開発した。このアルゴリズムは max-heap を用いてレイテンシが最長のカーネルを反復的に選択し、ユーザー定義ハイパーパラメータ `overall_unroll_size` に達するまでアンロール係数を増やす。この方法はカーネル間のレイテンシを均衡させ、スループットを改善する。アンロールサイズの決定後、ループ反復空間とテンソル形状を解析してベクトル化係数を推論する。置換には、reduction ループを外側へ移動しながら parallel ループを最内側に保つヒューリスティックを用い、パイプラインループの initiation interval（II）を短縮する。StreamTensor では、データフローカーネル融合の結果をフィードバックとして、ブラックボックス最適化器 Optuna [Aki19] により Linalg タイリング空間のハイパーパラメータを自動探索する。

<span id="section-5-2"></span>

### 5.2 カーネル融合空間

[第 4.2 節](#section-4-2) で述べたように、カーネル融合はカーネル間のストリーミングを可能にする。生産側と消費側の `itensor` 型が異なる場合は、コンバータを挿入しなければならない。Linalg タイリング空間の探索によってすべてのデータレイアウトと形状が決まるため、全データフローカーネルのインターフェースにおける `itensor` 型も固定される。その結果、任意のカーネル対を融合する際のメモリオーバーヘッドも確定する。オンチップメモリには限りがあるため、すべてのカーネルを融合することは一般に不可能である。メモリリソース制約を守りながら融合するカーネル対を効果的に選択するため、2 つのアルゴリズムを提案する。[Algorithm 1](#algorithm-01) はストリームレイアウトコンバータに必要な最小 ping-pong バッファ形状を推論し、[Algorithm 2](#algorithm-02) はオンチップメモリ制約下で大域的な融合計画を決定する。

<span id="algorithm-01"></span>

**Algorithm 1：ストリームレイアウトコンバータ生成の疑似コード。**

- **入力：** $\mathit{src}$、Source の `itensor` 型。$\mathit{res}$、Result の `itensor` 型。
- **出力：** $\mathit{bufShape}$、ping-pong バッファの形状。$\mathit{beforeLoop}$、ping-pong バッファを挿入するループインデックス。
- $\mathit{bufShape}\gets []$、$\mathit{beforeLoop}\gets 0$ と設定する。
- $\mathit{sharedLoops}\gets []$、すなわち $\mathit{src}$ と $\mathit{res}$ が共有するループのインデックスと設定する。
- $\mathit{dim}\gets 0$ **から** $\mathit{src}.\mathrm{rank}()-1$ **まで繰り返す**：
  - **もし** $\mathit{src}.\mathrm{elementSize}(\mathit{dim})\neq\mathit{res}.\mathrm{elementSize}(\mathit{dim})$ **なら**：**中断する**。
  - $\mathit{srcExpr}\gets\mathit{src}.\mathit{iterMap}[\mathit{dim}]$ と設定する。
  - $\mathit{resExpr}\gets\mathit{res}.\mathit{iterMap}[\mathit{dim}]$ と設定する。
  - **もし** 両方の $\mathrm{Expr}$ が同じ位置の次元 **なら**：
    - $\mathit{bufShape}.\mathrm{append}(\mathit{src}.\mathrm{elementSize}(\mathit{dim}))$ と設定する。
    - $\mathit{sharedLoops}.\mathrm{append}(\mathit{srcExpr}.\mathit{pos})$ と設定する。
    - $\mathit{beforeLoop}\gets\mathit{beforeLoop}+1$ と設定する。
  - **それ以外：** **中断する**。
- $\mathit{loop}\in\mathit{sharedLoops}$ かつ $\mathit{loop}\geq\mathit{beforeLoop}$ を満たす要素がある **間**：
  - $\mathit{bufShape}.\mathrm{pop}()$ および $\mathit{loop}\gets\mathit{sharedLoops}.\mathrm{pop}()$ と設定する。
  - **もし** $\mathit{loop}\neq -1$ **なら**：$\mathit{beforeLoop}\gets\mathit{beforeLoop}-1$ と設定する。
- $\mathit{bufShape}.\mathrm{append}(\mathit{src}.\mathit{shape}[\mathit{bufShape}.\mathrm{size}():])$ と設定する。
- **返り値：** $\{\mathit{bufShape},\mathit{beforeLoop}\}$。

<span id="section-5-2-1"></span>

#### 5.2.1 ストリームレイアウトコンバータの生成

[Algorithm 1](#algorithm-01) は、source と target の `itensor` を各データ次元について比較する（3-16 行目）。データ次元に沿って ping-pong バッファサイズを削減できるのは、次の 2 条件を満たす場合だけである。1）要素サイズが等しい（4-5 行目）。2）対応する反復次元が等しく、同じループネストレベルを参照している（8-16 行目）。たとえば [図 5](#figure-05) では、`itensor(b)` と `itensor(c)` の第 2 データ次元がどちらも反復次元 `d0` に対応するため、この次元を削減でき、バッファリングするタイルは 1 列だけでよい。Materialization では、この削減された次元に沿ってバッファを再利用する共有ループを生成する。一方、第 1 データ次元はそれぞれ反復次元 `d1` と `d2` に対応するため、削減できない。したがって、タイルの全行をバッファリングする必要がある。その結果、[図 5](#figure-05) に示すように、レイアウトコンバータには 2 タイル（ping-pong バッファリング後は 4 タイル）が必要となる。

削減可能なデータ次元と対応する共有ループを特定した後、アルゴリズムは共有不能な親ループを持つものを除外し、バッファが実現可能であることを保証する（17-19 行目）。たとえば loop-`{0,1,2,4}` が共有可能でも loop-3 が共有不能なら、loop-4 を除外しなければならない。最後に、バッファ形状と共有ループを返す。この処理の最悪ケースは、どの次元も削減できず、融合のためにデータ全体をオンチップへ保持しなければならない場合である。その場合、メモリオーバーヘッドが大きくなる可能性がある。

<span id="algorithm-02"></span>

**Algorithm 2：カーネル融合探索の疑似コード。**

- **入力：** $G$、カーネル融合の設計空間。$C_{\max}$、最大融合コスト。
- **出力：** $F$、融合するノード集合。$C$、融合ノードのコスト。
- $F\gets[\emptyset]$、$C\gets[0]$、およびノードから融合インデックスへのマップ $M\gets\{\}$ を設定する。
- $\mathrm{topo\_sort}(G)$ 内の各 $n$ **について**：
  - $\mathit{cand}\gets\{\}$、すなわち融合候補のインデックスからコストへのマップを設定する。
  - $G.\mathrm{predecessors}(n)$ 内の各 $p$ **について**：
    - $\mathit{cost}\gets\mathrm{compute\_memory\_cost}(G.\mathit{edges}[p,n,0])$ と設定する。
    - $\mathit{cand}[M[p]]\gets\mathit{cand}.\mathrm{get}(M[p],0)+\mathit{cost}$ と設定する。
  - $\mathit{f\_idx}\gets\mathrm{len}(F)$ および $\mathit{f\_cost}\gets 0$ と設定する。
  - **もし** $\mathrm{len}(\mathit{cand})>0$ **なら**：
    - $\mathit{f\_idx}\gets\max(\mathit{cand}.\mathrm{keys}())$ および $\mathit{f\_cost}\gets\mathit{cand}[\mathit{f\_idx}]$ と設定する。
  - **もし** $\mathit{f\_idx}=\mathrm{len}(F)$ **または** $\mathit{f\_cost}+C[\mathit{f\_idx}]>C_{\max}$ **なら**：
    - $F.\mathrm{append}(\{n\})$、$C.\mathrm{append}(0)$、および $M[n]\gets\mathrm{len}(F)-1$ と設定する。
  - **それ以外：**
    - $F[\mathit{f\_idx}].\mathrm{add}(n)$ および $C[\mathit{f\_idx}]\gets C[\mathit{f\_idx}]+\mathit{f\_cost}$ と設定する。
    - $M[n]\gets\mathit{f\_idx}$ と設定する。
  - $G.\mathit{nodes}[n][\texttt{"fusion\_index"}]\gets M[n]$ と設定する。
- **返り値：** $F,C$。

#### 5.2.2 カーネル融合の探索

[Algorithm 2](#algorithm-02) への入力 $C_{\max}$（*max fusion cost*）は、融合後の 1 つのカーネルが使用できるオンチップメモリの最大量を表す。FPGA では、通常これをオンチップメモリの総容量に設定する。そのため、カーネル融合処理はグラフ分割問題とみなすこともできる。融合後、得られた各融合カーネルは 1 台の FPGA を占有する。計算グラフがこのようなカーネルを複数含む場合、それらは複数の FPGA 上、単一の FPGA 上で逐次的に、または両者を組み合わせて実行できる。StreamTensor はコンパイラとして、これらすべての方式をサポートする。ただし、$M$ 個のカーネルを $N$ 台の FPGA へマッピングし、FPGA 間通信を管理することは本稿の範囲外である。[Algorithm 2](#algorithm-02) はすべての `kernel` をトポロジカル順に走査する（3 行目）。各カーネルについて、まず先行カーネルから融合候補を集め、融合コストを計算する（4-11 行目）。リソース上限を超えなければ（15-20 行目）、最も近い有効な候補とカーネルを融合する（13-14 行目）。融合結果をグラフへ書き戻し（22 行目）、[第 4.2 節](#section-4-2) で述べた最適化の設定に用いる。単一カーネルが 1 台の FPGA のリソースを超えない限り、データフローカーネル融合には必ず実行可能解が存在する。超える場合は結果をタイリング空間へフィードバックし、たとえばタイリング係数やアンロール係数を減らして再調整する。

<span id="section-5-3"></span>

### 5.3 リソース割り当て空間

FPGA のようなハードウェアでは、オンチップメモリと計算リソースが限られるため、効果的なリソース割り当てが配線混雑とクロック周波数に大きく影響する。この空間では、次の問題を解く必要がある。

1. **FIFO サイズ決定**：デッドロックを防ぎ、実行の重なりを増やせるよう FIFO 深さを決定する。詳細は本節で説明する。
2. **グラフ分割**：複数ダイを備えたハードウェアでは、`task` を各ダイへ割り当てる必要がある。この割り当て問題を Integer Linear Programming（ILP）として定式化し、解く。ILP モデルでは、二値リストが各 `task` の割り当てを表す。制約により、このリストでは 1 要素だけを「1」にでき、その位置が割り当て先のダイを示す。ILP の目的は、ダイ間通信とダイ間のリソース不均衡の両方を最小化することである。同様の定式化はすでに研究されているため [Guo21b, Du23b]、これ以上の詳細は省略する。
3. **メモリ割り当て**：各バッファをサイズに基づく優先順位で FPGA 上の LUTRAM、BRAM、または URAM へ配置する。このアルゴリズムは単純なため、詳細は省略する。

<span id="section-5-3-1"></span>

#### 5.3.1 トークン動作モデル

[第 1.3 節](#section-1-3) で述べた FIFO サイズ決定問題に対処するため、まず区分線形関数に基づくトークン生成・消費モデルを提案する。[図 8(a)](#figure-08) は、*InterFIFO* を介して融合された *Source* カーネルと *Target* カーネルの間のトークン通信を示す。Pipeline II は連続する 2 つの出力トークン間のサイクル数であり、initial delay は最初の出力トークンを生成するまでに必要なサイクル数である。トークンは、カーネル間で通信される最小単位のデータ要素と定義する。*time0* では 5 個すべての入力トークンが *InputFIFO* にあり、*time1* から *Source* へストリーミングされ始める。*time5* では、*Source* が *token1* を *InterFIFO* へ push する一方、*Target* が *token0* を消費するため、*InterFIFO* には 1 個のトークンが残る。*time6* では、*Target* が *token0* の処理に 2 サイクルを要するため、*token1* を消費できない。その間に *token2* が *InterFIFO* へ push され、トークン数は 2 へ増える。*time8* で *Source* がトークンの処理を終え、このとき *InterFIFO* は最大容量となる 3 個のトークンを保持している。その後 *Target* は残りのトークンを消費し続け、*time15* ですべてのトークンの処理が完了する。

これらの複雑な動作を解析可能な関数でモデル化するため、[図 8(a)](#figure-08) のトークン状態を [図 8(b)](#figure-08) のように再配置し、同じトークンの状態を同じ行に揃える。*Source*（青）と *InterFIFO*（赤）の領域間にある境界は、区分線形関数（青い曲線）で完全にモデル化できることが分かる。この関数は、*Source* が *生成* したトークン数を表す。同様に、*Target* が *消費* したトークン数をオレンジ色の曲線でモデル化できる。2 本の曲線の差が *InterFIFO* 内のトークン数を表す。これらの曲線は、カーネルのレイテンシ、initial delay、pipeline II で表せる。StreamTensor はフローの途中で HLS などのベンダーツールを自動的に呼び出し、各カーネルについてこれらの指標をプロファイリングする。これらの指標はベンダープラットフォームのアーキテクチャ、テクノロジーノード、マッピング戦略に固有であるため、このプロファイリング処理を通じて取得しなければならない。リソース割り当ては最後の設計空間であるため、その後の StreamTensor フローではカーネル設計が変化しない。ベンダーツールが決定的なスケジューリングアルゴリズムを使用する限り、最終アクセラレータの指標は事前にプロファイリングした値と一致する。この一貫性により、本アルゴリズムの妥当性が保証される。

<span id="section-5-3-2"></span>

#### 5.3.2 最大トークン数の計算

[図 8(c)](#figure-08) に示すように、$L$ を *Source* の実行にかかる総レイテンシ、$D$ を *Source* の実行開始から最初の出力トークン生成までの initial delay、$\mathit{delay}$ を *Source* の実行開始から *Target* の実行開始までの時間と定義する。*Source* が最初のトークンを生成する前に *Target* は実行を開始できないため、当然ながら $\mathit{delay}$ は常に $D$ 以上となる。$T$ は、アクセラレータを 1 回実行する際に *Source* から *Target* へ渡される正確なトークン数と定義する。$T$ は、StreamTensor でテンソル形状から解析的に推論できる静的な値である。動的テンソル形状の処理方法は [第 5.3.5 節](#section-5-3-5) で説明する。$T$ が静的であれば、*InterFIFO* 内の最大トークン数 $\mathit{max\_tokens}$ は $\mathit{delay}$ から解析的に計算できる。

<span id="equation-01"></span>

$$
\mathit{max\_tokens}=\min\left(T,~T-\left\lfloor\frac{L-\mathit{delay}}{\mathrm{II}_{\mathrm{Target}}}\right\rfloor\right)
$$

Pipeline $\mathrm{II}$ は曲線の傾き、すなわちカーネルのスループットを決定する。[図 8(c)](#figure-08) は、*Source* のスループットが *Target* より高い場合を示す。反対に *Source* のスループットが低い場合は、データ不足により *Target* のスループットが制限され得る。[図 8(d)](#figure-08) は $\mathit{delay}$ が十分に大きければ *Target* が影響を受けないことを示し、[図 8(e)](#figure-08) は *Target* が最終的にデータ不足となり、そのスループットが *Source* のスループットに揃うことを示す。どちらの場合も $\mathit{max\_tokens}$ は $\mathit{delay}$ から計算できる。

<span id="equation-02"></span>

$$
\mathit{max\_tokens}=\min\left(T,~\left\lceil\frac{\mathit{delay}-D}{\mathrm{II}_{\mathrm{Source}}}\right\rceil\right)
$$

[式 1](#equation-01) と [式 2](#equation-02) は、どちらも $\mathit{max\_tokens}$ と $\mathit{delay}$ の正の相関を示している。[図 8(c)-(e)](#figure-08) に示すように、*InterFIFO* の深さを $\mathit{max\_tokens}$ に設定すると、*Target* から *Source* へのバックプレッシャーを防げる。これにより、アクセラレータを複数回実行しても、任意の *Source* と *Target* の組において定常かつ周期的な動作が保証される。バックプレッシャーによるストールを防ぐことで、$\mathit{max\_tokens}$ と $\mathit{delay}$ の解析的な関係が維持される。

<span id="section-5-3-3"></span>

#### 5.3.3 均等化

[第 5.3.2 節](#section-5-3-2) で述べた手法を *Normal* 均等化戦略と呼ぶ。この戦略は、カーネルが常に元のスループットでトークンを生成すると仮定する。しかし、データフローアクセラレータのスループットを最終的に決めるのは、最も遅いカーネルである。このことに基づき、全カーネルの pipeline II を *scaling* し、最も遅いカーネルのスループットに合わせる *Conservative* 均等化戦略を提案する。任意の *Source* と *Target* の曲線間の差が最小化されるため、得られる *max_tokens* の値は *Normal* 戦略による値以下となる。欠点は、より高速なカーネルがバックプレッシャーによって頻繁にストールし、レイテンシが増加する可能性があることである。したがって、*Normal* 戦略と *Conservative* 戦略には面積と性能のトレードオフがあり、*Conservative* 戦略は全体のレイテンシ増加と引き換えに FIFO バッファサイズを最小化する。*Conservative* 戦略と *Normal* 戦略の主な違いは、初期段階で II をどのようにスケーリングするかにある。このスケーリングはカーネル曲線の区分線形性を維持するため、$\mathit{delay}$ から $\mathit{max\_tokens}$ を計算する式は両戦略で同一である。

<span id="section-5-3-4"></span>

#### 5.3.4 LP に基づく FIFO サイズ決定

トークン動作モデルを導入することで、FIFO サイズ決定問題をカーネル間の $\mathit{delay}$ 値を決定する問題へ変換する。[図 8(f)](#figure-08) は、データフローグラフの一例を示す。*Kernel0* には 2 つの出力があり、*Kernel1* は *Kernel0* に依存する。*Kernel2* は 2 つのオペランドを持ち、*Kernel0* と *Kernel1* の両方の最初のトークンを待たなければならない。*Kernel1* が `D[0]+D[1]` 後に最初のトークンを生成することから、`delay[0][2]` はこの値以上でなければならない。両者の関係を [図 8(f)](#figure-08) に示し、緑色の曲線が *Kernel1* を表す。続いて、*Kernel0* と *Kernel2* の間の FIFO における最大トークン数 `max_token[0][2]` を、`delay[0][2]` から計算できる。FIFO サイズがこの最大値より小さい場合、*Kernel0* はバックプレッシャーによってストールし、全体の性能が低下する。このストールは *Kernel1* と *Kernel2* へ伝播し、バックプレッシャーを解消できなくして、デッドロックを引き起こす可能性がある。FIFO サイズを `max_token[0][2]` と等しくすれば、バックプレッシャーとデッドロックを防ぐのに十分である。また、意図しないカーネルストールによる性能低下を防ぐためにも、このサイズが必要となる。$\mathit{delay}$ 値を最適に求める LP 定式化を提案する。$G=(V,E)$ とし、$V$ をカーネル集合、$E$ をカーネル間のエッジ集合とすると、LP の目的関数と制約は次のとおりである。

<span id="equation-03"></span>

<span id="equation-04"></span>

$$
\begin{aligned}
\mathrm{minimize} & \sum_{e_{i,j}\in E}\mathit{delay}(i,j) \\
\forall u,v\in V,\forall \mathit{path}\in P_{u,v}, & \sum_{e_{i,j}\in \mathit{path}}\mathit{delay}(i,j)\geq \mathrm{threshold}(u,v)
\end{aligned}
$$

$e_{i,j}\in E$ はグラフ内のすべてのエッジを対象とする。$\mathit{path}\in P_{u,v}$ は `u` および `v` と呼ぶ任意のカーネル対を接続するすべての完全な経路を対象とし、$e_{i,j}\in \mathit{path}$ は 2 つのカーネル `u` と `v` を接続する $\mathit{path}$ 上のすべてのエッジを対象とする。すべてのエッジ上の `delay` の総和を最小化する。これは $\mathit{max\_tokens}$ と $\mathit{delay}$ に正の相関があるため、FIFO サイズを最適化するための代理目的となる。$\mathrm{threshold}(u,v)$ は、2 つのカーネル `u` と `v` を接続する全経路のうち、累積 $D$ の最大値である。

<span id="equation-05"></span>

$$
\mathrm{threshold}(u,v)=\max_{\mathit{path}\in P_{u,v}}\sum_{e_{i,j}\in \mathit{path}}D(i)
$$

上の例に対する LP 定式化を [図 8(f)](#figure-08) に示す。この例では、*Kernel0* から分岐した 2 本の経路が *Kernel2* で単一入力に結合されるのではなく、異なる 2 つの入力オペランドとして再び合流する点に注意されたい。経路の結合などの動的動作の扱いは [第 5.3.5 節](#section-5-3-5) で説明する。この LP 問題には、次の 2 つの理由からリソース制約が不要である。第 1 に、[第 5.2 節](#section-5-2) で述べたように、融合コストを制限することで、データフローカーネル融合は融合後の全カーネルが利用可能なオンチップリソースへ収まることを保証する。第 2 に、ストリーム FIFO のメモリ使用量は、データフローカーネルとコンバータの使用量に比べて無視できるほど小さい。したがって、LP 問題は多項式時間で最適に解ける。ベンダーツールに $\mathit{delay}$ の実装を強制する必要がない点も重要である。$\mathit{delay}$ は、データフローカーネル間の FIFO 依存関係を通じて自動的に満たされる。上の例では、*Kernel2* は *Kernel1* の出力トークンに依存するため、自動的に *Kernel1* を待つ。

#### 5.3.5 動的動作

StreamTensor は、データフローアクセラレータ内の動的動作を次の方法で管理する。

1. **制御フロー**：StreamTensor はフロントエンドとして Torch-MLIR [Tor21] を利用する。Torch-MLIR は入力から静的なテンソル形状を可能な限り推論し、静的テンソル形状に関連する `if` を除去して `for` をアンロールできる。制御フローが実行時の値に依存する場合、対応するサブグラフはホスト上で単純な PyTorch 実行 [Ans24a] へフォールバックする。
2. **経路の結合**：これは制御フローがある場合、特に異なる source からの入力でデータフローカーネルを再利用する場合によく生じる。Torch-MLIR は制御フローを除去することで、対応する経路結合の問題を解決する。
3. **動的テンソル形状**：入力トークンや KV-cache など、動的形状を持つテンソルでは、形状ヒントによって可能な最大次元サイズ（例：最大シーケンス長）を定義する必要がある。これらのヒントにより、任意の 2 つのデータフローカーネル間で処理できるトークン総数 $T$ が決まる。この最大 $T$ 値から、StreamTensor は [第 5.3 節](#section-5-3) で説明した方法に基づいて $\mathit{max\_tokens}$ を推論する。
4. **FIFO ストール**：StreamTensor はデータフローアクセラレータに対する静的スケジュールを生成しない。代わりに、すべてのデータフローカーネルが FIFO 相互接続を介して依存関係を自動的に守る。そのため、外部メモリトラフィックなどの実行時イベントによって予期しない FIFO ストールが生じても、特別な処理は必要ない。ストールの原因となったイベントが解消されると、データフローアクセラレータはストールした地点からそのまま動作を再開する。

### 6.1 GPT-2

FPGA に関する先行研究の大半 [Che24v, Che24u, Hon22] は、GPT-2 [Rad19] を用いて各フレームワークを評価している。[表 4](#table-04) は、異なる入出力シーケンス長の設定における StreamTensor と先行研究の比較を示す。GPT-2 では、レイアウトコンバータとストリーム FIFO を挿入することで、Transformer block 全体を単一の FPGA へ融合し、すべての中間結果をオンチップで通信することに成功した。続いて、異なる重みパラメータを用いてこの単一 FPGA アクセラレータを複数回起動し、すべての Transformer block を順次実行する。StreamTensor は Allo [Che24v, Che24u] と比べて、総レイテンシを 0.76 倍、TTFT を 0.40 倍に短縮する。DFX [Hon22] と比べると、StreamTensor の改善はさらに大きく、たとえば TTFT は 0.19 倍となる。この改善は、StreamTensor がデータフローアーキテクチャの探索を自動化したことによる。一方、Allo と DFX では、すべてのデータフローカーネルとコンポーネントを手作業で設計しなければならない。たとえば、すべてのレイアウトコンバータ、DMA、FIFO は手作業で記述・設定されるため、誤りが生じやすく、最適でない設計を選ぶ可能性がある。新しいほかの LLM への柔軟性と生産性が限られているため、Allo と DFX が報告する LLM は GPT-2 だけであることに注意されたい。[表 4](#table-04) に示すように、TTFT は入力長に対してほぼ線形に増加し、設計のスケーラビリティを示している。[表 5](#table-05) では NVIDIA GPU とも比較しており、StreamTensor は A100 と 2080Ti に比べて総レイテンシをそれぞれ 0.64 倍、0.25 倍に短縮する。GPU は豊富な計算リソースを持つため、TTFT 指標では StreamTensor を大幅に上回ることが分かる。しかし、LLM 推論のデコード段階はメモリ帯域に強く制約されるため、StreamTensor が生成するデータフローアクセラレータは外部メモリアクセスを減らすことで GPU を上回り、デコード速度と全体レイテンシを改善できる。

#### 6.2.2 コンパイル時間の検討

[図 10（b）](#figure-10) は、PyTorch から RTL を生成する実行時間の内訳を示す。HLS 処理（C++ から RTL を生成する処理）が総時間の大半を占める。リソース割り当ての判断には正確なプロファイリング結果が必要なため、下流ツールによるプロファイリングも大きな割合を占める。それに比べ、StreamTensor のコンパイルとパラメータのパッキングが占める割合はごく小さい。[第 4.2 節](#section-4-2) で述べたように、StreamTensor は外部メモリ効率を最適化するため、インターフェースを自動的にパックして widening する。そのため、目的のメモリレイアウトに一致するよう、モデルパラメータも同様にパックしなければならない。パッキング後にバイナリファイルを生成し、実行時にロードする。[図 10（c）](#figure-10) では、[図 4](#figure-04) に示した段階に基づき、StreamTensor のコンパイル時間をさらに分解している。実験における総コンパイル時間は 26.8s から 63.4s の範囲である。高レベルの段階（Linalg 最適化からリソース割り当てまで）は比較的高速である。一方、低レベルの段階（bufferization、HLS 最適化、コード生成）にはより長い時間がかかる。これは、高レベルの `itensor` 最適化が効率的であることを裏付けている。

## 7 関連研究

先駆的な研究 [Lee87, Bil96, Bha01, Thi02, Neu04] は、ストリームベースのデータフローモデリングとコンパイルの基礎を築いた。その後の研究 [Gov02, Ven06, Naj13] は、データフローネットワークにおけるバッファ最小化と slack matching の問題を検討した。[Con14a, Che16i] は、逐次プログラムのデッドロック解析とバッファサイズ決定を検討した。これらの論文は定常状態のシナリオ（すなわち [第 5.3.3 節](#section-5-3-3) の *Conservative* 均等化戦略）に焦点を当て、面積と性能のトレードオフを考慮していない点に注意されたい。[Guo21b, Du23b] は、FPGA 上のストリーミングアプリケーションについて floorplanning とクロック周波数を改善した。[Jos21, Xu24g] は、動的スケジュール型データフロー回路 [Jos18] におけるバッファの挿入と配置の問題に取り組んだ。

アプリケーションを DSA や FPGA などの空間アーキテクチャへマッピングするには、コンパイラが不可欠である。SARA [Zha21h] は、Plasticine [Pra17] のような大規模 DSA 向けのコンパイラスタックを提供し、入れ子の制御フローを持つ命令型 DSL を変換するとともに、リソースの仮想化とメモリ一貫性の管理を行った。Revet [Ruc23] のコンパイラは、データ依存の制御フローに対応する「dataflow threads」抽象化を、ストリーミングテンソル演算によってベクトル化 DSA [Ruc21] へマッピングした。DSAGEN [Wen20a] などの研究は、データフローグラフ記述からプログラム可能な空間アクセラレータを直接合成した。制約に基づくスケジューリング手法 [Now13] は、空間プラットフォーム上で最適または最適に近い命令スケジューリングを行うため、ILP を用いることが多い。高レベルのプログラミング抽象化も重要である。たとえば Sigma [Zha23n] は、Einstein summation をデータフローハードウェアへコンパイルした。FPGA を対象とする Stream-HLS [Bas25] は、C/C++ または PyTorch から最適化された HLS ベースのデータフローアーキテクチャを自動生成した。これらの多様なコンパイラとフレームワークは、重要な最適化を自動化した。しかし、その多くが可能にする設計空間探索は部分的なものに限られ、柔軟なストリームベースのカーネル融合やほかの最適化を可能にする体系的な型システムが欠けている。ここでは Stream-HLS [Bas25] を例として、StreamTensor との違いを分析する。

- Stream-HLS は体系的な型システムを持たないため、外部メモリ用の DMA を自動生成できず、実世界のアプリケーションにおける実用性とスケーラビリティが制限される。
- Stream-HLS は FIFO サイズ決定問題を考慮していない。この問題は、データフローアクセラレータのデッドロックを防ぎ、実世界のアプリケーションへスケールさせるうえで不可欠である。
- Stream-HLS はデータフローカーネル間のストリーミングを可能にするため、2 つの条件を要求する。1）共有バッファへの書き込み回数と共有バッファからの読み出し回数が等しい。2）生産側の書き込み順序が消費側の読み出し順序と一致する。どちらの条件も満たすことが難しい場合が多いが、Stream-HLS はいずれか一方でも満たさなければカーネル融合を実行できない。一方、StreamTensor は `itensor` ベースの型システムによってこの 2 条件を解決し、あらゆるデータフローカーネルを設計上融合可能にする。
- 上記の理由により、Stream-HLS は StreamTensor のようなカーネル融合空間の探索をサポートせず、カーネル融合なしには完全なオンチップ配置が不可能な大規模ワークロードへの適用が制限される。たとえば Stream-HLS が報告するのは、Transformer block 全体の性能ではなく、multi-head attention 層と feed-forward 層それぞれの性能である。

## 8 結論と今後の課題

本稿では、ストリームベースのデータフローアクセラレータの生成と最適化を自動化するコンパイラフレームワーク StreamTensor を提案した。StreamTensor の主な貢献には、フレームワーク全体の基盤となる `itensor` ベースの型システム、PyTorch-to-device コンパイルパイプライン、主要なアーキテクチャパラメータを探索する設計空間群がある。StreamTensor は、既存フレームワークに共通する問題へ対処することで、データフローアクセラレータの効率を改善する。効率的な AI に対する需要が高まり続けるなか、StreamTensor はスケーラブルで拡張可能なデータフローコンパイルに向けた今後の研究につながる。

今後については、StreamTensor のモジュール設計と `itensor` 型システムにより、多様なデータフローアーキテクチャや特化型カーネル言語との互換性を拡張できる可能性がある。StreamTensor は、低レベルのコンパイル段階とコード生成段階のターゲットを変更することで、AMD Versal [Gai19]、Sambanova RDU [Pra24]、Groq LPU [Abt22] のようなプログラム可能アーキテクチャへ適応できる。この処理では、StreamTensor IR 内のデータフローカーネル、FIFO、レイアウトコンバータを、AMD Versal の AI engine やルーティングネットワークなど、プラットフォーム固有のコンポーネントへマッピングする。同様に、StreamTensor は Allo [Che24v] などのカーネル言語と統合でき、開発者は手作業で最適化したカーネルをブラックボックスコンポーネントとして組み込める。どちらの場合も、`itensor` システムは重要な抽象化層として機能する。StreamTensor はターゲット固有のバックエンドやブラックボックスコンポーネントと接続しながら、カーネル融合とデータフローコンポーネント生成を含む高レベルのデータフロー最適化を実行できる。これにより、多様なハードウェアプラットフォームとプログラミング言語が持つ固有の長所を活かし、StreamTensor の適用範囲を広げられると期待される。
