## 概要

Mooncake は、Moonshot AI が提供する主要な LLM サービス Kimi のサービングプラットフォームである。KVCache を中心とした分離型アーキテクチャを採用し、prefill クラスタと decoding クラスタを分離する。また、GPU クラスタで十分に活用されていない CPU、DRAM、SSD リソースも利用して、分離型の KVCache キャッシュを実装する。Mooncake の中核は KVCache 中心のスケジューラであり、レイテンシに関する Service Level Objectives （SLO） を満たしながら全体の実効スループットを最大化することのバランスを取る。従来の研究がすべてのリクエストを処理すると仮定するのに対し、Mooncake は非常に過負荷な状況に起因する課題にも直面する。これを緩和するため、予測に基づく早期拒否ポリシーを開発した。実験により、Mooncake は長いコンテキストのシナリオで優れていることが示された。ベースライン手法と比較すると、SLO を守りながら、特定のシミュレーションシナリオでスループットを最大 525% 増加させられる。実際のワークロードでは、このアーキテクチャにより Kimi は 75% 多くのリクエストを処理できる。

## 1 はじめに
<span id="section-01-01"></span>

### 1.1 Mooncacke 開発の動機

さまざまなシナリオで大規模言語モデル （LLM） が急速に普及するにつれて [Ope22, Tou23b, Che21, Pac23]、LLM サービングのワークロードは大きく多様化している。これらのワークロードは入力/出力長、到着頻度、到着分布が異なり、さらに重要なことに、異なる種類の Service Level Objectives （SLO） を要求する。Model as a Service （MaaS） プロバイダとして、Kimi [Moo23] の主な目標の一つは、複数の複雑な制約を持つ最適化問題を解くことである。最適化の目標は全体の実効スループットを最大化することであり、これは収益に直接影響する。一方、制約はさまざまなレベルの SLO を表す。これらの SLO は通常、レイテンシに関する要件、主に Time To First Token （TTFT） と Time Between Tokens （TBT） を含む。

<span id="figure-01"></span>

![Mooncake のアーキテクチャ](../../papers/mooncake/figure-01.png)

**図 1.** Mooncake のアーキテクチャ。

この目標を達成するには、GPU クラスタで利用可能なさまざまな種類のリソースを最大限に活用することが前提となる。
具体的には、現在の GPU サーバーは通常、DGX/HGX スーパーコンピュータなどの高度に統合されたノードとして提供されている [Nvi22]。しかし、これらを複数の分離型リソースプールに分解・再構成し、それぞれを異なるが協調的な目的に最適化する必要がある。例えば、多くの研究者 [Pat23, Zho24, Hu24b] は prefill サーバーと decoding サーバーを分離することを提案している。LLM サービングのこの 2 段階は計算特性が大きく異なり、リクエストが prefill サーバーから decoding サーバーへ移る際に KVCache も移動するからである。

この考えに基づき、KVCache のスケジューリングが LLM サービングのスケジューリングの中心にあることを見いだした。全体のスループットを向上させるため、一般に 2 つの方法がある。*1)* 必要な計算リソースを減らすため、KVCache を可能な限り再利用する。*2)* Model FLOPs Utilization （MFU） を高めるため、各バッチの Token 数を最大化する。しかし、遠隔地の KVCache を再利用すると TTFT が長くなり、バッチサイズを大きくすると TBT が大きくなる。そのため、これらのスループット指向の最適化をどちらも利用すると、レイテンシに関する SLO に違反する可能性がある。

以上の方針に従い、KVCache を中心にスケジューリングと最適化を行う分離型設計を提案する。[図 1](#figure-01) は、LLM サービング向けに現在実装している**KVCache 中心の分離型アーキテクチャ** Mooncake を示す。各リクエストについて、グローバルスケジューラ （Conductor） は prefill インスタンスと decoding インスタンスの組を選び、次の手順でリクエストをスケジュールする。*1)* 再利用可能な KVCache をできるだけ多く選択した prefill インスタンスへ転送する。*2)* prefill 段階をチャンク/レイヤー単位で完了させ、出力 KVCache を対応する decoding インスタンスへ連続的にストリームする。*3)* KVCache をロードし、リクエストを decoding インスタンスの continuous batching 処理に加えて出力を生成する。

この処理は単純に見えるが、多くの制約があるため選択ポリシーは複雑である。prefill 段階の主な目的は、冗長な計算を避けるため KVCache をできるだけ再利用することだ。しかし、低位のストレージに保存された KVCache を待つと TTFT SLO に違反する可能性がある。さらに、KVCache サーバーへの需要が高いとネットワークが混雑し、待ち時間が延びる。
そのため Conductor は、KVCache ブロックの将来の利用状況を予測し、それに応じて swap や複製などのスケジューリング操作も実行する。
最もホットなブロックは取得時の混雑を避けるため複数ノードに複製し、最もコールドなブロックは保持コストを下げるため swap out すべきである。
prefill スケジューリングは prefill ノードの利用可能な DRAM 容量にも制約される。特に、メモリの大部分をグローバル KVCache プールに予約している場合にこの制約が強い。

これに対して decoding 段階には異なる最適化目標と制約がある。目的は、MFU を高めるため decoding バッチにできるだけ多くの Token を集約することだ。
しかし、この目的は TBT SLO だけでなく、VRAM に収容できる集約 KVCache の総量によっても制限される。

さらに重要なのは、既存の LLM サービング研究が十分なリソースを仮定し、リソース利用率の向上に焦点を当てている点である。一方、現在の GPU/アクセラレータの供給は限られており、多くの MaaS プロバイダは、特にピーク時に深刻な過負荷に直面している。このような状況のスケジューリングには、既存研究が扱っていない固有の課題がある。例えば、prefill 段階の後に利用可能な decoding スロットがない場合に一部のリクエストを早期に拒否し、無駄な計算リソースを節約するには、将来の負荷を予測する必要がある。
しかし、このような早期拒否ポリシーを単純に実装すると、過負荷量がかえって変動する。このため、特定のクエリの生成長を予測し、短期的な全体負荷を予測して、よりよい拒否ポリシーを実装することを目指す。また、優先度に基づくスケジューリングを実現するには、リクエストの優先度を分類する必要もある。
本論文では、これらの問題を**過負荷指向スケジューリング**としてまとめ、初期の研究結果を示す。

### 1.2 Mooncacke の設計と結果

本論文の後半では、まず Mooncake のアーキテクチャ、主要コンポーネント、リクエスト処理の典型的なワークフローを概説する （[§ 3](#section-03)）。続いて、実装時に行った主な設計上の選択、特に現在の研究で扱われていないものを説明する。

まず [§ 5](#section-05) では、コンテキスト長の動的な分布を円滑に扱う独立した prefill ノードプールの実装方法を議論する。長いコンテキスト入力の TTFT を短縮するには、1 つのリクエストの処理を複数ノードへ拡張する必要があり、そのために chunked pipeline parallelism （CPP） を用いる。従来の sequence parallelism （SP） ベースの方式と比べ、CPP はネットワーク消費を抑え、頻繁な弾性スケーリングへの依存を減らす。この仕組みを layer-wise prefill が補い、KVCache をストリーム転送してレイテンシを重ね合わせる。

次に [§ 6](#section-06) では、TTFT と TBT の SLO で測ったインスタンス負荷とユーザー体験のバランスを取る、KVCache 中心のリクエストスケジューリングアルゴリズムを詳しく説明する。これには、KVCache の将来の利用状況を正確に予測せずにホットな KVCache ブロックを複製する、ヒューリスティックベースの自動ホットスポット移行方式が含まれる。実験結果は、キャッシュを考慮したスケジューリングにより実際のシナリオで TTFT を大きく下げられることを示す。公開データセット、シミュレーションデータ、実ワークロードを使ったエンドツーエンド実験で、Mooncake は長いコンテキストのシナリオに優れている。ベースライン手法と比べ、SLO を満たしながらスループットを最大 525% 増加できる。実ワークロードでは、Mooncake により Kimi は 75% 多くのリクエストを処理できる。

最後に、すべてのリクエストが処理されると仮定する既存の LLM サービング研究とは異なり、Mooncake は Kimi のユーザーリクエストが急増しているため、常に過負荷に直面している。そのため Mooncake のスケジューリングでは、システム負荷に基づいて到着リクエストを受け入れるか拒否するかを決める必要がある。[§ 7](#section-07) では、過負荷の状況で無駄になる計算リソースを減らす独自の早期拒否ポリシーを説明する。さらに、単純な早期拒否によって生じる負荷変動と、将来の負荷を予測することでこの問題を緩和する方法を検討する。

Mooncake は現在 Kimi を提供する主要プラットフォームであり、ワークロードの指数的な増加に対応して、大規模で非常に過負荷なワークロードへスケールアウトできることを示してきた。ただし、まだ検討すべき問題は多く、それらの将来の方向性も本論文に含めている。

> 独自情報を保護し、再現性を確保するため、本論文で報告する実験結果はすべて実ワークロードのトレースを再生したものだが、LLaMA2-70B と同じアーキテクチャに従う**ダミーモデル**を使用している。トレースにはリクエスト到着時刻、入力 Token 数、出力 Token 数、再マッピングされたブロックハッシュだけが含まれ、実際のユーザーコンテンツは含まれない。トレースは [https://github.com/kvcache-ai/Mooncake](https://github.com/kvcache-ai/Mooncake) で公開している。

## 2 予備知識と問題定義

現代の大規模言語モデル （LLM） は Transformer アーキテクチャに基づき、attention 機構と multilayer perceptron （MLP） を用いて入力を処理する。GPT [Rad19] や LLaMA [Tou23] などの代表的な Transformer ベースモデルは decoder-only 構造を採用する。各推論リクエストは論理的に 2 つの段階、すなわち prefill 段階と decoding 段階に分かれる。

<span id="figure-02"></span>

![ダミー LLaMA2-70B モデルの異なるシーケンス長またはバッチサイズにおける prefill と decoding の正規化スループットとレイテンシ](../../papers/mooncake/figure-02.png)

**図 2.** ダミー LLaMA2-70B モデルの異なるシーケンス長またはバッチサイズにおける prefill と decoding 段階の正規化スループットとレイテンシ。

prefill 段階では、すべての入力 Token を並列に処理する。この段階では最初の出力 Token を生成すると同時に、計算した key と value の中間結果、すなわち KVCache を保存する。続く decoding 段階では、この KVCache を使って新しい Token を自己回帰的に生成し、計算で得た新しい key と value を KVCache に追加する。prefill 段階は入力 Token を同時に処理できるため、短いリクエストを除けば通常は計算負荷が高い。attention ネットワークの計算量は入力長に対して二次的に増加し、MLP の計算量は線形に増加する。そのため、prefill 段階の計算時間は一般に入力長に対して超線形に増加し、[図 2](#figure-02) の左側に示すようになる。

これに対して decoding 段階では、自己回帰生成の制約により、バッチごとに一度に 1 Token だけを処理する。そのためメモリ制約を受け、計算時間はバッチサイズに対して劣線形に増加する。これは [図 2](#figure-02) の右側に示すとおりである。decoding 段階で広く使われる最適化に continuous batching がある [Yu22a, Kwo23]。各イテレーションの前にスケジューラはすべてのリクエストの状態を確認し、新しく到着したリクエストをバッチの prefill 段階へ追加し、完了したリクエストを削除する。

prefill 段階と decoding 段階の特性が異なるため、MaaS プロバイダは対応する Service Level Objectives （SLO） を測るために異なる指標を設定する。具体的には、prefill 段階ではリクエスト到着から最初の Token 生成までのレイテンシ、Time To First Token （TTFT） を主に扱う。一方、decoding 段階では同じリクエストで連続する Token 生成の間のレイテンシ、Time Between Tokens （TBT） に注目する。

MaaS プロバイダにとって、サービス契約で定めた SLO 指標を満たして品質を保証することは重要である。
例えば、$\mathrm{TTFT}_{\mathrm{P90}} = 4\times$ という指標は、推論リクエストの 90% が、同じ条件で干渉なしに 1 つのリクエストを実行した場合の 4 倍以下の TTFT になることを示す。具体的には、本論文のエンドツーエンド実験 （[§ 8.1](#section-08-01)） で $\mathrm{TTFT}_{\mathrm{P90}} = 10\times$、$\mathrm{TBT}_{\mathrm{P90}} = 5\times$ と設定した。実際のデプロイでは TTFT と TBT に固定 SLO を設定する。監視によって SLO 未達が検出された場合、推論リソースを追加するか、到着リクエストの一部を拒否する。

しかし、現在の GPU 供給は不安定であるため、推論クラスタを弾性的にスケールアウトすることは通常できない。したがって、どのリクエストを拒否するかを決めることが過負荷指向スケジューリングの中心的な問題になる。主な目的は SLO を守りながら全体のスループットを最大化することであり、他の研究ではこれを goodput と呼ぶ [Zho24, Wu24a]。
我々の方式では、処理を完全に終えたリクエストだけを goodput の測定に数える。そうでなければ、それまでに消費または生成したすべての Token は数えず、対応するリソースは無駄になる。つまり、SLO の下で最後まで実行できないリクエストは、できるだけ早く拒否すべきである。この目標を達成するには、prefill 段階と decoding 段階のアーキテクチャを最適化するだけでなく、短期的な将来負荷を予測する能力も必要になる。

## 3 Mooncake の分離型アーキテクチャの概要

[図 1](#figure-01) に示すように、Mooncake は prefill ノードと decoding ノードを分離するだけでなく、GPU クラスタの CPU、DRAM、SSD、RDMA リソースをまとめて分離型 KVCache を実装する分離型アーキテクチャを採用する。
この分離キャッシュは十分に利用されていないリソースを活用し、十分なキャッシュ容量と転送帯域幅を提供することで、追加コストなしに GPU 近傍の prefix caching を効率よく実現する。

<span id="figure-03"></span>

![CPU メモリ内の KVCache プール](../../papers/mooncake/figure-03.png)

**図 3.** CPU メモリ内の KVCache プール。各ブロックには、自身のハッシュとその prefix の両方で決まるハッシュ値が付与され、重複排除に使われる。

[図 3](#figure-03) は KVCache ブロックの保存と転送のロジックを示す。CPU メモリでは KVCache をページ化されたブロックとして保存する。リクエストパターンに応じて、LRU （Least Recently Used）、LFU （Least Frequently Used）、またはリクエスト特性に基づくアルゴリズムなどのキャッシュ削除アルゴリズムを利用できる。これらの KVCache ブロックを CPU と GPU の間で転送する処理は、独立した （GPUDirect） RDMA ベースのコンポーネント Messenger が担う。
このアーキテクチャにより、外部ユーザーへ context caching API を提供し、KVCache の再利用率を高めることもできる。

これらすべての分離コンポーネントをスケジュールするため、Mooncake は中心に Conductor というグローバルスケジューラを実装する。
Conductor は KVCache の現在の分布とワークロードに基づいてリクエストをディスパッチする。また、将来の推論に有利であれば、KVCache の一部のブロックを複製または swap する。
具体的には、[図 4](#figure-04) がリクエストの典型的なワークフローを示す。Token 化が終わると、Conductor は prefill ノードの組と decoding ノードを選び、4 つのステップからなるワークフローを開始する。

<span id="figure-04"></span>

![推論インスタンスのワークフロー](../../papers/mooncake/figure-04.png)

**図 4.** 推論インスタンスのワークフロー。（$*$） prefill インスタンスでは、KVCache 層のロードと保存をレイヤーごとに実行し、prefill 計算と並列化することで転送オーバーヘッドを抑える （[§ 5.2](#section-05-02) を参照）。（$\dagger$） decoding インスタンスでは、GPU decoding と並行して非同期ロードを行い、GPU のアイドルを防ぐ。

**1) KVCache の再利用:** 選択された prefill ノード （グループ） は、raw input、再利用可能な prefix cache のブロック ID、リクエストに割り当てた全キャッシュのブロック ID を含むリクエストを受け取る。prefix cache のブロック ID に基づき、prefix cache を遠隔 CPU メモリから GPU メモリへロードしてリクエストを開始する。prefix cache がなければこの手順を省く。この選択は、KVCache をできるだけ再利用すること、異なる prefill ノードのワークロードを均衡させること、TTFT SLO を保証することという 3 つの目的のバランスを取る。
これは KVCache 中心のスケジューリングにつながり、[§ 6](#section-06) で詳しく説明する。

**2) 増分 prefill:** prefill ノード （グループ） は prefix cache を使って prefill 段階を完了し、新しく生成した増分 KVCache を CPU メモリへ戻して保存する。キャッシュされていない入力 Token の数がある閾値 （$\mathit{prefill\_chunk}$） を超えると、prefill 段階を複数のチャンクに分け、パイプライン方式で実行する。この閾値は対応する GPU の計算能力を十分に使えるように選び、通常は 1000 Token より大きい。[§ 5.1](#section-05-01) では、チャンク化しながら分離型である prefill ノードを使う理由を説明する。

**3) KVCache 転送:** 前述の Messenger サービスを各ノードに配置してキャッシュの管理と転送を行う。各 Messenger は対応する推論インスタンス内で独立したプロセスとして動作し、高速なマシン間 KVCache 転送を行うためのシグナルを受け取る。このステップは非同期に実行され、上記の増分 prefill ステップと重ね合わせる。各モデル層で生成された KVCache を転送先 decoding ノードの CPU メモリへストリームし、待ち時間を短くする。

**4) decoding:** すべての KVCache が decoding ノードの CPU DRAM に届くと、リクエストは continuous batching 方式で次のバッチに参加する。Conductor は現在の負荷に基づいて decoding ノードを事前選択し、TBT SLO に違反しないようにする。しかし、prefill 段階の後には予想負荷が変化している可能性があるため、ローカルスケジューラがこの SLO を再確認する。この再確認によってリクエストが拒否されることがあり、その場合は対応する prefill コストが無駄になる。

## 5 prefill プールの実装

変更できない decoding ノードとは異なり、独立した弾性 prefill プールを設計する必要性とベストプラクティスについては議論が続いている。
例えば、多くの研究者 [Pat23, Zho24, Hu24b] は我々と同じく分離型アーキテクチャを使う考えを共有しているが、chunked prefill [Agr24a] の導入後もこの分離が必要かどうかは議論する価値がある。
Chunked prefill は入力 Token を複数の小さなチャンクに分割し、それらを continuous batch 処理に参加させる。この方式には 2 つの明確な利点がある。
*1)* 分離しなければすべてのノードを同じように扱えるため、スケジューリングが容易になる。
*2)* chunked prefill を decoding バッチへインライン化すると、decoding バッチの計算強度を高め、MFU を改善できる。

しかし、慎重に検討した結果、Mooncake の分離型アーキテクチャを維持することにした。リクエストの prefill は、チャンク化せずに転送でき、TBT SLO を損なわない場合にだけ decoding バッチへインライン化する。
この判断には 2 つの主な理由がある。
*1)* 長いコンテキストを処理するため、prefill ノードには異なるノード間並列設定が必要である （[§ 5.1](#section-05-01)）。
*2)* VRAM を節約する特別な機会が得られる （[§ 5.2](#section-05-02)）。

<span id="section-05-01"></span>

### 5.1 マルチノード prefill

最近の LLM が利用できるコンテキスト長は急速に増え、8k から 128K、さらには 1M まで広がっている [Goo24a]。
通常、このような長いコンテキストのリクエストでは入力 Token 数が出力 Token 数の 10 倍から 100 倍になるため、TTFT の最適化が重要になる。
長いコンテキストの prefill には豊富な並列性があるため、単一の 8x GPU ノードだけでなく、複数ノードを使って並列処理することが望ましい。
しかし、tensor parallelism （TP） を複数ノードに広げるには、各レイヤーで高価な RDMA ベースの all-reduce を 2 回行う必要があり、prefill ノードの MFU を大きく下げる。

最近では、sequence parallelism （SP） を提案する研究が多い [Sam23, Liu23, Bra23, Li23q, Kor22, Li23g, Fan24a]。
SP はリクエストの入力シーケンスを異なるノードに分割して高速化する。
これらの SP 手法は attention 演算子の結合性を利用し、Ring Attention [Liu23] または Striped Attention [Bra23] を実装する間、少なくともレイヤーごとに 1 回のノード間通信を必要とする。
これによりネットワーク消費を大きく減らし、MFU を高める。

しかし、SP を採用しても、単一ノード TP だけを使う場合より MFU は悪くなる。
望ましい配備では prefill ノードを 2 つのグループに分け、一方は TP のみ、他方は SP を使う。
TTFT SLO を満たす必要がある場合にだけ、リクエストを SP グループへ送る。
このさらなる分離は、各グループのノード数を動的に調整する際に問題を生む。並列設定を固定するとクラスタ全体の利用率が低くなる可能性があるためである。
最近の研究 [Wu24a] は SP グループを動的に拡大・縮小する弾性 sequence parallelism を提案している。
これは可能ではあるが、アーキテクチャを複雑にする。
例えば、あらかじめグローバル通信グループを作る必要があり、調整中にキャッシュ再利用率や SLO 要件違反などの指標を考慮すると Conductor の設計も複雑になる。
そのため、配備中に頻繁なオンザフライのスケーリングが必要な状況では扱いにくい。
さらに、SP は頻繁なノード間通信を必要とするため MFU を下げ、ノード間 KVCache 転送のネットワークリソースと競合する。

この問題に対処するため、Mooncake は decoder-only Transformer の自己回帰特性を利用し、長いコンテキストの prefill に chunked pipeline parallelism （CPP） を実装する。
prefill クラスタの X ノードごとに、パイプライン化した prefill ノードグループを構成する。
各リクエストの入力 Token をチャンクに分割し、各チャンクの長さを $\mathit{prefill\_chunk}$ 以下にする。
同じリクエストの異なるチャンクを異なるノードで同時に処理できるため、処理を並列化して TTFT を短縮できる。

CPP には 2 つの主な利点がある。*1)* 学習時の pipeline parallelism と同様に、各パイプライン段階の境界でだけノード間通信が必要であり、計算と容易に重ね合わせられる。その結果、MFU が向上し、KVCache 転送とのネットワークリソース競合が減る。*2)* 短いコンテキストと長いコンテキストの両方に自然に適合し、短いコンテキストの prefill に大きなオーバーヘッドを生じさせず、ノード分割の頻繁な動的調整を避けられる。
このパイプラインベースの高速化手法は学習システムで研究されている [Li21b]。しかし我々の知る限り、長いコンテキスト推論が現れたのは最近であり、推論段階への適用はこれが初めてである。

<span id="section-05-02"></span>

### 5.2 レイヤー単位の prefill

計算能力だけでなく、限られた VRAM サイズも貴重なリソースであり、主に KVCache などの状態が VRAM を占有する量を最小化したい。
理論上、リクエストの KVCache サイズが $S$、処理時間が $T$ なら、その占有コストは $S*T$ である。
リクエストをチャンク化し、各チャンクの処理を chunked prefill で他の decoding リクエストにインライン化すると、$T$ が増え、占有コストが大きくなる。

<span id="figure-07"></span>

![異なるリクエスト長における KVCache 保存レイテンシ](../../papers/mooncake/figure-07.png)

**図 7.** 異なるリクエスト長の KVCache を保存するレイテンシ （layer-wise latency は layer-wise prefill と KVCache を保存しない prefill のレイテンシ差を指す）。

さらに、prefill はレイヤーごとに処理され、計算律速であるため、KVCache の転送とダンプを計算に重ね合わせ、占有コストをさらに下げられる。
Mooncake では KVCache のロードと保存を launch 操作と wait 操作で非同期に実行する。各レイヤーの attention 計算を始める前に、そのレイヤーの KVCache の非同期ロードを待ち、次のレイヤーの KVCache の非同期ロードを開始する。attention 計算が終わると、そのレイヤーの KVCache の非同期保存を開始する。すべてのレイヤーの計算が終わったら、すべての非同期保存操作の完了を待つ。転送を重ね合わせることで、prefill インスタンスの実行時間は、入力長に対する prefix cache の割合に応じて、KVCache ロード時間または通常の prefill 時間のいずれかにほぼ等しくなる。[図 7](#figure-07) に示す KVCache 保存レイテンシの実験結果は、layer-wise prefill が長いコンテキストのリクエストのレイテンシを効果的に下げられることを示している。

この重ね合わせの主な利点は、1 つのリクエストを収容できる限り、prefill スケジューリングで利用可能な VRAM サイズを無視できることである。
[図 1](#figure-01) に示すように、prefill ノードのスケジューリングでは KVCache の分布と利用可能な DRAM サイズだけを考慮する。

今後は、この空いた VRAM の用途をさらに探る予定である。例えば OpenAI は最近、バッチ API の利用を提案した [Ope24a]。これはユーザーが非同期のリクエスト群を 50% 低いコストで送信できる一方、明確なターンアラウンド時間は 24 時間だけである。このサービスは即時応答を必要としないジョブに適している。これらのバッチリクエストには厳しい TBT がないため、対応する KVCache を収容する VRAM が十分なら、MFU を高めるため decoding 段階まで prefill 処理へインライン化できる。

### 6.1 prefill のグローバルスケジューリング

従来の LLM サービング研究では、通常、割り当てられたリクエスト数に基づいて各インスタンスの負荷を評価する負荷分散戦略を用いる。しかし Mooncake で prefill インスタンスを選ぶ際には、負荷だけでなく prefix cache のヒット長と再利用可能な KVCache ブロックの分布も考慮する。計算コストを減らすため prefix cache 長の長い prefill インスタンスへリクエストをルーティングすることが好ましい一方、システム全体の均衡を保ち TTFT SLO を満たすには別のノードへスケジュールした方がよい場合もある。これらの複雑さに対処するため、prefix cache による prefill 時間とインスタンス負荷に伴うキュー待ち時間の両方を考慮する、キャッシュを考慮したグローバルスケジューリングアルゴリズムを提案する。

[アルゴリズム 1](#algorithm-01) はキャッシュを考慮した prefill スケジューリングの仕組みを詳しく示す。新しいリクエストごとに入力 Token を複数のブロックに分け、各ブロックのハッシュキーを計算する。これはブロック内の Token と、利用可能なら前のブロックのハッシュキーを連結してハッシュキーを生成する処理である。次に、リクエストのブロックキーを各 prefill インスタンスのキャッシュキーと 1 つずつ比較し、prefix の一致長 （$\mathit{prefix\_len}$） を特定する。同様の再利用ロジックは vLLM にも実装されているが、オープンソース版 vLLM はローカル KVCache キャッシュしかサポートしない。

この一致情報を使い、Conductor はリクエスト長とインスタンスごとに異なる $\mathit{prefix\_len}$ から対応する実行時間を推定する。次に、そのインスタンスでリクエストが TTFT を得るまでの推定待ち時間を加える。最後に、Conductor は TTFT が最短のインスタンスへリクエストを割り当て、そのインスタンスのキャッシュ時間とキュー時間を更新する。SLO を達成できない場合、Conductor は上位層へ HTTP 429 Too Many Requests のステータスコードを直接返す。

このスケジューリングフレームワークの骨格は単純だが、各コンポーネントのエンジニアリング実装に複雑さが隠れている。例えば、リクエストの prefill 段階の計算時間を予測するため、オフラインテストデータから得た予測モデルを使う。このモデルはリクエスト長と prefix cache のヒット長に基づいて prefill 時間を推定する。Transformer の計算パターンは規則的なので、十分なオフラインデータがあれば予測の誤差範囲は小さい。リクエストのキュー時間は、キューにあるすべてのリクエストの prefill 時間を集計して計算する。実装では TTFT を並列に計算するため、処理時間は推論時間と比べて無視できる。

転送時間の予測はさらに難しい。転送するデータのサイズだけでなく、現在のネットワーク状態、特に送信ノードが混雑しているかどうかにも左右されるからである。そのためホットな KVCache ブロックを複製する必要もあり、これは次節で説明する。

<span id="section-06-02"></span>

### 6.2 キャッシュの負荷分散

Mooncake クラスタでは、各 prefill マシンが独自のローカル prefix cache 集合を管理する。これらのキャッシュの利用頻度は大きく異なる。例えば、システムプロンプトはほぼすべてのリクエストからアクセスされる一方、ローカルな長文書の内容を保存したキャッシュは 1 ユーザーだけが使うこともある。[§ 6.1](#section-06-01) で述べたように、Conductor の役割はキャッシュのマッチングとインスタンス負荷の最適なバランスを取ることである。したがって、分散キャッシュシステムの観点でも負荷分散は重要な役割を果たす。具体的には、グローバル prefill スケジューリングが高いキャッシュヒット率と低い負荷を両立できるよう、キャッシュをバックアップする方法を決める。

この KVCache スケジューリング問題への素朴な解決策は、各ブロックのグローバルな利用状況を集め、予測モデルで将来の利用状況を予測し、それに応じてスケジューリングを決めることだろう。しかし prefill 時間の推定とは異なり、ワークロードは非常に動的で、時間とともに大きく変化する。ユーザーベースが急速に拡大する MaaS プロバイダでは特に、将来の利用状況を正確に予測することは不可能である。そこで、キャッシュの負荷分散を改善するヒューリスティックベースの自動ホットスポット移行方式を提案する。

<span id="figure-08"></span>

![Mooncake クラスタでの prefill スケジューリング実験](../../papers/mooncake/figure-08.png)

**図 8.** Mooncake クラスタでの prefill スケジューリング実験。

前述のように、インスタンスの負荷が高いと、prefix cache 長が最も長い prefill インスタンスへ常にリクエストを送れるとは限らない。そのような場合、推定した追加 prefill 時間が転送時間より短ければ、conductor はキャッシュの場所とリクエストを別のインスタンスへ転送する。このインスタンスは保持元から KVCache を先に取得し、ローカルに保存する。さらに、最良のリモート prefix マッチ長が現在のローカルで再利用可能な prefix と閾値の積以下であれば、入力 Token を計算することを優先する [+threshold]。この 2 つの戦略はリクエストの prefill 時間を短くするだけでなく、ホットスポットキャッシュの自動複製も促し、複数マシンへ広く分散できるようにする。

この方式の有効性を検証するため、ランダムスケジューリング、負荷分散スケジューリング、我々の方式を比較する実験を行った。さらに [§ 6.1](#section-06-01) のキャッシュを考慮したスケジューリングと、本節のキャッシュ負荷分散を考慮した KVCache 中心スケジューリングを比較した。ランダムスケジューリングでは、リクエストごとに prefill インスタンスを任意に選ぶ。負荷分散スケジューリングでは、最も負荷の軽いインスタンスを選ぶ。評価のため、夜間に空いているマシンを使って 8 個の prefill インスタンスと 8 個の decoding インスタンスからなる Mooncake クラスタを構築し、23,000 件の実リクエストを再生した。各スケジューリングアルゴリズムを平均 TTFT と TTFT SLO 達成率で評価した。[図 8](#figure-08) に示す実験結果は、キャッシュを考慮した方式とキャッシュ負荷分散方式の両方がリクエストの TTFT を大幅に短縮することを示す。我々の KVCache 中心スケジューリングアルゴリズムは、両方の指標でランダムスケジューリングと負荷分散スケジューリングを上回る。追加の実験結果は [§ 8](#section-08) にある。

## 7 過負荷指向スケジューリング

既存の LLM サービング研究の大半は、すべてのリクエストを処理すると仮定し、それに応じてリクエストのスループットや TTFT、TBT を最適化する。しかし実際のシナリオでは、到着するすべてのリクエストを処理することは経済的でも現実的でもない。ユーザーリクエスト数が急速に増える商用推論サービスでは、クラスタの推論リソースの増加速度は到着リクエストの増加速度よりはるかに遅い。そのため現在の LLM サービングでは、特にピーク時に過負荷がよく起こる。

コストとユーザー体験のバランスを取るため、システム負荷があらかじめ定めた閾値に達するまで、システムはできるだけ多くのリクエストを処理すべきである。それ以降に残ったリクエストは直接拒否するか、後で再試行するため延期する。分離型推論システムとして実装された Mooncake はより柔軟なスケジューリング戦略を可能にする一方、非分離型システムにはない、また以前の研究 [Pat23, Zho24, Hu24b] では言及されていない固有のスケジューリング課題にも直面する。

本節では分離型アーキテクチャ専用に設計した早期拒否ポリシーを説明し、この方式が生む負荷変動に対処する。その後、これらの問題を緩和するには生成長の予測が必要であることを検討する。

<span id="section-07-01"></span>

### 7.1 過負荷シナリオでのスケジューリング

システムが過負荷になる状況では、スケジューリングはシステム負荷に基づいて到着リクエストを受け入れるか拒否するかを決める。ここで重要なのは「システム負荷」を何と定義するかであり、この定義がリクエストを拒否する閾値を左右する。従来の結合型システムでは、prefill 段階と decoding 段階の干渉により TTFT と TBT の予測が複雑になる。そのため負荷は、処理中のリクエスト数とシステム最大容量の比で単純に測ることが多い。

一方、Mooncake は分離型アーキテクチャで prefill 段階と decoding 段階を独立に処理する。そこで SLO の達成状況を直接の負荷指標として使う。具体的には、リクエストの TTFT と TBT の SLO 制約をそれぞれ $l_{\mathrm{ttft}}$ と $l_{\mathrm{tbt}}$ と定義する。prefill インスタンスと decoding インスタンスの負荷は、インスタンス上の予測最大 TTFT と TBT を $l_{\mathrm{ttft}}$、$l_{\mathrm{tbt}}$ と比較して決める。この 2 つの基準により、Mooncake のスケジューリングには 2 つの判断が必要になる。第 1 に prefill インスタンスの負荷に基づいて prefill 段階を受け入れるか、第 2 に decoding インスタンスの負荷に応じて decoding 段階へ進むかである。

<span id="section-07-02"></span>

### 7.2 早期拒否

実際には、prefill インスタンスまたは decoding インスタンス単独の負荷は、システムが処理した実際のリクエスト数を正確に表さない。この差は、1 つのリクエストの prefill インスタンスと decoding インスタンスをスケジュールする間に時間差があるため生じる。prefill 段階が完了した後、高負荷を理由に decoding インスタンスがリクエストを拒否すると、prefill 段階で使った計算リソースが無駄になる。その結果、prefill 中に正常に処理されたリクエストの実数は負荷指標が示す数より少なくなる。

この問題に対処するには、decoding インスタンスの負荷評価を prefill 段階の開始前に前倒しするのが自然である。この方式を**早期拒否**と呼ぶ。リクエストの到着時に Conductor は prefill プールと decoding プールのうち大きい方の負荷に基づいて受け入れを判断する。早期拒否は、拒否されたリクエストによる無効な計算を大幅に減らし、負荷分散を改善する。

![20 分間の prefill インスタンスと decoding インスタンスの負荷](../../papers/mooncake/figure-09.png)

**図 9.** 予測ベースの早期拒否を使う前の、20 分間における prefill インスタンスと decoding インスタンスの負荷。

<span id="section-07-03"></span>

### 7.3 早期拒否による負荷変動

しかし、早期拒否は新しい課題を生む。[図 9](#figure-09) は、20 台のマシンからなるクラスタで早期拒否方式を使った後に観測した、20 分間の実際のインスタンス負荷を示す。prefill マシンと decoding マシンの間に大きな逆位相の変動がある。prefill マシンが少ないクラスタや prefill 段階に時間がかかる状況では、この現象がより顕著になる。

さらに調べると、この負荷変動問題は decoding 負荷の予測と実際の実行の間の時間差に根ざしていることが分かった。現在の decoding 負荷に基づくスケジューリングには本質的な遅延がある。この遅延によって prefill インスタンスと decoding インスタンスの負荷に変動と位相ずれが生じ、[図 10](#figure-10) の理論例で示すようになる。緑の曲線は prefill インスタンスの負荷 （0 から 1 にスケール） を表し、黄色の曲線は decoding インスタンスの負荷を表す。

<span id="figure-10"></span>

![2 つの早期拒否ポリシーを適用したインスタンス負荷](../../papers/mooncake/figure-10.png)

**図 10.** 早期拒否と予測に基づく早期拒否を適用した場合のインスタンス負荷。

ステージ 1 では prefill インスタンスと decoding インスタンスの負荷がともに低いため、Conductor は prefill インスタンスの負荷が上限に達するまで大量のリクエストを受け入れる。ステージ 2 では prefill インスタンスで処理したリクエストが decoding インスタンスへスケジュールされ、decoding インスタンスの負荷が高くなる。その結果、Conductor は到着リクエストを拒否し、prefill インスタンスの負荷が下がる。ステージ 3 では新しいリクエストが decoding 段階へ入らないため、負荷が低下する。この時点で Conductor は再び大量のリクエストを受け入れ、prefill インスタンスが完全に負荷を受けるまで続ける。ステージ 4 では decoding インスタンスの負荷が増えると Conductor がリクエストを拒否し、prefill インスタンスの負荷が低くなる。このような prefill インスタンスと decoding インスタンスの負荷の大きな変動は、推論クラスタのリソース利用率を悪化させる。

<span id="section-07-04"></span>

### 7.4 予測に基づく早期拒否

負荷変動問題を解決するため、Mooncake のような分離型 LLM サービングシステムが過負荷シナリオで直面するスケジューリング課題に対処する、予測に基づく早期拒否フレームワークを提案する。[図 10](#figure-10) に示すように、このフレームワークは到着リクエストの prefill 段階後の decoding 負荷を予測し、その予測によってリクエストを受け入れるか決めることで変動を緩和する。この方式の中心は、次の期間の decoding 負荷を正確に予測することである。2 つの方法を導入する。

**リクエストレベル:** 先行研究は LLM サービングの負荷予測における大きな課題を指摘している。各リクエストの出力長が未知であることだ。出力長を事前に決められれば、TTFT と TBT をより正確に推定できる。これにより、decoding インスタンスが完了できるリクエスト数と、指定時間後に追加される新しいリクエスト数を予測し、その時点の負荷を得られる。しかし、各リクエストの出力長の予測はコストが高い [Hu24b] か精度が低く、特にリソースが乏しく正確な予測が必要な過負荷条件では、リクエストレベルの予測は難しい。

**システムレベル:** リクエストレベルの予測とは異なり、システムレベルの予測は個々のリクエストの完了時刻を予測しない。代わりに、指定時間後のインスタンスの全体バッチ数または TBT の状態を推定する。この予測は継続的に行い、精度をそれほど必要としないため、過負荷シナリオに適している。

Mooncake では現在、システムレベルの予測方式を使い、各リクエストの decoding 段階に一様な時間 $t_d$ がかかると仮定する。まず、ある時刻 $t$ について、時刻 $t$ に prefill インスタンスが完了できるリクエストを一様な decoding インスタンスへ追加する。次に、$t$ より前に完了するリクエスト （つまり実行時間が $t_d$ を超えるもの） を decoding インスタンスから削除する。最後に、すべての decoding インスタンスの平均 TBT と $l_{\mathrm{tbt}}$ の比を計算して負荷を予測する。リクエストレベルの予測は今後の課題とする。

**Testbed** 実験では、高性能計算ノードクラスタにシステムをデプロイして性能を測定した。クラスタの各ノードは次のように構成される。NVIDIA-A800-SXM4-80GB GPU 8 枚 （各 80GB HBM、NVLINK 接続）、ノード間の相互接続帯域が最大 800 Gbps の RDMA ネットワークカードを搭載する。各ノードは起動パラメータに応じて prefill インスタンスまたは decoding インスタンスをデプロイする。

**Metric** 実験では、定めた SLO の下で各システムのスループット性能に注目する。異なる RPS における TTFT と TBT を測定し、RPS が高いほどスループットが高いとみなす。リクエストの大半が SLO を満たすかを評価するため、TTFT と TBT の 90 パーセンタイル （P90） を最終指標として用いる。[§ 2](#section-02) で述べたように、TTFT と TBT の閾値は観測した最低 RPS 値のそれぞれ 10 倍と 5 倍に設定する。この閾値を超えることは SLO を満たせないことを示し、消費した対応リソースを無駄とみなす。比較しやすくするため、すべての TTFT と TBT をこれらの上限値で正規化し、ベースラインを 1.0 とする。

**Baseline** 実験のベースラインとして、最先端のオープンソース LLM サービングシステムの 1 つである vLLM を使う。vLLM は continuous batching と PagedAttention 技術を取り入れ、推論スループットを大きく高める。その一方で、vLLM の設計は推論リクエストの prefill 段階と decoding 段階を結合しているため、長いコンテキストの状況では decoding に混乱を生じさせる可能性がある。

### 8.2 過負荷シナリオでの性能

本節では [§ 7](#section-07) で述べたように、システムが処理できる最大リクエスト数に注目し、過負荷シナリオでの性能を評価する。ベースライン戦略は両段階の開始前に負荷に基づいてリクエストを拒否するため、すでに prefill 段階で処理したリクエストまで拒否してリソースを浪費する。これに対して、[§ 7.2](#section-07-02) と [§ 7.4](#section-07-04) で詳しく説明する早期拒否と予測に基づく早期拒否を提案する。これらの戦略はシステム負荷を総合的に考慮し、不要なリクエスト拒否を減らす。

具体的には、prefill インスタンス 8 個と decoding インスタンス 8 個からなる Mooncake クラスタを構築し、23,000 件のリクエストの実トレースでテストした。過負荷シナリオをシミュレートするため、再生速度を 2 倍にした。

<span id="table-03"></span>

![過負荷シナリオ実験でシステムが拒否したリクエスト数](../../papers/mooncake/table-03.png)

**表 3.** 過負荷シナリオ実験でシステムが拒否したリクエスト数。

[表 3](#table-03) は異なる戦略における Mooncake の性能を示す。ベースライン戦略ではシステムが 4,183 件を拒否する。これに対し、早期拒否と予測に基づく早期拒否では Mooncake がそれぞれ 3,771 件と 3,589 件を拒否する。これは、早期にリクエストを拒否すれば不要な prefill 計算を避け、システムリソースの実効利用率を高められることを示す。さらに decoding インスタンスの負荷を予測することで、Mooncake は負荷変動を抑え、リクエスト処理能力を高められる。

## 9 関連研究

スケジューリング、メモリ管理、リソース最適化によって LLM サービングシステムの効率を高めるため、これまでに多くの研究が行われてきた。
FasterTransformer [Nvi19a]、TensorRT-LLM [Ten23]、DeepSpeed Inference [Ami22] などの実運用向けシステムは、スループットを大幅に高めるよう設計されている。
Orca [Yu22a] はさまざまな段階での同時処理を促す iteration-level scheduling を採用し、vLLM [Kwo23] は動的な KVCache 管理でメモリを最適化する。
FlexGen [She23]、SARATHI [Agr24a]、FastServe [Wu23a] は、限られたハードウェアにワークロードを効果的に分配するため、新しいスケジューリングと swap 戦略を取り入れており、互いの最適化を補完することも多い。

Mooncake の設計はこれらの進展に基づき、特に vLLM のオープンソースコミュニティから多くを学んでいる。その貢献に深く感謝する。

さらに、prefill 段階と decoding 段階を分離するという我々の洞察を共有する研究があり、システムスループットを高める分離型アーキテクチャにつながっている。Splitwise [Pat23] の arXiv 論文は Mooncake の開発初期にあり、我々の進展をさらに後押しした。DistServe [Zho24] は各段階のリソース割り当てと並列戦略を最適化して GPU goodput を最大化し、TetriInfer [Hu24b] は chunked prefill と 2 段階の分離に加えて予測型の 2 段階スケジューリングアルゴリズムを取り入れてリソース利用率を最適化するなど、多くの同時期の研究が我々の知見を裏付けている。

Prefix caching も広く利用され、複数リクエスト間で KVCache を再利用し、LLM 推論システムの計算オーバーヘッドを減らす [Ten23, Kwo23]。Prompt Cache [Gim24] は頻繁に使われるテキストの KVCache を推論サーバーで事前計算・保存し、再利用を可能にして推論レイテンシを大幅に下げる。SGLang [Zhe24] は RadixAttention を利用し、基数木構造内の least recently used （LRU） キャッシュでさまざまな再利用パターンの自動共有を効率的に実現する。

これらの方式のうち、我々と同時期の AttentionStore [Gao24a] は、低コストのメモリとストレージ媒体を利用し、すべてのリクエストの KVCache を収容する階層型 KVCache システムを提案する。Mooncake のアーキテクチャは AttentionStore と多くの設計選択を共有する。しかし長いコンテキストの推論では KVCache が非常に大きくなるため、高い容量と効率的なデータ転送に加え、KVCache 中心のグローバルスケジューリングが必要になる。
また Mooncake は単独のキャッシュサービスではない。メモリ効率のよいキャッシュ保存機構とキャッシュを考慮したスケジューリングの両方を取り入れ、prefix caching の効率をさらに高める。

さらに、最近の研究 [Sri24] はプロンプトのスケジューリングを探り始めており、これは本質的に KVCache 中心のスケジューリングである。この分野の多くの結果を再確認したが、オンラインのトレースにおける実際の再利用率は、オープンソースベンチマークで再現された結果よりはるかに小さい。理論上、ストレージ容量と TTFT SLO が無限だと仮定しても、現在のワークロードで再利用できる KVCache は最大 50% にすぎない。ただし、この再利用率はアプリケーションシナリオに大きく依存し、例えば chat-to-paper サービス [https://papers.cool/](https://papers.cool/) のような特定のシナリオでは 90% に達しうる。スループットだけを志向するのではなく、SLO の下で過負荷を指向したスケジューリングが必要だとも強調する。

## 10 今後の課題

LLM サービングの各部分を専用のリソースプールに分離することが、Mooncake の高いリソース利用率の鍵である。
今後はこの方向で、特に異種アクセラレータの利用可能性を含め、さらなる機会を探る予定である。
現在のフラッグシップアクセラレータは、計算能力、メモリ帯域幅、容量など複数の指標のバランスを取るため、汎用的だが個々の指標では最適ではない。
例えば、ドルあたりの帯域幅またはワットあたりの帯域幅だけを考えると、現在の GDDR や LPDDR 方式はフラッグシップアクセラレータより 1 桁よい場合がある。
また、近い将来に高帯域幅と大容量の両方を提供できる、process-in-memory [Yan20b, Lag21, Li23r, Sri23a] や hybrid bonding [Akb24, Kor23, Zha13, Zha17a, Kim16a] 技術を使ったメモリ指向デバイスにも特に関心がある。
これらの技術は decoding 段階のメモリ律速操作の実行コストを下げるのに適している。

計算指向と帯域幅指向のアクセラレータを含む異種アクセラレータ環境では、より進んだ分離型アーキテクチャも検討できる。
例えば、他の線形変換演算子とは異なり、decoding 段階の attention 演算子の算術強度は attention ヘッド数を key/value ヘッド数で割った値にだけ比例する。
バッチサイズを大きくしてもこの強度は高められず、通常は他の演算子よりメモリ律速になる。
したがって、attention 演算子を他の線形演算子から分離して、リソース利用率をさらに高められる。
初期のシミュレーション結果 [Che24e] によれば、このアーキテクチャは全体のスループットを高める大きな可能性がある。
さらに、DeepSeek-v2 [Dee24] が最近提案した MLA 演算子は算術強度を直接高め、別の角度からこの問題を解決し、有望な結果を示す。

直交する方向として、KVCache のサイズ削減を目指す多くのアルゴリズムがあり、Mooncake に 2 つの面で利益をもたらす。1) 利用率を高めるためバッチサイズを大きくすること、2) prefill コストを減らすため KVCache のキャッシュヒット率を高めることだ。
この分野は現在非常に活発であり、KVCache を圧縮する方法 [Yu24, Cai24b, Liu24c, He24a, Liu24a, Liu24m]、さまざまな指標で重要な Token を選ぶ方法 [Guo24a, Dev24, Yao24a, Yan24f, Adn24, Li24c, Zha23g]、異なるレイヤー間で KVCache を共有する方法 [Zuh24, Wu24, Cha23b]、KVCache を使わない演算子を持つハイブリッドアーキテクチャ [Sun24b, Gu23, Pen23b, Dao24, Lie24, Bot24] などがある。

スケジューリングについては、リクエストの優先度の違いと異なる TTFT/TBT SLO のシナリオを考慮する高度なポリシーを開発中である。
このポリシーはさまざまな運用条件でシステムの応答性と効率を高めるよう設計する。
部分ヒットや有効期限切れのシナリオに対する複製、移行、専用の削除ポリシーを含む KVCache の効果的な管理も、キャッシュ再利用の最適化に重要である。
さらに、prefill インスタンスと decoding インスタンスを動的に均衡させ、バッチ指向のオフロードタスクでアイドルリソースを利用する方法を調べる予定である。
この方法により、ワークロードが変動する間もリソース利用率を最大化できる。

## 11 結論

本論文では、長いコンテキストと過負荷の状況を特に効率よく扱うための、KVCache 中心の分離型アーキテクチャ Mooncake を提示した。レイテンシに関する SLO 要件を満たしながら全体の実効スループットを最大化するという目標の必要性、課題、設計上の選択について議論した。
