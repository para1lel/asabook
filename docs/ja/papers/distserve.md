## 要約

DistServe は、LLM のプリフィル計算とデコーディング計算を分離し、大規模言語モデル（LLM）のサービング性能を向上させる。既存の LLM サービングシステムは 2 つのフェーズを同じ場所に配置し、すべてのユーザーとリクエストにわたってプリフィルとデコーディングの計算をバッチ処理する。我々の調査では、この戦略がプリフィルとデコーディングの強い干渉を引き起こすだけでなく、両フェーズのリソース割り当てと並列化計画を結び付けることがわかった。LLM アプリケーションでは、各フェーズの個別レイテンシ、すなわちプリフィルフェーズの Time To First Token（TTFT）と、デコーディングフェーズにおける各リクエストの Time Per Output Token（TPOT）が重視される。厳しいレイテンシ要件がある場合、既存システムは一方のレイテンシを優先するか、両方を満たすために計算資源を過剰に割り当てる必要がある。

DistServe は、プリフィルとデコーディングの計算を異なる GPU に割り当てることで、両者の干渉をなくす。アプリケーションの TTFT と TPOT の要件に応じて、各フェーズに適したリソース割り当てと並列化戦略を共同で最適化する。さらに、分離による通信を最小限にするため、サービングクラスタの帯域幅に応じて 2 つのフェーズを配置する。その結果、各 GPU が TTFT と TPOT の制約内で処理できる最大レートという指標で、LLM のサービング性能を大幅に高められる。評価の結果、さまざまな一般的な LLM、アプリケーション、レイテンシ要件において、最先端システムより $7.4\times$ 多くのリクエストを処理するか、$12.6\times$ 厳しい SLO を満たしつつ、$>90\%$ のリクエストをレイテンシ制約内に収められることがわかった。

## 1 はじめに

GPT-4 [Ope23]、Bard [Bar23]、LLaMA [Tou23d] などの大規模言語モデル（LLM）は、生成 AI に大きな変化をもたらした。これらは検索エンジンからパーソナルアシスタント [Inf23] まで、既存のインターネットサービスを変え始めており、ユニバーサルチャットボット [Sch22, Chi23b] やプログラミングアシスタント [Che21, Roz23] のような新しいアプリケーションも可能にしている。しかし、こうした進歩には重大な課題がある。エンドツーエンドの LLM クエリの処理は、標準的な検索クエリより大幅に遅くなる可能性がある [Reu23]。さまざまなアプリケーションの厳しいレイテンシ要件を満たすには、サービスプロバイダーは多くの GPU を含む計算資源を過剰に用意しなければならず、コスト効率が低下する。そのため、高い SLO 達成率（SLO を満たすリクエストの割合）を維持しながら LLM クエリあたりのコストを最適化することが、すべての LLM サービスでますます重要になっている。

**図 1.** 入力長 512、出力長 64 の合成ワークロードで、13B パラメータの LLM を 1 台の NVIDIA 80GB A100 上で提供した場合の性能。上：既存システムとプリフィルフェーズだけを提供するシステムの P90 Time To First Token（TTFT）レイテンシの比較。下：既存システムとデコーディングフェーズだけを提供するシステムの P90 Time Per Output Token（TPOT）レイテンシの比較。

LLM サービスは、2 つのフェーズでユーザーのクエリに応答する。*プリフィルフェーズ*では、トークン列で構成されたユーザープロンプトを処理し、応答の最初のトークンを*1 ステップで*生成する。続く*デコーディングフェーズ*では、後続のトークンを*複数ステップで*順に生成する。各デコーディングステップは、前のステップで生成したトークンに基づいて新しいトークンを生成し、終了トークンに達するまで続く。この 2 段階の処理により、LLM サービスは従来のサービスと異なる。LLM サービスのレイテンシは 2 つの主要な指標で測定する。*Time To First Token（TTFT）*はプリフィルフェーズの時間、*Time Per Output Token（TPOT）*は各リクエストでトークンを生成する平均時間（最初のトークンを除く）である [+1]。アプリケーションによって各指標の要件は異なる。例えば、リアルタイムチャットボット [Sch22] は応答を早く返すため低い TTFT を優先するが、TPOT は人間の読書速度（毎分 250 語）を上回るまでしか重要ではない。一方、文書要約アプリケーションでは、要約を早く生成するため低い TPOT が重視される。

したがって、アプリケーションの TTFT と TPOT の要件を考えると、効果的な LLM サービングシステムはこれらのニーズを両立し、各 GPU について SLO 達成目標（例えば 90%）を満たしながら処理できる最大リクエストレートとして定義される*GPU あたりグッドプット*を最大化すべきである。GPU あたりグッドプットが高いほど、クエリあたりのコストは直接低下する。

プリフィルフェーズとデコーディングフェーズは LLM の重みとワーキングメモリを共有するため、既存の LLM サービングシステムは通常、両フェーズを GPU 上に併置し、すべてのユーザーとリクエストについて 1 秒あたりに生成されるトークン数を最大化するため、リクエスト間でプリフィルステップとデコーディングステップをバッチ処理する [Yu22a, Kwo23a]。しかし、レイテンシ要件を満たすには、こうしたシステムは計算資源を過剰に用意しなければならない。これを確認するため、[図 1](#figure-01) は既存システムで 13B LLM を提供したとき、リクエストレートの増加に伴って P90 TTFT と TPOT がどう変化するかを示す [Kwo23]。ワークロードと 2 つのレイテンシ制約は、LLM で記事の短い要約を生成する状況を模したものである。SLO 達成率 90% では、TTFT と TPOT のうち厳しい方の要件に制約されるため、1 台の A100 GPU で達成できる最大グッドプットは約 1.6 requests per second（rps）である。各フェーズを別々の GPU で独立して提供すると、性能は大きく異なる。オレンジと緑の曲線が示すように、プリフィルフェーズでは GPU あたり 5.6 rps、デコーディングフェーズでは 10 rps のグッドプットを達成する。理想的には、プリフィルに 2 GPU、デコーディングに 1 GPU を割り当てれば、全体で 10 rps、すなわち GPU あたり 3.3 rps でモデルを提供でき、既存システムより 2.1 倍高い。グッドプットの差は、計算特性とレイテンシ要件が大きく異なるプリフィルとデコーディングを併置していることが主な原因である（§[2.1](#S2.SS1)）。

第 1 に、併置は強い*プリフィル・デコーディング干渉*を引き起こす。プリフィルステップはデコーディングステップよりはるかに長くかかることが多い。同じバッチに入れると、バッチ内のデコーディングステップはプリフィルステップによって遅れ、TPOT が大幅に延びる。同様に、デコーディングステップを加えると、[図 2](#figure-02) が示すように TTFT も無視できないほど増える。別々にスケジュールしても、資源を奪い合うため問題は残る。GPU での実行を待つデコーディングタスクは、実行中のプリフィルタスクによって待ち行列遅延が増え、その逆も同じである。一方のフェーズを優先すると、もう一方のレイテンシ要件を満たせないおそれがある。

第 2 に、プリフィルとデコーディングの計算ではレイテンシ要件が異なり、適する並列方式も異なる（§[3](#S3)）。しかし両者を併置するとリソース割り当てが結び付き、各フェーズ固有のレイテンシ要件に適した並列化戦略を個別に採用できない。

これらの課題に対し、LLM 推論のプリフィルフェーズとデコーディングフェーズを分離し、別々の GPU に割り当てる方法を提案する。この方法には 2 つの利点がある。第 1 に、各フェーズを異なる GPU 上で独立して動かすことで、プリフィルとデコーディングの干渉をなくせる。第 2 に、各フェーズを個別に拡張し、それぞれのレイテンシ要件を満たすようリソース割り当てとモデル並列化戦略を調整できる。分離すると GPU 間で中間状態を通信する必要があるが、現代の GPU クラスタでは通信オーバーヘッドが小さいことを示す（§[3.3](#S3.SS3)）。適切に管理すれば、分離によって GPU あたりグッドプットを大幅に高められる。

以上の知見に基づき、本研究ではプリフィルフェーズとデコーディングフェーズを分離し、グッドプットを最適化する LLM サービングシステム DistServe [+repo] を構築する。TTFT と TPOT の要件が与えられると、DistServe はまず、単一のモデルレプリカを提供すると仮定し、プリフィルフェーズとデコーディングフェーズの GPU 割り当てと並列化戦略を共同で最適化して、各フェーズを独立に拡張する。この最適化は GPU あたりグッドプットを最大化し、それぞれのレイテンシ要件に応じて、各フェーズに異なる数の GPU と並列化戦略を割り当てる場合がある。次に、この割り当てを複製によって複数インスタンスへ拡張し、ユーザーが要求するトラフィックレートを満たす（§[4](#S4)）。DistServe はさらに、各フェーズの割り当て方式とクラスタ帯域幅に応じてプリフィル計算とデコーディング計算を配置し、フェーズ間の中間状態通信を最小化するアルゴリズムを備える。

DistServe は LLM 推論エンジン上のオーケストレーション層として実装した。チャットボット、プログラミング支援、文書要約という 3 つの重要な実アプリケーションに基づいてワークロードを変え、さまざまな LLM で DistServe を評価した。最先端のソリューションと比較して、DistServe はさまざまなレイテンシ制約下で最大 $7.4\times$ 多くのリクエストを処理するか、$12.6\times$ 厳しい SLO を満たせる。我々の貢献は次の通りである：

- 既存の LLM サービングシステムにおけるプリフィル・デコーディング干渉とリソース結合の問題を明らかにし、2 つのフェーズを分離する方法を提案する。
- プリフィルインスタンスとデコーディングインスタンスについて、グッドプットが最大となる構成を自動的に選ぶ新しい配置アルゴリズムを設計する。
- 現実的なワークロードを用いて DistServe を包括的に評価する。

## 2 背景と動機

LLM サービスはクライアント・サーバー型のアーキテクチャを採る。クライアントは一連のテキストをリクエストとしてサーバーへ送る。サーバーは GPU 上で LLM を動かし、リクエストに対して推論を実行し、生成結果をクライアントへ返す（またはストリーミングする）。§[1](#S1) で説明したように、LLM サービスではプリフィルとデコーディングという固有の処理があるため、アプリケーションのニーズに応じて TTFT と TPOT の両方に厳しいサービスレベル目標（SLO）が課される場合がある。サービングシステムは両方の SLO を満たしながら、高価な GPU に伴うコストを最小化しなければならない。つまり、割り当てた各 GPU について SLO 達成目標を満たしながら、1 秒あたりに処理するリクエスト数、すなわち*GPU あたりグッドプット*を最大化したい。以下では LLM の推論計算（§[2.1](#S2.SS1)）を詳しく説明し、既存の LLM サービング最適化（§[2.2](#S2.SS2)）を取り上げる。

### 2.1 LLM推論

現代の LLM [Ope23, Tou23d] は、入力シーケンスから次のトークンを予測する。この予測では、シーケンス内の各トークンについて隠れ表現を計算する。LLM は可変数の入力トークンを受け取り、その隠れ表現を並列に計算できるが、計算量は並列処理するトークン数に対して超線形に増える。入力トークン数にかかわらず、LLM の重みと中間状態を GPU の HBM から SRAM へ移すために大量の I/O が必要となる。この点は入力サイズが変わっても同じである。

プリフィルステップは、多くのトークンを含むことが多い新しいシーケンスを扱い、それらを同時に処理する。これに対し、各デコーディングステップが処理するのは、前のステップで生成された新しいトークン 1 つだけである。この違いにより、2 つのフェーズの計算特性は大きく異なる。ユーザープロンプトが短くない場合、プリフィルステップは計算バウンドになりやすい。例えば 13B LLM では、512 トークンのシーケンスをプリフィルすると A100 はほぼ計算バウンドになる（§[3.1](#S3.SS1)）。一方、デコーディングフェーズは各ステップで新しいトークンを 1 つしか処理しないにもかかわらず、プリフィルフェーズと同程度の I/O が発生するため、GPU のメモリ帯域幅に制約される。

両方のフェーズにおいて、KVキャッシュとして知られる中間状態[Kwo23]が各トークン位置で生成され、後のデコーディングステップで再度必要となる。これを再計算しないために、GPUメモリに保存される。LLMの重みとKVキャッシュがメモリで共有されるため、ほとんどのLLM推論エンジンは、計算特性が異なるにも関わらず、プリフィルフェーズとデコーディングフェーズをGPU上で同じ場所に配置することを選ぶ。

### 2.2 LLMサービングの最適化

リアルタイムのオンラインサービングでは、複数のリクエストが到着し、SLO 内で処理しなければならない。それらの計算をバッチ化、並列化することが、低レイテンシ、高スループット、高い GPU 利用率を実現する鍵となる。

**バッチ処理。** 現在のサービスシステム [Yu22a, Kwo23, Agr23] は、*連続バッチ処理* と呼ばれる手法を使う。新しいリクエストのプリフィルと、処理中のリクエストのデコーディングを同じバッチに入れる方法である。GPU 利用率を高め、全ユーザー・全リクエストで 1 秒あたりに生成されるトークン数を最大化できる。しかし、§[1](#S1) で述べ、§[2.3](#S2.SS3) で詳しく説明するように、TTFT と TPOT の間にはトレードオフが生じる。連続バッチ処理の改良版 [Agr23] は、長いプリフィルを分割し、GPU の性能上限を超えない形でデコーディングジョブを組み合わせることで両者のバランスを取ろうとするが、実際には TTFT を犠牲にして TPOT を改善している。つまり、プリフィルとデコーディングをバッチ化すると、TTFT か TPOT のどちらかを妥協せざるを得ない。

**モデル並列性。** LLM サービングでは、モデル並列性を演算子内並列性と演算子間並列性に分ける [Li23j, Zhe22, Sho20]。どちらも大きなモデルを扱えるが、サービング性能への影響は異なる。演算子内並列性は行列乗算など計算集約型の演算子を複数 GPU に分割して計算を高速化する一方、通信量が増える。実行時間 [+2]、したがってレイテンシを短縮でき、特にプリフィル段階の TTFT で効果があるが、GPU 間の高帯域接続 (例: NVLINK) が必要になる。演算子間並列性は LLM のレイヤーを複数ステージに分け、各ステージを GPU で実行してパイプラインを作る。ステージ間通信で実行時間は多少増えるが、GPU を 1 台追加するたびにシステムの処理レートを線形に拡張できる。本論文では、実行時間が短くなることでプリフィルとデコーディングの待ち行列遅延も減るという、モデル並列性の別の利点を示す。詳しくは §[3](#S3) で分析する。モデル並列性に加え、モデルインスタンスを複製すれば、並列構成に関係なくシステムの処理レートを線形に拡張できる。

これらの並列化戦略が作る最適化空間では、アプリケーションのレイテンシ要件に応じて慎重にトレードオフを取る必要がある。

### 2.3 課題と機会

既存システムのようにプリフィルとデコーディングを同じ GPU に置いてバッチ処理し、全体のスループットを最大化する方法は、サービスプロバイダーにとってコスト効率がよい。しかし SLO があると、次の問題により高いサービス品質と低コストを同時に維持しにくい。

**プリフィル・デコーディング干渉。** [図 2](#figure-02) に示すように、デコーディングリクエストのバッチへプリフィルジョブを 1 つ加えるだけで、両方の処理が大幅に遅くなり、TTFT と TPOT が増加する。バッチ内のデコーディングタスクは長いプリフィルジョブの完了を待つため、TPOT が延びる。プリフィルが長いほど遅延は大きくなり、[図 2](#figure-02)(b) に表れている。プリフィルにデコーディングジョブを加えると、特に GPU がすでに限界に達している場合 ([図 2](#figure-02) の青い曲線) にプリフィル完了時間も延びる。

この干渉を緩和する試みの 1 つに、*デコーディングの相乗りを伴うチャンク化プリフィル* [Agr23, Dee23] がある。長いプリフィルをチャンクに分割し、プリフィルチャンクと少数のデコーディングジョブを同じバッチに入れる（相乗りさせる）方法である。長いプリフィルジョブによるデコーディングジョブの減速は緩和できるが、なくすことはできない。さらにプリフィルジョブに余分なオーバーヘッドが生じ、チャンクサイズの調整だけでは簡単に解消できない。第 1 に、チャンクサイズを GPU を飽和させる変曲点より大幅に小さくすると、プリフィルジョブは同じバッチのデコーディングジョブと競合して GPU 資源を単独で使えないため、実行時間が長くなる。第 2 に、GPU がほぼ飽和するまでチャンクサイズを増やすと、デコードトークン用の空きスロットが限られるため、相乗りの機会が減る。また、チャンク化プリフィルではプリフィルジョブのメモリアクセスが大幅に増える。後続の各チャンクを計算するたびに、それ以前の全チャンクの KV キャッシュを HBM から SRAM へ読み直す必要があるためである。具体的には、プリフィルジョブを $N$ 個の等しいチャンクに分割した場合、非チャンク化の場合の $O(N)$ に対し、合計 $N+(N-1)+...+1=O(N^2)$ 個分の KV キャッシュを読み込む必要がある。このオーバーヘッドはコンテキストが長くなるほど増える。

**効果のないスケジューリング。** プリフィルとデコーディングのジョブをバッチ化せず順番に処理しても、干渉は軽減されない。デコーディングジョブは GPU 上で実行中のプリフィルジョブを待つため、待ち行列遅延が長くなることがある。デコーディング専用バッチでは GPU を使い切れないことも多い。どちらかの段階を優先すれば、もう一方のレイテンシが悪化する。優先スケジューリングでは解決できない。

**リソースと並列性の結合。** プリフィルとデコーディングを同じ GPU に置くと、リソースと並列設定を共有せざるを得ない。しかし各フェーズには固有の計算特性とレイテンシ要件があり、より異質なリソース配分が必要になる。例えばプリフィルは、より多くの GPU と演算子内並列性で実行時間を短縮し、厳しい TTFT SLO を満たしやすくなる。デコーディングはプリフィルより少ない GPU で高いレートを処理でき、最適な並列設定は実行中のバッチサイズに依存する。既存システムでは結合のため、TTFT と TPOT のうち厳しい方に合わせてリソースと並列計画を決めることになり、もう一方には適さない場合がある。その結果、2 つの SLO を満たすためにリソースを過剰に割り当てることが多い。

**機会。** これらの問題に対処するため、プリフィル段階とデコーディング段階を分離する。「インスタンス」は、モデル重みの完全なコピーを 1 つ管理するリソース単位を指す。モデル並列性を適用すると、1 インスタンスが複数 GPU に対応することもある。2 段階を別々の GPU に分離すると、各段階が独自のモデル重みを管理し、*プリフィルインスタンス*と*デコーディングインスタンス*ができる。プリフィルインスタンスはリクエストを受けると、そのリクエストのプリフィル計算だけを行い、最初の出力トークンを生成する。次に、中間結果 (主に KV キャッシュ) をデコーディングインスタンスへ送り、後続のデコーディングステップを任せる。デコーディング計算は GPU 利用率が低いことが多いため、1 つのデコーディングインスタンスに複数のプリフィルインスタンスを割り当てることができる。これにより、より多くのデコーディングジョブをバッチ化し、GPU 利用率を高められる。

プリフィルとデコーディングを分離すれば、両フェーズ間の干渉がなくなり、それぞれが TTFT または TPOT の目標に集中できる。各タイプのインスタンスは、レイテンシ要件に合わせて異なるリソースと並列戦略を使える。2 種類のインスタンスに割り当てる GPU 数と並列度を調整すれば、システム全体の GPU あたりグッドプットを最大化し、過剰なリソース配備を避けられるため、SLO を守りながらクエリごとのコストを下げられる。次節では、各フェーズに最適なリソース割り当てと並列計画を求める方法を示す。

## 3 トレードオフ分析

2 つのフェーズを分離すると、各フェーズの特性を独立して分析でき、アルゴリズム設計に必要な知見を得られる。設計空間も広がり、各フェーズをそれぞれのレイテンシ要件に応じて個別に拡張、スケジューリングする必要が生じる。

本節では、分離後のプリフィルインスタンス (§[3.1](#S3.SS1)) とデコーディングインスタンス (§[3.2](#S3.SS2)) の計算パターンを分析する。各フェーズのバッチ処理と並列性に関する主要パラメータを特定し、指針を導くことが目的である。続いて、実際のデプロイで考慮すべき点を取り上げる (§[3.3](#S3.SS3))。この分析が GPU あたりグッドプット最適化の基礎となる。

### 3.1 プリフィルインスタンスの分析

<span id="figure-03"></span>

![キャプションを参照](../../papers/distserve/figure-03.png)

**図 3.** 13BパラメータのLLMを提供する際の、異なるバッチサイズおよび入力長でのプリフィルフェーズとデコーディングフェーズのスループット。

分離後、プリフィルフェーズはユーザープロンプトの全トークンを並列に処理し、最初のトークンを生成する。所定の到着率に対し、最小限の資源でサービスの TTFT 要件を満たすことが目標である。

**バッチ戦略。** プリフィルステップは通常、計算集約型である。[図 3](#figure-03)(a) は、入力長とバッチサイズに応じたプリフィル段階のスループットを示す。13B パラメータの LLM では、512 トークンのシーケンスを 1 件処理するだけで A100 GPU を飽和させられる。モデルが大きいほど、GPU 飽和に必要なシーケンスは短くなる。GPU が計算バウンドになると、バッチへリクエストを追加しても効率は上がらず、バッチ全体の処理時間が比例して延び、含まれるリクエストがすべて遅くなる。したがってプリフィルインスタンスでは、対象の LLM と GPU をあらかじめプロファイルし、プリフィルが計算バウンドになる臨界入力長 $L_{m}$ を求める必要がある。バッチ内のリクエスト数を増やすのは、スケジュールするリクエストの入力長が $L_{m}$ 未満の場合だけでよい。実際のユーザープロンプトは平均で数百トークンを超えることが多く [Sha23b]、プリフィルインスタンスのバッチサイズは通常小さい。

<span id="figure-04"></span>

![キャプションを参照](../../papers/distserve/figure-04.png)

**図4.** 2台のA100 GPUで異なる並列処理を用いた66BパラメータのLLMにサービスした場合の平均TTFT。

**並列計画。** プリフィル専用インスタンスがどの並列方式を選ぶか調べるため、2 台の A100 GPU 上で 66B LLM を演算子間並列または演算子内並列によって実行する。単純化のため、入力長は一律 512 トークン、到着過程はポアソン過程と仮定する。[図 4](#figure-04)(a) の平均 TTFT を比較すると、到着率が低いときは演算子内並列が効率的だが、到着率が上がると演算子間並列が優位になる。分離後のプリフィル段階は M/D/1 待ち行列と同様に振る舞うため、待ち行列理論でこの観察を検証できる。

まず、並列化しない単一デバイスの場合について記号を定義する。プリフィル長が一定であるため、$D$ と表す各リクエストの実行時間も一定となる。1 件のリクエストで GPU が飽和するので、リクエストはバッチ化せず、先着順（FCFS）でスケジュールする。ポアソン到着率を $R$、利用率の条件を $R D<1$ とすると、平均 TTFT（$\mathit{Avg\_TTFT}$）は M/D/1 待ち行列 [Sho18] の閉形式で次のようにモデル化できる：

$$
\small \mathit{Avg\_TTFT}=D+\frac{R D^{2}}{2(1-R D)},\tag{1}
$$

第 1 項は実行時間、第 2 項は待ち行列遅延を表す。[式 1](#S3.E1) を基に、以下では並列化を組み込む。

2 ウェイの演算子間並列では、リクエスト単位のレイテンシが $D_{s}$ となり、最も遅いステージの完了に $D_{m}$ かかると仮定する。レイヤー間のアクティベーション通信は無視できるため [Zhe22, Li23j]、$D\approx D_{s}\approx 2\times D_{m}$ である。2 ウェイの演算子間並列における平均 TTFT は次のように導ける：

$$
\small \mathit{Avg\_TTFT}_{\mathrm{inter}}=D_{s}+\frac{R D_{m}^{2}}{2(1-R D_{m})}=D+\frac{R D^{2}}{4(2-R D)}.\tag{2}
$$

演算子内並列では、速度向上係数 $K$ を導入する。$1<K<2$ は、演算子内並列の大きな通信オーバーヘッドによって速度向上が完全な 2 倍に達しないことを表す。実行時間を $D_{s}=\frac{D}{K}$ とすると、並列度 2 の演算子内並列における平均 TTFT は次のようになる：

$$
\small \mathit{Avg\_TTFT}_{\mathrm{intra}}=\frac{D}{K}+\frac{R D^{2}}{2K(K-R D)}.\tag{3}
$$

[式 2](#S3.E2) と [式 3](#S3.E3) を比較すると、到着率が低く実行時間（第 1 項）が支配的な場合、演算子内並列による実行時間の短縮が効くため、こちらが効率的である。到着率が上がり、待ち行列遅延（第 2 項）の影響が大きくなると演算子間並列が有利になる。この結果は [図 4](#figure-04)(a) と一致する。

プリフィルフェーズでどの並列方式が有利かは、TTFT SLO と速度向上係数 $K$ にも左右される。[図 4](#figure-04)(a) が示すように、SLO が厳しいほど、実行時間を短縮できる演算子内並列が有利になる。$K$ の値は入力長、モデルアーキテクチャ、通信帯域幅、配置 [Sho20, Zhe22] などに依存する。[図 4](#figure-04)(b) のとおり、$K$ が小さくなると演算子内並列の効果は大きく低下する。§[4](#S4) では、これらの条件を考慮してリソース構成と並列構成を最適化するアルゴリズムを示す。

### 3.2 デコーディングインスタンスの解析

プリフィルインスタンスと異なり、デコーディングインスタンスはプリフィルインスタンスから KV キャッシュと最初の出力トークンを受け取り、後続のトークンを 1 つずつ生成する。デコーディングインスタンスでは、最小限の計算資源でアプリケーションの TPOT 要件を満たすことが最適化目標となる。

**バッチ戦略。** 1 件のデコーディングジョブは主に帯域幅に制約されるため、バッチ処理は GPU 利用率の低下を防ぎ、GPU あたりグッドプットを高める鍵となる。プリフィルとデコーディングを同じ場所で実行する既存システムでは、デコーディングのバッチサイズを増やすとレイテンシ目標と衝突し、特にリクエストレートが高い場合に難しい。共有 GPU 上でプリフィルとデコーディングが競合し、TTFT と TPOT のトレードオフが生じるためである。例えば到着率が上がるとプリフィルジョブが増え、プリフィルを優先して TTFT を満たすにはより多くの GPU 時間が必要になり、TPOT が悪化する。

一方、分離すれば、1 つのデコーディングインスタンスに複数のプリフィルインスタンスを割り当てられる。これにより TPOT を犠牲にせず、デコーディングフェーズ専用の GPU 上でより大きなバッチを蓄積できる。

<span id="figure-05"></span>

![キャプションを参照](../../papers/distserve/figure-05.png)

**図 5.** バッチサイズ 128、入力長 256 の 13B LLM を異なる並列度で提供したときの、デコーディングフェーズのレイテンシとスループット。

**並列計画。** 分離後は、全アクティブリクエストの KV キャッシュを保持する必要があるため、デコーディングのバッチサイズが GPU メモリ容量に制約されることがある。モデル並列性でデコーディングインスタンスを拡張するか、PagedAttention [Kwo23] や GQA [Ain23a] など高度な KV キャッシュ管理技術を使えば、ほぼ計算バウンドになるまでバッチサイズを増やせる。バッチサイズが計算バウンドに近づくと、デコーディング計算はプリフィル段階に似てくる。この観察に基づき、[図 5](#figure-05) では大きなバッチにおける並列度別のレイテンシとスループットを調べる。演算子内並列はレイテンシを下げるが、通信と分割後の利用率低下により効果は逓減する。演算子間並列はスループットをほぼ線形に拡張できる。したがって TPOT SLO が厳しい場合、TPOT を下げてレイテンシ目標を満たすには演算子内並列が欠かせない。それ以外では、演算子間並列のほうがスループットを線形に伸ばしやすい。

モデルが 1 台の GPU メモリに収まる場合、プリフィルインスタンスとデコーディングインスタンスのどちらでも、モデル並列化に加えてレプリケーションも有力な選択肢となり、システムの処理レートを線形に拡張できる。さらに、リクエストを $N$ 個のレプリカへ均等に振り分けると仮定すれば、[式 1](#S3.E1) の $R$ を $R/N$ に置き換えることで待ち行列遅延も短縮できる。ただし、GPU メモリにモデル重みのレプリカを追加で保持する必要がある。

### 3.3 実務上の問題

ここまでで、各フェーズのバッチ処理と並列方式を選ぶための基本原則を示した。本節では、分離したプリフィルフェーズとデコーディングフェーズを実際にデプロイするときに生じる問題を取り上げる。

**可変プリフィル長。** §[3](#S3) では、リクエスト間でプロンプト長が均一だと仮定した。実際のデプロイでは、リクエスト長は LLM アプリケーションによって異なる。異なる長さのリクエストでは各パイプラインステージの実行時間が変わるため、演算子間並列を使うプリフィルインスタンスにパイプラインバブル [Hua19b, Nar19] が生じる可能性がある。その結果、M/D/1 待ち行列モデルから導いた結論とわずかにずれる。§[4](#S4) では、ワークロードに基づいて並列性を探索し、スケジューリングでバブルを最小化するアルゴリズムを示す (§[4.3](#S4.SS3))。

**通信オーバーヘッド。** KV キャッシュをプリフィルからデコーディングインスタンスへ転送すると、無視できないオーバーヘッドが生じる。例えば OPT-66B では、512 トークンのリクエスト 1 件の KV キャッシュが約 1.13GB になる。平均到着率を 10 rps とすると、毎秒 11.3GB のデータを転送する必要があり、オーバーヘッドを見えなくするには約 90Gbps の帯域幅が必要である。KV キャッシュのサイズは平均入力長と到着率に応じて増える。最近の LLM 用 GPU クラスタの多くは InfiniBand (例: 800Gbps) を備える。ノード間帯域幅が限られる場合、DistServe は一般的なノード内 NVLINK を使う。A100 GPU 間のピーク帯域幅は 600GB/s であり、転送オーバーヘッドを無視できる水準に抑えられる (§[6.3](#S6.SS3))。ただし、この要件はプリフィルとデコーディングインスタンスの配置に追加制約を課すため、次節で考慮する。

本節の分析から、ワークロードパターン、配置制約、SLO 要件、並列化戦略、リソース割り当てが、分離型サービングシステムを設計する際の主要なパラメータだとわかる。この探索空間から GPU あたりグッドプットが最大となる構成を自動的に見つける方法を、次節で示す。

## 4 方法

以上の課題を解決するため、DistServe を構築した。モデル、ワークロード特性、レイテンシ要件、SLO 達成目標が与えられると、DistServe は（a）プリフィルインスタンスとデコーディングインスタンスの並列化戦略、（b）各タイプのインスタンス数、（c）物理クラスタ上での配置方法を決定する。この解を「配置」と呼ぶ。目標は GPU あたりグッドプットを最大化する配置を見つけることである。

§[3.3](#S3.SS3) で説明したように、クラスタ構成に応じて分離したプリフィルフェーズとデコーディングフェーズ間の通信を管理することが、重要な設計課題となる。本節ではまず 2 つの配置アルゴリズムを示す。1 つは高速なノード間ネットワークを持つクラスタ向け（§[4.1](#S4.SS1)）、もう 1 つはそのような基盤がない環境向け（§[4.2](#S4.SS2)）で、後者には追加の制約がある。続いて、実ワークロードの特性に適応するオンラインスケジューリング最適化を示す（§[4.3](#S4.SS3)）。

### 4.1 高ノードアフィニティクラスター向け配置

<span id="alg1"></span>

**アルゴリズム 1：高ノードアフィニティ配置アルゴリズム。**

<div class="paper-algorithm">

- **入力：** LLM $G$、インスタンスごとのノード上限 $N$、ノードごとの GPU 数 $M$、GPU メモリ容量 $C$、ワークロード $W$、トラフィックレート $R$。
- **出力：** 配置 $\mathit{best\_plm}$。
- $\mathit{config_p},\mathit{config_d}\leftarrow\emptyset,\emptyset$。
- **各** $\mathit{intra\_op}\in\{1,2,...,M\}$ **について：**
  - **各** $\mathit{inter\_op}\in\{1,2,...,\frac{N\times M}{\mathit{intra\_op}}\}$ **について：**
    - **もし** $\frac{G.\mathit{size}}{\mathit{inter\_op}\times\mathit{intra\_op}}<C$ **ならば：**
      - $\mathit{config}\leftarrow(\mathit{inter\_op},\mathit{intra\_op})$。
      - $\hat{G}\leftarrow\mathrm{parallel}(G,\mathit{config})$。
      - $\mathit{config.goodput}\leftarrow\mathrm{simu\_prefill}(\hat{G},W)$。
      - **もし** $\frac{\mathit{config_p.goodput}}{\mathit{config_p.num\_gpus}}<\frac{\mathit{config.goodput}}{\mathit{config.num\_gpus}}$ **ならば：**
        - $\mathit{config_p}\leftarrow\mathit{config}$。
      - $\mathit{config.goodput}\leftarrow\mathrm{simu\_decode}(\hat{G},W)$。
      - **もし** $\frac{\mathit{config_d.goodput}}{\mathit{config_d.num\_gpus}}<\frac{\mathit{config.goodput}}{\mathit{config.num\_gpus}}$ **ならば：**
        - $\mathit{config_d}\leftarrow\mathit{config}$。
- $n,m\leftarrow\lceil\frac{R}{\mathit{config_p.goodput}}\rceil,\lceil\frac{R}{\mathit{config_d.goodput}}\rceil$。
- $\mathit{best\_plm}\leftarrow(n,\mathit{config_p},m,\mathit{config_d})$。
- **返す：** $\mathit{best\_plm}$。

</div>

InfiniBand を備える高ノードアフィニティクラスタでは、ノード間の KV キャッシュ転送オーバーヘッドを無視できるため、DistServe は任意の 2 ノードへ制約なくプリフィルインスタンスとデコーディングインスタンスを配置できる。このような環境向けに 2 段階の配置アルゴリズムを提案する。まず両インスタンスの並列構成を別々に最適化し、各フェーズの GPU あたりグッドプットを最大化する。次にレプリケーションを使って全体のトラフィックレートに合わせる。

ただし、プリフィルインスタンスのような 1 種類のインスタンスについて最適な並列構成を見つけることも難しい。入力長と出力長が多様で、到着パターンも不規則なワークロードでは、SLO 達成率（TTFT 要件を満たすリクエストの割合）を求める簡単な解析式がないためである。実テストベッドでプロファイリングして SLO を測るには時間がかかりすぎる。そこで、ワークロードの到着過程と入出力長の分布が既知だと仮定し、SLO 達成率を推定するシミュレータを構築する。短い時間間隔は予測できないが、数時間または数日といった長い時間尺度のワークロードパターンは予測できる場合が多い [Li23j, Zha23b]。DistServe は過去のリクエストトレースから分布を当てはめ、その分布から新しいトレースを再サンプリングしてシミュレータの入力ワークロードとし、SLO 達成率を計算する。次に配置を列挙し、二分探索とシミュレーションによって SLO 達成目標を満たす最大レートを求める。

[アルゴリズム 1](#alg1) にこの手順を示す。クラスタ容量の制約内で、プリフィルインスタンスとデコーディングインスタンスの実行可能な並列構成をすべて列挙する。例えば、特定のプリフィルフェーズ構成を `simu_prefill` でシミュレートし、二分探索によって最大グッドプットを求める。デコーディングには同様に `simu_decode` を使う。両インスタンスの最適な並列構成を決めた後、それぞれのグッドプットに従って複製し、ユーザーが要求する全体のトラフィックレートを満たす。

[アルゴリズム 1](#alg1) の計算量は $O(\mathrm{NM}^{2})$ である。$N$ はインスタンスあたりのノード上限、$M$ は現代のクラスタにおける一般的なノードあたり GPU 数（例えば 8）を表す。探索空間は扱える大きさであり、§[6.5](#S6.SS5) に示すように、最大の設定でも求解時間は 1.3 分未満である。

**シミュレータの構築。** [アルゴリズム 1](#alg1) は、ワークロードと並列計画が与えられたとき、さまざまな SLO と SLO 達成目標におけるグッドプットをシミュレータで推定する。正確なシミュレータを作るため、プリフィルフェーズとデコーディングフェーズについて FLOPs とメモリアクセス数をそれぞれ分析し、レイテンシモデルで推論の実行時間を近似する。詳細は付録 [A](#A1) に示す。DNN ワークロード [Guj20, Li23j] は予測可能性が高いため、シミュレータは実際のプロファイリング結果とよく一致する。この点は §[6.4](#S6.SS4) で検証する。

ここまでは、クラスタ内の任意の 2 ノード間（または同一ノード上）にプリフィルとデコーディングのインスタンスを配置でき、KV キャッシュ転送に高帯域ネットワークを使えると仮定して [アルゴリズム 1](#alg1) を設計した。しかし実際のクラスタの多くでは、ノード内の GPU は高帯域な NVLINK を使える一方、異なるノードに分散した GPU 間の帯域幅は限られる。次に、この制約を扱うアルゴリズムを示す。

### 4.2 低ノード親和性クラスタの配置

単純な方法は、プリフィルインスタンスとデコーディングインスタンスを常に同じノードに併置し、GPU ノード内で一般に利用できる NVLINK を使うことである。しかし 175B パラメータ（350GB）のような大規模モデルでは、8 GPU ノードにプリフィルとデコーディングのインスタンスを 1 組も置けない場合がある（$80G\times 8=640G<350\times 2\mathrm{GB}$）。これを追加の配置制約として組み込み、モデル並列化と共同で最適化する。[アルゴリズム 2](#alg2) にその方法を示す。

重要なのは、中間状態の転送がプリフィルインスタンスとデコーディングインスタンスの対応するレイヤー間だけで起こる点である。演算子間並列を使ってレイヤーをステージにまとめ、各インスタンスを*インスタンスセグメント*と呼ぶ区間へ分割し、各セグメントに特定の演算子間並列ステージを持たせる。同じステージのプリフィルセグメントとデコーディングセグメントを 1 ノード内に配置すれば、中間状態の転送を NVLINK 経由だけに制限できる。ノード内では、同じインスタンスのセグメントに同じ並列方式とリソース割り当てを設定する。ノードあたり GPU 数は通常 8 台に限られるため、1 ノード内の構成を列挙し、シミュレータでグッドプットが最大となる構成を特定できる。

[アルゴリズム 2](#alg2) に示すように、まず演算子間並列度を列挙して、可能なインスタンスセグメントをすべて求める。各セグメントについて `get_intra_node_configs` を呼び出し、ノード内で可能な構成をすべて取得する。次にシミュレーションで最適な構成を見つけ、それを複製して目標トラフィックレートを満たす。

### 4.3 オンラインスケジューリング

<span id="figure-06"></span>

![キャプションを参照](../../papers/distserve/figure-06.png)

**図 6.** DistServe ランタイムシステムのアーキテクチャ

DistServe のランタイムアーキテクチャを [図 6](#figure-06) に示す。DistServe は単純な FCFS (先着順) スケジューリングポリシーで動作する。すべてのリクエストは集中コントローラに到着し、プリフィル処理ではキューが最も短いプリフィルインスタンスへ、その後のデコーディング処理では負荷が最も小さいデコーディングインスタンスへ送られる。この構成は単純だが、実ワークロードの特性に合わせていくつかの最適化を加えている。

**パイプラインバブルの削減。** 不均一なプロンプト長によるパイプラインバブル（§[3.3](#S3.SS3)）を抑えるため、パイプライン内の各バッチの実行時間が釣り合うようリクエストをスケジュールする。プリフィルとデコーディングのどちらでも、バッチ内の新しいトークン数は実行時間のよい指標となる。プリフィルインスタンスでは対象モデルと GPU をプロファイルし、GPU を飽和させる最短のプロンプト長 $L_{m}$ を求める。$L_{m}$ より短いリクエストを複数まとめるか、$L_{m}$ より長いリクエストを個別に処理して、プリフィルバッチの合計シーケンス長を $L_{m}$ に近づける。デコーディングインスタンスでは、$L_{m}$ を最大バッチサイズとする。

**バースト性への対処。** ワークロードがバーストすると、プリフィルからデコーディングインスタンスへ大量の KV キャッシュが転送され、デコーディング側のメモリが過負荷になるおそれがある。これを避けるため、DistServe は KV キャッシュを「プッシュ」するのではなく「プル」する。デコーディングインスタンスが*必要に応じて*プリフィルインスタンスから KV キャッシュを取得し、プリフィルインスタンスの GPU メモリを待ち行列バッファとして使う。プリフィルインスタンスはプロンプト処理後も KV キャッシュを GPU メモリに残すだけで、別のプリフィルジョブを続けられる。したがって、2 種類のインスタンスは複雑な協調なしにそれぞれのペースで動作できる。

**再計画。** DistServe のリソースと並列計画は特定のワークロードパターン向けに最適化されるため、パターンが時間とともに変わると最適でなくなる場合がある。そこで定期的に再計画する。ワークロードプロファイラは、リクエストの平均入出力長や平均到着率などを監視する。大きな変化を検出すると、直近の履歴データに基づいて配置アルゴリズムを再実行する。この処理は速く、提案アルゴリズムは数秒で実行でき（§[6.5](#S6.SS5)）、LLM 重みの再読み込みも数分で完了する。実ワークロードの変化は通常時間単位で起こるため、十分に短い。

**プリエンプションとフォールトトレランス。** DistServe はプリエンプション [Han22a] やフォールトトレランス [Zha21c] といった高度なランタイムポリシーを実装していない。これらは分離を補完するため、DistServe へどう組み込めるかを述べる。FCFS ポリシーでは、長いリクエストがプリフィル段階で短いリクエストを遮る「コンボイ効果」が起こりうる。先行研究 [Wu23b] が示すように、プリエンプションを導入すれば効率を高められ、本システムのアーキテクチャでも実装できる。フォールトトレランスは現時点の主題ではないが、考慮が必要である。従来のコロケーション型またはレプリケーション型システムでは、1 インスタンスの障害が他のレプリカを妨げることは通常ない。一方 DistServe では、プリフィルとデコーディングインスタンスの依存関係から障害が伝播する可能性がある。例えば、複数のプリフィルインスタンスに対応する 1 つのデコーディングインスタンスが故障すると、サービスとクラスタ全体が停止しかねない。どちらも今後の課題とする。

## 5 実装

DistServe は、配置アルゴリズムモジュール、RESTful API フロントエンド、オーケストレーション層、並列実行エンジンからなる、LLM 向けのエンドツーエンド分散サービングシステムである。アルゴリズムモジュール、フロントエンド、オーケストレーション層は 6.5K 行の Python コードで実装している。並列実行エンジンは 8.1K 行の C++/CUDA コードで実装している。

配置アルゴリズムモジュールは、§[4](#S4) のアルゴリズムとシミュレータを実装し、モデルとクラスタの設定に応じた配置を決定する。フロントエンドは OpenAI API 互換インターフェースを備え、クライアントは最大出力長や temperature などのサンプリングパラメータを指定できる。オーケストレーション層はプリフィルとデコーディングのインスタンスを管理し、リクエストのディスパッチ、KV キャッシュ転送、結果の配信を担う。ノード間 GPU 通信には NCCL [Ncc23]、ノード内通信には非同期 CudaMemcpy を使い、転送中に GPU 計算がブロックされないようにする。各インスタンスは並列実行エンジンで動作する。このエンジンは Ray [Mor18] actor で GPU worker を実装し、LLM 推論と KV キャッシュ管理を分散実行する。連続バッチ処理 [Yu22a]、FlashAttention [Dao22c]、PagedAttention [Kwo23] などの最適化を統合し、OPT [Zha22a] や LLaMA [Tou23d] などのオープンソース LLM をサポートする。

### 6.1 実験設定

**クラスタテストベッド。** DistServe を 4 ノード、32 GPU のクラスタにデプロイする。各ノードには、NVLINK で接続された NVIDIA SXM A100-80GB GPU が 8 台ある。ノード間帯域幅は 25Gbps である。ノード間帯域幅が限られるため、シミュレーションを用いるアブレーション実験（§[6.4](#S6.SS4)）を除く大半の実験では、DistServe に低ノードアフィニティ配置アルゴリズム（[アルゴリズム 2](#alg2)）を用いる。

**モデルとワークロードの設定。** 先行する LLM サービング研究 [Kwo23] と同様に、学術界と産業界で広く使われる代表的な LLM ファミリである OPT [Zha22a] シリーズを選ぶ。新しい GPT モデルファミリでは、GQA [Ain23] や MQA [Sha19] のようなメモリ効率のよいアテンション機構が採用されつつある。これらのモデルでは KV キャッシュが小さくなり転送オーバーヘッドも減るため、DistServe の性能はさらに向上する。転送オーバーヘッドへ十分な負荷をかけるため、従来の MHA [Vas17] を用いる OPT を選んだ。すべての実験で FP16 精度を用いる。ワークロードについては、[表 1](#table-01) に示す 3 種類の典型的な LLM アプリケーションを選び、各アプリケーションに利用可能な SLO 設定がないため、サービス目標に基づいて経験的に SLO を定めた。各アプリケーションには適切なデータセットを選び、そこから評価用のリクエストをサンプリングする。いずれのデータセットにもタイムスタンプがないため、異なるリクエストレートのポアソン分布から到着時刻を生成する。紙面の制約上、チャットボットのワークロードは 3 種類すべての OPT モデルで評価し、残る 2 種類は近年のオープンソース LLM シリーズ [Tou23d] で最大のサイズに相当する OPT-66B で評価する。

- **チャットボット** [Sch22]：チャットボットには、ユーザーが共有した ChatGPT との会話を収録した ShareGPT データセット [Sha23b] を用いる。OPT-13B の TTFT SLO は応答性を考慮して 0.25 秒、TPOT SLO は通常の人間の読書速度より速い 0.1 秒に設定する。OPT-66B と OPT-175B では、モデル実行レイテンシの増加に応じて 2 つの SLO を少し緩める。
- **コード補完** [Che21]：コード補完には HumanEval データセット [Che21] を用いる。このデータセットには関数シグネチャまたは docstring を伴う 164 件のプログラミング問題があり、コード補完モデルの性能評価に使われる。コード補完モデルは個人向けのリアルタイムコーディング支援として使われるため、両方の SLO を厳しく設定する。
- **要約** [Sum23]：長い記事、エッセイ、学術論文などから簡潔な要約を生成する一般的な LLM タスクである。要約タスクを含む LongBench データセット [Bai23a] を用いる [+longbench]。[図 7](#figure-07) に示すように、LongBench の入力長は他の 2 つのデータセットよりはるかに長い。そのため、TTFT SLO は緩く、TPOT は厳しく設定する。

**評価指標。** 主な評価指標には *SLO 達成率*を用いる。特定の SLO 達成目標（例えば 90%）に対し、GPU あたりの最大グッドプットと、システムが扱える最も厳しい SLO の 2 点に注目する。特に SLO 達成率 90%（すべての曲線図に縦線で表示）を重視するが、リクエストレートとレイテンシ要件も変化させ、SLO 達成率の変化を調べる。さらに、より厳しい SLO 達成目標におけるシステム性能を示すため、達成率 99% の結果も付録に掲載する。

**ベースライン。** DistServe を次の 2 つのベースラインシステムと比較する。

- **vLLM [Kwo23]：** vLLM は学術界と産業界で広く使われる代表的な LLM サービングシステムである。スループットを高める*連続バッチ処理* [Yu22a] と、KV キャッシュ割り当て時のメモリ断片化を抑える *PagedAttention* [Kwo23] をサポートする。しかし、全体のスループットを最大化するためにプリフィルとデコーディングの計算をコロケーションするため、レイテンシ要件を低コストで満たすことが難しい。vLLM は演算子内並列化しかサポートしないため、先行研究 [Kwo23] に従い、3 つの OPT モデルの演算子内並列度をそれぞれ 1、4、8 に設定する。
- **DeepSpeed-MII [Dee23]：** DeepSpeed Model Implementations for Inference（MII）は、長いプロンプトを小さなチャンクに分け、短いプロンプトと組み合わせて目標トークン予算をちょうど満たす*チャンク化プリフィル*をサポートする。長いプリフィルジョブによるプリフィル・デコーディング干渉を緩和できるが、完全には除去できない。公平に比較するため、OPT-13B と OPT-66B の演算子内並列度を vLLM と同じに設定する。ただし、DeepSpeed-MII の基盤カーネルは $\mathit{vocab\_size}/\mathit{intra\_op}$ が 8 の倍数であることを要求するため、$\mathit{vocab\_size}=50272$ の OPT-175B を処理できない。演算子内並列度 8 ではこの条件を満たさず、4 にすれば条件は満たせるものの、メモリ不足になる。

### 6.2 エンドツーエンド実験

本節では、実アプリケーションのデータセットを用いて、DistServe とベースラインのエンドツーエンド性能を比較する。

**チャットボット。** 3 種類すべての OPT モデルで、チャットボットアプリケーションにおける DistServe の性能を評価する。[図 8](#figure-08) の 1 行目に示すように、リクエストレートを徐々に上げるとレイテンシ要件に違反するリクエストが増え、SLO 達成率が低下する。縦線は、90% を超えるリクエストでレイテンシ要件を満たせる GPU あたりの最大リクエストレートを示す。

ShareGPT データセットでは、DistServe は vLLM より $2.0\times$-$4.6\times$ 高いリクエストレートを維持できる。これは、DistServe が分離によってプリフィルとデコーディングの干渉を除去するためである。2 つのフェーズは別々のリソースを割り当て、各フェーズに適した並列化戦略を使って、それぞれの目標を最適化できる。具体的には、175B モデルに選ばれた配置戦略 [+3] を調べると、プリフィルインスタンスは inter-op = 3、intra-op = 3、デコーディングインスタンスは inter-op = 3、intra-op = 4 である。この配置により、DistServe は ShareGPT 上で 2 種類のインスタンス間の負荷をバランスさせ、最小コストでレイテンシ要件を満たせる。この自明でない配置戦略を手作業で見つけることは難しく、アルゴリズムの有効性を示している。vLLM では、プリフィルとデコーディングをコロケーションするとデコーディングフェーズが大きく遅くなり、TPOT が著しく増加する。チャットボットの TPOT 要件は厳しいため、ほとんどのリクエストが TTFT SLO を満たしていても、多数のリクエストが TPOT SLO に違反し、全体の SLO 達成率を下げる。DeepSpeed-MII と比べると、DistServe は $1.6\times$-$7.4\times$ 高いリクエストレートを維持できる。DeepSpeed-MII は、モデルが大きいほどプリフィルジョブも大きくなり、チャンク化プリフィルで干渉をある程度緩和できるため、大規模モデルでの性能が高い。しかし §[2.3](#S2.SS3) で述べた理由により、チャンク化プリフィルは完全なプリフィルより遅く、TPOT を改善する代わりに TTFT SLO を満たしにくい。

[図 8](#figure-08) の 2 行目は、2 つのシステムがレイテンシ要件の変化にどれだけ頑健かを示す。リクエストレートを固定し、*SLO Scale* というパラメータで [表 1](#table-01) の 2 つのレイテンシ要件を同時に線形スケーリングする。SLO Scale が小さいほど、レイテンシ要件は厳しい。達成目標を維持しながらシステムが耐えられる、最も厳しい SLO Scale を調べる。[図 8](#figure-08) に示すように、DistServe は vLLM より $1.8\times$-$3.2\times$、DeepSpeed-MII より $1.7\times$-$1.8\times$ 厳しい SLO を達成でき、ユーザーにより応答性の高いサービスを提供できる。

**コード補完。** [図 9](#figure-09)(a) は、OPT-66B をサービングするコード補完タスクでの DistServe の性能を示す。DistServe は vLLM より $5.7\times$ 高いリクエストレートと $1.4\times$ 厳しい SLO を維持できる。DeepSpeed-MII と比べると、$1.6\times$ 高いリクエストレートと $1.4\times$ 厳しい SLO を維持できる。リアルタイムのコーディング支援であるコード補完は、チャットボットより低い TTFT を必要とするため、どのシステムも最終的に TTFT 要件に制約される。DistServe はデコーディングジョブの干渉を除去し、探索アルゴリズムによってプリフィルインスタンスの演算子内並列度を自動的に高めるため、プリフィルジョブの平均レイテンシが下がり、より多くのリクエストが TTFT 要件を満たす。

**要約。** [図 9](#figure-09)(b) は、OPT-66B をサービングする要約タスクでの DistServe の性能を示す。DistServe は vLLM より $4.3\times$ 高いリクエストレートと $12.6\times$ 厳しい SLO を達成する。DeepSpeed-MII と比べると、$1.8\times$ 高いリクエストレートと $2.6\times$ 厳しい SLO を達成する。LongBench からサンプリングしたリクエストは入力長が長く、プリフィル計算に大きな負荷をかける。一方、要約タスクの TTFT 要件は緩いため、TPOT のサービス品質が特に重要になる。vLLM はプリフィルとデコーディングをコロケーションするため、長いプリフィルジョブがあるとデコーディングフェーズが大きく遅くなり、TPOT 要件を満たせない。

以上はすべて SLO 達成目標 90% での結果である。より厳しい達成目標（例えば 99%）では、DistServe の相対性能がさらに高くなることを確認した。結果は付録 [C](#A3) に示す。

### 6.4 アブレーション研究

DistServe の 2 つの主要な工夫、分離と配置探索アルゴリズムの有効性を調べる。§[6.2](#S6.SS2) では、vLLM の原論文 [Kwo23] に従ってデフォルトの並列設定を選ぶ。ここでは、異なる並列戦略を列挙して最良のものを選ぶ「vLLM++」を実装する。DistServe については、アルゴリズム [2](#alg2) が見つけた配置 (DistServe-Low) と、探索制約が少なく高いノード間帯域幅を仮定するアルゴリズム [1](#alg1) の配置 (DistServe-High) を比較する。vLLM は演算子間並列をサポートせず、物理テストベッドにも高いノード間帯域幅がないため、この実験にはシミュレーションを使う。

**シミュレーターの精度。** DNN モデルの実行は、並列設定下でも高い予測可能性を持つ [Guj20, Li23j, Zhe22]。 [表 2](#table-02) ではシミュレーターの精度を調べる。「vLLM」と「DistServe-Low」について、異なるレートでシミュレーターが報告する SLO 達成率とテストベッドでの実測値を比較する。すべてのケースで誤差は 2% 未満であり、シミュレーターの精度を確認できる。

**結果。** [図 11](#figure-11) は ShareGPT データセットで OPT-66B をサービングした 4 システムの性能を示す。「vLLM++」は「vLLM」と同じ性能だった。デフォルトの並列設定 (intra-op=4) が GPU あたりグッドプットで最良だったためである。これは分離の有効性をさらに示す。プリフィルとデコーディングの干渉は、並列度の調整による性能向上の余地を大きく削る。対照的に、「DistLLM-High」は「DistLLM-Low」より改善できる。プリフィルとデコーディングインスタンスが同じモデルステージを共有するという配置制約を受けないためである。分離により、プリフィルとデコーディングに適した並列戦略を使い、結合の影響なしにそれぞれの目標を最適化できる。

### 6.5 アルゴリズム実行時間

[図 12](#figure-12) は、96 コアの AWS m5d.metal インスタンス上で、単一インスタンスに割り当てる GPU 数（$N\times M$）を増やしたときの [アルゴリズム 1](#alg1)（DistServe-Low）と [アルゴリズム 2](#alg2)（DistServe-High）の実行時間を示す。結果から、DistServe は GPU 数に対してよくスケールし、モデルサイズには依存しないことがわかる。シミュレータが離散イベントだけを扱うため、モデルの大きさにかかわらず実行時間が同じだからである。また、異なる並列化戦略の探索は互いに独立しているため、どちらのアルゴリズムも高い並列性を持ち、CPU コア数を増やすと実行時間がほぼ線形に短縮する。

GPU 数が増えると、「Dist-Low」の実行時間は「Dist-High」より長くなる。「Dist-High」ではプリフィルインスタンスとデコーディングインスタンスの並列化戦略を独立に探索でき、並列化できるためである。一方「Dist-Low」では配置に追加制約があるため、両インスタンスについてノード内並列の組み合わせをすべて列挙する必要がある。それでもアルゴリズムの実行時間は数分であり、再デプロイの前に 1 度実行するだけなので、このオーバーヘッドは許容できる。

## 7 議論

本論文では、大規模 LLM サービングにおいてグッドプットを最適化する設定に焦点を当て、DistServe を提案した。LLM は、最適化目標やリソース制約が異なるさまざまなサービスで利用・導入されているため、あらゆる LLM サービングの課題を一つの手法で解決することはほぼ不可能である。本節では、DistServe の長所と短所、および別のシナリオでより適した手法について議論する。

**スループットを最適化するシナリオ。** レイテンシを重視しないオフラインアプリケーションでは、ユーザーが応答時間に求める条件は一般に緩い [She23]。この場合、サービングシステムはグッドプットではなく全体のスループット最大化に重点を移せるため、DistServe の効果が小さくなる可能性がある。各バッチを計算バウンドになるしきい値まで満たし、反復ごとの GPU 利用率を高く保てることから、デコーディングを相乗りさせるチャンク化プリフィル [Agr23, Dee23] などの手法が適している場合がある。

**リソースが制約されたシナリオ。** 小規模企業や個人研究者には、LLM を大規模クラスタへ導入するためのリソースが不足しがちである [She23, Son23]。数台、あるいは 1 台の GPU しかない環境では、DistServe の設計空間が大きく制限されるため、並列化戦略やリソース割り当てを調整してサービング性能を高めることが難しく、調整できない場合もある。この場合、vLLM や DeepSpeed-MII のような非分離型システム [Kwo23, Dee23] のほうが、デプロイの複雑さを抑えて運用効率を高められる可能性がある。

**長いコンテキストのシナリオ。** Claude-3 [Ant24]、Gemini-1.5 [Goo24a]、Large World Model（LWM）[Liu24l] など、100 万トークンのコンテキストウィンドウを持つ GPT モデルが増えている。このようなシナリオでは、KV キャッシュがプロンプト長に比例して大きくなるため、転送オーバーヘッドも増加する。ただし、プリフィル計算量は二次関数的に増えるため、プリフィルジョブに対する転送時間の相対的な割合は低下する。また、コンテキストが長くなるほどプリフィルとデコーディングの計算需要の差が広がり、両者の干渉が強くなる。したがって、DistServe が提案する分離手法は、長いコンテキストのサービングでも有望である。

## 8 関連研究

**推論サービング。** 近年、推論サービングについて多くの研究が行われている。TorchServe [Ser23] や NVIDIA Triton [Nvi19b] のような汎用の本番システムから、Transformer ベースの LLM に特化したシステム [Li23j, Yu22a, Agr23, Wu23b, Fan21, Nvi19a, Zho22, Su23] まで幅広い。Orca [Yu22a] は、スループットを高めるために連続バッチ処理を導入した。vLLM [Kwo23] は、KV キャッシュを細粒度で管理する PagedAttention を提案した。SARATHI [Agr23] はプリフィル要求をチャンクに分割し、デコーディング要求を相乗りさせてハードウェア利用率を高める。FastServe [Wu23b] は、長いジョブによるキューイング遅延を抑えるため、反復単位のプリエンプティブスケジューリングを実装した。しかし、いずれもプリフィルとデコーディングをコロケーションして処理するため、深刻な干渉が生じる。同時期の Splitwise [Pat23]、TetriInfer [Hu24b]、DéjàVu [Str24] も、同様の分離手法で LLM 推論を最適化しており、この手法の有効性を裏付けている。DistServe は、グッドプット最適化のシナリオをより重視し、ネットワーク帯域幅を詳しく検討する点で異なる。

**グッドプット最適化システム。** DL アプリケーションでは、グッドプット最適化が盛んに研究されている。Pollux [Qia21] はジョブのリソースを動的に調整し、DL クラスタのスケジューリング性能とクラスタ全体のグッドプットを高める。Sia [Sub23] は異種性を考慮したスケジューリングにより、クラスタリソースを弾力的でリソース適応型のジョブへ効率よく割り当てる。Clockwork [Guj20] と Shepherd [Zha23b] は、レイテンシを考慮したスケジューリングとプリエンプションによってサービングのグッドプットを高めるが、従来の小規模モデルのみを対象とする。AlpaServe [Li23j] は LLM を対象とし、モデル並列化によって GPU 実行を統計多重化してリソース利用率を高めるが、非自己回帰生成しか扱わない。DistServe は、自己回帰 LLM 推論のグッドプットを最適化する最初の研究である。

**リソース分離。** リソース分離型システム [Sha18b, Guo23d, Com23a] は、従来のモノリシックなサーバー基盤からハードウェアリソースを切り離し、独立して管理するリソースプールに分ける。これにより、柔軟で効率的かつスケーラブルなデプロイが可能になり、リソース利用率も高まる。高速なネットワーク帯域幅と異種ハードウェアを備えた、真に分離されたデータセンターは多くのアプリケーションに有益である [Zha23a, Aud22, Jin24]。DistServe もシステムコンポーネントを分離し、リソースを独立して拡縮・管理できるようにする。

**学習のためのモデル並列化。** DistServe は、学習時のモデル並列化に関する多くの研究 [Zhe22, Sho20, Hua19b, Raj20a, Nar19] と直交する。§[3.3](#S3.SS3) で述べたように、推論サービングのワークロードには学習環境にはない特性がある。これらのシステムと DistServe が交わるのは、さまざまな次元でモデル並列化を実装する方法である。DistServe は新しい並列化最適化を配置探索アルゴリズムに組み込める。

## 9 結論

本論文では、プリフィルとデコーディングの計算を分離する新しい LLM サービングアーキテクチャ DistServe を提案した。DistServe は GPU あたりのグッドプット、すなわち割り当てた各 GPU について SLO 達成目標を満たしながら処理できる最大リクエストレートを最大化する。その結果、SLO の達成を保証しつつ、LLM クエリあたりのコストを最大 $7.4\times$ 削減できる。本研究の結果は、LLM サービスにおいてレイテンシの重要性が増すにつれ、プリフィルとデコーディングの分離が性能とサービス品質保証の改善に有望な戦略となることを示している。

## 付録A LLM推論のレイテンシモデル

異なる配置戦略のグッドプットを正確にシミュレートするため、LLM 推論におけるプリフィルフェーズとデコーディングフェーズの実行時間を予測する解析モデルを使う。

現代の LLM サービングシステム [Nvi19a, Kwo23, Wu23b] では、Softmax や LayerNorm のようなメモリバウンドの演算を効率化のために行列乗算カーネルへ融合することが多い。そのため GEMM が全体のレイテンシを支配し、分析では主に GEMM に焦点を当てる。

### A.1 記号の定義

以下はモデルアーキテクチャに関する記号である。

- $h$: 隠れサイズ
- $n$: ヘッド数
- $s$: ヘッドサイズ ($h=n\cdot s$)
- $m$: FFN の中間サイズ

注: テンソル並列を使う場合、$h$、$n$、$m$ はテンソル並列度で割る。

以下は実行するバッチを表す記号である。

- $B$: バッチサイズ
- $l_{0},l_{1},\dots,l_{B-1}$: バッチ内の各リクエストの入力長
- $t$: バッチ内のトークン数 ($t=\sum_{i=0}^{B-1}l_{i}$)
- $t_{2}$: 入力長の二乗和 ($t_{2}=\sum_{i=0}^{B-1}l_{i}^{2}$)
- $b$: アテンションカーネルのブロックサイズ。このパラメータは FlashAttention [Dao22c] で使う。これは現在の LLM サービングシステムで採用されている一般的なカーネル最適化手法である。

T_{1}=C_{1}\cdot(4th^{2}+2thm)
$$

次に、FlashAttention [Dao22c] で最適化したプリフィルのアテンション演算を取り上げる。アテンションは同じリクエスト内のトークン間だけで計算するため、現在の実装では同じバッチ内のリクエストごとにアテンションカーネルを起動する。1 つのアテンションヘッドと $l$ トークンのリクエストについて、このカーネルは合計 $2sl+3sl\cdot(l/b)\approx 3sl\cdot(l/b)$ 回のメモリ読み書きと、$2sl^{2}+sl(l/b)\approx 2sl^{2}$ FLOPs を実行する。したがって AI は $b=16$ のとき $2b/3=10.677$、$b=32$ のとき $21.333$ となり、A100 GPU ではメモリバウンドの演算である。よって、全リクエストと全ヘッドを含むアテンション層全体のレイテンシは次のようにモデル化できる。

$$
T_{2}=C_{2}\cdot n\cdot\sum_{i=0}^{B-1}\frac{3sl_{i}^{2}}{b}=C_{2}\cdot\frac{3nst_{2}}{b}=C_{2}\cdot\frac{3ht_{2}}{b}
$$

全体として、プリフィルフェーズのレイテンシは次のようにモデル化できる。

$$
T_{\mathrm{Prefill}}=C_{1}\cdot(4th^{2}+2thm)+C_{2}\cdot\frac{3ht_{2}}{b}+C_{3}
$$

$C_{3}$ は Python ランタイムやシステムノイズなど、その他のオーバーヘッドを表す。$C_{1}$、$C_{2}$、$C_{3}$ の値はプロファイリングと補間によって求める。

![論文の表 4](../../papers/distserve/table-04.png)

**表 4.**

これらの演算の AI は $O(B)$ である。$B$ は GPU メモリ容量と厳しいレイテンシ要件によって制限されるため、既存のサービング環境ではメモリバウンドとなる。総メモリ読み書き量は $8Bh+4h^{2}+2hm+2Bm$ であり、$h$ と $m$ は通常 $B$ よりかなり大きいため、レイテンシは次のようにモデル化できる。

$$
T_{3}=C_{4}\cdot(4h^{2}+2hm)
$$

デコーディングのアテンション演算では、1 つのアテンションヘッドと $l$ 個の生成済みトークンを持つリクエストについて、$3sl$ 回のメモリ読み書きと $2sl$ FLOPs を実行する。メモリバウンドの演算であるため、デコーディングアテンションのレイテンシは次のようにモデル化できる。

$$
T_{4}=C_{5}\cdot n\cdot 3s\sum_{i=0}^{B-1}l_{i}=C_{5}\cdot 3ht
$$

以上より、デコーディングフェーズのレイテンシは次のようになる。

$$
T_{\mathrm{Decoding}}=C_{4}\cdot(4h^{2}+2hm)+C_{5}\cdot 3ht
$$

ここでは、プロファイリング段階の $C_{3}$ に相当するオーバーヘッド項を導入しない。$4h^{2}+2hm$ がすでに定数であり、オーバーヘッドを $C_{4}$ に含められるためである。同様に、$C_{4}$ と $C_{5}$ の値はプロファイリングと補間によって求める。
