## 要旨

本稿では、ハイブリッド・スライディングウィンドウ・アテンション（Hybrid SWA）、疎な Mixture-of-Experts（MoE）、およびマルチモーダルエンコーダを組み合わせた MiMo-V2.5 モデルファミリーに対する、推論パイプライン全体の最適化を提示する。Hybrid SWA は、理想的には Full Attention と比べてアテンションの計算量と KVCache の保存量をともに大幅に削減できるが、その効果を本番環境で実現するには相当なエンジニアリングが必要となる。そこで、レイヤー単位のプリフェッチ、SWA 対応のプレフィックスキャッシュ木、専用の配置戦略によって KVCache システムを体系的に最適化し、SWA の保存量を厳密に $O(W)$ に抑えながら高いキャッシュヒット率を達成した。さらに、RDMA 向けにネットワークを最適化した高性能分散キャッシュ基盤 GCache を構築し、負荷分散を維持したまま計算量を削減する KVCache 親和性ルータを開発した。GPU 画像前処理、並列動画デコード、マルチモーダルキャッシュ共有など、マルチモーダル入力についても最適化している。これらの最適化により、Hybrid SWA + MoE + マルチモーダルという複合アーキテクチャを効率よく扱う、初の大規模な本番 LLM サービングシステムが実現した。

## 1 はじめに

MiMo-V2.5 [Mim26a] と MiMo-V2.5-Pro [Mim26] を含む MiMo-V2.5 モデルファミリーは、複数のアーキテクチャ設計を組み合わせている。Hybrid Sliding Window Attention（Hybrid SWA）は KVCache の保存量を Full Attention の約 1/7 に圧縮し、疎な MoE の活性化はモデル容量を保ったままトークン当たりの計算量を削減し、マルチモーダルエンコーダは視覚・音声・動画にまたがるクロスモーダル理解を可能にする。これらの特性により、MiMo-V2.5 シリーズは長いコンテキストとマルチモーダルの場面で、性能と効率の両面に大きな可能性を持つ。

当初から目標は明確だった。長いコンテキストの推論に対して、強力かつ効率的なモデルを学習することである。この二つの目標は本質的に相反する。高度な推論には長距離依存関係のモデル化が必要であり、通常はより大規模なアテンション計算と大きな KVCache オーバーヘッドを伴う。従来の Full Attention アーキテクチャでは、アテンションの計算量と KVCache の保存量がコンテキスト長に応じて急増し、長いコンテキストの学習と推論には非常に大きなコストがかかる。Hybrid SWA は、各レイヤーで局所的な Sliding Window Attention（SWA）と大域的な Full Attention を交互に用いる。大半のレイヤーは局所窓内だけでアテンションを計算し、少数の重要なレイヤーが大域的な視野を維持する。理論上、この構造は長距離依存関係をモデル化する能力を保ちながら、アテンションの複雑度をほぼ線形まで削減する。

しかし、理論上のアーキテクチャ上の利点が、そのまま本番環境の効率になるわけではない。Hybrid SWA では、KVCache のヒット率管理、プレフィックス照合、Full Attention レイヤーと SWA レイヤーの二重の意味的一貫性を保つ処理が新たに複雑になる。実際のシステムにはさらに、多層ストレージ間のデータ移動、非同期プリフェッチとスケジューリングのずれ、分散キャッシュ状態の同期の難しさがあり、理論的な利点を直接得ることはできない。

Hybrid SWA 以外にも、MoE は分散スケジューリングと負荷分散に大きな要求を課し、マルチモーダルエンコーダは大きな画像や長い動画を扱う際のスループット上のボトルネックであり続ける。スケジューリング戦略と Prefill/Decode 実行パイプラインにも慎重な最適化が必要である。本稿では、KVCache 管理、階層キャッシュシステム、SWA 対応プレフィックスキャッシュ木、スケジューリング戦略、Prefill/Decode 実行パイプライン、マルチモーダル最適化を含む、MiMo-V2.5 シリーズ推論システムのエンドツーエンドなエンジニアリング実践を示し、本番環境でアーキテクチャ、特に Hybrid SWA の理論的な効率を体系的に実現する。

## 2 背景

個々の最適化に入る前に、Hybrid SWA の理論上の効率限界を定量化する。これは設計選択の根拠であり、後続のすべての最適化を評価する基準でもある。

<span id="section-2-1"></span>

### 2.1 計算量の分析

MiMo-V2.5-Pro を例に取ると、モデルは合計 70 レイヤーで、10 の Full Attention レイヤーと 60 の SWA レイヤーを持ち、スライディングウィンドウのサイズは 128 である。Full Attention と比較した Hybrid SWA の計算コストを下図に示す。SWA レイヤーは全レイヤーの 6/7 を占めるため、Hybrid SWA アーキテクチャ全体の計算量は Full Attention の約 1/7 となる。Prefill が主に計算律速となる Chunked Prefill の場面では、これは Prefill コストの比例的な削減に直接つながる。

<span id="section-2-2"></span>

### 2.2 KVCache 保存量の分析

SWA レイヤーは完全な系列ではなく、スライディングウィンドウ内の KV だけを保持すればよいため、KVCache のメモリ使用量も同様に 1/7 近くまで減少する。Decode フェーズは主にメモリ律速であり、そのレイテンシはモデルパラメータと KVCache から読み出す合計バイト数に比例する。長い系列では KVCache の容量がモデルパラメータを大きく上回ることがあるため、KVCache 保存量の削減は、トークン当たりの KV アクセスを減らす疎なアテンションを持つモデルを除き、長い系列での Decode コスト削減にほぼ直接つながる。

<span id="figure-01"></span>

![MiMo-V2.5-Pro における Hybrid SWA の理論効率分析](../../papers/mimo-v2-5-inference/figure-01.png)

**図 1.** MiMo-V2.5-Pro における Hybrid SWA の理論効率分析。アテンションの計算量と KVCache の保存量は、Full Attention と比べていずれも約 $7\times$ 削減される。

KVCache の保存量はモデルアーキテクチャによって大きく異なる。[図 2](#figure-02) では代表的なモデルを、パラメータ数が 500B 未満のモデルと 500B を超えるモデルの二群に分けて比較する。モデル構成は各公式チェックポイントから取得した [Dee26a, Dee26b, Min25, Kim25c, Qwe26, Hy26, Mim26a, Mim26, Zen26]。各群において、MiMo-V2.5 と MiMo-V2.5-Pro の推定 KV cache メモリ要件はそれぞれ 2 番目に小さく、DeepSeek-V4-Flash と DeepSeek-V4-Pro のみがこれらを下回る。

## 3 KVCache システムの再構築

MiMo-V2 と MiMo-V2.5 シリーズは Hybrid SWA アーキテクチャを早期に採用したモデルだったが、当時は主要なオープンソース推論フレームワークにもキャッシュシステムにも、完全な SWA サポートがなかった。MiMo API の公開時には、サービングバックエンドのコードベースとして SGLang v0.5.5 [Zhe24] を選択したが、すぐに深刻な問題に直面した。このバージョンの SGLang の HiCache は SWA をサポートしておらず、より正確には、初期の SWA サポートでは互換性を保つために完全な KVCache を保存していた。SWA を使いやすくするための回避策はいくつか存在したが、我々はより高い性能上限と優れた使い勝手を備えた KVCache システムを構築したいと考えた。

<span id="section-3-1"></span>

### 3.1 SWA KVCache 管理

<span id="section-3-1-1"></span>

#### 3.1.1 KVCache の二重プール設計

Hybrid SWA は根本的な保存上の競合を生む。Full Attention レイヤーは系列全体の KV（$O(N)$）を保存する必要がある一方、SWA レイヤーはスライディングウィンドウ内の KV（$O(W)$）だけを維持すればよい。従来の単一 KV プール設計では、すべてのレイヤーに対して $O(N)$ の GPU メモリを割り当てる必要があり、SWA の窓の疎性を活用できず、実質的にほぼ完全な KVCache 実装へ退化する。

自然な解決策は、KVCache を Full Attention 用と SWA 用の二つの独立したプールに分け、システムレベルでは統一された抽象を提供することである。

- **物理層：** Full KV プールと SWA KV プールを別々に維持する。SWA プールは窓の分だけ確保し、窓に基づく独立した退避をサポートすることで、SWA の保存量を厳密に $O(W)$ に制限する。この仕組みは L2 と L3 のストレージ階層にも適用される。
- **論理層：** 上位層（プレフィックス木、スケジューラ、転送プロトコル）には単一の系列ビューを公開し、Full Attention のインデックスを正本として、透過的な階層ストレージのために Full $\to$ SWA の対応関係を維持する。
- **スケジューリング制約：** リクエストを受け入れる際、Full KV と SWA KV の容量制約をともに検証し、単一の指標だけを調べることによるリソースの誤配分を防ぐ。
- **データ移動：** 階層間の転送は SWA mask だけに基づいて行い、窓内の有効なデータだけを移動して不要な帯域消費を避ける。

この設計により、SWA KVCache はシステムレベルで厳密な $O(W)$ の保存制約を達成し、KVCache 全体の容量効率を **約 $7\times$** 改善して、Hybrid SWA の構造上の利点を引き出す。主要な推論フレームワークも同様の実装方法を採用している。

<span id="section-3-1-2"></span>

#### 3.1.2 レイヤー単位の KVCache プリフェッチ

SWA KVCache の保存を最適化すると、SWA レイヤーがプリフェッチする KVCache はごく少量で済む。これにより、レイヤー単位のスケジューリングを通じて Host-to-Device の KVCache プリフェッチと計算をほぼ完全に重ねることができ、推論中のキャッシュ読み出しコストをほぼゼロにできる。

![レイヤー単位の KVCache プリフェッチ](../../papers/mimo-v2-5-inference/figure-03.png)

**図 3.** レイヤー単位の KVCache プリフェッチ：（a）計算ストリームが KVCache のロードを待って停止する。（b）SWA 対応のレイヤー単位スケジューリングがロードバックと計算を重ねるため、GPU は待機せずに動作する。

<span id="section-3-1-3"></span>

#### 3.1.3 SWA 対応プレフィックスキャッシュ木

従来の RadixAttention のヒット規則は、トークン系列が等しい $\to$ KV が等しいという単純な仮定に基づく。この仮定は Full Attention では成立する。二つのリクエストが同じトークン ID を共有していれば、対応する KV は必ずプールに残っており、そのまま再利用できる。

しかし、この仮定は SWA では崩れる。その理由は、プレフィックス木の論理的なライフサイクルと SWA KV の物理的なライフサイクルが一致しないことにある。プレフィックス木のノード長は SWA の窓に制約されず、ノードの系列長は窓より短いことも、はるかに長いこともあり、ノードはリクエストのマージ、分割、削除によって継続的に変化する。そのため、プレフィックス木のノードが論理的には完全なトークン系列を表していても、対応する SWA KV は末尾部分しか残っていないか、完全に退避されている場合がある。それでもプレフィックス木が「トークンが等しい $\to$ ヒット」という規則に従って再利用長を返すと、スケジューラは末尾の KV が退避済みの擬似ヒットを受け取る可能性があり、後続のアテンション計算は無効または上書きされたスロットを読み、モデルの正確性を直接損なう。

SWA でプレフィックスを正確かつ効率的に再利用するには、プレフィックス木の意味を次の三点で変更する必要がある。

1. **照合規則を「窓安全長」へ更新する：** トークンが等しいだけでなく、末尾の $W$ トークンが SWA プール内に有効なスロットを持っていなければならない。照合長はこの新しい境界までに切り詰められ、それを超える部分はミスとして扱う。これにより、ヒットした区間から取得する KV は常に有効になる。
1. **退避をリクエストのライフサイクルに結び付ける：** 長い Prefill で各 chunk が完了したとき、リクエストが終了したとき、Decode で $N$ トークンを生成するごとに、窓外の SWA を解放する。これにより、長いコンテキストや長い出力を扱うタスクでも、SWA プール使用量は系列長とともに増えるのではなく、$W$ または chunk の規模で一定に保たれる。
1. **ノードに二重インデックスを持たせる：** 各プレフィックス木ノードは、論理順序を決め Full Attention レイヤーの計算に参加する Full Attention 区間インデックスと、窓の安全性を決める SWA 区間の対応関係という二組の情報を記録する。退避は別々に管理する。窓外の SWA 区間だけを退避し、Full Attention 区間を残して Full Attention レイヤーからプレフィックスを再利用可能にすることも、区間全体を退避することもできる。

SWA が KV 容量を 1/7 に圧縮する効果は容量面の利点であり、ヒット率は再利用面の利点である。両者が実際の Prefill 計算コスト曲線を決める。「窓安全長」の照合規則を導入すると、一定のトークン容量に対する素のヒット率はわずかに低下するが、同じ保存容量に収まるトークン数は数倍に増える。**一定の保存容量を基準にすれば、実効ヒット率は大幅に向上する。**

![SWA 対応プレフィックスキャッシュ木](../../papers/mimo-v2-5-inference/figure-04.png)

**図 4.** SWA 対応プレフィックスキャッシュ木：各ノードは、窓サイズを 4 として、トークンごとの Full Attention 状態と SWA 状態を持ち、末尾のどのトークンに有効な SWA スロットが残っているかを追跡する。

<span id="section-3-1-4"></span>

#### 3.1.4 KVCache ヒット率の最適化

HiCache の三階層すべてを SWA 対応に再構築すると、デバイス、ホスト、ストレージバックエンドは、それぞれ「どの位置に有効な SWA があるか」という状態を維持する。しかし、HiCache のデータ移動パイプラインは非同期で、デプロイごとにキャッシュが異なり、セッション間で共有されるプレフィックス長も異なるため、階層間の Full Attention Cache と有効な SWA インデックスは簡単に同期を失う。SWA 対応プレフィックスキャッシュ木の照合規則では、系列が Full Attention Cache にヒットしても SWA Cache にミスすると、照合長が大幅に短縮される。短縮が大きいほど再計算が長くなり、SWA Cache 最適化の効果は低下する。そこで、異なる場面での分散一貫性とキャッシュヒット率を最適化した。

**Device は完全、Host は不足。** 帯域とレイテンシのトレードオフから L3$\to$L2 プリフェッチが末尾区間だけを取得する場合や、L1 プレフィックス木の再編成が L2/L3 へ同期されない場合に起きる。プレフィックス木のノードをマージするときや Prefill の完了時などに Device と Host の SWA 占有量の差分を事前に確認し、Host の SWA プールへ補助スロットを割り当て、Device の SWA KV を D2H 転送で非同期に書き込む。

**Host は完全、Device は不足。** 次の H2D 転送時に自然に整合するため、能動的な修復は不要である。

**高頻度系列の L3 プレフィックス退避。** 長い系列の先頭は高頻度アクセスによって L1/L2 に残り、キャッシュ親和性により同じプレフィックスのリクエストは同じノードへ送られる。L3 Cache は長期間直接アクセスされないため、ストレージの退避ポリシーによって削除されることがあり、全体として高頻度な系列の L3 Cache を早期に解放して、マシン間の再利用を大幅に悪化させる。L1/L2 Cache へアクセスする際に L3 Cache を定期的に問い合わせ、早すぎる退避を防ぐ。

**中・短系列の SWA 保持戦略。** ユーザーのリクエストパターンに基づき、中・短系列では固定長の位置に比較的密な SWA KV Cache を保持する。SWA の密度を上げると KVCache 全体に占める SWA の比率は増えるが、複数ユーザーでシステムプロンプトを共有するような場面には直接的な効果がある。

これらの最適化により、KVCache の容量拡大をより長い実効ヒット長へ変換し、セッションをまたぐ長いプレフィックスの再利用を可能にした。これは長時間のエージェントセッション、複数ユーザーで共有されるシステムプロンプト、同じコードベースに対するツールの反復呼び出しに特に有効である。

<span id="section-3-2"></span>

### 3.2 GCache：高性能分散キャッシュ基盤

GCache は Xiaomi のストレージチームが開発した高性能な汎用キャッシュシステムで、学習と推論を統合したストレージアーキテクチャの重要な構成要素である。初期の学習用途で、ある種のオープンソースキャッシュプロジェクトは分散ファイルシステムを十分に高速化できず、性能を引き出し切れないとストレージチームは判断し、社内向けの解決策の開発を始めた。その後、MiMo 大規模モデルの公開と推論サービスの開始に伴い、GCache をモデル配布用の独立したストレージ製品へ適応させ、推論エンジンの L3 KVCache としても使用した。

GCache はファイルと KV の両方の意味論、メモリ・ディスク・リモート階層にまたがる多段キャッシュ、共有メモリによる永続化と経路全体のゼロコピー、高並行のノンブロッキング IO と RDMA 通信をサポートし、優れたスケーラビリティを保ちながら、上位サービスが求める高スループットと低レイテンシを満たす。

<span id="section-3-2-1"></span>

#### 3.2.1 アーキテクチャ設計

GCache の全体アーキテクチャを[図 5](#figure-05) に示す。GCache には次の主要な特性がある。

1. **分散型メタデータ管理** によりクラスタを制限なく拡張できる。キーのコンシステントハッシュで保存位置を決定する。Master は Raft ベースの高可用構成だが、ハートビートとサービスディスカバリだけを管理し、IO 経路は Master を通らない。
1. **サーバー側でメモリキャッシュとディスクキャッシュの両方をサポートする。** メモリ内のコールドデータはディスクへ退避され、ディスク上のホットデータはメモリへ昇格する。この方式は推論用途に適しており、アクティブなセッションの性能を自動的に保証しつつ、長時間アイドル状態のセッションにかかるコストを抑える。キャッシュエントリは共有メモリへ永続化され、サービスを再起動しても失われない。キャッシュを失うことなく、滑らかなスケールアップとスケールダウンを行える。
1. **専用スレッドを持つ多言語 SDK** がリクエストを分割して配信する。これらのスレッドはユーザースレッドのリソースを消費しない。分割によって並行性を高め、IO サイズを RDMA に適した範囲へ保つ。スレッドは非同期コールバックを使い、単一 KV、バッチ、CUDA stream という柔軟なコールバック粒度を利用できる。

<span id="figure-05"></span>

![GCache のアーキテクチャ](../../papers/mimo-v2-5-inference/figure-05.png)

**図 5.** GCache のアーキテクチャ：SDK は、分割したリクエストをコンシステントハッシュで構成された gcache-server クラスタへ配信する。Raft ベースの Master がサービスディスカバリを担い、オブジェクトストレージ（Ceph/HDFS）がバックエンドとなる。

<span id="section-3-2-2"></span>

#### 3.2.2 ネットワーク最適化

現在の主要な GPU マシンには $8\times$ 400G の高性能 NIC が搭載されている。しかし、Prefill-Decode（PD）分離構成であっても、現在の推論フレームワークはネットワーク帯域を使い切ることが難しく、業界ではコスト削減のため NIC の仕様を下げようという声が上がるほどである。

高速ネットワークを十分に活用するため、GCache は通信にフロントエンド NIC よりも GPU NIC を優先し、NUMA バインドや同一 rail の親和性など、通信モジュールを幅広く最適化している。1MB の IO サイズによるベンチマークでは、単一プロセスの RDMA 読み出しスループットはわずか 280 $\mu$s のレイテンシで 170 GB/s に達する。GDR の場合は HBM 帯域が高いため、単一プロセスのスループットは約 350 GB/s に達し、推論フレームワークの通信要件を十分に満たす。

<span id="section-3-2-3"></span>

#### 3.2.3 ストレージコストの最適化

2026 年には、ストレージコストに対する業界の関心が高まっている。専用のストレージマシンを使う他社とは異なり、GCache は GPU マシンへの同居配置を優先し、Prefill ノードと Decode ノードのメモリの一部、およびマシン内蔵の NVMe SSD を利用することで、追加のストレージコストをゼロにしている。

<span id="section-3-2-4"></span>

#### 3.2.4 信頼性の確保

同居配置のため、GPU マシンの高い故障率が信頼性の課題となる。GCache の公開後、ホストマシンの故障はほぼ毎日起きている。第一に、チームは障害処理ロジックの強化に相当な労力を費やした。第二に、キーはコンシステントハッシュによって完全に分散されるため、事前にセッション ID を論理的な集合へまとめることで、関連するセッションを異なるノードへ分散し、単一ノード障害の影響範囲を抑える。第三に、基盤プラットフォームのハードウェア検出機能を利用し、障害の事前検出と自動データ移行を可能にする。事前に対処できないまれな突然のクラッシュについては、SDK のタイムアウトを短く設定することで、推論フレームワークがミスを速やかに検出して再計算でき、オンライン推論への影響をほぼ回避できる。

これらの対策により、GCache は同居配置でも単一レプリカで保存でき、可用性を保つための複数レプリカによる冗長化を必要としない。これはストレージコストを低く抑えられる重要な理由である。

<span id="section-3-3"></span>

### 3.3 キャッシュヒット率の考察

保存容量の削減と、より安定した大容量の L3 ストレージである GCache を組み合わせた上記の SWA KVCache 最適化により、Cache TTL（Time-To-Live）を大幅に延長し、KV Cache のヒット率を高めることができた。KVCache の退避は、根本的にはストレージ容量の制約から生じる。容量が飽和に近づくと、システムは新しいリクエストの KV Cache を優先して保持し、LRU に類するポリシーで過去にアクセスされたエントリを退避する。その結果、同じコンテキストを数時間後に再利用しても、しばしばミスとなる。SWA の保存容量は小さいため、同じコストで数倍の並行リクエストのキャッシュを保持でき、大容量 L3 によって低コストで利用可能な容量をさらに拡大できる。保存領域が広いほど KVCache の退避圧力は小さくなり、保持時間が長くなる。TTL が長くなると過去のコンテキストがヒットする時間幅が広がり、キャッシュヒット率も上昇する。また、SWA による転送帯域の削減は TTL に直接影響しないものの、階層間のデータ移動コストを大幅に下げ、キャッシュシステム全体の安定した効率的な動作を支える。

モデル公開後、サーバー側を継続的に観測した結果、主要な高品質 harness フレームワークでは **サーバー側 KV Cache のヒット率は平均 93%** であり、継続的に高負荷で利用するヘビーユーザーではさらに高く、95% 以上に達している。今後も SWA の KV Cache 管理ロジックを改善し、より多くの harness フレームワークと harness-inference の協調設計に取り組み、ヒット率の上限をさらに高めていく。

## 4 スケジューリングの最適化

初期の SGLang コミュニティのルータサービスはまだ十分に成熟しておらず、インスタンス間で状態が共有されていなかった。ルータサービスが予期せず停止した場合や、リクエストが別のルータインスタンスへ送られた場合、KVCache のスケジューリング性能は低下した。この問題を解決し、大規模クラスタ配置で高可用性を確保するため、Xiaomi は Redis を集中ストレージとして使用する、動的に拡張可能なステートレススケジューラ LLM-Router を開発した。これにより単一サービスの障害後も KVCache の性能低下を防ぎ、キャッシュヒット率を安定して保証できる。

<span id="section-4-1"></span>

### 4.1 KVCache と負荷親和性スケジューリング

HiCache は L2 ヒット率に非常に敏感である。L2 cache がミスすると、システムは L3 から KVCache を検索して取得し、その完了を待ってから推論を開始しなければならない。ルータ側で L2 ヒット率を高めれば、不要な同期待ちを減らし、スループットを直接向上できる。

ルータは、配信済みリクエストを Radix プレフィックス木で維持することにより、KVCache 親和性スケジューリングを実装する。複数の Prefill インスタンスのうち、現在のリクエストのプレフィックスをすでにキャッシュしているノードを優先しながら負荷も分散し、ホットスポットへの負荷偏在を避ける。この戦略を導入すると、L2 cache のヒット率は約 **25%**、ノード当たりの入力スループットは約 **30%** 向上した。主要な式はおおむね次のとおりである。

$$
\mathrm{score}(\mathrm{worker}) = \mathrm{matchWeight} \times \mathrm{prefixMatchPercentage} - \mathrm{normalizedLoad}
$$

<span id="section-4-2"></span>

### 4.2 TTFT の最適化

モデルサービスに待ち行列が生じた場合、従来の FCFS（First Come First Serve）戦略は、キャッシュヒット率の高いリクエストと低いリクエストの優先関係を考慮しない。キャッシュヒット率が高く計算量が少ないリクエストでも、ヒット率の低いリクエストの推論完了を待つ場合があり、TTFT P99 が異常に長くなって平均スループットも低下する。

この問題に対処するため、ルータは待ち行列からスケジューリングする際、未キャッシュのトークンが少ないリクエストを優先し、キャッシュを活用しやすいリクエストが遅いリクエストにブロックされて P99 が悪化することを防ぐ。ただし、この戦略では一部のリクエストが枯渇する可能性があるため、待ち時間に応じたペナルティ機構を追加して枯渇を緩和した。[図 6](#figure-06) に示すように、この戦略は短いリクエストのサービス品質を低下させず、長いリクエストの **TTFT P90 を最大 30% 削減** する。

<span id="figure-06"></span>

![FCFS と提案スケジューリング戦略の TTFT 比較](../../papers/mimo-v2-5-inference/figure-06.png)

**図 6.** 長いリクエスト（上）と短いリクエスト（下）に対する、FCFS と提案スケジューリング戦略の P50/P70/P90/P99 TTFT 比較。長いリクエストの P90 は 30.5% 低下し、短いリクエストの TTFT はほぼ変わらない。

## 5 Prefill の最適化

<span id="section-5-1"></span>

### 5.1 並列化構成

理論上、Prefill 段階で EP（Expert Parallelism）を小さくすると、三つの理由から性能とスループットが向上する。マシンをまたぐ範囲が小さくなり通信オーバーヘッドが減ること、DP（Data Parallelism）インスタンスが少なくなり DP 間のアテンション負荷不均衡の影響が減ること、各マシンのエキスパート数が増えて MoE の負荷分散が改善することである。しかし、EP サイズはモデルパラメータと KVCache の両方を収める GPU メモリに制約される。以前の SWA KVCache は全トークンの KVCache を保存する必要があり、大きな EP を使わざるを得なかった。最適化後は SWA の窓内にあるトークンだけを保存すればよくなり、EP を従来の半分まで縮小して、**エンドツーエンド性能を約 40% 向上** できた。今後は、EP をさらに縮小して全体のスループットを高めるため、Hybrid SWA 構造に対する PP（Pipeline Parallelism）の最適化も検討していく。

<span id="section-5-2"></span>

### 5.2 長さバケット戦略

MiMo-V2.5 シリーズのハイブリッドアーキテクチャは純粋な GQA よりも計算効率を大幅に改善するが、系列長が増えるにつれてスループットは依然として明確に低下する。[図 7](#figure-07) は、計算 chunk を 16K トークンに固定し、プレフィックス長を変えた Chunked Prefill のスループットを示す。

<span id="figure-07"></span>

![キャッシュ系列長に対する相対 Prefill スループット](../../papers/mimo-v2-5-inference/figure-07.png)

**図 7.** 計算 chunk を 16K に固定した場合の、キャッシュ系列長に対する相対 Prefill スループット。スループットはプレフィックスがほぼゼロのときの $1\times$ から、1M トークンのプレフィックスでは約 $0.12\times$ まで低下する。

エージェント用途では、非常に長いリクエストの大半は、大量のプレフィックスキャッシュを持つ複数ターンのエージェント対話から生じる。長さが大きく異なるリクエストを同じモデルインスタンスへ送ると、短いリクエストが長いリクエストに律速され、主に次の二つの場面で全体のスループットが低下する。

1. **DP-Attention の同期：** 各レイヤーのアテンション計算後、複数の DP は MoE 段階へ入る前に collective communication で同期しなければならない。同じ EP グループの複数 DP に長いリクエストと短いリクエストが混在すると、短いリクエストは長いリクエストの計算によって遅くなる。
1. **Chunked Prefill の干渉：** プレフィックス長の異なるリクエストを同じ chunk へバッチ化すると、短いプレフィックスのリクエストは長いプレフィックスのリクエストの計算によって遅くなる。

これらの負荷不均衡を緩和するため、**三段階の長さバケット戦略**（0-64K / 64K-256K / 256K-1M）を採用し、負荷特性が似たリクエストを同じバケットへまとめて計算することで、本番環境における平均 Prefill スループットを大幅に高めた。さらに、動的な本番ワークロードへ適応するため、より細粒度で柔軟なバケット機構を検討している。

<span id="section-5-3"></span>

### 5.3 MoE の負荷分散

MiMo-V2.5 シリーズの全モデルは MoE アーキテクチャを使用するため、Prefill 段階でエキスパートの負荷分散を考慮する必要がある。事前学習段階では負荷分散の学習目的を導入しており、学習プロセスも比較的安定していたため、モデルはかなり均一なエキスパートルーティング戦略を学習した。推論時にエキスパート負荷分散戦略を一切有効にしなくても、レイヤーごとの平均エキスパート負荷係数（すべての rank の平均トークン数と、そのレイヤーのいずれかの rank における最大トークン数の比）は約 0.85 であり、すでに十分均衡した分布である。そのため、現時点ではエキスパート負荷分散戦略を導入していない。今後もこの指標を監視し、本番負荷の変化に応じて必要な最適化を導入する。

<span id="figure-08"></span>

![全レイヤーにわたるレイヤー別エキスパート負荷分散](../../papers/mimo-v2-5-inference/figure-08.png)

**図 8.** 全レイヤーにわたるレイヤー別エキスパート負荷分散（平均/最大トークン数の比）。平均は 0.8495 で、理想値 1.0 に近い。

<span id="section-5-4"></span>

### 5.4 NUMA 競合の解消

一部の Ubuntu システムにある `numa_balancing` カーネルパラメータは SGLang の numa-node 設定と競合し、モデル推論中に計算 kernel 間で散発的に大きな実行の空白を発生させる。複数ノード・複数 GPU の配置では、この空白が rank ごとにランダムな位置で現れ、各 rank 間同期は最も遅い rank に律速されるため、全体の推論効率が大きく低下する。システムカーネルの `numa_balancing` パラメータを無効にすると問題が解消し、**エンドツーエンド性能が約 10% 向上** した。

## 6 Decode の最適化

<span id="section-6-1"></span>

### 6.1 GPU メモリの最適化

エージェント用途では、複数ターンの対話によりコンテキストが増え続けるため、KVCache の GPU メモリ使用量が Decode の主なボトルネックとなる。KVCache がメモリを使い切るとバッチサイズを拡大できず、GPU の計算ユニットは飽和せず、Decode のスループットが制限される。スループットを維持するにはノードを増やす必要があり、推論コストも上昇する。単一ノードの並行性を高めるため、複数のメモリ最適化を実装した。

1. **Decode KVCache の SWA サポート：** KVCache の実効容量を **${\sim}5\times$** に高めた。
1. **PD 分離構成における KVCache 事前割り当ての最適化：** 受信リクエストに対する KVCache の事前割り当てを GPU メモリから CPU メモリへ移し、Decode が実際に始まる時点でのみ GPU メモリへ転送することで、リソースの過剰予約による無駄をなくした。
1. **CUDA Graph のメモリ調整：** CUDA Graph のパラメータを最適化してメモリの無駄を減らし、KVCache 容量を増やした。

<span id="section-6-2"></span>

### 6.2 MTP の最適化

MiMo-V2.5 シリーズは Decode 出力を高速化する 3 レイヤーの MTP（Multi-Token Prediction）を標準でサポートするが、従来の Prefill では MTP が有効でなかったため、Decode で最初に出力される 128 トークンは MTP レイヤー内の KVCache が無効であり、予測の受理率が非常に低かった。エージェント用途の出力系列はほとんどが短いため、この制約によって MTP の実効的な高速化は大幅に制限されていた。Prefill に MTP サポートを導入し、HiCache L2/L3 向けの専用の適応と最適化を加えると、Decode の初期段階における MTP の高速化は大幅に改善した。**0-128 トークンでは $2.3\times$、128-256 トークンでは $1.5\times$ の高速化** に達し、エージェント用途における実際の Decode コストを効果的に削減した。

### 7.1 アーキテクチャの最適化

- **マルチモーダル embedding 転送と推論を重ねる：** Prefill スケジューラのメインループで、TP rank 間のマルチモーダル embedding データの非同期複製をサポートし、Prefill 推論と重ねることで GPU のアイドル時間を削減する。
- **Encoder のデータ並列：** Encoder モデルは比較的小さいため、$\mathrm{TP}>1$ に設定すると性能が低下する。Encoder は $\mathrm{TP}=1$ で配置しつつデータ並列をサポートし、単一マシン 8-GPU の配置と運用を単純化する。
- **Encoder のリクエスト間バッチ対応：** EPD Encoder Server にリクエスト間バッチを導入した。Encoder スケジューラは並行リクエストをモダリティ別に集約し、複数リクエストの画像や音声を一度の forward pass にまとめた後、リクエストごとに分割して結果を返すことで、リクエスト単位のエンコードに起因する低い GPU 使用率を改善する。

<span id="section-7-2"></span>

### 7.2 前処理の最適化

- **GPU 画像前処理：** 大きな画像に対して CPU 上で resize/normalize/patchify を実行するとエンドツーエンドのレイテンシが大幅に増えるため、前処理を GPU へ移植し、CPU のボトルネックを解消した。
- **画像の並列ダウンロードとデコード：** マルチプロセスのダウンロードと PIL デコードを使用し、直列ダウンロードと GIL 競合による遅延を避ける。
- **マルチモーダルデータのダウンロードと forward の並列化：** 初期の Encoder 実装では、データのダウンロードと推論がバッチ間でもバッチ内でも直列であり、ダウンロード中は GPU がアイドル状態だった。メッセージキューでダウンロードと推論を分離し、一つのバッチ内でダウンロードと推論を重ねた。
- **動画の並列デコード：** フレーム抽出インデックスを $N$ 個の chunk へ均等に分割し、chunk ごとに独立した VideoDecoder を起動して並列スレッドでデコードすることで、1 時間の動画に対する Encoder のエンドツーエンドレイテンシを **156 s から 23 s に短縮** した。

<span id="section-7-3"></span>

### 7.3 キャッシュの最適化

- **Encoder のコンシステントハッシュ：** Encoder が複数ある場合、Prefill がラウンドロビンで Encoder を選択するとマルチモーダルキャッシュのヒット率が低下する。コンシステントハッシュにより、同じキーを持つリクエストを同じ Encoder へ送り、**キャッシュヒット率を 30% 向上** した。
- **ノード内の Embedding キャッシュ共有：** 共有メモリを使用して、同じノード上の複数の Encoder GPU 間でマルチモーダルキャッシュデータを共有し、キャッシュヒット率を高める。

<span id="section-8"></span>

## 8 あとがき

振り返ると、MiMo-V2.5 シリーズの推論効率は、一つのブレークスルーではなく、複数の側面にわたる協調最適化によって得られた。Hybrid SWA は Prefill と Decode の両方に効果があるが、KVCache 実装の最適化が不十分であれば、両段階のコストがかえって増えることもある。この問題に対処するため、KVCache 管理、階層キャッシュ、プレフィックスキャッシュ木を体系的に再構築し、SWA 対応 KVCache の主要な課題を解決するとともに、スケジューリングと Prefill/Decode パイプラインを最適化した。すべての変更は本番環境で検証され、最終的に Hybrid SWA の理論上の効率向上を実現した。この段階に至って初めて、Hybrid SWA は長いコンテキストの推論で性能と効率を両立するというアーキテクチャ上の利点を十分に発揮した。MoE 構成とマルチモーダル推論パイプラインへの追加の最適化も、サービング性能を大幅に向上させた。

本稿では、Hybrid SWA + MoE + マルチモーダルという複合アーキテクチャを包括的に扱う初の大規模エンジニアリング実装を提示し、API の値下げを通じて得られたコスト削減をユーザーへ還元する。同時に、最適化の一部は PR を通じて SGLang オープンソースコミュニティへ提供しており、今後もオープンソースの取り組みを進めていく。その目的は、エンジニアリング最適化の障壁を下げ、こうした高性能かつ高効率な複合アーキテクチャをより広く検討し、採用できるようにすることである。
