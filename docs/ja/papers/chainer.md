## 概要

ニューラルネットワーク向けソフトウェアフレームワークは、深層学習手法の開発と応用において重要な役割を果たす。本稿では、研究者と実務家が必要とするあらゆる深層学習モデルを、柔軟かつ直感的に高い性能で実装するための Chainer フレームワークを紹介する。Chainer は CuPy を通じて使い慣れた NumPy 風 API による GPU（Graphics Processing Unit）高速化を提供し、Define-by-Run によって Python 上で汎用的かつ動的なモデルをサポートする。また、最先端のコンピュータビジョンモデルおよび分散訓練のためのアドオンパッケージも提供する。

## 1 はじめに

深層学習は人工知能研究の第三の波を牽引している [Lec15a]。近年の研究から、深層学習はパターン認識における初期の成功を越え、多様な領域と産業の新しい応用へ進みつつあることが分かる。こうした研究上の着想を実装するには、深層学習用ソフトウェアフレームワークが必要である。

ニューラルネットワーク（NN）の実装には、多次元配列、活性化関数、自動微分など、一連の専用構成要素が必要になる。これらのツールを重複して開発しないよう、多くの開発者は Caffe [Jia13] や Torch [Col08] などのオープンソース深層学習フレームワークを利用してきた。深層学習が最初に成功した分野はコンピュータビジョンと音声認識であったため、初期の深層学習フレームワークは主として畳み込みニューラルネットワーク（CNN）のようなフィードフォワードネットワークを対象に設計された。これは画像のような固定長データの分析に有効である。

その後、さらに多様な深層学習モデルが主要な研究対象になった。ゲームプレイで目覚ましい成果が得られたことで [Mni13]、深層強化学習は有望な研究領域となった。また、再帰型ニューラルネットワーク（RNN）がテキストのような可変長データで有望な結果を示して以来、その利用は増えている。長短期記憶（LSTM）を備えた RNN は、現在では機械翻訳 [Sut14] や対話モデル [Vin15a] に成功裏に用いられている。

しかし、既存の深層学習フレームワークの多くは CNN による画像処理向けに設計されており、より一般的な深層学習モデルを実装するためのデータ構造と訓練モデルの抽象化を十分に支援していない。さらに、多くの既存フレームワークは深層学習モデルの表現にドメイン固有言語を用い、それをインタプリタでメモリ上のデータ構造へ変換する。そのため、開発者は標準的なプログラミング言語のデバッガを使用できない。デバッグは深層学習モデルの開発と調整における主要な作業であり、これは重大な問題である。

本稿では、複雑なアルゴリズムの実装、モデルの訓練、モデルパラメータの調整を簡潔かつ効率的に支援するオープンソース深層学習フレームワーク Chainer を紹介する。以下の構成は次のとおりである。[第 2 節](#section-2)では、既存の深層学習フレームワークの標準的なアーキテクチャを説明する。[第 3 節](#section-3)では Chainer のアーキテクチャを紹介する。[第 4 節](#section-4)では、メモリ使用量の最適化や二重バックプロパゲーションなどの性能技術を説明する。[第 5 節](#section-5)では、GPU のバックエンドライブラリである CuPy を紹介する。[第 6 節](#section-6)では分散訓練機能を説明する。[第 7 節](#section-7)ではコンピュータビジョン向けアドオンパッケージ ChainerCV を紹介する。[第 8 節](#section-8)では関連研究を示す。最後に[第 9 節](#section-9)で本稿をまとめ、今後の方向性を述べる。

## 2 背景と動機

<span id="figure-01"></span>

![図 1。計算グラフの構築と訓練の関係。](../../papers/chainer/figure-01.png)

**図 1。** 計算グラフの構築と訓練の関係。

典型的な NN フレームワークでは、モデルは二つの段階で構築される。このパラダイムを *Define-and-Run* と呼ぶ（[図 1(a)](#figure-01)）。Define 段階では、まずモデルの計算グラフを定義して構築する。この段階は、層間接続のデータフローグラフ、初期重み、活性化関数を指定するモデル定義に基づき、ニューラルネットワークオブジェクトをインスタンス化することに相当する。通常は自動微分により順伝播と逆伝播の計算を定義し、必要に応じてグラフ最適化も行う。Run 段階では、グラフの実際の順方向計算と逆方向計算を実行する。一組の訓練例が与えられると、この段階で確率的勾配降下法などの最適化アルゴリズムを用いて損失関数を最小化し、モデルを訓練する。

Define-and-Run パラダイムでは、CNN のような静的 NN モデルを容易に実装できる。モデル定義は Protobuf や YAML [Goo13] などの特定のマークアップ言語で記述できる。深層学習フレームワークはモデル定義を実行するインタプリタとして機能し、このモデル定義は独立した NN プログラムとみなせる。NN プログラムは入力（データ例）を受け取り、それを処理し（順方向／逆方向計算）、モデルの内部状態を変更し（更新）、結果を出力する（予測）。

Define-and-Run パラダイムは CNN のような静的モデルに適している。完全な計算グラフを利用できるため、グラフ最適化によってメモリ効率や実行時性能を改善できる可能性があるからである。しかし、ほかの種類の NN モデルを実装する際には、二つの大きな問題が生じる。

第一に、一般的な動的グラフ、すなわち制御フローを持つニューラルネットワークのサポートは煩雑になり得る。TensorFlow [Aba15] のようなフレームワークでは、制御フローの判断はホスト言語の制御フロー構文ではなく、*Switch* や *Merge* といった特殊な演算子を用いてデータフローグラフ内に定義される。

第二に、Define-and-Run パラダイムでは、ユーザーがニューラルネットワークの内部機構へアクセスできない。このため、有効なモデルを作る際に複数の困難が生じる。例えばモデルを効果的にデバッグして調整するには、内部で何が起きているかを観察できなければならない。しかし、計算グラフは一つのクラスに属する大きなオブジェクトであり、構造、重み、勾配、ノード間演算というモデル全体の情報を含むため、実質的にはブラックボックスである。その結果、プロファイラやデバッガなどの開発ツールでは、モデルの不具合や改善方法を判断できない。フレームワークがグラフ最適化を実行する場合、この問題はいっそう深刻になる。

### 3.1 オンデマンドなグラフ構築

逆伝播は、入力配列に適用された演算の履歴を記録し、その履歴を逆にたどることで実行する。Define-by-Run パラダイムでは、具体的な入力配列に対する順方向計算と同時に演算履歴を記録する。各変数と各演算に対応するノードを計算グラフ内に作れば、これを実現できる。計算グラフは入力へ適用された演算をどう逆にたどるかだけを定義し、順方向計算は定義しない。計算グラフは二種類のノードで定義する。計算に関わる変数を表す*変数ノード*と、変数へ適用される演算を表す*関数ノード*である。関数 $f$ を入力変数 $x$ に適用して出力変数 $y$ を得ると、関数ノード $n_{f}$ は入力ノード $n_{x}$ への参照を持ち、出力ノード $n_{y}$ は関数ノード $n_{f}$ への参照を持つ。グラフを逆にたどる際には、これらの参照を用いる。

順方向計算を定義するプログラムは、勾配を計算しない通常の数値計算と似ている。異なるのは、各微分可能関数が出力の計算に加え、その計算履歴をグラフへ保存する点だけである。グラフ構築はプログラムの実行トレースのみに依存するため、条件分岐やループなど、ホスト言語の任意の構文要素と組み合わせられる。このようなプログラムは、正しい勾配計算を維持しながら、呼び出しごとにトポロジーや大きさの異なるグラフを生成する。利用できるホスト言語の力は、こうした基本的な言語構造に限られない。デバッガやプロファイラのような高度なツールも活用できる。

### 3.2 オブジェクト指向によるモデル定義

組合せ可能性は深層学習の重要な特性である。ネットワークの断片をさまざまに組み合わせて接続することで、多様なアーキテクチャが作られる。深いモデルを記述する API は、構成要素を柔軟に再利用し組み合わせられるよう、組合せ可能性を備えるべきである。

Define-by-Run パラダイムにおけるモデルは、順方向計算を定義するコードと、その挙動を決めるパラメータからなる。コードはホスト言語のプログラムとして書かれ、パラメータと結び付ける必要がある。

このパラメータ束縛の問題は、オブジェクト指向プログラミングで解決できる。固有のパラメータを持つ各ニューラルネットワーク断片をクラスとして定義し、それらを別のクラスへ組み合わせて、より大きなモデル構成要素を作る。これにより、ニューラルネットワークのモジュール化とパラメータ束縛が解決される。[図 2](#figure-02) は、全結合層と多層パーセプトロンを定義する例である。パラメータはオブジェクトの構築時に初期化し、順方向計算はメソッドとして記述する。

オブジェクト指向のモデル定義は、パラメータ処理という観点でもモデルに統一インターフェースを与える。モデルはモデル断片の木から構成されるため、木を走査すれば特定の部分木に含まれるパラメータを容易に収集できる。

このオブジェクト指向によるモデル定義様式は 2015 年に Chainer が初めて導入し、現在では PyTorch や TensorFlow Eager など、ほかの Define-by-Run フレームワークでも広く使われている。

## 4 技術的特徴

本節では、Chainer の簡潔さと効率を高めるいくつかの技術について述べる。これらは Define-by-Run パラダイムに基づくフレームワークへ適用できる。

<span id="section-4-1"></span>

### 4.1 メモリ効率の高い逆伝播

利用可能な物理メモリ量がモデルとデータの大きさを制限するため、メモリ効率は深層学習フレームワークの中心的な関心事である。フレームワークのレベルでも、特にピークメモリ使用量を減らすため、さらなる最適化が可能である。

<span id="section-4-1-1"></span>

#### 4.1.1 全体的なメモリ使用量の削減

Define-by-Run パラダイムに基づく深層学習フレームワークでは、メモリ管理は自然にホスト言語へ委ねられる。Chainer は参照カウント式ガベージコレクション（GC）に依存する。これは標準的な Python 実装（すなわち CPython）で用いられる主要なメモリ管理機構である。Define-by-Run パラダイムに基づく自動微分 API は参照カウント GC と相性がよく、計算履歴の部分グラフは到達不能になると直ちに解放される。

参照カウント GC がグラフを解放するとき、各ノードは計算グラフのトポロジカル順に解放される。一方、逆伝播アルゴリズムもトポロジカル順にノードを訪れる。この二つの処理を統合すれば、逆伝播のピークメモリ消費量を最小化できる。そのために、グラフを逆にたどって関数ノードを処理した直後、そのノードへの参照を手動で除去する。

<span id="section-4-1-2"></span>

#### 4.1.2 関数ごとの局所メモリ使用量の削減

一般に、関数の勾配（より正確にはヤコビ行列）は入力に依存する。そのため、逆方向計算のインターフェースを、入力配列と出力誤差の両方を引数に取るよう設計するのは自然である。しかしこのインターフェースでは、勾配計算に入力配列を必要としない演算について、メモリ使用量の最適化が妨げられる。例えば $\tanh$ などの演算では、勾配計算に入力配列ではなく出力配列を使用できる。出力へ適用される次の演算が勾配計算のために入力を必要とする場合、入力配列を削除して出力配列を残せば、逆伝播用にメモリ上へ保持するデータを最小化できる。入力配列も出力配列も必要としない演算もある。その場合は両方への参照を削除できる。

各微分可能演算は `FunctionNode` のサブクラスとして実装され、`forward` と `backward` メソッドをオーバーライドする。`forward` では、`retain_inputs` と `retain_outputs` のメソッド呼び出しを通じ、`backward` に必要な入力と出力を明示的に宣言する。これらの宣言に挙げられない入力や出力は、逆伝播のために保存されない。特に入力は `backward` メソッドへ渡されなくなり、`backward` の実装が必要な場合にだけ取得する。

Chainer は、不要になったメモリをできるだけ早く解放するよう設計された、特別な変数オブジェクト表現を用いる。Define-by-Run パラダイムによる素朴な自動微分実装では、各変数ノードが多次元配列を直接保持する（例えば属性として保持する）。この設計では、変数への最後の参照が削除されるまで、その配列が使うメモリを回収できない。特に、ユーザーコードが変数への直接参照を一切保持していなくても、計算グラフが参照を保持していればメモリは回収できない。この問題は、ユーザーコードからの参照とノード間参照を区別できないことから生じる。ユーザーコードによる変数への参照が生きている間は、変数に対応する多次元配列データを維持する必要がある点に注意したい。一方、計算グラフ内の参照は、必ずしもデータを生存させる必要がない。変数を入力または出力として保持する演算がなければ、データは解放すべきである。この観察に基づき、ユーザーコード内の変数と計算グラフ内の変数を別々のオブジェクトで表現すれば、問題を解決できる。Chainer では、各 `Variable` オブジェクトが配列データを保持し、グラフ内の変数ノードを表す対応する `VariableNode` オブジェクトとは分離されている。変数ノードオブジェクトが配列データへの参照を保持するのは、その変数が演算によって保持される場合だけである。この形式なら、ある演算が入力または出力として保持している場合を除き、ユーザーコードからの最後の参照が除去された時点で、変数のメモリを直ちに回収できる。

<span id="section-4-2"></span>

### 4.2 二重バックプロパゲーション

勾配計算を含む計算について逆伝播を行うことは、現代の深層学習フレームワークにおける主要な機能である。これはヘッセ行列とベクトルの積に対する自動微分に相当する。この機能は*二重バックプロパゲーション*と呼ばれることがある。

各演算の逆方向計算を微分可能な関数で実装すれば、二重バックプロパゲーションをサポートできる。この考え方は単純に見えるが、素朴な実装では参照サイクルが生じ、不要なメモリ消費を招く可能性がある。参照サイクルを避けるには、得られた勾配へアクセスするインターフェースと、各微分可能関数における出力の保持という二点を考慮しなければならない。

<span id="section-4-2-1"></span>

#### 4.2.1 得られた勾配へアクセスするインターフェース

逆伝播を開始するインターフェースには二つの様式がある。一つ目は、各入力に関する勾配を計算する `Variable.backward()` メソッドである。得られた勾配は変数オブジェクトへ直接保存される。もう一つは、入力集合と出力集合の両方を引数に取る `grad()` 関数である。この場合、指定された出力に対応する計算済み勾配の集合が返される。後者のインターフェースはオブジェクト間に新しい参照を導入しないが、前者は入力ノードから計算済み勾配への参照を追加する可能性がある。計算済み勾配は計算グラフを介して入力ノードを間接的に参照するため、参照サイクルが生じる。

[第 4.1 節](#section-4-1)で述べたように、ユーザーコードからの参照とノード間参照を区別することで、この参照サイクルを取り除く。変数から対応する勾配への参照は計算グラフの一部ではないため、`VariableNode` オブジェクトではなく `Variable` オブジェクトへ配置する。

<span id="section-4-2-2"></span>

#### 4.2.2 二重バックプロパゲーションにおける出力の保持

[第 4.1 節](#section-4-1)で詳述したように、各 `FunctionNode` 実装の `backward` メソッドは、順方向計算で保持すると宣言された出力変数を使用する場合がある。逆伝播を微分可能にするには特別な手順が必要である。関数ノードは出力ノードへの参照を維持できず、維持すれば参照サイクルが生じるからである。その結果、関数ノードの逆方向計算が実行される前に出力ノードが解放される可能性がある。それでも、この出力ノードについてグラフ構築を再実行すれば、微分可能な逆伝播の有効性を維持できる。すなわち逆伝播中に新しいノードオブジェクトを作成し、それが出力ノードであったかのように接続する。さらに、出力配列データをバックアップとして関数ノードへ保存し、再作成した出力ノードで使用する。これは計算の妥当性を損なわない。出力ノードが解放されたということは、ほかのノードやユーザーコードがそれへの参照を持っていないことを示すため、出力ノードの再作成が既存ノードと衝突することはない。

## 5 CuPy による GPU サポート

深層ニューラルネットワークの典型的な利用には大量の浮動小数点数値計算が必要であるため、深層学習フレームワークは GPU などの外部アクセラレータの計算能力を十分に活用しなければならない。深層ニューラルネットワークのコードを書く人にとって、柔軟性、簡潔さ、構成要素の拡張しやすさを保ちながら高性能 GPU プログラムを実装するのは容易ではない。CuPy は、NumPy 互換の構文で NVIDIA GPU の計算能力を提供するオープンソース Python ライブラリである。cuBLAS、cuDNN、cuRAND、cuSOLVER、cuSPARSE、NCCL を含む NVIDIA の CUDA プラットフォームを用いて GPU アーキテクチャを十分に活用し、NumPy 風の構文で記述されたあらゆる計算を高速化する。

CuPy のインターフェースは NumPy と高い互換性を持ち、多くの場合はそのまま置き換えられる。標準数値データ型、配列インデックス、スライス、転置、形状変更、ブロードキャストをサポートする。

ユーザーは C++ コード片を用いてカスタム CUDA カーネルを作り、コードを高速に実行できる。CuPy はコードを自動的にラップしてコンパイルし、CUDA バイナリを生成する。コンパイル済みバイナリはキャッシュされ、以後の実行で再利用される。

CuPy はもともと Chainer のバックエンドとして開発された。Chainer の初期版は、CUDA GPU 計算用として広く使われている Python ライブラリ PyCUDA [Klc12] を用いて実装されていた。しかし、PyCUDA は深層学習に必要な NumPy の機能を十分にサポートできず、CUDA のサポートも不十分だった。Chainer v2.0 と CuPy v1.0 がリリースされた 2017 年 6 月に、CuPy は Chainer から独立した。それ以降、多数の非深層学習プロジェクトが CuPy の高い性能と簡潔なインターフェースを活用している。例えば、Python ベースの確率モデリングソフトウェア Pomegranate [Sch17b] と自然言語処理ライブラリ spaCy [Hon17] は、CuPy を GPU バックエンドとして使用する。

<span id="section-5-1"></span>

### 5.1 CuPy の例

CuPy は NumPy と同様の Python パッケージであるため、同様の方法で Python プログラムへインポートできる。[図 3](#figure-03)のコードに示すように、NumPy の `np` と同じく、CuPy は `cp` と略す。`cupy.ndarray` クラスは CuPy の中核であり、`numpy.ndarray` に代わる GPU 向けクラスである。コード中の `x` は `cupy.ndarray` のインスタンスである。NumPy を CuPy に置き換えた点を除き、その作成構文は NumPy と同じである。`cupy.ndarray` と `numpy.ndarray` の主な違いは、内容が GPU メモリ上へ割り当てられる点にある。CuPy の配列操作の多くは NumPy と同様である。例えば NumPy は CPU 上でユークリッドノルムを計算するために `numpy.linalg.norm` を使い、CuPy は GPU 上で計算するために `cupy.linalg.norm` を使う。

### 5.2 サポートする機能

前小節で示したように、CuPy は `cupy.ndarray` オブジェクトに対して多数の関数を実装している。サポートする NumPy API の部分集合については、参考資料 [+1] を参照されたい。

<span id="section-5-2-1"></span>

#### 5.2.1 線形代数

CuPy は、固有値分解、コレスキー分解、QR 分解、特異値分解、線形方程式ソルバ、逆行列、ムーア・ペンローズ擬似逆行列など、NumPy の線形代数関数の大部分をサポートする。これらの関数は `cupy.linalg` で定義され、`numpy.linalg` と互換性がある。すべて、GPU 上で動作する LAPACK 実装である cuSOLVER をバックエンドに用いる。

#### 5.2.2 疎行列

<span id="section-5-2-3"></span>

#### 5.2.3 ソート

CuPy は NumPy 互換の sort、argsort、lexsort 関数を提供し、そのバックエンドには CUDA 対応 C++ で記述された並列アルゴリズムライブラリ Thrust を用いる。CuPy は GPU 向けの高度な並列ソートアルゴリズムを実装した Thrust の利点を活用する。

### 5.3 カスタム CUDA カーネル

CuPy は、演算子、二種類のカーネル、ジェネリック型を組み合わせることで、ユーザー定義カーネルにより容易に拡張できる。CUDA コード断片を用いて、GPU 上で任意のカーネルを容易に構成し起動できる。

要素ごとのカーネルは、すべての要素へ同じ演算を適用する。例えば `cupy.add` 関数は、各要素の組へ $+$ 演算子を適用する。リダクションカーネルは、二項演算子によってすべての要素を畳み込む。例えば `sum` 関数は $+$ 演算子ですべての要素を畳み込む。要素ごとのカーネルとリダクションカーネルは、それぞれ MapReduce [Dea04] の Map と Reduce に相当する。[図 4](#figure-04)はユーザー定義の要素ごとのカーネルの例である。第一引数と第二引数は、それぞれ入力変数のリストと出力変数のリストである。各変数の定義は型指定子と引数名からなる。第三引数は、ユーザーが定義する CUDA コード断片である。このコード断片には任意の CUDA コードを使用できる。

CuPy はジェネリック型もサポートする。`float32` のような具体的な型ではなく `T` のような型パラメータを指定すると、カスタムカーネルはテンプレート関数として生成される。ジェネリック型の引数は任意の型の配列を受け入れる。例えば入力型を `’T x, T y’` と指定すると、この関数は整数や浮動小数点数など、任意の同一データ型を持つ配列の組を受け取る。

## 6 分散並列訓練

本節では、以前は *ChainerMN* と呼ばれていた Chainer の分散学習機能コンポーネントを紹介する。

GPU の性能は継続的に向上しているが、最新の GPU を使っても訓練には依然として時間がかかる。例えば ImageNet データセット [Den09a] で ResNet-50 [He16d] を訓練すると、GPU 一基では通常一週間ほどかかる。Chainer の分散機能は、Define-by-Run 手法がもたらす柔軟性を保ちながら、複数 GPU の能力を統合してハードウェア性能を最大限に活用する。これにより、動的ニューラルネットワーク、敵対的生成ネットワーク、深層強化学習といった複雑なユースケースでも、分散学習を容易に行える。

<span id="section-6-1"></span>

### 6.1 分散深層学習の基礎

<span id="section-6-1-1"></span>

#### 6.1.1 データ並列とモデル並列

分散処理によって訓練を並列化する主な方法は、データ並列とモデル並列の二つである。データ並列では、各ワーカーがモデルの複製を持ち、異なるミニバッチの勾配を計算する。ワーカーはこれらの勾配を使って協調的にモデルを更新する。各ワーカーが処理するバッチサイズを $b$、ワーカー数を $n$ とすると、通信によって得られる勾配はバッチサイズ $bn$ の勾配に等しい。ワーカーが増えるほど、一回の反復でより多くの訓練データを用いて勾配を計算するため、勾配の質が向上し、学習処理が高速化する。

モデル並列では、各ワーカーがモデルの一部を持ち、ほかのワーカーと協力して一つのミニバッチを計算する [Dea12]。GPU メモリが小さかった時期には、モデル並列が特に積極的に採用されていた。現在ではデータ並列の方が効率的であることが示されているが、自然言語処理のようにモデルのパラメータ数が膨大な領域では、モデル並列をデータ並列と組み合わせて用いる [Sha18e]。

<span id="section-6-1-2"></span>

#### 6.1.2 同期と非同期

通信モデルを同期と非同期のどちらにするかは、並列計算全体を構築する上で重要な設計選択である。以下ではデータ並列に焦点を当て、両モデルを説明する。

分散訓練における同期データ並列は、順方向計算、逆方向計算、最適化からなる非並列訓練の系列に、all-reduce と呼ばれる手順を一つ加える。all-reduce はパラメータの合計を計算し、すべてのプロセスへ配布する並列計算操作であり、MPI の標準機能である。追加された all-reduce 通信手順でワーカー同士が通信し、個々のワーカーが計算した勾配の合計を得て配布する。各ワーカーは合計を複製数で割って勾配の平均を計算し、最適化の前に all-reduce 通信で得られた勾配を用いて自身のモデル複製を更新する。

一方、非同期モデルにはパラメータサーバーと呼ばれる特殊なワーカーがある。パラメータサーバーは訓練中のモデルパラメータを保持し管理する。通常のワーカーは、順方向計算と逆方向計算で勾配を得ると、それをパラメータサーバーへ送る。パラメータサーバーは勾配を受け取り、モデルの更新に使う。ワーカーは新しいモデルパラメータを受け取り、新しい勾配の計算を開始する。

<span id="section-6-2"></span>

### 6.2 並列化の設計

Chainer はデータ並列と同期通信モデルを採用する。以下では、[第 6.1 節](#section-6-1)で述べた選択肢からこれらを選んだ理由を説明する。

データ並列に必要なのは、データセットの分割とワーカー間における勾配平均の計算という、既存実装への少数の追加だけであり、変更は不要である。画像認識など多くの場合、データ並列化はミニバッチサイズを増やすことと同義だからである。このため、まずデータ並列を選び、後にモデル並列の実験的サポートを追加した。さらに、決定論的な挙動と収束性を理由に、同期通信モデルを採用した [Pan17, Goy17a]。

同期データ並列における勾配交換はワーカー間の all-reduce 通信で実現できるため、Chainer のコミュニケータ抽象化を用いれば、all-reduce 演算をサポートする任意の通信ライブラリ上で Chainer を実行できる可能性がある。Chainer が最初にサポートしたライブラリは OpenMPI であり、CUDA 対応ビルドでは特に効率が高い。しかし all-reduce 通信は訓練の反復ごとに呼び出され、大量のデータを処理するため、とりわけ効率が求められる。そこで NVIDIA が開発した NCCL [Ncc15] を all-reduce 実行用の主要ライブラリとして採用した。NCCL は高度に最適化された通信ライブラリであり、ノード内およびノード間の NVIDIA GPU で効率的な all-reduce 演算を可能にする。

<span id="section-6-3"></span>

### 6.3 API 設計

まず Chainer の分散学習機能の設計目標を述べ、続いて Chainer で書かれた既存の深層学習プログラムを分散訓練へ拡張するために必要な最小限の手順を説明する。

分散実行のために、Chainer の Define-by-Run 設計が持つ柔軟性を犠牲にしてはならない。Define-by-Run では、all-reduce のために単一の反復中だけワーカー間でモデル構造が同一であると仮定し、反復ごとにモデル構造を変えられる。勾配交換の通信は最適化手順の直前に発生し、ほかの Chainer コンポーネントからは見えない。この最小限の仮定の範囲内で、最適化手順の前後に任意のコードを配置でき、どの反復でもモデル構造を動的に変更できる。

[図 5](#figure-05)は、MNIST 分類モデルを訓練するプログラムの中核部分を示す。分散モードで主に追加されるのは、*(1)* すべてのプロセス間通信を制御するコミュニケータコンポーネント、*(2)* ワーカー間で勾配を交換するための `mutli_node_optimizer` へのオプティマイザ変換、*(3)* 全ワーカーへのデータセット配布、の三点である。

`mutli_node_optimizer` は Chainer を分散化する上で最も重要なコンポーネントである。通常のオプティマイザをラップし、モデルを最適化する前に all-reduce 演算を用いてプロセス間で勾配を交換する。通信を除けば、元のオプティマイザとまったく同様に振る舞う。最後に `scatter_dataset` は、データ並列化のために各ワーカーが訓練データのどの断片を読むかについて合意させる。訓練データセットは等しい大きさの断片へ分割され、ワーカープロセスへ配布される。

分散モードへの移植で必要となる変更を最小限に抑えたことで、Chainer は Define-by-Run パラダイムが与える柔軟性を維持できた。

## 7 ChainerCV

本節では、コンピュータビジョンタスク向けアドオンパッケージ *ChainerCV* を紹介する。

Chainer は強力な機能を備えるが、そのサポート範囲とコンピュータビジョンにおける深層学習の要件には、なお隔たりがある。深層学習モデルはますます強力かつ複雑になっているため、研究者や技術者がこれらのアルゴリズムを一から実装するのは難しい。また、データローダや非極大抑制 [Oro16] のような前処理／後処理関数など、コンピュータビジョンで一般的なユーティリティは多数あるが、Chainer の対象範囲外である。

ChainerCV は、非専門家による着想の迅速なプロトタイピングを助け、この分野へ参入する障壁を下げることを目的とする。このライブラリは、画像分類、物体検出、セマンティックセグメンテーション、インスタンスセグメンテーションといった各種コンピュータビジョンタスクに対して、最先端モデル、その事前訓練済み重み、訓練スクリプトを提供する。さらに、データローダや評価指標などのユーティリティも統一 API で提供する。設計は、*使いやすさ*、*統一 API*、*再現性*という三つの原則に基づく。

<span id="section-7-1"></span>

### 7.1 使いやすさ

ChainerCV は、画像分類 [Rus15]、物体検出 [Lin14b]、セマンティックセグメンテーション [Cor16]、インスタンスセグメンテーション [Li17b] の四タスクをサポートする。各タスクには複数のニューラルネットワークを実装できる。例えば物体検出には七つの実装が含まれる。

ChainerCV の実装では、同じタスク向けのモデルが簡潔なインターフェースを共有するため、推論は容易である。同じタスクを解くモデルでも、ニューラルネットワークの出力型や出力の後処理方法は異なる。推論インターフェースは、モデルごとの基礎実装の違いを隠蔽する。さらに、モデルオブジェクトのインスタンス化時に事前訓練済み重みを自動ダウンロードすることで、推論処理をいっそう簡略化する。[図 7](#figure-07)に示すように、事前訓練済み重みを使えば、わずか二行の Python コードで推論を実装できる。

ChainerCV は使いやすい推論を支援するだけでなく、一部のモデルについて容易にカスタマイズできる訓練スクリプトも提供する。訓練スクリプトは Chainer の訓練抽象化を使って記述されているため、訓練コンポーネントを簡単に差し替えられる。例えばユーザー独自のデータセットで訓練できるよう、スクリプトはユーザーが拡張することを前提に設計されている。

![図 7。二つの物体検出モデルで推論を実行する例。両モデルは推論用に同じインターフェースを持つ。](../../papers/chainer/figure-07.png)

### 7.2 統一 API

ChainerCV は、ユーザーが実装をさまざまな方法で組み合わせられるよう、統一 API によるモジュール設計を重視する。実装にはニューラルネットワークモデル、データローダ、評価指標、可視化ユーティリティが含まれる。ライブラリ全体で同じデータ表現を用いることで、API の一貫性を保つ。例えば画像、境界ボックス、ピクセル単位のセマンティックラベル、インスタンスマスク、キーポイントのデータ表現を定義する。類似する関数間でも API は一貫している。前述のように、すべてのモデルで推論メソッドは常に反復可能な画像集合を入力に取る。

統一 API はインターフェースを直感的にするだけでなく、その上にユーティリティを構築できるようにする。例えば、評価ループを抽象化する実装を提供している。内部では、データセットを反復し、画像から予測を行い、正解と予測を用いて評価指標を計算する。抽象化されたユーティリティがデータローダ、推論メソッド、評価指標の間でデータを受け渡せるよう、データローダと推論メソッドのインターフェースを仮定しなければならない点に注意されたい。[図 8](#figure-08)に例を示す。

### 7.3 再現性

機械学習とコンピュータビジョンにおける再現性は、研究の質を左右する重要な要素である。ChainerCV は、公表済みの結果と同等の性能を保証する訓練コードを提供し、その結果を再現する過程を容易にすることを目指す。これらのアルゴリズムは、改良を通じて新しい着想を得るためのベースラインとなり、新しい手法を既存手法と比較するツールにもなる。不注意な実装では、元のロジックやハイパーパラメータから外れることで、訓練済みモデルの性能が容易に変化する。このような誤りがあると、研究者は競争力のある結果を得られず、着想の影響を適切に評価できないため、その実装は有用なベースラインとしての資格を失う。[表 1](#table-01)は、ChainerCV がサポートするモデルと実験結果を示す。元論文または著者の実装で報告された参照スコアも併記する。表に示すとおり、再実装の性能は元の実装に近い。訓練に含まれるランダム性も、スコア差の原因となり得る点に注意されたい。

## 8 関連研究

我々の知る限り、Chainer が提案する以前に Autograd [Mac14] は Define-by-Run パラダイムを採用して逆方向グラフを構築していた。Autograd は NumPy [Oli06] に基づくライブラリであり、ユーザーが NumPy を使った Python コードで微分可能な計算グラフを書けるよう設計されている。しかし、深層学習フレームワークを目的としたものではないため、深いモデルの訓練に必要な GPU 高速化をサポートしない。したがって Chainer は、Define-by-Run パラダイムで深層学習ワークロードに焦点を当てた最初のフレームワークである。現在では、Define-by-Run を採用する深層学習フレームワークがほかにも複数存在する。PyTorch [Pas16] は Chainer に着想を得た人気の Define-by-Run フレームワークであり [+2]、その後 TensorFlow [Aba15] は Define-by-Run 型のモデル定義をサポートする「eager mode」という機能を導入した。MXNet [Che15b] は命令型のテンソル計算をサポートし、遅延評価によって宣言型のシンボル式と組み合わせられる。PaddlePaddle [Pad16] と CNTK [Aga14] は宣言型を同時にサポートしつつ、命令型をオプションのプログラミング様式として備える。これらのフレームワークの多くが Define-by-Run をオプションとしてサポートするのに対し、Chainer は実装と API の全体にわたって Define-by-Run に高度に最適化されている。その結果、コードベースが簡潔になり、新しい開発者が貢献するためのコストが下がる。

DistBelief [Dea12] は、深層ニューラルネットワークの分散訓練において、データ並列とモデル並列、非同期 SGD、マスター・ワーカー型の異種モデルという三つの重要技術を初めて統合した。その後、これらの技術は TensorFlow [Aba15]、MXNet [Che15b]、PaddlePaddle [Pad16] でも利用可能になった。しかし非同期 SGD では、精度に影響する古い勾配（[第 6.1.2 節](#section-6-1-2)）や、パラメータサーバーがボトルネックになる問題を避けられない。これらの問題を緩和するため、近年の各フレームワークは同期 SGD を実行するオプションを追加している [Pan17, Ser18]。

一方、Caffe2 と PyTorch [Pas16] は同期 SGD を用いる。同期コストを補うため、Caffe2 と PyTorch は、ある層の逆方向計算が完了すると直ちに all-reduce を開始し、計算と重ねることで all-reduce 通信のクリティカルパスを最小化した。

コンピュータビジョンモデルのオープンソース化は広く行われているが、ChainerCV と同様の考え方を追求する研究は少数しか見つからなかった。主な競合は、論文に付随する研究プログラムのコードである。主目的は検証可能な形で研究成果を共有することであるため、可読性やモジュール性はしばしば軽視される。

ChainerCV とより密接に関連するライブラリは *pytorch/vision* [Pyt16] と GluonCV [Glu18] である。*pytorch/vision* は PyTorch をバックエンドに用いるコンピュータビジョンライブラリである。本稿執筆時点で、事前訓練済みモデルのサポートは画像分類に限られる。GluonCV は最近リリースされたコンピュータビジョンライブラリであり、別の深層学習フレームワーク Gluon [Glu17] をバックエンドに用いる。ChainerCV と同様に、GluonCV は物体検出、セマンティックセグメンテーション、インスタンスセグメンテーションをサポートする。しかし、両者は再現性を中心的な目標としていない。

<span id="section-9"></span>

## 9 結論

本稿では、新しいアルゴリズムや複雑なニューラルネットワークを容易に実装できる深層学習フレームワーク Chainer を紹介した。Chainer は、深層強化学習 [Mni13]、word2vec 分散表現 [Mik13a]、再帰型ニューラルネットワーク言語モデル [Mik10]、人間姿勢推定 [Tos14]、変分オートエンコーダ [Kin14] など、さまざまな先端応用ですでに成功を収めている。世界中の熱心な開発者とユーザーが GitHub 上で積極的に協力して Chainer を改善していることから、今後はさらに汎用的で有用になると期待している。特に CuPy の改善による性能向上により、ユーザーは CPU／GPU に依存しないコードで多様な深層学習モデルを利用できる。深層学習コミュニティのすべての方々に、Chainer を試し、その開発へ貢献していただきたい。

### 10.1 分散訓練

[第 6.4 節](#section-6-4)の実験評価では、Chainer 3.0.0rc1 と ChainerMN 1.0.0 に基づく開発ブランチを使用した [+3]。基盤となる通信ライブラリには NCCL 2.0.5 と OpenMPI 1.10.2 を用いた。

128 ノードからなる社内クラスタを使用した。各ノードには Intel Xeon E5-2667 プロセッサ（3.20 GHz、8 コア）を 2 基、メモリを 256 GB、NVIDIA Tesla P100 GPU を 8 基搭載した。すべてのノードは Mellanox InfiniBand FDR で相互接続した。

ワーカーごとのミニバッチサイズは 32、1024 ワーカーでの総ミニバッチサイズは 32k とした。計算は原則として単精度で行い、ペイロードを減らすため、通信には半精度浮動小数点数を使用した。
