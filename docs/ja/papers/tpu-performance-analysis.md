## 概要

多くのアーキテクトは、コスト・エネルギー・性能を大きく改善するには、今やドメイン固有ハードウェアが必要だと考えている。本稿では、ニューラルネットワーク（NN）の推論段階を高速化するため、2015 年からデータセンターに配備されている Tensor Processing Unit（TPU）と呼ばれるカスタム ASIC を評価する。TPU の中核は、ピークスループット 92 TeraOps/秒（TOPS）を実現する 65,536 個の 8 ビット MAC から成る行列乗算ユニットと、大容量（28 MiB）のソフトウェア管理型オンチップメモリである。TPU の決定論的実行モデルは、平均スループットには寄与しても保証レイテンシにはあまり寄与しない CPU や GPU の時変的な最適化（キャッシュ、アウト・オブ・オーダー実行、マルチスレッディング、マルチプロセッシング、プリフェッチなど）よりも、我々の NN アプリケーションが求める 99 パーセンタイル応答時間に適している。このような機能を持たないことは、多数の MAC と大容量メモリを備えながら、TPU が比較的小型かつ低消費電力である理由の一端を説明する。我々は TPU を、同時期に同じデータセンターへ配備されたサーバークラスの Intel Haswell CPU および Nvidia K80 GPU と比較する。高水準の TensorFlow フレームワークで記述したワークロードには、我々のデータセンターにおける NN 推論需要の 95% を占める本番 NN アプリケーション（MLP、CNN、LSTM）を用いる。一部のアプリケーションでは利用率が低いにもかかわらず、TPU は同時代の GPU または CPU より平均で約 15X - 30X 高速であり、TOPS/Watt は約 30X - 80X 高い。さらに、GPU の GDDR5 メモリを TPU に採用すれば、実効 TOPS は 3 倍になり、TOPS/Watt は GPU の約 70X、CPU の約 200X に達する。

**索引語—** DNN、MLP、CNN、RNN、LSTM、ニューラルネットワーク、ドメイン固有アーキテクチャ、アクセラレータ。

## 1 ニューラルネットワーク入門

クラウド上の大規模データセットと、それを支える多数のコンピュータとの相乗効果によって、機械学習は復興を遂げた。とりわけ、ディープニューラルネットワーク（DNN）は、音声認識の単語誤り率を従来手法より 30% 削減するという過去 20 年で最大の改善 [Dea16]、2011 年以降の画像認識コンテストにおける誤り率の 26% から 3.5% への低下 [Kri12, Sze15, He16a]、囲碁の人間王者への勝利 [Sil16] といった飛躍をもたらした。一部のハードウェア対象とは異なり、DNN は広範な問題に適用できるため、音声、視覚、言語、翻訳、検索順位付けなどの解決策に DNN 専用 ASIC を再利用できる。

ニューラルネットワーク（NN）は脳に似た機能を目標とし、入力の重み付き和に対する非線形関数（max(0, value) など）という単純な人工ニューロンを基礎とする。これらの人工ニューロンは層にまとめられ、ある層の出力が順番に次の層の入力となる。DNN の「deep」は、層が数層を超えることに由来する。クラウド上の大規模データセットにより、より多く、より大きな層を用いて高水準のパターンや概念を捉え、より正確なモデルを構築できるようになり、GPU はその開発に十分な計算能力を提供した。

NN の 2 つの段階は、*訓練*（または *学習*）と *推論*（または *予測*）と呼ばれ、それぞれ開発と本番運用に対応する。開発者が層数と NN の種類を選び、訓練によって重みが決まる。現在、ほぼすべての訓練は浮動小数点で行われており、これが GPU が広く普及した理由の一つである。*量子化* と呼ばれる処理は、浮動小数点数を幅の狭い整数—多くの場合はわずか 8 ビット—に変換し、通常は推論に十分な精度を得る。8 ビット整数乗算は IEEE 754 の 16 ビット浮動小数点乗算よりエネルギーと面積をそれぞれ 6X 少なくでき、整数加算ではエネルギーが 13X、面積が 38X 有利である [Dal16]。

現在、次の 3 種類の NN が広く使われている。

1. *多層パーセプトロン*（MLP）：新しい各層は、直前の層の全出力（*全結合*）の重み付き和に対する非線形関数の集合であり、重みを再利用する。
2. *畳み込みニューラルネットワーク*（CNN）：後続の各層は、直前の層における空間的に近接した出力部分集合の重み付き和に対する非線形関数の集合であり、やはり重みを再利用する。
3. *リカレントニューラルネットワーク*（RNN）：後続の各層は、出力と直前の状態の重み付き和に対する非線形関数の集合である。最も普及している RNN は *Long Short-Term Memory*（LSTM）である。LSTM の要点は、何を忘れ、何を状態として次の層へ渡すかを決めることにある。重みは時間ステップ間で再利用される。

[表 1](#table-01) は、我々のデータセンターにおける NN 推論ワークロードの 95% を占め、ベンチマークに用いる 3 種類の NN について、それぞれ 2 例を示す。通常は TensorFlow [Aba16a] で記述され、そのコードは驚くほど短く、わずか 100-1500 行である。我々のベンチマークは、ホストサーバー上で動作する、数千行から数百万行に及ぶ C++ コードの大規模アプリケーションの一部分である。これらのアプリケーションは通常ユーザー向けであり、厳格な応答時間制限が生じる。

各モデルには 5M-100M 個の重み（[表 1](#table-01) の第 9 列）が必要であり、そのアクセスには多くの時間とエネルギーを要し得る。アクセスコストを償却するため、推論または訓練では、独立した例の *バッチ* 全体で同じ重みを再利用し、性能を向上させる。

本稿では *Tensor Processing Unit（TPU）* を説明・測定し、推論時の性能と消費電力を同時代の CPU および GPU と比較する。主な要点を先に示す。

- 推論アプリケーションはユーザー向けであることが多いため、通常はスループットより応答時間を重視する。
- レイテンシ制限により K80 GPU は推論で十分に活用されず、Haswell CPU よりわずかに高速なだけである。
- TPU のチップははるかに小型かつ低消費電力であるにもかかわらず、K80 GPU の 25 倍の MAC と 3.5 倍のオンチップメモリを備える。
- TPU は推論において K80 GPU および Haswell CPU より約 15X - 30X 高速である。
- 6 つの NN アプリケーションのうち 4 つは TPU 上でメモリ帯域幅律速である。TPU を K80 GPU と同じメモリシステムに改訂すれば、GPU および CPU より約 30X - 50X 高速になる。
- TPU の性能/Watt は同時代製品の 30X - 80X であり、K80 メモリを備える改訂版 TPU なら 70X - 200X に達する。
- 多くのアーキテクトが CNN を高速化してきた一方で、CNN は我々のデータセンターワークロードのわずか 5% を占める。

## 2 TPU の起源、アーキテクチャ、実装

2006 年にはすでに、我々はデータセンターへの GPU、FPGA、またはカスタム ASIC の配備を検討していた。専用ハードウェア上で動作できる少数のアプリケーションは、大規模データセンターの余剰容量を使えば実質無料で実行でき、無料を上回るのは難しい、という結論に至った。この状況が変わったのは 2013 年である。音声認識 DNN を用いた音声検索を人々が 1 日 3 分利用すると、計算需要を満たすためにデータセンターを 2 倍にする必要があるとの予測が示され、従来型 CPU で対応するには非常に高価だった。そこで我々は、推論用カスタム ASIC を迅速に製造する優先度の高いプロジェクトを開始した（訓練用には市販 GPU を購入した）。目標は GPU に対してコスト性能を 10X 改善することだった。この使命の下、TPU はわずか 15 か月で設計、検証 [Ste15]、製造され、データセンターに配備された。（紙幅の都合上、本稿で扱える TPU の情報量と詳細度には限りがある。詳しくは [Ros15, Ros15a, Ros15b, Ros15c, Tho15, You15] を参照されたい。）

配備の遅延リスクを抑えるため、TPU は CPU と密結合するのではなく、PCIe I/O バス上のコプロセッサとして設計され、GPU と同様に既存サーバーへ装着できるようにした。さらに、ハードウェア設計とデバッグを簡素化するため、TPU 自身が命令をフェッチするのではなく、ホストサーバーが実行すべき TPU 命令を送信する。したがって、TPU は GPU よりも FPU（浮動小数点ユニット）コプロセッサに近い。

![TPU のブロック図](../../papers/tpu-performance-analysis/figure-01.png)

**図 1。** TPU のブロック図。主要な計算部分は右上の黄色い Matrix Multiply ユニットである。その入力は青色の Weight FIFO と青色の Unified Buffer（UB）、出力は青色の Accumulators（Acc）である。黄色い Activation Unit は Acc に非線形関数を適用し、その結果は UB へ送られる。

<span id="figure-02"></span>

![TPU ダイのフロアプラン](../../papers/tpu-performance-analysis/figure-02.png)

**図 2。** TPU ダイのフロアプラン。配色は [図 1](#figure-01) に従う。薄い青色のデータバッファがダイの 37%、薄い黄色の計算部が 30%、中間色の緑の I/O が 10%、濃い赤色の制御部はわずか 2% である。CPU や GPU では制御部がはるかに大きく（設計もはるかに難しく）なる。

目標は、ホスト CPU とのやり取りを減らすために推論モデル全体を TPU 上で実行し、2013 年の NN に必要だったものだけでなく、2015 年以降の NN の要求にも対応できる十分な柔軟性を持たせることだった。[図 1](#figure-01) に TPU のブロック図を示す。

TPU 命令はホストから PCIe Gen3 x16 バスを介して命令バッファへ送られる。内部ブロック同士は通常、幅 256 バイトの経路で接続される。右上から見ると、Matrix Multiply Unit が TPU の中核である。ここには、符号付きまたは符号なし整数の 8 ビット乗算加算を実行できる 256x256 個の MAC が含まれる。16 ビット積は、行列ユニット直下にある 4 MiB の 32 ビット Accumulators に蓄積される。この 4 MiB は、256 要素・32 ビットのアキュムレータ 4096 個に相当する。行列ユニットは 1 クロックサイクルごとに 256 要素の部分和を 1 つ生成する。ピーク性能に達するために 1 バイト当たり必要な演算数（[第 4 節](#section-4) の Roofline の折れ曲がり点）が約 1350 であることをまず確認し、2048 へ切り上げたうえで、コンパイラがピーク性能での実行中にダブルバッファリングを使えるよう 2 倍にした結果、4096 を選んだ。

8 ビットの重みと 16 ビットの活性化を組み合わせる場合（またはその逆）、Matrix Unit は半分の速度で計算し、両方が 16 ビットなら 4 分の 1 の速度で計算する。1 クロックサイクルごとに 256 個の値を読み書きし、行列乗算または畳み込みを実行できる。行列ユニットは 64 KiB の重みタイルを 1 つ保持し、さらにダブルバッファリング用に 1 つ保持する（タイルをシフトインする 256 サイクルを隠蔽するため）。このユニットは密行列向けに設計されている。配備までの時間を優先したため、スパース性のアーキテクチャ支援は省いた。将来の設計ではスパース性を高い優先度で扱う。

行列ユニット用の重みは、*Weight Memory* と呼ぶオフチップ 8 GiB DRAM から読み出すオンチップ Weight FIFO を経由して準備される（推論では重みは読み取り専用であり、8 GiB なら多数のモデルを同時にアクティブにできる）。Weight FIFO の深さは 4 タイルである。中間結果は 24 MiB のオンチップ *Unified Buffer* に保持され、Matrix Unit への入力として利用できる。プログラマブル DMA コントローラが CPU Host メモリと Unified Buffer の間でデータを転送する。

[図 2](#figure-02) は TPU ダイのフロアプランを示す。24 MiB の Unified Buffer はダイのほぼ 3 分の 1、Matrix Multiply Unit は 4 分の 1 を占めるため、データパスはダイのほぼ 3 分の 2 を占める。24 MiB という容量は、一つにはダイ上で Matrix Unit のピッチに合わせるため、もう一つには短い開発日程を踏まえてコンパイラを簡素化するために選ばれた（[第 7 節](#section-7) を参照）。制御部はわずか 2% である。[図 3](#figure-03) は TPU を載せたプリント基板を示し、SATA ディスクと同様に既存サーバーへ挿入できる。

命令は比較的低速な PCIe バスを介して送られるため、TPU 命令は repeat フィールドを含む CISC の伝統に従う。これらの CISC 命令の命令当たり平均クロックサイクル数（CPI）は通常 10-20 である。命令は全体で約 12 種類あるが、主要な 5 種類は次のとおりである。

1. \`Read_Host_Memory\` は CPU ホストメモリから Unified Buffer（UB）へデータを読み込む。
2. \`Read_Weights\` は Weight Memory から Weight FIFO へ、Matrix Unit の入力となる重みを読み込む。
3. \`MatrixMultiply/Convolve\` は Matrix Unit に、Unified Buffer から Accumulators への行列乗算または畳み込みを実行させる。行列演算は、可変サイズの B*256 入力を受け取り、256x256 の定数重み入力を乗じて B*256 出力を生成し、完了までにパイプライン化された B サイクルを要する。
4. \`Activate\` は ReLU、Sigmoid などを選択肢として、人工ニューロンの非線形関数を実行する。入力は Accumulators、出力は Unified Buffer である。また、非線形関数ロジックに接続されているため、ダイ上の専用ハードウェアを用いて畳み込みに必要なプーリング演算も実行できる。
5. \`Write_Host_Memory\` は Unified Buffer から CPU ホストメモリへデータを書き込む。

ほかの命令には、別形式のホストメモリ読み書き、構成設定、2 種類の同期、ホストへの割り込み、debug-tag、nop、halt がある。CISC の \`MatrixMultiply\` 命令は 12 バイトで、そのうち 3 バイトが Unified Buffer アドレス、2 バイトがアキュムレータアドレス、4 バイトが長さ（畳み込みでは 2 次元の場合もある）、残りがオペコードとフラグである。

TPU マイクロアーキテクチャの方針は、行列ユニットを動かし続けることである。これらの CISC 命令には 4 段パイプラインを用い、各命令は別々の段で実行される。\`MatrixMultiply\` 命令とほかの命令の実行を重ねることで、後者の実行を隠蔽する計画だった。この目的のため、\`Read_Weights\` 命令は decoupled-access/execute の考え方 [Smi82] に従い、アドレスを送信した後、Weight Memory から重みがフェッチされる前に完了できる。入力の活性化データまたは重みデータが準備できていなければ、行列ユニットはストールする。

従来の RISC パイプラインでは各段が 1 クロックサイクルなのに対し、我々の CISC 命令は一つのステーションを数千クロックサイクル占有し得るため、明瞭なパイプライン重複図はない。興味深い状況は、あるネットワーク層の活性化が完了するまで次の層の行列乗算を開始できないときに生じる。そこでは「delay slot」が現れ、行列ユニットは Unified Buffer を安全に読み出すため、明示的な同期を待つ。

大容量 SRAM の読み出しは算術演算よりはるかに多くの電力を使うため、行列ユニットは Unified Buffer の読み書きを減らすシストリック実行によりエネルギーを節約する [Kun80, Ram91, Ovt15a]。これは、異なる方向からのデータが配列中のセルへ一定間隔で到着し、そこで結合されることに依拠する。[図 4](#figure-04) に示すように、データは左から流入し、重みは上からロードされる。256 要素の各積和演算は、対角線状の波面として行列内を移動する。重みは事前ロードされ、新しいブロックの先頭データとともに進む波に合わせて有効になる。制御とデータはパイプライン化され、256 個の入力が一度に読み出され、256 個のアキュムレータそれぞれの一つの位置を瞬時に更新するように見せる。正しさの観点では、ソフトウェアは行列ユニットのシストリック性を意識しないが、性能の観点ではユニットのレイテンシを考慮する。

TPU ソフトウェアスタックは、アプリケーションを迅速に TPU へ移植できるよう、CPU および GPU 向けに開発されたものと互換でなければならなかった。TPU 上で実行されるアプリケーション部分は通常 TensorFlow で記述され、GPU または TPU 上で実行可能な API へコンパイルされる [Lar16]。GPU と同様、TPU スタックは User Space Driver と Kernel Driver に分かれる。Kernel Driver は軽量で、メモリ管理と割り込みだけを扱う。これは長期的な安定性を意図して設計されている。User Space driver は頻繁に変更される。これは TPU の実行を設定・制御し、データを TPU の順序に並べ替え、API 呼び出しを TPU 命令へ変換し、アプリケーションバイナリを生成する。User Space driver はモデルが初めて評価される際にコンパイルし、プログラムイメージをキャッシュして重みイメージを TPU の重みメモリへ書き込む。2 回目以降の評価は最高速度で実行される。TPU はほとんどのモデルを入力から出力まで完全に実行し、TPU 計算時間と I/O 時間の比率を最大化する。計算は多くの場合 1 層ずつ行われ、実行の重複によって行列乗算ユニットがクリティカルパス外の演算の大半を隠蔽する。

## 3 CPU、GPU、TPU のプラットフォーム

[表 1](#table-01) の 6 つの本番アプリケーションを、本稿のワークロードとする。前述のように、この 6 つは我々のデータセンターにおける TPU 利用の 95% を代表する。皮肉にも、AlexNet や VGG のような人気のある小規模 DNN を本番機へ配備し測定するのは難しい。ただし、我々の CNN の一つは広く使われている Inception V2 を基にしている。

ベンチマーク用プラットフォームは、TPU が配備された 2015 年に利用可能だったサーバークラスのコンピュータである。この制約により、TPU と同様に内部 SRAM と外部 DRAM メモリの少なくとも SECDED 保護を備える必要があり、Nvidia Maxwell GPU など一部の候補は除外される。また、当社が購入・配備するには、ベンチマークで勝つためだけに組み立てた不自然な構成ではなく、合理的な構成のマシンでなければならなかった。

[表 2](#table-02) に選択した構成を示す。従来型 CPU サーバーは、Intel の 18 コア・デュアルソケット Haswell プロセッサで代表する。このプラットフォームは GPU または TPU のホストサーバーでもある。Haswell は Intel の 22nm プロセスで製造された。CPU と GPU はどちらも非常に大きなダイであり、約 600 mm² もある。

2.3 GHz の CPU クロック周波数に Turbo モードは含めない。NN アプリケーションを動かす我々のデータセンターでは、Turbo モードはほとんど発生しないためである。Haswell のクロック周波数は、プログラムが AVX 命令を使用するかどうかで異なり、我々の NN アプリケーションは AVX をよく使用する。Turbo モードの高いクロック周波数（AVX を避けるプログラム向け）は、全コアを使用しないときに生じる。したがって、我々のアプリケーションは通常すべてのコアを使用し、さらに空いているコアをほかのデータセンタージョブで埋められることも、データセンターで Turbo モードがまれな別の理由である。

GPU アクセラレータは Nvidia K80 である。各 K80 カードには 2 つのダイがあり、内部メモリと DRAM に SECDED を備える。Nvidia は「K80 Accelerator は、より少数で高性能なサーバーによってアプリケーション性能を提供し、データセンターコストを劇的に削減する」と述べている [Nvi16]。NN 研究者は 2015 年に K80 を頻繁に使用し、2016 年 9 月になっても新たなクラウドベース GPU サービスに K80 が選ばれていた [Bar16]。

このサーバーには 4 枚のカードで最大 8 個の K80 ダイを搭載でき、これが我々のベンチマーク構成である。最大 875 MHz までクロック周波数を上げる Boost モードを備える。Haswell の Turbo モードはハードウェア制御であるため、チップ温度が大幅に上昇するまで短いバーストで動作できる。一方、Boost モードはソフトウェアドライバの制御下にあり [Nvi15]、少なくとも数百ミリ秒は継続する。したがって、そうしなければチップが過熱しかねないため、K80 は実質的に常時 Boost モードで動作すると仮定して電力と冷却を用意する必要がある。このプラットフォームで Boost モードを有効にすると K80 カード数を減らさざるを得ず、総所有コストが悪化する。そこで Boost モードは無効にした。この制約によりピーク帯域幅と TOPS は低下する（[表 2](#table-02) のキャプションを参照）。有効にした場合は [第 8 節](#section-8) で検討する。

ベンチマーク対象サーバー当たりのダイ数は 2-8 個と異なるため、以下では通常、ダイ当たりに正規化した結果（[図 5](#figure-05)-[図 8](#figure-08)、[図 10](#figure-10)-[図 11](#figure-11)、[表 3](#table-03)、[表 4](#table-04)、[表 6](#table-06)）を示すが、場合によってはシステム全体も示す（[図 9](#figure-09)）。この区別が明確であることを願う。

## 4 性能：Roofline、応答時間、スループット

3 種類のプロセッサ上で動作する 6 つのアプリケーションの性能を示すため、高性能計算（HPC）の Roofline 性能モデル [Wil09] を応用する。この単純な視覚モデルは完全ではないが、性能ボトルネックの原因を洞察できる。このモデルは、アプリケーションがオンチップキャッシュに収まらず、計算律速またはメモリ帯域幅律速のいずれかになると仮定する。HPC では Y 軸が 1 秒当たりの浮動小数点演算性能であるため、ピーク計算率が Roofline の「水平」部分を形成する。X 軸は演算密度であり、アクセスした DRAM 1 バイト当たりの浮動小数点演算数で測る。メモリ帯域幅の単位は bytes/秒であり、（FLOPS/秒）/（FLOPS/Byte）= Bytes/秒であることから Roofline の「傾斜」部分となる。十分な演算密度がなければ、プログラムはメモリ帯域幅律速となり、Roofline の傾斜部分の下に位置する。

<span id="figure-05"></span>

![TPU ダイの Roofline](../../papers/tpu-performance-analysis/figure-05.png)

**図 5。** TPU（ダイ）の Roofline。稜線点は右方遠くの Weight Memory から取得した 1 バイト当たり 1350 演算にある。

アプリケーションの実際の 1 秒当たり演算数と、その真上にある上限との隔たりは、演算密度を変えずにさらに性能を調整した場合に得られる可能性を直接示す。もちろん、演算密度を高める最適化（キャッシュブロッキングなど）は、さらに大きな利点をもたらし得る。

TPU に Roofline モデルを適用するため、まず NN アプリケーションを量子化するときに、浮動小数点演算を整数演算へ置き換える。NN アプリケーションでは重みが通常オンチップメモリに収まらないため、2 つ目の変更として、演算密度を読み出した重み 1 バイト当たりの整数演算数と再定義する（[表 1](#table-01) の第 10 列を参照）。

[図 5](#figure-05) は、単一 TPU ダイの Roofline モデルを両対数目盛で示す。TPU の Roofline には長い「傾斜」部分があり、そこでは演算密度によって、性能がピーク計算能力ではなくメモリ帯域幅で制限される。6 つのアプリケーションのうち 5 つは上限にうまく頭をぶつけている。MLP と LSTM はメモリ律速、CNN は計算律速である。CNN1 は非常に高い演算密度にもかかわらず 14.1 TOPS にとどまる一方、CNN0 は 86 TOPS で動作する。

[表 3](#table-03) は、TPU の動作を部分的に観測できる性能カウンタに基づき、CNN1 で何が起きたかを説明する。TPU が CNN1 の行列演算に費やすサイクルは半分未満である（第 7 列、第 1 行）。それらのアクティブサイクルごとに、CNN1 の一部の層は特徴深度が浅いため、65,536 個の MAC のうち有用な重みを保持するのは約半分にすぎない。サイクルの約 35% は、重みをメモリから行列ユニットへロードする待ち時間であり、これは演算密度がわずか 32 の 4 つの全結合層の実行中に発生する（[第 8 節](#section-8) の最後の誤謬を参照）。これにより、行列関連カウンタでは説明できないサイクルが約 19% 残る。TPU では実行が重複するため、それらのサイクルを正確に説明できないが、23% のサイクルでパイプラインの RAW 依存によるストールがあり、1% は PCIe バス経由の入力待ちに費やされることが分かる。

<span id="section-5"></span>

## 5 コスト性能、TCO、性能/Watt

コンピュータを数千台単位で購入する場合、性能よりコスト性能が重要になる。データセンターで最適なコスト指標は総所有コスト（TCO）である。我々が数千個のチップに対して実際に支払う価格は、関係企業間の交渉に左右される。事業上の理由から、そのような価格情報や、価格を推定できるデータを公開することはできない。しかし、電力は TCO と相関し、サーバー当たりの Watt 数は公開できるため、本稿では性能/TCO の代理指標として性能/Watt を用いる。本節では、単一ダイではなく、[表 2](#table-02) の「Benchmarked Server」列に示すサーバー全体を比較する。

[図 9](#figure-09) は、Haswell CPU に対する K80 GPU と TPU の性能/Watt の幾何平均および加重平均を示す。性能/Watt は 2 通りの方法で計算する。第 1 の「total」は、GPU と TPU の性能/Watt を計算する際に、ホスト CPU サーバーの消費電力を含める。第 2 の「incremental」は、あらかじめ GPU と TPU からホスト CPU サーバーの電力を差し引く。

total-performance/Watt では、K80 サーバーは Haswell の 1.2 - 2.1X である。Haswell サーバーの電力を除いた incremental-performance/Watt では、K80 サーバーは 1.7- 2.9X となる。

TPU サーバーの total-performance/Watt は Haswell より 17-34 倍優れており、K80 サーバーの 14-16 倍に相当する。当社がカスタム ASIC を正当化した根拠である相対 incremental-performance/Watt は、TPU で 41-83 に達し、GPU の 25-29 倍の性能/Watt を実現する。

## 6 エネルギー比例性

熱設計電力（TDP）は電力供給設備のコストに影響する。ハードウェアが最大電力で動作するときに十分な電力と冷却を供給しなければならないためである。一方、電気料金は、ワークロードが 1 日を通して変動するなかで消費される平均電力に基づく。[Bar07] は、サーバーが 100% 稼働する時間は全体の 10% 未満であることを明らかにし、*エネルギー比例性*、すなわちサーバーは実行した仕事量に比例して電力を消費すべきだと提唱した。前節の消費電力推定は、我々のデータセンターで観測された TDP に対する割合に基づく。

提供するワークロードの利用率を 0% から 100% まで変化させ、ワークロードを 10% 刻みのバケットに分けて性能と電力を測定した [Lan09]。[図 10](#figure-10) は、CNN0 のワークロードを変化させたときの 3 種類のチップについて、サーバー電力をサーバー当たりのダイ数で除した値を示す。GPU と TPU について、incremental 電力（K80 と TPU）だけでなく total 電力（K80+Haswell/4 と TPU+Haswell/2）もプロットする。いずれにも同じバッチサイズを与えたことに注意されたい。

TPU の電力が最も低く、ダイ当たり total は 118W（TPU+Haswell/2）、ダイ当たり incremental は 40W（[図 10](#figure-10) の TPU）である一方、エネルギー比例性は低い。負荷 10% でも、TPU は負荷 100% 時の 88% の電力を使用する。（設計日程が短かったため、多くの省電力機能を組み込めなかった。）予想どおり、Haswell はこのグループでエネルギー比例性が最も高く、負荷 10% 時の電力は負荷 100% 時の 56% である。K80 は TPU より CPU に近く、ワークロード 10% 時に最大負荷電力の 66% を使う。計算律速ではない LSTM1 も同様であり、負荷 10% 時には CPU が最大電力の 47%、GPU が 78%、TPU が 94% を使う。

CNN0 を実行する CPU サーバーがアクセラレータのホストになると、サーバーの電力使用量はどうなるだろうか。GPU と TPU が負荷 100% のとき、CPU サーバーは GPU に対して最大電力の 52%、TPU に対して 69% を使う。（TPU は GPU よりはるかに高速であるため、CPU は TPU 向けにより多くの仕事を行う。）その結果、Haswell サーバーと 4 基の TPU の組み合わせは、Haswell サーバー単体より追加電力を 20% 未満に抑えながら、CNN0 を 80 倍高速に実行する（4 TPU 対 2 CPU）。

**図 11。** メモリ帯域幅、クロック周波数 + アキュムレータ、クロック周波数、行列ユニットの次元 + アキュムレータ、行列ユニットの次元を 0.25x-4x にスケーリングしたときの TPU 加重平均性能。加重平均では個々の DNN の寄与を把握しにくいが、MLP と LSTM はメモリ帯域幅を 4X にすると 3X 改善する一方、クロックを上げても効果がない。CNN では逆であり、クロックを 4X にすると 2X 改善するが、メモリを高速化しても効果は小さい。行列乗算ユニットを大きくしても、どの DNN にも効果はない。

第 1 に、メモリ帯域幅（*memory*）の増加が最も大きな影響を持ち、メモリを 4X にすると性能は平均 3X 改善する。第 2 に、クロック周波数は、アキュムレータを増やすかどうかにかかわらず、平均ではほとんど効果がない。これは、MLP と LSTM がメモリ律速であり、計算律速なのは CNN だけだからである。[図 11](#figure-11) は 6 つの DNN すべての加重平均だけを示すため判別しにくいが、クロック周波数を 4X にしても MLP と LSTM にはほとんど影響せず、CNN の性能は約 2X 改善する。第 3 に、[図 11](#figure-11) の平均性能は、行列ユニットを 256x256 から 512x512 へ拡大すると、アキュムレータを増やすかどうかにかかわらず、すべてのアプリケーションでわずかに低下する。この問題は大きなページの内部断片化に似ているが、2 次元で起きるためさらに深刻である。LSTM1 で使われる 600x600 行列を考える。256x256 行列ユニットでは、600x600 をタイル化するのに 9 ステップかかり、合計時間は 18 us である。より大きな 512x512 ユニットは 4 ステップで済むが、各ステップが 4 倍長くかかるため、合計は 32 us となる。我々の CISC 命令は長いため、デコードの影響は小さく、DRAM からのロードのオーバーヘッドを隠蔽しない。

[表 8](#table-08) は、当初 MLP を最大 2048 のバッチサイズで実行できるよう容量を決めた 24 MiB Unified Buffer の利用率を示す。最近、Unified Buffer のストレージアロケータを改善し、6 つのアプリケーションのうち最大のものに必要なメモリを 14 MiB へ削減した。配備後の最初の 18 か月間は、新しいアロケータの開発中に TPU が全容量を使用していた。現在、この余剰容量は、より大きなモデルを採用するための余裕となっている。

次に、性能モデルを用いて、15 か月を超える開発期間があれば同じプロセス技術で設計できたかもしれない仮想 TPU ダイ（TPU’）を評価した。より積極的な論理合成とブロック設計によって、クロック周波数を 50% 高められた可能性がある。K80 と同様に GDDR5 メモリ用インターフェース回路を設計すれば、Weight Memory の帯域幅は 5 倍超に改善し、Roofline の稜線点は 1350 から 250 へ移る。[図 11](#figure-11) が示すように、メモリを改善せずクロック周波数を 1050 MHz に上げても、ほとんど変化はない。クロックを 700 MHz のままにして Weight Memory に GDDR5 を使うと、幾何平均の増加率は 2.6、加重平均は 3.9 へ跳ね上がる。両方を行うと幾何平均は 2.9 へ上がるが、加重平均は上がらないため、TPU’ は単にメモリを高速化したものとする。

[図 11](#figure-11) はホストサーバー時間を含まない。[表 5](#table-05) を用いて、TPU に対するホストサーバー通信のオーバーヘッド時間を計算した。同じ追加時間を加えると、TPU’ の平均は 2.6 から 1.9、3.9 から 3.2 に下がる。この変更は、アプリケーションのホスト担当部分を実行する CPU 時間を含まないため楽観的である一方、3X 高速な TPU’ があればホストコードを積極的に調整する可能性が高いため悲観的でもある。

DDR3 Weight Memory だけを同等の GDDR5 メモリへ置き換えるには、メモリチャネル数を 4 へ倍増する必要がある。この改善によりダイ面積は約 10% 増える。しかし、メモリ帯域幅が高まると Unified Buffer への圧力が減るため、Unified Buffer を 14 MiB へ縮小すれば面積の 10% を取り戻せる。サーバー当たり 4 基の TPU があるため、GDDR5 は TPU システムの電力予算も 861 Watts から約 900 Watts へ増加させる。

## 8 議論

本節では [Hen18] に倣い、誤謬と落とし穴に反論を添える形式を採る。

- **誤謬：データセンターの NN 推論アプリケーションは、応答時間と同じ程度にスループットを重視する。**

  開発者が応答時間に厳しい要求を持っていたことは意外だった。2014 年には、バッチサイズは TPU がピーク性能に達するほど大きくなる、あるいはレイテンシ要件はそれほど厳しくならない、と考える者もいたためである。推進役となったアプリケーションの一つはオフライン画像処理であり、対話型サービスも TPU を必要とするなら、その大半は単により大きなバッチを蓄積するだろうという直感があった。2014 年に応答時間を重視していたあるアプリケーション（LSTM1）の開発者でさえ、2014 年には上限を 10 ms としていたが、実際に TPU へ移植した際には 7 ms へ短縮した。このような多くのサービスから予想外に TPU が求められたことに、短い応答時間がもたらす影響と、それを優先する姿勢が重なり、前提が変わった。アプリケーション開発者は、大きなバッチが蓄積するのを待つより、レイテンシの短縮を選ぶことが多かった。幸い、TPU は単純で再現性のある実行モデルによって対話型サービスの応答時間目標を満たしやすく、ピークスループットも非常に高いため、小さなバッチサイズでも同時代の CPU や GPU より高い性能を実現する。

- **誤謬：K80 GPU アーキテクチャは NN 推論に適している。**

  GPU は従来、高帯域幅 DRAM と数千のスレッドに依存して目標を達成する、高スループットアーキテクチャと見なされてきた。この観点は、K80 が推論において Haswell よりわずかに高速なだけで、TPU よりはるかに遅い理由を説明する。K80 の後継製品には、推論のピーク性能を高める最適化が確実に含まれるだろうが、スループット指向のアーキテクチャであるため、厳格なレイテンシ制限を満たすことは GPU にとってより難しい可能性がある。そして [第 7 節](#section-7) が示すように、TPU にも大きな改善余地があり、容易な目標ではない。

- **落とし穴：アーキテクトは重要な NN タスクを見過ごしてきた。**

  アーキテクチャ研究コミュニティが NN に注目していることは喜ばしい。ISCA 2016 の論文の 15% が NN 用ハードウェアアクセラレータを扱っていた [Alb16, Che16c, Chi16, Han16a, Kim16a, Lik16, Liu16, Rea16, Sha16b]。しかし残念ながら、9 本すべてが CNN を扱い、ほかの NN に言及したものは 2 本しかなかった。CNN は MLP より複雑で、NN コンテストでも目立つ存在であり [Rus15]、それが魅力を説明するかもしれないが、我々のデータセンター NN ワークロードの約 5% にすぎない。エッジデバイスでは CNN が一般的かもしれないが、データセンターにおける畳み込みモデルの量は、まだ MLP と LSTM に追いついていない。アーキテクトが少なくとも同じ熱意をもって MLP と LSTM の高速化に取り組むことを期待する。

- **落とし穴：NN ハードウェアでは、1 秒当たり推論数（IPS）は不正確な性能要約指標である。**

  我々の結果は、IPS が NN ハードウェア全体の性能要約として不適切であることを示す。これは単に、アプリケーションで典型的な推論の複雑さ（たとえば NN 層の数、大きさ、種類）の逆数だからである。たとえば TPU は、4 層の MLP1 を 360,000 IPS で実行する一方、89 層の CNN1 はわずか 4,700 IPS であり、TPU の IPS は 75X も変動する。したがって IPS を単一の速度要約として用いることは、通常のプロセッサに対する MIPS や FLOPS よりも NN アクセラレータに対してさらに誤解を招く [Hen18] ため、IPS はいっそう避けるべきである。NN マシンを適切に比較するには、多様な NN アーキテクチャへ移植できるよう高水準で記述されたベンチマークスイートが必要である。Fathom は、そのようなベンチマークスイートを目指す有望な新しい試みである [Ado16]。

- **誤謬：Boost モードを有効にすれば、K80 GPU の結果ははるかに良くなる。**

  K80 Boost モードが TCO に与える悪影響（[第 3 節](#section-3)）はさておき、LSTM1 で測定した。Boost モードはクロック周波数を最大 1.6 倍（560 MHz から 875 MHz）に高め、性能を 1.4X 向上させたが、電力も 1.3X 増加させた。性能/Watt の純増は 1.1X であり、したがって LSTM1 では、Boost モードが我々のエネルギー・速度分析に与える影響は小さい。

- **誤謬：CPU と GPU をもっと効率よく使用するか、新しい世代と比較すれば、TPU と同等の結果になる。**

  当初、CPU での 8 ビット結果は DNN 一つについてしか得られなかった。AVX2 の整数支援を効率よく利用するには相当な作業が必要だったためである。利点は約 3.5X だった。一つだけ例外を設け、専用の Roofline も示すより、CPU の全結果を浮動小数点で提示する方が混乱が少なく（紙幅も取らなかった）。すべての DNN が同様に高速化すると、性能/Watt 比は 41-83X から 12-24X へ低下する。新しい 16-nm、1.5GHz、250W のデータセンター向け P40 GPU は、毎秒 47 Tera の 8 ビット演算を実行できるが、2015 年初頭には利用できなかったため、我々の 3 プラットフォームと同時代ではない。また、厳格な時間制限内で P40 のピーク性能のどの程度を発揮できるかも分からない。より新しいチップと比較するなら、[第 7 節](#section-7) が示すように、K80 の GDDR5 メモリを使うだけで、28-nm、0.7GHz、40W の TPU の性能を 3 倍にできる（追加コストは 10W）。

- **落とし穴：性能カウンタを NN ハードウェアへ後付けする。**

  TPU には 106 個の性能カウンタがあり、できればさらに数個欲しいほどである（[表 3](#table-03) を参照）。NN アクセラレータの存在理由は性能であり、その進化は、何が起きているかについて確かな直感を持つにはまだあまりに初期段階にある。

- **誤謬：2 年間のソフトウェア調整を経た現在、TPU の性能を高める道はハードウェア更新しかない。**

  開発者とコンパイラ作成者が CNN1 を TPU ハードウェアへ適合させる作業をさらに進めれば、TPU 上の CNN1 性能は改善し得る。たとえば、開発者は畳み込み層から出る複数の短いバッチを、4 つの全結合層向けの単一の深いバッチ（32 から 128）へまとめるようアプリケーションを再構成できる。このような単一層により、行列ユニットの利用率は向上する（[表 3](#table-03)）。CNN1 は現在すでに TPU 上で CPU の 70 倍超の速度で動作しており、CNN1 の開発者は非常に満足しているため、そのような最適化が実施されるか、いつ実施されるかは明らかでない。

## 9 関連研究

2 本のサーベイ論文によれば、カスタム NN ASIC の歴史は少なくとも 25 年前に遡る [Ien96, Asa02]。たとえば CNAPS チップは、16 ビット x 8 ビット乗算器から成る 64 要素 SIMD アレイを備え、複数の CNAPS チップをシーケンサで接続できた [Ham90]。Synapse-1 システムは、MA-16 と呼ばれるカスタムのシストリック積和演算チップを基礎とし、一度に 16 個の 16 ビット乗算を実行した [Ram91]。このシステムは複数の MA-16 チップを連結し、活性化関数を実行するカスタムハードウェアを備えていた。

T0 カスタム ASIC で高速化した 25 台の SPERT-II ワークステーションは、音声認識の NN 訓練と推論の両方を行うため、1995 年から配備された [Asa98]。40-Mhz の T0 は MIPS 命令セットアーキテクチャにベクトル命令を追加した。8 レーンのベクトルユニットは、8 ビットおよび 16 ビット入力を基に、1 クロックサイクル当たり最大 16 個の 32 ビット算術結果を生成でき、SPARC-20 ワークステーションより推論で 25 倍、訓練で 20 倍高速だった。訓練には 16 ビットでは不十分だったため、代わりに 16 ビットワードを 2 つ使い、訓練時間は 2 倍になった。この欠点を克服するため、重みの更新に費やす時間を減らす 32-1000 データセットの「bunch」（バッチ）を導入し、1 ワードでバッチを使わない訓練より高速になった。

より新しい DianNao ファミリーの NN アーキテクチャは、NN アプリケーションに現れるメモリアクセスパターンを効率よく支援するアーキテクチャにより、チップ内と外部 DRAM の両方へのメモリアクセスを最小化する [Keu16, Che16j]。すべて 16 ビット整数演算を使用し、すべての設計がレイアウトまで行われたが、チップは製造されていない。初代 DianNao は 64 個の 16 ビット整数積和演算ユニットのアレイと 44 KB のオンチップメモリを使用し、面積 3 mm²（65 nm）、動作周波数 1 GHz、消費電力 0.5W と推定される [Che14b]。このエネルギーの大部分は重みの DRAM アクセスに費やされたため、後継の DaDianNao（「big computer」）は 36 MiB の重みをチップ上に保持する eDRAM を備える [Che14a]。目的は、マルチチップシステムに十分なメモリを搭載し、外部 DRAM アクセスを回避することだった。その後の PuDianNao（「general computer」）は、サポートベクターマシンなど、DNN 以外のより伝統的な機械学習アルゴリズムを対象とする [Liu15]。別の派生である ShiDianNao（「vision computer」）は CNN を対象とし、アクセラレータをセンサーへ直接接続することで DRAM アクセスを回避する [Du15]。

Convolution Engine も、画像処理用 CNN に焦点を当てている [Qad13]。この設計は 64 個の 10 ビット積和演算ユニットを配備し、45 nm で 800 MHz 動作と推定される Tensilica プロセッサをカスタマイズする。SIMD プロセッサよりエネルギー面積効率が 8X-15X 高く、特定カーネル専用に設計したカスタムハードウェアの 2X-3X 以内になると予測されている。

Fathom ベンチマーク論文は、GPU の推論が CPU よりはるかに高速であるという、我々と矛盾するように見える結果を報告している [Ado16]。しかし、同論文の CPU と GPU はサーバークラスではなく、CPU は 4 コアしかなく、アプリケーションは CPU の AVX 命令を使用せず、応答時間の上限もない（[表 4](#table-04) を参照）[Bro16a]。

Catapult は、DNN の支援に再構成可能性を用いた最も広範に配備されている例であり、多くの研究で提案されてきた [Far09, Cha10, Far11, Pee13, Cav15, Zha15]。彼らが GPU ではなく FPGA を選んだのは、消費電力に加えて、レイテンシに敏感なアプリケーションが GPU にうまくマッピングされないリスクも減らすためだった。FPGA は、検索、圧縮、ネットワークインターフェースカードなど、ほかの用途にも転用できる [Put15]。TPU プロジェクトも実際には FPGA から始まったが、当時の FPGA は当時の GPU と比較して性能面で競争力がなく、TPU なら GPU と同等以上に高速でありながら大幅に低消費電力にでき、FPGA と GPU の双方に対して大きな利点を得られる可能性があると分かったため、FPGA を断念した。

Catapult が初めて発表されたのは 2014 年だが [Put14]、TPU と同時期の 2015 年に 28-nm Stratix V FPGA をデータセンターへ配備したため、TPU と同時代である。Catapult はクロック周波数 200 MHz、3,926 個の 18 ビット MAC、5 MiB のオンチップメモリ、11 GB/s のメモリ帯域幅を備え、25 Watts を使用する。TPU はクロック周波数 700 MHz、65,536 個の 8 ビット MAC、28 MiB、34 GB/s を備え、通常 40 Watts を使用する。Catapult の改訂版はより新しい FPGA を使用し、2016 年により大規模に配備された [Cau16]。

Catapult V1 は、シストリック行列乗算器を用いて CNN を 2.1 GHz・16 コア・デュアルソケットサーバーより 2.3X 高速に実行する [Ovt15]。Catapult V2 の次世代 FPGA（14-nm Arria 10）を用いれば、性能は 7X まで向上し、より慎重にフロアプランニングすれば 17X に達する可能性もある [Ovt15a]。単純比較はできないが、現行 TPU ダイは、ある程度高速なサーバーに対して CNN を 40X-70X で実行する（[表 2](#table-02) と [表 6](#table-06)）。おそらく最大の違いは、最高性能を得るために、低水準のハードウェア記述言語 Verilog で長いプログラムを記述しなければならないこと [Met16, Put16] と、高水準の TensorFlow フレームワークを用いて短いプログラムを記述することの差である。つまり、再プログラム可能性は FPGA ではファームウェアに由来するのに対し、TPU ではソフトウェアに由来する。

TPU の配備後に発表された最近の研究は、重みとデータが非常に小さい、またはゼロである場合を最適化して DNN を高速化する。開発日程が厳しかったため TPU にそのような最適化を組み込めなかったが、我々の研究でも同じ機会を見いだしていた。Efficient Inference Engine は、まず非常に小さな値を除外する別工程によって重みの数を約 10 分の 1 に減らし [Han15a]、続いて Huffman 符号化によってデータをさらに縮小し、推論性能を向上させる [Han16a]。Cnvlutin [Alb16] は、活性化入力がゼロの場合—おそらく一部には負の値をゼロへ変換する ReLU 非線形関数のため、その割合は 44% である—に乗算を省略し、性能を平均 1.4 倍改善する。

Eyeriss は新しい低消費電力データフローアーキテクチャであり、ランレングス符号化によってゼロを利用してメモリフットプリントを減らし、入力がゼロのときに計算を省略して電力を節約する [Che16c]。Eyeriss の用語では、TPU の畳み込み層は C と M を行列ユニットの行と列へマッピングし、1 パスの実行に HWN サイクルを要する。C/M が大きい場合、層の処理には RS パスかかる。C/M が小さい場合は、いくつかの手法によってパス数を減らし利用率を改善する。（詳細はオンラインの参考文献 [Ros15, Ros15a, Ros15b, Ros15c, Tho15, You15] にある。）

Minerva はアルゴリズム、アーキテクチャ、回路の分野を横断する協調設計システムであり、一部には値の小さい活性化データを枝刈りし、一部にはデータを量子化することで、消費電力を 8X 削減する [Rea16]。[Gup15] は、推論ではなく訓練に 16 ビット固定小数点演算を用いることを検討する。ほかの研究では、計算中にアナログ回路を利用して DNN 計算の低精度性を活用し、エネルギーと性能を改善する [Lik16, Sha16b]。Cambricon は、命令セットを DNN に合わせることでコードサイズを削減する [Liu16]。最近の研究では NN 向けプロセッサ・イン・メモリアーキテクチャが検討されている [Chi16, Kim16a]。

TPU とこれらのアーキテクチャの一部を比較すると、次のようになる。

- [Che14b] は DRAM から入力バッファと重みバッファへデータを DMA 転送する。それらは、乗算、加算、非線形関数を実行する 3 段パイプライン NFU に読み出され、結果は出力バッファを経て DRAM へ送られる。NFU はストレージを持たず、シストリックでもない。
- [Gup15] は、部分和をシストリックアレイに格納しながら、行列の両入力をストリーミングしているように見える。TPU は、もう一方の入力と活性化前の部分和をストリーミングしながら、重み行列タイルを格納する。TPU は確率的丸めをサポートしない。
- [Zha15] は、TPU 行列ユニットの 4x2 版に相当する計算ユニットで構成される。ASIC では、入出力バッファをこれらの計算エンジンへ接続するクロスバーの配線コストが大きくなる。[Zha15] において、計算エンジンの結果を結合する追加のリダクションに対するアーキテクチャ支援が見られなかったことは意外である。

[Gup15, Che14b, Zha15] はいずれも計算中に活性化を DRAM へ格納するが、TPU の Unified Buffer は通常動作中に DRAM への退避や再ロードが起きない容量を備える。

## 10 結論

I/O バス上にあり、比較的少ないメモリ帯域幅が TPU の利用率を制限し、6 つの NN アプリケーションのうち 4 つがメモリ律速であるにもかかわらず、大きな数の小さな割合は、それでも比較的大きくなり得ることを Roofline 性能モデルが示している。この結果は、Amdahl の法則に対する「Cornucopia Corollary」を示唆する。巨大で安価な資源は、利用率が低くても高くコスト効率のよい性能を実現できる。

TPU は、K80 GPU の 32 ビット浮動小数点データパスに比べて 8 ビット整数シストリック行列乗算器のエネルギーと面積が 1 桁小さいことを活用し、比較的小さなダイで K80 の半分未満の電力しか使わずに、25 倍の MAC（65,536 個の 8 ビット対 2,496 個の 32 ビット）と 3.5 倍のオンチップメモリ（28 MiB 対 8 MiB）を搭載する。この大容量メモリはアプリケーションの演算密度を高め、豊富な MAC をさらに十分に活用できるようにする。

アーキテクチャ研究コミュニティでは近年 CNN が重視されているが、CNN は我々のデータセンターを代表する NN ワークロードの約 5% にすぎず、MLP と LSTM により注意を向けるべきであることが分かった。歴史の繰り返しであり、多くのアーキテクトが浮動小数点性能へ集中していたのに、主流ワークロードの大半は整数演算が支配的だった状況に似ている。

1 秒当たり推論数（IPS）は基盤ハードウェアより NN に左右されるため、NN プロセッサに対する IPS は、CPU や GPU に対する MIPS や MFLOPS よりさらに不適切な単一性能指標であることが分かった。

さらに、推論アプリケーションはユーザー向けアプリケーションの一部であることが多いため、厳しい応答時間制限があり、NN アーキテクチャは 99 パーセンタイルのレイテンシ期限に対応しながら良好に動作する必要があることも分かった。K80 は訓練に優れているかもしれないが、我々のワークロードの推論では平均して Haswell よりわずかに高速なだけである。おそらくレイテンシよりスループットを重視しているためであり、これは我々の推論アプリケーションの厳格な応答時間期限と相反する。

TPU ダイは、MAC とオンチップメモリの優位性を活かし、ドメイン固有 TensorFlow フレームワークで記述された短いプログラムを K80 GPU ダイの 15 倍の速度で実行する。その結果、性能/総所有コストと相関する性能/Watt では 29 倍の優位性を得る。Haswell CPU ダイと比べると、対応する比率は 29 と 83 である。将来の CPU と GPU は確実に推論を高速化するだろうが、2015 年頃の GPU メモリを用いて再設計した TPU なら 2-3 倍高速になり、性能/Watt の優位性を K80 に対して約 70、Haswell に対して 200 まで高められる。

要約すると、TPU が成功した理由は、大きいが大きすぎない行列乗算ユニット、大容量のソフトウェア制御オンチップメモリ、ホスト CPU への依存を減らす推論モデル全体の実行能力、99 パーセンタイル応答時間制限に適することが実証された単一スレッドの決定論的実行モデル、2013 年だけでなく 2017 年の NN にも対応できる柔軟性、大きなデータパスとメモリを備えながら小型で低消費電力のダイを可能にした汎用機能の省略、量子化されたアプリケーションでの 8 ビット整数の使用、そしてアプリケーションが TensorFlow で記述されていたことで、まったく異なる TPU ハードウェア上で良好に動作するよう書き直すことなく、高性能のまま容易に TPU へ移植できたことである。

商用製品間で 1 桁の差がつくことはコンピュータアーキテクチャではまれであり、TPU はドメイン固有アーキテクチャの典型となるかもしれない。さらに基準を引き上げる後継機を多くの人々が構築すると期待している。
