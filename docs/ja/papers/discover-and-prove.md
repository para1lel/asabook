## 概要

ほとんどの ATP ベンチマークは、最終回答を形式的な文に埋め込んでいる。本稿ではこの慣例を「Easy Mode」と呼ぶ。この設計は、人間の競技者が直面する問題に比べてタスクを簡単にするため、モデル能力を過大評価するおそれがある。本稿では、より厳格で現実的な設定を「Hard Mode」と呼ぶ。システムは形式的証明を構成する前に、回答を独力で発見しなければならない。Hard Mode の研究を可能にするため、本稿は 2 つの貢献を行う。第一に、広く使われている 2 つの ATP ベンチマークを専門家が再注釈した Hard Mode 版、MiniF2F-Hard と FIMO-Hard を公開する。第二に、Discover And Prove（*DAP*）を提案する。これは、明示的な自己省察を伴う LLM の自然言語推論で回答を発見し、Hard Mode の文を既存の ATP 証明器が扱える Easy Mode の文へ書き換えるエージェント型フレームワークである。*DAP* は最高性能を更新した。CombiBench では、解けた問題数を 7 問（従来の SOTA、Pass@16）から 10 問へ増やした。PutnamBench では、Hard Mode で 36 個の定理を形式的に証明した最初のシステムとなった。同時に、形式的証明器が 10% 未満しか扱えない同じ問題で、最先端 LLM の回答精度が 80% を超えることも明らかになった。この大きな隔たりは、Hard Mode ベンチマークだからこそ測定できる。

## 1 はじめに

AI による数学問題の解決は、教育や数学研究などへの具体的な応用が期待できることに加え、高度に抽象的な数学問題に取り組むには、複雑な現実世界のタスクへ汎化・転移しうる能力が必要になることから、大きな研究関心を集めている。こうした能力には、計画、探索、演繹的推論、帰納が含まれる [Yan24k]。数学タスクのなかでも、競技数学の問題、とりわけ国際数学オリンピック（IMO）水準の問題が特に注目されてきた。このような問題は、数値計算や単純な公式の適用だけでは解けない。通常、抽象化とモデル化、厳密な論理的議論が求められ、直観や創造性が必要になる場合も多い。そのため、IMO 水準の問題を解く能力は、AI にとって重要な到達点だと広く考えられている [Yan24k]。

数学問題を解く既存の手法は、非形式的手法と形式的手法の 2 種類に大別できる。非形式的手法は、大規模言語モデル（LLM）の強い推論能力を利用して自然言語で数学問題を解く。一方、形式的手法は Lean [Mou21] や Isabelle [Nip02] などの形式言語で解答を表す。形式的手法の主な利点は、形式言語で書かれた証明を証明支援プログラムが自動的かつ厳密に検証できることにある。2024 年の国際数学オリンピック（IMO）に参加した AI システムは形式的手法を用いていた [Alp24]。しかし 2025 年の IMO までには、評価されたシステムの大半が非形式的手法へ移行していた [Luo25i, Hua25h, Wei25i, Hua25i]。

現在の形式化では、証明すべき文に最終回答を直接埋め込むことが多い。本稿ではこれを「Easy Mode」と呼ぶ。Easy Mode は、形式的な問題解決タスクの難しさを大幅に下げる可能性がある。この問題に対処するため、先行研究である PutnamBench [Tso24] と CombiBench [Liu25ad] にならい、回答を求める問題を Lean 4 で 2 つの独立した目標（2 つの異なる `sorry`）として符号化する。この「Hard Mode」設定では、モデルは最初の `sorry` を回答で置き換えた後、残った目標に対する通常の形式的証明を生成しなければならない。この設定により、人間の競技者が自力で発見しなければならない追加情報が形式的な文へ埋め込まれることを防ぐ。定義上、*Hard Mode* では、人間の競技者が推論によって導くべき量を形式的な文の前提として与えてはならず、AI システムが独力で発見しなければならない。本稿では Lean コミュニティの慣例に従い、「Hard Mode」という用語を使う [+hard-mode-name]。CombiBench [Liu25ad] は同じ区別を「without solution」と「with solution」、PutnamBench [Tso24] は「no answer」と「with answer」と呼んでいる。Easy Mode と Hard Mode の違いを示す例を[図 1](#figure-01)に示す。本稿では、広く使われている 2 つの ATP 競技データセット MiniF2F と FIMO を専門家に再注釈してもらい、MiniF2F-Hard と FIMO-Hard を作成した。再注釈の際には、既存の形式的ベンチマークで知られていた整合性の問題も修正した [Wan25l, Lin25j]。

[+hard-mode-name]: [Lean コミュニティでの議論](https://leanprover.zulipchat.com/#narrow/channel/208328-IMO-grand-challenge/topic/IMO.202025.20problem.20statements)。

Hard Mode の問題を解くため、本稿は Discover and Prove（*DAP*）を提案する。これは Hard Mode ATP タスクに向けた、完全にオープンソースのエージェント型 ATP フレームワークである。*DAP* は発見モジュールと証明モジュールの 2 要素からなる。オープンソース LLM に推論と回答を生成させ、自己検証手順によって反復的に改善させる。発見モジュールが妥当な回答を「発見」して最初の `sorry` を埋めると、証明モジュールは従来の ATP 証明器を呼び出し、完全な形式的証明の生成を試みる。*DAP* は最高性能を達成した。PutnamBench の全データセットで評価すると、*DAP* は合計 36 問を解いた。Hard Mode 版がある解答型問題では 19 問を解いており、本稿の知る限り、この Hard Mode 評価設定における PutnamBench 初の公開結果である。CombiBench Hard Mode では 10 問を解き、8 問だった従来の最高性能（Kimina-Prover Preview）を大きく上回った。

本稿の貢献は 3 点である。

1. 広く使われている 2 つの ATP 競技データセット MiniF2F と FIMO を再注釈し、人間の競技者と AI システムに提示されるタスクを揃えた。Easy Mode による不一致を取り除き、AI の数学能力を評価するための、より原則に沿った基盤を提供する。
2. オープンソースのエージェント型 Hard Mode ATP フレームワーク *DAP* を提案する。単純で明快な設計により、*DAP* は PutnamBench と CombiBench で最高性能を達成する。
3. 提案する *DAP* 証明器の 2 モジュールが全体性能へそれぞれどの程度寄与するかを定量化する。結果は、競技水準の数学問題を解く際の非形式的手法と形式的手法の相対的な長所を明らかにする。

## 2 関連研究

<span id="figure-01"></span>

![図 1．自動定理証明における Easy Mode と Hard Mode の設定](../../papers/discover-and-prove/figure-01.png)

**図 1．** 自動定理証明における Easy Mode と Hard Mode の設定の違い。図の例は、1 つの IMO 問題を 2 通りの形式で Lean 4 に形式化したものである。この例は、再注釈によって修正する意味的不整合の種類を示すため、意図的に選んだ。Easy Mode の形式化は、$x$ が特定の範囲内にあることしか証明せず、その範囲内のすべての値が実現可能であることを示していない。そのため、元の必要十分条件を一方向の含意へ弱めている。これに対して、本稿の Hard Mode 形式化は回答を集合で表し、自然言語の問題が要求する内容を形式的な文に完全に反映している。

<span id="section-2-1"></span>

### 2.1 AI システムによる数学問題解決

CoT プロンプティングと RLVR 学習により、LLM の数学推論は大きく進歩した。最先端モデル（OpenAI o1 [Ope24h]、DeepSeek R1 [Dee25c]、Google Gemini 2.5 Pro [Com25a] など）は、GSM8K [Cob21]、MATH-500 [Lig23]、AIME 2024/2025 といった広く使われる数学ベンチマークで、飽和に近い性能を達成している。

非形式的手法の欠点の 1 つは、生成される解答過程を自動検証することが非常に難しい点である。生成された証明が妥当か判断するには、領域の専門家が注意深く読み、微妙な誤りを見つけなければならず [Lig23]、大規模には実施できない。このため、非形式的システムは通常、最終的な数値または記号による回答だけを求め、正解との直接比較で検証できる問題に使われる [Wen25a]。

<span id="section-2-2"></span>

### 2.2 自動定理証明

自動定理証明（ATP）の主な強みは、証明支援系が形式的証明を厳密かつ自動的に検査できることにある [You25, Wan23j]。形式的手法は形式データの不足という課題に直面してきたが [Xin25]、より大規模な LLM と探索計算量のスケーリングによって急速に進歩した [Xin25b, Che25h]。Kimina-Prover Preview [Wan25l]、DeepSeek-Prover-V2 [Ren25b]、Goedel-Prover-V2 [Lin25j] などの近年のシステムは、MiniF2F [Zhe22a] ベンチマークで大きく進歩している。Seed-Prover [Che25h] は、引理単位で証明全体を推論し、Lean コンパイラのフィードバック、証明済みの引理、自己要約を使って反復的に証明を改善するモデルである。PutnamBench で 50% を超え、MiniF2F を飽和させた。DSP [Jia23d] は自然言語の証明草稿と構造化されたスケッチで形式的定理証明器を導き、DSP+ [Cao25d] は現代の推論モデルでこの方式を復活させた。DAP と DSP/DSP+ の主な違いは 3 点あり、詳しくは[第 10 節](#section-10)で比較する。

Lean ベースの ATP を対象とするエージェント型フレームワークも複数提案されている [Tha23, Ana24, Bab25, Wan25an]。詳しくは[第 9 節](#section-9)を参照。

最終回答を求める非形式的な数学問題を扱うため、先行研究は通常、求解問題を証明問題へ変換する。すなわち、目的の回答を形式的な文へ埋め込み、その文を証明する [Zhe22a, Liu23s, Xio23a]。この慣行には 2 つの問題がある。第一に、回答を文に埋め込むと、問題本来の難しさが下がりうる。多くの求解問題では、回答を発見することが主な難所であり、回答が分かった後で帰結を証明することではないため、回答の提示は強いヒントになる。第二に、得られた形式的な文が、人間の競技者が直面するタスクと意味的に完全には一致しない場合がある。FMC [Xie25e] や OlympiadBench [He24d] などの分析が指摘したとおり、既存の形式的ベンチマークには不整合があり、一部の形式的な文は人間の解答者が達成すべき目標の一部しか捉えていないことがある。

<span id="section-2-3"></span>

### 2.3 形式化とデータキュレーション

高品質な形式データセットは少なく、多大な専門作業を要する [Xin25]。MiniF2F [Zhe22a] は最も広く使われている ATP ベンチマークの 1 つで、数学オリンピック、高校、大学学部の授業から形式化された文を収録する。Kimina-Prover Preview [Wan25l] は、その一部に修正を提供している。FIMO [Liu23s] は IMO ショートリスト問題から構築されているが、公開された Lean 4 版がなかったため、近年の研究での採用を妨げていた。PutnamBench [Tso24] は Putnam Competition 問題を手作業で形式化したもので、初めて「with answer」と「no answer」の両方の評価設定を提供した。CombiBench [Liu25ad] は、中学校水準から IMO・大学水準までの組合せ論 100 問を収録し、他のベンチマークが数論と代数に偏っている点を補う。IMOSLLean4 [San25] と IMO-Steps [You24] は完全な証明も提供する。データ不足を緩和するため、自動形式化手法 [Wu22a] は非形式的な問題を形式的な文へ自動翻訳する。代表的なリソースには Lean Workbook [Yin25a]、NuminaMath-LEAN [Wan25l]、Goedel-Pset-v1 [Lin25i]、FormalMATH [Yu25j] がある。出力は通常 LLM-as-a-judge [Yin25a] だけで検証されるため、意味的な正しさを保証できず、評価ベンチマークよりも証明器の RL 学習段階 [Wan25l, Xin25] で使われることが多い。本稿の知る限り、すべての自動形式化手法は Easy Mode に従い、目的の回答を生成する文へ直接埋め込んでいる。

## 3 方法

<span id="figure-02"></span>

![図 2．DAP フレームワークの主要フロー](../../papers/discover-and-prove/figure-02.png)

**図 2．** 主要フローチャート。数学問題はまず発見モジュールで処理され、解答が生成される。次に、書き換え段階でその解答を Easy Mode の文へ組み込む。オレンジ色の円は推論 LLM、青色の円は定理証明器（別の LLM）を表す。

2 つの `sorry` プレースホルダを含む Hard Mode の Lean 4 定理を証明するため、Discover and Prove（*DAP*）フレームワークを提案する。これは回答と詳細な証明の両方を与えることで、人間の数学者の取り組み方を模倣する。名称が示すように、*DAP* は発見モジュールと証明モジュールの 2 つの主要モジュールからなる。発見モジュールは自然言語で動作し、問題の正しい解答を見つけた後、元の Hard Mode の Lean 4 文を Easy Mode の文へ変換する。この変換により、`sorry` プレースホルダは 2 つから 1 つに減り、従来の自動定理証明器で解ける文が 1 つだけ残る。続いて、証明モジュールが Lean 4 形式言語を使い、発見モジュールが見つけた解答の厳密な証明を構成する。DAP フレームワークの完全なワークフローを[図 2](#figure-02)に示す。

<span id="section-3-1"></span>

### 3.1 発見モジュール

発見モジュールは元の数学問題を解き、その解答を Lean 4 Hard Mode 文の最初の `sorry` プレースホルダへ代入して、証明モジュールに渡す。この手順は、回答を仮定して証明探索を導くという、人間の問題解決を模している。OpenAI o1 [Ope24h] や DeepSeek R1 [Dee25c] などの長い Chain-of-Thought が登場してから LLM の推論能力は大きく向上したものの、極めて難しい IMO 水準の問題を 1 回で解くことは依然として実現していない。現在の研究によれば、最先端 LLM は深い推論を支えるため、情報検索、計算機、外部メモリなどの補助ツールを必要とすることが多い [Nak21, Luo25c, Yua24d]。LLM 推論システムの先行研究 [Hua25h] に着想を得て、本稿では、高度な推論モデルが解答手順を生成し、自己検証によって精度を高める比較的単純な構成を採用する。具体的な手順は次のとおりである。

1. **解答生成：** 自然言語の数学問題を与え、モデルの推論能力を使って、解答過程を記述する詳細な思考連鎖を生成する。
2. **自己検証：** 推論 LLM に手順中の潜在的な誤りを調べさせ、誤りの位置を示すエラーレポートを生成させる（代表例は[第 11.5 節](#section-11-5)）。自己検証で誤りが見つからなければ手順 4 へ進み、見つかった場合は手順 3 へ進む。
3. **自己修正：** 推論 LLM に、エラーレポートで指摘された誤りを修正した解答を生成させる。
4. **書き換え：** Lean 4 Hard Mode の文、自然言語の問題、モデルの思考連鎖による推論を使い、プレースホルダを 1 つだけ含み、自動定理証明に適した Lean 4 文を生成するよう LLM に指示する。

4 手順はいずれも綿密に設計した LLM プロンプトで実装し、[第 11 節](#section-11)に示す。発見モジュールが重要なのは、不正解が、最初から証明不能な誤った形式的な文につながることが多いためであり、モデルには深い推論と信頼できる自己検証が必要になる。このフレームワークは、再現を容易にし、ベースラインとして利用できるようオープンソースで公開する。発見モジュールには、自然言語の数学推論で高い性能を示すオープンソースモデル GPT-OSS-120B を用いる。原理上、強い数学推論能力と基本的な Lean の知識を併せ持つ任意のモデルをこのフレームワークに組み込める。

<span id="section-3-2"></span>

### 3.2 証明モジュール

発見モジュールが Hard Mode の文を Easy Mode 形式へ変換すると、タスクは従来の定理証明器で扱える標準 ATP 問題になる。そのため、変換後の問題には最先端のオープンソース定理証明器 Goedel-Prover-V2（32B）を用いる。推論モデルと ATP モデルを分離したため、基盤モデルのどれが進歩しても提案フレームワークを改善できる。また、証明支援言語で形式的な数学解答を生成する LLM を評価するための、現代的なベースラインにもなる。

<span id="section-4-1"></span>

### 4.1 注釈方針

再注釈は 3 つの方針に基づく。

**意味的正確性：** 専門家が注釈したデータセットは小規模だが信頼できる一方、自動形式化データセットは大規模だが検証できない。現在の検証手法（LLM-as-a-judge [Yin25a]、BEq [Liu24y]）では、元の自然言語問題との意味的整合性を保証できない。そのため、専門家が注釈したデータ源から出発し、各文を手作業で再検査する。

**解釈可能性：** 形式的な文は、人間の競技者に求められることを正確に反映すべきである。発見すべき量を前提として与えてはならず、証明すべき主張はすべて目標に含めなければならない。現在のベンチマークは、（1）最終回答を文に符号化する、（2）証明目標を元の目標の真部分集合へ弱める、（3）人間の競技者に与えられない前提を加える、という 3 通りの違反を繰り返している。代表例を[図 1](#figure-01)に示す。本稿では一貫して IMOLean [Mye25] の慣例に従った。

**一貫性：** 形式化のスタイルは ATP の成功率に実質的な影響を与える [Lin25i]。したがって、注釈者が任意の形式化を選べると、評価に偏りが入る。本稿では、「特定の英語版へ忠実に従おうとするより、慣用的な Lean の方向へさらに進む」という慣用的 Lean を重視した統一規約を提示した。これは、単一の標準的な文を提供する IMOLean [Mye25] の慣行と一致する。

<span id="section-4-2"></span>

### 4.2 データ選択

これらの不足へ対処するため、人間の専門家が注釈した 2 つのデータセット MiniF2F [Zhe22a] と FIMO [Liu23s] を Lean の専門家に再注釈してもらった。ProofNet も専門家が注釈した高品質なデータセットだが、自然言語項目がすべて本質的に証明型であるため、対象から除外した。注釈者は全員、Lean に 1 年以上携わった経験を持つ。MiniF2F と FIMO はもともと専門家が作成している。本稿では文献 [Wan25l] に記録されたエラーレポートを踏まえて再検査し、各問題を 2 人の専門家に独立して注釈してもらい、ラベルを相互検証して正しさを確保した。

<span id="section-4-3"></span>

### 4.3 データセット品質の修正

Hard Mode 版の作成に加え、注釈者は自明ではない 3 種類の品質改善を行った。詳細は[第 12 節](#section-12)に示す。**FIMO の Lean 4 への移植：** FIMO の全問題を Lean 3 から移植し、コンパイル可能で意味的に忠実であることを検証した。**意味的不整合の修正：** miniF2F で約 $15$ 件、FIMO で約 $20$ 件の誤りを発見・修正した。誤りは 4 種類に分かれる（[表 5](#table-05)）。**Hard Mode に向けた言い換え：** 未知の値を自由パラメータに変更し、明示的な付帯条件を追加した。[図 3](#figure-03)（[第 13 節](#section-13)）を参照。

## 6 議論

<span id="section-6-1"></span>

### 6.1 エージェントの有効性に関するアブレーション

高度な推論 LLM は、本質的に強い自己省察能力を持つ [Wen25a]。したがって、自己検証と自己修正の仕組みを明示的に導入すると、不要な推論オーバーヘッドを課す可能性がある。エージェントモードが有効になる条件を調べるため、PutnamBench、CombiBench、MiniF2F-Hard、FIMO-Hard でエージェントモードを無効にして実験した。結果は[表 2](#table-02)に示す。

エージェントによる明示的な自己検証と自己修正を無効にすると、PutnamBench のような難しいデータセットで性能が大幅に低下した。一方、CombiBench や MiniF2F のような難度の低いデータセットでは性能が低下しなかった。これは、こうしたデータセットに、推論 LLM がほとんど困難なく解ける比較的単純な問題（中学校の教科書問題など）がかなり含まれているためだと推測する。このような場合、明示的な自己検証を加えることで、モデルの指示追従行動が意図せず過度に支配的になり、過剰な自己疑念を招いて解答へ余分なノイズを加える可能性がある。

<span id="table-03"></span>

![表 3．正解が確定している Hard Mode 問題における発見モジュールの性能](../../papers/discover-and-prove/table-03.png)

**表 3．** 正解が確定している Hard Mode 問題の部分集合で、自然言語として提示された数学問題を解く発見モジュールの性能を評価した。

正解があり、自然言語の応答を直接評価できる Hard Mode 問題について、発見モジュールの精度を分析した（[表 3](#table-03)）。エージェント型の自己省察がなくても、Putnam 問題では約 78% の正解率を達成し、MiniF2F では性能が飽和に近い。難度の低い問題では、推論 LLM の 1 回の生成ですでに高い精度が得られるため、明示的な自己検証と自己修正は不要になりうる。しかし、PutnamBench や FIMO-Hard のような難しいベンチマークでは、こうしたエージェント要素が依然として重要である。CombiBench と FIMO における発見モジュールの詳細な失敗モード分析は[第 14 節](#section-14)に示す。

自己検証の反復回数を除去する実験では、10 回で飽和に近づき、30 回（標準設定）はわずかな改善しか加えない。[第 15 節](#section-15)を参照。

<span id="section-6-2"></span>

### 6.2 書き換え戦略のアブレーション

*DAP* の中心的な設計判断は、2 段階の書き換えパイプラインである。発見モジュールがまず自然言語で回答を導き、その後で Hard Mode の文を ATP 証明器用の Easy Mode の文へ変換する。この設計を検証するため、3 つの代替戦略を比較する。**No Rewriting：** 2 つの `sorry` プレースホルダを含む Hard Mode 問題文を、書き換えず ATP 証明器へ直接入力する。**Straight Rewriting：** 発見モジュールを取り除き、1 つの LLM に回答の発見と書き換え後の Easy Mode 文の生成を 1 ステップで同時に行わせる。**Proposed Rewriting（Ours）：** 発見モジュールがまず回答を見つけ、書き換え段階がその回答を使って文を変換する。

<span id="table-04"></span>

![表 4．3 つの書き換え戦略の Pass@32 比較](../../papers/discover-and-prove/table-04.png)

**表 4．** 3 つの書き換え戦略の Pass@32 比較。No Rewriting と Straight Rewriting の結果は、見せかけの証明を除外するため手作業で検証した。

[表 4](#table-04)の結果から、3 つの主要な観察が得られる。

**No Rewriting は Hard Mode 問題ではほとんど機能しない。** モデルは Hard Mode ATP タスクで学習しておらず、形式体系の中で回答の発見と証明を同時に求められると、分布外性能が大きく低下するためだと考える。

**Straight Rewriting は改善せず、悪化することさえある。** 回答発見と形式化を 1 ステップで同時に扱わせると、両方に失敗することが多い。非形式的な数学推論と、構文的に正確な Lean コード生成を同時に課すことで、ほとんどのベンチマークで性能が低下する。

**見せかけの証明が残る差を説明する。** No Rewriting と Straight Rewriting の両方で、*見せかけの証明*（不正な近道）が頻繁に見られた。モデルは解答時に `abbrev solution` 定義を含む Lean 文全体を確認できるため、問題の条件を証明へ直接コピーし、本当の数学推論を避けることがある。`fimo_2009_algebra_p3` の具体例を[図 4](#figure-04)（[第 16 節](#section-16)）に示す。*DAP* の分離設計はこの近道を防ぐ。証明器が受け取るのは、回答のプレースホルダを公開しない、書き換え後の Easy Mode 文だけであるため、このような不正はできない。

*DAP* のモジュール設計では、発見モジュールと証明モジュールを独立して交換できる。軽量な小型オープンソースモデルと、より強力な Aristotle API の両方を使った実験により、パイプラインは資源制約が変わっても機能し、より強い非形式推論モデルがさらに性能を高めることを確認した（[第 17 節](#section-17)）。

<span id="section-6-3"></span>

### 6.3 自然言語推論か形式言語推論か

自然言語推論と形式言語推論のどちらを選ぶかは、複雑な問題解決における AI の進歩にとって難しい問題である。OpenAI o1 と DeepSeek R1 に代表される Long Chain-of-Thought や人間のフィードバックからの強化学習（RLHF）など、自然言語推論における近年の革新は、LLM の能力を大きく高めた。自然言語表現は非常に高い経験的上限を示しうることが分かっており、AIME のような難しいデータセットでも性能が急速に飽和した [Ope24h, Wen25a]。2025 年の IMO では、AI システムの大半が形式表現から自然言語表現へ移行し、創造的な推論問題を解くことに成功した。複数の解答が金メダル水準に達した。対照的に、Seed Prover [Che25h] や Aristotle [Ach25] などの形式言語システムは、大規模な計算探索によってメダル水準の結果を達成し、一部の解答は正式な提出期限後に完成した。

本研究は、自然言語推論と形式言語推論を比較する中立的なベンチマークとして Hard Mode ATP を調べる。同様の乖離が観察された。自己省察を備えた最先端 LLM は PutnamBench で 80% を超える一方、形式言語システムは 10% 未満である

自然言語推論は実験的に高い性能を示すが、形式的な数学言語は今後の数学推論 AI システムにも不可欠であり続ける。自然言語の証明には、形式検証なしでは発見しにくい微妙な誤りが入りやすく、教育や高度な数学研究といった重要な応用での実用性を大きく制限する。Putnam や FIMO などの結果が示すように、形式的な数学推論にはなお大幅な進歩が必要である。そのため、自然言語手法と形式言語手法の長所を統合し、既存の性能差を埋めることが、有望な将来の研究方向だと提案する。

<span id="section-7"></span>

## 7 結論

本研究は、現在の Easy Mode 自動定理証明設定に、意味的正確性、解釈可能性、透明性の問題があることを明らかにした。統一された規約のもとで人間の専門家が手作業で注釈した Hard Mode の形式的な文は、数学競技の参加者が直面する問題解決要件をより正確に反映すると論じる。

Hard Mode ATP ベンチマークの不足に対処するため、Lean 4 の専門家に高品質データセットを Hard Mode 形式へ再注釈してもらい、MiniF2F-Hard と FIMO-Hard を作成した。同時に、既存の意味的不整合を修正し、統一された規約を適用した。

Hard Mode 問題に対処するため、複雑な形式的数学問題を解く AI システムの能力を厳密に評価する *DAP* フレームワークを提案した。このフレームワークは PutnamBench と CombiBench で最高性能を達成し、PutnamBench の Hard Mode 設定で初めて進展を報告した。結果は、自然言語推論で回答を導き、形式的手法で証明する組み合わせの有効性を示す。

<span id="section-8"></span>

## 8 制約

本研究の主な制約は、データセット汚染の可能性であり、報告した AI 性能が過大に見積もられているおそれがある。本研究で注釈した miniF2F と FIMO、その元になった自然言語問題（IMO ショートリスト問題など）、その他の関連データセットはインターネット上で公開されている。本研究で使った 2 つの主要 LLM、GPT-OSS-120B と Goedel-Prover-V2 はモデル重みを公開しているが、学習コーパスは公開していない。そのため、これらのデータセットが学習データに含まれていたかを断定できない。

発見モジュールと証明モジュールの性能差を示すことで、本研究は Hard Mode ATP のボトルネックが自然言語推論ではなく形式推論にあることを明らかにした。これは、DSP [Jia23d] のように自然言語推論で形式言語推論を補助する手法が有望であることを示唆する。ただし本研究では、証明モジュールへ渡す自然言語出力は回答候補に限られる。そのため、形式言語推論と自然言語推論の統合は依然として限定的である。理想的には、片方のモダリティが困難に直面したときにもう片方が補助できるよう、2 モジュールがより密接に相互作用すべきである。このような密接で協調的な統合は今後の課題とする。

純粋な証明探索以外にも、Lean ベースの ATP に向けたエージェント型フレームワークが複数研究されている。COPRA [Tha23] は、言語エージェントのループを通して汎用 LLM を Lean 証明の専門家へ変換する。LeanAgent [Ana24] は、高度な数学における LLM の性能を継続的に改善する生涯学習を研究する。ProverAgent [Bab25] は、非形式的モデルで補助定理を提案し、形式的証明を導く。MA-LoT [Wan25an] は、Lean ベースのマルチエージェント型の長い思考連鎖を使い、Lean コンパイラのフィードバックで証明を反復的に修復する。これらのシステムは標準（Easy Mode）ATP タスクを対象とし、設定を直接比較できないため、*DAP* との直接的な実験比較は行わない。

## 10 DAP と DSP/DSP+ の比較

DAP と DSP/DSP+ には 3 つの主な違いがある。第一に、**対象タスク**が異なる。DSP/DSP+ は完全な形式的な文がすでに与えられる標準 ATP を扱うが、DAP は証明の前に回答を発見しなければならない Hard Mode ATP を扱う。第二に、**モジュール間通信**が異なる。DSP は中間推論手順（草稿と証明スケッチ）を形式的証明器へ渡すが、DAP は最終回答だけを書き換え段階へ渡す。回答だけを渡すことで、特定の形式言語の慣用表現への依存を避け、自然言語の解答手順を tactic ベースの Lean 証明へ直接挿入すると不自然になったり逆効果になったりする問題を回避できる [Liu23s]。さらに、DSP の設計は Isabelle のサブゴール構文と密接に結びついているため Lean へ移植しにくい。一方、DSP+ のスケッチ手順は Lean の `have` 文で表せる単一の等式でなければならず、適用範囲を制限する。第三に、**検証設計**が異なる。DAP は証明器へ渡す前に発見モジュール内で自己検証を行う。DSP には自己検証がなく、DSP+ は形式スケッチに構文エラーがある場合だけ修復する。

<span id="section-11-1"></span>

### 11.1 解答生成用プロンプト

````text

* **厳密性を最優先する：** 最も重要な目標は、完全かつ厳密に正当化された解答を作ることである。解答の各手順は論理的に正しく、明確に説明されなければならない。最終回答が正しくても、不備のある推論や不完全な推論から導かれた場合は失敗とみなす。

  * 重要な補題を証明する。
  * 論理的に正しい場合分けによる証明で、1 つ以上の場合を完全に解決する。
  * 問題の数学的対象が持つ重要な性質を確立する。
  * 最適化問題について、上界または下界を証明するが、その境界を達成できることまでは証明しない。
* **すべての数学に TeX を使う：** すべての数学変数、式、関係を TeX の区切り記号で囲む（例：`$n$ を整数とする。`）。

### 出力形式 ###

回答は、以下の節を正確にこの順序で構成しなければならない。

**1. 概要**

結果を簡潔にまとめる。この節には次の 2 つを含めなければならない。

* **a. 判定：** 完全な解答を得たか、部分的な解答を得たかを明確に述べる。
  * **完全な解答の場合：** 最終回答を述べる。例：「問題を完全に解きました。最終回答は……です。」
  * **部分的な解答の場合：** 厳密に証明できた主要な結論を述べる。例：「完全な解答は得られませんでしたが、……を厳密に証明しました。」
* **b. 手法の概要：** 解答を概念的かつ高い水準から説明する。この概要だけで、専門家が詳細を読まずに議論の論理的な流れを理解できるようにする。次を含める。
  * 全体的な戦略の説明。
  * 重要な補題または主要な中間結果について、完全かつ正確な数学的記述。
  * 必要な場合、議論の根幹となる重要な構成や場合分けの説明。

**2. 詳細な解答**

完全な数学的証明を手順ごとに提示する。各手順を論理的に正当化し、明確に説明する。専門家が不足部分を補わずに推論の正しさを検証できるだけの詳細を含める。この節には完全かつ厳密な証明だけを含め、内部的なコメント、代替手法、失敗した試みを含めない。

### 自己修正の指示 ###

最終出力の前に、「手法の概要」と「詳細な解答」を注意深く見直し、明瞭かつ厳密であり、上記のすべての指示へ厳密に従っていることを確認する。すべての文が、最終的な一貫した数学的議論へ直接寄与することを検証する。
````

### 指示 ###

**1. 中核指示**
* 唯一の作業は、与えられた解答に含まれるすべての問題を見つけて報告することです。解答者ではなく**検証者**として行動してください。**見つけた誤りを修正したり、不足部分を補ったりしてはいけません。**

**2. 解答中の問題の扱い方**
手順に問題を見つけた場合、まず以下の 2 種類のいずれかに分類し、その後で指定された手順に従ってください。

* **a. 重大な誤り：**
  証明の論理的な連鎖を壊す誤りです。**論理的誤謬**（例：`A>B, C>D` から `A-C>B-D` を導けると主張すること）と**事実上の誤り**（例：`2+3=6` という計算ミス）の両方を含みます。
  * **手順：**
    * 具体的な誤りを説明し、それが**現在の推論経路を無効にする**と述べます。
    * この誤りに依存する後続手順は確認しません。
    * ただし、解答の残りを調べ、完全に独立した部分を見つけて検証しなければなりません。たとえば、証明が複数の場合に分かれているなら、1 つの場合の誤りによって他の場合の確認を中止してはいけません。

* **b. 正当化の欠落：**
  結論は正しい可能性があるものの、議論が不完全、曖昧、または十分に厳密でない手順です。
  * **手順：**
    * 正当化に何が欠けているか説明します。
    * 議論を続けるため、**その手順の結論を真と仮定する**と述べます。
    * その後、すべての後続手順の検証を続け、残りの議論が正しいか確認します。

**3. 出力形式**
回答は、**概要**と、それに続く**詳細な検証ログ**の 2 つの主要な節で構成しなければなりません。

* **a. 概要**

  * **指摘一覧**：発見した**すべての**問題を箇条書きでまとめます。各項目には次を含めます。
    * **位置：** 問題がある重要な語句または式を直接引用します。
    * **問題：** 問題を簡潔に説明し、**重大な誤り**または**正当化の欠落**に分類します。

* **b. 詳細な検証ログ**
  概要に続けて、中核指示で定義した完全な手順別の検証ログを示します。解答の特定部分に言及するときは、詳細な分析の前に**関連する文を引用**して対象を明確にしてください。

**必要な概要形式の例**
*これは必要な形式を示すための一般的な例です。実際の指摘は、以下に与えられる解答に基づかなければなりません。*

**最終判定：** 解答には重大な誤りが含まれるため、**無効**である。

**指摘一覧：**
* **位置：** 「極限と積分を交換すると、……を得る」

## 14 発見モジュールの失敗モード分析

発見モジュールの限界を理解するため、CombiBench の解答型問題 45 問と FIMO の解答型問題 70 問について、発見モジュールの出力をすべて分析した。この 2 つの問題群は難易度が中程度であり（miniF2F-Hard で見られた飽和を避けられる）、組合せ論、数論、代数という競技数学の幅広い領域を網羅しているため、実際の弱点を診断するのに適している。発見に失敗した事例をすべて手作業で分類し、主なエラーの種類を[表 6](#table-06)にまとめる。

<span id="table-06"></span>

![表 6．FIMO と CombiBench における発見モジュールの失敗モード](../../papers/discover-and-prove/table-06.png)

**表 6．** 自己検証（SV）の有無による、FIMO と CombiBench における発見モジュールの失敗モード分析。各数値は、それぞれの失敗類型が見られた問題数を示す。

**FIMO：数論と代数の難度が高い。** FIMO の多くの問題は、依然としてモデルの能力を超えている。最難関の事例では、自己検証を用いても正解を完全には取り戻せない。関数方程式の問題は特に難しく、検証を行ってもしばしば失敗する。これは、その推論に多段階の代数的変形が必要であり、基礎となる推論を自動的に確認することが難しいためである。

**CombiBench：理解の失敗。** CombiBench では、モデルが問題文を正しく理解していない場合や、元の問題にはない条件を捏造する場合が頻繁に見られた。このような理解の失敗は、自己検証を行っても大幅には減らない。人間には自然な組合せ論の表現であっても、現在の LLM には理解しにくいものがあり、そのため解析や解釈を誤るのではないかと推測する。

**自己検証は役立つが、万能ではない。** 数論と代数の問題では、自己検証によって軽微な計算誤り（$9 \to 4$）と一部の浅い推論の失敗（$4 \to 2$）が目立って減り、算術上の誤りによって失われた正答を取り戻せた。組合せ論では、推論の土台が誤っている事例が $5$ 件から $3$ 件に減ったが、理解の誤りや幻覚は解消されなかった。全体として、自己検証が最も有効なのは、問題を根本的に誤解している場合ではなく、局所的な誤り（たとえば算術上の見落とし）がある場合である。
