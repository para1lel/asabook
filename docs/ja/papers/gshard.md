## 要約

大量の学習データと計算資源を利用できる実際の機械学習応用では、ニューラルネットワークの規模拡大がモデル品質の改善に欠かせない。規模拡大はモデル品質を確実に高める方法だと確認されている一方、計算コスト、プログラミングのしやすさ、並列デバイス上での効率的な実装といった課題が残る。GShard は、軽量なアノテーション API 群と XLA コンパイラの拡張からなるモジュールである。既存のモデルコードをほとんど変更せずに、多様な並列計算パターンを表現できる。GShard の自動シャーディングにより、Sparsely-Gated Mixture-of-Experts を用いた多言語ニューラル機械翻訳 Transformer を 6000 億パラメータ超まで拡張できた。この巨大モデルを 2048 基の TPU v3 アクセラレータ上で 4 日間、効率的に学習し、100 言語から英語への翻訳で従来手法を大きく上回る品質を達成できることを示す。

## 1 はじめに

ニューラルネットワークの規模を拡大すると、幅広い機械学習課題で品質が大幅に向上する [Aro18, Fra18, Kap20, Dev18, Mah18, Bro20c]。コンピュータビジョンでは、モデル容量を増やすことで、さまざまなアーキテクチャの画像分類精度と検出精度が向上してきた [He16, He16a, Ghi19]。自然言語処理でも同様に、Transformer [Vas17b] の規模拡大によって、言語理解タスク [Dev18, Raf19, Bro20c]、言語横断の下流転移 [Dev18, Con19]、大規模多言語ニューラル機械翻訳 [Ari19, Hua19, Sha17] で一貫した改善が得られている。この傾向を受け、近年の研究では、過去の研究が示した学習データ量、モデルサイズ、使用計算量など、規模拡大の成功を左右する要因が詳しく調べられている [Adv17, Hes17, Hes19, Gei20, Kap20]。最終的なモデル品質はデータ量、計算量、モデルサイズとべき乗則の関係にあるが [Hes17, Kap20]、大規模モデルによる品質向上には、実用上のさまざまな課題も伴う。なかでも学習効率、すなわち既存の最良システムを上回るモデル品質を得るために使う計算量と学習時間は、特に重要であるにもかかわらず、しばしば見過ごされる。

**図 1.** MoE モデルを最大 600B まで拡大するにつれて、多言語翻訳の品質（バイリンガルベースラインと比較した平均 $\Delta$BLEU）は向上したが、エンドツーエンドの学習コスト（TPU v3 コア年）は亜線形にしか増加しなかった。モデルサイズを 37.5B から 600B へ 16 倍にすると、計算コストは 6 年から 22 年へ 3.6 倍に増加した。最高の翻訳品質を得た 600B パラメータのモデルは、2048 基の TPU v3 コアで 4 日間学習し、総コストは 22 TPU v3 コア年だった。これに対し、100 個のバイリンガルベースラインモデルをすべて学習するには 29 TPU v3 コア年を要する。本稿で最高品質の密な単一 Transformer モデル（2.3B パラメータ）は $\Delta$BLEU 6.1 を達成し、GPipe [Hua19] を用いて 2048 基の TPU v3 コアで 6 週間学習したため、総コストは 235.5 TPU v3 コア年だった。

### 1.1 スケーリングにおける実務上の課題

ここでは、単一アクセラレータ（GPU や TPU など）のメモリ容量を桁違いに超える巨大モデルを学習する際の、主な実用上の課題を挙げる。

**アーキテクチャ固有のモデル並列化サポート。** TensorFlow [Aba16] や PyTorch [Pas17] など、一般的な深層学習フレームワークは、効率的なモデル並列化アルゴリズムを十分に支援していない。グラフ分割による単純なモデル並列化には対応しているが、ネットワークの逐次依存と勾配ベース最適化のため、デバイス利用率が著しく低下しうる。既存モデルを効率よく拡張するには、モデルコードを専用フレームワークへ移すなど、通常は多大なエンジニアリング作業が必要になる [Sha18a, Hua19]。

**モデルサイズに対して超線形に増える計算コスト。** 深さや幅を増やしてモデルサイズをそのまま拡大すると [Bro20c, Hua19]、通常は学習ステップ時間が少なくとも線形に増える。一般には、層の重みと計算を複数デバイスへ分割するモデル並列化が必要になり、ネットワーク通信のオーバーヘッドとデバイス利用率の低下を招く。デバイス利用率が下がる原因は、基盤となるニューラルネットワークの割り当ての偏りと逐次依存にある。計算コストとモデルサイズのこの超線形な関係は、デバイスを増やすだけでは解消できず、巨大モデルの学習を非現実的なものにする。

**巨大モデル表現を支えるインフラストラクチャのスケーラビリティ。** 数千台のデバイスに分散した巨大モデルを単純なグラフで表現すると、深層学習フレームワークと最適化コンパイラの両方でボトルネックになりうる。例えば、inter-op 分割で層を $D$ 倍に増やしたり、$D$ 台のデバイスにまたがる intra-op 分割でモデル次元を拡大したりすると、ノード数 $O(D)$ のグラフが生じる場合がある。デバイス間の通信チャネルによって、グラフサイズはさらに最大 $O(D^2)$ まで増えうる（Gather や Transpose の分割など）。この増加により、巨大モデルのグラフ構築時間とコンパイル時間は現実的でないほど長くなる。

**分割戦略の実装に要する少なからぬ労力。** モデルを分割して多数のデバイス上で効率よく実行するには、デバイス間通信を調整しなければならず、実装は容易ではない。グラフレベルの分割では、別々のデバイスに割り当てたグラフ区画間の逐次依存が生むオーバーヘッドを抑えるため、高度なアルゴリズムが必要になる [Hua19, Har18]。演算子レベルの並列化では、部分結果の集約やデータシャードの再配置など、分割対象の演算子の意味に応じて通信パターンが異なる。TensorFlow のようなフレームワークには固有の意味を持つ演算子が多数あるため、経験上、これらをモデル内で手動処理するには相当な労力がかかる。どちらの場合も、モデルアーキテクチャを変えるたびに基盤のデバイス通信まで変更し、その影響が連鎖するため、モデル分割の実装は実務者にとって特に大きな負担となる。

### 1.2 大規模トレーニングの効率化のための設計原則

本稿では、Sparsely-Gated Mixture-of-Experts 層を備え、計算コストが亜線形に増加し、コンパイル時間が $O(1)$ となる 6000 億パラメータの sequence-to-sequence Transformer を構築して、これらの課題を克服する方法を示す。このモデルを 2048 台の TPU v3 デバイスで 4 日間、多言語機械翻訳タスクについて学習し、単一の非アンサンブルモデルで 100 言語から英語へ翻訳したとき、従来手法を大きく上回る翻訳品質を得た。さまざまなモデルサイズで実験したところ、モデルが大きいほど翻訳品質は向上する一方、学習に要する総実時間はモデルサイズに対して亜線形にしか増えなかった（[図 1](#figure-01)）。この巨大モデルを構築するため、次の設計を採用した。

**亜線形スケーリング。** 第一に、計算量と通信量がモデル容量に対して亜線形に増えるよう、モデルアーキテクチャを設計する必要がある。条件付き計算 [Ben15a, Sha17, Elb20, Bap20a] は、入力ごとに一つのサブネットワークだけを活性化し、学習と推論を効率化する。RNN ベースの機械翻訳モデルと言語モデルへ Position-wise Sparsely Gated Mixture-of-Experts（MoE）層 [Sha17] を追加して容量を拡大することで、亜線形の計算コストで最先端の結果が得られている。そこで、セクション [2](#section-02) では Transformer アーキテクチャを MoE 層で拡張する方法を示す。

**抽象化の力。** 第二に、モデル記述を分割の実装と最適化から切り離す必要がある。この分離によって、モデル開発者はネットワークアーキテクチャに集中して分割戦略を柔軟に変更でき、基盤システムは意味を保つ変換と効率的な並列実行を担える。そのために提案する GShard では、モデル内の少数の重要なテンソルへ分割方針を注釈するだけでよい。GShard は単純なアノテーション API 群と、自動並列化を行う XLA [Xla17] コンパイラ拡張からなる。モデル開発者は、巨大なメモリと計算能力を備えた一台のデバイスがあるものとしてモデルを記述し、コンパイラが注釈とヒューリスティクスに基づいて対象システム向けに計算を自動分割する。アノテーションの例はセクション [3.2](#section-03-02) でさらに示す。

<span id="figure-02"></span>

![4 台のデバイスにおける Dot 演算子の MPMD 分割と SPMD 分割](../../papers/gshard/figure-02.png)

**図 2.** 4 台のデバイスにおける Dot 演算子（$[M,K]\times[K,N]=[M,N]$）の MPMD 分割と、本稿で提案する SPMD 分割の比較。この例では、二つのオペランドを縮約次元 $K$ に沿って分割し、各デバイスが局所結果を計算した後、AllReduce で全体を結合する。MPMD 分割はデバイスごとに別の演算子を生成するため、スケーラビリティが制限される。一方、SPMD 分割は全デバイスで実行する一つのプログラムを生成する。本稿の SPMD 分割では、コンパイル時間は使用デバイス数に依存しない。

**スケーラブルなコンパイラ。** 第三に、計算表現とコンパイルを含むシステム基盤は、数千台のデバイスによる並列実行まで拡張できなければならない。[図 2](#figure-02) は、Dot 演算を 4 台のデバイス（色分け）へ分割する二つの方法を示す。通常の MPMD（Multiple Program Multiple Data）方式（[図 2a](#figure-02)）では、グラフのノード数がデバイス数に比例して増えるため、規模拡大が難しくなる。そこで、全デバイスで実行する一つのプログラムを生成する SPMD（Single Program Multiple Data）変換のコンパイラ技術を開発した。[図 2b](#figure-02) のように、コンパイル時間はデバイス数に依存せず一定に保たれる。この SPMD フレームワークはセクション [3.3](#section-03-03) で詳しく述べる。

### 2.1 トランスフォーマーアーキテクチャのスパーススケーリング

Transformer [Vas17b] アーキテクチャは自然言語処理で広く使われている。機械翻訳など、多くの sequence-to-sequence タスクで事実上の標準となった。Transformer はエンコーダとデコーダという二つの計算ブロックを使い、いずれも複数の Transformer 層を積み重ねて実装する。Transformer のエンコーダ層は、自己注意層と、それに続く position-wise フィードフォワード層からなる。デコーダには、エンコーダ出力を参照する第三の cross-attention 層が加わる。条件付き計算によって Transformer をスパースに拡張し、エンコーダとデコーダの両方で、一つおきのフィードフォワード層を top-2 ゲーティングの変種を用いた Position-wise Mixture-of-Experts（MoE）層 [Sha17] に置き換える（[図 3](#figure-03)）。モデル容量を拡大するため、Transformer の層数と MoE 層当たりのエキスパート数を変化させる。

各学習例は、サブワードトークン列の対からなる。各トークンは、学習時と推論時のどちらでも MoE Transformer の一つのサブネットワークを活性化する。サブネットワークの大きさは MoE 層当たりのエキスパート数にほぼ依存しないため、前節で述べたように計算コストを亜線形に拡大できる。計算量はセクション [3.1](#section-03-01) で、学習性能はセクション [5](#section-05) で詳しく扱う。

### 2.2 Position-wise Mixture-of-Experts 層

本モデルで使用する Mixture-of-Experts（MoE）層は [Sha17] に基づくが、スパースゲーティング関数と補助損失に変更を加えている。Transformer の MoE 層は、$E$ 個のフィードフォワードネットワーク $\mathrm{FFN}_{1}\dots\mathrm{FFN}_{E}$ からなる。

$$
\mathcal{G}_{s,E}=\mathrm{GATE}(x_s)
$$

$$
\mathrm{FFN}_e(x_s)=\mathit{wo}_e\cdot\mathrm{ReLU}(\mathit{wi}_e\cdot x_s)
$$

$$
y_s=\sum^E_{e=1}\mathcal{G}_{s,e}\cdot\mathrm{FFN}_e(x_s)
$$

ここで $x_s$ は MoE 層への入力トークンであり、$\mathit{wi}$ と $\mathit{wo}$ はフィードフォワード層（エキスパート）の入力射影行列と出力射影行列である。ベクトル $\mathcal{G}_{s,E}$ はゲーティングネットワークで計算される。$\mathcal{G}_{s,E}$ には各エキスパートに対応する非負値が一つずつあり、その大半はゼロ、すなわちトークンをそのエキスパートへ送らないことを表す。トークンはごく少数のエキスパートに送られる。本稿では、各トークンの送信先を最大二つのエキスパートとする。$\mathcal{G}_{s,E}$ の対応する要素は非ゼロで、各エキスパートがネットワークの最終出力にどれだけ寄与するかを表す。各エキスパート $\mathrm{FFN}_e$ は、ReLU [Nai10] 活性化関数を用いた全結合二層ネットワークを $x_s$ に適用する。MoE 層の出力 $y_s$ は、選択された全エキスパートの出力の加重平均である。

ゲーティング関数 $\mathrm{GATE}(\cdot)$ は MoE 層の中核であり、softmax 活性化関数を用いて、入力トークンを処理する各エキスパートの重みを表す。言い換えれば、入力トークンの処理に各エキスパートがどの程度適しているかを示す。さらに、ゲーティング関数は次の二つの目標を満たす必要がある。

- **負荷分散。** MoE 層では、各トークンに対してエキスパートをスパースに活性化することが望ましい。単純には softmax 確率分布に従って上位 $k$ 個のエキスパートを選べばよい。しかし、この方法は学習時に負荷の偏りを生むことが知られている [Sha17]。学習中の大半のトークンが少数のエキスパートへ送られ、その少数のエキスパートだけが巨大な入力バッファを抱える一方、残りのエキスパートは学習されず、学習全体が遅くなる。ほかの多数のエキスパートは十分に学習されない。より適切なゲーティング関数は、処理負荷を全エキスパートへ均等に分配する。

- **大規模環境での効率。** ゲーティング関数を逐次実行するなら、負荷分散は容易に実現できる。だが、$E$ 個のエキスパートに対して入力バッチ内の $N$ 個のトークンを処理するゲーティング関数だけでも、計算コストは少なくとも $O(NE)$ となる。本研究では $N$ が数百万、$E$ が数千のオーダーに達するため、ゲーティング関数を逐次実装すると、ほとんどの計算資源が長時間アイドル状態になる。したがって、多数のデバイスを活用できる効率的な並列実装が必要である。

以上の要件を満たすため、ゲーティング関数 $\mathrm{GATE}(\cdot)$ に次の仕組みを設けた（詳細は[アルゴリズム 1](#algorithm-01)）。

- **エキスパート容量。** 負荷を分散するため、一つのエキスパートが処理するトークン数に共通の上限を設け、これをエキスパート容量と定義する。学習バッチ内の総トークン数を $N$ とし、各トークンを最大二つのエキスパートへ送ると仮定すると、エキスパート容量は $O(N/E)$ に設定される。$\mathrm{GATE}(\cdot)$ は、各エキスパートへ送られたトークン数をカウンタ $c_e$ で追跡する。トークンが選んだ二つのエキスパートがどちらも容量を超えている場合、そのトークンをオーバーフロートークンとみなし、$\mathcal{G}_{s,E}$ はゼロベクトルに退化する。このトークンの表現 $x_s$ は残差接続を通って次の層へ渡される。

- **ローカルグループへの分配。** $\mathrm{GATE}(\cdot)$ は、学習バッチ内の全トークンを $G$ 個のグループへ均等に分ける。各グループには $S=N/G$ 個のトークンが含まれる。すべてのグループは互いに独立して並列処理される。各グループには、各エキスパート容量の一部として $2N/(G\cdot E)$ が与えられる。各グループは、一つのエキスパートへ送るトークン数がこの値を超えないようにする。これによりエキスパート容量を保ち、全体の負荷を分散できる。

- **補助損失。** ゲーティング関数が常に同じ少数のエキスパートを選ぶと、その少数だけが容量を超え、残りが十分に使われないため、これを避ける必要がある。[Sha17] に従い、この制約を課す補助損失項 $\ell_{\mathrm{aux}}$ を定義する。この項は定数係数 $k$ とともに、モデルの総損失 $\mathcal{L}=\ell_{\mathrm{nll}}+k*\ell_{\mathrm{aux}}$ へ加える。[アルゴリズム 1](#algorithm-01) の 13 行目にある補助損失 $\ell_{\mathrm{aux}}$ の形は、次の考えに基づく。$c_e/S$ は各エキスパートへルーティングされる入力の割合なので、$c_e/S$ の二乗平均を最小化したい。しかし $c_e$ は top-2 演算から得られるため微分不可能である。そこで、エキスパートごとの平均ゲート $m_e$ を微分可能な近似として使い、$(c_e/S)^2$ を $m_e(c_e/S)$ に置き換える。これにより、勾配降下法で最適化できる。

- **ランダムルーティング。** $y_s$ は選択されたエキスパートの返す値の加重平均なので、二番目のエキスパートの重みが非常に小さければ、そのエキスパートを無視して全体のエキスパート容量を節約できる。そこで $\mathrm{GATE}(\cdot)$ は、エキスパート容量の制約を守りつつ、重み $g_2$ に比例する確率で二番目のエキスパートへトークンを送る。

<span id="algorithm-01"></span>

**アルゴリズム 1：グループレベルの top-2 ゲーティングと補助損失。**

- **データ：** $x_{S}$、サイズ $S$ のトークンのグループ。
- **データ：** $C$、このグループに割り当てられたエキスパート容量。
- **結果：** $\mathcal{G}_{S,E}$、グループ結合重み。
- **結果：** $\ell_{\mathrm{aux}}$、グループ補助損失。
- $c_E\leftarrow 0$ $\triangleright$ エキスパートごとのゲーティング決定。
- $g_{S,E}\leftarrow \mathrm{softmax}(\mathit{wg}\cdot x_S)$ $\triangleright$ トークンおよびエキスパートごとのゲート。$\mathit{wg}$ は学習可能な重み。
- $m_E\leftarrow\frac{1}{S}\sum^s_{s=1}g_{s,E}$ $\triangleright$ エキスパートごとの平均ゲート。
- **反復** $s\leftarrow 1$ から $S$ まで：
  - $g_1,e_1,g_2,e_2=\mathrm{top\_2}(g_{s,E})$ $\triangleright$ top-2 ゲートとエキスパートインデックス。
  - $g_1\leftarrow g_1/(g_1+g_2)$ $\triangleright$ 正規化した $g_1$。
  - $c\leftarrow c_{e_1}$ $\triangleright$ エキスパート $e_1$ のバッファ内の位置。
  - **もし** $c_{e_1}<C$：
    - $\mathcal{G}_{s,e_1}\leftarrow g_1$ $\triangleright$ $x_s$ に対するエキスパート $e_1$ の結合重み。
  - $c_{e_1}\leftarrow c+1$ $\triangleright$ エキスパート $e_1$ の決定回数を一つ増やす。
- $\ell_{\mathrm{aux}}=\frac{1}{E}\sum^E_{e=1}\frac{c_e}{S}\cdot m_e$。
- **反復** $s\leftarrow 1$ から $S$ まで：
  - $g_1,e_1,g_2,e_2=\mathrm{top\_2}(g_{s,E})$ $\triangleright$ top-2 ゲートとエキスパートインデックス。
  - $g_2\leftarrow g_2/(g_1+g_2)$ $\triangleright$ 正規化した $g_2$。
  - $\mathit{rnd}\leftarrow \mathrm{uniform}(0,1)$ $\triangleright$ 確率 $\propto 2\cdot g_2$ で二番目のエキスパートへ送る。
  - $c\leftarrow c_{e_2}$ $\triangleright$ エキスパート $e_2$ のバッファ内の位置。
  - **もし** $c<C\land 2\cdot g_2>\mathit{rnd}$：
    - $\mathcal{G}_{s,e_2}\leftarrow g_2$ $\triangleright$ $x_s$ に対するエキスパート $e_2$ の結合重み。
  - $c_{e_2}\leftarrow c+1$。

## 3 GShard を使用した高並列実装

本節では、セクション [2](#section-02) のモデルを TPU デバイスのクラスタ上で効率よく実行する実装について述べる。

第一に、モデルを線形代数演算で表す。本稿のソフトウェアスタック（TensorFlow [Aba16]）とハードウェアプラットフォーム（TPU）は、この種の演算へ特化して最適化されている。元の Transformer と同じように、モデルの大半を線形代数で記述するのは容易である。ただし MoE 層、とりわけ[アルゴリズム 1](#algorithm-01) の $\mathrm{GATE}(\cdot)$ 関数は逐次的な性質を持つため、その表現には工夫を要する。詳細はセクション [3.1](#section-03-01) で述べる。

次に、線形代数計算へ注釈を付けて並列性を表現する。セクション [3.2](#section-03-02) のシャーディング API により、計算内の各テンソルをクラスタ上で複製または分散するよう指定できる。シャーディング注釈はモデル記述と効率的な並列実装を分離し、多様な並列化戦略を柔軟に表せるようにする。例えば、（1）Attention 層はバッチ次元に沿って分割し、重みを全デバイスへ複製する。一方、（2）MoE 層のエキスパートは巨大なため全デバイスへ複製できず、多数のデバイスへ分割するほかない。モデル全体はこの二つのモード（1）-（2）を交互に使う。注釈により、モデル開発者はシステム最適化から解放され、並列実装や低水準の詳細をモデルコードへ埋め込まずに済む。

最後に、コンパイラ基盤が（部分的に）注釈された線形代数計算を受け取り、数千台のデバイスまで拡張できる効率的な並列プログラムを生成する。セクション [3.3](#section-03-03) で述べるように、コンパイラは SPMD（Single Program Multiple Data）分割変換によってデバイスごとの計算を表現し、必要なデバイス間通信を挿入し、不均等分割などの不規則なパターンを処理したうえで、全デバイス上で起動する一つの並列実行プログラムを生成する。

<span id="section-03-01"></span>

### 3.1 線形代数で表現されたポジションごとのエキスパート混合層

本モデルの実装（[アルゴリズム 2](#algorithm-02)）では、アクセラレータクラスタ全体を一台のデバイスとみなし、中心となる数学的アルゴリズムを、クラスタの具体的な構成に依存しない少数のテンソル演算で表す。アインシュタインの縮約記法 [Ein23]（`tf.einsum`）はモデルを簡潔に表せるため、実装で広く使用している。softmax ゲートの計算は、一回の `einsum` とそれに続く softmax 関数で表せる。選択したエキスパートへの入力の分配は、dispatch mask と入力との一回の `einsum` で表す。全 $\mathrm{FFN}_e$ の重みは、それぞれ一つの三次元テンソル `wi` と `wo` にまとめ、$\mathrm{FFN}_1\dots\mathrm{FFN}_E$ の計算は三つの演算子（二回の `einsum` と一回の `relu`）で表す。最後に、全エキスパートの出力を加重平均して最終出力を得る処理を、別の `einsum` で表す。

[アルゴリズム 2](#algorithm-02) の `Top2Gating` は、[アルゴリズム 1](#algorithm-01) で述べたグループごとの $\mathcal{G}_{S,E}$ をすべて統合する。`combine_weights` は形状 `[G, S, E, C]` の四次元テンソルである。グループ $g$ の入力トークン $s$ がエキスパート $e$ の入力バッファ内の位置 $c$ へ送られるとき、`combine_weights[g, s, e, c]` は非ゼロとなる。特定の `g` と `s` に対し、スライス `combine_weights[g, s, :, :]` に含まれる非ゼロ値は最大二つである。二値の `dispatch_mask` は、`combine_weights` のすべての非ゼロ値を 1 にして生成する。

<span id="algorithm-02"></span>

**アルゴリズム 2：Position-wise MoE 層の順伝播。下線付きの文字（例：$\underline{G}$ と $\underline{E}$）は、テンソルを分割する次元を示す。**


<div class="paper-algorithm">

- $\mathrm{gates}\leftarrow\mathrm{softmax}(\mathrm{einsum}("\mathtt{\underline{G}SM,ME\to\underline{G}SE}",\mathrm{inputs},\mathrm{wg}))$。
- $\mathrm{combine\_weights},\mathrm{dispatch\_mask}\leftarrow\mathrm{Top2Gating}(\mathrm{gates})$。
- $\mathrm{dispatched\_expert\_inputs}\leftarrow\mathrm{einsum}("\mathtt{\underline{G}SEC,\underline{G}SM\to\underline{E}GCM}",\mathrm{dispatch\_mask},\mathrm{reshaped\_inputs})$。
- $h\leftarrow\mathrm{einsum}("\mathtt{\underline{E}GCM,\underline{E}MH\to\underline{E}GCH}",\mathrm{dispatched\_expert\_inputs},\mathrm{wi})$。
- $h\leftarrow\mathrm{relu}(h)$。
- $\mathrm{expert\_outputs}\leftarrow\mathrm{einsum}("\mathtt{\underline{E}GCH,\underline{E}HM\to\underline{G}ECM}",h,\mathrm{wo})$。
- $\mathrm{outputs}\leftarrow\mathrm{einsum}("\mathtt{\underline{G}SEC,\underline{G}ECM\to\underline{G}SM}",\mathrm{combine\_weights},\mathrm{expert\_outputs})$。

</div>

このアルゴリズムを $D$ 台のデバイスからなるクラスタへ拡張するには、グループ数 $G$ とエキスパート数 $E$ を適切に選ぶ必要がある。そこで、$N$ トークンの学習バッチを処理する一ステップについて、全体の計算量（浮動小数点演算の総数）を分析する。

デバイス数 $D$ に対して[アルゴリズム 2](#algorithm-02) の計算量がどう変化するかを、次の仮定の下で分析する。a）デバイス当たりのトークン数 $\frac{N}{D}=O(1)$ は一定である [+1]。b）$G=O(D)$、$S=O(1)$、$N=O(\mathrm{GS})=O(D)$。c）$M=O(1)$、$H=O(1)$。d）$E=O(D)$。e）$C=O(\frac{2S}{E})=O(\frac{1}{D})$ であり、$D<S$ は正の整数である [+2]。

[アルゴリズム 2](#algorithm-02) の浮動小数点演算総数 $\mathit{FLOPS}$ は次のとおりである。

$$
\begin{aligned}
&\mathit{FLOPS}_{\mathrm{Softmax}}+\mathit{FLOPS}_{\mathrm{Top2Gating}}+\mathit{FLOPS}_{\mathrm{Dispatch|Combine}}+\mathit{FLOPS}_{\mathrm{FFN}}\\
&=O(GSME)+O(GSEC)+O(GSMEC)+O(EGCHM)\\
&=O(D\cdot 1\cdot 1\cdot D)+O\left(D\cdot 1\cdot D\cdot\frac{1}{D}\right)+O\left(D\cdot 1\cdot 1\cdot D\cdot\frac{1}{D}\right)+O\left(D\cdot D\cdot\frac{1}{D}\cdot 1\cdot 1\right)\\
&=O(D^2)+O(D)+O(D)+O(D)
\end{aligned}
$$

したがって、デバイス当たりでは $\mathit{FLOPS}/D=O(D)+O(1)+O(1)+O(1)$ となる。デバイス当たりの softmax の計算量 $\mathit{FLOPS}_{\mathrm{softmax}}/D=O(D)$ はデバイス数に対して線形だが、実際には $D\ll H$ かつ $D<S$ なので、ほかの項が支配的になる。その結果、$\mathit{FLOPS}/D$ は $O(1)$ とみなせ、亜線形スケーリングという設計要件を満たす。セクション [5](#section-05) では、この分析を実験的に検証する。

計算コストに加えて、定数ではないデバイス間通信コストもあるが、$D$ を増やしても $O(\sqrt{D})$ という緩やかな割合でしか増えない（セクション [5](#section-05)）。

### 3.2 並列実行のための GShard アノテーション API

[アルゴリズム 1](#algorithm-01) のテンソルはサイズも計算量も膨大なので、アルゴリズムを多数のデバイスへ並列化しなければならない。各テンソルの直接的なシャーディング方法を、[アルゴリズム 2](#algorithm-02) の下線付き文字で示す。GShard の *sharding* API では、プログラム内のテンソルへ注釈を付け、分割方法を必要な箇所だけ指定できる。この情報がコンパイラへ伝わると、コンパイラは並列実行に必要な変換を自動適用する。本研究では TensorFlow/Lingvo [She19a] の次の API を用いる。

- `replicate(tensor)` は、テンソルを分割間で複製するよう注釈し、注釈済みテンソルを返す。本モデルでは、MoE 以外の層の重みを複製するときによく使う。

- `split(tensor, split_dimension, num_partitions)` は、テンソルを `split_dimension` に沿って分割するよう注釈し、注釈済みテンソルを返す。分割 $i$ は $i$ 番目のデバイスに配置し、`num_partitions` はシステムのデバイス数を超えてはならない。

- `shard(tensor, device_assignment)` は `split()` を一般化し、複数次元の分割と各分割の配置を指定できる。この API は[付録 A.3](#appendix-a-03) で詳しく説明する。

`split` や `shard` の呼び出しは注釈を加えるだけで、ユーザープログラム上の論理形状は変えない。ユーザーは引き続き完全な形状を扱い、不均等分割などの問題を意識する必要はない。

GShard は、単純な API をすべての次元へ同じように適用できるという点で汎用的である。用途に応じて、バッチ（データ並列）、特徴、エキスパート、さらには画像モデルの空間次元もシャーディング対象にできる。また、注釈はテンソル単位なので、モデルの部分ごとに異なる方法で分割できる。この柔軟性により、巨大な MoE の重みを分割し、MoE 層と非 MoE 層の間で分割モードを切り替えられる。本稿以外の用途、例えば大きな画像の空間分割 [Che19a]（[付録 A.4](#appendix-a-04)）にも対応する。

上記のシャーディング API により、[アルゴリズム 2](#algorithm-02) のシャーディング戦略を次のように表せる。入力テンソルを最初の次元で分割し、ゲート重みテンソルは複製する。エキスパートへ振り分けた入力を計算した後、`split` を適用して、シャーディングをグループ（$G$）次元からエキスパート（$E$）次元へ切り替える。$D$ はデバイス数である。


```pseudocode
# 入力をグループ (G) 次元に沿って分割
inputs = split(inputs, 0, D)
# ゲート重みを複製
wg = replicate(wg)
gates = softmax(einsum("GSM,ME->GSE", inputs, wg))
combine_weights, dispatch_mask = Top2Gating(gating_logits)
dispatched_expert_inputs = einsum(
  "GSEC,GSM->EGCM", dispatch_mask, reshaped_inputs)
# 振り分けた入力をエキスパート (E) 次元に沿って分割
dispatched_expert_inputs = split(dispatched_expert_inputs, 0, D)
h = einsum("EGCM,EMH->EGCH", dispatched_expert_inputs, wi)
...
```

**テンソルごとのシャーディング割り当て。** 上の例のように、プログラム内の全テンソルへ注釈を付ける必要はない。通常、注釈が必要なのは本モデルの Einsum のような少数の重要演算子だけで、残りのテンソルについてはコンパイラがヒューリスティクスによりシャーディングを推論する [+3]。例えば、入力テンソルが $G$ 次元で分割され、重みテンソルが複製されていれば、コンパイラは Einsum の出力も同じ $G$ 次元で分割する（5 行目）。同様に、入力を振り分ける Einsum（7 行目）では二つの入力がともに $G$ 次元で分割されているため、出力も $G$ 次元で分割すると推論する。その後、出力へ `split` 注釈を加え、$E$ 次元へ再シャーディングする。上の例にある注釈の一部（`replicate(wg)` など）もコンパイラで決定できるが、計算の最初の入力テンソルと最後の出力テンソルには注釈を付けることを推奨する。

現在のコンパイラは、ユーザーが注釈した演算子から始め、反復的なデータフロー解析によって近隣の演算子（オペランドと利用側）へシャーディング情報を伝播する。この解析は隣接演算子の判断を揃え、再シャーディングの発生を抑える。整数計画法や機械学習など、ほかの方法も考えられるが、自動シャーディング割り当ての改善は本稿の対象外であり、今後の課題とする。

**手動シャーディングと自動シャーディングの混在。** 一般的な場合はシャーディング注釈による自動分割で十分なことが多いが、GShard では手動分割した演算子と自動分割した演算子を混在させることもできる。これにより、演算子の分割方法をユーザーがさらに制御できる。例えば、ユーザーが演算子の意味だけでは得られない実行時情報を知っている場合がある。XLA と TensorFlow の Gather 演算子定義は、入力内の各範囲に対する索引境界を伝えないが、ユーザーは特定の Gather が各分割内だけでデータを並べ替えると知っているかもしれない。この場合、次元サイズを縮小してローカル Gather を行うだけで、演算子を容易に手動分割できる。そうでなければ、コンパイラは索引範囲を保守的に見積もり、不要な通信を追加しなければならない。例えば、[アルゴリズム 2](#algorithm-02) にある[アルゴリズム 2](#algorithm-02) 3 行目の入力振り分け Einsum は、one-hot 行列で入力を振り分けるが、単純に手動分割した Gather 演算子でも実装できる。モデルの残りは自動分割のままでよい。次の擬似コードにこの用例を示す。

```pseudocode
# input の形状は [G, S, M]; split() は論理形状を変更しない
input = split(input, 0, num_devices)
# s_indices の形状は [E, G, C, 1]; 値は input の S 次元への索引
s_indices = split(s_indices, 1, num_devices)

# 手動パーティショニングを開始
# partitioned_input の形状は [G/num_devices, S, M]
partitioned_input = auto_to_manual_spmd_partition(input)
# partitioned_s_indices の形状は [E, G/num_devices, C, 1]
partitioned_s_indices = auto_to_manual_spmd_partition(s_indices)
# partitioned_input の G 次元の索引を連結
partitioned_gs_indices = concat(
  iota([E, G/num_devices, C, 1], 1), partitioned_s_indices, 3)
# partitioned_data の形状は [E, G/num_devices, C, M]
partitioned_data = gather(partitioned_input, partitioned_gs_indices)

# 自動パーティショニングに戻す
# data の形状は [E, G, C, M]
data = manual_to_auto_spmd_partition(partitioned_data)
...
```

### 3.3 GShard の XLA SPMD パーティショナー

本節では、シャーディング注釈に従って計算グラフを自動分割するコンパイラ基盤を述べる。シャーディング注釈は、各テンソルをデバイス間へどう分配するかをコンパイラへ伝える。SPMD（Single Program Multiple Data）パーティショナー（以下「パーティショナー」）は、計算グラフを全デバイスで並列実行する一つのプログラムへ変換するコンパイラ部品である。この方式では、分割数にかかわらずコンパイル時間をほぼ一定に保ち、数千分割まで拡張できる [+4]。

パーティショナーは XLA コンパイラ [Xla17] に実装した。TensorFlow、JAX、PyTorch、Julia など複数のフロントエンドフレームワークには、各自のグラフ表現を XLA HLO グラフへ lowering する仕組みがすでにある。また XLA の演算子集合は TensorFlow など一般的なフロントエンドフレームワークよりはるかに小さいため、汎用性を失わずにパーティショナーの実装負担を減らせる。フロントエンドの既存 lowering 処理が、表現力を確保するための大部分の処理を担うからである。本インフラストラクチャは XLA 上に開発したが、ここで述べる手法は ONNX [Onn19]、TVM Relay [Roe18]、Glow IR [Rot18] など、ほかの機械学習フレームワークの中間表現にも適用できる。

XLA は、演算子をノード、演算子間を流れるテンソルを辺とするデータフローグラフで計算を表す。パーティショナーの中核は演算子ごとの処理であり、入出力に指定されたシャーディングに従って、各演算子を完全なサイズから分割サイズへ変換する。計算を分割すると、さまざまなデバイス間データ転送が生じる。大規模環境で性能を最大化するには、基本となる通信プリミティブ群を定義し、対象プラットフォーム向けに最適化する必要がある。

<span id="section-03-03-01"></span>

#### 3.3.1 通信プリミティブ

パーティショナーは全デバイスで同じプログラムを実行するため、通信パターンも規則的になる。XLA は MPI 形式の通信を行う集団演算子群を定義している [For09]。SPMD パーティショナーで使う一般的な通信プリミティブを次に示す。

**CollectivePermute。** 送信元と送信先の対を列挙し、送信元の入力データを対応する送信先へ送る。これは、シャーディングしたテンソルのデバイス順を分割間で変更するときと、本節で後述する halo 交換で使う。

**AllGather。** 指定された順序で全参加者のテンソルを連結する。シャーディングしたテンソルを複製テンソルへ変換するときに使う。

**AllReduce。** 全参加者からの入力へ、要素ごとの reduction（加算など）を施す。別々の分割で部分的に reduction した中間テンソルを結合するときに使う。TPU デバイスネットワークでは、分割数が増えても AllReduce のコストは一定である（セクション [5.2](#section-05-02)）。ほかのネットワークトポロジでも効率よく実装されている一般的なプリミティブである [Cho19]。

**AllToAll。** 各参加者の入力を一つの次元に沿って論理的に分割し、各部分を別の参加者へ送る。他の参加者からデータ片を受け取ると、各参加者はそれらを連結して結果を作る。これは、シャーディングされたテンソルを一つの次元から別の次元へ再シャーディングするために使う。TPU デバイスネットワークでは、AllToAll によって効率よく再シャーディングでき、分割数が増えてもコストは亜線形にしか増加しない（セクション [5.2](#section-05-02)）。

<span id="section-03-03-02"></span>

#### 3.3.2 演算子単位の SPMD 分割

パーティショナーの中核は、指定されたシャーディングに従い、完全なサイズの演算子を分割サイズの演算子へ変換する処理である。要素単位演算などは対応しやすいが、ここでは分割間通信を要するいくつかの一般的な場合を扱う。

一般的な場合にはいくつかの重要な技術課題があり、セクション [3.3.3](#section-03-03-03) で扱う。本節では MoE モデルに即して説明するため、Einsum の分割に絞って通信パターンを示す。また簡単のため、全テンソルを均等に分割できる、すなわち分割対象の次元サイズが分割数の倍数であると仮定する。

**Einsum のケーススタディ。** Einsum は MoE モデルの実装で最も重要な演算子である。XLA HLO では Dot 演算として表し、各オペランド（LHS または RHS）は三種類の次元からなる。

- バッチ次元は並列化しやすい。同じバッチ次元が LHS、RHS、出力のすべてに存在し、出力の各要素は LHS と RHS の対応するバッチだけに依存する。

- 縮約次元はオペランドだけに存在する。LHS と RHS は同じ縮約次元群を持ち、出力を得る際に和を取って消去する。

- 非縮約次元も並列化可能で、いずれか一方のオペランドと出力に存在する。LHS と RHS はそれぞれ固有の非縮約次元群を持ち、それらが出力へ引き継がれる。

シャーディングの伝播では、分割間通信を避けるため、LHS、RHS、出力のバッチ次元に同じシャーディングを選ぶことを優先する。ただし常に可能とは限らず、次の三つの場合は分割間通信が必要になる。

<span id="figure-04"></span>

![デバイス間通信を伴う Einsum の分割例](../../papers/gshard/figure-04.png)

**図 4.** デバイス間通信を伴う Einsum の分割例。

- **再シャーディング。** 本稿の MoE モデルでは、[アルゴリズム 2](#algorithm-02) 3 行目のエキスパートへの振り分けで、Einsum の後に分割次元を切り替える必要がある。AllToAll は再シャーディングを効率よく実行できるため（セクション [5.2](#section-05-02)）、まず Einsum を局所実行し、その後で目的の次元へ再シャーディングする（[図 4a](#figure-04)）。

- **部分結果の集約。** 入力を縮約次元に沿って分割すると、局所結果は部分結果になるため、AllReduce で結合して最終結果を得る（[図 4b](#figure-04)）。

- **ループ内でのスライス。** 各分割のテンソルサイズを抑えるため、場合によっては Cannon のアルゴリズム [Can69] に似た方法も実装した。例えば、二つのオペランドをそれぞれ非縮約次元で分割すると、双方に非縮約次元が残るため、局所 Einsum を直接計算できない。一方のオペランドを複製すれば計算の重複は生じないが、複製したオペランドがデバイスメモリへ収まらなければならない。そこでオペランドが大きすぎる場合は両方をスライスし、ループ内で結果の各スライスを反復計算しながら、CollectivePermute で入力スライスを転送する（[図 4c](#figure-04)）。

<span id="section-03-03-03"></span>

#### 3.3.3 完全なオペレーターセットのサポート

SPMD パーティショナーが、テンソル形状や演算子設定へ追加制約を課さず全演算子を扱えるように、いくつかの課題を解決した。多くは分割間で非対称な計算や通信パターンに関わるため、全分割を扱える一つの汎用プログラムが必要な SPMD では特に表現しにくい。実行時のデバイス ID に応じた分岐を単一プログラム内へ大量に作ると、プログラムサイズが爆発的に増えるため、この方法は使えない。

**静的形状と不均等分割。** テンソル形状は静的でなければならない [+5]。しかし、次元サイズが分割数で割り切れない場合があるため、計算を分割したとき、全分割が同じ入出力形状を持つとは限らない。この場合は形状サイズを分割数の次の倍数へ切り上げ、パディング領域のデータには任意の値を置ける。

演算子を計算する際、正しさを保つためにパディング領域へ既知の値を入れなければならない場合がある。例えば、加算による Reduce 演算子を分割する場合は、単位元のゼロを使う必要がある。分割する次元（15）が分割数（2）で割り切れず、分割 1 に余分な列が一つ生じる例を考える。範囲 $[0,8)$ の Iota 演算子を作り、分割オフセット（$\mathrm{PartitionId}\times 8$ で計算）を加えて、完全な形状の境界（15）と比較する。述語値に基づいてオペランドの値またはゼロを選択すると、マスク済みオペランドが得られる。

**静的な演算子設定。** XLA 演算子には、Convolution のパディング、ストライド、dilation のような静的設定がある。しかし、分割ごとに必要な設定が同じとは限らない。例えば Convolution では、左端の分割だけが左側のパディングを、右端の分割だけが右側のパディングを必要とする。この場合、パーティショナーは一部の分割で余分なデータを生成する設定を選び、不要部分を切り取ることがある。[付録 A.4](#appendix-a-04) で Convolution などの例を説明する。

**Halo 交換。** 演算子によっては隣接分割とデータの一部を交換する通信パターンがあり、これを *halo 交換*と呼ぶ。分割間の halo データ交換には CollectivePermute 演算子を使う。

<span id="figure-05"></span>

![Halo 交換の例](../../papers/gshard/figure-05.png)

**図 5.** Halo 交換の例。

Halo 交換の代表的な用途は、Convolution や ReduceWindow など、window ベース演算子の分割である。隣接する分割が重複した入力データを必要とする場合があるためだ（[図 5a](#figure-05)）。実際には、高度な window 設定（dilation、ストライド、パディング）や不均等な halo サイズへ対応するため、適切なパディング、スライス、マスキングを組み合わせることが多い。各場合は[付録 A.4](#appendix-a-04) で説明する。

Halo 交換のもう一つの用途は、形状サイズを変えるデータ形式演算子である。例えば Slice や Pad の後では、テンソル形状と分割間の境界が変わるため、別々の分割上にあるデータを再整列しなければならない。これも halo 交換の一種として扱える（[図 5b](#figure-05)）。

ほかのデータフォーマット演算子は論理上の形状サイズを変えないが、静的形状の制約や不均等な分割のために halo 交換が必要になる場合がある。例えば Reverse 演算子はテンソル内の要素順を反転するが、分割が不均等なら、パディングを論理上は結果テンソルの右側に保つため、分割間でデータを移動しなければならない。Reshape も一例である。テンソルを $[3,2]$ から $[6]$ へ変形する場合を考える。入力は最初の次元で不均等に分割され（分割形状は $[2,2]$）、出力も分割される（分割形状は $[3]$）。入力には不均等分割によるパディングがあるが、Reshape 後の出力テンソルにはパディングがないため、Slice と同様の halo 交換が必要になる（[図 5c](#figure-05)）。

**コンパイラ最適化。** SPMD パーティショナーは、スライス、パディング、連結、マスキング、halo 交換のために多くのデータ形式演算子を生成する。この問題に対し、TPU 向け XLA の Fusion と、Slice や Pad の code motion 最適化を使い、データ形式処理のオーバーヘッドをほぼ隠蔽する。その結果、マスキングとパディングを多用する畳み込みネットワークでも、実行時間のオーバーヘッドは通常無視できる。

## 4 大規模多言語、大規模機械翻訳（M4）

<span id="section-04-01"></span>

### 4.1 多言語翻訳

GShard による効率的な学習設計を検証するため、多言語ニューラル機械翻訳（MT）[Fir16, Joh16, Aha19] を選んだ。多言語 MT は本質的にマルチタスク学習であり、一つのニューラルネットワークで複数の言語対を同時に翻訳することを目指す。これは本稿の一連の研究 [Hua19, Ari19, Sha17] を Universal Machine Translation モデル [Mul20]、すなわち全分野について 100 以上の言語間を翻訳できる単一モデルへ拡張するものである。このような大規模多言語翻訳モデルは、大規模モデルのストレステストに便利なだけでなく、実運用システムでも有用だと示されている [Rec20]。

大規模多言語 MT でモデル品質の成功を測る基準は二つある。1）学習データが多い言語（高リソース言語）での改善と、2）データが限られる言語（低リソース言語）での改善である。一つの翻訳モデルで扱う言語対（タスク）が増えるにつれ、正の言語間転移 [Bal88] が低リソース言語へ大きな改善をもたらす。対象言語数を考えると、M4 は低リソースタスクの改善に明確な利点がある。反対に、高リソース言語ではタスク数の増加がモデル内のタスク当たり容量を制限し、一つの言語対だけで学習したモデルより翻訳品質が下がる。高リソース言語におけるこの容量ボトルネックは、追加容量を確保できる規模までモデルを拡大すれば緩和できる [Ari19, Hua19]。

したがって、大規模多言語・大規模 MT では、多言語化で正の転移を増やすことと、モデルの大規模化で容量ボトルネックを緩和することの両立を目指す。そのためには、モデルサイズと対象言語数の拡大に適したニューラルネットワークアーキテクチャが必要になる。正の転移を強め、負の転移 [+6] を減らすには、言語間で共有する構成要素（共有サブネットワーク）と、一部の言語に固有の構成要素（非共有の言語固有サブネットワーク）を併せ持つモデルが自然に考えられる。しかし、何を共有するかという設計探索空間は言語数とともに急速に広がり、適切なアーキテクチャをヒューリスティックに探すのは現実的でなくなる。そこで、ニューラルネットワークの接続パターンをデータから学ぶ方法が、拡張可能で実用的な選択肢となる。

本節では、Sparsely-Gated Mixture-of-Experts [Sha17] による条件付き計算 [Ben13a, Dav13a] が以上の要件を満たすことを述べ、ニューラル機械翻訳モデルを 1 兆パラメータ超へ拡張しながら、巨大ネットワークの学習時間を実用的な範囲に保つことで、その有効性を示す。例えば、M4 用の 600B GShard モデルは、1T トークン [+7] を 25 万ステップ、4 日未満で処理できる。モデル容量を増やすためエキスパートを追加し、収束、モデル品質、学習効率に影響する要因を調べる。また、条件付き計算によって学習を高速化できること [Ben15a]、さらにタスクや言語の関連性に関する事前知識がなくても、各トークンをネットワーク内でスパースにゲーティングし、ルーティングする方法を効率的に学べることを示す。すなわち、ルーティングの判断をデータから直接学習する。

<span id="section-04-02"></span>

### 4.2 データセットとベースライン

モデルを段階的に拡大して品質を高めるには、まず大量の学習データが必要である [Kap20]。多言語機械翻訳で密モデルを拡大した先行研究 [Hua19, Ari19] に続き、現実的な試験環境として実世界の MT を扱い、Web 規模の社内データセットを使う。Web から収集した学習コーパス [Usz10] は、英語との間で翻訳する 100 言語の対訳文書を含み、合計 250 億の学習例からなる。この学習セットにはいくつか特徴がある。Web 由来なので結合コーパスには相当なノイズがある一方、多様な分野と言語を含む。その広い範囲と引き換えに、言語対当たりの例数には大きな偏りがある。この偏りは急なべき乗則に従い、高リソース言語の数十億例から低リソース言語の数万例まで広がる。これらの特徴は本研究を難しくするが、同時に試験を可能な限り現実に近づける。データセットの詳細は [Hua19, Ari19] を参照されたい。

本研究では、100 言語すべてから英語への翻訳品質を、BLEU スコア [Pap02] で測定して改善することに注力する。このため、モデルの学習には約 130 億例を使用した [+8]。ベースラインとして、言語対ごとに個別の二言語ニューラル機械翻訳モデル（例えばドイツ語から英語への単一モデル）を学習し、各言語で利用できる学習データ量に応じて調整した [+9]。各言語対の BLEU スコアを個別に示す代わりに、ベースラインを $x$ 軸上のゼロに置く慣例に従い、GShard で学習した各大規模多言語モデルの $\Delta$BLEU トレンドラインを報告する（[図 6](#figure-06)）。[図 6](#figure-06) の $x$ 軸では、利用可能な学習データ量が多い言語から少ない言語へ左から右に並べており、左端が高リソース言語、右端が低リソース言語に対応する。Universal Machine Translation の最終目標は、全対象言語について、単一多言語モデルの $\Delta$BLEU トレンドラインをベースラインより上へ押し上げることである。また、同じデータセットで GPipe パイプライン並列化を用いて学習した 96 層の Transformer エンコーダ・デコーダネットワーク T（96L）の変種も、別のベースラインとして含める（[図 6](#figure-06) の破線）。2048 基の TPU v3 コアで収束まで学習するのに 6 週間以上を要したが [+10]、元の GPipe T（128L） [+11] [Hua19] を上回り、比較対象の中で最も強力な単一の密モデルとなった。

### 4.3 Sparsely-Gated MoE Transformer：モデルと学習

Transformer アーキテクチャの拡大は、近年盛んに探索されている研究分野である [Bap18, Iri19, Wan19d]。新しい手法は概して、層をさらに積み重ねる [Bap18, Hua19]、ネットワークの主要次元（モデル次元、隠れ次元、Attention head 数）を広げる [Dev18, Raf19]、そして近年では architecture search で接続構造を学ぶ [So19] [+12] という方向を取る。大規模多言語機械翻訳では、[Hua19] が GPipe pipeline parallelism を用いた拡大の実践例を示した。60 億パラメータ、128 層の Transformer は高リソース言語を改善し、低リソース言語に最も強い正の転移を示した。この結果は有望で、Universal Machine Translation に求める条件も満たすが、Transformer の密な拡大には、セクション [1](#section-01) で学習効率の観点から述べた実用上の制約がある。

実用的な学習時間を目標とし、学習効率を保証できるアーキテクチャを求める。戦略は三つの要素からなる。GPipe [Hua19] と同様に層を積み重ねてネットワークを深くする。セクション [2.2](#section-02-02) のようにフィードフォワードネットワーク（エキスパート）を複数用意してネットワークを広げる。そしてセクション [2.1](#section-02-01) のように、学習したルーティングモジュールでトークンをエキスパートへスパースに割り当てる。この三要素から、拡張しやすく、効率よく学習でき、表現力の高いアーキテクチャが得られる。これを Sparsely-Gated Mixture-of-Experts Transformer、略して MoE Transformer と呼ぶ。

**モデルの詳細。** 各エキスパートは通常の Transformer フィードフォワードネットワークと同じ形状とし、エキスパート（MoE 層）を Transformer 層一つおきに配置する。簡単のため、学習に使うデバイス数を MoE 層当たりのエキスパート数と同じにしたが、これは必須条件ではない。学習の安定性を保つため、モデル重みと activation の両方に float32 を使う。さらに、bfloat16 [Bfl20] activation と合計 1 兆個のモデル重みを持つ MoE（2048E, 60L）でもスケーラビリティ実験を行った。入念な手動診断を行えば学習できたものの、この深い 1 兆パラメータモデルでは数値安定性に関わる複数の学習上の問題が生じたため、再現性を考慮して結果には含めなかった。モデルと学習の詳細は[付録 A.2](#appendix-a-02) を参照されたい。

### 4.4 結果

学習効率を詳しく見る前に、MoE Transformer を構築する各設計判断の影響を調べる。探索空間を絞るため、Transformer encoder-decoder stack の層数（L）と、一つおきの MoE 層で使うエキスパート総数（E）という二変数を変化させた。深さは、元の Transformer と同じ 12 層（encoder 6 層、decoder 6 層）、36 層、60 層の三通りを試した。一つおきのフィードフォワード層を置き換えるエキスパート数も、128、512、2048 の三通りを試した。学習に使うデバイス数は、試す深さにかかわらず層当たりのエキスパート数と同じに固定し、それぞれ 128、512、2048 コアを使う。モデル構成の詳細は[表 1](#table-01) を参照されたい。

各実験（[表 1](#table-01) の各行）について、対応する MoE Transformer が 1 兆（$10^{12}$）トークンを処理するまで学習し、その時点の checkpoint で評価した。どの実験でも、この時点までに過学習は見られなかった。学習を続ければ、学習損失は引き続き改善した。held-out test set 上で、全言語対についてモデルの BLEU スコアを評価した。結果はすべて[図 6](#figure-06) に示す。

以下では各実験を定性的に分析し、高リソース言語と低リソース言語に対する各設定の意味を論じ、Universal Machine Translation への進展を確認する。分析の前提として、品質向上に期待する挙動を改めて述べる。一つのモデルで高リソース言語と低リソース言語を同時に改善するには、高リソースタスクへ十分な容量を割り当てて容量ボトルネックを緩和しつつ、十分なパラメータ共有によって低リソースタスクへの正の転移を強める必要がある。この種のシステムに期待される学習ダイナミクスを、幅と深さの拡大に関連して近年研究される、古くからの記憶と汎化のジレンマに大まかに対応づける [Che16a]。モデルが held-out test set へよく汎化することに加え、汎化性能の別の表れとして言語間で高い転移能力を示すことも期待する [Lam18]。

<span id="capacity-bottleneck"></span>

**容量のボトルネックを緩和すると品質の大幅な向上が得られる。** 前節 [4.1](#section-04-01) では、容量のボトルネックがタスク間の干渉に与える影響を取り上げ、特に高リソース言語で品質が低下することを示した。その後、層当たりのエキスパート数を増やしてこの問題を緩和したが、その代わり、対象モデルのパラメータ（重み）数は大幅に増えた。ここでは、この容量ボトルネックを明確に観測できるかを調べ、緩和した場合にモデルの品質と効率がどう変わるかを検討する。そのため、まず深さが同じ 12 層の三モデルを用意し、層当たりのエキスパート数を 128、512、2048 と順に増やす。層当たりのエキスパート数を 128 から 512 へ 4 倍にすると、モデル品質は大きく向上し、100 言語の平均 BLEU スコアが 3.3 上がる。しかし、512 から 2048 へさらに 4 倍にしても、平均 BLEU スコアの向上は 1.3 にとどまる。品質は大幅に改善するものの、利得の減少は収穫逓減が現れ始めたことを示唆する。

推測では、本実験のパラメータ設定、言語数、学習データ量に対する容量ボトルネックは、128 から 512 エキスパートの間にある。ボトルネックを緩和すると、その後の深さの拡大による改善を得られる。これは、いずれも 128 エキスパートの 12 層モデルと 36 層モデルを比べると分かる。興味深いことに、容量ボトルネックを緩和しなければ、深さを増やしても効果は小さい。

**エキスパートを増やすと、特に高リソースタスクの品質が向上する。** マルチタスクモデルの拡大による品質向上は、高リソース言語と低リソース言語で改善幅がどう異なるかという観点からも捉えられる。前述のとおり、低リソース言語は転移から恩恵を受ける一方、高リソース言語には容量の追加が必要になる。次に、深さを固定したまま層当たりのエキスパート数を増やした場合の効果を調べる。

[図 6](#figure-06) のように、12 層モデルではエキスパートを増やすと、高リソース言語で大きな改善が得られる一方、低リソース言語では先に見た収穫逓減が現れる。36 層モデルでも同じ傾向が見られる。エキスパートの追加は容量ボトルネックを緩和するが、共有サブネットワークを減らすため、同時に転移量も減る。

**深い密モデルは、低リソースタスクへの正の転移に優れる。** 最後に、前の実験から大まかに導かれる帰結として、低リソースタスクに対する深さの影響を見る。そのため、同じデータについて GPipe で学習した 96 層の密モデル T（96L）を分析へ加え、浅い MoE（128E, 12L）と比較する。高リソースから中リソースまでの大多数の言語では、二モデル間の差はほぼ一定だが、低リソース領域へ入ると、深い密モデル T（96L）が有利になり差が広がる。先に述べたように、タスク間で共有するサブネットワークの割合が増えるほど、転移の帯域幅は大きくなる。100% 共有する密な T（96L）では最大となり、浅いモデルより比較的高い品質をもたらす。また、370 億パラメータの MoE（36E, 128L）でも、低リソース言語について同じ転移品質を達成できる。

深さを増やすと低リソースタスクへの転移が強まり、この軸に沿った汎化も改善する可能性があると推測する。ただし、比較したモデルが必要とする学習資源は均等ではない。これは、次に扱う学習効率の重要性を改めて示す。

### 4.5 訓練効率

本節では MoE Transformer の学習効率を扱う。これまで、複数の軸でモデルを拡大すると品質が大きく向上するという実験的証拠を示し、改善幅を左右する要因を調べた。学習効率を測るため、まず所定の学習損失へ達するまでに処理したトークン数を追跡し、次に所定数のトークンを処理する実時間を追跡する。前節で分析した test error とは異なり、ほかの要因を変えながら学習時間と学習損失 [+13] に注目する。

**深いモデルはサンプル効率が高く、少ない例で速く収束する。** 深いモデルはサンプル効率が高く、同じ数の学習例からより小さな train/test error に到達すると示されている [Hua19, Sho19]。一般には、過剰パラメータ化による加速効果に起因すると考えられる [Aro18]。この仮説を GShard と MoE Transformer で改めて実験的に検証し、深いだけでなくスパースに活性化するモデルの trade-off を示す。

## 5 パフォーマンスとメモリ消費量

本節では、TPU 上で GShard が達成する計算効率とメモリ効率を論じる。測定と分析から、デバイス数とエキスパート数を増やしてもデバイスメモリ消費はほぼ一定で、ステップ時間は亜線形に増えることが分かった。すなわち、128 デバイスから 2048 デバイスへモデルを 16 倍に拡大しても、実行時間は 1.7 倍にしか増えない。さらに各種の分割演算子について microbenchmark と分析を示し、本稿以外の用途にも指針を与える。

<span id="section-05-01"></span>

### 5.1 メモリ効率とスケーラビリティ

GShard モデルのメモリ使用は主に三種類あり、いずれも SPMD 分割後のデバイス当たりサイズは、エキスパート数を増やしても一定である。

- 複製した重み（Transformer のフィードフォワード層など）。

- 分散した重み（MoE フィードフォワード層 [+15]）。

- Activation（順伝播と逆伝播の両方で使う各層の出力）。

[図 7](#figure-07) は $O(1)$ のメモリスケーリングを示し、モデルごとのデバイス当たりメモリ使用量を内訳している。層数を固定すれば、エキスパート数を増やしても重みメモリと activation メモリはどちらも一定に保たれる。

一方、重みメモリと activation メモリはいずれも層数に比例して増える。必要量が各デバイスのメモリを超えると、コンパイラによる rematerialization が逆伝播時に一部の activation を自動再計算し、activation のピークメモリを減らす。このため、MoE（2048E, 60L）の activation サイズは MoE（2048E, 36L）より小さい。Rematerialization のオーバーヘッドも最適化されている。例えば 36L と 60L の各モデルで再計算に使うのは総サイクルの 28% と 34% だけであり、デバイスメモリへ収まる 12L と 24L では 0% である。

### 5.2 実行時効率とスケーラビリティ

<span id="figure-08"></span>

![キャプションを参照](../../papers/gshard/figure-08.png)

**図 8.** 実測実行時間と roofline 実行時間の内訳。順伝播だけを示すが、逆伝播も同様の内訳となる。「MoE dispatch and combine」は AllToAll を用いた分割間通信を表す。

[図 8](#figure-08) は、MoE 層と隣接する Transformer 層について実行時間の内訳を示し、達成性能を roofline と比較する。Roofline は、計算、メモリ、通信のいずれかが律速する演算が、ピーク FLOPS、メモリ帯域幅、interconnect 帯域幅の 100% に達すると仮定して見積もる。多くの演算子は複数資源に制約されるため、非常に楽観的な見積もりである。小規模な 128 エキスパートでは、モデルが roofline 性能の 70% 超を達成する。モデルを 16 倍の 2048 エキスパートへ拡大するとデバイス時間は 1.7 倍に増えるが、それでも roofline 性能の 48% を達成する。

性能のスケーラビリティを分析する前に、セクション [3.1](#section-03-01) で述べたテンソル次元サイズの拡大方法を確認する。$D$ 台のデバイスに対し、エキスパート数 $E$ とグループ数 $G$ をどちらも $O(D)$ とする。グループごとの部分エキスパート容量 $C$ は $O(1/D)$ とする。$C$ は 1 以上でなければならないので無限には拡張できないが、数千エキスパートまでなら十分である。

**Transformer 層と MoE フィードフォワード層。** これらはモデルの密な部分で、TPU のピーク利用率を得られるよう設計している。各デバイス上では、エキスパートを増やしても計算コストは一定である。フィードフォワード層と Transformer の射影は主に大きな行列積であり、TPU の行列演算器を有効に使う。本実験でこれらの演算はピーク FLOPS の 85% 超に達した。Attention 演算は主に batch matmul からなり、系列長が短いとメモリ帯域幅に制約される。そのため、本実験で Attention 演算が達成したのはピーク FLOPS の 30% 超にとどまった。

**ゲート計算。** [図 8](#figure-08) の「Gate Einsum」は、[アルゴリズム 2](#algorithm-02) にある最初の二つと最後の Einsum を表す。最初の Einsum は、softmax へ渡すエキスパートごとの入力を計算する射影である。コストは $O(D)$ だが、層全体のごく一部にすぎない。ほかの二つの Einsum は、トークンの振り分けとエキスパート結果の結合を行う。実質的には one-hot 行列による Gather を実装しているため高コストだが、エキスパート数に依存しない $O(\mathrm{GC})=O(1)$ の一定コストである。エキスパートを 128 から 2048 へ 16 倍にすると、これらの Einsum の実行時間は約 2 倍になる。

デバイス当たりに残るゲーティング計算には、ArgMax や Cumsum など多くの汎用計算が含まれる。これらはメモリ帯域幅に制約されるか、本質的に逐次的であり、TPU を十分に活用できるよう設計された処理ではない。実行時間の大半は、トークンごとに選ばれたエキスパートを表す one-hot 行列を、エキスパートごとに選ばれたトークンを表す one-hot 行列へ反転する逐次 Cumsum 演算に費やされる。Cumsum の線形計算量は [図 8](#figure-08) に示す。ゲーティング計算のこの部分も $O(D)$ のコストを持つが、softmax 前の Einsum と同じく定数係数は非常に小さい。128 エキスパートでは実行時間を無視でき、2048 エキスパートでも MoE 層と Transformer 層の総実行時間の 10% 未満である。

ゲーティングで最も大きな部分は通信であり、[図 8](#figure-08) では「MoE dispatch and combine」として示す。これらは AllToAll 演算子で、セクション [5.3](#section-05-03) で述べるようにコストは $O(\sqrt{D})$ となる。エキスパート数を 128 から 2048 へ 16 倍にすると、実行時間は約 3.75 倍になり、MoE 層と Transformer 層の実行時間に占める割合は 16% から 36% へ増える。

### 5.3 通信のマイクロベンチマークとオペレータごとのスケーラビリティ

本節では、基本演算子に対する SPMD パーティショナーの性能スケーラビリティを測定・分析する。これは、本稿の MoE モデル以外の用途にも指針を与える。

**通信プリミティブの性能スケーリング。** MoE モデルで重要な二つの集団通信演算子は AllReduce と AllToAll である。AllReduce は部分結果の集約に、AllToAll は再シャーディングに使う（セクション [3.3.2](#section-03-03-02)）。[図 9](#figure-09) は、16 分割から 2048 分割までの性能スケーラビリティを示す。TPU 上の AllReduce はデバイス数に依存しない実行時間を持つ。[図 9](#figure-09) のばらつきは、正方形か長方形か、torus か mesh かといった各 topology の違いによる。

一方、AllToAll のコストは分割数とともに増えるが、その増加は亜線形である。本稿の 2D TPU クラスタでは、AllToAll のコストはおよそ $O(\sqrt{D})$ であり、$D$ は分割数を表す。各分割が送るデータ量を固定すると（[図 9](#figure-09) では 8 MB または 32 MB）、全分割の送信データ総量は $d=O(D)$ となる。一方、各データ片は平均 $h=O(\sqrt{D})$ hop を移動し、ネットワーク全体には $l=O(D)$ 本のデバイス間 link がある。したがって帯域幅律速なら、AllToAll の実行時間は

$$
t=\frac{\mathrm{dh}}{l}=O(\frac{D\sqrt{D}}{D})=O(\sqrt{D}).
$$

latency 律速でも、実行時間は $O(h)=O(\sqrt{D})$ のままである。2048 分割と 16 分割を比べると、$D$ は 128 倍になるが、AllToAll の実行時間は 9 倍にしか増えない。このため、再シャーディングによって分割間の振り分けを効率よく実装できる（[図 4a](#figure-04)）。

AllGather と CollectivePermute は、より簡単に分析できる。AllGather の出力は入力の $D$ 倍になるため、入力サイズを固定すると通信コストは $O(D)$ となる。CollectivePermute は一対一の通信パターンを持ち、送信元と送信先の組が近くなるよう適切にデバイスを配置すれば、入力サイズを固定したときのコストは $O(1)$ となる。

## 6 関連研究

**ニューラルネットワーク。** 深層学習モデルは人工知能の各分野で大きな成果を上げている。長年にわたり、コンピュータビジョン [Kri12, Sze14, He16]、自然言語理解 [Sut14, Bah14, Wu17]、音声認識と音声合成 [Hin12, Cha16, Chi18, Oor16, She18] で、さまざまなモデルアーキテクチャによる最先端結果が報告されてきた。近年は、attention ベースの Transformer モデルがこれらの分野の最先端をさらに押し上げている [Vas17b, Dev18]。

**モデルのスケーリング。** 学術研究でも産業応用でも、十分なデータセットや複雑なタスクでは、大きなニューラルネットワークほど性能が高い傾向にある。単一モデルファミリー内では、ネットワークを幅または深さの方向に拡大するだけで、経験的に性能が向上することが多い。例えば、より深い ResNet は [He16a]、より大きな Transformer は [Vas17b] で、より高い翻訳品質を示した。語彙を拡大したモデルや、埋め込みと特徴を組み合わせたモデルも [Ari19, Con19] で性能が向上している。異なるモデルファミリー間でも、大きなモデルは容量が大きいため学習データにより適合するだけでなく、テスト時にもよりよく一般化する [Zha17, Ney17, Hua19]。この観察を受け、通常の研究モデルや実運用モデルよりはるかに大きなニューラルネットワークを構築する研究が進められてきた。Shazeer らは、Mixture-of-Experts 層を用いた 690 億パラメータの再帰言語モデルが、one billion words（LM1B）ベンチマークで非常に低いテスト perplexity を達成したことを示した [Sha17]。Brown らは、非スパースな 1750 億パラメータモデルが、複数の下流 NLP タスクで高精度な few-shot 性能を示せることを報告した。

**ハードウェア。** ニューラルネットワークには無視できない計算能力が必要である。この需要に応えるため、学習と推論向けの専用ハードウェア（chip と network 接続した machine）は 25 年前から作られてきた [Ien96]。2000 年代後半には、ニューラルネットワークの高速化へ GPU が使われ始めた [Rai09, Kri12, Cir10]。近年は、費用対効果の高いニューラルネットワーク用ハードウェアを求め、産業界も専用システムへ多額を投資している [Jou17a]。ニューラルネットワークの主要計算（Convolution、行列積、Einsum など、積の総和を取る各種計算）は並列性の高い数値計算なので、こうした chip は多数の浮動小数点演算器（FPU）を備える。そのため、専用ハードウェアの計算能力は大きく伸びた。GPU の FLOPS 当たり価格は直近 4 年だけで 10 分の 1 に下がり [Rec19]、W 当たり FLOPS は過去 12 年で 2 桁増えたと報告されている [Sun19a]。広く利用できる低価格な計算能力は、ニューラルネットワークの成功を支える主要因である。

**ソフトウェア。** ニューラルネットワークを支えるソフトウェアシステムは、基盤ハードウェアの進歩とともに発展してきた [Dea12, Bas12a, Aba16, Pas17]。アクセラレータは高度に並列な計算機だが、直接のプログラミングは難しい。Framework はニューラルネットワークの構築を容易にし、ハードウェア固有の多くの詳細を実務者から隠蔽した。その一方で、専用ハードウェア（アクセラレータ）を効率よく駆動するため、Nvidia GPU 向け CUDA [Nic08] や Google TPU 向け XLA [Xla17] など、低水準 library に依存する。専用ハードウェアで高効率を得るには、これらの library が欠かせない。

**モデルの学習と推論における並列性。** 現代のニューラルネットワークは、複数アクセラレータを備えた machine 群を学習と推論に広く使う。Data parallelism [Kri12] は最も一般的で、TensorFlow [Aba16]、PyTorch [Pas17]、JAX [Bra18, Fro18] などの主要 framework が対応する。各デバイスは異なる入力データについて同じプログラムを実行し、重みを更新する前に局所勾配を結合する。一方、model parallelism は入力 batch 以外の軸でも計算を分割し、巨大モデルの構築に必要となる。例えば pipelining [Hua19, Har18] は大規模モデルの層を複数 stage へ分け、演算子単位の分割 [Sha18a, Jia19a] は個々の演算子を小さな並列演算子へ分ける。GShard は演算子単位の分割を使い、多数の並列エキスパートへモデルを拡張した。

**自動並列化。** 分散異種環境のプログラミングは、特に高水準のインターフェースを使う実務者には難しい。そのため深層学習フレームワークは、分散計算の実行方法をユーザーが指定する負担を軽減しようとしている。例えば TensorFlow [Aba16] は、データ並列に加え、ノード単位のデバイス割り当てでグラフを分割する基本的なモデル並列をサポートする。Mesh TensorFlow [Sha18a] では、TensorFlow 上の Python ライブラリを使って計算を書き換えることで、SPMD 式の演算子単位分割による大規模モデルを構築できる。これに対し、本手法はユーザーにモデルの書き換えを求めず、軽量なアノテーションに基づいてコンパイラ内でグラフを分割する。FlexFlow [Jia19a] は自動探索によってグラフ内の演算子に対する最適な分割を見つけ、性能を高める。FlexFlow が分割方針の決定に重点を置く一方、本稿の SPMD パーティショナーは、注釈付きグラフを変換する仕組みに重点を置く。Weight-update sharding [Xu20a] は XLA に基づく別の自動並列化変換で、主に TPU クラスタの性能最適化を扱い、概念上は GShard の特例とみなせる。Zero [Raj19] は、重み、活性化、オプティマイザ状態を別々に分割して並列学習デバイス上のメモリ冗長性を減らす一連の最適化を提示し、モデルを 1700 億パラメータまで拡張できる。これに対して GShard はこれらのテンソルを区別しないという意味でより汎用的であり、対応するテンソルへ注釈するだけで個々の分割手法をすべて実現できるため、1 兆以上のパラメータまで拡張し、より多くの設計を検討できる。

**条件付き計算と機械翻訳。** 条件付き計算 [Ben15a, Sha17, Elb20, Bap20a] では、入力依存のサブネットワークを活性化して例をネットワーク内でルーティングする。このルーティングは、例の推定難易度 [Lug20]、利用可能な計算予算 [Elb20, Bap20a]、あるいはスパース性を導入した Mixture-of-Experts による学習済み基準 [Sha17] など、特定の基準に条件付けられる。柔軟で、最新のニューラル系列モデルである Transformer [Vas17b] に拡張しやすいことから、本稿では Sparsely-Gated Mixture-of-Experts [Sha17] を拡張して学習効率を実現する。

## 7 結論

本稿では、大規模計算を自動分割する深層学習モジュール GShard を紹介した。GShard がユーザーのモデルコードに求めるのは軽量なシャーディング注釈だけであり、巨大ニューラルネットワークを拡張するための使いやすく柔軟な API を提供する。GShard を適用し、Sparsely-Gated Mixture-of-Experts 層を持つ Transformer（MoE Transformer）を拡張した。その結果、6000 億パラメータの多言語ニューラル機械翻訳モデルを 4 日間で効率よく学習し、一つのモデルで 100 言語から英語へ翻訳したとき、従来手法より高い性能と品質を達成できることを示した。翻訳品質だけでなく学習効率にも優れ、100 個のバイリンガル Transformer baseline をすべて学習する 29 TPU 年に対し、GShard の MoE Transformer は 22 TPU v3 コア年で学習できる。本稿の実験結果は、条件付き計算によるモデル拡大が実世界の機械学習応用の品質を高め、かつ学習時にも実用的でサンプル効率に優れることを確認した。提案手法はスケーラビリティとコストの良好な trade-off を示し、巨大ニューラルネットワークを拡張するためのモデル固有 framework や tool の必要性を減らす。以上の結果は、モデル品質を高めるニューラルネットワーク拡大の現実的かつ実用的な方向を明らかにする。

本研究からいくつかの教訓を得た。ニューラルネットワークを段階的に拡大すると一貫して品質が向上し、モデルを拡大しても改善がまだ頭打ちになっていないことが分かった。本稿の結果は、モデル拡大が深層学習実務者に必須の手段だと裏付ける一方、学習効率も追求すべきだと示す。そのため、学習効率に影響する要因を特定し、下流タスクの品質へ及ぼす影響を示した。条件付き計算で構築したニューラルネットワークは、規模と計算コストの間に良好な trade-off をもたらす。この重要な設計判断により、1 兆規模のパラメータを持つモデルを学習する実験 cycle を、数か月や数週間ではなく数日で回せた。

さらに、モデル記述と並列化実装を分ける適切な抽象化層があれば、モデル開発者はネットワーク実装へ集中でき、GShard が計算グラフを自動分割して全デバイスで並列実行するプログラムを生成する。すべての基盤デバイス上の計算を表せる一つの汎用プログラムを生成することが、コンパイルのスケーラビリティを確保する鍵だと分かった。分割ごとに専用プログラムを生成する従来方式では、数千分割まで拡大したときにコンパイル時間が爆発的に増える。この複雑さへ対処するため、SPMD シャーディングに基づく各種のコンパイラ改良を導入し、任意のテンソル次元を分割できるようにした。結論として、モデル拡大と学習効率は両立させる必要がある。条件付き計算などのアルゴリズム改善を使いやすい interface と組み合わせれば、大きな計算能力を有効に使える。

最後に、単なるパラメータ数は、大規模モデルの実効容量と必ずしも相関しないことを実験結果が支持する [Li18b, Mad20]。モデル比較では問題の性質、本稿のようにタスク間で学習データが大きく偏る大規模マルチタスク設定も考慮し、容量ボトルネックと正の転移という、ネットワークの異なる動作状態を左右する要因も統制すべきである。

### A.1 平坦ビームサーチによるデコーディング

Decoding では、[Wu17] と同様に長さ正規化を行う beam search を使う。Decoding は自己回帰的に対象系列を一 token ずつ生成するため、長さ $m$ の出力では decoder layer stack を逐次 $m$ 回実行する。特に各 decoder MoE 層には dispatch/combine 演算があり、デバイス間通信を要する。推論には、学習時と同じデバイス数の同じクラスタを使う。

Beam search 中は、全 token が交互に並ぶ一つの系列へ beam 仮説を平坦化し、各仮説が結合した平坦系列内の適切な位置だけへ attention するよう、decoder self-attention mask を変更する。各 decoder self-attention 層が保持する key/value tensor にも同じ変換を施す。これにより、beam を展開するたびに、計算済みの attention key/value を並べ替えずに済む。代わりに、現在 active な仮説を表す $0/1$ mask だけを並べ替える。ただし attention は $k$ 倍長くなる。

この trade-off の損得は実装の詳細による。[Sha19] が述べるように、Transformer の逐次 decoding ではメモリ帯域幅の制約が重要である。この観点では、beam の平坦化により、計算量/メモリ量比が低い二演算（attention の dot product と key/value の並べ替え）を、同じ総メモリ量へアクセスしながら、比率がやや高い一演算（より多くの key を含む長い系列上の attention dot product）へ置き換える。

### A.2 機械翻訳実験の詳細

機械翻訳実験の MoE Transformer は、a）Transformer model dimension 1024、b）Feed Forward と MoE の hidden dimension 8192、c）multi-head attention の 16 head、d）attention key/value dimension 128、e）input、residual、attention の dropout 率 0.1 を共通に使った。

Adafactor [Sha18] optimizer は、a）factorized second-moment estimation、b）first-moment decay $\beta_{1}=0.0$、c）$1-t^{-0.8}$ schedule による second-moment decay $\beta_{2}=0.99$、d）update clipping threshold 1.0、e）10k 学習 step 後に平方根 decay する learning rate 1.0、という設定で使った。

SentencePiece [Kud18] subword tokenizer を使い、source 側には 102 言語を対象とする 64000 語の単一多言語 vocabulary、target 側には英語だけの 32000 語 vocabulary を用いた。

### A.3 汎用シャーディング API

セクション [3.2](#section-03-02) に挙げた二つの一般的なシャーディング API（`replicate()` と `split()`）に加え、ユーザーまたはコンパイラは、データ転送を減らす高度なシャーディング戦略も使える。

`shard(tensor, device_assignment)` は、指定した device assignment でテンソルを分割するよう注釈し、注釈済みテンソルを返す。Device assignment は分割方法を表す多次元整数配列である。`device_assignment` はデータテンソルと同じ rank を持ち、要素数は総分割数に等しく、各要素は対応するデータ slice を置くデバイス ID を表す。例えば、形状 $[3,16,64]$ の 3D tensor に形状 $[1,2,4]$ の device assignment を与えると、分割形状は $[3,8,16]$ となる。Device assignment 内の要素順が、各分割の占める slice を決める。

<span id="figure-10"></span>

![キャプションを参照](../../papers/gshard/figure-10.png)

デバイス間のデータ移動は並列実行性能を大きく左右する。したがって、性能を最大化する device assignment へデバイス ID を割り当てる際は、対象デバイスの topology と、tensor の分割間通信の両方を考慮する必要がある。[図 10](#figure-10) は、デバイス topology と tensor 上の行方向通信 pattern に基づく二つの device assignment を示す。

### A.4 Convolution と window ベース演算子の SPMD 分割

GShard は Convolution の空間次元を分割でき、巨大画像のような用途にも対応できる汎用性を持つ [Che19a]。Convolution 層を空間分割するには、次のようにシャーディング API を使う。


```pseudocode
# 入力画像 [N, C, H, W] を W 空間次元に沿って分割
inputs = split(inputs, 3, D)
# カーネルを複製
kernel = replicate(kernel)
conv = conv2d(inputs, kernel)
...
```

GShard はその後、空間次元のシャーディングをほかの層と逆伝播へ伝播する。以下では、Convolution などの演算子を分割するときの具体的な難しさを述べる。Convolution や ReduceWindow などの window ベース演算は、window 間でデータを共有する場合があるため、いずれも何らかの halo 交換を必要とする。分割間の halo データ交換には CollectivePermute を使うが、CollectivePermute が静的形状を必要とする一方、halo サイズは分割ごとに異なることがある。

まず、SPMD パーティショナーが考慮する window 設定を示す。Convolution の各空間次元には、次の設定がある。

- Stride は、次の出力要素を生成するときに window が移動する距離（要素数）である。

- Low/high padding は、LHS（base）次元の low/high 側へ追加する要素数である。

- Base dilation は LHS の dilation factor、すなわち各要素間へ挿入する要素数に 1 を加えた値である（low/high padding は除く）。Base dilation を行わない場合は 1 とする。

- Window dilation は、RHS（window）の各要素間へ挿入する要素数に 1 を加えた値である。

**一定でない halo サイズ。** Dilation のない単純な例で、一定でない halo サイズが一般に生じることを示す。[図 11](#figure-11) は 4 分割した Convolution で、各分割の右 halo サイズは（1, 2, 3, 4）となり、分割 ID の線形関数 $\mathrm{partition}\_\mathrm{id}+1$ で表せる。分割 1 は二つの出力要素（赤い cell）を生成するため、分割 0 から 0 要素、分割 2 から 2 要素（二つの赤い点線 window が覆う領域）を受け取る必要がある。

**図 11.** Halo サイズが一定でない Convolution。

**図 13.** Base dilation を伴う分割 Convolution。

**Base dilation。** 各分割の offset が dilation hole 上に来る場合があり、low/high padding は dilation 後に適用されるので、端と内部要素の挙動が異なる。そのため base dilation は halo 交換をさらに複雑にする。Base dilation は三つの場合に分けて扱う（[図 13](#figure-13)）。

- $\mathrm{stride}\times \mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}$ が $\mathrm{dilation}$ で割り切れる場合。$\mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}$ は各分割が処理する window 数、すなわち分割当たりの出力要素数である。この条件により、全分割は LHS の最初のデータ要素より前に、同数の内部 padding または low padding 要素を置いて始まるため、同じ low padding を使える。Halo 交換は dilation も padding も施していない base 領域で行い、分割 $i$ に必要なデータの終端 index は次式で求める。

$$
\frac{\mathrm{stride}\times \mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}\times i+\mathrm{window}\_\mathrm{size}-\mathrm{low}\_\mathrm{pad}+\mathrm{dilation}-1}{\mathrm{dilation}},
$$

この値から右 halo のサイズが決まる。$\mathrm{stride}\times \mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}$ は $\mathrm{dilation}$ で割り切れるので、$a$ と $b$ を定数とする $a\times i+b$ へ簡約できる。

- $\mathrm{stride}==1$ だが、$\mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}$ が $\mathrm{dilation}$ で割り切れない場合。分割ごとに必要な low padding は異なるが、window 演算では静的設定なので、SPMD 実行時に分割別の設定を使えない。オペランドへ Pad と DynamicSlice を適用する方法も機能しない。これらの演算子は dilation より先に適用され、すべてが dilation factor 倍されるためである。ただし $\mathrm{stride}==1$ なら、padding と dilation を施した base 領域の全位置が有効な window 開始位置になる。そこで全分割の最大 low padding を使い、各分割で必要な window をすべて計算した後、分割済み window 演算子の出力へ DynamicSlice を適用して余分なデータを除く。分割 $i$ について、padding 前の base 領域で必要なデータの終端 index は先ほどと同じく、

$$
\frac{\mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}\times i+\mathrm{window}\_\mathrm{size}-\mathrm{low}\_\mathrm{pad}+\mathrm{dilation}-1}{\mathrm{dilation}},
$$

となるが、$a\times i+b$ には簡約できない。

- $\mathrm{stride}\neq 1$ で、$\mathrm{stride}\times \mathrm{per}\_\mathrm{shard}\_\mathrm{window}\_\mathrm{count}$ が $\mathrm{dilation}$ で割り切れない場合。上のどちらにも当てはまらなければ、分割ごとに開始時の padding 要素数が異なる可能性があり、すべての offset が有効な window 開始位置になるわけではない。[図 13](#figure-13) の最後の例では、どの low padding を選んでも無効になる分割がある。$\mathrm{stride}\neq 1$ なので、有効な window を飛び越える場合があるためだ。この問題は、base 領域だけでなく window にも padding を施して解決する。Base 領域には全分割が必要とする最大 low padding を使い、その分だけ window サイズを増やす。ただし window 側の low/high padding 量は分割ごとに異なるので、Pad の後に DynamicSlice を行って実装する。Window padding で base 領域の整列していない要素を mask し、padding していない window 要素の先頭を、各分割の base 領域で必要な開始位置へ揃える。

**Window dilation。** RHS を複製する場合、window dilation は LHS に基づいて演算子を分割するときの実効 window サイズだけに影響する。Dilation 済み RHS も分割する場合は、通常 stride 付き Convolution の勾配計算で生じるが、RHS には low/high padding がないため、window dilation は base dilation より扱いやすい。実装の詳細は省略する。
