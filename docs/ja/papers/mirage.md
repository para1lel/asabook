## 概要

本稿では、テンソルプログラム向けとして初のマルチレベル・スーパーオプティマイザ Mirage を提案する。Mirage の中核となる着想は、GPU 計算階層のカーネル、スレッドブロック、スレッドの各レベルでテンソルプログラムを統一的に表現する μGraph である。μGraph により、Mirage は代数変換、スケジュール変換、新しいカスタムカーネルの生成を組み合わせた新規の最適化を発見できる。広大な探索空間を扱うため、Mirage は抽象化に基づく枝刈り手法を導入し、探索空間を大幅に縮小するとともに一定の最適性保証を与える。最適化後の μGraph が入力プログラムと等価であることを保証するため、Mirage は強い理論的保証を備えた確率的等価性検証手続きを導入する。評価の結果、広く利用され入念に最適化されている DNN においてさえ、Mirage は既存手法を大幅に上回ることが示された。Mirage は [https://github.com/mirage-project/mirage](https://github.com/mirage-project/mirage) で公開されている。

## 1 はじめに

GPU 上でディープニューラルネットワーク（DNN）を高性能に実行できることは、現代の ML アプリケーションにとって不可欠である。現在の DNN フレームワークでは一般に、テンソルプログラムを用いて DNN 計算を記述する。テンソルプログラムは有向非巡回グラフであり、そのノードとエッジはテンソル代数演算子（行列乗算など）と、演算子間で共有されるテンソル（すなわち $n$ 次元配列）を表す。

入力テンソルプログラムを最適化するため、既存フレームワーク（PyTorch [Pyt17] や TensorFlow [Aba16] など）は、人手で設計した規則によりテンソルプログラムを専門家が記述した GPU カーネルへ対応付ける。これらの手法では通常、最適化規則の設計と実装に多大なエンジニアリング作業が必要となり、最適化の機会を見逃す場合もある。この課題に対処するため、近年では包括的なプログラム変換空間を探索し、対象 GPU 上での性能に基づいて変換を適用することでテンソルプログラムを最適化する*自動化*手法が提案されている。これらの手法は概ね二つに分類できる。

第 1 の分類には Halide [Rag13]、TVM [Che18]、Ansor [Zhe20] などがあり、Halide で導入されたアルゴリズムとスケジュールの分離 [+1] という着想に基づき、アルゴリズムを固定したままテンソルプログラムの*スケジュール*を最適化する。所与のアルゴリズムに対して、これらのオプティマイザは対象ハードウェア上でカーネルを実行する戦略の候補を探索し、高性能なカーネルを自動生成する。しかし DNN は線形代数的な性質をもつため、一つのテンソルプログラムを数学的に等価な幅広いアルゴリズムで表現できる。既存のスケジュールベース・オプティマイザは、ユーザがアルゴリズムを手動指定したカーネルのみを対象とするため、最適化の機会を逃している。

第 2 の分類には TASO、Grappler、Tensat、PET などがあり、テンソルプログラムに対する異なるアルゴリズム間の数学的等価性を利用する*代数変換*を扱う [Jia19b, Opt19, Yan21f, Wan21]。代数変換の例には、（1）畳み込みを行列乗算へ変換するなど、ある線形代数演算子を別の演算子へ変換すること、（2）複数の演算子を融合してメモリアクセスとカーネルのオーバーヘッドを減らすこと、（3）可換則、結合則、分配則に基づいて演算子を再編成することがある。これらのオプティマイザはアルゴリズムレベルで代数変換を行い、利用可能な演算子群とその実装をプログラマが手動で指定する必要がある。そのため、与えられたカーネルの性能に制約される。

どちらの分類に属する既存の自動最適化手法も、依然としてプログラマがカーネル群（各カーネルはテンソル関数で定義される）を手動指定し、その後で代数変換*または*スケジュール変換の探索空間を探索する必要がある。しかし一部の高度な性能最適化には、GPU 計算階層のカーネル、スレッドブロック、スレッドの各レベルをまたぐ協調的な変換が必要であり、まったく新しいカーネル計算の導入も伴う（たとえば、標準カーネルを分解し、一部の計算だけを融合するカスタムカーネル）。このような最適化は既存の自動手法の探索空間に含まれておらず、今なお手動で実装しなければならない。

その一例が FlashAttention [Dao23]（詳細は[第 8.2 節](#section-8-2)を参照）である。FlashAttention は、アルゴリズムレベルで演算子を並べ替え（代数変換）、GPU カーネル間で計算を再編成して新しいカスタムカーネルを作り、各カーネルの並列化戦略を GPU アーキテクチャへ適応させる（スケジュール変換）ことで、GPU 上の attention [Wol22a] を最適化する。この例に必要な変換は既存フレームワークでは自動発見できないため、手動で実装しなければならない。広く使われているテンソルプログラム・オプティマイザ Triton [Til19] による FlashAttention の実装は、700 行を超えるコードからなる [Htm23]。

本稿では、テンソルプログラム向けとして初の*マルチレベル・スーパーオプティマイザ* Mirage を提示する。Mirage は、代数変換、スケジュール変換、新しいカスタムカーネルの発見を一体として最適化する必要がある高度なテンソルプログラム最適化を、自動で発見し検証する。

Mirage の中核となる着想は、GPU 計算階層の複数レベルにわたってテンソルプログラムを記述する*階層グラフ表現* μGraph である。カーネル、スレッドブロック、スレッドの各レベルを統一的に扱うことで、μGraph はこれらのレベルにまたがる代数変換とスケジュール変換の両方を表現できる。さらに、μGraph の最適化では、代数変換とスケジュール変換の範囲を越えて新しいカスタムカーネルを導入できる。たとえば Mirage は、FlashAttention [Dao23] とその推論版 FlashDecoding [Htm23a] を表す μGraph に加え、特定の用途ではこれらの人手設計カーネルを最大 $2.2\times$ 上回る別の μGraph も自動発見する。Mirage が発見する最適化の大半は、既存手法の探索空間には含まれない。

<span id="figure-01"></span>

![図 1。Mirage の概要。](../../papers/mirage/figure-01.png)

**図 1。** Mirage の概要。

[図 1](#figure-01) に Mirage の概要を示す。Mirage はまず、入力テンソルプログラムを制限された Lax フラグメントに属するサブプログラムへ分割する。[第 5 節](#section-5)で形式的に定義する Lax フラグメントには、行列乗算や畳み込みなどの多重線形演算子、除算（正規化に有用）、制限付きの指数演算（活性化に有用）が含まれる。テンソルプログラムを Lax サブプログラムへ分割すると、大半の最適化機会を保ちながら探索空間を縮小でき、Mirage の確率的等価性検証器も利用可能になる。

**式誘導型 μGraph 生成器。** Mirage の*式誘導型生成器*は、各 Lax サブプログラムについて、それと等価になり得る μGraph を網羅的に探索する。Mirage が対処すべき重要な課題は、従来のスーパーオプティマイゼーション手法に比べて探索空間が著しく大きいことである。たとえば TASO [Jia19b] と PET [Wan21] は固定された事前定義カーネル群を用い、カーネルレベルのテンソルプログラムだけを探索する一方、Mirage はカーネル、スレッドブロック、スレッドの各レベルをまたいでスーパーオプティマイゼーションを行う。この大幅に大きな探索空間を効率よく進むため、Mirage は*抽象式*に基づく新しい枝刈り手法を導入する。この手法は、発見される μGraph の最適性について一定の理論的保証を与えながら、Mirage が検討すべき μGraph の数を大幅に減らす。さらに Mirage は、探索をカーネルレベルとブロックレベルへ集中させ、スレッドレベルには規則ベースの手法を用いることで探索空間を縮小する。

**確率的等価性検証器。** Mirage が発見した μGraph の入力プログラムに対する機能的等価性の検証にも、別の課題がある。プログラムの入出力テンソルには最大で数百万個もの要素が含まれるからである。Mirage の鍵となる着想は、有限体上でランダムテストを行い μGraph 間の等価性を確認する*確率的等価性検証*である。一般のプログラムではランダムテストから得られる正当性保証は通常限られるが、Mirage は Lax フラグメントが課す制約により、Lax プログラムに対する有限体上のランダムテストが強い正当性保証を与えることを示す新たな理論的結果を利用する。具体的には、多項式恒等性テスト（PIT）アルゴリズム [Sch80, Zip79] を Lax プログラムへ一般化でき、精度を任意に高められる Lax プログラム等価性の乱択アルゴリズムが得られることを示す。Mirage はこの乱択アルゴリズムを用い、最適化後の各プログラムが入力プログラムと等価であることを確率的に保証する。

**μGraph オプティマイザ。** 検証済みの各 μGraph に対し、Mirage の μGraph *オプティマイザ*は、候補となるテンソルレイアウト、演算子実行順序のスケジューリング、カーネル、スレッドブロック、スレッドの各レベルにおけるメモリ割り当て計画をさらに検討し、実行時性能を最大化する。最終的に Mirage は、個々の Lax サブプログラムについて発見された最良の μGraph に基づく最適化済みテンソルプログラムを返す。

**評価結果。** NVIDIA A100 および H100 GPU 上で、一般的に使われる多様な DNN ベンチマークを用いて Mirage を評価する。LLM で使われる group-query attention [Mod24] のように、広く利用され既存システムで入念に最適化されている DNN ベンチマークにおいてさえ、Mirage は既存システムにない巧妙なカスタムカーネルと最適化を活用し、現行手法を最大 $3.3\times$ 上回る。

## 2 マルチレベル・グラフ表現

Mirage は、GPU 上でのテンソルプログラムの実行を μGraph で記述する。μGraph は複数レベルの階層グラフをもち、カーネル、ブロック、スレッドの各レベルにおける計算を表現する [+2]。本節ではまず GPU の階層を説明し、[図 3](#figure-03)を一貫した例として用いながら、μGraph の主要な構成要素を紹介する。

<span id="figure-02"></span>

![図 2。GPU の計算階層とメモリ階層。](../../papers/mirage/figure-02.png)

**図 2。** GPU の計算階層とメモリ階層。

**GPU 階層。** [図 2](#figure-02) に現在の GPU の階層を示す。GPU 上の計算は*カーネル*として編成され、各カーネルは単一プログラム・複数データ（SPMD）方式で複数の GPU コア上に同時に実行される関数である。カーネルには*スレッドブロック*のグリッドが含まれ、各ブロックは一つの GPU ストリーミングマルチプロセッサ上で実行され、個々のデータ要素を計算する複数の*スレッド*を含む。各スレッドにはスレッドごとの*レジスタファイル*が対応し、一つのスレッドブロック内の全スレッドは、協調演算を可能にする*共有メモリ*へアクセスできる。最後に、カーネルのすべての入力と出力は GPU の*デバイスメモリ*に格納される。

<span id="figure-03"></span>

![図 3。RMSNorm と MatMul の計算グラフ、および Mirage が発見した最良の μGraph。](../../papers/mirage/figure-03.png)

**図 3。** [図 3a](#figure-03) は RMSNorm と MatMul の計算グラフである。[図 3b](#figure-03) は RMSNorm と MatMul を計算するために Mirage が発見した最良の μGraph を示す。この μGraph は計算を単一カーネルへ融合してデバイスメモリアクセスとカーネル起動オーバーヘッドを減らし、既存手法を $1.9\times$ 上回る。角括弧内の数値はテンソル形状を、波括弧内の数値は対応する演算子の *imap*、*omap*、または *fmap* を示す。

**カーネルグラフ。** 各テンソルプログラムは一つの*カーネルグラフ*に対応し、各ノードは GPU 全体で動作するカーネルを、各エッジはカーネル間で共有されるテンソルを表す。異なるカーネル間ではレジスタファイルや共有メモリのデータを共有できないため、カーネルグラフ内のすべてのテンソルは GPU デバイスメモリに格納される。カーネルグラフの各ノードには、cuDNN [Che14] による畳み込みや cuBLAS [Cub16] による行列乗算など、既存のカーネルライブラリがサポートする*事前定義*カーネル演算子を使用できる。さらに、カーネル融合のような細粒度のカーネル間最適化を可能にするため、カーネルグラフのノードには、その意味と挙動を下位レベル（すなわちブロック）のグラフで定義する*グラフ定義*カーネル演算子も使用できる。一例として、[図 3b](#figure-03)のカーネル演算子は、ブロックグラフで指定されたグラフ定義演算子である。

**ブロックグラフ。** *ブロック*グラフはスレッドブロックに対応する計算を記述する [+3]。各ノードはブロック内の計算を指定する*ブロック演算子*を表し、各エッジ（[図 3b](#figure-03)の青い矢印）はブロック演算子間で共有されるテンソルを表す。Mirage は、二つの理由から、ブロックグラフ内のすべての中間テンソルを GPU の*共有メモリ*に格納する。第 1 に、GPU 共有メモリはデバイスメモリよりもはるかに高い帯域幅をもつ。この設計により、中間結果を可能な限り共有メモリへ保持し、デバイスメモリアクセスを減らせる。第 2 に、サイズが共有メモリ容量を超えてデバイスメモリへ格納する必要があるテンソルについては、それらを境界として計算を複数のブロックグラフへ分割し、各グラフが共有メモリ内のテンソルだけを含むようにする。この分割によって、デバイスメモリへの追加アクセスは生じない。

各ブロックグラフには実行を指定する属性も対応付けられており、以下で説明する。

<span id="figure-04"></span>

![図 4。*imap* と *fmap* により、入力テンソルがブロックおよび for ループの反復に分割される様子。](../../papers/mirage/figure-04.png)

**図 4。** *imap* と *fmap* により、入力テンソルがブロックおよび for ループの反復に分割される様子。

**グリッド次元。** 一つのカーネル内の全ブロックは、$x$、$y$、$z$ で識別される最大 3 次元のメッシュとして編成される。ブロックグラフには、$x$、$y$、$z$ の各次元に沿ったブロック数を指定する最大三つの*グリッド次元*が対応付けられる。[図 3b](#figure-03)のブロックグラフは $128$ 個のブロックを起動する。

まず、グラフ定義カーネル演算子への各入力テンソル（たとえば[図 3b](#figure-03)のカーネルグラフ内の $X$、$G$、$W$）について、対応するブロックグラフは入力テンソルを個々のブロック用のサブテンソルへ分割する方法を指定する *imap* をもつ。各グリッド次元（すなわち $x$、$y$、$z$）は *imap* により、（1）入力テンソルのデータ次元、または（2）特殊な*複製*次元 $\phi$ のいずれかへ写像される。（1）の場合、対応するデータ次元は、そのグリッド次元に沿うブロック間で*等分*される。（2）の場合、入力テンソルはそれらのブロック間で*複製*される。たとえば[図 3b](#figure-03)のブロックグラフは、各ブロックへの入力テンソルを表す $\overline{X}$、$\overline{G}$、$\overline{W}$ の三つを入力とする。$\overline{W}$ の $\operatorname{imap}=\{x\leftrightarrow d\}$ は、テンソル $W$ の $d$ 次元が同じ大きさの 128 個のチャンクへ分割されることを示す。その結果、$\overline{W}$ の形状は $[h=1024,d=32]$ となる。

次に、ブロックグラフの各出力テンソル（たとえば[図 3b](#figure-03)の $\overline{Z}$）について、ブロックグラフは全ブロックの出力を連結してカーネル演算子の最終出力を構成する方法を指定する *omap* をもつ。異なるブロックはデバイスメモリ上の互いに素なテンソルを格納しなければならないため、*omap* では各グリッド次元を出力テンソルのデータ次元へ写像する必要がある。[図 3b](#figure-03)の形状 $[b=16,d=32]$ をもつ $\overline{Z}$ では、$\operatorname{omap}=\{x\leftrightarrow d\}$ は同じ $x$ インデックスをもつブロックが $d$ 次元に沿って連結され、その結果、形状 $[b=16,d=4096]$ のテンソル $Z$ が得られることを示す。

**for ループ本体。** 大きな入力テンソルを共有メモリへ収め、デバイスメモリからのデータ読み込みと計算を重ね合わせるため、ブロックグラフにはカーネルを完了するまで複数回実行される *for ループ本体*を含められる。カーネル内の for ループの後には、後処理が続くことが多い。たとえば平均値を計算する場合、for ループは $n$ 個の値を合計し、後処理で $n$ により除算する。Mirage は[図 3b](#figure-03)のオレンジ色の枠に示すように、*入力イテレータ*、*for ループ・アキュムレータ*、およびその間にあるすべての演算子を用いてブロックグラフの for ループ本体を指定する。ブロックグラフへの各入力テンソルは、まず*入力イテレータ*を通り、テンソルの一部（たとえば $\overline{X}$、$\overline{G}$、$\overline{W}$）がデバイスメモリから共有メモリへ読み込まれる。各入力イテレータには、反復ごとに入力テンソルのどの部分を読み込むかを指定する *fmap* が対応付けられる。形式的には、*fmap* は各 for ループ次元を（1）入力テンソルのデータ次元、または（2）複製次元 $\phi$ のいずれかへ写像する。*imap* と同様に、（1）ではテンソルがその次元に沿って等分され、（2）では複製される。[図 4](#figure-04)は、異なる *imap* と *fmap* により入力行列がブロックおよび for ループの反復へ分割される様子を示す。

各ブロックグラフには、カーネルの完了まで for ループ本体を何回実行するかを決める *for ループ次元*も対応付けられる。加えて Mirage は、*for ループ・アキュムレータ*（たとえば[図 3b](#figure-03)の二つの `Accum` 演算子）を用いて各反復で計算した中間結果を（加算や max などの標準アキュムレータにより）蓄積し、共有メモリへ格納する。for ループ本体が完了すると、Mirage は本体の外側に残る演算子を蓄積結果へ直接適用する。その後、*出力セーバ*が共有メモリからデバイスメモリへ最終結果を書き戻す。

**スレッドグラフ。** *スレッドグラフ*は、計算範囲をブロックから一つのスレッドへさらに縮小する。ブロックグラフと同様に、各スレッドグラフにもブロック内のスレッド構成を指定する*ブロック次元*と、定義された計算の完了に必要な総反復回数を定める *for ループ次元*が対応付けられる。各スレッドグラフには、入力テンソル（たとえば[図 3b](#figure-03)の $\overline{\overline{A}}$ と $\overline{\overline{B}}$）を共有メモリからレジスタファイルへ読み込む*入力イテレータ*と、出力テンソルをレジスタファイルから共有メモリへ格納する*出力セーバ*（たとえば $\overline{\overline{C}}$）が含まれる。スレッドグラフは μGraph の最下位グラフであり、事前定義スレッド演算子だけを含む。

**テンソルレイアウト。** カーネル、ブロック、スレッドの各グラフ内のテンソルには、メモリ上でテンソルを線形化する方法を指定する*テンソルレイアウト*が対応付けられる（簡潔さのため[図 3](#figure-03)では省略）。テンソルレイアウトは μGraph の性能にのみ影響し、出力の正当性には影響しない。

**定義 2.1（μGraph の妥当性）。** μGraph $G$ が*妥当*であるとは、次を満たすことをいう。（1）$G$ 内の各カーネル、ブロック、スレッド演算子 $o\in G$ について、その入出力テンソルが $o$ の仕様と一致する。（2）各カーネル、ブロック、スレッドグラフ内のすべてのテンソルが、それぞれ GPU デバイスメモリ、共有メモリ、レジスタファイルへ収まる。（3）for ループ本体をもつ各ブロックグラフとスレッドグラフについて、入力から出力への任意の経路が、入力イテレータ、for ループ・アキュムレータ、出力セーバをそれぞれ正確に一つ通る。

**従来研究との比較。** 従来研究は代数変換 [Jia19b, Wan21] とスケジュール変換 [Rag13, Che18, Mul16] を別々に扱う一方、μGraph は両者を統一的に表現できる。具体的には、グリッド次元と for ループ次元、およびそれらからテンソル次元への対応する写像（すなわち *imap*、*omap*、*fmap*）が、グラフ定義演算子に対するスケジュール候補の包括的な探索空間を構成する。カーネル、ブロック、スレッドの各レベルにまたがる階層グラフにより、Mirage はこれらのレベルで代数変換を探索できる。

## 3 ケーススタディ：RMSNorm

本節では、二乗平均平方根レイヤ正規化（RMSNorm）[Zha19l] をケーススタディとして用い、μGraph 表現と Mirage のスーパーオプティマイゼーション手法の利点を示す。RMSNorm は近年の大規模言語モデルで広く使われている正規化手法である [Mod24]。形式的には、RMSNorm は二つのテンソル $X$ と $G$ を入力とし、その要素積を二乗平均平方根に従って正規化する。

<span id="equation-01"></span>

$$
Y_{ij}=\frac{X_{ij}G_{j}}{\operatorname{RMS}(X_{i})},\operatorname{RMS}(X_{i})=\sqrt{\frac{1}{d}\sum_{j=1}^{d}X_{ij}^{2}},
$$

ここで $d$ は $X$ の隠れ次元の大きさである。

RMSNorm の後には行列乗算（MatMul）が続くことが多い。[図 3a](#figure-03)に、RMSNorm 演算子の後に MatMul 演算子が続く計算グラフを示す。$X$ は入力テンソル、$G$ と $W$ は二つの重みテンソルを表す。RMSNorm と MatMul はどちらも内部で入力次元に沿う縮約を行うため、両者の計算を単一カーネルへ融合することは難しく、既存の ML コンパイラは一般に二つの別々のカーネルを起動する。この手法では、異なるカーネル間で共有メモリやレジスタファイルのデータを共有できないため、中間結果（すなわち $Y$）をデバイスメモリへ格納する必要がある。

[図 3b](#figure-03)は、RMSNorm と MatMul を単一カーネルで計算するために Mirage が自動発見した最良の μGraph を示す。計算を単一のグラフ定義カーネル演算子へ融合することで、中間結果（すなわち $Y$）のデバイスメモリへの保存を避け、カーネル起動のオーバーヘッドを減らす。

Mirage が発見した μGraph と元の μGraph との主な違いを示す。これらの違いは、新しいカスタムカーネルの発見と代数変換およびスケジュール変換の組み合わせを伴うため、代数変換とスケジュール変換を別々に検討して最終的な μGraph を発見することは現実的でない。第 1 に、Mirage は行列乗算と要素ごとの除算の可換性を利用し、MatMul と RMSNorm の除算を並べ替える（代数変換）。第 2 に、二乗平均平方根の累積（すなわち $A_{i}=\sum_{j}X_{ij}^{2}$）と行列乗算の累積（すなわち $B_{ik}=\sum_{j}X_{ij}G_{j}W_{jk}$）を並列に行い（スケジュール変換）、累積結果のデバイスメモリへの書き込みを避ける。続いて Mirage はスレッドグラフを具現化し、すべての中間結果をレジスタファイルへ保持しながら、一連の要素単位演算子を実行する（スケジュール変換）。最後に、発見された最良の μGraph は新しいカスタムカーネルを用いて RMSNorm と MatMul の計算を融合し、デバイスメモリアクセスとカーネル起動オーバーヘッドを減らす。この μGraph は、NVIDIA A100 および H100 GPU 上で、既存システムの手書きカーネルをそれぞれ $1.5\times$ および $1.9\times$ 上回る。

## 4 式誘導型 μGraph 生成器

本節では、入力テンソルプログラムに対する μGraph の候補を自動発見する Mirage の μGraph 生成器を紹介する。カーネル、ブロック、スレッドの各レベルにおける最適化を捉える μGraph を生成するため、Mirage はカーネルレベルの最適化だけを扱う既存のスーパーオプティマイザよりもはるかに大きな探索空間を扱わなければならない。Mirage はこの課題に二つの主要技法で対処する。第 1 に、デバイスメモリと共有メモリへのアクセスはレジスタファイルへのアクセスより桁違いに高コストであるため、カーネルレベルとブロックレベルの最適化はスレッドレベルの最適化より性能への影響がはるかに大きいという観察に基づき、Mirage の μGraph 生成器は*ハイブリッド手法*を用いる。すなわち、カーネルレベルとブロックレベルでは一定サイズ以下の可能なグラフをすべて網羅的に検討し、スレッドレベルのグラフ構築には規則ベースの戦略を用いる。この手法は、性能上重要な最適化の大半を保ちながら探索空間を縮小する。第 2 に、探索空間をさらに枝刈りするため、Mirage は*抽象式*と呼ぶ μGraph の抽象化に基づく枝刈り手法を導入する。この手法は、発見される μGraph の最適性について一定の理論的保証を与えながら、Mirage が検討すべき μGraph の数を減らす。[第 4.1 節](#section-4-1)と[第 4.2 節](#section-4-2)でハイブリッド μGraph 生成アルゴリズムを、[第 4.3 節](#section-4-3)で式誘導型の枝刈り技法を説明する。

### 4.1 カーネルグラフとブロックグラフの生成

[図 5](#figure-05)の第 2 部に示すように、Mirage はカーネルグラフとブロックグラフを漸進的に生成し、複数の枝刈り技法で探索空間を縮小する。具体的には、Mirage は妥当な μGraph の*接頭グラフ*を保持し、新しい演算子で反復的に拡張する。グラフ $G=(V,E)$ について、$G^{\prime}=(V^{\prime},E^{\prime})$ が $G$ の部分グラフで、$\forall u\in V^{\prime},\forall(v,u)\in E,v\in V^{\prime}$ を満たすとき、$G^{\prime}$ を $G$ の*接頭グラフ*と呼ぶ。

カーネルグラフの次の演算子を生成するため、Mirage はカーネル演算子型 $t$ と入力テンソル集合 $I$ を列挙する。$t$ がグラフ定義演算子型を表す場合、Mirage はカーネル計算を定義する対応ブロックグラフを次の手順で生成する。（1）[第 2 節](#section-2)で導入したグリッド次元と for ループ次元を列挙し、ブロックグラフの入力テンソル形状を計算可能にする。（2）カーネルレベルと同様の入れ子生成手続きを、グラフ定義演算子は考慮せずに行う。[アルゴリズム 1](#algorithm-01)の $\operatorname{GenerateNextKernelOperator}$ と $\operatorname{GenerateNextBlockOperator}$ は、Mirage がカーネル演算子とブロック演算子をそれぞれ生成する方法を示す。Mirage は $\operatorname{ConstructOp}$ でテンソル形状とメモリ使用量を検査してから演算子を追加し、妥当な接頭グラフであることを保証する。

同一の μGraph が一度だけ生成されるように、Mirage は μGraph の*正準形*を定義する。演算子がトポロジカル順 $o_{1},\ldots,o_{n}$ に並ぶ μGraph $G$ が与えられたとき、$o_{i}$ の $j$ 番目の出力の*インデックス*を組 $(i,j)$ と定義する。$G$ 内の各演算子 $o_{i}$ には*ランク* $(\mathit{input}_{i},\mathit{type}_{i})$ を割り当てる。ここで $\mathit{input}_{i}$ は $o_{i}$ の入力テンソル・インデックスのリスト、$\mathit{type}_{i}$ は演算子型である。演算子がランクの昇順に並んでいるとき、μGraph は正準形である。Mirage は二つの演算子生成手続きで演算子をランクの昇順に追加することを要求し、正準形の μGraph だけを生成する。各 μGraph は演算子を並べ替えることで正準形へ変換できるため、この手法が妥当な解を枝刈りすることはない。

さらに Mirage は、特定の制約を満たさない接頭グラフを枝刈りするために*抽象式*技法を用いる。この技法は[第 4.3 節](#section-4-3)で説明する。

### 4.3 抽象式による枝刈り

可能な μGraph の空間を探索するとき、途中結果が目的の計算に寄与し得ない μGraph の接頭グラフは避けたい。たとえば入力プログラム $X\cdot Z+Y\cdot Z$ に対して、$X\cdot Y$ を計算する接頭グラフは枝刈りできる一方、$(X+Y)\cdot Z$ は入力プログラムと等価なので、$X+Y$ を計算する接頭グラフは枝刈りすべきでない。しかし、目的の計算を探索している最中に、ある接頭グラフがその計算へ寄与し得るかをどう判断すればよいだろうか。以下では、この直観に基づき、*抽象化*によって「鶏と卵」の問題を回避する枝刈り手法を構築する。まず抽象化である*抽象式*を示し、次に枝刈りへの利用方法を説明する。最後に、一定の条件下でこの枝刈りが最適な μGraph を除外しないという理論的保証を与える。

**抽象式。** μGraph のエッジは、入力テンソルに対するテンソル値関数に対応する。直観的には、抽象式は同じ入力テンソル内の要素間の差異を無視して、これらの関数を抽象化する。形式的には、抽象式は整数理論と未解釈関数をもつ一階述語論理の項である。μGraph における各エッジの抽象式を $\mathrm{E}(\cdot)$ と表し、[表 1](#table-01)で定義する。μGraph の抽象式を計算するとき、すべてのグラフ定義演算子を「インライン化」する。具体的には、グラフ定義演算子の入力について計算した式をその下位グラフへ渡し、下位グラフから得られた出力式をグラフ定義演算子の出力式とする。[図 6](#figure-06)は attention の部分グラフに対する抽象式を示す。

抽象式は各エッジで計算される関数の情報をある程度捉える一方、多くの詳細を捨象する。たとえば $X$ が $k\times k$ 行列なら、行方向の和と列方向の和はどちらも同じ抽象式 $\mathsf{sum}(k,\mathrm{E}(X))$ となる。しかし、有効な枝刈りには $k$ を抽象式の一部として保持することが不可欠である。

<span id="figure-06"></span>

**図 6。** 抽象式の例。テンソルの抽象式をエッジ上に注記している。ここでは人が読みやすい表記を用いる。$\mathrm{e}^{a}$ は $\operatorname{exp}(a)$、$\sum_{k}a$ は $\mathsf{sum}(k,a)$、$a/b$ は $\mathsf{div}(a,b)$、$a*b$ は $\mathsf{mul}(a,b)$ を表す。テンソル $I_{1}$、$I_{2}$、$O$ はすべて $64\times 64$ 行列である。

**抽象部分式と枝刈り。** 抽象式上に等価性と抽象部分式という二つの関係を形式化し、μGraph の探索空間を枝刈りする。具体的には、その抽象式が、入力プログラムの抽象式と等価な何らかの抽象式の部分式でない μGraph の接頭グラフを枝刈りする。抽象式を整数算術理論と未解釈関数をもつ一階述語論理上の未解釈関数として形式化し、[表 2](#table-02)の二つの公理集合 $A_{\text{eq}}$ と $A_{\text{sub}}$ に基づいて SMT ソルバで推論する。

第 1 に、$A_{\text{eq}}$ は抽象式間の等価性を公理化する。後に明らかになるように、これらの公理が健全である必要はない。等価でない μGraph が同じ抽象式をもつ場合があるため、抽象式が等価な μGraph 同士が機能的に等価であることは要求しない。第 2 に、$A_{\text{sub}}$ は抽象式間の部分式関係を公理化する。$A_{\text{sub}}$ の重要な性質は、μGraph $G_{1}$ が $G_{2}$ の接頭グラフである、すなわち $G_{1}$ に演算子を追加して $G_{2}$ を構築できるなら、$\mathrm{E}(G_{1})$ が $\mathrm{E}(G_{2})$ の抽象部分式になることである。形式的には $A_{\text{sub}}\models\operatorname{subexpr}(\mathrm{E}(G_{1}),\mathrm{E}(G_{2}))$ であり、$\models$ は整数算術理論と未解釈関数を法とする含意を表す。

探索中、アルゴリズム 1 はまず入力 Lax プログラムの抽象式 $E_{O}$ を計算し、$A_{\text{eq}}\cup A_{\text{sub}}\not\models\operatorname{subexpr}(\mathrm{E}(G),E_{O})$ である μGraph 接頭グラフ $G$ を枝刈りする。すなわち、抽象式が $E_{O}$ の部分式でないグラフを枝刈りする。この検査には SMT ソルバ（Z3 [Dem08]）を用いる。Mirage は探索中に同じ抽象式をもつ複数の μGraph に遭遇し得るため、最適化として検査結果をキャッシュし再利用する。

**理論的保証と枝刈り・最適性のトレードオフ。** 直観的には、この枝刈りは、入力 Lax プログラムの抽象式と（$A_{\text{eq}}$ によれば）等価な抽象式をもつ μGraph へ到達し得る接頭グラフをすべて残す。形式的には次のとおりである。

**定理 1（抽象式による枝刈り）。** 入力 μGraph $G_{0}$ と、それに等価な μGraph $G$ について、$A_{\text{eq}}\models E(G_{0})=E(G)$ ならば、$G$ はアルゴリズム 1 によって生成される。

::: details 証明
[表 1](#table-01)と[表 2](#table-02)から、任意の演算子 *op* について、$Y=\mbox{\rm op}(X_{1},\ldots,X_{n})$ ならば、$1\leq i\leq n$ に対して $A_{\text{sub}}\models\operatorname{subexpr}(\mathrm{E}(X_{i}),\mathrm{E}(Y))$ であることを示す。つまり、*op* の各入力の抽象式は常に *op* の出力の部分式である。$A_{\text{sub}}$ は反射律と推移律の公理を含むため、$G$ の任意の接頭グラフ $G^{\prime}$ について $A_{\text{sub}}\models\operatorname{subexpr}(\mathrm{E}(G^{\prime}),\mathrm{E}(G))$ が従う。仮定 $A_{\text{eq}}\models E(G_{0})=E(G)$ と合わせると、$A_{\text{eq}}\cup A_{\text{sub}}\models\operatorname{subexpr}(\mathrm{E}(G^{\prime}),\mathrm{E}(G_{0}))$ を得る。したがって $G$ の接頭グラフは一つも枝刈りされず、Mirage は $G$ を生成する。
:::

この定理は、先に述べた「鶏と卵」の問題を解く上で抽象式が果たす役割を明らかにする。接頭 μGraph が有用かを判断するため、それが有用な計算の接頭グラフであるかを*抽象上で*推論する。抽象化と公理 $A_{\text{eq}}$ の選択は、最適性と枝刈りのトレードオフを表す。定理 1 が示すように、$A_{\text{eq}}$ の下で入力プログラムと抽象式が等価となる最適な μGraph の発見だけが保証される。より強い公理は定理が対象とする μGraph の集合を広げるが、部分式検査を通過する接頭グラフが増えるため、枝刈りの効果を弱める。特に $A_{\text{eq}}$ は相殺則（たとえば $\mathsf{div}(\mathsf{mul}(x,y),y)=y$）を含まない。その結果、Mirage は等価な μGraph の一部を見逃す可能性がある。しかし、そのような公理を含めると、あらゆるものがあらゆるものの部分式となり、意図した枝刈りが無効になる。評価結果が示すように、選択した $A_{\text{eq}}$ は枝刈りと最適性の良好な均衡をもたらす。

## 5 確率的等価性検証器

Mirage の*確率的等価性検証器*は、μGraph の候補が目的の Lax プログラムと等価かを検査する。鍵となる着想は、二つの有限体上の*ランダム入力*で両者を評価することである。浮動小数点数の代わりに有限体を使うことで、浮動小数点誤差を回避するだけでなく、等価でない μGraph を受理する確率を任意に低くできるという強い理論的保証も得られる。

一般のプログラムでは、ランダムテストから正当性保証を得ることはほぼできない。しかし、以下で形式的に定義する Lax プログラムでは、ランダムテストが確率的な正当性保証を与え、テストを反復すれば誤り確率を任意に小さい閾値まで下げられることを示す。

従来研究 [Wan21] では、線形演算子（行列乗算や畳み込みなど）だけを含むテンソルプログラム間の等価性検査に同様の技法を適用している。本研究では、多くの DNN 最適化（たとえば[第 3 節](#section-3)の RMSNorm の例）に必要な除算と指数演算にも対応するランダムテスト手法を構築する。

Mirage は、以下で定義する Lax μGraph（線形演算、除算、指数演算）間の等価性を検証する。[第 5.1 節](#section-5-1)で主な理論的結果を紹介し、[第 5.2 節](#section-5-2)で Mirage の検証方法を示す。

**定義 5.1（Lax μGraph）。** μGraph $G$ が Lax μGraph であるとは、（1）$G$ が多重線形演算子 [+4]、除算、指数演算だけを含み、（2）$G$ 内の入力から出力への各経路が指数演算を高々一つ含むことをいう。

<span id="section-5-1"></span>

### 5.1 理論的基礎

一般性を失わず、Lax μGraph $G$ は $n$ 個の入力テンソルを取り、一つの出力テンソルを生成すると仮定する。本稿の理論的結果は、複数出力をもつ Lax μGraph へ直接一般化できる。各 Lax μGraph は線形演算子、除算、各経路上で高々一つの指数演算を含むため、出力テンソルの各要素に対する計算は、$\frac{\frac{a}{b}}{\frac{c}{d}}=\frac{ad}{bc}$、$\frac{a}{b}+\frac{c}{d}=\frac{ad+bc}{bd}$、$e^{x}e^{y}=e^{x+y}$ といった標準的な恒等式を使って次の形に表せる。

<span id="equation-02"></span>

$$
\frac{\sum_{i=1}^{k}f_{i}\exp(g_{i}/h_{i})}{\sum_{i=1}^{k^{\prime}}f^{\prime}_{i}\exp(g^{\prime}_{i}/h^{\prime}_{i})}
$$

ここで $f_{i}$、$g_{i}$、$h_{i}$、$f_{j}^{\prime}$、$g_{j}^{\prime}$、$h_{j}^{\prime}$（$1\leq i\leq k$、$1\leq j\leq k^{\prime}$）は、入力テンソルの要素を変数とする多項式である。

本稿の乱択等価性検証を支える主な理論的結果が次の定理であり、有限体上の多項式恒等性テスト（PIT）[Sch80, Zip79] を Lax μGraph へ拡張する。二つの Lax μGraph の差も[式 2](#equation-02)の形になることに注意されたい。したがって、二つの Lax μGraph の恒等性テストは、この形の式がゼロかを調べる問題へ帰着する。指数演算が存在するため、一つではなく二つの有限体を用いる。 [+5]

**定理 2。** $P$ を[式 2](#equation-02)で記述される形の関数とし、$f_{i},g_{i},h_{i},f_{i}^{\prime},g_{i}^{\prime},h_{i}^{\prime}$ は次数が高々 $d$、係数が $[-w,w]$ の範囲の整数である非零多項式とする。$p,q$ を $q\mid p-1$ かつ $q>2w$ を満たす素数とする。$\mathcal{G}$ を $\mathbb{Z}_{p}$ における $q$ 乗根の集合とする。$P$ が零関数でないならば [Li25af]

$$
\Pr_{(\vec{u},\vec{v},\omega)\leftarrow\mathbb{Z}_{p}^{N}\times\mathbb{Z}_{q}^{N}\times\mathcal{G}}\left[\frac{\sum_{i=1}^{k}f_{i}(\vec{u})\omega^{g_{i}(\vec{v})/h_{i}(\vec{v})}}{\sum_{i=1}^{k^{\prime}}f^{\prime}_{i}(\vec{u})\omega^{g^{\prime}_{i}(\vec{v})/h^{\prime}_{i}(\vec{v})}}\right]\leq 8dk^{4}/q+q^{-1/k^{2}}.
$$

<span id="section-5-2"></span>

### 5.2 有限体上のランダムテスト

<span id="table-03"></span>

![表 3。ランダムテスト用の算術演算。Mirage は $q$ が $p-1$ を割り切る二つの素数 $p$ と $q$ を選ぶ。$x_{p}$ と $x_{q}$ は、それぞれ有限体 $\mathbb{Z}_{p}$ と $\mathbb{Z}_{q}$ の値である。表記 $x^{-1}$ と $\sqrt{x}$ は、対応する有限体における $x$ の乗法逆元と平方根を表す。具体的には、$xx^{-1}\bmod p=1$ および $\sqrt{x}\sqrt{x}\bmod p=x$ である。](../../papers/mirage/table-03.png)

**表 3。** ランダムテスト用の算術演算。Mirage は $q$ が $p-1$ を割り切る二つの素数 $p$ と $q$ を選ぶ。$x_{p}$ と $x_{q}$ は、それぞれ有限体 $\mathbb{Z}_{p}$ と $\mathbb{Z}_{q}$ の値である。表記 $x^{-1}$ と $\sqrt{x}$ は、対応する有限体における $x$ の乗法逆元と平方根を表す。具体的には、$xx^{-1}\bmod p=1$ および $\sqrt{x}\sqrt{x}\bmod p=x$ である。

Mirage は定理 2 を利用し、そこで定義した有限体 $\mathbb{Z}_{p}$ と $\mathbb{Z}_{q}$ 上でランダムテストを行うことにより、二つの μGraph の等価性を確率的に検証する。二つの μGraph の等価性を検査するため、Mirage はまず、各要素を $\mathbb{Z}_{p}\times\mathbb{Z}_{q}$ から一様にサンプリングした入力テンソルを生成する。指数演算に使う $\omega$ も、$\mathbb{Z}_{p}$ の $q$ 乗根集合から一様にサンプリングする。次に Mirage は、[表 3](#table-03)で定義した演算を用い、これらの入力上で二つの μGraph を評価する。[第 5.1 節](#section-5-1)で説明したように、$\mathbb{Z}_{p}$ と $\mathbb{Z}_{q}$ はそれぞれ指数の外側と内側の計算に使う。指数演算以外のすべての演算は、$\mathbb{Z}_{p}$ と $\mathbb{Z}_{q}$ で独立に剰余算術を用いて実装する。指数演算では $\mathbb{Z}_{q}$ の値 $x_{q}$ を用い、$\omega^{x_{q}}\bmod p$ を計算して $\mathbb{Z}_{p}$ の結果を得る。

Lax μGraph では、各経路上で指数演算が高々一度しか行われないことに注意されたい。最後に Mirage は、二つの μGraph が同一の出力を生成するかを検査する。この処理を複数回繰り返し、すべてのランダムテストに合格した二つの μGraph を等価とみなす。定理 2 から従う次の定理は、この処理により誤り率を任意に低くできることを示す。

**定理 3。** 等価な μGraph は、必ず μGraph 検証に合格する。等価でない二つの μGraph と所与の確率閾値 $0<\delta\leq 1$ について、それらの μGraph が $\Omega(\frac{k^{2}}{\ln q}\cdot\ln\frac{1}{\delta})$ 回のランダムテストすべてに合格する確率は高々 $\delta$ である。

**数値安定性。** この定理は有限体上の計算と実数計算を橋渡しするが、浮動小数点演算では実数計算との間に相違が生じ得る。特に大きな中間値によるオーバーフローやアンダーフローが関係する場合である。Mirage は浮動小数点テストを用い、大きな数値誤差をもつ μGraph を除外する。

## 6 μGraph オプティマイザ

[図 1](#figure-01)に示すように、Mirage の μGraph *オプティマイザ*は、検証済みの各 μGraph に対して*レイアウト最適化*、*演算子スケジューリング*、*メモリ計画*をさらに行い、性能を最大化する。Mirage がこれらの μGraph 最適化を検証後まで遅らせる理由は二つある。第 1 に、これらの最適化は生成された μGraph の正当性に影響*しない*。μGraph の生成時にこれらを省くと、同じグラフトポロジをもちテンソルレイアウト、演算子順序、メモリ割り当て計画の選択だけが異なる μGraph は生成器から同一とみなされるため、Mirage が検討すべき探索空間を縮小できる。第 2 に、検証後にこれらの最適化を適用すると、その最適化自体の探索空間も縮小できる。μGraph オプティマイザは入力と機能的に等価な μGraph だけを最適化すればよいからである。

**テンソルレイアウト。** μGraph オプティマイザは、カーネル、ブロック、スレッドの各レベルにあるすべての中間テンソルについて可能なデータレイアウトを探索し、性能を最大化する最良の組み合わせを選ぶ。レイアウト選択を制約付き最適化問題として定式化し、整数線形計画（ILP）アルゴリズムで最適に解く。具体的には、各テンソル $t$ と $t$ の各候補レイアウト $l$ について、テンソル $t$ がレイアウト $l$ を使うかを示すブール変数 $B_{t,l}$ を導入する。カーネル、ブロック、スレッドの各レベルの演算子は、テンソルレイアウトへさまざまな制約を課す場合がある。たとえば行列乗算に cuBLAS ライブラリ [Cub16] のカーネルを使うには、二つの入力テンソルの最内次元が末尾 2 次元のいずれかでなければならない。これらの制約は $B_{t,l}$ に関する一連の線形制約へ変換される。テンソルレイアウトが異なれば、性能も異なり得る。たとえば、デバイスメモリから共有メモリへの一括コピーをサポートする入力テンソルレイアウトもあれば、サポートしないものもある。Mirage はコスト関数を導入し、異なるレイアウト選択における各演算子の性能をモデル化する。Mirage は既製の ILP ソルバ（すなわち Z3 [Dem08]）を使い、すべてのレイアウト制約を満たしながらコストを最小化する最適なレイアウト戦略を求める。

**演算子スケジューリング。** μGraph には演算子を実行するトポロジカル順序が複数あり、順序によって性能が異なり得る。所与の入力 μGraph に対し、μGraph オプティマイザは各スレッドブロック内のスレッドレベル同期（すなわち CUDA の `__syncthreads()`）を最小化することで、効率的な演算子スケジューリング戦略を特定する。このため Mirage は各ノードへ*深さ*を付与する。深さは、任意の入力演算子からそのノードまでの最長経路長である。Mirage は動的計画法アルゴリズムで各ノードの深さを計算し、深さの昇順ですべての演算子をスケジュールする。Mirage は深さの異なる演算子間にだけ同期点を挿入すればよいため、この手法は生成 CUDA カーネルで必要なスレッドレベル同期の回数を最小化する。

**メモリ計画。** 検証後に行う第 3 の最適化はメモリ計画であり、カーネル、ブロック、スレッドの各レベルにあるすべての中間テンソルのメモリオフセットを決定する。Mirage はメモリ計画を*動的記憶域割り当て*問題として定式化し、考えられる割り当て計画をすべて網羅的に列挙して最適な戦略を発見する。

## 7 実装

![表 4。評価に用いた DNN ベンチマーク。](../../papers/mirage/table-04.png)

**表 4。** 評価に用いた DNN ベンチマーク。

Mirage は C++、CUDA、Python による 3 万行のコードで実装されている。カーネル演算子は cuDNN および cuBLAS ライブラリ [Che14, Cub16] で、ブロック演算子とスレッド演算子は cuTLASS [Ker22] および CUDA PTX で実装されている。Mirage は入力テンソルプログラムごとに、候補となる μGraph を自動生成し検証する。検証済みの各 μGraph について、そのすべてのカスタムカーネルに対する CUDA ソースコードを生成し、CUDA コンパイラでバイナリへコンパイルする。この手法は一般のテンソルプログラムに対する実行時（JIT）コンパイルとデプロイを可能にし、生成カーネルは数行のコード変更だけで PyTorch プログラムへ直接統合できる。Mirage の SMT および ILP ソルバは Z3 4.12.6 [Dem08] で実装されている。

本実装は[表 1](#table-01)に挙げた演算子をサポートする。Mirage は、畳み込みや行列乗算の派生形などの新しい演算子を、カーネル、ブロック、スレッドの各レベルまたはその一部へ追加できる。新しい線形演算子をサポートするため、Mirage には（1）μGraph オプティマイザが CUDA カーネル生成に使う、カーネル、ブロック、スレッドの各レベルまたはその一部における演算子の浮動小数点実装、（2）剰余算術上の演算子実装（[第 5 節](#section-5)を参照）、（3）その演算子に対する抽象式公理 $A_{\text{eq}}$ と $A_{\text{sub}}$ の拡張（[第 4.3 節](#section-4-3)を参照）が必要である。

定理 2 と定理 3 を利用するには、十分に大きな素数 $p$ と $q$ でランダムテストを行い、複数回反復する必要がある。現在の実装は、積が 16 ビット整数に収まる $p$ と $q$ の最大値（すなわち $p=227,q=113$）を用い、GPU 上でランダムテストを行う。中間結果を共有メモリへ保持するなど、Mirage の GPU 最適化を活用して探索手続きを高速化する。また、反復せずにランダムテストを 1 回だけ行い、出力テンソルの全要素を比較する。この等価性検証手続きは偽陰性を生じさせない。理論上は偽陽性が生じ得るものの、実際には観測されていない。以上の理由から、この手続きは探索処理には十分であると考え、最適化処理の最後に、最良の μGraph だけを対象として理論的保証を与える最終検証段階を追加する予定である。

**非 Lax プログラムの等価性検証。** Mirage は任意のテンソルプログラムに対して μGraph を生成できるが、確率的等価性検証器は Lax プログラムに限定され、ReLU [Nai10] など一部の DNN 演算子をサポートしない。代替として、任意のテンソルプログラム向けにソルバベースの検証器を開発した。この検証器は、ユーザが与える個々の演算子の数学的性質（線形性、結合則、可換則、分配則など）を一階述語論理で定義したものに依拠し、自動定理証明器でその性質を利用して等価性を検証する。確率的等価性検証器に比べ、ソルバベース検証器はより一般的なプログラムをサポートする一方、新しい演算子ごとに性質を指定する追加の手作業を要する。ソルバベース検証器の詳細な議論は本稿の範囲外である。

### 8.1 実験設定

<span id="figure-07"></span>

![図 7。A100 および H100 GPU 上の 6 ベンチマークで Mirage と既存システムを比較。全システムの性能を Mirage で正規化している（高いほどよい）。Mirage の棒の上の数値は、最良のベースラインに対する高速化率を示す。](../../papers/mirage/figure-07.png)

**図 7。** A100 および H100 GPU 上の 6 ベンチマークで Mirage と既存システムを比較。全システムの性能を Mirage で正規化している（高いほどよい）。Mirage の棒の上の数値は、最良のベースラインに対する高速化率を示す。

Mirage は Lax プログラム向けのスーパーオプティマイザであるため、既存 DNN で一般的に使われ、それぞれが Lax プログラムである多様な DNN ベンチマークに評価を絞る。これらのベンチマークは、Mirage と既存システムの性能を最も細粒度で比較できる。[表 4](#table-04)に評価対象の 6 ベンチマークを示す。GQA、RMSNorm、GatedMLP は大規模言語モデル（LLM）の主要な構成要素である。QKNorm はモデルの収束性を高めるため、attention の前に query-key 正規化を導入する [Cha24]。LoRA は、異なるタスク向けに DNN をファインチューニングするための low-rank adaptation を可能にする。GQA には 8K、QKNorm には 4K のコンテキスト長を用いる。これはそれぞれ LLaMA-3-70B [Mod24] と Chameleon-7B [Cha24] がサポートする最大値に対応する。加えて、Mirage が生成したカーネルによる、Chameleon [Cha24]、nGPT [Los24]、LLaMA-3 [Mod24]、LoRA [Hu21] を含む完全な DNN のエンドツーエンド性能の改善も評価する。

実験は、それぞれ 40GB のメモリを備えた NVIDIA A100 および H100 GPU で行った。LLaMA-2-70B で使う GQA を除く全ベンチマークは単一 GPU に収まる。GQA は一般にテンソルモデル並列性 [Sho19] を用いて 4 GPU に並列化される。そのため GQA はこの並列化戦略の下で評価し、8 個の key-value head を 4 GPU へ均等に分割する。Mirage とすべてのベースラインの性能は入力テンソル形状だけに依存するため、各実験をランダム入力で 1,000 回繰り返し、平均実行時間を報告する。

ベンチマークの一つである LoRA では、二つの行列乗算を連結によって融合する一般的な最適化を表現するために連結が必要となる。Mirage でこの最適化をサポートするため、四つの入力を受け取り $f(W,X,Y,Z)=(W\|X)\times(Y\|Z)$ を計算する新しい線形演算子を導入する。ここで $\|$ はテンソル連結である。この演算子は $W\times Y+X\times Z$ の計算と等価である。この演算子に対応する抽象式を $\mathrm{E}(f(W,X,Y,Z))=\mathsf{add}(\mathsf{sum}(k_{1},\mathsf{mul}(\mathrm{E}(W),\mathrm{E}(Y))),\mathsf{sum}(k_{2},\mathsf{mul}(\mathrm{E}(X),\mathrm{E}(Z))))$ と定義する。ここで $k_{1}$ と $k_{2}$ は $W$ と $X$ の最終次元である。

特に断らない限り、Mirage はカーネルグラフで最大 5 演算子、各ブロックグラフで最大 11 演算子を考慮する。

### 8.2 ベンチマーク結果

[図 7](#figure-07)は、NVIDIA A100 および H100 GPU 上の 6 種類の DNN ベンチマークについて、Mirage と各システムの性能を比較する。すべてのシステムが半精度浮動小数点数でこれらの DNN ベンチマークを実行する。TASO [Jia19b] と PET [Wan21] は、カーネルレベルの代数変換を自動生成する DNN スーパーオプティマイザである。最新の TASO 実装は PET の部分等価変換を特殊な置換として含むため、TASO/PET をまとめたベースラインを報告する。PyTorch [Pyt17] は、高度に最適化された cuDNN および cuBLAS ライブラリ [Cub16, Che14] を用いて GPU 上で DNN 演算子を実行する。PyTorch ベースラインでは `torch.compile` を有効にし、FlashAttention カーネルを用いて性能を最大化する。TensorRT とその LLM 版 TensorRT-LLM は、attention など一般的なテンソル演算子向けに人手で設計され高度に最適化されたカーネル群を含む [Ten17a]。FlashAttention とその推論版 FlashDecoding は、効率的な attention 向けに手書きされたカーネルである [Dao23, Hon24d]。最後に、Triton は高性能カーネルを生成するスケジュールベース・オプティマイザであり、本番システムで採用され、ほかのスケジュールベース手法を上回っている [Til19]。すべてのベースラインは CUDA Graphs を使い、カーネル起動オーバーヘッドを最小化する。

Mirage は代数変換、スケジュール変換、新しいカスタムカーネルの生成を組み合わせ、これらのベンチマークで最良の既存手法を最大 $3.3\times$ 上回る。[第 3 節](#section-3)では RMSNorm 向けに発見された最良の μGraph を示した。続いて、残るベンチマークのケーススタディを示す。

<span id="figure-08"></span>

![図 8。QKNorm と attention について、既存オプティマイザと Mirage が用いる μGraph を比較。](../../papers/mirage/figure-08.png)

**図 8。** QKNorm と attention について、既存オプティマイザと Mirage が用いる μGraph を比較。

**GQA。** Group-query attention は LLM の中核であり、既存フレームワークで入念に最適化されている。たとえば FlashAttention と FlashDecoding は専門家が設計した attention カーネルであり、既存の LLM 推論システムに採用されている [Dao23]。Mirage はこれらの専門家設計カーネルに加え、それらを最大 $2.2\times$ 上回る別の μGraph も発見する。この高速化は、既存の手書きカーネルに二つの最適化を追加することで得られる。第 1 に、現行手法は固定されたヒューリスティクスで GQA のグリッド次元を決めており、状況によっては準最適となる。たとえば TensorRT-LLM は、バッチサイズがそれぞれ 1 と 8 のとき、グリッド次元（8, 2, 1）と（8, 2, 8）で GQA カーネルを起動する。しかし、どちらの構成も A100（108 SM）と H100（132 SM）GPU の全 SM を活用できない。これに対し Mirage は、各 μGraph に最適なグリッド次元を自動探索し、SM を完全に活用する。追加のアブレーション調査では、Mirage が発見した最良の μGraph に TensorRT-LLM と同じグリッド次元を用いると、性能が 18% 低下することが示される。

第 2 に、既存手法は固定されたテンソル次元を用い、スレッドブロック間で GQA を並列化する。たとえば FlashAttention [Dao23] は attention を*サンプル*、*head*、*query sequence* の各次元で並列化する一方、FlashDecoding と TensorRT-LLM は*サンプル*、*head*、*key-value sequence* の各次元を利用する。どちらの戦略も、多数の head をもつ従来の multi-head attention には効率的だが、attention head が少ない GQA には準最適である。これに対し Mirage は、サンプル、KV head、query sequence、key-value sequence の各次元から選択し、最も効率的な並列化戦略を自動決定する。さらに Mirage は、異なる attention の状況ごとに調整した異なる μGraph を生成し、既存システムのヒューリスティクスと比べてデバイスメモリアクセスを最大 $7\times$ 削減する。

Mirage の μGraph を既存システムへ実装することは可能だが、状況ごとに異なるカーネルをサポートするには多大なエンジニアリング作業を要する。これに対し、Mirage はそれらを自動生成し、正当性を検証する。

**QKNorm。** モデルの発散を抑えるため、近年の複数の DNN は Transformer アーキテクチャへ query-key 正規化（QKNorm）を導入している [Cha24]。[図 8a](#figure-08)に示すように、QKNorm は attention の前に query ベクトルと key ベクトルへレイヤ正規化を適用する。これらの追加正規化層は既存の attention 実装（FlashAttention や TensorRT-LLM など）ではまだサポートされておらず、正規化と attention に別々のカーネルを起動する必要がある。

[図 8b](#figure-08)に示すように、Mirage は QKNorm と attention の計算を一つのカスタムカーネルへ統合する μGraph を自動発見する。この μGraph は attention の計算を再編成して二つのレイヤ正規化との融合を可能にし、中間結果を GPU デバイスメモリへ書き込まず、カーネル実行時間を最大 $1.4\times$ 短縮する。

<span id="figure-09"></span>

![図 9。LoRA について、既存オプティマイザと Mirage が用いるテンソルプログラムを比較：$O=W\times X+B\times A\times X$。行列 $A$ と $B$ はどちらも low-rank である。](../../papers/mirage/figure-09.png)

**図 9。** LoRA について、既存オプティマイザと Mirage が用いるテンソルプログラムを比較：$O=W\times X+B\times A\times X$。行列 $A$ と $B$ はどちらも low-rank である。

**LoRA。** Low-rank adaptation（LoRA）は、事前学習済み DNN の線形演算子へ一対の low-rank adapter を導入し、下流タスクでの性能を向上させる。既存のテンソルプログラム・オプティマイザは、元の線形演算子と LoRA が導入する二つの追加線形演算子に別々のカーネルを起動する（[図 9a](#figure-09)）。これらの LoRA 演算子は計算量が少ないため、高いカーネル起動オーバーヘッドが生じる。[図 9b](#figure-09)は、Mirage が LoRA 向けに発見した最良の μGraph を示し、三つの `Matmul` と後続の `Add` を単一カーネルへ融合する。Mirage は次の代数変換を利用し、計算を二つのブロックレベル `Matmul` へ再編成する：$W\times X+B\times A\times X=(W\|B)\times\big(X\|(A\times X)\big)$。[図 9b](#figure-09)の `Concat` は計算を伴わず、GPU 共有メモリ内のテンソルオフセットを更新することで実行される。この μGraph は LoRA の実行コストを 1.1-$2.4\times$ 削減する。

<span id="figure-10"></span>

![図 10。GatedMLP について、既存オプティマイザと Mirage が用いる μGraph を比較。](../../papers/mirage/figure-10.png)

**図 10。** GatedMLP について、既存オプティマイザと Mirage が用いる μGraph を比較。

**GatedMLP。** Gated multi-layer perceptron は、非線形表現を捉えるため DNN で一般的に使われる。Falcon-7B [Alm23b] で導入された GatedMLP 構成を用い、そのカーネルグラフを[図 10a](#figure-10)に示す。既存のテンソルプログラム・オプティマイザは一般に、入力テンソル $X$ を一度だけ読み込めばよいことから、GPU デバイスメモリアクセスを減らすため二つの `Matmul` を単一カーネルへ融合する。しかし `SiLU` 活性化と要素単位乗算は `Matmul` と融合されないため、この手法でも複数カーネルを起動し、中間結果、具体的には二つの `Matmul` の出力をデバイスメモリへ格納する必要がある。

これに対し、Mirage が発見した最良の μGraph（[図 10b](#figure-10)）は、同じブロックグラフ内で二つの `Matmul` を並列に実行し、残りの計算（すなわち `SiLU` と `Mul`）を同じブロックグラフ内の後処理として融合する。この手法は、A100 GPU で $1.5\times$、H100 GPU で 2.7-$3.3\times$ の高速化をもたらす。

**nTrans。** モデル学習を高速化するため、nGPT は Transformer 内のすべての中間結果を正規化する normalized Transformer を導入する [Los24]。形式的には、計算を $y=\texttt{Norm}(x+\alpha(\texttt{Norm}(h-x)))$ と定義する。ここで `Norm` は正規化層、$x$、$h$、$\alpha$ は入力テンソルである。nTrans は正規化と要素単位の加算および乗算を交互に行うため、既存システムは三つの別々のカーネルを起動する。Mirage は計算を単一カーネルへ融合し、すべての中間結果を GPU 共有メモリへ格納する μGraph を自動発見する。Mirage はほかのベースラインを上回るが、TensorRT よりは遅い。この性能差は、Mirage がグラフ定義カーネル内の各テンソルについて、グローバルメモリから共有メモリへデータを読み込み、書き戻すために生じる。この設計はメモリ効率を高め、非同期パイプラインを可能にする。しかし計算の軽いカーネルでは、このメモリ転送のオーバーヘッドがカーネル実行時間を支配し得る。このオーバーヘッドを緩和するため、データ読み込み時に共有メモリを迂回し、不要なデータ移動を避けられるよう Mirage を拡張する予定である。

### 8.3 エンドツーエンド結果

マイクロベンチマーク性能に加え、Mirage が生成したカーネルが一般的な DNN のエンドツーエンド・レイテンシへ与える影響も評価する。Mirage は実行時コンパイルとデプロイをサポートし、生成カーネルを PyTorch プログラムへ直接統合できる。4 種類の DNN モデルについて、ネイティブの手書き CUDA カーネルを使う PyTorch と、Mirage が生成したカーネルを使う PyTorch を比較する。[図 11](#figure-11)に結果を示す。Mirage は高度に最適化されたカーネルを自動生成し、これらのモデルのエンドツーエンド・レイテンシを 0.9-$1.9\times$ 短縮する。この改善に必要なのは、PyTorch プログラムへの数行のコード変更だけである。

### 8.4 探索時間

![表 5。μGraph 生成を高速化する Mirage の技法に関するアブレーション調査。RMSNorm の探索時間に対するマルチスレッド化と抽象式の影響を評価する。](../../papers/mirage/table-05.png)

**表 5。** μGraph 生成を高速化する Mirage の技法に関するアブレーション調査。RMSNorm の探索時間に対するマルチスレッド化と抽象式の影響を評価する。

本評価では、Mirage が Lax プログラムを最適化するのに最大 4 時間かかる。この最適化は対象ハードウェアへデプロイする前の一度限りのコストである。本小節では Mirage の探索手続きについて詳細な結果とアブレーション調査を示し、低い探索時間を維持しながら大規模な μGraph の探索を可能にする技法に焦点を当てる。具体的には、抽象式による枝刈り（[第 4.3 節](#section-4-3)）とマルチスレッド化という二つの技法の影響を評価する。[表 5](#table-05)は、ブロックグラフで許可する演算子の最大数を変化させたときの RMSNorm の探索時間を報告する。

マルチスレッド化は探索時間を大幅に短縮し、抽象式による枝刈りは Mirage のスケーラビリティに不可欠である。具体的には、枝刈り技法により Mirage は各ブロックグラフが最大 11 個の演算子をもつ μGraph を探索できる一方、抽象式による枝刈りを無効にすると、10 時間の探索枠内では最大 6 個の演算子をもつブロックグラフしか扱えない。[図 3](#figure-03)に示した RMSNorm の最適化 μGraph を発見するには、11 個の演算子をもつブロックグラフを探索する必要がある。

### 8.5 最適化のアブレーション調査

<span id="figure-12"></span>

**図 12。** Mirage で使う最適化に関するアブレーション調査。各最適化を個別に無効化したときの性能低下を評価する。評価はバッチサイズ $1$ の GQA を用い、A100 上で実施した。

## 9 関連研究

**人手設計カーネル。** TensorFlow XLA [Xla17, Aba16]、PyTorch [Pyt17]、TensorRT [Ten17a] など多くの既存フレームワークは、GPU の専門家が ML 演算子向けカーネルを手動設計することに依存している。近年では、一般的な DNN、特に基盤モデル [Bom22] 向けの GPU カーネルを手作業で最適化するため、多大なエンジニアリング作業が投じられている。たとえば attention 計算 [Wol22a] を高速化するため、FlashAttention [Dao23, Htm23a, Hon24d, Fas21] に基づく複数の専用カーネルが開発されている。A100 の tensor core [Mar18b] や H100 の thread block cluster [Htt23] など、現代 GPU は複雑さを増しており、人手設計カーネルは手動では発見しにくい巧妙な最適化を見逃す可能性がある。

**スーパーオプティマイゼーションに基づく手法。** スーパーオプティマイゼーションは、最適な命令列を発見するために導入された [Mas87, Sch13, Ban06]。近年の研究では、スーパーオプティマイゼーション技法がテンソルプログラムへ適用されている [Jia19b, Wan21, Zhe23f, Yan21d, Ung22, Jia19a, Hu24d, Jeo25]。しかし、いずれもカーネルレベルの代数変換だけを扱い、カーネル、ブロック、スレッドの全レベルにおける代数変換とスケジュール変換を一体として検討する必要がある、より高度な最適化は発見できない。本評価では Mirage が既存の DNN スーパーオプティマイザを大幅に上回り、マルチレベル共同最適化の重要性を示している。

**スケジュールベース手法。** 近年では、GPU カーネルの実行スケジュールを自動最適化する ML コンパイラが提案されている。TVM [Che18, Che18a]、Ansor [Zhe20]、Triton [Til19] などのシステムと、そのほかの手法 [Zhe20a, Hag23, Fen22] は、Halide が導入したアルゴリズムとスケジュールの分離という着想に基づく。これらは、ユーザ指定アルゴリズムを GPU 上で実行するための最適化スケジュールを探索する。しかし、スケジュールベース手法ではユーザが各カーネルのアルゴリズムを明示的に指定する必要があり、その性能は与えられたアルゴリズムの品質に制約される。

**マルチレベル・グラフ表現。** Welder [Shi23a] と ASPEN [Par23c] は、どちらも GPU 階層に従うという点で Mirage の μGraph と共通する、マルチレベル・タイルグラフを導入する。しかし従来研究がスケジュール変換に焦点を当てる一方、Mirage は代数変換と新しいカスタムカーネルの発見も検討し、スケジューリングを越えている。本稿で示した最適化の大半は、これらの従来手法の範囲外にある。

<span id="section-10"></span>

## 10 おわりに

本稿では、テンソルプログラム向けとして初のマルチレベル・スーパーオプティマイザ Mirage を提案した。Mirage は、GPU 実行階層のカーネル、スレッドブロック、スレッドの各レベルでテンソルプログラムを記述する階層グラフ表現を導入し、抽象化に基づく新しい枝刈り手法を用いて、一定の最適性保証を与えながら、Mirage が検討すべき探索空間を大幅に縮小する。広く使われ入念に最適化された DNN においてさえ、Mirage は既存のテンソルプログラム・オプティマイザを最大 $3.3\times$ 上回る。
