## 概要

TensorFlow Eager は、ハードウェアアクセラレーションを用いる機械学習のための、マルチステージかつ Python 埋め込み型のドメイン固有言語であり、対話的な研究にも本番環境にも適している。TensorFlow Eager が拡張する TensorFlow では、計算をデータフローグラフとして表現する必要がある。この表現はコンパイラ最適化を可能にし、デプロイを簡単にする一方で、迅速なプロトタイピングと実行時の動的性質を妨げる。TensorFlow Eager はグラフがもたらす利点を損なわずに、こうした使い勝手の代償を取り除く。すなわち、演算を即時実行する TensorFlow の命令型フロントエンドと、TensorFlow 演算からなる Python 関数を実行可能なデータフローグラフへ変換する JIT トレーサを提供する。このように TensorFlow Eager は、一つのパッケージ内で命令型実行とステージ化実行を容易に行き来できるマルチステージプログラミングモデルを提供する。

## 1 はじめに

現在の機械学習ライブラリの多くは似た構造を持つ。基本演算の集合と、それらの合成を自動微分する関数を提供している（例えば [Ber10, Tok15, Mac15, Che15b, Aba16, Pas17, Glu17, Neu17, Inn18, Fro18] を参照）。実際、これらのソフトウェアパッケージはライブラリというよりドメイン固有言語（DSL）に近い [Inn18a]。自動微分ソフトウェアを用いて記述されたモデルは、しばしば*微分可能プログラム*と呼ばれる。

微分可能プログラミング用 DSL は通常、ホスト言語に埋め込まれ [Hud96]、プログラミング言語における意味で、おおまかに*命令型*または*宣言型*に分類できる。微分可能プログラミング用の命令型 DSL でプログラムを書くことは、Python のような命令型プログラミング言語でプログラムを書くことに似ている。基本演算の構築と実行は切り離せず、各演算は具体的な数値データを返す。命令型 DSL は自然なプログラミングパラダイムを提供するが、Chainer [Tok15] や PyTorch [Pas17] のように Python などのインタプリタ言語へ埋め込むと、性能がインタプリタによって律速され、モデルのシリアライズも難しくなる。この問題に対処するため、宣言型 DSL はモデルの指定と実行を分離する。こうした「define-before-run」ライブラリでは、モデルをデータフローグラフとしてステージ化する必要がある。それにより、コンパイラ最適化と並列性の利用が可能になり、デプロイ、分散、コード生成も簡単になる（例えば [Ber10, Aba16] を参照）。しかし、宣言型 DSL ではホスト言語の任意の構文を使えないため、学習曲線が急であり、データ依存の構造を持つモデルの表現にも適さない。

理想的な DSL は、命令型実行の柔軟性と使いやすさに宣言型プログラミングの多くの利点を組み合わせ、どちらの代償も負わないものである。この動機から、私たちは TensorFlow Eager を提案する。これは微分可能プログラミングのための Python 埋め込み型 DSL であり、一つのパッケージ内で命令型計算とステージ化計算を行き来できる。TensorFlow Eager は*マルチステージプログラミング*モデルを提供し、プログラムを迅速に試作して、加速またはシリアライズしたい部分を選択的にステージ化できる。TensorFlow のオプトイン拡張として実装されており、プログラム開始時に TensorFlow のライブラリ関数を一つ呼び出すだけで有効にできる。

機械学習の実務家と研究者が最初から生産的に作業できるよう、TensorFlow Eager はデフォルトで命令型実行を行う。データフローグラフの利点を活かすため、TensorFlow Eager は Python デコレータを提供する。このデコレータはグラフ構築コンテキスト内で Python 関数をトレースし、基本演算をステージ化して、名前付きの入力と出力を持つデータフローグラフを構築し、実行可能な*グラフ関数*を返す。グラフ関数の呼び出しは、その生成元である Python 関数の呼び出しと構文上は同じだが、実行時には Python を経由しない。C++ のデータフローランタイムで実行されるか、コンパイルによって CPU、GPU、ASIC 向けの最適化コードが生成される。グラフ関数と命令型コードは字句環境を共有するため、命令型コードからグラフ関数を呼び出すこと、命令的に構築したデータを閉じ込めるグラフ関数を作ること、アンステージング注釈によってグラフ関数内へ命令型コードを埋め込むことが容易になる。

本論文の貢献は二つある。

- 私たちの実装は簡潔である。TensorFlow Eager は TensorFlow のマルチステージフロントエンドとみなせる。命令型とステージ化の TensorFlow Eager コードは、基本演算、カーネル、ユーザー向け API を一式共有する。この共有によって保守しやすい実装になるだけでなく、実行モードに依存しない一貫した API をユーザーへ提供し、TensorFlow のために開発された豊富なツール群を利用できる。
- 微分可能プログラミングのコミュニティで、命令型プログラミングと宣言型プログラミングを橋渡しする価値に初めて気づいたのは私たちではないが、この研究をマルチステージプログラミングの文脈で提示した最初期のグループに属する。この文脈づけは議論を明確にし、従来は別々だった二つのコミュニティを結びつける点で、本論文の貢献である。

本論文の残りは次のように構成される。[第 2 節](#section-2)では関連研究を概観する。[第 3 節](#section-3)では、使いやすさと研究者の生産性を重視する設計原則を示す。[第 4 節](#section-4)では、自動微分、状態、ハードウェアアクセラレーション、分散、ステージング、アンステージングを含むマルチステージプログラミングモデルを説明する。[第 5 節](#section-5)では実装を論じる。[第 6 節](#section-6)では、機械学習モデル上で TensorFlow Eager の性能を定量評価する。その結果、命令型 TensorFlow Eager は単一 GPU 上で TensorFlow と同じ速さで ResNet-50 を訓練でき、ステージ化 TensorFlow Eager は TPU 上で命令型 TensorFlow Eager よりはるかに高速に ResNet-50 を訓練でき、小さな演算を持つモデルでは最小限のコード変更だけでステージ化による大幅な高速化を得られることを示す。

## 2 関連研究

TensorFlow Eager では、ユーザーが計算を手動でステージ化する必要があり、コードのリファクタリングを伴うことがある（[第 4.1 節](#section-4-1)を参照）。理想的な微分可能プログラミングフレームワークは、プログラマの介入なしに計算を自動ステージ化する。一つの方法は、コンパイルされる手続き型言語へフレームワークを埋め込み、グラフ抽出と自動微分をコンパイラの書き換えとして実装することである。例えば DLVM、Swift for TensorFlow、Zygote はこの方法を採る [Wei17, Lat18, Inn19]。Python は柔軟であるため、そこに埋め込まれた DSL が同じ方法を使うのは難しい。AutoGraph [Mol19] など一部のプロジェクトは Python の抽象構文木を操作し、命令型コードをデータフローグラフ構築コードへ書き換えるが、この種の技術は本論文の範囲外である。

性能のために計算をグラフとしてステージ化する代わりに、融合カーネルを実装する方法もある。例えば NVIDIA は、一般的な再帰型ニューラルネットワーク演算に対して、非融合実装より大幅に高速な融合 CuDNN カーネルを提供している [Che14]。この方法は有用だが、プログラマによる多くの作業を要するため、規模を拡大しにくい。

TensorFlow Eager は、マルチステージプログラミングモデルを提供する最初の Python ライブラリではない。JAX [Fro18] は XLA [Xla17] を通じて異種デバイス向けコードを生成するトレーシング JIT コンパイラであり、同様のプログラミングパラダイムを提供する。MXNet と Gluon も命令型計算とステージ化計算を行き来できるが、その抽象度は私たちのものより高い [Che15b, Glu17]。PyTorch も私たちと同様のステージングトレーサを実装中である [Pyt18]。微分可能プログラミング以外では、Terra はコード生成を支援する Lua 埋め込み型 DSL であり、その提案論文はマルチステージプログラミングを本論文より形式的かつ詳細に扱っている [Dev13]。別の例として、OptiML はステージングとコード生成を支援する Scala 埋め込み型の機械学習 DSL だが、自動微分は支援しない [Suj11]。DSL 以外にも Python の Just-In-Time（JIT）コンパイルを提供するプロジェクトがいくつかあり、Numba [Lam15] と PyPy [Bol09] はその例である。

マルチステージプログラミングは、プログラミング言語分野で長く研究されてきた。[Tah04] は優れた参考文献であり、私たちは Scala の軽量モジュラーステージング [Rom10] という現代的な設計から着想を得た。マルチステージプログラミングは、コンパイラのステージング変換およびプログラミング言語の部分評価と関係し、それぞれ [Jor86] と [Jon93] が古典的な参考文献である。

## 3 設計原則

私たちの設計は二つの目標を満たそうとしている。TensorFlow Eager は Python プログラマがすぐに理解できるものであるべきであり、例えば IPython ノートブックで API を探索しモデルを試作するときに馴染みやすくなければならない。同時に、アイデアを大規模に検証し、異種デバイス上の推論用にモデルをデプロイするまでの滑らかな経路も提供すべきである。以下の三原則のうち、最初の二つは前者の目標に、三つ目は後者の目標に寄与する。

**命令型実行を優先する。** Python は命令型言語なので、TensorFlow Eager はデフォルトで命令的に動作する。ステージ化実行はオプトインであり、多くの場合は不要である（詳しくは[第 4.1 節](#section-4-1)と[第 6 節](#section-6)を参照）。

**Python へシームレスに埋め込む。** TensorFlow コードを書くことがメタプログラミングの作業であるのに対し、命令型実行ではホスト言語を余すところなく利用できる。プログラマは、ネイティブな制御フロー（Python の `if` 文や `while` ループなど）、再帰、任意のデータ構造、さらには `pdb` ブレークポイントまで、馴染みのある言語構文を備えた Python らしいコードを書く。私たちはトレースによって自動微分を実装するため（[第 4.2 節](#section-4-2)）、プログラマはこれらすべての構文を通じて微分できる。ホスト言語との統合は単なる糖衣構文ではなく、セグメンタル再帰型ニューラルネットワークや再帰型ニューラルネットワークのようなデータ依存モデルの実装を大幅に簡単にする [Kon15, Soc11]。

**命令型コードをデータフローグラフとしてステージ化する。** データフローグラフの利点を活かすため、TensorFlow Eager は Python 関数をトレースし、その演算をグラフ関数としてステージ化する仕組みを提供する。ステージングのワークフローは[第 4.1 節](#section-4-1)で詳述し、仕組みは[第 4.6 節](#section-4-6)で説明する。TensorFlow グラフには独自の設計原則があり、[Aba16] で示されている。

## 4 実行モデル

本節では TensorFlow Eager の実行モデルを支える要素を示す。[第 4.1 節](#section-4-1)では命令型実行とステージ化実行、および両者を混在させるワークフローを説明する。[第 4.2 節](#section-4-2)ではトレースに基づく自動微分の実装を説明する。[第 4.3 節](#section-4-3)では可変状態の表現とシリアライズの支援方法を定める。[第 4.4 節](#section-4-4)では TensorFlow Eager が異種デバイスにまたがる実行をどのように支援するか詳述する。[第 4.5 節](#section-4-5)では分散実行の仕組みを示す。[第 4.6 節](#section-4-6)ではトレーシング JIT を詳しく論じる。[第 4.7 節](#section-4-7)ではステージ化計算を抜け出す仕組みを論じる。

以下では次の用語を使う。*テンソル*とは型付き多次元配列、*演算*とはテンソルを入力としてテンソルを出力する、状態を持つこともある基本関数、*カーネル*とは演算をデバイスごとに実装したもの、*モデル*とは基本演算を合成したものである。

<span id="section-4-1"></span>

### 4.1 マルチステージプログラミング

TensorFlow Eager は、演算を命令的に実行する方法と、静的データフローグラフの一部として実行する方法の二つを提供する。どちらの実行モデルも同じ演算とカーネルの集合を利用できるが、カーネルのディスパッチ方法が異なる。

**命令型実行。** TensorFlow Eager はデフォルトで演算を即時実行する。`tf.matmul` などのライブラリ関数は演算を構築し、直ちにそのカーネルを実行する。この体制では、TensorFlow Eager はハードウェアアクセラレーションを用いる数値計算と機械学習のための NumPy 風ライブラリに似ている。テンソルに対して `.numpy()` を呼び出すと、そのデータを格納した NumPy 配列が得られ、テンソルは NumPy 配列を期待する matplotlib などの外部ライブラリにも渡せる（NumPy については [Oli15] を参照）。例えば、

```python
import tensorflow as tf
tf.enable_eager_execution()

def select(vector):
  A = tf.constant([[1.0, 0.0]])
  return tf.matmul(A, vector)

x = tf.constant([[2.0], [-2.0]])
print(select(x))
```

は次を出力する。

```text
tf.Tensor(
[[ 2.]], shape=(1, 1), dtype=float32).
```

**ステージ化実行。** 命令型実行はプロトタイピングを簡単にするが、Python インタプリタとの間を行き来するオーバーヘッドが性能を制限する。計算を実行前にデータフローグラフとして表現すれば、このボトルネックを取り除けるだけでなく、演算間並列性や定数畳み込み、バッファ再利用などの最適化も利用できる。そのため TensorFlow Eager は、計算をデータフローグラフとして*ステージ化*する仕組みを提供する。具体的には、Python 関数の実行をトレースし、すべての TensorFlow 演算とその間を流れるテンソルをデータフローグラフに記録するデコレータ `function` を提供する。`function` は、Python 関数に対して最適化された多相関数を生成するオプトイン JIT コンパイラとみなせる。実行時の素直な束縛時解析を通じて、データフローグラフに裏づけられた具体的な関数を作る。`function` が生成するトレースは TensorFlow 演算だけを記録し、任意の Python コードを記録するわけではないため、コンパイラという類推は完全ではないが、おおよそのメンタルモデルとしては役立つ。このトレース機構には、基盤となるデータフローグラフ形式が、トレース対象 Python コードの動的性質をすべて支援する必要がないという利点がある。トレースに含まれる演算の集合が Python の状態に依存しない限り、正しいトレースを生成できる。

`function` が返した callable を呼び出すと、対応する Python 関数ではなくデータフローグラフが実行される。実際、グラフ関数自体も、テンソルを入力とし関数名を属性とする演算によって実行され、これらの演算はユーザーのために自動で構築、実行される。例えば、前段で定義した `select` 関数を `@function` で装飾すると、`select(x)` は演算を一つ実行し、その演算が適切なグラフ関数を実行する。C++ で記述されたデータフローグラフのランタイムは、デバイス間でサブグラフを自動分割し、可能な場合は演算を並列化する。ランタイムに関心のある読者は [Aba16] を参照されたい。

`function` デコレータは XLA [Xla17] によるコード生成を支援する。TensorFlow Eager は、Tensor Processing Unit（TPU）[Sat17] でコードを実行するために XLA を利用する（[第 4.4 節](#section-4-4)を参照）。性能とハードウェアアクセラレーションに加え、データフローグラフは分散（[第 4.5 節](#section-4-5)）とデプロイを簡単にする。`function` の仕組みは[第 4.6 節](#section-4-6)で説明する。

**マルチステージワークフロー。** 多くのユーザーにとって、命令型実行の性能は十分である。ResNet-50 [He16] のように十分大きなカーネルを持つモデルを訓練する場合、純粋な命令型 TensorFlow Eager はグラフ実行と同等の性能を得られる（[第 6 節](#section-6)を参照）。命令型実行の性能が期待に届かない場合、[Tah04] を基にした次のマルチステージワークフローを推奨する。

1. *実装。* 単一ステージの命令型プログラムを開発、デバッグ、テストする。
2. *分析。* ユーザーが使い慣れた任意のプロファイリングツールを使い、性能上重要な演算ブロックを特定して、それらをステージ化しやすい Python 関数または callable object として表現する。
3. *ステージング。* 前段で特定した関数を `@function` で装飾する。

分析段階について、念頭に置くべき重要な点は、`function` が任意の Python コード用のコンパイラでは*ない*ことである。これはグラフ構築コンテキスト内で Python 関数を実行し、演算とテンソルだけを記録する JIT トレーサである。グラフ構築コンテキストでは、演算は具体的な値ではなく計算される値の記号表現を返し、TensorFlow 以外の Python コードは通常どおり実行される。ステージ化に適した Python 関数は、グラフ構築コンテキストで呼び出したときに、目的の計算を包含するグラフを生成する関数である。したがって Python 関数が TensorFlow 以外のコードを実行する場合、Python 関数の実行と、トレースされたデータフローグラフの実行との間に意味上の差が生じうる。例えば、次の Python 関数は、

```python
def add_noise():
  eye = tf.eye(5)
  randn = np.random.randn(5, 5)
  return eye + randn
```

呼び出すたびに異なる出力を返すが、`function(add_noise)` が生成するデータフローグラフは呼び出すたびに同じ値を返す。これは NumPy が生成した特定のランダムなオフセットが定数としてグラフへ挿入されるためである。状態を*演算*として表現すれば（例えば `np.random.randn` の呼び出しを `tf.random_normal` に置き換えれば）、このトレースモデルでも意味を保てる。系として、Python 関数 `f` が Python の副作用を持つ場合（例えば、呼び出すたびにグローバルな Python カウンタを増やす場合）、複数回の関数実行は `function(f)` が返す callable の反復実行と意味的に等しいとは限らない。`function` が元の Python 関数を複数回トレースすることもあるため、Python 関数は複数回実行されても問題がないようにする必要がある（[第 4.6 節](#section-4-6)の多相性に関する議論を参照）。

`function` はソースコード解析ではなくトレースによってグラフを生成するため、Python の `for` と `while` ループを完全に展開し、大きなグラフを作る可能性がある。問題になる場合、プログラマはループを同等の TensorFlow 制御フロー構文へ置き換える必要がある。同様に、トレース時に選ばれた `if` 文の分岐は生成されたグラフへ焼き込まれる。テンソル値に依存する条件分岐は `tf.cond` で記述し、テンソル値に依存する `while` ループは `tf.while_loop` で書き直す必要がある。テンソル値へ複雑に依存する Python 関数（例えば、データ構造がテンソル値に依存する関数）は、正しくステージ化することが困難すぎる場合もある。その場合、関数をステージ化しやすいヘルパー関数とステージ化しにくいヘルパー関数へ分ける必要がある（他の選択肢については[第 4.7 節](#section-4-7)のステージ化計算から抜け出す方法を参照）。

ステージングは、性能と引き換えに命令型実行、したがって対話性と、Python 統合、したがって実行時の動的性質を手放す。いつこのトレードオフを受け入れ、ステージング注釈を慎重に使うかはプログラマが決める。抽象構文木を操作して Python の制御フローをデータフロー制御へ書き換える AutoGraph のようなツールを使えば、このトレードオフを小さくできる [Mol19]。

<span id="section-4-2"></span>

### 4.2 自動微分

私たちはトレースに基づくリバースモード自動微分 [Bay18] の一種を実装し、部分的にステージ化された計算をよりよく支援するためにいくつか変更を加えた。実装は Chainer [Tok15]、Autograd [Mac15]、PyTorch [Pas17] の実装と似ているが、私たちの API では、どの計算をトレースするかをより細かく制御できる。

勾配 API でユーザーが目にする中心的な概念は*テープ*である。テープがある値を*監視*していれば、その値を入力とする演算が記録される。テープが有効な間に計算された任意のスカラーを、監視中の任意の値について微分できる。テープは合成可能なデータ構造である。複数のテープを同時に有効にでき、あるテープが勾配を計算する間に別のテープで記録すれば、高階勾配を計算できる。[リスト 1](#listing-01)は、テープを入れ子にして二階導関数を計算する例である。

<span id="listing-01"></span>

```python
x = tf.constant(3.0)
with tf.GradientTape() as t1:
  with tf.GradientTape() as t2:
    t1.watch(x)
    t2.watch(x)
    y = x * x
  dy_dx = t2.gradient(y, x)  # 6.0
d2y_dx2 = t1.gradient(dy_dx, x)  # 2.0
```

**リスト 1。** テープを入れ子にして高階導関数を計算できる。

高レベルの Autograd 風勾配関数だけでなくテープを直接公開することで、自動微分のために計算のどの部分をトレースするかをユーザーが制御でき、トレース処理で生じる実行時オーバーヘッドを抑えられる。

テープはコードのステージ化を担うロジックと密接に統合されている。テープが有効で、かつグラフ関数の入力の一つを監視している状態で、そのグラフ関数を初めて呼び出すと、名前付き出力に加えて逆向きの処理に必要な中間値をすべて返す「forward」版の関数を構築する。そのため、特定の関数をステージ化するかアンステージ化するかによって、逆伝播に必要な計算量やメモリ量が有意に変わることはなく、性能を予測しやすくなる。さらに、順伝播で計算をステージ化した場合は、対応する逆伝播も必ずステージ化される。

勾配計算自体も基本演算を実行する関数として表されるので、ステージ化してもよいし、しなくてもよい。

<span id="section-4-3"></span>

### 4.3 状態

TensorFlow と同様に、TensorFlow Eager はプログラムの状態を*変数*に保持する。復元演算から変数へ値を代入して値を復元し、変数値を保存演算へ送って定期的にディスクへ保存する。変数はモデルの実装に役立つ。変数値にアクセスすると、[リスト 2](#listing-02)に示すように、有効なすべてのテープがその変数を自動で監視するためである。

<span id="listing-02"></span>

```python
x = tf.Variable(3.0)
with tf.GradientTape() as t1:
  with tf.GradientTape() as t2:
    y = x * x
  dy_dx = t2.gradient(y, x)  # 6.0
d2y_dx2 = t1.gradient(dy_dx, x)  # 2.0
```

**リスト 2。** 勾配テープは変数を自動で監視する。このコードを[リスト 1](#listing-01)と比較されたい。

TensorFlow Eager では、変数は Python オブジェクトに対応する。各変数オブジェクトは固有の保存領域を持ち、Python がオブジェクトを削除するとその領域も削除される。トレースされた計算でも同じであり、ステージ化された*読み出し*、*書き込み*、*保存*、*復元*演算が変数とやり取りする場合がある。ステージ化計算は一意な識別子で変数を参照するが、参照先の Python 変数オブジェクトが存在しなければ、その識別子は使えない。この対応関係により、TensorFlow Eager の状態はプログラマの予想どおり、他の Python 状態と同じように保存され、Python 識別子からアクセスできる。

純粋なステージ化計算から Python オブジェクトへ状態を保持する方式へ移る際の課題の一つは、同じプログラムの複数回の実行間で状態を対応づけることである。TensorFlow はプログラム内の各変数に一意な名前を使うため、ユーザーが一貫した順序で変数を作る必要がある。例えば同じモデルを二つ作る場合、二つ目のモデルの復元には特別な配慮が必要になる。TensorFlow Eager はグラフに基づくマッチングシステムを使い、オブジェクト間に名前付きの辺を持つ有向グラフをプログラム状態とともにシリアライズする。復元時には貪欲マッチングにより、シリアライズされた Python 状態と復元対象オブジェクトの対応を決める。このマッチングは局所的であり、保存、復元するオブジェクトだけに依存し、プログラムの他の部分には依存しない。[リスト 3](#listing-03)と[図 1](#figure-01)に短い例を示す。

<span id="listing-03"></span>

```python
class Net(tf.keras.Model):
  def __init__(self):
    super(Net, self).__init__()
    self.v = tf.Variable(1.)
    self.out = tf.layers.Dense(1)

  def call(self, x):
    return self.out(
      tf.nn.softplus(x * self.v))
```

**リスト 3。** 状態のマッチングに使われる、名前付き有向辺（属性名に由来）を持つグラフを暗黙に構築するモデル構築コード。

<span id="figure-01"></span>

![名前付き有向辺を持ち、塗りつぶされていないノードに状態を保持する依存グラフ](../../papers/tensorflow-eager/figure-01.png)

**図 1。** [リスト 3](#listing-03)の依存グラフを可視化したもの。塗りつぶされたノードは中間ノードで、塗りつぶされていないノードは状態を含む。

変数は最も一般的な状態だが、他の状態も同様に Python オブジェクトへスコープされ、名前付き辺を持つ有向グラフの一部としてマッチングされる。例えば、入力データのイテレータではデータセット内の位置をシリアライズでき、可変ハッシュテーブルもシリアライズできる。トレースされたコードの外側では、NumPy 配列など各種 Python 状態もグラフベースの状態マッチングを利用できる。

TensorFlow と同様に、ステージングによって、Python インタプリタなしで使えるようプログラムをシリアライズできる。典型的な開発ワークフローでは、TensorFlow Eager プログラムの記述、調整中はグラフベースの状態マッチングを使い、その後トレースをシリアライズして、TensorFlow の C++ API でトレースを実行する本番環境で利用する。

<span id="section-4-4"></span>

### 4.4 デバイス

TensorFlow Eager では CPU、GPU、TPU など多様なデバイスを容易に利用できる。プログラムの起動時に、ランタイムはマシンで利用可能なデバイスを検出し、その上で演算を実行しデータを保存できるようにする。命令型計算とステージ化計算は同じ基盤の `Device` 抽象化を使うため、どちらもデバイス上で演算を実行し、データを保存できる。ユーザー向け API エンドポイント `list_devices` も公開されており、ランタイムが認識するすべてのデバイスを列挙する。

ユーザーに公開されるテンソルはすべて、特定のデバイスに保存されたデータへのハンドルである。ランタイムは異なる種類のデバイス間でデータをコピーする方法も把握し、その機能をテンソルインスタンス上の API エンドポイントとして公開する。

<span id="listing-04"></span>

```python
a = tf.constant(1.0)  # stored on CPU
b = a.gpu()  # stored on GPU
```

**リスト 4。** CPU と GPU の間でテンソルをコピーする。

演算の実行時、ランタイムはその演算を走らせる特定のデバイスを必要とする。TensorFlow Eager はコンテキストマネージャ `device` を公開し、演算を実行するデバイスをユーザーが制御できるようにする。この API の使用は必須ではなく、ランタイムはカーネルの有無に基づいてデバイスを選べる。演算の入力が実行先とは異なるデバイス上にある場合、ランタイムは入力を正しいデバイスへ透過的にコピーする。したがってユーザーがさまざまなデバイス間でテンソルを明示的にコピーする必要はない。

<span id="listing-05"></span>

```python
# stored on CPU
a = tf.constant(1.0)
b = tf.constant(2.0)

with tf.device("/gpu:0"):
  c = tf.add(a, b)

assert c.numpy() == 3.0
```

**リスト 5。** CPU 上の入力を用いて GPU 演算を実行する。

グラフ関数は基本演算を通じて実行されるため、`device` コンテキストマネージャを使って各種デバイス上でグラフ関数を実行することもできる。グラフ関数内の演算が別のデバイスへ明示的に配置されている場合は、外側のデバイスコンテキストよりその配置が優先される。

グラフ関数はアクセラレータ向けコンパイルの単位になりうる。私たちはこれを用いて TPU 上でコードを効率よく実行する。ステージ化計算を TPU へ配置すると、TensorFlow Eager は自動的に XLA を呼び出してグラフをコンパイルし、TPU 互換の実行可能形式を生成する。TensorFlow Eager では TPU 上でコードを命令的に実行することも可能だが、TPU 向けの演算コンパイルと生成コードのディスパッチには大きなオーバーヘッドがある。大きなグラフ関数にわたって償却すれば、このオーバーヘッドは無視できる（定量的な例は[第 6 節](#section-6)を参照）。このプログラミングモデルは、トレースと XLA で関数を JIT コンパイルする Python デコレータを提供する JAX [Fro18] に似ている。さらに、ステージ化計算を XLA でコンパイルすると、レイアウト最適化、並行性のための命令スケジューリング、演算融合など、より多くの最適化機会が得られる。テンソル再実体化などの技術を使えば、演算ごとの実行では不可能な場合でも、ステージ化モデルを TPU メモリへ収められる。

<span id="section-4-5"></span>

### 4.5 分散

現在のシステムは、一台の中央サーバーでメインの（通常は Python）プログラムを実行し、複数のワーカーサーバーをリモートホスト上で動かす分散実行を支援する。各ワーカーサーバーは、ローカルで利用可能なデバイス（CPU、GPU、TPU など）をメインプログラムが利用できるデバイスプールへ追加する。メインプログラムはワーカーサーバーを通じて、リモートデバイス上で個別の演算またはグラフ関数全体を実行できる。

リモートデバイスはアプリケーションレベルの名前で識別される。名前にはジョブ名、ジョブ内のタスク、そのタスクで利用できる具体的なデバイスが含まれる。例えば `/job:training/task:2/device:GPU:0` である。サーバーがクラスタの一部として起動すると、アプリケーションレベルの名前を、DNS 名または IP アドレスで識別される具体的なサーバーインスタンスへ対応づけるマッピングが与えられる。

リモートデバイス上で演算を実行するには、ローカルデバイスと同じ構文を使うが（[第 4.4 節](#section-4-4)を参照）、ローカルデバイス名の代わりにリモートデバイス名を用いる。リモートデバイス上で演算した結果のテンソルは、そのリモートデバイス上に留まる。その後、これらのテンソルへさらに演算を適用するか、中央サーバーへコピーできる（例えば `if` 文で値を使うため）。

リモートデバイス上で動く計算の中には、互いに直接通信、同期できるものもある。その場合、開発者は Python スレッドなどを用いて、これらの計算を並行に開始する必要がある。

<span id="section-4-6"></span>

### 4.6 計算のステージ化

TensorFlow Eager が支援するステージングは、軽量モジュラーステージング [Rom10] と似ており、後者は部分評価 [Jon93] の一形態である。[第 4.1 節](#section-4-1)で述べたように、私たちは `function` というユーザー向け API エンドポイントを公開している。これは Python 関数を受け取り、呼び出されると、ユーザー提供の Python 関数をグラフ構築コンテキストで実行して作られたデータフローグラフを実行するオブジェクトを返す。本節では `function` の実装を詳しく論じる。

**多相性。** すべての Python 関数は入力について多相的である。対照的に、グラフ関数は多相的ではなく、入力数が固定され、静的に型付けされている。Python 関数とグラフ関数の意味上の隔たりを埋めるため、JAX [Fro18] で説明されたものと似たトレースキャッシュを実装する。オブジェクト `F = function(f)` は、推論された入力シグネチャを具体的なグラフ関数へ対応づけるキャッシュを保持する。具体的には、`F` を呼び出すたびに入力を処理し、そのシグネチャを推論する。テンソルは抽象型（数値型と形状のタプル）として表し、テンソル以外の値はオブジェクト同一性で符号化する。この入力シグネチャは、要求されたデバイスなど周辺プログラム状態に関する少量のメタデータと組み合わされ、グラフ関数キャッシュのキーとなる。キャッシュミスが起きると与えられた入力で `f` をトレースし、キャッシュヒット時には以前作ったグラフ関数を再利用する。この意味で `function` はアドホック多相 [Str00]、すなわち関数オーバーロードを提供する。

入力型に応じた関数の特殊化は正しさのために必要なだけでなく、最適化されたグラフの生成も可能にする。この種の最適化はよく知られ、部分評価の主な動機の一つでもある [Jon93, Tah04, Rom10]。

JAX と同様に、`function` はテンソルではない引数の実行時値に対して特殊化し、その値で計算をパラメータ化できる（`function` は自動で特殊化するが、JAX では手動で行う）。例えば、Python 関数がブール引数 `is_training` を受け取り、dropout を適用するかどうかを決めることは多い。私たちの束縛時解析の実装により、グラフ関数はそのブール引数の値に応じて特殊化される（例は[リスト 6](#listing-06)を参照）。

<span id="listing-06"></span>

```python
@tf.contrib.eager.function
def lossy_matmul(W, x, training=True):
  outputs = tf.matmul(W, x)
  if training:
    outputs = tf.nn.dropout(outputs, 0.2)
  return outputs

W = tf.random_normal((3, 5))
x = tf.random_normal((5, 1))
# Executes a graph with dropout.
lossy_outputs = lossy_matmul(W, x,
  training=True)
# Executes a graph without dropout.
exact_outputs = lossy_matmul(W, x,
  training=False)
```

**リスト 6。** このコードは二つのグラフ関数を透過的に生成する。

ユーザーは入力シグネチャを指定して入力の多相性をなくすこともできる。この場合、シグネチャで指定された形状と数値型の情報だけを使い、グラフ関数を一つだけ生成することを保証する。これはシリアライズとエラーチェックに有用であり、任意のバッチサイズやシーケンス長を扱える単一の関数を作る際にも役立つ。

**字句クロージャ。** `function` は、テンソルや変数を字句的に閉じ込める Python 関数をトレースできる。閉じ込められたオブジェクトは「captured」入力として扱われ、プログラマの介入なしに呼び出し時にグラフ関数へ暗黙に渡される。変数は値ではなく参照によって捕捉されるため、グラフ関数は自由に変更できる。[リスト 7](#listing-07)に例を示す。

<span id="listing-07"></span>

```python
v = tf.Variable(0.0)

@tf.contrib.eager.function
def mutate():
  v.assign_add(1.0)
  return v.read_value()

mutate()
assert float(v.read_value()) == 1.0
v.assign_add(1.0)
assert float(v.read_value()) == 2.0
mutate()
assert float(v.read_value()) == 3.0
```

**リスト 7。** `function` は閉じ込められたテンソルと変数を透過的に捕捉し、入力として TensorFlow 関数へ転送する。

**合成。** グラフ関数の実行は演算として実装されるため、グラフ関数は自然に合成できる。ある関数のグラフに、別の関数を実行する関数呼び出し演算を含められる。例えば次のコードブロックを考える。

<span id="listing-08"></span>

```python
@tf.contrib.eager.function
def inner(a):
  return tf.nn.relu(a)

@tf.contrib.eager.function
def outer(a, b):
  return inner(tf.matmul(a, b))

outer(tf.eye(3), tf.diag([-1.0, 1.0, 2.0]))
```

**リスト 8。** グラフ関数は入れ子にできる。

`outer` を呼び出すと、`inner` 用と `outer` 用の二つのグラフ関数が生成され、後者には `inner` のグラフ関数の呼び出しが含まれる。[図 2](#figure-02)に対応するグラフを示す。

<span id="figure-02"></span>

![outer と inner に生成されたグラフ。outer から inner への call 演算を含む](../../papers/tensorflow-eager/figure-02.png)

**図 2。** `function` は合成できる。上図は[リスト 8](#listing-08)のグラフである。（a）`outer` に生成されたグラフ。`inner` のグラフ関数を実行する `call` 演算に注目されたい。（b）`inner` に生成されたグラフ。

**状態の作成。** 機械学習モデルを構築する際、最初の呼び出し時に変数を作成、初期化する Python 関数を書くことが多い。この慣用句を支援するため、`function` は装飾対象の関数 `f` にいくつかの要件を課す。TensorFlow 変数などの状態は `f` の初回呼び出し時にだけ作らなければならず、その方法は `f` の実装に任される。`f` の初回実行時に変数が作られた場合、`function` は `f` をもう一度トレースし、以後使われる振る舞いを記録する。二度目のトレースでも、それ以降のトレースでも変数を作ってはならない。

<span id="section-4-7"></span>

### 4.7 ステージ化計算から抜け出す

**グラフへの命令型コードの埋め込み。** [第 4.1 節](#section-4-1)で述べたように、計算をステージ化するには、対象コードを、トレース時にデータフローグラフを構築する Python 関数へリファクタリングする必要がある。この処理は難しすぎると感じられる場合がある。複雑な Python 制御フローを TensorFlow 制御フローへ置き換えたり、カスタム演算とカスタム C++ カーネルを実装したりする必要さえあるからである。実際、この事情は TensorFlow Eager を構築した動機の一つだった。

具体的に、ある Python 関数をステージ化したいとする。その関数はほぼ全体がステージ化しやすいが、テンソル上でいくつかの演算を行うデータ依存の再帰 Python 関数を一度だけ呼び出す。この場合、三つの選択肢がある。関数を三つに分け、再帰呼び出しの前後をステージ化して、再帰呼び出しはステージ化しないままにする。リファクタリングの負担が大きすぎるなら、関数のステージ化を諦める。あるいは関数全体をステージ化しつつ、再帰呼び出しを `py_func` で包む。`py_func` は Python 関数を属性として受け取り、ステージ化コードの中でもそれを命令的に実行する演算である。

`py_func` は勾配テープの下で Python 関数を実行するため（[第 4.2 節](#section-4-2)を参照）微分可能であり、CPU と GPU の両方のカーネルを持つ。命令型モードで Python 関数を `py_func` に包んでも、実質的には何も変わらない。しかし、ステージ化計算、すなわちデータフローグラフでは、`py_func` 演算によって命令型の Python らしいコードをデータフローグラフへ埋め込める。同じことを別の角度から言えば、`py_func` は C++ の代わりに Python を使ってカスタム演算を素早く実装する方法とみなせる。

`py_func` の利点は、大きな Python 関数を `@function` で装飾しやすくなることである。欠点としては、`py_func` が制御をシングルスレッドの Python インタプリタへ戻すことによる性能低下の可能性と、`py_func` を含むグラフは一般にシリアライズできないことが挙げられる。

**トレースから抜け出す。** トレースを一時停止して命令型コンテキストへ移る Python コンテキストマネージャ `tf.init_scope` を提供する。私たちはこのスコープを `function` の状態作成契約の実装に用いるが、大半のユーザーが使うことはない。

## 5 実装

[第 4 節](#section-4)で示した設計を実装し、コードはすべてオープンソースにしている [+1]。TensorFlow Eager は TensorFlow の拡張として構築されたため、実装は大きくない。ステージングは約 2000 行の Python、自動微分は 900 行の Python と 600 行の C に分かれ、命令型ランタイム、すなわち演算の構築と実行を担うコードは約 4000 行の C++ で実装されている。TensorFlow Eager はランタイムを公開する軽量な C API も提供し、複数の同僚が自身のプロジェクトからこの API を直接利用している。

[+1]: [TensorFlow ソースコード](https://github.com/tensorflow/tensorflow)。

TensorFlow Eager は TensorFlow の実装上の利点を受け継ぐ。具体的にはクロスプラットフォームであり、Linux、Mac OS X、Windows、Android、iOS の各 OS と、さまざまな x86、ARM、NVIDIA GPU アーキテクチャ上で動作する。ステージ化計算は、一万を超えるサブグラフを並列実行でき、可能な場合は複数の CPU コアまたは GPU ストリームにまたがってカーネルを並列実行するデータフロー実行系で処理する。モデル訓練用の高レベル Python API と推論用 C++ API も提供する（[Aba16] の実装節を参照）。さらに、TensorFlow が提供する 900 を超える基本演算を利用できる。

TensorFlow Eager と TensorFlow のステージ化実行の実装には、小さいが重要な違いがある。TensorFlow では、データフローグラフはグラフの作者が関心を持ちうる計算すべての和集合を定義する。実際に実行する計算は、プログラマがグラフ内のテンソル集合から具体的な値を取得するようランタイムへ要求した時点で定まる。これは Python で表現した内容と TensorFlow ランタイムが実行する内容の不一致につながる。より Python らしいプログラミングモデルを提供するため、TensorFlow Eager はステージ化計算をそれぞれグラフ関数、すなわち名前付きの入力と出力を持ち、対象となる*正確な*計算を表すグラフとして表現する。この方法でもグラフ最適化は可能である。例えば関数の出力から到達できない、状態を持たない演算は TensorFlow と同様に削除される。

グラフ関数は使いやすさ以外にも利点をもたらす。グラフ関数は演算を通じて実行されるため、関数合成がそのまま得られる。単一コーディネータによる分散訓練で、一つのサブグラフを $N$ 個のワーカーが実行する場合、グラフ関数はコーディネータのメモリ負荷を減らせる。コーディネータは、サブグラフを $N$ 個保持する代わりに、$N$ 個の関数呼び出し演算を含むグラフ関数を一つだけ保持すればよい。

## 6 評価

TensorFlow Eager は迅速なプロトタイピングを大幅に簡単にする。その際、開発の容易さと引き換えに実行速度を下げることがある。本節では、`function` を使って TensorFlow の速度を取り戻す方法を例 [+2] で示す。

[+2]: これらのモデルとその他の例のコードは [TensorFlow リポジトリ](https://github.com/tensorflow/tensorflow/tree/master/tensorflow/contrib/eager/python/examples)で公開されている。

**実験環境。** ベンチマークは Docker コンテナ内で実行し、12 コア、3.7 GHz の Intel(R) Xeon(R) W-2135 CPU、64 GB のメモリ、8 GB のメモリを持つ GTX 1080 GPU を備えたマシンを用いた。TPU ベンチマークは一般公開された Cloud TPU 上で実行した。各ベンチマークは 10 イテレーションとし、3 回の平均を報告した。ステージ化計算では、構築時間と最適化時間は一度きりのコストで、通常は複数回の実行に償却されるため、計測に含めなかった。

**ResNet-50。** [図 3](#figure-03)では ResNet-50 モデルの訓練性能を示し、TensorFlow Eager、前向きパスと勾配適用を `function` でステージ化した TensorFlow Eager、TensorFlow を比較する。上のチャートは 1 秒当たりの生のサンプル数を、下のチャートは TensorFlow Eager に対する、`function` を使った TensorFlow Eager と TensorFlow の改善率を示す。バッチサイズが小さいと、計算のステージ化によって大幅に高速化する。バッチサイズが増えると、Python に費やす時間に対するカーネル実行時間の比率が高くなるため、この高速化は消える。さらに、ResNet の訓練は演算間並列化から大きな恩恵を受けないので、ステージ化計算は実質的にアンステージ化計算と同じく直列である。この性能特性は、十分大きい他のモデルにも当てはまるはずである。すなわち、命令型実行の性能はステージ化実行と同程度になることが多い。これらのベンチマークを生成するコードはすべて同じ `Model` クラスに依存する。`function` を使うための変更は、二つの関数を装飾するだけである。

## 7 結論

私たちは TensorFlow Eager を提示した。これは TensorFlow を拡張し、従来は微分可能プログラミング用の宣言型 DSL だったものを、マルチステージで命令型優先の DSL に変える。TensorFlow Eager はデフォルトで命令的に動作するため、初心者にも研究者にも適している。計算をグラフ関数としてステージ化する選択肢により、命令型実行がもたらす対話性と Python 統合を、性能やシリアライズの容易さを含む静的グラフの利点と交換できる。

Alphabet 内では数十人が TensorFlow Eager を採用した。例えば、動的言語モデルや強化学習手法の実装に使う研究者がおり、TensorFlow Eager の社内ワークショップにも多くの参加者が集まった。複数のグループが機械学習フレームワークを再構成し、TensorFlow Eager をデフォルトの利用法にしようとしている（確率的機械学習と強化学習のライブラリを含む）。少なくとも一つの大規模研究グループは、TensorFlow Eager の支援専任エンジニアを置いている。社外では、一部の大学講義が TensorFlow Eager をカリキュラムへ取り入れた。2018 TensorFlow Developer Summit で配布したアンケートでは、回答者の 48 パーセントが「［TensorFlow Eager］は反復的な開発とデバッグのツールとして私にとって重要である」という文に同意した。

TensorFlow Eager は発展途上の技術である。研究にも教育にも適しているが、命令型で駆動する分散訓練については、すぐ使える解決策をまだ開発中である。また、マルチステージプログラミングは強力であり、大きな Python 関数を `function` で包むとしばしば「正しく動く」が、動的制御フローを持つ計算のステージ化には少なからぬプログラマの介入が必要になることがある。Autograph [Mol19] によってこの摩擦を減らしたいと考えている。

最後に、TensorFlow Eager は TensorFlow 自体の発展にも影響を与えた。次期 TensorFlow 2.0 は私たちの実装を使い、本論文で述べたものと同様の命令型優先、マルチステージプログラミングモデルを提供する。
